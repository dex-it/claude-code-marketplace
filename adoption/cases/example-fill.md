# Профиль команды клиента (ПРИМЕР - проверка анкеты)

> Выдуманный клиент для проверки, что анкета заполняет профиль без дыр. Не реальное обследование.

Клиент: Acme (пример)  Дата: 2026-07-15  Консультант: (пример)

## 1. Цель клиента
- Боль/цель: релизы долгие, много ручного regression-QA после каждого мерджа; привязана к шагам приёмки и тестирования
- Ожидаемый эффект + критерий успеха: сократить время от мерджа до релиза вдвое; критерий - время цикла релиза (сейчас ~2 недели)
- Ограничения, сроки, no-go зоны: пилот за квартал; не трогать legacy-модуль расчёта пеней (регуляторный, заморожен)

## 2. Постановка
- BRD: отрывочные
- Критерии приёмки: расплывчатые, пишутся после кода
- NFR: всплывают постфактум
- Валидация требований: нет
- Где хранится постановка: вразнобой (часть в Jira-тикетах, часть в головах)

## 3. Разработка
- Локальная сборка/тесты: воспроизводимы
- DoD инкремента: неформальный
- Legacy без тестов: есть, ~30% кодовой базы (модули биллинга и отчётов)

## 4. Ревью и тесты
- Ревью MR: обязательно
- Автотесты + покрытие: есть без метрики; тесты после кода
- Доступ к репозиторию и diff (git): есть

## 5. Процесс
- Методология: Scrum
- Приёмка после деплоя: нет
- Где фиксируются критерии: дозревают по ходу спринта

## 6. Инструменты
- Трекер: Jira
- Хостинг репо: GitLab
- CI: GitLab CI
- Инфра для диагностики: PostgreSQL, Redis
- E2E: нет

## 7. Стек
- Языки: C#/.NET
- Фреймворки: ASP.NET Core, EF Core
- Менеджер пакетов / сборка: NuGet, dotnet build

## 8. Люди и власть
- Спонсор: CTO, полномочия есть
- Владельцы CI/инфры: DevOps-команда
- Ожидаемое сопротивление: senior-разработчики (страх замены)
- Команда для пилота: команда биллинга (доброволец)
