# Claude Code Marketplace

> **Нормативный дом правил разработки**: как писать плагины, ревьюить, проверять перед коммитом - не обзор. Обзор проекта (концепция, 3 уровня, структура папок, тех-стек, MCP по ролям) - [README.md](README.md); устройство фреймворков - `docs/*_FRAMEWORK.md`.

Источники истины: `.claude-plugin/marketplace.json` - каталог всех плагинов; `tools/validate-{agent,skill,command,bundle}.js` - валидаторы; `docs/` - фреймворки и гайды; `.claude/rules/` - path-scoped правила репозитория.

## Уровень продукта: ценность и принципы

Три документа уровня 0 - вход в любой спор о содержании каталога: правила ниже выводятся из них, не наоборот.

- **[docs/product/brd.md](docs/product/brd.md)** - ценность: кому каталог служит, что считается успехом (`BR-NNN` с мерой `MOE`), что вне охвата (`non-goals`), что нельзя ухудшить ради целей (anti-metrics), конфликты целей с названной ценой разрешения. Новая работа сверяется с целью отсюда; цели, которой в BRD нет, не существует - её сначала заводят единицей.
- **[docs/domain/domain-model.md](docs/domain/domain-model.md)** - словарь: одно имя - один смысл, у термина названы дом определения и соседний термин, с которым его смешивают. Расхождения между носителями стоят пунктами `D-N` и закрываются решением, а не сводятся молча.
- **[docs/domain/constitution.md](docs/domain/constitution.md)** - инварианты `INV-NNN` (нарушение = дефект, не компромисс) и сквозные меры `NFR-P-NNN`, у каждой единицы источник, `traced from` на `BR` и метод проверки с пометкой автоматическая / ручная. Нормативный текст нормы конституция не дублирует - несёт обязательство и ссылку на дом; разойдутся - действует дом нормы.

## Каталог плагинов

Полный перечень плагинов с описаниями и версиями - **единственный источник истины: `.claude-plugin/marketplace.json`**. Структуру уровней (Skills / Utilities / Specialists / Bundles) и обзор - см. [README.md](README.md); поштучный список здесь не дублируем (растёт и устаревает молча). Нормативные исключения, которые не выводятся из README:

- **Тип skill - валидируемая ось** (`trap-skill` / `process-skill`): от типа зависит, как `tools/validate-skill.js` проверяет файл. Дефолт - trap-skill; process-skill **требует регистрации в allowlist `PROCESS_SKILLS` в валидаторе**, маркер `<!-- skill-type: process -->` в теле - для читателя, валидатор его не парсит. Типология и полная калибровка проверок по типу - [docs/SKILL_FRAMEWORK.md](docs/SKILL_FRAMEWORK.md) («Два типа skill», «Калибровка валидатора по типу»); копию калибровки здесь не держим.
- **delivery/ и review/ специалисты - языко-агностичны**: глубину даёт by-stack загрузка `dex-skill-<стек>-*`, добавление стека их не меняет; когда стековый агент всё же оправдан - «Имя агента» ниже.
- **Состав bundle живёт в `bundle.json` `includes[]`, НЕ в `plugin.json`**: Claude Code строго валидирует `plugin.json` и тихо ломает плагины с неизвестными полями.

## Структура плагина

Все плагины: `.claude-plugin/plugin.json` (манифест) + содержимое по типу - Skill: `skills/<name>/SKILL.md`; Specialist: `agents/<name>.md` (+ опц. `commands/<name>.md`); Bundle: `bundle.json` (`{"includes": [...]}`) + `README.md`; Utility: `hooks/` и/или `commands/` (нотификаторы, CLI-обёртки).

## Гайдлайны: как писать Skills / Specialists / Commands

Устройство (формат, анти-паттерны, рецепты, валидатор) - в фреймворках, читать перед созданием/правкой артефакта:

- **Skill** - [SKILL_FRAMEWORK.md](docs/SKILL_FRAMEWORK.md). Суть: skill - ловушки и anti-patterns, не документация API; формат «Плохо / Правильно / Почему», 3-5 строк на ловушку. Цель и потолки размера - там же («Размер skill»), число здесь не дублируем.
- **Specialist (агент)** - [AGENT_FRAMEWORK.md](docs/AGENT_FRAMEWORK.md) (+ карта «слот процесса -> агент» - [DEV_PROCESS_COVERAGE.md](docs/DEV_PROCESS_COVERAGE.md); выбор «общий vs стек-специфичный» - «Имя агента» ниже). Суть: агент = workflow через фазы (декларативный контракт goal/output/exit/gate, не процедура); условные skills (по стеку/diff) грузятся императивно через Skill tool в фазах, безусловный process-skill узла - pre-load через `skills:` во frontmatter. Два конститутивных принципа - «фаза = контракт» и «у агента стандартный вход и выход» - развёрнуты там же ([«Inter-agent handoff»](docs/AGENT_FRAMEWORK.md#inter-agent-handoff-последовательный-стык): сигнатура в двух носителях, проверка входящего, возврат нехватки наверх, решения в выход). Дом рантайм-контракта узла (режим `interactive`/`autonomous`, словарь полей, graceful degradation) - `dex-skill-node-contract:node-contract`: там же граница «где оператор в петле, где автономно», а порядок работ зоны требований - [docs/pipelines/analytics/PIPELINE.md](docs/pipelines/analytics/PIPELINE.md).
- **Command** - [COMMAND_FRAMEWORK.md](docs/COMMAND_FRAMEWORK.md). Суть: команда = точечное действие (`/build`, `/test`); Goal + Output format, не bash-скрипт. Цель и потолки размера - там же («Размер»), число здесь не дублируем.

## Конвенции

### Именование
- **Skills**: `dex-skill-{name}`. Для стек-специфичных skills `{name}` = `{стек}-{тема}` (`dotnet-ef-core`, `ts-patterns`, `python-pytorch`) - единый стековый префикс обязателен для by-stack loading (см. ниже). Язык-нейтральные skills (docker, solid, ddd) префикса стека не несут.
- **Specialists**: `dex-{domain}-{role}` или `dex-{name}-specialist`
- **Bundles**: `dex-bundle-{role}`
- **Utilities**: `dex-{name}`
- **Skill-оракул качества артефакта**: `{тип}-quality` (`requirement-quality`, `requirement-set-quality`, `adr-quality`). Оракул судит готовый артефакт названного типа и даёт вердикт для метки `quality-checks`; конвенция удерживает соответствие «тип -> оракул» именем, а не догадкой. Реестр соответствий - явная таблица в `dex-skill-node-contract:node-contract` («Реестр "тип артефакта -> оракул"»), новый оракул добавляется строкой туда же; тип без оракула закрывается записью `unverifiable` с причиной, не молчанием (`n/a` в `quality-checks` не пишется - п.7 контракта).

#### Имя агента (frontmatter `name`): стек в имени - только у стек-специфичных

Имя плагина-специалиста (директория `dex-*`) и имя **агента** в его frontmatter (`name`) - разные вещи. Правило для `name`:

- **Стек-специфичный агент** (специфика стека живёт в теле артефакта - идиомы языка, библиотеки экосистемы) -> стек в имени: `dotnet-coder`, `dotnet-test-writer`, `dotnet-ef-specialist`, `ts-test-writer`, `ts-fullstack-assistant`. Generic-имя (`coding-assistant`, `test-writer`) для стекового агента запрещено - оно не отличает агента от общего и даёт коллизию при росте стеков (два `test-writer`'а).
- **Общий (языко-агностичный) агент** (стек грузится через skills по реестру, тело нейтрально) -> чистая роль без стека: `debugger`, `bug-fixer`, `security-reviewer`, `mr-reviewer`, `self-reviewer`.

Имя файла агента совпадает с `name`. Rename агента = major bump (директория плагина и `plugin.json` `name` при этом не меняются - `bundle.json` ссылается на директорию, а не на агента).

#### By-stack loading: общий агент грузит профильные skills по реестру

Общие агенты не хранят зашитый список «если .NET -> skill X»: они грузят process-skill `dex-skill-stack-registry:stack-registry`, определяют стек по манифесту и фильтруют available-skills по префиксу `dex-skill-{стек}-*`. Отсюда конвенция репо: **новый стек = новые `dex-skill-{стек}-*` + строка реестра, агенты не правятся**. Механизм отбора и эмпирическое обоснование префикса - [docs/AGENT_FRAMEWORK.md](docs/AGENT_FRAMEWORK.md#by-stack-loading-общий-агент-грузит-профильные-skills-по-реестру).

### Frontmatter агентов

Поля и правила (`skills:` - только pre-load безусловного process-skill узла полной формой `dex-skill-node-contract:node-contract` (не голым именем плагина, иначе не резолвится); условные trap-skill грузятся императивно через Skill tool в фазах; `allowed-tools:` не поддерживается; явный `model` по характеру суждения, не `inherit`; выбор opus/sonnet/haiku) - нормативный дом [AGENT_FRAMEWORK.md](docs/AGENT_FRAMEWORK.md#выбор-модели-model) (чеклист frontmatter + раздел «Стоимость: `model` и `effort`»).

**`model` и `effort` - разные оси, и ведут себя по-разному.** `model` - потолок (удешевляет дорогую сессию), `effort` - **override** сессионного уровня, то есть поднятие перебивает режим, выбранный пользователем. Отсюда асимметрия: вниз (`low`/`medium`) - для механической работы свободно, вверх - только с названной в теле причиной, сомневаешься - не ставь (наследование). Значения, таблица решений, модель-специфичность нижнего порога и связка верха с thinking - [AGENT_FRAMEWORK.md](docs/AGENT_FRAMEWORK.md#глубина-рассуждения-effort).

**Каскад tools под fact-check.** Агент с фазой Fact Verification (грузит `dex-skill-fact-verification:fact-verification`) обязан нести в `tools` весь каскад: `ToolSearch` **и** `WebSearch, WebFetch`. Нет звена - каскад молча деградирует до latest-доки; ловит `npm run validate:agents` (`factcheck-cascade-incomplete`). Почему именно эти три и что ломается без каждого - [AGENT_FRAMEWORK.md](docs/AGENT_FRAMEWORK.md#fact-verification-и-ответ-второй-стороны) («Tools для каскада»).

### Frontmatter skills
```yaml
---
name: skill-name
description: Ключевые слова для автоматической активации
---
```
> **Важно:** `keywords` не поддерживается в skills - ключевые слова включать в `description`. Это единственное поле, которое ловит валидатор. Перечень валидных полей не дублируем: нормативный дом - [SKILL_FRAMEWORK.md](docs/SKILL_FRAMEWORK.md) (там же дата сверки с документацией).

## Механизмы композиции в Claude Code

Проверено по официальной документации (code.claude.com/docs/en/skills + tools-reference.md):

| Путь | Работает | Механизм |
| ---- | -------- | -------- |
| command -> skill | ✓ | `Skill` в `allowed-tools` команды, вызов в теле |
| agent -> skill | ✓ | условный: `Skill` tool в frontmatter, императивный вызов в фазе (`{plugin}:{skill}`). Безусловный process-skill: pre-load через `skills:` во frontmatter |
| agent -> agent | ✓ | `Agent` tool - спавн субагента. Глубина рекурсии не задокументирована |
| skill -> skill | косвенно | автоматической загрузки по имени в теле нет - API нет. Рабочий путь: тело предписывает исполнителю (главному потоку либо агенту с `Skill` в `tools`) явно вызвать `Skill` `{plugin}:{skill}` - тул есть у исполнителя, не у скилла. Прецедент: `dex-skill-artifact-review` (`SKILL.md:41`) |
| skill -> agent | косвенно | тот же механизм, что и `skill -> skill`: спавнит главный поток, исполняя текст скилла - тул есть у исполнителя, не у скилла |
| command -> agent | ✓ на практике | команда-делегат: тело команды поручает работу агенту. `Agent` в `allowed-tools` команде не давать - оркестрация живёт не в команде: порядок работ зоны - в скилле-оркестраторе, фан-аут внутри одной работы - в агенте (конвенция репо, ревью PR#51) |

**Практические правила:**

- **Skill не загружает другой skill автоматически.** Упоминание `dex-skill-X` в теле SKILL.md его не запускает - только справочная сноска (`> см. dex-skill-X`). Рабочий путь - предписать: тело просит исполнителя (главный поток или агента) вызвать `Skill` `{plugin}:{skill}` явно (прецедент `artifact-review`). Формулировка «загружает / активирует / подключает» без слова «предписывает» / «вызывает `Skill`» - ложь, переписать.
- **Дублирование ловушек между skills - зло.** При пересечении тем оставить содержимое в одном skill, из другого - сноска.
- **Композиция skills - явным вызовом `Skill`.** Исполнитель (агент в своей фазе, либо главный поток, которому это предписано телом скилла) вызывает `Skill` с точным именем `{plugin}:{skill}`; сам факт «оба носителя - skill» композицию не даёт.
- **Связь между специалистами в bundle** - это установка вместе, не runtime-вызов.

## Чек-лист при изменении плагинов

Уроки, накопленные в работе над маркетплейсом. Проходить по списку **до коммита** любых правок в `plugins/` или `docs/`.

### Принципы содержания

- **Skill = обобщённое правило, не конкретика одного проекта.** Читая критику конкретного MR, извлекать универсальный принцип. Сигналы необобщённости: имена Entity / классов / доменных терминов из реального проекта (`UpCore`, `MergeRequest`, `EyeLineData`, `ArchValue`); привязка к IDE-specific конвенциям (`.junie/`, `.cursorrules`) вместо обобщённого «любые документы проекта с конвенциями». Граница: имена API стека в стековом скилле допустимы, имена конкретного продукта - нет. Принцип проверки: «убери имена проекта - правило всё ещё читается и применяется?». Развёрнуто - анти-паттерн №10 в [SKILL_FRAMEWORK.md](docs/SKILL_FRAMEWORK.md).
- **Агент описывает workflow через фазы, не процедуры.** Goal / Output / Exit criteria / Gate. Ни «сделай grep», ни примеров кода. Mandatory-фазы обязательно с обоснованием «зачем».
- **Создаёшь / правишь агента -> сверься с его рецептом в `AGENT_FRAMEWORK.md`** (Analyst / Diagnostician / Creator / Designer / Operator / Planner / Reviewer): состав фаз, mandatory-список и обоснование берутся оттуда. Состав фаз рецепта в CLAUDE.md не дублировать - нормативный дом один; полные контракты фаз живут в референс-агенте рецепта.
- **Формулировки фаз / гейтов / правил не должны допускать тихий пропуск этапа или проверки.** Описывая обязательный шаг в агенте, команде или skill - закрыть все лазейки, через которые исполнитель может «легально» его не выполнить. Сигналы лазейки: «обычно / часто опирается на ...» (даёт решить, что в этом случае не опирается), «если не нашёл / недоступно» без указания, что делать дальше (даёт закрыть проверку самим фактом отсутствия), «по усмотрению / при необходимости» (делает обязательное опциональным), ветвление или шаг без терминала на ветке - «если X -> Y» без «иначе -> что», шаг с проверкой без названного исхода провала (откат / возврат наверх / статус) - оставляет поведение на ветке неопределённым. Правило: любой уход от проверки фиксируется **явным статусом с обоснованием** (`n/a` + почему, `unverifiable`, `contradicted`), а не молчанием; недоступность инструмента переключает на запасной, а не отменяет шаг; «очевидно» не освобождает от сверки. Принцип проверки формулировки: «может ли добросовестный исполнитель прочитать это так, что проверку можно не делать и в отчёте не останется следа?» - если да, переписать жёстче.
- **Формулировка правила / ловушки / фазы должна быть однозначной.** Каждая единица читается одним способом и не оставляет лазейки для игнорирования. Двусмысленность - это дефект ревью, не стилистика: если формулировку можно прочитать двумя способами, или «Правильно» допускает толкование, при котором правило не применяется, или соседние единицы в одном skill дают взаимоисключающие указания (один приём осуждён в одной ловушке и рекомендован в соседней) - переписать до однозначности или развести область применения явным условием. Критерий проверки: «может ли добросовестный исполнитель прочитать это так, что правило к его случаю не относится или противоречит соседнему?» - если да, формулировка не готова. Это шире, чем запрет тихого пропуска проверки (см. выше): касается любого нормативного текста, а не только обязательных шагов.
- **Формулировки в артефактах пишутся для LLM, не для человека - сухо и по делу.** Skill, агент, команда читаются моделью; нести механизм, условие, исход - не пересказ. Не путать с тихим пропуском проверки (см. выше): сжимаем подачу, а не нормативную силу - лазеек, статусов и обоснований не сокращаем. Лаконичность - обязательная ось ревью (`dex-skill-artifact-review:artifact-review`). Операционализация принципа (что резать, как писать, информационная архитектура, поле срабатывания `description`, проверка результата) - `dex-skill-optimize-for-llm:optimize-for-llm`, нормативный дом операционных правил. Дисциплину формы (атомарность, терминал ветки, узкий escape, реестр статусов) держать как критерий письма и ревью, но НЕ выносить метками-операторами (`GATE:`, `ESCAPE:`) в текст артефакта: прогон `optimize-for-llm` на собственной размеченной версии показал - видимые метки режутся как накладные токены уровня 3, нормативную силу несёт проза правила + реестр статусов.
- **Пунктуация в артефактах - ASCII, не Unicode.** Дефолт: `-` вместо `—`/`–`, `->` вместо `→`, `<-`/`<->` вместо `←`/`↔`, `<=`/`>=`/`!=` вместо `≤`/`≥`/`≠`, `...` вместо `…`. Причина: для артефакта-входа модели типографика на качество не влияет, но ASCII токенизируется стабильнее (1 байт = 1 токен; `—` - UTF-8 3 байта, у части токенизаторов 2-3 токена) и даёт единый стиль. Решает консистентность, не экономия. НЕ трогать: кавычки «», box-drawing диаграмм (`│├└─`), эмодзи-статусы, `№`, надстрочные индексы, `×`, Unicode-примеры внутри `inline code` (там символ - предмет показа, не текст). Миграция **пофайловая**: не сквозняком по репо за раз, но тронул файл по любой причине - приводишь его к ASCII целиком (не только свои строки). Единица миграции = файл. Нетронутые файлы на Unicode до своей правки - не дефект.
- **Документ каталога из тела артефакта не адресуется вовсе.** Тело команды, агента и skill (вместе с его `references/`) исполняется в проекте пользователя, а `docs/` каталога в установленный плагин не входит. `docs/` - дизайн-тайм: он нормирует авторство артефактов, не их исполнение. Ни относительный путь, ни абсолютный URL исполнителю файл не открывают: первый указывает в `docs/` чужого проекта, второй уводит за нормой в сеть посреди прогона. Исход хуже отсутствия ссылки - адрес выглядит валидным, и модель либо молча его не находит, либо сочиняет содержимое. Норма, нужная в рантайме, живёт **в самом артефакте** либо в скилле, который у пользователя установлен (`dex-skill-node-contract:node-contract` и прочие плагины каталога); дрейфующие числа (лимиты размера носителя, минимум активаторов) берутся **прогоном валидатора** - он называет порог прямо в сообщении, - а не переписываются в тело. Тем же правилом адресуется **соседний плагин** (`../<плагин>/README.md`): у пользователя плагины ставятся по отдельности, поэтому сосед называется именем скилла или плагина, не путём. Механизировано двумя правилами (error) во всех трёх валидаторах: `catalog-docs-link` на адрес документа каталога, `link-escapes-plugin` на ссылку, выводящую за корень плагина. Подъём внутри своего плагина законен - решает разрешённый путь, а не число `../`. НЕ применять к пути **в проекте пользователя** (`docs/discover/README.md` как выход агента, `docs/brd/payments.md` как вход) - там относительный путь верен.
- **Адрес документа каталога из README плагина - абсолютный URL, не относительный путь.** README едет в установленный плагин вместе с ним, `docs/` - нет, поэтому относительный `docs/X.md` из него указывает в чужой проект. Форма: `https://github.com/dex-it/claude-code-marketplace/blob/main/<путь>`, при указании на раздел - с якорем; отступы вверх ловятся `rg '\]\(\.\.[^)]*\)' plugins`. `main` здесь не произвольная ветка, а канал поставки: установка **без `ref`** берёт дефолтную ветку («`ref` - Optional. Git branch or tag (defaults to repository default branch)», [plugin-marketplaces](https://code.claude.com/docs/en/plugin-marketplaces), сверено 28.07.2026). **Синхронность носителя и цели - условие, а не свойство: форма верна, пока `main` получает `develop` целиком.** Частичный перенос носителя без его документа даёт ложно-валидный адрес; проверка - `git grep -o 'blob/main/[^)]*' origin/main -- plugins`, каждая цель существует в том же снапшоте **вместе с разделом, если адрес несёт якорь** (файл на месте, а раздела в нём нет - тот же исход, и `git cat-file -e` его не ловит). Якорь ищется в двух формах сразу - HTML-тег `<a id="...">` и заголовок markdown; проверка по одной форме даёт ложное срабатывание, в каталоге есть обе. Пин поддержан («To pin to a branch or tag, append `@ref`...», там же), и у поставившего каталог как `...@develop` синхронности нет вовсе. Файлы за пределами `plugins/` (корневой `README.md`, `install-bundle/`, сам `CLAUDE.md`) правилом не покрыты - читаются в клоне репозитория, где `docs/` рядом. Голое имя пути в backticks разрешаемого адреса не обещает и правилом не покрывается.

### Ревью артефактов (skill / агент / команда)

Ревью = прогон по 5 обязательным осям: соответствие фреймворку, fact-check, полезность,
лаконичность, сверка с гайдом объявленной в артефакте модели. «Всё валидно по фреймворку» ревью не
закрывает - формальная валидность не отвечает на «стоит ли это держать в каталоге».

Ответ на этот вопрос берётся не из вкуса ревьюера: ось полезности сверяется с целями продукта -
каждая единица несёт `BR-NNN` из [docs/product/brd.md](docs/product/brd.md), которой служит.
Ни одна цель не продвигается - находка (цель заводится единицей BRD либо единица убирается);
продвигает ценой anti-metric - находка с названной ценой; нарушает `INV-NNN`
[конституции](docs/domain/constitution.md) - находка независимо от пользы. Механика - в skill.

Механика осей, разметка охвата модель-специфичных пунктов, реестр статусов ухода от проверки и
критерий завершённости - нормативный дом `dex-skill-artifact-review:artifact-review` (грузить
полной формой). Почему вынесено в skill, а не оставлено здесь: это многошаговая процедура, а
пересказ её по памяти уже расходился с оригиналом.

### Самоконтроль при правках фреймворков и документации

Нормативный дом - `.claude/rules/docs-changes.md` (path-scoped, перечень путей - `paths` в самом файле): один факт - один дом, что кладём сюда, кто читает CLAUDE.md, сверка утверждений о платформе и о валидаторе, запрет хардкода чисел состояния, кросс-сверка дублей.

### Версии, синхронизации, гейт перед коммитом

Нормативный дом - `.claude/rules/plugin-changes.md` (path-scoped, перечень путей - `paths` в самом файле): таблица semver-бампов и версия каталога, обязательные синхронизации (marketplace.json, замкнутость бандла, Skill-ссылки), `npm run validate` и то, что CI не закрывает.
