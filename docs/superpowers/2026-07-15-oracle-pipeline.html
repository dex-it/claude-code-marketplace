Агентный SDLC · конвейер после замыкания оракула

Как течёт оракул: вход и выход каждого узла

Каждый агент - узел: принимает поля стыка на входе, отдаёт на выходе. Красная нить конвейера - оракул (критерий «готово», против которого судят работу). До этой ветки оракул никто не производил, и потребители вставали в halt. Теперь два узла его рождают, а метка [FR-NNN] протягивает требование от идеи до теста.

Продуктовый оракул - acceptance criteria, что видит пользователь Технический оракул - success criteria / DoD, как проверить инкремент Halt - нет оракула -> возврат оркестратору, не додумывать
01 business-analyst формализует идею Требования

Вход

  • Сырая идея / бриф
  • constraints (ограничения бизнеса)
  • mode (дефолт autonomous)

Выход

  • status первым полем
  • BRD + перечень FR / NFR
  • non-goals, открытые вопросы, риски
  • FR/NFR - вход user-story-writer
несёт: FR-NNN (требование, ещё без оракула)
02 user-story-writer рождает продуктовый оракул Спецификация

Вход

  • [blocking] источник с FR-NNN из BRD
  • контекст репо
  • halt источник без FR / бизнес-цели -> возврат

Выход

  • status
  • рождает acceptance criteria
  • Given-When-Then, метка [FR-NNN] на каждом
  • перечень stories, non-goals
acceptance criteria + [FR-NNN]
03 architect рождает технический оракул Спецификация

Вход

  • [blocking] бизнес-задача / постановка
  • NFR, constraints, контекст репо (brownfield)
  • halt нет бизнес-цели -> нечего проектировать

Выход

  • status, дизайн-решение, CAP/PACELC
  • Deep Dive (КАК устроено) + implementation plan
  • рождает success criteria
  • критерии приёмки инкремента, метка [FR-NNN]
acceptance criteria + success criteria + diff-scope позже
04 coder реализует против оракула Разработка

Вход

  • [blocking] requirements R/I
  • [blocking] оракул success criteria / acceptance criteria
  • Deep Dive НЕ засчитывается за оракул - это лазейка, закрыта
  • halt нет оракула -> нечем мерить «готово»

Выход

  • status, diff-scope (файлы + ветка)
  • success criteria - что закрыто
  • run-status (build / test / lint)
  • принятые решения с прецедентом
diff-scope (пути) + оракул оба типа
05 tester судит работу оракулом Тест-инжиниринг

Вход

  • [blocking] diff-scope - пути (тела читает с диска)
  • [blocking] публичные контракты
  • [blocking] оракул: success criteria + acceptance criteria - продуктовый старше
  • тесты держатся за критерии, не за реализацию

Выход

  • status, тест-файлы, run-status
  • coverage (branch % по diff-scope)
  • тест наследует [FR-NNN] - иначе нить рвётся
код зелёный -> перед push и в чужой MR его судят ревью
06 self-reviewer саморевью перед push Ревью · pre-push

Вход

  • intent - источник намерения (оракул: success criteria / план) для intent-gate
  • захват сам из git (committed + staged + worktree)
  • намерения нет -> ось intent: n/a, находки НЕ глушатся (не halt)

Выход

  • 8 блоков находок (anchor + severity), вкл. non-code
  • run-status - реальный прогон build / test
  • рекомендация push / чеклист loose ends
push -> MR открыт -> первичное ревью чужого кода
07 mr-reviewer первичное ревью MR Ревью · входящий MR

Вход

  • [blocking] указатель MR/PR + BASE_SHA / HEAD_SHA
  • intent (оракул для intent-gate) - нет -> intent: n/a
  • publish (дефолт false) - санкция на запись в чужой MR
  • код читает сам через gh/glab, не из handoff

Выход

  • находки с severity / confidence / scope 🟢🟡🟠🔴🟣
  • verdict + overview
  • инлайн-треды - только при publish: true
автор правит -> re-review дельты (петля до чистого verdict)
08 mr-check-reviewer ре-ревью после правок Ревью · дельта

Вход

  • [blocking] указатель MR + LAST_REVIEW_SHA (граница прошлого раунда)
  • intent, publish
  • дельту строит сам: git range-diff + diff LAST_REVIEW..HEAD

Выход

  • статус прежних находок: closed / partial / open / disputed
  • новые находки только в дельте
  • verdict. Ответ автора = claim, проверяется по коду

Правило старшинства оракулов

На узле, судящем чужую работу (тест, ревью), оба оракула могут разойтись. Тогда держатся за продуктовый: он судит бизнес-результат, технический - лишь способ его достичь. Технический критерий, противоречащий продуктовому, - дефект спецификации: status: blocked оркестратору, не молчаливый выбор.

acceptance criteria (продуктовый) > success criteria / DoD (технический)
Ветка без постановки - brownfield

Когда постановки никогда не было, оракула нет вовсе. Его восстанавливают дисциплиной, а не выдумывают из кода.

L legacy-reconstruction восстановление оракула из кода process-skill

Три шага - средний не пропускается

  • 1. Реконструкция (агент) -> черновик спецификации из кода
  • 2. Валидация (человек) -> размечает: замысел или баг в проде
  • 3. Тесты (агент) -> против валидированного оракула, не против кода

Шаг 2 не автоматизируется: агент не отличит замысел от бага - оба «как код себя ведёт». Пропустить -> тесты зафиксируют баг как контракт.

Транспорт полей - контракт node-contract (словарь + правило стыка). Красная нить [FR-NNN] едет внутри значений полей, отдельного поля нет: BRD -> acceptance criteria -> критерий приёмки -> тест. Обрыв метки на любом узле = обрыв нити требования. Маршрут между узлами решает оркестратор; каналом к пользователю владеет только главный цикл.
