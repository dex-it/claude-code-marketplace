# Анкета обследования клиента - Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Написать анкету-интервью `adoption/01-assessment.md` и шаблон профиля `adoption/templates/company-profile.md`, по которым консультант снимает профиль клиента и видит точки встраивания агентного SDLC, упорядоченные по порядку внедрения.

**Architecture:** Два markdown-артефакта. Анкета - оси в порядке ВНЕДРЕНИЯ (быстрый вход -> постановка -> разработка -> процесс -> инструменты -> стек) + строка люди/власть; вопрос-суждение несёт таблицу `ответ -> точка встраивания`, факты идут сводной таблицей блока. Профиль - зеркало осей в два слоя (сырой ответ + ВЫВОД). Оба ссылаются на существующие сущности каталога (`DEV_PROCESS_COVERAGE.md`, `CLI_UTILITIES.md`), не заводят новый словарь.

**Порядок = внедрение, не конвейер.** Анкета читается как черновик плана: сперва то, что даёт эффект сразу при минимальной зависимости (ревью+тесты по коду), затем корень качества (постановка), затем зависящее от него (кодеры). Это обратно потоку разработки (требования -> код); внедряемся снизу вверх.

**Ревью и тесты по коду включаемы всегда; оракул усиливает, не предусловие.** С требованиями тесты проверяют «все ли кейсы реализованы, граничные покрыты»; без требований - regression-режим с пометкой риска зеркалирования (тест без оракула цементирует баги реализации). Оракул-как-предусловие остаётся только для агентов-кодеров (блок 3): кодер без критериев приёмки не знает, что реализовать - halt (`dex-skill-node-contract`, бизнес-нехватка).

**Терминология:** снаружи (текст вопросов, имена блоков) - язык PMI-Agile / DA-ACP: acceptance criteria, Definition of Done, requirements, phase gate, validation. «Оракул» - внутренний диагностический термин консультанта, живёт ТОЛЬКО в подсказках «на что смотреть» (свойство: работают ли acceptance criteria оракулом - зафиксированы до кода и не подгоняются). Клиент термина «оракул» не слышит. Имена активов (`dex-*` агенты, CLI-плагины) - как есть, это не клиентский словарь.

**Tech Stack:** Markdown. Не код - нет сборки/тестов; верификация = структурная проверка + пробное заполнение профиля на выдуманном клиенте.

## Global Constraints

- Каталог `adoption/` - в корне репозитория, НЕ в `docs/` (у playbook другой читатель - консультант/клиент).
- Язык - русский.
- Пунктуация - ASCII (`-` вместо `—`, `->` вместо `→`) по конвенции репо.
- Анкета не заводит новый словарь: выводы ссылаются на реальные имена агентов (`DEV_PROCESS_COVERAGE.md`), CLI-плагинов (`CLI_UTILITIES.md`), скиллов (`dex-skill-{стек}-*`), понятия «волна 0» / `legacy-reconstruction` (родительская спека).
- Таблицу вывода несут ТОЛЬКО вопросы-суждения (ответ разветвляет стратегию). Фактические вопросы - сводной таблицей блока, без индивидуальных таблиц.
- **Порядок осей = порядок внедрения:** быстрый вход (встаёт сразу) -> постановка (корень качества) -> разработка (после постановки) -> процесс/инструменты/стек (чем цепляться). НЕ порядок конвейера разработки - это явно оговаривается в шапке анкеты.
- **Ревью и тесты по коду не имеют предусловия оракула** - встают сразу; оракул усиливает. Предусловие оракула - только у агентов-кодеров (блок 3).
- **Блоки этапов внедрения (1 Быстрый вход, 2 Постановка, 3 Разработка) открываются таблицей требований** `требование -> уровень -> как проверить`; вопросы-суждения идут ПОСЛЕ и диагностируют эти требования. Уровни: **must** (без этого агенты этапа не включаются - стоп/волна 0), **should** (включаются, но деградируют), **nice** (усиливает, не блокирует). Блоки 4-6 и Люди/власть таблицы требований НЕ несут (не этап со своими агентами).
- Язык вопросов/блоков - PMI-Agile (DA/ACP): acceptance criteria, Definition of Done, requirements, phase gate. «Оракул» - только в подсказках «на что смотреть» (диагностический термин консультанта), не в тексте вопросов.
- Люди/власть - без таблицы вывода (механического вывода нет, влияет на порядок раскатки).
- Область: только анкета + профиль. Планировщик, `03-planning`, `02-maturity-matrix`, балльная зрелость - НЕ входят.
- Точные имена агентов по слотам (из `DEV_PROCESS_COVERAGE.md`): `dex-business-analyst` (Требования/BRD), `dex-user-story-writer` (продуктовый оракул acceptance criteria), `dex-requirements-analyst` (валидация требований), `dex-architect`/`dex-architect-dotnet` (спецификация, NFR+системный анализ, технический оракул), `dex-dotnet-tester`/`dex-ts-tester` (тесты), `dex-dotnet-coder`/`dex-ts-fullstack-coder` (код), `dex-mr-reviewer`/`dex-mr-check-reviewer` (ревью MR), `dex-self-reviewer` (pre-push), `dex-stand-reviewer` (приёмка на стенде), `dex-debugger`/`dex-dotnet-runtime-diagnostician` (диагностика).
- Точные CLI-плагины (из `CLI_UTILITIES.md`): трекер - `dex-jira-cli` (`jira`); хостинг/CI - `dex-github-cli` (`gh`), `dex-gitlab-cli` (`glab`); CI - `dex-jenkins-cli`, `dex-teamcity-cli`; инфра - `dex-kubectl-cli`, `dex-psql-cli`, `dex-redis-cli`, `dex-kaf-cli`, `dex-rabbitmqadmin-cli`, `dex-aws-s3-cli`; E2E - `dex-playwright-cli`.

- [ ] **Step 2: Дописать блок «Быстрый вход»**

Добавить в конец файла. Блок первый: точка максимального эффекта при минимальной зависимости. Ревью MR и тесты по коду встают сразу, оракул усиливает:

```markdown
## Блок 1. Быстрый вход (ревью и тесты по коду)

Что можно внедрить сразу и максимально просто: агент-ревью MR и автоматическое покрытие
тестами. Они цепляются за уже существующий код, требований не ждут, дают эффект
немедленно. Требования (блок 2) усиливают - тесты проверяют против критериев, все ли
кейсы реализованы, граничные покрыты, - но не являются предусловием для этого блока.

### Требования к встраиванию

| Требование | Уровень | Как проверить |
|---|---|---|
| Система контроля версий (git), доступ на чтение diff | must | есть репозиторий, ветка/MR доступны |
| Обязательное ревью MR перед мерджем | should | гейт в настройках хостинга (protected branch) |
| Автотесты, гоняются в CI | should | pipeline с тест-джобой |
| Измеряемое покрытие (branch coverage) | nice | отчёт покрытия в CI |

*Разрыв must (нет git/доступа к diff) - агентам ревью/тестов не за что цепляться, вход
невозможен. should-разрывы вход не блокируют, но снижают эффект (см. вопросы ниже).*

### 1.1. Есть ли обязательное ревью MR перед мерджем?

*На что смотреть:* обязательный гейт ревью до мерджа vs мерж по кнопке. Ревью встаёт
сразу - читает diff, не требований. Признак дыры: мерж без обязательного ревью.

| Ответ клиента | Точка встраивания |
|---|---|
| Обязательное ревью MR перед мерджем | Усилить: `dex-mr-reviewer` (первичное) + `dex-mr-check-reviewer` (ре-ревью дельты) |
| Ревью неформальное / по желанию | Ввести гейт + `dex-mr-reviewer`; `dex-self-reviewer` (pre-push) на стороне автора |
| Мерж без ревью | `dex-self-reviewer` минимум сразу; вводить обязательный гейт ревью MR |

### 1.2. Есть ли автотесты и измеряется ли покрытие?

*На что смотреть (усиление или зеркало):* тесты по коду встают сразу. Риск без
требований: тест зеркалит реализацию и цементирует её баги - без оракула ловит только
регрессию к текущему поведению, не расхождение с замыслом. С требованиями (блок 2) -
проверка против критериев приёмки.

| Ответ клиента | Точка встраивания |
|---|---|
| Автотесты есть, покрытие измеряется | Тестеры (`dex-dotnet-tester`/`dex-ts-tester`) усиливают покрытие по diff-scope |
| Тесты есть, покрытие не меряется | Тестеры + branch coverage по diff; с требованиями - против критериев |
| Автотестов нет | Тестеры сразу в regression-режиме (фиксация текущего поведения); пометить риск зеркалирования до постановки |

### Сводка блока 1

- Ревью MR: [обязательно / неформально / нет] -> усиление или ввод гейта.
- Автотесты + покрытие: [есть с метрикой / без метрики / нет] -> тестеры сразу.
- Быстрый вход даёт эффект до постановки; после блока 2 тесты переключаются на проверку
  против критериев приёмки.
```

- [ ] **Step 1: Дописать блок «Постановка»**

Добавить в конец файла. Блок - корень качества: без постановки нечем мерить «готово», агенты-кодеры не включаемы. Ступени цепи производства постановки, вопрос-суждение на каждую:

```markdown
## Блок 2. Постановка (BRD -> требования -> критерии приёмки)

Корень качества всего конвейера. Постановка - цепь: бизнес-требования (BRD) ->
функциональные требования + критерии приёмки -> нефункциональные требования (NFR) ->
валидация постановки на корректность. Рвётся на любой ступени - постановки нет, и
дальше по течению строить не на чем: агент-кодер не знает, что реализовать, тест не
знает, против чего проверять. Блок показывает, на какой ступени цепь рвётся, - чтобы
точечно поставить недостающий трек (**волна 0**), а не «налаживать всё».

### Требования к встраиванию (агентов-кодеров)

| Требование | Уровень | Как проверить |
|---|---|---|
| Критерии приёмки как оракул (до кода, проверяемы, не подгоняются) | must | критерии есть в тикете ДО начала кода, формулировка проверяема |
| Бизнес-требования (BRD): цели, границы, Out of Scope | should | есть постановка уровня эпика, не «тикет = строка» |
| NFR зафиксированы (перфоманс, безопасность, нагрузка) | should | NFR заданы до разработки, а не постфактум |
| Валидация требований на полноту/конфликты | nice | есть роль/ритуал проверки на gaps перед разработкой |

*Разрыв must (нет критериев-оракула) - агент-кодер не знает, что реализовать: стоп на
этапе, волна 0 (производитель критериев) до включения кодеров. Первая разорванная
ступень цепи определяет трек волны 0 (см. вопросы).*

### 2.1. Кто и как ставит бизнес-требования (BRD)?

*На что смотреть:* есть ли осмысленная постановка «зачем/что» на уровне эпика - цели,
FR/NFR, риски, Out of Scope. Признак отсутствия: «задача = тикет с одной строкой».

| Ответ клиента | Точка встраивания |
|---|---|
| Есть аналитик/PO, ставит BRD с целями и границами | Ступень BRD закрыта; `dex-business-analyst` опционален как усилитель |
| Постановка отрывочная / «тикет = описание» | Ступень рвётся здесь -> `dex-business-analyst` (BRD: FR/NFR, риски, Out of Scope) |

### 2.2. Фиксируются ли проверяемые критерии приёмки (acceptance criteria)?

*На что смотреть (оракул или зеркало):* работают ли критерии оракулом - зафиксированы
до кода и не подгоняются под результат. «Реализовать экспорт» - не критерий; «экспорт
отдаёт CSV с колонками X,Y,Z; пустой список -> файл с заголовком без строк» - критерий.
Признаки зеркала: пишутся после кода; правятся, чтобы тест сошёлся.

| Ответ клиента | Точка встраивания |
|---|---|
| Критерии проверяемы, до разработки, не правятся под код | Оракул есть -> агенты-кодеры включаемы; тесты против критериев |
| Критерии есть, но расплывчатые / после кода | Полу-оракул -> `dex-user-story-writer` обязателен как производитель acceptance criteria `[FR-NNN]` |
| Критериев нет | Ступень рвётся -> `dex-user-story-writer`; агентов-кодеров не включать до этого |

### 2.3. Фиксируются ли нефункциональные требования (NFR)?

*На что смотреть:* производительность, безопасность, нагрузка, доступность - заданы до
разработки или всплывают постфактум («на проде тормозит»). NFR - часть постановки, не
опция. Признак: про нагрузку/безопасность вспоминают после инцидента.

| Ответ клиента | Точка встраивания |
|---|---|
| NFR фиксируются и сверяются с архитектурой | Ступень закрыта; `dex-architect`/`dex-architect-dotnet` опционален |
| NFR всплывают постфактум / не заданы | `dex-architect`/`dex-architect-dotnet` (NFR + системный анализ сверкой с кодом, технический оракул на инкремент) |

### 2.4. Кто проверяет требования на полноту и противоречия?

*На что смотреть:* требования могут быть, но с дырами (нет негативных путей,
конфликтуют между собой). Признак: требования пишет один человек, никто не проверяет на
пробелы перед разработкой.

| Ответ клиента | Точка встраивания |
|---|---|
| Есть роль/ритуал проверки требований на пробелы и конфликты | Валидация закрыта; `dex-requirements-analyst` опционален |
| Требования не проверяются на полноту/конфликты | `dex-requirements-analyst` (валидация: gaps/conflicts/ambiguity) перед разработкой |
| Работа по legacy без постановки вообще | Слот `legacy-reconstruction` + гейт валидации человеком (поведение из кода человек размечает: замысел или баг; не автоматизируется) |

### Сводка блока 2

- Ступени цепи: BRD [есть/нет] -> критерии [оракул/зеркало/нет] -> NFR [есть/нет] ->
  валидация [есть/нет].
- Первая разорванная ступень -> волна 0 на неё (business-analyst / user-story-writer /
  architect / requirements-analyst).
- Цепь цела -> агенты-кодеры включаемы (блок 3).
```

## Блок 3. Разработка (готовность кодовой базы к кодерам)

Агенты-кодеры включаются последними: им нужны и критерии приёмки как оракул (блок 2), и
готовая среда - воспроизводимая сборка/тесты, гейты, понятная ветковая модель. Блок
выясняет готовность среды помимо требований.

### Требования к встраиванию

| Требование | Уровень | Как проверить |
|---|---|---|
| Постановка с критериями приёмки (блок 2 пройден) | must | оракул есть - иначе кодер не включается |
| Воспроизводимая сборка + прогон тестов локально | must | одна команда билд+тест, агент верифицирует себя |
| DoD инкремента (тесты зелёные, coverage, миграции) | should | технический критерий готовности инкремента задан |
| Понятная ветковая модель + CI-гейты | should | branching задокументирован, CI блокирует красное |
| Покрытие legacy или план его реконструкции | nice | legacy-модули покрыты или размечены под reconstruction |

*Два must: без постановки (блок 2) кодер не знает ЧТО делать; без воспроизводимой
локальной сборки/тестов кодер не может проверить, что сделал. Любой разрыв must -
кодеров не включать до закрытия.*

### 3.1. Воспроизводится ли сборка и прогон тестов локально одной командой?

*На что смотреть:* агент-кодер верифицирует себя локально (build/test/lint). Если сборка
неповторяема или тесты не гоняются локально - агент не может проверить свою работу.

| Ответ клиента | Точка встраивания |
|---|---|
| Сборка + тесты воспроизводятся локально | Кодеры (`dex-dotnet-coder`/`dex-ts-fullstack-coder`) верифицируются локально; `dex-self-reviewer` гоняет build/test |
| Сборка/тесты только в CI, локально не поднять | Наладить локальный прогон до включения кодеров; иначе саморевью деградирует до статического |

### 3.2. Есть ли DoD инкремента, отдельный от продуктовых критериев?

*На что смотреть:* технический DoD (тесты зелёные, coverage, миграции применены) -
отдельный от acceptance criteria оракул на своём уровне. Оба нужны; при конфликте
продуктовый старше.

| Ответ клиента | Точка встраивания |
|---|---|
| DoD инкремента есть, отдельный от acceptance criteria | Технический оракул есть -> кодеры знают критерий готовности инкремента |
| DoD нет или неформальный | `dex-architect`/`dex-architect-dotnet` производит критерии приёмки инкремента с трассировкой к требованиям |

### 3.3. Есть ли код без тестов и без постановки (legacy)?

*На что смотреть:* brownfield - код, который нельзя покрыть тестами напрямую (тест
зеркалит реализацию и цементирует баги). Нужна реконструкция оракула из кода до TDD.

| Ответ клиента | Точка встраивания |
|---|---|
| Код покрыт или есть постановка | Обычный поток кодер/тестер |
| Legacy без тестов и постановки | `dex-skill-legacy-reconstruction` (восстановить оракул из кода) до TDD-слота; гейт человека на разметку замысел/баг |

### Сводка блока 3

- Локальная сборка/тесты: [воспроизводимы / только CI] -> можно ли верифицировать кодера.
- DoD инкремента: [есть / нет] -> технический оракул.
- Legacy без тестов: [есть / нет] -> legacy-reconstruction.
- Готовность среды + постановка (блок 2) -> включение агентов-кодеров.
