# Анкета обследования клиента - Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Написать анкету-интервью `adoption/01-assessment.md` и шаблон профиля `adoption/templates/company-profile.md`, по которым консультант снимает профиль клиента и видит точки встраивания агентного SDLC.

**Architecture:** Два markdown-артефакта. Анкета - 4 оси (оракул -> процесс -> инструменты -> стек) + строка люди/власть; вопрос-суждение несёт таблицу `ответ -> точка встраивания`, факты идут сводной таблицей блока. Профиль - зеркало осей в два слоя (сырой ответ + ВЫВОД). Оба ссылаются на существующие сущности каталога (`DEV_PROCESS_COVERAGE.md`, `CLI_UTILITIES.md`), не заводят новый словарь.

**Tech Stack:** Markdown. Не код - нет сборки/тестов; верификация = структурная проверка + пробное заполнение профиля на выдуманном клиенте.

## Global Constraints

- Каталог `adoption/` - в корне репозитория, НЕ в `docs/` (у playbook другой читатель - консультант/клиент).
- Язык - русский.
- Пунктуация - ASCII (`-` вместо `—`, `->` вместо `→`) по конвенции репо.
- Анкета не заводит новый словарь: выводы ссылаются на реальные имена агентов (`DEV_PROCESS_COVERAGE.md`), CLI-плагинов (`CLI_UTILITIES.md`), скиллов (`dex-skill-{стек}-*`), понятия «волна 0» / `legacy-reconstruction` (родительская спека).
- Таблицу вывода несут ТОЛЬКО вопросы-суждения (ответ разветвляет стратегию). Фактические вопросы - сводной таблицей блока, без индивидуальных таблиц.
- Порядок осей: оракул первым (решает «с чего начать»), инструменты/стек в конце (решают «чем цепляться»).
- Люди/власть - без таблицы вывода (механического вывода нет, влияет на порядок раскатки).
- Область: только анкета + профиль. Планировщик, `03-planning`, `02-maturity-matrix`, балльная зрелость - НЕ входят.
- Точные имена агентов по слотам (из `DEV_PROCESS_COVERAGE.md`): `dex-business-analyst` (Требования), `dex-user-story-writer` (продуктовый оракул acceptance criteria), `dex-requirements-analyst` (валидация требований), `dex-architect`/`dex-architect-dotnet` (спецификация, технический оракул), `dex-dotnet-tester`/`dex-ts-tester` (тесты), `dex-dotnet-coder`/`dex-ts-fullstack-coder` (код), `dex-mr-reviewer`/`dex-mr-check-reviewer` (ревью MR), `dex-self-reviewer` (pre-push), `dex-stand-reviewer` (приёмка на стенде), `dex-debugger`/`dex-dotnet-runtime-diagnostician` (диагностика).
- Точные CLI-плагины (из `CLI_UTILITIES.md`): трекер - `dex-jira-cli` (`jira`); хостинг/CI - `dex-github-cli` (`gh`), `dex-gitlab-cli` (`glab`); CI - `dex-jenkins-cli`, `dex-teamcity-cli`; инфра - `dex-kubectl-cli`, `dex-psql-cli`, `dex-redis-cli`, `dex-kaf-cli`, `dex-rabbitmqadmin-cli`, `dex-aws-s3-cli`; E2E - `dex-playwright-cli`.

- [ ] **Step 2: Дописать блок «Оракул»**

Добавить в конец файла. Блок «Оракул» - первый и центральный (тезис продукта: без оракула нет валидации). Три вопроса-суждения:

```markdown
## Блок 1. Оракул

Оракул - зафиксированный проверяемый критерий «готово», против которого судят работу.
Без него агент-тестописатель пишет тесты против фактического поведения кода (включая
баги), а не против замысла. Этот блок решает: можно ли включать агентов-кодеров и
тесты - или сперва нужна «волна 0» (поставить производство критериев приёмки).

### 1.1. Как команда понимает, что задача готова?

*На что смотреть:* не «есть ли ТЗ», а есть ли проверяемое условие готовности ДО начала
работы. «Реализовать экспорт» - не критерий; «экспорт отдаёт CSV с колонками X,Y,Z;
пустой список -> файл с заголовком без строк» - критерий. Признак отсутствия: на «как
поймём, что готово» отвечают «когда смержим» / «когда тестировщик посмотрит».

| Ответ клиента | Точка встраивания |
|---|---|
| Аналитик/PO пишет проверяемые критерии до разработки | Оракул есть -> тесты включаемы сразу; `dex-user-story-writer` опционален (усилитель) |
| Критерии есть, но расплывчатые / пишутся после кода | Полу-оракул -> `dex-user-story-writer` обязателен как производитель критериев приёмки; тесты - после него |
| «Задача = тикет с описанием», критериев нет | Оракула нет -> **волна 0**: сперва поставить постановку (`dex-business-analyst` -> `dex-user-story-writer`); агентов-кодеров и тесты не включать |
| Работа идёт по legacy без постановки вообще | Слот `legacy-reconstruction` + гейт валидации человеком (реконструкцию поведения из кода человек размечает: замысел или баг; не автоматизируется) |

### 1.2. Кто и как валидирует, что критерии полны и непротиворечивы?

*На что смотреть:* критерии могут быть, но с дырами (нет негативных путей, конфликт
между собой). Признак: критерии пишет один человек и никто не проверяет на пробелы.

| Ответ клиента | Точка встраивания |
|---|---|
| Есть роль/ритуал проверки требований на пробелы и конфликты | Слот "Спецификация" закрыт со стороны валидации; `dex-requirements-analyst` опционален |
| Критерии пишутся, но на полноту/конфликты не проверяются | Включить `dex-requirements-analyst` (валидация требований) перед разработкой |
| Ни критериев, ни валидации | Смотри 1.1 - волна 0 первичнее, валидацию включать после производителя |

### 1.3. Есть ли технический критерий приёмки инкремента (DoD), отдельный от продуктового?

*На что смотреть:* продуктовый критерий (что видит пользователь) и технический DoD (как
проверить инкремент - тесты зелёные, coverage, миграции применены) - разные оракулы.
Признак смешения: «готово = я так задумал» без независимой проверки.

| Ответ клиента | Точка встраивания |
|---|---|
| Есть DoD инкремента (проверяемый), отдельный от продуктового | Технический оракул есть -> `dex-architect`/`dex-architect-dotnet` опционален как усилитель |
| DoD нет или неформальный | `dex-architect`/`dex-architect-dotnet` производит критерии приёмки инкремента `[FR-NNN]` |
| Продуктовый и технический критерии смешаны в один | Развести: при конфликте продуктовый старше (правило старшинства node-contract) - зафиксировать в регламенте |
```

```markdown
Варианты: Scrum / Kanban / waterfall / нет формального процесса.

### 2.2. Где в вашем потоке проходит ревью кода и приёмка?

*На что смотреть:* есть ли обязательный MR-ревью перед мерджем и отдельная приёмка
после деплоя. Признак дыры: мерж без ревью, или «приёмка = задеплоили и закрыли тикет».

| Ответ клиента | Точка встраивания |
|---|---|
| Обязательный MR-ревью + приёмка на стенде после мерджа | Гейты есть -> `dex-mr-reviewer`/`dex-mr-check-reviewer` на ревью, `dex-stand-reviewer` на приёмке |
| MR-ревью есть, приёмки после деплоя нет | Включить `dex-stand-reviewer` (зелёный деплой != рабочая фича) как post-merge гейт |
| Мерж без обязательного ревью | Ввести гейт ревью перед мерджем; `dex-self-reviewer` (pre-push) как минимум на стороне автора |

### 2.3. Куда в потоке ложится момент «критерии приёмки зафиксированы»?

*На что смотреть:* гейт оракула (человек подтверждает, что критерии проверяемы) должен
стоять ДО начала кода. В Scrum - на груминге/планировании; в Kanban - на входе в
колонку In Progress; в waterfall - на выходе аналитики.

| Ответ клиента | Точка встраивания |
|---|---|
| Есть точка, где критерии фиксируются до разработки | Вешать гейт оракула туда (переход тикета в In Progress / выход аналитики) |
| Критерии дозревают по ходу разработки | Гейт оракула ставить искусственно на входе в разработку; иначе тесты писать не против чего |

### Сводка блока 2

- Методология: [Scrum / Kanban / waterfall / нет] -> куда физически вешать гейты.
- Расположение гейтов оракула / ревью / приёмки - в профиль.
```

```markdown
### Сводная таблица: стек -> специалисты + LSP

LSP-сервер даёт агенту type-resolved навигацию (ground truth для типизированных языков) -
меняет глубину работы кодера на стеке клиента. Выбирается по языку, поэтому в блоке
«Стек», не «Инструменты». Установка LSP - тот же второй шаг: сервер в PATH + агент
должен знать, что он есть (обычно уже в контексте LSP-тула, но проверить).

| Стек клиента | Агенты-кодеры/тестеры | By-stack скиллы | LSP-сервер |
|---|---|---|---|
| .NET / C# | `dex-dotnet-coder`, `dex-dotnet-tester`, `dex-architect-dotnet` | `dex-skill-dotnet-*` (см. реестр `dex-skill-stack-registry`) | `csharp-ls` |
| TypeScript / Node | `dex-ts-fullstack-coder`, `dex-ts-tester` | `dex-skill-ts-*` | `typescript-language-server` |
| Другой стек (Python/Go/...) | общие агенты (`dex-feature-implementer`, `dex-debugger`) | by-stack скиллов может не быть - пометить пробел | сервера может не быть -> `tldr`/`rg`/`ast-grep` вместо LSP |

Стек без профильных агентов/скиллов -> работает на общих агентах, глубина by-stack и
LSP недоступна; пометить в профиле.
```
