# Анкета обследования клиента - Implementation Plan

> **Исторический документ.** План фиксирует, как артефакты создавались изначально;
> нумерация блоков и перечни вопросов ниже отражают первую версию. Актуальный контракт
> анкеты (состав блоков, вопросы, обоснование каждого против нашего слота автоматизации)
> держит спека [2026-07-15-assessment-questionnaire-design.md](../specs/2026-07-15-assessment-questionnaire-design.md)
> и сами артефакты в `adoption/`. При расхождении верна спека, не этот план.

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Написать анкету-интервью `adoption/01-assessment.md` и шаблон профиля `adoption/templates/company-profile.md`, по которым консультант собирает данные о процессе и целях клиента. Точки встраивания по этим данным определяет планировщик (отдельная работа), не анкета.

**Architecture:** Два markdown-артефакта. Анкета - вопросы-факты по осям процесса + блок цели; каждый вопрос несёт подсказку «на что смотреть» (как отличить настоящий ответ от желаемого при сборе). Профиль - зеркало осей в один слой (собранный факт). Ни таблиц «ответ -> точка встраивания», ни имён агентов, ни ВЫВОДов: это решения планировщика. Оба ссылаются на нормативку каталога только на уровне «про что спрашивать».

**Граница: анкета собирает, план решает.** Анкета фиксирует состояние клиента (что есть, чего нет, как именно, зачем). Планировщик по профилю определяет точки встраивания. Клиент участвует только в сборе; точки встраивания мы определяем сами, клиент их не видит.

**Tech Stack:** Markdown. Не код - нет сборки/тестов; верификация = структурная проверка + пробное заполнение профиля на выдуманном клиенте.

## Global Constraints

- Каталог `adoption/` - в корне репозитория, НЕ в `docs/` (у playbook другой читатель - консультант/клиент).
- Язык - русский.
- Пунктуация - ASCII (`-` вместо `—`, `->` вместо `→`) по конвенции репо.
- **Анкета - только сбор данных.** В анкете и профиле НЕТ: таблиц «ответ -> точка встраивания», имён агентов `dex-*` в выводах, сводных таблиц «инструмент -> плагин -> как в контекст», поля ВЫВОД с трактовкой. Всё это - решение планировщика (отдельная работа).
- Что в анкете ОСТАЁТСЯ (это сбор, не решение): вопросы-факты; подсказка «на что смотреть» (калибровка сбора - как отличить настоящий ответ от желаемого); цель клиента.
- Где у ответа есть типовые варианты - они даны как подсказка формулировки ответа (записать единообразно), без колонки следствия.
- **Порядок блоков** - по фазам SDLC (цель -> постановка -> разработка -> ревью/тесты -> процесс -> инструменты -> стек -> люди), не задаёт порядок внедрения. Порядок раскатки решает планировщик.
- **Блок «Цель клиента» - первым**: задаёт рамку интервью, консультант калибрует вопросы по фазам под известную боль. Цель - вход планировщика наравне с фактами.
- Профиль - один слой (собранный факт), без слоя ВЫВОД. Точки встраивания в профиле не фиксируются.
- Терминология: PMI-Agile (DA/ACP) снаружи (acceptance criteria, DoD, requirements); «оракул» - только в подсказках «на что смотреть» (диагностический термин консультанта при сборе).
- Область: только анкета + профиль. Планировщик, `03-planning`, `02-maturity-matrix`, балльная зрелость - НЕ входят.
- `tools-dictionary.md` - актив планировщика (маппинг фактов на плагины), помечен как таковой; анкета на него не ссылается.
