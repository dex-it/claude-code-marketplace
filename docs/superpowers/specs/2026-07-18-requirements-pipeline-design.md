## 1. Проблема и цель

**Проблема.** Дефект требования дёшев в момент рождения и дорог в конце цепочки. Требование с дырой проходит BRD -> story -> код -> тесты и всплывает как «баг» уже в проде, хотя код правильный. Сейчас каталог ловит дефект требования в основном на ревью кода (mr-reviewer, self-reviewer грузят requirement-quality) - то есть в самом конце, когда код уже написан по дырявому ТЗ.

**Вторая проблема (вскрыта при написании плана).** Автономный движок `autonomous-task` несёт треки «Требования», «Согласование/Спецификация», «Проектирование», но их критерий «готово» упирается в **апрув автора** - а движок стартует от задачи и работает автономно, канала к автору у него нет («спросить некого» - его кредо). Треки с обязательным человеческим апрувом внутри автономного движка противоречивы: гейт апрува либо игнорируется, либо вырождается в тупик. Эти стадии по своей природе **интерактивные** и должны жить до движка, а не внутри него.

**Цель.**
1. Сдвинуть контроль качества требований влево - к моменту рождения. Каждый порождённый артефакт (BRD, stories) проверяется сразу после создания, до следующей стадии, чтобы дефект не размножился на N нижележащих артефактов.
2. Пересмотреть треки движка: вынести интерактивные до-разработочные стадии (требования, спецификация/проектирование) в отдельные интерактивные контуры перед движком; движок оставить чисто автономным - от задачи.

## 2. Три зоны: граница на «задаче»

Пайплайн разбит на три зоны. **Граница между интерактивной и автономной частью - «задача»:** до задачи (пока требование/дизайн рождаются и согласуются людьми) - интерактивно; от задачи (born из апрувнутой story или из бага) - автономно.

```
ЗОНА 1 - АНАЛИТИК (человек A), интерактивная
  создание:    /feature (НОВАЯ)
    идея/тема -> BRD -> [апрув аналитика] -> stories + AC [FR-NNN] -> [апрув аналитика]
  согласование: /review-requirements (НОВАЯ)
    чужой готовый BRD/stories -> находки (оракулы) -> обсуждение с оператором
           -> правки автору (в задачу ИЛИ в документ, по месту)
  выход: апрувнутый BRD + stories с трассировкой FR->AC + метка quality-checks
        |
        |  handoff: апрувнутые stories
        v
ЗОНА 2 - АРХИТЕКТОР (человек B), интерактивная
  создание:    /design (СУЩЕСТВУЕТ, доработка)
    stories -> спека + дизайн + ADR + диаграммы  (архитектор, ОДИН прогон на эпик)
           -> [апрув архитектора, Phase 5]
  согласование: /review-design (НОВАЯ)
    чужой готовый дизайн -> находки (оракулы) -> обсуждение с оператором
           -> правки автору (в задачу ИЛИ в документ, по месту)
  выход: апрувнутая спека = Definition of Ready
        |
        |  граница: ЗАДАЧА (born из апрувнутой story ИЛИ баг)
        v
ЗОНА 3 - ДВИЖОК autonomous-task (автономный, от задачи)
  задача -> Разработка -> Тест -> Ревью -> ... -> Документ
  канал к юзеру НЕТ; дефект -> status: blocked наверх оркестратору
```

**Три архитектурных решения зон:**

1. **Два владельца - два человека - два апрува.** Требования - зона аналитика (`/feature` создание + `/review-requirements` согласование чужого); архитектуру - зона архитектора (`/design` создание + `/review-design` согласование чужого дизайна). Разные агенты И разные люди. Слить в один прогон нельзя: аналитик не решает за архитектора, архитектор не переписывает требования. У каждого свой апрув-гейт. Внутри каждой зоны создание и ревью чужого - тоже разные роли/агенты (Operator/создатель vs Reviewer; как кодер vs mr-reviewer): `requirements-orchestrator`/`architect` создают, `requirements-reviewer`/`design-reviewer` судят чужое.

2. **Спека - на эпик, не на каждую story.** Архитектор прогоняет `/design` один раз на эпик (набор stories), не на каждую story. Выход - спека + дизайн + ADR + диаграммы вместе.

3. **Движок стартует от задачи.** Задача рождается из апрувнутой story (зона 1->2->задача) ИЛИ из бага (минуя зоны 1-2). Всё до задачи - интерактивно и вне движка; движок - чисто автономный, от задачи.

## 3. Пересмотр треков движка

Движок сбрасывает три до-разработочных трека (у всех критерий «готово» = апрув автора, что автономному движку недоступно) и оставляет 7 разработческих.

| Трек движка (было) | Диспозиция | Куда |
|---|---|---|
| **Требования** | **удалить из движка** | зона 1 `/feature` (формализация уже в `business-requirements-analyst`) |
| **Согласование/Спецификация** | **удалить из движка** | зона 2 `/design` (архитектор, спека на эпик) |
| **Проектирование** | **удалить** (дубль Спецификации) | поглощён зоной 2 - архитектор в `/design` выдаёт спеку + дизайн + ADR вместе |
| Разработка | остаётся автономным | движок |
| Тест-инжиниринг | остаётся | движок |
| Ревью входящего MR | остаётся | движок |
| Обработка ревью своего MR | остаётся | движок |
| Приёмка слитой фичи на стенде | остаётся | движок |
| Документирование | остаётся | движок |
| Диагностика/инцидент | остаётся | движок |

**«Спец поглощает Проектирование».** Трек Спецификации (архитектор, один прогон на эпик) поглощает отдельный трек Проектирования - в движке это был дубль (оба «код не пишем», оба про дизайн до кода). Архитектор в `/design` производит спеку + дизайн + ADR + диаграммы одним актом.

**Что удаляется физически (правки движка):**
- файлы `tracks/requirements.md`, `tracks/specification.md`, `tracks/design.md`;
- строки таблицы треков в `SKILL.md` (Требования, Согласование/Спецификация, Проектирование);
- записи маппинга «трек -> исполнитель» для этих треков;
- детект трека на шаге 1 (если он различал эти три).

**Что НЕ трогаем:** 7 разработческих треков и их файлы - без изменений.

## 4. Распад дома логики

Тело удаляемых треков **не переезжает целиком в один новый дом** - оно распадается по существующим домам. Отдельный process-skill `feature-pipeline` НЕ создаётся (симметрия с движком ложна: у конвейера 2 стадии, не 10 треков; оркестрация укладывается в фазы агента).

| Что было в теле трека | Куда переезжает |
|---|---|
| Формализация/декомпозиция (бизнес-анализ -> FR/NFR; story -> AC) | **уже** в агентах `business-requirements-analyst` и `user-story-writer` - трек их только звал; дубль-описание в треке удаляется |
| Оркестрация + гейты + режим (interactive/autonomous, апрув-паузы, спавн составителей) | **фазы агента-дирижёра** зоны 1 (новый) |
| Нить `FR-NNN` (трассировка требование->story->AC) + межзонный handoff | **`dex-skill-node-contract`** (сквозное поле + правило приёмки) |

**Итог:** новый код - только (а) агент-дирижёр зоны 1 + тонкая команда `/feature`; (б) новый set-оракул; (в) расширение node-contract. Составители и `/design` - доработка, не создание.

## 5. Зона 1, создание: дирижёр + команда /feature

**Новый агент** `dex-requirements-orchestrator` (рецепт Operator - ведёт процесс через необратимые гейты с explicit confirmation; сам артефакты не пишет) + **тонкая команда** `/feature`.

**Команда `/feature`** (паттерн `/discover`, `/design`):
- `allowed-tools`: НЕ содержит `Agent` (конвенция репо - оркестрация в агенте, не в команде, ревью PR#51);
- тело: делегирует агенту-дирижёру, передаёт `mode: interactive` во входе (канал к юзеру есть - команда в главном цикле);
- логики пайплайна в команде НЕТ - только `mode: interactive` + аргумент оператора. Все фазы/гейты/оркестрация - в теле агента (COMMAND_FRAMEWORK: команда 20-50 строк, Goal+Output, не workflow; эталон `/design` -> `architect`);
- `argument-hint`: описание фичи / тема от оператора.

**Агент-дирижёр** (`tools: Read, Write, Grep, Glob, Skill, Agent, ToolSearch, WebSearch, WebFetch`):
- держит канал к оператору (главный цикл);
- спавнит составителей (`business-requirements-analyst`, `user-story-writer`) как autonomous-субагентов через `Agent`;
- между стадиями: прогон set-оракула + предъявление находок оператору + сбор апрува.

**Фазы дирижёра (контракты, не процедуры):**

| Фаза | Goal | Gate |
|---|---|---|
| Bootstrap | понять запрос, определить объём; **классифицировать вход: сырая тема / проработанная идея / чужой готовый артефакт** | - |
| Стадия 1: Ideate->BRD (conditional) | брейнсторм с оператором (сам дирижёр, грузит `product-discovery` как knowledge) -> спавн BA -> BRD | ГЕЙТ BRD: single+set -> находки оператору -> explicit approval |
| Стадия 2: Decompose | спавн user-story-writer (авто) -> stories | ГЕЙТ stories: оракул + трассировка FR->AC -> оператору -> approval |
| Handoff | передача апрувнутых stories в зону 2 (`/design`) | - |

**Толерантный вход (Стадия 1 conditional).** Bootstrap классифицирует вход:
- `/feature` без аргумента / сырая тема -> идея не проработана -> **Стадия 1 включается**, дирижёр штормит сам;
- `/feature <проработанная идея>` (итог из внешнего брейншторма или свой) -> **Стадия 1 skip**, сразу BA пишет BRD;
- `/feature <чужой готовый BRD/требования>` -> **входная приёмка** чужого артефакта (прогон `requirement-quality` + `requirement-set-quality` до построения stories; полноценное согласование чужого входа - `/review-requirements`, §6);
- критерий skip - наличие проработанного входа, а не размер (как `Study Project Context` у кодеров);
- внешний `superpowers:brainstorming` (штормить до `/feature`) - валидная рекомендация оператору, но `/feature` его не вызывает (внешний скилл, не часть каталога); встроенный шторм Стадии 1 - самодостаточная альтернатива.

**Инвариант режима** (обязателен по AGENT_FRAMEWORK «Интерактивность - свойство позиции вызова»): каждая интерактивная фаза разводится на `interactive` (диалог/апрув) и `autonomous` (дефолт - если дирижёра заспавнили субагентом, гейты вырождаются в возврат наверх). Дефолт `autonomous`; нет поля `mode` -> `autonomous`.

**Explicit confirmation на гейтах.** Необратимый переход между стадиями (BRD -> раскладка размножает дефект на N stories) требует явного апрува оператора в interactive; в autonomous - `status: blocked` + возврат наверх, не авто-approve.

**Правая граница зоны 1 (создание)** - апрувнутые stories. Дальше - зона 2 (`/design`), другой человек и другой апрув.

## 6. Зона 1, согласование: /review-requirements (новая)

Симметричный слот зоны 1 для случая, когда требования (BRD/stories) подготовил **другой** аналитик или пришли из внешнего источника, а их надо провалидировать и согласовать - не переписать. Тот же паттерн, что `/review-design` в зоне 2: ревью/согласование чужого готового артефакта, отдельная роль от порождения.

**Новый агент** `requirements-reviewer` (рецепт Reviewer - выносит находки с фальсификацией, сам чужой артефакт не пишет) + **тонкая команда** `/review-requirements`. Отдельный агент, не режим дирижёра `/feature`: дирижёр порождает/оркестрирует (Operator), ревьюер судит чужое (Reviewer) - разные роли, смешение ломало бы симметрию с зоной 2 (где `architect` создаёт, `design-reviewer` судит).

**Команда `/review-requirements`** (паттерн `/mr-review`, `/review-design`):
- `allowed-tools`: НЕ содержит `Agent`; делегирует агенту-ревьюеру, передаёт `mode: interactive`;
- `argument-hint`: путь к документу требований (BRD/stories) от оператора.

**Агент-ревьюер** (`tools: Read, Grep, Glob, Skill, ToolSearch, WebSearch, WebFetch` - без `Write`/`Edit`: чужой документ не мутирует):
- **оракулы переиспользуются** - те же, что грузит дирижёр на гейтах (§9): `requirement-quality` (дефект единицы) + `requirement-set-quality` (полнота/непротиворечивость набора, трассировка). Новый оракул не создаётся;
- дефект единицы читается из текста одного требования; полнота набора - из всего документа против источника (если источник приложен).

**Роль (по решению оператора, симметрично `/review-design`):**
1. **вынести проблемы** - прогон оракулов по требованиям, находки с фальсификацией (severity/confidence);
2. **обсудить с оператором** (interactive) - находки предъявляются оператору, не сразу автору;
3. **предложить автору правки** - сформулировать, что автору поправить;
4. **доставка правок - по месту, интерактивно** - либо задача в трекер, либо правка в сам документ; оператор решает канал, агент не выбирает молча.

**Инвариант режима:** `interactive` (диалог) vs `autonomous` (дефолт - находки в Output + `verdict`, канала нет). Нет поля `mode` -> `autonomous`.

**Граница.** `requirements-reviewer` судит чужие требования и предлагает правки - **не вписывает их сам** (нет `Write`). Правку вносит автор (аналитик через `/feature`) либо оператор. Это закрывает вопрос приёмки чужих требований (§14) - слот теперь есть в обеих зонах.

## 7. Зона 2, создание: /design (доработка)

**`/design` -> `architect` уже замыкает контур архитектора** - создавать заново не нужно. По разведке (`architect.md`, `design.md`):
- interactive-режим есть (команда передаёт `mode: interactive`);
- апрув-гейт архитектора есть (Phase 5 - explicit confirmation);
- спека + дизайн + ADR + диаграммы производятся вместе.

**Минимальная доработка (только это):**
- **принять `stories` как явный вход.** Сейчас вход `/design` - «бизнес-задача в свободной форме»; добавить, что валидный вход - апрувнутые stories из зоны 1 (эпик);
- **input-acceptance метки `quality-checks`.** Архитектор на входе смотрит метку: stories проверены оракулом требований (аналитиком) -> доверяет, не перепроверяет требования; метки нет -> прогоняет `requirement-quality`/`requirement-set-quality` сам, дефект -> возврат в зону 1 (не дочиняет чужие требования - это зона аналитика).

**Выход зоны 2 (создание)** - апрувнутая спека = Definition of Ready для движка. Из неё рождаются задачи.

## 8. Зона 2, согласование: /review-design (новая)

Симметричный слот зоны 2 для случая, когда дизайн подготовил **другой** архитектор (спека/дизайн/ADR/диаграммы), а его надо провалидировать и согласовать - не переписать. Предмет - **дизайн-документ до кода**, не архитектура реализованного кода (её ревьюит существующий `/review-arch` - другой предмет: стек по csproj, N+1, circular deps, файл+строка).

**Новый агент** `design-reviewer` (рецепт Reviewer - выносит находки с фальсификацией, сам чужой артефакт не пишет) + **тонкая команда** `/review-design`. Отдельный агент, не доработка `architect`: создание и ревью чужого - разные роли (как кодер vs `mr-reviewer`; создатель предвзят к своему решению).

**Команда `/review-design`** (паттерн `/mr-review`):
- `allowed-tools`: НЕ содержит `Agent`; делегирует агенту-ревьюеру, передаёт `mode: interactive`;
- `argument-hint`: путь к дизайн-документу (спека/ADR) от оператора.

**Агент-ревьюер** (`tools: Read, Grep, Glob, Skill, ToolSearch, WebSearch, WebFetch` - без `Write`/`Edit`: чужой документ не мутирует; правку доставляет автору, не вписывает молча):
- **оракулы переиспользуются, новый `design-quality` НЕ создаётся** - дефекты дизайн-документа уже покрыты существующими, ревьюер грузит набор по фазам:

| Аспект дизайн-документа | Оракул (существующий) |
|---|---|
| полнота и осмысленность NFR (числа, SLA/SLO, security-NFR) | `nfr` |
| противоречия требований, конфликт с инвариантом/Accepted ADR, невыполнимость | `requirement-quality` |
| качество ADR-решений (drivers, альтернативы, trade-off) | `adr-quality` (после rename, §11) |
| консистентность (CAP/PACELC), слои/зависимости, доменная декомпозиция | `cap-consistency`, `clean-architecture`, `ddd` (по стилю) |

**Роль (по решению оператора):**
1. **вынести проблемы** - прогон оракулов по дизайн-документу, находки с фальсификацией (severity/confidence), как у `mr-reviewer`;
2. **обсудить с оператором** (interactive) - находки предъявляются оператору, не сразу автору; оператор фильтрует/подтверждает;
3. **предложить автору правки** - сформулировать, что автору поправить;
4. **доставка правок - по месту, интерактивно** - жёстко не зашита: либо заводится задача в трекер, либо правка вносится в сам документ. Оператор решает канал доставки в диалоге; агент не выбирает молча.

**Инвариант режима** (как у всех интерактивных): `interactive` (диалог с оператором) vs `autonomous` (дефолт - находки в Output + `verdict`, канала нет). Нет поля `mode` -> `autonomous`.

**Граница.** `design-reviewer` судит чужой дизайн-документ и предлагает правки - **не вписывает их сам** (нет `Write`). Правку в документ вносит автор (`architect`) либо оператор; ревьюер только формулирует. Это отделяет «судить» от «чинить», как в код-ревью.

## 9. Гейты качества (single + set)

Каждый гейт - двухслойная проверка перед апрувом оператора.

**Слой 1 - single-артефакт (есть у составителей).** Составитель прогоняет `requirement-quality` на выходе, несёт метку `quality-checks`. Ловит дефект отдельной единицы: противоречие, неоднозначность, невыполнимость, happy-path. Дирижёр видит метку - слой не перепроверяет (доверие полное, узел отвечает за свой выход).

**Слой 2 - set-completeness (новое, делает дирижёр).** Субагент-составитель видит только свой артефакт, полноту НАБОРА против источника не проверяет - это работа оркестратора (как cross-linking в discover). Дирижёр прогоняет новый set-оракул `requirement-set-quality`:

| Гейт | Источник | Проверка полноты набора |
|---|---|---|
| ГЕЙТ BRD | запрос оператора / брейнсторм | все цели/акторы/сценарии источника покрыты `FR`; нет осиротевших `FR` без бизнес-цели; набор FR/NFR непротиворечив внутри; scope не разъехался |
| ГЕЙТ stories | BRD (`FR-NNN`) | трассировка: каждый `FR` из BRD -> >=1 story с AC; нет story без `FR`-источника; полнота набора AC (частично есть в user-story-writer Phase 4, дирижёр верифицирует) |

**Исход гейта:**
- находки set-оракула -> дирижёр предъявляет оператору как вопросы (interactive): «FR-4 "экспорт" не покрыт ни одной story - добавить или non-goal?»;
- оператор дополняет/подтверждает -> `status: approved` -> переход;
- autonomous (дирижёр заспавнен субагентом) - находки в Output, `status: blocked`, возврат наверх.

Это закрывает системную дыру set-completeness для требований - она вливается сюда, перестаёт быть отдельной задачей бэклога (в части требований; ADR<->ADR и API-спека остаются - см. §14).

## 10. Раскладка ISO/IEC/IEEE 29148

Стандарт (ISO/IEC/IEEE 29148:2018) задаёт характеристики качества на двух уровнях. Термины и §-номера сверены с текстом стандарта (fact-check).

**§5.2.5 - характеристики отдельного требования -> `requirement-quality` (есть).** 9 характеристик:

| Characteristic (29148) | Покрытие в requirement-quality |
|---|---|
| Unambiguous | «требование без проверяемого критерия» |
| Feasible | «технически несовместимо с реальностью» |
| Complete (единичная - всё для понимания) | «описан только happy path» |
| Correct | конфликт с инвариантом/ADR (адекватность нужде) |
| Verifiable | измеримый критерий приёмки |
| Singular | (частично, через «одно требование = один аспект») |
| Appropriate | «требование диктует реализацию вместо результата» (неадекватный уровень абстракции) |
| Conforming | «требование не следует принятому шаблону» (форма формулировки) |
| **Necessary** | **не оракул - советническое мнение дирижёра, см. ниже** |

**§5.2.6 - характеристики набора требований -> `requirement-set-quality` (новый).** 5 характеристик:

| Characteristic набора (29148) | Что проверяет set-оракул |
|---|---|
| Complete (полнота набора) | набор покрывает все нужды источника; нет забытого класса; трассируемость цель->требование сидит здесь |
| Consistent | никакие два требования набора не конфликтуют, нет дублей, единый термин на понятие |
| Affordable | набор выполним в рамках жизненного цикла (стоимость/сроки/техника/legal) |
| Bounded | набор в границах scope, не разросся за пределы нужд |
| Able to be Validated | возможно провалидировать, что набор ведёт к достижению целей |

**Явная граница между оракулами (чтобы не дублировали):**
- `requirement-quality` судит ЕДИНИЦУ - читается из текста одного требования + кода; грузят все (составители, ревьюеры, потребители);
- `requirement-set-quality` судит МНОЖЕСТВО - требует весь набор + источник; грузит только оркестратор/дирижёр, не составитель-субагент.

**Necessary - опциональное советническое мнение, не судящий оракул.** По решению: агент высказывает мнение о необходимости требования, решение за оператором.
- механизм строго советнический: дирижёр на ГЕЙТ BRD МОЖЕТ высказать мнение («FR-5 дублирует FR-2 по цели - нужен ли отдельно?»); это мнение, не находка - не блокирует апрув, не ставит `blocked`, не требует устранения;
- решение за оператором: согласиться / отвергнуть / проигнорировать. Оракульного вердикта «дефект» нет;
- граница: Necessary-мнение звучит ТОЛЬКО в interactive (есть кому высказать и кто решит). В autonomous субагент бизнес-необходимость не оценивает вообще (решать за продакта запрещено), в Output не тащит;
- дом: тело дирижёра, ГЕЙТ BRD, отдельный interactive-шаг - НЕ в `requirement-set-quality` (там судящие характеристики).

## 12. Транспорт метки (node-contract)

Дом правила приёмки и метки - существующий `dex-skill-node-contract` (все узлы грузят через `skills:` pre-load), не новый skill. Расширение раздела C «Приём входа».

**(а) Поле `quality-checks` в словарь полей:**

| Поле | Смысл | Форма |
|---|---|---|
| `quality-checks` | какие артефакты уже проверены своим оракулом в этом флоу | список `{artifact, check, verdict}` |

Сквозное (п.6 node-contract) - переносится по цепочке, даже если узел его не трогал. Ключ записи - тип артефакта: потребитель ищет запись по типу того, что потребляет; метка одного типа не закрывает проверку другого.

**(б) Врезка «Входная приёмка артефакта»** (страховочный слой):
- потребитель на входе смотрит `quality-checks` по типу артефакта;
- запись `{тип, check, verdict: passed}` есть -> skip (доверие полное);
- записи нет / `verdict != passed` -> прогнать оракул типа по реестру;
- оракул нашёл дефект -> `status: blocked` + перечень, возврат оркестратору; потребитель НЕ дочиняет чужой артефакт.

Это ровно механизм межзонного handoff зона1->зона2 (§7): архитектор проверяет метку stories.

**(в) Реестр «тип -> оракул»** (таблица во врезке):
```
требование (BRD/story) -> requirement-quality  (single, у потребителя-единицы)
набор требований       -> requirement-set-quality  (у оркестратора)
ADR                    -> adr-quality
API-спека              -> api-spec-quality   (задел; оракул в set-completeness PR)
```
По конвенции `-quality` реестр читается почти как правило `{тип}-quality`, но держим явной таблицей - точное имя, ноль вероятностного матча по description.

**(г) Простановка метки** (раздел B, состав выхода): узел, проверивший артефакт своим оракулом (составитель на выходе ИЛИ потребитель, прогнавший проверку сам), добавляет запись в `quality-checks` выхода. Метка накапливается по цепочке.

**Доверие метке полное** - `verdict: passed` от составителя принимается без перепроверки (узел отвечает за свой выход). Ложная метка - дефект составителя, ловится ревью-контуром отдельно, не обязанность потребителя (anti-gaming не механизмом - см. §14).

## 14. Границы (что НЕ входит) + открытые вопросы

**Не входит:**
- **Нарезка задач и разработка** - не входят; граница = задача, born из апрувнутой story (после зоны 2) или бага. Дальше - движок.
- **set-completeness для ADR<->ADR и API-спеки** - НЕ в этом PR. Здесь set только для требований (BRD, stories). ADR<->ADR (обход всего `docs/adr/`) и выходная спека api-designer - остаются в бэклоге set-completeness как отдельная работа. `api-spec-quality` в реестре node-contract - задел (строка), оракул не создаётся здесь.
- **Necessary как судящий оракул** - не делаем; только советническое мнение дирижёра в interactive.
- **Автоматический апрув** - нет; апрув всегда явный оператором (в autonomous - возврат наверх, не авто-approve).
- **Anti-gaming метки** (составитель поставил `passed` формально) - не механизмом; ловится ревью-контуром отдельно (доверие метке полное).

**Приёмка чужих готовых артефактов - закрыта в обеих зонах.** Слот «провалидировать и согласовать чужой готовый артефакт без порождения нового» теперь есть симметрично: требования - `/review-requirements` + `requirements-reviewer` (§6); дизайн - `/review-design` + `design-reviewer` (§8). Оба рецепта Reviewer, интерактивный контур, оракулы переиспользуются. Старый трек «Согласование/Спецификация» этот слот явно не выделял (размазан по входу трека Спецификации) - теперь выделен командами.

**Открытые вопросы (не решены, вынести в отдельную проработку):**
- **set-completeness для ADR<->ADR и API-спеки** (см. первый буллет выше) - остаётся отдельной работой бэклога.
