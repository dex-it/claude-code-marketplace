# Замыкание legacy-reconstruction: узлы-потребители реконструкции оракула из кода

## Проблема

`dex-skill-legacy-reconstruction` (создан в PR #118) - process-skill дисциплины
«восстановить оракул/требования из кода, когда постановки никогда не было». Он повис:
ни один агент не грузит его через Skill tool, он не входит ни в один bundle, единственный
путь активации - авто-семантика по `description`.

План (`docs/superpowers/plans/2026-07-15-oracle-closure.md:349`) назвал потребителей
приблизительно: «грузится debugger/discover-агентами при brownfield-входе». Про debugger
угадал класс (он потребитель - см. ниже), про discover ошибся (технический инвентарь,
оракул не нужен), и главное - ни у одного из них слота под скилл фактически нет. Ревьюер
поймал разрыв (тред #3593715596 PR#118); замыкание отложили как «отдельную работу»,
и скилл остался сиротой.

Момент использования скилла - **реконструкция ожидаемого поведения/оракула из кода,
когда источника постановки нет**. Он возникает у трёх классов узлов:
- **аналитики требований**, когда вход - код без постановки (brownfield, ТЗ никогда не было);
- **ревьюер кода**, когда ревьюится код без источника-намерения (`intent: n/a`);
- **debugger**, когда `[blocking]`-вход «ожидаемое корректное поведение» не пришёл: сейчас
  это глухой halt, а дисциплина скилла даёт реконструировать «как должно быть» из кода -
  что планировали, что уже реализовано - и тем дать расследованию контекст (см. ниже про
  риск закольцевания). Обычный вход debugger шире голого кода: к багу, как правило,
  приложен лог/стек-трейс, реконструкция опирается и на него, не только на исходники.

discover исключён отдельно: он инвентаризирует **технические** проблемы (мёртвый код, дубли,
нарушения слоёв), не бизнес-требования. Эталон «как должно быть по бизнесу» ему не нужен -
технический дефект виден из самого кода, реконструировать оракул нечего.

## Целевые потребители (по факту наличия момента «код без ТЗ»)

| Агент | Момент | Потребитель? |
|---|---|---|
| `business-requirements-analyst` | Phase 3 Deep Scan; вход - идея/код | да (при коде без ТЗ) |
| `requirements-analyst` | Phase 3 Deep Scan; детализация FR/NFR | да (при коде без ТЗ) |
| `mr-reviewer` | вход `intent` - `[default-ok]`; «нет источника -> `intent: n/a`, корректностные находки не глушатся» | да - ревью кода без постановки штатный вход |
| `mr-check-reviewer` | ре-ревью дельты; тот же intent-gate: «нет источника -> ось `intent: n/a`, корректностные находки в дельте не глушатся» | да - тот же момент, слот у своего intent-gate (Phase 4; наследование «по логике mr-reviewer Phase 3» слот в Phase 6 не подхватило бы) |
| `debugger` | вход `[blocking]` «ожидаемое поведение»; нет его -> сейчас глухой halt | да - реконструкция «как должно» вместо halt (гипотеза, не success criteria) |
| `requirements-reviewer` | судит готовый набор требований как документ; ТЗ на входе ЕСТЬ | нет - реконструировать нечего |
| `stand-reviewer` | вход `[blocking]` ТЗ; «нет ТЗ -> halt» | нет |
| `discover` | инвентаризирует ТЕХНИЧЕСКИЕ проблемы, не бизнес-требования | нет - технический дефект виден из кода, оракул не нужен (скилл называет discover опорой ШАГА 1 методически, но узлом-вызывателем не является) |

Итог: пять потребителей - `business-requirements-analyst`, `requirements-analyst`,
`mr-reviewer`, `mr-check-reviewer`, `debugger`.

## Условие загрузки: hard gate

Скилл грузится **обязательно**, когда установлено, что источника постановки нет и оракул
надо реконструировать из кода (brownfield, ТЗ никогда не было / ревью кода с `intent: n/a`).
Это не «по усмотрению» и не авто-семантика: авто-активация по `description` ненадёжна
(ревьюер PR#118), а мягкое условие оставляет исполнителю легальный путь пропустить дисциплину
ровно там, ради чего она написана.

Формулировка слота (проза, без меток-операторов - по конвенции репо):
> Вход - код без постановки (ТЗ никогда не было; для ревьюера - `intent: n/a` и предмет
> ревью - корректность): загрузи `dex-skill-legacy-reconstruction:legacy-reconstruction`
> и веди реконструкцию оракула по её дисциплине. Постановка/ТЗ на входе есть - скилл не
> грузится (реконструировать нечего).

Терминал ветки закрыт с обеих сторон: есть ТЗ -> не грузим; нет ТЗ -> грузим обязательно.

## Автономный случай: шаг 2 недоступен

Скилл требует шаг 2 (валидация человеком: замысел или баг). У автономного узла
(`mode: autonomous`, спавн - канала к человеку нет) шаг 2 невыполним. Поведение:
реконструкция (шаг 1) выполняется, но выдаётся **как гипотеза** со статусом
«реконструировано, не согласовано» (ярлык тела скилла, слоты используют его же -
один дом статуса), и **никогда не за оракул корректности**; открытый
вопрос (что из реконструированного - замысел, что - баг) уходит наверх оркестратору.

Тело скилла это уже несёт («черновик помечается "реконструировано, не согласовано" до
валидации»; «тест на невалидированное поведение фиксирует "как есть", не выдавать за
проверку корректности»). Правки тела скилла не требуется - только слот агента ссылается
на этот статус для автономной ветки.

### Риск закольцевания у debugger

У debugger реконструкция особая: «как должно быть» выводится в т.ч. из **того же кода, где
сидит баг**. Наивно это закольцовывает - «баг определяется относительно гипотезы, выведенной
из багованного кода». Частично размыкает опору лог/стек-трейс, приложенный к багу: это
внешний по отношению к исходникам сигнал (что реально произошло в рантайме), и реконструкция
опирается и на него. Но лог даёт факт сбоя, не эталон «как должно» - тавтологию он снимает
не полностью. Поэтому для debugger реконструированное ожидаемое:
- служит только гипотезой, **что вообще считать багом** (сформулировать расследуемое
  расхождение), никогда - success criteria фикса («починено» против реконструкции из того
  же кода недоказуемо);
- всегда уходит вердиктом наверх оркестратору как «ожидаемое реконструировано, не
  подтверждено» - решение, баг это или замысел, за человеком/постановщиком, не за узлом.

Это снимает глухой halt (debugger хоть что-то расследует), не подменяя оракул. Если
реконструкция не даёт даже гипотезы расхождения - остаётся прежний halt + возврат.

## Замыкание бандлов

Каждый агент-потребитель грузит скилл императивно -> скилл обязан быть в `includes[]`
бандлов, которые везут этого агента (правило `bundle-not-closed`, `validate:bundles`).
`legacy-reconstruction` - язык-нейтральный process-skill (не `dex-skill-<стек>-*`),
исключение by-stack на него не распространяется.

| Потребитель | Бандлы | Действие |
|---|---|---|
| `business-requirements-analyst` | `dex-bundle-product-manager` | + `dex-skill-legacy-reconstruction` в includes |
| `requirements-analyst` | `dex-bundle-system-analyst` | + то же |
| `mr-reviewer` | `dex-bundle-code-review`, `dex-bundle-dotnet-developer`, `dex-bundle-dotnet-fullstack` | + то же в каждый |
| `mr-check-reviewer` | `dex-bundle-code-review` | покрыт `mr-reviewer` - скилл уже в includes этого бандла |
| `debugger` | `dex-bundle-dotnet-developer`, `dex-bundle-dotnet-fullstack` | покрыты `mr-reviewer` - тот же скилл в тех же двух бандлах |

Затронутые бандлы (уникальные): `product-manager`, `system-analyst`, `code-review`,
`dotnet-developer`, `dotnet-fullstack` - пять. debugger новых бандлов не добавляет.

## Правка плановой сноски

`oracle-closure.md:349` («грузится debugger/discover-агентами при brownfield-входе»)
привести к реальности: потребители - аналитики требований, `mr-reviewer` и `debugger`
при входе без постановки; discover исключён. Это docs (план), не нормативный дом; правка
снимает ложную декларацию (discover как потребитель) и уточняет механизм для debugger.

## Что НЕ входит

- Правка тела `legacy-reconstruction/SKILL.md` - дисциплина трёх шагов и статусы уже
  корректны, дефект был в замыкании (кто грузит), не в содержании.
- Новый brownfield-узел / отдельная команда `/reconstruct` - за рамками; момент
  реконструкции живёт внутри существующих фаз потребителей.
- Слот у discover - отвергнут: инвентаризация технических проблем, оракул из кода не нужен.
- Слот у `requirements-reviewer`/`stand-reviewer` - отвергнут: ТЗ у них на входе есть,
  реконструировать нечего.

## Версионирование

- 5 агентов (`business-requirements-analyst`, `requirements-analyst`, `mr-reviewer`,
  `mr-check-reviewer`, `debugger`) - minor каждому (новый слот загрузки skill в фазе),
  в паре plugin.json + marketplace.json.
- `debugger` - minor осознанно, не major: вход расширен (прежде отвергаемый класс
  «нет ожидаемого» теперь обрабатывается), выход для прежних валидных входов не
  изменился, новое поле `expected-basis` аддитивно; единственный spawn-потребитель
  (`autonomous-task`) сам требует «отсутствие документа - не повод встать».
- Бандлы (`product-manager`, `system-analyst`, `code-review`, `dotnet-developer`,
  `dotnet-fullstack`) - minor каждому (изменён `includes[]`), в паре.
- `dex-skill-autonomous-task` - patch (уточнение двух строк карты маршрутизации,
  brownfield-исключение аналитиков), в паре.
- Версия каталога не меняется (плагины не добавляются/не удаляются).

## Проверки

- `npm run validate` - 0 ошибок (agents/skills/commands/bundles), в т.ч.
  `bundle-not-closed` по пяти тронутым бандлам.
- Слот у каждого потребителя: терминал ветки закрыт (есть ТЗ / нет ТЗ), автономная
  ветка ссылается на статус «реконструировано, не согласовано» (ярлык тела скилла).
- `sync-plugins.sh` после установки: `legacy-reconstruction` нужен пятерым агентам, drift
  закрыт.
