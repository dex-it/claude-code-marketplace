# Нейтральная ось производительности в ревью diff'а (issue #122)

## Проблема

Реестр `stack-registry` подбирает тематические skills двумя осями (стек x тема),
и ревьюеры грузят их блоком «Всегда» в Deep Scan. Для каждой крупной сквозной
темы есть язык-нейтральный skill-дом: security -> `owasp-security`,
надёжность -> `distributed-resilience`, наблюдаемость -> `observability`.
**У производительности нейтрального дома нет.** На не-.NET diff ревьюер судит перф
на голых знаниях: N+1, sync-over-async, лишняя материализация систематически
проскакивают. Issue #122 родился из вопроса «ловит ли mr-reviewer перф» -
ловит лозунгом в фокусе Language correctness и одной MEDIUM-строкой severity,
без дома-skill.

## Что уже есть и почему не закрывает

| Артефакт | Слой | Стек | Момент |
|---|---|---|---|
| `dotnet-performance-analyst` (агент) | диагност | .NET | runtime (уже медленно) |
| `perf-profiling` (skill) | механика perf/FlameGraph | Linux/.NET/Java | runtime (профиль живого) |
| **дыра #122** | **ось ревью** | **нейтрально** | **diff, до прода** |

Оба существующих - про **runtime-диагностику живой системы** (профилировать процесс,
что уже тормозит). Дыра - про **превентивное ревью изменения**: найти перф-грабку
в diff до того, как она станет slow query в проде. Разные моменты жизненного цикла,
разные оси (нейтрально vs .NET). Наличие runtime-диагноста не даёт MR-ревьюеру
нейтральной оси ревью diff'а.

## Аудит всей тематической оси (политика: прагматично, по ценности)

Дыра закрывается новым нейтральным skill ТОЛЬКО если тема даёт реальные неочевидные
грабли уровня owasp. Слабая тема -> явный статус `n/a + причина`, не плодить skills
ради симметрии.

| Тема | Нейтральный дом? | Вердикт |
|---|---|---|
| производительность | НЕТ | **закрыть** - реальные неочевидные грабли ревью diff'а (см. ниже) + прямой запрос #122 |
| миграции схемы/данных | НЕТ (EF-специфично) | **n/a в этой спеке** - грабли реальны (drop column до деплоя читателей, блокирующий DDL, expand-contract, backfill), но это отдельная дыра; тащить в #122 = раздуть scope -> кандидат в отдельный issue |
| доступность (a11y) | НЕТ | **n/a** - грабли есть, но узко (только UI-diff) и в ревью-контуре нет frontend-ревьюера как естественного дома; отдельный разговор |
| логирование как ось | нет (стеково) | **n/a** - покрыто Content-Level pass (mr-reviewer) + security PII-строкой + `dotnet-logging` |
| i18n | нет | **n/a стеково** - не нейтральная ось ревью любого diff'а, зависит от типа проекта |
| обр. совместимость | есть | покрыто (`contract-drift` + `completeness-mapping` + `api-specification` + фокус Architecture) |

Итог: #122 = закрыть одну клетку (производительность). Остальные - зафиксированы статусом.
Миграции схемы - завести отдельный issue (не в этой работе).

## Новый skill: `dex-skill-performance-review`

Язык-нейтральный trap-skill (не `dex-skill-<стек>-*`), калька архитектуры `owasp-security`:
категории H2, грабли H3 в формате «Плохо / Правильно / Почему» (3-5 строк), чек-лист ревью
в конце. Момент - **ревью diff'а**, не профилирование. Область охвата расширена по цели
«полное покрытие перф-граблей, видимых в diff нейтрально»: не только доступ-к-данным/async,
но и конкурентность, память/строки/массивы, I/O (БД/сеть/файлы), натив-граница. Размер -
до 250 строк (потолок trap-skill): 6 осей x 2-4 грабли; костяк не дробится по размеру.
Хвосты, специфичные для стека, и грабли «часто не видно в diff» в тело не тащатся -
уводятся сносками/статусом.

### Над-слой: 4 сквозных принципа (шапка перед осями)

Оси - *где искать*; принципы - *что именно не так*. Ревьюер, увидев паттерн вне списка
граблей, выводит вердикт из принципа (как owasp: категории A0x + сквозной чек-лист).
Короткая шапка перед H2, 4 строки:

1. **Не делай в цикле то, что делается разом** - round-trip, запрос, вызов границы,
   аллокация, компиляция regex, захват лока на итерацию. (loop-invariant: инвариантное
   выносится из цикла.)
2. **Не тащи в память больше/раньше, чем нужно** - overfetch, весь файл/payload, жадная
   материализация ветки, которая может не понадобиться, unbounded cache.
3. **Работай со ссылкой/потоком, не с копией** - стрим vs буфер, срез vs копия, пул vs new.
4. **Переноси работу туда, где она дешевле** - фильтр/агрегация в источник, независимое -
   в параллель, дорогое - за проверку (уровень лога, ленивое вычисление).

Принципы не заменяют грабли (ревьюеру нужны конкретные «Плохо/Правильно» для распознавания) -
дают рамку вывода. Loop-invariant как отдельная H3 не заводится: он живёт принципом 1 и
проявляется в конкретных гранях (regex-в-цикле, аллокация-в-цикле - уже в осях 5).

Категории (H2) - шесть осей перф-граблей, видимых в diff нейтрально по стекам
(собрано из разведки .NET/Python/JS + классов конкурентность/память/строки/натив/IO):

1. **Доступ к данным** (ORM/запросы) - N+1 (навигация/запрос в цикле), unbounded result
   set (нет пагинации), overfetch колонок (проекция), exists-vs-count, фильтр/агрегация
   в память вместо источника. tri-stack: EF `Include`/Django `select_related`/Prisma
   `include`; `AnyAsync`/`.exists()`/`findFirst`; push predicate to WHERE.
2. **I/O: как ходим к ресурсу** (БД/сеть/файлы) - НЕ «сколько данных» (это overfetch выше),
   а физика доступа. Сквозные под-паттерны: запись/запрос в цикле вместо батча
   (`AddRange`+один SaveChanges / `bulk_create` / `createMany`); клиент/соединение/хендл
   на итерацию (socket exhaustion: `new HttpClient()` в цикле / сессия requests заново /
   pool на запрос); весь payload/файл в память вместо стрима (`ReadAllText`/`resp.content`/
   `readFileSync` vs `ReadLines`/`iter_content`/`createReadStream`); транзакция вокруг
   внешнего I/O.
3. **Асинхронность и конкурентность** - await-in-loop независимых операций -> параллель
   (флагман: `Promise.all(map)`/`Task.WhenAll`/`asyncio.gather`); sync-over-async
   (`.Result`/`requests` в `async`/`time.sleep` в корутине); лок вокруг тяжёлой/IO-операции
   (сужай секцию); не занимай поток пула синхронным ожиданием; пул вместо ручных потоков
   (`new Thread`/`Thread`/`new Worker` per-item). Оговорка JS: однопоточный event loop -
   часть грабель конкурентности N/A.
   **Тяжёлая операция на потоке запроса - развилка по природе нагрузки (НЕ «сделай async»):**
   I/O-bound (диск/сеть/БД) -> async-API, поток свободен на ожидании (это sync-over-async выше);
   CPU-bound (хеш/парсинг/сжатие/картинка) -> `async`/`await` НЕ лечит (счёт держит поток),
   вынести из горячего пути в фон/очередь/worker; `Task.Run` вокруг CPU-работы в хендлере -
   антипаттерн (перекладывает занятость на другой поток пула, не устраняет). Грабля принципа 4
   («тяжёлое - долой с потока запроса»). Формулировать с развилкой I/O vs CPU: «сделай async»
   без различения природы - ровно наивная ловушка, от которой skill защищает. Fact-check при
   сборке: поведение `Task.Run` в ASP.NET, thread-pool starvation.
4. **Материализация и коллекции** - needless materialization (`list(gen)`/`ToList` ради
   len/any); повторный обход одного lazy-источника; поиск в списке O(n) в цикле ->
   `Set`/`Map`/`dict`/`HashSet` (структурный O(n^2)); повторная итерация исчерпанного потока;
   (де)сериализация/маппинг в цикле (JSON/DTO per-item, `JsonSerializer` без переиспользования
   options, рефлексия-маппер на горячем пути, маппер-в-память вместо проекции в источнике).
5. **Память, строки, массивы** (слияние - разведчик подтвердил, что отдельные H2 не нужны) -
   аллокация инвариантного в горячем цикле; удержание крупного объекта/подписки (граница
   жизни); срез/копия крупной структуры вместо ссылки; конкатенация строк в цикле O(n^2)
   (`StringBuilder`/`''.join`/`arr.join`); regex создаётся/компилируется в цикле (частный
   случай принципа 1); catastrophic backtracking / ReDoS (экспонента времени на входе - перф-грань,
   не «вредоносный ввод»: та часть у security-reviewer, см. сноску); unbounded cache без границы
   (`lru_cache(maxsize)`/`SizeLimit`/LRU+TTL).
6. **Граница натив<->управляемый код** - одна нейтральная H3 (не H2 - редко в обычном diff,
   сильная стековая специфика): минимизируй число пересечений границы, батчируй данные,
   не маршалируй/копируй per-call. Конкретика (P/Invoke, NumPy-векторизация, N-API/WASM) -
   стековые сноски.

Плюс одна грабля принципа 4 в оси 3 (Асинхронность) либо строкой чек-листа: **дорогое
вычисление за проверкой** - интерполяция дорогого аргумента лога до проверки уровня
(`LogDebug($"{expensive()}")` считает всегда); ленивое вычисление ветки, которая может не
понадобиться. Перф-грань (лишняя работа), не «что и куда логировать» - та часть у observability,
см. сноску.

Точные грабли и их «Правильно» - fact-check при сборке (см. Проверки): каждая строка
«Правильно» сверяется, что это действительно неочевидная грабля ревью diff'а, а не
банальность. Разведка уже дала fact-check-оговорки, которые тело обязано учесть:
- .NET `lock` + `await` в одном блоке НЕ компилируется - грабля «лок вокруг IO» для .NET
  через `Monitor`/синхронный IO под локом, не через `await`.
- Boxing при интерполяции `$"{i}"` устранён для многих случаев с .NET 6 - формулировать
  осторожно; в нейтральное ядро идёт «не аллоцируй инвариантное в цикле», не boxing-конкретика.
- `str +=`/`s +=` в цикле имеют движковые оптимизации (V8 rope, CPython in-place) - квадратичность
  не гарантирована, но паттерн хрупкий; правило «используй join/builder» валидно.
- Python `re` имеет внутренний кэш - формулировать «не полагайся на кэш, компилируй явно»,
  не «re.match всегда пересоздаёт».
- DBAPI `executemany` НЕ гарантирует один INSERT (драйвер-зависимо) - не утверждать
  «executemany = один запрос»; истинный батч в Postgres - `execute_values`/`execute_batch`.
- `HttpClient` per-request - проблема не «нельзя dispose», а короткоживущий хендлер плодит
  сокеты в TIME_WAIT; формулировать точно.

### Грабли «часто НЕ видно в diff» - НЕ в тело как основные

Разведка I/O honest-статусом пометила грабли, невидимые без схемы/рантайма/домена:
- SELECT без индекса - без DDL/плана в diff не виден; исключение - когда в том же PR
  есть и миграция колонки, и горячий фильтр по ней. В чек-лист как условная строка, не как
  безусловная H3.
- деградация от долгой транзакции/локов, «это hot path», «payload крупный» - паттерн виден,
  серьёзность требует контекста; подавать severity-зависимыми, не безусловными находками.

Эти грабли либо не входят, либо входят строкой с явной оговоркой «severity зависит от
размера/горячести - подтверди контекстом», а не выдаются за безусловный дефект.

**Разграничение с смежными домами (сноски в теле, не загрузка - `skill->skill` нет):**
- `> runtime-профилирование живого процесса (perf/FlameGraph) - dex-skill-perf-profiling`
- `> .NET-специфичная диагностика (EF-запросы, APM, память) - агент dotnet-performance-analyst`
- `> тайм-аут/ретрай/backoff/circuit breaker - dex-skill-distributed-resilience`
- `> ReDoS как вектор атаки (вредоносный ввод, DoS) - security-reviewer/owasp; здесь только перф-грань`
- `> что и куда логировать (уровни, PII, структурность) - dex-skill-observability; здесь только лишняя работа лога`

Так skill остаётся про ревью diff'а, дом runtime-диагностики - отдельно; расползания нет.

## Проверки

- **Fact-check каждой строки «Правильно»** (анти-паттерн №11): грабля перфа - реальная
  и неочевидная (не банальность), «Правильно» сверено с текущим поведением API/языка
  где применимо (context7 -> WebSearch fallback). Симметрично дописанная half - красный флаг.
- **Обобщённость**: ни одного имени конкретного проекта/Entity; правило читается без стека.
  Стековые имена API (`Include`, `asyncio.gather`, `Promise.all`) допустимы как примеры-иллюстрации,
  но H3 читается как нейтральный принцип и без них.
- **Стековые хвосты - сноской, не в тело**: `ArrayPool`/`Span`/`[LibraryImport]` (.NET),
  GIL/NumPy-векторизация (Python), `SharedArrayBuffer`/React-memo (JS) - `> см. стековый skill`,
  не H3 нейтрального тела. React-грабли (key, ре-рендеры, useMemo) - UI-специфика, исключены.
- `npm run validate` - 0 ошибок (skills + bundles, в т.ч. `bundle-not-closed`).
- Размер skill - до 250 строк (6 осей; потолок trap-skill, костяк не дробится); `description`
  <= 750 (keywords по симптомам: N+1, query in loop, await in loop, sync over async,
  materialization, hot path allocation, socket exhaustion, readAllText vs stream, string concat loop).
- `optimize-for-llm` прогон на готовом теле.
- Сноски-разграничители на runtime-дом присутствуют.
