# Нейтральная ось производительности в ревью diff'а (issue #122)

## Проблема

Реестр `stack-registry` подбирает тематические skills двумя осями (стек x тема),
и ревьюеры грузят их блоком «Всегда» в Deep Scan. Для каждой крупной сквозной
темы есть язык-нейтральный skill-дом: security -> `owasp-security`,
надёжность -> `distributed-resilience`, наблюдаемость -> `observability`.
**У производительности нейтрального дома нет.** На не-.NET diff ревьюер судит перф
на голых знаниях: N+1, sync-over-async, лишняя материализация систематически
проскакивают. Issue #122 родился из вопроса «ловит ли mr-reviewer перф» -
ловит лозунгом в фокусе Language correctness и одной MEDIUM-строкой severity,
без дома-skill.

## Что уже есть и почему не закрывает

| Артефакт | Слой | Стек | Момент |
|---|---|---|---|
| `dotnet-performance-analyst` (агент) | диагност | .NET | runtime (уже медленно) |
| `perf-profiling` (skill) | механика perf/FlameGraph | Linux/.NET/Java | runtime (профиль живого) |
| **дыра #122** | **ось ревью** | **нейтрально** | **diff, до прода** |

Оба существующих - про **runtime-диагностику живой системы** (профилировать процесс,
что уже тормозит). Дыра - про **превентивное ревью изменения**: найти перф-грабку
в diff до того, как она станет slow query в проде. Разные моменты жизненного цикла,
разные оси (нейтрально vs .NET). Наличие runtime-диагноста не даёт MR-ревьюеру
нейтральной оси ревью diff'а.

## Аудит всей тематической оси (политика: прагматично, по ценности)

Дыра закрывается новым нейтральным skill ТОЛЬКО если тема даёт реальные неочевидные
грабли уровня owasp. Слабая тема -> явный статус `n/a + причина`, не плодить skills
ради симметрии.

| Тема | Нейтральный дом? | Вердикт |
|---|---|---|
| производительность | НЕТ | **закрыть** - реальные неочевидные грабли ревью diff'а (см. ниже) + прямой запрос #122 |
| миграции схемы/данных | НЕТ (EF-специфично) | **n/a в этой спеке** - грабли реальны (drop column до деплоя читателей, блокирующий DDL, expand-contract, backfill), но это отдельная дыра; тащить в #122 = раздуть scope -> кандидат в отдельный issue |
| доступность (a11y) | НЕТ | **n/a** - грабли есть, но узко (только UI-diff) и в ревью-контуре нет frontend-ревьюера как естественного дома; отдельный разговор |
| логирование как ось | нет (стеково) | **n/a** - покрыто Content-Level pass (mr-reviewer) + security PII-строкой + `dotnet-logging` |
| i18n | нет | **n/a стеково** - не нейтральная ось ревью любого diff'а, зависит от типа проекта |
| обр. совместимость | есть | покрыто (`contract-drift` + `completeness-mapping` + `api-specification` + фокус Architecture) |

Итог: #122 = закрыть одну клетку (производительность). Остальные - зафиксированы статусом.
Миграции схемы - завести отдельный issue (не в этой работе).

## Новый skill: `dex-skill-performance-review`

Язык-нейтральный trap-skill (не `dex-skill-<стек>-*`), калька архитектуры `owasp-security`:
категории H2, грабли H3 в формате «Плохо / Правильно / Почему» (3-5 строк), чек-лист ревью
в конце, 80-120 строк. Момент - **ревью diff'а**, не профилирование.

Категории (H2) - оси перф-граблей, видимых в diff нейтрально по стекам:

- **Доступ к данным** - N+1 (запрос в цикле по коллекции), загрузка всей таблицы
  вместо фильтра в БД, отсутствие пагинации на неограниченной выборке, повторный
  идентичный запрос в пределах операции.
- **Асинхронность** - sync-over-async (блокирующее ожидание async в hot path),
  последовательный await независимых операций вместо параллельного, отсутствие
  отмены/тайм-аута на внешнем вызове.
- **Материализация и коллекции** - материализация всей последовательности ради
  Count/Any/First, повторный полный обход одной коллекции, аллокация в горячем
  пути (буфер/строка в цикле), выбор структуры под операцию (поиск по списку O(n)).
- **Границы и объём** - перенос фильтрации/агрегации на клиент вместо источника,
  overfetch полей, кэш без инвалидации / кэш горячего изменяемого значения.

Точные грабли и их «Правильно» - fact-check при сборке (см. Проверки): каждая строка
«Правильно» сверяется, что это действительно неочевидная грабля ревью diff'а, а не
банальность, которую модель и так знает.

**Разграничение с существующим перф-домом (сноски в теле, не загрузка - `skill->skill` нет):**
- `> runtime-профилирование живого процесса (perf/FlameGraph) - dex-skill-perf-profiling`
- `> .NET-специфичная диагностика (EF-запросы, APM, память) - агент dotnet-performance-analyst`

Так skill остаётся про ревью diff'а, дом runtime-диагностики - отдельно; расползания нет.

## Подключение к ревьюерам (только ревью-контур)

Добавить `dex-skill-performance-review:performance-review` в блок «Всегда» фазы Deep Scan:

| Ревьюер | Действие | Обоснование |
|---|---|---|
| `mr-reviewer` | + в «Всегда» Phase 3 | источник #122, первичное ревью diff |
| `self-reviewer` | + в «Всегда» Phase 3 | pre-push, тот же перф на своём diff |
| `mr-check-reviewer` | + в «Всегда» Phase 3 | ре-ревью дельты, перф-регрессия от фикса |
| `security-reviewer` | НЕ трогать | вне scope - «только security» |
| `discover-reviewer` | НЕ трогать | топик 9 «Производительность» уже есть; skill там опционален по топику |

Авторов (coder'ы, feature-implementer) НЕ трогаем: перф - ось ревью diff'а, не написания;
автор пишет по стек-skills, ось ловит ревьюер, автор чинит по находке. Дублировать
нейтральную ось в авторов - разнести один дом по двум слоям.

## Что НЕ входит

- Skill/слот для миграций схемы, a11y - зафиксированы как `n/a`/отдельный issue.
- Правка авторов (coder'ы, feature-implementer) - перф не ось написания.
- Runtime-профилирование - уже покрыто (`perf-profiling`, `dotnet-performance-analyst`).
- security-reviewer / discover-reviewer - вне scope.

## Проверки

- **Fact-check каждой строки «Правильно»** (анти-паттерн №11): грабля перфа - реальная
  и неочевидная (не банальность), «Правильно» сверено с текущим поведением API/языка
  где применимо (context7 -> WebSearch fallback). Симметрично дописанная half - красный флаг.
- **Обобщённость**: ни одного имени конкретного проекта/Entity; правило читается без стека.
- `npm run validate` - 0 ошибок (skills + bundles, в т.ч. `bundle-not-closed`).
- Размер skill 80-120 строк; `description` <= 750 (keywords по симптомам: N+1, slow query
  review, sync over async, materialization, hot path allocation).
- `optimize-for-llm` прогон на готовом теле.
- Сноски-разграничители на runtime-дом присутствуют.
