## 0. Терминология (закрывает F-3 гейта BRD)

BRD использует два термина на одно понятие без глоссария. В этом документе термин зафиксирован один, с указанием соответствия:

| Термин здесь | Роль | Соответствует в BRD |
|---|---|---|
| **Инициатор** | HR-администратор или руководитель подразделения, вызывающий экспорт | «оператор» (UC-3, UC-4, UC-6, UC-9, BR-007), «инициатор» (BR-005, BR-006) |
| **Получатель** | человек/сторона, работающая с выгруженным файлом после передачи (может совпадать с инициатором) | «получатель» (BR-002, BR-003), «потребитель файла» (раздел 4) |

## 1. Функциональные требования (FR)

Шаблон формы: «Система должна <действие> <объект>» - единая модальность, актор системного уровня - система (актор бизнес-уровня, инициатор/получатель, остаётся в `BR`).

### FR-001. Экспорт отобранной выборки без ручного переноса

Система должна по действию инициатора на экране списка сотрудников формировать единый файл, содержащий полный набор строк, отобранный текущими фильтрами экрана (не ограниченный текущей страницей отображения), за одно действие инициатора.

- **Приоритет:** Must
- **Критерий:** число строк файла равно числу строк, удовлетворяющих применённым фильтрам, за одно действие инициатора (без постраничного повтора).
- **traced from:** BR-001

### FR-002. Целостность строк и столбцов

Система должна формировать файл так, чтобы каждая строка соответствовала ровно одному сотруднику отобранной выборки, а каждое значение находилось строго в столбце своего поля, без потери строк и без смещения значений между столбцами.

- **Приоритет:** Must
- **Критерий:** доля выгрузок, потребовавших ручного исправления перенесённых данных (потеря/смещение), = 0 за первые 3 месяца эксплуатации (унаследовано из MOE BR-002).
- **traced from:** BR-002

### FR-003. Пригодность файла к открытию в штатных инструментах получателя

Система должна формировать файл так, чтобы получатель открывал его в Excel и Google Sheets и работал с данными без предварительного переформатирования или восстановления читаемости текста.

- **Приоритет:** Must
- **Критерий:** 0 обращений получателей «файл не открывается / текст нечитаем / всё в одной колонке» за первые 3 месяца (унаследовано из MOE BR-003). Технический контракт кодировки/разделителя вынесен в `NFR-003`.
- **traced from:** BR-003

### FR-004. Ограниченный состав полей

Система должна включать в файл ровно семь полей - ФИО, табельный номер, подразделение, должность, дата приёма, статус, корпоративный email - и не должна включать никакое иное поле, включая зарплатные данные, личный телефон, домашний адрес, паспортные данные.

- **Приоритет:** Must
- **Критерий:** число полей вне согласованного состава в поставленной выгрузке = 0 (MOE BR-004); проверяется при приёмке и при каждом последующем изменении состава колонок.
- **traced from:** BR-004; ограничение `C-002`.

### FR-005. Ролевой охват выгрузки

Система должна ограничивать содержимое файла зоной ответственности инициатора: для роли HR-администратор - все сотрудники компании; для роли руководитель подразделения - сотрудники его подразделения и всех подчинённых ему подразделений по существующей иерархии.

- **Приоритет:** Must
- **Критерий:** 0 выгрузок, содержащих сотрудников вне зоны ответственности инициатора (MOE BR-005); проверяется на тестовой иерархии подразделений с несколькими уровнями вложенности до запуска (риск R-2) и выборочной сверкой журнала.
- **traced from:** BR-005; ограничение `C-001` (существующая ролевая модель, новая не проектируется).

### FR-006. Граница правила охвата - руководитель без подчинённых подразделений

Система должна для инициатора-руководителя без подчинённых подразделений ограничивать выгрузку составом только его собственного подразделения, без ошибки и без обходного случая в реализации.

- **Приоритет:** Must
- **Критерий:** покрывается тем же приёмочным набором, что и FR-005 (UC-5); выделено отдельным пунктом ввиду высокой вероятности и высокого влияния риска R-2 (неверная реализация иерархии).
- **traced from:** BR-005

### FR-007. Журнал выгрузок

Система должна для каждой попытки выгрузки, включая повторные подряд, создавать отдельную запись журнала, фиксирующую: инициатора (идентификатор и роль), момент времени, число выгруженных строк, применённые фильтры.

- **Приоритет:** Must
- **Критерий:** доля выгрузок с полной записью в журнале = 100% (MOE BR-006); запись доступна на горизонте 3 лет (см. `NFR-004`).
- **Открытый пункт:** входит ли значение строки поиска по ФИО в состав фиксируемых фильтров - не решено, см. Q-004 (перенесено, не домыслено).
- **traced from:** BR-006; допущение `A-003` (каждая попытка - отдельная запись).

### FR-008. Соответствие содержимого файла видимому срезу

Система должна включать в файл ровно тех сотрудников, которые отображаются на экране при применённых фильтрах инициатора, включая умолчание «только действующие сотрудники», если инициатор явно не изменил фильтр статуса.

- **Приоритет:** Must
- **Критерий:** 0 выгрузок с расхождением состава файла и ожидаемого среза (MOE BR-007).
- **traced from:** BR-007

### FR-009. Включение уволенных по явному действию

Система должна выгружать сотрудников со статусом «уволен» только тогда, когда инициатор явно переключил фильтр статуса на экране.

- **Приоритет:** Must (для факта «только по явному переключению»)
- **Открытый пункт:** глубина охвата уволенных (весь справочник или ограничение по дате увольнения) бизнес-решением не задана - см. Q-008 BRD. Требование сформулировано до границы известного; глубина не домыслена.
- **traced from:** BR-007

### FR-010. Отсутствующие значения полей сотрудника

Система должна представлять отсутствующее значение поля сотрудника (например, нет корпоративного email или даты приёма) пустым значением ячейки, не исключая строку сотрудника из выгрузки.

- **Приоритет:** Should (основано на допущении `A-002` BRD - постановщик случай не оговаривал)
- **traced from:** BR-001, BR-002 (через допущение `A-002`)

### FR-011. Пустая выборка

Система должна обрабатывать выборку, не содержащую ни одной строки после применения фильтров, без ошибки.

- **Приоритет:** Must (для «без ошибки»)
- **Открытый пункт:** точная форма файла в этом случае не решена - см. Q-002 BRD. Предложение (перенесено из BRD, не подтверждено): файл с заголовками колонок и нулём строк данных, чтобы «нет данных» отличалось от сбоя.
- **traced from:** BR-001, BR-007

## 2. Нефункциональные требования (NFR)

### NFR-001. Время готовности файла

Система должна формировать файл не дольше 10 секунд от запроса инициатора до готовности файла к передаче, на верхней границе объёма выборки (1200 строк).

- **Число:** <= 10 секунд при 1200 строках.
- **Приоритет:** Must (прямое ожидание постановщика).
- **traced from:** отсутствует в BRD - ни один `BR` пункт не называет. Источник: раздел 10 BRD, п. 1 (материал п. 8, п. 10). Находка гейта BRD `F-2`.

### NFR-002. Поддерживаемый объём данных

Система должна корректно (без потери строк, без отказа FR-001/FR-002 на границе) обрабатывать штат в диапазоне 400-1200 действующих сотрудников и одиночную выгрузку от 50 до 1200 строк.

- **Число:** диапазон 400-1200 сотрудников / 50-1200 строк на выгрузку.
- **Приоритет:** Should (контекстный параметр объёма, лежит в основании `NFR-001`; самостоятельным требованием постановщик не формулировал).
- **traced from:** отсутствует в BRD - ни один `BR` пункт не называет. Источник: раздел 10 BRD, п. 2 (материал п. 8). Находка гейта BRD `F-2`.

### NFR-003. Кодировка и разделитель CSV

Файл должен быть закодирован и структурирован так, чтобы кириллические символы корректно отображались, а значения корректно разбивались по столбцам при открытии в русскоязычной локали Excel и в Google Sheets. Конкретная кодировка и разделитель - решение реализации, не зафиксированы здесь (см. `dex-skill-requirement-quality`: требование задаёт результат, не диктует «как»).

- **Число неприменимо:** контракт бинарный (открывается корректно / не открывается), не пороговая величина. Критерий приёмки унаследован от MOE BR-003 (0 обращений «нечитаемо/не открывается» за 3 месяца) и риска R-3 (приёмка на реальных Excel и Google Sheets, не на машине разработчика).
- **Приоритет:** Must
- **traced from:** BR-003 (раздел 10 BRD, п. 3, назван явно как «техническое воплощение BR-003»).

### NFR-004. Срок хранения записи журнала

Записи журнала выгрузок должны оставаться доступными для проверки комплаенсом не менее 3 лет с момента выгрузки.

- **Число:** 3 года (36 месяцев).
- **Приоритет:** Must
- **traced from:** BR-006 (раздел 10 BRD, п. 4, «техническое воплощение BR-006»).

### NFR-005. Неудержание файла на сервере

Система не должна сохранять сгенерированный файл выгрузки ни в каком серверном хранилище (диск, БД, временный кэш, лог) дольше времени, необходимого для передачи файла в ответе инициатору.

- **Число:** 0 хранимых на сервере файлов выгрузки на момент проверки ИБ (MOE BR-008), проверка не реже раза в квартал.
- **Приоритет:** Must
- **traced from:** BR-008; ограничение `C-003`.

### NFR-006. Авторизация вызова экспорта

Система должна разрешать вызов функции экспорта только аутентифицированным пользователям с одной из двух ролей существующей ролевой модели админ-панели (HR-администратор, руководитель подразделения) и должна отклонять вызов от иной роли или неаутентифицированного пользователя.

- **Число:** 100% отклонённых попыток вызова вне двух названных ролей (проверяется на приёмке).
- **Приоритет:** Must
- **traced from:** BR-005; ограничение `C-001`.

Оси `dex-skill-nfr`, закрытые явным `n/a` (не молчанием):

- **Secrets management** - `n/a`: фича не вводит новых credentials/токенов, использует существующую сессию админ-панели.
- **Multi-tenant / tenant_id** - `n/a`: система однотенантная (одна компания), изоляции по tenant в этой фиче нет.
- **Data classification** - частично закрыто: категория данных PII зафиксирована составом полей (`FR-004`) и запретом хранения (`NFR-005`); явной метки уровня классификации (internal/PII) в системе - гэп, см. раздел 4.

## 7. Допущения этого набора

Всё, что добавлено сверх сказанного постановщиком и сверх BRD - на этом уровне:

- Актор всех `FR`/`NFR` - «система» (единая модальность «должна»), а не роль-инициатор, как в части `BR` BRD. Решение формы, не решение содержания.
- `NFR-003` сознательно не фиксирует конкретную кодировку/разделитель (например, UTF-8 BOM, `;`) - оставлено решением реализации, чтобы не диктовать «как» вместо «что» (ловушка `dex-skill-requirement-quality`, «Неадекватный уровень абстракции»).
- Терминология раздела 0 (инициатор/получатель) - решение этого узла, BRD не переписан.

## 8. Constraints и non-goals (сквозные, из BRD, без изменений)

**Constraints:**
- C-001. Ролевая модель админ-панели существует; новая не проектируется.
- C-002. Состав полей согласован с ИБ и в рамках фичи не пересматривается.
- C-003. Файл на сервере не хранится: отдаётся в ответ и не сохраняется.
- C-004. Явных технических ограничений (стек, платформа, сроки, бюджет) постановщик не передал - «нет данных».

**Non-goals:**
Планировщик и регулярная автоматическая отправка; форматы кроме CSV (xlsx, pdf); отправка файла на почту и любые каналы доставки кроме получения оператором; выгрузка из других разделов админ-панели; выгрузка зарплатных данных; интеграция с внешними системами-потребителями; проектирование новой ролевой модели; пересмотр состава полей; технический контроль обращения с файлом после выгрузки (DLP, водяные знаки) - остаточный риск принят явно.
