# User stories: экспорт списка сотрудников в CSV из админ-панели

> Нумерация `US` локальная. Корпус документации проекта недостижим (прогон вне проекта) -
> сверка с уже существующими stories/ADR проекта не проводилась (`unverifiable`).

Источник: `docs/requirements/employee-csv-export-system.md` (`FR-001`..`FR-014`, `NFR-001`..`NFR-007`,
`status: approved`). Материал использован целиком, включая находки обоих пройденных гейтов (BRD Phase 2,
требования системы Phase 3) - см. раздел «Допущения» и «Non-goals» ниже.

Разбиение на 5 историй по бизнес-правилам/workflow-шагам (splitting strategy: rules + workflow),
все historii Must-приоритета - единый MVP-объём, эпик не заводился (сам источник: «объём ниже
порога эпика», BRD раздел «Epics»).

## Порядок реализации (рекомендация, не жёсткая зависимость)

`US-1` (доступ) -> `US-2` (базовая генерация) -> `US-3` (уволенные) / `US-4` (guardrails) параллельно
-> `US-5` (журнал, тесно связана с `US-2` через `FR-005`: журнал - предусловие выдачи файла).
Каждая история тестируема изолированно при застабленном предусловии соседних (см. `Dependencies`).

## US-1: Доступ к выгрузке ограничен ролью HR / администратора кадров

**Story:** Как пользователь с ролью HR / администратора кадров, я хочу видеть и использовать действие
«Выгрузить в CSV» для списка сотрудников, чтобы получить данные для работы вне системы без обращения
к ИТ; и как владелец продукта/ответственный за ПДн, я хочу, чтобы пользователь без этой роли не мог
выполнить выгрузку никаким способом, чтобы право видеть строку на экране не превращалось в право унести
список файлом.

**Acceptance Criteria:**

- AC-1 (доступность действия): Given пользователь с ролью HR/администратора кадров открыл список
  сотрудников в админ-панели, When он ищет способ выгрузить список, Then действие «Выгрузить в CSV»
  видимо и доступно для запуска. `[FR-001]`
- AC-2 (запрет для чужой роли, любой способ вызова): Given пользователь без роли HR/администратора
  кадров, When он пытается выполнить операцию выгрузки любым способом - через интерфейс (элемент скрыт
  или недоступен) либо прямым вызовом операции в обход интерфейса, Then операция отклоняется и файл не
  выдаётся, независимо от способа вызова. `[FR-003]`
- AC-3 (проверка на сервере при каждом вызове, не только в интерфейсе): Given любой вызов операции
  выгрузки, When запрос достигает сервера, Then роль вызывающего пользователя проверяется на стороне
  сервера перед выполнением - проверка не полагается только на скрытие элемента интерфейса. `[NFR-003]`
- AC-4 (отзыв роли в открытой сессии): Given у пользователя была роль HR и открыта страница списка,
  When роль отозвана и пользователь повторно вызывает операцию выгрузки (в т.ч. без перезагрузки
  страницы), Then операция отклоняется - проверка роли выполняется заново при каждом вызове, а не
  один раз при открытии страницы. `[FR-003][NFR-003]`

**Technical Notes:** Расширение существующей RBAC-модели админ-панели (`NFR-003`) новой проверяемой
операцией; новых ролей и механизмов аутентификации работа не вводит (см. `NFR-003` источника, метод
Inspection). Server-side authorization check - на каждый вызов, включая нестандартные пути вызова
(не только основной UI-компонент). Данные о ролях и их назначении - существующий механизм панели,
вне scope этой работы.

**Definition of Done:** AC-1..AC-4 покрыты тестами (в т.ч. тест прямого вызова операции без роли);
security-ревью пути авторизации; UI-элемент скрыт для не-HR роли; серверная проверка независима от
клиентского скрытия (проверяется тестом с поддельным/модифицированным запросом).

**Story Points:** 3

**Priority:** Must

**Dependencies:** нет (базовая история, открывает остальные).

## US-2: HR получает CSV-файл, точно соответствующий видимому списку

**Story:** Как пользователь с ролью HR / администратора кадров, я хочу получить CSV-файл с составом
строк и полей, точно соответствующим тому, что я вижу на экране с учётом своих фильтров и сортировки,
в формате, который открывается в табличном редакторе без ручной починки, чтобы работать с данными вне
системы без искажений и без лишнего раскрытия.

**Acceptance Criteria:**

- AC-1 (состав полей - минимум, не шире): Given HR-пользователь запускает выгрузку, When файл
  сформирован, Then он содержит ровно 4 колонки - ФИО, должность, подразделение, рабочий email - и не
  содержит иных полей карточки сотрудника. `[FR-002]`
- AC-2 (состав строк = видимый набор, не шире и не уже): Given HR-пользователь применил фильтр F и
  видит N строк на экране, When он выгружает список, Then файл содержит ровно те N строк с теми же
  данными - не больше и не меньше. `[FR-006]`
- AC-3 (состав определяется на момент выгрузки, не на момент последней отрисовки экрана): Given
  данные сотрудника, видимого в текущем отфильтрованном наборе, изменились (или сотрудник перестал
  подпадать под фильтр) после отрисовки экрана, но до нажатия кнопки экспорта, When экспорт
  выполняется, Then файл отражает состояние на момент выполнения выгрузки, а не устаревший снимок
  экрана - буквальное чтение `FR-006` («на момент выгрузки»). `[FR-006]`
- AC-4 (значение поля содержит служебный символ разделителя, кавычку или перенос строки): Given
  значение одного из 4 полей содержит `;`, символ `"` или перенос строки, When значение попадает в
  файл, Then оно экранируется по стандартным правилам CSV-квотирования, так что состав колонок не
  ломается и данные не переносятся в соседнюю колонку. `[FR-002][FR-012][Assumption: стандартное
  CSV-квотирование (RFC 4180-подобное); источник не специфицирует escaping явно, но `FR-006` требует
  точного совпадения состава, а `FR-012` фиксирует `;` разделителем - без экранирования оба требования
  невыполнимы совместно на значении со служебным символом; цена ошибки низкая (искажение отображения),
  альтернативы у экранирования по сути нет]`
- AC-5 (значение поля начинается с символа-триггера формулы): Given значение одного из 4 полей
  начинается с `=`, `+`, `-` или `@` (например, часть названия подразделения), When значение попадает
  в файл, Then оно записывается так, чтобы табличный редактор получателя не интерпретировал его как
  формулу при открытии. `[NFR-008]` - расширение AC на гейте Phase 4 переведено в требование системы:
  защита от CSV/formula injection (OWASP) с ценой ошибки до высокой (исполнение постороннего кода у
  получателя) - это самостоятельное требование безопасности, а не деталь `FR-002`; в исходном наборе
  аспект отсутствовал (находка K-2).
- AC-6 (пропавшее значение поля не ломает файл): Given у сотрудника не заполнено одно из 4 полей
  (например, подразделение), When он попадает в выгрузку, Then соответствующая ячейка пуста, без
  плейсхолдера, и остальной состав колонок не нарушается. `[FR-002][Assumption: стандартная табличная
  конвенция для отсутствующего значения; источник не описывает этот случай, цена ошибки низкая]`
- AC-7 (кодировка и разделитель): Given файл сформирован, When он открывается в табличном редакторе,
  Then он кодирован UTF-8 с BOM, поля разделены `;`, кириллица не искажена. `[FR-012]`
- AC-8 (уникальность имени файла для двух выгрузок одного пользователя в один день): Given один
  пользователь выполняет вторую выгрузку в тот же день с другим фильтром, When обе выгрузки завершены,
  Then имена файлов различаются (метка времени с точностью до секунды) и один файл не перезаписывает
  другой у получателя. `[FR-009]`
- AC-9 (время отклика в пределах порога): Given объём выгрузки не превышает порогового значения
  (`NFR-001` = 2000 записей), When пользователь запускает выгрузку, Then файл доставлен не позднее чем
  за 5 секунд в 95% случаев (p95) при типовой нагрузке. `[NFR-002]` - значение 5с инженерный дефолт;
  платформенный SLA `unverifiable` (прогон вне проекта), подлежит замене при обнаружении такого SLA.
- AC-10 (отзывчивость списка на экране не деградирует): Given возможность выгрузки включена в
  админ-панели, When измеряется время отклика самого списка сотрудников на экране (без выгрузки), Then
  оно не хуже замера, сделанного до внедрения возможности. `[NFR-007]`
- AC-11 (сбой при получении данных для файла): Given список сотрудников для выгрузки не удаётся
  получить из-за сбоя инфраструктуры (независимо от журнала выгрузок, см. `US-5`), When пользователь
  запускает выгрузку, Then выгрузка прерывается без частичного или повреждённого файла, и пользователю
  сообщается, что выгрузка не выполнена. `[FR-006][Assumption: расширение принципа «нет частичной
  выдачи, есть явная причина», явно установленного источником для двух других видов сбоя (`FR-005` -
  сбой журнала, `FR-011` - превышение порога); распространение того же паттерна на сбой чтения данных
  - последовательное применение уже принятого в наборе решения, не новая политика; цена ошибки низкая]`

**Non-goal (внутри истории):** машинное потребление файла (стабильный контракт колонок, версия схемы) -
не входит, единственный потребитель - человек в табличном редакторе (non-goal системного уровня,
`FR` этого класса не заведено).

**Technical Notes:** Формирование файла - синхронная операция в рамках одного запроса; данные
читаются единым запросом на момент выполнения выгрузки (не переиспользуют состояние отрисованного
экрана - AC-3). CSV-квотирование и защита от formula injection - стандартные библиотечные механизмы
генерации CSV, не специфическое решение проекта. Классификация данных - PII для внутреннего
использования (`NFR-004`); дополнительное шифрование при передаче не требуется, поскольку передача за
периметр вне scope (non-goal BRD раздел 3) - `NFR-004` не порождает отдельного AC, закрыт структурно
составом полей (AC-1) и non-goal.

**Definition of Done:** AC-1..AC-11 покрыты тестами, включая значения со служебными символами,
формула-триггерами и пропущенными полями; нагрузочный прогон подтверждает `NFR-002`; замер
отзывчивости списка до/после подтверждает `NFR-007`; ревью на предмет CSV/formula injection.

**Story Points:** 5

**Priority:** Must

**Dependencies:** `US-1` (действие должно быть доступным для запуска генерации).

## US-3: Уволенные сотрудники включаются в выгрузку только по явному выбору и в пределах срока

**Story:** Как пользователь с ролью HR / администратора кадров, я хочу, чтобы по умолчанию в выгрузку
попадали только действующие сотрудники, а уволенные - только если я явно это выбрал, и чтобы данные
сотрудников, уволенных более 3 лет назад, не выгружались вообще, чтобы раскрытие данных бывших
работников не было побочным эффектом обычной выгрузки.

**Acceptance Criteria:**

- AC-1 (дефолт - только действующие): Given пользователь не включал опцию «включить уволенных», When
  он выгружает список, Then файл содержит только действующих сотрудников. `[FR-007]`
- AC-2 (явный выбор включает уволенных в пределах срока): Given пользователь явно включил опцию
  «включить уволенных» и в наборе есть сотрудник, уволенный 2 года назад, When выгрузка выполняется,
  Then этот сотрудник присутствует в файле наравне с действующими. `[FR-007][FR-008]`
- AC-3 (граница 3 года - исключение включительно): Given пользователь включил опцию «включить
  уволенных» и в наборе есть сотрудник, уволенный ровно 3 года назад (день в день) от даты выгрузки,
  When выгрузка выполняется, Then этот сотрудник исключён из файла. `[FR-008][Assumption: граница
  трактуется включительно - решение составителя требований, зафиксировано в источнике («Собственные
  решения», п.4); P-9 BRD не задаёт правило округления, цена ошибки незначительная]`
- AC-4 (за пределами границы - исключение всегда): Given сотрудник уволен 3 года и 1 день назад, When
  пользователь выгружает с включённой опцией «включить уволенных», Then сотрудник исключён из файла
  независимо от выбора пользователя. `[FR-008]`
- AC-5 (граница вычисляется на едином моменте выполнения, не «плывёт» во время генерации): Given
  выполняется одна выгрузка, When вычисляется 3-летняя граница для каждого сотрудника в наборе, Then
  граница вычисляется от единой точки времени - момента начала выполнения выгрузки (тот же момент,
  что и AC-3 `US-2`), а не пересчитывается заново по каждой строке во время формирования файла. `[FR-
  008][Assumption: прямое следствие AC-3 `US-2` (единый снимок на момент выполнения); отдельного
  решения не требует]`

**Non-goal (внутри истории):** глубина истории свыше 3 лет, автоматическое продление или сокращение
срока - вне scope; число 3 года - решение постановщика (P-9 BRD), уточняется без пересмотра требования.

**Technical Notes:** Признак занятости и дата увольнения - существующие поля карточки сотрудника
(BRD раздел 9, «Есть в системе»). Вычисление границы - на бэкенде, использует момент начала запроса
выгрузки (общий со снимком данных `US-2` AC-3), не текущее время клиента.

**Definition of Done:** AC-1..AC-5 покрыты тестами, включая точную границу (ровно 3 года) и день после
неё; тест дефолтного поведения без выбора опции.

**Story Points:** 3

**Priority:** Must

**Dependencies:** `US-2` (расширяет базовую генерацию файла бизнес-правилом отбора строк).

## US-4: Система защищает от пустой и от избыточной выгрузки

**Story:** Как пользователь с ролью HR / администратора кадров, я хочу заранее видеть, сколько строк
попадёт в файл, получать понятный сигнал, если выгружать нечего, и получать явный отказ с
рекомендацией сузить фильтр, если строк слишком много, чтобы не получать пустой или неожиданно
усечённый файл.

**Acceptance Criteria:**

- AC-1 (предпросмотр числа записей): Given пользователь применил фильтр(ы) к списку, When он готовится
  запустить выгрузку (до подтверждения), Then система показывает число записей, которые будут
  выгружены, соответствующее текущим применённым фильтрам. `[FR-014]`
- AC-2 (предпросмотр не скрывает превышение порога): Given применённый фильтр даёт 2001 запись
  (выше порога `NFR-001`), When пользователь видит предпросмотр, Then показано реальное число (2001),
  а не 0 и не заниженное значение - иначе предупредительная цель `FR-014` (раздел 14 BRD,
  «Предсказуемость объёма») не достигается. `[FR-014][Assumption: предпросмотр показывает фактический
  отфильтрованный счёт независимо от исхода самой попытки выгрузки; иначе теряется весь смысл
  заблаговременного предупреждения, ради которого `FR-014` введено; источник не уточняет это явно,
  цена ошибки при обратном толковании - высокая (guardrail теряет предупредительную функцию)]`
- AC-3 (пустой результат - явный сигнал, файл не формируется): Given применённый фильтр даёт 0
  сотрудников, When пользователь пытается выгрузить, Then система явно сообщает, что выгружать нечего,
  и не формирует пустой файл. `[FR-010]`
- AC-4 (превышение порога - полный отказ, не усечение): Given применённый фильтр даёт 2001 запись
  (порог `NFR-001` = 2000), When пользователь пытается выгрузить, Then выгрузка не выполняется ни
  частично, ни полностью; пользователю названа причина отказа и предложено сузить фильтр; усечённый
  файл не выдаётся. `[FR-011][NFR-001]`
- AC-5 (порог включителен): Given применённый фильтр даёт ровно 2000 записей, When пользователь
  выгружает, Then выгрузка выполняется полностью, отказа нет. `[NFR-001]`
- AC-6 (счёт для решения «отказ/выполнить» пересчитывается на момент выполнения, не берётся из
  устаревшего предпросмотра): Given предпросмотр показал число ниже или выше порога, но фактический
  отфильтрованный набор изменился к моменту нажатия кнопки экспорта (например, штат увеличился и
  пересёк порог), When выполняется сама выгрузка, Then решение «выполнить / отказать» принимается по
  счёту на момент выполнения (тот же принцип, что `US-2` AC-3), а не по значению из ранее показанного
  предпросмотра. `[FR-011][Assumption: согласованность с методологией `FR-006` («на момент выгрузки»,
  `US-2` AC-3); предпросмотр (`FR-014`) явно назван предварительным ("до выполнения выгрузки"), значит
  не может быть источником истины для самого решения; цена ошибки низкая - редкое дрейфующее пограничное
  состояние, разрешается безопасно (отказ либо успех по актуальному состоянию)]`

**Non-goal (внутри истории):** усечённая частичная выдача сверх порога - явный запрет источника
(`FR-011`); фоновая генерация для объёмов сверх порога - non-goal системного уровня (A-4 BRD).

**Technical Notes:** Предпросмотр (`FR-014`) и проверка порога (`FR-011`) используют общий механизм
подсчёта, применяемый к тому же фильтру, что и генерация файла `US-2`/`US-3`. Разница между
предпросмотром и финальной проверкой - только момент выполнения (AC-6).

**Definition of Done:** AC-1..AC-6 покрыты тестами, включая точную границу порога (2000 и 2001) и
пустой результат; UI-тексты отказа содержат причину и рекомендацию сузить фильтр.

**Story Points:** 5

**Priority:** Must

**Dependencies:** `US-2` (guardrails оборачивают тот же запуск генерации файла).

## US-5: Каждая выгрузка фиксируется в неизменяемом журнале, доступном не менее 6 месяцев

**Story:** Как ответственный за обработку персональных данных / служба безопасности, я хочу, чтобы
каждая выгрузка фиксировалась в журнале с автором, временем, числом записей и применённым фильтром, и
чтобы выгрузка, которую не удалось зафиксировать, не выполнялась, чтобы любой инцидент с выгруженным
файлом оставался расследуемым в течение как минимум 6 месяцев.

**Acceptance Criteria:**

- AC-1 (запись создаётся при успешной выгрузке): Given выгрузка успешно завершена, When операция
  закончена, Then создана запись журнала с автором (идентификатором пользователя), датой и временем,
  числом выгруженных записей и применённым фильтром. `[FR-004]`
- AC-2 (журнал - предусловие, а не следствие): Given запись в журнал не может быть создана (например,
  хранилище журнала недоступно), When пользователь запускает выгрузку, Then выгрузка не выполняется -
  файл не отдаётся - и пользователю сообщается причина отказа. `[FR-005]`
- AC-3 (сбой журнала не даёт частичного результата): Given сбой создания записи журнала происходит
  после того, как файл уже сформирован в памяти, When операция завершается, Then пользователь не
  получает файл ни в каком виде - атомарность операции «файл + журнал». `[FR-005]`
- AC-4 (журнал не хранит значения полей сотрудников): Given выгрузка завершена (успешно или отказом),
  When запись журнала просматривается, Then она не содержит значений полей выгруженных сотрудников
  (ФИО, должность, подразделение, email) - только метаданные операции. `[FR-013]`
- AC-5 (исключение - значения фильтра сохраняются как есть, даже если это ПДн): Given пользователь
  применил фильтр, содержащий персональное значение (например, часть фамилии), When создаётся запись
  журнала, Then значение фильтра сохраняется в записи как введено пользователем, даже если оно является
  персональными данными - решение постановщика на гейте требований системы (находка M-4, вариант (a)).
  `[FR-013]`
- AC-6 (без фильтра - явно зафиксировано отсутствие фильтра): Given пользователь не применял фильтр
  (выгружал полный видимый набор), When создаётся запись журнала, Then поле фильтра явно фиксирует
  отсутствие фильтра, а не остаётся неопределённым - иначе восстановимость выборки (`MOE BR-004`) не
  гарантируется для этого случая. `[FR-004][Assumption: явное значение "фильтр не применён" вместо
  null/пропуска поля; источник не описывает этот случай отдельно, но MOE `BR-004` («по обращению
  восстанавливаются автор, время, объём и фильтр») требует детерминированного значения для любого
  случая, включая отсутствие фильтра; цена ошибки низкая]`
- AC-7 (запись неизменяема через приложение): Given запись журнала создана, When любой пользователь
  приложения (включая автора записи) пытается отредактировать или удалить её средствами приложения,
  Then операция отклонена или недоступна - интерфейс редактирования/удаления записей журнала
  пользователям не предоставляется. `[NFR-005]`
- AC-8 (доступность записи не менее 6 месяцев): Given запись журнала создана, When к ней обращаются в
  течение 6 месяцев с момента создания (включая ровно 6-й месяц), Then запись доступна для чтения.
  `[NFR-006][Assumption: «не менее 6 месяцев» трактуется включительно на границе - запись доступна
  вплоть до 181-го дня и не удаляется раньше; источник не уточняет округление границы, по аналогии с
  собственным решением составителя для границы 3 лет (`US-3` AC-3); цена ошибки низкая]`
- AC-9 (защита от повторной отправки/двойного клика не создаёт дублирующую запись за одну выгрузку):
  Given пользователь дважды подряд инициирует одну и ту же выгрузку (например, двойной клик), When
  операция выполняется, Then создаётся ровно одна запись журнала и выдаётся ровно один файл на одно
  логическое действие пользователя - стандартная защита от повторной отправки. `[FR-004][Assumption:
  общепринятая инженерная защита от double-submit при операции с побочным эффектом (создание записи
  журнала + выдача файла); источник не описывает этот случай, альтернативы у защиты по сути нет
  (без неё число записей журнала не равно числу выполненных пользователем действий); цена ошибки
  низкая - лишняя идентичная запись журнала, не искажает MOE `BR-004`, но засоряет журнал]`

**Non-goals (внутри истории, из источника):**

- автоматическое удаление записей журнала по истечении 6 месяцев - не требуется; `NFR-006` задаёт
  только минимальный срок доступности, решение об удалении сверх срока - организационная процедура
  (non-goal `BR-008`, разрешение вопроса составителя 1);
- владелец журнала и регламент его просмотра - организационные, не системное поведение (non-goal
  `BR-008`);
- логирование отклонённых попыток выгрузки не-HR ролью (`US-1` AC-2) - явно не входит в эту работу,
  кандидат отдельной заявки по безопасности (разрешение вопроса составителя 2).

**Technical Notes:** Журнал - append-only на уровне операций, доступных пользователю приложения;
прямое администрирование хранилища вне scope требования (`NFR-005` источника: «на уровне доступных
пользователю операций»). Хранение фильтра - структурированное представление (поле+значение), не
свободный текст (собственное решение составителя требований, п.6 источника) - обеспечивает
восстановимость выборки для `MOE BR-004`. Доступ к записям журнала (включая ПДн в значениях фильтра)
наследует режим доступа владельца журнала - руководителя кадровой службы (P-10 BRD); управление этим
доступом - организационная процедура, не эта история.

**Definition of Done:** AC-1..AC-9 покрыты тестами, включая сбой хранилища журнала (журнал недоступен
-> файл не выдан), попытку редактирования/удаления записи, границу 6 месяцев; security-ревью состава
полей журнала (отсутствие значений полей сотрудников, кроме фильтра).

**Story Points:** 5

**Priority:** Must

**Dependencies:** тесно связана с `US-2`: `FR-005` делает создание записи журнала предусловием выдачи
файла - точка стыка контракта между историями.
