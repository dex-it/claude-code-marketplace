# Пользовательские истории: антифрод для SMS-регистрации

| | |
|---|---|
| Вход | FR-1 ... FR-22, NFR-1 ... NFR-13 (системный уровень; FR-19 ... FR-22 дописаны по находке гейта 3) |
| Акторы | настоящий пользователь, дежурный эксплуатации, владелец продукта |
| Стадия | `checked` (оба оракула прогнаны, гейт 3 закрыт) |
| Режим | `interactive` |

Порядок историй - по ценности с учётом одного жёсткого предшествования: US-1 (наблюдаемость)
раньше US-3 (лимиты), решение D-8 - иначе значения лимитов берутся из воздуха.

## Волна 1

### US-1. Видеть, куда уходят деньги и где стоит пользователь

**Как** владелец продукта, **я хочу** видеть расход на SMS, конверсию регистраций и время
прохождения регистрации в разбивке по сегментам и по исходу каждого барьера, **чтобы** отличать
эффект введённых мер от эффекта ухода атакующего и не смягчать защиту вслепую.

**Acceptance criteria**

- `[FR-13]` Given отправка выполнена When запрос прошёл барьеры Then событие содержит сегмент
  признаков запроса и исход каждого барьера (доказательство работы, лимит, задержка, видимый
  барьер) отдельным значением, а не общим «прошёл».
- `[FR-13]` Given запрос отклонён барьером When событие записано Then в нём указан **конкретный**
  барьер-причина; событие без причины считается дефектом наблюдаемости.
- `[FR-14]` Given регистрация завершена в штатном режиме When измерено время Then оно разложено по
  шагам (ввод номера -> отправка -> ввод кода), а не одним итогом.
- `[FR-13]` Given сегментов за интервал ноль (трафика нет) When открыт отчёт Then отображается
  «нет данных за интервал», не пустая страница и не нулевая конверсия.
- `[NFR-6]` Given событию 91 день When запущена очистка Then оно удалено; событию 89 дней - Then
  доступно.
- `[NFR-12]` Given месяц закрыт When посчитан SLI (успешные отправки / запросы, прошедшие барьеры)
  Then значение доступно как метрика для сверки с SLO 99.5%.
- `[NFR-9]` Given событие содержит номер телефона When оно попало в журнал, метрику или сегмент
  Then номер представлен необратимым преобразованием; сырой номер в этих артефактах не встречается.

**Technical notes.** Точка записи - контур отправки; сегмент вычисляется до применения барьеров,
исход - после каждого. Разложение времени требует сквозного идентификатора попытки регистрации,
живущего до ввода кода.

**DoD.** События пишутся, отчёт открывается, очистка по сроку прогоняется на данных старше 90
дней. Story points: 5. Priority: Must.

### US-2. Зарегистрироваться, не заметив защиты

**Как** настоящий пользователь, **я хочу** ввести номер и получить код как раньше, **чтобы**
защита от злоупотреблений не превращалась в мою проблему.

**Acceptance criteria**

- `[FR-1]` Given клиент предъявил валидное доказательство работы When запрос принят Then SMS
  отправлена.
- `[FR-2]` Given доказательство работы отсутствует или невалидно When запрос принят Then SMS не
  отправляется, а ответ **не различает** случаи «номер известен» и «номер неизвестен».
- `[FR-19]` Given доказательство работы просрочено (выдано за пределами срока жизни челленджа)
  When запрос принят Then он отклонён как невалидный, а не принят «по старой памяти».
- `[FR-19]` Given одно и то же доказательство работы предъявлено дважды When приходит второй запрос
  Then он отклонён: повторное использование решённого челленджа не даёт бесплатной отправки.
- `[NFR-1]` Given типовой клиент When решается доказательство работы Then p95 времени решения - не
  более 1.5 с, p99 серверной проверки - не более 5 мс.
- `[NFR-13]` Given штатный режим When измерена добавка антифрода ко времени ответа эндпоинта
  Then она не превышает 50 мс (p99), не считая времени решения на клиенте.
- `[NFR-11]` Given ключ подписи челленджа ротируется When ротация идёт Then эндпоинт продолжает
  принимать челленджи, подписанные прежним ключом, до истечения их срока жизни.

**Technical notes.** Челлендж подписывается серверным ключом из секрет-хранилища (NFR-11); срок
жизни челленджа задаёт окно replay-защиты. Проверка - до любых обращений к провайдеру SMS.

**DoD.** Замеры p95/p99 сняты на типовом клиенте, replay и просрочка покрыты тестами. Story
points: 5. Priority: Must.

### US-3. Не дать оплатить массовость

**Как** владелец продукта, **я хочу** ограничить число и темп отправок по нескольким независимым
осям, **чтобы** кампания из тысяч запросов упиралась в потолок расхода, а не в мой бюджет.

**Acceptance criteria**

- `[FR-4]` Given лимиты заданы по четырём осям (адрес источника, номер получателя, сессия,
  отпечаток клиента) When запрос обрабатывается Then превышение по каждой оси оценивается
  независимо от остальных.
- `[FR-5]` Given запрос превысил лимит хотя бы по одной оси When он обработан Then SMS не
  отправляется - **независимо** от состояния нарастающей задержки US-4 (решение D-3: лимит старше
  задержки).
- `[FR-4]` Given два запроса по одному номеру пришли одновременно и остаток лимита равен единице
  When оба обработаны Then отправка выполнена ровно одна: счётчик изменяется атомарно, «оба
  прошли проверку до записи» недопустимо.
- `[FR-4]` Given значение счётчика ровно равно лимиту When приходит следующий запрос Then он
  отклонён (граница закрыта сверху, а не «строго больше»).
- `[NFR-2]` Given данных FR-13 ещё нет When выставляются начальные значения Then они заведомо
  широкие и хранятся в конфигурации, а не в коде.
- `[NFR-2]` Given данные FR-13 накоплены When значения пересматриваются Then они выводятся из
  перцентилей наблюдаемого трафика (решение D-8).

**Technical notes.** Хранилище счётчиков - общее для экземпляров сервиса, иначе лимит делится на
число реплик молча. Атомарность обязательна на уровне хранилища, не на уровне приложения.

**DoD.** Гонка воспроизведена тестом, счётчики переживают перезапуск экземпляра. Story points: 8.
Priority: Must.

### US-4. Повторить, но не бесконечно

**Как** настоящий пользователь, **я хочу** повторить отправку, если код не пришёл, **чтобы**
разовый сбой доставки не отнимал у меня регистрацию.

**Acceptance criteria**

- `[FR-6]` Given на номер уже была отправка When приходит повтор внутри окна наблюдения Then он
  выполняется после задержки, а задержка при каждой следующей попытке больше предыдущей.
- `[NFR-3]` Given первая попытка выполнена When пользователь повторяет Then повтор доступен не
  позднее чем через 60 с; потолок задержки - 15 мин.
- `[FR-7]`, `[NFR-3]` Given попыток по номеру не было 1 ч When приходит новая Then счётчик задержки
  сброшен и задержка начинается с минимальной - без действия человека.
- `[FR-6]` Given задержка активна When пользователь шлёт повтор Then ответ сообщает **оставшееся
  время**, а не «попробуйте позже» без числа.
- `[FR-6]` Given номер под задержкой и одновременно превысил лимит US-3 When приходит запрос
  Then он отклонён по лимиту (D-3), и сообщение соответствует отказу, а не ожиданию.

**Technical notes.** Окно наблюдения и потолок - конфигурация (NFR-3, допущение A-6). Сброс -
истечением записи, не фоновой задачей: фоновая задача не отработала = ограничение вечное.

**DoD.** Сброс проверен на истечении окна, взаимодействие с лимитом покрыто тестом. Story points:
5. Priority: Must.

### US-5. Пройти барьер, если автоматическая проверка недоступна мне

**Как** настоящий пользователь на среде без поддержки доказательства работы, **я хочу**
подтвердить, что я человек, **чтобы** не остаться без регистрации из-за своего браузера.

**Acceptance criteria**

- `[FR-3]`, `[FR-8]` Given клиент не может выполнить доказательство работы When он запрашивает
  отправку Then он получает видимый барьер, и при его прохождении SMS отправляется.
- `[FR-8]` Given барьер не пройден When пользователь повторяет Then предъявляется новый барьер, а
  прежний результат не переиспользуется.
- `[FR-20]` Given барьер пройден When тот же результат предъявлен повторно Then он отклонён
  (одноразовость подтверждения).
- `[FR-3]` Given барьер пройден When выполняется отправка Then лимиты US-3 применяются к запросу
  как обычно: прохождение барьера не выводит запрос из-под лимитов.
- `[FR-8]`, `[Assumption A-8]` Given поставщик барьера недоступен When клиент не может выполнить
  доказательство работы Then отправка выполняется без барьера, а факт фиксируется как деградация
  (перенос решения D-6 на этот компонент - см. «Допущения»).

**Technical notes.** Волна 1 применяет барьер по единственному детерминированному условию (клиент
не выполнил доказательство работы). Применение по правилу подозрения - US-9, волна 2.

**DoD.** Ветка без поддержки доказательства работы проверена на реальной среде-примере. Story
points: 5. Priority: Must.

### US-6. Остановить отток за минуты

**Как** дежурный эксплуатации, **я хочу** включить аварийный режим одной операцией и так же снять
его, **чтобы** останавливать отток без согласования в момент инцидента.

**Acceptance criteria**

- `[FR-10]` Given порог превышен When дежурный включает аварийный режим Then применяется
  ужесточённый профиль лимитов и барьер применяется шире.
- `[NFR-5]` Given операция выполнена When измерено время до вступления режима в силу Then оно не
  превышает 60 с.
- `[FR-12]` Given режим включён и операция снятия не выполнена When истёк таймаут режима Then режим
  снят автоматически и восстановлен штатный профиль.
- `[FR-12]` Given режим снят When приходит запрос Then применяется штатный профиль, а ограничения,
  наложенные в аварийном режиме, доживают только до своего срока (US-7).
- `[FR-22]` Given два дежурных выполняют операцию одновременно When обе обработаны Then итоговое
  состояние режима определено и совпадает у всех экземпляров сервиса; расхождение между экземплярами
  недопустимо.
- `[NFR-10]` Given операцию выполняет сторона без роли дежурного When она отправлена Then операция
  отклонена.
- `[NFR-8]` Given режим переключён When записан журнал Then в нём есть кто, когда, прежнее и новое
  состояние.

**Technical notes.** Таймаут режима - страховка от «включил и ушёл»: без него аварийный режим
переживает инцидент и режет конверсию молча.

**DoD.** Автоснятие проверено по таймауту, разграничение ролей - негативным тестом. Story points:
5. Priority: Must.

### US-7. Не остаться заблокированным навсегда

**Как** настоящий пользователь, попавший под ограничение по ошибке, **я хочу**, чтобы ограничение
снялось само, **чтобы** ложное срабатывание стоило мне ожидания, а не регистрации.

**Acceptance criteria**

- `[FR-15]` Given наложено любое ограничение (лимит, задержка, режим) When истёк его срок Then оно
  снято без действия человека.
- `[FR-15]` Given срок ограничения истёк When пользователь повторяет попытку Then она
  обрабатывается штатно, без обращения в поддержку и без ручного разблокирования.
- `[FR-15]` Given процесс фоновой очистки не работает When срок ограничения истёк Then ограничение
  всё равно не применяется: срок проверяется при обращении, а не только фоновой уборкой.

**Technical notes.** Требование запрещает вечные записи в любом хранилище состояния антифрода -
включая счётчики US-3 и задержки US-4.

**DoD.** Ветка «фоновая очистка остановлена» покрыта тестом. Story points: 3. Priority: Must.

### US-8. Узнать о проблеме раньше, чем из счёта провайдера

**Как** дежурный эксплуатации, **я хочу** получать уведомление при превышении порога и при отказе
самого антифрода, **чтобы** реагировать по сигналу, а не по факту списанных денег.

**Acceptance criteria**

- `[FR-11]` Given расход или темп превысил утверждённый порог When превышение зафиксировано Then
  дежурный уведомлён.
- `[FR-11]` Given порог задан в конфигурации владельцем продукта до выкатки When значение не задано
  Then сервис не стартует с пустым порогом молча, а сообщает о незаданном значении.
- `[FR-18]` Given компонент антифрода недоступен (проверка доказательства работы, счётчики,
  источник конфигурации) When приходит запрос на отправку Then SMS отправляется без проверки
  (решение D-6, fail-open).
- `[FR-18]` Given идёт деградация When она началась Then дежурный уведомлён тем же каналом, что и о
  превышении порога, а длительность окна деградации видна в наблюдаемости US-1.
- `[FR-18]` Given деградация закончилась When компонент снова доступен Then проверки применяются
  без ручного вмешательства.

**Technical notes.** Fail-open делает недоступность антифрода целью атаки - поэтому сигнал здесь
не удобство, а условие принятого решения.

**DoD.** Деградация воспроизведена отключением зависимости, уведомление доставлено. Story points:
5. Priority: Must.

## Волна 2

### US-9. Требовать подтверждения только у подозрительных

**Как** владелец продукта, **я хочу**, чтобы видимый барьер применялся адресно по правилу
подозрения, **чтобы** защита не стоила конверсии у настоящих пользователей.

**Acceptance criteria**

- `[FR-9]` Given правило подозрения задано конфигурацией When обрабатывается запрос Then решение
  вычисляется из признаков запроса и данных наблюдаемости US-1.
- `[FR-8]` Given запрос подпадает под правило When он обработан Then предъявляется видимый барьер;
  прохождение человеком приводит к отправке.
- `[FR-9]` Given правило изменено When изменение применено Then новое поведение действует без
  выкладки кода (US-10).
- `[NFR-4]` Given барьер применяется по правилу When измерена доля настоящих пользователей,
  получивших барьер Then она видна в наблюдаемости US-1. **Пороговое значение доли - открытый
  вопрос Q-3 источника**: критерий приёмки задаётся владельцем продукта по накопленным данным, до
  этого числом не задан.

**Technical notes.** Правило строится на подделываемых признаках, поэтому даёт ошибки обеих сторон
по построению; смысл наблюдаемости здесь - измерить цену ошибки, а не устранить её.

**DoD.** Доля пользователей под барьером видна в отчёте. Story points: 8. Priority: Should.

### US-10. Менять пороги без релиза и откатывать ошибку

**Как** владелец продукта, **я хочу** менять пороги и правила без выкладки кода и откатывать
изменение одной операцией, **чтобы** гонка с адаптирующимся атакующим не упиралась в цикл релиза.

**Acceptance criteria**

- `[FR-16]` Given значение изменено в конфигурации When изменение применено Then новое поведение
  действует без выкладки кода.
- `[NFR-7]` Given изменение применено When измерено время до вступления в силу Then оно не
  превышает 60 с.
- `[FR-17]` Given изменение оказалось ошибочным When выполнен откат Then действует предыдущее
  значение, и откат - одна операция.
- `[FR-21]` Given значение в конфигурации некорректно (не число, вне допустимого диапазона) When
  оно применяется Then оно отклонено, а действует прежнее; сервис не остаётся без лимитов.
- `[FR-16]` Given источник конфигурации недоступен When приходит запрос Then действуют последние
  успешно применённые значения (кэш), а недоступность источника фиксируется как деградация US-8 -
  не как «лимитов нет».
- `[NFR-10]` Given конфигурацию меняет сторона без роли владельца продукта When операция отправлена
  Then она отклонена.
- `[NFR-8]` Given конфигурация изменена When записан журнал Then в нём есть кто, когда, прежнее и
  новое значение.

**Technical notes.** Ветка «источник недоступен» разведена с fail-open US-8 намеренно: отсутствие
свежей конфигурации не равно отсутствию антифрода, и деградировать до «без лимитов» здесь не
нужно.

**DoD.** Откат проверен, некорректное значение отклонено, работа на кэше проверена отключением
источника. Story points: 8. Priority: Should.
