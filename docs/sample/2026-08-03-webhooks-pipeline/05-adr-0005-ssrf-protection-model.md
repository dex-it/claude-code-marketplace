# ADR-0005: Модель защиты от обращения во внутренние диапазоны

## Status

Proposed

## Date

2026-08-03

## Decision Drivers

- `FR-011`: платформа обязана отклонять адреса подписки, разрешающиеся во внутренние или частные
  диапазоны сети, как часть валидации адреса.
- `SW-3` (находка зоны 1, перенесённая ограничением в дизайн): проверка, выполненная единожды при
  создании подписки, не закрывает разрыв между проверкой и использованием - DNS-запись может измениться
  между проверкой и моментом отправки (DNS rebinding), а следование редиректу способно увести
  соединение за пределы уже проверенного адреса.
- Адрес получателя - явно недоверенный ввод (`BR-009`, обоснование).
- `NFR-009`: создание и верификация подписок обязаны быть ограничены по частоте, чтобы сам механизм
  доставки не стал средством сканирования или усиления атаки на произвольные адреса.

## Context

Адрес конечной точки подписки задаётся интегратором и позже используется платформой для исходящих
HTTP-запросов; это недоверенный ввод, способный указывать на внутреннюю инфраструктуру платформы -
напрямую, посредством изменения DNS-записи между проверкой и использованием, либо посредством
редиректа, возвращённого иначе валидным адресом. Требуется модель защиты, охватывающая весь жизненный
цикл адреса, а не только момент его создания.

## Decision

Защита в четырёх слоях уровня приложения плюс пятый слой на уровне сети; ни один слой не считается
достаточным в одиночку:

1. **Валидация формы.** Допускается только схема `https`, только доменное имя или публичный
   IP-литерал; встроенная в URL пользовательская часть и нестандартные схемы отклоняются.
2. **Проверка резолва при создании и при верификации владения.** Все адреса, полученные разрешением
   имени, проверяются против перечня внутренних и зарезервированных диапазонов (loopback, частные
   диапазоны, link-local включая адрес метаданных облачной инфраструктуры, carrier-grade NAT,
   multicast, IPv4-в-IPv6, уникальные локальные IPv6-адреса).
3. **Повторная проверка на момент каждой попытки отправки с пином соединения на проверенный адрес.**
   Резолв повторяется непосредственно перед каждой попыткой, проверяется заново, и соединение
   устанавливается к уже проверенному адресу (с сохранением исходного имени для указания имени сервера
   при TLS-согласовании и заголовка узла). Проверить адрес и затем "просто подключиться по имени" не
   является защитой: между проверкой и соединением разрешение имени способно вернуть другой адрес.
4. **Редиректы не выполняются.** Ответ с кодом переадресации считается неуспешной попыткой доставки.
   Следование редиректу обнуляет действие всех трёх слоёв выше, отдавая выбор конечного адреса ответу,
   который платформа иначе не проверяет.
5. **Сетевая политика вне приложения.** Исходящий трафик процесса доставки ограничен на сетевом уровне
   запретом внутренних диапазонов - рубеж на случай дефекта в любом из четырёх слоёв выше.

## Consequences

### Positive

- Защита остаётся действенной даже при дефекте в одном отдельно взятом слое, поскольку ни один слой не
  является единственным источником доверия.
- DNS rebinding и отложенное изменение адреса закрываются структурно, а не политикой или процедурой
  ручной проверки.

### Negative

- Получатели, полагающиеся на HTTP-редирект (например, при миграции конечной точки), и получатели без
  поддержки HTTPS не поддерживаются.
- Интеграторы за адресами carrier-grade NAT отклоняются наравне с внутренними, даже когда конкретный
  адрес не является внутренним для платформы.

### Risks

- Перечень зарезервированных диапазонов обязан поддерживаться в актуальном состоянии по мере
  перераспределения адресного пространства регистраторами; устаревший перечень заново открывает ровно
  тот класс разрыва, который это решение закрывает. Это эксплуатационный риск сопровождения, а не
  разовая цена проектирования.

## Alternatives Considered

### Проверка резолва только при создании подписки

Единственная проверка адреса в момент заведения подписки, без повторной проверки перед отправкой.

- **Pros:** простейший и наименее затратный вариант.
- **Cons:** не закрывает разрыв, названный `SW-3`: DNS-запись может быть перенаправлена на внутренний
  адрес после прохождения проверки, и каждая последующая попытка доставки будет использовать уже
  вредоносное разрешение имени.
- **Why rejected:** оставляет ровно ту атаку, для закрытия которой заводится эта защита.

### Повторная проверка резолва перед каждой попыткой, но соединение по имени

Резолв повторяется и проверяется перед каждой попыткой, но соединение всё равно устанавливается по
доменному имени, а не к уже проверенному адресу.

- **Pros:** проще пина соединения, всё же добавляет проверку на каждую попытку.
- **Cons:** повторное разрешение имени, выполняемое самим соединением, может отличаться от только что
  проверенного - тот же разрыв между проверкой и использованием, лишь сокращённый до миллисекунд вместо
  всего срока жизни подписки.
- **Why rejected:** только пин соединения к уже проверенному адресу делает проверку и использование
  атомарными; проверка без пина оставляет зазор, пусть и меньший.

### Следование редиректам с проверкой каждого перехода

Редиректы выполняются, но каждый промежуточный адрес прогоняется через тот же перечень запрещённых
диапазонов.

- **Pros:** сохраняет совместимость с получателями, использующими редирект по операционным причинам.
- **Cons:** заново вводит тот же класс разрыва другим путём и умножает число проверок (а с ним - шанс
  ошибиться в одной из них) вместо устранения риска.
- **Why rejected:** отклонено в пользу более простого и доказуемо замкнутого правила - редиректы не
  выполняются вовсе.
