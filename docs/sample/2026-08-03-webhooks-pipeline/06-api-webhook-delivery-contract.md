## 1. Приёмка входа (отдельно от качества артефактов)

Журнал решений (`docs/brd/webhooks-decision-log.md`, 1069 строк на момент чтения) достижим,
`P-01..P-37`, `AR-01..AR-24`, `AW-01..AW-04` на месте. Отдельного handoff-файла от `architect`/`adr-writer`
к `api-designer` не заводилось - design doc раздел 10 сам служит носителем задания (то же основание, что
у `adr-writer`, журнал, раздел «Приёмка входа зоны 2 узлом `adr-writer`»).

Комплектность: раздел 8.1 design doc называет для этого контракта транспорт, состав тела, метаданные
доставки, семантику ответа, запрет на носитель раскрытия, версионирование - все пункты присутствуют.
Раздел 10 адресует `api-designer` детальную спецификацию обеих внешних поверхностей. Пробелов не найдено.

**Расхождение, найденное приёмкой (не находка к design, разрешено здесь как своё решение, `AD-10`).**
Однострочный гейт задания перечисляет «перечни недоставленного и пропущенного» единым списком под
управляющим API, тогда как design doc 8.1 (таблица модулей) относит недоставленное и ручную переотправку

проведена нормативно, `FR-006` дословно адресован «эксплуатации», `FR-007`/`FR-013` разведены постановщиком
по сторонам явно, П-27/BA-31). Разрешено в пользу design doc: недоставленное и ручная переотправка не входят

- см. `AD-10` там же.

Порог входа: `quality-checks` по типу `design` в пакете нет - его ставит судья зоны 2, не вызванный на

используется как принятый вход с design-специфичными допущениями (раздел 13 design doc), перенесёнными

## 2. Транспорт

- Метод: `POST`.
- Схема: только `https` (ADR-0005). Иные схемы не поддерживаются.
- `Content-Type: application/json; charset=utf-8` на запросе платформы к получателю.
- Редиректы (`3xx`) не выполняются - засчитываются неуспешной попыткой (ADR-0005, раздел «Decision», п.4).
- Соединение устанавливается к адресу, прошедшему повторную проверку и пин на момент попытки (ADR-0005);
  получатель этого не наблюдает - это обязанность платформы, не часть контракта, которую реализует получатель.

## 3. Тело оповещения

Ровно пять полей активной версии схемы (`FR-002`, P-02/P-26/`BR-008`). Список закрыт **на активную
версию**; нижняя граница (непустой `event_id`) версионно-независима (design, раздел 8.1). Дополнительные
поля в теле не допускаются - `additionalProperties: false`.

| Поле | Тип | Формат | Обязательность | Смысл |
|---|---|---|---|---|
| `event_id` | string | UUID (`format: uuid`) | required | идентификатор события; ключ идемпотентности получателя (П-1) |
| `event_type` | string | `minLength: 1`, точечная нотация домена (пример: `order.created`) | required | тип события, определяет применимость подписки |
| `entity_id` | string | `minLength: 1`, опаковый идентификатор сущности-источника | required | ссылка на сущность для дочитывания подробностей через API продукта (P-02) |
| `occurred_at` | string | `format: date-time` (RFC 3339 §5.6, JSON Schema 2020-12 vocabulary) | required | момент наступления события, не момент отправки |
| `schema_version` | integer | `minimum: 1` | required | версия контракта доставки, которой соответствует и тело, и метаданные (P-29) |

**JSON Schema (версия 1, `$id` = `https://.../schemas/webhook-event.v1.schema.json` - пример пути, домен
назначается при выпуске):**

```json
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "$id": "webhook-event.v1.schema.json",
  "title": "WebhookEventV1",
  "type": "object",
  "additionalProperties": false,
  "required": ["event_id", "event_type", "entity_id", "occurred_at", "schema_version"],
  "properties": {
    "event_id": { "type": "string", "format": "uuid" },
    "event_type": { "type": "string", "minLength": 1 },
    "entity_id": { "type": "string", "minLength": 1 },
    "occurred_at": { "type": "string", "format": "date-time" },
    "schema_version": { "type": "integer", "minimum": 1, "const": 1 }
  }
}
```

Примечание к `format`: JSON Schema 2020-12 не включает вокабулярий `format-assertion` в дефолтный диалект
- `format` здесь аннотация для генераторов кода и человека, а не гарантированная рантайм-валидация;
контрактный тест (design, `FR-002` verification) обязан проверять форму значений отдельно от схемы.
Верификация ключевых слов сверена: `format: date-time` определён по RFC 3339 §5.6 (JSON Schema 2020-12
Validation, раздел «Defined Formats») - **verified**, WebFetch/WebSearch, 2026-08-03.

**Запрет носителя (П-10, P-28).** Ни одно поле тела не расширяется сведениями об интеграторе или подписке
сверх пяти перечисленных - это не «удобное дополнительное поле», а нарушение верхней границы `FR-002`.

**AD-13 (решение этого документа).** Тип `schema_version` - положительное целое число, монотонно растущее
с каждым несовместимым выпуском (design использует нумерацию v1/v2 как порядковую). Отклонена альтернатива
- строка произвольного формата (semver-подобная): design и ADR-0006 говорят о «номере версии» как о едином
счётчике контракта целиком, semver-подобное дробление (major.minor) подразумевало бы совместимость по
дробной части, что прямо противоречит P-29 (один номер = один неделимый контракт).

## 4. Метаданные доставки (заголовки)

Только заголовки; ни один не несёт сведений о событии, сущности или интеграторе (П-10, P-28, design 8.1
«запрет»). Заголовки вида `X-Event-Type`, `X-Entity-Id`, `X-Subscription-Name` не вводятся.

| Заголовок | Формат | Смысл |
|---|---|---|
| `Webhook-Delivery-Id` | UUID, уникален **на попытку** (`AR-09`), не на пару (событие, подписка) | различение штатного повтора и воспроизведения (`FR-012`); входит в каноническую строку подписи |
| `Webhook-Signature` | `v1,keyid=<secret_id>,t=<unix>,sig=<hex>` (ADR-0004, `AR-08`); при активном окне перекрытия секрета либо периоде сосуществования механизмов - заголовок повторяется по одному вхождению на каждый действительный ключ | признак подлинности; получателю достаточно валидности одного вхождения |

**AD-01 (решение этого документа).** Отдельного заголовка-метки времени нет: временная метка уже несётся
внутри `Webhook-Signature` (`t=<unix>`) и одновременно входит в каноническую строку подписи (раздел 5) -
дублирующий заголовок дал бы два источника истины об одном значении с риском расхождения. Design doc 8.1
перечисляет «метку времени доставки» как категорию метаданных, а не как отдельное имя заголовка - категория
закрыта присутствием значения в `Webhook-Signature`, вторая независимая величина в контракте не заведена.

**AD-02 (решение этого документа).** Множественность подписи (окно перекрытия секрета 24 ч, `FR-009`;
период сосуществования механизмов при экстренном выпуске, P-30) выражена **повторением заголовка**
`Webhook-Signature` - по HTTP-семантике поля со списочным значением повторное вхождение эквивалентно
объединению через запятую (RFC 9110 §5.3, «Field Order», verified WebSearch 2026-08-03); получатель
перебирает все вхождения и принимает доставку, если валидно хотя бы одно. Отклонена альтернатива - JSON-
массив подписей внутри одного заголовка: усложняет парсинг без выигрыша, при этом сам формат значения
(`v1,keyid=...`) уже фиксирован ADR-0004 и не переоткрывается.

Заголовки называются в формате `Train-Case` без префикса `X-` (RFC 6648, «Deprecating the "X-" Prefix and
Similar Constructs in Application Protocols» - устоявшаяся практика, не проверялась отдельным запросом
в этой сессии, риск версийного дрейфа отсутствует).

## 5. Подпись и верификация (алгоритм)

Механизм зафиксирован ADR-0004/`AR-08`, здесь - точная процедура для получателя, не переоткрытие решения.

**Каноническая строка** (design, раздел 8.7): `timestamp . LF . delivery_id . LF . raw_body`, где:

- `timestamp` - значение `t=` из `Webhook-Signature`, как есть (десятичная строка unix-секунд, не число);
- `delivery_id` - значение заголовка `Webhook-Delivery-Id`, как есть;
- `raw_body` - необработанные байты тела запроса **до** разбора JSON (design, раздел 8.7: «тело
  подписывается в сыром виде... не пересериализованное представление»).
- `LF` - единственный байт `0x0A`.

**Проверка получателем:**

1. Разобрать все вхождения `Webhook-Signature`; для каждого извлечь `keyid`, `t`, `sig`.
2. Проверить давность `t` относительно локальных часов получателя в пределах допустимого окна
   (рекомендуемое значение - 5 мин, объявляется документацией `FR-014`, платформой не навязывается - design,
   раздел 8.7). Значение старше окна - отвергнуть как воспроизведение либо задержку сети.
3. Для каждого известного получателю секрета, соответствующего `keyid`, вычислить HMAC-SHA256 канонической
   строки и сравнить с `sig` (константное по времени сравнение - стандартная практика против timing-атаки,
   не отдельно проверялась в этой сессии - общеизвестная практика реализации HMAC-сравнения).
4. Доставка подлинна, если хотя бы одно вхождение прошло проверки 2-3.

**Обязанность синхронизации часов** - эксплуатационное требование платформы (design, раздел 8.7): без NTP
рекомендация в 5 минут даёт ложные отвержения.

## 6. Семантика ответа и повторов, видимая получателю

- Успех - **только** `2xx`. Любой иной код, таймаут ответа, отказ установления соединения - неуспех (П-6,
  три категории исхода `NFR-011`: `http_status`/`response_timeout`/`connect_error`).
- `3xx` не считается успехом и не порождает переход по ссылке - неуспешная попытка (раздел 2).
- Гарантия: at-least-once, без гарантии порядка (P-01, `non-goals`). Не менее 8 попыток за 24-часовое окно
  с неубывающим интервалом (`NFR-003`); текущая конфигурация платформы - 9 попыток, интервалы 1м/5м/15м/
  45м/2ч/4ч/6ч/8ч с ограниченным джиттером (design, `AR-04`) - **не часть контракта версии**, эксплуатационный
  параметр, может измениться без выпуска новой версии схемы, поскольку не входит в объём P-29 (тело и
  метаданные, не расписание).
- Таймауты платформы на попытку (соединение <= 3 с, полный ответ <= 10 с) - текущая конфигурация (design,
  `X-6`/`AR-24`), не гарантия контракта; получатель, отвечающий дольше, наблюдается как таймаут.
- Исчерпание окна без успеха - `undelivered`; интегратор восстанавливает его через недоставленное только
  эксплуатацией (не входит в этот контракт, см. раздел 10 `subscription-management-api.md`).
- Ручная переотправка (`FR-007`, ops-инициируемая) наблюдается получателем как штатный повтор того же
  `event_id` с новым `Webhook-Delivery-Id` - неотличима от автоматического повтора на стороне получателя,
  что и требуется идемпотентностью по `event_id`.

## 8. Версионирование контракта доставки - первая из двух независимых осей

**Единица версионирования - контракт целиком**: тело, набор заголовков метаданных, способ вычисления
признака подлинности (P-29, ADR-0006, `AR-13`). Одно число `schema_version`, не переиздаётся частично.

- Подписка закрепляет версию при создании (`subscription-management-api.md`, ресурс `Subscription`).
  Платформа обслуживает N версий одновременно; переход - явное действие интегратора через управляющий API,
  не автопереключение.
- **Аддитивное изменение** (новый `event_type`, новое поле тела, новый элемент метаданных) - совместимо,
  в текущей версии, существующие получатели не меняют код (`FR-018`).
- **Несовместимое изменение** (переименование/изъятие поля, смена способа вычисления подписи) - новая
  версия, одна из двух ветвей уведомления:
  - **Плановая** (`FR-019` а): дата прекращения >= дата объявления + 90 суток (П-11), уведомление всем
    подписанным интеграторам заранее.
  - **Экстренная** (`FR-019` б, P-30): только при подтверждённой уязвимости/компрометации механизма
    подтверждения подлинности, требует записанной оценки безопасности; период сосуществования (в том числе
    нулевой) назначает безопасность. Ненулевой период - двойная подпись (раздел 4, `AD-02`); нулевой -
    старый признак не отправляется, неперешедшие получатели отвергают доставку и уходят под порог
    автоотключения (принятое следствие, риск C-11, не дефект этого контракта).
- Две ветви структурно независимы на одном предмете (P-33): экстренная запись не поглощает и не сбрасывает
  уже открытую плановую по тому же предмету.

**Вторая независимая ось - версия управляющего API** (`subscription-management-api.md`, раздел
«Версионирование API»). Смешение осей - типовая ошибка, которую эта пара документов явно разводит: версия
схемы управляет **формой оповещения**, версия API - **формой управляющих ресурсов**; они меняются по
разным причинам, в разные моменты, независимым циклом выпуска. Ни одно изменение одной оси не требует
изменения номера другой.

## 9. Не входит в этот контракт

- Управление подпиской (создание, изменение, приостановка, удаление, секрет, версия подписки) -
  `subscription-management-api.md`.
- Подтверждение владения адресом (запрос-эхо, TTL) - механика описана в `subscription-management-api.md`,
  раздел «EndpointVerification», хотя технически это исходящий запрос платформы к кандидатному адресу
  (та же природа действия, что доставка) - решение о размещении названо там (`AD-04`).
- Перечень недоставленного, перечень пропущенного, ручная переотправка - см. `AD-10`,
  `subscription-management-api.md`, приложение «Операционная поверхность».
- Интеграционная документация целиком, включая рекомендуемое окно давности метки времени как публичное
  обещание, - `FR-014`, отдельный deliverable (design, раздел 9, инкремент 6), не эта спецификация.

## 10. Self-check (самоконтроль автора; проверкой для приёмника не является)

**Оракулы недоступны в среде.** `api-specification`, `microservices`, `doc-standards`, `nfr` и прочие
профильные skills лежат внутри `claude-code-marketplace`, чтение которого запрещено рабочим ограничением
этого прогона (см. `RUN-PROMPT.md`). `dex-skill-api-specification:api-specification` не загружался.
Проверка выполнена по знанию + внешней сверке (WebSearch/WebFetch, не ограничены рабочей директорией).
Статус фазы - `Phase 4 (Document) без проверки api-specification`.

**Что сверено внешним источником (не по памяти).**

- RFC 9457 «Problem Details for HTTP APIs» - обсуждается в `subscription-management-api.md` (формат ошибок
  общий для обеих поверхностей); здесь не используется напрямую (у этого контракта нет ответа платформы,
  наблюдаемого интегратором, в формате ProblemDetails - ответ на попытку доставки даёт получатель, не
  платформа).
- RFC 9110 §5.3 (объединение повторных полей заголовка) - `verified`, WebSearch 2026-08-03.
- JSON Schema 2020-12, ключевое слово `format: date-time` от RFC 3339 §5.6 - `verified`, WebFetch/WebSearch
  2026-08-03; уточнение про необязательность `format-assertion` вокабулярия по умолчанию учтено в тексте.
- Формат `Stripe-Signature` (`t=...,v1=...`) сверен как отраслевой референс, не как источник нормы для
  этого документа - алгоритм и формат значения уже зафиксированы ADR-0004/`AR-08` и не переоткрывались;
  референс использован только для проверки, что решение о разделении на два заголовка (`Delivery-Id` +
  `Signature`) не противоречит практике, а не для выбора алгоритма.

**Что не проверено внешним источником и почему.** Название заголовков (`Webhook-Delivery-Id`,
`Webhook-Signature`) - собственное решение (`AD-01`), не заимствование чужого зарегистрированного
пространства имён; проверка на коллизию с IANA-реестром HTTP-полей не выполнялась (риск низкий: префикс
`Webhook-` доменно-специфичен, коллизия маловероятна, но не исключена формально).

**Найдено и устранено при написании.** Первая редакция вводила отдельный заголовок метки времени наравне
с `t=` внутри подписи - устранено (`AD-01`) как дублирующий источник истины после сверки RFC 9110 §5.3 на
способ представления повторных значений, что сняло необходимость держать метку и в подписи, и отдельно.
