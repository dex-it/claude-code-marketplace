# ADR-0003: Управление конкурентным изменением подписки

## Status

Proposed

## Date

2026-08-03

## Decision Drivers

- `FR-008`/P-32 (ограничение постановщика, не переоткрывается здесь): изменение подписки поверх
  устаревшего представления её состояния отклоняется, сторона получает отказ с указанием причины;
  тихая потеря параллельного изменения запрещена. Механизм закрытия этого требования оставлен зоне
  дизайна.
- Позиция CAP/PACELC (ADR-0002) требует, чтобы обнаружение конфликта не зависело от распределённой
  блокировки поверх нескольких реплик - конфликт обязан разрешаться в рамках одной согласованной
  записи.
- Клиентский опыт: сторона, получившая отказ, должна иметь возможность немедленно повторить операцию
  с актуальным состоянием без дополнительного цикла чтения.
- Состояние подписки - машина состояний (активна/приостановлена/отключена, адрес, состав типов), а не
  набор независимых полей: механизм конкурентности обязан сочетаться с этим, а не разрешать конфликты
  на уровне отдельных полей.

## Context

Состояние подписки (активность, адрес получателя, состав отслеживаемых типов и другие управляемые
поля) может изменяться более чем одним запросом одновременно. Системное требование `FR-008`,
раскрывающее бизнес-требование, зафиксированное постановщиком (P-32), запрещает разрешать такой
конфликт молчаливым применением более позднего изменения поверх более раннего - механизм обязан
отклонить изменение, сделанное поверх устаревшего представления, и назвать причину отказа. Выбор
конкретного механизма - предмет этого решения, не пересмотр самого требования.

## Decision

Оптимистичная конкурентность по версии ресурса. Каждый ресурс подписки несёт идентификатор версии,
предъявляемый клиенту как значение entity tag представления. Любая изменяющая операция обязана нести
это значение как предварительное условие запроса. Условие, переставшее совпадать с текущим состоянием,
приводит к отказу с телом, называющим причину ("представление устарело"), текущую версию и текущее
представление ресурса - так, что повтор запроса не требует отдельного цикла чтения. Отсутствие
предварительного условия в изменяющем запросе приводит к отдельному отказу, а не к молчаливому
применению изменения - иначе отсутствие условия вырождает механизм в last-write-wins для любого
клиента, который просто не прислал его. Сравнение условия и запись происходят одной атомарной условной
операцией.

## Consequences

### Positive

- Сторона, чьё изменение конфликтует с чужим, всегда получает сигнал об этом, а не молчаливую потерю.
- Повтор после отказа дёшев: актуальное представление и новая версия возвращаются прямо в теле отказа.
- Механизм не требует специальной обработки отдельных полей и сочетается с любой семантикой машины
  состояний подписки.

### Negative

- Каждый изменяющий вызов требует предшествующего чтения версии ресурса.
- Клиент, не приславший предварительное условие, получает отказ безусловно, а не снисходительную
  обработку по умолчанию.

### Risks

- Клиентская библиотека, кеширующая версию ресурса на протяжении длительной сессии, будет видеть
  растущую долю отказов по конфликту при параллельном использовании нескольких клиентов одним
  интегратором; смягчается тем, что актуальное представление возвращается прямо в отказе.
- Механизм полагается на предпосылку read-your-writes управляющего API (ADR-0002); ослабление этой
  предпосылки без пересмотра данного решения сделает отказы по конфликту ложными.

## Alternatives Considered

### Last-write-wins

Более позднее по времени изменение молча применяется поверх более раннего.

- **Pros:** не требует от клиента ничего дополнительного - ни чтения версии, ни обработки отказа.
- **Cons:** допускает тихую потерю параллельного изменения.
- **Why rejected:** прямо запрещено P-32.

### Пессимистичная сериализация на ресурсе

Блокировка или очередь операций над одной подпиской: второй одновременный запрос ждёт завершения
первого и затем применяется поверх уже изменённого состояния.

- **Pros:** клиенту не нужно ничего присылать и обрабатывать - конфликт разрешается платформой
  прозрачно.
- **Cons:** конфликт не называется проигравшей стороне, а маскируется ожиданием - второй запрос
  завершается успехом, применённым поверх чужого изменения; формально потери нет, но и сигнала об
  устаревшем представлении сторона не получает. Дополнительно требует распределённой блокировки и
  таймаутов.
- **Why rejected:** маскирование конфликта вместо его называния противоречит цели P-32 - обязать
  платформу сообщить стороне об устаревшем представлении, а не просто не потерять данные.

### Слияние изменений по полям (merge)

Конфликтующие изменения разных полей одного ресурса применяются оба, если не пересекаются буквально.

- **Pros:** часть конфликтов разрешается автоматически без вмешательства клиента.
- **Cons:** состояние подписки - машина состояний, а не набор независимых полей: "приостановить" и
  "сменить адрес" не имеют осмысленного слитого результата.
- **Why rejected:** для этого ресурса не существует корректной семантики слияния по полям.

### Версия внутри тела запроса вместо предварительного условия

Тот же механизм сравнения версий, но версия передаётся полем тела запроса, а не заголовком условия.

- **Pros:** не требует специального заголовка на транспортном уровне.
- **Cons:** конфликт перестаёт быть выразимым стандартным кодом ответа условного запроса и уезжает в
  тело; посредники, кеширующие по заголовкам условности, его не видят.
- **Why rejected:** тот же механизм ценой утраты стандартной формы выражения конфликта, без
  компенсирующего преимущества.
