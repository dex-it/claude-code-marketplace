## 2. Аутентификация и авторизация

**Механизм аутентификации не назначен входом** (BRD/требования/design стек-нейтральны; регистрационные
данные интегратора - «существующий реестр интеграторов», design 8.12, вне охвата этой работы). Инженерная
нехватка, восполняется допущением, не бизнес-развилка (`node-contract`, реакция на нехватку):

**AD-14 (допущение этого документа).** Аутентификация - API-ключ, выдаваемый существующим реестром
интеграторов, предъявляемый заголовком `Authorization: Bearer <api-key>`; `integrator_id` (tenant)
разрешается платформой по ключу. Цена ошибки: если существующий реестр использует иной протокол (OAuth2,
mTLS), заголовок и способ разрешения арендатора меняются, состав ресурсов и кодов ответа - нет.

**Авторизация - per-resource ownership** (`NFR-008`): каждая операция предикатом `integrator_id` в запросе
к хранилищу, не проверкой после выборки (design, 8.12, против IDOR).

**AD-06 (решение этого документа).** Запрос к подписке другого арендатора и запрос к несуществующей
подписке отвечают **одинаково `404 Not Found`** - неразличимость исключает перечисление чужих идентификаторов
подбором (IDOR-энумерация). `NFR-008` verification допускает оба кода (`403`/`404`) как приемлемый исход;
выбран `404` единообразно. `403 Forbidden` зарезервирован за иным классом отказа - вызов операции
операционной поверхности (раздел 8) учётными данными интегратора, где сам факт существования эндпойнта не
чувствителен, а роль недостаточна.

## 3. Общие конвенции

### 3.1. Версия API - вторая независимая ось (см. `webhook-delivery-contract.md`, раздел 8)

**AD-11.** Версия управляющего API выражается префиксом пути `/v1/...`. Независима от `schema_version`
подписки (форма оповещения): смена версии API не требует смены версии схемы доставки и наоборот - они
управляют разными предметами и выпускаются по разным причинам (design, 8.1).

### 3.2. Формат ошибки

**AD-03.** `application/problem+json`, RFC 9457 «Problem Details for HTTP APIs» (obsoletes RFC 7807;
`verified`, WebFetch 2026-08-03). Обязательные для этого API члены: `type`, `title`, `status`, `detail`,
`instance`. Расширения по коду:

| Код | Расширение | Смысл |
|---|---|---|
| `400`, `422` | `errors: [{ "field": string, "message": string }]` | построчные причины валидации |
| `412` | `current_version: string`, `current_representation: object` | текущий `ETag` и текущее представление ресурса - повтор не требует отдельного `GET` (ADR-0003) |
| `429` | - (сигнал через заголовок `Retry-After`, не тело) | см. 3.5 |

### 3.3. Конкурентность - `ETag`/`If-Match`

Механизм зафиксирован ADR-0003/`AR-07`, не переоткрывается. `GET`/`201`/`200` несут заголовок `ETag`
(значение = `subscriptions.version`, opaque strong validator). Любая изменяющая операция обязана нести
`If-Match: <ETag>`.

- `If-Match` не совпадает с текущей версией -> `412 Precondition Failed` (RFC 9110 §15.5.13, `verified`
  WebSearch 2026-08-03), тело - ProblemDetails с расширением 3.2.
- `If-Match` отсутствует -> `428 Precondition Required` (RFC 6585 §3, «lost update problem» - ровно этот
  случай: сервер требует условности запроса именно потому, что параллельное изменение иначе применяется
  молча; `verified` WebFetch 2026-08-03).
- Сравнение и запись - одной атомарной условной операцией на стороне хранения (design, 8.6).

**AD-05.** `If-Match` обязателен на **всех** операциях, меняющих подписку или её секрет: `PATCH`, `DELETE`,
`POST .../secret`, `POST .../endpoint`. Буквальный текст `FR-008` называет «изменение состояния подписки»;
удаление и замена секрета текстом не названы поимённо, но раздел 8.6 design doc определяет механизм как
общий для «любой изменяющей операции», а `subscription_secrets`/`endpoint_verifications` в схеме хранения
(design, 8.2) - состояние, принадлежащее той же подписке. Отклонена альтернатива - `If-Match` только на
`PATCH`: два параллельных запроса на замену секрета создавали бы гонку с непредсказуемым порядком окон
перекрытия без сигнала ни одной из сторон, тот же класс дефекта, от которого защищает `FR-008`/P-32.

### 3.4. Пагинация перечней

**AD-08.** Курсорная (design, 8.1: offset неприменим на перечнях в сотни тысяч записей). Параметры запроса
`?cursor=<opaque>&limit=<n>`; ответ - конверт `{ "items": [...], "next_cursor": string | null }`. `cursor`
непрозрачен для клиента (кодирует внутреннюю пару сортировки, формат не часть контракта). `limit`: дефолт
50, максимум 500 - инженерные значения этого документа, не выведены из внешнего источника, не проверялись
запросом (низкий риск: не завязаны на семантику протокола).

### 3.5. Ограничение частоты (`NFR-009`)

Создание подписки (`POST /v1/subscriptions`) и операции, инициирующие проверку владения адресом
(`POST .../endpoint`, `POST .../endpoint-verification/resend`), лимитированы на `integrator_id`. Превышение
-> `429 Too Many Requests` + заголовок `Retry-After` (секунды, RFC 9110 §10.2.3, `verified` WebSearch
2026-08-03). **AD-09.** Конкретные пороги частоты - эксплуатационная конфигурация, не часть контракта
версии; названы находкой к дизайну не требуются - `NFR-009` не задаёт число, назначение числа делегировано
эксплуатации сознательно (design этого не фиксирует, и здесь не фиксируется тоже - иначе решение архитектуры
о конфигурации попало бы в контракт, что при пересмотре потребовало бы версионирования API без причины).

### 3.6. Идемпотентность создания

**AD-07.** Заголовок `Idempotency-Key` (обязателен на `POST /v1/subscriptions`) - опирается на практику
`draft-ietf-httpapi-idempotency-key-header` (IETF httpapi WG, черновик, **не ратифицирован RFC** на момент
проверки - `verified как draft`, WebSearch 2026-08-03, версия -07, октябрь 2025). Обязательность - решение
этого документа: создание запускает пробу владения адресом к стороннему URL (раздел 6), и повтор без ключа
идемпотентности на сетевом ретрае клиента создавал бы вторую пробу того же кандидата, потребляя лимит 3.5
без необходимости. Повторный вызов с тем же ключом и тем же телом -> исходный ответ без повторного создания.
Повторный вызов с тем же ключом и **иным** телом -> `422 Unprocessable Content` (несовпадение отпечатка
запроса) - общепринятая практика (Stripe и аналоги), не сверялась отдельным запросом в этой сессии
(инженерная конвенция, не именованный стандарт).

Общий JSON-стиль: `snake_case` для полей тела, единообразно с `webhook-delivery-contract.md`.

## 4. Ресурс `Subscription`

| Поле | Тип | Изменяемость | Смысл |
|---|---|---|---|
| `id` | string (UUID) | нет | идентификатор подписки |
| `state` | enum: `pending_verification`\|`active`\|`paused`\|`disabled` | через операции ниже | машина состояний (design, 8.2) |
| `endpoint_url` | string (URI, `https`) | через `POST .../endpoint` + верификация | подтверждённый адрес доставки |
| `pending_endpoint_url` | string (URI) \| null | сервер | кандидат на смену адреса, до подтверждения (`FR-010`) |
| `event_types` | array[string], `minItems: 1` | `PATCH` | фильтр по типу (P-06 - только по типу, не по содержимому) |
| `schema_version` | integer | нет после создания | версия контракта доставки, закреплённая подпиской (P-29) |
| `created_at` | string (`date-time`) | нет | - |
| `last_success_at` | string (`date-time`) \| null | сервер | последняя успешная доставка |
| `disabled_at` | string (`date-time`) \| null | сервер | момент автоотключения (`FR-005`) |
| `disabled_reason` | string \| null | сервер | причина отключения |

Секрет **не входит** в представление `Subscription` ни на одном `GET` (`NFR-007`) - отдельный разовый ответ
операций создания/замены (раздел 6).

### 4.1. Операции

| Операция | Метод и путь | Успех | Отказы |
|---|---|---|---|
| Создать | `POST /v1/subscriptions` | `201`, `Location`, `ETag`, тело `Subscription` + разовое `secret` | `400`/`422` (валидация, включая SSRF-деньлист адреса - ADR-0005), `429` |
| Получить | `GET /v1/subscriptions/{id}` | `200`, `ETag`, тело `Subscription` | `404` |
| Перечислить | `GET /v1/subscriptions` | `200`, конверт 3.4 | - |
| Изменить состав типов / состояние | `PATCH /v1/subscriptions/{id}` | `200`, новый `ETag`, тело | `404`, `412`, `428`, `422` (недопустимый переход состояния) |
| Удалить | `DELETE /v1/subscriptions/{id}` | `204` | `404`, `412`, `428` |
| Сменить адрес | `POST /v1/subscriptions/{id}/endpoint` | `202`, тело `EndpointVerification` | `404`, `412`, `428`, `422` (SSRF-деньлист) |
| Статус верификации адреса | `GET /v1/subscriptions/{id}/endpoint-verification` | `200`, тело `EndpointVerification` | `404` (нет ни одной подписки/верификации) |
| Повторить пробу владения | `POST /v1/subscriptions/{id}/endpoint-verification/resend` | `202` | `404`, `409` (нет активной ожидающей верификации), `429` |
| Заменить секрет | `POST /v1/subscriptions/{id}/secret` | `200`, тело `{secret, secret_id, overlap_until}` | `404`, `412`, `428` |
| Перечень пропущенного | `GET /v1/subscriptions/{id}/missed-events` | `200`, конверт 3.4 | `404` |

**Переходы состояния через `PATCH { "state": ... }`.** Допустимые переходы: `active <-> paused` (обе
стороны - явное действие интегратора, `FR-008`); `disabled -> active` (только явное действие интегратора,
design 8.5 - «автоматической реактивации по восстановлению получателя нет»); `pending_verification` не
принимает прямых переходов `state` (только следствие подтверждения/истечения верификации). Недопустимый
переход -> `422` с `errors` (3.2), не `400` - тело синтаксически валидно, конфликтует бизнес-правило.

**`DELETE` (P-36).** Каскадно удаляет `deliveries`, `missed_events`, секреты, верификации подписки, включая
не истёкшие по сроку хранения; аудит переживает удаление (design, 8.3). Восстановления нет ни через этот
API, ни через операционную поверхность (раздел 8).

**Создание (`POST /v1/subscriptions`).** Тело запроса: `{ "endpoint_url": string, "event_types": [string,
...] }`. Валидация адреса - слои 1-2 ADR-0005 (форма, резолв против deny-листа) синхронно на запрос; слои
3-4 (повторная проверка, запрет редиректа) - на момент отправки, не на момент создания подписки, вне этого
API. Успешное создание -> `state: pending_verification`, платформа немедленно инициирует пробу владения
(раздел 6); секрет создаётся и возвращается в теле ответа один раз.

## 5. Схема тела запроса (JSON Schema, создание/изменение)

```json
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "$id": "subscription-create-request.v1.schema.json",
  "type": "object",
  "additionalProperties": false,
  "required": ["endpoint_url", "event_types"],
  "properties": {
    "endpoint_url": { "type": "string", "format": "uri", "pattern": "^https://" },
    "event_types": { "type": "array", "items": { "type": "string", "minLength": 1 }, "minItems": 1 }
  }
}
```

`PATCH` использует то же множество полей частично (`event_types` и/или `state`), `additionalProperties:
false` сохраняется - неизвестное поле в теле отклоняется `400`, не игнорируется молча.

## 6. Ресурс `EndpointVerification` - подтверждение владения адресом (`FR-010`, ADR-0005)

Механизм (challenge-response, эхо токена, TTL 24 ч) зафиксирован `AR-12`, не переоткрывается. Здесь -
точная форма пробы, которую платформа отправляет **на кандидатный адрес** (та же природа действия, что
доставка оповещения - исходящий HTTP-запрос платформы, не вызов интегратором API платформы).

**AD-04.** Проба переиспользует конверт и механизм подписи доставки (раздел 5
`webhook-delivery-contract.md`), а не вводит параллельный формат:

- `POST` на кандидатный `endpoint_url`/`pending_endpoint_url`, `Content-Type: application/json`.
- Заголовки: `Webhook-Delivery-Id` (идентификатор попытки верификации), `Webhook-Signature` (тем же
  алгоритмом, тем же секретом подписки - секрет уже создан к моменту пробы, создание подписки и генерация
  секрета атомарны).
- Тело: `{ "type": "endpoint.verification", "token": "<opaque>" }`.
- Ожидаемый ответ: `2xx` с телом `{ "token": "<тот же opaque>" }` - точное эхо, не любой `2xx` (design,
  `AR-12`: «ответ 200 без эха не доказывает контроль над содержимым»).
- Отклонено/просрочено (нет валидного эха до `expires_at`) -> `EndpointVerification.state = expired` либо
  `rejected`; при создании подписка не активируется, при смене адреса `pending_endpoint_url` сбрасывается,
  доставка продолжается по прежнему `endpoint_url` без разрыва (`P-35`, `FR-010`).

Причина переиспользования подписи: получатель проверяет свою реализацию верификации HMAC на пробе до того,
как получит первое реальное оповещение - тот же код путь, дешёвая интеграция. Отклонена альтернатива - проба
без подписи («адрес ответил корректным эхом - достаточно»): не даёт получателю проверить, что кандидатный
URL действительно принадлежит домену конфигурации платформы, до выхода в прод.

**Автоматических повторов пробы нет** (в отличие от доставки оповещения) - только явный
`POST .../endpoint-verification/resend` интегратора, лимитированный `NFR-009` (3.5).

`EndpointVerification`: `{ id, subscription_id, candidate_url, state: pending|confirmed|expired|rejected,
expires_at, created_at }`.

## 7. Секрет (`NFR-007`, `FR-009`)

`POST /v1/subscriptions/{id}/secret` создаёт новое значение, действительное **наряду** со старым 24 ч
(окно перекрытия, `A-RA6` принято `AR-08`). Ответ - `200`, тело `{ "secret": "<plaintext, один раз>",
"secret_id": string, "overlap_until": "<date-time>" }`. Повторное чтение секрета невозможно ни этой, ни
любой другой операцией (`NFR-007`) - в представлении `Subscription` поля `secret` нет.

## 8. Операционная поверхность (внутренняя, не входит в публичный контракт интегратора)

**AD-10.** Design doc, раздел 8.1 («Модули»), относит перечень недоставленного и ручную переотправку к
**Ops surface**, отдельному от интеграторской поверхности («не владеет публичным контрактом интегратора»);
к интеграторской поверхности отнесён только перечень пропущенного (`FR-013`, раздел 4 этого документа).
Однострочный гейт задания перечисляет «перечни недоставленного и пропущенного» одной фразой под управляющим
API - design doc точнее и внутренне согласован (`FR-006` дословно адресован «эксплуатации»; `FR-007`/
`FR-013` разведены постановщиком по сторонам явно, П-27/BA-31, design 8.1 «Разведение контрактов - жёсткое»).
Разрешено в пользу design doc, не в пользу гейта: операционная поверхность размещена здесь отдельным
разделом с собственной моделью доступа, а не смешана с ресурсами раздела 4-7.

**Модель доступа - внутренняя**, роли эксплуатации, не `integrator_id`-предикат раздела 2. Учётные данные
интегратора на эти операции отвечают `403` (раздел 2, `AD-06`) - в отличие от `404` на чужой подписке,
здесь сам факт существования эндпойнта не является чужой тайной, поэтому `403`, не `404`.

| Операция | Метод и путь | Смысл |
|---|---|---|
| Перечень недоставленного | `GET /v1/ops/subscriptions/{id}/undelivered` | `FR-006`; конверт 3.4; каждая запись несёт одну из трёх категорий исхода (`NFR-011`) |
| Перечень пропущенного (эксплуатация) | `GET /v1/ops/subscriptions/{id}/missed-events` | `FR-006`; та же модель данных, что раздел 4, иной путь и модель доступа |
| Ручная переотправка | `POST /v1/ops/deliveries/{delivery_id}/resend` | `FR-007`; создаёт новую доставку `origin = manual_resend`, собственное окно 24 ч, не продлевает срок хранения исходной записи (design, `AR-18`, находка `F-AR-3`) |
| Доля доставленного и время исключения | `GET /v1/ops/metering/daily?date=` | `FR-020`; поле `finalized: bool` - доля суток окончательна через 24 ч после их конца (design, `AR-20`); вырожденный знаменатель - явный признак, не `0`/`100` (P-34) |

Формат ошибки, `ETag`/`If-Match` там, где применимо (переотправка недоставленного - не изменяющая операция
над `Subscription`, `If-Match` не требуется - она создаёт новую запись `deliveries`, не меняет ресурс с
версией), пагинация - те же конвенции раздела 3.

## 9. Self-check (самоконтроль автора; проверкой для приёмника не является)

**Оракулы недоступны в среде.** `api-specification`, `microservices`, `owasp-security`, `nfr`, `doc-standards`
лежат внутри `claude-code-marketplace`, запрещённого этим рабочим ограничением. `dex-skill-api-specification:
api-specification` не загружался - `Phase 4 (Document) без проверки api-specification`. Проверка выполнена по
знанию и внешней сверке источников (WebSearch/WebFetch, не ограничены рабочей директорией).

**Сверено внешним источником.**

- RFC 9457 (obsoletes RFC 7807) - `verified`, WebFetch 2026-08-03.
- `412 Precondition Failed` - RFC 9110 §15.5.13; `If-Match`/`ETag` - RFC 9110 §13.1.1/§8.8.3 - `verified`,
  WebSearch 2026-08-03 (косвенно, через вторичные источники, цитирующие секции; текст самой секции RFC не
  получен дословно из-за усечения документа при выборке - см. ограничение ниже).
- `428 Precondition Required` - RFC 6585 §3, включая формулировку «lost update problem» - `verified`,
  WebFetch 2026-08-03, дословная цитата получена.
- `Retry-After` - RFC 9110 §10.2.3 - `verified` по номеру секции (WebSearch), дословный текст секции не
  получен (усечение при выборке); семантика (секунды ожидания на `429`/`503`) - общеизвестная, риск низкий.
- `Idempotency-Key` - **не RFC**, IETF httpapi WG draft, версия -07 (октябрь 2025) - зафиксировано явно как
  `unverifiable: не ратифицирован`, не выдаётся за стандарт.

**Ограничение сверки, названное явно.** Для `412`/`If-Match`/`ETag`/`Retry-After` `WebFetch` по прямому URL
секции RFC 9110 возвращал усечённое содержимое (документ большой, секция за пределами полученного фрагмента);
номер и назначение секции подтверждены вторичными источниками (MDN, отраслевые статьи, поиском), не дословной
цитатой первоисточника. Статус - `verified по номеру и общей семантике`, не `verified дословно`. Риск ошибки
низкий (это одни из самых стабильных и часто цитируемых частей HTTP-семантики), но отличие от `AD-03`
(RFC 9457, дословная цитата получена) и `428` (дословная цитата получена) названо, не скрыто.

**Не проверено и почему.** Механизм аутентификации (`AD-14`) - вход не называет протокол, восполнено
допущением с ценой ошибки. Пороги `NFR-009` (частота) - явно не назначены ни входом, ни design doc, оставлены
эксплуатационной конфигурацией сознательно (3.5), не находка - решение делегирования, а не пробел.

**Найдено и устранено при написании.** Первая редакция раздела 8 держала перечень недоставленного в этом же
файле без явного разведения модели доступа от раздела 4 (интеграторской) - устранено выделением отдельного
раздела с иной моделью доступа (`403` вместо `404`) и явным разбором расхождения гейта задания с design doc
(`AD-10`), а не тихим слиянием под одной моделью авторизации.
