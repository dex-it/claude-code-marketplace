## 3. Non-goals (перенесены без изменений, требования раздел 5 / BRD раздел 3)

- Внутренняя шина событий платформы - предмет внутренней архитектуры, не обещания интегратору.
- Гарантия порядка доставки - отклонена постановщиком как непропорционально дорогая (P-01).
- Фильтры подписки по содержимому события (только по типу) - получатель отфильтровывает лишнее у себя (P-06).
- Повторное проигрывание истории глубже срока хранения (7 суток) - требует отдельного хранилища истории событий.
- Полный снимок сущности в теле оповещения - раскрытие вовне сужено до идентификаторов (P-02).
- Заведение подписок сотрудником поддержки по заявке - отклонено в пользу самообслуживания (P-03).
- Публичное предъявление интегратору способа счёта доли доставленного (время исключения в отчётности стороне, на статус-странице, в ответе API) - договорная ось вне охвата (P-20); внутреннее предъявление продукту и эксплуатации входит в охват (`FR-020`, S-3.6).

Ни один non-goal не породил story на этом проходе - сверено построчно при декомпозиции.

## 4. Каталог историй по epic

### Epic E-1. Доставка оповещений

**S-1.1. Платформа порождает и отправляет оповещение по событию без опроса**

Story: Как интегратор, я хочу получать оповещение о событии моей активной подписки автоматически, чтобы не опрашивать API и не терять время между событием и знанием о нём.

Acceptance Criteria:
- `[FR-001]` Given активная подписка на тип события T, When событие типа T происходит для сущности в области подписки, Then платформа отправляет HTTP-запрос на адрес подписки без действия интегратора.
- `[FR-001]` Given подписка неактивна (отключена или приостановлена) в момент события, When событие происходит, Then оповещение не порождается; событие фиксируется как пропущенное (см. S-3.5, `FR-013`) - `[Assumption], источник: глоссарий BRD «пропущенное»`.
- `[FR-001]` Given два события одного типа для разных сущностей происходят одновременно, When оба подпадают под одну активную подписку, Then оба оповещения порождены и отправлены независимо (нет потери при конкурентных событиях).

Technical Notes: транспорт - HTTP POST, JSON-тело (A1, design constraint BRD). Release-gate: `NFR-001` (p95 <= 5 с) проверяется нагрузочным тестом перед релизом, далее - continuous production-мониторинг (см. раздел 2).

Definition of Done: интеграционный тест на каждый тип события активной подписки; нагрузочный прогон подтверждает p95 <= 5 с при штатной нагрузке (`NFR-004`); code review; наблюдаемость (лог попытки, `NFR-011`, зависимость S-3.3) на месте.

Story Points: 5. Priority: Must. Dependencies: нет (базовая история epic'а).

**S-1.2. Тело оповещения ограничено пятью полями активной версии схемы**

Story: Как получатель (система интегратора), я хочу получать оповещение со стабильным, предсказуемым составом полей, чтобы не тратить ресурс на обработку непредвиденных данных и не ломаться при появлении новых полей.

Acceptance Criteria:
- `[FR-002]` Given активная версия схемы объявляет пять полей (id события, тип события, id сущности, момент события, версия схемы), When оповещение сформировано, Then тело не содержит иных полей сверх названных для этой версии (верхняя граница, версионно-зависимая).
- `[FR-002]` Given любая версия схемы, любая история платформы, When оповещение отправлено, Then тело содержит непустой идентификатор события - без исключений, независимо от версии (нижняя граница, версионно-независимая).
- `[FR-002]` Given получатель обрабатывает по старой версии схемы, When платформа выпускает новую версию с дополнительным полем (`FR-018`), Then получатель продолжает обрабатывать прежние оповещения без доработки - верхняя граница не читается как «пять полей навсегда».
- `[FR-012]` Given признак подлинности, идентификатор доставки и метка времени доставки, When оповещение отправлено, Then эти три элемента переданы HTTP-заголовками (метаданные доставки), не полями JSON-тела - не входят в подсчёт верхней границы.

Technical Notes: contract-тест схемы (JSON Schema `additionalProperties: false` относительно набора полей активной версии) переиздаётся при каждом расширении состава, не зафиксирован навечно на пяти именах. Метаданные доставки - предмет S-2.8 (`FR-012`), здесь только граница «в тело не входят».

Definition of Done: contract-тест на обе границы; regression-тест не ломается при добавлении поля новой версией (зависимость `FR-018`, S-5.1); code review.

Story Points: 3. Priority: Must. Dependencies: S-2.8 (`FR-012`, метаданные доставки не входят в тело), S-5.1 (`FR-018`, совместимость новой версии).

**S-1.3. Платформа повторяет попытку доставки при отказе или таймауте**

Story: Как интегратор, я хочу, чтобы платформа сама повторяла доставку при кратковременной недоступности моей системы, чтобы не терять события из-за временного сбоя на моей стороне.

Acceptance Criteria:
- `[FR-003]` Given попытка доставки не подтверждена успешным ответом (любой код кроме успеха, либо таймаут - П-6), When окно повторных попыток (24 ч) не истекло, Then платформа повторяет попытку.
- `[FR-003]` Given получатель отвечает успехом на N-ю попытку в пределах окна, When успех получен, Then повторы прекращаются, доставка считается состоявшейся.
- `[FR-003]` Given окно повторных попыток (24 ч) истекло без подтверждённого успеха, When наступает 24-й час, Then повторы прекращаются, оповещение переходит в статус «недоставленное» (см. S-3.3, `FR-006`).
- `[NFR-003]` Given попытки идут в пределах 24-часового окна, When измеряется число попыток и интервалы между ними, Then попыток не менее 8, интервал между последовательными попытками не убывает (защита от эффекта стада).

Technical Notes: конкретная кривая backoff - решение архитектуры (`NFR-003`, `RA-02`), число 8 и монотонность интервала - предмет AC этой истории, не архитектуры.

Definition of Done: unit-тест retry-планировщика (число попыток, монотонность интервала); симуляция отказа/таймаута в интеграционном тесте; code review.

Story Points: 5. Priority: Must. Dependencies: S-1.1.

**S-1.4. Событие не теряется при недоступности собственной подсистемы доставки**

Story: Как интегратор, я хочу быть уверен, что событие не потеряется, даже если у платформы временно откажет собственная подсистема доставки, чтобы не строить у себя компенсирующую сверку на этот случай.

Acceptance Criteria:
- `[NFR-006]` Given подсистема доставки платформы недоступна, When событие происходит в этот период, Then событие накапливается в durable-хранилище, а не теряется.
- `[NFR-006]` Given подсистема доставки восстановилась после периода недоступности, When обработка возобновляется, Then все накопленные события дожимаются (доставляются либо переходят в стандартный цикл ретраев/недоставленного) без потерь.
- `[NFR-002, доля потерь]` Given контролируемый сценарий отказа собственной подсистемы доставки, When период отказа завершён и очередь дожата, Then доля безвозвратно утраченных в пределах срока хранения (7 суток) равна 0%.

Technical Notes: своевременность (`NFR-001`) в этом режиме допустимо нарушается - явное решение раздела 13 BRD («обещание по задержке нарушается явно»); в AC не заявляется как нарушение договора, а как принятый режим деградации.

Definition of Done: chaos-тест - контролируемая остановка подсистемы доставки, проверка отсутствия потерь и полного дожатия очереди после восстановления; code review.

Story Points: 8. Priority: Must. Dependencies: S-1.1.

**S-1.5. Наблюдение доли доставленных событий за представительный период**

Story: Как продукт платформы, я хочу видеть долю событий, доставленных за сутки по активным подпискам, за представительный период, чтобы подтверждать соответствие обещанию (>= 99.5%) и замечать деградацию раньше, чем она станет проблемой интегратора.

Acceptance Criteria:
- `[NFR-002, доля]` Given логи доставки (`NFR-011`) за представительный период (30 суток), When рассчитывается доля доставленного, Then расчёт учитывает только активные подписки (П-9) - знаменатель исключает периоды отключения/приостановки.
- `[NFR-002, доля]` Given рассчитанная доля доставленного за период, When доля предъявляется продукту и эксплуатации, Then она предъявляется вместе со временем исключения за тот же период (см. S-3.6, `FR-020`) - не в одиночку.

Technical Notes: расчёт по логам доставки (`NFR-011`, зависимость S-3.3) + автотест нулевой потери в контролируемом сценарии отказа (`NFR-006`, S-1.4) как дополняющая проверка полноты. Перцентильный/долевой характер метрики не проверяется единичным сценарием - AC описывают наблюдаемость и корректность знаменателя, а не конкретное числовое значение доли на конкретном прогоне.

Definition of Done: расчёт по логам за 30-суточный период доступен продукту/эксплуатации; неразрывность с `FR-020` подтверждена (нет предъявления доли без времени исключения рядом); code review.

Story Points: 3. Priority: Must. Dependencies: S-3.3 (`NFR-011`), S-3.6 (`FR-020`), S-1.4 (`NFR-006`).

### Epic E-2. Самообслуживание подписок

**S-2.1. Интегратор создаёт подписку через API**

Story: Как интегратор, я хочу создать подписку самостоятельно через API (типы событий, адрес), чтобы подключиться без обращения в поддержку.

Acceptance Criteria:
- `[FR-008]` Given интегратор аутентифицирован в управляющем API, When он отправляет запрос на создание подписки с типами событий и адресом, Then подписка создаётся в состоянии «ожидает подтверждения владения адресом» (см. S-2.2).
- `[FR-008]` Given запрос на создание подписки с пустым списком типов событий, When запрос отправлен, Then API отклоняет запрос с указанием причины (пустой список типов не создаёт подписку без предмета).
- `[FR-008]` Given запрос на создание подписки, When адрес указан в неверном формате (не URL), Then API отклоняет запрос до попытки верификации.

Technical Notes: создание не активирует доставку - активация только после `FR-010` (S-2.2). Секрет подписи выдаётся при создании, открытым текстом единожды (`NFR-007`, S-2.8).

Definition of Done: e2e тест создания подписки без обращения к поддержке-эмулятору; негативные тесты на пустой список типов и неверный формат адреса; code review.

Story Points: 5. Priority: Must. Dependencies: нет.

**S-2.2. Платформа подтверждает владение адресом перед активацией подписки**

Story: Как получатель (владелец адреса), я хочу подтвердить, что оповещения будут приходить именно мне, чтобы платформа не начала слать данные по адресу, которым я не владею.

Acceptance Criteria:
- `[FR-010]` Given подписка в состоянии «ожидает подтверждения», When платформа отправляет challenge-response запрос с одноразовым токеном на указанный адрес и получает корректный ответ с этим токеном, Then подписка активируется.
- `[FR-010]` Given токен отправлен, When за 24 ч корректного ответа не получено, Then заявка на подписку отбрасывается, доставок не было.
- `[FR-010]` Given токен отправлен, When получен ответ с неверным токеном, Then подписка не активируется, заявка остаётся в состоянии ожидания до истечения окна 24 ч.

Technical Notes: `[Assumption]` (`A-RA4`, требования раздел 6): конкретный механизм - challenge-response HTTP-хендшейк, токен действителен 24 ч; окончательный выбор механизма - решение архитектуры, здесь зафиксирован критерий результата (MOE `BR-009`: ноль доставок на неподтверждённый адрес).

Definition of Done: UC-12 (недоказанное владение -> подписка не активируется) проходит; тест на истечение токена; code review.

Story Points: 5. Priority: Must. Dependencies: S-2.1.

**S-2.3. Платформа отклоняет адреса подписки во внутренних/частных диапазонах сети**

Story: Как платформа (владелец риска SSRF), я хочу отклонять адреса подписки, разрешающиеся во внутренние или частные диапазоны сети, чтобы механизм доставки нельзя было использовать для сканирования внутренней инфраструктуры.

Acceptance Criteria:
- `[FR-011]` Given адрес подписки разрешается в localhost, link-local или частный диапазон сети, When подписка создаётся или проходит верификацию, Then запрос отклоняется на этапе создания либо верификации, подписка не активируется.
- `[FR-011]` Given адрес проходит через DNS-редирект на приватный диапазон уже после первичной проверки, When платформа выполняет challenge-response (S-2.2), Then повторная проверка резолва на момент отправки также отклоняет приватный адрес - `[Assumption], источник: обоснование FR-011 «адрес - недоверенный ввод» распространяется на весь жизненный цикл проверки, не только на первичное создание; цена ошибки - TOCTOU-обход SSRF-защиты через DNS rebinding, если проверка выполняется только один раз`.

Technical Notes: security-тест обязателен в CI (verification `FR-011`).

Definition of Done: security-тест на localhost/link-local/частный диапазон в CI; тест на DNS rebinding сценарий; code review.

Story Points: 3. Priority: Must. Dependencies: S-2.1, S-2.2.

**S-2.4. Платформа ограничивает частоту создания и верификации подписок**

Story: Как платформа (владелец риска злоупотребления), я хочу ограничить частоту создания и верификации подписок на аккаунт интегратора, чтобы механизм не использовался для DDoS или сканирования чужих адресов через массовое создание подписок.

Acceptance Criteria:
- `[NFR-009]` Given аккаунт интегратора создаёт подписки чаще установленного лимита, When лимит превышен, Then последующие запросы на создание отклоняются (rate limit).
- `[NFR-009]` Given аккаунт интегратора инициирует верификацию (challenge-response, S-2.2) чаще установленного лимита, When лимит превышен, Then последующие запросы на верификацию отклоняются.

Technical Notes: конкретное значение лимита не задано источником (design constraint архитектуры) - AC проверяют факт применения лимита, не число.

Definition of Done: security-тест превышения частоты создания/верификации; code review.

Story Points: 3. Priority: Must. Dependencies: S-2.1, S-2.2.

**S-2.5. Интегратор изменяет состав типов и адрес подписки**

Story: Как интегратор, я хочу изменить состав типов событий и адрес подписки самостоятельно, чтобы адаптировать интеграцию без обращения в поддержку.

Acceptance Criteria:
- `[FR-008]` Given активная подписка интегратора, When он меняет состав типов событий через API, Then изменение вступает в силу без участия поддержки, дальнейшие события доставляются по новому составу.
- `[FR-008, P-32]` Given активная подписка, When два запроса на изменение одной подписки идут параллельно и второй выполняется поверх представления состояния, устаревшего первым, Then второй запрос отклоняется с указанием причины отказа; итоговое состояние подписки не теряет молча первое изменение (конкретный механизм обнаружения устаревшего представления - решение зоны 2, требованием не назначается).
- `[FR-008, FR-010]` Given активная подписка, When интегратор меняет адрес, Then новый адрес проходит подтверждение владения заново (S-2.2) прежде, чем доставка пойдёт по нему.
- `[FR-010, P-35]` Given интегратор сменил адрес активной подписки, When верификация нового адреса ещё не завершена (ожидает ответа, либо ответ отклонён или просрочен), Then доставка продолжает идти по прежнему подтверждённому адресу без разрыва - приостановка доставки на время верификации не применяется; после подтверждения нового адреса доставка переключается на него, после отклонённого/просроченного ответа адрес подписки остаётся прежним.

Technical Notes: `OQ-SW-1` закрыт постановщиком (`P-32`, гейт stories, раунд 1): результат гонки - отказ с причиной, тихая потеря запрещена; механизм (условный запрос по версии, сериализация на ресурсе, иное) не назначается требованием и остаётся решением зоны 2. `Finding F14` (дизъюнкция «прежний адрес либо приостановлена» в прежней редакции) закрыт `P-35`, перенесённым в `FR-010` ревизии 4: доставка на период верификации однозначно продолжается по прежнему адресу, приостановка отклонена как решение (событие окна верификации иначе стало бы пропущенным без воли интегратора, против чего заведены `BR-002`/`FR-013`).

Definition of Done: e2e тест изменения типов/адреса через API; негативный тест конкурентности - два параллельных запроса на одну подписку, второй поверх устаревшего представления отклонён с явной причиной; e2e тест смены адреса - до ответа на верификацию доставка идёт по прежнему адресу, после подтверждения переключается на новый, после отклонённого/просроченного ответа остаётся на прежнем без разрыва; code review.

Story Points: 5. Priority: Must. Dependencies: S-2.1, S-2.2.

**S-2.6. Интегратор приостанавливает и удаляет подписку**

Story: Как интегратор, я хочу приостановить или удалить подписку самостоятельно, чтобы управлять интеграцией на время своих работ или прекратить её полностью.

Acceptance Criteria:
- `[FR-008]` Given активная подписка, When интегратор приостанавливает её через API, Then подписка переходит в неактивное состояние, события периода приостановки записываются как пропущенное (`FR-013`, S-3.5).
- `[FR-008]` Given приостановленная подписка, When интегратор возвращает её в работу явным действием, Then подписка снова активна, пропущенное за период приостановки доступно к восстановлению (S-3.5).
- `[FR-008]` Given подписка (активная либо приостановленная), When интегратор удаляет её через API, Then подписка перестаёт существовать, дальнейшие события по её типам не порождают оповещений для неё.
- `[FR-008, P-32]` Given подписка, When конкурентный запрос (например, `PATCH` состава/адреса и `DELETE`) выполняется поверх представления состояния, устаревшего другим запросом, Then выполняемый поверх устаревшего представления отклоняется с указанием причины; итоговое состояние не теряет молча параллельное изменение.
- `[FR-013, P-36]` Given подписка с непустыми накопленными записями недоставленного (`FR-006`) и пропущенного (`FR-013`), When интегратор удаляет подписку, Then накопленные записи обеих категорий удаляются вместе с ней; восстановление этих записей после удаления недоступно ни интегратору (выборка/переотправка через API), ни эксплуатации (ручная переотправка, `FR-007`) - в том числе записи, ещё не истёкшие по сроку хранения (7 суток).
- `[FR-013, P-36]` Given подписка была удалена и её записи недоставленного/пропущенного более недоступны, When интегратор заводит новую подписку на тот же адрес, Then записи удалённой подписки к новой подписке не привязываются и не восстанавливаются - новая подписка не тождественна удалённой.

Technical Notes: удаление - необратимая операция; повторное подключение требует новой подписки (S-2.1) и новой верификации (S-2.2). `P-32` (закрывает `OQ-SW-1`) - см. обоснование механизма в S-2.5, здесь применяется к парам операций, включающим `DELETE`. `P-36` (закрывает `Finding F15`) - отклонённая альтернатива: хранить записи удалённой подписки до истечения срока хранения и отдавать их по вновь созданной подписке того же интегратора на тот же адрес - отклонено, т.к. новая подписка не тождественна удалённой, а выдача истории по совпадению адреса открывает канал получения чужих данных при перехвате адреса.

Definition of Done: e2e тест полного цикла приостановка/возврат/удаление; негативный тест конкурентности (`DELETE` поверх устаревшего представления отклонён); тест удаления - подписка с непустыми недоставленным и пропущенным удаляется -> записи недоступны ни через API интегратора, ни через инспекцию эксплуатации; тест - повторное создание подписки на тот же адрес не восстанавливает записи удалённой подписки; code review.

Story Points: 5. Priority: Must. Dependencies: S-2.1.

**S-2.7. Интегратор заменяет секрет подписи с окном перекрытия**

Story: Как интегратор, я хочу заменить секрет подписи самостоятельно (регламент или подозрение на компрометацию), чтобы восстановить доверие к каналу без разрыва доставки «в полёте».

Acceptance Criteria:
- `[FR-009]` Given активная подписка, When интегратор инициирует замену секрета, Then платформа принимает оповещения, подписанные и старым, и новым секретом, в течение окна перекрытия.
- `[FR-009]` Given окно перекрытия (24 ч - `[Assumption]`, `A-RA6`, требования раздел 6) истекло, When получатель подписывает запоздавший ретрай старым секретом, Then платформа считает подпись невалидной - старый секрет больше не действует.
- `[NFR-007]` Given секрет создан или заменён, When интегратор запрашивает его повторно, Then открытое значение не возвращается - секрет предъявляется открытым текстом только один раз, в момент создания/замены.
- `[NFR-007]` Given хранилище секретов скомпрометировано (security review сценарий), When значение секрета извлекается из хранилища, Then исходное значение не восстанавливается (хранится хешированным/зашифрованным at rest).

Technical Notes: `A-RA6` - окно перекрытия 24 ч выведено из необходимости не отвергнуть ни одну доставку «в полёте» при максимальной глубине ретраев (`NFR-003`); цена ошибки - более короткое окно отвергнет валидный запоздавший ретрай как подделку.

Definition of Done: тест смены секрета во время активной доставки (обе подписи валидны в окне); тест истечения окна; security review хранения; тест API (повторный запрос секрета не возвращает значение); code review.

Story Points: 5. Priority: Must. Dependencies: S-2.1.

**S-2.8. Каждая доставка несёт признак подлинности и данные различения повтора**

Story: Как получатель, я хочу отличать подлинное оповещение платформы от подделки и штатный повтор от воспроизведения перехваченного оповещения третьей стороной, чтобы не обрабатывать чужие данные как свои и не путать ретрай с атакой.

Acceptance Criteria:
- `[FR-012]` Given оповещение отправляется, When запрос формируется, Then он несёт криптографический признак подлинности (вычисленный на основе секрета подписки, покрывающий тело), идентификатор доставки и метку времени доставки - все три метаданными доставки (HTTP-заголовками), не полями тела.
- `[FR-012]` Given тело, секрет или метка времени изменены относительно исходных, When получатель проверяет признак подлинности, Then признак невалиден.
- `[FR-012]` Given получатель получил штатный повтор (тот же идентификатор события, П-1), When он сравнивает с ранее принятым, Then распознаёт дубль по идентификатору события и не выполняет обработку дважды (UC-10) - `[покрыт инвариантом П-1/BR-004, at-least-once + обязанность идемпотентности получателя]`.
- `[FR-012]` Given третья сторона перехватывает и повторно отправляет подлинное оповещение получателю напрямую (не через платформу), When получатель проверяет метку времени/одноразовость идентификатора доставки, Then он отвергает воспроизведение, а не обрабатывает как штатный дубль (UC-13).

Technical Notes: `[Assumption]` (`A-RA5`, требования раздел 6) - иллюстративный механизм HMAC-SHA256 над телом с меткой времени и идентификатором доставки (отраслевой дефолт, A4); окончательный алгоритм и окно допустимой давности метки времени, которое проверяет получатель, - решение архитектуры/документации получателя (`FR-014`, S-4.1b). Исключение П-11 (экстренная замена самого механизма) - предмет S-5.3, не этой истории (здесь - секрет одной подписки уже покрыт S-2.7, замена механизма для всех подписок - другой предмет).

Definition of Done: контрактный тест (признак невалиден при изменении тела/секрета/устаревшей метки); тест сверяет передачу вне тела (заголовками); UC-13 воспроизведён и отвергнут; code review.

Story Points: 5. Priority: Must. Dependencies: S-1.1, S-2.7.

**S-2.9. Интегратор не может получить доступ к чужой подписке**

Story: Как интегратор, я хочу быть уверен, что другой интегратор не может прочитать, изменить или удалить мою подписку, чтобы моя интеграция была изолирована от чужих ошибок и злого умысла.

Acceptance Criteria:
- `[NFR-008]` Given интегратор A аутентифицирован, When он запрашивает чтение подписки, принадлежащей интегратору B, Then API отвечает отказом (403/404), данные подписки B не раскрываются.
- `[NFR-008]` Given интегратор A аутентифицирован, When он пытается изменить или удалить подписку интегратора B (зная либо угадав её идентификатор), Then операция отклоняется, состояние подписки B не меняется.

Technical Notes: модель авторизации (per-resource ownership, tenant_id во всех сущностях подписки) - решение архитектуры; здесь зафиксирован критерий изоляции (IDOR/multi-tenant).

Definition of Done: security-тест cross-tenant доступа (чтение/изменение/удаление) в CI; code review.

Story Points: 5. Priority: Must. Dependencies: S-2.1.

**S-2.10. Эксплуатация видит аудит-лог операций с подпиской**

Story: Как эксплуатация, я хочу видеть журнал всех операций с подпиской (кто, когда, что изменилось), чтобы разбирать инциденты и подтверждать, что автоматика (автоотключение, реактивация) сработала штатно.

Acceptance Criteria:
- `[NFR-010, часть а]` Given операция с подпиской произошла (создание, изменение, приостановка, удаление, автоотключение, реактивация, замена секрета), When она завершена, Then запись аудит-лога фиксирует инициатора (интегратор либо автоматика платформы), момент и предыдущее/новое состояние.
- `[NFR-010, часть а]` Given серия тестовых операций с подпиской выполнена, When эксплуатация инспектирует аудит-лог, Then каждая операция представлена отдельной записью, ни одна не потеряна.

Technical Notes: retention аудит-лога отдельно не задан BRD (не критично для этой работы - подписки и их история не регулируемые сведения, П-10, A9).

Definition of Done: инспекция аудит-лога после серии тестовых операций с подпиской подтверждает полноту; code review.

### Epic E-3. Эксплуатация доставки

**S-3.1. Отказ одной подписки не задерживает доставку по остальным**

Story: Как эксплуатация, я хочу, чтобы неисправность одного получателя не расходовала общий ресурс доставки, чтобы отказ одного интегратора не превращался в инцидент для всех остальных.

Acceptance Criteria:
- `[FR-004]` Given одна подписка "отравлена" (100% неуспех доставки), When доставка по остальным исправным подпискам продолжается, Then очередь доставки по другим подпискам не задерживается и не блокируется накоплением неуспешных попыток отравленной.
- `[NFR-005]` Given одна подписка "отравлена" (100% неуспех), When измеряется p95 своевременности доставки по остальным исправным подпискам во время отказа, Then p95 остаётся в пределах `NFR-001` (<= 5 с) без измеримой деградации.

Technical Notes: способ изоляции - предмет дизайна (design constraint BRD, `BR-005`).

Definition of Done: нагрузочный тест с одной "отравленной" подпиской (100% отказ), сравнение p95 остальных до/во время отказа; количественный критерий деградации подтверждён `NFR-005`; code review.

Story Points: 5. Priority: Must. Dependencies: S-1.1, S-1.3.

**S-3.2. Платформа автоматически отключает устойчиво неисправную подписку**

Story: Как эксплуатация, я хочу, чтобы платформа сама отключала подписку, устойчиво не принимающую доставку, чтобы неисправный получатель не расходовал общий ресурс доставки бесконечно.

Acceptance Criteria:
- `[FR-005]` Given подписка непрерывно не получает ни одной успешной доставки 24 ч подряд (окно скользящее по подписке, не цикл ретраев одного события - `P-22`), When порог достигнут, Then подписка автоматически отключается.
- `[FR-005]` Given подписка получила хотя бы один успех внутри 24-часового скользящего окна, When окно продолжается, Then подписка НЕ отключается.
- `[FR-005]` Given подписка отключена автоматикой, When отключение произошло, Then интегратор уведомлён каналом, не зависящим от подписки (регистрационные контактные данные, P-19).
- `[FR-005]` Given подписка отключена автоматикой, When интегратор не совершил явного действия по возврату, Then подписка остаётся отключённой - реактивация только явным действием интегратора.
- `[FR-005, P-34]` Given подписка достигла порога отключения одновременно с недоступностью канала уведомления (bounce/timeout стороннего сервиса контактов), When платформа обрабатывает срабатывание порога, Then подписка тем не менее отключается в срок - недоступность канала не откладывает и не отменяет отключение; неуспех попытки уведомления виден эксплуатации в аудит-логе (`NFR-010`), повторная попытка уведомления фиксируется в пределах срока хранения (7 суток).
- `[Race, множественное срабатывание]` Given несколько подписок разных интеграторов достигают порога 24 ч одновременно (например, при выпуске по исключению П-11 с нулевым периодом сосуществования - S-5.3, BRD C-11), When срабатывает автоотключение, Then каждая обрабатывается независимо, отключение одной не задерживает отключение/уведомление остальных - `[покрыт AC, наследует изоляцию S-3.1: механизм автоотключения работает по той же per-подписочной модели, что и доставка]`.

Technical Notes: зависит от `NFR-003` (S-1.3, график ретраев - таймаут засчитывается отказом, П-6) как готового графика попыток, не дублирует его AC. Уведомление и сама операция автоотключения фиксируются аудит-логом (S-2.10, `NFR-010`). `Finding F18` (часть 1, недоступность канала уведомления) закрыта `P-34`, перенесённым в `FR-005` ревизии 4: отключение - функция самого порога, не функция успеха уведомления, иначе неисправный получатель продолжал бы расходовать общий ресурс доставки из-за отказа стороннего канала - против цели `BR-005`.

Definition of Done: симуляция continuous failure -> подписка отключена по достижении 24 ч; симуляция единичного успеха внутри окна -> НЕ отключается; негативный тест канала - недоступный канал уведомления одновременно с continuous failure -> подписка тем не менее отключена в срок, неуспех виден в аудит-логе, повторная попытка зафиксирована в пределах срока хранения; симуляция массового одновременного срабатывания (>= 3 подписок) -> все обработаны без взаимной задержки; code review.

Story Points: 8. Priority: Must. Dependencies: S-1.3 (`NFR-003`), S-2.10 (`NFR-010`), S-3.1.

**S-3.3. Эксплуатация видит недоставленное и пропущенное с причиной**

Story: Как эксплуатация, я хочу видеть перечень недоставленного и пропущенного с указанной причиной, чтобы разбирать инциденты, не занимаясь ручным поиском по логам.

Acceptance Criteria:
- `[FR-006]` Given событие не доставлено (окно ретраев исчерпано), When эксплуатация открывает перечень недоставленного, Then запись видна с причиной последнего отказа - одной из трёх категорий исхода `NFR-011` (HTTP-статус ответа получателя, признак таймаута ответа либо признак ошибки установления соединения - получатель недостижим на уровне DNS/TCP/TLS).
- `[FR-006]` Given событие пропущено (подписка была неактивна в момент события), When эксплуатация открывает перечень пропущенного, Then запись видна с причиной «подписка неактивна» (единственная причина по построению).
- `[NFR-011]` Given попытка доставки (успешная либо неуспешная) произошла, When платформа регистрирует попытку, Then лог хранит момент попытки, исход попытки в одной из трёх категорий (HTTP-статус ответа получателя, признак таймаута ответа, признак ошибки установления соединения), связь с событием и подпиской - исход всегда относится к одной из трёх категорий, четвёртой не остаётся.
- `[Пусто]` Given за период нет ни недоставленного, ни пропущенного, When эксплуатация открывает перечни, Then оба перечня показывают пустое состояние явно (не ошибку, не бесконечную загрузку) - `[Assumption], источник: стандартный UX-паттерн пустого состояния, cм. dex-skill-user-stories «пустые данные не учтены»; цена ошибки - неотличимость «всё доставлено» от «сервис недоступен»`.

Technical Notes: наблюдаемость доставки (`NFR-011`) - основа для этой истории и для `FR-007` (S-3.4). Раунд 4 требований расширил `NFR-011` третьей категорией исхода (отказ на этапе установления соединения - получатель недостижим до попытки HTTP-обмена: DNS не резолвится, TCP отклонён, TLS-хендшейк не проходит), найдено сверх задания дирижёра тем же приёмом, что нашёл F9/F11 (закрытый список без элемента); `FR-006`, дословно повторявший прежний двухкатегорийный перечень, поправлен тем же раундом - здесь синхронизировано вслед за источником.

Definition of Done: инспекция API/UI для тестового недоставленного и пропущенного события - причина видна и совпадает со смоделированным сценарием; инспекция лога попытки для тестового события по каждой из трёх категорий исхода (HTTP-статус ошибки, таймаут ответа, отказ на этапе соединения) - каждая записана под своей категорией; code review.

Story Points: 5. Priority: Must. Dependencies: S-1.1, S-1.3.

**S-3.4. Эксплуатация переотправляет недоставленное событие вручную**

Story: Как эксплуатация, я хочу переотправить конкретное недоставленное событие вручную, чтобы закрыть инцидент без ожидания следующего автоматического цикла (которого уже нет - окно исчерпано).

Acceptance Criteria:
- `[FR-007]` Given недоставленное событие в пределах срока хранения (7 суток), When эксплуатация инициирует ручную переотправку, Then событие доставляется получателю.
- `[FR-007]` Given запись имеет причину «подписка неактивна» (пропущенное, не недоставленное), When эксплуатация пытается переотправить её вручную, Then API отклоняет операцию - переотправка недоступна для пропущенного, интегратор восстанавливает его сам (`FR-013`, S-3.5).

**S-3.5. Интегратор восстанавливает пропущенное после возврата подписки**

Acceptance Criteria:
- `[FR-013]` Given подписка была отключена или приостановлена, When интегратор возвращает её в работу и запрашивает перечень пропущенного, Then он получает полный перечень событий периода неактивности в пределах срока хранения (7 суток), без потерь.
- `[FR-013]` Given срок хранения (7 суток) истёк, When интегратор запрашивает перечень пропущенного за этот период, Then просроченные записи не возвращаются.
- `[Повторное чтение]` Given интегратор уже запрашивал перечень пропущенного, When он запрашивает его повторно в пределах срока хранения, Then перечень возвращается снова (чтение не расходует запись) - `[Assumption], источник: FR-013 говорит «получить перечень», не «подтвердить получение»; в отличие от FR-007 (мутирующая переотправка), здесь нет признака одноразового потребления; цена ошибки - если система на деле однократно консумирует список, интегратор теряет видимость после первого чтения без предупреждения`.

Technical Notes: восстановление - действие интегратора, эксплуатация пропущенное не переотправляет (`FR-007`, S-3.4 - разведены по предмету явно).

Definition of Done: e2e тест - пауза подписки на период с событиями -> после возврата интегратор получает полный перечень без потерь; негативный тест - запрос после истечения срока хранения не возвращает просроченные записи; code review.

Story Points: 3. Priority: Must. Dependencies: S-2.6 (приостановка/возврат), S-3.2 (автоотключение).

**S-3.6. Продукт и эксплуатация видят время исключения рядом с долей доставленного**

Story: Как продукт платформы, я хочу видеть время исключения подписок из знаменателя доли доставленного рядом с самой долей, чтобы не принять массовое отключение получателей за улучшение метрики.

Acceptance Criteria:
- `[FR-020]` Given период, для которого вычислена доля доставленного (S-1.5), When доля предъявляется продукту и эксплуатации, Then время исключения подписок из знаменателя за тот же период отображается рядом, в том же представлении.
- `[FR-020]` Given доля доставленного за период обновляется, When обновление происходит, Then время исключения обновляется не реже, чем сама доля (не реже раза в сутки).
- `[FR-020, P-34]` Given период, за который знаменатель доли (число событий, предъявленных к доставке по активным подпискам, П-9) равен нулю (например, все подписки периода отключены либо приостановлены), When доля предъявляется продукту и эксплуатации, Then вместо числового значения предъявляется явный признак «нет доставок за период», отличный от 0% и от 100% - подмена вырожденного случая любым из этих двух чисел не допускается.
- `[FR-020, P-34]` Given период с ненулевым знаменателем, When доля предъявляется, Then предъявляется обычное числовое значение - третье состояние («нет доставок за период») не подменяет собой штатный расчёт там, где он применим.

Technical Notes: форма предъявления (панель, отчёт, API) - design constraint, решение архитектуры, не фиксируется здесь. `Finding F18` (часть 2) закрыта `P-34`, перенесённым в `FR-020` ревизии 4: оба числа-кандидата для вырожденного знаменателя вводят в заблуждение - 0% неотличимо от «все доставки провалены» (ложный сигнал инцидента), 100% выглядит недостижимым идеалом там, где измерять было нечего; потребитель метрики обязан обрабатывать третье состояние помимо числа.

Definition of Done: инспекция/автотест - для любого периода время исключения присутствует рядом с долей в том же представлении; негативный тест вырожденного знаменателя - период с нулём событий, предъявленных к доставке, возвращает признак «нет доставок за период», не 0% и не 100%; позитивный тест - период с ненулевым знаменателем возвращает обычное числовое значение; code review.

Story Points: 5. Priority: Must. Dependencies: S-1.5, S-3.2 (источник периодов отключения).

**S-4.1a (FR-014, часть - переживает срез). Платформа объявляет условия изменения контракта доставки**

Acceptance Criteria:

- `[FR-014]` Given документация опубликована и выпуск по ветви (б) состоялся (S-5.3), When эксплуатация выборочно сверяет обращения интеграторов за период после выпуска, Then в выборке не встречается ни одного упоминания того, что интегратор узнал о возможности экстренной замены только из самой замены, а не заранее из документации - критерий оценивает найденное в выборке, не всю популяцию обращений.

Technical Notes: класс - документационный/процессный deliverable, не поведение кода (как и весь `FR-014`). Technical Notes: измеряется отдельно от ветви (б) (S-5.3) - раздельные счётчики, не общая доля (по образцу `FR-001`/`FR-016`, `BA-09`); смешение сделало бы 100% недостижимыми при первом же выпуске по исключению. `OQ-SW-2` закрыт постановщиком (`P-33`, гейт stories, раунд 1): обе ветви `FR-019` действуют независимо на одном предмете - отклонённые альтернативы (приостановка отсчёта планового окна; поглощение планового уведомления экстренным) требовали бы механизма связывания ветвей, которого не называет ни `BR-016`, ни `FR-019`, либо забирали бы у интегратора плановое предупреждение о более широком выводе предмета. **S-5.3. Экстренная замена механизма подтверждения подлинности как мера безопасности**

Story: Как безопасность (владелец оценки применимости исключения П-11), я хочу выпустить замену скомпрометированного механизма подтверждения подлинности немедленно, без выдержки 90-суточного срока, и уведомить интеграторов одновременно с выпуском, чтобы устранить уязвимость без окна, в течение которого подделка остаётся принимаемой.

Acceptance Criteria:
- `[FR-019, ветвь б]` Given подтверждена уязвимость либо компрометация механизма подтверждения подлинности (`FR-012`), When безопасность оценивает применимость исключения П-11 и подтверждает её, Then изменение выпускается новой версией схемы без выдержки 90-суточного срока.
- `[FR-019, ветвь б]` Given выпуск по исключению произошёл, When подписанные интеграторы уведомляются, Then уведомление уходит одновременно с выпуском (не раньше и не позже), с объявлением назначенного безопасностью периода сосуществования старого и нового признака (при компрометации секрета механизма - нулевого).
- `[FR-019, ветвь б, негативный]` Given изменение помечено как срочное, When post-factum разбор проверяет запись оценки безопасности в аудит-логе, Then при отсутствии такой записи изменение не признаётся покрытым исключением - идёт по обычному сроку ветви (а) (S-5.2).
- `[FR-019, P-33]` Given по тому же предмету уже идёт плановое окно ветви (а) (S-5.2), When выпуск по ветви (б) происходит на этом предмете, Then выпуск не отменяет, не поглощает и не приостанавливает плановое окно; подписанный интегратор получает оба уведомления (плановое и экстренное) и различает их сам по названному предмету каждого.
- `[FR-019, P-34, A-RA8]` Given канал уведомления недоступен для отдельного адресата, When наступает момент выпуска по ветви (б), Then недоступность канала для этого адресата не откладывает и не отменяет момент выпуска ни для него, ни для остальных подписанных интеграторов; неуспех уведомления адресата наблюдаем эксплуатацией (`NFR-010`), попытка повторяется в пределах срока хранения (7 суток).
- `[NFR-010, часть в]` Given выпуск по исключению произошёл, When эксплуатация инспектирует аудит-лог, Then зафиксирована отдельная запись: момент оценки применимости безопасностью, момент выпуска, назначенный период сосуществования, факт и исход рассылки экстренного уведомления по каждому адресату (доставлено/не доставлено/таймаут).
- `[NFR-010, P-33]` Given ветвь (а) и ветвь (б) сработали на одном и том же предмете, When эксплуатация инспектирует аудит-лог, Then обе записи присутствуют раздельно - запись одной ветви не объединяется и не замещает запись другой по тому же предмету.
- `[Каскад]` Given период сосуществования назначен нулевым (компрометация секрета механизма), When получатели, не успевшие перейти на новый признак, отвергают доставку, Then отвергнутые доставки уходят в стандартный цикл: недоставленное (S-3.3) -> при непрерывном отказе 24 ч -> автоотключение (S-3.2) -> время исключения растёт и предъявляется рядом с долей доставленного (S-3.6) - `[покрыт составом существующих историй, BRD находка C-11: разрешена с ценой, новых требований не порождает]`.

Technical Notes: применимость исключения к конкретному изменению оценивает безопасность, не автор изменения (тот же порядок, что и П-10) - RACI: `R` разработка платформы, `A` безопасность. От замены секрета одной подписки интегратором (`FR-009`, S-2.7, всегда с окном перекрытия) отличается предметом: здесь меняется сам механизм для всех подписок платформы, там - значение секрета для одной. `OQ-SW-2` закрыт `P-33` (см. Technical Notes S-5.2 для полного разбора отклонённых альтернатив); недоступность канала уведомления закрыта требованиями допущением `A-RA8` по аналогии с `P-34` (`FR-005`).

Definition of Done: e2e тест ветви (б) - симуляция экстренного выпуска, уведомление зафиксировано в тот же момент, что и выпуск; негативный тест - выпуск без записи оценки безопасности не признан покрытым исключением; тест независимости - выпуск по ветви (б) на предмете с уже идущим плановым окном не меняет плановое окно, обе записи присутствуют в аудит-логе раздельно; негативный тест канала - недоступный канал уведомления у одного адресата не откладывает момент выпуска, неуспех виден в аудит-логе, повторная попытка зафиксирована в пределах срока хранения; каскадный сценарий (нулевой период -> массовое отключение -> рост времени исключения) воспроизведён и наблюдаем в S-3.6; code review.

Story Points: 8. Priority: Must. Dependencies: S-2.8 (`FR-012`), S-3.2, S-3.6, S-2.10, S-4.1a (документация об исключении должна существовать до первого реального выпуска по этой ветви - иначе интегратор узнаёт о возможности из самой замены).

**Находка (к источнику, не к этому файлу):** ранжирование T-shirt-оценок BRD раздела 18 (L > M > S по определению T-shirt-шкалы) не воспроизводится в сумме story points после декомпозиции:

- E-2 (`M`) = 44 story points - **больше**, чем E-1 (`L`) = 24. Медиум-эпик тяжелее крупного по сумме карточек.
- E-3 (`M`) = 37 story points - также больше E-1 (`L`) = 24, тем же образом.
- E-4 (`S`) = 24 story points - **равен** E-1 (`L`) = 24. Малый эпик по сумме сравнялся с крупным.
- E-5 (`S`) = 18 - меньше E-1 (`L`), единственная пара, где порядок T-shirt и порядок SP согласованы.

Инверсия не привнесена правками этого раунда: пересчёт по состоянию ревизии 1 (до находок F14-F18) даёт тот же порядок с меньшим разрывом (E-1=24, E-2=39, E-3=32, E-4=24, E-5=18) - находка существовала с раунда 1, ось её просто не прогоняла (это и есть предмет F17). Правки раунда 2 (S-2.5 +2, S-2.6 +3 в E-2; S-3.2 +3, S-3.6 +2 в E-3) увеличили разрыв, но не создали его.

**Разбор причины (для постановщика, не решение узла):** возможных объяснений два, и разграничить их - не в полномочиях этого узла: (1) T-shirt-калибровка BRD раздела 18 недооценивает E-2/E-3 относительно E-1 либо переоценивает E-1 относительно E-4; (2) декомпозиция E-2/E-3 на стори получилась мельче/детальнее, чем декомпозиция E-1, и часть story points по факту отражает не сложность, а гранулярность разбиения. Оба объяснения требуют решения постановщика (пересмотр T-shirt либо укрупнение/дробление карточек), не подстановки узлом.

**Цель называется отдельным полем находок к источнику** (BRD, раздел 18, T-shirt-оценки эпиков E-1/E-2/E-3/E-4) - по правилу «дефект источника - находка вверх, не своя дыра» не понижает `status` этого выхода: FR/NFR-полнота набора историй (раздел 7) не задета, каждый FR/NFR по-прежнему закрыт минимум одной историей независимо от того, верна ли T-shirt-калибровка эпика, которому эта история принадлежит.

## 9. Открытые вопросы (обе закрыты постановщиком на гейте stories, раунд 2)

**OQ-SW-1. Политика конфликта при параллельном изменении состояния одной подписки - ЗАКРЫТ (`P-32`, постановщик, гейт stories раунд 1).**

Был поднят: `FR-008` даёт интегратору изменять состав типов, адрес, приостанавливать и удалять подписку через API, но не называл политику при конкурентных запросах на одну подписку (два `PATCH` состава типов одновременно; `PATCH` адреса против `DELETE`; смена адреса против отправки оповещения «в полёте»). Из трёх вариантов, названных узлом в раунде 1 ((а) last-write-wins, (б) оптимистичная блокировка, (в) сериализация по ресурсу), рекомендовался (б).

Решение постановщика (`P-32`): конкурентное изменение поверх устаревшего представления подписки отклоняется с названной причиной; тихая потеря параллельного изменения запрещена. Конкретный механизм (ETag/If-Match, сериализация в очереди и т.п.) - решение зоны 2/архитектуры, не фиксируется на уровне истории и в AC не назван по имени. Применено в `S-2.5` и `S-2.6` (AC `[FR-008, P-32]`); реестр полноты (раздел 7) закрыл клетку «гонка» этой строкой.

**OQ-SW-2. Взаимодействие планового 90-суточного уведомления (`FR-019` ветвь а) и экстренного релиза по исключению П-11 (`FR-019` ветвь б) на одном и том же элементе - ЗАКРЫТ (`P-33`, постановщик, гейт stories раунд 1).**

Был поднят: источник описывает обе ветви `FR-019` как измеряемые раздельно (`BA-09`), но не описывал случай, когда для одного и того же элемента уже идёт плановое 90-суточное окно, а посреди него наступает необходимость экстренного релиза по исключению П-11. Из трёх вариантов, названных узлом в раунде 1 ((а) независимое отслеживание, (б) приостановка планового окна, (в) поглощение планового экстренным), рекомендовался (а) - тот же вариант, который выбрал постановщик.

Решение постановщика (`P-33`, вариант а - независимое отслеживание): обе ветви действуют независимо на одном предмете, ни одна не отменяет/не поглощает/не приостанавливает другую; интегратор получает оба уведомления, `NFR-010` фиксирует обе записи раздельно без замещения. Применено в `S-5.2` и `S-5.3` (AC `[FR-019, P-33]` и `[NFR-010, P-33]`); реестр полноты (раздел 7) закрыл клетку «гонка» этой строкой.

Обе развилки, из-за которых исход узла в ревизии 1 был `partial` (не статус документа - см. пояснение носителей в шапке выше), закрыты постановщиком без искажения предложенной узлом рекомендации; узел решение не подставлял, только сверил внесённое `P-32`/`P-33` с материалом требований rev.4 (`FR-008`, `FR-019`, `NFR-010`).

### Новые допущения этого узла (источник, цена ошибки - в реестре полноты раздела 7 и в карточках историй)

| # | Story | Принято | Цена ошибки |
