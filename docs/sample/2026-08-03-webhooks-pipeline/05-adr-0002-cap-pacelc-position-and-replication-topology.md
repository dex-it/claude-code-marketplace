# ADR-0002: Позиция по CAP/PACELC и топология репликации

## Status

Proposed

## Date

2026-08-03

## Decision Drivers

- `FR-008`/P-32 требует, чтобы конкурентное изменение подписки поверх устаревшего представления
  отклонялось с причиной, а тихая потеря была невозможна в принципе - две расходящиеся копии состояния
  подписки делают это требование неисполнимым структурно, а не по вероятности.
- `NFR-006` явно разрешает жертвовать своевременностью доставки ради нуля потерь при отказе подсистемы,
  но не разрешает обратное.
- Оптимистичная конкурентность на подписке (см. ADR-0003) требует read-your-writes: клиент, только что
  получивший актуальную версию ресурса, не должен получить отказ по причине устаревшего чтения на
  следующем же запросе.
- Захват задачи доставки (claim) и учёт лиза обязаны исходить из единственного согласованного взгляда
  на состояние очереди - чтение с отстающей реплики способно нарушить уникальность лиза и превысить
  лимит одновременных попыток на подписку (изоляция, отдельное решение дизайна).
- Наблюдаемость (`FR-020`) требует обновления не реже раза в сутки - отставание в секунды не задевает
  ни одно требование к этой поверхности.

## Context

Платформа несёт два класса состояния с разными требованиями к согласованности: управляющее состояние
(реестр подписок с версией, конвейер доставки с захватом задач и лизами) и наблюдательное состояние
(метрики доли доставленного, операционные перечни). Для управляющего состояния действует запрет тихой
потери конкурентного изменения (`FR-008`/P-32) и запрет безвозвратной потери события (`NFR-002`); для
наблюдательного - только суточная свежесть (`FR-020`). Требуется явная позиция по поведению при
сетевом разделении и топология репликации хранилища, обслуживающая обе поверхности без единой
неверной по умолчанию настройки.

## Decision

**Позиция CAP:** для состояния подписки и конвейера доставки платформа выбирает согласованность, а не
доступность записи при сетевом разделении (CP) - сторона, лишённая доступа к первичному узлу хранения,
не принимает записи (управляющий API отвечает отказом "сервис временно недоступен"; конвейер доставки
приостанавливает выдачу новых задач, а не продолжает работу поверх потенциально расходящейся копии).

**Позиция PACELC - по операциям, не одна на систему:**

- Запись и чтение состояния подписки (управляющий API) - PC/EC: чтения обязаны идти с первичного узла,
  чтобы клиент, получивший версию ресурса, немедленно видел её в следующем запросе.
- Захват задачи доставки и фиксация исхода попытки - PC/EC: захват с отстающей реплики нарушает
  уникальность лиза и способен превысить лимит одновременных попыток на подписку.
- Наблюдаемость (доля доставленного, операционные перечни) - PA/EL: чтение допускается с реплики,
  отставание которой не задевает суточную свежесть, требуемую `FR-020`.

**Репликация:** синхронная репликация в кворуме "любая 1 из 2" кандидатов-реплик, а не единственный
синхронный standby. Единственный синхронный standby делает свой собственный отказ причиной остановки
записи на первичном узле - защита долговечности данных превращается в отказ доступности записи; кворум
из двух кандидатов устраняет эту зависимость ценой третьего узла хранения.

## Consequences

### Positive

- Запрет тихой потери конкурентного изменения (`FR-008`/P-32) выполняется структурно: расходящихся
  копий состояния подписки не существует по построению, а не по добросовестности реализации.
- Read-your-writes для управляющего API гарантирован без клиентских обходных решений (повторных чтений,
  задержек перед следующим запросом).
- Наблюдательная поверхность не нуждается в специальной обработке согласованности - обычное чтение с
  реплики достаточно для заявленной свежести.

### Negative

- Доступность записи приносится в жертву при сетевом разделении: сторона без первичного узла
  отказывает в записи вместо продолжения работы поверх временно расходящейся копии.
- Единственный первичный узел хранения остаётся единой точкой отказа для операций записи по построению
  этого решения.

### Risks

- Кворум "1 из 2" стоит третьего узла хранения вместо двух - это принятая цена, а не побочный эффект.
- Пауза доставки на время разделения сети превращается в задержку, которая догоняется после
  восстановления (`NFR-006` это прямо допускает); расхождение состояния подписки, будь оно допущено, не
  "догонялось" бы уже никогда - именно этой асимметрией мотивирован выбор CP.
- Решение принято при известной, умеренной географии развёртывания; распределённая по нескольким
  географически разнесённым точкам запись потребует пересмотра этой позиции - основания для такого
  пересмотра сейчас нет.

## Alternatives Considered

### AP для состояния подписки

При разделении сети обе стороны продолжают принимать записи, расхождение улаживается позже.

- **Pros:** доступность записи сохраняется во время любого сетевого разделения.
- **Cons:** две расходящиеся копии состояния подписки делают запрет тихой потери конкурентного
  изменения (`FR-008`/P-32) неисполнимым в принципе - улаживание расхождения после факта неизбежно либо
  теряет одно из изменений молча, либо требует ручного вмешательства на каждый случай.
- **Why rejected:** прямое противоречие ограничению постановщика, не вопрос степени риска.

### Чтение управляющего API с реплики

Запросы на чтение представления подписки обслуживаются любой доступной репликой для снижения нагрузки
на первичный узел.

- **Pros:** снижает нагрузку чтения на первичный узел, повышает доступность чтения при его перегрузке.
- **Cons:** клиент, только что получивший версию ресурса с первичного узла, может получить отказ 412 на
  корректный следующий запрос, если реплика ещё не догнала эту запись - ложный отказ вместо
  подтверждённого конфликта.
- **Why rejected:** подрывает механизм оптимистичной конкурентности (ADR-0003), для которого read-your-
  writes - предпосылка, а не удобство.

### Единственный синхронный standby

Одна синхронная реплика вместо кворума из двух кандидатов.

- **Pros:** дешевле на один узел хранения.
- **Cons:** отказ единственного standby останавливает коммиты первичного узла - защита долговечности
  данных превращается в отказ доступности записи именно в момент, когда репликация больше всего нужна.
- **Why rejected:** цена узла принята сознательно ради устранения этой зависимости; альтернатива меняет
  один риск на другой без явного выигрыша.
