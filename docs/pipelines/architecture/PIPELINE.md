# Конвейер дизайна: фазы, диспетчинг, гейты

Как устроена зона «требования -> одобренный дизайн» движка `dex-sdlc:engine`: какими фазами она
ведётся, кто их исполняет, где решение делегируется специализированному узлу, и в каких случаях
работа останавливается ради решения человека. Конспект `dex-skill-architecture-track:
architecture-track` (`SKILL.md`) - полные формулировки фаз, входные/выходные контракты по полям и
handoff-механика читаются там; здесь - обзор устройства для читателя, которому операционный формат
скилла не нужен.

**Целевое состояние: одобренный дизайн-документ + implementation plan без переигрывания
архитектурного решения оркестратором.** Прежний монолит (`architect`) решал архитектуру и вёл фазы
сам в одном теле; трек существует, чтобы развести «вести зону» (требования, capacity, план,
диспетчинг документации) и «решить архитектуру» (специализированный узел) - тот же принцип, что у
`development-track` с кодом.

Вызывается движком (`/design`), не запускается отдельно от него: движок ведёт цикл и стоп-линию,
трек - порядок этой зоны.

## Фазы

| # | Фаза | Кто исполняет | Делегирование |
|---|---|---|---|
| 0 | Bootstrap | трек | - |
| 1 | Understand Requirements | трек | - |
| 2 | Capacity Estimation | трек | - |
| 3 | Design Decision | узел по стеку | `dex-architect:architect` / `dex-architect-dotnet:architect-dotnet` |
| 4 | Implementation Plan | трек | - |
| 5 | Document (условно) | узел по типу артефакта | `dex-adr-writer` / `dex-api-designer` / `dex-diagram-creator` |
| 6 | Design Acceptance | узел | `dex-design-reviewer:design-reviewer` |

Фазы 0-2 и 4 трек ведёт сам (`channel: self` в журнале исполнителей); фазы 3, 5, 6 - всегда делегированы
(`channel: delegated`) - архитектурное решение и приёмку трек не переигрывает.

Bootstrap восстанавливает контекст репо (recall-источники, стек по манифесту, `Accepted` ADR,
журнал решений) и классифицирует запрос - новый дизайн или дельта-прогон над уже принятым решением;
дельта ищется в журнале раньше повторного вопроса. Understand Requirements переводит бизнес-задачу
(или выход зоны требований - `FR`/`NFR`+stories из `/feature`) в проверяемые FR/NFR и security/data-
sensitivity слоты; вход только BRD без системного уровня принимается, но с явной пометкой «звено
зоны требований не пройдено», не молчаливой выдачей за полный набор. Capacity Estimation - back-of-envelope
QPS/storage/bandwidth, опора для решения узла. Implementation Plan раскладывает принятое решение на
инкременты с DoD, success metric и критериями `[FR-NNN]`/`[NFR-NNN]` - вход `development-track`;
свёрнутая форма (один инкремент) допустима только для точечного изменения без нового
сервиса/инфраструктуры/миграции данных. План - файловый артефакт по ключу `plans` расклада корпуса
со своим оракулом (`plan-quality`) и вердиктом Phase 6, не раздел ответа трека: зона разработки
читает файл.

## Диспетчинг по стеку (Phase 3)

Манифест затронутой папки несёт `*.csproj`/`*.sln`/`Directory.Build.props` -> узел
`dex-architect-dotnet:architect-dotnet`; иначе -> `dex-architect:architect` (стек-нейтральный).
Монорепо - диспетчинг по папке, не по корню репозитория. Узел получает FR/NFR, цифры, constraints,
`mode`, `Accepted` ADR и журнал решений; исполняет свой внутренний порядок (Reference Architecture
Match -> Propose Alternatives -> Decide -> Deep Dive) и отдаёт решение-only - без implementation-
плана и документов, это работа треков-фаз 4 и 5.

## Гейты

Гейт блокирующий тогда и только тогда, когда решение стоит на внешнем оракуле - источнике вне кода,
требований и фактов о системе. Решение, выводимое из материала, не блокирует ни в каком режиме.

| Гейт | Тип | Фаза | `interactive` | `autonomous` |
|---|---|---|---|---|
| Бюджетная/продуктовая рамка, приоритет NFR | блокирующий | 1, поздний 3 | работа встаёт, решает оператор | `partial` + перечень несогласованного |
| Выбор альтернатив, содержание deep-dive | неблокирующий | 3 | предъяви + продолжай на предложенном | решает узел, допущением в Output |
| Вердикт `design-reviewer` не `passed` | блокирующий | 6 | возврат на доработку / эскалация | `partial` + перечень |

`mode` приходит на входе трека (дефолт `autonomous`) и передаётся без изменения во все делегированные
вызовы - узел канал сам не определяет.

## Document (Phase 5) и Design Acceptance (Phase 6)

Диспетчинг документации - независимые условные вызовы, не монолитный шаг: решение необратимо или
дорого обратимо - порог считается перечнем задетого при отмене, а не новизной нормы (pre-check
`project-docs-map`) -> `adr-writer`; новый/изменённый API-контракт ->
`api-designer`; структурная диаграмма затребована или сложность решения того требует ->
`diagram-creator`. Не затребованный артефакт помечается явно, не тишиной.

Design Acceptance отдаёт пакет решения (Phase 3/5) `design-reviewer` до передачи в
`development-track` - независимый взгляд, которого не было у монолитного узла. Цикл автор-судья:
находки -> доработка тем же узлом Phase 3 -> повторная приёмка, с потолком ревизий
(`docs/AGENT_FRAMEWORK.md#inter-agent-handoff-последовательный-стык`). Метку `quality-checks`
(`design-quality`) ставит судья, не автор.

## Handoff в development-track

Путь файла плана (Phase 4, `quality-checks: plan-quality passed`) + одобренный design-документ
(`quality-checks: design-quality passed`) + путь к журналу решений + `quality-checks` сквозным
полем. Маршрут решает движок, не трек.

## Journal и границы

Каждый узел, принявший решение, дописывает журнал своими строками: `architect`/`architect-dotnet` -
за Phase 3, трек сам - за Phase 1 (эскалированные гейты) и Phase 4 (объём инкрементов).

Трек не принимает архитектурного решения и не переигрывает узел Phase 3. Ревью уже реализованной
кодовой архитектуры (`/review-arch`) - точечный вход у `dex-architect` напрямую, не через этот трек:
другой источник (код, не бизнес-задача). Код зона не пишет - выход всегда design-документ +
файл implementation plan.
