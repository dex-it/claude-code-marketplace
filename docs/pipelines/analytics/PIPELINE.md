# Конвейер требований: классы, порядок, гейты

Как устроена работа зоны «идея -> допуск к разработке»: какими единицами она ведётся, в каком
порядке, что проверяется на стыках и в каких случаях останавливается ради решения человека.

**Целевое состояние: сформулированная идея доходит до кода без участия человека.** Конвейер
существует не ради документов, а ради комплекта, которого достаточно для автоматической реализации;
всё, что реализатору пришлось бы додумать, - дефект комплекта, а не свобода исполнителя (раздел 13).

## Требования к конвейеру

Чего мы ждём от конвейера. Каждое требование написано так, как его читает оператор, и рядом сказано,
чем его проверить: требование, для которого способ проверки назвать нельзя, в список не входит - по
тому же правилу, по какому сам конвейер не принимает требование без метода проверки (раздел 2).

| # | Чего ждём | Как проверить |
|---|---|---|
| R-1 | по готовому набору можно писать код, ничего не додумывая | человек читает набор так, как читал бы перед написанием кода, и выписывает всё, что пришлось бы решить самому; список пуст (раздел 13) |
| R-2 | человека не дёргают по пустякам | пока не всплыло невыводимое - решение, цена ошибки которого лежит вне артефакта, граница объёма, приоритет при конфликте целей, - оператора останавливают ровно дважды: после BRD и на приёмке набора. Всё, что выводится из уже принятого, конвейер достраивает сам и пишет строкой отчёта (разделы 1, 6) |
| R-3 | ничего не придумано молча | у каждого решения о том, как система себя ведёт, назван источник: принятое требование, записанное решение человека или открытый пункт, который ждёт ответа (разделы 1, 5) |
| R-4 | работа заканчивается, а не крутится по кругу | при правке каждое требование пересматривается один раз за проход; у переписки автора с судьёй есть счётчик ревизий; список того, что пришлось бы додумать, от ревизии к ревизии уменьшается (разделы 8, 11, 13) |
| R-5 | второй запуск ничего не портит, прерванный - продолжается | запуск без новых данных не меняет ни одного документа; прерванный прогон подхватывает с первой незакрытой фазы, а не начинает заново (раздел 10) |
| R-6 | видно, откуда требование взялось | у каждого требования записано, на чём оно держится (идея, другое требование, решение человека, внешний документ); потребители единицы хранимым списком не ведутся, а находятся поиском по номеру в момент правки (раздел 8); проверенное помечено версией, по которой судили (разделы 5, 8, 12) |
| R-7 | чужое не портим | правка нашей фичи не меняет требования соседней фичи мимо её приёмки - только помечает их «основание изменилось» для владельца (раздел 8) |
| R-8 | конвейер не отказывается работать | тема в одну строку, чужой документ или код без постановки - нормальный вход: работа идёт, недостающее восстанавливается и помечается (раздел 1) |
| R-9 | каждое требование можно проверить | у каждого `FR` и `NFR` назван способ проверки; принимает не тот, кто писал, а отдельный проверяющий (разделы 2, 12) |
| R-10 | требования не противоречат друг другу | два требования, которые нельзя выполнить одновременно, и расхождение с уже принятым выносятся находкой - обе формулировки рядом; если одно требование поглощает другое, это находка «возможно, дубль» (разделы 5, 10) |

Кейсы [pipeline-basic.md](../../../tests/_cases/pipeline-basic.md) несут обратную ссылку: у каждого
названо, какое требование он держит, - иначе непокрытое требование видно только на живом прогоне.

**Требования конвейера сталкиваются друг с другом, и приоритет схемой не назначается.** Полнота
(R-1) требует поднять каждое незакрытое место, экономия внимания (R-2) - не поднимать ничего
выводимого; на границе, где место незакрыто, а вывести его можно лишь допущением, обе стороны
обоснованы одинаково. Это ровно строка «приоритет при конфликте целей» таблицы раздела 1: обе цели
приняты, основание для выбора в них не содержится - значит выбор идёт оператору вопросом, вместе с
названной ценой каждой стороны, а не разрешается фиксированным весом в схеме. Вес, записанный здесь,
был бы решением за оператора, принятым один раз и молча применённым ко всем фичам.

Дом норм стандартов - [NORMS.md](NORMS.md): этап, информационный элемент, атрибуты требования, слои
нормы, стадии документа. Здесь эти нормы не пересказываются; предмет этого документа - порядок работ
и единицы, которыми он идёт. Контракт узла (вход, выход, статусы, сквозные поля) - `node-contract`,
расположение артефакта - `project-docs-map`, `docs-layout` и `artifact-naming`.

## 1. Целевая функция: рутина уходит машине, человеку остаётся невыводимое

Конвейер сводит `BR`, `UC`, `FR`, `AC` друг с другом. Большая часть этой работы счётная: развернуть
расширения сценария в правила-кандидаты, подобрать к правилу граничные примеры, пересчитать
покрытие стыка, продолжить нумерацию, собрать свод, найти дубль и противоречие, при правке назвать
задетые единицы по трассе. Всё перечисленное выводится из уже принятого и **человека не касается**.

Человека касается только то, что из источника не выводится:

| Не выводится | Почему |
|---|---|
| полномочная ось | цена ошибки лежит вне артефакта |
| приоритет при конфликте целей | обе цели приняты, основание для выбора в них не содержится |
| граница объёма | «этого не делаем» - решение, а не следствие |
| мера, которой нет в источнике | число берётся из намерения стороны, не из текста |
| исход, у которого нет основания ни в одной принятой единице | догадка станет нормой без решения |

**Ось - предмет решения, по которому у фичи возможны разные исходы с разной ценой.** Оси не берутся
из перечня: их видно при разборе конкретной фичи, и называет их тот, кто разбор ведёт, - узел либо
оператор. Ось **полномочная**, когда цена ошибки лежит вне артефакта: последствие несёт сторона за
границей набора, и правильный исход не выводится ни из одной принятой единицы.

**Названная узлом ось полномочий не даёт.** Ось - имя предмета решения, а не санкция на его закрытие:
закрыть пункт за человека позволяет режим (`autonomous`) и выводимость исхода из принятого, а не то,
как ось названа и кем. Обратный ход запрещён тем же: пункт не становится выводимым оттого, что его
ось названа инженерной, проектной или технической.

Признак применяется к пункту, не к теме. Пример: «одна незавершённая смена на пользователя против
нескольких» - ось, увиденная при разборе фичи и ни в каком перечне не стоящая; цену ошибки несут
пользователь и поддержка, то есть она лежит вне артефакта - ось полномочная, и названа она при этом
инженерной. Обратный пример: «формат идентификатора во внутреннем вызове» - цена ошибки замкнута в
реализации, исход выводится из принятых единиц, человек не нужен.

**След остаётся всегда, остановка - только на невыводимом.** Выведенное чинится в ходе работы и
фиксируется строкой отчёта: что достроено и из чего выведено. Это не тихая правка - проверяемый след
есть; но ответа он не требует и работу не держит. Смешение двух вещей даёт либо конвейер, дёргающий
человека на каждом шаге, либо конвейер, достраивающий требования молча.

**Невыводимое поднимается пачкой и в форме вопроса-с-предложением**, не голым вопросом: назван
предложенный исход и основание («принял X, потому что Y»). Ответ «да» закрывает пункт без работы, и
это и есть снятая рутина. Пачкой - потому что три остановки подряд по одному пункту стоят дороже
одной с тремя пунктами.

**У невыводимого две формы, и они не смешиваются.** **Допущение**: предложенный исход применяется
сразу, помечается допущением с названным основанием, и пачка подтверждается целиком - молчание работу
не держит. **Вопрос**: пункт остаётся открытым до ответа, решается поштучно, и производное от него не
пишется. Разделение не косметическое: пункт, поданный допущением вместо вопроса, закрывается
молчанием, а пункт, поданный вопросом вместо допущения, раздувает пачку до неотвечаемой и возвращает
конвейер к остановке на каждом шаге.

**Форму различает тест на самом пункте, не тема пункта и не его ось.** У исхода назван отклонённый
вариант сопоставимой цены - был выбор, а не вывод: пункт идёт **вопросом**. Вне артефакта есть
общепринятый дефолт, и отклонённый вариант либо не назван, либо заведомо хуже, - исход существует без
решения стороны: пункт идёт **допущением**. Одна ось даёт и то и другое, поэтому форма назначается
пункту, а не оси целиком; в `autonomous` тест решает не форму предъявления, а состав: вопрос
закрывается выводом из принятого и идёт в перечень принятых за оператора решений вместе с
альтернативой, которая была отклонена.

**Ответ на часть пачки работу не блокирует.** Продолжается всё, что от открытых пунктов не зависит;
сами пункты остаются названными в выходе и в `decision-log`, и набор с открытым пунктом
завершённым не считается. Догадкой открытый пункт не закрывается - иначе остановка теряет смысл.

**Снаружи процесс - один вход и одна остановка.** Классы, гейты и стыки этого документа - внутреннее
устройство; оператор называет фичу, отвечает на одну пачку вопросов и принимает набор. Число
внутренних узлов на его работу не влияет и в его поле зрения не выносится.

**Непроработанный вход работу не останавливает.** Идея без меры, документ, написанный вне конвейера,
требования, живущие только в коде, - это материал, а не дефект: узел разбирает его, восстанавливает
недостающее и фиксирует в форме своего класса - новой единицей, а не правкой исходного текста:
исходник остаётся источником. Восстановленное помечается реконструкцией, несёт указание, из чего
выведено (абзац документа, место в коде), и подтверждается на ближайшей остановке - вместе с прочим
невыводимым, отдельного разбирательства не заводит. Место, где источник допускает два прочтения, -
невыводимое: оно идёт вопросом, а не выбирается разбором.

**След пишется на диск, а не растворяется в ответе узла**, и лежит он в трёх местах по сроку жизни
и по ценности:

| След | Что несёт | Где | Что при утрате |
|---|---|---|---|
| `decision-log` - журнал решений `node-contract` на предмете «требование» | решение человека на остановке, допущение с исходом, открытый пункт, находку гейта с её исходом, отклонённые альтернативы, род изменения при правке | корпус фичи, едет с MR | решения поднимаются заново - невосстановимо иначе |
| записи `quality-checks` | вердикт проверки: что судилось, чем, с каким исходом и по какой версии текста | файлом рядом с артефактом (`node-contract`, словарь полей) | пересуживается |
| `feature-ledger` | где остановились, какие фазы закрыты, какие вопросы заданы и ждут ответа, какие пути разрешены | вне рабочего дерева, как `auto-ledger` автономного движка | прогон начинается сначала, корпус цел |
| `.req_counter` | последний выданный номер по ключу, файл на ключ: `feature` плюс формы `NN.<КЛАСС>` в блоке фичи (`NN.BR`, `NN.UC`, `NN.FR`, `NN.NFR`, `NN.ST`, перечень не закрытый) | при корпусе (репозиторий корпуса), едет с MR; путь к нему - в `.docs_layout` | восстанавливается проходом по номерам единиц; теряются блоки фич, не успевших ничего записать (раздел 10) |
| `.docs_layout` | пути: корень корпуса, места классов, путь `.req_counter` | корень репозитория, имя фиксировано конвенцией, едет с MR | восстанавливается поиском по стандартным местам и записывается заново (`project-docs-map`) |

Разделение не бухгалтерское. **На `decision-log` ссылаются сами требования** - это вид основания
(раздел 8), и его потеря переоткрывает принятое; поэтому находка с её исходом живёт там же, где
решение, а не в метке: метка сообщает, что источник дефектен, и не сообщает чем. Записи
`quality-checks` несут финальное состояние проверок и восстанавливаются повторным судом.
`feature-ledger` - служебное состояние прогона: он даёт дирижёру продолжить с места остановки, в том
числе после того, как контекст сессии свёрнут, и **в корпус не пишется** - иначе служебное состояние
утекает в MR (`project-docs-map`, разграничение с `auto-ledger`). Карта фич, наоборот, лежит в
корпусе и едет с MR: она общая для всех прогонов проекта, и вне рабочего дерева от неё не было бы
толку - соседняя ветка её бы не увидела.

Сверх аудита `decision-log` несёт главное: **однажды принятое решение человека не
переспрашивается**.

## 2. Класс требования - единица нормирования

Норма нарезана по классам, не по этапам: у `FR` и `NFR` разные входы, разные меры и разные способы
проверки, и оракул, судящий их одним набором правил, обязан угадывать слой единицы
([NORMS.md](NORMS.md), раздел 4). Класс даёт слою носитель.

| Класс | Вход | Выход единицы | Мера |
|---|---|---|---|
| `BR` | идея, цель стороны, бриф | исход для стороны | MOE, качественная допустима |
| `UC` | `BR` | актор, цель, ход, расширения, терминал у каждого | - |
| `FR` | шаги и расширения `UC`; несценарные ветки | правило одним предложением | MOP, метод верификации |
| `NFR` | `BR`, ограничения среды, чеклист качеств | мера с числом | MOP, метод верификации |
| `AC` | ветка `UC`, её `FR`, применимые `NFR` | пример к правилу: число, ветка, граница | - |

Граница `FR` и `NFR` проходит по способу проверки, не по теме: «ссылка действительна 15 минут» -
правило, проверяется примером; «письмо доставляется за 30 секунд в 95% случаев» - мера, проверяется
испытанием под нагрузкой.

**Форма правила задана тремя частями, а не шаблоном.** В предложении должно быть названо: случай,
когда правило действует; субъект, который действует; наблюдаемый результат. «Система должна работать
быстро» не проходит - нет ни случая, ни результата. Готовые шаблоны отраслевых нотаций берутся
образцами письма в class-skill `FR`, но проверка идёт по трём частям: буквальный шаблон по-русски
даёт канцелярит и натягивается не на всякое правило, а три части ловят главное - правило без условия
срабатывания и правило без наблюдаемого исхода.

**Метод верификации обязателен у каждого `FR` и `NFR`** - это сужение каталога, и оно названо
сужением, а не требованием стандарта. Методов может быть несколько: формулировка «ровно один из
четырёх» первоисточником не подтверждается (реестр: `contradicted`), поэтому записываются все
применяемые. Требование, для которого метод назвать нельзя, требованием не является: оно
возвращается в переформулировку либо поднимается как невыводимое.

**Чеклист ветки `NFR` - характеристики верхнего уровня модели качества 25010**, по одной проверке на
характеристику: дала `NFR` с числом либо объявлена неприменимой с основанием. Подхарактеристики
раскрываются только у применимых - иначе проход вырождается в два десятка отметок «нет». Полный
перечень уровней несёт статус `unverifiable` (реестр: текст за paywall, имена характеристик - по
описанию каталога и открытым вторичным источникам), поэтому в class-skill он называется опорой, а не
требованием стандарта.

Каждый класс несёт свой skill (создание и правка единицы) и свой оракул (вердикт по единице).

## 3. Контейнер - не класс

| Контейнер | Что несёт |
|---|---|
| BRD | `BR` плюс разделы бизнес-постановки |
| файл сценария | один `UC` |
| SRS | `FR` и `NFR` фичи |
| story | `AC` плюс нарезку работы |

Состав контейнера нормируется отдельно от единицы: иначе одна и та же таблица разделов расползётся
по двум class-skill и разойдётся при первой правке.

**BRD продукта и BRD фичи - один класс в двух вместилищах.** `BR` живёт там, где его предмет:
привязанное к фиче - в её BRD, общее для продукта - в продуктовом. Уровней у класса от этого не
появляется: пул номеров общий, за фичей закреплён блок. **Цель фичи трассируется на цель продукта,
где та есть**: `traced from` у `BR` фичи указывает на `BR-NNN` продуктового BRD, когда подходящая
цель найдена; не найдена - атрибут несёт цель или сторону, и факт называется строкой выхода. Второго
слоя требований трасса не заводит: она выражена существующим атрибутом, а не новым, и обязанности
заводить цель продукта ради неё нет - дельта-прогон `/product` решает оператор.
Разделение - способ не держать один список на весь продукт, а не второй слой требований.

**Единица, обслуживающая несколько фич, живёт на продуктовом уровне.** `NFR` про отклик всего API,
`BR` про общую цель, правило из общего словаря - дом у них продуктовый контейнер, фичи ссылаются на
них по ID. Копия в SRS фичи запрещена по той же причине, по какой мера `NFR` не переписывается в
story: две копии расходятся при первой правке.

**SRS наполняется по ходу разбора, а не собирается после него.** Правило пишется сразу в свой дом,
пример - сразу в story; промежуточного хранения у разбора нет, поэтому нет и шага переноса, на
котором свод расходится с источником. Рамочные разделы - назначение, объём, контекст, допущения,
ограничения среды, глоссарий - наследуются из BRD и сценариев выжимкой; собственного текста,
порождающего требования, в SRS нет.

Отсюда правило, которое держит всю конструкцию: **SRS не бывает источником правила.** Понадобилось
правило при сборке рамки - оно заводится разбором и проходит стык `UC -> FR`, а не появляется прямо
в документе. Иначе контейнер становится вторым входом в набор, мимо гейта.

## 4. Порядок выводится из входов

```
идея ──► BR ──┬──► UC ──► FR ──► нарезка на stories с AC
              │                   ▲
              └──► NFR ───────────┴──► свод в SRS
```

Порядок не задаётся прозой: он читается по колонке «Вход» раздела 2, и разойтись с ней не может.

**`NFR` идут своей веткой и сценариев не ждут.** У нагрузки, отклика, совместимости и регуляторики
нет ни актора, ни шага; из `UC` они не выводятся ни при каком качестве разбора.

**`AC` рождаются при нарезке в историю; черновик берётся с веток сценария.** Правило пишется вместе
с методом верификации - чем убедиться, что оно соблюдается, - и правило, для которого метод назвать
нельзя, не принимается. Пример же на конкретных данных принадлежит истории: одно правило проявляется
в нескольких историях разными примерами, и написанный при правиле пример пришлось бы растаскивать по
ним руками. К тому же между правилом и историей встают меры `NFR`, которых в сценарии нет вовсе, -
критерий, написанный до них, будет переписан.

Обратный порядок остаётся запрещённым: правило, извлечённое из готовых `AC` задним числом, не несёт
ничего сверх учёта и делает story вторым домом поведения.

Полнота проверяется с двух сторон: каждая ветка сценария покрыта хотя бы одним критерием в
какой-нибудь истории, и каждое правило породило хотя бы один критерий. Непокрытая ветка и правило
без примера - находки, а не умолчание.

Норма этого шага отдельного носителя не получает: форму правила держит class-skill `FR`, форму
примера и процедуру разбора - class-skill `AC`, техники подбора (границы, классы эквивалентности,
таблица решений, переходы состояний) берутся ссылкой на тест-дизайн - дом у них один, и второй
копией он не заводится. Вопрос, оставшийся без ответа при разборе, идёт наверх по правилу раздела 1,
а не превращается в правило-догадку.

**Несценарная ветка.** Фича, у которой наблюдаемого актором поведения нет вовсе - миграция,
регламент, техдолг, - идёт от `BR` сразу к правилам. Это условие с проверкой, а не исход по
умолчанию: иначе ветка станет способом пропустить разбор.

## 5. Стык: что передаётся и что проверяется

Форма стыка - `node-contract`: статусы исхода, словарь полей, транспорт указателями, реакция на
неполный вход, журнал решений. Здесь - предмет: какие единицы и какие поля едут по каждому ребру
конвейера требований и кто на нём что считает.

### Что передаётся

**Сквозной минимум ребра** едет на каждом стыке, даже если узел его не трогал:

| Что | Зачем |
|---|---|
| расположение: корень корпуса, путь артефакта | ступень 1 раздела 9 - следующий узел путь заново не разрешает |
| номер фичи | из него выводится старший разряд номеров, поэтому номера параллельных фич не пересекаются (раздел 10) |
| режим | канал ответа на остановке (раздел 6) |
| путь к `decision-log` фичи | принятые решения не переспрашиваются (раздел 1) |
| статусы единиц источника и записи `quality-checks` | производное не поднимается выше источника |
| открытые пункты и допущения | набор с открытым пунктом завершённым не считается |

Предмет каждого ребра - сверх этого минимума:

| Ребро | Что несёт вход потребителя | Что возвращается наверх |
|---|---|---|
| идея -> `BR` | тема либо проработанный вход как есть; известные ограничения и non-goals | путь BRD, `BR-NNN` со статусами, пачка невыводимого |
| `BR` -> `UC` | путь BRD и перечень `BR-NNN`, взятых в разбор | пути сценариев, `UC-...` с трассой на `BR`, расширения без исхода |
| `BR` + среда -> `NFR` | ограничения среды, чеклист характеристик, продуктовые `NFR` ссылками | `NFR-NNN` с мерой, методом и уровнем проверки |
| `UC` -> `FR` | пути сценариев и `UC-...`; действующие рамки (ADR, описание архитектуры) ссылками | `FR-NNN` с трассой и методом верификации, находки стыка |
| `UC`, `FR`, `NFR` -> story с `AC` | пути сценариев с их ветками; `FR-NNN` для нарезки; применимые `NFR` перечнем ID с путём SRS; non-goals | story с `AC` и ссылками, покрытие веток и правил, критерии-сироты находкой |
| набор -> допуск | корень корпуса, перечень единиц по классам со статусами, контракт интерфейса путём, действующие решения ссылками | список домыслов пробного разбора, вердикт приёмки |

**По ребру едут указатели, не копии.** ID и путь; формулировка переносится только там, где
потребитель обязан её процитировать (`AC` с меткой своего `FR`). Перенос нормативной формулировки
делает переносящего её автором и требует сверки с источником - правило и его цена в `node-contract`.

**Каждое поле именовано.** «Найди нужное в абзаце» на автоматическом стыке не работает: приёмник
тащит поля по именам. Расположение корпуса имени в словаре полей сегодня не имеет - завести при
реализации, иначе каждый узел назовёт его по-своему и сквозным оно быть перестанет.

**Производное не старше источника.** Единица, выведенная из того, что стоит в `review`, `approved`
не получает: иначе набор принят раньше, чем принято его основание.

**Статус носит единица, а не документ.** Один контейнер держит единицы в разных состояниях: правило
снято, соседнее в `review`, остальные приняты - потому апрув и отзывается в изменяемой части
(раздел 11), а «производное не старше источника» считается по единицам, не по файлам. По ребру едет
перечень единиц со статусами; форма записи статуса при единице решается при реализации.

**Покрытие стыка считает судья набора.** Ни производитель, ни потребитель: у первого нет входа
целиком, у второго - выхода. Комплектность входа при этом проверяет потребитель и отдельно от
качества артефактов (`node-contract`, приём входа): не пришёл `decision-log` или корень - статус с
перечнем того, что из-за этого не сверено, а не молчание.

**Стык `FR` -> `AC` лежит между узлами, а проверка на нём не зависит от числа узлов.** Правило без
примера покрытым не считается независимо от того, кто и когда его писал; критерий без правила в
набор не входит.

### Что проверяется

| Стык | Сверху вниз: каждая единица входа | Снизу вверх: чем замкнута каждая единица выхода |
|---|---|---|
| идея -> `BR` | дала `BR` с MOE либо объявлена вне объёма | фрагментом входа либо записью решения; `BR`, под которым нет ни того ни другого, - находка |
| `BR` -> `UC` | раскрыто сценарием, ушло в ветку `NFR`, признано несценарным (раздел 4) или вне объёма с основанием | `BR`, взятым в разбор; сценарий без `BR` - незаказанный объём |
| `BR` + среда -> `NFR` | категория чеклиста дала `NFR` с числом, объявлена неприменимой либо число поднято как невыводимое | `BR` либо нормой среды - ссылкой с ревизией; категория чеклиста - способ обнаружения, не основание; число сверх источника несёт запись `decision-log` |
| `UC` -> `FR` | каждый шаг и каждое расширение дали правило либо помечены «без правила» с основанием | `UC`; несценарная ветка - `BR` напрямую, правило из рамки - действующей нормой; вид основания назван |
| `FR` -> `AC` | у правила есть хотя бы один пример; правило без примера покрытым не считается | своим `FR`; пример без правила в набор не входит |
| `FR` -> story | каждое правило попало в нарезку | меткой `FR`; критерий-сирота - находка, а не мелочь оформления |
| `NFR` -> story | каждая применимая `NFR` получила назначенную проверку хотя бы в одной story | ссылкой на ID `NFR` (раздел 7) |

Строки идут в порядке таблицы передачи: у каждого ребра видно, что по нему едет и что на нём
считается. Вторая колонка - не зеркало первой: сирота дефект не везде. Правило без расширения
законно (несценарная ветка, правило из рамки), сценарий без `BR` - нет; поэтому колонка называет не
«источник во входе», а какой вид основания на этом ребре годится.

**У каждой строки есть третий исход - поднято как невыводимое** (раздел 1). Расширение, исход
которого ни из одной принятой единицы не следует, пометкой «без правила» не закрывается: она
означает «правила здесь не нужно», а не «правило неизвестно». Стык при этом проходится: строка
считается закрытой открытым пунктом, а набор с открытым пунктом завершённым не считается.

Стык `UC -> FR` - самый дорогой и сегодня не проверяется ничем: расширение без исхода это списанные
деньги при неудачной доставке и незакрытая блокировка.

**Сценарий, не давший ни одного правила, - находка, а не пройденный стык.** Пометки «без правила» с
основанием на каждом шаге для формального прохождения хватает, и ровно поэтому случай называется
отдельно: либо разбор не сделан, либо сценарий набору не нужен.

**Стык проверяется в обе стороны.** Сверху вниз - покрытие: каждая единица входа дала выход. Снизу
вверх - замкнутость: каждая единица выхода несёт годное на этом ребре основание; виды основания и
правило «хотя бы одно у каждой единицы» - раздел 8. Правило, чьё `BR` снято, висячим не остаётся:
оно либо снимается вместе с примерами, либо переприкрепляется к другому `BR` с основанием, либо
предъявляет основание другого вида - решение из `decision-log`, действующую норму. Тихое переприкрепление к
ближайшему подходящему это и есть потеря основания.

**Внешняя граница набора - всё принятое: ADR, описание архитектуры, требования соседних фич.**
Требование, противоречащее принятому, - находка: названы обе формулировки и предложен исход
(пересмотр требования либо пересмотр принятого). Молча ослабить формулировку до внешне
непротиворечивого вида нельзя, а выбор между двумя пересмотрами лежит на полномочной оси раздела 1.

**Правила сверяются друг с другом внутри набора.** Пара, не выполнимая одновременно («ссылка живёт
15 минут» против «ссылка действует до смены пароля»), - находка с обеими формулировками: каждое
правило выводимо из своего расширения, несовместима пара. Пара с общим предметом, где одно правило
поглощает другое, идёт находкой «возможный дубль» по ключу раздела 10. Без этой проверки набор
сходится по покрытию и расходится по существу: оба стыка пройдены, а реализовать оба правила
нельзя.

**Ветки сверяются между собой.** Правило, исполнение которого делает меру недостижимой («письмо
уходит синхронно в том же запросе» против «ответ за 200 мс»), - находка стыка набора, а не дефект
одной из двух единиц: обе выводимы из своих входов, несовместима пара. Проверка идёт на сборке
набора - раньше вторая ветка ещё не закрыта.

Гейт считает покрытие сам и называет пробелы; выводимое достраивает автор по его находкам - без
вопроса наверх, потому что оно выводимо (раздел 1). Наверх идёт остаток - единицы, у которых исход
не выводится.

## 6. Остановки

Безусловных две: **после BRD** - границы и цели приняты, и **финальная приёмка набора**. Между ними
остановка условная: сработала невыводимая находка либо затронута полномочная ось раздела 1.

**Финальная приёмка предъявляет результат пробного разбора** (раздел 13): разбор идёт до неё, и его
остаток входит в ту же пачку. Иначе порог достаточности превращается в третью остановку, а человек
получает два разговора о готовности одного набора.

**Фаза, закрывшаяся без остановки, апрува себе не выдаёт.** Её артефакт стоит в `review` до
финальной приёмки: отсутствие вопросов означает, что вопросов не возникло, а не что документ принят.

**Ответ человека - вход, а не предмет разбора.** Он применяется как есть, включая ответ без
обоснования; дальше пересчитывается задетое и показывается, что изменилось. Конфликт ответа с уже
принятым называется находкой - обе формулировки и задетые единицы, - но выбор остаётся за
человеком: собственное предложение конвейер не сохраняет на том основании, что оно обосновано.
Два ответа одной пачки, несовместимых между собой, не применяются оба: названо, какие пункты и в
чём расходятся, и уточнение становится следующей остановкой.

**В `autonomous` полномочную ось закрывает агент, и каждое такое решение выводится из уже принятого.**
Отвечать некому, но ветка обязана иметь терминал: иначе обе безусловные остановки оказываются без
исполнителя, набор остаётся в `review` навсегда и прогон всегда возвращает `blocked`. Поэтому пункт
не подвешивается, а закрывается - но не свободным выбором: исход выводится из действующего набора
требований, принятых решений и внешних норм, и без такого основания пункт остаётся открытым.

Все закрытые так пункты идут **отдельным списком в выходе прогона**: что решено, из чего выведено,
что было альтернативой. Список - предмет первой же встречи с человеком: он смотрит не весь набор, а
только те места, где за него решили. Запись каждого такого исхода идёт в `decision-log` как решение
с пометкой «принято за оператора», чтобы отличаться от решения, которое человек принял сам.

## 7. Приёмка истории

Приёмка story = примеры её правил + назначенные проверки применимых `NFR` + названные non-goals.
Своих критериев сверх этого у story нет.

- **Критерий, не выводимый ни из `FR`, ни из `NFR`, - недостающее требование**, а не критерий story:
  поднимается находкой и возвращается тем классом, которого недостаёт, - правилом или мерой уровня
  системы, а при отсутствующей ветке поведения сценарием (раздел 13). Иначе поведение просачивается в
  систему через нарезку, минуя гейт.
- **`NFR` попадает в story ссылкой на ID**, не пересказом: «проверяется по `NFR-NNN`». Ни число, ни
  метод, ни уровень в story не переписываются - все три правятся вместе с мерой (раздел 11), и
  переписанные расходятся с источником одинаково. Своё story добавляет только роль проверки в
  нарезке: какая её часть эту меру предъявляет.
- **Правило не режется между историями.** Нарезка требует разрезать `FR` - значит крупно само
  правило, и делится оно, а не его примеры: иначе трассировка рвётся посередине.
- **Работа без единого `FR` и `NFR`** - рефакторинг, обновление зависимостей, чистка мёртвого кода -
  единицей конвейера требований не является: ни внутри набора историей, ни на входе заявкой. Исход
  называется явно - что из входа не выводится и почему; гейт покрытия по такой работе не заводится,
  а `BR` ради прохождения конвейера не сочиняется.
- **Пример договаривается о правиле, тест ловит регресс.** `AC` не перебирает комбинации и не
  смотрит внутреннее состояние: перебор - работа тест-дизайна на этапе верификации, и в примере он
  топит правило, ради которого пример написан. Из одного `AC` вырастает сколько угодно тест-кейсов;
  обратно в набор они не поднимаются.

## 8. Трасса живёт в единице

`FR` несёт `traced from` на `BR`, `UC` ссылается на `FR`. Обратная ссылка на шаг сценария («шаг 5
`UC-...-002`») не заводится нигде: шаги плывут при каждой правке сценария, ID правила стабилен.
Связь `BR -> FR` не выводится из совпадения номеров - одно `BR` раскрывается несколькими правилами.

**Связь «расширение - правило» живёт в сценарии, и только там.** Правило трассируется на `UC`
целиком; номер пункта в его трассе не пишется по правилу выше. Учёт покрытия стыка `UC -> FR` идёт
со стороны сценария: у каждого расширения либо ссылка на правило, либо пометка «без правила» с
основанием, либо открытый пункт (раздел 5). Двух списков связи не заводится - иначе они разойдутся,
и покрытие станет считаться по тому, который судья открыл первым.

**Ссылка на порождённое учётная: статуса источника она не меняет.** Появившаяся у расширения
`-> FR-NNN` не переводит сценарий в `review` - нормативно он тот же, изменился учёт. Апрув
отзывается правкой хода, актора, цели или терминала; иначе каждое новое правило возвращало бы в
приёмку сценарий, из которого само же выведено, и стык `UC -> FR` не сошёлся бы никогда.

**Обратный обход идёт по корпусу, а не по папке фичи.** Правка единицы поднимает всех, кто на неё
ссылается, до корня корпуса: одна `NFR` обслуживает несколько фич, одно `BR` раскрывается в разных
наборах, общий словарь предметной области читают все. Область обхода - корень из раздела 9, за
корень обход не выходит. Потребители находятся поиском по номеру единицы в момент правки; хранимого
списка «что из меня выведено» нет ни у одной единицы. Такой список пришлось бы дописывать в чужую
единицу - фича, заводящая story на продуктовую `NFR`, не вправе её править (R-7), - и он протухает
молча, а поиск не протухает никогда.

**Чужую единицу правит её владелец.** Владелец - набор, в контейнере которого единица живёт; у
продуктовых единиц владелец продуктовый. Задевший переводит её в `review` с пометкой «основание
изменено» и называет, что именно изменилось; текст соседнего набора он не переписывает - иначе
чужой набор меняется мимо своей приёмки. Пометка держится до прогона владельца и **свой набор не
блокирует**: незакрытый чужой `review` - законное состояние корпуса, а не открытый пункт этой фичи.

Список задетого показывается до применения правки, а не после: **правка, вышедшая за свой набор, -
остановка**, даже если внутри своего набора она полностью выводима.

**Ссылка между единицами - по ID, а не по пути.** Папку переименовали, документ переехал, единица
уехала в другой контейнер - трасса это переживает; ссылка путём живёт до первой раскладки.

**У основания четыре вида, и вид записывается вместе со ссылкой.** Хотя бы одно основание несёт
каждая единица: без него стык снизу вверх не замыкается (раздел 5).

| Вид | Чем ссылается | Что делает обход при изменении |
|---|---|---|
| фрагмент входа - идея, бриф, код при реконструкции | цитатой либо указателем на вход; ревизии корпуса у него нет, способ получения называется (реконструкция - пометкой) | вход сменился - единицы на нём предъявляются заново |
| принятая единица корпуса | ID | правка источника поднимает производное (раздел 11) |
| запись `decision-log` - решение человека либо допущение | номером записи | решение отменяется только явным входом; допущение при опровержении получает исход - подтверждено, пересмотрено, снято |
| действующая внешняя норма - ADR, описание архитектуры, ограничение среды, регламент | путём и ревизией | изменение нормы поднимает стоящие на ней единицы |

Вид нужен самому обходу: он говорит, чьё изменение эту единицу поднимает, и различает решение с
допущением там, где ссылка у обоих ведёт в `decision-log`. Без четвёртого вида `NFR`, стоящая на
ограничении среды, и правило, выведенное из архитектурной рамки (раздел 4), выпадают из обхода
целиком - норма изменилась, а кто на ней стоял, не знает никто.

**Единица, принятая до введения вида, вида задним числом не получает.** Прогон корпус ради
недостающего поля не переписывает (раздел 10): пустой вид у принятой единицы - известное состояние,
а не находка, и заполняется он при ближайшей правке этой единицы. Иначе первый же повторный прогон
тронет весь корпус и свойство «прогон без новых данных ничего не меняет» перестанет держаться.

**Утраченная запись основания не отменяет.** Ссылка вида «запись `decision-log`» повисает
вместе с ним (раздел 10): основание помечается утраченным, решение поднимается заново и
помечается поднятым повторно, но единица безоснова́тельной не объявляется и висячей не считается -
иначе потеря следа снимает то, что человек решил.

**Категория чеклиста качеств основанием не является.** Она инструмент полноты: каждая
характеристика дала `NFR` либо объявлена неприменимой (раздел 2). Найденная через неё мера стоит на
`BR` или на ограничении среды - на том, из чего выведено её содержание, а не на способе, которым её
хватились.

**Решение человека, породившее единицу, входит в её основание наравне с источником.** Исход,
выбранный на полномочной оси, требованием не становится, но правило на нём держится: трасса несёт и
`BR`, и запись `decision-log`. Без этого снятие `BR` объявляет висячим правило, у которого
основание есть, - и обратный обход отправляет на пересмотр решение, которое никто не отменял
(раздел 11).

**Обход захватывает допущения и решения `decision-log`, а не только единицы.** Допущение принято при
названном основании и вместе с ним поднимается: правка `BR` может его опровергнуть, и тогда оно
получает исход - подтверждено, пересмотрено или снято - той же ревизией, что и задетые единицы.
Допущение, не несущее ссылки на то, при чём оно принято, обходом не находится: ссылка - часть его
записи, а не пояснение.

**Обход конечен: единица входит в него один раз.** `FR` фичи A задел `BR` фичи B, чей пересмотр
задевает `FR` фичи A - это одна волна, а не круг: помеченная единица второй раз не обходится, а
список задетого копится по всей волне и показывается один раз. Без этого правила взаимные ссылки
двух наборов дают бесконечный каскад на ровном месте.

## 9. Расположение артефакта - процедура узла, а не свойство класса

Место в class-skill не называется. Порядок разрешения одинаков для всех узлов:

1. расположение пришло сквозным полем входа - берётся как есть, заново не разрешается;
2. не пришло -> `project-docs-map`: корень корпуса, дом путей - `.docs_layout` в корне репозитория, поиск и запись
   найденного; корпус недостижим -> `unverifiable` с причиной;
3. корень есть и артефакт этого класса в нём уже лежит -> **раскладка повторяется по факту**:
   каталог и форма имени берутся с образца, конвенция не применяется;
4. образца нет - корпус пуст либо класс в нём ещё не встречался -> каталог и имя берутся из дерева
   норматива раскладки `docs-layout`, слаг прогона и границы применения конвенции - `artifact-naming`;
5. корня нет -> заготовка дерева разворачивается там, где записывать можно, с пометкой допущения, и
   разворачивает её трек, а не составитель; выбранное место записывается по ступени 2, места на
   выбор разбираются правилом кандидатов ниже; записать некуда вовсе -> `blocked`;
6. разрешённый путь возвращается в выход - следующий узел не разрешает его заново.

**Факт сильнее конвенции.** Третья ступень стоит перед четвёртой по той же причине, по какой
расположение корпуса ищется, а не назначается: корпус мог сложиться до конвейера либо по чужой
раскладке, и своё правило поверх чужого порядка заводит второй каталог рядом с существующим.
Конвенция - дефолт для пустого места, а не закон для занятого.

Последняя ступень несёт всю конструкцию: без неё два узла разрешают путь по разным ступеням и кладут
артефакты в разные места.

**Кандидатов корня нашлось несколько - выбор не делается разбором.** `interactive` спрашивает;
`autonomous` берёт тот корень, где уже лежит корпус этой фичи, при пустом пересечении - первый по
порядку раскладки, и помечает выбор допущением. Найденный корень записывается на ступени 2, чтобы
следующий прогон не выбирал заново и корпус не разъехался по двум деревьям.

## 10. Прогон идёт от состояния корпуса

Режима «с чистого листа» у конвейера нет: вход прогона - всегда пара «что просят» плюс «что уже
принято». Первый шаг узла - чтение принятого по своему классу; дальше работа идёт дельтой, и новая
единица заводится только там, где принятого совпадения не нашлось.

**Совпадение ищется по ключу тождества, а не по тексту.** Формулировка переписывается при каждой
правке, номер выдаётся при записи и на входе прогона ещё не существует, поэтому ключ у каждого
класса свой:

| Класс | Ключ тождества |
|---|---|
| `BR` | сторона плюс её исход |
| `UC` | актор плюс цель |
| `FR` | предмет правила - что и при каком условии ограничивается |
| `NFR` | характеристика качества плюс объект измерения |
| `AC` | правило плюс проверяемая им граница |

Ключ совпал - единица либо правится по разделу 11, либо остаётся как есть; не совпал - заводится
новая, и снятый номер ей не достаётся: номера не переиспользуются. Отсюда свойство, которого без
ключа не бывает: **повторный прогон без новых входных данных корпус не меняет** - ни новых номеров,
ни переформулировок, ни повторно заданных вопросов; отчёт такого прогона состоит из строк «совпало,
изменений нет».

**Старший разряд номера выводится из номера фичи, младший берётся из файла своего класса в
счётчике, и счёт идёт в пределах своего класса.** Фича `01` нумерует с тысячи (`FR-1001`), фича
`02` - с двух тысяч. У
каждого класса пространство номеров своё: `FR-1001` и `NFR-1001` - две законные единицы, а не
столкновение, потому что класс - часть номера. Номера фич не пересекаются, поэтому реестра занятых
номеров единиц не нужно и договариваться параллельным прогонам не о чем: общее место одно -
`.req_counter`, и в нём один файл на класс блока, а не запись на каждую единицу.

**Номер выдаёт тот, кто единицу пишет.** Составитель считает свободный номер сам и отдельного
нумератора со стартовыми отрезками не требует: два составителя не сталкиваются, потому что пишут в
разные пространства классов, а внутри класса в прогоне пишет один узел - ветка мер и ветка правил
идут параллельно, но `NFR` и `FR` нумеруются независимо. Гонка появилась бы у двух экземпляров
одного класса, запущенных одновременно; такого спавна в схеме нет, и заводить его, не введя внешнего
нумератора, нельзя - это условие, а не запрет навсегда.

**Номер фичи составителю взять неоткуда - его разрешает тот, кто ведёт прогон**, один раз до первого
спавна, и дальше он едет сквозным полем. Берётся он из **счётчика** - директории `.req_counter`, где
файл на ключ: `feature` даёт номер фичи, `NN.BR`, `NN.UC`, `NN.FR`, `NN.NFR` - последний выданный
номер этого класса в блоке фичи `NN`. Номер выдаётся инкрементом: прочитал, увеличил, записал
тем же действием, каким завёл единицу. Пришёл номер явным полем входа - счётчик не спрашивается, но
запись в нём подтягивается всё равно.

**Конфликт - это и есть детектор, и он же вход процедуры.** Все прогоны правят одни и те же строки
одного файла, поэтому две ветки, взявшие номер под одним ключом, дают конфликт слияния - в отличие от
совпавших номеров в разных файлах, которые сливаются чисто и молча. **Конфликт читается как факт, а
не как текст:** строку увеличили дважды - значит номер выдан двум единицам. Выбор стороны запрещён -
он гасит сигнал, оставляя столкновение в корпусе. Значение берётся максимальным, перенумеровывается
**входящая** сторона (её номера с меньшей вероятностью успели разойтись), вместе с единицами правятся
ссылки на них - трасса, `AC`, записи гейтов, `decision-log`, - и область поиска здесь корень корпуса,
а не папка фичи. Конфликт по ключу `feature` перенумеровывает блок целиком, по ключу класса - только
столкнувшиеся единицы. Номер, успевший уйти за пределы корпуса - в код, тесты, тикеты, - правится
внутри репозитория, внешнее называется находкой. Разрешение - работа того, кто ведёт слияние, либо
дирижёра, если столкновение всплыло внутри прогона; порядок - `project-docs-map`.

**Где лежат счётчики, говорит `.docs_layout`** - файл путей в корне репозитория. Процедура раздела 9
его не выводит: имя фиксировано конвенцией, поэтому адрес известен без записи о том, где он записан.
Сам он хранит пути - корень корпуса, места классов, путь `.req_counter`. Путей фич в нём нет: где
лежит корпус фичи, выводится поиском в корне по номеру, а на чужой раскладке, где папок под фичи нет
вовсе, - из номеров в самих единицах. Пути **могут указывать наружу**: корпус требований живёт и
отдельным репозиторием, и это штатная форма (раздел 9, `project-docs-map`).

**Счётчик один на корпус, а не на репозиторий.** Реп у продукта бывает много, а требования
принадлежат продукту: одна фича, сделанная тремя сервисами, имеет один блок номеров, иначе трасса
рвётся на границе репозитория. Отсюда раскладка: `.docs_layout` - в каждой репе (он указатель),
`.req_counter` - один, при корпусе. Разные продукты со своими корпусами имеют свои счётчики, и
пересекаться им нечем.

**Счётчика нет - он строится один раз, а не вычисляется каждый раз.** На занятом проекте, куда
конвейер приходит впервые, значения восстанавливаются сплошным проходом: максимальные номера, уже
стоящие в единицах корпуса, по классам и блокам. Считать по номерам единиц, а не по папкам: на чужой
раскладке (ступень 3 раздела 9) папок под фичи нет вовсе, а номера есть. Корпус пуст - счётчики
пусты, первая фича получает `01`. Дальше живёт файл, и пересчёта по корпусу больше не делается.

**Счётчик отстал от корпуса - чинится по корпусу, и это находка, а не тихая правка.** Единица,
написанная мимо конвейера, номер заняла, а строку не тронула; значение подтягивается до
максимального в корпусе, факт называется в выходе. Обратное расхождение - счётчик больше
максимума - штатно: так выглядят дырки от снятых единиц.

**Счётчик недостижим - остановка, а не номер вслепую.** Путь записан, а файл не прочитать -
репозиторий корпуса не склонирован, закрыт по правам. Это **не** случай «корпус не читается», при
котором работа идёт дальше с пометкой: выдать номер вслепую значит записать блок, который сойдётся с
чужим молча. Исход - `blocked` с указанием, чего не хватает; клонировать узлы зоны требований не могут, у них
нет для этого инструмента.

**Счётчик назад не откручивается:** фича снята - её блок остаётся дыркой, `feature` не уменьшается.
Иначе следующая фича получает блок, в котором уже могут лежать чужие единицы и ссылки на них, и
происходит это невидимо.

**Счётчик - не реестр занятых номеров единиц.** Реестра единиц нет намеренно: запись **на каждую
единицу** превращает нумерацию в очередь и требует, чтобы параллельные ветки видели друг друга.
Счётчик хранит одно число на класс блока - он не перечисляет единицы и не растёт от их числа, но
даёт то, чего счётом по корпусу не получить: занятый блок виден до того, как в нём появилась первая
единица.

Отсюда цена утраты: **счётчики восстановимы** тем же сплошным проходом, которым строились, -
потеряны будут только блоки, выданные под фичи, ещё ничего не записавшие. Такой номер никому не
мешает: он достанется следующей фиче. `feature-ledger` источником номера при этом не является вовсе:
он служебный след прогона, живёт вне рабочего дерева и на другой машине его нет.

**Следующий номер внутри блока даёт файл своего класса в `.req_counter`** - прочитал, увеличил,
записал тем же действием, каким завёл единицу. Состояние живёт в файле, а не в памяти прогона: обрыв
и повторный запуск на нумерацию не влияют. Счёт по корпусу нумерацию не ведёт, он её **восстанавливает**:
потерянный или ещё не заведённый файл ключа собирается один раз как максимальный занятый в своём классе
**по корню корпуса в пределах своего блока**. Область счёта здесь - корень, а не папка фичи: единица
блока может лежать в чужой папке (мера, обслуживающая несколько фич; заимствованный номер), и счёт по
своей папке её не увидит. Номер снятой единицы остаётся дыркой и не переиспользуется: иначе старая
ссылка укажет на другое требование. Блок исчерпан - `feature` увеличивается, фича получает следующий
свободный блок целиком, и под него заводятся файлы ключей класса; `feature-ledger` в этом не
участвует (см. выше), а заимствованный номер виден соседу и помимо счётчика - восстановление считает
по корню. Раскладка артефактов (раздел 9) номеров не касается.

**Ключ ищет кандидатов, тождество подтверждается сверкой формулировок.** Совпадение ключа - повод
сравнить по существу, а не вывод: тот же предмет и то же ограничение - одна единица; разные - две, и
совпадение записывается находкой «возможный дубль». Молчаливое слияние по ключу хуже дубля: дубль
виден в наборе, а слитое правило исчезает без следа. Два принятых совпадения по одному ключу - тоже
находка: в корпусе уже дубль, и выбор между ними не дело прогона.

**Примеры сопоставляются вместе со своим правилом.** По корпусу `AC` не ищется: он живёт при своём
`FR` и пересматривается вместе с ним, а его ключ работает внутри правила - не даёт задвоить пример
при пересборке. Иначе правка границы объявляла бы все примеры правила новыми и гнала бы номера на
каждом прогоне.

**Снятое и отклонённое хранится записью, а не исчезает.** Единица, снятая решением человека или
объявленная вне объёма, остаётся в корпусе с основанием и статусом. Ключ нового вывода совпал с
такой записью - это не новая единица, а находка «ранее снято решением»: восстановить или оставить
снятым, решает человек. Без этого правила каждый прогон заводит заново ровно то, что уже отклонили,
и решение человека живёт до первого повторного прогона.

**Область поиска - корпус, а не папка своей фичи** (корень берётся из раздела 9). Правило, принятое
в другой фиче, повторно не заводится: новый набор ссылается на принятое. Расходятся
формулировки по существу - это находка, а не повод завести соседнюю единицу и не повод переписать
чужую под свои нужды (раздел 8).

Прерванный прогон продолжается тем же порядком: состояние берётся из корпуса и **`feature-ledger`**,
закрытые фазы не переигрываются, работа идёт с первой незакрытой. Леджер ведёт дирижёр, он же с него
стартует - и по той же записи прогон продолжается после того, как контекст сессии свёрнут: где
остановились, читается с диска, а не из памяти разговора. Живёт он вне рабочего дерева и в корпус не
пишется (раздел 1).

**Текст, разошедшийся с принятым состоянием, - находка.** Запись гейта несёт ревизию единицы, по
которой судила, - то же требование, что к производной форме в разделе 12, и по той же причине.
Единица, правленная мимо конвейера - руками в файле, чужим инструментом, - опознаётся по расхождению
текущего текста с этой версией: запись без неё говорит, что судили, но не говорит - что. Она
возвращается в
`review` и судится заново, прежний `approved` ей не наследуется. Прогон такую правку не откатывает и
молча не «чинит»: содержание менял человек, решение о содержании остаётся за ним.

**След утрачен - состояние берётся из корпуса, потери объявляются, и цена у следов разная.**
Счётчики восстанавливаются сплошным проходом по номерам единиц; теряются только блоки фич, не
успевших ничего записать.
Утрата `feature-ledger` стоит дешевле всего: прогон начинается сначала, корпус при этом цел. Утрата
записей `quality-checks` обходится пересудом - единицы и их статусы потерю переживают. Решения
человека не переживают: то, что не отражено в тексте единиц, поднимается заново и помечается
поднятым повторно из-за утраты `decision-log`. Это единственный случай, когда принятое решение
переспрашивается, и он называется вслух.

## 11. Правка принятой единицы

Правка - часть контракта класса, отдельным процессом не ведётся: class-skill нормирует и создание, и
изменение. Задетые по трассе единицы называются при правке - `FR` тянет свои `AC` и производные
формы, `BR` тянет `UC` и `FR`. Механика ревизий, счётчик и роды изменения - `node-contract`,
раздел «Ревизия»; здесь только место правки в конвейере.

**Род изменения объявляется до правки файлов, задетое возвращается в `review`.** Каждая задетая
единица получает исход - пересмотрена, признана незатронутой с основанием или снята - и помечается
«основание изменено»; апрув отзывается в изменяемой части, а не во всём документе. Принятый набор
при этом не переписывается заново: правится дельта (раздел 10), а единицы, чей исход из правки
выводится, идут без вопроса.

**Правка адресуется ID, ключ пересчитывается после неё.** Ключ изменился - это переименование
единицы, а не рождение новой: старая формулировка не остаётся висеть рядом. Новый ключ совпал с
другой принятой единицей - находка о слиянии, и слияние решает человек: оба ID уже разошлись по
трассам, и выбор выжившего меняет чужие ссылки.

**Расщепление: исходная единица снимается, потомки получают свои номера.** У снятой остаётся запись
«заменено на X, Y», трасса вверх наследуется каждым потомком, ссылки снизу переадресуются по
предмету. Висячей ссылки на снятый ID в корпусе не остаётся - иначе нарезка крупного правила рвёт
трассу ровно там, где она нужнее всего.

**Круги правки конечны.** Счётчик и его исчерпание - `node-contract`; исчерпан - работа закрывается
остановкой с открытым пунктом, а не выходом «как получилось». Расхождение, не сошедшееся за два
ревизии, - признак невыводимого: этот пункт уходит из ревизий и закрывается по своей форме из раздела 1
- допущением либо вопросом, - а не третьей ревизией. Потолок пробы этим не расходуется: остальные
пункты добираются ревизиями по числу своего режима (раздел 13). Спросить некого (`autonomous`) - вопрос
не снимается и не подменяется допущением: он записывается открытым и предъявляется оператору на
ближайшей остановке, производное от него не пишется, а работа продолжается тем, что от него не
зависит.

**Ранее принятое решение отменяется только явным входом.** Тогда запись `decision-log` помечается
отменённой (не стирается), задетое пересчитывается по трассе, новое решение получает свою запись.
Несогласие узла с принятым решением поводом переспросить не является (раздел 1).

## 12. Валидация - по классу

Оракул класса судит единицу: форма, мера, обязательные атрибуты. Оракул набора судит стыки раздела
5. Оракула для класса не существует -> артефакт закрывается записью `unverifiable` с причиной
([NORMS.md](NORMS.md), раздел 6), молчанием случай не закрывается.

**Проверку делает судья, автор её не дублирует.** Прогон того же оракула автором над собственным
выходом даёт второй результат того же прогона и заводит поле, неотличимое от вердикта; чинит автор
по находкам судьи - для этого и есть ревизия. Исключение одно: у класса нет судьи - тогда
авторский прогон записывается как единственная проверка и вердиктом не называется.

Производная форма собственного класса не получает и повторно не судится - порог взят её источником.
Такая форма несёт источник и его версию: неизменяемую ссылку на состояние, из которого собрана
(ссылка на изменяемое состояние версией не является). Состав производных форм схема не задаёт - он
решается при реализации.

## 13. Порог достаточности: комплект как вход автоматической реализации

Набор требований готов не тогда, когда заполнены разделы, а тогда, когда по нему пишется код без
единого вопроса наружу. Проверяемая форма этого условия: **реализатор принимает решения только о
способе** - алгоритм, структура кода, имена внутри модуля. Любое решение о наблюдаемом исходе, мере
или границе, которое ему пришлось бы принять самому, - незакрытое место комплекта.

| Что должно быть определено | Носитель | Что домысливается без него |
|---|---|---|
| правило и его примеры | `FR` + `AC` | поведение и его границы |
| мера и метод проверки | `NFR` | рамка «достаточно быстро» |
| исход каждой отказной ветки | терминалы расширений `UC` -> `FR` | что видит актор при сбое |
| данные: сущности, поля, состояния и переходы | `FR`, контракт интерфейса | модель предметной области |
| интерфейс вызова и формат ошибок | контракт этапа 4 | протокол |
| действующие архитектурные рамки | ADR, описание архитектуры | место фичи в системе |
| граница объёма | non-goals | объём работы |

Строки 5 и 6 лежат за зоной требований: комплект автоматической реализации - это набор зоны требований плюс
контракт интерфейса и действующие решения. Конвейер требований отвечает за первые четыре строки и за
то, чтобы недостающие последние были названы, а не молча оставлены реализатору.

**Дом контракта интерфейса - рядом с кодом, не в `docs/`.** Он участвует в сборке, генерации
клиентов и контрактных проверках, а копия в документации расходится с работающим протоколом молча.
Набор требований ссылается на него путём и содержимого не пересказывает.

**Порог проверяется пробным разбором, а не осмотром таблицы.** Таблица выше - первичный фильтр: она
ловит пустой носитель, но не ловит набор, где носители заполнены, а исход всё равно неоднозначен.
Поэтому допуск даёт читатель-реализатор: он разбирает набор так, как разбирал бы перед написанием
кода, и выписывает всё, что пришлось бы додумать, - каждое решение о наблюдаемом исходе, мере или
границе, основания которому в наборе нет. **Порог взят, когда этот список пуст.** Каждый пункт
непустого списка - либо находка, либо явное решение «отдаём на усмотрение реализации» с основанием.
**Находка возвращается тем классом, который порождает недостающее:** отсутствующая ветка поведения -
сценарием, правило или мера - сводом, пример - критерием истории. Класс - по предмету домысла:
правило, заведённое под ветку, которой в сценариях нет, трассируется на ближайший похожий шаг и
проходит проверку покрытия, ничего не покрывая. Читатель разбирает, но не пишет: найденное он не
достраивает сам, иначе домысел войдёт в набор под видом проверки.

**Список домыслов обязан сходиться, и сходимость мерится остатком:** перечень предметов на выходе
ревизии против предыдущей, а не число пунктов, получивших исход, - ревизия, закрывшая пять и
принёсшая шесть, продвижения не дала. Список не убавился - ревизия непродуктивна, остаток не выводится и идёт на остановку
решением «требование либо усмотрение реализации», а не в следующую ревизию.

**Считаются различимые предметы домысла, не строки списка, и перечисляет их сама проба.** Пункт тот
же, если он про то же место набора и ту же нехватку: переформулировка тождества не меняет, и в убыль
такой пункт не идёт; два прежних пункта, слитые в одну формулировку, дают убыль ноль, а не единицу.
Отсюда обязанность выхода пробы: она отдаёт перечень предметов, по строке на предмет, и два пункта
про одно место и одну нехватку сводит в один до сдачи. Без этого правила длина перечня предметов не
считает, и стороны вычитания расходятся: одна берёт число строк, другая - число предметов. Счёт
предметами разрешает и смешанную ревизию, где часть пунктов закрыта, а часть переписана: убыль засчитывается по предметам,
исчезнувшим из списка, - ревизия продуктивна, когда убавилось их число.

**Тождество устанавливает дирижёр, он же ведёт счёт.** У пробы прошлого списка нет по построению:
контекст ей чистят намеренно, а собственный список прошлой ревизии подсказывает, где смотреть, ровно
как след прогона, - после него ревизия перестаёт быть сплошным чтением. Сличаются два перечня на диске:
прошлый - перечнем предметов в записи метки прошлой ревизии, новый - тем же перечнем текущего.
Носитель именно метка, а не `decision-log`: у метки есть номер ревизии, и перечень ревизии из неё
выделяется, тогда как в журнале записи всех ревизий лежат вперемешку и признака ревизии у них нет по
норме журнала (служебный ход прогона в него не пишется). Журнал держит **исход** каждого пункта -
находка либо решение «усмотрение реализации», - и вторым носителем перечня не служит. Счёт воспроизводим по этим записям третьей стороной;
расхождение закрывается пересчётом по ним, а не прозой сторон. Вердикт готовности остаётся у пробы:
дирижёр считает продуктивность ревизии, набор он не судит.

**Число ревизий задано и зависит от режима.** `interactive` - два: оператор в петле, и спросить его
дешевле, чем крутить разбор ради того, что он называет одной строкой. `autonomous` - три: спрашивать
некого, поэтому лишняя ревизия оправдана, а четвёртая нет - порог, не взятый третьей ревизией, не берётся и
десятым. Проба закрывается тем, что наступит раньше: исчерпанный потолок или непродуктивная ревизия.
Счёт ревизий ведёт судья пробы номером ревизии в записи метки (`node-contract`, «Ревизия»); счёт
прозой рядом с записями расходится с ними молча. Это и есть содержание допуска к разработке, у которого
собственного информационного элемента в стандартах нет ([NORMS.md](NORMS.md), раздел 2, этап 6).
