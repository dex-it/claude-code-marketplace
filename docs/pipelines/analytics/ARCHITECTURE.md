# Конвейер аналитики: архитектура исполнения

Предмет - **как устроен исполнитель**: кто кого вызывает, какие служебные скиллы держат каркас, что
едет по каждому ребру, что остаётся на диске. Нормативная схема - что за единицы, в каком порядке и
по каким проверкам - в [PIPELINE.md](PIPELINE.md); расхождение правится здесь, а не там. Состав
исполнителей и принятые решения реализации - [IMPLEMENTATION.md](IMPLEMENTATION.md).

## 1. Поток единиц

```
идея ──► BR ──┬──► UC ──► FR ──► нарезка на stories с AC ──► допуск
              │            ▲                                   ▲
              └──► NFR ────┴──────── свод в SRS ───────────────┘

несценарная ветка (миграция, регламент, техдолг): BR ──► FR, минуя UC
```

`NFR` идут своей веткой от `BR` и ограничений среды: у нагрузки, отклика и регуляторики нет ни
актора, ни шага, из сценария они не выводятся ни при каком качестве разбора. `AC` рождаются при
нарезке в историю, а не при написании правила: одно правило проявляется в разных историях разными
примерами, и между правилом и историей встают меры `NFR`, которых в сценарии нет вовсе.

## 2. Узлы

```
дирижёр (dex-requirements-orchestrator)
   ├── dex-business-analyst        → BR
   ├── dex-usecase-writer          → UC
   ├── dex-requirements-analyst    → FR и NFR
   └── dex-user-story-writer       → истории с AC
судьи: гейт дирижёра · dex-requirements-reviewer (автор себя не судит)
```

Дирижёр держит номер фичи, `decision-log`, гейты и остановки оператора. Составители нумеруют себя
сами - каждый по своему ключу счётчика; двух составителей одного класса параллельно не спавнить -
там ключ общий и гонка настоящая.

**Имя узла - предмет плюс `-analyst`:** все четыре берут единицы предыдущего класса и **выводят**
свои, а не оформляют надиктованное; `-writer` остаётся за агентами, которые записывают уже принятое
(`adr-writer`, `doc-writer`). Два имени пока не по правилу (`usecase-writer`, `user-story-writer`) -
переименование едет отдельным заходом, оно ломающее (`IMPLEMENTATION.md`, раздел 7).

## 3. Служебные скиллы - каркас

| Скилл | Что даёт | Кто грузит |
|---|---|---|
| `node-contract` | форма стыка: статусы исхода, словарь полей, транспорт указателями, реакция на неполный вход, журнал решений | все |
| `project-docs-map` | где корпус (`.docs_layout`), где `.req_counter`, что делать при отсутствии и недостижимости | все |
| `unit-identity` | та же единица или новая; номера, дырки, конфликт счётчика | все |
| `artifact-naming` | имя и раскладка, когда образца в корпусе нет | дирижёр и все четыре составителя |
| `decision-log` | форма журнала решений | только дирижёр - писать в него больше некому |

## 4. Предметные скиллы и оракулы

| Узел | Класс-скилл | Дополнительно | Оракул |
|---|---|---|---|
| `business-analyst` | `business-analysis` | `product-discovery`, `doc-standards`, `legacy-reconstruction` | `requirement-quality` |
| `usecase-writer` | `use-cases` | `legacy-reconstruction` | - |
| `requirements-analyst` | `functional-requirements`, `nfr` | `legacy-reconstruction` | `requirement-quality` |
| `user-story-writer` | `user-stories` | `test-design` - техники подбора примеров | `requirement-quality` |
| дирижёр (как судья) | `business-analysis`, `use-cases` | - | `requirement-quality`, `requirement-set-quality` |
| `requirements-reviewer` | все четыре класс-скилла | `fact-verification`, `review-evidence`, `output-hygiene`, `codebase-conventions`, `ddd` | `requirement-quality`, `requirement-set-quality` |

`legacy-reconstruction` включается на brownfield-входе «код без постановки» и общий у трёх
составителей. Оракул **единицы** судит форму и атрибуты, оракул **набора** - стыки рёбер; второй
есть только у судей: автор своим прогоном вердикта не ставит, иначе независимой проверки не
остаётся.

## 5. Данные на рёбрах

**Сквозной минимум** едет на каждом стыке, даже если узел его не трогал:

```
корень корпуса + путь артефакта      следующий узел путь заново не разрешает
номер фичи                           из него старший разряд номеров единиц
режим (autonomous / interactive)     канал ответа на остановке
путь decision-log фичи               принятые решения не переспрашиваются
статусы единиц + записи quality-checks   производное не поднимается выше источника
открытые пункты и допущения          набор с открытым пунктом не завершён
```

**Предмет ребра** - сверх минимума:

| Ребро | Вниз | Наверх |
|---|---|---|
| идея -> `BR` | тема либо проработанный вход как есть; ограничения, non-goals | путь BRD, `BR-NNN` с мерой успеха, пачка невыводимого |
| `BR` -> `UC` | путь BRD, перечень `BR-NNN`, взятых в разбор | пути сценариев, `UC-...` с трассой, расширения без исхода |
| `BR` + среда -> `NFR` | ограничения среды, чеклист характеристик, продуктовые `NFR` ссылками | `NFR-NNN` с мерой, методом и уровнем проверки |
| `UC` -> `FR` | сценарии и `UC-...`; действующие рамки (ADR, описание архитектуры) ссылками | `FR-NNN` с трассой и методом верификации, находки стыка |
| `UC`, `FR`, `NFR` -> истории | ветки сценариев, `FR-NNN` для нарезки, применимые `NFR` перечнем ID, non-goals | истории с `AC` и метками правил, покрытие веток и правил, критерии-сироты |
| набор -> допуск | корень корпуса, единицы по классам со статусами, контракт интерфейса путём | список домыслов пробного разбора, вердикт приёмки |

**По рёбрам едут указатели, не копии** - ID и путь. Формулировка переносится только там, где
потребитель обязан её процитировать (`AC` с меткой своего `FR`); перенёсший нормативный текст
становится его автором и обязан сверяться с источником.

## 6. Что узел трогает на диске

```
читает:   корпус (по root из .docs_layout) · .req_counter · decision-log
          · quality-checks вместе с полем revision
пишет:    свой артефакт · свою строку счётчика · строки решений (возвращает дирижёру)
дирижёр:  + decision-log · + feature-ledger (вне рабочего дерева)
судья:    + записи quality-checks
```

| След | Где живёт | Цена утраты |
|---|---|---|
| корпус единиц | `root` из `.docs_layout`, едет с MR | сам продукт работы |
| `decision-log` | в корпусе фичи, едет с MR | решения человека переоткрываются |
| `quality-checks` | при артефакте, с ревизией судимого текста | пересуживается |
| `.req_counter` | при корпусе, один на продукт | восстанавливается проходом по номерам единиц |
| `.docs_layout` | корень репозитория, имя фиксировано конвенцией | ищется и записывается заново |
| `feature-ledger` | вне рабочего дерева, у каждой фичи свой | прогон с начала, корпус цел |

Разделение писателей жёсткое: `decision-log` пишет только дирижёр - у файла со многими писателями
порядок записи не определён; записи `quality-checks` ставит судья, автор себе метку не ставит.

## 7. Номера

Старший разряд - из номера фичи (`01` нумерует с тысячи), младший - инкремент строки счётчика.
Ключи: `feature` - номер фичи, `NN.<КЛАСС>` - последний номер класса в блоке. Выдача одним заходом:
прочитал, увеличил, записал тем же действием, каким завёл единицу.

Столкновение делается **видимым**: все прогоны правят одни и те же строки одного файла, поэтому две
ветки, взявшие номер под одним ключом, конфликтуют при слиянии. Конфликт `.req_counter` - вход
процедуры перенумерации, а не поломка (`project-docs-map`, п.6; исполнитель - `dex-conflict-resolver`).

## 8. Границы

Вверх - две безусловные остановки оператора: после `BRD` и на финальной приёмке набора. В автономном
режиме решения принимает агент, выводя каждое из принятого набора, и возвращает их отдельным списком
«принято за оператора, основание такое-то».

Вниз - порог достаточности: набор готов, когда реализатор принимает решения только о способе.
Контракт интерфейса и действующие архитектурные рамки лежат **за** зоной 1; конвейер отвечает за то,
чтобы недостающее было названо, а не молча оставлено реализатору.

Вбок - **архитектура это отдельный конвейер**, а не узел этого: у неё свой предмет, свои единицы и
свой порог. ADR входит сюда четвёртым видом основания - действующей внешней нормой, ссылкой с
ревизией.

## 9. Известное незакрытое

- контроля расхождения между принятым набором и написанным кодом нет ни у одной зоны: ревизия ловит
  расхождение только внутри корпуса;
- `decision-log` - единственный след, который едет с MR и читается целиком при каждом продолжении
  прогона, - не имеет ни сжатия, ни архивации, ни правила разделения;
- слой принципов проекта до зоны 1: вид основания «действующая внешняя норма» на новом проекте
  недостижим, норм ещё нет.
