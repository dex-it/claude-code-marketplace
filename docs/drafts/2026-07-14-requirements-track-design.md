# Дизайн: трек «Требования» в AI-SDLC конвейере

> Черновик под реализацию. Статус: approved (согласован в брейншторме 2026-07-14).
> Нормативный дом после реализации - `autonomous-task/SKILL.md`, `tracks/requirements.md`,
> `docs/DEV_PROCESS_COVERAGE.md`. Этот файл - обоснование решений, не источник истины.

## Проблема

Конвейер `autonomous-task` начинается не с начала. Трек «Согласование/Спецификация»
стартует от **присланного плана/постановки** («его изучаешь, а не сочиняешь с нуля») -
то есть движок молча предполагает, что требования уже кто-то собрал. Кто именно, не
сказано нигде:

- В таблице треков `SKILL.md` трека требований нет (7 треков, файлов в `tracks/` - 7).
- В `docs/DEV_PROCESS_COVERAGE.md` строки требований нет.
- Агент `business-requirements-analyst` (BRD, use cases, риски) существует, но не привязан
  ни к одному треку и в карте покрытия не упомянут.

Следствие: вход конвейера не стандартизован. Требования приходят в произвольной форме,
каждое звено ниже по потоку декомпозирует их заново, полнота стыка не проверяема.

## Решение

Новый трек **«Требования»** - отдельный, не под-вид «Спецификации».

Обоснование отдельного трека (рассмотренная альтернатива - под-вид `specification`):
единица работы разная. BRD живёт на уровне эпика (много задач, стейкхолдеры, метрики),
спека - на уровне одного инкремента (контракты, пути правок по репам). При склейке гейт
«спека полна» перестаёт быть проверяемым (полна на каком уровне?), а `Out of Scope`
начинает означать две разные вещи - продуктовую границу и границу инкремента, которые
меняют разные субъекты (автор vs агент).

Конвейер после изменения:

```
Требования -> Спецификация -> Проектирование -> Разработка -> Тест-инжиниринг
   ^ human-in-loop  ^ human-in-loop        ^--- автомат, эскалация наверх при дефекте
```

`DoD` каждого трека = `DoR` следующего (правило уже сформулировано для пары
«спека -> разработка», распространяется на новую пару «требования -> спека»).

## Контракт трека (строка в таблицу треков `SKILL.md`)

| Трек | Выполнение | Верификация / «готово» | Артефакт |
|---|---|---|---|
| **Требования** | сырая идея/бриф -> бизнес-анализ (use cases, stakeholders, риски) -> нумерованные ФТ/НФТ -> проверка на дефекты требований -> проверка осмысленности НФТ | каждый дефект требований устранён (противоречие / неполнота / неоднозначность / невыполнимость); каждое ФТ имеет проверяемый критерий; каждое НФТ имеет число; **И** бизнес-вопросы приняты автором | BRD в месте, заданном проектом; **код не пишем и с кодом не сверяем**; трекер: эпик заведён |

### Границы трека (D1)

**Трек «Требования» не открывает код.** Ни для сверки, ни для оценки выполнимости.
Сверка с кодом - работа трека «Спецификация» (там она обязательна: «уже в коде» /
«реальный остаток» / «против ADR»). Если оба трека читают код, они делают одну работу и
расходятся в выводах.

Цена решения принята сознательно: BRD не проверяется на техническую выполнимость в момент
написания. Невыполнимое требование вскроется на треке «Спецификация» при системном анализе
и вернётся возвратом (см. «Эскалация»).

**Трек не решает «как».** Выбор паттерна, границы транзакции, синхронный вызов против
outbox - `I-decide` в спецификации и проектировании. BRD формулирует «отмена отражается в
статусе не позднее 3 с (p99)», не «через outbox».

**Единица - эпик, не инкремент.**

### Место артефакта (D2)

Путь BRD **не хардкодится в трек**. Движок проектно-нейтрален: конкретику берёт из
`CLAUDE.md` / `RULES.md` / memory проекта («Адаптация под проект»). В таблицу адаптации
добавляется строка «Куда складывать BRD/спеки -> `CLAUDE.md`/конвенции проекта». Факт
неизвестен - выяснить и записать в memory, не выдумывать.

## Формат BRD

Канонический состав (правки к текущему `Phase 4` агента отмечены):

```
metadata: type, status (draft -> review -> approved), owner, updated   [новое; doc-standards]
Executive Summary
Business Context
Stakeholders (RACI)
Use Cases: primary / alternative / edge
Requirements:
  FR-001 ...   (приоритет MoSCoW; у каждого - проверяемый критерий)
  NFR-001 ...  (у каждого - число; проверяется skill nfr)
Метрики успеха + Anti-metrics          [anti-metrics новое; doc-standards]
Risks & Mitigation
Out of Scope                           [новое, обязательное; doc-standards]
Открытые бизнес-вопросы                [новое; вопрос-с-предложением, не голый вопрос]
Допущения                              [новое; требование node-contract п.5]
Epics (опц.)
```

`Implementation Plan` (phases, milestones, dependencies) **удаляется** из BRD: съезжает в
«как» и дублирует `epic-planning` / `roadmap-planner`.

Три отсутствующих секции (`Out of Scope`, `Допущения`, `Открытые вопросы`) - не косметика:
без `Out of Scope` автономный участок не знает границы и додумывает; допущениям и решениям
узла по `node-contract` обязано быть место в выходе.

## Сквозная нить идентификаторов (D3)

Коллизия имён, которую разводим явно: в словаре `node-contract` поле `requirements R/I`
означает **R = явные (из ТЗ), I = неявные (из конвенций проекта)** - ось происхождения. В
BRD `FR`/`NFR` - ось природы (функциональное / нефункциональное). Обе на букву R.

Разведение: BRD нумерует по природе (`FR-001`, `NFR-001`); в handoff эти же требования
едут как `R` (явные), а `I` добавляет исполнитель из конвенций.

```
BRD                    FR-001, NFR-001
   ->  Спека           критерии приёмки помечены [FR-001]
   ->  handoff         requirements R/I:  R = FR-001/NFR-001,  I = «валидация как в OrderQuery.cs:34»
   ->  success criteria  «POST /orders/{id}/cancel в Shipped -> 409»  [FR-002]
   ->  тест             оракул = success criteria                      [FR-002]
   ->  self-reviewer    intent = [FR-*] из спеки
```

**Новых полей в `node-contract` не требуется.** `FR`/`NFR` - метки внутри значений
существующих полей (`requirements`, `success criteria`, `intent`). Нить даёт один
гейт: «FR без критерия приёмки» (спека требует метку `[FR-NNN]`); связка «тест -> FR» -
материал для сверки, отдельным гейтом тест-агенты её сегодня не требуют.

## Эскалация обратно в требования (D4)

Узел автономного участка упёрся в дефект требования (противоречие, неописанный кейс) -
по `node-contract` это бизнес-нехватка: `status: blocked` оркестратору, не вопрос юзеру и
не догадка. Оркестратор эскалирует человеку.

**Починка = новая ревизия BRD.** BRD апрувнут и лежит в VCS, значит правка дефекта - коммит
в документ, а не устная правка в чате: иначе код расходится со спекой в момент рождения и
нить `FR -> тест` начинает врать.

Отсюда у трека **два режима входа**: (1) сырая идея/бриф; (2) возврат с дефектом от нижнего
узла. Во втором случае работа - точечная: закрыть названный дефект, не переписывать BRD.

## Правки агента `business-requirements-analyst`

Рецепт не меняется: текущие фазы (`Context Gathering?` -> `Direct Analysis` ->
`Skill-Based Deep Scan` -> `Report`) дословно совпадают с рецептом **Analyst** из
`AGENT_FRAMEWORK`. Правки точечные:

| Что | Зачем |
|---|---|
| `skills: dex-skill-node-contract` во frontmatter | агент становится узлом конвейера; валидатор разрешает (allowlist `ALLOWED_PRELOAD_SKILLS`) |
| `Input (handoff)` в Phase 1 | `mode`, идея/бриф, `constraints`. Бизнес-ось входа не обязательна: сырая идея и есть работа агента |
| `Output (handoff)` в Phase 4 | первым полем `status`; далее путь BRD, перечень `FR`/`NFR`, открытые вопросы, допущения |
| `dex-skill-nfr:nfr` в Skill-Based Deep Scan | **дыра**: сейчас подключены `doc-standards` и `requirement-quality`, но НФТ никто не проверяет на осмысленность (числа, SLA/SLO/SLI, p99, security-NFR) |
| Состав BRD в Phase 4 | по разделу «Формат BRD» выше |
| `model: sonnet` -> `opus` | работа = выявление противоречий между требованиями (фальсификация); цена ошибки на входе конвейера максимальная - дефект требований отравляет всё ниже. Альтернатива: оставить `sonnet` (human-in-loop частично страхует); фреймворк велит давать `opus` скупо |
| `Boundaries` | + «код не открываем, выполнимость не оцениваем - это трек Спецификация» |

Проверено: строка Boundaries «Не писать user stories - это SA/user-story-writer» **корректна**,
агент `dex-user-story-writer` существует в каталоге. Не трогать.

`tools` менять не нужно: `Bash` агенту не требуется (следствие границы D1), `Read/Grep/Glob`
нужны для чтения существующих документов проекта (ADR, прошлые BRD), не кода.

## Вне scope

- Треки «Приёмка на стенде» и «Аналитика/ресёрч» (есть в `DEV_PROCESS_COVERAGE`, нет в
  движке) - отдельные задачи, механичнее: агенты уже есть, нужна только дельта трека.
- Привязка к трекам агентов `review-planner`, `conflict-resolver`, `code-discovery` и
  продуктового блока (`backlog-manager`, `roadmap-planner`, `metrics-analyst`).
- Задача 110 (переработка 57 агентов под AGENT_FRAMEWORK) целиком. Пересечение: пункт 110
  «`skills:` во frontmatter запрещён» **устарел** - issue создан 2026-06-29, а pre-load
  `skills:` узаконен позже, 2026-07-01 в PR #107, и подтверждён валидатором
  (`ALLOWED_PRELOAD_SKILLS = {node-contract}`). Мигрировать `skills:` не нужно; пункт в
  issue стоит поправить.

## Решённые развилки

- `model` агента: **`opus`** (решено 2026-07-14). Работа фальсификационная, цена ошибки на
  входе конвейера максимальная. Отвергнуто: `sonnet` (human-in-loop страхует лишь частично).
