# Claude 5: конспект источников для миграции контекста

Фактическая база миграции. Каждый тезис привязан к источнику. Тезисы, к нашему репозиторию не применимые, помечены явно - они тоже результат аудита.

Дата сверки источников: 2026-07-25. Материалы вышли 24.07.2026, то есть за день до сверки; поиск более свежих публикаций Anthropic по теме результата не дал (см. «Что искали и не нашли»).

Конспект под конкретную миграцию, привязан к одной дате сверки и одному поколению моделей; источником истины для каталога не является. Удалить после завершения миграции; пережившие её выводы переезжают в нормативные доки со своей сверкой.

## Шесть сдвигов S1: что следует для нас

Заголовки приведены дословно по S1. Где наше прочтение шире исходного, это помечено: обобщение - наша ответственность, а не цитата.

| Сдвиг S1 (дословно) | Что говорит источник | Применимость к репозиторию |
|---|---|---|
| Then: Give Claude rules -> Now: Let Claude use judgement | Жёсткое правило заменяется описанием намерения | **Применимо частично.** Канонический пример S1 (правило про комментарии -> «пиши как соседний код») у нас уже реализован целым скиллом `dex-skill-codebase-conventions`. Остаточные случаи - чек-листы-развилки в агентах |
| Then: Give Claude examples -> Now: Design interfaces | Few-shot сужает пространство решений; лучше самоописательный интерфейс | **Применимо.** Проверять: примеры «вот так пиши» в агентах. Не трогать: примеры формата/схемы/контракта |
| Then: Put it all upfront -> Now: Use progressive disclosure | Детали переезжают в подгружаемые по необходимости материалы | **Уже сделано на уровне механизма:** условные skills грузятся императивно в фазах, pre-load только у безусловного `node-contract`. Остаточное - длинные `SKILL.md`, не разбитые на вход + дерево |
| Then: Repeat yourself -> Now: Simple tool descriptions | Дословный предмет узкий: «our system prompt would sometimes have references to tools in the main system prompt as well as instructions in the tool description. We found we could delete these repeat examples and put instructions on how to use tools in the tool descriptions rather than the system prompt» | **Буквально к нам не относится:** своих tool descriptions у репозитория нет. Обобщение «инструкция живёт в одном слое» - **наше**, и опирается оно на собственное правило репо «один факт - один нормативный дом», которое старше статьи. Под это обобщение попала главная находка аудита: skill-дом `dex-skill-fact-verification:fact-verification` грузят десятки агентов, и часть из них дополнительно пересказывала его правила своими словами. Числа снимка - в [claude5-context-inventory.md](claude5-context-inventory.md), они привязаны к своему коммиту и здесь не дублируются (правило «числа состояния каталога не хардкодить»). Пересказ снят в PR #145; на `4c5c76d` в телах агентов остаётся только привязка статуса к собственному маркеру агента, не изложение механизма скилла |
| Then: Memory in CLAUDE.md files -> Now: Auto-memory | Ставка на авто-память | **Применимо к одной строке.** Авто-память Claude Code включена по умолчанию (S10), поэтому инструкция «запоминай инсайты» лишняя. Но `CLAUDE.md` репозитория авто-память не заменяет: он не журнал состояния, а нормативный дом правил разработки, нужный каждому контрибьютору, а не одной машине |
| Then: Simple specs -> Now: Rich references | Тестовый набор, рабочий код, рубрика вместо плоского текста | **Применимо ограниченно.** Референс-реализации у нас уже названы (`dex-mr-reviewer` как референс рецепта Reviewer). Полноценные тестовые наборы - за рамками задачи |

**Что S1 говорит про skills и `CLAUDE.md`, дословно.** Про скиллы: «It's best when skills encode particular opinions, knowledge, or best practices that are particular to you, your team, or product» и «Think of skills as lightweight guides to let Claude find information when needed». Про корневой файл: «Keep your CLAUDE.md lightweight and briefly describe what your repo is for, but spend most of the tokens on gotchas inside of the codebase».

Отсюда честная картина, а не удобная. Первая половина поддерживает нашу позицию: мнения и практики команды - законное содержимое скиллов, доменные грабли - законное содержимое корневого файла. Вторая половина работает против нас: `CLAUDE.md` статья просит держать **lightweight**, а наш корневой файл этому не отвечает и является нормативным доком, а не описанием проекта. Это расхождение мы принимаем осознанно и фиксируем здесь, а не выдаём статью за одобрение текущего размера.

## Поведенческие отличия Opus 5 (S2, S4)

| Поведение | Источник | Что делать |
|---|---|---|
| Ответы пользователю длиннее, чем у прошлых Opus; `effort` видимую длину не регулирует | S2 «Response length and verbosity», S4 «Model behavior differences», S6 | Просить краткость промтом явно |
| Чаще комментирует ход работы в агентских сессиях | S2 «User-facing progress updates», S4 | Задать каденцию: что до первого вызова, когда промежуточный апдейт, чем начинать финал |
| Письменные артефакты на диск выходят длиннее | S2 «Written deliverable length», S5 (пункт «Re-tune length and verbosity prompts») | Калибровка длины по существу задачи |
| Проверяет свою работу сам; унаследованные инструкции верификации дают переверификацию | S2 «Task scope and over-verification», S4, S3 («Ask Claude to self-check» с оговоркой про Opus 5) | **Удалять** такие инструкции, а не переписывать |
| Расширяет объём задачи, добавляет незаказанные шаги | S2 «Task scope and over-verification» | Для узких агентов зафиксировать границу объёма |
| Делегирует сабагентам охотнее прошлых моделей | S2 «Controlling subagent spawning», S4, S3 «Subagent orchestration» | Делегирование только на крупных независимых треках; не для проверки своей же работы |
| Чаще проговаривает исправления своих прежних утверждений | S2 «Self-correction» | Оговаривать правку, только если она меняет решение читателя |
| Ревью: «сообщай только критичное» / «будь консервативен» исполняется буквально и снижает охват | S2 «Capability improvements», раздел Code review | Просить полный список, фильтровать отдельным проходом |

Оговорка про сабагентов: S2 и S4 одновременно называют координацию команд сабагентов сильной стороной Opus 5, с эффективными writer-verifier паттернами. То есть резать надо **безусловный** спавн и делегирование мелочи, а не writer-verifier как приём.

Оговорка про делегирование в S3: базовая рекомендация там обратная нашей - «Let Claude orchestrate naturally: Claude will delegate appropriately without explicit instruction», а явное правило порога прописывается только «if you're seeing excessive subagent use». Наш случай именно этот: в агентах стояли безусловные императивы «запускай субагентов по осям», то есть предписанная избыточность, а не наблюдаемая. Порог мы вводим на этом основании, а не потому, что его требуют доки по умолчанию.

## Охват вывода: таблица выше про Opus 5, а не про поколение

Корневая страница S3 устроена как хаб: сначала модель-специфичные страницы (Fable 5, Sonnet 5, Opus 5, Opus 4.8), затем техники для всех актуальных моделей, затем миграция. Значит вывод, снятый с листа одной модели, к артефакту на другой модели не применяется без сверки. Проверка на Sonnet 5 (сверено 27.07.2026) показала, что два вывода таблицы там читаются иначе:

| Вывод по Opus 5 | Что на странице Sonnet 5 |
|---|---|
| Проверяет себя сам, унаследованные инструкции верификации удалять | Раздел «Tool use triggering»: «Claude Sonnet 5 is more agentic than Claude Sonnet 4.6 by default and **will reach for tools and run self-verification loops more readily**» |
| Консервативный фильтр в ревью срезает охват | То же, но заявлено сильнее и отдельным разделом «Code review harnesses», с готовой формулировкой промта на покрытие |
| Инструкцию с одного пункта на соседний модель молча не переносит | Подтверждено: «It **does not silently generalize** an instruction from one item to another» - значит область применения правила пишется явно |

Практическое следствие для миграции: у каждого артефакта каталога свой `model:`, и правка, выведенная из гайда Opus 5, законна только для артефактов на `opus`. Для остальных нужна сверка со своей страницей, а у тира без своей страницы (на 27.07.2026 - `haiku`) остаётся кросс-модельная часть корня плюс статус `unverifiable`, не перенос выводов с соседней модели. Это же ограничение действует и в обратную сторону: наблюдение с Sonnet 5 не переносится на Opus 5 молча.

## Что доки требуют оставить или добавить, а не резать (S3)

Раздел появился по итогам повторной сверки: при первом проходе эти пункты были пропущены, и один из них противоречил уже сделанной правке.

| Тезис источника | Дословно | Следствие |
|---|---|---|
| Инструкция «сначала прочитай код, потом отвечай» - рекомендуемая, а не устаревшая | S3 «Minimizing hallucinations in agentic coding»: «Never speculate about code you have not opened. If the user references a specific file, you MUST read the file before answering. Make sure to investigate and read relevant files BEFORE answering questions about the codebase» | **Правка пилота отменена.** Строку `перед изменениями - изучи существующий код` мы сняли как компенсатор прошлого поколения. Доки для актуальных моделей прямо предлагают инструкцию этой формы, причём с усилением («To encourage this behavior even more»). Строка возвращена |
| Над-промптинг триггеров инструментов вреден | S3 «Overthinking and excessive thoroughness» (раздел назван по Opus 4.6: «Claude Opus 4.6 does more upfront exploration than previous models... you should tune that guidance for Claude Opus 4.6»): «Remove over-prompting. Tools that undertriggered in previous models are likely to trigger appropriately now. Instructions like "If in doubt, use [tool]" will cause overtriggering» | Подтверждает снятие `используй подходящие скиллы и агенты`: это ровно инструкция-триггер, которая теперь перетриггеривает. **Перенос на актуальное поколение - наш**, по правилу охвата (см. «Охват вывода»): вывод снят с модель-специфичного раздела, для артефакта не на этом тире сверяется по своей странице |
| Защитное программирование - только на границах | S3 «Overeagerness» (раздел общий для актуальных моделей, вводный абзац назван по Opus 4.5 и 4.6): «Don't add error handling, fallbacks, or validation for scenarios that can't happen. Trust internal code and framework guarantees. Only validate at system boundaries» | Подтверждает снятие `контроль входящих аргументов` |
| У актуальных моделей стиль короче, у Opus 5 наоборот | S3 «Communication style and verbosity»: «Less verbose: May skip detailed summaries for efficiency unless prompted otherwise», и тут же «Claude Opus 5 is an exception on verbosity» | Инструкцию про краткость ставим адресно под Opus 5, а не как общее правило поколения |

## Effort (S6, S4, S5)

- Полная лестница на Opus 5: `low`, `medium`, `high` (дефолт), `xhigh`, `max`. Дефолт API - `high`; `high` эквивалентен неуказанию параметра (S6).
- Рекомендация Opus 5: старт с `high`, вверх `xhigh`/`max` для тяжёлой агентской и кодинговой работы, **`low` и `medium` использовать свободно как основной рычаг стоимости и времени ответа там, где эвалы показывают, что качество держится** (S6 «Recommended effort levels for Claude Opus 5»).
- Настройки, перенесённые с прошлой модели, требуют свежего прогона effort sweep на своих эвалах, а не переиспользования (S6, S5 чек-лист).
- Effort влияет на все токены ответа, включая вызовы инструментов: на низком уровне модель делает меньше вызовов (S6 «How effort works», «Effort with tool use»).
- Effort управляет объёмом размышления, **не видимой длиной ответа** - длину задавать промтом (S6, S2).
- Смена effort между запросами инвалидирует кеш префикса: внутри одной кешируемой сессии уровень держать постоянным (S6 «Changing effort mid-conversation»).
- В Claude Code `effort` - штатное поле frontmatter субагента, перекрывает уровень сессии, дефолт - наследование (S9). В списке полей, игнорируемых у плагинных субагентов (`hooks`, `mcpServers`, `permissionMode`), его нет.

**Следствие для нас:** в `run-claude/` и конфигурациях уровни effort не зашиты (проверено грепом, см. инвентаризацию) - подкручивать нечего. Ось effort у агентов вводится как возможность, значения без замеров не проставляются.

## Прочие API-факты, к артефактам не применимые

Зафиксированы, чтобы не всплывали как «а вдруг надо»:

- Thinking включён по умолчанию на Opus 5; отключение допустимо только при effort `high` и ниже, иначе 400 (S4, S5). Нас не касается: плагины не формируют HTTP-запросы, `thinking` наследуется от сессии Claude Code (S9).
- Минимум кешируемого промта снижен до 512 токенов, mid-conversation tool changes, fallbacks `"default"`, fast mode (S4). Уровень API-интеграции, у нас его нет.
- 1M контекст как дефолт и максимум, 128k max output (S4). На правила написания артефактов не влияет, кроме общего вывода: экономия контекста перестала быть выживанием и стала гигиеной.
- `budget_tokens` на моделях 4.7 и новее возвращает 400 (S3, «Overthinking and excessive thoroughness»). У нас параметр нигде не зашит (проверено грепом), но факт фиксируем: если он появится в чьём-то конфиге, это будет отказ, а не деградация.

**Один API-факт всё-таки применим к артефактам.** S6 перечисляет модели с поддержкой `effort` поимённо: Fable 5, Mythos 5, Opus 5, Opus 4.8, Mythos Preview, Opus 4.7, Opus 4.6, Sonnet 5, Sonnet 4.6, Opus 4.5. Ни одной модели Haiku в перечне нет, и S9 говорит то же общим правилом - «available levels depend on the model». Значит, `effort` во frontmatter агента с `model: haiku` смысла не имеет. Это ограничение попало в `AGENT_FRAMEWORK` и в валидатор (PR #130).

## Верификация через skills (S8)

S8 описывает, как **намеренно** проектировать петли верификации скиллами (standalone / embedded / chained / on every PR) и приводит внутренний пример команды Claude Code: «/code-review hunts for bugs, /simplify cleans up the diff, a /verify skill confirms end-to-end behavior, and a custom /design skill checks against guidelines».

Важная оговорка после повторной сверки: **S8 вопрос о новых моделях не поднимает вообще.** Значит, ссылаться на него как на довод «верификация всё ещё нужна на Opus 5» нельзя, это было бы натяжкой. Что S8 действительно даёт - источник доверия к шагу проверки: «Claude already does some of this from observing the deterministic signals in your codebase, including type checkers, linters, tests, and runtime errors». Детерминированный сигнал извне - вот на чём держится законная петля.

Противоречия с S2 нет, если развести:

- **Инструкция модели перепроверить себя** («убедись ещё раз», «добавь финальный шаг верификации») - складывается с собственным поведением Opus 5, даёт переверификацию. Убирать (S2, S4).
- **Петля верификации с внешней опорой** (прогон тестов, линтер, сверка с источником, отдельный проход по диффу) - остаётся приёмом и по S8 оформляется скиллом.

Рабочий критерий: **какой факт извне появляется по итогу шага?** Нет ответа - это самоперечитывание, режем. Есть - это петля верификации, оставляем. Критерий **наш**: S2 требует удалять инструкции верификации и называет примером в том числе «use a subagent to verify», а исключения по внешней опоре не описывает. Опору под него даёт формулировка S8 про детерминированные сигналы, но само разведение - инженерное решение репозитория, и на источник его списывать нельзя.

## Что искали, что нашли и чего нет

Повторная сверка 25.07.2026, отдельным проходом по стороннему полю.

- **Независимого воспроизведения эксперимента с 80% нет.** Поиск отдаёт первоисточник, тред автора в X и вторичные пересказы (the-decoder, charlesjones.dev, claudeainews, агрегаторы). Ни один из них не проводит собственных замеров, все ссылаются на те же внутренние оценки Anthropic. В правки такие материалы не идут.
- **Внешних замеров эффекта у нас тоже нет.** Единственная опора на цифру 80% - заявление вендора о своих эвалах на своём продукте. Для решений по каталогу этого достаточно как ориентира и недостаточно как основания резать по проценту.
- **Независимые бенчмарки контекста для SE существуют и говорят скорее в пользу «держать».** S11 (CL4SE, arXiv 2602.23047, 26.02.2026) строит таксономию типов контекста и меряет их эффект по задачам SE: в абстракте заявлены среднее улучшение 24.7% по задачам и, что для нас важнее всего, рост качества code review до 33% именно от **процедурного** контекста. Это тот самый класс, к которому относятся наши workflow-контракты агентов. Рядом лежат SWE Context Bench (arXiv 2602.08316), CL-bench (arXiv 2602.03587), LoCoBench (arXiv 2509.09614). Оговорка, без которой цитата была бы нечестной: прочитан только абстракт CL4SE, полный текст не читался; и ни одна из этих работ не меряет **цену избыточного и дублирующегося** контекста, то есть ни подтвердить, ни опровергнуть рез 80% они не могут.
- **Прямого утверждения «сокращайте доменные знания и договорённости команды» в S1-S11 нет.** S1 в части скиллов противоположен: «It's best when skills encode particular opinions, knowledge, or best practices that are particular to you, your team, or product». Но там же есть «Keep your CLAUDE.md lightweight», и это работает против размера нашего корневого файла - см. разбор шести сдвигов.

## Главный вывод для объёма правок

Резали продуктовый слой «как быть агентом»: как звать инструменты, как форматировать, как не лениться (S1). Артефакты каталога - другой слой: грабли предметной области, workflow-контракты, конвенции репозитория. Пропорциональный рез здесь удалил бы то, ради чего каталог существует.

Поэтому целевая метрика миграции - **не процент удалённого текста**, а число снятых дублей между слоями, снятых конфликтов и удалённых инструкций, компенсирующих слабости прошлого поколения.

Единственная внешняя опора под этим выводом на сегодня - S11: процедурный контекст даёт наибольший измеренный прирост именно на code review, а процедурный контекст у нас это и есть фазовые контракты агентов. Опора слабая (один бенчмарк, прочитан абстракт, другие модели), поэтому она приводится как согласующийся сигнал, а не как доказательство.
