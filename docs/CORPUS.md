# Корпус на диске: носители, уровни, раскладка

Карта: **что за артефакт, на каком уровне, в каком носителе и по какому ключу пути он лежит, кто его
судит**. Нормативного текста здесь нет - у каждого факта назван дом, и при расхождении действует дом,
а не эта карта. Заводится карта потому, что раскладка собирается из шести домов сразу
(`project-docs-map`, `docs-layout`, `artifact-naming`, `business-analysis-29148`, треки зон,
`node-contract`), и ни один из них не виден целиком.

**Предмет карты - корпус проекта, который ведут конвейеры каталога**, то есть репозиторий
пользователя, а не документы этого репозитория. Уровень 0 самого каталога (`docs/product/brd.md`,
`docs/domain/`) устроен по той же модели, но раскладку ему задаёт [CLAUDE.md](../CLAUDE.md), не эта
карта.

Словарь терминов (`BR`, `UC`, `FR`, `NFR`, корпус уровня 0, уровень артефакта) - [docs/domain/domain-model.md](domain/domain-model.md).
Порядок работ зоны требований - [docs/pipelines/analytics/PIPELINE.md](pipelines/analytics/PIPELINE.md).

## 1. Три носителя

Смешивать нельзя: у каждого своя судьба относительно git и MR.

| Носитель | Где | В git | Что несёт | Дом |
|---|---|---|---|---|
| корпус проекта | по ключам `.docs_layout` (`root`, `usecases`, `strategy`, `verification`, `product`, `domain`, `adr`, `specs`, `plans`, `counter`) | да | принятое: требования, ADR, дизайн, планы, уровень 0 | `dex-skill-project-docs-map:project-docs-map` |
| документация задачи | `docs/<TASK>/` | да, едет с MR | рабочие документы одной задачи | тот же |
| auto-ledger | `auto-ledger/<TASK>.md` в папке сессии Claude Code, вне рабочего дерева | нет | журнал автономного прогона движка | `dex-sdlc:engine` (`P-auto-ledger`), хук `dex-sdlc-resume` |

Запись не по назначению даёт либо утечку служебного состояния в MR, либо потерю документации задачи
вместе со средой.

## 2. Уровни артефакта

Нумеруется только уровень артефакта; зона имени-номера не несёт (`D-1` доменной модели).

| Уровень | Что | Где | Кто ведёт |
|---|---|---|---|
| 0 - продукт | BRD продукта (`brd.md`), доменная модель, конституция (`INV`, `NFR-P`) | ключи `product`, `domain` | зона продукта, `/product` |
| 1 - фича | цели фичи, сценарии, правила и меры, истории с `AC` | дерево фичи в `root` | зона требований, `/feature` |
| 2 - реализация | дизайн-документ, ADR, API-спеки, план реализации | ключи `specs`, `adr`, `plans` | зона дизайна, `/design` |
| 3 - код и тесты | код, тесты, миграции, конфиги | рабочее дерево репозитория | зоны разработки и тестирования |

**Признак уровня 0 проверяемый: единица переживает удаление любой одной фичи.** Не переживает - это
уровень 1, и в `product`/`domain` она не кладётся. Ключей `product`/`domain` в `.docs_layout` нет ->
уровень 0 в проекте **не заведён**; это не то же, что «пути не найдены»: узел называет отсутствие
строкой выхода и работает без него.

## 3. Раскладка на диске

Дефолт для пустого места держит норматив раскладки `dex-skill-docs-layout:docs-layout`: дерево
каталогов, имена файлов классов, минимум обязательного, глубина. Второго дерева здесь нет -
соответствие «класс - адресующий его ключ» лежит разделом ниже, и адресуют корпус ключи, а не имена
каталогов дефолта.

Занятый корпус диктует раскладку сам: конвенция к нему не применяется, каталог и форма имени берутся
с образца (`dex-skill-artifact-naming:artifact-naming`, «Границы конвенции»). Дефолт включается
там, где выбирать не из чего, - корпус пуст либо класс в нём ещё не встречался.

**Уровень различает путь, а не имя жанра.** BRD продукта и BRD фичи - один жанр на двух уровнях:
второго имени под второй уровень не заводится, иначе один документ читается как два. Отдельного PRD
по той же причине нет.

**Путь разрешается один раз за прогон и едет сквозным полем.** Ступени: поле входа -> `project-docs-map`
-> образец в корпусе -> дерево норматива раскладки. В телах агентов путей нет - прописанный путь не
знает ни о чужой раскладке, ни о недостижимом корне.

**Дерева под класс нет вовсе - заготовку разворачивает трек зоны**, по нормативу раскладки
`docs-layout` (что завести, минимум обязательного, глубина). Разворачивает только трек: `Write` есть
у всех составителей, и два параллельных прогона дали бы две папки с одним номером. Ключи дописываются
тем же действием, и дальше адресуют корпус они - имена каталогов из норматива остаются дефолтом
пустого места, а не вторым адресом.

## 4. Пути и счётчики

Соответствие «что лежит - по какому ключу»; форма файлов, поиск при их отсутствии и терминалы
недостижимости - `dex-skill-project-docs-map:project-docs-map`.

| Ключ `.docs_layout` | Адресует |
|---|---|
| `root` | корпус требований фичи |
| `usecases` | сценарии `UC`: папка на фичу, файл на сценарий |
| `strategy` | идеи до входа в конвейер (one-pager, opportunity canvas) |
| `verification` | план верификации и собранные из `AC` исполняемые примеры |
| `product`, `domain` | корпус уровня 0 |
| `adr`, `specs`, `plans` | решения, спеки, планы реализации |
| `counter` | директория `.req_counter` |

Ключа класса нет -> класс в проекте не заведён; ключ заводит тем же заходом тот, кто пишет первый
его артефакт. Имя каталога адресом не служит: адресует ключ. Ключа нет, а писать надо -> имя берётся из дерева
`docs-layout` и тем же заходом записывается ключом.

`.req_counter` - директория, ключ в ней - файл, содержимое - последний выданный **полный** номер:
`feature`, `BR`/`INV`/`NFR-P` (уровень 0, без старшего разряда), `NN.<КЛАСС>` в блоке фичи `NN`
(`NN.BR`, `NN.UC`, `NN.FR`, `NN.NFR`, `NN.ST`; перечень не закрытый). Счётчик **один на корпус, а
не на репозиторий**: у продукта бывает много реп, а
номер требования принадлежит продукту. Конфликт слияния по ключу читается как факт двойной выдачи
номера, а не как текст - выбор стороны запрещён.

## 5. Зона -> артефакт -> оракул

Судья артефакта - никогда его автор. Реестр «тип артефакта -> оракул» с указанием судьи -
`dex-skill-node-contract:node-contract`, `references/quality-and-review.md` п.1; здесь - только
маршрутная сводка.

| Зона (команда) | Артефакт на диске | Оракул типа |
|---|---|---|
| продукт (`/product`) | `brd.md`, доменная модель, конституция | `requirement-quality` + `requirement-set-quality`; словарь - `domain-model-quality` не существует -> `unverifiable` |
| требования (`/feature`) | BRD и SRS фичи, сценарии, истории с AC | `requirement-quality` на единицу, `requirement-set-quality` на набор, проба готовности на допуск |
| дизайн (`/design`) | дизайн-документ, ADR, API-спека, план реализации | `design-quality`, `adr-quality`, `plan-quality`, `api-spec-quality` |
| разработка (`/implement`) | код, edit-план | `plan-quality` на edit-план; код судит ревью |
| тестирование (`/test`) | тесты, матрица покрытия | оракул - корпус требований (`AC`, `FR`), не отдельный skill |
| ревью MR (`/mr-review`) | треды и находки в MR | - |
| приёмка (`/review-stand`) | отчёт приёмки против ТЗ | - |
| документация (`/documentation`) | документы по жанру | - |

Метка результата - `quality-checks` рядом с артефактом; `verdict` из трёх значений (`passed`,
`failed`, `unverifiable`), `n/a` в нём не пишется.

## 6. Трассировка

Хранится **одно направление - на чём единица стоит**; производные находятся поиском по номеру в
момент правки.

| Единица | `traced from` |
|---|---|
| `BR` фичи | `BR-NNN` продуктового BRD, когда подходящая цель там найдена; не найдена -> цель или сторона, и строка выхода несёт перечень `BR-NNN`, по которым шла сверка |
| `UC` | `BR-NNN` своей фичи |
| `FR` | шаг или расширение сценария `UC` |
| `NFR` | `BR` либо ограничение среды |
| story / `AC` | `FR-NNN` (метка источника у каждого `AC`) и ветки сценария |
| `INV`, `NFR-P` | `BR` продуктового BRD |
| план реализации | `FR`/`NFR`, закрываемые инкрементом |

**Трасса «цель фичи -> цель продукта» мягкая и второго слоя требований не заводит**: она выражена
существующим атрибутом, а не новым. Обязанности заводить цель продукта ради трассы у узла нет -
дельта-прогон `/product` решает оператор.

## 7. Статусы вместо молчания

Уход от проверки фиксируется явным статусом; молчание - дефект. Дома: `business-analysis-29148` (проверка
3 состава BRD), `node-contract` (вердикты и поля выхода).

| Статус | Когда | Носитель |
|---|---|---|
| `n/a` + причина | раздел или проверка к случаю неприменимы | артефакт (шапка раздела) |
| «нет данных» + номер открытого вопроса | применимо, данных нет | артефакт |
| `inherited` + ссылка на раздел продуктового BRD | данные есть, их дом - уровень 0; **только `level: feature`** | артефакт |
| `unverifiable` + причина | оракула для типа нет, текст оракула недоступен, источник не читается | `quality-checks`, выход узла |
| `contradicted` | сверка дала противоречие источнику | выход узла |
| `pending-judgement` | автор объявил ожидаемую, но не состоявшуюся проверку | только выход узла |
| `self-check` | самоконтроль автора до суда; вердиктом не является | только выход узла |

## 8. Почему на уровне фичи не PRD

Отраслевые контуры разделяют документы по **субъекту требования** (ISO/IEC/IEEE 29148: BRS -> StRS ->
SyRS -> SRS) либо по **уровню решения** (продуктовая практика: BRD на проект, PRD на фичу; SAFe: Lean
Business Case на эпик, benefit hypothesis + AC на фичу). Каталог берёт первый контур: норма нарезана
по **классам единиц** (`BR`, `UC`, `FR`, `NFR`, `AC`) - у каждого свой skill и свой оракул, - а
контейнеры нормируются отдельно («контейнер - не класс», `PIPELINE.md` раздел 3).

PRD на этом контуре не нужен как отдельный тип: то, что он держит в одном файле (цели, сценарии,
требования, критерии приёмки), у нас разложено по BRD фичи, сценариям, SRS и историям с AC, и
каждая часть судится своим оракулом. Завести PRD означало бы завести контейнер без
собственного класса единиц и без оракула - то есть документ, чью готовность нечем проверить.

Статусы сверки со стандартами - [docs/standards/README.md](standards/README.md).
