# Entity Framework Core - чек-лист

Пункт называет ситуацию, которую изменение проверяет; решение - по документации EF Core / Npgsql версии из манифеста проекта.

- Ленивая загрузка навигации в цикле: Связанные данные, нужные в цикле, загружаются заранее одним запросом (Include или проекция), а не отдельным round-trip на каждую итерацию
- Трекинг выборки только для чтения: Сущности, которые в этой единице работы не изменяются, не попадают в change tracker (no-tracking запрос, no-tracking по умолчанию в контексте или проекция без сущностей)
- Полная сущность там, где нужна часть полей: Для чтения запрос выбирает из БД только нужные столбцы (проекция в DTO/анонимный тип), а не полные сущности со всеми колонками
- Фильтр после материализации: Бизнес-фильтр выполняется в SQL (WHERE) до материализации: из БД приходят только прошедшие его строки, а не вся таблица для фильтрации в памяти
- Группировка и агрегаты после материализации: Группировка и агрегаты (Count/Sum/Max/Any…) вычисляются в SQL (GROUP BY, агрегатные функции): клиент получает ключи и итоги, а не все строки
- Нетранслируемое условие фильтра: Условие фильтра выражено через маппленные свойства и транслируемые функции и выполняется в SQL; клиентская часть - только явно (AsEnumerable) после серверного сужения выборки
- `!` на nullable-значении без фильтра по null: Значение из nullable-колонки разыменовывается только после исключения null в запросе (IS NOT NULL) или явной проверки в коде; `!` защитой не считается - в runtime он ничего не делает
- `Single` на условии, которое в домене не уникально: Single/SingleOrDefault - только на условии, уникальность которого гарантирует схема (PK/уникальный индекс); при допустимых дубликатах выбор строки детерминирован или обрабатываются все
- Динамически собираемый `FromSqlRaw`: Значения в динамическом FromSqlRaw уходят как DbParameter; в текст SQL вставляются только проверенные фрагменты/идентификаторы (белый список), не пользовательский ввод
- `Add` и `AddAsync`: Сущность добавляется синхронным Add; AddAsync - только если генератор значений ключа обращается к БД (HiLo/sequence)
- `DateTime` и тип колонки в Npgsql: с Npgsql 6 свойство без явного типа - `timestamptz`; Kind DateTime соответствует колонке: в timestamptz (дефолт для DateTime) пишется только Kind=Utc, в timestamp - только Unspecified/Local; иначе Npgsql бросает при записи
- Soft-delete (`HasQueryFilter`) и каскад FK: У FK на soft-delete сущность нет ON DELETE CASCADE в БД; при HasQueryFilter у principal и required-связи у зависимых согласованный фильтр или связь optional
- Разрыв required-связи (`Clear()` коллекции зависимых): при `Restrict` и `ClientSetNull` разрыв required-связи в `SaveChanges` бросает `InvalidOperationException`; Код, разрывающий required-связь, рассчитан на один из исходов: зависимые удаляются (Cascade/ClientCascade) или SaveChanges бросает; открепить без удаления - только при optional FK
- Параллельная правка одной записи: Параллельная правка одной записи не перезаписывается молча: устаревшее сохранение обнаруживается (concurrency token → DbUpdateConcurrencyException или изоляция) и обрабатывается
- `FOR UPDATE` и граница транзакции: SELECT … FOR UPDATE, изменение и SaveChanges идут в одной явной транзакции на одном соединении; блокировка держится до Commit, без транзакции снимается сразу после SELECT
- `SaveChanges` в цикле по строкам: Изменения набора строк уходят одним SaveChanges после цикла (EF батчит) или одним set-based ExecuteUpdate/ExecuteDelete, а не round-trip на каждую строку
- Массовое удаление одной транзакцией
- `UpdateRange` на отслеживаемых сущностях: Для уже отслеживаемых сущностей Update/UpdateRange не вызывается: SaveChanges сам находит изменения и пишет только изменённые колонки
- Несколько коллекций в одном `Include`-запросе: Для запроса с ≥2 коллекциями одного уровня режим задан явно (split или single, на запросе или глобально) с учётом декартова роста строк; без этого EF пишет предупреждение
- Split query на выборке одной сущности
- Применение миграции на production: Применяемые на production миграции заранее проверены и протестированы; катятся артефактом (SQL-скрипт или migration bundle), а не `dotnet ef database update` с SDK и исходниками
- Схемная миграция и исторические данные: Миграция, меняющая место хранения данных, переносит существующие строки в новую структуру до удаления источника; новый код с первого деплоя видит исторические данные
- Время жизни `DbContext`: Экземпляр DbContext живёт одну единицу работы (в веб - scope запроса), освобождается после неё и никогда не используется параллельно; не singleton и не static
- `DbContext` в `BackgroundService`: BackgroundService не держит DbContext из конструктора: на каждую единицу работы создаётся и освобождается свой экземпляр (scope через IServiceScopeFactory или IDbContextFactory)
