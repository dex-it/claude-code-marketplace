# Entity Framework Core - чек-лист

Пункт называет ситуацию, которую изменение проверяет; решение - по документации EF Core / Npgsql версии из манифеста проекта.

- Ленивая загрузка навигации в цикле: Связанные данные для набора строк грузятся фиксированным числом запросов (Include, проекция, split query), а не запросом на каждый элемент цикла
- Трекинг выборки только для чтения: Выборка, которую не изменяют и не сохраняют через этот контекст, не отслеживается (AsNoTracking*, NoTracking по умолчанию, проекция не-сущностей)
- Полная сущность там, где нужна часть полей: Запрос, чей результат не сохраняется через change tracker, тянет из БД только колонки, которые использует потребитель (Select в DTO/анонимный тип)
- Фильтр после материализации: Каждое транслируемое условие фильтра применяется к IQueryable до материализации (SQL WHERE); на клиенте — только нетранслируемый остаток
- Группировка и агрегаты после материализации: Группировки и агрегаты (Count, Sum, Max, Any…) вычисляются в БД до материализации (GROUP BY/агрегат в SQL), а не над загруженной коллекцией
- Нетранслируемое условие фильтра: Условие вне финального Select выражено транслируемо (развёрнутое выражение, HasDbFunction) или явно уходит на клиент после AsEnumerable на суженной выборке
- `!` на nullable-значении без фильтра по null: Nullable-значение (колонка, агрегат над пустым набором) разыменовывается только после фильтра по null в запросе или явной проверки; `!` проверкой не является
- `Single` на условии, которое в домене не уникально: Single/SingleOrDefault — только где >1 строки гарантированно исключено (ключ, уникальный индекс); иначе условие сужено до уникального или выбор одной явный
- Динамически собираемый `FromSqlRaw`: Динамический FromSqlRaw: значения — только параметрами (DbParameter, {0}), идентификаторы и фрагменты — из кода/белого списка и ссылаются на алиасы из FROM
- `Add` и `AddAsync`: AddAsync/AddRangeAsync — только при генераторе ключей, который обращается к БД (HiLo/sequence); в остальных случаях Add/AddRange
- `DateTime` и тип колонки в Npgsql: с Npgsql 6 свойство без явного типа - `timestamptz`; Npgsql 6+ (без legacy-режима): DateTime без типа — timestamptz, в него только Kind=Utc (DateTimeOffset — Offset=0); в timestamp — только Local/Unspecified
- Soft-delete (`HasQueryFilter`) и каскад FK: Soft-delete: в БД нет ON DELETE CASCADE к мягко удаляемому принципалу; required-навигация к нему согласована фильтром на зависимом или сделана optional
- Разрыв required-связи (`Clear()` коллекции зависимых): при `Restrict` и `ClientSetNull` разрыв required-связи в `SaveChanges` бросает `InvalidOperationException`; Код, рвущий required-связь, рассчитан на удаление зависимых (Cascade/ClientCascade) или исключение; «открепление» без удаления — только при optional FK
- Параллельная правка одной записи: Конкурентная правка не теряет чужие изменения молча: конфликт исключается блокировкой/изоляцией или ловится токеном (xmin, rowversion) и обрабатывается
- `FOR UPDATE` и граница транзакции: FOR UPDATE и защищаемая им запись выполняются в одной явной транзакции (BeginTransaction, TransactionScope), открытой до SELECT и завершённой после записи
- `SaveChanges` в цикле по строкам: Изменения многих строк уходят пакетно: SaveChanges на единицу работы/пакет (EF батчит) или ExecuteUpdate/ExecuteDelete, а не SaveChanges на каждую строку
- Массовое удаление одной транзакцией
- `UpdateRange` на отслеживаемых сущностях: Отслеживаемые сущности сохраняются SaveChanges без Update/UpdateRange (те помечают все свойства Modified); Update — для неотслеживаемых графов
- Несколько коллекций в одном `Include`-запросе: Режим загрузки ≥2 коллекций одного уровня задан явно (AsSplitQuery/AsSingleQuery, UseQuerySplittingBehavior) по их размеру; N×M строк не тянется молча
- Split query на выборке одной сущности
- Применение миграции на production: Миграция проверена и протестирована до prod и применяется одним шагом деплоя (SQL-скрипт, bundle), а не dotnet ef database update или Migrate() из реплик
- Схемная миграция и исторические данные: Если новая структура заменяет старую как источник данных, миграция переносит существующие строки (Sql, UpdateData) до удаления источника и чтения новым кодом
- Время жизни `DbContext`: Экземпляр DbContext живёт одну единицу работы и не используется параллельно (Scoped через AddDbContext, фабрика, pooling) — не singleton и не static
- `DbContext` в `BackgroundService`: В singleton-сервисе (BackgroundService) DbContext берётся на каждую единицу работы из нового scope (IServiceScopeFactory) или IDbContextFactory
