# Entity Framework Core - чек-лист

Пункт называет ситуацию, которую изменение проверяет; решение - по документации EF Core / Npgsql версии из манифеста проекта.

- Ленивая загрузка навигации в цикле
- Трекинг выборки только для чтения: попадает ли выборка в Change Tracker
- Полная сущность там, где нужна часть полей
- Фильтр после материализации
- Группировка и агрегаты после материализации
- Нетранслируемое условие фильтра: где выполняется условие - в SQL или после материализации
- Репозиторий материализует выборку
- `!` на nullable-значении без фильтра по null
- `Single` на условии, которое в домене не уникально: уникально ли условие в домене и что вернёт метод при нескольких совпадениях
- Null-guard в спецификации на ненулевом параметре
- Динамически собираемый `FromSqlRaw`: алиас в собираемых условиях против алиаса шаблона
- `Add` и `AddAsync`
- Owned-тип из одного поля
- `DateTime` и тип колонки в Npgsql: с Npgsql 6 свойство без явного типа - `timestamptz`; `Kind` против типа колонки при записи, чтении и в параметре запроса
- Soft-delete (`HasQueryFilter`) и каскад FK: что сделает БД с зависимыми строками при физическом `DELETE` родителя
- Разрыв required-связи (`Clear()` коллекции зависимых): при `Restrict` и `ClientSetNull` разрыв required-связи в `SaveChanges` бросает `InvalidOperationException`; что делает `SaveChanges` с зависимым, убранным из required-коллекции, при выбранном `OnDelete`
- Параллельная правка одной записи
- `FOR UPDATE` и граница транзакции
- `SaveChanges` в цикле по строкам
- Массовое удаление одной транзакцией
- `UpdateRange` на отслеживаемых сущностях
- Несколько коллекций в одном `Include`-запросе
- Split query на выборке одной сущности: сколько строк даёт JOIN коллекций этой выборки
- Применение миграции на production: какой SQL уйдёт в базу и кто увидит его до применения
- Данные и схема в одной миграции
- Схемная миграция и исторические данные
- Время жизни `DbContext`
- `DbContext` в `BackgroundService`
