Нашёл 12 дефектов, которые стоит исправить до мерджа: 3 critical, 5 high, 3 medium, 1 low. Код я не менял, сборку и тесты не запускал, поэтому всё ниже основано на чтении кода, README и `.gitlab-ci.yml`. Тот же ответ записан в `_answer.md`.

## Critical

**1. `Services/InpatientReportService.cs` → `GetOccupancyAsync`: SQL-инъекция в `FromSqlRaw`**
- **Что не так:** `ward` и `sortBy` приходят из query-строки и вставляются в текст SQL. Любой вошедший пользователь может выполнить произвольный SQL, например `ward=' OR 1=1; --`. Это нарушает правило «значения идут параметрами».
- **Исправление:**
  - `ward` передавать параметром (`FromSql` с интерполяцией) или фильтровать через LINQ.
  - Имя столбца параметром передать нельзя, поэтому `sortBy` нужно сверять с белым списком и сортировать через LINQ `OrderBy`.
- **Второй дефект там же:** на запрос с `ORDER BY` накладывается `Select`, и EF оборачивает его в подзапрос. PostgreSQL не обязан сохранять порядок строк из подзапроса, так что сортировка может потеряться.

**2. `Services/WardService.cs` → `ReplaceMedicationPlanAsync`: `Clear()` при `Restrict` и физическое удаление назначений**
- **Что не так:** `Clear()` разрывает обязательную связь. При `DeleteBehavior.Restrict` EF не удаляет «осиротевшие» назначения, и `SaveChanges` бросает `InvalidOperationException`. В итоге `PUT /stays/{id}/medications` всегда отдаёт 500, если назначения уже есть.
- **Почему нельзя просто сменить на Cascade:** назначения начнут удаляться физически, а README это запрещает (отменённое назначение получает `CancelledAt`).
- **Исправление:** у действующих назначений ставить `CancelledAt = DateTime.UtcNow` и добавлять новые.

**3. `Program.cs`: `MigrateAsync()` при старте**
- **Что не так:**
  - В проде приложение работает под ролью `vet_app` без прав на изменение схемы. При любой неприменённой миграции все реплики упадут на старте.
  - При rolling update три реплики мигрируют одну базу одновременно. В EF Core 8 блокировки миграций нет, возможны гонки и наполовину применённая схема.
  - Обходится принятый процесс (скрипт → ревью DBA → джоба `db-migrate`), и SQL миграции `AddInpatient`, которой нет в MR, никто не проверит.
- **Исправление:** убрать автоприменение; если оно нужно, то только для Development. Забыть `db-migrate` и так не получится: `deploy` от него зависит (`needs`).

## High

**4. Глобальный фильтр на `Box` (`Data/ClinicDbContext.cs`) прячет пациентов выведенных боксов**
- **Что не так:** `Box` — обязательная сторона связи со `Stay`. Обращение `s.Box` в запросе превращается в INNER JOIN с отфильтрованной таблицей боксов, и госпитализации в выведенном боксе исчезают.
- **Последствия:**
  - `GetWardPatientsAsync`, `GetLongStaysAsync` и отчёт занятости не показывают этих пациентов, хотя по README они должны оставаться в списках до выписки.
  - `DischargeAsync` бросает исключение, то есть такого пациента нельзя выписать.
- **Исправление:** убрать глобальный фильтр и явно фильтровать боксы при поступлении, либо добавить `IgnoreQueryFilters()` в запросы от `Stay`.

**5. `WardService.GetLongStaysAsync`: условие не переводится в SQL**
- **Что не так:** `DaysInWard` — вычисляемое C#-свойство, EF не может перевести его в SQL. Эндпоинт `/long-stays` всегда отдаёт 500.
- **Исправление:** заранее вычислить дату-границу и фильтровать по ней: `AdmittedOn < today.AddDays(-14)`.

**6. `WardService.GetBoxCardAsync`: `SingleOrDefaultAsync` на неуникальном условии**
- **Что не так:** в боксе может лежать до `Capacity` животных. Если невыписанных больше одного, метод бросает исключение и карточка бокса отдаёт 500.
- **Исправление:** возвращать список текущих пациентов через проекцию, а не загружать целые сущности.

**7. `WardService.DischargeAsync`: неверная стоимость**
- **Что не так:** по README оплачиваются календарные дни включая день поступления и день выписки, а код этот день теряет. Каждый счёт занижен на один суточный тариф, при выписке в день поступления выходит 0.
- **Исправление:** прибавить `+ 1` к числу дней. Та же ошибка в `Stay.DaysInWard`.

**8. `Api/InpatientEndpoints.cs` → `POST /stays/{id}/discharge`: не та политика авторизации**
- **Что не так:** стоит `.RequireAuthorization()`, то есть выписать может любой вошедший пользователь. По README выписывает только врач.
- **Исправление:** `.RequireAuthorization("Vet")`.

## Medium

**9. `WardService.GetLatestStayAsync`: неоднозначная сортировка и фильтр в памяти**
- **Что не так:**
  - Повторная госпитализация в тот же день бывает, поэтому сортировка только по `AdmittedOn` может выбрать не последнюю госпитализацию.
  - Вместе с `AsSplitQuery` это опаснее: назначения и наблюдения могут загрузиться для другой строки и вернуться пустыми.
  - Отменённые назначения загружаются из базы и отбрасываются уже в памяти.
- **Исправление:** добавить `ThenByDescending(s => s.Id)`; отменённые назначения отсекать в запросе (Include с фильтром или проекция).

**10. `ReplaceMedicationPlanAsync` / `DischargeAsync`: нет защиты от параллельной правки**
- **Что не так:** у `Stay` нет токена конкурентности (например, `xmin`).
  - Если два врача одновременно заменяют план, появятся две активные копии назначений.
  - Две параллельные выписки перезапишут дату выписки и сумму друг друга.

**11. `ClinicDbContext` → `Stay`: каскадное удаление**
- **Что не так:** связи `Stay → Box`, `Stay → Pet` и `Observation → Stay` по умолчанию удаляются каскадом. Случайное физическое удаление бокса или питомца сотрёт историю госпитализаций со счетами и медкарту. Боксы и так скрываются мягко, каскад им не нужен.
- **Исправление:** `Restrict` для этих связей.

## Low

**12. `ReplaceMedicationPlanAsync`, `DecommissionBoxAsync`, `DischargeAsync`: 500 вместо 404**
- **Что не так:** при несуществующем id `SingleAsync` бросает исключение, и клиент получает 500 вместо 404.
- **Также:** в `DecommissionBoxAsync` из-за глобального фильтра то же самое происходит при повторном выводе уже выведенного бокса.
