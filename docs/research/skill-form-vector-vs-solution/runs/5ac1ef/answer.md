Провёл ревью MR !238. Основные находки (полный текст также записан в `work/_answer.md`):

**1. `VehicleService.cs: ReplaceEquipmentAsync`/`FindVehicleAsync` — critical**
`FindVehicleAsync` не делает `Include(v => v.Equipment)`, поэтому `vehicle.Equipment.Clear()` работает над пустым in-memory списком, а не реальными строками БД. Старые записи `vehicle_equipment` не удаляются: при повторном коде получится `DbUpdateException` (нарушение уникального индекса `vehicle_id, code`), а при смене набора — старая комплектация копится вечно. Это ломает саму суть FLEET-104 («заменяем целиком»).

**2. `TripService.cs: StartTripAsync` — high**
Проверка допуска `p.ValidUntil > today` вместо `>= today` — противоречит требованию «допуск действует... включительно», ложно блокирует выпуск в последний день действия допуска.

**3. `VehicleService.cs: GetLastInspectionAsync` — high**
«Последний» осмотр выбирается по `CreatedAt` (время приёма сервером), а не по `InspectedAt` (время реального осмотра). Поскольку планшеты синхронизируются пачками офлайн, порядок синка может не совпадать с хронологией — это может как необоснованно заблокировать выпуск, так и пропустить машину с неустранённым блокирующим замечанием. Критично для безопасности FLEET-107.

**4. `Program.cs`: `PUT /api/vehicles/{id}/equipment` — high**
В отличие от всех остальных мутирующих эндпоинтов, здесь нет `.RequireAuthorization("...")` с конкретной политикой — любой аутентифицированный пользователь может менять комплектацию машины.

**5. `TripService.cs: GetOpenWaybillsAsync` — high**
Raw SQL оканчивается `;`. При фильтре по `vehicleId` EF оборачивает запрос как подзапрос (`FROM (<raw sql>) AS t WHERE ...`) — точка с запятой внутри подзапроса даёт синтаксическую ошибку Postgres. Именно фильтр по машине явно требуется FLEET-112, и именно этот кейс не упомянут как протестированный в MR.

**6. Миграция `VehicleEquipmentAndModelLength` — high**
Сужение `vehicles.model` с 200 до 40 символов без шага усечения существующих данных. Если в проде есть строки длиннее 40 символов (а именно это мотивирует задачу FLEET-115), `ALTER COLUMN` упадёт на проде, деплой сломается.

**7. `TripService.cs: StartTripAsync` — medium**
Нет проверки на уже открытый путевой лист по машине/водителю — возможен повторный выпуск.

**8. `TripService.cs: OffDayTripsAsync` — low**
Незакрытые поездки получают `Km=0` и проваливаются в конец отчёта «самые длинные сверху».

**9. `ReplaceEquipmentAsync` — low**
Нет валидации `Qty`/`Code` на границе API — ошибки БД вместо 400.
