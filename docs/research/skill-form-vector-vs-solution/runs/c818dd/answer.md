# Ревью MR !231 «Процедурный кабинет»

До мерджа стоит исправить 7 находок, из них 1 critical и 2 high. Код я не менял, сборку и тесты не запускал. Тот же текст записан в `_answer.md`.

### 1. `Services/ProcedureService.cs` — `CalculateDoseMlAsync`: доза завышена в 1000 раз — **critical**
- **Что не так:** вес хранится в граммах, а дозировка задана в мг/кг. Код считает `weightGrams * drugMgPerKg` и не переводит граммы в килограммы.
- **Почему это дефект:** для кота 4 кг при 2,5 мг/кг и 10 мг/мл метод вернёт 1000 мл вместо 1 мл. Результат идёт прямо в инфузию, это угроза жизни пациента. Комментарий в коде («вес, кг × мг/кг») тоже не совпадает с тем, что делает код.
- **Исправление:** `weightGrams / 1000m * drugMgPerKg` и unit-тест на известном примере.

### 2. `Domain/Pet.cs` и `CalculateDoseMlAsync`: при неизвестном весе считается доза 0 — **high**
- **Что не так:** `WeightGrams` объявлен как ненулевой `int`, и миграция проставит 0 всем существующим питомцам.
- **Почему это дефект:** «вес неизвестен» нельзя отличить от реального значения. Для невзвешенного питомца метод молча вернёт 0 мл.
- **Исправление:** `int? WeightGrams`. Если веса нет или он `<= 0`, бросать явную ошибку «питомец не взвешен», а не возвращать число.

### 3. `Services/ProcedureSheetService.cs` — `GetDaySheetAsync`: пагинация сдвинута на страницу — **high**
- **Что не так:** по контракту страницы нумеруются с 1, а код делает `Skip(page * PageSize)`.
- **Почему это дефект:** при `page=1` первые 30 процедур дня пропускаются, и в обычный день лист дня приходит пустым. Кроме того, при `page <= 0` в базу уходит отрицательный `OFFSET`, и клиент получает 500.
- **Исправление:** проверка `page >= 1` и `Skip((page - 1) * PageSize)`.

### 4. `Services/ProcedureService.cs` — `RemoveConsumableAsync`: гонка с закрытием процедуры — **medium**
- **Что не так:** сначала проверяется статус «не закрыта», потом строка удаляется, и между этими шагами ничего не защищает от параллельной правки.
- **Почему это дефект:** если процедуру закроют в этот промежуток, строка удалится из уже закрытой процедуры. Это нарушает правило из README («после закрытия — нельзя») и меняет отчёт по расходу. Concurrency-токен на `Procedure` здесь не поможет: удаление дочерней строки не трогает строку процедуры.
- **Исправление:** удалять одним запросом с условием на статус в `WHERE` (`ExecuteDeleteAsync`) и проверять число удалённых строк. Другой вариант — транзакция с `FOR UPDATE` на строку процедуры, и закрытие процедуры тоже должно брать эту блокировку.
- **Попутно (low):** чтобы удалить одну строку, метод загружает все расходники процедуры, а у инфузий их сотни.

### 5. `Services/ProcedureService.cs` — `RescheduleAsync`: та же гонка по статусу — **low**
- **Что не так:** проверка `Status == Scheduled` и запись идут без concurrency-токена.
- **Почему это дефект:** процедуру, которую параллельно начали, закрыли или отменили, всё равно можно перенести.
- **Исправление:** токен через `xmin` и обработка `DbUpdateConcurrencyException`, или условный `ExecuteUpdateAsync` с проверкой статуса.

### 6. `Data/ClinicDbContext.cs` — `OnModelCreating`, связь `Procedure → Pet`: каскадное удаление журнала — **low**
- **Что не так:** обязательная связь по умолчанию получает `ON DELETE CASCADE`.
- **Почему это дефект:** удаление карточки питомца без предупреждения сотрёт все его процедуры, а через них расходники и заметки персонала. Это медицинский журнал и данные о списании материалов.
- **Исправление:** `.OnDelete(DeleteBehavior.Restrict)`.

### 7. `Services/ProcedureService.cs` — `ScheduleAsync` / `RescheduleAsync`: время со смещением молча искажается — **low**
- **Что не так:** `SpecifyKind(..., Unspecified)` правильно подходит для колонки `timestamp without time zone`. Но если клиент пришлёт время со смещением или `Z`, привязка модели уже пересчитает его в другой пояс.
- **Почему это дефект:** в журнал попадёт сдвинутое время по настенным часам, а клиент не увидит ошибки.
- **Исправление:** отклонять входное время, у которого `Kind != Unspecified`, ответом 400.

### Проверено, дефектами не считаю
- **`GetCardAsync`:** `AsNoTracking` и split query для двух коллекций одного уровня — правильный выбор при сотнях строк.
- **`FindPetByChipAsync`:** `SingleOrDefault` подходит, у номера чипа уникальный индекс.
- **`SearchNotesAsync`:** `FromSql` с интерполяцией передаёт значения параметрами.
- **`GetConsumptionAsync`:** `ORDER BY` берётся из белого списка, значения идут параметрами.
- **Типы времени:** обращение с `DateTime` для обеих колонок корректно.

### Замечание к SKILL.md
Пункт про `DateTime` говорит, что значение, прочитанное из `timestamp without time zone`, помечается `Utc`. Насколько я знаю Npgsql 6+, такое значение читается с `Kind=Unspecified`, а записать в эту колонку `Kind=Utc` нельзя — будет исключение. По документации я это в этот раз не проверял. На этот MR замечание не влияет: код такой пометки не делает, и правило из README соблюдено.
