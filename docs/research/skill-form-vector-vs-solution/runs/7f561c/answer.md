Самые серьёзные: SQL-инъекция в отчёте о занятости, пропадание пациентов из выведенных боксов (выписать их тоже нельзя), сломанная замена плана назначений, нерабочий запрос длительных госпитализаций и занижение каждого счёта на одни сутки. Код не менял, сборку и тесты не запускал. Тот же ответ записан в `_answer.md`.

## Critical

**1. `Services/InpatientReportService.cs` — `GetOccupancyAsync`: SQL-инъекция**
- **Что не так:** `ward` и `sortBy` приходят из query-строки и вставляются прямо в текст запроса для `FromSqlRaw`: `ward` — внутрь строкового литерала `'{ward}'`, `sortBy` — как имя столбца `s."{sortBy}"`.
- **Почему дефект:** эндпоинт закрыт только `RequireAuthorization()`, поэтому любой вошедший пользователь может выполнить произвольный SQL под ролью `vet_app`. Например, `ward=x' OR 1=1 --` читает все данные. У роли есть права на чтение и изменение данных, значит их можно и менять, и удалять.
- **Как исправить:** переписать на LINQ — `Where(s => s.DischargedOn == null && s.Box.Ward == ward)`. Сортировку выбирать по белому списку через `switch`, на неизвестный столбец отвечать 400. Если сырой SQL всё же нужен — значения только параметрами, имя столбца только из белого списка.

## High

**2. `Data/ClinicDbContext.cs` — глобальный фильтр `HasQueryFilter(!IsDecommissioned)` на `Box`: пациенты из выведенного бокса пропадают**
- **Что не так:** связь `Stay → Box` обязательная. Из-за фильтра любое обращение к `s.Box` превращается во внутреннее соединение с уже отфильтрованными боксами. Госпитализации в выведенном боксе:
  - пропадают из списков в `GetWardPatientsAsync`, `GetLongStaysAsync` и `GetOccupancyAsync`;
  - не находятся в `DischargeAsync` — там `Include(s => s.Box)`, и `SingleAsync` бросает исключение;
  - карточка такого бокса в `GetBoxCardAsync` отдаёт 404.

  EF Core сам выдаёт предупреждение на такую конфигурацию (10622).
- **Почему дефект:** README требует обратного: бокс выводят и тогда, когда в нём ещё лежат пациенты, а они должны оставаться в списках отделения до выписки. Сейчас реально лежащий пациент исчезает из списков врачей, а выписать его и выставить счёт нельзя.
- **Как исправить:** убрать глобальный фильтр и отсекать выведенные боксы явно — только там, где бокс предлагают при поступлении.

**3. `Services/WardService.cs` — `ReplaceMedicationPlanAsync`: замена плана не работает, если назначения уже есть**
- **Что не так:** `MedicationOrders.Clear()` разрывает обязательную связь, на которой стоит `DeleteBehavior.Restrict`. В этом случае `SaveChangesAsync` бросает `InvalidOperationException`. В MR это не заметили, потому что сценарий прогоняли на пустом плане.
- **Почему дефект:** основной сценарий врача падает. Но даже с каскадным удалением это нарушало бы README: назначения — часть медкарты и физически не удаляются, отменённому ставится `CancelledAt`.
- **Как исправить:** коллекцию не очищать. Действующим назначениям проставить `CancelledAt = DateTime.UtcNow`, новые добавить.

**4. `Services/WardService.cs` — `GetLongStaysAsync`: запрос всегда падает**
- **Что не так:** `DaysInWard` — вычисляемое свойство C#, не замапленное на столбец. EF не может перевести такой фильтр в SQL и бросает исключение, поэтому `/long-stays` всегда отвечает 500.
- **Как исправить:** заранее посчитать пороговую дату и фильтровать по ней: `s.AdmittedOn < today.AddDays(-14)`. Границу «больше 14 дней» согласовать с правилом подсчёта дней из п. 6.

**5. `Services/WardService.cs` — `GetBoxCardAsync`: `SingleOrDefaultAsync` по неуникальному условию**
- **Что не так:** запрос ищет одну текущую госпитализацию в боксе. Но по README в боксе может лежать до `Capacity` животных (помёт, животные одного владельца). При двух и больше пациентах запрос бросает исключение, и карточка отдаёт 500.
- **Почему дефект:** падение в штатной ситуации. К тому же `BoxCardDto` с одним `PetName` не может описать бокс с несколькими пациентами.
- **Как исправить:** вернуть список текущих пациентов проекцией и поменять DTO. Попутно уйдёт лишний `Include(s => s.Pet)`, который сейчас грузит всю сущность ради одного имени.

**6. `Services/WardService.cs` — `DischargeAsync`: счёт занижен на одни сутки**
- **Что не так:** дни считаются как разность дат, то есть число ночей. По README считаются календарные дни, включая день поступления и день выписки.
- **Почему дефект:** каждый счёт меньше на один суточный тариф, а выписка в день поступления стоит 0. Это прямые финансовые потери.
- **Как исправить:** прибавить 1 к разности дат. Ту же формулу использовать в `Stay.DaysInWard`.

**7. `Api/InpatientEndpoints.cs` — `POST /stays/{id}/discharge`: выписать может кто угодно**
- **Что не так:** стоит `RequireAuthorization()` без политики, то есть доступ есть у любого вошедшего пользователя.
- **Почему дефект:** по README выписку оформляет только врач (политика `Vet`), администраторы ресепшена не выписывают.
- **Как исправить:** `RequireAuthorization("Vet")`.

**8. `Program.cs` — `MigrateAsync()` при старте приложения**
- **Что не так:** миграции применяются из приложения при каждом запуске.
- **Почему дефект:**
  - в проде приложение работает под ролью `vet_app` без прав менять схему, поэтому при новой миграции каждая реплика будет падать на старте и перезапускаться по кругу;
  - при rolling update три реплики одновременно пытаются мигрировать одну базу, а EF Core 8 не берёт для этого блокировку;
  - обходится принятый процесс: идемпотентный скрипт → ревью DBA → джоба `db-migrate`.
- **Как исправить:** убрать вызов или оставить его только для `IsDevelopment()`.

## Medium

**9. `InpatientReportService.GetOccupancyAsync`: сортировка ненадёжна**
- **Что не так:** EF оборачивает сырой SQL в подзапрос, а PostgreSQL не гарантирует, что порядок строк подзапроса сохранится снаружи. Кроме того, на экране сортируют по `PetName` и `BoxCode`, которых нет в `"Stays"`, — такой запрос упадёт.
- **Как исправить:** сортировать в LINQ после проекции.

**10. `WardService.GetLatestStayAsync`: «последняя» госпитализация выбирается случайно при одинаковой дате**
- **Что не так:** сортировка только по дате поступления. Повторная госпитализация в тот же день бывает (это прямо отмечено в модели).
- **Почему дефект:** врач может увидеть старую, уже закрытую карточку вместо текущей.
- **Как исправить:** добавить `ThenByDescending(s => s.Id)`, как уже сделано в `GetPetHistoryAsync`.

**11. `WardService.ReplaceMedicationPlanAsync` и `DischargeAsync`: нет защиты от одновременной правки**
- **Что не так:** у `Stay` нет concurrency token. Если два врача одновременно меняют план, после исправления п. 3 активными останутся оба плана — это риск двойной дозы.
- **Как исправить:** concurrency token через `xmin`, при замене плана менять и саму строку `Stay`. Другой вариант — `SELECT … FOR UPDATE` внутри явной транзакции. На конфликт отвечать 409.

**12. `ClinicDbContext`: каскадное удаление `Stay → Box`**
- **Что не так:** у обязательной связи по умолчанию каскадное удаление, а миграцию не правили. Боксы удаляются мягко, но в базе каскад остаётся.
- **Почему дефект:** один случайный `DELETE` из `Boxes` удалит историю госпитализаций и наблюдений.
- **Как исправить:** поставить `Restrict`. То же стоит пересмотреть для `Stay → Pet` и `Observation → Stay`.

## Low

**13. `GetLatestStayAsync`: лишние данные из базы.** Отменённые назначения загружаются и отфильтровываются уже в памяти, наблюдения сортируются тоже в памяти. Лучше фильтровать и сортировать прямо в `Include` или сразу проецировать в DTO. Разделение на два запроса (`AsSplitQuery`) здесь оправдано.

**14. `Stay.DaysInWard`: «сегодня» берётся по UTC,** а дата поступления — по журналу клиники, то есть местная. Ночью, пока даты расходятся, дней получается на один меньше. Брать текущую дату в часовом поясе клиники.

**15. `SingleAsync` в `ReplaceMedicationPlanAsync`, `DecommissionBoxAsync` и `DischargeAsync`:** при несуществующем id ответ 500 вместо 404. Повторный вывод уже выведенного бокса из-за фильтра тоже даёт 500.
