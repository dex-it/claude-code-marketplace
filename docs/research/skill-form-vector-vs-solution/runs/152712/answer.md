## Critical

**1. Групповой заказ: повтор с тем же `Idempotency-Key` создаёт второй счёт в 1С**
`Services/GroupOrderService.cs`, `CreateAsync`

Ключ проверяется до транзакции, а счёт в 1С выставляется до записи заказа в базу. Сценарий из описания MR: шина отвечает 5–10 с, а фронт через 5 с повторяет POST.
- Первый запрос держит блокировку `FOR UPDATE` и ждёт шину.
- Повтор не находит ключ (запись ещё не закоммичена) и ждёт ту же блокировку.
- Когда первый запрос коммитит, повтор получает блокировку и **снова вызывает `CreateInvoiceAsync`**. В 1С появляется второй счёт.
- Только после этого повтор падает на уникальном индексе.

Уникальный индекс защищает только таблицу `GroupOrders`, а не 1С. По контракту `IBillingClient` каждый вызов создаёт новый счёт, и аннулировать его можно только вручную.

Есть похожий сценарий: фронт обрывает запрос, и `RequestAborted` отменяется уже после того, как шина создала счёт. Заказ не сохраняется, повтор выставляет ещё один счёт.

**Как исправить:** сначала атомарно вставить заказ со статусом «счёт выставляется» и закоммитить, потом вызывать шину. Вызов делать вне транзакции и не с токеном запроса.

**2. Учёт мест не учитывает резерв групповых заказов: места продаются сверх вместимости**
`Services/CapacityService.cs`, `FreeSeatsAsync`

Занятыми считаются только неотменённые регистрации, а выкупленные заказом места (`GroupOrder.Quantity`) нет. По MR места под заказ должны резервироваться сразу.

Пример: заказ на 100 мест не уменьшает число свободных. Одиночные регистрации раскупают все 600 мест, потом администратор вписывает 100 человек (`AddParticipantAsync` вместимость не проверяет), и на площадке 700 человек. То же самое при отмене участника заказа: место «освобождается» для всех, хотя оно оплачено организацией.

**Как исправить:** занято = регистрации без `GroupOrderId` + сумма `Quantity` по заказам.

**3. В счёт сверху добавляется 20 % НДС, хотя цены уже включают НДС**
`Services/InvoiceBuilder.cs`, `ForGroupOrder`

По модели цены билетов уже с НДС, но код считает `Total = amount + amount*20/100`. Организации выставляется счёт на 120 % от цены, и эта сумма сохраняется в `AmountKopecks`.

**Как исправить:** выделять НДС из суммы: `vat = amount*20/120`, `Total = amount`.

## High

**4. Промокод складывается с ранним тарифом**
`Services/PricingService.cs`, `Quote`

Скидка применяется к ранней цене. По условиям договоров (комментарий к `PromoCode`) скидка считается от полной цены и не складывается с ранним тарифом. Сейчас участник получает двойную скидку.

**5. Лимит использований промокода не работает**
`Services/RegistrationService.cs`, `RegisterAsync`

Промокод загружается через `AsNoTracking()`, поэтому `promo.UsedCount++` не сохраняется. Счётчик в базе всегда 0, «исчерпан» никогда не срабатывает.

Кроме того, проверка лимита идёт без конкурентного контроля, и параллельные регистрации превысят лимит.

**Как исправить:** атомарный `UPDATE ... SET "UsedCount"="UsedCount"+1 WHERE "UsedCount" < "UsageLimit"`. Если ни одна строка не обновилась, отвечать 422.

**6. На место отменённого сотрудника нельзя вписать другого**
`Services/GroupOrderService.cs`, `AddParticipantAsync`

Проверка `Participants.Count >= Quantity` учитывает и отменённые регистрации. Сценарий из MR «отменить сотрудника и вписать другого» получает 409.

Кроме того, проверка идёт без блокировки, и параллельные добавления превысят `Quantity`.

**7. Паспортные данные видны администраторам организаций и всему оргкомитету**
`Contracts/RegistrationContracts.cs`, `ParticipantDto.Projection`; `Controllers/ParticipantsController.cs`, `List`

Паспорт возвращается всем с ролями `Organizer` и `OrgAdmin`. По MR его видит только визовая группа: на эти данные отдельное согласие. Это утечка персональных данных (152-ФЗ).

**Как исправить:** убрать паспортные поля из DTO и отдавать их отдельным эндпоинтом под отдельной ролью.

**8. Отчёт: границы периода в UTC и параметр с `Kind=Unspecified`**
`Controllers/ReportsController.cs`, `Registrations`

`DateOnly.ToDateTime` даёт `Kind=Unspecified`. Npgsql 8 не принимает такое значение для `timestamptz`, и отчёт падает с 500.

Если просто поставить `Utc`, границы суток будут по UTC, а не по Москве. Регистрации с 00:00 до 03:00 МСК попадут в предыдущий день.

**9. Шину вызывают, пока заблокирована строка конференции**

**10. HttpClient шины не настроен**
`Program.cs`, `AddHttpClient<IBillingClient, BillingBusClient>`

`BillingOptions` нигде не используются: у клиента нет `BaseAddress` и `ApiKey`. Запрос `PostAsJsonAsync("invoices")` с относительным URI бросает `InvalidOperationException`. Если клиент не настраивается где-то вне этого MR, создать заказ нельзя вообще.

**11. Повторная отмена может вернуть деньги дважды**
`Services/RegistrationService.cs`, `CancelAsync`

Нет конкурентного контроля. Две параллельные отмены обе видят `Paid` и обе отвечают «возврат N».

**Как исправить:** условный `UPDATE ... WHERE Status <> Cancelled` или `xmin` как concurrency token.
