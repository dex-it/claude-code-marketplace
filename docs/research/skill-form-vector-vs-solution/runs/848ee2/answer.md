Ревью MR !231 «Процедурный кабинет»: до мерджа стоит исправить 8 находок, самая серьёзная — доза препарата в 1000 раз больше нужной. Сборку и тесты я не запускал, выводы сделаны по чтению кода. Тот же ответ записан в `_answer.md`.

## 1. Объём препарата в 1000 раз больше нужного — **critical**
**Файл:** `Services/ProcedureService.cs`, метод `CalculateDoseMlAsync` (строки 91–98)

Код читает вес в граммах (`Pet.WeightGrams`) и сразу умножает его на дозировку в мг/кг: `doseMg = weightGrams * drugMgPerKg`. Перевода граммов в килограммы нет, хотя комментарий над расчётом прямо говорит «вес, кг».

Пример: кошка 4000 г, препарат 2,5 мг/кг, концентрация 10 мг/мл. Правильный объём — 1 мл, а метод вернёт 1000 мл. Это расчёт дозы для инфузии живому животному, поэтому ошибка опасна для его жизни.

**Исправление:** `doseMg = weightGrams / 1000m * drugMgPerKg`. Нужен тест на известном примере.

## 2. Нулевой или неизвестный вес даёт нулевую дозу без ошибки — **high**
**Файлы:** `Domain/Pet.cs` (`WeightGrams`), `Services/ProcedureService.cs`, метод `CalculateDoseMlAsync`

`WeightGrams` объявлен как `int`, не nullable. Миграция `AddProcedures` добавит колонку NOT NULL со значением по умолчанию 0, и у всех уже существующих питомцев вес станет 0. «Не взвешен» и «0 г» при этом не различаются.

`CalculateDoseMlAsync` вес не проверяет. Для такого питомца API спокойно вернёт `0` мл как нормальный ответ. В расчёте дозы это недопустимо: метод должен отказать, а не выдать ноль.

**Исправление:** сделать `int?` (или проверять `> 0`) и бросать доменную ошибку «вес не указан».

## 3. Лист дня теряет первую страницу — **high**
**Файл:** `Services/ProcedureSheetService.cs`, метод `GetDaySheetAsync` (строка 37)

По контракту MR страницы нумеруются с 1, а код делает `Skip(page * PageSize)`. Для `page=1` пропускаются первые 30 процедур дня. В загруженный день кабинет просто не увидит утренние процедуры. При `page<=0` запрос тоже ведёт себя неправильно: `0` случайно отдаёт первую страницу, а отрицательное значение даёт отрицательный OFFSET и ошибку PostgreSQL.

**Исправление:** `Skip((page - 1) * PageSize)` и проверка `page >= 1`.

## 4. Параллельные правки процедуры перезаписываются без обнаружения, правило «после Closed нельзя» можно обойти — **medium**
**Файлы:** `Services/ProcedureService.cs`, методы `RemoveConsumableAsync` и `RescheduleAsync`; `Data/ClinicDbContext.cs` (у `Procedure` нет concurrency token)

Оба метода сначала читают `Status`, проверяют его в памяти, затем пишут. Между чтением и `SaveChanges` другой запрос может закрыть или отменить процедуру. Проверка тогда проходит по устаревшим данным:
- `RemoveConsumableAsync` удалит строку списания уже у закрытой процедуры, а README это прямо запрещает;
- `RescheduleAsync` пишет только колонку `ScheduledLocal` и перенесёт процедуру, которая уже `Closed` или `Cancelled`;
- из двух одновременных переносов молча победит последний.

Ни токена конкурентности, ни блокировки, ни условия в UPDATE/DELETE нет.

**Исправление:** добавить concurrency token на `Procedure` (например, `xmin` через `IsRowVersion()` в Npgsql) и обрабатывать `DbUpdateConcurrencyException`. Другой вариант — делать изменения с условием на статус в SQL (`ExecuteUpdate`/`ExecuteDelete` с `Status != Closed`) или через `SELECT … FOR UPDATE` в явной транзакции.

## 5. Ради удаления одной строки загружаются и отслеживаются все расходники — **medium**
**Файл:** `Services/ProcedureService.cs`, метод `RemoveConsumableAsync` (строки 65–75)

`Include(p => p.Consumables)` загружает в change tracker все строки расходников. В MR сказано, что у инфузий их бывают сотни, а удаляется одна. Получается лишний трафик и материализация на каждое удаление.

Сам механизм удаления корректен: FK обязательный, каскад по умолчанию, поэтому `Remove` из коллекции удалит сироту.

**Исправление:** загрузить только статус процедуры и нужную строку либо выполнить `ExecuteDeleteAsync` с условием по `ProcedureId` и статусу. Это заодно закрывает гонку из п. 4.

## 6. Поиск «по заметкам» не ищет по заметкам персонала — **medium** (сверить с постановкой)
**Файл:** `Services/ProcedureSheetService.cs`, метод `SearchNotesAsync`

Полнотекстовый поиск идёт только по `Procedures.Notes`. Записи персонала, ради которых и заведена `StaffNote`, в поиск не попадают. Если «поиск по заметкам» из MR включает их, функция неполная.

Ещё в MR нет GIN-индекса по `to_tsvector('russian', …)`. Без него каждый поиск — полный проход по таблице.

Сама параметризация в порядке: `FromSql` с интерполяцией передаёт `{text}` как параметр.

## 7. Удаление питомца каскадно стирает журнал процедур и расход материалов — **low/medium**
**Файл:** `Data/ClinicDbContext.cs`, `OnModelCreating`, связь `Procedure → Pet`

Связь обязательная, и по соглашению на неё ставится `ON DELETE CASCADE`. Дальше каскад идёт на `ConsumableLines` и `StaffNotes`. Удаление карточки питомца сотрёт историю процедур и исказит задним числом отчёт по расходу материалов.

**Исправление:** нужен `OnDelete(DeleteBehavior.Restrict)` или архивирование питомца.

## 8. Несуществующий id даёт 500 вместо 404 — **low**
**Файл:** `Services/ProcedureService.cs`, методы `RescheduleAsync`, `RemoveConsumableAsync`, `CalculateDoseMlAsync`

`SingleAsync` на отсутствующем id бросает `InvalidOperationException`, и клиент получает 500. В том же сервисе для отсутствующей строки расходников бросается `KeyNotFoundException` — обработка непоследовательная.

`ScheduleAsync` не проверяет, существует ли `PetId`: нарушение FK превратится в `DbUpdateException` и тоже 500.
