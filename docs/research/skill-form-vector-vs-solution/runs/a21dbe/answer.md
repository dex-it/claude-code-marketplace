**Решения**
- **Сортировка (а).** `sort`/`dir` сверяются со списком разрешённых значений, иначе 400. Значение из запроса никогда не подставляется в SQL как есть. Статус сортируется по порядку прохождения заявки, а не по алфавиту. Последним ключом идёт `r.id`, чтобы порядок между страницами не прыгал. Общее количество (б) считается отдельным `COUNT(*)` с теми же фильтрами.
- **Лицевой счёт (в).** В проде уже есть задвоенные счета после переноса из биллинга 2023, поэтому обычный уникальный индекс не создастся, и релиз упадёт. Миграция ничего не удаляет: на старые записи ссылаются заявки. Она помечает старые копии как `is_legacy_duplicate`. Индекс уникальный, но не распространяется на эти копии и на пустые счета. На время миграции таблица `apartments` блокируется, ожидание блокировки ограничено 10 секундами. Если миграция упрётся в этот лимит, её достаточно перезапустить. В приложении — сначала проверка, затем перехват ошибки уникальности на случай одновременного заведения, ответ 409.
- **План обслуживания (г).** Работы сопоставляются по коду: существующие обновляются, новые добавляются. Работы, которых нет в присланном плане, уходят в архив, а не удаляются: при удалении каскадом пропали бы акты о выполнении. Если работу пришлют снова, она вернётся вместе с историей. Одновременные PUT по одному дому выполняются по очереди за счёт блокировки строки дома. Присланный список проверяется: дубли кодов, пустые поля, периодичность ≤ 0 — ответ 400.
