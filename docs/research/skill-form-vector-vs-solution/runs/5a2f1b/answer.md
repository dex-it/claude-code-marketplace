## Critical

### 1. `Services/GroupOrderService.cs` — `CreateAsync`: повтор с тем же `Idempotency-Key` создаёт второй счёт в 1С
- **Что не так.** Ключ проверяется один раз, до транзакции и блокировки (`FindByKeyAsync`, стр. 37). Затем `_billing.CreateInvoiceAsync` (стр. 58) вызывается внутри транзакции, до вставки строки с ключом. Уникальный индекс срабатывает только на `SaveChanges`, то есть уже после того, как счёт выставлен.
- **Сценарий.** Шина отвечает 5–10 с, фронт через 5 с повторяет POST. Первый запрос ещё не закоммитил строку, поэтому повтор не находит ключ и ждёт `FOR UPDATE`. Когда первый запрос коммитит, второй получает блокировку и не перепроверяет ключ. Он вызывает шину ещё раз, и в 1С появляется второй счёт. Потом второй запрос ловит `UniqueViolation` и отдаёт заказ первого («Replayed»). Лишний счёт остаётся в 1С, а аннулировать его можно только вручную. Двойное нажатие кнопки в бухгалтерии даёт тот же результат.
- **Ещё сценарий.** Если шина создала счёт, но запрос завершился таймаутом или отменой (`ct` — это `RequestAborted`), транзакция откатывается. Каждый следующий повтор выставляет новый счёт.
- **Почему это дефект.** Прямо нарушено требование MR: «повтор не должен создавать второй заказ», а бухгалтерия организации получает дубли счетов.
- **Как исправить.** Сначала отдельной транзакцией застолбить ключ: вставить заказ в состоянии «счёт выставляется», уникальный индекс отсечёт параллельный повтор. Счёт выставлять уже после этого и вне блокировки, а в шину передавать идемпотентный ключ. Ключ нужно перепроверять и после получения блокировки.

### 2. `Services/CapacityService.cs` — `FreeSeatsAsync`: групповые заказы не резервируют места, возможна перепродажа
- **Что не так.** Метод считает занятыми только строки `Registrations`. Выкупленные, но ещё не заполненные места `GroupOrder.Quantity` в подсчёт не попадают. При `AddParticipantAsync` вместимость не проверяется.
- **Последствие.** Места, оплаченные организацией, продаются ещё раз через обычную регистрацию, и на площадку на 600 человек приходит больше людей, чем она вмещает.
- **Почему это дефект.** В MR сказано: «Места под заказ резервируются сразу».
- **Как исправить.** Занятые места = неотменённые регистрации без `GroupOrderId` + `SUM(GroupOrders.Quantity)` по конференции.

## High

### 3. `Services/InvoiceBuilder.cs` — `ForGroupOrder`: НДС начисляется сверху на цену, которая уже включает НДС
- **Что не так.** `vat = amount * 20 / 100`, `total = amount + vat`, хотя по модели «все цены указаны с НДС».
- **Последствие.** Счёт организации завышен на 20 %, и это же значение сохраняется в `AmountKopecks`.
- **Как исправить.** Выделять НДС из суммы: `vat = amount * 20 / 120` (с явным округлением), `total = amount`.

### 4. `Services/PricingService.cs` — `Quote`: промокод применяется к раннему тарифу
- **Что не так.** Скидка считается от `BasePrice`, а в период раннего тарифа это ранняя цена.
- **Почему это дефект.** По договорам с партнёрами скидка считается от полной цены и с ранним тарифом не суммируется. Сейчас участники получают лишнюю скидку, и это прямые финансовые потери.
- **Как исправить.** Если есть промокод, считать от `PriceKopecks`. Если по договору участнику положена лучшая из двух цен, взять `min(early, full − discount)`.

### 5. `Services/RegistrationService.cs` — `RegisterAsync` и `PricingService.FindPromoAsync`: лимит использований промокода не работает
- **Что не так.** Промокод загружается с `AsNoTracking()`, поэтому `promo.UsedCount++` не сохраняется. `UsedCount` в БД всегда 0, и проверка «Промокод исчерпан» не срабатывает никогда.
- **Вторая проблема.** Проверку делают вне транзакции и без блокировки. Даже если включить трекинг, параллельные регистрации перезапишут друг друга (lost update) и превысят лимит.
- **Как исправить.** Внутри транзакции выполнить атомарно `ExecuteUpdateAsync(UsedCount + 1)` с условием `UsedCount < UsageLimit && ValidUntil >= today`. Если обновлено 0 строк, отвечать 422.

### 6. `Services/GroupOrderService.cs` — `AddParticipantAsync`: на место отменённого сотрудника нельзя вписать другого
- **Что не так.** `Participants.Count >= Quantity` считает и отменённых участников, поэтому замена из MR не работает и возвращает 409.
- **Расхождение.** `GroupOrdersController.List` считает `SeatsUsed` без отменённых, и UI показывает свободное место, которое занять нельзя.
- **Сопутствующее.** Ради подсчёта в трекер загружается вся коллекция со всеми колонками, включая паспорта. Нужен `CountAsync` в SQL.

### 7. `Controllers/ParticipantsController.cs` — `List` и `ParticipantDto.Projection`: паспортные данные отдаются всем, кто видит список
- **Что не так.** Проекция всегда включает `PassportNumber` и `PassportCountry`, а эндпоинт доступен ролям `OrgAdmin` и `Organizer`.
- **Почему это дефект.** По MR паспорт видит только визовая группа, на это есть отдельное согласие на обработку. Сейчас персональные данные раскрываются без основания.
- **Как исправить.** Убрать паспортные поля из DTO и сделать отдельный эндпоинт под роль визовой группы.

### 8. `Controllers/ReportsController.cs` — `Registrations`: `DateTime` с `Kind=Unspecified` сравнивается с колонкой `timestamptz`
- **Что не так.** `DateOnly.ToDateTime(...)` возвращает `Kind=Unspecified`, а `CreatedAt` по умолчанию имеет тип `timestamptz`. Npgsql при передаче такого параметра бросает `InvalidCastException`, так что отчёт всегда падает с 500.
- **Второе.** Даже с `Kind=Utc` границы дня будут по UTC, а даты в системе считаются по Москве.
- **Как исправить.** Брать полночь по Москве и переводить её в UTC.
