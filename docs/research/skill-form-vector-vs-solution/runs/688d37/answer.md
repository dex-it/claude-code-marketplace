Провёл ревью MR по списанию баллов лояльности. Ключевые проблемы (полный текст также записан в `_answer.md`):

**CRITICAL**
1. `schemas.py: RedeemRequest.confirm_amount` — комментарий утверждает, что `Optional` без default делает поле обязательным, но в Pydantic 1.10.13 (закреплён в requirements.txt) это не так: default автоматически `None`. Старый клиент без этого поля тихо получит `None` → полное списание баланса вместо ожидаемого 422.
2. `redeem.py: redeem()` — нет проверки `confirm_amount >= 0`; отрицательная сумма проходит проверку `amount > balance` и **начисляет** баллы вместо списания.
3. `redeem.py:11` — `POINT_VALUE = 0.1` как `float`, а не `Decimal("0.1")`; `Decimal(0.1)` тянет бинарную погрешность float в денежные расчёты.

**HIGH**
4. `redeem.py:28` — `int(...)` усекает вниз, из-за чего заявленная `redeemed`-сумма может не совпадать с реально списанными баллами.
5. `repo.py` + `redeem.py` — чтение и запись баланса не в одной транзакции, нет `SELECT ... FOR UPDATE`/версии — гонка/double-spend при параллельных запросах.
6. `repo.py: save_member()`/`write_audit()` — раздельные транзакции; при сбое после списания аудиторская запись может не создаться, хотя аудит — явное требование MR.

**MEDIUM**
7. Комментарий в `schemas.py` про то, что pydantic по умолчанию отвергает лишние поля — неверно для v1 (default `Extra.ignore`), заявленная защита от опечаток не работает.
8. `RedeemRequest.points` — обязательное поле, но нигде не используется в логике `redeem.py`.
9. Заявленный в MR «срок действия баллов» фактически не реализован — `valid_until` косметический, без реального контроля истечения.

**LOW**
10. `HTTPException(404)` без `detail`, в отличие от 409.
11. Нет видимой авторизации на `/redeem` — возможно, вне зоны ответственности этого MR, но стоит уточнить у авторов.

Блокирующими для мерджа считаю находки 1–6.
