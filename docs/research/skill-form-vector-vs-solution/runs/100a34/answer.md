## Решения

- **Удаление клиента.** Записи не удаляются физически (так требует README). Клиент, его питомцы, их визиты и аллергии помечаются удалёнными одной транзакцией через `ExecuteUpdate` с общим `DeletedAt`. Поэтому поддержка может восстановить ровно этот набор. Кроме того, фильтры зависимых теперь смотрят на родителя: в расписании врача визиты питомца удалённого клиента не покажутся, даже если какая-то строка не была помечена. Каскад в БД заменён на `RESTRICT`, чтобы случайный физический `DELETE` не уничтожил историю.
- **Замена аллергий.** `Clear()` здесь не подходит: при `Restrict` он падает с исключением, а при каскаде удалил бы строки физически. Поэтому записи сопоставляются по аллергену без учёта регистра:
  - совпавшие обновляются;
  - лишние помечаются удалёнными;
  - новые добавляются.

  Всё сохраняется одним `SaveChanges` в транзакции. Строка питомца на это время блокируется (`FOR UPDATE`), так что две одновременные замены идут по очереди. Если в присланном списке аллерген повторяется или пуст, эндпоинт возвращает 400.
- **Анамнез.** Колонка переименовывается, а не пересоздаётся, поэтому старые заметки остаются. Выкладка идёт по обычной схеме из `.gitlab-ci.yml`: CI собирает идемпотентный SQL, DBA его проверяет, `db-migrate` выполняется в окно обслуживания при остановленном приложении, затем `deploy`. Старый и новый код с базой одновременно не работают, так что переименование безопасно.
