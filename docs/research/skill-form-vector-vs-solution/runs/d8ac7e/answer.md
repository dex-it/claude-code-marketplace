Провёл ревью MR, сверив ключевые допущения о поведении pydantic 1.10.13 / FastAPI 0.95.2 с исходниками/докой этих версий. Полный текст сохранён в `_answer.md`.

## Находки

**Critical**
1. `app/redeem.py` (`POINT_VALUE`, `redeem`) — `POINT_VALUE = 0.1` это `float`, `Decimal(POINT_VALUE)` фиксирует двоичную погрешность float (`Decimal(0.1) != Decimal('0.1')`, подтверждено докой Python `decimal`). Все суммы списания/баланса неточны. Нужно `Decimal("0.1")`.
2. `app/redeem.py:redeem` — нет проверки `confirm_amount >= 0`. Отрицательное значение проходит проверку `amount > balance` и при вычитании увеличивает баланс баллов — можно начислять себе баллы через API списания.
3. `app/redeem.py:redeem` + `app/repo.py:get_member/save_member` — чтение и запись баланса в разных транзакциях без блокировки (`SELECT ... FOR UPDATE`) или optimistic-lock условия. Гонка при параллельных запросах даёт lost update / двойное списание.

**High**
4. `app/redeem.py:redeem` — обновление баланса и запись аудита не в одной транзакции; при сбое между ними баллы списаны, а аудита нет — при том что аудит явно заявлен целью MR.
6. `app/redeem.py:redeem` — нет проверки, что вызывающий вправе списывать баллы именно этого `member_id`; во всей новой директории нет auth-слоя.

**Medium**
5. `app/repo.py:write_audit` — в аудит пишется только исходный запрос, не фактически списанная сумма/итоговый баланс; для случая `confirm_amount is None` (полное списание) реальная сумма не восстановима из аудита.
7. `app/schemas.py:RedeemRequest` — комментарий утверждает, что pydantic 1.10 по умолчанию отклоняет лишние поля; по исходнику pydantic на теге v1.10.13 дефолт — `Extra.ignore` (лишние поля молча игнорируются), а `Config.extra="forbid"` не задан — комментарий вводит в заблуждение, опечатки в полях клиента теряются молча.
8. `app/schemas.py:RedeemResult` — `Decimal`-поля (`redeemed`, `balance_left`) при сериализации через FastAPI 0.95.2/pydantic 1.10 default encoder превращаются в JSON `float` (подтверждено по `pydantic/json.py` на теге v1.10.13) — точность денег теряется на границе API.
9. `app/schemas.py:RedeemRequest.points` — обязательное поле, но нигде не используется в `redeem()`; похоже на мёртвый код или забытую сверку с `confirm_amount`.

**Low**
10. `app/redeem.py:redeem` — `valid_until` всегда `today+365`, не привязан к реальной дате начисления и не влияет на то, какие баллы уже просрочены — заявленный в MR «срок действия баллов» не реализован как правило, а только возвращается как декоративное поле.
11. `app/redeem.py:redeem` — усечение (`int(...)`) при обратной конвертации суммы в баллы, без документированного правила округления.
12. `app/redeem.py:redeem` — `HTTPException(404)` без `detail`, несогласованно с веткой 409.

Note: по одному из пунктов (переход "Optional без дефолта" в pydantic 1.10) моя первичная гипотеза через WebSearch была неверной — исходник pydantic на теге v1.10.13 подтвердил, что `Optional[X]` без значения по умолчанию действительно required с v1.2, так что соответствующий комментарий в коде корректен и в отчёт как дефект не попал.
