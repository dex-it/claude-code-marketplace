Главное: оба комментария о валидации в `schemas.py` неверны для pydantic 1.10, который стоит в проекте. Поэтому клиент, не приславший `confirm_amount`, получает не 422, а **списание всего баланса**. Ниже тот же ответ, что записан в `_answer.md`.

Версии из `requirements.txt`: fastapi 0.95.2, pydantic 1.10.13, SQLAlchemy 1.4.49. Утверждения о фреймворках я сверил с документацией этих версий через WebFetch, потому что context7 в сессии недоступен. Проб не запускал: по условиям задачи запрещены запуск кода и запись вне каталога. Расчёты Decimal в находке №4 сделаны вручную и так и помечены.

1. **`app/schemas.py`, `RedeemRequest.confirm_amount` — critical.**
   - Комментарий говорит, что `Optional` без значения по умолчанию делает поле обязательным. Это **опровергнуто**: в pydantic 1.10 (раздел документации «Required Optional fields») такое поле необязательно и по умолчанию равно `None`. Обязательным его делает только `...`.
   - Последствие: старый клиент не получит 422. Он попадёт в ветку `amount = balance`, и у него **молча спишется весь баланс**.
   - Исправление: `Field(...)` или явный флаг полного списания.

2. **`app/schemas.py`, `RedeemRequest` — medium.**
   - Комментарий «лишние поля pydantic по умолчанию отвергает» **опровергнут**: в 1.10 по умолчанию `Config.extra = Extra.ignore`.
   - Последствие: опечатка вроде `confirm_amout` будет молча проигнорирована. Вместе с находкой №1 это даёт полное списание баланса.
   - Исправление: добавить `extra = Extra.forbid`.

3. **`app/redeem.py`, `redeem` — critical.** Знак и ноль у `confirm_amount` не проверяются.
   - При отрицательной сумме проверка `amount > balance` проходит, а `points -= int(...)` **начисляет** баллы.
   - Исправление: `condecimal(gt=0)`.

4. **`app/redeem.py`, `redeem` — high.** `POINT_VALUE = 0.1` задан как float.
   - `Decimal(0.1)` даёт точную двоичную величину `0.1000000000000000055…` (это есть в документации Python). Затем `int(...)` усекает результат.
   - По ручному расчёту выходит следующее:
     - при запросе 10 ₽ списывается 99 баллов вместо 100;
     - после «полного» списания 100 баллов остаётся 1 балл;
     - запрос на 0.05 ₽ списывает 0 баллов, а в ответе `redeemed = 0.05`, то есть скидка бесплатная и её можно повторять.
   - В ответе также появляется «мусор» float.
   - Исправление: `Decimal("0.1")`, кратность или явное округление в пользу системы, расчёт в целых баллах.

5. **`app/redeem.py` / `app/repo.py`, `get_member` → `save_member` — critical.**
   - Схема read-modify-write: чтение и запись абсолютного значения `points = :p` идут в разных транзакциях, без `FOR UPDATE` и без условного апдейта.
   - Параллельные запросы приводят к lost update и двойной трате.
   - Исправление: `UPDATE … SET points = points - :n WHERE … AND points >= :n`.

6. **`app/repo.py`, `save_member` / `write_audit` — high.**
   - Каждый `engine.begin()` коммитится отдельно (документация SQLAlchemy 1.4).
   - Если аудит упадёт, баллы уже списаны, записи нет, а клиент получит 500 и, скорее всего, повторит запрос.
   - Исправление: одна транзакция на оба действия.

7. **`app/redeem.py`, `redeem`, `write_audit(req.dict())` — medium.**
   - В аудит пишется запрос, а не результат. При полном списании там `confirm_amount: null`, а фактически списанные баллы не записываются и расходятся с запросом из-за находки №4.
   - По такому аудиту операцию не восстановить.

8. **`app/redeem.py`, `redeem`, `valid_until` — medium.**
   - `today + 365` при подсчёте «включая сегодняшний» даёт 366 дней, код расходится с комментарием.
   - Срок действия нигде не хранится и не проверяется, то есть заявленная в MR фича не реализована.
   - Используется `date.today()`, то есть локальная TZ сервера.

9. **`app/schemas.py`, `RedeemRequest.points` — low.** Поле обязательное, но нигде не используется, и контракт вводит в заблуждение.

10. **`app/redeem.py`, `redeem` — low.** 404 отдаётся без `detail`.
