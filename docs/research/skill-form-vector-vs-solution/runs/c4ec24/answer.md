## Итоги ревью

Ключевые находки (полный список с обоснованием — в `_answer.md`):

**Critical**
- `app/redeem.py:redeem()` — отсутствие проверки `confirm_amount > 0` позволяет отрицательным значением **увеличивать** баланс баллов вместо списания.
- `app/repo.py get_member/save_member` + `redeem()` — классическая гонка (read-then-write без блокировки/условного UPDATE), при конкурентных запросах возможно некорректное двойное списание.

**High**
- `app/schemas.py RedeemRequest.confirm_amount` — комментарий в коде утверждает, что поле обязательное, но в pydantic 1.10 `Optional[X]` без `...` даёт default `None` — поле фактически необязательно, что противоречит замыслу и открывает путь к непреднамеренному списанию всего баланса.
- Тот же файл — комментарий про отклонение лишних полей тоже неверен: дефолт pydantic v1 — `Extra.ignore`, а не `forbid`.
- `save_member` и `write_audit` (app/repo.py) — раздельные транзакции, нет атомарности списания и аудита.
- Заявленный в MR «срок действия баллов» по факту не реализован (нет хранения партий/сроков, `valid_until` — просто `today+365`).

**Medium** — `POINT_VALUE = 0.1` как float→Decimal (потеря точности), усечение через `int()`, потеря точности Decimal→float при JSON-сериализации ответа (подтверждено известным issue pydantic #1511), неиспользуемое поле `RedeemRequest.points`.

**Low** — необработанный `KeyError` при отсутствии `DATABASE_URL`, `psycopg2-binary` для прод (по докам psycopg2 рекомендован только для dev/test), отсутствие точки входа, монтирующей роутер в приложение.
