## Решения

- **Сортировка.** Значения `sort` и `dir` принимаются только из заранее заданного списка, неизвестное значение даёт 400. SQL там собирается строкой, поэтому без такой проверки была бы SQL-инъекция. При одинаковых значениях строки дополнительно упорядочиваются по номеру заявки, чтобы страницы не перемешивались. Статус сортируется по ходу работы с заявкой, а не по алфавиту. Общее количество считается отдельным `COUNT(*)` с теми же фильтрами.
- **Лицевые счета.** В проде уже есть дубли после переноса из биллинга 2023 года (об этом комментарий в `FindByAccountAsync`). Обычный уникальный индекс уронил бы миграцию при релизе. Поэтому миграция помечает старые дубли флагом `account_superseded`, актуальной остаётся запись с максимальным id. Индекс уникален только среди непомеченных записей, данные не удаляются. В коде есть проверка перед вставкой. Если параллельный запрос успел вставить тот же счёт раньше, ошибка БД `23505` превращается в 409. Старая версия приложения с миграцией работает, так что обычный порядок из `release.yml` (сначала миграции, потом раскатка) подходит.
- **План обслуживания.** PUT приводит план к присланному списку, работы сопоставляются по коду. Совпавшие обновляются, новые добавляются. Отсутствующие в списке не удаляются, а помечаются как архивные через `archived_at`: иначе вместе с ними каскадом пропали бы отметки о выполнении и номера актов. Два одновременных PUT по одному дому выполняются по очереди. Пустой код или название, периодичность ≤ 0 или повтор кода дают 400.
