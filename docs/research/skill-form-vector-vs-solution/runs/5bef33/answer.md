**Решения:**
- **(а, б) Сортировка и общее количество.** Значения `sort` и `dir` не подставляются в SQL напрямую: столбец берётся из белого списка, на неизвестное значение API отвечает 400. Статус сортируется по порядку этапов, а не по алфавиту. При равных значениях добавляется сортировка по номеру заявки, чтобы строки не перескакивали между страницами. Вместе со страницей возвращается `Total` — это отдельный `COUNT(*)` с теми же фильтрами.
- **(в) Уникальный лицевой счёт.** В проде уже есть дубли лицевых счетов после переноса из старого биллинга (2023), и на них ссылаются заявки. Обычный уникальный индекс уронил бы миграцию при релизе. Поэтому миграция помечает все записи по счёту, кроме последней, флагом `is_superseded`, а уникальный индекс проверяет только остальные записи с непустым счётом. Сервис сначала проверяет счёт сам. Если две квартиры с одним счётом заводят одновременно, ошибку от индекса он превращает в понятное исключение.
- **(г) PUT /houses/{id}/plan.** Работы сопоставляются по коду: существующие обновляются, новые добавляются, а пропавшие из списка помечаются датой исключения `removed_at`. Удалить план и вставить заново нельзя: вместе с работами каскадом удалились бы акты выполнения. Входные данные проверяются (повторы кодов, периодичность больше нуля). На время замены строка дома блокируется, чтобы два одновременных запроса не мешали друг другу.
