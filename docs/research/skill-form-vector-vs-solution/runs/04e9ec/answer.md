**Решения:**
- **Сортировка.** ORDER BY собирается только из заранее заданных вариантов, последним ключом всегда идёт `r.id`, чтобы страницы не «плыли». Статусы упорядочены по ходу работы с заявкой, а не по алфавиту. Квартиры сортируются по числовой части номера, поэтому «10» идёт после «2». Неверные `sort`/`dir` дают 400. Реестр читается через `FromSqlRaw`, поэтому новые колонки добавлены в его SELECT, иначе запрос падал бы.
- **Закрытие заявки.** Статус проверяется и меняется одним `ExecuteUpdate` с условием `status = InProgress`, чтобы два одновременных запроса не прошли оба. Ответы: 409, если заявка не в работе; 404, если её нет; 400, если комментарий пустой.
- **Замена плана.** Работы сопоставляются по `WorkCode`. Оставшиеся обновляются на месте и сохраняют историю, новые добавляются. Удалённые работы удаляются явно вместе со своими отметками о выполнении, в одной транзакции: в контексте `DeleteOrphansTiming = Never`, и простое удаление из коллекции упало бы на сохранении. Пустой список очищает план и стирает историю удалённых работ (акты). Если её нужно хранить, понадобится мягкое удаление.
