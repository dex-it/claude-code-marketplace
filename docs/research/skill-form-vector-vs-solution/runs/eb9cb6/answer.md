**Решения:**
- **(а) и (б):** все выборки только на чтение (`AsNoTracking`), позиции и платежи подгружаются явно через `Include`. Иначе при включённой ленивой загрузке будет отдельный запрос на каждый заказ. Позиции и платежи грузятся отдельными запросами (`AsSplitQuery`). Иначе на тысячах заказов один JOIN двух коллекций даёт произведение строк. В (б) заказы отсортированы по `Id`, чтобы эти запросы сходились между собой.
- **(в):** параметр `warehouse` сделал `string?`. Если склад передан, ищется пара SKU + склад. Если склад `null`, продукт возвращается, только когда SKU лежит на одном складе. Если складов несколько, бросается исключение, а не отдаётся случайная запись. При сравнении с `null` EF искал бы продукты с пустым складом и не нашёл бы ничего, поэтому случаи со складом и без него обрабатываются раздельно.
- **(г):** `GetLastShippedAtAsync` возвращает `DateTime`. Если у клиента нет отгруженных заказов, он бросает исключение, а не отдаёт `DateTime.MinValue`. Для случаев, где отсутствие отгрузок — норма, добавил `TryGetLastShippedAtAsync`, он возвращает `DateTime?`. Удалённые заказы исключаются существующим фильтром модели.

**Проблемы в модели, которые я не трогал:**
- Контекст использует ленивую загрузку (`UseLazyLoadingProxies`), а для неё все навигации должны быть `virtual`. `Order.Items`, `Order.Payments` и `Customer.Orders` сейчас не `virtual`, поэтому приложение, скорее всего, упадёт при старте, пока их не поправят.
- Стоит добавить уникальный индекс `(Sku, Warehouse)` на `Product`, чтобы база гарантировала уникальность SKU на складе. Для этого нужна миграция.
