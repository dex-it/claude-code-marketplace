## Итоги ревью MR «Списание баллов лояльности»

Отчёт записан в `_answer.md`. Ключевые находки:

**Critical**
1. `redeem.py:11,20` — `POINT_VALUE = 0.1` (float) → `Decimal(POINT_VALUE)` даёт неточное десятичное значение, ломает все денежные расчёты.
2. `schemas.py:15` — комментарий про `Optional` без default неверен для pydantic 1.10.13 (проверено по docs.pydantic.dev/1.10 и pydantic/pydantic#5481): поле фактически **не обязательно** и получает `None` по умолчанию → старые клиенты без `confirm_amount` спишут весь баланс вместо ожидаемой ошибки `422`.
3. `redeem.py:redeem()` — нет проверки `confirm_amount > 0`: отрицательное значение **увеличивает** баланс баллов вместо списания.
4. `repo.py`+`redeem.py` — гонка (lost update): чтение баланса и запись — разные транзакции без блокировки; Read Committed (дефолт PostgreSQL) не защищает от параллельного двойного списания.

**High**
5. `save_member`/`write_audit` — не атомарны, возможно списание без аудита.
6. `write_audit` — сохраняет только входящий запрос, не фактический результат операции (сумму, баланс до/после).

**Medium**
7. Тот же комментарий в `schemas.py` неверно утверждает, что pydantic отвергает лишние поля — дефолт `Extra.ignore`, опечатки в полях клиента молча проглатываются.
8. Поле `RedeemRequest.points` нигде не используется в логике списания.
9. «Срок действия баллов» из описания MR не реализован — `valid_until` только возвращается в ответе, истёкшие баллы не отслеживаются.
10. Дефолтная JSON-сериализация `Decimal` в pydantic 1.10 лоссовая (через `float`) — риск потери точности сумм в ответе API.

**Low**
11. Усечение (`int()`) вместо округления при пересчёте рублей в баллы.
12. `HTTPException(404)` без `detail`.
