**Решения:**
- **(а) и (б)** Запросы только читают данные, поэтому результат сразу собирается в DTO. Изменения не отслеживаются, ленивая загрузка наружу не выходит, из базы берутся только нужные поля. Удалённые заказы отсекает уже настроенный в модели фильтр. Карточка одного заказа читается одним SQL-запросом. Выгрузка тысяч заказов делится на отдельные запросы для заказов, позиций и платежей: иначе позиции и платежи перемножаются и строк становится слишком много.
- **(в)** Склад теперь может быть null. Если склад передан, продукт ищется по паре SKU и склад, которая уникальна. Если склад не передан, а SKU лежит на нескольких складах, метод бросает `AmbiguousSkuException`, а не возвращает случайный склад. Раз бизнес сейчас передаёт только SKU, на таких товарах этот метод будет падать, пока не начнут передавать склад. Для полного списка по SKU я добавил `GetProductsBySku(sku)`.
- **(г)** Самая поздняя дата отгрузки считается в SQL, учитываются только отгруженные заказы. Если у клиента нет ни одного отгруженного заказа, метод бросает `InvalidOperationException`: при типе без null вернуть «пусто» нельзя, а пустая дата выглядела бы как настоящая.

**Схему БД не менял, но стоит сделать отдельной миграцией:**
- Уникальный индекс на пару SKU и склад. Сейчас уникальность ничем не гарантирована.
- Тип колонок с датами. `ShippedAt` не настроен, поэтому Npgsql хранит его с часовым поясом (время в UTC), а `CreatedAt` явно задан без часового пояса.
