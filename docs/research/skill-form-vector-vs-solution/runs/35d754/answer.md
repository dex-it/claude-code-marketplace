# Ревью MR !58: приёмка мёда и выплаты

В MR 16 находок: 4 critical, 4 high, 5 medium, 3 low. Код, сборку и тесты я не трогал, всё найдено по чтению кода. Тот же ответ записан в `_answer.md`.

## Critical

1. **`Services/IntakeService.cs` → `RegisterAsync`: вес `"41,250"` разбирается как 41 250 кг.**
   - **Что не так:** `decimal.Parse(dto.Gross, CultureInfo.InvariantCulture)` по умолчанию допускает разделитель тысяч, а в InvariantCulture это запятая.
   - **Почему дефект:** вес, а с ним и выплата, без всякой ошибки становятся в 1000 раз больше. На кривой строке `FormatException` даёт 500, и терминал будет повторять отправку бесконечно, хотя нужен 4xx.
   - **Как исправить:** разбирать через `TryParse` с запятой как десятичным разделителем, при ошибке отвечать 400/422.

2. **`Services/IntakeService.cs` → `RegisterAsync`: дубликат ищется только по `WeighingNo`, без `TerminalId`.**
   - **Что не так:** у разных терминалов номера взвешиваний пересекаются.
   - **Почему дефект:** настоящая партия с другого пункта будет принята за дубликат. Терминал получит 200 и удалит её из буфера, и пчеловоду за неё не заплатят. Уникальный индекс в БД при этом задан правильно, а проверка в коде с ним не совпадает.

3. **`Services/PayoutService.cs` → `CalculateAsync`: `batch.PayoutId = payout.Id` выполняется до `SaveChanges`.**
   - **Что не так:** в этот момент `Id` ещё равен 0.
   - **Почему дефект:** при сохранении нарушается FK, и пользователь получает 500. Рассчитать выплату пчеловоду, у которого есть партии, невозможно.
   - **Как исправить:** `batch.Payout = payout`.

4. **`Services/PayoutService.cs` → `CalculateAsync`: `member.AdvanceBalance = 0`.**
   - **Что не так:** весь остаток аванса обнуляется, а удерживается только `min(due, balance)`.
   - **Почему дефект:** непогашенный остаток аванса теряется. В месяц без партий списывается весь аванс, а не удерживается ничего.
   - **Как исправить:** `AdvanceBalance -= withheld`.

## High

5. **`Services/PayoutService.cs` → `CalculateAsync`: цена берётся на `DateTime.UtcNow`, а не на день приёмки каждой партии.**
   - Это прямо нарушает требование MR.
   - Если для сорта нет цены, `KeyNotFoundException` даёт 500.

6. **`Services/PayoutService.cs` → `CalculateAsync`: партии последнего дня месяца не попадают в выплату.**
   - **Что не так:** верхняя граница `to` — последний день месяца 00:00, условие `<= to`.
   - **Почему дефект:** партии последнего дня не попадут ни в этот месяц, ни в следующий, то есть не будут оплачены никогда.
   - **Как исправить:** `< from.AddMonths(1)`.

7. **`Services/PayoutService.cs` → `ApproveAsync`: не проверяется принцип четырёх глаз.**
   - Нет проверки `accountantId != payout.CreatedBy`, поэтому бухгалтер может сам утвердить свой расчёт.

8. **`Controllers/TerminalController.cs` → `Post`: на `UnknownMember`/`UnknownContainer` возвращается 200.**
   - Терминал удаляет запись после любого 2xx, поэтому взвешивание с опечаткой молча теряется.
   - Нужен 4xx с `reason`, чтобы приёмщик увидел причину и исправил запись.

## Medium

9. **`Services/IntakeService.cs` → `GradeFor`: граница сорта A не включена.**
   - Стоит `< 18.5`, нужно `<=`. Мёд ровно 18,5 % записывается в сорт B и оплачивается дешевле.

10. **`Services/IntakeService.cs` → `RegisterAsync`: не проверяется, что брутто больше тары.**
    - Партия с нетто ≤ 0 принимается и уменьшает выплату.

11. **`Services/PayoutService.cs` → `CalculateAsync` и `Services/IntakeService.cs`: месяц и день приёмки считаются в UTC, а не в местном времени.**
    - Взвешивание в 01:00 по местному времени 1-го числа попадёт в прошлый месяц и получит цену прошлого дня.

12. **`Services/PayoutService.cs` → `CalculateAsync`: партии, пришедшие после расчёта за свой месяц, не оплачиваются.**
    - Терминал может дослать партию из буфера после сбоя сети.
    - Повторный расчёт за этот месяц вернёт 409, а в следующий месяц партия не попадёт по дате.

13. **`Services/PayoutService.cs` → `CalculateAsync`: гонка при изменении `AdvanceBalance`.**
    - Изменение идёт без транзакции и без токена конкурентности.
    - При параллельных расчётах или выдаче аванса возможен lost update.

## Low

14. **`Services/IntakeService.cs` → `RegisterAsync`: гонка между проверкой и вставкой.**
    - При одновременной повторной отправке второй запрос падает на уникальном индексе с 500.
    - Данные не теряются, но лучше ловить `23505` и отвечать как на дубликат.

15. **`Services/PayoutService.cs` → `CalculateAsync`: та же гонка на уникальном индексе выплаты.**
    - При двух одновременных расчётах за один месяц второй получит 500 вместо 409.

16. **`Services/PayoutService.cs` → `ApproveAsync`: параллельное утверждение.**
    - Оба запроса проходят, второй перезаписывает `ApprovedBy`.
    - **Как исправить:** условный UPDATE `WHERE Status = Draft` или токен конкурентности.
