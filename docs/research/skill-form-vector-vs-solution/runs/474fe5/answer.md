# Ревью MR «Списание баллов лояльности»

Контекст: pydantic 1.10.13, FastAPI 0.95.2, SQLAlchemy 1.4.

## Critical

1. **`app/schemas.py`, `RedeemRequest.confirm_amount` + `app/redeem.py`, `redeem`: если поле не прислать, списывается весь баланс.**
   Комментарий в схеме неверен для pydantic v1: `Optional[Decimal]` без значения по умолчанию там **не** обязательное поле, оно неявно получает `None`. Старый клиент, который не знает про `confirm_amount`, не получит 422: запрос пройдёт, и `redeem` спишет весь баланс (`amount = balance`). Получается необратимая потеря баллов у пользователей из-за обычного запроса. Как исправить: `confirm_amount: Optional[Decimal] = Field(...)` (так поле станет обязательным и при этом допускающим null) или отдельный явный флаг `redeem_all: bool`.

2. **`app/schemas.py`, `RedeemRequest` (конфиг модели): лишние поля не отвергаются.**
   Комментарий «лишние поля pydantic по умолчанию отвергает» неверен: в pydantic v1 по умолчанию `Extra.ignore`. Опечатка вроде `"confirm_amout": 10` будет молча проигнорирована, `confirm_amount` станет `None`, и спишется весь баланс. Вместе с п.1 это прямой путь к полному списанию. Нужно `class Config: extra = Extra.forbid`.

3. **`app/redeem.py`, `redeem`: нет проверки знака и нуля у `confirm_amount`.**
   При отрицательном `confirm_amount` проверка `amount > balance` проходит, а `member.points -= int(отрицательное)` **увеличивает** баланс. Любой клиент может начислить себе сколько угодно баллов. Нужна валидация `confirm_amount > 0` (`condecimal(gt=0)`) и, скорее всего, ограничение на количество знаков после запятой.

4. **`app/redeem.py`, `redeem` / `app/repo.py`, `get_member`/`save_member`: гонка read-modify-write, возможна двойная трата.**
   Баланс читается в одной транзакции, а новое абсолютное значение `points` записывается в другой, без блокировки (`SELECT ... FOR UPDATE`) и без условного `UPDATE ... SET points = points - :n WHERE id = :id AND points >= :n`. Два параллельных запроса оба пройдут проверку баланса, одно из обновлений потеряется, и сумма будет списана (выдана скидкой) дважды при однократном уменьшении баланса.

## High

5. **`app/redeem.py`, `POINT_VALUE = 0.1` и `Decimal(POINT_VALUE)`: деньги считаются через float.**
   `Decimal(0.1)` = `0.1000000000000000055511151231257827…`. Из-за этого:
   - `int(amount / Decimal(POINT_VALUE))` для `amount = 10` даёт `99.9999999999999994…` → `99`: списывается на балл меньше, чем выдано скидки. При полном списании остаток тоже может оказаться неверным;
   - в ответе `redeemed`/`balance_left` приходят «грязные» значения вроде `10.00000000000000055511151231`.
   Нужно `POINT_VALUE = Decimal("0.1")` и вести расчёт в целых баллах.

6. **`app/redeem.py`, `redeem`: `int()` отбрасывает дробную часть, клиент получает больше, чем оплатил баллами.**
   При `confirm_amount = 0.15` списывается 1 балл (0.1 ₽), а в ответе `redeemed = 0.15`. Если повторять запрос с суммами меньше 0.1 ₽ (например, 0.09), скидка выдаётся, а баллы вообще не списываются (`int(0.9) = 0`). Нужно либо отклонять суммы, не кратные стоимости балла, либо округлять вверх (`ROUND_CEILING`) и возвращать фактически списанную сумму.

7. **`app/redeem.py`, `redeem` / `app/repo.py`, `save_member` + `write_audit`: списание и аудит не атомарны.**
   Это две разные транзакции. Если `write_audit` упадёт после `save_member`, баллы уже списаны, а записи аудита нет (и наоборот при переносе порядка). Оба действия должны выполняться в одной транзакции. Кроме того, `save_member` не проверяет `rowcount`: если участника удалили между чтением и записью, ошибка не возникнет.

8. **`app/redeem.py`, `redeem`: в аудит пишется запрос, а не результат операции.**
   `write_audit(member.id, req.dict())` сохраняет `confirm_amount: null` при полном списании и игнорируемое поле `points`. Фактически списанные баллы и сумма, баланс до и после в аудит не попадают, так что по аудиту операцию не восстановить.

## Medium

9. **`app/redeem.py`, `redeem`, вычисление `valid_until`: ошибка на единицу.**
   По комментарию баллы действуют «365 дней … включая сегодняшний», значит последний день — `today + 364`, а код возвращает `today + 365`. Кроме того, `date.today()` берёт часовой пояс сервера, а не бизнес-часовой пояс.

10. **`app/redeem.py`, `redeem`: `valid_until` только вычисляется и возвращается, но нигде не сохраняется и не проверяется.**
    Срок действия заявлен в описании MR, но просроченные баллы можно списать, а новая дата не записывается в БД. Ответ API вводит клиента в заблуждение.

11. **`app/schemas.py`, `RedeemRequest.points`: обязательное поле, которое нигде не используется.**
    Клиент обязан его прислать, но сервер его игнорирует. Клиент может решить, что списывается `points` баллов, а на деле спишется `confirm_amount` или весь баланс. Поле нужно либо убрать, либо использовать (и сверять с `confirm_amount`).

## Low

12. **`app/redeem.py`, `redeem`: полное списание при нулевом балансе проходит успешно.**
    Получается «списание» на 0 с записью в аудит. Лучше отвечать 409/422.
13. **`app/redeem.py`, `redeem`: `HTTPException(status_code=404)` без `detail`.** Клиенту непонятна причина ошибки.
14. **`app/redeem.py`: в роуте `/redeem` нет аутентификации и авторизации.** Любой, кто знает `member_id`, может списать чужие баллы. Если это не решается на уровне gateway, severity повышается до critical.
