Провёл ревью MR, ответ записан в `_answer.md`. Ключевые находки:

**Critical**
1. `redeem.py:redeem()` — `confirm_amount` не проверяется на знак: отрицательное значение проходит проверку `amount > balance` и **увеличивает** `member.points` вместо списания.
2. `schemas.py:RedeemRequest.confirm_amount` — комментарий про «Optional без default = обязательное поле» верен для pydantic v2, но проект закреплён на `pydantic==1.10.13`, где `Optional[X]` без default неявно получает `default=None` (подтверждено migration guide pydantic). Заявленная защита от старых клиентов не работает — они получат полное списание баланса вместо 422.
4. `redeem.py`: `POINT_VALUE = 0.1` — float, а `Decimal(POINT_VALUE)` даёт неточное значение `0.1000...055511...` (документировано в Python docs) — погрешность попадает в финансовый расчёт.
6. `repo.py`+`redeem.py` — чтение и запись баланса идут в разных несинхронизированных транзакциях без блокировки строки — классический race/lost update при параллельных списаниях.

**High**
3. Комментарий про «pydantic отвергает лишние поля» ложен для v1.10 (дефолт `Extra.ignore`, подтверждено докой) — опечатки в полях молча игнорируются.
5. `int(amount / Decimal(POINT_VALUE))` усекает без проверки кратности — сумма и фактически списанные баллы могут расходиться.
7. Обновление баланса и запись аудита — разные транзакции, возможна потеря аудита при сбое.
9. «Срок действия баллов» из описания MR не реализован — `valid_until` только вычисляется и возвращается, никак не сохраняется и не влияет на баланс.
10. Нет проверки авторизации по `member_id` в показанном коде (нужно подтверждение, что это обеспечено снаружи).

**Medium/Low**
8. Поле `points` в `RedeemRequest` обязательно, но не используется в логике.
11. `HTTPException(404)` без `detail`, в отличие от 409.
