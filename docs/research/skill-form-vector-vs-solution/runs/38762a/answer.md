Ревью проведено, находки сохранены в `_answer.md`. Ключевое:

**critical**
- `app/redeem.py` — `POINT_VALUE = 0.1` (float) конвертируется в `Decimal` уже с бинарной погрешностью — нужен `Decimal("0.1")`.
- `app/redeem.py` (`redeem`) — нет проверки, что `confirm_amount` положителен: отрицательная сумма проходит проверку баланса и увеличивает баллы клиента (можно накручивать баллы через эндпоинт списания).
- `app/redeem.py` + `app/repo.py` — `get_member`/`save_member` не в одной транзакции, нет блокировки строки → гонка/double-spend при параллельных списаниях.

**high**
- Усечение при `int(amount / Decimal(POINT_VALUE))` без проверки кратности — ответ `redeemed` может не соответствовать реально списанным баллам.
- `valid_until` только возвращается в ответе, нигде не сохраняется и не используется — срок действия баллов, заявленный в MR, фактически не реализован.
- В показанном коде нет проверки прав на списание баллов у произвольного `member_id`.

**medium**
- `RedeemRequest.points` объявлено обязательным, но нигде не используется в логике.
- Комментарий в `app/schemas.py` про то, что «pydantic по умолчанию отвергает лишние поля», фактически неверен для pydantic 1.10.13 (проверено по официальной документации: дефолт — `Extra.ignore`, а не `forbid`) — заявленной защиты от опечаток в полях нет.
- `write_audit` пишет только сырой запрос, а не фактические `redeemed`/`balance_left` — аудит неполный.

**low**
- `HTTPException(404)` без `detail`, несогласованно с 409.
- `date.today()` зависит от таймзоны сервера вместо UTC.

Также по ходу проверил по дисциплине SKILL.md два конкретных утверждения о поведении Pydantic 1.10 по официальной документации: про `Optional` без default (что поле обязательно) — подтвердилось, претензий нет; про отклонение лишних полей по умолчанию — опровергнуто.
