Нашёл 8 дефектов, до мерджа стоит исправить все: 3 critical, 2 high, 2 medium, 1 low. Два комментария в `schemas.py` неверно описывают поведение pydantic. Я сверил их с документацией pydantic 1.10 и с исходником версии v1.10.13. Утверждение про `Decimal(0.1)` сверено с документацией Python. Код я не менял, тесты не запускал. Ответ записан в `_answer.md`.

1. **`app/schemas.py` — `RedeemRequest.confirm_amount` — critical.** Комментарий говорит, что `Optional[Decimal]` без значения по умолчанию делает поле обязательным. В pydantic 1.10 это не так. Если у `Optional[...]` есть только аннотация, поле необязательное и по умолчанию равно `None`. Обязательным его делает только `= ...` (раздел документации «Required Optional fields»; в исходнике `fields.py` для такого поля ставится `required = False`). Старый клиент, который не знает про `confirm_amount`, не получит 422. Вместо этого у него **спишется весь баланс**. Исправление: `confirm_amount: Optional[Decimal] = ...`.

2. **`app/redeem.py` — `redeem` — critical.** Нет проверки, что `confirm_amount > 0`. При отрицательной сумме проверка `amount > balance` проходит, а `points -= int(отрицательное)` **начисляет** баллы. Сумма 0 тоже пропускается, и в аудит пишется пустая операция.

3. **`redeem.py` — `redeem` и `repo.py` — `get_member`, `save_member` — critical.** Баланс читается в одной транзакции, а записывается целиком (`SET points = :p`) в другой, без блокировки строки. Два параллельных запроса оба пройдут проверку и оба спишут баллы. Кроме того, запись затирает начисления, прошедшие между чтением и записью. Исправление: атомарный `UPDATE … SET points = points - :d WHERE id = :id AND points >= :d` с проверкой числа изменённых строк, либо `SELECT … FOR UPDATE` в одной транзакции.

4. **`redeem.py` — `redeem`, `Decimal(POINT_VALUE)` — high.** `POINT_VALUE = 0.1` — это float. `Decimal(0.1)` даёт `0.1000000000000000055…`, это подтверждено документацией Python. Поэтому деление суммы на стоимость балла даёт чуть меньше целого, и `int()` отбрасывает остаток: например, за 1 рубль спишется 9 баллов вместо 10. При этом в ответе `redeemed` показывает полную сумму. Суммы, не кратные стоимости балла, молча округляются вниз. Исправление: `Decimal("0.1")` и явный перевод суммы в баллы с отказом для некратных сумм.

5. **`redeem.py` — `redeem` и `repo.py` — `write_audit` — high.** Списание и запись аудита идут в разных транзакциях: если аудит упадёт, баллы уже списаны, а записи нет. К тому же в аудит пишется запрос (`req.dict()`, при полном списании `confirm_amount = null`), а не фактически списанные баллы. Восстановить операцию по такому аудиту нельзя.

6. **`redeem.py` — `redeem`, `valid_until` — medium.** Если считать 365 дней «включая сегодняшний», как в комментарии, `today + 365` даёт на день больше. Кроме того, срок только возвращается в ответе: он не сохраняется и нигде не проверяется, так что заявленная в MR функция «срок действия баллов» фактически не работает.

7. **`app/schemas.py` — `RedeemRequest`, комментарий про лишние поля — medium.** По документации pydantic 1.10 значение по умолчанию — `Extra.ignore`, то есть лишние поля молча игнорируются, а не дают 422. Если клиент опечатается в имени `confirm_amount`, поле проигнорируется и тоже спишется весь баланс (см. п. 1). Если отказ действительно задуман, нужно `Extra.forbid`.

8. **`app/schemas.py` — `RedeemRequest.points` — low.** Поле обязательное, но в `redeem` не используется. Клиент может думать, что списывает `points` баллов, а на деле списывается `confirm_amount` или весь баланс.
