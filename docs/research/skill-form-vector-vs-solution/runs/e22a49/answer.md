## Critical
1. **`Services/InpatientReportService.cs`, `GetOccupancyAsync`: SQL-инъекция.** Параметры `ward` и `sortBy` приходят из query-строки и вставляются в `FromSqlRaw` строковой интерполяцией. Эндпоинт требует только входа в систему, поэтому любой пользователь, в том числе ресепшен, может читать и менять данные в базе. `ward` нужно передавать параметром, `sortBy` сверять с белым списком столбцов и сортировать через LINQ.

## High
2. **`WardService.DischargeAsync`: счёт меньше на одни сутки.** Сейчас дни считаются как `выписка − поступление`. По README оплачиваются и день поступления, и день выписки, так что нужно `+1`. Выписка в день поступления сейчас стоит 0. В `Stay.DaysInWard` та же ошибка.
3. **`InpatientEndpoints`, `POST /stays/{id}/discharge`: выписать может кто угодно.** На эндпоинте `RequireAuthorization()` без политики. По README выписывает только врач, нужна политика `"Vet"`.
4. **`ClinicDbContext`: фильтр на `Box` прячет пациентов из выведенных боксов.** Фильтр «бокс не выведен» стоит на обязательной связи «госпитализация → бокс», поэтому EF Core применяет его и к госпитализациям. README разрешает выводить бокс с пациентами и требует, чтобы они оставались в списках до выписки. Последствия:
   - такие пациенты пропадают из списка отделения, из обхода главврача и из отчёта по занятости;
   - `DischargeAsync` для них падает: **выписать пациента и выставить счёт нельзя**;
   - карточка такого бокса возвращает 404;
   - повторный вывод бокса из эксплуатации даёт 500.
5. **`WardService.ReplaceMedicationPlanAsync`: назначения удаляются, а на деле метод падает.**
   - `MedicationOrders.Clear()` задуман как физическое удаление. Это нарушает правило README: назначения не удаляются, отменённым ставится `CancelledAt`.
   - Из-за `DeleteBehavior.Restrict` EF при сохранении бросает исключение, так что поменять уже существующий план нельзя (500).
   - Входные данные не проверяются: `Drug.Trim()` при `null` падает.
6. **`WardService.GetLongStaysAsync`: запрос не переводится в SQL.** `DaysInWard` — вычисляемое C#-свойство, EF Core его не транслирует, поэтому `/long-stays` всегда отвечает 500.
7. **`WardService.GetBoxCardAsync`: падает на боксе с несколькими животными.** `SingleOrDefaultAsync` бросает исключение, если в боксе больше одного пациента, а README это разрешает (до `Capacity` животных). Ответ к тому же рассчитан только на одного питомца.
8. **`WardService.GetLatestStayAsync`: врач видит не ту госпитализацию.** Сортировка только по дате без времени. При повторной госпитализации в тот же день открывается утренняя, уже закрытая, с чужими назначениями. Нужно добавить `ThenByDescending(Id)`, как уже сделано в `GetPetHistoryAsync`.
9. **`Program.cs`: миграции при старте приложения.**
   - В проде приложение работает под ролью `vet_app` без прав на изменение схемы. Если миграция не применена, старт падает.
   - Три реплики при rolling update будут мигрировать одновременно.
   - Схема меняется в обход скрипта, который проверяет DBA, и джобы `db-migrate`.

## Medium
10. **`GetOccupancyAsync`: выбранная на экране сортировка может не работать.** EF оборачивает сырой SQL в подзапрос, и PostgreSQL не обязан сохранять порядок строк подзапроса.
11. **`DischargeAsync`: нет защиты от одновременной выписки.** Два параллельных запроса оба проходят проверку «ещё не выписан», и второй перезаписывает дату и сумму счёта. Кроме того, при несуществующем id везде возвращается 500 вместо 404.

## Low
12. **`Stay.DaysInWard`: «сегодня» считается по UTC, а не по дате клиники.** Около полуночи дата расходится с журналом поступлений.
