## Итоги ревью MR «Списание баллов лояльности»

Разобрал все изменённые файлы (`app/redeem.py`, `app/repo.py`, `app/schemas.py`, `app/db.py`) и сверил ключевые утверждения из комментариев в коде с документацией Pydantic 1.10 (версия закреплена в `requirements.txt`) и Python `decimal`, а не принял их на веру.

**Critical:**
1. `app/schemas.py::RedeemRequest.confirm_amount` — комментарий утверждает, что поле обязательное из-за `Optional` без дефолта; в Pydantic v1 это ложь (подтверждено документацией) — поле фактически необязательно и тихо становится `None` → полное списание баланса вместо ожидаемой ошибки 422.
2. `app/redeem.py::redeem` — нет проверки `confirm_amount` на отрицательное значение → можно увеличивать баланс баллов через публичный эндпоинт.
3. `app/redeem.py::redeem` + `app/repo.py` — чтение/запись баланса и запись аудита идут в трёх независимых транзакциях без блокировки строки → лост-апдейт при гонке запросов и возможность рассинхронизации баланса с аудитом.

**High:**
4. `app/schemas.py` — комментарий про отклонение лишних полей тоже ложный (дефолт Pydantic v1 — `Extra.ignore`, не `forbid`), подтверждено документацией.
5. `app/redeem.py::redeem` — `POINT_VALUE = 0.1` (float), обёрнутый в `Decimal()`, а не заданный строкой — классическая ошибка точности Decimal/float.

**Medium:**
6. Усечение через `int()` при пересчёте суммы в баллы — расхождение между возвращённым `redeemed` и фактически списанными баллами.
7. `valid_until` — заглушка `today()+365 дней`, не реализующая заявленную в MR логику срока действия баллов.
8. `RedeemRequest.points` — обязательное поле, которое нигде не используется в бизнес-логике.

**Low:**
9. `HTTPException(status_code=404)` без `detail`, в отличие от 409.
