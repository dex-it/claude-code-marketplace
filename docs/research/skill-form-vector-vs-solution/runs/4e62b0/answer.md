Нашёл 13 дефектов: 2 critical, 6 high, 4 medium, 1 low. Код не менял, сборку и тесты не запускал. Тот же ответ записан в `_answer.md`.

## Critical
1. **`Services/InpatientReportService.cs` → `GetOccupancyAsync`: SQL-инъекция.** `ward` и `sortBy` приходят из query string и вставляются прямо в текст SQL для `FromSqlRaw`. Эндпоинт открыт любому вошедшему пользователю. Нужно передавать `ward` параметром, а `sortBy` сверять с белым списком столбцов. Ещё лучше переписать на обычный LINQ.
2. **`Program.cs`: `MigrateAsync()` при старте.**
   - В проде приложение работает под ролью `vet_app`, у которой нет прав на DDL. Миграция упадёт, и все поды уйдут в crash-loop.
   - Даже если права есть, 3 реплики при rolling update будут применять миграции одновременно. В EF Core 8 нет блокировки миграций.
   - Это обходит принятый процесс: SQL-скрипт, ревью DBA и джобу `db-migrate`.

## High
3. **`WardService.ReplaceMedicationPlanAsync`: `Clear()` при `Restrict`.** На required-связи `SaveChanges` бросает `InvalidOperationException`, поэтому заменить уже существующий план нельзя. Кроме того, назначения по README физически не удаляются: им нужно ставить `CancelledAt`.
4. **`WardService.GetLongStaysAsync`: фильтр не переводится в SQL.** `DaysInWard` — вычисляемое свойство без маппинга. EF не может перевести его в SQL и бросает исключение, так что `/long-stays` не работает совсем.
5. **`ClinicDbContext`: фильтр `HasQueryFilter` на `Box` при required-связи `Stay → Box`.** EF соединяет госпитализации только с невыведенными боксами (INNER JOIN), поэтому пациенты из выведенных боксов:
   - пропадают из `GetWardPatientsAsync`, `GetLongStaysAsync` и отчёта занятости;
   - не выписываются: `DischargeAsync` падает на `SingleAsync`.

   README прямо требует, чтобы такие пациенты оставались в списках до выписки.
6. **`WardService.GetBoxCardAsync`: `SingleOrDefaultAsync` по неуникальному условию.** В боксе может лежать до `Capacity` животных. Как только там два пациента, запрос бросает исключение и карточка бокса отвечает 500.
7. **`WardService.DischargeAsync`: счёт занижен на один день.** По README считаются и день поступления, и день выписки, а в коде нет `+ 1`. При выписке в день поступления счёт равен 0.
8. **`InpatientEndpoints`, `POST /stays/{id}/discharge`: не та авторизация.** Стоит `RequireAuthorization()` без политики, поэтому выписать может кто угодно, включая ресепшен. По README нужна политика `"Vet"`.

## Medium
9. **`WardService.GetLatestStayAsync`: «последняя» госпитализация выбирается непредсказуемо.**
   - Сортировка только по `AdmittedOn`, а повторная госпитализация в тот же день возможна. Нужно добавить `ThenByDescending(Id)`.
   - Из-за `AsSplitQuery` с `FirstOrDefault` назначения и наблюдения могут загрузиться не от той госпитализации, и карточка выйдет с пустыми или чужими данными.
   - Грузятся полные сущности, а отмена назначений отфильтровывается уже в памяти. Лучше одна проекция в DTO.
10. **`GetOccupancyAsync`: выбранная сортировка не работает.** EF оборачивает `FromSqlRaw` в подзапрос, и `ORDER BY` оказывается внутри него. PostgreSQL не гарантирует, что этот порядок сохранится во внешнем запросе.
11. **`DischargeAsync` и `ReplaceMedicationPlanAsync`: нет защиты от одновременной правки.** Два одновременных запроса молча перезаписывают друг друга. Нужен concurrency token (`xmin`) и ответ 409 при конфликте.
12. **`ClinicDbContext` / миграция: каскадное удаление.** Связи `Stay → Box` и `Stay → Pet` получат `ON DELETE CASCADE`. Физическое удаление бокса, который по модели удаляется мягко, удалит в БД его госпитализации вместе с наблюдениями. Нужно явно задать `Restrict`.

## Low
13. **`DecommissionBoxAsync` (а также `DischargeAsync` и `ReplaceMedicationPlanAsync`): 500 вместо 404/409.** Из-за фильтра повторный вывод бокса падает на `SingleAsync`, как и запрос с несуществующим `id`.
