Код не менял, сборку и тесты не запускал. Нашёл 9 проблем: одну critical, две high, три medium и три low. Самая серьёзная — расчёт объёма препарата: он завышен в 1000 раз. Тот же список записан в `_answer.md`.

## 1. `Services/ProcedureService.cs` → `CalculateDoseMlAsync`: вес в граммах умножается на дозу в мг/кг — **critical**
`doseMg = weightGrams * drugMgPerKg`. Доза задаётся на килограмм, а вес хранится в граммах, перевода в кг нет. Поэтому объём получается **в 1000 раз больше**. Пример: кошка 4000 г, 2,5 мг/кг, 10 мг/мл. Метод вернёт 1000 мл вместо 1 мл. Это прямой риск передозировки при инфузии. Комментарий в коде («вес, кг × мг/кг») с самим кодом не совпадает.
Исправление: `weightGrams / 1000m * drugMgPerKg` и тест на расчёт с известным ответом.

## 2. `Domain/Pet.cs` (`WeightGrams`), миграция `AddProcedures`, `CalculateDoseMlAsync`: у существующих питомцев вес станет 0 — **high**
`WeightGrams` объявлен как non-nullable `int`. Миграция добавит колонку `NOT NULL DEFAULT 0` в уже заполненную таблицу `Pets`. У всех старых питомцев окажется вес «0 г», хотя на самом деле он неизвестен. Расчёт дозы такой вес не проверяет и молча вернёт 0 мл.
Исправление: сделать поле `int?`. В расчёте при `null` или `<= 0` бросать явную ошибку «питомец не взвешен».

## 3. `Services/ProcedureSheetService.cs` → `GetDaySheetAsync`: смещение страницы считается с 0, а по контракту страницы с 1 — **high**
По контракту страницы нумеруются с 1, а код делает `Skip(page * PageSize)`. Поэтому `page=1` пропускает первые 30 процедур дня. Начало листа дня никогда не показывается. Кроме того, `page <= 0` не проверяется: при отрицательном значении PostgreSQL падает на отрицательном `OFFSET`.
Исправление: `Skip((page - 1) * PageSize)`, при `page < 1` возвращать 400.

## 4. `Services/ProcedureService.cs` → `RemoveConsumableAsync`: гонка с закрытием процедуры и загрузка всех строк ради одной — **medium**
- **Гонка.** Статус проверяется в памяти, удаление идёт отдельной командой, токена конкурентности нет. Если процедуру закроют между чтением и сохранением, строка исчезнет из уже закрытого списания. README это прямо запрещает. Токен `xmin` на `Procedure` здесь не поможет: удаление зависимой строки не меняет строку процедуры.
- **Загрузка.** `Include(Consumables)` загружает и отслеживает сотни строк расходников ради удаления одной.

Исправление: одна атомарная команда:
`db.ConsumableLines.Where(c => c.Id == lineId && c.ProcedureId == procedureId && c.Procedure.Status != ProcedureStatus.Closed).ExecuteDeleteAsync()`.
Если удалено 0 строк, отдельно выяснить причину: строки нет или процедура закрыта. Сам `Remove` корректен: связь обязательная, каскад по умолчанию, оторванная строка удаляется.

## 5. `Services/ProcedureService.cs` → `RescheduleAsync`: перенос без защиты от параллельной смены статуса — **medium**
Проверка «статус = запланирована» и запись нового времени ничем не защищены. Если процедуру параллельно начали, отменили или закрыли, перенос всё равно пройдёт.
Исправление: токен `xmin` на `Procedure` с обработкой `DbUpdateConcurrencyException`. Другой вариант — условный `ExecuteUpdateAsync` с `Where(p => p.Id == id && p.Status == Scheduled)`.

## 6. `Data/ClinicDbContext.cs` → `OnModelCreating` (связь `Procedure → Pet`): журнал процедур удаляется каскадом вместе с питомцем — **medium**
Связь обязательная, поведение при удалении не задано, поэтому по умолчанию стоит каскад. При удалении питомца удалятся его процедуры, а за ними расходники и заметки персонала. Это медицинский журнал и источник отчёта по расходу материалов.
Исправление: `.OnDelete(DeleteBehavior.Restrict)`.

## 7. `Services/ProcedureSheetService.cs` → `SearchNotesAsync`: заметки персонала в поиск не попадают, индекса нет — **low**
В MR заявлен «поиск по заметкам», но запрос смотрит только колонку `"Notes"`, а записи в `StaffNotes` не ищутся. Кроме того, полнотекстовое выражение считается на лету без GIN-индекса, поэтому каждый запрос — полный проход по `Procedures`. Подстановка текста параметризована, SQL-инъекции нет.

## 8. `Services/ProcedureService.cs` → `GetCardAsync`: загружаются полные сущности вместо нужных полей — **low**
Загружаются полные `Pet`, строки расходников и заметки, хотя карточке нужна лишь часть полей: от `Pet`, например, только `Name`. Лучше сразу собирать DTO в запросе через `Select`. Тогда лишние колонки не грузятся, а заметки сортируются в БД. Раздельный запрос (`AsSplitQuery`) при двух коллекциях здесь уместен. Строки расходников приходят без явного порядка, поэтому их порядок в карточке может меняться.

## 9. `RescheduleAsync`, `RemoveConsumableAsync`, `CalculateDoseMlAsync`: «не найдено» превращается в 500 — **low**
Если записи нет, `SingleAsync` бросает `InvalidOperationException`. Это то же исключение, что и у бизнес-отказа «перенести можно только запланированную», поэтому клиент не отличит 404 от 409. Лучше `SingleOrDefaultAsync` с `KeyNotFoundException`, как уже сделано для строки расходников. Похоже и в `ScheduleAsync`: несуществующий `PetId` всплывает только как ошибка внешнего ключа при сохранении.

---

**Проверено, дефектов нет:**
- **Время.** Расписание хранится как `timestamp without time zone` с `Kind=Unspecified`, `CreatedAt` — `timestamptz` с `UtcNow`. Границы дня и месяца в отчётах сравниваются корректно.
- **SQL в отчёте по расходникам.** Сортировка выбирается только из разрешённого списка, значения передаются параметрами.
- **Поиск по чипу.** `SingleOrDefault` по номеру чипа подкреплён уникальным индексом.
- **Прочее.** `Add` используется вместо `AddAsync`, у выборок только для чтения есть `AsNoTracking`.
