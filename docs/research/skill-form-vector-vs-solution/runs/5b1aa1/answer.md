В MR нашлось 8 дефектов, их стоит исправить до мерджа. Самый серьёзный — ошибка в расчёте дозы препарата. Код я не менял, сборку и тесты не запускал. Тот же ответ записан в `_answer.md`.

## 1. `Services/ProcedureService.cs` — `CalculateDoseMlAsync`: вес в граммах умножается на дозу в мг/кг — **critical**
`doseMg = weightGrams * drugMgPerKg`, но `Pet.WeightGrams` хранит граммы, а доза задаётся на килограмм. Деления на 1000 нет, поэтому объём получается в 1000 раз больше нужного. Пример: кошка 4 кг (4000 г), 2,5 мг/кг, 10 мг/мл. Метод вернёт 1000 мл вместо 1 мл. Комментарий в коде («вес, кг × мг/кг») с самим кодом не совпадает. Это расчёт объёма препарата для инфузии, так что ошибка грозит передозировкой.
Исправление: `weightGrams / 1000m * drugMgPerKg`, плюс тест с известными значениями.

## 2. `Domain/Pet.cs` + миграция `AddProcedures` — `WeightGrams` как non-nullable `int` без переноса данных; `CalculateDoseMlAsync` не проверяет вес — **high**
Колонка `WeightGrams` (`int NOT NULL`) добавляется к таблице, где уже есть питомцы. Миграция по умолчанию проставит всем существующим строкам `0`. В MR сказано, что это «вес с последнего взвешивания», но данные из истории взвешиваний миграция не переносит (правило «Схемная миграция и исторические данные»). Для любого старого питомца `CalculateDoseMlAsync` молча вернёт `0` мл, хотя должен был сообщить, что вес неизвестен.
Исправление: сделать `int? WeightGrams` (или заполнить его в миграции из источника взвешиваний), а в расчёте дозы при `null`/`<= 0` бросать понятную ошибку, а не считать.

## 3. `Services/ProcedureSheetService.cs` — `GetDaySheetAsync`: страницы считаются с 0, а по контракту с 1 — **high**
В контракте API сказано, что `page` нумеруется с 1. Код при этом делает `Skip(page * PageSize)`. Запрос `page=1` пропускает первые 30 процедур дня. Если в дне ≤ 30 процедур, лист дня приходит пустым. Первую страницу получить вообще нельзя: при `page=0` контракт нарушен, а при отрицательном значении Skip бросает исключение.
Исправление: `Skip((page - 1) * PageSize)` и проверка `page >= 1`.

## 4. `Services/ProcedureService.cs` — `RemoveConsumableAsync`: «проверил статус → удалил» без защиты от параллельной правки — **medium**
Сначала статус процедуры читается без блокировки и без concurrency token, удаление идёт позже. Если процедуру закроют между SELECT и `SaveChanges`, строка расходника удалится уже из закрытой процедуры. По README это запрещено, и отчёт по расходу за месяц исказится. Concurrency token на `Procedure` сам по себе не поможет: удаление `ConsumableLine` не делает UPDATE строки `Procedures`, поэтому токен не проверится (правила «Параллельная правка одной записи» и «FOR UPDATE и граница транзакции»).
Исправление: явная транзакция и `SELECT … FOR UPDATE` по процедуре (тот же lock должно брать и закрытие процедуры). Другой вариант — xmin-токен на `Procedure` и явная пометка процедуры изменённой в той же операции.
Попутно: чтобы удалить одну строку, загружаются все расходники процедуры, а их у инфузий сотни. Достаточно выбрать одну строку по `Id` и `ProcedureId`.

## 5. `Services/ProcedureService.cs` — `RescheduleAsync`: lost update и гонка со сменой статуса — **medium**
Concurrency token у `Procedure` нет. Если два сотрудника переносят одну процедуру одновременно, последний молча перезапишет первого. Если процедуру параллельно начинают или отменяют, проверка `Status == Scheduled` проходит по устаревшим данным, и перенос применится к уже начатой или отменённой процедуре. Устаревшее сохранение не обнаруживается и не обрабатывается.
Исправление: concurrency token (в Npgsql — `xmin`, `uint` + `IsRowVersion()`), обработка `DbUpdateConcurrencyException` (вернуть 409); либо условный `ExecuteUpdateAsync(... WHERE Id = @id AND Status = Scheduled)` с проверкой числа затронутых строк.

## 6. `Services/ProcedureService.cs` — `GetCardAsync`: полные сущности вместо проекции, недетерминированный порядок расходников — **low**
Карточка только читает данные, но тянет целиком `Pet` и все колонки `ConsumableLine`/`StaffNote` и потом маппит их в памяти (правило «Полная сущность там, где нужна часть полей»). Проекцию прямо в `ProcedureCardDto` (с `.AsSplitQuery()` из-за двух крупных коллекций) EF выполнит, выбрав только нужные столбцы. У `Consumables` нет `OrderBy`, поэтому порядок строк в карточке от запроса к запросу может меняться. Split-запросы без транзакции могут вернуть несогласованный снимок, если карточку в этот момент правят; для просмотра это допустимо, но стоит иметь в виду.

## 7. `Services/ProcedureService.cs` — `ScheduleAsync` / `CalculateDoseMlAsync` / `RescheduleAsync`: «не найдено» и неверный ввод дают 500 — **low**
`SingleAsync` на несуществующем `id` бросает `InvalidOperationException`, а несуществующий `PetId` — `DbUpdateException` (нарушение FK). Пустой или `null` `Title` не валидируется: при `null` будет NRE, при пустой строке запишется пустое название. Клиент получит 500 вместо 404/400.

## 8. `Data/ClinicDbContext.cs` — `Procedure → Pet`: каскадное удаление истории процедур — **low**
Связь required, поведение удаления не задано, значит в БД будет `ON DELETE CASCADE`. Удаление питомца сотрёт его процедуры, а через них расходники и заметки, то есть медицинскую историю и данные отчёта по расходу. Для журнала процедур разумнее `OnDelete(DeleteBehavior.Restrict)`.
