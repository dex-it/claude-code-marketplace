Нашёл 11 дефектов, которые стоит исправить до мерджа: два critical и три high. Два самых опасных позволяют обнулить баланс без явной команды и начислить себе баллы. Тот же ответ записан в `_answer.md`.

Поведение pydantic сверил с исходником `pydantic/fields.py` по тегу v1.10.13 и с документацией 1.10. Поведение `Decimal(float)` — с документацией Python. Инструмента context7 в сессии нет, поэтому использовал веб-источники. Код не запускал: сборка и тесты запрещены условиями.

1. **critical** — `app/schemas.py`, `RedeemRequest.confirm_amount`. Комментарий говорит, что `Optional[Decimal]` без значения по умолчанию — обязательное поле. В pydantic 1.10 это не так: в `_type_analysis` для `Optional` выставляется `required = False`, и поле по умолчанию равно `None`. Обязательным такое поле стало только в v2. Поэтому старый клиент, который не присылает поле, попадает в ветку «null — списываем весь баланс» и молча теряет все баллы.
2. **critical** — `app/redeem.py`, `redeem`. Сумма не проверяется на знак и ноль. При отрицательном `confirm_amount` проверка `amount > balance` проходит, и `points -= int(-X / 0.1)` начисляет баллы.
3. **high** — `POINT_VALUE = 0.1` и `Decimal(0.1)`. Из-за точного перевода float `Decimal(0.1)` равен `0.1000000000000000055511…`. Запрос на 1 ₽ списывает `int(9.99…) = 9` баллов вместо 10, а баланс в ответе приходит с «хвостом» из цифр.
4. **high** — `int()` отбрасывает дробную часть. При сумме 0.15 ₽ списывается 1 балл (0.10 ₽), а в ответе `redeemed = 0.15`: клиент получает больше, чем с него списано.
5. **high** — гонка между чтением и записью (`get_member` → вычисление в Python → абсолютный `UPDATE` в отдельной транзакции, без блокировки). Два параллельных запроса могут потратить один и тот же баланс дважды. Нужен `SELECT … FOR UPDATE` или атомарный `UPDATE … SET points = points - :d WHERE points >= :d`.
6. **medium** — `save_member` и `write_audit` выполняются в разных транзакциях. Если запись аудита упадёт, баллы уже будут списаны, а записи не останется.
7. **medium** — в аудит пишется сырой запрос `req.dict()`. При полном списании там `null`, а фактическая сумма и число баллов не записаны, так что восстановить операцию по аудиту нельзя.
8. **medium** — `valid_until` на день длиннее заявленного. Комментарий обещает «365 дней, включая сегодняшний», а код даёт `today + 365`, то есть 366 дней. Кроме того, срок нигде не сохраняется и не проверяется при списании: «срок действия баллов» из описания MR фактически не реализован.
9. **low** — комментарий про лишние поля неверен. В pydantic 1.10 по умолчанию `Extra.ignore`: поле с опечаткой молча отбрасывается, а вместе с находкой 1 опечатка в имени `confirm_amount` приводит к списанию всего баланса.
10. **low** — поле `RedeemRequest.points` обязательно, но обработчик его не использует.
11. **low** — ответ 404 приходит без `detail`, и клиент не отличит «участник не найден» от неверного маршрута.
