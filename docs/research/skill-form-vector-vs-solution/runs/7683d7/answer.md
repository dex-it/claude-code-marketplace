Я просмотрел все 8 файлов из MR и нашёл 14 дефектов, их стоит исправить до мерджа. Сборку и тесты не запускал, код не менял, как и просили. Тот же список записан в `_answer.md`.

## Critical

1. **`Controllers/PaymentWebhookController.cs`, `Handle`: копейки записываются как рубли.**
   - **Что не так:** провайдер присылает `evt.Amount` в копейках. Сумма без деления на 100 попадает в `Payment.Amount` и в `PaidAmount`. Остальной код (`Deposit`, `PaidAmount`, `RefundAsync`) считает в рублях.
   - **Почему это дефект:** `PaidAmount` получается в 100 раз больше реального. Бронь подтверждается, даже если оплачена 1/100 депозита. При отмене клиенту возвращается в 100 раз больше, чем он заплатил.
   - Валюта `evt.Currency` тоже не проверяется.

2. **`Controllers/PaymentWebhookController.cs`, `Handle`: нет идемпотентности.**
   - **Что не так:** провайдер может прислать одно событие несколько раз, но `ProviderEventId` нигде не проверяется. В `MarinaDbContext` на это поле нет уникального индекса.
   - **Почему это дефект:** каждый повтор добавляет ещё одну строку `Payment` и снова увеличивает `PaidAmount`. При отмене деньги возвращаются по нескольку раз.
   - **Как исправить:** уникальный индекс по `ProviderEventId`; на повтор отвечать 2xx без изменений.

3. **`Controllers/BookingsController.cs`, `List`: через `?vesselId=` видны чужие брони.**
   - **Что не так:** если передан `vesselId`, фильтр `OwnerId == userId` не применяется (ветка `else if`).
   - **Почему это дефект:** любой владелец, перебирая `vesselId`, получает чужие брони, включая `ContactPhone` шкипера и суммы.
   - **Как исправить:** фильтр по владельцу должен действовать всегда, кроме начальника порта; `vesselId` только дополнительно сужает выборку.

## High

4. **`Controllers/BookingsController.cs`, `Calendar`: анонимный эндпоинт отдаёт личные и финансовые данные.**
   - **Что не так:** публичный календарь без авторизации возвращает полный `BookingDto`: `VesselName`, `ContactPhone`, `Total`, `Deposit`, `PaidAmount`, `Status`, `Id`.
   - **Почему это дефект:** утечка персональных данных (телефонов) и коммерческой информации.
   - **Как исправить:** календарю достаточно отдавать занятые интервалы (`Arrival`/`Departure`). Заодно ограничить диапазон `from`/`to`: сейчас можно выгрузить всю историю.

5. **`Services/TariffCalculator.cs`, `Calculate`: неверное округление длины.**
   - **Что не так:** «каждый начатый метр» — это `Math.Ceiling`, а в коде `Math.Round(..., AwayFromZero)`. Яхта 10.3 м тарифицируется как 10 м вместо 11.
   - **Почему это дефект:** марина недополучает деньги почти на каждой яхте с дробной длиной.

6. **`Services/BookingService.cs`, `CreateAsync`: сезонные ставки не применяются.**
   - **Что не так:** место читается через `FromSql(... FOR UPDATE)` без `.Include(b => b.SeasonalRates)`, поэтому список сезонных ставок всегда пуст.
   - **Почему это дефект:** расчёт всегда идёт по базовой ставке, летние тарифы не работают.

7. **`Services/BookingService.cs`, `CancelAsync`: ошибка возврата проглатывается.**
   - **Что не так:** при `PaymentGatewayException` ошибка только логируется, а бронь всё равно становится `Cancelled` с `RefundedAmount = refund`.
   - **Почему это дефект:** в базе записано, что деньги вернули, хотя возврата не было. Повторить его через API нельзя: отмена отвечает «уже отменена».
   - **Как исправить:** либо не отменять бронь и возвращать ошибку, либо хранить состояние «возврат ожидает» с повтором. `RefundedAmount` записывать только после фактического успеха.

8. **`Services/BookingService.cs`, `CreateAsync`: неоплаченные брони держат место бессрочно.**
   - **Что не так:** брони в `AwaitingDeposit` считаются занятостью, но у них нет срока истечения и фоновой очистки.
   - **Почему это дефект:** любой владелец может бесплатно занять все места на сезон.
   - То же происходит, если `CreateDepositAsync` падает после коммита: клиент получает 500 без ссылки на оплату, а место остаётся заблокированным.

## Medium

9. **`Services/BookingService.cs`, `CreateAsync`: стыковые брони отклоняются.**
   - **Что не так:** проверка пересечения включительная (`<=` / `>=`). Заезд в день выезда предыдущей яхты считается конфликтом.
   - **Почему это дефект:** противоречит MR (выезд до 12:00, заезд с 14:00, место можно отдать в тот же день).
   - **Как исправить:** строгие `<` / `>`, как уже сделано в `Calendar`.

10. **`Services/BookingService.cs`, `CancelAsync`: перепутаны часовые пояса в правиле 48 часов.**
    - **Что не так:** 14:00 по местному времени марины сравнивается с `DateTime.UtcNow`.
    - **Почему это дефект:** для Москвы ошибка 3 часа, для других поясов в любую сторону. На границе 48 часов депозит возвращается или не возвращается неправильно.
    - **Как исправить:** переводить местное время в UTC через `Marina.TimeZoneId`.
    - В `CreateAsync` похожая проблема: «сегодня» берётся по дате UTC, а не по местной дате марины.

11. **`Services/BookingService.cs`, `CancelAsync`: деньги возвращаются до сохранения брони.**
    - **Что не так:** `RefundAsync` вызывается до `SaveChangesAsync`.
    - **Почему это дефект:** если сохранение упадёт из-за конфликта версий (`xmin` изменил параллельный вебхук), деньги уже ушли, а бронь не отменена. Повторная отмена вернёт деньги ещё раз. Конфликт версий нигде не обрабатывается, клиент получает 500.
    - **Как исправить:** сделать возврат идемпотентным (ключ — id брони или операции) и фиксировать статус до вызова провайдера.

12. **`Controllers/PaymentWebhookController.cs`, `Handle`: оплата отменённой брони молча принимается.**
    - **Что не так:** если клиент оплатил по ссылке после отмены или отмена прошла параллельно, `PaidAmount` растёт, бронь остаётся `Cancelled`.
    - **Почему это дефект:** деньги никто не возвращает. Такие платежи нужно возвращать или хотя бы помечать для разбора.

## Low

13. **`Services/BookingService.cs`, `CreateAsync`: телефон не проверяется.**
    `ContactPhone` не проверяется на пустоту и формат. Строка длиннее 32 символов (ограничение в базе) даст 500 вместо 422.

14. **`Services/BookingService.cs`, `CancelAsync`: можно отменить уже начавшуюся или прошедшую стоянку.**
    Даты не проверяются, поэтому отмена задним числом меняет историю и занятость места.
