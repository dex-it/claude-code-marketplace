# Ревью MR «Списание баллов лояльности»

До мерджа нужно исправить 10 дефектов, два из них critical: через этот эндпоинт можно накрутить себе баллы и дважды списать один и тот же баланс. Тот же текст записан в `_answer.md`.

Версии из `requirements.txt`: pydantic 1.10.13, SQLAlchemy 1.4.49, fastapi 0.95.2. Context7 в этой сессии не было, поэтому утверждения о pydantic сверял по его документации версии 1.10, а о `Decimal` — по docs.python.org.

1. **`app/redeem.py` — `redeem`, critical.** Отрицательная сумма не отклоняется. Код проверяет только `amount > balance`, поэтому при `confirm_amount=-100` строка `points -= int(-100/0.1)` **начисляет** 1000 баллов. Нужна проверка `amount > 0`, например `condecimal(gt=0)` в схеме.

2. **`app/redeem.py` и `app/repo.py` — `redeem`, `get_member`, `save_member`, critical.** Гонка при чтении и записи баланса. Баланс читается в одном соединении, а в другой транзакции записывается готовое значение `SET points = :p`. Блокировки строки (`SELECT … FOR UPDATE`) нет, условного `UPDATE … SET points = points - :n WHERE points >= :n` тоже нет. Два параллельных запроса пройдут проверку на одном балансе, и оба спишут деньги.

3. **`app/redeem.py` — `redeem`, high.** `POINT_VALUE = 0.1` задан как float. По документации Python `Decimal(0.1)` даёт точное двоичное значение `0.1000000000000000055…`, поэтому `int(amount/Decimal(0.1))` округляет вниз. Мой расчёт, без запуска: 0.30 ₽ → списывается 2 балла, то есть 0.20 ₽. Если сумма не кратна цене балла, результат тоже усекается: 0.19 ₽ → 1 балл. Нужно `Decimal("0.1")` плюс либо проверка кратности, либо округление вверх. Возможную ошибку округления при полном списании не проверял.

4. **`app/schemas.py` — `RedeemRequest.confirm_amount`, high.** Комментарий неверен. По документации pydantic 1.10 поле `Optional[X]` без значения по умолчанию необязательно и по умолчанию равно `None`; обязательным его делает только `= ...`. Значит, старый клиент не получит 422, а спишет **весь баланс**. Исправление: `confirm_amount: Optional[Decimal] = ...`.

5. **`app/schemas.py` — `RedeemRequest`, medium.** Комментарий про лишние поля неверен. В pydantic 1.10 `extra` по умолчанию равен `Extra.ignore`, так что лишние поля молча отбрасываются. Если клиент опечатается в `confirm_amount`, поле станет `None`, и вместе с п. 4 это приведёт к полному списанию. Нужно `Config.extra = Extra.forbid`.

6. **`repo.py` — `save_member` и `write_audit`, high.** Списание и запись аудита идут в разных транзакциях. Если запись аудита упадёт, баллы уже будут списаны, а следа операции не останется. Нужна одна транзакция на обе операции.

7. **`redeem.py` — `redeem`, medium.** В аудит пишется `req.dict()`, а не фактическая операция. При полном списании там `confirm_amount: null`, и сколько реально списано денег и баллов, не видно. Нужно записывать сумму, число баллов и остаток.

8. **`redeem.py` — `redeem`, medium.** Срок действия посчитан с ошибкой на один день и нигде не хранится.
   - Комментарий обещает «365 дней включая сегодняшний», а `today + 365` даёт 366 дней.
   - Дата последнего списания не сохраняется, а истечение баллов нигде не проверяется. Заявленная в MR функция «срок действия баллов» фактически не реализована, клиент получает ложную дату.
   - `date.today()` берёт часовой пояс сервера.

9. **`schemas.py` — `RedeemRequest.points`, low.** Поле обязательное, но код его не использует. Оно может противоречить сумме и вводит в заблуждение в аудите.

10. **`redeem.py` — `redeem`, low.** Ответ 404 возвращается без `detail`, и клиент не отличит его от несуществующего маршрута.

**Что сверено по документации:**
- **Комментарии в `schemas.py` (п. 4 и 5):** оба опровергнуты документацией pydantic 1.10.
- **Поведение `Decimal(float)` (п. 3):** подтверждено документацией Python. Пример «0.30 ₽ → 2 балла» посчитан вручную, без запуска.
- **Комментарий про 365 дней (п. 8):** опровергнут арифметикой `timedelta`.
