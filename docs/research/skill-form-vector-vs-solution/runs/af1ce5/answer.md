# Ревью MR «Списание баллов лояльности»

Мерджить нельзя: нашёл 9 дефектов, из них 3 critical. Версии из `requirements.txt`: fastapi 0.95.2, pydantic 1.10.13, SQLAlchemy 1.4.49. Этот же ответ записан в `_answer.md`.

## Находки

**1. `app/schemas.py` — `RedeemRequest.confirm_amount`: поле не обязательное, без него списывается весь баланс — critical**
- **Что не так:** комментарий в коде утверждает, что `Optional[Decimal]` без значения по умолчанию делает поле обязательным. В pydantic 1.10 это не так: такое поле необязательное и по умолчанию равно `None`. Обязательным оно становится только с `= ...` или `Field(...)`.
- **Почему дефект:** старый клиент не получит 422. У него будет `confirm_amount=None`, а `redeem` понимает `None` как «списать весь баланс» и молча его обнулит.
- **Сверено** с документацией pydantic 1.10, раздел «Required Optional fields». Комментарий описывает поведение pydantic v2, а в проекте закреплена v1.

**2. `app/schemas.py` — `RedeemRequest`: лишние поля не отвергаются — critical (вместе с №1)**
- **Что не так:** в pydantic 1.10 по умолчанию стоит `Extra.ignore`, то есть лишние поля молча отбрасываются. Комментарий утверждает обратное.
- **Почему дефект:** если клиент опечатается (например, пришлёт `confirm_amont`), поле проигнорируется, `confirm_amount` станет `None`, и спишется весь баланс.
- **Как исправить:** `extra = Extra.forbid` плюс явная обязательность поля из №1.
- **Сверено** с документацией pydantic 1.10, Model Config → `extra`.

**3. `app/redeem.py` — `redeem`: отрицательная сумма начисляет баллы — critical**
- **Что не так:** `confirm_amount` никак не ограничен. При `-1000` проверка `amount > balance` проходит, а `points -= int(-1000/0.1)` добавляет 10000 баллов.
- **Почему дефект:** через эндпоинт списания можно бесконечно начислять себе баллы. Сумма 0 тоже проходит и оставляет пустую запись в аудите.
- **Как исправить:** `condecimal(gt=0)` или явная проверка.

**4. `app/redeem.py` — `redeem` и `app/repo.py`: гонка и неатомарность — high**
- **Что не так:** чтение, запись баланса (`save_member` пишет абсолютное значение) и запись аудита идут в трёх отдельных транзакциях.
- **Почему дефект:**
  - параллельные запросы читают один и тот же баланс, оба проходят проверку, и списывается больше, чем было;
  - одно из обновлений при этом теряется;
  - если упадёт `write_audit`, баллы уже списаны, а записи аудита нет.
- **Как исправить:** одна транзакция с `SELECT … FOR UPDATE` или атомарный `UPDATE … SET points = points - :n WHERE points >= :n` с проверкой `rowcount`; аудит в той же транзакции.

**5. `app/redeem.py` — `POINT_VALUE = 0.1` / `redeem`: деньги считаются через float — high**
- **Что не так:** `Decimal(0.1)` строится из float и получается `0.1000000000000000055…` (документация Python показывает это на примере `Decimal(float('1.1'))`).
- **Почему дефект:** для `amount = 1` деление даёт `9.9999…`, `int()` отбрасывает дробь, и списывается 9 баллов вместо 10, хотя в ответе `redeemed=1`.
- **При полном списании** обратное деление тоже может не совпасть с `points`. Это вывод из арифметики, пробой не проверял.
- **Как исправить:** `Decimal("0.1")`, а лучше считать в целых баллах.

**6. `app/redeem.py` — `redeem`: сумма, не кратная стоимости балла — medium**
- **Что не так:** при `0.15` списывается 1 балл (0.10 ₽), а в ответе `redeemed=0.15`.
- **Почему дефект:** ответ и аудит расходятся с тем, что реально списано.
- **Как исправить:** отвергать такую сумму или явно округлять и возвращать фактически списанное.

**7. `app/redeem.py` — `redeem`, `valid_until`: срок на день длиннее и нигде не сохраняется — medium**
- **Что не так:** по комментарию срок «365 дней включая сегодняшний», но `today + 365` при таком счёте даёт 366 дней.
- **Почему дефект:** кроме ошибки на день, срок только возвращается в ответе и не сохраняется ни в БД, ни в аудите. Заявленная в MR функция «срок действия баллов» фактически не работает.
- **Дополнительно:** `date.today()` берёт локальную дату сервера, и около полуночи результат зависит от таймзоны хоста.

**8. `app/schemas.py` — `RedeemRequest.points`: обязательное поле, которое не используется — medium**
- **Что не так:** клиент обязан прислать `points`, но `redeem` его игнорирует и считает списание по `confirm_amount`.
- **Почему дефект:** контракт вводит в заблуждение: клиент, приславший `points: 10`, ждёт списания 10 баллов.
- **Как исправить:** удалить поле или считать списание по нему, сверяя с `confirm_amount`.

**9. `app/redeem.py` — `redeem`, вызов `write_audit(..., req.dict())`: аудит не фиксирует саму операцию — low**
- **Что не так:** пишется только сырой запрос. Фактически списанные баллы и сумма, баланс до и после и время не сохраняются. При `confirm_amount=None` в аудите нет даже суммы.
- **Почему дефект:** по такому аудиту нельзя восстановить, что произошло, особенно с учётом расхождений из №5 и №6.

## Итог
- №1–3 позволяют обычным запросом обнулить баланс участника или неограниченно его пополнить.
- №4–5 дают неверное списание при параллельных запросах и на обычных суммах.
