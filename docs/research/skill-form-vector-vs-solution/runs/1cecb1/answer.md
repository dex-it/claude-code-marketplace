## Critical

**1. Повторный запрос создаёт второй счёт в 1С.** `Services/GroupOrderService.cs`, `CreateAsync`
- **Что не так:** ключ идемпотентности проверяется один раз, до блокировки и до вызова шины. Фронт повторяет запрос через 5 с, а шина отвечает 5–10 с, поэтому повтор ключ ещё не видит. Он ждёт на `FOR UPDATE`, затем без перепроверки ключа снова вызывает `CreateInvoiceAsync`, и только после этого падает на уникальном индексе.
- **Почему это дефект:** каждый вызов создаёт в 1С новый счёт, а аннулировать его можно только вручную. Организация получает два счёта на одну покупку. Если клиент оборвал соединение и отменился `ct`, счёт в 1С остаётся, а заказа в базе нет.
- **Исправление:** сначала занять ключ, то есть закоммитить заказ без номера счёта, потом вызывать шину. Как минимум, перепроверять ключ после блокировки.

**3. Места групповых заказов не резервируются, будет овербукинг.** `Services/CapacityService.cs`, `FreeSeatsAsync`
- **Что не так:** свободные места считаются только по регистрациям, `GroupOrder.Quantity` не учитывается.
- **Почему это дефект:** пока в заказ никого не вписали, эти места продаются ещё раз. По MR места под заказ должны резервироваться сразу.

**8. НДС начисляется сверху на цены, которые уже с НДС.** `Services/InvoiceBuilder.cs`, `ForGroupOrder`
- **Что не так:** считается `Total = amount + 20 %`, хотя цены на сайте указаны с НДС. Завышенная сумма попадает и в `GroupOrder.AmountKopecks`.
- **Почему это дефект:** организации переплачивают 20 %.
- **Исправление:** выделять НДС из суммы, `amount * 20 / 120`.

## High

**2. Вызов шины выполняется под блокировкой конференции.** `GroupOrderService.CreateAsync`
- Пока шина отвечает (5–10 с, таймаут клиента 30 с), строка конференции заблокирована через `FOR UPDATE`. Все регистрации на конференцию в это время стоят.

**4. Нельзя вписать замену после отмены сотрудника.** `GroupOrderService.AddParticipantAsync`
- `Participants.Count` учитывает и отменённые регистрации, поэтому описанный в MR сценарий замены получает ответ 409.

**6. Лимит использований промокода не работает.** `RegistrationService.RegisterAsync` и `PricingService.FindPromoAsync`
- Промокод загружается через `AsNoTracking`, поэтому `UsedCount++` в базу не записывается.
- Проверка лимита идёт вне транзакции, так что параллельные регистрации превысят лимит, даже когда инкремент починят. Нужен атомарный `UPDATE … WHERE "UsedCount" < "UsageLimit"`.

**7. Промокод суммируется с ранним тарифом.** `PricingService.Quote`
- По договорам с партнёрами скидка считается от полной цены и с ранним тарифом не суммируется. Код применяет её к ранней цене, и участник получает обе скидки.

**9. Паспортные данные видны не только визовой группе.** `ParticipantsController.List` и `ParticipantDto.Projection`
- Номер и страна паспорта уходят администраторам организаций и всему оргкомитету. По MR их должна видеть только визовая группа, на это есть отдельное согласие на обработку. Это утечка персональных данных.

**10. Отчёт не работает.** `ReportsController.Registrations`
- Границы периода передаются как `DateTime` с `Kind=Unspecified`, а `CreatedAt` хранится как `timestamptz`. Npgsql 8 на таком параметре бросает исключение, поэтому отчёт всегда отвечает 500.
- Даже после исправления дни будут считаться по UTC, а не по Москве.

## Medium

**5. Гонка при добавлении участников.** `GroupOrderService.AddParticipantAsync`
- Проверка заполненности и вставка идут без блокировки, поэтому параллельные запросы переполнят заказ сверх оплаченного.

**11. Клиент шины не настроен.** `Program.cs`, `AddHttpClient<IBillingClient, BillingBusClient>`
- Нет `BaseAddress` и API-ключа, а `BillingOptions` нигде не используются. Запрос на относительный адрес `"invoices"` упадёт.
- Если клиент настраивается где-то вне этого MR, находку можно снять.

**13. Неверное число занятых мест в ответе.** `GroupOrdersController.ToDto`
