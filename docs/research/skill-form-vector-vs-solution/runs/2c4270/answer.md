**Решения:**
- **Миграция.** Колонка `greenhouse_id` добавляется пустой, заполняется «Теплицей №1» и только потом становится обязательной, поэтому обычный pipeline её выкатит. Площадь «Теплицы №1» нам неизвестна, поэтому площадь в базе может быть пустой; для новых теплиц сервис её требует. Площадь «Теплицы №1» нужно будет внести вручную.
- **Время приёма пакета.** `taken_at` хранится в местном времени площадки, поэтому момент приёма переводится в часовой пояс из настройки `Monitoring:SiteTimeZone` (например `Europe/Moscow`). Её нужно добавить в конфиг и зарегистрировать через `services.Configure<MonitoringOptions>(...)`. Пока настройки нет, пакеты без времени по-прежнему отклоняются, но с понятной ошибкой.
- **Фильтр по метке.** Введённый фрагмент передаётся в запрос как параметр, символы `%` и `_` в нём ищутся буквально. Для правильного сравнения кириллицы без учёта регистра используется ICU-сортировка `und-x-icu`, PostgreSQL должен быть собран с ICU. Сортировку отчёта я перенёс из SQL в LINQ: после добавления второго соединения таблиц порядок строк из SQL больше не гарантировался.

**Нужно учесть перед выкаткой:**
- **Окно между миграцией и выкаткой.** Пока старая версия приложения ещё работает после миграции, регистрация нового датчика будет падать из-за обязательной колонки. Не регистрируйте датчики в это время.
- **Вызывающий код.** У `RegisterSensorAsync` появился обязательный параметр теплицы, а у конструктора сервиса — параметр настроек. Контроллеров и `Program.cs` в каталоге нет, поэтому вызовы и регистрацию настроек нужно поправить там.
- **Служебные файлы EF.** В репозитории нет `*.Designer.cs` и `ModelSnapshot` — их нет и у начальной миграции. Атрибуты `[DbContext]` и `[Migration]` я прописал прямо в файле миграции, чтобы она попала в bundle. Снапшот модели стоит перегенерировать, иначе следующий `migrations add` построит неверную разницу.
