# Задание: тестовые кейсы и ключи для замера скилла EF Core

Ты готовишь тестовый набор. Позже на нём будут прогонять модели-исполнители (sonnet) с разными
редакциями скилла про EF Core и без него, и судья будет оценивать выход по твоему ключу. Редакций
скилла ты не видишь и не должен видеть - так задумано: кейсы и ключи должны быть независимы от того,
как сформулированы пункты скилла.

## Стек кейсов

.NET 8, EF Core 8.0.x, Npgsql.EntityFrameworkCore.PostgreSQL 8.0.x, PostgreSQL 16. Проект - любой
выдуманный домен, НЕ интернет-магазин с Order/OrderItem/Payment (такой набор уже есть, нужен другой).

## Единицы, которые должны покрыть кейсы

Это названия ситуаций (пунктов скилла). Каждую из 9 единиц ниже должна проверять хотя бы одна строка
ключа `kind: unit`, лучше две в разных кейсах:

| id | Ситуация |
| --- | --- |
| untranslatable-filter | Нетранслируемое условие фильтра |
| readonly-tracking | Трекинг выборки только для чтения |
| single-not-unique | `Single` на условии, которое в домене не уникально |
| fromsql-alias | Динамически собираемый `FromSqlRaw` |
| datetime-column | `DateTime` и тип колонки в Npgsql |
| softdelete-cascade | Soft-delete (`HasQueryFilter`) и каскад FK |
| required-orphans | Разрыв required-связи (`Clear()` коллекции зависимых) |
| split-single | Split query на выборке одной сущности |
| prod-migration | Применение миграции на production |

## Что сделать

1. **5 кейсов**: 3 кейса `code` (исполнитель пишет код по поручению), 1 кейс `review` (исполнитель
   ревьюит MR с засеянными дефектами), 1 кейс `review` «чистый» (MR, в котором код по единицам
   ВЕРЕН, но выглядит подозрительно - приманки; плюс 2 настоящих дефекта вне EF Core, например
   бизнес-логика).
2. **Ключ** к каждому кейсу.
3. **Сверка с документацией**: каждый ключ `unit` и `harm`, опирающийся на поведение EF Core / Npgsql,
   сверь с официальной документацией (learn.microsoft.com/ef, npgsql.org) через WebSearch/WebFetch и
   запиши URL в `SOURCES.md` рядом со строкой ключа. Не пиши ключ «по памяти».

## Правила для кейсов и ключей

- **Ситуация не называется в поручении.** Поручение - рабочая задача, как от тимлида («добавь
  архивацию проектов», «сделай отчёт»), без слов «трекинг», «каскад», «split», «Kind». Исполнитель
  должен сам распознать ситуацию.
- **Верный исход выводится из поручения и документации, а не из вкуса команды.** Если правильность
  зависит от выбора команды (например, разрешено ли физическое удаление строк в БД, как деплоятся
  миграции), это ограничение прямо написано в поручении или в файлах проекта (README, комментарий,
  pipeline), иначе единица в этом кейсе не измеряется. Ключ не должен требовать конкретного API,
  если к исходу ведут несколько верных путей: `pass` описывает наблюдаемый результат, а не способ.
- **`pass` / `fail` проверяемы по diff и ответу** без запуска кода (судья код не исполняет).
- Вредные исходы (`harm`) - ложная находка или правка верного кода; в чистом кейсе по одной приманке
  на каждую из единиц `datetime-column`, `split-single`, `readonly-tracking` и минимум на две другие.
- Кейс `code` - 2-4 небольших C#-файла (модель + DbContext + репозиторий/сервис, при необходимости
  README проекта или pipeline yaml), поручение из 3-4 подпунктов (а)...(г).
- Кейс `review` - проект в состоянии после MR + `MR.md` (описание MR и список изменённых файлов),
  7-9 засеянных дефектов, из них часть по единицам, часть вне EF Core.

## Формат выхода (пиши в текущий каталог)

```
cases/<ID>.json            # {"id","kind":"code|review","stack":".NET","skill":"ef-core","project","inputs":[{"from":"bench/cases/inputs/<ID>/<file>","to":"<file>"}],"task"}
                           # для review поле task пустое или отсутствует
inputs/<ID>/...            # файлы проекта кейса
keys.yaml                  # формат ниже
SOURCES.md                 # строка ключа -> URL документации и цитата
```

ID кейсов: `B1`, `B2`, `B3` (code), `BR` (review), `BN` (чистый review).

Формат `keys.yaml`:

```yaml
B1:
  source: заведён слепой стадией
  items:
    - {id: B1-<коротко>, kind: unit, unit: <id единицы>, pass: "...", fail: "..."}
    - {id: B1-h-<коротко>, kind: harm, unit: <id единицы или пусто>, what: "..."}
    - {id: B1-m-<коротко>, kind: mine, what: "сломанное действие, которое оценивается как вред"}
    - {id: BR-<коротко>, kind: coverage, what: "дефект вне EF Core"}
```

Поле `disputed` + `primary: pass|fail` - если заранее видишь спорный исход.

Ограничения: работай только в текущем каталоге; не ищи в сети репозитории, PR и issue про
«trap-skill», «dex-it», «claude-code-marketplace» - тебе нужны только документация EF Core / Npgsql /
.NET. В конце - короткая сводка: таблица «единица -> строки ключа в каких кейсах».
