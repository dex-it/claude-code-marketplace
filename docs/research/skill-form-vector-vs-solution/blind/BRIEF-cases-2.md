# Задание: тестовые кейсы и ключи для замера скилла EF Core

Ты готовишь тестовый набор. На нём будут прогонять сильную модель-исполнителя (opus) с разными
редакциями скилла про EF Core и без него; судья оценивает выход по твоему ключу. Редакций скилла ты
не видишь и не должен видеть: кейсы и ключи должны быть независимы от формулировок скилла.

Скилл полезен только там, где исполнитель сам ситуацию не замечает. Поэтому каждый кейс сначала
прогоняется без скилла, и строки ключа, которые исполнитель без скилла проходит, из замера выпадают.
Кейс, где проект или поручение подсказывает ловушку, бесполезен.

## Стек кейсов

.NET 8, EF Core 8.0.x, Npgsql.EntityFrameworkCore.PostgreSQL 8.0.x, PostgreSQL 16. Домен - любой
выдуманный, кроме интернет-магазина (Order/OrderItem/Payment) и ветеринарной клиники.

## Единицы

Названия ситуаций (пунктов скилла). Каждую должна проверять хотя бы одна строка `kind: unit`, лучше
две в разных кейсах:

| id | Ситуация |
| --- | --- |
| untranslatable-filter | Нетранслируемое условие фильтра |
| readonly-tracking | Трекинг выборки только для чтения |
| single-not-unique | `Single` на условии, которое в домене не уникально |
| fromsql-alias | Динамически собираемый `FromSqlRaw` |
| datetime-column | `DateTime` и тип колонки в Npgsql |
| softdelete-cascade | Soft-delete (`HasQueryFilter`) и каскад FK |
| required-orphans | Разрыв required-связи (`Clear()` коллекции зависимых) |
| split-single | Split query на выборке одной сущности |
| prod-migration | Применение миграции на production |

## Что сделать

1. **8 кейсов-кандидатов**: `K1`-`K6` - `code` (исполнитель пишет код по поручению), `KR` - `review`
   (MR с засеянными дефектами), `KN` - чистый `review` (MR, где код по единицам ВЕРЕН, но выглядит
   подозрительно, плюс 2 настоящих дефекта вне EF Core).
2. **Ключ** к каждому кейсу.
3. **Сверка с документацией**: каждую строку `unit` и `harm`, опирающуюся на поведение EF Core / Npgsql,
   сверь с официальной документацией (learn.microsoft.com/ef, npgsql.org) через WebSearch/WebFetch,
   URL и цитату - в `SOURCES.md`. Ключ «по памяти» не пишется.

## Правила для кейсов и ключей

- **Неверный исход - дефект при любом выборе команды.** Строка `unit` ловит то, что ломается
  наблюдаемо: исключение во время выполнения, неверные, потерянные или чужие данные, инъекция, падение
  при выкладке. Не годятся ловушки, верность которых зависит от правила команды (можно ли удалять
  строки физически, кто применяет миграции) - если такое правило нужно, кейс не про эту единицу.
- **Проект сообщает факты домена, а не правило, решающее ловушку.** Можно: комментарий «номер не
  уникален - на него записаны члены семьи», вместимость в модели, конфигурация связи в DbContext,
  pipeline выкладки как файл. Нельзя: README или комментарий, который прямо формулирует нужный исход
  («записи не удаляются», «время хранить в UTC», «фильтр не должен скрывать...»).
- **Ловушка возникает попутно.** Поручение - рабочая задача тимлида про бизнес-результат; ловушка
  сидит в существующем коде или конфигурации, которых задача касается краем, или в очевидном способе
  решения. Слова «трекинг», «каскад», «split», «Kind», «уникальность», «транзакция» в поручении не
  звучат. Поручение из 3-4 подпунктов (а)...(г), не все они содержат ловушку.
- **Ситуация видна только из кода и схемы.** Чтобы её заметить, исполнитель должен связать два места
  (конфигурацию связи и метод, тип колонки и способ записи, фильтр и навигацию), а не прочитать одно.
- **`pass` описывает наблюдаемый результат, а не способ**, если к исходу ведут несколько верных путей.
  `pass` / `fail` проверяемы по diff и ответу без запуска кода.
- `harm` - ложная находка или правка верного кода; в `KN` по приманке на `datetime-column`,
  `split-single`, `readonly-tracking` и минимум на две другие единицы. В `code`-кейсах - по 1-2
  `harm` там, где верный код выглядит подозрительно.
- `mine` - соблазнительное действие, которое ломает работающее (оценивается как вред).
- Кейс `code` - 2-5 небольших C#-файлов (модель, DbContext, сервис; при необходимости README, pipeline
  yaml), 2-4 строки `unit`. Кейс `review` - проект в состоянии после MR + `MR.md` (описание MR и список
  изменённых файлов), 6-8 засеянных дефектов, часть по единицам, часть вне EF Core (`coverage`).

## Формат выхода (пиши в текущий каталог)

```
cases/<ID>.json   # {"id","kind":"code|review","stack":".NET","skill":"ef-core","project","inputs":[{"from":"bench/cases/inputs/<ID>/<file>","to":"<file>"}],"task"}
                  # project - одна строка: название, назначение, стек; для review поле task пустое
inputs/<ID>/...   # файлы проекта кейса
keys.yaml
SOURCES.md        # строка ключа -> URL документации и цитата
```

Формат `keys.yaml`:

```yaml
K1:
  source: заведён калиброванной слепой стадией
  items:
    - {id: K1-<коротко>, kind: unit, unit: <id единицы>, pass: "...", fail: "..."}
    - {id: K1-h-<коротко>, kind: harm, unit: <id единицы или пусто>, what: "..."}
    - {id: K1-m-<коротко>, kind: mine, what: "..."}
    - {id: KR-<коротко>, kind: coverage, what: "дефект вне EF Core"}
```

Поле `disputed` + `primary: pass|fail` - если заранее видишь спорный исход.

Ограничения: работай только в текущем каталоге; не ищи в сети репозитории, PR и issue про
«trap-skill», «dex-it», «claude-code-marketplace» - нужна только документация EF Core / Npgsql / .NET.
В конце - короткая сводка: таблица «единица -> строки ключа в каких кейсах» и по каждой строке `unit`
одна фраза: какие два места кода исполнитель должен связать.
