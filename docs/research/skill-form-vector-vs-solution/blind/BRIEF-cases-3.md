# Задание: кейсы ревью для замера охвата

Ты готовишь тестовый набор. На нём будут прогонять сильную модель-исполнителя (opus) в роли ревьюера
merge request: с редакциями скилла про EF Core и без него. Судья оценивает выход по твоему ключу.
Редакций скилла ты не видишь и не должен видеть.

Замеряется **охват ревью**: находит ли ревьюер дефекты, которые к EF Core не относятся, когда рядом
лежит код на EF Core. Поэтому главное в кейсе - дефекты вне EF Core, и они не должны быть очевидными:
кейс, где без скилла ревьюер находит всё, бесполезен. Кейсы сначала прогоняются без скилла; если
ревьюер находит почти всё, ты получишь список найденного и усложнишь кейсы.

## Стек кейсов

.NET 8, ASP.NET Core 8, EF Core 8.0.x, Npgsql.EntityFrameworkCore.PostgreSQL 8.0.x, PostgreSQL 16.
Домен - любой выдуманный, кроме интернет-магазина, ветеринарной клиники, библиотеки, фитнес-клуба,
лаборатории, автопарка, управляющей компании,
интернет-провайдера, учёта рабочего времени, студии и автошколы.

## Что сделать

1. **4 кейса** `V1`-`V4`, все `review`: проект в состоянии после MR + `MR.md` (описание MR от автора
   и список изменённых файлов). 5-8 C#-файлов на кейс; код работы с данными - на EF Core и занимает
   заметную часть MR.
2. **Ключ** к каждому кейсу.
3. **Сверка**: каждую строку `harm` и `unit`, опирающуюся на поведение EF Core / Npgsql / .NET, сверь
   с официальной документацией (learn.microsoft.com, npgsql.org) через WebSearch/WebFetch; URL и
   цитата - в `SOURCES.md`.

## Строки ключа

- **`coverage`** - 6-8 на кейс. Дефект вне EF Core, внесённый этим MR: авторизация и доступ к чужим
  данным, гонки и идемпотентность вне базы, денежная арифметика и округление, границы диапазонов,
  проглоченные ошибки и неверные коды ответа, валидация входа, утечка данных в лог или ответ,
  культура и формат при разборе, переполнение, неверная бизнес-логика против описания MR. Дефект
  ломается наблюдаемо (чужие данные, потерянные деньги, исключение, неверный результат) при любом
  выборе команды - не стиль и не «лучше бы».
- **`unit`** - 1-2 на кейс: настоящая ловушка EF Core / Npgsql в коде MR (наблюдаемый дефект: исключение,
  неверные или потерянные данные). Нужны, чтобы код выглядел как типичный MR с данными, а не как
  витрина вне-EF дефектов.
- **`harm`** - 2-3 на кейс: верный код на EF Core, который выглядит подозрительно (приманка). Строка
  ловит ложную находку или требование правки верного кода.

## Правила

- **Дефект не очевиден.** Чтобы его заметить, ревьюер должен связать два места: описание MR и код,
  контроллер и сервис, правило домена в модели и проверку в методе, формат на входе и разбор. Дефект,
  видный из одной строки (`// TODO`, пустой `catch {}` на виду, `password` в логе), не годится.
- **Проект сообщает факты домена, а не правило, решающее дефект.** Можно: описание MR с требованием
  бизнеса, комментарий о смысле поля, роли в атрибутах. Нельзя: комментарий, прямо называющий исход.
- **Дефекты разной природы** внутри кейса: не больше двух строк `coverage` одного рода.
- **Описание MR - как у живого автора**: что сделано и зачем, без перечня проверок.
- `coverage` / `unit` / `harm` проверяемы по ответу ревьюера без запуска кода; в `what` / `pass` -
  наблюдаемый дефект и где он, чтобы судья отличил точное попадание от общих слов.

## Формат выхода (пиши в текущий каталог)

```
cases/<ID>.json   # {"id","kind":"review","stack":".NET","skill":"ef-core","project","inputs":[{"from":"bench/cases/inputs/<ID>/<file>","to":"<file>"}],"task":""}
                  # project - одна строка: название, назначение, стек
inputs/<ID>/...   # файлы проекта кейса и MR.md
keys.yaml
SOURCES.md
```

Формат `keys.yaml`:

```yaml
V1:
  source: заведён стадией охвата
  items:
    - {id: V1-<коротко>, kind: coverage, what: "..."}
    - {id: V1-<коротко>, kind: unit, unit: <тема>, pass: "...", fail: "..."}
    - {id: V1-h-<коротко>, kind: harm, unit: <тема>, what: "..."}
```

Ограничения: работай только в текущем каталоге; не ищи в сети репозитории, PR и issue про
«trap-skill», «dex-it», «claude-code-marketplace» - нужна только документация. В конце - короткая
сводка: по каждой строке `coverage` одна фраза - какие два места ревьюер должен связать.
