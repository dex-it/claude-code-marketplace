## Вопрос

Держит ли качество trap-skill, если пункт задаёт вектор (название ситуации), а не решение
(триада «Плохо / Правильно / Почему» с готовым ответом)? Если держит, то для каких ловушек и на каком
тире модели?

## Гипотезы

- **H1 (Макс).** Форма F1 (название) даёт применение не ниже формы F5 (триада с готовым ответом).
- **H2.** F5 даёт больше вреда, чем F1: ложные находки на приманках, неверный готовый ответ,
  сломанные мины, сужение охвата ревью.
- **H3.** Эффект формы зависит от класса ловушки: в классе A F1 не хуже F5; в классах B и C F1
  хуже F5, и нужный шаг лестницы - 2 или 3 («Форма пункта»).
- **H4.** Эффект зависит от тира (sonnet против opus) и от предписания искать документацию.
  Ожидание по Anthropic («What works perfectly for Opus might need more detail for Haiku»): на
  opus разрыв F1 и F5 меньше, чем на sonnet; с предписанием поиска разрыв в классе B меньше.

H3 и H4 - вторичные. Решения по ним описательные, мощность мала.

## Классы ловушек

Класс единицы назначается до прогонов по признаку. Признаки проверяются по порядку, первый
сработавший задаёт класс:

1. **D - неверный готовый ответ.** «Правильно» старой ловушки противоречит документации версии
   или контексту кейса.
2. **C - конвенция команды.** Верный исход не выводится из документации: это выбор команды, и
   противоположный выбор тоже работает.
3. **B - пробел знания.** Верный исход зависит от поведения или дефолта библиотеки версии, в
   котором сильная модель ошибается (есть провал прошлого прогона или сверенный первоисточником
   факт, противоречащий распространённому мнению).
4. **A - пробел узнавания.** Исход выводится из общего знания, провал - ситуация не замечена.

| Класс | Единица (кейс, ключ) | Признак |
| --- | --- | --- |
| A | `untranslatable-filter` (E1-filter) | правило известно, E1 заход 1 - 1/2 |
| A | `readonly-tracking` (E1-tracking) | то же |
| A | `softdelete-cascade` (E4-cascade) | «каскад в БД не заподозрил» при прочитанной документации (E4-d1) |
| A | `fromsql-alias` (R-D3) | в коде E5 база 2/2, в ревью R 0/2 |
| A | `count-any` (MRA-A4) | база 1/2 |
| A | `dedup-batch` (L5-dedup) | база 3/4, на ef-core без пункта 0/2 |
| B | `datetime-column` (E3-kind, E4-ts) | Npgsql 6: `timestamptz` по умолчанию, `Kind=Utc` в `timestamp` бросает |
| B | `required-orphans` (E4-clear) | `Restrict` / `ClientSetNull` при разрыве required-связи бросают |
| B | `latest-vs-version` (FVB-KB1) | pydantic 1.10 против 2 |
| B | `fact-on-faith` (FVB-KB2) | дефолт `extra` в pydantic |
| C | `prod-migration` (E6-prod) | script, bundle или `update` - выбор процесса команды |
| C | `keyed-literal` (K1-key) | литерал работает, требование «одна константа» - конвенция |
| C | `staging-gt-prod` (CFG-K9) | соотношение сред - выбор команды |
| C | `default-duplicated` (CFG-K8) | то же |
| D | `single-not-unique` (E2-single) | 2.6.2 «Правильно»: `FirstOrDefault` - молчаливый выбор склада |
| D | `split-single` (R-h-B1, N0-h-split) | 2.6.2 «без AsSplitQuery для single entity» - неверно для двух коллекций |
| D | `contains-list` (L5-h-chunk) | linq 2.3.1 «Contains с огромным списком» - неверно для EF 8 + Npgsql |
| D | `nonnullable-required` (CFG-h-required) | config 1.3.1: `required` к валидации опций отношения не имеет |

Итого единиц-в-кейсе: A - 6, B - 5, C - 4, D - 5.

## Условия

- **Тир.** sonnet (`claude-sonnet-5`, `--effort high` - дефолт API) - основной. opus
  (`claude-opus-5-5`, `--effort medium` - дефолт API) - репликация. haiku (`claude-haiku-4-5`) - только
  по решению пользователя.
- **Поиск.** Основная ячейка: WebSearch и WebFetch доступны, в задании не предписаны.
  Модификатор: строка «Поведение и дефолты библиотек ... сверь с документацией версии из манифеста
  проекта (WebSearch/WebFetch)».
- **Подача.** Основная ячейка: путь к `SKILL.md` в задании (как все прошлые прогоны).
  Модификатор: плагин через `--plugin-dir`, скилл вызывается Skill tool по `description`.
- **Изоляция.** `claude -p --restricted --strict-mcp-config`, инструменты Read, Write, Edit, Glob,
  Grep, WebSearch, WebFetch (+ Skill в подаче плагином). Сборка запрещена заданием, Bash недоступен.
  Вне подачи плагином - `--disable-slash-commands`. Каждый прогон - свой каталог
  `~/.cache/research/runs/<id>` с `git init`; `init`-событие каждого прогона пишется в `meta.json`,
  прогон с посторонним скиллом или плагином в init исключается и перезапускается.

## Метрики

На прогон и строку ключа (`bench/keys.yaml`):

- **применение** (первичная) - строки `unit`: pass / fail / disputed. Для класса D применение - pass
  по `unit` или отсутствие вреда по строке `harm` класса D;
- **вред** - доля прогонов хотя бы с одним событием `harm` или `mine`; отдельно по видам;
- **охват** - доля найденных строк `coverage` (дефекты вне скилла);
- **recall скилла** - доля найденных строк `skill`;
- **стоимость** - токены (input, cache read, cache write, output), `total_cost_usd`, длительность,
  число ходов, вызовы инструментов по именам, вызовы WebSearch/WebFetch.

`disputed` в основном анализе считается по полю `primary` ключа, в анализе чувствительности -
наоборот.

## Оценка

1. Прогон пишет `answer.md`, `diff.patch`, `meta.json` в `runs/<id>/`. id случайный, план «id ->
   условие» лежит в `~/.cache/research/sealed/` и в репозиторий попадает после оценки стадии.
2. E4 - исполнением: стенд `tests/trap-skills/dotnet-ef-core/inputs/e4-harness/`, Postgres 16 в
   docker. Код прогона не правится; не собирается - все три `unit` E4 fail, сборка пишется отдельной
   колонкой.
3. Остальное - судьёй: `claude -p` (opus, effort high) получает ключ кейса, `diff.patch` и
   `answer.md`, в которых строки со словами `SKILL.md` и именем скилла заменены на `[скрыто]`.
   Условие судье не видно. Выход - JSON по строкам ключа с цитатой-основанием.
4. Ручная перепроверка: случайные 20% оценок судьи + все `disputed` + все расхождения цитаты с
   исходом. Согласие судьи с ручной оценкой - число в отчёте. Меньше 90% - судья исправляется, и
   стадия переоценивается целиком.
5. Таблица оценок - `results/results.csv`, строка на пару «прогон x строка ключа». Анализ -
   `results/analyze.mjs`, все числа отчёта строятся им из csv.

## Статистика

- Доля k/n с 95% интервалом Уилсона.
- Сравнение двух форм: разность долей d с 95% интервалом Ньюкомба (гибридный score) и точный
  двусторонний тест Фишера. По ячейке «единица x форма» (n=4) - описательно; решения - по пулу
  класса (A - 24 наблюдения на форму, B - 20, C - 16, D - 20).
- Наблюдения внутри единицы не независимы (одна единица - четыре повтора). Анализ
  чувствительности - по единицам: доля единиц, где F1 не ниже F5 по числу pass.
- Мощность: при 20 наблюдениях на форму различимы разности около 40 п.п. (0.9 против 0.5 -
  p около 0.01). Разность 10-20 п.п. стадия A не различает, и отчёт так и говорит.

## Решающие правила

Для класса X на стадии A (sonnet, поиск не предписан, подача путём):

- **Вектора достаточно** - одновременно:
  - d = p(F1) - p(F5) не ниже -10 п.п.;
  - нижняя граница 95% интервала d выше -30 п.п.;
  - доля прогонов с вредом у F1 не выше, чем у F5.
- **Вектора не хватает** - верхняя граница 95% интервала d ниже 0.
- **Не решено** - всё остальное.

Порог -10 п.п.: меньшую разность стадия не различает, а на практике одна пропущенная ловушка из
десяти - цена, которую сжатие скилла окупает только при заметном выигрыше во вреде и объёме.
Граница -30 п.п. исключает вывод «достаточно» при интервале, допускающем большой проигрыш.

- **H1** поддержана, если вектора достаточно в A, B и C; опровергнута, если его не хватает хотя бы
  в одном классе; иначе частично.
- **H2** поддержана, если в пуле всех кейсов доля прогонов с вредом у F5 выше, чем у F1, и тест
  Фишера p < 0.05, или если F5 выше по вреду в классе D с тем же порогом.
- **H3** поддержана, если в A вектора достаточно, а в B или C его не хватает.
- **H4** - описательно: разность d по классам на opus против sonnet; F1 с предписанием поиска против
  F1 без него в классе B.
- Лестница (стадия B): для единицы нужный шаг - низшая форма F1-F4, у которой pass не меньше, чем у
  F5, минус один прогон из четырёх.

## Отклонения от плана

- **28.09.2026, до стадии A. Стенд E4 - копия с поправками** (`bench/grade/e4-harness/`, исходный
  `tests/trap-skills/dotnet-ef-core/inputs/e4-harness/` не тронут). Причины - проверка стенда на смоуке и
  на прошлых прогонах E4-b1, E4-x1, E4-w4 (вердикты совпали с протоколом ef-core):
  - `ClearItems` ищется в любом классе сборки, а не только в `OrderRepository`: поручение класс не
    называет;
  - прочитанное время сравнивается с записанным с допуском 1 мс: Postgres хранит микросекунды, .NET -
    такты по 100 нс, строгое равенство ложно проваливало бы верный маппинг;
  - если запись заказа через EF падает (провал E4-ts), заказ вставляется сырым SQL по метаданным модели,
    мимо конвертеров прогона. Без этого провал маппинга `CreatedAt` засчитывался бы и провалом
    `ClearItems` (E4-clear), которого не проверяли: на смоуке F0 так получал E4-clear fail при
    `Cascade`, с которым `Clear()` проходит.
