| # | Finding | Source URL | Seen |

| E1 | Research system: Opus 4 lead + Sonnet 4 subagents beat single-agent Opus 4 by **90.2%**; agents ~4x chat tokens, multi-agent ~15x; token usage explains ~80% of BrowseComp variance. Each subagent needs "an objective, an output format, guidance on the tools and sources to use, and clear task boundaries." ## 5. Patterns to adopt

For the planner (P) and the executor (X). Sources in brackets.

1. **Decide "delegate or not" first (P).** Multi-model/orchestrator setups pay only for varied difficulty plus bulk, independent work. A single dependent chain, or work that fits one context, is better done by one model at lower effort [E4]. Keep trivial work inline: a spawned worker carries a fixed floor (system prompt + CLAUDE.md + env; ruflo measured ~$0.26 per `claude -p` sub-agent) [S8, ruflo]. Batch same-shape micro-edits into one dispatch [superpowers].
2. **Effort before tier (P).** "Tuning effort is often a better lever than switching models" [E10]. Knowledge work is nearly flat across effort. Long-horizon coding is where effort buys accuracy [E6]. Default ladder: lower effort on the same tier, then drop a tier.
3. **Rubric, not keywords (P).** Score each subtask on a few axes and record the scores plus a one-line reason in the plan. Candidate axes: ambiguity, blast radius, novelty, verifiability [model-router-claude]; files touched, whether complete code is specified, need for design judgment [superpowers]. Hard overrides: security/auth/data/deploy -> never the cheapest tier; reviewers >= author tier [BMAD]; final whole-branch review on the most capable model [superpowers]. Opus is reserved for hard research and cross-verification, as the brief asks.
4. **Turn count beats token price (P).** Use the cheapest tier only for transcription (plan holds the complete code), single-file mechanical fixes, lookups and log/status digestion. Mid-tier is the floor for reviewers and for prose-spec implementers [superpowers]. Haiku 5.5 at `low` is risky in long agent prompts [E11]. For Haiku agentic work start at `medium`.
5. **Always pass both model and effort explicitly (X).** Use the Agent `model` param (highest precedence, S3) and `effort` (S5: allowed when a skill explicitly asks, so the executor skill must state it per dispatch). For reusable roles, also ship tiered agent files (`worker`/`worker-deep`) with `model:`+`effort:` frontmatter as the first-party plugins do [claude-plugins-official]. Validate the tier against a fixed enum and reject unknown values instead of guessing [claude-security].
6. **Indirection: category -> (model, effort) table (P/X).** The plan names a category per task (e.g. `scout`, `mechanical`, `standard`, `deep`, `verify-hard`). A separate table maps categories to alias + effort, with provider-aware variants and fallback chains [OmO, model-router-claude profiles, GSD profiles]. Use aliases, not dated IDs [M1/M2; Amitro anti-example].
7. **Escalation ladder driven by failure signals (X).** Run checkable tasks cheap first and re-run failures at higher effort (measured: ~97% pass at ~60% of all-high cost) [E5]. Then go one tier up [superpowers rounds 4-5; GSD `max_escalations: 1`; model-router "raise effort, then model"]. Escalate on deterministic triggers (round number, test failure, BLOCKED status), not on the worker's self-assessment [math-proof; E7]. Cap loops (3-5) and end in an explicit `blocked` state with a reason [BMAD, GSD, OmO].
8. **Plan-as-file + ledger (P/X).** The plan file is the single source of truth. It carries a status machine, `depends_on`, `files_modified`/owned files, acceptance criteria/`must_haves`, per-task `category/model/effort/reason`, and an escalation counter [BMAD, GSD, wshobson]. A ledger records completed tasks, rulings and re-routes as one line each, and is what the executor trusts after compaction [superpowers]. Skill content survives compaction only as its first 5,000 tokens [K6], so put the core rules at the top of SKILL.md.
9. **Minimal dispatch prompts (X).** Each dispatch carries the brief path, the interfaces from earlier tasks, ambiguity rulings, and the report path. The worker writes its full report to a file and returns a short status [superpowers, BMAD, GSD]. Subagent summaries are about 1-2k tokens [E3]. Never paste accumulated history.
10. **Independent verification (X).** The verifier is never the author. A DoneClaim -> AdversarialVerify contract [OmO, ECC]. Cheap Haiku scorers can filter findings (0-100 confidence) before expensive review [code-review plugin]. For cross-verification of facts, use N independent refuters [workflow-authoring "Adversarial verify"].
11. **Dynamic re-planning (P/X).** Re-route at checkpoints and log one line per switch (`Re-route: builder -> architect (cause unknown)`) [model-router-claude]. New subtasks found mid-run go through the same rubric. Only escalate to the top-model planner when a subtask changes scope or the rubric says `deep`.
12. **Pick the execution substrate by size (X).** For a few tasks per turn, use the Agent tool. For more than about 10 agents or fan-outs with verification, compile the plan into a Workflow script where `agent(prompt, {model, effort, schema, isolation, agentType})` carries per-agent tiers. You get deterministic control flow, sibling cache sharing, resume, `budget`, and `schema` outputs [W1, W2, C4]. Agent teams only when workers must talk to each other: experimental, ~7x tokens in plan mode, not under `-p` [T1, T2].
13. **Guardrails and limits (X).** Workers get no `Agent` tool, or set `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH=1` for worker-only runs [S7; superpowers "no-subagents contract"]. Use `maxTurns` per worker [S11]. Respect the 20-concurrent cap [S13]. In headless runs use `--max-budget-usd`, which includes subagents [H1]. One owner per file; worktree isolation only for parallel mutation [wshobson, workflows]. Do not pass `name` on Agent calls if agent teams might be enabled (named calls become teammates) [T1].
14. **Cache-aware execution (X).** Don't put `model:` frontmatter on the orchestrator skill itself, since that is a model switch and a full cache miss [K2/C1]. Keep sibling worker definitions identical so fan-outs share a prefix [C4]. Consider `subagentPromptCacheTtl: 1h` if workers pause more than 5 min [C3]. Use forks for side tasks that need the parent's context; they share the cache but run on the same model [S15].
15. **Telemetry for the feedback loop (X).** Read `modelUsage`/`total_cost_usd` (both include subagents) and `subagent_stats` (observed) from `-p` JSON [H2, H3], plus completion notifications' `total_tokens`/`duration_ms` [H6]. Log tier, effort, outcome and cost per task, so the rubric can be recalibrated. A cost-asymmetric reward penalizes over-tiering, as in ruflo's bandit [ruflo].
16. **Prompt add-ons per tier (X).** For Haiku 5.5 workers, include today's date, "keep working until done" and "verify your change" paragraphs [Prompting Haiku 5.5]. For Opus 5.5 orchestrators, add the time-signal sentence or `elapsed Ns / budget` lines [E8; Prompting Opus 5.5 "Time signals for multiagent harnesses"]. Treat a text-only end of turn as a report, not completion, and allow at most 2-3 automatic continuations [Prompting Opus 5.5 "Unattended agentic runs"].
17. **Optional cost lever: orchestrator one layer down (X).** Run the controller loop itself as a mid-tier subagent, keeping the top model for planning and final review only [superpowers claude-code-tools.md].

## 6. Anti-patterns

1. **Omitting `model` on dispatch.** The subagent silently inherits the main model, often Opus/Fable [S3; superpowers].
2. **Setting model without effort.** Effort falls back to the session level or the model's default. In Claude Code, Opus/Sonnet/Haiku 5.5 default to `medium` [M4]. The Codex analogue resets to the model default [superpowers codex-tools.md].
3. **Keyword/lexical difficulty heuristics.** Examples: ruflo's word-length complexity and keyword lists, m4rio's "opus only if prompt contains 'architecture'". Ruflo's own docs admit over-tiering [ruflo].
4. **Trusting the cheap worker to self-escalate.** Haiku/Sonnet executors consulted an Opus advisor on 0/198 questions; low effort "can stop detecting that it is stuck" [E7, E13].
5. **Hardcoded dated model IDs in skills, and ignoring provider alias drift.** On Bedrock/Google Cloud `haiku` = Haiku 4.5 and `sonnet` = Sonnet 4.5 [M1]. Haiku 4.5 has no effort support [M3], so an "effort: low" plan silently means nothing there.
6. **Giant always-loaded context.** Examples: ruflo's ~71 KB CLAUDE.md, SuperClaude's 55-60% of context, 200-agent catalogs with overlapping descriptions (Claude Code warns past 15k tokens of subagent descriptions [S14]), task-master's ~21k tokens of MCP schemas.
7. **Unmeasured savings claims, and docs that disagree with the files.** VoltAgent's README names opus agents that are `inherit`. OMC claims 30-50% savings from a scorer that appears unwired.
8. **Hook outputs in an undocumented shape.** m4rio returns `modify_input` and top-level `decision` for PreToolUse. The documented field is `hookSpecificOutput.updatedInput` [H5]. This likely fails silently.
9. **Workers spawning their own subagents or reviewers.** This duplicates review seats [superpowers].
10. **Pasting session history into dispatches** (42k-char dispatch, 99% history) [superpowers]. Inlining large files instead of paths [GSD].
11. **Parallel implementers on shared files; agent teams for sequential or same-file work** [superpowers; T1]. Parallel worktree spawns raced on `.git/config.lock` [GSD].
12. **Accidental agent teams.** With `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1`, any named Agent call becomes a teammate [T1].
13. **Orchestrating a single dependent chain.** You pay for plan, handoff and merge for nothing [E4]. Spawning many subagents for simple queries [E1].
14. **Mid-conversation model switches in the orchestrator.** A skill `model:` frontmatter or `opusplan` toggles invalidate the cache [K2, C1].
15. **Cheapest model for multi-step work or as reviewer** (2-3x turns) [superpowers]. A reviewer below the author's capability [BMAD].
16. **Uncapped fix/continuation loops** [BMAD, GSD, OmO].
17. **Relying on `CLAUDE_CODE_SUBAGENT_MODEL` to force tiers.** It now ranks below per-invocation and frontmatter models. Use `CLAUDE_CODE_SUBAGENT_MODEL_FORCE=1` only if you really want one model everywhere [S3]. ECC's advice is version-sensitive.

## 7. Haiku-as-router assessment

**Question:** can Claude Haiku 5.5 be the cheap decision maker for routing (difficulty -> model -> effort) instead of an external routing API?

**Short answer:** Yes, as a *proposer and classifier* inside Claude Code with structured output and conservative policies. No, as the *sole judge* of what is hard. The top-model planner should label the initial plan itself. Haiku fits re-labelling new subtasks mid-run and checkable triage. The real safety net is failure-driven escalation, not prediction accuracy.

Evidence for:
- **Positioning.** Anthropic lists Haiku 5.5 "for high-volume, latency-sensitive tasks such as classification, extraction, and routing" and "subagent tasks" (models overview; Haiku 5.5 overview/what's new, seen 2026-10-08). The ticket-routing guide recommends Haiku 5.5 at `low` effort for classification and suggests Haiku for hierarchical (cascaded) classifiers because of latency (https://platform.claude.com/docs/en/about-claude/use-case-guides/ticket-routing). "Building effective agents" describes routing easy queries to Haiku and hard ones to Sonnet [E2].
- **Cost and latency.** $0.10/$0.50 per MTok (<=100K prompt), 20x cheaper than Sonnet 5.5 and 40x cheaper than Opus 5.5. A local `claude -p --model haiku --effort low` difficulty label cost **$0.00076 in 0.78 s**, dominated by a one-time ~3.8k-token cache write; repeat calls read cache at $0.01/MTok [H3]. That is roughly 2-3 orders of magnitude below the floor of one spawned worker [ruflo].
- **Capability.** GPQA Diamond 85% vs 91% for Sonnet/Opus 5.5. HLE with tools 57.4% vs 64.5% (Sonnet 5.5). A big jump over Haiku 4.5 on every published row (announcement). Effort levels and adaptive thinking let it reason more on ambiguous items.
- **No new infrastructure.** It runs in-harness via the Agent tool (`model: haiku`), a Workflow `agent(..., {model:'haiku', effort:'low', schema})`, or `claude -p --model haiku --json-schema ...` [W2, H1]. External routers add a dependency and secrets, and the evidence for them is weak. LLMRouterBench (arXiv:2601.07206, Jan 2026): "many routing methods exhibit similar performance under unified evaluation" and "several recent approaches, including commercial routers, fail to reliably outperform a simple baseline". RouteLLM (arXiv:2406.18665) reports ">2 times" cost reduction, but with routers *trained* on preference data, which we would not have.

Evidence against / limits:
- **The judgment gap.** "Gating the consult well requires a cheap signal; asking the executor to recognize the hard cases itself demands the very judgment it's missing" [E13]. Haiku 5.5 and Sonnet 5.5 called an Opus advisor on **0 of 198** GPQA questions [E7]. Judging *others'* subtasks is easier than self-assessment, but subtle hardness looks small in text (a one-line concurrency change, a "simple" auth tweak), and that is exactly where under-tiering hurts. The routing literature notes that query text and semantic similarity are weak proxies for difficulty (VDAR-Router, Brick: seen only via aggregator pages, **unverified**).
- **Context poverty.** A fresh Haiku call sees only what it is given. The Opus planner already holds the task, the codebase findings and the dependencies, so its marginal cost to emit labels during decomposition is near zero.
- **Model quirks.** At `low` in long prompts it skips checks or stops early [E11]. Sampling params can't be set (no temperature; use schema plus voting for consistency). Safety classifiers can return `stop_reason: "refusal"` with no server-side fallback (cyber/bio/frontier_llm/general_harms), so security-flavoured subtasks may be refused and the router must fall back to Sonnet. Prompts over 100K tokens cost 5x. On Bedrock/Google Cloud/Foundry the `haiku` alias is still Haiku 4.5 (no effort, weaker) [M1].
- **Prediction is not the right lever anyway.** Anthropic's measured cheapest policy for checkable work is *run low, re-run failures higher* (~97% pass at ~60% of all-high cost) [E5]. That needs a failure signal, not a perfect router.

Recommended design:
1. **The planner (Opus/Fable) assigns `category/model/effort` + reason during decomposition**, using an explicit rubric and hard overrides (security, data, deploy and final review are never on Haiku; reviewer >= author). This is in-context and costs nothing extra.
2. **Haiku 5.5 router for incremental decisions** (new subtasks discovered by workers, re-labelling after a failure), when waking the top model is overkill. Use structured output, e.g. `{"axes":{"ambiguity":0-2,"blast_radius":0-2,"novelty":0-2,"verifiability":0-2,"files":n,"complete_code_given":bool},"category":"...","confidence":0-1,"needs_planner":bool}`. Let the *executor's deterministic table* map scores to tiers; Haiku does not pick models free-form. Policy: confidence < threshold, or any axis = 2 on blast radius, -> escalate to Sonnet/planner. Asymmetric default: when unsure, go one tier up ("When unsure, take HEAVY" [OmO]).
3. **Haiku as a worker-side triage tool** where outputs are checkable: extract pass/fail from logs, decide whether a diff touches more than N files, score finding confidence 0-100 before expensive review (as in the official `code-review` plugin).
4. **Calibrate before trusting.** Build 30-50 historical subtasks labelled with the cheapest tier that actually succeeded. Measure Haiku-router vs planner-only labels vs a trivial baseline (e.g. "everything Sonnet/medium"), tracking under-tiering rate and cost per completed task, per the LLMRouterBench lesson. Re-check at each model release [E4: "Recheck at every model release"].
5. **Don't use the advisor tool as the router.** Advisor consults are model-driven, uncapped in Claude Code, and cheap executors under-consult [A1, E7].
