# Оркестрация по тирам моделей 5.5: когда окупается и кто выбирает тир

**Вопрос.** Окупается ли план, в котором старшая модель разбивает работу, а исполняют её модели
Haiku 5.5, Sonnet 5.5 и Opus 5.5 с разным effort, против одной модели на всю работу; и кому
доверять выбор тира: старшей модели в плане, `haiku` как дешёвому решателю или внешнему
платному роутеру.

**Ответ.** Не окупается на проверенном предмете, а выбор тира предсказанием не работает.

- **Оркестрация проиграла одной сессии.** Тринадцать независимых кусков `optimize-for-llm`: одна
  сессия Opus 5.5 `medium` - в среднем 12.3 из 13 за $2.11; лучшая оркестрация (четыре партии на
  Sonnet 5.5, оркестратор Sonnet `high`) - 13 из 13 за $2.93 исполнения и ещё $2.44 на план;
  наивная раздача Sonnet-субагентам без скиллов - 13 из 13 за $4.32 и 25 запусков субагентов. Выигрыша по качеству нет, цена выше в
  1.4-2.5 раза без учёта плана, время такое же или больше. Это совпадает с руководством Anthropic
  по стоимости: оркестратор окупается, только когда есть что раздавать и оно не помещается в
  один контекст.
- **Шлюз «оркестрировать ли» работает.** Планировщик с измеренными приорами выбирает `solo` и
  обосновывает его цифрами; с неверными приорами (цена отдельной сессии на кусок вместо цены
  общей) выбирал `orchestrate` по ошибочному расчёту. Качество плана равно качеству данных, на
  которых он считает.
- **Сначала дёшево, повтор провалов выше - лучшая политика из измеренных.** При проверке, ловящей
  провал, лестница `haiku medium` -> `haiku high` -> `sonnet medium` -> `sonnet high` проходит 100%
  кейсов по $0.08 за кейс против $0.21 у «Sonnet `medium` на всё» (88%) и $0.46 у «Opus на всё».
  Всё держится на проверке: её качество ограничивает потолок.
- **Предсказание тира по описанию задачи не работает.** Триаж `haiku` `medium` дал всем 13
  однотипным задачам одинаковые оценки; `sonnet` и `opus` различали одну ось и ошибались в
  сторону труднейших кейсов. Внешний платный роутер доказательствами не подкреплён: шесть
  коммерческих роутеров не обогнали случайный выбор между двумя хорошо выбранными моделями
  (arXiv:2610.02762). Решение остаётся за планировщиком на старшей модели и за лестницей повторов.
- **Протокол исполнителя держится.** Явные `model` и `effort` в каждом запуске, проверка самим
  оркестратором, лестница по сигналу, потолок запусков, возобновление по журналу - 15 из 15
  прогонов X-кейсов на итоговой редакции, плюс отказ принять заведомо противоречивый пакет.
- **Среда ломает допущения, которые выглядели надёжными.** Инструмент записи отклоняет у
  субагента файлы-отчёты («Subagents should return findings as text, not write report files»),
  и одна из первых версий скилла из-за этого терялась на пяти кейсах из тринадцати; отчёт теперь
  возвращается текстом, а файл пишет оркестратор.

## Метод

Живые прогоны `claude -p` (Claude Code 2.1.294, семейство 5.5, 2026-10-08) из рабочих деревьев
вне репозитория; скиллы подключены `--plugin-dir` рабочей копии. Предмет - существующий скилл
каталога `optimize-for-llm` на 13 независимых кейсах с дословным грейдером
(`tests/optimize-for-llm/grade.mjs`): качество - число пройденных кейсов, без судьи-модели.
Цена - `total_cost_usd` результата, включающий субагентов. Оснастка и кейсы -
[tests/orchestration/](../../../tests/orchestration/README.md).

## Что не проверено

- Один предмет. Выводы о цене и проходимости относятся к `optimize-for-llm`; на другом предмете
  приоры пересматриваются по журналу маршрутизации.
- Грейдер судит дословную половину инвариантов; смысловая половина в сравнение не входит.
- Режим, где работа не помещается в один контекст, не проверен. Попытка получить его копиями
  набора в соседних папках недействительна: модель клала результат первой копии в остальные байт
  в байт, а цена и проходимость такого прогона ничего не говорят.
- Смены контекста долгого исполнителя (потолок и передача) в скиллы не вошли: механизм замера и
  остановки исполнителя не подтверждён прогоном.
- `Jev`: в постановке задачи упомянут внешний платный API для решений, который не хотелось
  подключать; что именно имелось в виду, неизвестно, сравнение сделано с классом внешних
  роутеров по литературе (arXiv:2610.02762, 2601.07206), а не с конкретным продуктом.
- Приоритет параметра `effort` вызова `Agent` относительно `CLAUDE_CODE_EFFORT_LEVEL` не
  проверен; сам параметр проходит и меняет объём рассуждения (Haiku 5.5, thinking-токены:
  3.4 тыс. на `low` против 4.8 тыс. на `max`, один прогон).
