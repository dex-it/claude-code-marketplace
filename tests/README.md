# Сквозные прогоны конвейера

Тесты композиции зон - не юнит-проверки артефактов. Валидность единицы (skill, агент, команда) закрыта `npm run validate`; здесь проверяются **стыки**: передача полей между узлами, поведение на границах зон, честность статусов.

Группировка - по фиче, под которую прогон делался: тесты служат регрессионной историей («что нашлось тогда-то»), а не оглавлением маршрутов.

## Метод: трассировка белым ящиком

Прогон виртуальный - обход фаз агента по **тексту артефактов**, без запуска. Для каждой фазы: что предписывает Output/Exit criteria на данном входе -> куда ведёт -> где ломается. Опора на конкретную строку артефакта, не на общее впечатление.

Находки делятся по доказуемости, и смешивать сорта нельзя:

- **предписывает** - выводится из текста фазы, живым прогоном не изменится;
- **допускает** - гипотеза о поведении модели, читающей текст; подтверждается только живым прогоном.

Чего метод не даёт: как модель поведёт себя вопреки тексту - импровизацией обойдёт дыру или, наоборот, не заметит явного правила. Виртуальный прогон показывает потолок качества артефакта, не фактическое поведение.

## Метод: живой прогон

Второй метод, дополняющий первый: узел спавнится субагентом и реально исполняется на заданном
входе. Он отвечает ровно на тот вопрос, который трассировка оставляет открытым, - как модель ведёт
себя при живом чтении артефакта. Находки сорта «допускает» подтверждаются или снимаются только
здесь.

Эталона текста у живого прогона нет и быть не может: артефакт порождается моделью и от прогона к
прогону не совпадает. Проверяется поведение контура - где встал, с каким `status`, что попало в
`quality-checks`, чем закрыт уход от проверки. Отсюда формат: **кейс** = вход плюс инварианты, а не
ожидаемый выход. Матрица кейсов - [`_cases/`](_cases/); формат кейса описан там же.

Порядок прогона:

1. **Синхронизировать установку с рабочей копией - плагин за плагином.** Маркетплейс каталога
   указывает на директорию репозитория, но кеш установки сам не обновляется, и `claude plugin
   marketplace update dex-claude-marketplace` этого не делает тоже: он обновляет метаданные
   маркетплейса, а установленный плагин остаётся на своей версии (проверено 02.08.2026 - после
   `marketplace update` дирижёр остался на 1.2.0 при 4.x в рабочей копии). Версию поднимает только
   `claude plugin update <плагин>@<маркетплейс>` по каждому участнику маршрута, включая скиллы и
   контракт; изменения применяются со следующей сессии. Расхождение молчаливое - узел рассуждает по
   снятой норме и звучит убедительно (прогон 2026-08-02 оперировал осью `stage`, снятой днём
   раньше, и объявил непредписанным правило, введённое накануне). Версии установленных узлов
   записываются в итог прогона, и находка, относящаяся к снятой норме, при разборе снимается. Обновления мало:
   плагин, лежащий в кеше, но выключенный в `~/.claude/settings.json` (`"<плагин>@<маркетплейс>":
   false`), для узла неотличим от несуществующего - прогон 2026-08-02 объявил «не существует» три
   skill, из которых два были установлены и выключены, а один не установлен, и все три есть в
   каталоге. Перед прогоном сверять enabled-статус каждого плагина, который узлы грузят по
   маршруту; иначе `unverifiable` в выходе читается как дефект нормы, хотя это дефект среды.
2. **Вход подавать по кейсу дословно** - отсебятина делает прогон невоспроизводимым.
3. **Канал оператора держит вызывающий.** У субагента канала к человеку нет: апрув гейта приходит
   отдельным сообщением от ведущего прогон. Контур, апрувящий сам себя, - провал кейса, а не
   удачный прогон.
4. **Сверить выход с инвариантами кейса** явным «да / нет» по каждому.
5. Артефакты, интересные как форма, уходят пакетом в [`docs/sample/`](../docs/sample/README.md);
   итог прогона - строка в реестре ниже.

Недетерминированность лечится повтором: кейс, прошедший один раз из трёх, не пройден - его
нестабильность сама по себе находка.

Оснастка платформы (`claude plugin eval`: кейсы в `evals/**/case.yaml`, LLM-грейдеры, `--runs`,
`--ablation` с базой без плагина) на 02.08.2026 в early access и в установленной сборке не
запускается. Кейсы держатся в человекочитаемом виде; поля совпадают с тем, что просит `case.yaml`,
поэтому перенос будет механическим.

## Структура

```
_templates/          шаблоны маршрутов, не привязанные к фиче
_cases/              матрица кейсов живого прогона: вход + инварианты, по зонам
<имя-фичи>/
  scenario-*.md      копия шаблона с подставленным входом; находки и их
                     закрытие живут в самом сценарии, отдельного файла нет
```

Маршрутов на фичу может быть несколько - тогда несколько `scenario-*.md` по именам шаблонов.

## Общие критерии провала

Действуют во всех прогонах сверх частных таблиц:

- `complete` выдан при незакрытых допущениях или непройденном гейте;
- поле `quality-checks` потеряно на стыке (не перенесено вниз как сквозное);
- `verdict` вне закрытого перечня `node-contract` п.7 (`passed` / `failed` / `unverifiable`);
- `verdict` несёт историю прогона, а не финальное состояние: `failed` рядом с закрытыми находками и `status: complete`;
- `status` в шапке документа не проставлен либо поднят выше, чем позволяет исход гейта (`approved` без апрува оператора, при открытых вопросах либо без записи оракула в `quality-checks`);
- уход от проверки закрыт молчанием, а не явным статусом с причиной;
- субагент, которого спавнит узел, отсутствует в бандле (установка плоская, каскада нет);
- **оператору предъявлено выводимое из материала** - вопрос, ответ на который лежит во входе, в домене задачи или в соседнем поле. Перебор наверх - такой же провал, как молчаливый пропуск проверки: узел вернул оператору работу, ради которой вызван;
- вопрос предъявлен голым - без вариантов и без рекомендации узла с обоснованием;
- решение, принятое узлом за постановщика, не попало в перечень допущений (обратная сторона того же критерия: разгрузка не отменяет записи).
