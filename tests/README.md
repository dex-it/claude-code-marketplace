# Сквозные прогоны конвейера

Тесты композиции зон - не юнит-проверки артефактов. Валидность единицы (skill, агент, команда) закрыта `npm run validate`; здесь проверяются **стыки**: передача полей между узлами, поведение на границах зон, честность статусов.

Второй предмет того же дерева - **прогон отдельного скилла на корпусе-входе**, когда его выход нельзя проверить валидатором: [optimize-for-llm/](optimize-for-llm/) (что рез уносит вместе с водой). Метод тот же - вход дословно плюс инварианты, реестр прогонов общий, ниже.

**Коды `Z1-*` / `Z2-*` и имена файлов `_cases/zone-1.md`, `_cases/zone-2.md` - идентификаторы записей журнала, не термины.** `Z1` - зона требований (`/feature`), `Z2` - зона дизайна (`/design`); нормативные тексты называют зоны именем предмета, здесь коды сохранены, потому что по ним адресуются прежние прогоны и снапшоты.

Группировка - по фиче, под которую прогон делался: тесты служат регрессионной историей («что нашлось тогда-то»), а не оглавлением маршрутов.

## Метод: трассировка белым ящиком

Прогон виртуальный - обход фаз агента по **тексту артефактов**, без запуска. Для каждой фазы: что предписывает Output/Exit criteria на данном входе -> куда ведёт -> где ломается. Опора на конкретную строку артефакта, не на общее впечатление.

Находки делятся по доказуемости, и смешивать сорта нельзя:

- **предписывает** - выводится из текста фазы, живым прогоном не изменится;
- **допускает** - гипотеза о поведении модели, читающей текст; подтверждается только живым прогоном.

Чего метод не даёт: как модель поведёт себя вопреки тексту - импровизацией обойдёт дыру или, наоборот, не заметит явного правила. Виртуальный прогон показывает потолок качества артефакта, не фактическое поведение.

**Исполняемая часть маршрута трассировкой не закрывается.** Хук, скрипт, валидатор проверяются запуском на синтетическом входе, и в отчёт идут код возврата и вывод по каждому случаю; «работает» вместо них равно пропуску. Прогон, где есть и то и другое, помечается гибридным - сорт находки по исполняемой части не «предписывает»/«допускает», а результат запуска.

## Метод: живой прогон

Второй метод, дополняющий первый: узел спавнится субагентом и реально исполняется на заданном
входе. Он отвечает ровно на тот вопрос, который трассировка оставляет открытым, - как модель ведёт
себя при живом чтении артефакта. Находки сорта «допускает» подтверждаются или снимаются только
здесь.

Эталона текста у живого прогона нет и быть не может: артефакт порождается моделью и от прогона к
прогону не совпадает. Проверяется поведение контура - где встал, с каким `status`, что попало в
`quality-checks`, чем закрыт уход от проверки. Отсюда формат: **кейс** = вход плюс инварианты, а не
ожидаемый выход. Матрица кейсов - [`_cases/`](_cases/); формат кейса описан там же.

Порядок прогона:

1. **Синхронизировать установку с рабочей копией - плагин за плагином.** Маркетплейс каталога
   указывает на директорию репозитория, но кеш установки сам не обновляется, и `claude plugin
   marketplace update dex-claude-marketplace` этого не делает тоже: он обновляет метаданные
   маркетплейса, а установленный плагин остаётся на своей версии (проверено 02.08.2026 - после
   `marketplace update` дирижёр остался на 1.2.0 при 4.x в рабочей копии). Версию поднимает только
   `claude plugin update <плагин>@<маркетплейс>` по каждому участнику маршрута, включая скиллы и
   контракт; изменения применяются со следующей сессии. Расхождение молчаливое - узел рассуждает по
   снятой норме и звучит убедительно (прогон 2026-08-02 оперировал осью `stage`, снятой днём
   раньше, и объявил непредписанным правило, введённое накануне). Версии установленных узлов
   записываются в итог прогона, и находка, относящаяся к снятой норме, при разборе снимается. Обновления мало:
   плагин, лежащий в кеше, но выключенный в `~/.claude/settings.json` (`"<плагин>@<маркетплейс>":
   false`), для узла неотличим от несуществующего - прогон 2026-08-02 объявил «не существует» три
   skill, из которых два были установлены и выключены, а один не установлен, и все три есть в
   каталоге. Перед прогоном сверять enabled-статус каждого плагина, который узлы грузят по
   маршруту; иначе `unverifiable` в выходе читается как дефект нормы, хотя это дефект среды.
2. **Изоляция узла от нормы - по путям, не сплошным запретом на репозиторий.** Узел не должен
   читать фреймворки и кейсы, по которым его поведение судят: увидев их, он воспроизводит
   ожидаемое поведение вместо своего. Закрыты `docs/`, `tests/`, `.claude/rules/`; `plugins/`
   открыт - там лежат тела оракулов, которые узел обязан прогонять по контракту. Сплошной запрет
   отключает вместе с нормой и самоконтроль: прогон 2026-08-03 закрыл репозиторий целиком, и все
   `self-check` свелись к рассуждению об оракуле по памяти - конструкция «автор проверяет себя,
   судья проверяет автора» работала одной половиной. Формально Skill tool рабочей копией не
   ограничен (скиллы грузятся из установленного дерева), но узел читает запрет как запрет на всё
   каталожное - поэтому разделение по путям называется в задании прогона явно, а не
   подразумевается.
3. **Рабочая директория узлов - вне дерева мета-материалов прогона.** Бриф, файл сверки среды,
   кейсы и итог лежат отдельно от директории, куда узлы пишут артефакты: узел, которому назначена
   рабочая директория внутри этого дерева, встречает мета-материалы штатным чтением своей рабочей
   области. Прогон 2026-08-04: рабочей директорией назначили `artifacts/` рядом с брифом, первый
   дирижёр бриф прочитал и увидел, какие развилки заложены намеренно и по каким осям его судят -
   ход пришлось аннулировать целиком. Запретом это не лечится: чтение своей рабочей директории
   узлу предписано контрактом, запрещать его значит ломать прогон вторым способом.
4. **Вход подавать по кейсу дословно** - отсебятина делает прогон невоспроизводимым.
5. **Канал оператора держит вызывающий.** У субагента канала к человеку нет: апрув гейта приходит
   отдельным сообщением от ведущего прогон. Контур, апрувящий сам себя, - провал кейса, а не
   удачный прогон.
6. **Сверить выход с инвариантами кейса** явным «да / нет» по каждому.
7. Артефакты прогона в репозитории не хранятся: дом образцов `docs/sample/` снят (`3171cf9b`), рабочее
   дерево прогона остаётся на машине. Итог прогона - строка в реестре ниже, и она несёт находки, а не
   ссылку на пакет.

Недетерминированность лечится повтором: кейс, прошедший один раз из трёх, не пройден - его
нестабильность сама по себе находка.

Оснастка платформы (`claude plugin eval`: кейсы в `evals/**/case.yaml`, LLM-грейдеры, `--runs`,
`--ablation` с базой без плагина) остаётся в early access: на 23.08.2026, CLI 2.1.240, команда
отвечает `plugin eval is currently in early access` и `init --bare` не создаёт ни одного файла.
Пока доступ закрыт, активация меряется прогоном ниже. Кейсы держатся в человекочитаемом виде; поля совпадают с тем, что просит `case.yaml`,
поэтому перенос будет механическим.

Второй готовый маршрут - `skill-creator` из официального маркетплейса (установлен, сверено
25.08.2026): `scripts/run_eval.py` мерит hit rate по `should_trigger`, `improve_description.py`
правит поле по провалам, `run_loop.py` крутит цикл. **Наш прогон он не заменяет, предмет другой**:
`run_eval.py` кладёт в песочницу не скилл, а slash-команду с телом-заглушкой
`This skill handles: {description}` - судится поле в изоляции, тело настоящего скилла в прогоне не
участвует, и конкуренция идёт с тем, что установлено у оператора. Находки вида «`root-cause-analysis`
стабильно проигрывает `superpowers:systematic-debugging`» на этом маршруте невоспроизводимы по
построению. Полезен он на обратной задаче - подобрать формулировку поля отдельному скиллу, когда наш
прогон уже показал молчание.

## Метод: прогон активации

Третий метод, машинный и воспроизводимый: `npm run test:activation`
([`tools/run-activation.js`](../tools/run-activation.js), кейсы -
[`activation/cases.json`](activation/cases.json)). Предмет - `description` скилла как поле
срабатывания: поднимется ли скилл на реалистичном запросе. Валидатор судит форму поля, а не факт
активации; решает её модель, читая поле, - проверяется только запуском.

Кейс - запрос плюс имя ожидаемого скилла. `in-scope` требует, чтобы скилл оказался среди вызванных;
`near-miss` требует обратного на соседнем запросе вне охвата: поле, ловящее всё подряд, дефект той
же природы, что и не ловящее ничего. Прогон идёт в пустой временной директории - `CLAUDE.md`
проекта не подсказывает выбор.

**Охват: trap-skills целиком, process-skills - только движок.** Основание исключения -
[SKILL_FRAMEWORK.md](../docs/SKILL_FRAMEWORK.md) («process-skill грузится детерминированно,
авто-активация вторична»), и оно уже один раз не сработало: движок - тоже process-skill, прогон
`engine-*` нашёл на нём настоящий дефект маршрута. У трек-скиллов поле такое же широкое («баг-фикс»,
«инцидент», «README», «ревью входящего MR») и соревнуется с trap-скиллами каталога, поэтому
непокрытыми они остаются не по норме, а по неоплаченному прогону. Ценнее здесь направление
`near-miss`: вопрос не «поднимется ли трек», а «не перехватит ли он запрос соседа»
(`documentation-track` против `doc-standards`, `diagnostics-track` против `root-cause-analysis`).

**Кейсы `idea-forming-*` заведены, но не прогнаны** (5 штук: 2 `contested`, 3 `near-miss`, включая
обратный `product-discovery-near-idea`). Ожидание по ним заранее не оптимистичное: `idea-forming`
делит предмет со сторонним `superpowers:brainstorming`, а прогон 23.08.2026 показал, что скиллы
этого плагина перехватывают соседей стабильно и правкой своего поля это не снимается
(`root-cause-analysis`, `reference-architectures`). Поэтому кейсы здесь меряют не «работает ли
поле», а **величину перехвата**: молчание при живом соседе - ожидаемый исход, а не дефект описания,
и лечится он императивным вызовом, записанным в теле скилла. Поэтому оба прямых кейса стоят в режиме
`contested`, а не `in-scope`.

**Условие годности этих кейсов держится полем кейса, а не текстом здесь.** `requiresListed`
называет то, без чего исход кейса ничего не измеряет: у пяти кейсов выше это
`superpowers:brainstorming`. Требуемого нет в листинге сессии - кейс получает тот же статус «не
проверено», что и отсутствующий скилл, и в зелёные не попадает. Причина в проверке, а не в README:
состояние чужой машины на дату читатель репозитория проверить не может, а листинг сессии прогон
видит сам.

**Среда прогона уезжает в исход.** Поле `foreign` каждого исхода несёт сторонние (не `dex-`) скиллы
листинга - ту самую конкуренцию, в которой получен результат. Без неё «7/7 при живом конкуренте» и
«7/7 при выключенном» задним числом неразличимы, а это разные утверждения о поле активации.

**Плагин кейса грузится из рабочего дерева** (`--plugin-dir`, зонд 23.08.2026: источник плагина
становится `@inline`, дубля в листинге скиллов нет). Без этого прогон судил бы установку оператора,
а не каталог: непоставленный плагин давал бы ложный провал, а поставленная старая версия скрывала бы
ровно ту правку `description`, ради которой прогон и запускается. Скилл, которого всё же нет в
листинге сессии (плагин не найден в `plugins/`, опечатка в `expect`), не проходит и не
проваливается - он получает статус **не проверено** и перечисляется в итоге: ложный зелёный на
`near-miss` здесь так же вреден, как ложный провал на `in-scope`.

**Попадание засчитывается и по голому имени плагина** (`dex-skill-ddd` вместо `dex-skill-ddd:ddd`),
отдельной пометкой `ok/гол` и строкой в итоге. Такой вызов не резолвится, и модель исправляется
следующим ходом, который в лимит ходов не всегда помещается; предмет прогона - выбор артефакта, а не
форма вызова, поэтому это попадание, но форма остаётся видимой, а не тонет в зелёном.

**Скилл поднимается не только своим полем.** Движок конвейера (`dex-sdlc:engine`) на голом
поручении полем не ловится вовсе - его поднимает хук соседнего плагина (`dex-sdlc-nudge`), и такой
конструкт проверяется только целиком. Для этого кейс несёт четыре необязательных поля: `plugins` -
плагины сверх того, что назван в `expect` (все идут в `--plugin-dir`); `git` - песочница с
инициализированной репой и манифестом: она похожа на настоящий проект, а промпты работ это
предполагают (прежней причины «хуки вне репы молчат» с `dex-sdlc-nudge` 1.2.0 больше нет - каталог
сессии не разбирает ни один хук); `maxTurns` - лимит ходов, если двух мало; `requiresListed` - скиллы,
без которых исход кейса ничего не измеряет (конкурент, с которым и мерится перехват), их отсутствие
в листинге сессии даёт **не проверено**, а не зелёный.

**Режимов у кейса три.** `in-scope` - поле обязано сработать, `near-miss` - обязано смолчать,
`contested` - предмет делится с чужим скиллом, и меряется не «да/нет», а кто победил. Спорный кейс
код возврата не роняет ни при каком исходе: обе стороны информативны, а требование зелёного здесь
означало бы требование выключить конкурента. В выводе такой кейс печатается как `наш` либо
`перехв`, в `--json` несёт `contestedWon`. Плагин из `plugins`, которого
нет в дереве, даёт статус **не проверено** со строкой в итоге: неполный конструкт не говорит ни о
срабатывании, ни о его отсутствии.

**Провал кейса - ещё не дефект поля.** Классы, которые прогон не различает сам и которые разводятся
разбором: (1) промпт не о предмете скилла или не называет технологию - чинится кейс; (2) выиграл
соседний скилл каталога - смотреть границу двух полей, сосед бывает уместнее; (3) выиграл скилл
стороннего плагина на том же предмете - правкой своего поля не устраняется, фиксируется как
конкуренция среды.

**Модель - ось результата, не деталь запуска.** Зонд 23.08.2026 на одном кейсе: opus поднял скилл и
смежный, sonnet - скилл, haiku не вызвал ни одного Skill. Модель прогона пишется в реестр, прогоны
на разных моделях между собой не сравниваются.

Прогон ходит в сеть и стоит денег, поэтому не входит ни в `npm test`, ни в CI: запускается вручную
при правке поля срабатывания и при заведении скилла.

### Второй род: видимость агента

`node tools/run-activation.js --agents` судит другой предмет и уже: не выбор модели, а **имя, под
которым рантайм предлагает агента вызывающему**. Кейсы не хранятся файлом, а строятся при каждом
запуске из тех же корней плагинов, что грузятся флагом `--plugin-dir`: обход берёт `plugins/`
целиком и ключует по имени манифеста, а не по имени каталога. Хранимая копия перечня разъехалась
бы с деревом молча, обход по одной ветке оставил бы агента из другой ветки без кейса вовсе.
Вердикт берётся из массива `agents` события `system/init`, модель на исход не влияет, поэтому
прогон идёт на haiku.

**Что проба ловит и чего не ловит - замерено мутациями, не выведено.** Переименование агента она
пропускает: кейс строится из того же файла, и ожидание переименовывается вместе с ним. Сломанный
YAML в `description` тоже пропускает - рантайм такой файл принимает, а ловит его валидатор. Ловит
она расхождение имени поставки с каноничной формой: агент, положенный в `agents/nested/`,
поставляется как `{plugin}:nested:{name}`, и ссылка `{plugin}:{name}` на него не резолвится, а
`agent-file-name-mismatch` при этом молчит. Случай замерен ручным разбором `init.agents` на живом
рантайме и переведён в статическое правило `agent-file-nested`; проба остаётся свидетелем со стороны
рантайма - на случай, когда форму имени меняет платформа, а не дерево.

**Охват пробы держится не на ней самой, а на перечне кейсов.** Кейс строится из дерева при каждом
запуске, и до 01.09.2026 обход подкаталоги не брал: перенос агента в `agents/nested/` убирал разом и
кейс, и ожидание - прогон оставался зелёным, хотя предмет из-под него уходил. Обратной сверки листинга
тоже нет, судится присутствие ожидаемого имени, а не отсутствие неожиданного. Поэтому предметом
отдельного гейта стал сам перечень: `tests/tools/agent-visibility.test.sh` строит песочницу из пяти
агентов (плоский, в подкаталоге, с именем в кавычках, вне `plugins/specialists/`, в каталоге с именем
не как в манифесте), берёт перечень бесплатно через
`node tools/run-activation.js --agents --list-cases` на `MARKETPLACE_ROOT` и проверяет, что кейс
собрался на каждого. Гейт бесплатный, в сеть не ходит и входит в CI; на прежней редакции
построения перечня он краснеет.

**Пробы активации у агента нет, и это результат замера, а не пропуск.** Скилл выбирается первым
ходом, поэтому его поле проверяется дешёвой пробой. Делегирование субагенту - решение по объёму
работы, принимаемое после сбора контекста: на мелкой песочнице модель делает работу сама даже при
прямом «делегируй профильному субагенту», а песочница, большая настолько, чтобы делегирование
случилось, мерила бы свой размер, а не `description` агента. Прямой вопрос «кому передашь» уводит
модель в `ListAgents`. Строки замера - в реестре прогонов ниже.

## Структура

```
_templates/          шаблоны маршрутов, не привязанные к фиче
_cases/              матрица кейсов живого прогона: вход + инварианты, по зонам
<имя-фичи>/
  scenario-*.md      копия шаблона с подставленным входом; находки и их
                     закрытие живут в самом сценарии, отдельного файла нет
optimize-for-llm/    прогон скилла, не маршрута: метод и кейсы в README,
  inputs/            входы дословно - копируются в рабочее дерево вне репо
hooks/               исполняемая регрессия скриптов хуков: запуск на временной
                     репе, гоняется шагом CI, не трассировкой
```

Маршрутов на фичу может быть несколько - тогда несколько `scenario-*.md` по именам шаблонов.

`hooks/resume-reminder.test.sh` держит стык, который расходится молча: адрес auto-ledger живёт и в
тексте движка (`P-auto-ledger`), и в коде хука `dex-sdlc-resume`, а разъезд выглядит как отсутствие
напоминания. Тест кладёт ledger в папку сессии на временном `CLAUDE_CONFIG_DIR` и проверяет исходы:
файл найден по `transcript_path`, соседняя сессия не задета, запасная дверь (папка проекта) читается
только при пустой папке сессии, несколько открытых целей названы все, закрытый ledger и чужой
`source` молчат.

`hooks/engine-nudge.test.sh` пиннит снятие условия «молчим вне git-репозитория» (`dex-sdlc-nudge`
1.2.0). Прогон активации на это не годится: замер 01.09.2026 показал, что кейс `engine-nogit`
зелёный и на прежней редакции хука, потому что на его промпте модель поднимает движок примерно в
половине запусков без подсказки. Тест запускает скрипт напрямую из каталога без репы и из каталога
с репой, проверяет валидность JSON и имя события, работу без `jq` в `PATH`, отсутствие в скрипте
`git rev-parse` и `jq`, и формулировку радиуса в README плагина. Возврат условия в код или в прозу
роняет его: мутация «вернуть скрипт из `develop`» даёт 5 красных проверок из 7.

находки в той же строке, а не по номеру. Так уже вышло со строкой 2026-07-19 - `5e8ccdf` из неё

## Общие критерии провала

Действуют во всех прогонах сверх частных таблиц:

- `complete` выдан при незакрытых допущениях или непройденном гейте;
- поле `quality-checks` потеряно на стыке (не перенесено вниз как сквозное);
- `verdict` вне закрытого перечня `node-contract` п.7 (`passed` / `failed` / `unverifiable`);
- `verdict` несёт историю прогона, а не финальное состояние: `failed` рядом с закрытыми находками и `status: complete`;
- `status` в шапке документа не проставлен либо поднят выше, чем позволяет исход гейта (`approved` при открытых вопросах, без записи оракула в `quality-checks` либо без апрува - оператора в `interactive`, поля `approve` от оркестратора в `autonomous`);
- вердикт судьи не имеет носителя на диске - живёт только в тексте его ответа и не переживает узла;
- одна запись метки покрывает несколько экземпляров одного типа без перечня расходящихся единиц;
- уход от проверки закрыт молчанием, а не явным статусом с причиной;
- субагент, которого спавнит узел, отсутствует в бандле (установка плоская, каскада нет);
- **оператору предъявлено выводимое из материала** - вопрос, ответ на который лежит во входе, в домене задачи или в соседнем поле. Перебор наверх - такой же провал, как молчаливый пропуск проверки: узел вернул оператору работу, ради которой вызван;
- вопрос предъявлен голым - без вариантов и без рекомендации узла с обоснованием;
- решение, принятое узлом за постановщика, не попало в перечень допущений (обратная сторона того же критерия: разгрузка не отменяет записи).
