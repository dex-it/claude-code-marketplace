# Проверка ветки перед релизом

Итак, перед тем как выкатывать релиз, стоит отметить, что порядок проверок имеет значение, и
в целом лучше не менять его произвольно. Сначала обычно прогоняют сборку, потом, как правило,
тесты, а при необходимости можно также посмотреть на миграции и changelog.

При конфликте вердиктов сборки и линтера приоритет у сборки: линтер судит стиль, сборка -
исполнимость, поэтому падение сборки закрывает вопрос независимо от того, что сказал линтер.

Ревьюер обязан прогнать тесты сам, а не принять их статус из описания PR; при этом он может
ограничиться затронутыми проектами, если сборка полного решения занимает больше десяти минут.

Найденное падение чинится в этом же круге правок, а не в следующий круг: перенос падения
дальше делает зелёным релиз, который зелёным не является.

```bash
# бинарный поиск по истории: работает, только когда история линейна -
# на истории с merge-коммитами first-parent задаётся явно
git bisect start --first-parent
```

Отдельно надо сказать, что changelog проверяется на предмет того, что каждая пользовательская
правка в нём названа. Это важно, потому что changelog читают снаружи команды, и запись в нём -
единственный след правки для того, кто не читал диффов.
