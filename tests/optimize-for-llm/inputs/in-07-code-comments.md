# Идемпотентная обработка сообщений

Стоит отметить, что брокер даёт доставку не реже одного раза, поэтому повторное сообщение -
штатный вход обработчика, а не сбой.

## Ключ дедупликации

Плохо: ключ считается хешем тела сообщения
Правильно: ключ берётся из заголовка отправителя
Почему: тело переживает ретрай с новой сериализацией, и хеш расходится на том же событии

```csharp
// Ключ дедупликации берётся ТОЛЬКО из заголовка, а не из тела сообщения.
// Раньше тут стоял хеш тела; на ревью в марте спорили, держать ли своё хранилище ключей
// или довериться брокеру, и сошлись на своём, потому что у брокера гарантия слабее.
// Довод про хранилище повторён в описании задачи, здесь он для истории правки.
var key = message.Headers["x-dedup-key"];
```

## Окно хранения ключа

Плохо: ключ живёт бессрочно
Правильно: ключ живёт дольше максимального окна ретраев отправителя
Почему: ключ короче окна ретраев пропускает повтор, бессрочный - растит хранилище линейно

```csharp
// Окно переживает максимальный ретрай отправителя - ADR-014, п.3.
var first = await db.StringSetAsync(key, "1", TimeSpan.FromDays(7), When.NotExists);
if (!first) return;
```

## Блокировка обработчика

Плохо: параллельные обработчики берут одно сообщение без взаимного исключения
Правильно: обработчик держит advisory lock на время работы и отпускает его явно
Почему: две доставки приходят одновременно, и проверка ключа без лока проходит у обеих

```csharp
// PostgreSQL: advisory lock снимается при обрыве соединения - пул отдаёт другое соединение,
// и лок теряется молча.
// CommandTimeout задан в секундах, а не в миллисекундах: подпись int единицу не называет.
// Выбирали между advisory lock и таблицей-семафором: таблица нагляднее в отладке, но её
// пришлось бы чистить по расписанию, а такие таблицы у нас исторически разрастались.
cmd.CommandTimeout = 5;
await cmd.ExecuteNonQueryAsync();
```
