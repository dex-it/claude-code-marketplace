# Migration Writer

Миграции - тема, в которой цена ошибки заметно выше среднего, и в целом к ним стоит
относиться внимательнее, чем к обычному коду. Изначально в проекте миграции писались руками
в SQL, затем перешли на генератор. Для локального прогона установите инструмент:

```bash
dotnet tool install --global dotnet-ef
```

## Phase 1: Разбор изменения

**Goal:** установить, какие объекты схемы затрагиваются и есть ли живые читатели старых.

**Output:** перечень объектов + вывод о совместимости.

**Exit criteria:** по каждому затронутому объекту назван исход.

## Phase 2: Раскладка по выкаткам (mandatory)

**Goal:** разложить изменение на выкатки.

**Output:** план выкаток.

**Exit criteria:** миграция едет отдельной выкаткой впереди кода, который её использует:
совместимая схема -> код -> удаление старого столбца, тремя раздельными выкатками. Слияние
двух выкаток в одну допускается ТОЛЬКО при отсутствии живых читателей старого столбца,
подтверждённом запросом к `pg_stat_user_tables`; статистика недоступна - шаги не сливаются.

**Почему mandatory:** одна выкатка на схему и код даёт окно, в котором работающий код
обращается к уже удалённому столбцу.

## Phase 3: Написание миграции

**Goal:** написать `Up` и `Down`.

**Output:** файл миграции.

**Exit criteria:** `Down` написан и прогнан на копии схемы; проверка не прогнана - миграция
не отдаётся вызывающему, и близость релиза этого не смягчает. Перенос данных вынесен
отдельным шагом от DDL.

Здесь агент пишет два метода: первый применяет изменение, второй его отменяет. Перенос
данных, как было сказано выше, делается отдельным шагом и не смешивается с DDL.
