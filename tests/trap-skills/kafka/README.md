Контроль без скилла (`c1`, `c2`) на G-K (код) и RV-K (ревью); `n` - редакция из трёх названий; `o` - K8 с исходом.

|---|---|---|---|
| K1 Fire-and-forget без callback | 2/2 | 2/2 | снята |
| K2 Random partition key | 2/2 | 2/2 | снята |
| K3 Нет Flush() при shutdown | 1 из 2 и n/a (все публикации через `await ProduceAsync`) | 2/2 | снята |
| K4 Нет идемпотентности producer | 2/2 | 0/2 | **название**, `n` 2/2 ревью |

| K7 Consumer без idempotency | 2/2 | 2/2 | снята (шаг 0) |

Вне скилла (RV-K): O1 (`Quantity + UnitPrice`) 2/2 в контроле, 2/2 в `n` и `o`; O2 (email клиента в логе) 2/2 везде.
Приманки: P2 (ключ `customerId` в `customers.touched`) 2/2 везде; P1 (`ReplaceOne` с upsert) - дефект ключа выше, 1/2 в
контроле, 2/2 в `n`, 1/2 в `o`.

**Исход K8.** Название «Ядовитое сообщение блокирует партицию потребителя» не изменило код: в `n1`, `n2` нечитаемое сообщение
по-прежнему уходило в `.dlq` сразу, а сбой обработки повторялся на месте бесконечно (спорная клетка: исполнитель считал такие
сбои временными). Ступень 3 (обязательный исход: после ограниченного числа попыток - разбор с содержимым и причиной, смещение
движется; повтор на месте без предела не освобождает партицию) дала 2/2 в коде (`g-k-o1`, `g-k-o2`) и 2/2 в ревью
(`rv-k-o1`, `rv-k-o2`). Факт версии (ступень 2) не вводился: в Confluent.Kafka 2.16.0 встроенного DLT нет, исход описывает
поведение, а не API; сверка с документацией клиента - отсутствие такого API в пакете, источника с нормой «N попыток» нет,
число попыток в пункт не пишется.

**Единицы с регрессией на редакции.** Клетки единиц, не входящих в пункты (K3 `rv-k-o1`: Flush не назван; P1 `rv-k-o2`),
не хуже контроля в пределах шума при n=2 (K3: контроль 2/2, `n` 2/2, `o` 1/2; P1: контроль 1/2). Решение по K3 - в «Открыто».

## Открыто

- **K3** (Flush): контроль 2/2 в ревью, `o1` не назвал; пункт не возвращается (одна клетка из шума n=2), решение владельцу.
- **K8, ступень 3:** исход без источника в документации клиента; число попыток не названо намеренно.
- **Расхождение с донором `microservices`** по B4 (код 0/2) и B9 (G-B `c1`) - оба держатся в `rabbitmq`; вопрос владельцу,
  принимается ли замер в коде за свидетельство против вердикта ревью дизайна.
- **Судья и спорные клетки.** Решения оператора по спорным клеткам - в таблицах `judge/`; буквальное чтение ключа применено
  ко всем (в частности B1: `Nack` с возвратом при транзиентной ошибке засчитан - провал по ключу только `autoAck: true`).
- **N-RV не чист** и приманки Kafka P1 и MongoDB P1 ломаются в контроле (см. выше); чистая ветка для следующей группы -
  вне этой работы.
- Контроль без `docker compose`: рантайм-эффекты (потеря сообщений при крахе, ребаланс) не наблюдались, судилось по коду.
