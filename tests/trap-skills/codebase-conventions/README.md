# codebase-conventions: сжатие по свидетельству, группа 0

Скилл `dex-skill-codebase-conventions` 1.10.0 ([`inputs/SKILL-1.10.0.md`](inputs/SKILL-1.10.0.md)),
эпик #291, группа 0 (#292). Вход - общий мини-проект [`_projects/billing`](../_projects/billing/README.md),
ключ там же. Исполнитель - sonnet (нижний тир потребителей: `dotnet-coder`, `self-reviewer`),
субагент без `Skill` tool, сборка и dotnet разрешены. Прогон со скиллом подаёт копию `SKILL.md` путём.

Модель. Первый заход (2026-10-04, коды без `-p`) шёл алиасом `sonnet`; полный ID, effort и набор
MCP не записаны. Алиас с 28.09.2026 разрешается в `claude-sonnet-5-5` (эпик #291), и перепрогон кейса A
набора fact-verification это подтверждает: на `claude-sonnet-5-5` он повторяет выходы заходов
(KA1-KA3 2/2), на `claude-sonnet-5` - нет (KA3 1/4 на нетронутом пункте). Прогоны по ревью PR #312
(коды `*-p*`): `claude -p --effort high`, CLI 2.1.287, без пользовательских настроек и скиллов
(`--setting-sources project`, `--disable-slash-commands`, `--disallowedTools Skill`), без MCP
(`--strict-mcp-config`); модель - в легенде кодов. Вердикт - по `claude-sonnet-5-5` (эпик #291,
решение 1: калибруется пара, которую получают sonnet-потребители); `claude-sonnet-5` - справочно.
Потребитель `dotnet-coder` идёт с effort по умолчанию, прогоны - с high.

Засчитывание. Находка засчитывается за ловушку, если стоит в месте ключа и её исход снимает дефект
ключа или его симптом; слово ловушки в находке не требуется (шаг 2 метода: применение, а не
упоминание). По этому правилу KG засчитан перестановкой аргументов без typed-id, KN - выносом
правила замены из `AddAsync` либо сменой имени. Единица снимается, если её применили все прогоны
контроля; прогон со скиллом, где пункта нет, - сверка охвата (шаг 6 эпика), не вердикт.

  создаёт второй.»

Ось 6 и свод. Репозиторий кейсов мал: все ADR и свод читаются одной командой, контроль не мерил
поиск источника - то, ради чего эти пункты существуют. По шагу 2 эпика это `unverifiable`: в такой
среде контроль проходит тривиально и снятием не засчитывается. Пункты остаются названиями до кейса
на большом репозитории - #311. Это правило эпика, а не отступление: вердикт «открыто», не «снята».

Пункт об имени. Контроль на R2 не назвал имя `AddAsync` ни в одном из 4 прогонов, но во всех 4
предложил вынести правило замены из `AddAsync` в `CreateInvoiceHandler` и нашёл, что через
`SaveAsync -> AddAsync` новое поведение получают оплата и отмена. Это второй исход, который пункт
1.11.0 сам называл верным, - по засчитыванию выше контроль 4/4, пункт снят. В R2 исход
достигается через находку о слое; случай, где поведение сменилось в верном слое, кейсом не мерен.

Модель. R4 разводит две модели: `claude-sonnet-5` пропускает KI, KY и KF, которые
`claude-sonnet-5-5` применяет сам. Под `claude-sonnet-5` нужны были бы ещё два названия - редакция
[`SKILL-p2.md`](inputs/SKILL-p2.md) дала на `pg` KF, KI, KW, KE 2/2, KY 0/2.

## Дефекты кейсов

- R1: `CreateInvoiceHandler` стал upsert, doc-комментарий `NotificationRequest` назвал Mailer. Ключ
  спорный: create-or-update заявлен в описании MR, тип - проводной контракт Mailer. Из ключа R1
  выведены, предмет перенесён в R2.
- R2: doc-комментарий `Invoice` называл несуществующего потребителя («выгрузка в отчёт финансового
  отдела»), находка смешивала предмет ловушки с ложностью утверждения. Заменён реальными хендлерами,
  перепрогон - `r2b`.
- R0: `QuoteInvoiceQuery` и новый `InvoiceQuote` - пара с разным порядком слов, тот же случай, что
  KW, не засеянный. Находка по нему (`r0-pq1:7`, `r0-pr1:6`) верна и ложной не считается; «ничего
  не менять» R0 держит для ADR-пунктов (приманки ADR-0005, ADR-0007).
- R4: верные находки вне ключа - стандартный конвейер повторяет POST без ключа идемпотентности,
  `documentId` не сохраняется, `body!` без проверки, `BaseAddress` без завершающего `/`; дописаны
  после прогонов, в счёт ловушек не идут.
