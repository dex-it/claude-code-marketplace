среде контроль проходит тривиально и снятием не засчитывается. Пункты оставались названиями до кейса
на большом репозитории - #311; исход - в разделе «Заход: большой репозиторий».

Пункт об имени. Контроль на R2 не назвал имя `AddAsync` ни в одном из 4 прогонов, но во всех 4
предложил вынести правило замены из `AddAsync` в `CreateInvoiceHandler` и нашёл, что через
`SaveAsync -> AddAsync` новое поведение получают оплата и отмена. Это второй исход, который пункт
1.11.0 сам называл верным, - по засчитыванию выше контроль 4/4, пункт снят. В R2 исход
достигается через находку о слое; случай, где поведение сменилось в верном слое, кейсом не мерен.

Модель. R4 разводит две модели: `claude-sonnet-5` пропускает KI, KY и KF, которые
`claude-sonnet-5-5` применяет сам. Под `claude-sonnet-5` нужны были бы ещё два названия - редакция
[`SKILL-p2.md`](inputs/SKILL-p2.md) дала на `pg` KF, KI, KW, KE 2/2, KY 0/2.

## Дефекты кейсов

- R1: `CreateInvoiceHandler` стал upsert, doc-комментарий `NotificationRequest` назвал Mailer. Ключ
  спорный: create-or-update заявлен в описании MR, тип - проводной контракт Mailer. Из ключа R1
  выведены, предмет перенесён в R2.
- R2: doc-комментарий `Invoice` называл несуществующего потребителя («выгрузка в отчёт финансового
  отдела»), находка смешивала предмет ловушки с ложностью утверждения. Заменён реальными хендлерами,
  перепрогон - `r2b`.
- R0: `QuoteInvoiceQuery` и новый `InvoiceQuote` - пара с разным порядком слов, тот же случай, что
  KW, не засеянный. Находка по нему (`r0-pq1:7`, `r0-pr1:6`) верна и ложной не считается; «ничего
  не менять» R0 держит для ADR-пунктов (приманки ADR-0005, ADR-0007).
- R4: верные находки вне ключа - стандартный конвейер повторяет POST без ключа идемпотентности,
  `documentId` не сохраняется, `body!` без проверки, `BaseAddress` без завершающего `/`; дописаны
  после прогонов, в счёт ловушек не идут.
