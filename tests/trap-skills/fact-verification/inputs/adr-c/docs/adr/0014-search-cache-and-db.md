# ADR-0014: Кэш поиска на прокси и платформа БД каталога

Статус: предложено
Дата: 2026-09-24

## Контекст

Сервис Catalog.Search отдаёт выдачу поиска по каталогу (около 1,2 млн товаров). Запрос поиска -
`POST /search` с телом JSON: строка запроса, фильтры (категория, цена, наличие), сортировка,
страница. Пиковая нагрузка - 900 RPS, 70% запросов - первые страницы популярных запросов. База -
PostgreSQL 13 на управляемом кластере, миграции применяет Flyway: каждая миграция выполняется в
своей транзакции. В выдаче показываются цена и признак «в наличии»; остатки обновляются из WMS
потоком событий, в среднем раз в 2-3 минуты по популярному товару.

## Решение

1. **Кэш выдачи на reverse-proxy.** Ответы `POST /search` кэшируются на прокси (nginx) на 60 секунд.
   Основание: по RFC 9110, раздел 9.3.3, ответы на POST кэшируемы, поэтому прокси вправе отдать
   сохранённый ответ на повторный POST. Ключ кэша - метод и URI запроса. Сервис выставляет
   `Cache-Control: max-age=60`. Инвалидация не нужна: TTL 60 секунд достаточно мал.
2. **Ошибки** отдаются в формате `application/problem+json` по RFC 9457 (заменила RFC 7807).
3. **Индекс под фильтр наличия.** Миграция `V41__search_in_stock_idx.sql` создаёт индекс
   `CREATE INDEX CONCURRENTLY idx_items_in_stock ON items (category_id, price) WHERE in_stock;`
   штатным порядком Flyway, чтобы не блокировать запись в `items` на время построения.
4. **Платформа БД.** Остаёмся на PostgreSQL 13: это поддерживаемая сообществом версия, плановое
   обновление мажорной версии переносим на 2027 год, когда закончится заморозка платформы.

## Последствия

- Нагрузка на сервис поиска снижается примерно в 3 раза за счёт попаданий в кэш прокси.
- Выдача может отставать от каталога не более чем на 60 секунд.
- Индекс строится без блокировки записи.
