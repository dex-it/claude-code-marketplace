# Ревью MR: списание баллов лояльности

Область: весь каталог (новый код) - `app/redeem.py`, `app/repo.py`, `app/db.py`, `app/schemas.py`, `app/__init__.py`, `requirements.txt`.
Стек: fastapi==0.95.2, pydantic==1.10.13 (v1), SQLAlchemy==1.4.49.

## Blocker

### 1. `app/schemas.py:15` - `confirm_amount: Optional[Decimal]` не required, вопреки комментарию строк 11-14
Комментарий утверждает: "Optional без значения по умолчанию делает поле обязательным, поэтому старые клиенты... получат 422". Это неверно для pydantic 1.10 (v1): аннотация `Optional[X]` без явного `= ...` получает **неявный дефолт `None`**, а не становится required.
Источник: pydantic v1 docs / migration guide - "a type annotated as `Any` or wrapped by `Optional` would be given an implicit default of `None` even if no default was explicitly specified" (это поведение убрано только в v2). Required нужен явный `Optional[Decimal] = ...`.
Чем кончится: старый клиент, не знающий о поле `confirm_amount`, не получает 422 - запрос проходит с `confirm_amount = None`, что по `redeem.py:21-22` трактуется как "списать весь баланс". Т.е. вместо отказа старому клиенту система списывает 100% баллов без его согласия - обратное тому, что задумано автором и записано в комментарии.

### 2. `app/redeem.py:11,20,28` - `POINT_VALUE = 0.1` (float) конвертируется в `Decimal` из float, а не из строки
`Decimal(0.1)` не даёт `Decimal('0.1')`, а даёт точное бинарное представление `0.1000000000000000055511151231257827021181583404541015625` (документация `decimal`: "the binary floating-point value is losslessly converted to its exact decimal equivalent"; для 0.1 в примерах документации: `Decimal(0.1) == Decimal('0.1000000000000000055511151231257827021181583404541015625')`).
Чем кончится: при явном `confirm_amount`, заданном клиентом как точная десятичная сумма (например `"10.00"` при балансе 100 баллов = 10.00 руб по "грязному" `POINT_VALUE`), деление `amount / Decimal(POINT_VALUE)` даёт `99.999999999999999...`, а `int()` truncates к `99` вместо `100`. Клиент, запросивший полное списание явной суммой (а не `null`), теряет на 1 балл меньше, чем должен - расхождение накапливается на каждой операции и ломает инвариант "сумма списанных баллов == сумма выплаченных денег". `POINT_VALUE` должен конструироваться как `Decimal("0.1")`.

### 3. `app/schemas.py:15` (используется в `app/redeem.py:21-28`) - нет валидации `confirm_amount >= 0`
Поле объявлено просто `Optional[Decimal]`, без `Field(ge=0)`/`condecimal(ge=0)`. Проверка `amount > balance` (`redeem.py:25`) отрицательное значение пропускает (оно всегда `<= balance`).
Чем кончится: клиент может отправить `confirm_amount: -1000`. `member.points -= int(amount / Decimal(POINT_VALUE))` при отрицательном `amount` даёт отрицательное вычитаемое, т.е. `points` увеличивается. Эндпоинт, названный "списание", позволяет накрутить баланс произвольно большим отрицательным `confirm_amount` - прямая уязвимость бизнес-логики/безопасности.

### 4. `app/repo.py:16-29` + `app/redeem.py:16-29` - чтение и запись баланса в разных транзакциях без блокировки, race condition
`get_member` (`repo.py:16-21`) читает баланс в одном `engine.connect()`, `save_member` (`repo.py:24-29`) пишет в отдельном `engine.begin()` без `SELECT ... FOR UPDATE`, без проверки версии/оптимистичной блокировки, без охвата чтения+записи одной транзакцией. Между чтением и записью нет никакой синхронизации.
Чем кончится: два параллельных запроса `redeem` для одного `member_id` оба читают одинаковый исходный баланс, оба проходят проверку `amount > balance`, оба пишут `UPDATE members SET points = :p` с рассчитанным на устаревшем балансе значением - lost update. Классический double-spend: клиент, отправив два одновременных запроса на полное списание, может списать баланс лишь один раз "по факту", но получить выгоду (или наоборот эффективное дублирование при частичном списании) в зависимости от порядка коммитов. Для денежного эквивалента баллов это прямая финансовая дыра.

## Major

### 5. `app/schemas.py:16-17` - комментарий про отказ лишних полей не соответствует дефолту pydantic v1
Комментарий: "Лишние поля pydantic по умолчанию отвергает, так что опечатка в имени поля у клиента даст 422". Дефолт `Config.extra` в pydantic v1/v2 - `Extra.ignore` ("whether to ignore, allow, or forbid extra attributes... default: `Extra.ignore`", докстрока pydantic). В `RedeemRequest` нет `class Config: extra = "forbid"`.
Чем кончится: опечатка в имени поля у клиента (например `comfirm_amount`) не даёт 422, а молча игнорируется - поле `confirm_amount` останется незаданным и (см. находку 1) даст `None` -> полное списание баланса вместо ошибки валидации, которую комментарий обещает.

### 6. `app/redeem.py:29-30` (реализация - `app/repo.py:24-37`) - обновление баланса и запись аудита - разные транзакции
`save_member` и `write_audit` - два отдельных `engine.begin()`. Между ними нет ничего, что гарантирует атомарность.
Чем кончится: если процесс упадёт (или БД разорвёт соединение) между `save_member` и `write_audit`, баланс уже списан, а аудиторской записи операции не будет. Описание MR явно называет "аудит операции" частью фичи - именно этот случай (списание без следа в аудите) остаётся неприкрытым.

### 7. `app/redeem.py:32-38` - "срок действия баллов" не реализован, только фиктивно вычисляется
`Member` (`repo.py:11-13`) хранит только `id, points` - нет даты начисления, даты последнего списания или срока годности баллов в БД. `valid_until = date.today() + timedelta(days=365)` (`redeem.py:33`) вычисляется от текущей даты запроса всегда одинаково и никак не привязан к истории конкретных баллов; никакой проверки "не просрочены ли списываемые баллы" в коде нет вообще.
Чем кончится: описание MR обещает "срок действия баллов" как часть фичи; фактически API возвращает клиенту дату, которая ничего не отражает (всегда "сегодня+365", независимо от того, когда баллы реально были начислены) и не используется для отказа в списании просроченных баллов. Потребитель API, доверяющий полю `valid_until`, получает недостоверную информацию.

### 8. `app/schemas.py:10` (`points: int`) - поле объявлено, но не используется в `app/redeem.py`
`redeem.py` использует только `req.member_id` и `req.confirm_amount`; `req.points` не читается ни для валидации, ни для сверки с `confirm_amount`, только попадает в аудит через `req.dict()` (`redeem.py:30`).
Чем кончится: клиент обязан прислать `points`, но это поле никак не влияет на списание и не проверяется на согласованность с `confirm_amount` (клиент может прислать `points=1` и `confirm_amount=9999` - расхождение не отследится). В аудит-лог пишется значение, которое выглядит как "количество списанных баллов", но не является таковым - это создаёт ложное свидетельство при последующем разборе инцидентов по аудиту.

### 9. `app/redeem.py:14-18` - эндпоинт `/redeem` не проверяет право вызывающего на `member_id`
В роуте нет `Depends(...)` для аутентификации/авторизации, `member_id` берётся напрямую из тела запроса без сверки с текущим пользователем. В предоставленном коде (весь каталог - новый код к MR) какого-либо auth-слоя не видно.
Чем кончится: если авторизация не подключена выше по стеку (не входит в этот MR), любой вызывающий может списать баллы произвольного `member_id` - IDOR на денежном эквиваленте. Если авторизация действительно реализована в другом, не входящем в этот MR компоненте - находка снимается, но в текущем диффе такого свидетельства нет.

## Minor

### 10. `app/schemas.py:10` - `points: int` без ограничения `ge=0`
Поле не используется (см. находку 8), но раз оно есть в контракте и обязательно - на него нет валидации знака/диапазона. Раз поле мёртвое, это не эксплуатируется напрямую, но усиливает путаницу контракта: непонятно, что и когда должно проверяться по `points`.
