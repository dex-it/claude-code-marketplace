# Ревью ADR-0014: Кэш поиска на прокси и платформа БД каталога

## Находка 1 - Ключ кэша игнорирует тело POST-запроса

**Пункт ADR:** п.1 «Кэш выдачи на reverse-proxy» - «Ключ кэша - метод и URI запроса.»

**Что не так:** `POST /search` несёт весь смысл запроса в теле (строка запроса, фильтры, сортировка,
страница) - URI у всех запросов один и тот же. Ключ «метод + URI» не различает разные поисковые
запросы. Ссылка на RFC 9110 §9.3.3 верна лишь в узком смысле - спецификация допускает кэшировать
ответ на POST при явной freshness-информации (`Cache-Control: max-age=60` эту часть закрывает), но
сам механизм подбора сохранённого ответа описан в RFC 9111 §2 и §4: по умолчанию сравниваются метод,
URI и заголовки, названные в `Vary`; тело запроса в сравнении не участвует и механизма варьировать
кэш по телу в HTTP-кэшировании нет вовсе (проверено по тексту RFC 9111). Nginx это поведение не
меняет - `proxy_cache_key` по умолчанию не включает тело, и даже с добавлением `$request_body` в
ключ нужна отдельная явная настройка, которой в решении нет. Плюс кэширование POST у nginx само по
себе не включено по умолчанию (`proxy_cache_methods` по умолчанию `GET HEAD`) - директивы
`proxy_cache_methods POST;` в решении не названо.

**Чем кончится:** первый пришедший на данный URI запрос кэширует ответ на 60 секунд, и все
последующие запросы с другим текстом запроса, фильтрами, сортировкой или номером страницы получат
чужую закэшированную выдачу - пользователь увидит результаты не своего поиска. Заявленное в
«Последствиях» снижение нагрузки «примерно в 3 раза» при этом дефекте будет фактически куда выше
(кэш почти всегда «хитует», раз ключ не зависит от тела), но ценой массово неверной выдачи, а не
ускорения. Если же `proxy_cache_methods POST` не включена отдельно - кэш просто не работает, и
эффект по нагрузке не возникает вовсе.

**Severity:** blocker.

## Находка 2 - CREATE INDEX CONCURRENTLY внутри транзакционной миграции Flyway

**Пункт ADR:** п.3 «Индекс под фильтр наличия» + Контекст: «миграции применяет Flyway: каждая
миграция выполняется в своей транзакции.»

**Что не так:** `CREATE INDEX CONCURRENTLY` в PostgreSQL не может выполняться внутри блока
транзакции - это документированное ограничение самого `CREATE INDEX CONCURRENTLY` (ошибка
`CREATE INDEX CONCURRENTLY cannot run inside a transaction block`). Контекст ADR прямо говорит, что
у Flyway в этом проекте каждая миграция идёт в своей транзакции - «штатный порядок Flyway»,
на который решение ссылается, этому условию противоречит. Никакой оговорки про
non-transactional/mixed-режим для этой миграции в решении нет.

**Чем кончится:** миграция `V41__search_in_stock_idx.sql` упадёт при первом же прогоне с ошибкой
БД - индекс не создастся, деплой миграции остановится (Flyway помечает миграцию failed). При
повторной попытке без явной уборки останется risk оставить `invalid`-индекс, требующий ручного
`DROP INDEX` перед повтором - тоже не описано в решении.

**Severity:** blocker.

## Находка 3 - PostgreSQL 13 названа «поддерживаемой сообществом» версией

**Пункт ADR:** п.4 «Платформа БД» - «Остаёмся на PostgreSQL 13: это поддерживаемая сообществом
версия, плановое обновление мажорной версии переносим на 2027 год.»

**Что не так:** PostgreSQL 13 вышла 2020-09-24, и по политике версионирования PostgreSQL (5 лет
поддержки на мажорную версию) вышла из community support 2025-11-13 (сверено по
postgresql.org/support/versioning - EOL 2025-11-13, текущая минорная 13.23, статус «not
supported»). На дату ADR (2026-09-24) версия уже почти год как не получает патчей безопасности от
сообщества - утверждение о поддерживаемости фактически неверно.

**Чем кончится:** решение продлевает работу на неподдерживаемой версии БД (без security-фиксов) ещё
на срок до обновления в 2027 году - это больше года без патчей для новых CVE на управляемом
кластере с 1,2 млн товаров и 900 RPS. Обоснование «поддерживаемая версия» ложное, и «заморозка
платформы» не сопровождается компенсирующей мерой (например, переходом на последний доступный
минорный релиз 13.x или отдельным риск-приёмочным решением).

**Severity:** blocker.

## Находка 4 - Не рассмотрен cache stampede при истечении TTL популярного запроса

**Пункт ADR:** п.1 «Кэш выдачи на reverse-proxy» (60 секунд TTL, 70% нагрузки - первые страницы
популярных запросов, пик 900 RPS).

**Что не так:** решение не упоминает защиту от одновременного промаха кэша по горячему ключу
(`proxy_cache_lock` у nginx или аналог). При 900 RPS и концентрации 70% трафика на популярных
первых страницах, момент истечения TTL для такого ключа означает, что все конкурентные запросы к
нему в этот момент одновременно уходят в backend, а не один запрос с блокировкой остальных.

**Чем кончится:** каждые 60 секунд по каждому горячему запросу - всплеск нагрузки на
Catalog.Search, кратный числу конкурентных клиентов этого запроса за такт TTL. Заявленное «снижение
нагрузки примерно в 3 раза» - это усреднённая оценка, которая не учитывает пиковые всплески именно
в момент истечения TTL, то есть именно тогда, когда защита от нагрузки нужнее всего.

**Severity:** major.

## Находка 5 - «Последствия» недооценивают реальную задержку данных для пользователя

**Пункт ADR:** «Последствия» - «Выдача может отставать от каталога не более чем на 60 секунд.»

**Что не так:** формулировка отсчитывает задержку только от кэша прокси и игнорирует уже названную
в Контексте задержку выше по потоку - обновление остатков из WMS происходит «в среднем раз в 2-3
минуты по популярному товару». Итоговая задержка от физического изменения остатка до показа
пользователю - это сумма задержки WMS-потока (2-3 минуты, и это средняя, не максимальная величина)
и до 60 секунд кэша прокси, а не изолированные 60 секунд.

**Чем кончится:** читатель ADR (например, бизнес-заказчик или на онколл при инциденте с «висящим
наличием») получит неверное представление о максимальной задержке данных и будет ориентироваться на
60 секунд там, где реальная цифра кратно больше.

**Severity:** minor.

## Находка 6 - Отсутствуют рассмотренные альтернативы

**Пункт ADR:** документ целиком - раздел с альтернативами и их trade-off отсутствует.

**Что не так:** ни для одного из четырёх пунктов решения не показано, какие варианты были
рассмотрены и почему отклонены. Особенно заметно для п.4 (заморозка мажорной версии до 2027) - не
обсуждён даже минимальный компенсирующий шаг (обновление на последнюю минорную версию 13.x для
получения патчей безопасности в рамках той же мажорной версии).

**Чем кончится:** решение непроверяемо на полноту рассмотрения - при пересмотре или ревизии ADR
никто не может понять, взвешивалась ли цена альтернативы или же альтернатива просто не
рассматривалась.

**Severity:** minor.

## Находка 7 - Партиционированный индекс на часто меняющемся предикате

**Пункт ADR:** п.3 - `CREATE INDEX CONCURRENTLY idx_items_in_stock ON items (category_id, price)
WHERE in_stock;`

**Что не так:** предикат индекса (`in_stock`) - тот самый столбец, который по Контексту обновляется
потоком событий из WMS каждые 2-3 минуты по популярным товарам. Каждое такое обновление у строки,
меняющей `in_stock`, означает вход или выход строки из партиционированного индекса (эффективно
удаление+вставка записи индекса). Решение не упоминает эффект на bloat/vacuum индекса при таком
профиле обновлений на 1,2 млн строк.

**Чем кончится:** индекс будет расти мёртвыми записями быстрее обычного B-tree на статичном
предикате, потенциально требуя более частого `REINDEX`/агрессивного autovacuum, что не заложено в
план сопровождения.

**Severity:** minor.
