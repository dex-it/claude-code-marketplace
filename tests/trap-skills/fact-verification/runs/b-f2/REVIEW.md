# Review: списание баллов лояльности (redeem)

Область: весь каталог - новый код. Ревью кода без правок, факты о поведении pydantic 1.10.13
(версия из `requirements.txt`) сверены с официальной документацией/migration guide (WebFetch,
docs.pydantic.dev, redirect на pydantic.dev/docs/validation/1.10/...) и migration-guide v1->v2.

## Blocker

### 1. `app/schemas.py:11-15` - комментарий про "Optional без default = обязательное поле" неверен для запинённой версии pydantic
```python
11:    # Обязательное поле: клиент обязан прислать его явно - сумму частичного
12:    # списания либо null, если списывается весь баланс. Optional без значения
13:    # по умолчанию делает поле обязательным, поэтому старые клиенты, которые
14:    # его не знают, получат 422 и будут вынуждены обновиться.
15:    confirm_amount: Optional[Decimal]
```
Что не так: в Pydantic v1 (проект пинует `pydantic==1.10.13`) поле, аннотированное как
`Optional[X]` без явного значения, получает **неявный default `None`** - это документированное
поведение v1, изменённое только в v2 ("In Pydantic V1, fields annotated with Optional or Any
would be given an implicit default of None even if no default was explicitly specified" -
migration guide v1->v2; чтобы сделать такое поле обязательным в v1, нужен `Optional[X] = ...`).
Комментарий описывает поведение v2, а не установленной v1.10.13; в коде нет `= ...` и нет
`Config`, меняющего это поведение.
Чем кончится: клиент, который вообще не передаёт ключ `confirm_amount` (старый клиент из
комментария, либо просто клиентский баг), НЕ получит 422. Запрос пройдёт с
`confirm_amount = None` и попадёт в ветку "списываем весь баланс" (`app/redeem.py:21-22`) -
у пользователя списываются вообще все баллы вместо ожидаемого частичного списания или ошибки.
Severity: blocker (некорректное списание всей суммы вместо предполагаемой валидации).

### 2. `app/redeem.py:21-28` (вход `app/schemas.py:15`) - нет проверки `confirm_amount >= 0`
Что не так: `confirm_amount: Optional[Decimal]` не ограничен `Field(ge=0)` ни где-либо ещё.
Отрицательное значение проходит проверку `amount > balance` (строка 25) - отрицательное число
всегда `<= balance`, ветка `raise HTTPException(409)` не срабатывает.
Чем кончится: на строке 28 `member.points -= int(amount / Decimal(POINT_VALUE))` при
отрицательном `amount` вычитает отрицательное число, то есть **начисляет** баллы. Клиент,
отправивший `confirm_amount: -100`, увеличивает свой баланс баллов вместо списания - произвольная
эмиссия баллов через публичный контракт списания.
Severity: blocker.

### 3. `app/repo.py:16-29` + `app/redeem.py:16-29` - чтение и запись баланса не атомарны, нет блокировки строки
Что не так: `get_member` (repo.py:16-21) открывает своё соединение и читает `points`;
обработчик (redeem.py) считает новый баланс в Python; `save_member` (repo.py:24-29) в отдельной
транзакции делает `UPDATE members SET points = :p` - абсолютным значением, не атомарным
декрементом (`SET points = points - :delta`), и без `SELECT ... FOR UPDATE` / any locking между
чтением и записью.
Чем кончится: классический TOCTOU/lost-update. Два параллельных запроса `/redeem` на одного
`member_id` оба читают один и тот же баланс, оба проходят проверку "хватает баллов", оба пишут
своё независимо посчитанное значение `points` - итоговое значение в БД равно результату
последнего `UPDATE`, второе списание "съедает" эффект первого (или наоборот member уходит в
overdraft, если оба списания были частичными и рассчитывались от одной стартовой суммы).
Severity: blocker (потеря или задвоение денег/баллов под конкурентной нагрузкой - обычный
сценарий для эндпоинта списания).

### 4. `app/redeem.py:11,20,28` - `POINT_VALUE = 0.1` как float, `Decimal(POINT_VALUE)` даёт неточное значение
```python
11: POINT_VALUE = 0.1  # рублей за балл
...
20:    balance = Decimal(member.points) * Decimal(POINT_VALUE)
...
28:    member.points -= int(amount / Decimal(POINT_VALUE))
```
Что не так: `Decimal(0.1)` строит Decimal из точного бинарного представления float `0.1`, а не из
десятичного литерала - получается `Decimal('0.1000000000000000055511151231257827021181583404541015625')`,
а не `Decimal('0.1')`. Правильно - `Decimal("0.1")`.
Чем кончится: `balance` и промежуточные частные (`amount / Decimal(POINT_VALUE)`) получают
"мусорный" хвост после запятой. В паре с усечением `int()` на строке 28 (см. находку 6) это даёт
систематическое расхождение между тем, сколько денег/баллов клиент видит в ответе, и сколько
реально списывается со счёта - причём расхождение накапливается с каждым частичным списанием.
Severity: blocker (искажение денежной величины в самой сути операции списания).

## Major

### 5. `app/redeem.py:29-30` / `app/repo.py:24-37` - изменение баланса и запись аудита не в одной транзакции
Что не так: `save_member` (repo.py:24-29) и `write_audit` (repo.py:32-37) - два отдельных
`engine.begin()`, то есть две отдельные транзакции. Между вызовом `save_member(member)` и
`write_audit(...)` в `redeem.py:29-30` нет ничего, что гарантирует совместный commit/rollback.
Чем кончится: если процесс упадёт или БД станет недоступна между этими двумя вызовами, баланс
члена программы лояльности уже изменён, а запись в аудит не появится - ровно тот случай, для
которого аудит и заводится (реконструкция происшедшего). Нарушает заявленную в MR фичу "аудит
операции" при частичном отказе.
Severity: major.

### 6. `app/redeem.py:28` - усечение `int()` вместо валидации кратности/явного округления
```python
28:    member.points -= int(amount / Decimal(POINT_VALUE))
```
Что не так: если `amount` не кратен `POINT_VALUE` (клиент прислал, например,
`confirm_amount = Decimal("5.05")`), `amount / Decimal(POINT_VALUE)` даёт дробное число баллов,
и `int()` **обрезает** дробную часть в сторону нуля, а не округляет и не отвергает такой запрос.
Чем кончится: реально списывается меньше баллов, чем соответствует возвращённой в ответе сумме
`redeemed` (строка `redeemed=amount` в `RedeemResult`) - клиент получает в ответе "списано 5.05",
а с баланса эквивалент вычтен только на 5.00; сумма расхождения "теряется" (не списывается и не
возвращается) при каждом нецелом-в-баллах partial redeem.
Severity: major (усиливает находку 4, отдельная точка входа - отсутствие валидации кратности).

### 7. `app/redeem.py:30` - аудит не фиксирует фактически списанную сумму при полном списании
```python
30:    write_audit(member.id, req.dict())
```
Что не так: в аудит пишется только сериализованный входящий запрос (`req.dict()`), а не
рассчитанные `amount`/`balance_left`. Когда `confirm_amount is None` (клиент просит списать весь
баланс, строка 21-22), в записи аудита будет `confirm_amount: null` - фактически списанная сумма
(`amount`, посчитанная как весь `balance`) в аудит не попадает вовсе.
Чем кончится: по записи аудита для полного списания невозможно восстановить, сколько баллов/денег
было списано - именно тот кейс ("списываем весь баланс"), который проще всего перепутать при
разборе инцидента. Ломает заявленную фичу "аудит операции" в самом частом/рискованном сценарии.
Severity: major.

### 8. `app/schemas.py:16-18` - комментарий про поведение pydantic на лишних полях не соответствует дефолту v1.10.13
```python
16:    # Лишние поля pydantic по умолчанию отвергает, так что опечатка в имени
17:    # поля у клиента даст 422, а не молчаливое игнорирование.
18:    comment: Optional[str] = None
```
Что не так: дефолт `Config.extra` в Pydantic v1 - `Extra.ignore` ("`'ignore'` will silently ignore
any extra attributes" - официальная документация 1.10). Ни в `RedeemRequest`, ни где-либо ещё в
файле не задан `class Config: extra = Extra.forbid`, который бы дал заявленное поведение.
Чем кончится: опечатка в имени поля у клиента (например, `commnet` вместо `comment`, или
устаревшее имя поля) не даст 422, как обещано в комментарии, а будет тихо проигнорирована -
поле-опечатка теряется без следа, а разработчик, читающий комментарий, ошибочно считает контракт
защищённым от такого класса ошибок.
Severity: major.

### 9. `app/redeem.py:15-16` / `app/schemas.py:10` - поле `points` из запроса принимается, но не используется
Что не так: `RedeemRequest.points: int` (schemas.py:10) - обязательное поле без валидации, но в
обработчике `redeem()` (redeem.py) оно ни разу не читается: расчёт полностью идёт через
`confirm_amount`/`balance`, вычисленный из `member.points` в БД.
Чем кончится: контракт публичного эндпоинта списания баллов содержит обязательное поле, не влияющее
ни на что - клиент обязан его прислать (иначе 422 по required), но любое значение (в т.ч.
не совпадающее с фактическим намерением или текущим балансом) молча принимается. Как минимум
дезориентирует клиентов и ревьюеров контракта; как максимум - признак недописанной логики
(например, ожидавшейся проверки "запрошено списать N баллов, но сервер посчитал иначе").
Severity: major.

### 10. Нет защиты от повторной отправки запроса (idempotency)
Что не так: `RedeemRequest` (`app/schemas.py`) не содержит idempotency-ключа, `write_audit`/
`save_member` (`app/repo.py`) не делают проверку на дубликат операции.
Чем кончится: при таймауте/сетевом сбое между сервером и клиентом клиент, не получивший ответ,
типично повторяет запрос - повторный `/redeem` с тем же `confirm_amount` списывает баллы ещё раз
(эндпоинт не идемпотентен по построению, а не только из-за конкурентности - находка 3 отдельно
про параллельность, эта - про повтор одного и того же запроса последовательно во времени).
Severity: major.

### 11. Заявленная в описании MR фича "срок действия баллов" не реализована
Что не так: описание MR называет "срок действия баллов" отдельной фичей. В коде это сведено к
вычислению `valid_until = date.today() + timedelta(days=365)` (`app/redeem.py:33`) - значение,
которое ни от чего не зависит (не привязано к дате начисления конкретных баллов), никуда не
сохраняется (`write_audit` его не получает) и ни на что не влияет при следующем списании. Таблица
`members`, судя по SQL в `app/repo.py:19,27` (`id, points`), не содержит колонки со сроком
действия/датой начисления. Эндпоинт списания не проверяет, не истекли ли уже баллы на балансе,
перед тем как их списать.
Чем кончится: `valid_until` в ответе - декоративное поле, не подкреплённое ни хранимым состоянием,
ни проверкой при последующих операциях; фактического учёта срока действия баллов в системе нет,
хотя фича заявлена как реализованная.
Severity: major.

## Minor

### 12. `app/redeem.py:32-33` - расчёт `valid_until` расходится с собственным комментарием (off-by-one)
```python
32:    # Баллы действуют 365 дней с даты последнего списания, включая сегодняшний.
33:    valid_until = date.today() + timedelta(days=365)
```
Что не так: если период действия - 365 дней, **включая** сегодняшний день, последний действующий
день - `today + 364` (день 1 = сегодня, день 365 = today+364), а не `today + 365`.
Чем кончится: возвращаемая дата на 1 день больше, чем описывает сам комментарий - расхождение
между заявленным правилом и реализацией на границе периода действия.
Severity: minor.

### 13. `app/__init__.py` - пустой, роут `redeem.router` нигде не подключается к приложению
Что не так: файл пустой; в предоставленном каталоге нет ни создания `FastAPI()`, ни
`app.include_router(router)` для роутера из `app/redeem.py:9`.
Чем кончится: если это весь новый код фичи (как указано в постановке ревью) и подключение роута не
живёт вне этого каталога - эндпоинт `/redeem` не будет доступен ни в каком приложении. Отмечаю с
пометкой неопределённости: возможно, подключение сделано в файле вне этого MR/каталога.
Severity: minor.
