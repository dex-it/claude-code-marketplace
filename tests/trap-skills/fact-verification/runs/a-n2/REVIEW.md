# Review: Pricing.Api MR

Дисциплина: `dex-skill-fact-verification`. Факты о поведении библиотек ниже сверены с источником
(context7 недоступен - квота исчерпана; сверка через официальную документацию Microsoft Learn и
issue-трекер dotnet/runtime, ссылки в тексте находки).

---

## 1. `src/SupplierFeedParser.cs:8-10` - regex-вырезание комментариев корёжит валидный JSON

**Что не так.** Комментарий утверждает: «В System.Text.Json нет настройки, которая позволяет
пропускать комментарии» - это неверно. `JsonSerializerOptions.ReadCommentHandling` /
`JsonReaderOptions.CommentHandling` с значением `JsonCommentHandling.Skip` штатно пропускает `//`
и `/* */` комментарии при разборе, начиная с .NET Core 3.0 (System.Text.Json.JsonCommentHandling,
Microsoft Learn: `Skip = 1` - «Allows comments within the JSON input and ignores them»).

Вместо штатной опции код вырезает всё после первого `//` до конца строки регэксом
`@"//.*$"` (`RegexOptions.Multiline`). Это ловит не только комментарии поставщика, но и любую
подстроку `//` внутри JSON-строкового значения - в частности, `ImageUrl` того же MR
(`src/SupplierFeedParser.cs:22`) документирован примером `https://cdn.supplier.example/img/123.png`.
Начиная с `//` внутри `https://` регэкс вырезает всё до конца строки, включая закрывающую кавычку
и скобку - на выходе незакрытая JSON-строка.

**Чем кончится.** Любой реальный элемент фида с `ImageUrl` ломает `JsonSerializer.Deserialize` -
либо `JsonException` на всём документе (если фид на одной строке - обрезается всё, что после
первого URL), либо на конкретной строке (если фид с переносами). Парсер поставщика не разбирает
ровно те данные, для которых он написан.

**Severity: blocker.**

## 2. `src/PriceService.cs:22` - скидка не применяется из-за целочисленного деления

**Что не так.** `discountPercent` - `int`, `100` - `int`-литерал: `discountPercent / 100` -
целочисленное деление с усечением. Для любого `discountPercent` из диапазона 1-99 (проверка на
входе - `src/PricesController.cs:14` - разрешает 0..100) результат деления равен `0`, то есть
`discounted = basePrice - basePrice * 0 = basePrice`. Скидка отсутствует для всех значений, кроме
100 (тогда `100/100=1` и цена становится нулевой - товар «бесплатный»).

**Чем кончится.** Заявленная в MR фича «финальная цена со скидкой» не работает: клиент получает
полную цену при любом дисконте 1-99% и нулевую цену при 100%.

**Severity: blocker.**

## 3. `src/PriceService.cs:9-17` - `IMemoryCache.GetOrCreateAsync` не даёт single-flight, риск бана ключа поставщика

**Что не так.** Комментарий (`:7-8`) утверждает: «GetOrCreateAsync гарантирует, что фабрика
вызовется один раз на ключ даже при параллельных запросах». Это неверно для
`Microsoft.Extensions.Caching.Memory.CacheExtensions.GetOrCreateAsync` - метод делает
`TryGetValue`, и при промахе КАЖДЫЙ параллельный вызов проходит проверку и запускает фабрику
самостоятельно; синхронизации нет. Задокументировано как известное поведение в
dotnet/runtime issue #71581 («CacheExtensions.GetOrCreate{Async} thread-safety») и #36499
(«GetOrCreate is not atomic ... serious issue for a cache»): «If you call GetOrCreateAsync from
multiple threads the factory Func will be called multiple times».

`ISupplierClient.GetPriceAsync` (`src/Contracts.cs:5`) документирован жёстким лимитом: «не больше
5 запросов в секунду на ключ; превышение - бан ключа на час». При параллельных запросах на один
`sku` в момент промаха кэша (холодный старт, истечение 5-минутного TTL под нагрузкой) каждый из
них уходит к поставщику отдельным HTTP-запросом - всплеск конкурентных запросов на один и тот же
SKU способен пробить лимит 5 rps и забанить ключ на час, что кладёт получение цен вообще для всех
SKU, а не только для затронутого.

Примечание: в этом же MR используется `HybridCache` (`src/CatalogCache.cs`), у которого
stampede-защита встроена (single-flight по ключу) - именно её здесь и не хватает.

**Severity: blocker.**

## 4. `src/CatalogCache.cs:14-18` / `src/PricesController.cs:19-25` - инвалидация «по событию» ни к чему не подключена

**Что не так.** Комментарий на `InvalidateAsync` (`:14`) утверждает: «Вызывается из обработчика
события "каталог обновлён"». В этом MR (весь новый код) нет ни одного вызова
`InvalidateAsync` - `grep -rn InvalidateAsync .` находит только само определение метода. Нет и
обработчика события «каталог обновлён» как такового.

Единственный сигнал о смене данных в этом MR - `POST /prices/{sku}/notify`
(`src/PricesController.cs:19-25`), но он ничего не инвалидирует: ни кэш каталога
(`CatalogCache.InvalidateAsync`), ни кэш базовой цены (`PriceService`, ключ `price:{sku}` в
`IMemoryCache`) - он только шлёт HTTP-уведомление во внешний сервис `notifications`.

**Чем кончится.** Заявленная фича «кэш страниц каталога с инвалидацией по событию» не
реализована целиком: метод инвалидации существует, но ничто его не вызывает - кэш каталога живёт
до истечения TTL независимо от реальных изменений. Отдельно: после `notify` о смене цены
`GetFinalPriceAsync`/`GetBasePriceAsync` до 5 минут (TTL в `PriceService.cs:13`) продолжают
отдавать старую цену - уведомление о смене цены и фактическая цена в API расходятся.

**Severity: major.**

## 5. `src/PricesController.cs:19-25` - уведомление о смене цены без обработки отказа и с непроверенной регистрацией клиента

**Что не так.** Два связанных пробела в одном методе:

- `client.PostAsync($"/price-changed/{sku}", null, ct)` - относительный URI. Он резолвится только
  если у именованного клиента `"notifications"` где-то настроен `BaseAddress`
  (`IHttpClientFactory` / `AddHttpClient("notifications", ...)`). В этом MR (весь диапазон нового
  кода) такой регистрации нет ни в одном файле (`grep -rn notifications .` находит только точку
  вызова) - если она не задана и в непоказанной части приложения, вызов бросает
  `InvalidOperationException: ... BaseAddress must be set`.
- Результат `PostAsync` не проверяется (ни статус-код, ни исключение при сетевом отказе/таймауте
  внешнего сервиса) - падение или недоступность `notifications` роняет запрос целиком (500) без
  retry и без какого-либо способа узнать, дошло ли уведомление.

**Чем кончится.** Функция «уведомление о смене цены» либо не работает совсем (если
`BaseAddress` не сконфигурирован), либо работает без гарантии доставки - единичный сетевой сбой
теряет уведомление молча для клиента (кроме 500-го ответа) и без повтора.

**Severity: major.**

## 6. `src/PriceService.cs:23` - `Math.Round` по умолчанию округляет банковским способом

**Что не так.** `Math.Round(discounted, 2)` без явного `MidpointRounding` использует
`MidpointRounding.ToEven` («банковское» округление к чётной цифре) - для денежных сумм обычно
требуется `AwayFromZero`/«округление вверх», иначе цена на границе `x.xx5` округляется
непредсказуемо для наблюдателя (то вверх, то вниз, в зависимости от чётности предыдущей цифры).

**Чем кончится.** При исправлении находки №2 (целочисленное деление) финальная цена на некоторых
значениях скидки будет отличаться от ожидаемой на 1 копейку не в сторону, привычную для
прайсинга/бухгалтерии.

**Severity: minor.**

## 7. `src/CatalogCache.cs:7-12` - лишняя замыкающая аллокация вместо state-overload `HybridCache`

**Что не так.** Лямбда `async token => await repo.LoadPageAsync(page, token)` захватывает `page`
и `repo` через замыкание. `HybridCache.GetOrCreateAsync` имеет перегрузку с явным `TState`
(`GetOrCreateAsync<TState, T>(key, state, factory, ...)`), рекомендуемую именно для избежания
аллокации замыкания на каждый вызов делегата.

**Чем кончится.** Не дефект поведения - лишняя аллокация на каждый вызов `GetPageAsync`, заметно
только под высокой частотой запросов страниц каталога.

**Severity: minor.**
