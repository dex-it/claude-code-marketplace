# Ревью MR: Pricing.Api

В каталоге нет Program.cs и регистрации DI. Что регистрируется, судить нельзя, поэтому часть находок написана как условные.

## Blocker

### 1. src/PriceService.cs:22 — скидка не применяется из-за целочисленного деления
- **Что не так:** `discountPercent / 100` делится как `int / int`. Для 0..99 результат 0, для 100 результат 1.
- **Чем кончится:** финальная цена при скидке 1–99% равна базовой, при 100% равна 0. Клиенты не получают скидку, а скидка 100% даёт бесплатный товар. Тест на любую «обычную» скидку это покажет.
- **Исправление:** `basePrice * discountPercent / 100m`.

### 2. src/SupplierFeedParser.cs:10,14 — регэксп `//.*$` портит строковые значения JSON
- **Что не так:** регэксп вырезает всё от `//` до конца строки, не различая комментарии и содержимое строк. В `ImageUrl` по контракту лежит `https://cdn.supplier.example/...` (см. строку 22).
- **Чем кончится:** у каждого элемента фида с картинкой URL обрезается до `https:`, а закрывающая кавычка и запятая теряются. JSON становится невалидным, `Deserialize` бросает `JsonException`, и весь фид не разбирается.
- **Утверждение в комментарии неверно:** в System.Text.Json такая настройка есть. Это `JsonSerializerOptions.ReadCommentHandling = JsonCommentHandling.Skip`. Регэксп не нужен.

## Major

### 3. src/PriceService.cs:7-15 — нет защиты от «толпы» запросов, лимит поставщика будет превышен
- **Что не так:** комментарий неверен. `IMemoryCache.GetOrCreateAsync` не гарантирует однократный вызов фабрики. Параллельные запросы по одному промахнувшемуся ключу вызовут фабрику каждый. Лимит поставщика (`Contracts.cs:5`) — 5 запросов в секунду на ключ, превышение даёт бан ключа на час. Никакого ограничителя скорости нет.
- **Чем кончится:** при старте, после истечения 5-минутного TTL популярного SKU или при пачке разных SKU мы превысим лимит. Ключ API забанят на час, и цены перестанут отдаваться во всём сервисе.
- **Исправление:** single-flight на ключ (`SemaphoreSlim`/`Lazy<Task>` на ключ или `HybridCache.GetOrCreateAsync`, который склеивает параллельные вызовы) и общий rate limiter на вызовы поставщика.

### 4. src/PriceService.cs:11-14 — токен отмены запроса попадает в общую фабрику
- **Что не так:** `ct` первого запроса захватывается замыканием. Если клиент отключится, вызов поставщика отменится.
- **Чем кончится:** для других запросов, которые ждут этот же результат (после исправления п.3), будет `OperationCanceledException`. Сейчас это даёт лишние отменённые обращения к поставщику.
- **Исправление:** для общей фабрики использовать собственный токен или таймаут, а не токен конкретного запроса.

### 5. src/PricesController.cs:12-15, src/PriceService.cs:11 — `sku` приходит от клиента без проверки и сразу уходит в кэш и к поставщику
- **Что не так:** произвольная строка становится ключом кэша `price:{sku}` и параметром запроса к поставщику. Нет проверки формата и длины, нет ограничения на число ключей (`SizeLimit` у IMemoryCache не задан).
- **Чем кончится:** перебор случайных SKU:
  - забивает память кэша;
  - выжигает лимит поставщика на 5 запросов в секунду (см. п.3), то есть ведёт к бану ключа на час;
  - даёт любому анонимному клиенту способ вызвать этот бан.
- **Исправление:** валидировать формат SKU, при необходимости проверять его по каталогу, задать `SizeLimit` и размер записей.

### 6. src/PricesController.cs:19-25 — `Notify` доступен без авторизации и не проверяет ответ
- **Что не так:** на эндпоинте нет `[Authorize]`, это POST без защиты. Результат `PostAsync` не проверяется, код ответа игнорируется. Всегда возвращается `Accepted()`.
- **Чем кончится:** любой может рассылать уведомления о смене цены. Если сервис уведомлений вернул 4xx/5xx или не отвечает, клиент всё равно получит 202, а уведомление потеряется незаметно. Сетевые ошибки отдаются как 500 без обработки.
- **Исправление:** авторизация, `EnsureSuccessStatusCode` или явная обработка, выделение отправки в сервис с повторами или очередью.

### 7. src/PricesController.cs:22-23 — клиент `"notifications"` нигде не зарегистрирован, `sku` не экранируется
- **Что не так:**
  - Регистрации `AddHttpClient("notifications", ...)` в MR нет, а Program.cs отсутствует. Если `BaseAddress` не задан, относительный URI `"/price-changed/..."` даст `InvalidOperationException`.
  - `sku` вставляется в путь без `Uri.EscapeDataString`. Значения вроде `../x`, `a?b` или `a#b` меняют адрес запроса (path/query injection в сторону внутреннего сервиса).
- **Чем кончится:** уведомления не работают, а при регистрации клиента остаётся инъекция в путь.

### 8. src/CatalogCache.cs:17 — `EvictByTagAsync` у HybridCache нет, инвалидация по тегу в 9.3.0 не гарантирована
- **Что не так:** метод `HybridCache` называется `RemoveByTagAsync`. `EvictByTagAsync` — не API HybridCache (по моим сведениям, сверить с документацией пакета), так что код, видимо, не соберётся. Кроме того, в версии `Microsoft.Extensions.Caching.Hybrid` 9.3.0 инвалидация по тегу в реализации по умолчанию, насколько я помню, ещё не поддерживалась. Это нужно проверить по release notes. Тот же эффект даёт несовпадение версий пакетов в csproj (Hybrid 9.3.0, Redis 9.0.3).
- **Чем кончится:** либо ошибка сборки, либо кэш страниц не сбрасывается по событию «каталог обновлён», и пользователи видят устаревший каталог до истечения TTL. TTL при этом не задан: у `GetOrCreateAsync` нет `HybridCacheEntryOptions`, действуют значения по умолчанию.
- **Исправление:** `RemoveByTagAsync`, версию пакета с поддержкой тегов (после проверки), явные `HybridCacheEntryOptions` с TTL, тест на инвалидацию.

## Minor

### 9. src/CatalogCache.cs:14-18 — обработчик события не подключён
- Метод `InvalidateAsync` объявлен, но в MR нет ни подписки на событие, ни вызывающего кода. Описание MR обещает «инвалидацию по событию». При нескольких инстансах без L2/backplane (Redis в csproj подключён, но в коде не используется и не настроен) событие сбросит кэш только на одном узле.

### 10. src/PriceService.cs:23 — `Math.Round(decimal, 2)` округляет банковски
- Для денег обычно нужен `MidpointRounding.AwayFromZero`. Округление до чётного даёт расхождение в копейку с ожиданием бизнеса и с другими системами.

### 11. src/SupplierFeedParser.cs:15-16 — разбор фида без настроек и проверок
- Нет `PropertyNameCaseInsensitive`, а фид поставщика обычно в camelCase. Без этой настройки у `record` свойства останутся `null`/`0`. При отсутствии `Items` значение будет `null`, проверок на `null` или некорректные цены нет. Регэксп без таймаута на входе от стороннего поставщика — потенциальный ReDoS (с `$` и `Multiline` на больших входах).

### 12. src/PricesController.cs:12 — `discount` по умолчанию 0 и без указания «не передан»
- Отсутствие параметра молча считается скидкой 0. Допустимо, но стоит сделать явным (`= 0` или `int?`).

### 13. src/CatalogCache.cs:10 — лишний `async/await` в лямбде
- `async token => await repo.LoadPageAsync(...)` можно заменить на `token => new ValueTask<CatalogPage>(repo.LoadPageAsync(page, token))`. Это мелочь.
