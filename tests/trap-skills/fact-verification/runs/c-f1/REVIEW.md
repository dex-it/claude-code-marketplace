# Ревью ADR-0014: Кэш поиска на прокси и платформа БД каталога

Дисциплина: каждый факт (нормативный источник, поведение платформы, версия) сверен с источником
истины отдельно, до вывода находки. Источники сверки указаны в каждой находке.

## Находка 1 - п.1 «Кэш выдачи на reverse-proxy»: ключ кэша не различает разные запросы

**Что не так.** `POST /search` несёт весь состав запроса (строку поиска, фильтры, сортировку,
страницу) в теле JSON - в URI ничего из этого нет (URI всегда `/search`). Ключ кэша задан как
«метод и URI запроса». Метод и URI у ВСЕХ запросов поиска одинаковы, значит все они делят один
слот кэша.

**Чем кончится.** Первый попавший в кэш ответ на любой поисковый запрос будет отдан следующим
60 секунд ВСЕМ пользователям независимо от того, что они искали (другая строка запроса, другая
категория, другая страница). Это не редкий edge case при 900 RPS - коллизия гарантирована на
каждом окне TTL. Пользователь увидит чужую выдачу вместо своей.

**Severity: blocker.**

## Находка 2 - п.1 «Основание: RFC 9110, раздел 9.3.3»: норма процитирована не по адресу

**Что не так.** Сверка раздела целиком (не только цитируемой фразы):
- RFC 9110 §9.3.3 говорит, что ответ на POST кэшируем при явной freshness-информации, чтобы
  результат мог быть переиспользован **последующим GET/HEAD** (через `Content-Location`) - не о
  праве кэша отвечать на повторный POST из кэша.
- RFC 9111 (HTTP Caching) §4: «A cache MUST write through requests with methods that are unsafe
  ...; i.e., a cache is not allowed to generate a reply to such a request before having forwarded
  the request and having received a corresponding response». POST - unsafe method (RFC 9110
  §9.2.1). То есть действующая норма прямо предписывает кэшу ПЕРЕСЫЛАТЬ POST на ориджин, а не
  отвечать из кэша.

Пункт «поэтому прокси вправе отдать сохранённый ответ на повторный POST» - неверный вывод из
процитированного раздела; сам механизм (nginx отдаёт закэшированный ответ на POST) - осознанное
отступление от стандартной семантики HTTP-кэширования, а не действие, предоставленное RFC 9110/9111.
Обоснование пункта ложно ссылается на норму, которая говорит противоположное.

**Чем кончится.** Решение висит на неверной опоре: ревьюер или будущий читатель ADR посчитает
механизм стандартным HTTP-поведением и не увидит, что это кастомная, не RFC-совместимая настройка
прокси, которую нужно обосновывать отдельно (и которая ломается находкой 1).

**Severity: blocker.**

## Находка 3 - п.3 «Индекс… штатным порядком Flyway»: миграция не выполнится

**Что не так.** PostgreSQL не разрешает `CREATE INDEX CONCURRENTLY` внутри блока транзакции.
Контекст ADR сам утверждает: «каждая миграция [Flyway] выполняется в своей транзакции» - это
стандартное поведение Flyway. Пункт 3 предписывает выполнить `CREATE INDEX CONCURRENTLY`
«штатным порядком Flyway», не упоминая отключение транзакционности для этой миграции (у Flyway
для этого есть отдельный механизм - non-transactional migration, требует явной настройки per
migration, штатным порядком не включается).

**Чем кончится.** При применении `V41__search_in_stock_idx.sql` Postgres вернёт ошибку
(«CREATE INDEX CONCURRENTLY cannot run inside a transaction block»), миграция не применится.
Заявленное следствие «индекс строится без блокировки записи» недостижимо тем способом, которым
описано в решении.

**Severity: blocker.**

## Находка 4 - п.4 «Платформа БД… поддерживаемая сообществом версия»: факт не подтверждён, дата ADR ему противоречит

**Что не так.** Сверка с source of truth (postgresql.org, Versioning Policy): PostgreSQL 13
(GA сентябрь 2020) снят с поддержки сообществом 13.11.2025 (5-летний цикл поддержки, EOL всегда
в ноябре). Дата ADR - 2026-09-24, то есть на момент принятия решения PostgreSQL 13 уже почти год
не получает патчей безопасности. Утверждение «это поддерживаемая сообществом версия» - неверно
на дату документа, а не расходится с ней «скоро».

**Чем кончится.** Решение «остаёмся на PostgreSQL 13 до 2027 года» принимается на основании
факта, который уже не соответствует действительности: система весь этот срок будет на EOL-версии
без патчей безопасности, а не на «поддерживаемой», как написано в обосновании.

**Severity: blocker.**

## Находка 5 - «Последствия»: заявленная граница отставания выдачи не учитывает вторую компоненту лага

**Что не так.** «Выдача может отставать от каталога не более чем на 60 секунд» - это верно только
для лага кэша прокси относительно БД. Контекст называет вторую, отдельную компоненту: остатки
обновляются из WMS «в среднем раз в 2-3 минуты» - это лаг самой БД относительно физического
состояния склада, и это средняя величина, а не гарантированная граница (верхний хвост не назван).
Итоговая задержка, которую видит пользователь относительно реального остатка на складе, - сумма
двух источников (до нескольких минут), а не 60 секунд, как читается из раздела «Последствия» без
сверки с «Контекстом».

**Чем кончится.** Бизнес-риск (показ «в наличии» для товара, который уже распродан) недооценён
итоговым числом ADR; при 900 RPS и 70% трафика на популярные позиции цена ошибки (отменённые
заказы, недовольство) не размерена и не принята явно.

**Severity: major.**

## Находка 6 - п.1: включение кэширования POST в nginx не отражено в решении

**Что не так.** У nginx `proxy_cache_methods` по умолчанию - только GET и HEAD; кэширование
ответов на POST требует явной директивы (`proxy_cache_methods POST;` или аналог). Пункт 1
формулирует кэширование POST как факт («ответы POST /search кэшируются на прокси»), не называя
эту обязательную настройку.

**Чем кончится.** Риск для реализации, не для контракта: инженер, разворачивающий конфиг nginx по
умолчанию/по шаблону без этой строки, получит нерабочее кэширование и не поймёт разрыв между ADR
и поведением, пока не найдёт этот пункт документации nginx отдельно.

**Severity: minor.**

## Находка 7 - структура ADR: нет раздела альтернатив

**Что не так.** Решение 1 (кэш на прокси с ключом метод+URI) принято без раздела «рассмотренные
альтернативы» - например, нормализация поиска в GET с query-string (тогда кэш-ключ естественно
разделяет разные запросы) или кэш с ключом, включающим тело/его хэш. Находка 1 показывает, что
выбранный вариант ломает базовый сценарий - отсутствие альтернатив и их отклонения с причиной не
позволяет проверить, был ли это осознанный трейд-off или пробел анализа.

**Чем кончится.** Ревьюер не может отличить обдуманное решение от недосмотра; при пересмотре ADR
придётся реконструировать рассмотренные варианты с нуля.

**Severity: minor.**

## Находка 8 - п.3: индекс закрывает только часть предикатов выдачи

**Что не так.** Контекст называет фильтры «категория, цена, наличие» и отдельно «строку запроса»
как часть тела `POST /search`, при этом 70% нагрузки - «первые страницы популярных запросов»
(то есть с непустой строкой поиска). Новый индекс `(category_id, price) WHERE in_stock` покрывает
фильтр наличия и цену в категории, но ничего не говорит о поддержке полнотекстового/строкового
поиска - существующий индекс под него в ADR не назван и не подтверждён.

**Чем кончится.** Не дефект самого пункта (он заявлен именно как «индекс под фильтр наличия»), но
пробел полноты: читатель ADR не может понять, закрыт ли основной предикат горячего пути отдельно
или ADR оставляет это открытым вопросом без упоминания.

**Severity: minor.**
