# Review: списание баллов лояльности

Область: весь каталог (`app/*.py`, `requirements.txt`) - новый код. Ревью без запуска Python/тестов, факты о поведении фреймворков сверены с официальной документацией (python docs, pydantic 1.10 docs) - ссылки даны при находке.

## Находки

### 1. `app/redeem.py:11,20,28` - `POINT_VALUE` как float даёт неточный `Decimal`
`POINT_VALUE = 0.1` - обычный float; `Decimal(POINT_VALUE)` берёт точное двоичное представление float, а не десятичное 0.1. Подтверждено документацией Python (`docs.python.org/3/library/decimal.html`): `Decimal(0.1) == Decimal('0.1000000000000000055511151231257827021181583404541015625')`. Значит `balance` (строка 20) и обратное деление при списании (строка 28) считаются с этим "хвостом" ошибки, а не с точным 0.1.
Чем кончится: `balance_left`/`redeemed` в ответе несут паразитные незначащие цифры, а сравнение `amount > balance` (строка 25) и деление на строке 28 работают не с тем числом, которое подсказывает код (`0.1`). Корень следующих двух находок.
Severity: **blocker**.

### 2. `app/redeem.py:28` - `int(amount / Decimal(POINT_VALUE))` списывает баллы не по правилу "1 балл = 0.1"
Деление на `POINT_VALUE` и усечение `int()` (округление к нулю) не проверяет, что `amount` кратно `POINT_VALUE`. Пример без учёта находки 1 (чистая арифметика): `confirm_amount = 0.09` -> `0.09/0.1 = 0.9` -> `int(0.9) = 0` баллов списано, но `amount = 0.09` уходит в ответ (`redeemed=0.09`, строка 36) и в аудит (`req.dict()`, строка 30) как успешное списание. С учётом находки 1 то же самое воспроизводится и на "круглых" суммах: при полном списании (`confirm_amount is None`, строка 22) `amount` равен `balance`, но `amount / Decimal(POINT_VALUE)` из-за паразитного хвоста даёт число чуть меньше целого (`99.999999999999999...`), и `int()` срезает вниз - "полное списание" оставляет на счёте 1 балл, хотя в ответе `balance_left` может показывать почти ноль.
Чем кончится: клиент может многократно слать `confirm_amount` чуть меньше 0.1 (например 0.09) - в ответе и в аудите фиксируется "списание", реальные баллы не уменьшаются; заявленное в MR "полное списание" не гарантирует нулевой остаток. Финансовая утечка и разрыв между audit-трейлом и фактическим балансом.
Severity: **blocker**.

### 3. `app/redeem.py:20-28`, `app/schemas.py:15` - нет проверки `confirm_amount >= 0`
`confirm_amount: Optional[Decimal]` без `ge=0`/`gt=0` (нет `Field` с ограничением). В `redeem.py` единственная проверка - `amount > balance` (строка 25); отрицательное `amount` всегда меньше положительного `balance` и проходит. На строке 28 `member.points -= int(amount / Decimal(POINT_VALUE))` с отрицательным `amount` даёт вычитание отрицательного числа, то есть **начисление** баллов.
Чем кончится: любой вызывающий "Списание баллов" эндпойнт с `confirm_amount: -1000` увеличивает баланс баллов участника вместо списания - неограниченная эмиссия баллов через операцию, которая по описанию MR должна их только списывать.
Severity: **blocker**.

### 4. `app/redeem.py:15-16` - нет проверки, что вызывающий - владелец `member_id`
В роутере нет зависимости аутентификации/авторизации (`Depends(...)`), нет сверки `member_id` из тела запроса с идентичностью вызывающего; `app/__init__.py` пуст, других файлов wiring/auth в каталоге нет. В рамках просмотренного кода любой, кто знает `member_id`, может списать (а с находкой 3 - начислить) чужие баллы.
Чем кончится: IDOR на операции, которая двигает баллы лояльности как деньги. Если авторизация реализована где-то за пределами этого MR (не входит в просмотренный код) - находка снимается тем кодом; в текущем каталоге защиты нет.
Severity: **blocker** (в границах просмотренного кода).

### 5. `app/redeem.py:16-29`, `app/repo.py:16-29` - списание без блокировки строки/версии
`get_member` (repo.py:16-21) читает баланс на своём соединении, `redeem.py` считает новое значение в Python-переменной, `save_member` (repo.py:24-29) перезатирает `points` абсолютным значением на отдельной транзакции `engine.begin()`. Ни `SELECT ... FOR UPDATE`, ни оптимистической версии (`WHERE points = :old`) нет.
Чем кончится: два параллельных запроса на списание для одного участника читают один и тот же стартовый баланс и оба проходят проверку `amount > balance`; итоговая запись одного перетирает другого - classic lost update, двойное списание/некорректный остаток при конкурентных запросах.
Severity: **blocker**.

### 6. `app/redeem.py:29-30` - списание баланса и запись аудита не атомарны
`save_member(member)` (строка 29) и `write_audit(...)` (строка 30) - две независимые транзакции (`repo.py:24-29` и `repo.py:32-37`), между ними нет общей транзакции/outbox.
Чем кончится: при сбое процесса (или ошибке INSERT в `audit`) между строками 29 и 30 баланс уже списан, а аудит-запись не создана - разрыв между фактическим движением баллов и журналом операции, который MR прямо заявляет как часть фичи ("аудит операции").
Severity: **major**.

### 7. `app/schemas.py:9-10` - поле `points: int` обязательно, но не используется бизнес-логикой
`RedeemRequest.points` нигде не читается в `redeem.py`; используется только неявно через `req.dict()` (строка 30) при записи в аудит.
Чем кончится: клиент обязан присылать число, которое ни на что не влияет и не проверяется против реального баланса, а произвольное клиентское значение `points` попадает в аудит-лог как будто это часть зафиксированной операции - подрывает доверие к аудиту как источнику истины и наводит на мысль о недописанной проверке (например ожидаемого баланса для защиты от гонки из находки 5), которая не была подключена.
Severity: **major**.

### 8. `app/redeem.py:32-33,37-38`, `app/repo.py` - "срок действия баллов" не хранится и не проверяется
`valid_until` считается на лету (`date.today() + timedelta(days=365)`) и возвращается в ответе; ни `Member`, ни таблицы `members`/`audit` (по коду `repo.py`) не несут никакого поля срока действия/даты начисления, и ничего в `redeem.py` не проверяет, не истёк ли срок у списываемых баллов.
Чем кончится: заявленная в описании MR часть "срок действия баллов" по факту не реализована как ограничение - это косметическое поле в ответе, которое ничего не гейтит; баллы, которые по бизнес-правилу должны были обесцениться, остаются списываемыми бессрочно.
Severity: **major**.

### 9. `app/redeem.py:32-33` - расчёт `valid_until` даёт на день больше заявленного
Комментарий на строке 32 фиксирует правило: "365 дней ... включая сегодняшний" - то есть сегодня считается днём 1, день 365 должен быть `today + timedelta(days=364)`. Код прибавляет `timedelta(days=365)`, что даёт включительный диапазон в 366 дней.
Чем кончится: срок действия баллов на 1 день длиннее собственного описанного в коде правила - минорное расхождение бизнес-правила и реализации.
Severity: **minor**.

### 10. `app/schemas.py:16-17` - комментарий о поведении pydantic не соответствует дефолту версии 1.10
Комментарий утверждает: "Лишние поля pydantic по умолчанию отвергает, так что опечатка в имени поля у клиента даст 422, а не молчаливое игнорирование". Проверено документацией pydantic 1.10 (`pydantic.dev/docs/validation/1.10/usage/model_config/`): дефолт `Config.extra` - `Extra.ignore` ("whether to ignore, allow, or forbid extra attributes during model initialization", default `Extra.ignore`) - лишние атрибуты молча игнорируются. `RedeemRequest` не задаёт `class Config: extra = "forbid"`, значит поведение по умолчанию не отвергает лишние поля.
Чем кончится: опечатка клиента в имени необязательного поля (например `comment`) не даст 422, как утверждает комментарий, а будет молча проигнорирована - разработчик опирался на несуществующую защиту.
Severity: **major**.
