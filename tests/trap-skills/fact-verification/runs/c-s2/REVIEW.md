# Ревью ADR-0014: Кэш поиска на прокси и платформа БД каталога

Ревью формального документа `docs/adr/0014-search-cache-and-db.md`, ADR не правился. Каждый
факт о поведении платформы/фреймворка сверен с источником истины (RFC, документация nginx,
трекер Flyway, endoflife-данные PostgreSQL) - см. "Источник" в каждом пункте.

## Находка 1 - п.1 "Кэш выдачи на reverse-proxy": ключ кэша не различает запросы

**Где:** п.1, "Ключ кэша - метод и URI запроса."

**Что не так:** запрос поиска - `POST /search` с телом JSON (строка запроса, фильтры, сортировка,
страница - см. Контекст); сам URI везде один и тот же `/search`, никаких различающих query-
параметров нет. Ключ кэша "метод + URI" в nginx по умолчанию (`proxy_cache_key` =
`$scheme$proxy_host$request_uri`) тело запроса не учитывает. Значит для ВСЕХ запросов поиска -
любых текстов, фильтров, страниц, от любых пользователей - в кэше ровно одна ячейка.

**Чем кончится:** первый `POST /search`, попавший на прокси в 60-секундном окне, кладёт свой
ответ в кэш; все остальные запросы (с другим текстом, другими фильтрами, другой страницей, от
других пользователей) следующие 60 секунд получают этот же чужой ответ. Поиск перестаёт находить
то, что искали - под нагрузкой 900 RPS почти вся выдача каталога заменяется одной случайной
выдачей, обновляемой раз в 60 секунд. Заявленное в "Последствиях" снижение нагрузки "примерно в 3
раза" при таком ключе тоже не совпадает с механизмом - при полном совпадении ключа для всего
трафика попадание в кэш близко к 100%, а не к 3-кратному снижению; расхождение оценки с
описанным механизмом - дополнительный сигнал, что ключ спроектирован неверно (не хватает хеша
тела запроса, например `proxy_cache_key $request_uri|$request_body`).

**Источник:** nginx docs, `ngx_http_proxy_module` (`proxy_cache_key` default), подтверждено
независимо разбором типового кейса кэширования POST в nginx (тело не входит в ключ по умолчанию,
для корректной работы нужно добавлять `$request_body` в ключ явно).

**Severity: blocker.**

## Находка 2 - п.1 "Основание": цитата RFC 9110 обратна тому, для чего она приведена

**Где:** п.1, "Основание: по RFC 9110, раздел 9.3.3, ответы на POST кэшируемы, поэтому прокси
вправе отдать сохранённый ответ на повторный POST."

**Что не так:** RFC 9110 §9.3.3 разрешает кэшу переиспользовать сохранённый ответ POST только для
последующего GET или HEAD к тому же URI - не для повторного POST (POST как потенциально
небезопасный метод из кэша повторным POST не обслуживается). Разрешение действует ещё и при
условии, что ответ несёт явную freshness-информацию И заголовок `Content-Location`, совпадающий с
целевым URI POST-запроса; про `Content-Location` в решении ничего не сказано, сервис его не
выставляет. То есть из нормы взята половина (кэшируемость POST-ответа вообще) без условия
применимости (только для GET/HEAD, только с `Content-Location`), а вывод сделан ровно про
запрещённый нормой случай - повторный POST.

**Чем кончится:** нормативное основание пункта декларативно неверно. Технически nginx это не
остановит - он кэширует то, что настроено, независимо от RFC-семантики (при добавлении
`proxy_cache_methods POST`, которого решение тоже не называет, см. находку 4), поэтому находка 1
сработает независимо от этой ошибки. Но при ревью/аудите на соответствие HTTP-семантике текущая
формулировка не защитит решение - цитата подтверждает не то, что ею обосновывается, и будущий
читатель ADR унаследует неверное представление о том, что RFC разрешает такое поведение.

**Источник:** RFC 9110 §9.3.3 (POST) - в независимых пересказах спецификации (restguide.info,
разборы поведения кэшей на POST) формулировка совпадает: "cacheable only with explicit freshness
information and a Content-Location header field equal to the target URI"; "a cached POST response
can satisfy a later GET or HEAD request... a POST request cannot be satisfied by a cached POST
response because POST is potentially unsafe".

**Severity: major.**

## Находка 3 - п.4 "Платформа БД": заявленный статус PostgreSQL 13 не соответствует факту на дату ADR

**Где:** п.4, "Остаёмся на PostgreSQL 13: это поддерживаемая сообществом версия, плановое
обновление... переносим на 2027 год".

**Что не так:** PostgreSQL 13 достигла конца жизненного цикла сообщества (community EOL)
13 ноября 2025 года - PostgreSQL Global Development Group с этой даты не выпускает для 13-й ветки
патчи безопасности и исправления багов. ADR датирован 2026-09-24, то есть на момент принятия
решения версия уже почти 11 месяцев не поддерживается сообществом - утверждение "поддерживаемая
сообществом версия" на эту дату ложно.

**Чем кончится:** решение "оставаться до 2027 года" продлевает работу продового сервиса каталога
(цена, наличие) на неподдерживаемой community-версии Postgres суммарно больше чем на год без
патчей безопасности от апстрима, и обоснование этого шага в тексте ADR фактически неверное - при
разборе инцидента безопасности или при последующем аудите заявленная причина не подтвердится.
(Управляемые облачные площадки иногда продают платное extended support на 13.x отдельно от
community-цикла, но в ADR это не названо и не является заявленным основанием - основание именно
"поддерживаемая сообществом".)

**Источник:** postgresql.org / endoflife.date - PostgreSQL 13 EOL 2025-11-13; независимо
подтверждено разборами (Percona, TuxCare) той же даты.

**Severity: major.**

## Находка 4 - п.3 "Индекс под фильтр наличия": риск конфликта CONCURRENTLY с транзакционной миграцией и необработанный failure-mode

**Где:** п.3, "Миграция ... создаёт индекс ... штатным порядком Flyway"; Контекст, "миграции
применяет Flyway: каждая миграция выполняется в своей транзакции."

**Что не так:** `CREATE INDEX CONCURRENTLY` в PostgreSQL не может выполняться внутри
транзакционного блока - это жёсткое ограничение движка, а ADR сам заявляет транзакционный режим
миграций Flyway как норму проекта. У Flyway есть автоопределение таких операторов (парсер ищет
шаблон `CREATE INDEX CONCURRENTLY` и выполняет конкретно эту миграцию нетранзакционно) - но это
поведение по трекеру Flyway регрессировало в части релизов (ломалось начиная с 9.1.2, чинилось
позже) и известно зависанием на advisory-lock при параллельном старте нескольких инстансов
приложения. ADR не называет версию Flyway и не описывает ветку отказа: если сборка индекса
прервётся (таймаут, конфликт блокировок, гонка параллельных деплоев), в базе останется индекс со
статусом INVALID, который Flyway не пересобирает и не откатывает сам - нужен ручной `DROP INDEX`
и повторный прогон.

**Чем кончится:** миграция либо не пройдёт вовсе (явная ошибка Postgres про транзакционный блок,
если автоопределение Flyway на использованной версии не сработает), либо пройдёт, но при сбое
конкурентной сборки оставит невалидный индекс и заблокирует последующие деплои до ручного
вмешательства - ADR как нормативный текст этот путь восстановления не называет.

**Источник:** документация PostgreSQL (`CREATE INDEX CONCURRENTLY` вне транзакции), issue-трекер
flyway/flyway (детектирование `CREATE INDEX CONCURRENTLY` в `PostgreSQLParser`, регрессии между
релизами 9.x, зависания на advisory lock при параллельном старте).

**Severity: major.**

## Находка 5 - п.1: не названа обязательная настройка кэширования POST на nginx

**Где:** п.1, "Сервис выставляет `Cache-Control: max-age=60`."

**Что не так:** у nginx `proxy_cache_methods` по умолчанию - только `GET HEAD`; ответ с
`Cache-Control: max-age=60` на POST не будет положен в кэш прокси, пока на самом nginx явно не
включён метод POST (`proxy_cache_methods GET HEAD POST` + кэш-ключ, учитывающий тело - см.
находку 1). Решение называет только серверную часть (заголовок ответа) и не называет обязательную
конфигурацию самого прокси, без которой пункт 1 не даёт заявленного эффекта.

**Чем кончится:** инженер, реализующий ADR буквально по тексту решения, выставит заголовок и не
увидит кэширования POST вовсе (кэш прокси тихо продолжит пропускать все `POST /search` мимо себя,
без ошибки) - расхождение между заявленным и фактическим поведением обнаружится не по тексту
ADR, а по логам/метрикам прокси.

**Источник:** nginx docs, `ngx_http_proxy_module`, директива `proxy_cache_methods` (default
`GET HEAD`).

**Severity: minor.**
