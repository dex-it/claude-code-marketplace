# Ревью ADR-0014: Кэш поиска на прокси и платформа БД каталога

## Находка 1 - п.1 "Основание", ссылка на RFC 9110 9.3.3

Что не так: ADR обосновывает кэширование ответа на повторный POST ссылкой на RFC 9110 9.3.3,
но раздел говорит обратное для этого случая. Условие кэшируемости ответа на POST - явная
freshness-информация И заголовок `Content-Location`, совпадающий с целевым URI запроса; при этом
переиспользовать такой сохранённый ответ разрешено только для последующего GET/HEAD с тем же
`Content-Location`. Ответ на POST нельзя использовать для удовлетворения следующего POST:
RFC 9111 4 требует от кэша "write through" для небезопасных методов - переслать запрос на origin,
а не ответить из кэша, поскольку POST потенциально unsafe. Прокси, отдающий сохранённый ответ на
повторный `POST /search`, действует не по норме, на которую ссылается ADR, а против неё.
Источник: RFC 9110 9.3.3 (POST, условия кэшируемости и правило "POST cannot be satisfied by a
cached POST response"), RFC 9111 4 (write-through для unsafe-методов).

Чем кончится: решение принимается на неверно прочитанной норме; при ревью или аудите ссылка не
подтвердится, обоснование пункта 1 придётся переписывать с нуля.

Severity: blocker.

## Находка 2 - п.1 "Ключ кэша - метод и URI запроса"

Что не так: весь смысл поискового запроса (строка, фильтры, сортировка, страница) лежит в теле
JSON `POST /search`, а не в URI. Ключ кэша "метод и URI" не различает запросы с разным телом.
Это ровно дефолт nginx: `proxy_cache_key` по умолчанию - `$scheme$proxy_host$request_uri`, без
`$request_body` (nginx docs, ngx_http_proxy_module). ADR фиксирует именно такой ключ явно, без
добавления тела запроса в ключ.

Чем кончится: первый пришедший на `/search` запрос в окне 60 секунд кладёт свой ответ в кэш по
ключу `POST /search`; все последующие запросы с другими фильтрами/строкой/страницей в эти 60 секунд
получат тот же самый закэшированный ответ - результаты чужого поиска вместо своего. Это не
деградация производительности, это разрушение корректности выдачи для всех, кроме первого запроса
в каждом окне TTL.

Severity: blocker.

## Находка 3 - п.1, отсутствие конфигурации `proxy_cache_methods`

Что не так: у nginx `proxy_cache_methods` по умолчанию - `GET HEAD`; POST не кэшируется, пока это
явно не включено директивой. ADR описывает кэширование `POST /search` как решённый факт
("ответы... кэшируются на прокси"), но не называет обязательную донастройку
`proxy_cache_methods POST` - без неё пункт 1 не заработает вовсе.

Чем кончится: если при реализации об этой директиве забудут (а ADR ничего о ней не говорит),
кэш прокси останется пустым, весь трафик пойдёт в Catalog.Search как и раньше, и заявленное в
Последствиях "нагрузка снижается примерно в 3 раза" не подтвердится - при этом никто не заметит
до нагрузочного теста или инцидента, потому что сервис продолжит работать, просто без эффекта
кэша.

Severity: major.

## Находка 4 - "Последствия", "выдача может отставать... не более чем на 60 секунд"

Что не так: в Контексте самого ADR сказано, что остатки WMS обновляются "в среднем раз в 2-3
минуты" - то есть данные о наличии в БД на момент, когда ответ попадает в кэш, уже отстают от
реального состояния склада на 2-3 минуты. Кэш прокси добавляет к этому ещё до 60 секунд сверху.
Заявление "не более чем на 60 секунд" учитывает только задержку кэша и молчит про задержку WMS,
которая уже присутствует и складывается с кэшем.

Чем кончится: итоговая задержка, которую видит пользователь (сравнивая с реальным складом), может
доходить до ~3-4 минут, а не до 60 секунд, как заявлено; при обсуждении SLA по свежести выдачи
цифра из ADR даст неверную оценку риска.

Severity: major.

## Находка 5 - п.3, `CREATE INDEX CONCURRENTLY` "штатным порядком Flyway"

Что не так: Контекст ADR сам фиксирует, что "каждая миграция выполняется в своей транзакции" - это
дефолтное поведение Flyway для PostgreSQL. При этом `CREATE INDEX CONCURRENTLY` прямо запрещён
внутри транзакционного блока: "a regular CREATE INDEX command can be performed within a
transaction block, but CREATE INDEX CONCURRENTLY cannot" (официальная документация PostgreSQL,
CREATE INDEX). Чтобы выполнить такую миграцию, её нужно вывести из транзакции Flyway - директива
`executeInTransaction=false` для конкретного скрипта доступна только в платных редакциях Flyway
Teams/Enterprise; в Community edition обходятся через callback вне обычного потока миграций. Ни
вывод миграции из транзакции, ни выбор способа для этого в решении не упомянуты - миграция описана
как обычная, "штатным порядком Flyway".

Чем кончится: миграция V41 в текущем описании не накатится обычным прогоном Flyway (ошибка
PostgreSQL на `CREATE INDEX CONCURRENTLY` внутри транзакции, по опыту сообщества - зависание) либо
потребует незаявленной в ADR донастройки инфраструктуры миграций (платная лицензия Flyway или
callback). Заявленный в Последствиях эффект "индекс строится без блокировки записи" недостижим тем
механизмом, который назван в решении.

Severity: blocker.

## Находка 6 - п.4, "Остаёмся на PostgreSQL 13: это поддерживаемая сообществом версия"

Что не так: утверждение не соответствует действительности на дату ADR (2026-09-24).
Community-поддержка PostgreSQL 13 закончилась 2025-11-13 (5 лет от релиза 2020-09-24 - таковы
правила версионирования postgresql.org). На момент принятия решения кластер уже почти год работает
на версии, для которой нет ни security-патчей, ни bugfix-релизов, а перенос обновления на 2027 год
продлевает этот срок минимум до полутора-двух лет без патчей.

Чем кончится: обоснование пункта 4 ложно, и решение "остаться на PG13 до 2027" принимается без
учёта того, что версия уже не поддерживается - известные и будущие CVE для PG13 останутся без
патча всё это время, при том что решение прямо называет отсутствие такого риска аргументом
("поддерживаемая сообществом версия").

Severity: blocker.
