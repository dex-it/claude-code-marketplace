# REVIEW: Pricing.Api

Источник сверки фактов: context7 (/dotnet/aspnetcore.docs, /dotnet/docs). Версии из csproj: net9.0, Microsoft.Extensions.Caching.Hybrid 9.3.0.

## Blocker

### 1. src/CatalogCache.cs:27 - `EvictByTagAsync` не существует
- Что не так: у `HybridCache` метод инвалидации по тегу называется `RemoveByTagAsync` (документация: hybrid.md, «Remove cache entries by tag»; есть перегрузка с коллекцией тегов). `EvictByTagAsync` в документации нет.
- Чем кончится: проект не соберётся, инвалидация кэша каталога по событию не работает.
- Статус: имя `RemoveByTagAsync` подтверждено документацией. Совпадение с версией пакета 9.3.0 по документации не проверялось (в ней нет разбивки по версиям), поэтому для 9.3.0 это `unverifiable`. Проверить сборкой нельзя, она запрещена ограничениями.

### 2. src/SupplierFeedParser.cs:104,108 - regex `//.*$` вырезает часть строковых значений
- Что не так: регулярка не различает комментарий и содержимое JSON-строки. В `ImageUrl` по контракту лежит `https://cdn.supplier.example/img/123.png` (Contracts-комментарий на строке 116), и `//cdn...` до конца строки будет вырезано.
- Чем кончится: компактный JSON (всё в одной строке) теряет хвост целиком. Форматированный теряет закрывающую кавычку и запятую. Результат - `JsonException` на любом фиде с URL, то есть почти на каждом. Если разбор не падает, `ImageUrl` приходит обрезанным.
- Отрицательный факт «в System.Text.Json нет настройки для комментариев» (строка 102) неверен. Документация (invalid-json.md): `JsonSerializerOptions.ReadCommentHandling = JsonCommentHandling.Skip` (плюс при необходимости `AllowTrailingCommas`). Штатная замена: передать эти options в `Deserialize` и убрать regex.

### 3. src/PriceService.cs:91 - целочисленное деление в расчёте скидки
- Что не так: `discountPercent` имеет тип `int`, поэтому `discountPercent / 100` равно 0 при любом значении от 0 до 99 и 1 только при 100.
- Чем кончится: скидка не применяется нигде, кроме 100%. Клиент получает базовую цену вместо финальной, при 100% - ноль. Требование «финальная цена со скидкой» не выполнено. Нужно `discountPercent / 100m`.

## Major

### 4. src/PriceService.cs:76-84 - нет защиты от параллельных промахов, при этом лимит поставщика 5 rps
- Что не так: комментарий утверждает, что `IMemoryCache.GetOrCreateAsync` гарантирует единственный вызов фабрики. Документация этого не обещает. Защиту от stampede она описывает как свойство `HybridCache` (hybrid.md, overview), а у `IMemoryCache` такой гарантии нет. Утверждение автора `unverifiable` и расходится с документацией. Что именно не гарантируется, я явно в тексте документации не нашёл.
- Чем кончится: при истечении TTL (5 минут) или холодном старте параллельные запросы на один sku идут к поставщику одновременно. Контракт `ISupplierClient`: больше 5 rps на ключ даёт бан на час. Итог - бан ключа и недоступность цен на час. Также нет ограничения общей скорости по разным sku.
- Исправление: использовать `HybridCache` (он уже подключён в проекте) либо `SemaphoreSlim` по ключу, плюс ограничитель частоты на клиенте поставщика.

### 5. src/PriceService.cs:80-83 - `ct` первого запроса захвачен в общую фабрику
- Что не так: фабрика использует `ct` запроса-инициатора, а не токен кэша. Отмена одного HTTP-запроса обрывает загрузку, и ожидающие этот же ключ получают `OperationCanceledException`.
- Чем кончится: ложные ошибки или 499/500 у других клиентов при отключении одного.
- Примечание: в `GetOrCreateAsync` у `IMemoryCache` в 9.x нет перегрузки с токеном, это следствие выбора API.

### 6. src/CatalogCache.cs:17-28 - инвалидация затрагивает только текущий сервер
- Что не так: документация (hybrid.md): при инвалидации по ключу или тегу данные сбрасываются на текущем сервере и во вторичном хранилище (Redis), а in-memory кэш других серверов не затрагивается.
- Чем кончится: при нескольких инстансах и событии «каталог обновлён», обработанном одним из них, остальные отдают устаревшие страницы до истечения срока жизни L1. Срок не задан, действует дефолт.
- Исправление: ограничить L1 (`HybridCacheEntryOptions.LocalCacheExpiration`) либо доставлять событие всем инстансам.

### 7. src/PricesController.cs:65-67 - результат уведомления не проверяется, имя клиента и адрес не определены
- Что не так: ответ `PostAsync` игнорируется, возвращается `Accepted()` даже при 5xx. В репозитории нет регистрации именованного клиента `"notifications"` и `BaseAddress`. Без них `CreateClient("notifications")` вернёт клиент без базового адреса, а относительный URI `/price-changed/{sku}` даст `InvalidOperationException`. `sku` вставляется в путь без `Uri.EscapeDataString`.
- Чем кончится: уведомление о смене цены молча теряется, клиент видит 202. Либо 500 на каждый вызов. В `sku` с `/`, `?`, `..` путь меняется (path injection).
- Исправление: `response.EnsureSuccessStatusCode()` или явная обработка, регистрация клиента с `BaseAddress` и политикой повторов, экранирование sku.
- Комментарий про `IHttpClientFactory` по существу верен (фабрика переиспользует обработчики). Как факт о версии это не проверялось, на вывод не влияет.

### 8. src/PricesController.cs:55-58 - ручная проверка `discount`, `sku` без валидации, нет авторизации на POST notify
- Что не так: `discount` без параметра по умолчанию равен 0, отсутствие значения не отличить от явного нуля. `sku` не валидируется (длина, формат) и идёт в ключ кэша и в запрос к поставщику. Любой клиент может вызвать `POST notify` для произвольного sku.
- Чем кончится: произвольные sku раздувают кэш (`price:{sku}`) и бьют по лимиту поставщика. Открытый notify позволяет спамить подписчикам.
- Класс: нужны `[Range(0,100)]`, ограничение формата sku, авторизация. Конфигурации авторизации в репозитории нет, поэтому оценка условная.

## Minor

### 9. src/PriceService.cs:92 - банковское округление денег
- `Math.Round(x, 2)` по умолчанию округляет `MidpointRounding.ToEven`. Для цен обычно ожидается `AwayFromZero`. Итог - расхождение в копейку с ожиданиями бизнеса и других систем. Требуемая политика округления не указана, `unverifiable`.

### 10. src/SupplierFeedParser.cs:109 - десериализация с дефолтными options
- Сопоставление имён по умолчанию чувствительно к регистру (`PascalCase` свойств против `camelCase` в JSON). Формат фида в репозитории не показан. Если у поставщика `sku`/`price`/`imageUrl`, все поля будут `null`/0 без ошибки. Нужно `JsonSerializerDefaults.Web` или явные `JsonPropertyName`. Это зависит от реального формата фида, поэтому `unverifiable`.
- Заодно: `Items` и `ImageUrl` non-nullable, но при отсутствии поля в JSON получат `null`, nullable-аннотации этого не проверяют. `Price` без поля станет 0, а ноль уйдёт в цены.

### 11. src/CatalogCache.cs:20-22 - сигнатура `GetOrCreateAsync` не сверена для 9.3.0
- Использованы именованные параметры `tags:` и `cancellationToken:`. В примерах документации параметр токена назван `token:`. По версии 9.3.0 именование параметров `unverifiable` (в документации разбивки по версиям нет, пробу собрать нельзя). Если имя не совпадёт, будет ошибка компиляции.
- Лишний `async/await` в лямбде (`async token => await repo...`) можно заменить прямым возвратом, мелочь.

### 12. Pricing.Api.csproj:7-8 - несогласованные версии пакетов и нет композиции
- Hybrid 9.3.0 и StackExchangeRedis 9.0.3 - разные минорные версии. Нет `Program.cs`: не зарегистрированы `AddHybridCache`, `AddStackExchangeRedisCache`, `AddMemoryCache`, `PriceService`, `CatalogCache`, `ISupplierClient`, `ICatalogRepository` и именованный клиент. Нет реализаций интерфейсов и обработчика события инвалидации. Кэш каталога заявлен как с инвалидацией по событию, но вызывающего `InvalidateAsync` в MR нет.
- Чем кончится: приложение не запускается (DI не разрешает зависимости) либо инвалидация никогда не вызывается. Если это сделано в соседнем MR, это нужно указать в описании.

### 13. Тестов в MR нет
- Ни одного теста на скидку, парсер с URL, инвалидацию. Баги 2 и 3 ловились бы простейшими тестами.
