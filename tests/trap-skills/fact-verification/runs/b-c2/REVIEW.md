# Review: списание баллов лояльности

Диапазон: весь каталог (новый код). Файлы: `app/redeem.py`, `app/repo.py`, `app/db.py`,
`app/schemas.py`, `app/__init__.py`, `requirements.txt`.

## Blocker

### 1. `app/schemas.py:13-15` — `Optional[Decimal]` без default в Pydantic v1 не делает поле обязательным
Комментарий (строки 11-14) утверждает: «Optional без значения по умолчанию делает поле
обязательным, поэтому старые клиенты... получат 422». Это неверно для Pydantic v1 (пин в
`requirements.txt:2` — `pydantic==1.10.13`): в Pydantic v1 `Optional[X]` без явного default
автоматически получает `default=None` и становится НЕобязательным (задокументированная
особенность v1; чтобы Optional-поле было обязательным, нужен явный `= ...`).
Чем кончится: старый клиент, который вообще не передаёт `confirm_amount` (а не передаёт `null`),
пройдёт валидацию с `confirm_amount=None` и получит **полное списание баланса** вместо ожидаемой
422-ошибки — то есть ровно тот сценарий, который код пытается запретить своим же комментарием.
Это ломает заявленную в MR семантику «частичное или полное списание» для клиентов, которые не
знают о новом поле.
Severity: blocker.

### 2. `app/redeem.py:11,20,28` — `Decimal(POINT_VALUE)` из float-литерала теряет точность
`POINT_VALUE = 0.1` — Python `float`. `Decimal(0.1)` даёт не `Decimal('0.1')`, а точное
представление бинарной дробности float (`0.1000000000000000055511151231257827021181583404541015625`),
это документированное поведение модуля `decimal` (лоссless конверсия float → decimal сохраняет
ошибку float). Используется в трёх местах: расчёт `balance` (redeem.py:20), деление при списании
баллов (redeem.py:28), расчёт `balance_left` (redeem.py:37).
Чем кончится: сравнение `amount > balance` (строка 25) и конверсия суммы в баллы дают
систематические расхождения на денежных величинах — то полный баланс не разойдётся с
`confirm_amount` ровно, то списание баллов округлится не в ту сторону. Для операции списания
денег/баллов это не единичный edge case, а систематическая порча каждого расчёта.
Severity: blocker.

### 3. `app/redeem.py:21-28` — нет проверки `confirm_amount >= 0`
`req.confirm_amount` не имеет ограничения `ge=0` ни в схеме (`app/schemas.py:15`), ни в
`redeem()`. Проверка `amount > balance` (строка 25) отрицательные суммы не отсеивает — для
`amount < 0` условие всегда `False`, проверка проходит.
Чем кончится: `member.points -= int(amount / Decimal(POINT_VALUE))` при отрицательном `amount`
**увеличивает** баланс баллов. Клиент, отправив `confirm_amount: -100`, начисляет себе баллы через
эндпоинт списания — произвольная инфляция баланса без какого-либо начисляющего события.
Severity: blocker.

### 4. `app/redeem.py:16-29` и `app/repo.py:16-29` — списание без блокировки строки/оптимистичной проверки
`get_member` (repo.py:16-21) делает `SELECT` в одном соединении, `save_member` (repo.py:24-29) —
отдельный `UPDATE` в отдельной транзакции без `WHERE points = :original` и без `SELECT ... FOR
UPDATE`. Между чтением и записью ничего не удерживает состояние member.
Чем кончится: два параллельных запроса на списание для одного `member_id` оба читают один и тот
же баланс, оба проходят проверку `amount > balance`, оба пишут `UPDATE` — итоговое состояние
теряет одно из списаний (lost update) либо баланс уходит в отрицательные значения при повторных
параллельных списаниях полного остатка. Для операции списания баллов (по сути денег) это
классический double-spend через race condition.
Severity: blocker.

### 5. `app/redeem.py:28` — конверсия суммы в баллы округляется вниз без проверки кратности и не согласована с ответом
`int(amount / Decimal(POINT_VALUE))` усекает дробную часть без валидации, что `amount` кратен
`POINT_VALUE`, и без `Decimal.quantize`/явного round. При этом в ответе (строка 36) и в
audit-payload (через `req.dict()`, строка 30) фигурирует именно исходный `amount`, а не то, что
фактически конвертировано в списанные баллы.
Чем кончится: запрос `confirm_amount=0.19` списывает `int(1.9)=1` балл (0.10 фактической
стоимости), но в ответе и аудите записано `redeemed=0.19` — заявленная и фактическая величина
списания расходятся. Повторяемый запрос такой суммы даёт клиенту больше учтённой «выкупленной»
суммы, чем реально списанных баллов — эксплуатируемая утечка ценности, дополнительно усиленная
багом №2.
Severity: blocker.

## Major

### 6. `app/redeem.py:29-30` — изменение баланса и запись аудита не атомарны
`save_member(member)` (строка 29) и `write_audit(...)` (строка 30) открывают две отдельные
транзакции (`engine.begin()` в `repo.py:25` и `repo.py:33` соответственно). Между ними нет общей
транзакции и никакого rollback одной операции при падении другой.
Чем кончится: если `write_audit` упадёт (сетевая ошибка БД, ограничение схемы и т.п.) после того,
как `save_member` уже закоммитил списание, баланс изменится без единой записи в аудите —
нарушение самого требования MR «аудит операции».
Severity: major.

### 7. `app/repo.py:32-37` — audit-payload не содержит фактического результата операции
`write_audit` пишет ровно то, что передано (в `redeem.py:30` это `req.dict()` — сырые поля
запроса: `member_id`, `points`, `confirm_amount`, `comment`). Ни фактически списанная сумма, ни
баланс до/после, ни временная метка операции в payload не попадают.
Чем кончится: для запроса с `confirm_amount=None` (списание всего баланса) в аудите будет лежать
`confirm_amount: null` — по этой записи невозможно восстановить, сколько баллов/денег было
реально списано в конкретный момент. Аудит операции списания не может подтвердить сам факт и
размер списания, что противоречит цели «аудит операции» из описания MR.
Severity: major.

### 8. `app/schemas.py:16-17` — комментарий о поведении Pydantic на лишних полях не соответствует дефолту
Комментарий утверждает: «Лишние поля pydantic по умолчанию отвергает, так что опечатка в имени
поля у клиента даст 422». Дефолт `Config.extra` в Pydantic v1 — `Extra.ignore` (лишние поля
молча отбрасываются), а не `forbid`. В `RedeemRequest` `Config` не переопределён.
Чем кончится: опечатка в имени поля у клиента (например, `commnet` вместо `comment`) не даёт
422 — поле молча теряется и не попадает ни в бизнес-логику, ни в аудит. Комментарий закладывает
у последующих читателей кода ложную уверенность в наличии защиты, которой на самом деле нет.
Severity: major.

### 9. Срок действия баллов («срок действия баллов» из описания MR) не реализован
`valid_until` (`app/redeem.py:33`, `app/schemas.py:25`) вычисляется как `date.today() +
timedelta(days=365)` на каждый ответ и никуда не сохраняется. В `Member` (`repo.py:10-13`) и в
SQL (`repo.py:16-21`, `24-29`) нет ни колонки срока действия, ни какой-либо проверки, что уже
списываемые баллы не просрочены. Заявленная в MR функциональность «срок действия баллов»
фактически отсутствует — `valid_until` в ответе не подтверждён никаким хранимым состоянием и не
влияет на то, можно ли эти баллы списать.
Чем кончится: потребитель API, ориентируясь на `valid_until` в ответе, может считать, что система
отслеживает срок действия и не даст списать просроченные баллы — реального контроля за этим нет,
поле декоративное.
Severity: major.

## Minor

### 10. `app/schemas.py:10` — поле `points: int` объявлено обязательным, но не используется
`RedeemRequest.points` (обязательное, без default) ни разу не читается в `redeem()`
(`app/redeem.py:15-39`). Клиент обязан передавать значение, которое ни на что не влияет —
контракт вводит в заблуждение относительно назначения поля (например, ожидание, что это
проверка ожидаемого баланса на стороне клиента для защиты от гонок, см. находку №4).
Severity: minor.

### 11. `app/db.py:5` — `DATABASE_URL` читается без обработки отсутствия переменной
`os.environ["DATABASE_URL"]` при отсутствии переменной поднимет непойманный `KeyError` на этапе
импорта модуля (создание `engine` на уровне модуля). Приложение не стартует с невнятной
трассировкой вместо явного сообщения о конфигурации.
Severity: minor.

### 12. Роутер `redeem.router` не подключён к приложению FastAPI ни в одном файле каталога
В просмотренном каталоге нет файла, создающего `FastAPI()` и вызывающего
`app.include_router(router)` (`app/__init__.py` пуст, других модулей уровня приложения нет).
Если в рамках этого MR каталог `app/` — это весь новый код целиком, эндпоинт `/redeem` не
экспонируется никаким приложением. Пишу с осторожностью: возможно, включение роутера находится
в файле, не входящем в диапазон ревью.
Severity: minor.
