# Ревью ADR-0014 (docs/adr/0014-search-cache-and-db.md)

Сверка утверждений с источником истины: RFC 9110 (rfc-editor.org/rfc/rfc9110.txt), официальная
документация nginx (nginx.org/en/docs/http/ngx_http_proxy_module.html), документация PostgreSQL 13
(postgresql.org/docs/13/sql-createindex.html) и таблица версий (postgresql.org/support/versioning).
ADR не правился.

## F1 - п.1, строки 18-20: цитата RFC 9110 §9.3.3 перевёрнута

Пункт ADR: «по RFC 9110, раздел 9.3.3, ответы на POST кэшируемы, поэтому прокси вправе отдать
сохранённый ответ на повторный POST».

Что не так: точный текст §9.3.3 - «Responses to POST requests are only cacheable when they include
explicit freshness information ... and a Content-Location header field that has the same value as
the POST's target URI. A cached POST response can be reused to satisfy a later GET or HEAD request.
**In contrast, a POST request cannot be satisfied by a cached POST response because POST is
potentially unsafe**». Норма прямо запрещает то, что ADR из неё выводит: сохранённый ответ на POST
разрешено отдавать только на последующий GET/HEAD, не на повторный POST. Условие «Content-Location
с тем же значением, что и целевой URI POST» в решении не выставлено вовсе - сервис отдаёт только
`Cache-Control`, второе обязательное условие кэшируемости не выполнено даже по букве нормы.

Чем кончится: заявленное основание пункта ложно вдвойне (перевёрнутая причинность + опущенное
условие применимости), решение принято без действительного нормативного основания под него.

Severity: blocker.

## F2 - п.1, строки 19-20: ключ кэша «метод и URI» не учитывает тело POST

Пункт ADR: «Ключ кэша - метод и URI запроса».

Что не так: `/search` - единый URI для всех поисковых запросов, различие между ними лежит в теле
POST (строка запроса, фильтры, сортировка, страница). Документация nginx подтверждает: дефолтный
`proxy_cache_key` не включает тело запроса, и чтобы кэшировать POST раздельно по телу, тело нужно
явно добавить в ключ (`$request_body`) плюс включить POST в `proxy_cache_methods` (дефолт - только
`GET HEAD`). Ключ «метод + URI» без тела - ровно тот случай, который nginx не поддерживает из
коробки для различающихся запросов.

Чем кончится: первый пришедший на `/search` POST кэширует ответ на 60 секунд под ключом, общим для
всех разных поисковых запросов; следующие 60 секунд все пользователи с любым текстом запроса,
категорией или страницей получают чужую выдачу первого запроса. Заявленный в «Последствиях» эффект
«нагрузка снижается в 3 раза за счёт попаданий в кэш» недостижим тем же механизмом - он описывает
работающий per-query кэш, которого текущий ключ не создаёт.

Severity: blocker.

## F3 - п.3, строки 22-24: CREATE INDEX CONCURRENTLY в транзакционной миграции Flyway

Пункт ADR: миграция `V41__search_in_stock_idx.sql` с `CREATE INDEX CONCURRENTLY ...` «штатным
порядком Flyway».

Что не так: документация PostgreSQL 13 (`CREATE INDEX`, раздел про `CONCURRENTLY`) - «a regular
CREATE INDEX command can be performed within a transaction block, but CREATE INDEX CONCURRENTLY
cannot» - жёсткое ограничение уровня СУБД, не настройки. Сам ADR в разделе «Контекст» (строка 11)
заявляет: «миграции применяет Flyway: каждая миграция выполняется в своей транзакции». Штатный
Flyway-прогон оборачивает SQL-миграцию в транзакцию именно так, как описано в собственном контексте
ADR, а `CONCURRENTLY` внутри такой транзакции запрещён на уровне PostgreSQL безусловно.

Чем кончится: применение миграции штатным порядком падает с ошибкой PostgreSQL «CREATE INDEX
CONCURRENTLY cannot run inside a transaction block» - индекс не создаётся, деплой миграции блокирует
релиз. Обход существует (вынести миграцию в свой файл и отключить транзакцию, например
`executeInTransaction=false`/конфиг-файл миграции), но в решении он не назван.

Severity: blocker.

## F4 - п.4, строки 25-26: PostgreSQL 13 уже не «поддерживаемая сообществом версия»

Пункт ADR: «Остаёмся на PostgreSQL 13: это поддерживаемая сообществом версия, плановое обновление
мажорной версии переносим на 2027 год».

Что не так: по официальной таблице версий PostgreSQL (postgresql.org/support/versioning) версия 13
вышла 24.09.2020, EOL - 13.11.2025, графа «Supported» - «No». Дата ADR - 24.09.2026, то есть более
10 месяцев после конца поддержки сообществом; патчи безопасности для 13-й ветки не выпускаются с
ноября 2025 года. Утверждение о поддерживаемости не соответствует действительности на дату решения,
а не только устарело со временем.

Чем кончится: решение сознательно продлевает эксплуатацию БД без патчей безопасности минимум до
2027 года, но ADR представляет это как продолжение штатной поддержки, а не как принятие риска -
компенсирующая мера (расширенная поддержка вендора, усиленный периметр, план на случай уязвимости)
не названа и не взвешена.

Severity: major.

## Не находки (сверено, утверждение подтверждено)
