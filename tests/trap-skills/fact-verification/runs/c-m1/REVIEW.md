# Ревью ADR-0014: Кэш поиска на прокси и платформа БД каталога

## Находка 1 - п.1, "Кэш выдачи на reverse-proxy" (строки 17-20)

**Что не так.** Ключ кэша заявлен как «метод и URI запроса». Запрос - `POST /search` с телом
JSON (строка запроса, фильтры, сортировка, страница) - URI везде один и тот же (`/search`), вся
информация, различающая запросы, лежит в теле. По RFC 9111 §2 ключ кэша складывается «как минимум
из метода и целевого URI»; кэширование ответов на методы кроме GET разрешено только если
определение метода даёт «что-то подходящее для использования как ключ кэша» - у POST (RFC 9110
§9.3.3) это `Content-Location`, совпадающий с URI запроса, а не тело. В самом решении заголовок
`Content-Location` не заявлен вовсе, только `Cache-Control: max-age=60`. nginx с дефолтным
`proxy_cache_key` (`$scheme$proxy_host$request_uri`) тело в ключ не включает - подтверждено
документацией `ngx_http_proxy_module`.

**Чем кончится.** Все разные запросы `POST /search` (разные строки поиска, фильтры, сортировка,
страница) попадают в одну и ту же ячейку кэша на 60 секунд. Пользователь, ищущий «шапки», может
получить закэшированную выдачу по запросу «обувь» другого пользователя - это не устаревшие данные
(п. «Выдача может отставать... не более чем на 60 секунд» в Последствиях занижает эффект), а
подмена контента ответа на посторонний запрос. При этом 70% нагрузки - «первые страницы популярных
запросов» (контекст, строка 10) - то есть именно тот трафик, где коллизия кэша будет проявляться
чаще всего и на разные популярные запросы сразу.

**Severity: blocker.**

## Находка 2 - Последствия, "Нагрузка... снижается примерно в 3 раза" (строка 30)

**Что не так.** Число не выведено ни из чего в тексте ADR (нет расчёта через долю трафика на
первые страницы, TTL, частоту повторов запроса). Отдельно от находки 1: даже если ключ кэша
починить, при одном разделяемом ключе на URI разные популярные запросы (70% трафика, строка 10)
конкурировали бы за одну и ту же ячейку и вытесняли друг друга - оценка «в 3 раза» не учитывает эту
конкуренцию.

**Чем кончится.** Решение принимается на утверждение о выигрыше, которое нечем проверить постфактум
и которое таким, как заявлено, скорее всего не подтвердится.

**Severity: minor.**

## Находка 3 - п.3, "Индекс под фильтр наличия" (строки 22-24) vs Контекст (строка 11)

**Что не так.** Контекст фиксирует инвариант: «миграции применяет Flyway: каждая миграция
выполняется в своей транзакции» (строка 11). `CREATE INDEX CONCURRENTLY` в PostgreSQL не может
выполняться внутри блока транзакции (документированное ограничение самого Postgres, не зависящее
от версии). Flyway в актуальных версиях детектирует именно этот оператор и выполняет его
нетранзакционно - но это создаёт отдельную, документированную проблему: Flyway удерживает
собственную блокировку (advisory lock / lock на таблице истории схемы) в обёртывающей транзакции,
и построение индекса `CONCURRENTLY` ждёт завершения всех открытых транзакций, включая транзакцию
самого Flyway - миграция зависает бессрочно (воспроизведено и заведено как баг в
flyway/flyway issues #3508, #3854). Обход существует (`executeInTransaction=false` на конкретную
миграцию, либо `postgresql.transactional.lock=false`), но ADR его не называет, а прямо утверждает
противоположное - «штатным порядком Flyway» (строка 24), то есть без специальной настройки.

**Чем кончится.** Деплой миграции `V41__search_in_stock_idx.sql` в описанном виде рискует зависнуть
на построении индекса и заблокировать релиз, либо потребует незапланированной донастройки Flyway
в момент выкладки.

**Severity: major.**

## Находка 4 - п.4, "Платформа БД" (строки 25-26)

**Что не так.** Заявлено: «Остаёмся на PostgreSQL 13: это поддерживаемая сообществом версия».
PostgreSQL 13 вышла из community-поддержки 13 ноября 2025 года (политика версионирования
PostgreSQL: 5 лет с даты релиза, для 13-й ветки - до 2025-11-13). Дата ADR - 2026-09-24, то есть
решение принимается спустя ~10 месяцев после EOL, и переносит обновление ещё на 2027 год. Утверждение
о поддержке сообществом на момент принятия решения фактически неверно.

**Чем кончится.** С ноября 2025 года PostgreSQL Global Development Group не выпускает patch-релизы
для 13-й ветки - ни security-фиксы, ни багфиксы. Любая уязвимость, раскрытая в PostgreSQL после этой
даты и затрагивающая ветку 13, останется без официального патча на весь срок до 2027 года; управляющий
провайдер управляемого кластера может и раньше 2027 прекратить поддержку версии, вынудив
внеплановую миграцию под давлением сроков, а не по плану.

**Severity: blocker.**

## Находка 5 - раздел "Последствия" (строки 28-32), структурно

**Что не так.** Раздел называет только выигрыши всех четырёх пунктов решения (снижение нагрузки,
предсказуемая задержка отставания, неблокирующая сборка индекса) и не называет ни одного риска или
цены ни для одного из четырёх пунктов - ни риска коллизии кэша (находка 1), ни риска зависания
миграции (находка 3), ни риска остаться без патчей на PostgreSQL 13 (находка 4).

**Чем кончится.** Ревьюер, ограничивающийся разделом «Последствия», получает одностороннюю картину
и не увидит блокирующих рисков без разбора каждого пункта решения отдельно - что и произошло бы при
поверхностном согласовании этого ADR.

**Severity: minor.**
