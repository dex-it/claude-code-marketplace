# Ревью MR: списание баллов лояльности

Стек: FastAPI 0.95.2 + Pydantic 1.10.13 + SQLAlchemy 1.4.49 (`requirements.txt`). Версии зафиксированы пином - факты о поведении pydantic сверены с документацией версии 1.10, а не latest (в 2.x поведение других полей ниже другое).

## Находки

### 1. `app/schemas.py:11-15` - `confirm_amount: Optional[Decimal]` без default НЕ обязателен в pydantic 1.10, комментарий врёт

Комментарий (строки 11-14) утверждает: "Optional без значения по умолчанию делает поле обязательным, поэтому старые клиенты... получат 422". Сверено с официальной документацией pydantic 1.10 (`Models` -> "Required Optional fields"): начиная с v1.2 голый `Optional[T]` без default **не обязателен** и получает неявный default `None` (обязательным становится только `Optional[T] = ...` / `Field(...)`). Мигрейшн-гайд pydantic 2.0 прямо называет это breaking change V1->V2 - автор применил модель V2 к коду, запиненному на V1.

Чем кончится: старый клиент, который не знает о поле `confirm_amount` и не передаёт его вовсе, НЕ получит 422. pydantic подставит `None`, `redeem()` (`app/redeem.py:21-22`) прочитает это как "списываем весь баланс" и списывает 100% баллов там, где клиент ожидал частичное/нулевое списание. Ни ошибки, ни предупреждения.

Severity: **blocker**

### 2. `app/schemas.py:16-18` - "лишние поля pydantic отвергает" неверно для pydantic 1.10, `Config.extra` не задан

Комментарий утверждает, что опечатка в имени поля даст 422. Сверено с документацией pydantic 1.10 (`Model Config`, поле `extra`): дефолт - `Extra.ignore` (тихо игнорировать), не `forbid`. В `RedeemRequest` класс `Config` не объявлен вовсе - подтверждаю по файлу, никакого `extra = "forbid"` нет.

Чем кончится: клиент, опечатавшийся в имени поля (`confirmAmount`, `confirm_amout` и т.п.), получит 200, а не 422. Опечатанное значение тихо отбрасывается, `confirm_amount` остаётся `None` -> тот же исход, что в находке 1: полное списание баланса вместо ожидаемого частичного, без единого сигнала об ошибке.

Severity: **blocker**

### 3. `app/redeem.py:11,20,28` - `Decimal(POINT_VALUE)` от float-литерала + `int()`-усечение при обратной конвертации

`POINT_VALUE = 0.1` - float. `Decimal(0.1)` не равен `Decimal("0.1")`: конструктор `Decimal` от float даёт точное бинарное представление float (`0.1000000000000000055511151231257827021181583404541015625`), а не десятичное 0.1. Это документированное поведение модуля `decimal`, не зависит от версий из requirements.txt.

Строка 28 обращает конвертацию `int(amount / Decimal(POINT_VALUE))`, где `amount` - Decimal, пришедший от клиента (`confirm_amount`) независимо от вычисленного здесь `Decimal(POINT_VALUE)`. Деление точного клиентского значения на неточный делитель даёт результат вида `99.999999999999999...` вместо `100`, а `int()` усекает к нулю (не round) - при частичном списании итог систематически смещён в сторону недосписания баллов относительно списанной суммы в рублях (учёт "поплывёт": в ответе `redeemed` больше, чем фактически списанные баллы конвертируют).

Severity: **major**

### 4. `app/redeem.py:21-28` - отсутствует проверка `confirm_amount > 0`, отрицательное значение начисляет баллы

Единственная проверка - `if amount > balance: raise 409` (строка 25). Отрицательный `confirm_amount` (например, `-50`) проходит эту проверку (отрицательное всегда `<= balance`). Далее `member.points -= int(amount / Decimal(POINT_VALUE))` (строка 28): вычитание отрицательного числа = сложение. Для `amount = -50`, `POINT_VALUE = 0.1`: `int(-50 / 0.1...) ≈ int(-499.9999...) = -499`, `member.points -= (-499)` => `member.points += 499`.

Чем кончится: любой клиент, зная контракт, может начислить себе баллы, отправив отрицательное `confirm_amount` в запросе на списание. Ни схема (`schemas.py`), ни `redeem()` не валидируют знак.

Severity: **blocker**

### 5. `app/redeem.py:16-29` + `app/repo.py:16-29` - нет блокировки строки / версии при чтении-изменении баланса

`get_member` (`repo.py:16-21`) читает баланс обычным `SELECT` без `FOR UPDATE`, в отдельном `engine.connect()`. `save_member` (`repo.py:24-29`) пишет новое значение в отдельной последующей транзакции без оптимистической версии (нет `WHERE points = :expected`). Между чтением и записью нет блокировки.

Чем кончится: два параллельных запроса на списание одного `member_id` оба прочитают один и тот же баланс, оба пройдут проверку `amount > balance` и оба применят вычитание - классический lost update. Итоговый баланс в базе учтёт только последнюю запись, дав возможность списать больше баллов, чем было на счету (double-spend баллов).

Severity: **blocker**

### 6. `app/redeem.py:29-30` / `app/repo.py:24-37` - списание и аудит в разных транзакциях

`save_member(member)` и `write_audit(...)` - два независимых вызова, каждый открывает свой `engine.begin()` (`repo.py:25` и `repo.py:33`). Между ними нет общей транзакции.

Чем кончится: при сбое процесса (или исключении) между этими двумя вызовами баллы уже списаны в БД, а аудит-запись об операции не создана - ровно то, что заявлено целью MR ("аудит операции"), не гарантировано при отказе на границе двух вызовов.

Severity: **major**

### 7. `app/repo.py:32-37` - аудит записывает только входящий payload, не результат операции

`write_audit(member.id, req.dict())` кладёт в `payload` только поля запроса (`member_id`, `points`, `confirm_amount`, `comment`). Фактически посчитанные `amount` (реально списанная сумма, особенно когда `confirm_amount is None` и списывается весь баланс) и `balance_left` (баланс до/после) в аудит не попадают.

Чем кончится: по аудиту нельзя восстановить, сколько баллов/рублей было фактически списано в операциях с `confirm_amount = null` - в записи будет `null`, а не реальная сумма. Аудит операции списания не самодостаточен для собственной цели MR.

Severity: **major**

### 8. `app/redeem.py:32-38` - "срок действия баллов" из описания MR не реализован

`valid_until = date.today() + timedelta(days=365)` - вычисляется от текущей даты и просто возвращается в ответе. Он не привязан к дате начисления конкретных баллов, не сохраняется никуда (в `Member`/БД нет поля срока действия - `repo.py:10-13`), и ничего в `redeem()` не проверяет истёкшие баллы перед списанием (баланс читается как единое число `member.points`, без разбивки по датам начисления).

Чем кончится: заявленная в описании MR фича "срок действия баллов" на деле - косметическое поле в ответе, не влияющее на бизнес-логику. Просроченные баллы (если такое понятие когда-либо появится) будут списываться так же, как свежие; никакого фактического ограничения по сроку нет.

Severity: **major**

### 9. `app/schemas.py:9-10` / `app/redeem.py` - обязательное поле `points` объявлено, но не используется

`RedeemRequest.points: int` (обязательное, без default) объявлено в контракте, но в `redeem()` не читается ни разу - вся логика управляется только `confirm_amount`. Поле попадает лишь в `req.dict()` для аудита (находка 7), на расчёт не влияет.

Чем кончится: клиент, ожидающий, что `points` задаёт объём списания в баллах (естественная трактовка имени поля рядом с `confirm_amount` в рублях), получит списание, управляемое исключительно `confirm_amount` - несовпадение поля и эффекта тихо проходит валидацию и не даёт клиенту сигнала о том, что `points` игнорируется.

Severity: **major**

### 10. Отсутствует точка входа приложения

В каталоге нет `main.py`/`app.py` с `FastAPI()` и `include_router(router)` - только сам роутер (`app/redeem.py`). `uvicorn` присутствует в `requirements.txt`, но нечем запускать: непонятно, что сервер отдаёт как ASGI app. Если это весь новый код MR (как указано в задаче), приложение не собирается в рабочий сервис.

Severity: **minor** (возможно, вне охвата этого MR, если сборка приложения уже есть в другом месте репозитория - в предоставленном каталоге её нет)
