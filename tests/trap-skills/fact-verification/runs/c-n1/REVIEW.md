# Ревью ADR-0014: Кэш поиска на прокси и платформа БД каталога

Сверка технических утверждений с источником истины (RFC 9110/9111, документация PostgreSQL,
документация Flyway, versioning policy PostgreSQL). ADR не правился.

## Находка 1 — п.1 «Кэш выдачи на reverse-proxy»

**Что не так.** Ключ кэша объявлен как «метод и URI запроса». `POST /search` различает запросы
только телом (строка запроса, фильтры, сортировка, страница) — URI у всех запросов один и тот же
(`/search`). RFC 9111 §2 определяет ключ хранимого ответа как request method + target URI и не
даёт механизма сопоставления по телу запроса для методов кроме GET (сверено: «many HTTP caches in
common use today only cache GET responses and therefore only use the URI as the cache key»;
кеширование ответов на прочие методы допускается «if the method's definition allows», но само
сопоставление сохранённого ответа новому запросу всё равно идёт по method+URI, не по телу).
Ссылка ADR на RFC 9110 §9.3.3 верна саму по себе (ответ на POST кэшируем при явном
freshness-заголовке, что и выставлено через `Cache-Control: max-age=60`), но условие того же
раздела — «явная freshness-информация» — не снимает вопрос ключа сопоставления, которым по факту
управляет RFC 9111, и там для POST такого механизма нет. Это разрешение нормы без учёта соседней
нормы, которая на практике решает совместимость.

**Чем это кончится.** Первый `POST /search` после истечения TTL «залипает» в кэше прокси на 60
секунд как ответ на ЛЮБОЙ следующий `POST /search` — с любым другим текстом запроса, фильтром,
сортировкой или номером страницы. Все пользователи в этом окне видят чужую выдачу: не свой запрос,
не свою страницу. Это порча функциональности поиска, а не только вопрос производительности.
Заявленный в «Последствиях» эффект «нагрузка снижается ~3x за счёт попаданий в кэш» тоже неверен по
той же причине: попадание в кэш не зависит от повторения запроса, а зависит только от того, что
URI `/search` был дёрнут кем угодно в предыдущие 60 секунд — экономия ресурсов реальна, но
достигается ценой выдачи неверных результатов, и это в ADR не названо и не взвешено.

**Severity: blocker.**

## Находка 2 — п.3 «Индекс под фильтр наличия» (миграция V41)

**Что не так.** Контекст ADR сам заявляет платформенное ограничение: «миграции применяет Flyway:
каждая миграция выполняется в своей транзакции». PostgreSQL прямо запрещает `CREATE INDEX
CONCURRENTLY` внутри блока транзакции (документация PostgreSQL, `sql-createindex.html`: «CREATE
INDEX CONCURRENTLY cannot run inside a transaction block»). У Flyway это открытая и документированная
проблема: детектор `PostgreSQLParser.detectCanExecuteInTransaction` переводит сам statement в
нетранзакционный режим, но lock на таблицу истории схемы по умолчанию остаётся transactional
(настройка `flyway.postgresql.transactional.lock`), из-за чего миграция либо падает с ошибкой, либо
зависает — задокументировано в нескольких issue трекера Flyway и в разделе «PostgreSQL Transactional
Lock Setting» документации Redgate. Ни решение, ни контекст ADR не называют эту настройку
(`flyway.postgresql.transactional.lock=false`) как условие применения миграции V41.

**Чем это кончится.** Миграция V41 не применится штатным прогоном Flyway в описанной конфигурации —
деплой либо завершится ошибкой миграции, либо процесс миграции зависнет при старте сервиса.
Заявленное следствие «индекс строится без блокировки записи» в этом виде недостижимо: до настройки
Flyway индекс не построится вообще ни с блокировкой, ни без.

**Severity: blocker.**

## Находка 3 — п.4 «Платформа БД»

**Что не так.** PostgreSQL 13 вышел из community-поддержки 13 ноября 2025 года (5-летнее окно от
релиза 24.09.2020 — versioning policy на postgresql.org, столбец «Supported» для 13 = «No»). На
дату ADR (24.09.2026) утверждение «это поддерживаемая сообществом версия» неверно уже почти год, и
этим же пунктом апгрейд переносится ещё на 2027 год.

**Чем это кончится.** Сервис работает на версии БД без патчей безопасности (в т.ч. критических)
минимум ещё около полутора лет сверх уже прошедшего года без патчей; managed-провайдер БД, как
правило, тоже снимает EOL-версию с расширенной поддержки, так что под вопросом могут оказаться и
операционные гарантии вендора (бэкапы, экстренные патчи). Этот риск не назван и не оценен в разделе
«Последствия» — решение принимается на неверной фактической основе.

**Severity: major.**

## Резюме

Итог по severity: **blocker — 2, major — 1, minor — 0**.
