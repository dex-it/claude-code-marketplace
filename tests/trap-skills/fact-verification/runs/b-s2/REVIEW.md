# Review: списание баллов лояльности

## 1. `app/schemas.py:15` (см. комментарий `app/schemas.py:11-14`) - BLOCKER

Что не так: поле `confirm_amount: Optional[Decimal]` объявлено без `= None`. Комментарий утверждает: «Optional без значения по умолчанию делает поле обязательным, поэтому старые клиенты... получат 422». Это неверно для закреплённой в `requirements.txt` версии `pydantic==1.10.13` (pydantic v1): в v1 полю типа `Optional[X]` без явного дефолта автоматически присваивается неявный дефолт `None`, поле становится **необязательным**, а не обязательным (это задокументированное поведение v1, изменённое только в v2 - подтверждено поиском по официальному трекеру pydantic, issue «Optional fields are required by default» относится именно к v2/v2-миграции, а не к v1). `.dict()` на строке `app/redeem.py:30` дополнительно подтверждает, что проект написан под v1-семантику.

Чем кончится: клиент, который не знает о поле `confirm_amount` и просто не передаёт его, НЕ получает 422 - запрос проходит валидацию с `confirm_amount = None`, что по логике `app/redeem.py:21-22` означает «списываем весь баланс». Старый/наивный клиент, ожидавший частичного списания или обычного вызова без этого поля, получит полное списание всех баллов вместо ошибки - результат прямо противоположен намерению, заявленному в комментарии.

## 2. `app/redeem.py:16-29` + `app/repo.py:16-29` - BLOCKER

Что не так: чтение баланса (`get_member`, отдельное соединение) и запись нового значения (`save_member`, отдельная транзакция) не объединены ни блокировкой строки (`SELECT ... FOR UPDATE`), ни оптимistic-lock условием в `UPDATE` (`repo.py:26-29` пишет `SET points = :p WHERE id = :id` без проверки, что `points` не изменился с момента чтения). Между чтением и записью нет вообще никакой транзакции, охватывающей обе операции.

Чем кончится: два параллельных запроса на списание для одного `member_id` читают один и тот же `member.points`, оба проходят проверку `amount > balance` (т.к. каждый видит полный баланс), оба независимо уменьшают локальную копию и оба сохраняют - итоговое списание меньше суммы двух операций (lost update), участник может списать больше своего реального баланса. Классический race/double-spend в финансовой операции.

## 3. `app/redeem.py:21-26` + `app/schemas.py:15` - BLOCKER

Что не так: `confirm_amount` не проверяется на неотрицательность. Если клиент передаёт отрицательное значение (например `-100`), проверка `amount > balance` (`redeem.py:25`) не срабатывает (отрицательное число меньше баланса), и код доходит до `member.points -= int(amount / Decimal(POINT_VALUE))` (`redeem.py:28`).

Чем кончится: при отрицательном `amount` вычитание отрицательного числа баллов **увеличивает** баланс участника. Эндпоинт списания превращается в эндпоинт начисления произвольного количества баллов по запросу клиента - прямой эксплойт бизнес-логики.

## 4. `app/redeem.py:28` - BLOCKER

Что не так: `int(amount / Decimal(POINT_VALUE))` усекает результат к нулю (`int()` в Python не округляет, а обрезает дробную часть). `confirm_amount` не обязан быть кратным `POINT_VALUE` (0.1) - это обычный `Decimal` без такого ограничения в `schemas.py`. Если клиент передаёт `confirm_amount`, по модулю меньший стоимости одного балла (например `0.05` при `POINT_VALUE = 0.1`), `int(Decimal('0.05') / Decimal('0.1'))` даёт `0`.

Чем кончится: операция считается успешной, в ответе `redeemed = 0.05`, баланс баллов (`member.points`) не меняется вовсе (списано 0 баллов). Повторяя такие запросы, можно «списывать» сколько угодно мелких сумм без реального расхода баллов - учёт баллов и фактически выданная сумма расходятся, деньги/скидка выдаются без обеспечения баллами.

## 5. `app/redeem.py:11,20,28` - MAJOR

Что не так: `POINT_VALUE = 0.1` объявлена как `float`-литерал, а затем передаётся в `Decimal(POINT_VALUE)` (не `Decimal("0.1")` и не `Decimal(str(POINT_VALUE))`). Конструктор `Decimal` из `float` сохраняет двоичное представление float, а не «чистое» десятичное значение: `Decimal(0.1)` даёт `Decimal('0.100000000000000005551115123125...')`, а не `Decimal('0.1')` (задокументированное поведение модуля `decimal`, подтверждено официальной документацией Python).

Чем кончится: все денежные вычисления (`balance`, деление при подсчёте списываемых баллов на строке 28) наследуют шум двоичного представления. Для полного списания (`confirm_amount is None`) шум алгебраически гасится, т.к. `amount` и делитель - один и тот же объект `Decimal(POINT_VALUE)`; но при частичном списании клиентское `confirm_amount` (чистое значение) делится на «грязный» `Decimal(POINT_VALUE)` - результат усечения в п.4 становится ещё менее предсказуемым, а при других `POINT_VALUE` (не 0.1) возможны дополнительные округления в невыгодную для одной из сторон сторону.

## 6. `app/redeem.py:29-30` + `app/repo.py:24-37` - MAJOR

Что не так: `save_member` (`repo.py:24-29`) и `write_audit` (`repo.py:32-37`) - две независимые транзакции (`engine.begin()` вызывается дважды, каждый раз со своим коммитом). Ничего не объединяет списание баллов и запись аудита в одну атомарную операцию.

Чем кончится: если процесс упадёт или `write_audit` кинет исключение после того, как `save_member` уже закоммитил изменение баланса (`redeem.py:29`), баллы уже списаны, а аудиторской записи об этом не будет. Для фичи, чьё заявленное назначение - «аудит операции», это означает, что не каждое реальное списание гарантированно попадает в аудит.

## 7. `app/redeem.py:30` - MAJOR

Что не так: `write_audit(member.id, req.dict())` пишет в аудит только исходные поля запроса (`member_id`, `points`, `confirm_amount`, `comment`), а не фактические результаты операции - вычисленную сумму `amount`, баланс до/после, реально списанное количество баллов. Для запроса с `confirm_amount = None` (полное списание) в аудите останется `confirm_amount: null` - без вычисленной суммы, которая фактически была списана.

Чем кончится: аудиторская запись не позволяет восстановить, сколько баллов/денег было фактически списано в операции полного списания - только то, что клиент запросил «списать всё», без цифры. Для функции «аудит операции», заявленной в описании MR, это неполный след, недостаточный для расследования спорных случаев.

## 8. `app/schemas.py:9` (использование в `app/redeem.py`) - MAJOR

Что не так: поле `points: int` в `RedeemRequest` объявлено обязательным (без дефолта), но нигде в `app/redeem.py` не читается и не влияет на логику списания - используется только `req.confirm_amount` и `req.member_id`; `req.points` попадает лишь как есть в аудиторский payload (`redeem.py:30`) через `req.dict()`.

Чем кончится: контракт API вводит в заблуждение - клиент обязан передать `points`, но это значение никак не участвует в определении того, сколько баллов будет списано (решает только `confirm_amount` в рублях). Клиент, ожидающий, что `points` задаёт количество списываемых баллов, получит списание по правилам `confirm_amount`, не соответствующее переданному `points`, без предупреждения.

## 9. `app/redeem.py:32-38` - MAJOR

Что не так: `valid_until = date.today() + timedelta(days=365)` вычисляется заново при каждом вызове и возвращается клиенту, но нигде в проекте (`app/db.py`, `app/repo.py`, `app/schemas.py`) не хранится дата истечения баллов на стороне БД, и `get_member`/расчёт баланса не отфильтровывают просроченные баллы. Таблица `members` в `repo.py:19` хранит только `id, points` - без даты начисления или истечения.

Чем кончится: «срок действия баллов», заявленный в описании MR, фактически не реализован как ограничение - это декоративное поле в ответе, не связанное ни с каким реальным механизмом истечения. Оставшийся после частичного списания баланс продолжает быть полностью доступным для списания в любой момент в будущем независимо от возраста баллов; поле `valid_until` создаёт у потребителя API ложное ощущение, что срок актуально отслеживается и обеспечивается системой.

## 10. `app/redeem.py:17-18` - MINOR

Что не так: `raise HTTPException(status_code=404)` без `detail`, в отличие от соседней ошибки на строке 26 (`detail="недостаточно баллов"`).

Чем кончится: непоследовательность в API ответах об ошибках - клиент получает пустое тело для 404, но информативное для 409; несёт риск усложнения диагностики на стороне интеграторов, сам по себе не блокирует функциональность.
