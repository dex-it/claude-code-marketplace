# Ревью ADR-0014: Кэш поиска на прокси и платформа БД каталога

## 1. Пункт 1 (кэш выдачи на reverse-proxy) - ключ кэша не различает запросы

**Что не так.** Тело `POST /search` несёт всё, что отличает один поиск от другого - строку запроса,
фильтры, сортировку, страницу. URI при этом всегда один и тот же (`/search`). ADR фиксирует ключ
кэша как «метод и URI запроса», то есть тело в ключ не входит. RFC 9110 §9.3.3 действительно
разрешает кэшировать ответ на POST при явных freshness-заголовках, но это не снимает требование
RFC 9111 к выбору сохранённого ответа - кэш обязан отличать запросы, которые различаются
семантически значимой частью (здесь - телом), а не только методом и URI. Ссылка на RFC оправдывает
«кэшировать POST в принципе», а не выбранный ключ.

Дополнительно: nginx по умолчанию кэширует только GET/HEAD (`proxy_cache_methods` не включает POST
без явной настройки). ADR не описывает ни включение POST в `proxy_cache_methods`, ни кастомный
`proxy_cache_key`, учитывающий тело запроса. Пункт решения читается как «просто включили
Cache-Control: max-age=60» - для POST этого недостаточно, чтобы кэш вообще начал работать так, как
описано.

**Чем кончится.** Если конфигурация всё же заставит nginx кэшировать POST с ключом «метод+URI» (как
буквально написано в ADR): первый пришедший запрос на `/search` закэшируется на 60 секунд, и все
последующие запросы с другим текстом/фильтрами/страницей в этом окне получат ЧУЖУЮ выдачу - не
устаревшую, а неправильную по составу (не поиск, а рандомный результат прошлого запроса). Это
корректностный дефект, а не деградация свежести, и он бьёт по 70% трафика (популярные первые
страницы), то есть массово. Если же оставить nginx как есть (без правки `proxy_cache_methods`),
кэш вообще не сработает, и заявленный в «Последствиях» трёхкратный выигрыш по нагрузке не
случится - ADR декларирует эффект, недостижимый описанной настройкой.

**Severity: blocker**

## 2. Пункт 3 (индекс `idx_items_in_stock`) - `CREATE INDEX CONCURRENTLY` внутри транзакции Flyway

**Что не так.** Контекст ADR сам утверждает: «миграции применяет Flyway: каждая миграция
выполняется в своей транзакции». `CREATE INDEX CONCURRENTLY` в PostgreSQL прямо запрещён внутри
блока транзакции - сервер отклоняет его с ошибкой «CREATE INDEX CONCURRENTLY cannot run inside a
transaction block». Пункт 3 предписывает применить эту миграцию «штатным порядком Flyway», то есть
без отключения транзакционной обёртки для конкретного файла (Flyway это умеет через отдельную
пометку/конфиг, но ADR её не называет).

**Чем кончится.** Миграция `V41__search_in_stock_idx.sql` упадёт при первом же прогоне Flyway с
ошибкой Postgres, а не «построит индекс без блокировки записи», как обещано в «Последствиях». Само
решение противоречит собственному же контексту документа.

**Severity: blocker**

## 3. Пункт 4 (остаёмся на PostgreSQL 13) - версия уже вне поддержки на дату ADR

**Что не так.** PostgreSQL 13 вышел 24.09.2020; по политике версионирования PostgreSQL (5 лет
поддержки после релиза) EOL для 13-й ветки - 13.11.2025. Дата ADR - 24.09.2026, то есть на момент
принятия решения версия уже почти год как не получает патчей безопасности и багфиксов. Утверждение
«поддерживаемая сообществом версия» в основании пункта 4 фактически неверно на дату документа.

**Чем кончится.** Решение сознательно продлевает работу продовой БД каталога (1,2 млн товаров,
900 RPS) на неподдерживаемой версии до 2027 года - это ещё +1 год сверх уже прошедшего EOL без
патчей CVE. ADR не называет компенсирующих мер (усиленный мониторинг известных CVE, WAF/сетевые
ограничения и т.п.) и не помечает это как принятый риск с owner'ом - решение выглядит принятым на
устаревшей фактической基礎.

**Severity: blocker**

## 4. Пункт 1 (Последствия: «отставание не более 60 секунд») - занижена реальная граница устаревания

**Что не так.** В контексте ADR сказано, что остатки из WMS обновляются «в среднем раз в 2-3
минуты». Заявление в «Последствиях» - «выдача может отставать от каталога не более чем на 60
секунд» - учитывает только TTL кэша прокси и игнорирует уже существующее отставание от WMS, которое
само по себе больше заявленной границы. Эти два источника устаревания независимы и складываются, а
не поглощают друг друга.

**Чем кончится.** Читатель ADR (например, при инциденте с ценой/остатком) будет ориентироваться на
неверную оценку максимального лага и не совпадёт с фактическим поведением системы - реальное
отставание «наличия» может достигать нескольких минут, а не 60 секунд.

**Severity: major**

## 5. Пункт 1 - не оговорено кэширование ошибочных ответов

**Что не так.** ADR не указывает, применяется ли `Cache-Control: max-age=60` только к успешным
ответам поиска или безусловно ко всем ответам `/search`, включая `4xx`/`5xx`. Без явного исключения
ошибок из кэшируемых ответов прокси закэширует и код ошибки.

**Чем кончится.** Транзиентная ошибка бэкенда (пиковая перегрузка, разовый таймаут к БД) при
попадании в кэш продлится на весь TTL для конкретного ключа - кратковременный сбой превращается в
гарантированные 60 секунд отказа для этого запроса, что усугубляет, а не смягчает инцидент, который
кэш должен был бы амортизировать.

**Severity: major**

## 6. Пункт 1 - нет решения по «cache stampede» на популярных запросах

**Что не так.** 70% трафика - первые страницы популярных запросов, то есть у кэша будет небольшое
число «горячих» ключей с высокой конкурентной нагрузкой. ADR не упоминает механизм сериализации
промаха (аналог `proxy_cache_lock` в nginx) на момент истечения TTL горячего ключа.

**Чем кончится.** Каждые 60 секунд по горячему ключу возможен одновременный «пролёт» пачки
запросов на бэкенд поиска (thundering herd) в момент истечения TTL - именно в те секунды, когда
нагрузка на Catalog.Search выше среднего пикового значения, которое и обосновывало необходимость
кэша.

**Severity: minor**

## 7. Пункт 1 (Последствия: «нагрузка снижается примерно в 3 раза») - число без расчёта

**Что не так.** Оценка «~3х» не выводится из указанных величин (900 RPS, 70% на популярные первые
страницы, TTL 60 с, ключ кэша). Нет ни формулы, ни допущений (частота повторов одного и того же
запроса в окне TTL), которые бы объясняли, откуда взялась именно тройка, а не другое число.

**Чем кончится.** Показатель нельзя использовать как проверяемую цель capacity-планирования -
он не подтвердится и не опровергнется по факту внедрения, вплоть до случая из находки №1
(если ключ кэша сработает по методу+URI без учёта тела, реальное снижение будет ближе к 100%
запросов из кэша, но за счёт выдачи неверных результатов, а не «в 3 раза»).

**Severity: minor**

## 8. Пункт 1 - не закрыт вопрос персонализации ответа

**Что не так.** ADR не утверждает явно, что ответ `/search` не зависит от пользователя/сессии
(персональные цены, промо, локаль, валюта). Решение о разделяемом кэше на прокси предполагает
эту инвариантность как данность, но нигде её не фиксирует.

**Чем кончится.** Если хотя бы одно поле ответа зависит от пользователя, разделяемый кэш на nginx
отдаст данные одного пользователя другому в пределах TTL - утечка персональных условий между
покупателями. Условие применимости решения (ответ user-independent) должно быть явно названо в
ADR, иначе решение принимается на непроверенном допущении.

**Severity: major**

## 9. Общая структура документа - четыре несвязанные решения под одним заголовком

**Что не так.** Заголовок ADR - «Кэш поиска на прокси и платформа БД каталога» (2 темы), но пункты
решения содержат 4 разные темы: кэш прокси, формат ошибок (RFC 9457), индекс в БД, версия
Postgres. Формат ошибок не относится ни к кэшу, ни к платформе БД.

**Чем кончится.** Единый статус «предложено» на весь документ не позволяет принять/отклонить
пункты по отдельности (например, согласиться с индексом и форматом ошибок, но отправить кэш и
версию Postgres на переработку) - трассировка решений и история их принятия смешивается в одном
файле.

**Severity: minor**

## Итог по severity

- **Blocker: 3** (пп. 1, 3, 4 списка находок выше - ключ кэша, `CREATE INDEX CONCURRENTLY` в
  транзакции Flyway, PostgreSQL 13 вне поддержки)
- **Major: 3** (занижена граница устаревания, кэширование ошибок, персонализация ответа)
- **Minor: 3** (cache stampede, необоснованное число «~3х», бандл нескольких решений в одном ADR)
