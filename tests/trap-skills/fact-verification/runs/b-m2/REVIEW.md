# Review: списание баллов лояльности

Контекст пакета не читал (ограничение задачи), поведение библиотек сверено с
документацией/issue-трекером pydantic 1.10.x и Python `decimal` (requirements.txt
пинует `pydantic==1.10.13`).

## Blocker

### 1. `app/redeem.py:25` (в связке с `app/schemas.py:15`) - нет проверки `confirm_amount > 0`
`confirm_amount` принимается любым `Decimal`, включая отрицательные значения. Проверка
`amount > balance` (redeem.py:25) для отрицательного `amount` всегда `False`, дальше
`member.points -= int(amount / Decimal(POINT_VALUE))` (redeem.py:28) при отрицательном
`amount` **увеличивает** баланс баллов. Кончится тем, что клиент запросом
`confirm_amount: -100` начисляет себе баллы вместо списания - эксплойт бизнес-логики.
Severity: blocker.

### 2. `app/redeem.py:11,20,28,37` - `Decimal(POINT_VALUE)` из float-константы
`POINT_VALUE = 0.1` - float. `Decimal(0.1)` наследует бинарную неточность float
(`Decimal('0.1000000000000000055511151231257827021181583404541015625')`), а не точные
0.1 руб/балл. Документация `decimal` явно рекомендует конструировать из строки
(`Decimal("0.1")`), а не из float, ровно из-за этой проблемы (docs.python.org/3/library/decimal.html;
подтверждено поиском). Дальше `int(amount / Decimal(POINT_VALUE))` (redeem.py:28) на
неточном делителе может округлиться не туда: списанная в баллах величина не совпадёт
с суммой `amount`, которую видит клиент и которая попадёт в audit. Для домена
«списание баллов» это прямая денежная ошибка накопления погрешности, не косметика.
Severity: blocker.

### 3. `app/schemas.py:11-15` - комментарий про обязательность `confirm_amount` не соответствует поведению pydantic 1.10
Комментарий утверждает: «Optional без значения по умолчанию делает поле обязательным».
Для pydantic v1 (пин `pydantic==1.10.13` в requirements.txt) это неверно: поле,
аннотированное `Optional[X]` без явного дефолта, получает **неявный дефолт `None`** и
не является обязательным (issue pydantic/pydantic#2142, pydantic/pydantic#5481,
docs.pydantic.dev/1.10 - обязательность требует `Optional[X] = ...`). Требуется
`... `явно). Следствие в `app/redeem.py:21-22`: старый клиент, который не знает про
`confirm_amount` (или сделал опечатку в имени поля), не получит 422, как рассчитывал
автор, а тихо получит `None` -> код молча трактует это как «списываем весь баланс»
(redeem.py:22). Т.е. любой клиент, забывший поле, спишет 100% баланса вместо
намеченного отказа. Severity: blocker.

### 4. `app/redeem.py:16-30` + `app/repo.py:16-29` - нет блокировки строки, race condition на списании
`get_member` (repo.py:16-21) читает баланс в одном соединении/транзакции,
`save_member` (repo.py:24-29) пишет в другом, без `SELECT ... FOR UPDATE`, без
optimistic-lock (версии/etag) и без единой транзакции, охватывающей оба шага.
Два параллельных запроса на списание для одного `member_id` читают одинаковый
устаревший баланс, оба проходят проверку `amount > balance` и оба независимо
уменьшают `points` - classic lost update. Кончится двойным (или N-кратным)
списанием одобренной суммы с одного и того же баланса баллов, т.е. дырой в учёте,
которую сам MR называет целью («аудит операции»). Severity: blocker.

### 5. «Срок действия баллов» из описания MR фактически не реализован
`Member` (repo.py:10-13) хранит только суммарный `points: int` - без даты
начисления, без партий/лотов. `valid_until` (redeem.py:32-38) - это
`date.today() + timedelta(days=365)`, число, вычисленное на лету и просто
возвращённое клиенту в ответе; оно никуда не пишется и нигде не проверяется при
следующем списании. Нет ни одного места в коде, где протухшие баллы списывались бы
или блокировались от списания. Кончится тем, что заявленная в описании MR фича
«срок действия баллов» на практике не существует - клиент получает правдоподобную
дату в ответе, но баллы годами позже спишутся так же беспрепятственно.
Severity: blocker.

## Major

### 6. `app/schemas.py:16-18` - комментарий про отклонение лишних полей не соответствует дефолту pydantic 1.10
Комментарий: «Лишние поля pydantic по умолчанию отвергает». Дефолт `Config.extra`
в pydantic v1 - `Extra.ignore` (docs.pydantic.dev/1.10/usage/model_config,
подтверждено поиском), не `forbid`. У `RedeemRequest` нет `class Config` с
`extra = "forbid"`. Кончится тем, что опечатка в имени поля клиента
(`cofirm_amount` вместо `confirm_amount`) не даст 422, как рассчитывает автор, а
будет молча проигнорирована - и упадёт в ветку «поле не передано» (см. находку
№3: `confirm_amount` останется `None` -> списание всего баланса). Severity: major.

### 7. `app/redeem.py:29-30` / `app/repo.py:24-37` - списание и аудит не атомарны
`save_member` (repo.py:24-29) коммитит отдельной транзакцией, `write_audit`
(repo.py:32-37) - другой. Если процесс упадёт или `write_audit` не выполнится после
успешного `save_member`, баллы уже списаны, а записи в аудите не будет. Кончится
операцией списания без аудиторского следа - противоречит собственной цели MR
(«аудит операции»). Severity: major.

### 8. `app/schemas.py:10` - поле `points: int` обязательно, но не используется
`RedeemRequest.points` не имеет дефолта (обязательное поле), но в `redeem.py`
нигде не читается - вся логика списания идёт через `confirm_amount`. Кончится тем,
что клиент обязан передавать значение, которое ни на что не влияет: либо это
мёртвый параметр контракта (путает интеграторов - «зачем оно, если списывается
`confirm_amount` в рублях/баллах-эквиваленте»), либо это след недописанной
альтернативной ветки (списание по количеству баллов), которая не реализована.
Severity: major.

### 9. `app/repo.py:32-37` - аудит хранит только запрос, не результат операции
`write_audit(member.id, req.dict())` (redeem.py:30) пишет в лог только то, что
прислал клиент (`member_id`, `points`, `confirm_amount`, `comment`), но не
фактически списанную сумму, не баланс до/после. Когда `confirm_amount is None`
(полное списание, redeem.py:22), в аудите останется `confirm_amount: null` - по
такой записи невозможно восстановить, сколько баллов реально было списано.
Кончится тем, что при расследовании (в т.ч. расхождений из находок №1, №2, №4)
audit-таблица не даёт ответа на вопрос «что произошло», хотя весь смысл записи -
аудит операции. Severity: major.

## Minor

### 10. `app/redeem.py:32-33` - расчёт `valid_until` не соответствует комментарию
Комментарий: «Баллы действуют 365 дней с даты последнего списания, включая
сегодняшний». Если сегодняшний день считается первым из 365, последний день
действия - `today + timedelta(days=364)`, а код считает `today + timedelta(days=365)`
- на день больше заявленного правила. Расходится комментарий с кодом на 1 день.
Severity: minor.

### 11. `app/redeem.py:20-26` - `confirm_amount = 0` принимается как валидное списание
Ничто не отклоняет запрос с `confirm_amount: 0`: проверка `amount > balance` не
срабатывает, `member.points -= 0` не меняет баланс, но `write_audit` всё равно
пишет операцию, а клиент получает `200` с `redeemed: 0`. Кончится шумом в аудите
операциями, которые ничего не списывают, и неоднозначностью для интеграторов
(является ли 0 валидным «частичным списанием» по смыслу MR или должен быть отказ).
Severity: minor.
