# Review: списание баллов лояльности (redeem)

Область: весь каталог - новый код. Дисциплина сверки фактов - `dex-skill-fact-verification`
(прочитан SKILL.md напрямую). Версии сверялись с `requirements.txt` (`pydantic==1.10.13`,
`fastapi==0.95.2`, `SQLAlchemy==1.4.49`) через официальную документацию/migration guide
Pydantic и Python `decimal` docs, а не по памяти "общеизвестного".

## Blocker

### 1. app/schemas.py:11-15, app/redeem.py:21-22 - `confirm_amount` фактически НЕ required
Комментарий утверждает: `Optional[Decimal]` без значения по умолчанию делает поле обязательным,
старые клиенты без него получат 422. Это неверно для закреплённой версии - Pydantic v1
(`1.10.13`): бинарный `Optional[X]` без явного default получает **неявный `= None`**, то есть
поле остаётся опциональным (поведение изменилось только в Pydantic v2 - "In V1, Optional[str]
meant optional field with default None; in V2, required field that can be None",
migration guide docs.pydantic.dev/latest/migration, discussion #2353). Запрос без поля
`confirm_amount` (в т.ч. любой JSON-сериализатор, который по умолчанию не отправляет `None`-поля)
пройдёт валидацию с `confirm_amount=None`, попадёт в `redeem.py:22` (`amount = balance`) и снимет
**весь баланс** вместо ожидаемого отказа 422. Чем кончится: незапрошенное полное списание у любого
клиента, который забыл/не знал про поле - ровно то, что комментарий обещает предотвратить.
Severity: blocker.

### 2. app/repo.py:16-29 (используется из app/redeem.py:16-29) - race condition / lost update
`get_member` читает баланс в своей транзакции (`engine.connect()`), `save_member` пишет
абсолютное значение в отдельной транзакции (`engine.begin()`) простым
`UPDATE members SET points = :p WHERE id = :id` - без `SELECT ... FOR UPDATE`, без
`WHERE points = :old_points` (optimistic lock), без атомарного `points = points - :delta`.
Два параллельных `/redeem` для одного `member_id` читают одинаковый стартовый баланс, каждый
считает свой конечный `points` в Python и перезатирает результат другого. Чем кончится:
одно из двух списаний физически не применяется (double-redeem / lost update) при обычной
параллельной нагрузке - это ядро описанной в MR фичи ("частичное или полное списание"), не
краевой случай. Severity: blocker.

### 3. app/redeem.py:11,20,28,37 - `Decimal(0.1)` вместо `Decimal("0.1")` + `int()`-округление вниз
`POINT_VALUE = 0.1` - float-литерал, передаётся в `Decimal(POINT_VALUE)` (строки 20, 28, 37).
`Decimal(float)` берёт точное бинарное представление float, а не десятичное - для `0.1` это
`0.1000000000000000055511151231257827021...` (Python docs, раздел `decimal`: "Decimal.from_float
(0.1) is not the same as Decimal('0.1')"). `member.points -= int(amount / Decimal(POINT_VALUE))`
(строка 28) не только теряет точность, но и **округляет вниз к нулю** (`int()` - truncation, не
`floor`/`round`). Чем кончится: запрос с `confirm_amount`, которая при делении на искажённый
множитель даёт дробное число меньше 1 (например, `confirm_amount=0.09` при цене балла `0.1`),
даёт `int(...) == 0` - баллы не списываются вовсе, при этом `redeemed`/аудит фиксируют запрошенную
сумму как выполненную. Повторный вызов с такими суммами - списание "рублей" без реального
списания баллов. Severity: blocker.

### 4. app/redeem.py:20-28 / app/schemas.py:15 - нет проверки `confirm_amount >= 0`
Ни в `schemas.py`, ни в `redeem.py` не проверяется знак `confirm_amount`. Отрицательное значение
проходит `if amount > balance` (отрицательное число никогда не больше баланса), а затем
`member.points -= int(amount / Decimal(POINT_VALUE))` **увеличивает** `member.points`, потому что
вычитается отрицательное число. Чем кончится: вызов `/redeem` с отрицательным `confirm_amount`
начисляет баллы члену программы под видом операции списания, и это же попадает в `write_audit`
как обычная запись - способ обхода механики баллов, замаскированный под легитимную операцию.
Severity: blocker.

## Major

### 5. app/schemas.py:16-18 - "лишние поля pydantic отвергает" - тоже неверно для v1
Комментарий утверждает, что опечатка в имени поля даёт 422. По умолчанию `Config.extra` в
Pydantic v1 - `Extra.ignore` (документация docs.pydantic.dev/1.10/usage/model_config), а не
`forbid`; в `RedeemRequest` никакого `class Config` с `extra = "forbid"` нет. Чем кончится: любое
неизвестное/опечатанное поле от клиента молча отбрасывается, а не отклоняется - защита, на которую
ссылается находка №1 (что клиент "будет вынужден узнать про новое поле через 422"), не работает и
здесь. Severity: major.

### 6. app/redeem.py:28-30 (repo.py:24-37) - списание баллов и запись аудита не атомарны
`save_member` и `write_audit` - два независимых `engine.begin()` (два отдельных commit). Если
процесс упадёт или БД откажет между строками 29 и 30 (например, при записи аудита), баллы уже
списаны навсегда, а аудит-записи об этом нет. Чем кончится: ровно та гарантия, которую заявляет
MR ("аудит операции"), не выполняется в момент частичного отказа - расхождение между реальным
балансом и аудиторским следом без возможности его восстановить. Severity: major.

### 7. app/schemas.py:10 - поле `points` обязательно, но нигде не используется
`RedeemRequest.points: int` не имеет default (значит обязателен), но `req.points` не читается ни
в `redeem.py`, ни в `repo.py` (проверено `grep -rn "req.points" app/` - нет попаданий помимо
`member.points`). Чем кончится: клиент обязан присылать число, которое не влияет на результат -
либо мёртвый код, либо нереализованное требование "списание по количеству баллов" (в отличие от
`confirm_amount` в рублях), которое читатель API естественно предположит по названию поля.
Severity: major.

### 8. app/repo.py:32-37, app/redeem.py:30 - аудит не фиксирует, кто выполнил операцию
`write_audit(member.id, req.dict())` сохраняет только `member_id`, `points`, `confirm_amount`,
`comment` - нет поля исполнителя/оператора/сервиса, инициировавшего списание. Чем кончится:
при расследовании спорной или ошибочной операции ("кто списал баллы") аудит не отвечает на
основной вопрос, для которого он заведён по описанию MR. Severity: major.

### 9. app/redeem.py (весь роутер) - нет аутентификации/авторизации на `/redeem`
В ревьюемом каталоге (весь его код - новый по условию задачи) нет ни одной зависимости
`Depends(...)`, проверки токена/сессии или сверки вызывающего с `member_id`; в `requirements.txt`
нет ни одной auth-библиотеки. Чем кончится: если роутер смонтирован без внешней проверки на
уровне gateway (в данном коде это не видно и не подтверждено), любой вызывающий, который знает или
подбирает `member_id`, может списать чужой баланс. Оговорка: могло быть закрыто выше по стеку - в
этом каталоге подтверждений нет ни за, ни против. Severity: major.

### 10. app/redeem.py:32-33 (repo.py:10-13) - "срок действия баллов" не персистится и не влияет ни на что
`valid_until = date.today() + timedelta(days=365)` - фиксированное значение, вычисляемое заново на
каждый вызов и только возвращаемое в ответе. `Member` (repo.py:10-13) хранит только `id` и
`points`, `get_member` выбирает только `id, points` (repo.py:19) - нигде не хранится и не читается
дата начисления или существующий срок действия баллов. Чем кончится: заявленная в описании MR
фича "срок действия баллов" не является реальным механизмом expiry (баллы не "протухают" сами по
себе, значение в ответе ни на что не влияет и не сохраняется) - это декоративное поле ответа, а
не учёт срока действия. Severity: major.

### 11. app/redeem.py (весь эндпоинт) - нет идемпотентности
Нет ключа идемпотентности ни в `RedeemRequest`, ни проверки повторного запроса в `redeem.py`/
`repo.py`. Чем кончится: повторная отправка того же запроса (обычный сетевой retry клиента после
таймаута ответа) выполнит списание дважды - без входного идентификатора операции сервер не может
отличить повтор от нового намерения. Severity: major.

## Minor

### 12. app/schemas.py:18 - `comment: Optional[str]` без ограничения длины
Поле пишется без валидации размера напрямую в `write_audit` -> `json.dumps` -> INSERT. Чем
кончится: клиент может передать сколь угодно длинную строку, попадающую в БД аудита без контроля
объёма. Severity: minor.

### 13. app/schemas.py:23-24 - `Decimal`-поля ответа сериализуются в JSON с потерей точности
Pydantic v1 (закреплённая версия) кодирует `Decimal` в JSON через `decimal_encoder`, который при
ненулевой дробной части отдаёт `float` (issue pydantic/pydantic#1511, `ENCODERS_BY_TYPE`). Чем
кончится: `redeemed`/`balance_left` в ответе `/redeem` уходят клиенту как обычный float, а не
точное десятичное значение, хотя внутри для денежных величин осознанно выбран `Decimal` - смысл
выбора типа теряется на границе API. Severity: minor.
