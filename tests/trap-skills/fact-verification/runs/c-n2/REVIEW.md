# Ревью ADR-0014: Кэш поиска на прокси и платформа БД каталога

Каждая находка сверена с источником истины (официальная документация / RFC / PostgreSQL versioning
policy), не принята со слов ADR. ADR не правился.

## Находка 1 - Ключ кэша не различает запросы

- **Пункт ADR**: п.1, «Кэш выдачи на reverse-proxy» - «Ключ кэша - метод и URI запроса.»
- **Что не так**: тело `POST /search` несёт строку запроса, фильтры, сортировку и страницу; всё это
  не входит в URI. Дефолтный `proxy_cache_key` nginx - `$scheme$proxy_host$request_uri`, тело запроса
  в ключ не входит (подтверждено официальной документацией `ngx_http_proxy_module`). Дополнительно
  nginx по умолчанию кэширует только GET/HEAD (`proxy_cache_methods`), кэширование POST требует
  явного `proxy_cache_methods GET HEAD POST` - в ADR эта настройка не упомянута вовсе.
- **Чем кончится**: любые два разных поисковых запроса (разный текст, фильтры, страница, сортировка)
  на `POST /search` попадают в один и тот же кэш-слот. После первого запроса все последующие
  запросы в течение TTL получают чужую выдачу - пользователь видит не свои результаты поиска.
  Это не деградация производительности, а функциональный дефект выдачи.
- **Severity**: blocker.

## Находка 2 - Основание из RFC 9110 §9.3.3 неверно применено

- **Пункт ADR**: п.1 - «по RFC 9110, раздел 9.3.3, ответы на POST кэшируемы, поэтому прокси вправе
  отдать сохранённый ответ на повторный POST».
- **Что не так**: RFC 9110 §9.3.3 ставит cacheable-ответу на POST два условия сразу: явную
  freshness-информацию (есть, `max-age=60`) **и** заголовок `Content-Location`, совпадающий с
  target URI самого POST (в ADR не упомянут и не выставляется). Ключевое - направление реюза:
  RFC разрешает использовать закэшированный ответ на POST только для удовлетворения **последующего
  GET или HEAD**; отдавать его на повторный POST RFC прямо не разрешает, поскольку POST потенциально
  небезопасен. ADR цитирует условие freshness и утверждает ровно тот случай реюза (повторный POST),
  который норма не покрывает - разрешение нормы взято без её условия.
- **Чем кончится**: единственное нормативное основание пункта 1 не подтверждает описанный
  механизм; сам nginx кэширует POST не по факту соответствия RFC 9110, а по конфигурации
  (`proxy_cache_methods`), так что ссылка на RFC ничего не гарантирует и ничего не меняет в
  поведении - при пересмотре решения (аудит, смена прокси на более строго RFC-конформный кэш)
  обоснование придётся переписывать с нуля.
- **Severity**: blocker (фундамент решения п.1 некорректен; в связке с находкой 1 механизм кэша
  ошибочен и по конфигурации, и по заявленной норме).

## Находка 3 - CREATE INDEX CONCURRENTLY внутри транзакции Flyway

- **Пункт ADR**: п.3 - «Миграция `V41__search_in_stock_idx.sql` создаёт индекс ... штатным порядком
  Flyway» против Контекста - «миграции применяет Flyway: каждая миграция выполняется в своей
  транзакции».
- **Что не так**: `CREATE INDEX CONCURRENTLY` не может выполняться внутри блока транзакции - это
  жёсткое ограничение PostgreSQL (документировано в `CREATE INDEX` reference: операция коммитит
  несколько внутренних транзакций по ходу построения). Контекст ADR сам фиксирует, что Flyway
  оборачивает каждую миграцию в транзакцию «штатным порядком» - именно тем порядком, которым
  запускается V41. Работающая версия Flyway может распознавать `CONCURRENTLY` и исполнять
  миграцию вне транзакции автоматически, но это специфично для версии Flyway и требует явной
  настройки (`flyway.mixed` / нетранзакционный режим) - в ADR версия Flyway и такая настройка не
  названы, только «штатный порядок».
- **Чем кончится**: как описано, миграция V41 в штатном Flyway-транзакционном режиме падает с
  ошибкой Postgres «CREATE INDEX CONCURRENTLY cannot run inside a transaction block» и деплой
  ломается на шаге миграции, либо (в другой конфигурации) индекс остаётся в статусе `INVALID` и
  требует ручной уборки (`DROP INDEX` + повтор). Заявленная цель «не блокировать запись» не
  достигается без изменения режима выполнения миграции, которое ADR не описывает.
- **Severity**: blocker.

## Находка 4 - PostgreSQL 13 не является поддерживаемой версией

- **Пункт ADR**: п.4 - «Остаёмся на PostgreSQL 13: это поддерживаемая сообществом версия, плановое
  обновление ... переносим на 2027 год, когда закончится заморозка платформы».
- **Что не так**: по PostgreSQL Versioning Policy (postgresql.org/support/versioning) каждая
  мажорная версия поддерживается сообществом 5 лет с релиза. PostgreSQL 13 вышла 2020-09-24, финальный
  минорный релиз 13.23 - 2025-11-10, EOL - 2025-11-13. ADR датирован 2026-09-24: на момент принятия
  решения версия уже почти год как не получает патчей от сообщества. Утверждение «поддерживаемая
  сообществом версия» - факт, прямо проверяемый и неверный.
- **Чем кончится**: решение п.4 держится на ложной предпосылке. Кластер каталога до планового
  обновления в 2027 году (по факту - около 2,5 лет с момента EOL) не получит от сообщества ни
  одной security- или bug-фиксной минорной версии; любая уязвимость или дефект, найденные в этом
  окне, остаются в проде без патча от апстрима, если только не оформлена платная extended-support
  подписка - о ней в ADR ничего не сказано.
- **Severity**: blocker.

## Находка 5 - Заявленный предел отставания выдачи не учитывает лаг WMS

- **Пункт ADR**: раздел «Последствия» - «Выдача может отставать от каталога не более чем на 60
  секунд» против Контекста - «остатки обновляются из WMS потоком событий, в среднем раз в 2-3
  минуты по популярному товару».
- **Что не так**: внутреннее противоречие документа. Итоговое отставание цены/наличия, которое
  видит пользователь, от истинного состояния каталога - это лаг WMS-события плюс TTL кэша, а не
  только TTL кэша. Контекст называет лаг WMS «в среднем» 2-3 минуты, то есть без верхней границы;
  «Последствия» тем не менее объявляют суммарный предел в 60 секунд, посчитанный только по кэшу и
  игнорирующий больший и неограниченный сверху вклад WMS.
- **Чем кончится**: читатель ADR, оценивающий риск (например, «можем ли мы 60 секунд показывать
  товар как имеющийся в наличии, если его раскупили») получает on-документ цифру, которая занижает
  реальное окно в разы; решения о допустимости риска, принятые по этой цифре, ошибочны.
- **Severity**: major.
