# Ревью MR: Pricing.Api

Описание MR: базовая цена от поставщика с кэшем, финальная цена со скидкой, кэш страниц каталога
с инвалидацией по событию, разбор JSON-фида поставщика, уведомление о смене цены.

Весь каталог - новый код, ревью построчное по всем 5 файлам. Факты о поведении библиотек сверены
с официальной документацией (Microsoft Learn / issue-трекеры dotnet), где утверждение в коде
расходилось с ожидаемым API или дефолтным поведением - см. пометки "сверено".

## Находки

### 1. CatalogCache.cs:17 - вызов несуществующего метода `EvictByTagAsync`
```csharp
await cache.EvictByTagAsync("catalog", ct);
```
У `HybridCache` (Microsoft.Extensions.Caching.Hybrid, пакет закреплён в csproj на 9.3.0) метод
инвалидации по тегу называется `RemoveByTagAsync`, а не `EvictByTagAsync` (сверено: Microsoft Learn,
`HybridCache.RemoveByTagAsync` - https://learn.microsoft.com/en-us/dotnet/api/microsoft.extensions.caching.hybrid.hybridcache.removebytagasync;
обсуждение переименования Evict->Remove в dotnet/aspnetcore#55332). Метода с именем `EvictByTagAsync`
в публичном API класса нет.
**Чем кончится:** код не компилируется - CS1061, вся фича "инвалидация каталога по событию" не
собирается.
**Severity: blocker**

### 2. SupplierFeedParser.cs:10,14 - регекс вырезания комментариев ломает URL внутри JSON-строк
```csharp
private static readonly Regex LineComment = new(@"//.*$", RegexOptions.Multiline | RegexOptions.Compiled);
...
var clean = LineComment.Replace(json, string.Empty);
```
Паттерн `//.*$` не различает "комментарий поставщика" и любую другую подстроку `//` внутри JSON-строки.
`SupplierItem.ImageUrl` в этом же файле документирован как абсолютный URL вида
`https://cdn.supplier.example/img/123.png` (строка 22-23) - то есть штатное значение поля само
содержит `//` сразу после `https:`. Как только регекс встречает это `//`, он вырезает всё до конца
строки (`$` в Multiline-режиме - конец текущей строки; если фид - однострочный/минифицированный JSON,
то до конца всего документа).
**Чем кончится:** на любом реальном фиде с картинками (а `ImageUrl` - обязательное поле контракта)
парсинг либо возвращает обрубленный `ImageUrl` с оборванной строкой (невалидный JSON,
`JsonException` из `Deserialize` на строке 15), либо, если фид в одну строку, теряет весь хвост
документа после первого товара с картинкой. Фича "разбор JSON-фида поставщика" не работает на
собственном же примере данных из этого MR.
**Severity: blocker**

### 3. PriceService.cs:22 - целочисленное деление гасит скидку
```csharp
var discounted = basePrice - basePrice * (discountPercent / 100);
```
`discountPercent` - `int`, `100` - `int`-литерал, `discountPercent / 100` - целочисленное деление.
Для любого `discountPercent` в диапазоне 1..99 результат деления - `0` (округление к нулю), то есть
`discounted == basePrice` - скидка не применяется вообще. Совпадает с ожиданием только на границах:
`discount=0` (нет скидки - и так верно) и `discount=100` (цена уходит в 0 - совпадает случайно).
**Чем кончится:** основная фича MR "финальная цена со скидкой" возвращает полную цену без скидки
для всех практических значений скидки (1-99%), молча и без исключения - баг не будет замечен без
теста на нецелой доле от 100.
**Severity: blocker**

### 4. PriceService.cs:7-8 (комментарий) vs фактическое поведение `IMemoryCache.GetOrCreateAsync`
```csharp
// GetOrCreateAsync гарантирует, что фабрика вызовется один раз на ключ даже при
// параллельных запросах, поэтому отдельная блокировка вокруг поставщика не нужна.
```
Утверждение не подтверждается: `IMemoryCache.GetOrCreateAsync` (расширение из
Microsoft.Extensions.Caching.Memory) не даёт stampede-protection - фабрика может выполниться
параллельно несколько раз на один и тот же ключ при одновременном промахе кэша (сверено:
dotnet/runtime#71581 "CacheExtensions.GetOrCreate{Async} thread-safety"; эту защиту как раз и
добавляет `HybridCache`, которым в этом же MR обёрнут каталог, но не цена). Комментарий описывает
поведение `HybridCache`, а не `IMemoryCache`, которым в этом файле кэшируется цена.
**Чем кончится:** `ISupplierClient.GetPriceAsync` в `Contracts.cs:5` явно документирован лимитом
поставщика "не больше 5 запросов в секунду на ключ; превышение - бан ключа на час". Без
однопоточного гейта параллельный всплеск запросов на один и тот же `sku` в момент истечения
5-минутного TTL кэша даёт несколько одновременных вызовов `GetPriceAsync` на этот ключ - при
достаточной параллельности это и есть прямой путь к часовому бану ключа у поставщика, который
комментарий ошибочно объявляет невозможным.
**Severity: major**

### 5. CatalogCache.cs - класс не используется ни одним потребителем в этом MR
`GetPageAsync` и `InvalidateAsync` не вызываются ни из одного файла каталога (grep по всему MR не
находит ссылок на `CatalogCache` вне его собственного определения). Комментарий на строке 14
("Вызывается из обработчика события "каталог обновлён"") описывает обработчик события, которого в
делаемом MR нет.
**Чем кончится:** заявленная в описании MR фича "кэш страниц каталога с инвалидацией по событию" в
этом MR не подключена ни к одному эндпоинту или подписчику события - код мёртв, инвалидация никогда
не будет вызвана тем механизмом, который описывает сам комментарий.
**Severity: major**

### 6. PricesController.cs:20-24 - `Notify` не инвалидирует цену, которую сам же кэширует
`Notify` только форвардит уведомление во внешний сервис (`httpFactory.CreateClient("notifications")`),
но не вызывает ни `CatalogCache.InvalidateAsync`, ни любую инвалидацию ключа `price:{sku}` из
`PriceService` (5-минутный `AbsoluteExpirationRelativeToNow`, `PriceService.cs:13`).
**Чем кончится:** сразу после того как этот же API объявит подписчикам "цена изменилась", он до 5
минут продолжит отдавать по `GET /prices/{sku}` старую цену из собственного кэша - подписчики узнают
о смене цены раньше, чем сам API готов её показать.
**Severity: major**

### 7. PricesController.cs:22-23 - `PostAsync` с относительным URI без видимой регистрации `BaseAddress`
```csharp
var client = httpFactory.CreateClient("notifications");
await client.PostAsync($"/price-changed/{sku}", null, ct);
```
В каталоге MR нет `Program.cs`/composition root и, соответственно, нет `AddHttpClient("notifications", ...)`
с настройкой `BaseAddress`. `HttpClient.PostAsync` с относительным URI требует, чтобы у клиента был
установлен `BaseAddress`, иначе бросается `InvalidOperationException` в момент запроса. Проверить
регистрацию по коду MR невозможно - её здесь просто нет; если она не задана где-то за пределами
этого MR, `Notify` будет падать на каждом вызове.
**Чем кончится:** при отсутствии регистрации именованного клиента с `BaseAddress` - `500` на каждый
вызов `/prices/{sku}/notify`. Отмечаю с пометкой неопределённости: composition root мог остаться вне
диффа этого MR - если так, находка снимается ревью того файла, где регистрация действительно есть.
**Severity: major (need confirmation: не найден Program.cs/DI-регистрация "notifications" в MR)**

### 8. SupplierFeedParser.cs:15 - десериализация без `JsonSerializerOptions`, чувствительна к регистру
```csharp
return JsonSerializer.Deserialize<SupplierFeed>(clean)
```
Без явных `JsonSerializerOptions` `System.Text.Json` по умолчанию сопоставляет имена свойств с
учётом регистра. Контракт (`Sku`, `Price`, `ImageUrl`, `Items`) - PascalCase. Реальная схема
JSON-фида поставщика в этом MR не показана; если фид отдаёт camelCase-ключи (частая практика для
внешних JSON-фидов), совпадения по имени не будет и поля тихо останутся `default` (`null`/`0`)
вместо исключения.
**Чем кончится:** непроверяемо по коду этого MR - реальная схема фида не входит в диф. Отмечаю как
риск с пометкой неподтверждённости, не как факт: если у поставщика camelCase - разбор фида тихо
теряет данные без единого исключения.
**Severity: minor (unverifiable - схема фида поставщика не входит в MR)**

### 9. CatalogCache.cs:7-12 - `GetOrCreateAsync` без `TState`-перегрузки
```csharp
public ValueTask<CatalogPage> GetPageAsync(int page, CancellationToken ct) =>
    cache.GetOrCreateAsync(
        $"catalog:page:{page}",
        async token => await repo.LoadPageAsync(page, token),
        ...
```
Официальная рекомендация для `HybridCache` на горячем пути - перегрузка с явным `TState`, чтобы не
аллоцировать замыкание на каждый вызов (лямбда захватывает `page` и `repo`). Не влияет на
корректность.
**Чем кончится:** лишняя аллокация замыкания на каждый промах кэша страницы каталога - заметно
только под нагрузкой/профилированием, функционально безопасно.
**Severity: minor**

### 10. PricesController.cs:12,14 - `discount` без значения по умолчанию
```csharp
public async Task<ActionResult<decimal>> Get(string sku, [FromQuery] int discount, CancellationToken ct)
{
    if (discount is < 0 or > 100) return BadRequest();
```
`discount` - невалидируемый (`int`, не `int?`) параметр без default. Запрос без query-параметра
`discount` не пройдёт биндинг как "0 по умолчанию" - ASP.NET Core вернёт `400` на отсутствующий
required-параметр (стандартное поведение `[ApiController]`), а не выполнит подстановку 0. Для
"обычной цены без скидки" клиент обязан явно писать `?discount=0`.
**Чем кончится:** не баг корректности, а неудобный контракт - "цена без скидки" не имеет короткого
пути вызова, что расходится с тем, как обычно ожидают использовать этот эндпоинт.
**Severity: minor**

### 11. PricesController.cs:20-24 - `Notify` отправляет пустое тело, без данных о том, что изменилось
```csharp
await client.PostAsync($"/price-changed/{sku}", null, ct);
```
Уведомление о смене цены не несёт ни старой, ни новой цены, ни времени события - только `sku` в URL.
Получатель обязан сам сходить за актуальной ценой (см. находку 6 - в момент такого re-fetch она
ещё может быть в кэше устаревшей).
**Чем кончится:** downstream не может отличить "цена выросла" от "цена упала" без дополнительного
запроса, теряется дедупликация/идемпотентность события (нет ID события или временной метки).
**Severity: minor**
