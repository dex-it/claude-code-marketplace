# Ревью ADR-0014: Кэш поиска на прокси и платформа БД каталога

ADR не правился. Ниже — находки со ссылкой на пункт, дефект, исход и severity.

## F1. п.1, ключ кэша — разные поисковые запросы схлопываются в один

**Где:** «Ключ кэша - метод и URI запроса.»

**Что не так:** По контексту ADR все параметры поиска (строка запроса, фильтры, сортировка,
страница) передаются в теле `POST /search`, а не в URI — URI у всех запросов один и тот же
(`/search`). Ключ кэша nginx по умолчанию — `$scheme$proxy_host$request_uri`, тело запроса в него
не входит; чтобы разные тела давали разные записи кэша, `proxy_cache_key` нужно явно переопределить
(например, добавить `$request_body`) — ADR это не делает и даже прямо фиксирует ключ как «метод и
URI». Проверено: nginx `ngx_http_proxy_module` docs + независимые источники по кэшированию POST в
nginx — тело не входит в дефолтный ключ, добавляется отдельно.

**Чем кончится:** В пределах каждого 60-секундного окна кэш хранит ответ ПЕРВОГО запроса к
`/search` и отдаёт его всем последующим — независимо от их строки поиска, фильтров, сортировки и
страницы. Это не устаревание данных (как заявлено в «Последствиях»), а показ пользователю чужой
выдачи: поиск по «телефон» может вернуть результаты чьего-то поиска по «холодильник». При 900 RPS и
70% трафика на топ-запросы эффект будет систематическим, а не редким.

**Severity:** blocker.

## F2. п.1, обоснование через RFC 9110 §9.3.3 — норма процитирована не полностью

**Где:** «по RFC 9110, раздел 9.3.3, ответы на POST кэшируемы, поэтому прокси вправе отдать
сохранённый ответ на повторный POST»

**Что не так:** Раздел разрешает кэширование ответа POST только при одновременном выполнении двух
условий: явная freshness-информация (есть — `Cache-Control: max-age=60`) И заголовок
`Content-Location`, совпадающий с целевым URI запроса (в решении не упомянут и, судя по описанию,
не выставляется). Кроме того, по семантике HTTP-кэширования (RFC 9111) сохранённый ответ
предназначен для обслуживания последующих GET/HEAD к тому же URI, а не для обслуживания следующего
POST — POST как потенциально небезопасный метод не должен удовлетворяться из кэша. ADR цитирует
только половину условия и делает из неё вывод, который норма не поддерживает.

**Чем кончится:** Основание пункта 1 держится на неполном прочтении нормы; независимо от F1, сама
схема «отдавать сохранённый ответ на повторный POST по URI» не то, что описывает процитированный
раздел. Решение нужно обосновывать иначе (как политику самого прокси, а не как соответствие HTTP
caching semantics), иначе ссылка на RFC ложная.

**Severity:** major.

## F3. Последствия — заявленное отставание выдачи занижено

**Где:** «Выдача может отставать от каталога не более чем на 60 секунд.» (сверено с Контекстом:
«остатки обновляются из WMS потоком событий, в среднем раз в 2-3 минуты по популярному товару»)

**Что не так:** 60 секунд — это задержка, которую добавляет только кэш прокси сверх уже
существующего отставания БД от WMS (в среднем 2-3 минуты по популярным товарам). Формулировка
«не более 60 секунд» читается как итоговая граница отставания выдачи от фактического состояния
каталога, а не как добавка к уже имеющемуся лагу.

**Чем кончится:** Итоговое расхождение показанных цены/наличия с реальным состоянием каталога по
популярным товарам может доходить до ~3-4 минут, а не до 60 секунд, как написано. Решение о
приемлемости TTL=60s принимается на основании неверной оценки итогового риска (продажа товара,
которого уже нет, показ неверной цены).

**Severity:** major.

## F4. п.3 — миграция с `CREATE INDEX CONCURRENTLY` несовместима с заявленным режимом Flyway

**Где:** «Индекс под фильтр наличия... штатным порядком Flyway» + Контекст: «миграции применяет
Flyway: каждая миграция выполняется в своей транзакции»

**Что не так:** `CREATE INDEX CONCURRENTLY` не может выполняться внутри блока транзакции — это
прямо задокументированное ограничение PostgreSQL («CREATE INDEX CONCURRENTLY cannot be executed
inside a transaction block», docs `sql-createindex.html`). ADR сам фиксирует, что Flyway оборачивает
каждую миграцию в транзакцию, и не называет никакого исключения (например, отключения
транзакционности для конкретного скрипта) для миграции `V41`.

**Чем кончится:** При применении миграции «штатным порядком Flyway» Postgres вернёт ошибку, миграция
не применится ни разу — сам механизм, которым предполагается решить проблему производительности
фильтра `in_stock`, не работает в описанном виде. Внутреннее противоречие документа: пункт решения
противоречит факту, названному в его же Контексте.

**Severity:** blocker.

## F5. п.4 — PostgreSQL 13 на дату ADR уже не поддерживается сообществом

**Где:** «Остаёмся на PostgreSQL 13: это поддерживаемая сообществом версия, плановое обновление
мажорной версии переносим на 2027 год»

**Что не так:** По политике версионирования PostgreSQL (5 лет поддержки от даты выпуска; 13.0 вышла
24.09.2020) PostgreSQL 13 достигла EOL 13.11.2025 и с этой даты не получает патчей безопасности от
community (сверено: `postgresql.org/support/versioning`, актуальная таблица версий на дату
ADR — 2026-09-24). Утверждение, на котором держится решение не обновляться, фактически неверно уже
почти год на момент ADR.

**Чем кончится:** Решение откладывает обновление до 2027 года, опираясь на несуществующую
поддержку; сервис поиска (900 RPS, ~1.2 млн товаров) в проде работает на БД без патчей безопасности
как минимум ещё год, и это не названо риском и не компенсируется (например, коммерческой extended
support или compensating controls) — ADR представляет отсутствие апдейтов как штатную, безопасную
ситуацию.

**Severity:** blocker.

## F6. п.1 — кэширование POST не включено по умолчанию, конфигурация не названа

**Где:** «Ответы `POST /search` кэшируются на прокси (nginx) на 60 секунд.»

**Что не так:** nginx по умолчанию кэширует только GET/HEAD (`proxy_cache_methods` по умолчанию —
`GET HEAD`); чтобы кэшировать POST, нужно явно добавить `POST` в `proxy_cache_methods`. Решение не
называет эту настройку как часть изменения — при развёртывании «как написано» кэш для `POST /search`
просто не заработает без дополнительной, не упомянутой конфигурации.

**Чем кончится:** Само по себе не ломает корректность (в отличие от F1) — при отсутствии настройки
ожидаемого снижения нагрузки (пункт «Последствия»: «снижается примерно в 3 раза») не произойдёт,
и это будет выглядеть как несостоявшийся деплой, а не как явно спроектированный шаг.

**Severity:** minor.

## F7. Раздел «Решение» — нет рассмотренных альтернатив и плана отказа/раскатки

**Где:** документ целиком (раздел «Решение»).

**Что не так:** Для пунктов 1 и 4 (кэш на прокси при некорректном разрешении конфликта с ключом
запроса; отложенное обновление БД) не зафиксированы ни альтернативы (например: кэш по составному
ключу/хешу тела, кэш на уровне приложения, cache warm-up), ни признаки, по которым решение будет
пересмотрено раньше 2027 года (например, объявление уязвимости в PG13, рост несоответствий
выдачи).

**Чем кончится:** При пересмотре решения (инцидент из-за F1 или F5) нет зафиксированного основания,
почему альтернативы не подошли — ревизия ADR откатится к обсуждению с нуля.

**Severity:** minor.

## Источники сверки фактов

- PostgreSQL versioning policy / таблица поддерживаемых версий — `postgresql.org/support/versioning` (PG13 EOL 2025-11-13).
- PostgreSQL docs, `CREATE INDEX` — `postgresql.org/docs/current/sql-createindex.html` («CREATE INDEX CONCURRENTLY cannot be executed inside a transaction block»).
- RFC 9110 §9.3.3 (POST) и RFC 9111 (HTTP Caching) — условия кэшируемости ответа POST (explicit freshness + `Content-Location`) и назначение сохранённого ответа для последующих GET/HEAD, не для повторного POST.
- RFC 9457 vs RFC 7807 — подтверждено: RFC 9457 (июль 2023) обсолетит RFC 7807, пункт 2 ADR фактически верен, находки по нему нет.
- nginx `ngx_http_proxy_module` (`proxy_cache_key`, `proxy_cache_methods`) — дефолтный ключ кэша не включает тело запроса; POST не кэшируется без явного `proxy_cache_methods POST`.
