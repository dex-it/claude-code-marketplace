`POST /api/orders/:id/pay` готов, `npm run typecheck` и `npm test` проходят (в api 18 тестов, в web 2). Вживую против шлюза или песочницы я его не запускал.

**Изменённые файлы**
- `api/src/app.ts` — эндпоинт оплаты.
- `api/src/payments/http-gateway.ts` (новый) — HTTP-реализация `PaymentGateway`.
- `api/src/server.ts` — подключает `HttpPaymentGateway` вместо заглушки.
- `api/src/config.ts` — читает `PAYMENT_URL` и `PAYMENT_API_KEY`.
- `api/src/domain/order.ts` — у заказа появилось поле `transactionId`.
- `api/test/orders.test.ts`, `api/test/http-gateway.test.ts` (новый) — тесты.
- `README.md` — описание новых переменных окружения.

**Решения**
- **Переменные окружения:** `PAYMENT_URL` и `PAYMENT_API_KEY` обязательны. Без них API не запустится, а не упадёт при первой оплате.
- **Сбои шлюза:** при обрыве соединения, ответах `409` и `5xx` запрос повторяется до 3 раз с тем же `order_id`. Шлюз по контракту не списывает повторно, так что это безопасно. Если шлюз так и не ответил, покупатель получает `502 payment_unavailable`, а заказ остаётся в статусе `new`. Ответы `400` и `401` не повторяются и дают `500`.
- **Параллельные запросы:** повторный запрос оплаты того же заказа, пока первый в работе, получает `409`. Эта защита работает только внутри одного процесса.
- **Письмо и аналитика:** если `notifier.orderPaid` или `analytics.track` падают после успешного списания, ошибка пишется в лог, а ответ остаётся `200`.
- **Обёртка для async:** в Express 4 ошибки из async-обработчиков не попадают в `errorHandler`, поэтому я добавил небольшую обёртку `asyncHandler` в `app.ts`.

Тесты на эндпоинт покрывают успех, отказ банка (`402`), чужой или несуществующий заказ (`404`) и повторную оплату (`409`). Отдельно проверены `502` и сбои письма и аналитики.
