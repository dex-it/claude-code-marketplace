Я добавил два workflow, ничего не коммитил. Ни один из них не запускал: сборок и сети нет, YAML не проверен.

**Изменённые файлы** (оба новые):
- `.github/workflows/ci.yml`
- `.github/workflows/size-label.yml`

**Что в `ci.yml`**
- **Триггеры:** запускается на каждый PR и на push в `main`. Права по умолчанию `contents: read`. Повторные push в тот же PR отменяют предыдущий прогон.
- **Тесты на ubuntu:** `test` собирает решение и гоняет все тесты на `ubuntu-latest`, Docker для Testcontainers там есть.
- **Тесты на windows:** `contracts-windows` гоняет только категорию `Contracts`.
- **Результаты и покрытие:** оба тестовых job сохраняют trx и coverlet-покрытие артефактами с `retention-days: 14`.
- **Форматирование:** `format` проверяет через `dotnet format --verify-no-changes`. Отчёт сохраняется артефактом. Job помечен `continue-on-error`, поэтому ничего не блокирует.
- **Аудит зависимостей:** отдельный job `audit` падает, если `dotnet list package --vulnerable --include-transitive` находит уязвимые пакеты. Его в задаче нет, я добавил по `ci-gates`, где аудит входит в минимум гейтов.
- **Лицензии:** `license-check` вызывает reusable workflow `@v2` после `test` и `contracts-windows`.
- **Образ и деплой:** на `main` после всех проверок `publish` собирает образ и пушит `registry.example.com/depot/api:<sha>`. Затем `deploy-stage` запускает `deploy.yml` в `dex/depot-infra`. Оба job-а запускаются только на push в `main`, так что форки секретов не касаются.

**Что в `size-label.yml`**
- Метка ставится по сумме добавленных и удалённых строк: меньше 50 — `size/S`, меньше 300 — `size/M`, иначе `size/L`. Пороги я выбрал сам, в задаче их нет.
- Для форков используется `pull_request_target`. Код PR в этом workflow не выкачивается и не исполняется, число строк берётся из API.

**Замечания к задаче**
1. **Токен для деплоя.** `GITHUB_TOKEN` не может запускать workflow в другом репозитории. Я использовал секрет `DEPOT_INFRA_DISPATCH_TOKEN` (PAT или GitHub App с правом Actions: write на `dex/depot-infra`). Его нужно завести, имя можно поменять.
2. **Что передавать в деплой.** Входы `workflow_dispatch` в `deploy.yml` неизвестны, поэтому я вызываю его без входов. Деплой не узнает тег образа (`<sha>`). Нужно сверить входы в `dex/depot-infra` и передать тег.
3. **Обязательные проверки.** Гейты (`test`, `contracts-windows`, `audit`, `license-check`) надо объявить required checks в защите ветки `main`. Из файла этого не сделать. `format` в required не добавлять.
4. **Лок-файлов нет.** В репозитории нет `packages.lock.json`, поэтому восстановление идёт не в locked-mode, а `ci-gates` требует установку по лок-файлу. Без `dotnet` я их сгенерировать не могу. Нужно включить `RestorePackagesWithLockFile`, закоммитить лок-файлы и добавить `--locked-mode` в restore.
5. **Статический анализ.** Отдельного линтера нет: его заменяют `TreatWarningsAsErrors` при сборке и отчёт `dotnet format`, который по задаче не блокирует.
6. **Self-hosted раннеры `depot-linux` не использованы.** PR приходят из форков, а исполнение чужого кода на раннерах внутри сети компании небезопасно. Для `push` в `main` их можно подключить отдельно, если нужно. Исключение — job `publish`: ему нужен Docker, а на этих раннерах он неизвестен.
7. **Версия reusable workflow.** `@v2` — это подвижный тег. Лучше закрепить SHA. Кроме того, неизвестно, нужны ли этому workflow секреты или входы. В форках секреты недоступны.
8. **Образ собирается заново.** Образ собирается из Dockerfile, а не из артефактов тестового job. Это нормально, но сборка выполняется дважды.
9. **Метки.** Метки `size/S`, `size/M` и `size/L` должны существовать в репозитории, иначе `gh pr edit` упадёт. Создайте их заранее.
