# Ревью MR: отчёты по клиентам и счета

Контекст: прод, 40 тыс. клиентов, 3 млн заказов. EF Core 8 + Npgsql, `UseLazyLoadingProxies` включён глобально.

Итог: blocker - 6, major - 8, minor - 8. В текущем виде MR не мерджить.

## Blocker

### B1. Controllers/OrderExportController.cs:15 - SQL-инъекция
`FromSqlRaw($"... WHERE status = '{status}'")`: интерполяция собирает обычную строку до вызова, и `status` из query string попадает в SQL как есть. `FromSqlRaw` параметры из такой строки не делает.
Чем кончится: `?status=x' OR 1=1; DROP TABLE ...--` читает или портит любые данные БД. Эндпоинт открыт без авторизации (B6).
Правка: `FromSql($"... WHERE status = {status}")` (параметр) или обычный LINQ `Where(o => o.Status == status)`.

### B2. Controllers/OrderExportController.cs:14-24 - выгрузка без предела целиком в память
Все заказы со статусом материализуются (`ToListAsync`, `SELECT *`), потом весь CSV собирается в `StringBuilder`, потом копируется ещё раз в `byte[]` (`GetBytes`). Для частого статуса (например, выполненные) это большая часть из 3 млн строк: три полные копии на запрос, строка и массив в LOH.
Чем кончится: один запрос бухгалтерии поднимает память пода на сотни МБ, при нескольких параллельных - OOM и рестарт сервиса; время ответа растёт вместе с таблицей.
Правка: проекция на 5 нужных полей, `AsAsyncEnumerable()` и запись строк прямо в `Response.Body` (или `PipeWriter`) по мере чтения; либо фильтр по периоду с обязательным пределом.

### B3. Controllers/CustomerReportsController.cs:25-26 - вся таблица заказов в память ради одного числа
`db.Orders.ToListAsync()` без фильтра тянет все 3 млн заказов (с отслеживанием изменений и lazy-прокси), затем считает `Count` в памяти.
Чем кончится: каждый вызов сводки - полный скан таблицы, передача всех строк по сети и гигабайты в памяти. Под нагрузкой - OOM и таймауты.
Правка: `await db.Orders.CountAsync(o => o.CustomerId == customerId && o.CreatedAt >= from)`: фильтр и агрегат в БД.

### B4. Controllers/CustomerReportsController.cs:28 - сериализация графа заказов падает на цикле, выполняется при любом уровне логирования
1. `JsonSerializer.Serialize(orders)` обходит навигации: `Order.Customer` -> `Customer.Orders` -> `Order` ... Заказы связаны с уже загруженным клиентом (fixup плюс lazy loading), сериализатор по умолчанию (без `ReferenceHandler`) бросает `JsonException: A possible object cycle was detected`. Попутно lazy loading дочитывает строки заказов.
2. Аргумент - интерполированная строка, и она вычисляется до вызова `LogDebug`, то есть и там, где Debug выключен (в проде тоже).
3. В лог при включённом Debug уходят персональные данные клиента: email, заметки, фото.
Чем кончится: `Summary` отвечает 500 для каждого клиента, у которого есть хотя бы один заказ. Даже без исключения это лишняя сериализация всех заказов клиента на каждый запрос.
Правка: убрать сериализацию, писать структурный лог с ключами (`logger.LogDebug("Summary for {CustomerId}: {Orders} orders", ...)`); если нужен дамп, то под `IsEnabled(LogLevel.Debug)` и из DTO без навигаций.

### B5. Services/CurrencyConverter.cs:15-17 (через Controllers/InvoiceController.cs:48) - глобальный lock вокруг синхронного HTTP-вызова
Singleton держит один `lock` на процесс, а внутри блокирующе ждёт `GetRateAsync(...).GetAwaiter().GetResult()`, то есть сетевой запрос к сервису курсов. Таймаута нет, у `HttpClient` по умолчанию 100 с.
Чем кончится: все запросы `total-in` по всему поду идут строго по одному, каждый ждущий держит поток пула. При медленном сервисе курсов потоки кончаются (thread-pool starvation) и встают все эндпоинты сервиса, не только конвертация.
Правка: `ConvertAsync` с `await` до конца цепочки. Lock не нужен: счётчик уже можно вести через `Interlocked.Increment`. Курс кэшировать с TTL, у клиента курсов задать таймаут.

### B6. Program.cs:7-18, все контроллеры - нет аутентификации и авторизации
В пайплайне нет `AddAuthentication`/`AddAuthorization`/`UseAuthorization`, на контроллерах нет `[Authorize]`. Анонимно доступны: список email всех клиентов с согласием на рассылку (`mailing-list`, перебор страниц), выгрузка всех заказов, счета любого заказа по перебору `orderId` (IDOR).
Чем кончится: утечка персональных данных 40 тыс. клиентов и коммерческих данных. Если авторизацию делает шлюз перед сервисом, это нужно подтвердить; иначе блокер.
Правка: схема аутентификации, политики на контроллерах, проверка владельца для счёта.

## Major

### M1. Controllers/CustomerReportsController.cs:19-22 - N+1 через lazy loading и сумма в памяти
Цикл по заказам клиента обращается к `order.Lines`, и каждое обращение - отдельный запрос (lazy-прокси). У клиента с сотней заказов это 1 + 100 запросов на один вызов сводки.
Чем кончится: латентность растёт линейно с числом заказов клиента, пул соединений БД под нагрузкой выедается.
Правка: `await db.OrderLines.Where(l => l.Order.CustomerId == customerId).SumAsync(l => l.Quantity * l.UnitPrice)`: один запрос и агрегат в БД; сами заказы для этого не загружать.

### M2. Controllers/CustomerReportsController.cs:30 (+ :8) - денежная сумма обрезается до int
`(int)linesTotal`: копейки отбрасываются, а при сумме больше `int.MaxValue` явное приведение `decimal` к `int` бросает `OverflowException`.
Чем кончится: неверная сумма в сводке почти для любого клиента; у крупного клиента - 500.
Правка: `LinesTotal` типа `decimal`.

### M3. Controllers/OrderExportController.cs:15 - имена таблицы и колонок в raw SQL не совпадают с маппингом модели
Модель не задаёт имён и snake_case-конвенцию не включает (Data/OrdersDbContext.cs), поэтому EF с Npgsql ждёт таблицу `"Orders"` и колонки `"Id"`, `"Status"`, ... в кавычках, с учётом регистра. SQL обращается к `orders`/`status` без кавычек, и Postgres ищет их в нижнем регистре.
Чем кончится: либо `relation "orders" does not exist` на экспорте, либо (если в БД на самом деле snake_case) не работают все остальные LINQ-запросы. В любом случае один из двух путей сломан. Сверить с реальной схемой. После правки B1 через LINQ проблема уходит сама.

### M4. Controllers/InvoiceController.cs:22 - sync-over-async
`rates.GetRateAsync("EUR").Result` в async-действии блокирует поток пула на время HTTP-запроса к сервису курсов.
Чем кончится: под нагрузкой thread-pool starvation, рост латентности всех эндпоинтов. Исключение придёт обёрнутым в `AggregateException`.
Правка: `var eurRate = await rates.GetRateAsync("EUR");`.

### M5. Controllers/InvoiceController.cs:24-28, 33 - запрос строк счёта выполняется дважды, итог может разойтись со строками
`rows` - это `IQueryable`, объявленный как `IEnumerable`. `rows.Sum(...)` (Enumerable.Sum) выполняет запрос первый раз, `Render` перечисляет его второй раз, и это второй запрос в БД.
Чем кончится: два round-trip вместо одного. Если строки заказа изменились между запросами, `Total` в PDF не совпадёт с суммой напечатанных строк, а бухгалтерский документ выйдет неконсистентным.
Правка: материализовать один раз (`await ... .ToListAsync()`), считать сумму по списку и его же отдавать в рендер.

### M6. Controllers/InvoiceController.cs:30-31 - каталог вложений может отсутствовать, и тогда падает весь счёт
`Directory.EnumerateFiles` бросает `DirectoryNotFoundException`, если у заказа нет каталога `Attachments:Root/{orderId}`. Вдобавок `.ToList().Count > 0` материализует весь листинг ради факта наличия, и синхронный I/O идёт на потоке запроса.
Чем кончится: 500 на счёт для каждого заказа без вложений (если каталоги не создаются заранее для всех заказов, это надо подтвердить).
Правка: `Directory.Exists(dir) && Directory.EnumerateFiles(dir).Any()`.

### M7. Services/Checksum.cs:7-19 - P/Invoke на каждый байт и непереносимая сигнатура
1. `Crc32` вызывается в цикле по одному байту: на PDF размером N байт это N переходов через натив-границу, каждый с маршалингом и пиннингом массива. На счёте в десятки КБ это десятки тысяч переходов вместо одного.
2. `uLong` у zlib - C `unsigned long`, 32 бита на Windows и 64 на Linux x64; `ulong` в C# верен только на части платформ. Имя `libz` резолвится в `libz.so`, а этот симлинк есть только с dev-пакетом zlib; в runtime-образе обычно лежит лишь `libz.so.1`, и возможен `DllNotFoundException`. Проверить на прод-образе.
Чем кончится: лишний CPU на каждом счёте; риск падения счёта целиком на другом образе или ОС.
Правка: управляемый `System.IO.Hashing.Crc32` (векторизован, без натива) либо один вызов `crc32(0, buf, len)` на весь буфер.

### M8. Controllers/CustomerReportsController.cs:41-49 - overfetch всей сущности клиента и неограниченный pageSize
1. Нужен только `Email`, а загружается вся сущность `Customer`, включая `Photo` (`byte[]`) и `Notes`: на странице из 500 клиентов это до 500 фото, переданных по сети и отслеживаемых контекстом.
2. `pageSize` приходит от клиента без верхней границы: `pageSize=100000` отдаёт весь список за раз. Отрицательный `page` даёт отрицательный `OFFSET`, Postgres отвечает ошибкой, клиент получает 500.
Чем кончится: тяжёлые ответы и память на каждом вызове; обход лимита страницы.
Правка: `.Select(c => c.Email)` до `ToListAsync`, `AsNoTracking`, clamp `pageSize` (например, до 500) и проверка `page >= 0`; для глубоких страниц лучше keyset по `Id`.

## Minor

### m1. Controllers/CustomerReportsController.cs:36-37 - CountAsync > 0 для проверки наличия
Чем кончится: БД считает все заказы клиента, хотя достаточно первого.
Правка: `await db.Orders.AnyAsync(o => o.CustomerId == customerId)`.

### m2. Controllers/CustomerReportsController.cs:16 - загрузка клиента целиком ради Name
Тянутся `Photo` и `Notes`, хотя нужны `Id` и `Name`. Если убрать N+1 (M1), сущность здесь не нужна вовсе: хватит проекции или `AnyAsync` для 404.

### m3. Controllers/CustomerReportsController.cs:14, 24, 26 - `since` без нормализации Kind
`since` из query string приходит с Kind `Unspecified` или `Local`, а `CreatedAt` читается из timestamptz как UTC. В памяти сравнение идёт по тикам без учёта Kind, и граница сдвигается на смещение пояса. После переноса фильтра в БД (B3) Npgsql 6+ бросит исключение на `Local`/`Unspecified` при записи параметра timestamptz.
Правка: принимать `DateTimeOffset` или явно приводить к UTC.

### m4. Controllers/InvoiceController.cs:35-36 - копия всего PDF ради среза
`new byte[]` + `Array.Copy` дублирует документ только для подсчёта контрольной суммы.
Правка: `pdf.AsSpan(PdfRenderer.HeaderSize)` (с `System.IO.Hashing.Crc32` принимает span напрямую).

### m5. Controllers/InvoiceController.cs:37 - Task.Run вокруг CPU-работы в хендлере
Масштабируемость это не улучшает: счёт просто переезжает на другой поток пула, а добавляется лишнее переключение. После правки M7 CRC считается за микросекунды, и его можно вызвать синхронно.

### m6. Program.cs:9 - глобальный UseLazyLoadingProxies
Прокси включают lazy loading для всего контекста, и любое обращение к навигации в цикле молча превращается в N+1 (M1) или в обход графа (B4). Для нового кода лучше явные `Include`/проекции без прокси; если прокси нужны, это стоит согласовать отдельно.

### m7. Services/RateService.cs:12-15 - нет отмены, null-разыменование, непроверенный currency в URL
`CancellationToken` не пробрасывается (здесь и во всех действиях контроллеров), поэтому оборванный клиентом запрос продолжает ходить в БД и к сервису курсов. `dto!.Rate` при ответе `null` даёт `NullReferenceException` вместо внятной ошибки. `currency` подставляется в путь без проверки (`../...` уводит на другой путь того же хоста). Кэша курса нет: каждый счёт и каждая конвертация идут в сеть.
Правка: `CancellationToken`, проверка формата ISO 4217 (3 буквы), кэш курса с TTL.

### m8. Controllers/OrderExportController.cs:22 - формат CSV зависит от культуры и не экранирует поля
`{o.Total}` форматируется текущей культурой потока: разделитель дроби меняется между окружениями, и бухгалтерия получит разные файлы с одного кода. `Number` с `;` или переводом строки ломает структуру файла.
Правка: `CultureInfo.InvariantCulture` (или явно оговорённый формат) и экранирование полей по RFC 4180.
