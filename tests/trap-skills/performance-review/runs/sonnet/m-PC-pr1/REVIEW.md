# REVIEW MR: импорт транзакций, отчёт, синхронизация партнёров и валют

Масштаб: ~500 тыс. строк/сутки, ~2000 правил, ~40 тыс. участников. Проверено по дисциплине performance-review плюс корректность.

## Blocker

1. **loyalty/import_transactions.py:15** — `re.search(rule.pattern, ...)` со строкой-паттерном, в цикле по правилам, внутри цикла по строкам. Объект, не зависящий от итерации, не вынесен из цикла. Кэш `re` держит 512 паттернов, а правил ~2000, поэтому при линейном переборе кэш постоянно вытесняется и каждый вызов перекомпилирует regex. Получается до 500k × 2000 = 10⁹ компиляций и поисков. Импорт за сутки не уложится в разумное время и займёт CPU. Нужно один раз скомпилировать правила в `load_rules` (`re.compile(p, re.I)`), а для поиска использовать индекс или единое объединённое выражение.

2. **loyalty/import_transactions.py:51-59** — `except Exception` вокруг `cur.execute` внутри одной транзакции Postgres. После первой ошибки транзакция в состоянии aborted, все следующие UPDATE падают с `InFailedSqlTransaction`, а цикл их глушит через `continue`. Затем `conn.commit()` на aborted-транзакции делает откат, и вставки `accruals` тоже пропадают. Итог: молча потерян весь файл, а `report.render()` возвращает «начислено: N». Нужно убрать проглатывание, при ошибке откатывать всё и падать (либо savepoint на запись, но лучше не нужно, см. п.4).

3. **loyalty/import_transactions.py:46-50** — вставка без идемпотентности: нет `ON CONFLICT (tx_id)` и нет проверки уже импортированных `tx_id`. Повторный запуск того же файла (ретрай после падения, дубль выгрузки от партнёра) задвоит начисления и баланс (`balance + points` повторно). Это деньги участников. Нужен уникальный индекс по `tx_id` (или `(partner_id, tx_id)`), `ON CONFLICT DO NOTHING`, а баланс обновлять только по реально вставленным строкам (`RETURNING`).

## Major

4. **loyalty/import_transactions.py:46-59** — `executemany` в psycopg2 делает отдельный round-trip на строку, плюс по одному `UPDATE members` на каждую транзакцию: ≈1 млн запросов за импорт. Участников всего ~40 тыс., а обновлений баланса 500k, и каждое берёт блокировку строки. Вставлять через `execute_values`/`COPY` батчами, баланс обновлять одним агрегированным запросом: сумма `points` по `member_id` с `UPDATE ... FROM (VALUES ...)`, ~40 тыс. строк максимум.

5. **loyalty/report.py:10,14** — `self.body += ...` на атрибуте: оптимизация CPython на месте не срабатывает, строка копируется каждый раз. Для 500k строк (десятки МБ) это квадратичное копирование. Копить в `list[str]` и делать `"".join` в `render()`. Заодно подумать, нужно ли отдавать отчёт по 500k строк целиком одной строкой, возможно, достаточно сводки и пропусков.

6. **loyalty/import_transactions.py:13-17 и rules.py:11-17** — `SELECT ... FROM partner_rules WHERE active` без `ORDER BY`, а `match_rule` берёт первое совпадение. При пересекающихся паттернах правило выбирается недетерминированно, поэтому один и тот же файл может дать разные баллы или партнёра. Нужен явный приоритет и сортировка.

7. **loyalty/import_transactions.py:15,26-43** — `re.error` (невалидный паттерн из БД), `TypeError` (`row["merchant"]` равен `None` при короткой строке CSV, у `DictReader` недостающие поля `None`), а также `Decimal * float`, если `points_per_rub` в БД `numeric` (psycopg2 вернёт `Decimal`), не ловятся: ловятся только `KeyError`/`ValueError`. Одна плохая строка или правило роняет весь импорт. Валидировать правила при загрузке, строку обрабатывать с полным перехватом ожидаемых ошибок.

8. **loyalty/import_transactions.py:28,33** — деньги и баллы через `float`, `round()` банковским округлением. Накопление ошибок и расхождение с партнёрским расчётом. Использовать `Decimal` и явное правило округления. Отрицательные суммы (возвраты) тоже дают отрицательные баллы без проверки.

9. **loyalty/partners_sync.py:24** — `asyncio.gather` без ограничения параллелизма по всем активным партнёрам: всплеск соединений и риск 429/бана со стороны API. Первое исключение (`raise_for_status`, таймаут) прерывает `gather` и теряет всю синхронизацию, остальные запросы продолжают висеть. Нужны `Semaphore`, `return_exceptions=True` и ретраи.

10. **loyalty/partners_sync.py:18-32** — соединение пула держится на всё время сетевых запросов, а синхронный psycopg2 вызывается внутри `async`-функции и блокирует event loop. Пул — всего 10 соединений (db.py:6), `ThreadedConnectionPool.getconn` при исчерпании не ждёт, а бросает `PoolError`. Читать ids, отпустить соединение, ходить в сеть, затем взять соединение для записи; БД-вызовы выносить в `asyncio.to_thread`.

## Minor

11. **loyalty/partners_sync.py:30** — используется `p["id"]` из ответа API, а не запрошенный `i`. Если API вернёт другой id, обновится чужой партнёр. Также нет проверки наличия ключей `name`/`cashback_cap` (`KeyError` после чтения всех ответов) и обновление построчно вместо батча.

12. **loyalty/reference.py:5,9** — `$` в regex допускает завершающий `\n` (`"USD\n"` пройдёт), нужен `fullmatch`. Невалидные коды отбрасываются молча, без лога и счётчика. Дубли `code` в одном `rows` приведут к `ON CONFLICT DO UPDATE command cannot affect row a second time`. Функция сама делает `commit()` на переданном снаружи соединении, что ломает транзакцию вызывающего.

13. **loyalty/import_transactions.py:21-61** — соединение из пула удерживается на всё чтение файла; весь `accruals` (500k кортежей) и отчёт держатся в памяти. `UPDATE members` не проверяет `rowcount`: начисление несуществующему `member_id` молча теряется (если нет FK). Читать файл до взятия соединения и обрабатывать батчами.

14. **loyalty/db.py:6** — пул создаётся при импорте модуля и требует `LOYALTY_DSN` уже на этапе импорта (то же для `PARTNERS_API` в partners_sync.py:8): падение при импорте, неудобство для тестов. Лучше ленивая инициализация.
