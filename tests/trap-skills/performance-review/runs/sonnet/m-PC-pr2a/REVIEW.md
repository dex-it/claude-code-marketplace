# Ревью MR: импорт транзакций, отчёт, синхронизация партнёров и валют

Масштаб: ~40 тыс. участников, ~500 тыс. строк в сутки, ~2000 активных правил.
Дисциплина: SKILL.md (performance-review): запись и внешний вызов в цикле вместо пакета, лишние копии/накопления.

## Blocker

### 1. `loyalty/import_transactions.py:51-59` — `except Exception` вокруг `execute` в общей транзакции, затем `commit`
Первая же ошибка UPDATE переводит транзакцию в состояние aborted. Все следующие UPDATE падают с `InFailedSqlTransaction`, их ловит тот же `except`, и в лог уходит по строке на каждую. Итоговый `conn.commit()` на aborted-транзакции делает откат. В итоге **не сохраняются ни INSERT в `accruals`, ни балансы**, а `report.render()` возвращает «начислено: N». Баллы потеряны, отчёт врёт, ошибка замаскирована логами. Если ошибка не транзакционная, часть начислений в `accruals` есть, а баланс не обновлён — расхождение. Нужно убрать `try/except`, чтобы ошибка прерывала импорт и делала откат, либо использовать savepoint осознанно. Отчёт нужно формировать только после успешного commit.

### 2. `loyalty/import_transactions.py:13-17, 29` — regex по 2000 правилам на каждую строку, без компиляции
До 500 тыс. × 2000 ≈ 10⁹ вызовов `re.search` в худшем случае (для строк без совпадения всегда). Кэш `re` хранит 512 шаблонов, при 2000 правилах и циклическом переборе он постоянно вытесняется, и шаблоны перекомпилируются заново. Импорт идёт часами и держит соединение из пула. Нужно один раз скомпилировать правила (`re.compile(..., re.I)` в `load_rules`) и кэшировать результат по `merchant` (`dict`/`lru_cache`: уникальных мерчантов сильно меньше, чем строк). Лучше объединить правила в индекс по префиксу или токену.

### 3. `loyalty/import_transactions.py:45-59` — запись в цикле: `executemany` и по UPDATE на каждое начисление
В psycopg2 `executemany` отправляет запросы по одному, то есть ~500 тыс. round-trip для INSERT и ещё ~500 тыс. для UPDATE баланса. Это ~1 млн запросов за сеанс, десятки минут, транзакция висит открытой и держит блокировки строк `members`. Нужно: INSERT через `psycopg2.extras.execute_values` (с `page_size` в тысячи) или `COPY`. Баланс считать агрегатом по `member_id` в Python (≤40 тыс. участников) и обновить одним `UPDATE ... FROM (VALUES ...)`. Тогда на одну строку members придётся один UPDATE вместо десятков.

## Major

### 4. `loyalty/import_transactions.py:46-50` — нет идемпотентности по `tx_id`
`INSERT` без `ON CONFLICT`. При повторном запуске файла (сбой, ретрай, дубль в выгрузке) возможны два исхода: либо падает вся пачка по unique, либо, если уникальности нет, баллы начисляются дважды. Нужен `ON CONFLICT (tx_id) DO NOTHING` и баланс только по реально вставленным строкам (`RETURNING`). Дубли `tx_id` внутри одного файла тоже не отсекаются.

### 5. `loyalty/rules.py:13-16` — нет `ORDER BY`, при этом в `match_rule` побеждает первое совпадение
Порядок строк без `ORDER BY` не определён. При пересекающихся шаблонах (на 2000 правилах это вероятно) один и тот же мерчант получает разный `partner_id` и баллы в зависимости от плана запроса. Начисления становятся невоспроизводимыми. Нужны явный приоритет и `ORDER BY`.

### 6. `loyalty/import_transactions.py:15` — невалидный или «тяжёлый» regex из БД не обрабатывается
`re.error` не входит в `(KeyError, ValueError)` и обрывает весь импорт одним битым правилом (`re.error` наследуется от `Exception`, не от `ValueError`). Катастрофический backtracking (ReDoS) в одном правиле тоже подвесит весь импорт. Нужно валидировать и компилировать правила при загрузке, битые пропускать с логом/алертом.

### 7. `loyalty/import_transactions.py:28, 33` — деньги и коэффициенты во `float`, `round()` банковский
`amount` — `float`, `points_per_rub` — `float`; `round(x.5)` округляет к чётному. Начисления дают расхождения на копейки/баллы и зависят от представления числа. Нужны `Decimal`/`NUMERIC`, явная политика округления (`ROUND_HALF_UP` или как в договоре с партнёрами). Отрицательные суммы (возвраты) тоже не обработаны: можно начислить отрицательные баллы и увести баланс в минус без проверки.

### 8. `loyalty/partners_sync.py:23-24` — `gather` по всем активным партнёрам без ограничения и без обработки ошибок
Первая ошибка (`raise_for_status`, таймаут) пробрасывается из `gather`. Результаты остальных запросов теряются, синхронизация не применяется вовсе. Остальные задачи продолжают работать «в фоне». Запросов по одному на партнёра (N внешних вызовов). Нужны `asyncio.Semaphore`/`httpx.Limits`, `return_exceptions=True` или `TaskGroup` с понятной политикой, ретраи с backoff. Если у API есть пакетный эндпоинт, использовать его.

### 9. `loyalty/partners_sync.py:26-31` — UPDATE в цикле
По одному round-trip на партнёра, по тому же принципу, что в п.3. Использовать `execute_values` + `UPDATE ... FROM (VALUES ...)`. Условие `WHERE` без `IS DISTINCT FROM` приводит к лишней записи и росту мёртвых версий строк при неизменных данных.

### 10. `loyalty/partners_sync.py:18-32` — соединение из пула занято на всё время HTTP-вызовов; блокирующий psycopg2 внутри `async`
Соединение берётся до сетевой фазы и держится всё время `gather` (до таймаута 10 с и дольше). При этом `cur.execute` — синхронный вызов в корутине, он блокирует event loop. Пул `max=10` небольшой, а `getconn()` при исчерпании не ждёт, а сразу бросает `PoolError`. Нужно читать id, освобождать соединение, ходить в сеть, затем брать соединение для записи (или вынести БД в `run_in_executor`).

### 11. `loyalty/report.py:8-14` и `import_transactions.py:41` — отчёт копит строку на каждое начисление
`self.body += ...` на ~500 тыс. строк даёт многомегабайтную строку. Конкатенация через атрибут не оптимизируется CPython, получается квадратичное копирование. Плюс возвращается один гигантский `str` и держится в памяти вместе с `accruals`. Отчёту нужны счётчики, а построчно — только пропущенные (и с лимитом), либо список + `"".join`, либо запись в файл потоком.

## Minor

### 12. `loyalty/import_transactions.py:42-43` — перехват ограничен `(KeyError, ValueError)`
Короткая строка CSV даёт `None` в значении, а `re.search(..., None)` бросает `TypeError`, и весь импорт падает. `row.get("tx_id")` для пропущенных тоже может дать `None`.

### 13. `loyalty/import_transactions.py:22-60` — соединение занято всё время чтения файла и матчинга
Соединение берётся до чтения CSV. Разбор файла (долгая CPU-фаза, п.2) идёт под открытым соединением из пула на 10 штук. Лучше разбирать файл до `connection()` или хотя бы брать соединение после парсинга.

### 14. `loyalty/import_transactions.py:51-56` — порядок UPDATE `members` совпадает с порядком файла
Два параллельных импорта с разным порядком участников могут получить дедлок. После агрегации по `member_id` (п.3) нужно сортировать по `member_id`.

### 15. `loyalty/reference.py:9-16` — молчаливый отброс невалидных валют и дубли кодов
Невалидные строки отбрасываются без лога и счётчика. Дубль `code` внутри одного батча даёт `ON CONFLICT DO UPDATE command cannot affect row a second time` и падение. Регэксп с `$` пропускает код с завершающим `\n` (нужен `fullmatch`). Дополнительно `commit()` внутри функции, принимающей чужое соединение, лишает вызывающего управления транзакцией.

### 16. `loyalty/db.py:6`, `loyalty/partners_sync.py:8` — побочные эффекты на импорте модуля
Пул создаётся и `os.environ[...]` читается при импорте. Любой импорт (тесты, линтер) требует БД и переменные окружения, а при недоступности БД падает с трудночитаемой ошибкой. Нужна ленивая инициализация.

### 17. `loyalty/partners_sync.py:30` — `p["id"]` берётся из ответа API
Запрос шёл по `partner_id`, а UPDATE по id из тела ответа. Ответ с другим/отсутствующим `id` обновит не ту запись или даст `KeyError`. Использовать id запроса, а схему ответа проверять.
