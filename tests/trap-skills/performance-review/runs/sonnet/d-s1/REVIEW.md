# Ревью MR: модуль возвратов (Shop.Api)

Контекст нагрузки: 2 млн заказов, ~15 тыс. возвратов/мес, ~400 RPS, список возвратов открывают постоянно.
Дисциплина производительности из SKILL.md применена; пункты 4, m1, m2 отсюда напрямую.

## Blocker

### B1. Нет аутентификации и авторизации, approve/reject доступны любому
- `Program.cs:28-33`, `Returns/ReturnsController.cs:46-52`
- Нет `AddAuthentication`/`UseAuthentication`/`UseAuthorization`, нет `[Authorize]`. Единственная "защита" - тенант по заголовку Host (`TenantFilter.cs:10`), его выбирает вызывающий.
- Кончится тем, что любой, кто знает хост тенанта, одобряет возвраты (деньги уходят через шлюз), отклоняет чужие заявки и читает список заявок с именами клиентов. Список "для поддержки" открыт всему интернету.
- Нужно: аутентификация, роль поддержки на List/Approve/Reject, проверка владельца заказа на Create.

### B2. Двойной возврат денег: нет идемпотентности, нет защиты от гонки, шлюз вызывается до фиксации статуса
- `Returns/ReturnService.cs:45-54` (также `:62-66`)
- Статус читается, затем внешний вызов `RefundAsync` (без ключа идемпотентности, `RefundGateway.cs:13`), затем `SaveChanges`. У `ReturnRequest` нет concurrency token / `xmin`, нет блокировки строки.
- Сценарии: (а) два параллельных approve (двойной клик, ретрай прокси) оба видят `Requested` и оба вызывают шлюз - клиент получает деньги дважды; (б) шлюз вернул успех, `SaveChanges` упал (или упал процесс) - статус остаётся `Requested`, повторный approve возвращает деньги второй раз, а `RefundExternalId` потерян; (в) approve и reject параллельно: деньги ушли, статус `Rejected` и клиенту ушло письмо об отказе.
- Промежуточного статуса нет (`Approved` в enum объявлен и не используется): "ушёл в шлюз" и "завершён" неразличимы.
- Нужно: перевести в `Approved` с concurrency token до вызова шлюза, передавать шлюзу idempotency key (Id заявки), затем `Refunded`; повторный вход подхватывает `Approved`.

### B3. Валидация количества не сравнивает с купленным: можно вернуть больше, чем было в заказе
- `Returns/ReturnValidator.cs:29`
- Условие `line.Quantity <= 0 || orderLine.Quantity < 0` проверяет количество в заказе на отрицательность (всегда ложно), а не `line.Quantity > orderLine.Quantity`. Дубли `OrderLineId` в `cmd.Lines` тоже не отсекаются (цикл `:24`).
- Кончится тем, что заявка на 1000 шт. вместо 1 проходит валидацию, `ApproveAsync` (`ReturnService.cs:49-50`) считает сумму как `UnitPrice * Quantity` из заявки и платит её через шлюз. Прямая финансовая потеря, усиливается B1.
- Нужно: `line.Quantity > orderLine.Quantity` -> ошибка, уникальность `OrderLineId`, и повторная проверка суммы при approve.

### B4. N+1 на списке возвратов: ленивая загрузка в цикле маппинга, ~4 запроса на строку
- `Returns/ReturnsController.cs:27-33`, `Returns/ReturnMapper.cs:10-19`, `Program.cs:12` (`UseLazyLoadingProxies`)
- Список грузит `ReturnRequest` без `Include` и без проекции, затем `mapper.ToListItem` для каждой строки трогает `r.Lines`, `r.Order`, `r.Order.Lines` (целиком, ради `First`) и `r.Order.Customer`. Каждое обращение - отдельный синхронный запрос (lazy loading синхронный даже внутри async-метода, блокирует поток пула). Все сущности ещё и трекаются.
- Страница из 50 строк (дефолт) = ~1 + 200 запросов. Эндпоинт "открывают постоянно" при 400 RPS: это тысячи запросов в секунду к БД и занятые потоки; под нагрузкой - пул соединений и thread pool исчерпаны, деградируют все эндпоинты.
- Нужно: проекция `Select` прямо в `ReturnListItem` (имя клиента, `Sum(Quantity)`, сумма через join на `OrderLines`) + `AsNoTracking`; не использовать ленивые прокси или убрать `UseLazyLoadingProxies` из регистрации. Та же ленивая цепочка - в `ApproveAsync` (`ReturnService.cs:49-50`): 3 синхронных запроса внутри async.

## Major

### M1. Тенант определяется синхронным блокированием и запросом в БД на каждый запрос
- `Infrastructure/TenantFilter.cs:11`, `Infrastructure/TenantService.cs:20-23`
- `.Result` внутри `OnActionExecuting` блокирует поток пула на каждый из 400 RPS; плюс отдельный запрос к `Tenants` по Host без кэша на каждый вызов. Всплеск latency БД превращается в starvation пула потоков.
- Нужно: `IAsyncActionFilter` или middleware, кэш Host -> TenantId (`IMemoryCache`, с TTL). Индекс на `Tenants.Host` в этом MR не создан, таблицы `Tenants` в миграции нет вовсе (создана ли ранее - проверить).

### M2. Окно возврата считается по `DateTime.Now` (локальное время сервера) против UTC
- `Returns/ReturnPolicy.cs:9`
- `Order.CreatedAt` - UTC (`timestamptz`, а `clock.UtcNow` пишется в `ReturnService.cs:33`). Сравнение с локальным временем сдвигает границу срока на смещение часового пояса хоста (до +-14 ч): возврат на границе 14 дней одобряется или отклоняется ошибочно, результат зависит от настроек контейнера. `IClock` есть, но не используется (заодно тест на границу окна невозможен).
- Нужно: `IClock.UtcNow`.

### M3. Уведомление после коммита: необработанные исключения ломают уже выполненную операцию
- `Notifications/ReturnNotifier.cs:23`, вызовы `Returns/ReturnService.cs:39, 56, 68`
- Ловится только `HttpRequestException`. Таймаут (`TaskCanceledException`/`TimeoutException`) и сериализация пролетают наружу. К этому моменту деньги уже ушли и статус сохранён, а клиент получает 500: ретрай даёт `NotFound` (статус уже не `Requested`), заявка у оператора выглядит упавшей. Дефолтный таймаут `HttpClient` - 100 с, он же добавляется к latency approve/create (уведомление в горячем пути запроса). Потеря письма при падении процесса не компенсируется (нет outbox/очереди).
- Нужно: ловить все не-отменные исключения, короткий таймаут/резилиенс-политика на клиенте, вынести отправку из запроса (очередь/outbox).

### M4. Ночная сверка: `List.Contains` в цикле и неограниченная загрузка ответа шлюза
- `Returns/ReturnsReconciliationJob.cs:32, 46`, `Returns/RefundGateway.cs:19-23`
- `gatewayIds` - `List<string>`, `Contains` в цикле по локальным возвратам: O(N*M). За 90 дней порядка 45 тыс. возвратов в каждой стороне - около 1e9 сравнений строк за прогон, минуты CPU в фоне процесса, обслуживающего API. Весь ответ шлюза читается одним `GetFromJsonAsync` без пагинации.
- Нужно: `HashSet<string>` (или join), постраничное чтение шлюза.

### M5. Сверка не ловит основной сбой: деньги ушли, локально статус не обновился
- `Returns/ReturnsReconciliationJob.cs:37-41, 46`
- Проверяется только "локально Refunded - у шлюза нет". Обратное направление (возврат есть у шлюза, локально заявка `Requested`/нет `RefundExternalId`, это ровно сценарий B2б) не проверяется, а `gatewayRefunds` собраны и не используются дальше. Итог: расхождения, ради которых сверка и написана, остаются незамеченными. Результат - только `LogWarning`, без метрики/алерта; сумму не сверяет.
- Нужно: двусторонняя сверка по `RefundExternalId`/orderId + суммам, метрика расхождений.

### M6. Миграция без атрибутов и снапшота: EF её не увидит
- `Migrations/20260910120000_AddReturns.cs:5`
- Класс `partial`, без `[DbContext(typeof(ShopDbContext))]` и `[Migration("20260910120000_AddReturns")]`; Designer-файла и `ShopDbContextModelSnapshot` в MR нет. Без атрибута `Migrate()`/`database update` миграцию не находят: таблицы возвратов не создадутся, в проде всё упадёт на первом запросе. Если Designer лежит вне MR - подтвердить, иначе добавить.

## Minor

### m1. Наличие через `CountAsync(...) > 0` вместо `AnyAsync`, и гонка при создании
- `Returns/ReturnValidator.cs:21`
- Считает все совпадающие строки вместо остановки на первой (по правилу из SKILL.md - `Any`). Кроме того, проверка "нет активной заявки" и вставка не атомарны, уникального индекса на `(OrderId)` для статусов не `Rejected` нет - два параллельных POST создают две заявки на один заказ. Нужно: `AnyAsync` + частичный уникальный индекс `WHERE "Status" <> 2`.

### m2. `new HttpClient` на каждый вызов шлюза
- `Returns/RefundGateway.cs:12, 21`
- Новый клиент (и соединение) на каждый вызов: накопление сокетов в TIME_WAIT, нет повторного использования соединений, нет единого таймаута и политики ретраев. На 15 тыс./мес риск малый, но это платёжный путь. Нужно: `AddHttpClient<RefundGateway>` с таймаутом, как сделано для `ReturnNotifier` в `Program.cs:24`.

### m3. Индексы и целостность в миграции
- `Migrations/20260910120000_AddReturns.cs:44-46`
- Список сортируется `ORDER BY "CreatedAt" DESC` по тенанту, а индекс только `(TenantId, Status)`: сортировка в памяти по всем заявкам тенанта (при росте - медленнее с каждым месяцем). Нужен `(TenantId, CreatedAt DESC)` (+ вариант со `Status`). У `ReturnLines.OrderLineId` нет FK на `OrderLines`, `ReturnRequests.TenantId` не связан с `Orders.TenantId`.

### m4. `CreatedAtAction(nameof(List), new { id })` ведёт не туда
- `Returns/ReturnsController.cs:43`
- У `List` нет параметра `id`: `Location` превратится в `/api/returns?id=N`, который игнорируется. Нужен GET по id либо убрать Location.

### m5. Сверка стартует сразу при запуске и на каждой реплике
- `Returns/ReturnsReconciliationJob.cs:13-25`
- `do/while` выполняет первый прогон немедленно: каждый деплой/рестарт дёргает шлюз и БД, N реплик делают то же N раз. Нужно: расписание на ночь, распределённая блокировка или отдельный воркер.

### m6. Нет ограничения длины `Reason` и верхней границы количества
- `Returns/ReturnValidator.cs:14-16`, `Migrations/...:18`
- `Reason` - неограниченный `text` из тела запроса; `Quantity` без верхней границы (см. B3).

### m7. `First()` в маппере бросает на "осиротевшей" строке
- `Returns/ReturnMapper.cs:12`
- Нет FK `ReturnLines.OrderLineId -> OrderLines` (m3): одна битая строка даёт исключение и 500 на всей странице списка. Решается проекцией из B4 и FK.
