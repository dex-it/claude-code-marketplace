# Ревью MR: модуль возвратов (Shop.Api)

Итого: blocker — 4, major — 5, minor — 7 (всего 16).

## Blocker

### B1. Нет аутентификации и авторизации, тенант определяется только по заголовку Host
`Returns/ReturnsController.cs:8-53`, `Program.cs:28-33`, `Infrastructure/TenantFilter.cs:10`
Ни `[Authorize]`, ни `UseAuthentication/UseAuthorization`. Любой, кто достучался до API, может вызвать `POST /api/returns/{id}/approve` и инициировать выплату денег через шлюз, а также прочитать список возвратов с именами клиентов. Тенант берётся из клиентского заголовка Host, так что подменой Host читаются и меняются данные чужого тенанта. `Create` не проверяет, что заказ принадлежит вызывающему клиенту: возврат можно оформить по любому номеру заказа.
Итог: несанкционированные выплаты, утечка ПДн, межтенантный доступ.

### B2. Двойной возврат денег при одобрении: гонка и нет идемпотентности
`Returns/ReturnService.cs:45-54` (то же для Reject, :62-67)
Читаем `Status == Requested`, вызываем шлюз, и только потом сохраняем статус. Нет concurrency-токена, транзакции и idempotency-key для шлюза. Два параллельных approve (двойной клик, ретрай, два оператора) оба проходят проверку и оба вызывают `RefundAsync`, клиент получает деньги дважды. Если `SaveChanges` падает после успешного вызова шлюза, статус остаётся `Requested`, повторное одобрение выплатит ещё раз. Approve и Reject тоже могут гоняться: возврат окажется отклонён, а деньги ушли.
Что сделать: сначала атомарно перевести в `Approved` (`xmin`/RowVersion или `ExecuteUpdate ... WHERE Status = Requested`), передавать в шлюз ключ идемпотентности (Id возврата), потом завершать в `Refunded`.

### B3. Валидатор не проверяет количество к возврату относительно купленного
`Returns/ReturnValidator.cs:29`
Условие `orderLine.Quantity < 0` проверяет количество в заказе, а должно быть `line.Quantity > orderLine.Quantity`. Можно вернуть 100 штук из заказа на 1. Сумма в `ReturnService.ApproveAsync:49-50` считается как `UnitPrice * line.Quantity` и уходит в шлюз.
Итог: завышенные выплаты. Кроме того, одну и ту же `OrderLineId` можно передать в `Lines` несколько раз, и сумма умножается (проверки на дубли нет).

### B4. Миграция не будет обнаружена EF
`Migrations/20260910120000_AddReturns.cs:5`
У класса нет `[DbContext(typeof(ShopDbContext))]` и `[Migration("20260910120000_AddReturns")]`, а Designer/ModelSnapshot в MR отсутствуют. `Migrate()` и `dotnet ef database update` её не увидят, таблиц `ReturnRequests` и `ReturnLines` не будет. Все эндпоинты упадут с 500 после деплоя. Снапшот модели тоже нужно обновить, иначе следующая миграция сгенерирует CreateTable повторно.

## Major

### M1. N+1 на списке возвратов (lazy loading proxies)
`Returns/ReturnsController.cs:27-33`, `Returns/ReturnMapper.cs:10-22`
Загружается страница `ReturnRequest` без Include. Маппер на каждую строку лениво подгружает `Lines`, `Order`, `Order.Lines` и `Order.Customer`: порядка 4 запросов на строку, 200 запросов на страницу из 50 строк. `Order.Lines` грузится целиком ради суммы, плюс `First` внутри цикла. Список открывают постоянно при 400 RPS, поэтому это сотни тысяч запросов в секунду к БД и исчерпание пула соединений.
Что сделать: `AsNoTracking` и проекция в `ReturnListItem` одним запросом (`Sum` через join на OrderLines, `Customer.Name`).

### M2. Sync-over-async в фильтре тенанта и запрос в БД на каждый запрос
`Infrastructure/TenantFilter.cs:11`
`.Result` на асинхронном вызове блокирует поток пула на каждом запросе. Под 400 RPS это thread-pool starvation, а при медленной БД каскадные таймауты. Сам резолв хоста тоже идёт в БД без кэша. Нужен `IAsyncActionFilter` (или middleware) и `IMemoryCache` для host→tenant.

### M3. Исключения нотификатора после коммита и ёмкость побочных эффектов
`Notifications/ReturnNotifier.cs:23`, вызовы в `ReturnService.cs:39,56,68`
Ловится только `HttpRequestException`. Таймаут HttpClient даёт `TaskCanceledException`, он не ловится и вылетает из `ApproveAsync` после того, как деньги выплачены и статус сохранён. Оператор видит 500, повторяет, и получает 404/false, потому что статус уже не `Requested`. Для Create клиент видит 500 при сохранённой заявке. Уведомление нужно отправлять по принципу best effort (ловить всё, кроме отмены по ct) или через outbox.

### M4. `new HttpClient` на каждый вызов шлюза, нет таймаутов и ретраев
`Returns/RefundGateway.cs:12,21`
Новый HttpClient на запрос (`using`) приводит к накоплению сокетов в TIME_WAIT и не учитывает DNS. Таймаут по умолчанию 100 с, и все это время занят запрос пользователя. Для денежной операции нет политики ретраев с идемпотентностью. Нужен `AddHttpClient<RefundGateway>` с явным таймаутом.

### M5. Дубли заявок по заказу: проверка без блокировки и без уникального индекса
`Returns/ReturnValidator.cs:21`, `Migrations/...AddReturns.cs:44-45`
Проверка «уже есть заявка» (check-then-insert) не защищена ничем. Два параллельных Create создадут две заявки по одному заказу, и обе потом можно одобрить. Нужен уникальный частичный индекс по `OrderId` `WHERE Status <> Rejected` (учитывая, что Rejected = 1 в enum).

## Minor

### m1. `DateTime.Now` в политике окна возврата
`Returns/ReturnPolicy.cs:9`
`CreatedAt` хранится в UTC (`timestamp with time zone`, `IClock.UtcNow`), а сравнение с локальным временем сервера. Окно сдвигается на смещение часового пояса, тест на границе будет флакать. Использовать `IClock.UtcNow`.

### m2. Индекс не покрывает сортировку списка
`Migrations/...AddReturns.cs:44`, `Returns/ReturnsController.cs:27-31`
Индекс `(TenantId, Status)`, а запрос сортирует по `CreatedAt DESC`, то есть будет сортировка всех строк тенанта. Лучше `(TenantId, Status, CreatedAt DESC)`; для запроса без статуса нужен отдельный индекс `(TenantId, CreatedAt DESC)`.

### m3. Таблица Tenants вне модели и миграций
`Infrastructure/TenantService.cs:21`
Сырой SQL к `"Tenants"`, которой нет ни в `DbContext`, ни в миграции MR. Если её создаёт другой сервис, нужно это зафиксировать; иначе все запросы вернут 404/500. Также нет индекса по `Host` в этом MR.

### m4. Неверный Location в ответе Create
`Returns/ReturnsController.cs:43`
`CreatedAtAction(nameof(List), new { id })`: у `List` нет параметра `id`, в Location окажется список без указания на созданный ресурс.

### m5. Сверка: O(n·m) поиск по списку
`Returns/ReturnsReconciliationJob.cs:32,46`
`gatewayIds` это `List<string>`, `Contains` линейный: порядка 45 тыс. возвратов за 90 дней, то есть до ~10⁹ сравнений строк. Заменить на `HashSet<string>`. Весь ответ шлюза читается одним списком без пагинации.

### m6. Сверка односторонняя и не «ночная»
`Returns/ReturnsReconciliationJob.cs:13,37-53`
Таймер 24 ч стартует с момента запуска приложения, а не ночью, и срабатывает на каждом инстансе (дублирование логов/нагрузки на шлюз, без распределённого lock). Проверяется только «локально есть, на шлюзе нет». Обратное (на шлюзе есть, локально нет или расхождение суммы) не проверяется, а результат только в лог без метрики/алерта.

### m7. Статус `Approved` не используется
`Returns/ReturnService.cs:53`, `Data/ShopDbContext.cs:32`
Заявка прыгает `Requested → Refunded`. Промежуточного состояния нет, а оно необходимо для починки B2 и для восстановления после падения между шлюзом и БД.
