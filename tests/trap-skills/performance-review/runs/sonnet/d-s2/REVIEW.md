# Ревью MR: модуль возвратов (Shop.Api)

Нагрузка для оценки: 2 млн заказов, ~15 тыс. возвратов/мес, ~400 RPS, список возвратов открывают постоянно. Сборка и запуск не выполнялись, выводы по чтению кода.

## Blocker

### B1. Список возвратов: N+1 через lazy-loading proxies, до ~4 запросов на строку
- Файлы: Returns/ReturnsController.cs:27-33, Returns/ReturnMapper.cs:10-12,19, Program.cs:12
- Что не так: `UseLazyLoadingProxies()` включён глобально. Список грузит только `ReturnRequest` (без Include и без проекции, с трекингом), затем `ToListItem` для каждой строки лениво дёргает `r.Lines`, `r.Order`, `r.Order.Lines` и `r.Order.Customer`. Каждое обращение - отдельный синхронный запрос в БД. `Order.Lines` грузится целиком ради поиска цен.
- Чем кончится: при pageSize=50 это ~200 запросов на открытие страницы, при 100 - ~400. Синхронный I/O внутри async-метода занимает потоки пула. Самый частый экран падает под нагрузкой: деградация БД, thread pool starvation, таймауты.
- Как чинить: убрать lazy-loading proxies (или не полагаться на них) и строить `ReturnListItem` одной проекцией `Select` на стороне БД (имя клиента, сумма и число позиций считаются подзапросами/JOIN). Добавить `AsNoTracking`.

### B2. Одобрение возврата: двойная выплата (гонка и нет идемпотентности)
- Файл: Returns/ReturnService.cs:45-56
- Что не так: проверка `Status == Requested` не атомарна с обновлением. Нет ни токена конкурентности/rowversion, ни условного `UPDATE ... WHERE Status = Requested`. Вызов шлюза (стр. 52) идёт до сохранения статуса и без ключа идемпотентности (RefundGateway.cs:13). Статус и `RefundExternalId` сохраняются после, отдельным `SaveChanges`.
- Чем кончится: двойной клик или два оператора одновременно - два вызова шлюза, деньги уходят дважды. Если шлюз принял, а `SaveChanges` упал (БД, таймаут, рестарт), заявка остаётся `Requested`, повторное одобрение платит ещё раз. Ночная сверка этого не ловит (см. m4).
- Как чинить: сначала атомарно перевести статус `Requested -> Approved` (условный update или concurrency token), затем вызвать шлюз с ключом идемпотентности (Id заявки), затем зафиксировать `Refunded`. Зависшие `Approved` добирать сверкой.

### B3. Валидатор не проверяет количество к возврату (деньги)
- Файл: Returns/ReturnValidator.cs:24-31 (ключевая строка 29), сумма считается в ReturnService.cs:49-50
- Что не так: условие `orderLine.Quantity < 0` сравнивает количество в заказе с нулём, а не `line.Quantity > orderLine.Quantity`. Количество к возврату ничем не ограничено сверху. Одна и та же `OrderLineId` может повторяться в `Lines`, и каждый повтор проходит проверку.
- Чем кончится: можно оформить возврат 1000 шт. по позиции, где куплена 1 шт., или продублировать позицию. `Approve` посчитает `UnitPrice * Quantity` и выплатит эту сумму через шлюз - прямая потеря денег.
- Как чинить: проверять `line.Quantity <= orderLine.Quantity`, учитывать уже возвращённое по заказу, запретить дубли `OrderLineId`.

### B4. Нет аутентификации и авторизации, тенант определяется только заголовком Host
- Файлы: Program.cs:28-33 (нет `UseAuthentication/UseAuthorization`), Returns/ReturnsController.cs:8-52 (нет `[Authorize]`), Infrastructure/TenantFilter.cs:10
- Что не так: список заявок «для поддержки», одобрение с выплатой и отклонение открыты любому, кто достучался до сервиса. Единственный разделитель тенантов - `Request.Host`, который клиент задаёт сам.
- Чем кончится: любой может подставить Host чужого тенанта, читать его заявки (имена клиентов) и одобрять возвраты с выплатой денег. Утечка данных между тенантами плюс денежные операции без проверки роли.
- Как чинить: аутентификация, политика/роль «поддержка» на approve/reject/list, тенант берётся из проверенного источника (клейм токена или доверенный прокси с whitelisting Host).

## Major

### M1. Синхронная блокировка `.Result` в фильтре на каждый запрос + неким­шируемый запрос тенанта
- Файлы: Infrastructure/TenantFilter.cs:11, Infrastructure/TenantService.cs:20-23
- Что не так: `IActionFilter` вызывает `ResolveAsync(...).Result` - sync-over-async на каждом из ~400 RPS. Плюс каждый запрос делает SQL к `Tenants` без кэша.
- Чем кончится: блокировка потоков пула, при любом замедлении БД - starvation и каскад таймаутов всего API. Лишний запрос на каждый вызов.
- Как чинить: `IAsyncActionFilter` (или middleware) с `await`, результат резолва по Host кэшировать (`IMemoryCache` с TTL).

### M2. Approve грузит граф через lazy loading синхронно
- Файл: Returns/ReturnService.cs:45-50
- Что не так: `FindAsync` возвращает прокси, затем `request.Lines`, `request.Order`, `request.Order.Lines` грузятся тремя синхронными запросами внутри `async`, в цикле `First(...)` по уже загруженному.
- Чем кончится: блокировка потока на 3 round-trip к БД на каждое одобрение; тот же класс проблемы, что B1.
- Как чинить: один запрос с явным `Include`/проекцией нужных цен (и фильтр по `TenantId` в самом запросе), всё через `await`.

### M3. `new HttpClient` на каждый вызов шлюза
- Файл: Returns/RefundGateway.cs:12, 21
- Что не так: `using var client = new HttpClient(...)` на каждый вызов, шлюз зарегистрирован синглтоном и читает конфиг в каждом вызове. Нет таймаута и политик ретраев.
- Чем кончится: каждое одобрение открывает новое соединение, сокеты остаются в TIME_WAIT (socket exhaustion), DNS не обновляется; шлюз без таймаута (дефолт 100 с) держит запрос и поток.
- Как чинить: типизированный клиент через `AddHttpClient<RefundGateway>` с таймаутом и политикой, как это уже сделано для `ReturnNotifier`.

### M4. Ночная сверка: `List.Contains` внутри цикла, O(N*M)
- Файл: Returns/ReturnsReconciliationJob.cs:32, 44-46
- Что не так: `gatewayIds` - `List<string>`, `Contains` вызывается для каждой локальной записи. За 90 дней это ~45 тыс. локальных возвратов против ~45 тыс. записей шлюза.
- Чем кончится: порядка 2 млрд сравнений строк за прогон; десятки секунд-минуты CPU на узле, который обслуживает 400 RPS.
- Как чинить: `HashSet<string>` для `gatewayIds` (O(1) на проверку).

### M5. Миграция не будет подхвачена EF, таблицы `Tenants` нет в схеме
- Файл: Migrations/20260910120000_AddReturns.cs:5
- Что не так: у класса нет `[DbContext(typeof(ShopDbContext))]` и `[Migration("20260910120000_AddReturns")]`, модель-снимок (`ModelSnapshot`) в каталоге отсутствует. EF не обнаруживает такую миграцию. Кроме того, `TenantService` читает таблицу `"Tenants"` сырым SQL (TenantService.cs:21), а ни миграции, ни `DbSet` для неё нет - EF её не управляет.
- Чем кончится: `Migrate()`/`database update` не создаёт таблицы возвратов, приложение падает на первом обращении; без `Tenants` любой запрос завершается 500 в резолве тенанта.
- Как чинить: сгенерировать миграцию штатно (`dotnet ef migrations add`) с атрибутами и снимком, завести сущность `Tenant` (с уникальным индексом по `Host`) или явно задокументировать, где живёт таблица.

### M6. Проверка «уже есть заявка» не защищена от гонки, уникального индекса нет
- Файлы: Returns/ReturnValidator.cs:21-22, Migrations/20260910120000_AddReturns.cs:45
- Что не так: проверка и вставка не атомарны, индекс `IX_ReturnRequests_OrderId` не уникальный.
- Чем кончится: два одновременных POST по одному заказу создают две заявки, каждую можно одобрить - возврат по заказу дважды.
- Как чинить: частичный уникальный индекс по `OrderId` для `Status <> Rejected` (Npgsql: `HasIndex(...).IsUnique().HasFilter(...)`), обработка нарушения как ошибки валидации.

### M7. Индекс не покрывает сортировку списка
- Файлы: Migrations/20260910120000_AddReturns.cs:44, Returns/ReturnsController.cs:23-30
- Что не так: запрос `WHERE TenantId [AND Status] ORDER BY CreatedAt DESC OFFSET/LIMIT`, индекс только `(TenantId, Status)`. Без фильтра по статусу используется префикс `TenantId`, затем сортировка всех заявок тенанта; при фильтре - сортировка внутри статуса.
- Чем кончится: по мере роста таблицы (~180 тыс. возвратов в год) каждое открытие списка сортирует десятки тысяч строк; самый частый запрос деградирует со временем.
- Как чинить: индекс `(TenantId, Status, CreatedAt DESC)` плюс `(TenantId, CreatedAt DESC)`; рассмотреть keyset-пагинацию вместо `Skip` (см. m5).

### M8. Уведомление после денег: частичный отказ даёт 500 при уже проведённой выплате, ловится только `HttpRequestException`
- Файлы: Notifications/ReturnNotifier.cs:18-26, Returns/ReturnService.cs:39, 56, 68
- Что не так: `ReturnNotifier` глотает только `HttpRequestException`. Таймаут (`TaskCanceledException`) и отмена токена уходят наверх. У клиента нет таймаута, уведомление идёт синхронно в запросе, после `SaveChanges`.
- Чем кончится: выплата уже проведена и записана, но сервис отвечает 500; оператор жмёт повторно и получает 404 (статус уже `Refunded`) - путаница, клиент не получил письмо, нет повтора. Медленный сервис уведомлений удлиняет все approve/create.
- Как чинить: таймаут и ловля `TaskCanceledException`/любого сбоя уведомления без влияния на исход операции; идеально - outbox или фоновая очередь с ретраями.

## Minor

### m1. `CountAsync(...) > 0` вместо `AnyAsync`
- Файл: Returns/ReturnValidator.cs:21
- Не так: наличие проверяется счётом. Чем кончится: лишний подсчёт вместо остановки на первой строке; при росте числа заявок на заказ - лишняя работа. Заменить на `AnyAsync`.

### m2. `DateTime.Now` против UTC, в обход `IClock`
- Файл: Returns/ReturnPolicy.cs:9
- Не так: `order.CreatedAt` хранится в UTC, сравнение идёт с локальным временем сервера; остальной код использует `IClock.UtcNow`. Чем кончится: окно возврата сдвигается на смещение часового пояса хоста (до часов), тесты на время недетерминированы. Использовать `IClock`.

### m3. `CreatedAtAction(nameof(List), new { id })` указывает на несуществующий маршрут
- Файл: Returns/ReturnsController.cs:43
- Не так: у `List` нет параметра `id`, заголовок `Location` собирается как `/api/returns?id=N`. Чем кончится: клиент получает бесполезную ссылку. Добавить `GET {id}` или отдавать 201 без Location.

### m4. Сверка односторонняя, без защиты от повторного запуска
- Файл: Returns/ReturnsReconciliationJob.cs:13, 30, 37-51
- Не так: проверяется только «локально Refunded, на шлюзе нет». Обратный случай (деньги ушли, статус не сохранён - сценарий из B2) не ищется. Таймер стартует от запуска приложения, а не ночью, при нескольких репликах прогон выполняется на каждой, результат только в логе.
- Чем кончится: расхождения, ради которых сверка задумана, остаются необнаруженными. Добавить обратное сравнение, привязку ко времени и блокировку/один исполнитель.

### m5. Список: трекинг и OFFSET-пагинация
- Файл: Returns/ReturnsController.cs:23-31
- Не так: нет `AsNoTracking`, пагинация `Skip/Take` (глубокие страницы читают и отбрасывают все предыдущие строки). Чем кончится: лишний расход памяти на трекинг и деградация глубоких страниц. Использовать `AsNoTracking`, keyset-пагинацию.

### m6. Статус `Approved` объявлен, но не используется
- Файлы: Data/ShopDbContext.cs:32, Returns/ReturnService.cs:53
- Не так: заявка сразу переходит `Requested -> Refunded`, промежуточного состояния нет. Чем кончится: нельзя отличить «одобрено, выплата идёт» от «выплачено», отсюда невозможна безопасная обработка сбоя (см. B2).

### m7. Неограниченная длина причины
- Файлы: Returns/ReturnValidator.cs:14-15, Migrations/20260910120000_AddReturns.cs:18
- Не так: `Reason` проверяется только на пустоту, колонка `text`. Чем кончится: можно записать мегабайты текста в каждую заявку. Ограничить длину в валидаторе и в модели.

### m8. (не проверено) `Cast<int?>()` поверх `SqlQuery<int>`
- Файл: Infrastructure/TenantService.cs:22
- Не так: приём нужен, чтобы `FirstOrDefault` вернул `null`, а не 0; перевод `Cast` для скалярного `SqlQuery` в EF 8 не проверялся (запуск запрещён). Если не транслируется, резолв тенанта падает или возвращает 0. Проверить интеграционным тестом.
