# Ревью MR: модуль возвратов (Shop.Api)

Итого: blocker 5, major 6, minor 6 (всего 17).
Нагрузка для оценки: 2 млн заказов, ~15 тыс. возвратов в месяц, ~400 RPS, список возвратов открывают постоянно.
Код не запускался и не собирался, выводы по чтению.

## Blocker

### B1. Нет аутентификации и авторизации, approve/reject/список открыты всем
- Файл: Program.cs:28-33, Returns/ReturnsController.cs:8-52
- Не так: нет AddAuthentication/UseAuthentication/UseAuthorization и ни одного [Authorize]. Тенант определяется только по заголовку Host (Infrastructure/TenantFilter.cs:10), его задаёт клиент.
- Чем кончится: любой, кто достучался до API, вызывает POST /api/returns/{id}/approve и выводит деньги через шлюз, читает список возвратов с именами клиентов (ПДн). Подменой Host читает и меняет данные чужого тенанта. Одобрение денег доступно без роли "поддержка".
- Что сделать: аутентификация, политика для approve/reject/list (роль поддержки), тенант брать из проверенного claim или сверять с ним, а не доверять Host.

### B2. Одобрение возврата: деньги уходят до фиксации, нет идемпотентности и защиты от гонки
- Файл: Returns/ReturnService.cs:45-54 (и RefundGateway.cs:13)
- Не так: порядок "проверить Status -> вызвать шлюз -> SaveChanges" без транзакции, без токена конкурентности (xmin/RowVersion) и без ключа идемпотентности в запросе к шлюзу. В шлюз и в SaveChanges передан ct запроса.
- Чем кончится:
  1. Два параллельных approve (двойной клик, ретрай прокси) оба видят Requested и оба вызывают шлюз: двойной возврат денег.
  2. Клиент оборвал запрос после ответа шлюза: ct отменяет SaveChanges. Деньги возвращены, статус остаётся Requested, повторный approve платит второй раз.
  3. Любое падение SaveChanges после RefundAsync даёт тот же исход.
- Что сделать: перевести заявку в промежуточное состояние (Approved) атомарно (условный UPDATE / xmin), слать шлюзу ключ идемпотентности (Id возврата), вызов шлюза и финальный SaveChanges делать с CancellationToken.None, добивать зависшие Approved ретраем или сверкой.

### B3. Валидатор не проверяет количество к возврату
- Файл: Returns/ReturnValidator.cs:29
- Не так: условие `line.Quantity <= 0 || orderLine.Quantity < 0` сравнивает количество заказа с нулём, а не с `line.Quantity`. Лимита "не больше купленного" нет. Одна и та же OrderLineId может повторяться в Lines.
- Чем кончится: заявка на 1000 шт. при покупке одной. Сумма в Approve (ReturnService.cs:49-50) = UnitPrice * Quantity уходит в шлюз как есть: возврат больше стоимости заказа.
- Что сделать: `line.Quantity > orderLine.Quantity` -> ошибка, запретить дубли OrderLineId (или суммировать), проверить итог против суммы заказа.

### B4. Список возвратов: N+1 через lazy-loading прокси на горячем пути
- Файл: Returns/ReturnsController.cs:23-33, Returns/ReturnMapper.cs:10-22, Program.cs:12
- Не так: запрос грузит только ReturnRequests без Include/проекции. Маппер на каждую строку лениво дёргает r.Lines, r.Order, r.Order.Lines, r.Order.Customer (UseLazyLoadingProxies). Загрузка синхронная, внутри async-метода.
- Чем кончится: страница в 50 строк = около 1 + 4*50 = 200 запросов к БД. При постоянно открываемом списке и 400 RPS: тысячи запросов в секунду, исчерпание пула соединений Npgsql, блокировка потоков (sync I/O), рост p99 до секунд. Грузятся и целые заказы со всеми позициями ради суммы и имени.
- Что сделать: проекция Select прямо в ReturnListItem (имя клиента, сумма и число позиций считаются в SQL), AsNoTracking, без маппера по сущностям. Ленивые прокси лучше отключить совсем.

### B5. Миграция не будет применена
- Файл: Migrations/20260910120000_AddReturns.cs:5
- Не так: у класса нет [DbContext(typeof(ShopDbContext))] и [Migration("20260910120000_AddReturns")], нет Designer-файла и ShopDbContextModelSnapshot. EF Core находит миграции только по этим атрибутам. В MR нет и таблиц Tenants, Orders, Customers, OrderLines, хотя код на них опирается (TenantService.cs:21).
- Чем кончится: Database.Migrate/dotnet ef database update не увидят миграцию, таблиц возвратов нет, любой запрос модуля падает с "relation does not exist". Следующая сгенерированная миграция попытается создать всё заново.
- Что сделать: сгенерировать миграцию штатно (`dotnet ef migrations add`) вместе со snapshot. Убедиться, что Tenants, Orders и прочие таблицы создаются другими миграциями.

## Major

### M1. RefundGateway: новый HttpClient на каждый вызов, таймаута нет
- Файл: Returns/RefundGateway.cs:12, 21
- Не так: `new HttpClient` в using на каждый запрос, вместо IHttpClientFactory/typed client. Таймаут стандартный 100 с, ретраев и политик нет. Сам сервис зарегистрирован Singleton (Program.cs:23).
- Чем кончится: на каждый вызов новое соединение, TIME_WAIT-сокеты накапливаются (socket exhaustion), DNS-изменения не подхватываются. При подвисшем шлюзе approve висит до 100 с и держит поток.
- Что сделать: AddHttpClient<RefundGateway>, явный Timeout, политика ретраев только для идемпотентных вызовов (с ключом из B2). Заодно нет проверки `body!` на null (стр. 16).

### M2. TenantFilter: sync-over-async и запрос в БД на каждый запрос
- Файл: Infrastructure/TenantFilter.cs:11, Infrastructure/TenantService.cs:20-23
- Не так: `.Result` внутри синхронного IActionFilter. Тенант не кэшируется: на каждый из ~400 RPS отдельный SELECT по Tenants.
- Чем кончится: блокируются потоки пула (вместе с B4 ведёт к thread pool starvation), лишние 400 запросов в секунду к БД на данных, которые почти не меняются. Исключение БД приходит как AggregateException.
- Что сделать: IAsyncActionFilter или middleware, кэш host -> tenantId (IMemoryCache с TTL).

### M3. Нет индекса под сортировку списка, оффсетная пагинация
- Файл: Migrations/20260910120000_AddReturns.cs:44, Returns/ReturnsController.cs:27-31
- Не так: индекс (TenantId, Status), а запрос сортирует по CreatedAt DESC и делает Skip/Take. Без фильтра по статусу индекс помогает лишь по TenantId.
- Чем кончится: на каждый заход в список сортировка всех строк тенанта (годовой объём ~180 тыс., растёт), глубокие страницы всё дороже.
- Что сделать: индекс (TenantId, Status, CreatedAt DESC) и (TenantId, CreatedAt DESC), keyset-пагинация по (CreatedAt, Id).

### M4. Сверка не видит главный дефект: деньги ушли, локально не записано
- Файл: Returns/ReturnsReconciliationJob.cs:31-51
- Не так: сверка идёт только в одну сторону (локально Refunded, а шлюз не знает). Возвраты на шлюзе без локальной записи (сценарии из B2) и расхождения по суммам не проверяются. Результат только лог.
- Чем кончится: двойные и "потерянные" выплаты остаются незамеченными, сверка создаёт видимость контроля.
- Что сделать: сравнивать в обе стороны по RefundId/OrderId и сумме, расхождения писать в таблицу или алерт.

### M5. Дубль заявки на заказ: проверка без уникальности
- Файл: Returns/ReturnValidator.cs:21-22, Migrations/20260910120000_AddReturns.cs:45
- Не так: "по заказу уже есть заявка" проверяется CountAsync до вставки, индекс по OrderId не уникальный.
- Чем кончится: два одновременных POST создают две заявки на один заказ, обе можно одобрить: двойной возврат.
- Что сделать: уникальный частичный индекс по OrderId (где Status != Rejected), обработка конфликта как ошибки валидации.

### M6. Исключения уведомлений ломают уже выполненную операцию
- Файл: Notifications/ReturnNotifier.cs:18-26, Returns/ReturnService.cs:39, 56, 68
- Не так: ловится только HttpRequestException. Таймаут HttpClient (TaskCanceledException) и отмена запроса пролетают наружу. Отправка синхронна внутри запроса после коммита, без таймаута.
- Чем кончится: после успешного возврата денег клиент получает 500 (повторный approve даст 404, потому что статус Refunded), при создании заявки 500, а повтор упрётся в "уже есть заявка". Письмо при падении процесса теряется.
- Что сделать: ловить Exception кроме отмены вызывающего, короткий таймаут, лучше outbox/очередь для уведомлений.

## Minor

### m1. Окно возврата считается по DateTime.Now, а не UTC
- Файл: Returns/ReturnPolicy.cs:9
- Не так: CreatedAt хранится в UTC (clock.UtcNow, timestamptz), сравнение с локальным временем сервера, мимо IClock.
- Чем кончится: окно сдвигается на часовой пояс сервера (часы на границе 14 дней), тесты времени не воспроизводимы.
- Что сделать: `IClock.UtcNow`.

### m2. Статус Approved не используется
- Файл: Data/ShopDbContext.cs:32, Returns/ReturnService.cs:53
- Не так: Requested сразу превращается в Refunded, Approved нигде не выставляется, хотя описание MR различает "одобрение" и возврат денег.
- Чем кончится: нет места для безопасного промежуточного состояния (см. B2), зависшие возвраты неотличимы от необработанных.

### m3. CreatedAtAction указывает на List с параметром id
- Файл: Returns/ReturnsController.cs:43
- Не так: у List нет параметра id, GET по id нет вовсе.
- Чем кончится: Location вида /api/returns?id=5 игнорируется сервером, клиент не получает созданный ресурс.

### m4. Сверка: расписание и O(n*m)
- Файл: Returns/ReturnsReconciliationJob.cs:13, 32, 46
- Не так: PeriodicTimer(24h) стартует сразу при запуске, то есть работает не "ночью", а в момент деплоя/рестарта, и в каждой реплике. `gatewayIds` это List, Contains линейный.
- Чем кончится: около 45 тыс. возвратов за 90 дней * ~45 тыс. ID: порядка 2*10^9 сравнений строк за прогон, лишняя нагрузка на шлюз при нескольких репликах. Ошибка первого прогона откладывает следующий на сутки. Весь ответ шлюза грузится одним JSON без пагинации.
- Что сделать: HashSet, расписание на ночное окно, лидер/блокировка (pg advisory lock), пагинация ответа шлюза.

### m5. Сортировка списка без детерминированного тай-брейка
- Файл: Returns/ReturnsController.cs:28
- Не так: OrderByDescending(CreatedAt) без Id.
- Чем кончится: при равных CreatedAt строки на соседних страницах дублируются или пропадают.

### m6. Нет связей в схеме, маппер падает на битых данных
- Файл: Migrations/20260910120000_AddReturns.cs:25-41, Returns/ReturnMapper.cs:12, Returns/ReturnService.cs:50
- Не так: ReturnLines.OrderLineId без FK на OrderLines, ReturnRequests.TenantId без FK на Tenants. `First(...)` бросает InvalidOperationException, если позиции нет.
- Чем кончится: одна битая запись роняет весь список или approve 500-кой.
