# Ревью MR: Catalog.Worker (импорт CSV, синхронизация цен, событие изменения цены)

Масштаб: ~200 тыс. товаров. Код не правился, сборка не запускалась; выводы из чтения. Применена дисциплина из performance-review (счёт вместо Any, объекты вне цикла, копии буферов) плюс общий обход.

## Blocker

### B1. Подписка на событие не снимается, обработчик держит освобождённый DbContext
`Pricing/PriceSyncWorker.cs:30-32` (+ `Program.cs:10`, `Pricing/CatalogEvents.cs:7`)
Что не так: на каждом цикле создаётся scope, `PriceChangeHandler` (захватил `db` из scope) подписывается на singleton `CatalogEvents` и никогда не отписывается (`-=` нет). Scope освобождается в конце `SyncOnceAsync`, а обработчик остаётся в делегате события.
Чем кончится: на втором цикле (через 10 минут) первое же изменение цены вызовет обработчик первого цикла с освобождённым `DbContext` -> `ObjectDisposedException` из `RaisePriceChanged`. Исключение вылетает из `ExecuteAsync`, и по умолчанию (.NET 8, `BackgroundServiceExceptionBehavior.StopHost`) останавливается весь хост, включая ночной импорт. До этого - рост списка подписчиков и удержание контекстов и `_applied` в памяти. Цены перестают обновляться со второго цикла.

### B2. `PriceCache` растёт без границ и при этом бесполезен
`Pricing/PriceSyncWorker.cs:13, 37-41`
Что не так: статический `Dictionary` с ключом `sku:yyyyMMddHHmm`. Минута входит в ключ, цикл идёт раз в 10 минут, значит попаданий в кэш нет никогда (кроме повтора внутри той же минуты), а записи не вытесняются. За цикл добавляется до 200 тыс. записей, ~144 цикла в сутки.
Чем кончится: ~29 млн строк-ключей в сутки, OOM воркера за часы. Кэш не даёт эффекта, только цену утечки. Плюс `DateTime.UtcNow` читается на каждой итерации, ключ может смениться посреди цикла. Убрать кэш, либо ключ без времени и TTL/ограничение размера.

### B3. Любая ошибка API поставщика роняет воркер; нет таймаута и повтора
`Pricing/PriceSyncWorker.cs:20-24, 40, 54-58`
Что не так: `FetchPriceAsync` без try/catch, `GetFromJsonAsync` бросает на 404/5xx/таймаут/невалидный JSON, `dto!` падает NRE на `null`. Ни `catch` на уровне цикла, ни таймаута, ни повтора, ни `Polly`/resilience. Один товар из 200 тыс. с ошибкой прерывает цикл.
Чем кончится: исключение выходит из `ExecuteAsync` -> `StopHost` -> воркер падает целиком (импорт тоже). При ежедневном шуме внешнего API - постоянные перезапуски.

### B4. ReDoS: катастрофический откат в regex описания на данных поставщика
`Import/CatalogImportJob.cs:11, 28`
Что не так: `^([\p{L}\p{N}]+[ ,.-]?)*$` - вложенные квантификаторы с необязательным разделителем; слово из n букв можно разбить 2^(n-1) способами. На строке из слова ~25+ символов с недопустимым символом в конце (скобка, кавычка, `/`, `%`) движок перебирает все разбиения. `RegexOptions.Compiled` не помогает, `matchTimeout` не задан.
Чем кончится: входные данные - внешняя выгрузка, строка вроде `Кабель-удлинитель (5м)` с длинным словом подвешивает ночной импорт на минуты-часы с загрузкой ядра, второй `PriceSyncWorker` голодает по пулу. Заменить паттерн (`^[\p{L}\p{N} ,.-]*$`), добавить `RegexOptions.NonBacktracking` или `matchTimeout`.

## Major

### M1. `existingSkus.Contains` по `List<string>` на каждую строку
`Import/CatalogImportJob.cs:17, 33`
Что не так: 200 тыс. SKU в `List`, линейный поиск для каждой из ~200 тыс. строк -> ~4*10^10 сравнений строк.
Чем кончится: импорт тратит на проверку существования минуты и более; растёт квадратично с каталогом. Нужен `HashSet<string>` (с `StringComparer.Ordinal`). Видно и по пункту: выборка всех SKU в память вместо `WHERE Sku IN` пачками тоже лишняя, но допустима при 200 тыс.

### M2. `SaveChangesAsync` на каждую строку, трекер не очищается
`Import/CatalogImportJob.cs:44-54`
Что не так: 200 тыс. отдельных round-trip'ов INSERT, и все добавленные `Product` остаются в `ChangeTracker` (нет `Clear()`); `DetectChanges` на каждом `SaveChanges` обходит всё отслеживаемое.
Чем кончится: на первичной загрузке время растёт квадратично, память - линейно (200 тыс. сущностей с `Attributes`). Нужны батчи (500-5000) с `SaveChangesAsync` и `ChangeTracker.Clear()` либо `COPY`/bulk-вставка.

### M3. Не изолирована ошибка строки: одна битая строка обрывает импорт и роняет хост
`Import/CatalogImportJob.cs:24-51`, `Import/ImportScheduler.cs:16`
Что не так: `cols[2]`, `cols[4]`, `cols[5]` без проверки длины (IndexOutOfRange); `decimal.Parse` (FormatException), `JsonSerializer.Deserialize` (JsonException; для пустого `cols[5]` тоже) без try/catch. Исключение выходит из `RunAsync` -> `ExecuteAsync` -> StopHost. Наивный `Split(';')` ломается на описании с `;` или кавычках CSV.
Чем кончится: одна строка выгрузки поставщика останавливает воркер (и синхронизацию цен) в 02:00, при этом часть товаров уже закоммичена (SaveChanges по строке) - частичный импорт без отчёта. Нужны: парсер CSV (CsvHelper), TryParse, учёт ошибок строки, ловить на уровне `ImportScheduler` и продолжать цикл.

### M4. Дубликаты SKU в самом файле дают нарушение PK
`Import/CatalogImportJob.cs:33`
Что не так: `existingSkus` не пополняется после добавления; повторный SKU в файле проходит проверку и падает на `SaveChanges` по PK `Sku`.
Чем кончится: импорт обрывается (см. M3). Добавлять SKU в множество после вставки и считать дубликат пропуском.

### M5. Импорт только добавляет: существующие товары не обновляются
`Import/CatalogImportJob.cs:33`
Что не так: `if (existingSkus.Contains(sku)) continue;` - название, описание, атрибуты, валюта существующих товаров из ночной выгрузки никогда не применяются; цена правится только отдельным синхронизатором.
Чем кончится: каталог расходится с выгрузкой поставщика, изменения описаний/атрибутов теряются молча. Если upsert не предполагался - переименовать задачу и задокументировать; иначе реализовать обновление.

### M6. Синхронизация цен: 200 тыс. последовательных HTTP-запросов за цикл
`Pricing/PriceSyncWorker.cs:35-41`
Что не так: по запросу на SKU, строго последовательно, без параллелизма и без пакетного эндпоинта. При 50 мс на запрос цикл идёт ~2,8 часа при интервале 10 минут.
Чем кончится: цикл не укладывается в интервал (`PeriodicTimer` пропускает тики), цены устаревают на часы, нагрузка на API поставщика постоянная. Нужен bulk-эндпоинт поставщика либо ограниченный параллелизм (`Parallel.ForEachAsync`, `MaxDegreeOfParallelism`), либо дельта-опрос.

### M7. `new HttpClient` на каждый запрос
`Pricing/PriceSyncWorker.cs:56`
Что не так: клиент создаётся и освобождается на каждый SKU (200 тыс. раз за цикл), без `IHttpClientFactory`.
Чем кончится: исчерпание сокетов (TIME_WAIT), потеря переиспользования соединений, нет DNS-ротации. Использовать типизированный клиент/`IHttpClientFactory` с таймаутом и resilience-хендлером.

### M8. Обработчик события: по UPDATE на каждый товар, синхронно
`Pricing/PriceChangeHandler.cs:12-14`
Что не так: `ExecuteUpdate` синхронный (блокирует поток пула в async-воркере), отдельный round-trip на каждое изменение, без `CancellationToken`; весь ход обновления цен зависит от синхронного вызова события.
Чем кончится: при массовой смене цен (например, 100 тыс. изменений) - 100 тыс. round-trip'ов, блокировка потока на каждом. Накапливать изменения и применять пакетом (`UPDATE ... FROM (VALUES ...)` или батчи по Sku), асинхронно с токеном.

## Minor

### m1. `new Regex` в цикле
`Import/CatalogImportJob.cs:27` - `skuFormat` не зависит от итерации, но создаётся на каждую строку (200 тыс. разборов паттерна, без `Compiled`/кэша). Вынести в `static readonly` (или `[GeneratedRegex]`).

### m2. `JsonSerializerOptions` и `CultureInfo` создаются в цикле
`Import/CatalogImportJob.cs:40, 42` - оба не зависят от итерации. Новый `JsonSerializerOptions` на каждый вызов обходит кэш метаданных System.Text.Json (на каждый экземпляр - своя разогревка и аллокации); `new CultureInfo("ru-RU")` тоже на каждой строке. Вынести в статические поля.

### m3. Весь файл в памяти и две копии
`Import/CatalogImportJob.cs:16, 21` - `File.ReadAllText` + `text.Split('\n')` материализует и текст, и массив всех строк (LOH на десятках МБ), плюс синхронное чтение в async-методе. Читать потоком (`File.ReadLinesAsync`/`StreamReader`).

### m4. Накопление `skipped` конкатенацией строки
`Import/CatalogImportJob.cs:18, 30, 36, 57` - `skipped += ...` в цикле: квадратичное копирование и гигантская строка в логе при массовом пропуске. Копить счётчик + ограниченный список в `List<string>`, в лог - количество и первые N.

### m5. Парсинг цены по `ru-RU` без проверки формата
`Import/CatalogImportJob.cs:42, 49` - формат цены поставщика не зафиксирован; точка вместо запятой даёт `FormatException` (см. M3) или неверную цену при разделителях групп. Зафиксировать формат (InvariantCulture, если выгрузка с точкой) и использовать `TryParse`. При `InvariantGlobalization=true` в контейнере `new CultureInfo("ru-RU")` бросит `CultureNotFoundException`.

### m6. Расписание по локальному времени
`Import/ImportScheduler.cs:9-12` - `DateTime.Now`: зависит от часового пояса контейнера, переход на летнее/зимнее время может дать сдвиг; нет защиты от пропуска/дубля прогона при падении после 02:00. Использовать UTC и `TimeProvider`.

### m7. Счётчик `_changed`: лишняя блокировка, чтение вне неё
`Pricing/PriceSyncWorker.cs:14-15, 47, 51` - единственный писатель, `lock` избыточен, а чтение в логе (стр. 51) - вне блокировки, то есть синхронизация неполная и вводит в заблуждение. `Interlocked` либо убрать; «changed so far» нарастающий итог без сброса - неинформативен.

### m8. Мёртвое состояние и шум в логах
`Pricing/PriceChangeHandler.cs:8, 15-16` - `_applied` только пишется (память растёт, никто не читает); `LogInformation` на каждое изменение цены (до 200 тыс. строк за цикл). Убрать `_applied`, логировать итог/Debug.

### m9. Цена от поставщика не валидируется; `Currency` не сверяется
`Pricing/PriceSyncWorker.cs:44, 57-58` - `dto!.Price` без проверки на `<= 0`, `null` DTO; валюта товара (`Product.Currency`) не сопоставляется с валютой ответа, сравнение просто по числу. Чем кончится: обнуление/подмена цен при дефекте API.

### m10. Маппинг `Dictionary<string,string>` в `jsonb` не подтверждён
`Data/CatalogDbContext.cs:12` - в Npgsql 8 без явного `EnableDynamicJson` (или конвертера) такой тип может не маппиться/падать на первом запросе. Не проверялось сборкой - проверить на реальной БД и добавить интеграционный тест.

### m11. Нет тестов, миграций, обработки отмены на границах
Весь MR - нет проекта тестов и миграций; `Task.Delay`/`PeriodicTimer` корректно принимают токен, но `RunAsync`/HTTP не используют его в синхронных участках (`ExecuteUpdate`, `File.ReadAllText`). URL `prices/{sku}` без `Uri.EscapeDataString`.
