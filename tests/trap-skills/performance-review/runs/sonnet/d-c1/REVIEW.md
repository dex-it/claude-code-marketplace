# Ревью MR: модуль возвратов (Shop.Api)

Итого: blocker 4, major 7, minor 7 (всего 18).

## Blocker

### B1. Нет аутентификации и авторизации; тенант определяется по заголовку Host
`Returns/ReturnsController.cs:8-9, 46-52`, `Program.cs:28-33`, `Infrastructure/TenantFilter.cs:10`
- Что не так: ни `AddAuthentication/UseAuthentication/UseAuthorization`, ни `[Authorize]`. Единственная "защита" - тенант из `Request.Host`, а Host шлёт сам клиент.
- Чем кончится: любой анонимный вызов `POST /api/returns/{id}/approve` запускает выплату денег через шлюз; список возвратов (имена клиентов) читается без входа; подменой Host читаются и одобряются возвраты чужого тенанта. Роль "поддержка" в коде не существует.
- Нужно: аутентификация, политика/роль для list/approve/reject, tenant брать из claim'ов, а не из Host (Host - только сверка).

### B2. Проверка количества возврата перепутана, можно вернуть больше купленного
`Returns/ReturnValidator.cs:29`
- Что не так: `line.Quantity <= 0 || orderLine.Quantity < 0` - второе условие проверяет количество в заказе на отрицательность и никогда не срабатывает. Условие `line.Quantity > orderLine.Quantity` отсутствует.
- Чем кончится: заявка на 1000 шт. при покупке 1 проходит валидацию, `ApproveAsync` считает сумму `UnitPrice * Quantity` и отправляет шлюзу завышенный возврат. Прямая денежная потеря.

### B3. Одобрение не атомарно и не идемпотентно: двойная выплата
`Returns/ReturnService.cs:45-54`
- Что не так: (а) статус читается как `Requested`, затем внешний платёж, потом `SaveChanges`; нет concurrency token/rowversion/условного UPDATE - два параллельных `approve` (двойной клик, ретрай) оба проходят проверку и оба платят; (б) шлюзу не передаётся ключ идемпотентности (`RefundGateway.cs:13`); (в) если платёж прошёл, а `SaveChanges` упал или `RefundAsync` вернул таймаут после фактического списания - в БД остаётся `Requested`, повторное одобрение платит снова; (г) статус `Approved` объявлен, но не используется - промежуточного состояния "платёж инициирован" нет, восстановиться нечем. Параллельный `reject` в том же окне тоже даёт Rejected + реальный возврат.
- Чем кончится: дублирующие выплаты, расхождение БД и шлюза, ручной разбор.
- Нужно: перевод в `Approved` условным UPDATE/версией строки до вызова шлюза, idempotency key (например Id заявки), затем `Refunded`; сверка добивает зависшие `Approved`.

### B4. Список возвратов: N+1 на lazy-loading прокси, на самом горячем эндпоинте
`Returns/ReturnsController.cs:23-33`, `Returns/ReturnMapper.cs:10-12, 19-22`, `Program.cs:12`
- Что не так: запрос грузит только `ReturnRequests`, затем маппер лениво тянет на каждую строку `r.Lines`, `r.Order`, `r.Order.Lines`, `r.Order.Customer` (`UseLazyLoadingProxies`). Это до 4 синхронных запросов на строку, при `pageSize` до 100 - до ~400 round-trip'ов на один GET. Загрузка ленивая и синхронная, т.е. блокирует поток пула внутри async-метода. Плюс отслеживаемые сущности (нет `AsNoTracking`), грузятся все колонки, включая лишние.
- Чем кончится: список открывают постоянно (~400 RPS на систему): сотни запросов в БД на каждый вызов, исчерпание пула соединений Npgsql и потоков, деградация всего API; рост с числом возвратов только ухудшает.
- Нужно: проекция в `ReturnListItem` одним запросом (`Select` с суммой по join'у `ReturnLines`/`OrderLines`, имя клиента), `AsNoTracking`; lazy-loading прокси убрать из проекта или хотя бы из этого пути.

## Major

### M1. Проверка "заявка по заказу уже есть" - гонка, уникального ограничения нет
`Returns/ReturnValidator.cs:21`, `Migrations/20260910120000_AddReturns.cs:44-46`
- check-then-insert без уникального индекса: два параллельных POST создают две заявки на один заказ, обе потом одобряются -> двойной возврат за один заказ. Нужен частичный уникальный индекс по `OrderId` для статусов != Rejected (и обработка нарушения как 409).

### M2. Дубли `OrderLineId` в одной заявке и нет учёта уже возвращённого
`Returns/ReturnValidator.cs:24-31`
- Цикл проверяет каждую строку отдельно: `[{line:5,qty:1},{line:5,qty:1}]` обходит любую проверку количества по строке (даже после исправления B2) - суммируется при выплате. Нужно группировать по `OrderLineId` и сравнивать сумму с купленным.

### M3. `TenantFilter` блокирует поток (`.Result`) и ходит в БД на каждый запрос без кэша
`Infrastructure/TenantFilter.cs:11`, `Infrastructure/TenantService.cs:20-23`
- Sync-over-async на каждом запросе при ~400 RPS: thread pool starvation под нагрузкой (особенно вместе с B4), исключения приходят как `AggregateException`. Плюс отдельный SQL на каждый запрос ради разрешения тенанта - справочник хостов нужно кэшировать (`IMemoryCache`, короткий TTL) и делать фильтр `IAsyncActionFilter`/middleware.

### M4. `RefundGateway`: `new HttpClient` на каждый вызов, без таймаута, авторизации и ретраев
`Returns/RefundGateway.cs:12, 21`
- `using var client = new HttpClient` на каждый вызов - исчерпание сокетов (TIME_WAIT), нет переиспользования DNS/пула; таймаут по умолчанию 100 с держит запрос и транзакционное состояние (см. B3); у платёжного шлюза нет ни заголовка авторизации, ни политики ретраев/circuit breaker. Нужен типизированный `AddHttpClient<RefundGateway>` с таймаутом и аутентификацией.
- Также `ListRefundsAsync` не пагинирован, читает весь ответ в память.

### M5. Уведомления шлются синхронно внутри запроса и ломают ответ после коммита
`Notifications/ReturnNotifier.cs:20-26`, вызовы `Returns/ReturnService.cs:39, 56, 68`
- Ловится только `HttpRequestException`. Таймаут HttpClient даёт `TaskCanceledException`, он уходит наверх -> клиент получает 500, хотя заявка создана / деньги возвращены. Клиент ретраит: создание отвечает "уже есть заявка", одобрение - 404. Плюс медленный notify-сервис (таймаут 100 с по умолчанию, см. `Program.cs:24-25`) блокирует ответ. Отправку делать вне запроса (outbox/очередь), ошибки не пробрасывать, таймаут задать явно.

### M6. Миграция не будет обнаружена и не создаёт нужных таблиц
`Migrations/20260910120000_AddReturns.cs:5`
- Нет атрибутов `[DbContext(typeof(ShopDbContext))]` и `[Migration("20260910120000_AddReturns")]`, нет `ModelSnapshot`. EF Core такой класс не найдёт - `Database.Migrate()`/`dotnet ef database update` её не применит, таблицы `ReturnRequests/ReturnLines` не появятся -> 500 на всех эндпоинтах. Кроме того, запрос тенанта (`TenantService.cs:21`) читает таблицу `Tenants`, которой нет ни в модели, ни в миграции. Миграцию нужно сгенерировать `dotnet ef migrations add`.

### M7. Сверка: O(n*m) по `List.Contains` и полная выгрузка шлюза
`Returns/ReturnsReconciliationJob.cs:32, 46`
- За 90 дней ~45 тыс. возвратов; `gatewayIds` - `List<string>`, `Contains` в цикле - порядка 2*10^9 сравнений строк, десятки секунд CPU на ночную задачу, горячая точка в процессе API. Заменить на `HashSet<string>`; список из шлюза брать страницами.

## Minor

### m1. `DateTime.Now` вместо UTC/IClock в проверке срока возврата
`Returns/ReturnPolicy.cs:9`
- `CreatedAt` хранится в UTC (timestamptz), сравнение идёт с локальным временем сервера: окно сдвигается на смещение часового пояса; `IClock` в проекте есть, но не используется, тест времени невозможен. Использовать `IClock.UtcNow`/`TimeProvider`. Аналогично `DateTime.UtcNow` в `ReturnsReconciliationJob.cs:30`.

### m2. Сверка неполная и запускается не по ночам
`Returns/ReturnsReconciliationJob.cs:13-25, 44-51`
- Цикл `do/while` выполняет сверку сразу при старте каждого инстанса (не "ночью"), на каждой реплике; период 24 ч дрейфует от рестартов. Сверка односторонняя (в шлюзе есть возврат, которого нет локально - главный сценарий из B3 - не ловится), суммы не сравниваются, результат только `LogWarning` без алерта/исправления.

### m3. Нет индекса под сортировку списка
`Migrations/20260910120000_AddReturns.cs:44`
- Индекс `(TenantId, Status)`, а запрос сортирует по `CreatedAt DESC` (`ReturnsController.cs:28`): для тенанта с большим числом заявок - сортировка всего набора на каждый запрос. Нужен `(TenantId, Status, CreatedAt DESC)` и `(TenantId, CreatedAt DESC)`. Нет индекса/FK на `ReturnLines.OrderLineId`.

### m4. `CreatedAtAction(nameof(List), new { id })` указывает на несуществующий маршрут
`Returns/ReturnsController.cs:43`
- Метода получения по id нет; `Location` будет `api/returns?id=N`, который игнорируется. Добавить `GET {id}` либо вернуть `Created` без ложной ссылки.

### m5. Неверные HTTP-статусы бизнес-ошибок
`Returns/ReturnService.cs:46, 63`, `Returns/ReturnsController.cs:48, 52`
- Повторное одобрение/одобрение отклонённой заявки даёт 404 ("не найдено") - клиент и поддержка не отличают ошибку состояния от отсутствия. Должен быть 409.

### m6. Сумма возврата не сохраняется, пересчитывается по текущим ценам
`Returns/ReturnService.cs:49-50`, `Returns/ReturnMapper.cs:12-13`
- Сумма вычисляется налету из `OrderLine.UnitPrice`, в заявке не фиксируется: изменение цены/строки заказа после создания меняет "сумму" в списке и сделает невозможной сверку по сумме со шлюзом. `First(...)` в маппере бросает `InvalidOperationException` и роняет весь список при одной битой строке (FK на `ReturnLines.OrderLineId` отсутствует). Хранить `Amount` в `ReturnRequest`.

### m7. Мелочи валидации
`Returns/ReturnValidator.cs:14, 21`
- `Reason` без ограничения длины (колонка text, вход неограничен); `CountAsync(...) > 0` вместо `AnyAsync`.
