# Ревью MR: импорт транзакций, отчёт, синхронизация партнёров и валют

Масштаб: ~40k участников, ~500k строк/сутки, ~2000 активных правил.
Код не запускался, выводы получены чтением.

## Blocker

1. **loyalty/import_transactions.py:46-50 — вставка начислений не идемпотентна.**
   `INSERT` без `ON CONFLICT (tx_id)` и без проверки дублей. Повторный запуск того же файла (ретрай, перезагрузка выгрузки, дубли `tx_id` внутри файла) начислит баллы второй раз. Итог: двойные начисления деньгами лояльности. Если на `tx_id` есть unique, весь `executemany` упадёт одной ошибкой и пакет не импортируется. Нужен `ON CONFLICT (tx_id) DO NOTHING` и баланс только по реально вставленным строкам (`RETURNING`).

2. **loyalty/import_transactions.py:51-59 — `try/except` вокруг `UPDATE` внутри одной транзакции.**
   В psycopg2 после первой ошибки транзакция в состоянии aborted. Все следующие `execute` падают с `InFailedSqlTransaction`, их глотает `except Exception: continue`. Затем `conn.commit()` на aborted-транзакции фактически делает rollback без исключения. Итог: вставленные `accruals` откатываются вместе с балансами, а функция возвращает отчёт «начислено: N». Ошибка скрыта, данные потеряны. Если же сбой не затрагивает всю транзакцию, получится обратное: начисление есть, баланса нет, расхождение молчаливое. Убрать `except`, пусть падает вся транзакция, или использовать savepoint на строку.

## Major

3. **loyalty/import_transactions.py:51-56 — построчный `UPDATE members` (до 500k round-trip) и риск deadlock.**
   Участников ~40k, строк 500k, поэтому один участник обновляется многократно. Это медленно, и блокировки на строках `members` берутся в порядке файла. Два параллельных импорта (или импорт с другой записью баланса) могут получить deadlock. Агрегировать дельты по `member_id`, обновлять одним запросом (`UPDATE ... FROM (VALUES ...)` / `execute_values`) в отсортированном порядке `member_id`.

4. **loyalty/import_transactions.py:13-17 — линейный перебор правил с `re.search`.**
   500k строк × до 2000 правил ≈ 10⁹ regex-вызовов. Кэш `re` хранит ~512 скомпилированных паттернов, а их 2000, поэтому идёт постоянная перекомпиляция. Итог: импорт идёт часами. Прекомпилировать паттерны один раз в `load_rules`, кэшировать результат по `merchant` (мерчантов мало), рассмотреть индексацию по префиксу.

5. **loyalty/rules.py:13-17 и import_transactions.py:15 — паттерны из БД, порядок и ошибки.**
   - Нет `ORDER BY`, а берётся первое совпадение. При пересечении правил партнёр и ставка недетерминированы и меняются между запусками.
   - Невалидный regex в одном из 2000 правил бросает `re.error`. Он не ловится (не `ValueError`), и импорт падает целиком. Катастрофический паттерн приводит к ReDoS и зависанию.
   - Поиск без якорей (`re.search`) даёт ложные совпадения по подстроке.
   Нужны явный приоритет (`ORDER BY priority, id`), валидация и компиляция при загрузке с пропуском и логом плохих правил.

6. **loyalty/import_transactions.py:28,33 и rules.py:8 — деньги и ставки во `float`.**
   Баллы считаются как `round(float * float)` с банковским округлением и ошибками представления. Итог: расхождения в баллах на границе .5, невоспроизводимость. Нет валидации: `inf` даёт `OverflowError` (не ловится, импорт падает), `nan` даёт ValueError (попадает в skipped), отрицательные и нулевые суммы (возвраты) дают отрицательные баллы и уход баланса в минус. Использовать `Decimal`/`numeric`, явный режим округления, правило для возвратов, проверку `amount > 0`.

7. **loyalty/import_transactions.py:26-43 — непойманные исключения на кривых строках.**
   Короткая строка CSV даёт `None` в полях, затем `float(None)` / `int(None)` бросают `TypeError`, который не ловится. Один плохой ряд валит импорт целиком. `UnicodeDecodeError` и `re.error` тоже не ловятся. Файл с BOM (`utf-8`, а не `utf-8-sig`) даёт `KeyError` на каждой строке, и весь файл уходит в skipped.

8. **loyalty/import_transactions.py:45-56 — не проверяется существование участника.**
   `UPDATE` по несуществующему `member_id` обновляет 0 строк без ошибки (`rowcount` не проверяется). Если нет FK, в `accruals` остаются сироты, баллы нигде не начислены, а отчёт говорит «начислено». Проверять `rowcount` / использовать FK и пропускать с записью в отчёт.

9. **loyalty/db.py:9-15 — `putconn` без rollback и без обработки ошибок.**
   При исключении внутри `with connection()` соединение возвращается в пул с открытой или aborted-транзакцией. Следующий потребитель получит «грязное» соединение: `InFailedSqlTransaction`, висящие блокировки, `idle in transaction`. В `finally` нужен `conn.rollback()` (или `putconn(conn, close=True)` при ошибке). Дополнительно пул создаётся при импорте модуля и читает `os.environ["LOYALTY_DSN"]`. Импорт любого модуля без переменной падает с `KeyError`, тестирование затруднено.

10. **loyalty/partners_sync.py:23-24 — `asyncio.gather` без ограничения параллелизма и с fail-fast.**
    Запросов столько, сколько активных партнёров, все одновременно, без `Semaphore`. Это риск rate-limit/бана от API партнёров и исчерпания сокетов. Одна ошибка (`raise_for_status`, таймаут) обрывает всю синхронизацию. Остальные задачи продолжают работать «в пустоту», ни один партнёр не обновляется, ретраев нет. Нужны `Semaphore`, `return_exceptions=True` с учётом частичного успеха, ретраи с backoff.

11. **loyalty/partners_sync.py:18-32 — соединение из пула и открытая транзакция держатся на время HTTP.**
    После `SELECT` транзакция остаётся открытой (`idle in transaction`) на всё время сетевых вызовов (до десятков секунд). Это держит соединение (пул всего 10) и снапшот. Нужно прочитать id, закончить транзакцию, сходить по HTTP и взять соединение заново для записи.

12. **loyalty/partners_sync.py:29-30 — данные API партнёров не валидируются.**
    `p["id"]` берётся из ответа, а не из запрошенного id. Ошибка или подмена на стороне API обновит не того партнёра. Отсутствие ключа даёт `KeyError` после всех запросов. `cashback_cap` и `name` пишутся без проверки типа, диапазона и `None`, значит возможен сброс лимита кешбэка. Использовать запрошенный id, валидировать схему и диапазоны.

## Minor

13. **loyalty/report.py:10,14 — отчёт копится конкатенацией строки в памяти.**
    `self.body +=` на 500k строк даёт строку десятки МБ и квадратичную деградацию там, где нет оптимизации CPython. `render()` возвращает всё одной строкой. Использовать список строк и `join`, а для пропусков писать в файл или ограничивать детали. Кроме того, `add_accrual` вызывается до записи в БД (import_transactions.py:41), поэтому отчёт отражает намерение, а не результат (см. п. 2).

14. **loyalty/import_transactions.py:24,34 — все начисления копятся в памяти и вставляются одним `executemany`.**
    `executemany` в psycopg2 делает построчные запросы и работает медленно. Использовать `execute_values` или `COPY` батчами. Единая транзакция на весь файл не даёт частичного прогресса и держит длинные блокировки.

15. **loyalty/import_transactions.py:39 — `datetime.fromisoformat` без часового пояса.**
    Наивное время трактуется в TZ сервера или БД. Возможны сдвиги дат начислений около границ суток и расхождения с партнёрскими отчётами. Задать TZ явно.

16. **loyalty/reference.py:5,9 — `^[A-Z]{3}$` пропускает `"USD\n"`.**
    `$` совпадает перед завершающим переводом строки, нужен `fullmatch` или `\Z`. Невалидные коды отбрасываются молча, без лога и счётчика.

17. **loyalty/reference.py:11-16 — `execute_values` на пустом или дублирующем списке.**
    При пустом `valid` генерируется некорректный SQL и функция падает. Дубли `code` в одном батче дают `ON CONFLICT DO UPDATE command cannot affect row a second time`. Функция сама коммитит соединение вызывающего, а при ошибке не делает rollback. Нужны ранний выход на пустой список, дедупликация и управление транзакцией на стороне вызывающего.

18. **loyalty/partners_sync.py:8 — `os.environ["PARTNERS_API"]` читается при импорте.**
    Нет значения по умолчанию и нет проверки, импорт падает с `KeyError`. Читать лениво или передавать параметром.

19. **requirements.txt:1 — `psycopg2-binary` для продакшена.**
    Сам проект psycopg2 не рекомендует binary-сборку для прод-окружений (своя libpq/OpenSSL). Нет и тестов в MR для критичной денежной логики.
