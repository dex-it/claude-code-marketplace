# Ревью MR: Loyalty.Sync (импорт транзакций, отчёт, синхронизация партнёров и валют)

Масштаб для оценки: 40 тыс. участников, ~500 тыс. строк/сутки, ~2000 активных правил.

## Blocker

### B1. loyalty/import_transactions.py:51-59 - проглоченная ошибка внутри транзакции Postgres
Любой сбой `cur.execute` (дедлок, serialization, нарушение ограничения) переводит транзакцию в aborted-состояние. Каждый следующий `execute` падает с `InFailedSqlTransaction`, `except Exception: continue` их гасит, а `conn.commit()` (стр. 60) на aborted-транзакции молча откатывает всё.
Итог: вся пачка (INSERT из стр. 46 тоже) пропадает, функция возвращает отчёт «начислено: N», в логе по строке на каждую запись. Участники баллов не получают, оператор считает импорт успешным. Нужно убрать try/except (пусть падает и откатывается) либо работать savepoint-ами и считать ошибки в отчёте. Статус отчёта должен зависеть от результата commit.

### B2. loyalty/import_transactions.py:46-50 - нет идемпотентности по tx_id
`INSERT INTO accruals` без `ON CONFLICT (tx_id)` и без дедупликации внутри файла. Запуск одного файла дважды, ретрай после обрыва или повторная выгрузка пересекающихся суток дают одно из двух: при unique на tx_id весь импорт падает на дубле; без unique баллы начисляются повторно (стр. 54 безусловно прибавляет баланс). Нужен `ON CONFLICT DO NOTHING` с `RETURNING`, а баланс обновлять только по реально вставленным строкам. Заодно нужен лок или запись о файле, чтобы два одновременных импорта не гонялись.

## Major

### M1. loyalty/import_transactions.py:13-17, 29 - 2000 regex на каждую из 500 тыс. строк
До 1e9 вызовов `re.search` в сутки на горячем пути. Кэш `re` хранит около 512 скомпилированных паттернов (`re._MAXCACHE`), при 2000 правил он трэшится и паттерны перекомпилируются постоянно. Нужна предкомпиляция в `load_rules`/при старте и индекс (кэш результата по `merchant`, у мерчантов высокая повторяемость). Паттерны приходят из БД: без ограничения сложности возможен ReDoS, и один плохой паттерн вешает импорт. Порядок правил не задан (`SELECT` без `ORDER BY`, rules.py:13-16), «первое совпавшее» недетерминировано, одна транзакция может получить разные правила от запуска к запуску. Нужны `ORDER BY` с приоритетом и явная семантика (`search` ловит подстроку, возможно нужен `fullmatch`).

### M2. loyalty/import_transactions.py:46-59 - построчные запросы на 500 тыс. строк
`executemany` в psycopg2 - это цикл отдельных `execute`, плюс отдельный `UPDATE members` на каждую строку: ~1 млн round-trip-ов за импорт, минуты вместо секунд. Построчные обновления берут блокировки на members в порядке файла, поэтому два параллельных импорта (или импорт и онлайн-начисление) дают дедлоки. Нужно `execute_values` для вставки, агрегация очков по `member_id` (`SUM`) и один `UPDATE ... FROM (VALUES ...)` с сортировкой по id.

### M3. loyalty/import_transactions.py:28-43 - исключения, которые не ловятся, и мусорные значения, которые проходят
- `float("inf")` -> `round(inf)` даёт `OverflowError`, `nan` - `ValueError`, а None (короткая строка, `DictReader` подставляет `None`) в `re.search(..., None)` и `int(None)` даёт `TypeError`. Эти типы не в `except (KeyError, ValueError)`, один битый ряд роняет весь импорт 500 тыс. строк.
- Отрицательные суммы (возвраты) дают отрицательные баллы и уводят баланс в минус без проверки; нулевые/пустые тоже.
- Нет проверки, что `member_id` существует: `UPDATE ... WHERE id = %s` на несуществующий id затрагивает 0 строк без ошибки, accrual остаётся осиротевшим, баллы никому не начислены. Нужно проверять `rowcount` либо FK.
- Дубли `tx_id` в одном файле не отсекаются (см. B2).

### M4. loyalty/import_transactions.py:28, 33; rules.py:8 - деньги и баллы во float
`float(amount)` и `points_per_rub: float` дают ошибки представления, а `round()` - банковское округление (`round(2.5) == 2`). Начисления расходятся с расчётом партнёра и бухгалтерией на копейки/баллы, в масштабе суток накапливается. Нужны `Decimal`, `NUMERIC` в БД и явная политика округления (`ROUND_HALF_UP`).

### M5. loyalty/partners_sync.py:24 - неограниченный gather и «всё или ничего»
`asyncio.gather` запускает запросы ко всем активным партнёрам разом: сотни/тысячи параллельных соединений к внешнему API (лимиты, 429, исчерпание дескрипторов у `httpx` по умолчанию 100 соединений в пуле, остальные ждут и упираются в `timeout=10` на пул). Первое исключение (`raise_for_status`, таймаут) пробрасывается из `gather`, а остальные задачи продолжают работать без присмотра. Итог: один недоступный партнёр срывает синхронизацию всех, ни одно обновление не применяется, ретраев нет. Нужны `Semaphore`/лимит, `return_exceptions=True` с учётом ошибок, ретраи с backoff и отчёт по сбойным.

### M6. loyalty/partners_sync.py:17-33 - блокирующий psycopg2 внутри `async def`
Запросы к БД синхронные и идут прямо в event loop: на время запросов loop встаёт. Плюс соединение из пула держится (и транзакция открыта после `SELECT`, стр. 20) всё время HTTP-запросов, то есть «idle in transaction» на десятки секунд, держит снапшот и занимает один из 10 слотов пула. Нужно закрывать транзакцию до сетевой части и брать соединение заново только для записи, либо выносить DB-часть в `asyncio.to_thread`.

### M7. loyalty/reference.py:8-17 - дубль ключа в пачке и тихая потеря строк
- `INSERT ... ON CONFLICT DO UPDATE` через `execute_values` падает с `CardinalityViolation` («cannot affect row a second time»), если в одной выгрузке `code` встречается дважды; весь справочник не обновляется. Нужна дедупликация до вставки.
- Невалидные коды отбрасываются без лога и без счётчика (стр. 9): справочник валют «успешно» загружен, но часть валют отсутствует, потом начисления/конвертации ломаются с непонятной причиной.
- `CURRENCY_CODE.match` с `$` пропускает `"USD\n"`; нужен `fullmatch`. `code=None` даёт `TypeError`.
- `conn.commit()` внутри хелпера забирает управление транзакцией у вызывающего: нельзя сделать атомарно «валюты + что-то ещё».

### M8. loyalty/partners_sync.py:29-31; import_transactions.py - `cashback_cap` синхронизируется, но не применяется
Лимит кэшбэка партнёра записывается в `partners`, а при начислении (стр. 33) не читается: баллы начисляются без ограничения. Если лимит - бизнес-правило, оно не реализовано; если нет, колонка и синхронизация лишние. Нужно уточнить требование у автора MR. Аналогично игнорируется валюта транзакции: сумма считается в «рублях» (`points_per_rub`), тогда как в MR заведён справочник валют.

## Minor

### m1. loyalty/report.py:10, 14 - накопление отчёта конкатенацией строк
`self.body += ...` на 500 тыс. строк: квадратичное копирование в худшем случае и весь отчёт в памяти (десятки МБ) вместе со списком `accruals` (import_transactions.py:24). Нужен `list` + `"".join` либо потоковая запись в файл/БД; отчёт и данные импорта лучше не держать целиком в памяти (батчи).

### m2. loyalty/import_transactions.py:25 - кодировка без BOM
`encoding="utf-8"` оставляет BOM в имени первой колонки (`"﻿tx_id"`), CSV из Excel/1С не читается: каждая строка уходит в «пропущено» с `tx_id="?"`. Нужен `utf-8-sig` и проверка заголовка (если обязательных колонок нет - сразу ошибка файла, а не 500 тыс. «пропусков»).

### m3. loyalty/import_transactions.py:39 - время без часового пояса
`datetime.fromisoformat` возвращает naive datetime для строк без смещения. При колонке `timestamptz` значение трактуется в часовом поясе сессии БД, в отчётах по суткам границы плывут. Нужна явная зона (UTC или зона партнёра).

### m4. loyalty/db.py:6, 9-15 - пул создаётся при импорте, нет таймаута ожидания
`ThreadedConnectionPool(1, 10, os.environ[...])` на уровне модуля: импорт любого модуля без `LOYALTY_DSN` падает с `KeyError`, тесты не изолировать. При занятых 10 соединениях `getconn` сразу бросает `PoolError`, а не ждёт. Нужны ленивая инициализация и очередь/семафор. То же для `PARTNERS_API` (partners_sync.py:8).

### m5. loyalty/partners_sync.py:12, 29-30 - ответ API без валидации, обновление по `p["id"]`
`resp.json()` не проверяется (нет `KeyError`-обработки для `name`/`cashback_cap`), а запись идёт по `p["id"]` из ответа, а не по запрошенному `partner_id`: рассинхронный/подменённый ответ обновит чужого партнёра. Запросы без аутентификации (заголовки не передаются), проверьте требование API. `cashback_cap` без проверки типа и диапазона.

### m6. loyalty/import_transactions.py:20, 25 - путь файла без ограничений
`import_file(path)` открывает любой переданный путь; если путь формируется из пользовательского ввода/имени из выгрузки - чтение произвольных файлов (в отчёт попадёт текст ошибки). Проверьте вызывающую сторону; нужна привязка к каталогу выгрузок.
