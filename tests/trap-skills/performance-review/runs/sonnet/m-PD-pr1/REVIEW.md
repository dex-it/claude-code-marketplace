# Ревью MR: модуль возвратов (Shop.Api)

Масштаб: ~2 млн заказов, ~15 тыс. возвратов/мес, ~400 RPS, список возвратов открывают постоянно.
Пройден чек-лист из SKILL.md (Count vs Any, объекты в цикле, копии буферов) и общий ревью.

## Blocker

1. **Returns/ReturnsController.cs:23-33, Returns/ReturnMapper.cs:10-22 (+ Program.cs:12)** - N+1 в списке возвратов. Запрос читает только `ReturnRequests` (с tracking), а маппер при включённых `UseLazyLoadingProxies` обращается к `r.Lines`, `r.Order`, `r.Order.Lines` и `r.Order.Customer`. Это 3-4 отдельных синхронных запроса на каждую заявку, то есть до ~200 запросов на страницу из 50. Lazy loading к тому же синхронный, поэтому он блокирует потоки пула. Эндпоинт открывают постоянно, поэтому пул соединений Npgsql закончится, p99 вырастет на порядки, а остальной API начнёт отдавать таймауты. Нужна одна проекция `Select` в `ReturnListItem` с `AsNoTracking`, сумма и количество считаются в SQL. Лучше убрать lazy-proxies совсем или хотя бы не использовать их в read-путях.

2. **Returns/ReturnService.cs:45-57, Returns/RefundGateway.cs:10-17** - одобрение возврата не защищено от повторов и не атомарно. Нет токена конкурентности и блокировки, нет ключа идемпотентности для шлюза. Сначала идёт внешний вызов `RefundAsync`, и только потом `SaveChanges`.
   - Двойной клик или два модератора одновременно оба увидят `Requested`, и деньги вернут дважды.
   - Если `SaveChanges` упадёт после успешного возврата, в БД останется `Requested`, деньги уже ушли, а повторное одобрение вернёт их второй раз.
   - Одобрение гоняется и с `Reject`.
   
   Нужно: `xmin`/`RowVersion` как токен конкурентности, переход в промежуточный статус `Approved` с коммитом до вызова шлюза, `Idempotency-Key` (например, id возврата) в запросе к шлюзу, обработка `DbUpdateConcurrencyException`.

3. **Returns/ReturnsController.cs:8-53, Program.cs:28-34** - нет аутентификации и авторизации: нет `[Authorize]`, `UseAuthentication`/`UseAuthorization`. Любой, кто знает URL, может одобрить возврат (то есть вывести деньги через шлюз) или отклонить его. Любой может создать заявку на чужой заказ, если знает `OrderId`: проверки, что заказ принадлежит клиенту, нет. Единственная «граница» - тенант по заголовку `Host`, а его задаёт клиент. Нужны роли (support для approve/reject и списка), а для создания - проверка владельца заказа.

## Major

4. **Returns/ReturnValidator.cs:29** - проверка количества сломана: `orderLine.Quantity < 0` бессмысленна (количество в заказе не бывает отрицательным), а условие `line.Quantity > orderLine.Quantity` отсутствует. Можно заявить возврат 1000 штук при покупке одной, и сумма в `Approve` (ReturnService.cs:49-50) посчитается из заявленного количества. Итог - возврат больше уплаченного. Кроме того, не проверяются повторы одного `OrderLineId` в `cmd.Lines`, и повторы в сумме тоже дают превышение. Нужно сравнивать с `orderLine.Quantity` и группировать по `OrderLineId`.

5. **Infrastructure/TenantFilter.cs:11, Infrastructure/TenantService.cs:20-23** - `.Result` на асинхронном вызове в фильтре (sync-over-async), да ещё и запрос в БД на каждый запрос API без кэша. При 400 RPS это блокирует потоки пула, возможен thread starvation, а база получает лишние 400 запросов/с. Нужны `IAsyncActionFilter` (или middleware) и кэш `host -> tenantId` (`IMemoryCache` с TTL). Индекс по `Tenants.Host` из этого MR проверить нельзя, таблицы `Tenants` в миграции нет.

6. **Returns/RefundGateway.cs:12, 21** - `new HttpClient` на каждый вызов (хотя в DI уже есть `AddHttpClient`, как для `ReturnNotifier`). Это ведёт к накоплению сокетов в TIME_WAIT и не учитывает смену DNS. Таймаут по умолчанию 100 секунд, значит запрос одобрения может висеть так долго. Повторов и Polly нет. Нужен типизированный клиент через `AddHttpClient<RefundGateway>` с коротким таймаутом.

7. **Returns/ReturnPolicy.cs:9** - `DateTime.Now` (локальное время сервера) сравнивается с `CreatedAt`, который хранится в UTC. Срок возврата смещается на величину часового пояса сервера, и в граничные часы заявки принимаются или отклоняются неверно. Кроме того, в проекте уже есть `IClock`, а policy его не использует, поэтому код нельзя тестировать. Нужно `IClock.UtcNow`.

8. **Returns/ReturnsReconciliationJob.cs:32, 46** - `gatewayIds` это `List<string>`, а в цикле по `refunded` стоит `Contains`. Сложность O(N*M): за 90 дней ~45 тыс. возвратов против ~45 тыс. записей шлюза, это порядка 2·10^9 сравнений строк, то есть минуты нагрузки на CPU в процессе, который обслуживает API. Нужен `HashSet<string>`. `ListRefundsAsync` также грузит весь список одним ответом без пагинации (RefundGateway.cs:22).

9. **Notifications/ReturnNotifier.cs:23, Returns/ReturnService.cs:39, 56, 68** - ловится только `HttpRequestException`. Таймаут `HttpClient` приходит как `TaskCanceledException`/`OperationCanceledException`, и он вылетает наружу. Для `Approve` это значит: деньги возвращены, статус сохранён, а клиент получает 500. Повторный клик вернёт 404 (статус уже не `Requested`), и оператор не поймёт, что произошло. Уведомление при этом отправляется синхронно внутри запроса и удлиняет его. Нужно ловить и таймаут (отличая от отмены запроса), а лучше вынести отправку в outbox или фоновую очередь.

10. **Migrations/20260910120000_AddReturns.cs:5-7** - у класса нет `[DbContext(typeof(ShopDbContext))]` и `[Migration("20260910120000_AddReturns")]`, снимка модели тоже нет. EF Core такую миграцию не найдёт, и `Database.Migrate()` её не применит, так что в проде таблиц не будет. Кроме того, в `ReturnLines` нет FK на `OrderLines`.

11. **Returns/ReturnValidator.cs:21-22, Migrations/20260910120000_AddReturns.cs:44-46** - проверка «по заказу уже есть заявка» выполняется в коде без уникального ограничения в БД. Два параллельных `POST` проходят проверку и создают две заявки на один заказ, а потом обе можно одобрить. Нужен частичный уникальный индекс на `OrderId` для `Status <> Rejected` и обработка нарушения.

## Minor

12. **Returns/ReturnValidator.cs:21** - наличие проверяется через `CountAsync(...) > 0` (пункт чек-листа Count vs Any). Нужно `AnyAsync`, чтобы запрос мог остановиться на первой строке.

13. **Returns/ReturnsController.cs:27-30, Migrations/20260910120000_AddReturns.cs:44** - сортировка по `CreatedAt` без уникального tie-breaker (`Id`) при пагинации через `Skip/Take` даёт нестабильные страницы: записи дублируются или пропадают. Индекс `(TenantId, Status)` не покрывает сортировку, а для запроса без фильтра по статусу нужен `(TenantId, CreatedAt DESC)`. Сейчас таблица небольшая, но будет расти.

14. **Returns/ReturnsController.cs:43** - `CreatedAtAction(nameof(List), new { id })`: у `List` нет параметра `id`, а `Location` не указывает на созданный ресурс. Нужен `GET` по id или `Created` без ссылки.

15. **Returns/ReturnService.cs:53, Data/ShopDbContext.cs:32** - статус `Approved` объявлен, но не используется: `Approve` переводит сразу в `Refunded`. Это и есть причина проблемы №2 (нет промежуточного состояния).

16. **Returns/ReturnsReconciliationJob.cs:13-18, 37-51** - «ночная» сверка запускается при старте процесса и затем раз в 24 часа от старта (не ночью), а в нескольких репликах выполняется несколько раз. Сверка односторонняя: возвраты, которые есть в шлюзе, но отсутствуют локально (самый опасный случай из №2), не обнаруживаются. Результат только пишется в лог, без метрики или алерта.

## Итого

Blocker: 3, major: 8, minor: 5 (всего 16).
