# Ревью MR: модуль возвратов

Контекст нагрузки: 2 млн заказов, ~15 тыс. возвратов/мес, ~400 RPS, список возвратов открыт у поддержки постоянно.

Итого: blocker - 4, major - 7, minor - 9.

## Blocker

### 1. Эндпоинты возвратов без аутентификации и авторизации
`Returns/ReturnsController.cs:8-53`, `Program.cs:28-33`

Ни `[Authorize]`, ни `AddAuthentication`/`UseAuthorization` в пайплайне нет. `POST api/returns/{id}/approve` запускает реальный возврат денег через шлюз, `GET api/returns` отдаёт имена клиентов и суммы.

Чем кончится: любой, кто знает хост тенанта, перебором `id` одобряет все заявки в статусе `Requested` и выводит деньги, а заодно выгружает персональные данные клиентов из списка. Роль «оператор поддержки» для approve/reject и list нужна явная политика.

### 2. Одобрение не защищено от повторного и конкурентного вызова: двойной возврат денег
`Returns/ReturnService.cs:45-54`, `Returns/RefundGateway.cs:13`

Цепочка «прочитать статус -> проверить `Requested` -> вызвать шлюз -> сохранить `Refunded`» идёт без concurrency token (`xmin`/`[ConcurrencyCheck]`), без блокировки строки и без idempotency key в запросе к шлюзу.

Чем кончится:
- два оператора (или двойной клик, или ретрай клиента) одновременно проходят проверку статуса, и шлюз проводит два возврата;
- шлюз вернул успех, а `SaveChangesAsync` упал, или запрос отменён через `ct` после ответа шлюза. Статус остаётся `Requested`, повторное одобрение возвращает деньги второй раз. Ночная сверка этот случай не видит (см. minor 14).

Нужны перевод статуса в промежуточный (`Approved`/`RefundPending`) условным UPDATE до вызова шлюза и idempotency key (например, id заявки) в запросе к шлюзу.

### 3. Валидация количества не ограничивает возврат купленным: возврат больше оплаченного
`Returns/ReturnValidator.cs:29`

```csharp
else if (line.Quantity <= 0 || orderLine.Quantity < 0)
```
Второе условие проверяет количество в заказе, а не превышение: должно быть `line.Quantity > orderLine.Quantity`. Дубликаты одной `OrderLineId` в `cmd.Lines` тоже не сворачиваются (цикл `:24-31` проверяет каждую строку отдельно).

Чем кончится: заявка «вернуть 1000 шт.» по позиции, купленной в одном экземпляре, проходит валидацию, а `ApproveAsync` (`ReturnService.cs:49-50`) считает сумму как `UnitPrice * Quantity` и отправляет в шлюз сумму, кратно превышающую оплату. В связке с blocker 1 это прямой вывод денег.

### 4. sync-over-async в глобальном фильтре: блокировка потока пула на каждый запрос API
`Infrastructure/TenantFilter.cs:11`, `Program.cs:28`

`tenants.ResolveAsync(...).Result` - запрос в БД синхронно ждёт в `IActionFilter`, а фильтр добавлен глобально и выполняется на каждом запросе всех контроллеров, не только возвратов.

Чем кончится: на 400 RPS каждый запрос держит поток пула на время запроса к Postgres. При любой задержке БД пул потоков голодает, рост потоков идёт медленно (hill climbing), латентность всего API растёт лавинообразно вплоть до таймаутов. Фильтр нужно сделать `IAsyncActionFilter` (или middleware).

## Major

### 5. N+1 через lazy loading в списке возвратов: до 4 запросов на строку
`Returns/ReturnsController.cs:27-33`, `Returns/ReturnMapper.cs:10-19`, `Program.cs:12`

Запрос грузит только `ReturnRequests`, а маппер обходит `r.Lines`, `r.Order`, `r.Order.Lines`, `r.Order.Customer` - каждое обращение через lazy-loading proxy отдельный запрос. Грузятся целые сущности вместо нужных полей.

Чем кончится: страница по умолчанию (50) - около 200 round-trip, при `pageSize=100` - около 400, на одном соединении пула, синхронно на каждый refresh у операторов. Список, который открыт постоянно, будет давать заметную долю нагрузки на БД и секунды латентности. Нужна одна проекция в `Select` с `Customer.Name`, `Lines.Sum(Quantity)` и суммой через join на `OrderLines`, считаемая в SQL.

### 6. Новый `HttpClient` на каждый вызов шлюза
`Returns/RefundGateway.cs:12`, `Returns/RefundGateway.cs:21`

`using var client = new HttpClient {...}` на каждый возврат и сверку: новое TCP/TLS-соединение каждый раз, сокеты остаются в `TIME_WAIT`. Таймаут по умолчанию 100 с, ретраев/политик нет.

Чем кончится: лишние TLS-рукопожатия на каждом approve, при пиках - исчерпание портов (`SocketException`) и отказ возвратов. Нужен typed client через `AddHttpClient<RefundGateway>` с таймаутом, как уже сделано для `ReturnNotifier`.

### 7. Сверка: линейный поиск по списку внутри цикла, O(n*m)
`Returns/ReturnsReconciliationJob.cs:32`, `Returns/ReturnsReconciliationJob.cs:46`

`gatewayIds` - `List<string>`, `Contains` в цикле по всем локальным возвратам.

Чем кончится: окно 90 дней - порядка 45 тыс. возвратов с обеих сторон, то есть ~10^9 сравнений строк за прогон: минуты CPU на процессе, который параллельно обслуживает 400 RPS. Нужен `HashSet<string>`.

### 8. Проверка «уже есть заявка» - check-then-act без ограничения в БД
`Returns/ReturnValidator.cs:21`, `Migrations/20260910120000_AddReturns.cs:45`

Уникальность активной заявки по заказу проверяется только чтением; индекс `IX_ReturnRequests_OrderId` не уникальный, частичного уникального индекса (`WHERE "Status" <> Rejected`) нет.

Чем кончится: два одновременных POST (двойной клик, ретрай клиента после таймаута уведомления, см. minor 15) создают две заявки на один заказ, обе одобряемы - двойной возврат денег по одному заказу.

### 9. Список: сортировка и OFFSET-пагинация не поддержаны индексом
`Returns/ReturnsController.cs:23-31`, `Migrations/20260910120000_AddReturns.cs:44`

Индекс `(TenantId, Status)` не покрывает `ORDER BY CreatedAt DESC`, а без фильтра статуса (дефолтный экран) Postgres читает все заявки тенанта и сортирует их на каждый запрос. Пагинация через `Skip`, глубокие страницы читают и выбрасывают все предыдущие строки.

Чем кончится: 15 тыс. заявок в месяц - за год ~180 тыс. строк, стоимость каждого открытия списка растёт линейно с историей. Нужны индексы `(TenantId, CreatedAt DESC)` и `(TenantId, Status, CreatedAt DESC)`, для глубоких страниц - keyset-пагинация.

### 10. Создание заявки не проверяет, что заказ принадлежит вызывающему клиенту
`Returns/ReturnService.cs:19`, `Returns/ReturnsController.cs:37-39`

Заказ ищется только по `tenantId` и `orderId`, идентичность клиента не участвует.

Чем кончится: любой пользователь тенанта создаёт заявку на возврат по чужому заказу перебором `OrderId` (IDOR), а активная чужая заявка блокирует владельцу создание своей (`ReturnValidator.cs:21`).

### 11. Резолв тенанта - запрос в БД на каждый HTTP-запрос без кэша
`Infrastructure/TenantService.cs:20-23`, `Infrastructure/TenantFilter.cs:11`

Соответствие «хост -> тенант» практически неизменно, но читается из `Tenants` на каждом из 400 RPS всего API.

Чем кончится: +400 запросов/с к Postgres и занятое соединение пула на каждый запрос ради константы. Нужен кэш (`IMemoryCache` с TTL) на уровне singleton-резолвера.

## Minor

### 12. Проверка наличия через `CountAsync(...) > 0`
`Returns/ReturnValidator.cs:21`

`COUNT` считает все подходящие строки, `AnyAsync` останавливается на первой (`EXISTS`). Чем кончится: лишняя работа на каждом создании заявки; на объёме одной заявки на заказ разница мала, но паттерн тиражируется.

### 13. Окно возврата сравнивает UTC-время заказа с локальным `DateTime.Now`
`Returns/ReturnPolicy.cs:9`

`CreatedAt` из `timestamp with time zone` приходит в UTC, `DateTime.Now` - локальное время сервера; `IClock` зарегистрирован, но не используется. Чем кончится: граница окна сдвигается на смещение таймзоны контейнера (в UTC-контейнере совпадёт, при `TZ=Europe/Moscow` - на 3 часа), и политику нельзя протестировать с фиксированным временем.

### 14. Сверка односторонняя и привязана к старту процесса
`Returns/ReturnsReconciliationJob.cs:13`, `Returns/ReturnsReconciliationJob.cs:37-51`

Проверяется только «Refunded локально, но нет в шлюзе»; обратный случай (возврат в шлюзе есть, заявка осталась `Requested` - ровно сценарий blocker 2) не ищется. `PeriodicTimer(24h)` запускает сверку при старте каждого пода и дальше раз в сутки от старта, а не ночью; на N репликах сверка выполняется N раз. Фильтр по `CreatedAt` заявки, а не по времени возврата, теряет заявки, созданные до окна и возвращённые внутри него. Чем кончится: сверка не ловит самый дорогой класс расхождений, а при деплоях шлюз получает серию тяжёлых запросов в рабочее время.

### 15. Уведомление синхронно на пути запроса после коммита, ошибки кроме `HttpRequestException` пробрасываются
`Returns/ReturnService.cs:39`, `Returns/ReturnService.cs:56`, `Returns/ReturnService.cs:68`, `Notifications/ReturnNotifier.cs:23`

Таймаут `HttpClient` приходит как `TaskCanceledException` и не ловится. Чем кончится: при медленном сервисе уведомлений заявка уже сохранена (или деньги уже возвращены), а клиент получает 500 через 100 с и повторяет запрос. Уведомление теряется без следа, т.к. outbox нет. Уведомление стоит вынести из запроса (outbox / фоновая очередь).

### 16. Одобрение подгружает строки и заказ через lazy loading с линейным поиском
`Returns/ReturnService.cs:49-50`

`request.Lines`, `request.Order`, `request.Order.Lines` - три отдельных запроса после `FindAsync`, плюс `First` по строкам заказа на каждую строку возврата. Чем кончится: лишние round-trip на каждом approve; сумму можно посчитать одним запросом.

### 17. Lazy loading proxies включены глобально для всего контекста
`Program.cs:12`, `Data/ShopDbContext.cs:18-20`, `Data/ShopDbContext.cs:39`, `Data/ShopDbContext.cs:44`

Модуль возвратов включает `UseLazyLoadingProxies()` на общий `ShopDbContext`. Чем кончится: во всём существующем коде (заказы, клиенты) любое обращение к навигации начнёт тихо ходить в БД вместо null/пустой коллекции - N+1 появится там, где их не было, без изменений в коде этих модулей.

### 18. Выгрузка всех возвратов шлюза за 90 дней одним ответом в память
`Returns/RefundGateway.cs:22`, `Returns/ReturnsReconciliationJob.cs:30-41`

И ответ шлюза, и локальная выборка целиком материализуются в список. Чем кончится: десятки тысяч элементов в одном JSON-ответе без пагинации - риск таймаута на 100 с и пик памяти; с ростом объёма растёт линейно.

### 19. `CreatedAtAction` указывает на список, у которого нет параметра `id`
`Returns/ReturnsController.cs:43`

Чем кончится: `Location` получает вид `/api/returns?id=123`, который возвращает первую страницу списка, а не созданную заявку. Эндпоинта `GET api/returns/{id}` нет.

### 20. У `ReturnLines.OrderLineId` нет внешнего ключа
`Migrations/20260910120000_AddReturns.cs:35`, `Migrations/20260910120000_AddReturns.cs:38-42`

Чем кончится: целостность держится только валидатором; строка возврата может ссылаться на несуществующую позицию, и тогда `First` в `ReturnMapper.cs:12` / `ReturnService.cs:50` бросает `InvalidOperationException` - падает весь список возвратов тенанта.
