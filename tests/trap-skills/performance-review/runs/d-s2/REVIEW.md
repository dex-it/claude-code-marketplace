# Ревью MR: модуль возвратов

Контекст: 2 млн заказов, ~15 тыс. возвратов в месяц (~180 тыс. в год, ~45 тыс. за 90 дней), ~400 RPS, список возвратов постоянно открыт у поддержки.

Итого: blocker - 4, major - 5, minor - 8.

## Blocker

### 1. Одобрение и отклонение возврата доступны без авторизации
- **Где:** `Returns/ReturnsController.cs:8-52`, `Program.cs:28-33`
- **Что не так:** на контроллере нет `[Authorize]`, в `Program.cs` нет `AddAuthentication`/`AddAuthorization`/`UseAuthorization`. Доступ ограничен только тенантом по хосту. `POST api/returns/{id}/approve` может вызвать любой, кто знает хост магазина, а не только поддержка.
- **Чем кончится:** клиент создаёт заявку и сам же её одобряет, а деньги уходят через шлюз без участия оператора. `GET api/returns` отдаёт анонимному вызывающему имена клиентов и суммы возвратов всего тенанта. Id перебираются подряд (`int` identity).
- **Severity:** blocker

### 2. Проверка количества не ограничивает возврат сверх купленного, из-за этого возвращается больше денег
- **Где:** `Returns/ReturnValidator.cs:29`, сумма - `Returns/ReturnService.cs:49-50`
- **Что не так:** условие `line.Quantity <= 0 || orderLine.Quantity < 0` сравнивает количество в заказе с нулём, а не с запрошенным. Сравнения `line.Quantity > orderLine.Quantity` нет. Повтор одного `OrderLineId` в `cmd.Lines` тоже не проверяется.
- **Чем кончится:** заявка «вернуть 100 шт.» по строке, где куплена 1 шт. (или одна строка, повторённая 20 раз), проходит валидацию, и `ApproveAsync` отправляет в шлюз `UnitPrice * 100`. Возврат выходит больше оплаченной суммы. Вместе с находкой 1 это эксплуатируется без оператора.
- **Severity:** blocker

### 3. Одобрение не защищено от двойного возврата денег
- **Где:** `Returns/ReturnService.cs:45-54`, `Returns/RefundGateway.cs:13`
- **Что не так:** порядок такой: прочитать статус -> вызвать шлюз -> `SaveChanges`. Токена конкурентности нет, условного перехода `WHERE Status = Requested` нет, ключа идемпотентности в запросе к шлюзу нет.
  - Два одновременных `approve` (двойной клик оператора, два оператора, ретрай прокси) оба видят `Requested`, и оба вызывают `RefundAsync`.
  - Шлюз вернул деньги, а `SaveChangesAsync` упал (обрыв БД, отмена `ct` после ответа шлюза). Статус остаётся `Requested`, повторное одобрение возвращает деньги ещё раз.
  - Таймаут HTTP после того, как шлюз уже провёл операцию, даёт тот же исход.
- **Чем кончится:** двойные выплаты клиентам. Ночная сверка их не ловит, потому что проверяет только направление «локально Refunded -> есть в шлюзе».
- **Severity:** blocker

### 4. Синхронная блокировка `.Result` в глобальном фильтре на каждом запросе
- **Где:** `Infrastructure/TenantFilter.cs:11` (фильтр глобальный, `Program.cs:28`)
- **Что не так:** `ResolveAsync(...).Result` в синхронном `IActionFilter` на каждый запрос API блокирует поток пула на время похода в БД.
- **Чем кончится:** при 400 RPS любой всплеск латентности БД умножается на число заблокированных потоков: 100 мс * 400 RPS = около 40 потоков стоят на `.Result`. Пул потоков наращивается медленно, начинается thread-pool starvation, растут таймауты по всему API, а не только в возвратах. Лечится заменой на `IAsyncActionFilter` с `await`.
- **Severity:** blocker

## Major

### 5. N+1 через lazy loading в списке возвратов для поддержки
- **Где:** `Returns/ReturnsController.cs:27-33`, `Returns/ReturnMapper.cs:10-22`, причина - `Program.cs:12` (`UseLazyLoadingProxies`)
- **Что не так:** страница грузит полные tracked-сущности `ReturnRequest`, а маппер потом на каждой заявке дёргает навигации `r.Lines`, `r.Order`, `r.Order.Lines` и `r.Order.Customer`. Это 4 ленивых запроса на элемент. Lazy loading в EF выполняется синхронным I/O прямо в async-хендлере.
- **Чем кончится:** 1 + 4*50 = 201 синхронный round-trip на страницу по умолчанию и 401 при `pageSize=100`. Список постоянно открыт у операторов, поэтому получаются сотни миллисекунд на запрос плюс заблокированные потоки (усиливает находку 4). Кроме того, из-за глобально включённых прокси любой новый код по 2 млн заказов по умолчанию будет получать N+1. Нужна одна проекция `Select` в `ReturnListItem` с суммой и количеством, посчитанными в SQL, плюс `AsNoTracking`. Прокси стоит убрать.
- **Severity:** major

### 6. Сверка ищет через `List.Contains` в цикле, это квадратичная сложность
- **Где:** `Returns/ReturnsReconciliationJob.cs:32`, `:46`
- **Что не так:** `gatewayIds` - это `List<string>`, и `Contains` вызывается внутри цикла по `refunded`. За 90 дней это порядка 45 тыс. * 45 тыс., то есть около 2*10^9 сравнений строк.
- **Чем кончится:** сверка минутами держит CPU ядра на том же хосте, который обслуживает 400 RPS, и время растёт как квадрат объёма возвратов. Нужен `HashSet<string>` (одна строка правки).
- **Severity:** major

### 7. Индекс не покрывает сортировку горячего списка
- **Где:** `Migrations/20260910120000_AddReturns.cs:44`, запрос - `Returns/ReturnsController.cs:23-30`
- **Что не так:** список фильтрует по `TenantId` (и по `Status`, если он передан) и сортирует `ORDER BY CreatedAt DESC ... OFFSET/LIMIT`. Индекс `(TenantId, Status)` без `CreatedAt` не даёт брать строки в порядке сортировки. Без фильтра по статусу Postgres читает все заявки тенанта и делает top-N sort на каждый запрос.
- **Чем кончится:** таблица растёт примерно на 180 тыс. строк в год, и латентность постоянно открытого списка растёт вместе с ней. На тестовых данных этого не видно. Нужен индекс `(TenantId, CreatedAt DESC)` и/или `(TenantId, Status, CreatedAt DESC)`.
- **Severity:** major

### 8. Уведомление после коммита может превратить успешную операцию в 500
- **Где:** `Returns/ReturnService.cs:39`, `:56`, `:68`, `Notifications/ReturnNotifier.cs:20-26`
- **Что не так:** `SendAsync` ловит только `HttpRequestException`. Таймаут `HttpClient` (`TaskCanceledException`, по умолчанию 100 с) и отмена `RequestAborted` улетают наружу, хотя возврат уже сохранён, а деньги уже ушли. Кроме того, запрос оператора синхронно ждёт сервис уведомлений.
- **Чем кончится:** при медленном notify клиент или оператор получает 500 (или висит до 100 с) по уже выполненной операции. Повтор `approve` отвечает 404 (статус уже не `Requested`), повтор `create` - ошибкой «уже есть заявка», и оператор не понимает, прошёл ли возврат. Уведомление нужно выносить из транзакционного пути (outbox или фон) либо хотя бы ловить все исключения и не передавать туда `ct` запроса.
- **Severity:** major

### 9. Проверка «одна активная заявка на заказ» подвержена гонке
- **Где:** `Returns/ReturnValidator.cs:21`, `Returns/ReturnService.cs:36-37`, `Migrations/20260910120000_AddReturns.cs:45`
- **Что не так:** схема «проверить -> вставить» без ограничения в БД. Индекс `IX_ReturnRequests_OrderId` не уникальный, частичного уникального индекса по `OrderId WHERE Status <> Rejected` нет.
- **Чем кончится:** два параллельных `POST` (двойная отправка формы) создают две заявки на один заказ. Обе можно одобрить, и получится двойной возврат денег за тот же товар (связано с находкой 3).
- **Severity:** major

## Minor

### 10. `CountAsync(...) > 0` вместо `AnyAsync`
- **Где:** `Returns/ReturnValidator.cs:21`
- **Что не так:** для проверки «есть ли» считаются все строки.
- **Чем кончится:** лишняя работа БД. Строк на заказ мало, поэтому эффект небольшой, но `AnyAsync` точнее выражает смысл.
- **Severity:** minor

### 11. `new HttpClient()` на каждый вызов шлюза, таймаут не задан
- **Где:** `Returns/RefundGateway.cs:12`, `:21`
- **Что не так:** клиент создаётся и освобождается на каждый вызов, и каждый раз остаётся сокет в TIME_WAIT. Таймаут стандартный, 100 с.
- **Чем кончится:** при нынешнем темпе одобрений (сотни в день) исчерпание портов маловероятно, отсюда minor. Но паттерн сломается при росте, и запрос оператора может висеть до 100 с на медленном шлюзе. Нужен типизированный клиент через `AddHttpClient`, как у `ReturnNotifier`.
- **Severity:** minor

### 12. Окно возврата считается от локального времени сервера
- **Где:** `Returns/ReturnPolicy.cs:9`
- **Что не так:** `DateTime.Now` сравнивается с `CreatedAt` из `timestamptz` (UTC). `DateTime` при сравнении `Kind` не учитывает. `IClock` обойдён.
- **Чем кончится:** на хосте с TZ не UTC окно сдвигается на смещение пояса: заявку отклонят или примут на несколько часов раньше или позже срока. Логику нельзя проверить тестом с фиксированным временем.
- **Severity:** minor

### 13. «Ночная» сверка запускается при старте каждого экземпляра, а не ночью
- **Где:** `Returns/ReturnsReconciliationJob.cs:13-25`
- **Что не так:** `do/while` выполняет первую итерацию сразу при старте, дальше раз в 24 часа от момента старта. Координации между репликами нет.
- **Чем кончится:** каждый деплой или рестарт на каждой реплике запускает тяжёлую сверку (находка 6) в дневной пик. Дубли предупреждений в логах идут по числу реплик.
- **Severity:** minor

### 14. Тенант резолвится запросом в БД на каждый запрос API
- **Где:** `Infrastructure/TenantService.cs:20-23`
- **Что не так:** для почти неизменного справочника «хост -> тенант» нет кэша.
- **Чем кончится:** лишние 400 round-trip в секунду к БД, и латентность каждого запроса зависит от БД ещё до контроллера (усиливает находку 4).
- **Severity:** minor

### 15. `ApproveAsync` считает сумму через lazy loading
- **Где:** `Returns/ReturnService.cs:49-50`
- **Что не так:** `request.Lines`, `request.Order` и `request.Order.Lines` грузятся тремя синхронными ленивыми запросами внутри async-метода.
- **Чем кончится:** лишние блокирующие round-trip на каждое одобрение. Темп низкий, отсюда minor. Нужны явный `Include` или проекция.
- **Severity:** minor

### 16. `CreatedAtAction` ссылается на список, у которого нет параметра `id`
- **Где:** `Returns/ReturnsController.cs:43`
- **Что не так:** в `Location` попадает `api/returns?id=N`, а это URL списка, который `id` игнорирует. Эндпоинта получения одной заявки нет.
- **Чем кончится:** клиенты, которые идут по `Location`, получают первую страницу списка, а не созданную заявку.
- **Severity:** minor

### 17. Схема не держит целостность строк возврата
- **Где:** `Migrations/20260910120000_AddReturns.cs:35`, `:18`
- **Что не так:** у `ReturnLines.OrderLineId` нет FK на `OrderLines`, длина `Reason` не ограничена.
- **Чем кончится:** после удаления или правки строки заказа `ReturnMapper.cs:12` и `ReturnService.cs:50` падают на `First(...)` с `InvalidOperationException`, и список для поддержки отвечает 500 на всей странице. Неограниченный `Reason` принимает мегабайтные строки.
- **Severity:** minor
