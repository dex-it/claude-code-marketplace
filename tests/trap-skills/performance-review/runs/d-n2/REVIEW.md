# Ревью MR: модуль возвратов

Контекст нагрузки: 2 млн заказов, ~15 тыс. возвратов в месяц (~45 тыс. за 90 дней), API ~400 RPS, список возвратов открыт у операторов поддержки постоянно.

## Blocker

### 1. Returns/ReturnsController.cs:16-52, Program.cs:28-33 - эндпоинты без аутентификации и авторизации
В `Program.cs` нет `AddAuthentication`/`AddAuthorization`, на контроллере нет `[Authorize]`. Кто угодно, кто знает хост тенанта, может:
- `POST api/returns/{id}/approve` - одобрить любую заявку и провести возврат денег через шлюз;
- `GET api/returns` - выгрузить список возвратов с именами клиентов (ПДн);
- `POST api/returns` - создать заявку на чужой заказ перебором `OrderId` (проверки, что заказ принадлежит вызывающему клиенту, нет).

Итог: прямые финансовые потери и утечка ПДн. Нужны схема аутентификации, политика «оператор поддержки» на list/approve/reject и проверка владельца заказа в create.

### 2. Returns/ReturnValidator.cs:29 - количество к возврату не ограничено купленным
Условие `line.Quantity <= 0 || orderLine.Quantity < 0` сравнивает количество в заказе с нулём, а не с запрошенным. Заявка «вернуть 1000 шт.» при купленной 1 проходит валидацию, `ApproveAsync` (ReturnService.cs:49-50) считает сумму `UnitPrice * 1000` и отправляет её в шлюз. Дополнительно не проверяются повторяющиеся `OrderLineId` в одной заявке (`Lines = [{1,1},{1,1},...]` до `MaxLinesPerRequest`) - тот же эффект. Итог: возврат суммы больше оплаченной. Правильно: `line.Quantity > orderLine.Quantity` и группировка строк по `OrderLineId` с суммой количества.

### 3. Returns/ReturnService.cs:45-54 - двойной возврат денег при параллельном или повторном одобрении
Чтение статуса и его смена не защищены: нет concurrency-токена (`xmin`/rowversion), нет условного `UPDATE ... WHERE Status = Requested`, нет ключа идемпотентности в запросе к шлюзу (RefundGateway.cs:13). Два оператора (или двойной клик/ретрай клиента) одновременно читают `Requested`, оба вызывают `RefundAsync` - клиенту возвращается двойная сумма.
Вторая сторона того же места: внешний вызов идёт до `SaveChangesAsync`. Если после успешного возврата падает `SaveChanges`, десериализация (`body!.RefundId`, RefundGateway.cs:16 - NRE на пустом теле) или запрос отменяется по `ct` - деньги ушли, заявка остаётся `Requested`, повторное одобрение вернёт деньги ещё раз. Нужны: перевод в промежуточный статус (`Approved`, который в enum есть, но не используется) с сохранением до вызова шлюза, условное обновление статуса, идемпотентный ключ (например, id заявки) в запросе к шлюзу.

### 4. Infrastructure/TenantFilter.cs:11 - sync-over-async на каждом запросе
`tenants.ResolveAsync(...).Result` блокирует поток пула на время запроса в БД; фильтр глобальный (Program.cs:28), то есть это каждый из ~400 RPS. При росте латентности БД потоки пула заканчиваются, пул добавляет их медленно - starvation, лавинный рост латентности и таймауты по всему API. Нужен `IAsyncActionFilter` (или middleware) с `await`.

## Major

### 5. Infrastructure/TenantService.cs:18-25 - запрос в БД на определение тенанта на каждом HTTP-запросе
Соответствие host -> tenant почти не меняется, но резолвится SQL-запросом на каждый запрос: +400 запросов/с к БД и лишний round-trip в латентности каждого эндпоинта. Нужен кэш (`IMemoryCache` с TTL / ограниченный словарь хостов).

### 6. Returns/ReturnsController.cs:27-33 + Returns/ReturnMapper.cs:10-19, Program.cs:12 - N+1 через lazy loading в списке возвратов
Запрос грузит только `ReturnRequests`; маппер дёргает `r.Lines`, `r.Order`, `r.Order.Lines`, `r.Order.Customer` - включены `UseLazyLoadingProxies`, поэтому на каждую заявку до 4 отдельных запросов: при `pageSize` 50 (дефолт) около 200 запросов на открытие страницы, при 100 - около 400. Lazy loading в EF выполняет загрузку синхронно - это ещё и блокирующий I/O внутри async-обработчика. Список открыт у операторов постоянно - это постоянная нагрузка на БД и пул потоков. Кроме того, выбираются целые сущности (все колонки `Order`, `Customer`) вместо нужных полей.
Правильно: одна проекция в SQL - `Select(r => new ReturnListItem(r.Id, r.OrderId, r.Order.Customer.Name, ..., r.Lines.Sum(l => l.Quantity), сумма через join ReturnLines/OrderLines))`, без маппера по сущностям. Глобальное включение lazy-проксей для БД с 2 млн заказов стоит пересмотреть отдельно: оно делает N+1 поведением по умолчанию для всего проекта.

### 7. Migrations/20260910120000_AddReturns.cs:44 - индекс не покрывает сортировку списка
Список фильтрует `TenantId` (+ опционально `Status`) и сортирует по `CreatedAt DESC` с `OFFSET/LIMIT`. Индекс `(TenantId, Status)` не содержит `CreatedAt`: при фильтре без статуса Postgres читает все заявки тенанта и сортирует их, при фильтре по `Requested`/`Refunded` - все заявки в статусе. Объём растёт на ~15 тыс./мес (180 тыс./год), запрос частый. Нужны `(TenantId, CreatedAt)` и `(TenantId, Status, CreatedAt)`.

### 8. Migrations/20260910120000_AddReturns.cs:5 - миграция не будет найдена EF
У класса нет атрибутов `[DbContext(typeof(ShopDbContext))]` и `[Migration("20260910120000_AddReturns")]` (обычно в `.Designer.cs`, которого в MR нет), нет и обновлённого `ShopDbContextModelSnapshot`. EF обнаруживает миграции по `MigrationAttribute` - `database update` таблицы не создаст, эндпоинты упадут на первом запросе; следующая сгенерированная миграция без снапшота попытается создать эти таблицы заново. Миграцию нужно сгенерировать через `dotnet ef migrations add`. Там же: нет FK `ReturnLines.OrderLineId -> OrderLines.Id`.

### 9. Returns/ReturnValidator.cs:21 + Returns/ReturnService.cs:36-37 - гонка при проверке «уже есть заявка»
Проверка наличия и вставка разнесены, уникального ограничения в БД нет (миграция, строка 45 - обычный индекс). Два параллельных запроса по одному заказу (двойная отправка формы) оба проходят проверку - по заказу две активные заявки, каждую можно одобрить - двойной возврат. Нужен частичный уникальный индекс `OrderId WHERE Status <> Rejected` и обработка нарушения как ошибки валидации.

### 10. Returns/ReturnsReconciliationJob.cs:32,46 - линейный поиск в цикле
`gatewayIds` - `List<string>`, `Contains` внутри цикла по `refunded`. За 90 дней обе стороны порядка 45 тыс. записей: ~45 тыс. x 45 тыс. = ~2 млрд сравнений строк, минуты CPU внутри процесса API, который держит 400 RPS. Нужен `HashSet<string>(gatewayIds)`.

### 11. Notifications/ReturnNotifier.cs:23 + Returns/ReturnService.cs:39,56,68 - сбой уведомления ломает ответ после выполненной операции
`catch` ловит только `HttpRequestException`; таймаут `HttpClient` приходит как `TaskCanceledException` и пролетает наружу. Уведомление вызывается после `SaveChanges` (а в `ApproveAsync` - после реального возврата денег), поэтому при медленном сервисе уведомлений клиент/оператор получает 500 при уже созданной заявке или уже проведённом возврате; повтор создания упирается в «уже есть заявка», оператор не понимает, прошёл ли возврат. Плюс ожидание уведомления целиком входит в латентность запроса. Нужно ловить таймаут/отмену, а лучше отправлять уведомление вне запроса (outbox/очередь).

## Minor

### 12. Returns/RefundGateway.cs:12,21 - новый HttpClient на каждый вызов
`new HttpClient` на вызов открывает новое соединение (TLS-рукопожатие к платёжному шлюзу на каждый возврат) и оставляет сокеты в TIME_WAIT; тайм-аут не задан (дефолт 100 с). Частота одобрений низкая (~500/день), поэтому исчерпания сокетов сейчас не будет, но клиент нужно брать из `IHttpClientFactory` (типизированный клиент, как у `ReturnNotifier`) с явным таймаутом.

### 13. Returns/ReturnsReconciliationJob.cs:22,31 (RefundGateway.cs:22) - весь список возвратов шлюза за 90 дней одним ответом в память
Ответ на ~45 тыс. элементов десериализуется в `List` целиком; растёт с объёмом возвратов, на стороне шлюза ответ без пагинации может упереться в лимиты. Нужна пагинация/`GetFromJsonAsAsyncEnumerable`.

### 14. Returns/ReturnsReconciliationJob.cs:13-25 - «ночная» сверка запускается при старте и на каждой реплике
`PeriodicTimer(24h)` отсчитывает от старта процесса: сверка идёт на каждом деплое/рестарте в рабочее время и параллельно на всех репликах API (при 400 RPS реплик, очевидно, несколько). Нужен запуск по расписанию и единственный исполнитель (лок/отдельный воркер). Также фильтр `CreatedAt >= since` (строка 39) сравнивает дату создания заявки, а не дату возврата - заявки на границе окна выпадают из сверки.

### 15. Returns/ReturnValidator.cs:21 - `CountAsync(...) > 0` вместо `AnyAsync`
Для проверки наличия считает все строки вместо остановки на первой. Строк на заказ единицы, индекс по `OrderId` есть - эффект небольшой, но это путь каждого создания заявки.

### 16. Returns/ReturnPolicy.cs:9 - окно возврата считается от локального времени
`order.CreatedAt` - UTC (timestamptz, Npgsql возвращает `Kind=Utc`), сравнение с `DateTime.Now` сдвигает границу окна на смещение часового пояса сервера. Инжектированный `IClock` в политике не используется - граница ещё и нетестируема. Нужен `clock.UtcNow`.

### 17. Returns/ReturnService.cs:49-50 - lazy loading при одобрении
`request.Lines`, `request.Order`, `request.Order.Lines` - три синхронных ленивых запроса на одобрение. Путь нечастый, но это синхронный I/O в async-методе; нужен `Include`/проекция.

### 18. Returns/ReturnsController.cs:43 - `CreatedAtAction(nameof(List), new { id })` даёт неверный Location
У `List` нет параметра `id`, Location будет `api/returns?id=N` - ссылка на весь список, а не на созданную заявку. Нужен GET по id.

### 19. Returns/ReturnService.cs:53 - статус `Approved` никогда не выставляется
Одобрение сразу пишет `Refunded`; статус `Approved` в enum мёртвый, сверка (ReconciliationJob.cs:39) и список не различают «одобрено» и «деньги ушли». Связано с п.3.
