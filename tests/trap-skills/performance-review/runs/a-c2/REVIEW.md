# Ревью MR: отчёты по клиентам и счета

Объём: весь каталог (новый код). Контекст нагрузки: 40 тыс. клиентов, 3 млн заказов, прод.
Сборка и тесты не запускались (ограничение ревью), выводы получены чтением кода.

## Blocker

### B1. SQL-инъекция в выгрузке заказов
`Controllers/OrderExportController.cs:15` - `FromSqlRaw($"... WHERE status = '{status}'")`: значение из query string подставляется в SQL строкой. Интерполяция в `FromSqlRaw` не параметризуется, это делает только `FromSql`/`FromSqlInterpolated`.
Чем кончится: `?status=x' OR '1'='1` выгрузит все заказы, а `'; DROP TABLE ...; --` или `UNION SELECT` из других таблиц даёт чтение и запись в БД с правами сервиса.

### B2. Эндпоинты без аутентификации и авторизации: утекают PII и чужие счета
`Program.cs:15-18` - нет `AddAuthentication`/`AddAuthorization`, нет `UseAuthentication`/`UseAuthorization`. На контроллерах нет `[Authorize]`.
Чем кончится: `Controllers/CustomerReportsController.cs:40` отдаёт анонимному клиенту email-адреса всех 40 тыс. клиентов (если перебирать `page`). `InvoiceController.cs:16` и `CustomerReportsController.cs:13` открывают счёт и сводку любого заказа и клиента перебором id (IDOR). То же с `OrderExportController.cs:11`: бухгалтерская выгрузка доступна любому.

### B3. Сводка по клиенту поднимает в память все 3 млн заказов
`Controllers/CustomerReportsController.cs:25-26` - `db.Orders.ToListAsync()` без фильтра, `Count` считается в памяти. Выборка ещё и с трекингом, и под lazy-loading прокси.
Чем кончится: каждый запрос сводки тащит из БД всю таблицу и материализует 3 млн отслеживаемых сущностей: сотни МБ - ГБ на запрос, секунды и десятки секунд ответа. Несколько параллельных запросов приводят к OOM пода и нагружают БД. Фильтр и `CountAsync` нужно выполнять на стороне БД.

### B4. Сводка по клиенту падает с исключением при каждом вызове: цикл в сериализации для лога
`Controllers/CustomerReportsController.cs:28` - `JsonSerializer.Serialize(orders)` вычисляется всегда: аргумент интерполированной строки считается до `LogDebug`, уровень логирования здесь не помогает. У `Order` есть навигация `Customer`, у `Customer` - `Orders`. После строк 16 и 19 обе стороны связаны fixup'ом трекинга, а lazy-loading дозагрузит их в любом случае. Получается цикл Order -> Customer -> Orders -> Order, на котором System.Text.Json по умолчанию бросает `JsonException` (object cycle).
Чем кончится: `/summary` отвечает 500 для каждого клиента, у которого есть заказы. Если цикл разорвать, останутся две проблемы: сериализация всех заказов с lazy-дозагрузкой на каждом запросе и PII клиента (email, notes, photo) в логах. Логировать нужно шаблоном с параметрами, без дампа сущностей.

## Major

### M1. N+1 через глобальные lazy-loading прокси
`Program.cs:9` (`UseLazyLoadingProxies`) + `Controllers/CustomerReportsController.cs:21-22` - `order.Lines` в цикле делает отдельный запрос на каждый заказ.
Чем кончится: у клиента с 2000 заказов сводка сделает 2000+ запросов к БД. Глобальный lazy loading распространяет эту проблему на весь будущий код сервиса, а N+1 так станет невидимым. Сумму нужно считать агрегатом в БД (`SelectMany(o => o.Lines).SumAsync(...)`). Lazy-прокси лучше не включать.

### M2. Денежная сумма обрезается до int и может переполниться
`Controllers/CustomerReportsController.cs:8,30` - `LinesTotal` имеет тип `int`, `(int)linesTotal`.
Чем кончится: копейки молча отбрасываются, сводка расходится с суммами заказов. Если оборот клиента больше 2 147 483 647, явное приведение `decimal -> int` бросит `OverflowException`, и запрос ответит 500. Поле должно быть `decimal`.

### M3. Счёт падает с 500 для заказа без каталога вложений
`Controllers/InvoiceController.cs:30-31` - `Directory.EnumerateFiles` бросает `DirectoryNotFoundException`, если каталога `{Root}/{orderId}` нет. Для заказов без вложений это обычный случай. Если ключа `Attachments:Root` нет в конфиге, `Path.Combine(null, ...)` бросит `ArgumentNullException`.
Чем кончится: PDF-счёт не выдаётся для большинства заказов. Попутно `.ToList().Count > 0` перечисляет весь каталог, хотя достаточно `Any()`. Ввод-вывод здесь синхронный.

### M4. Sync-over-async в обработчике счёта
`Controllers/InvoiceController.cs:22` - `rates.GetRateAsync("EUR").Result` внутри async-метода.
Чем кончится: поток пула блокируется на всё время HTTP-запроса к сервису курсов. Под нагрузкой или когда сервис курсов медленный, начинается thread pool starvation и растёт латентность всего API. Ошибки к тому же приходят обёрнутыми в `AggregateException`. Нужен `await`.

### M5. Конвертер валют сериализует все конвертации приложения глобальным lock вокруг сетевого вызова
`Services/CurrencyConverter.cs:15-17` - блокирующий `GetAwaiter().GetResult()` на HTTP-запросе выполняется внутри `lock` синглтона. Вызывающий код `Controllers/InvoiceController.cs:48` синхронный.
Чем кончится: в каждый момент времени во всём процессе идёт не больше одной конвертации. Остальные запросы `/total-in` занимают потоки пула и ждут на lock до 100 с (таймаут HttpClient по умолчанию) на каждый медленный ответ сервиса курсов. Итог: голодание пула и деградация всех эндпоинтов. Lock нужен только для счётчика, его заменяет `Interlocked.Increment`. `Convert` должен быть async.

### M6. Выгрузка для бухгалтерии не работает при стандартных именах EF и грузит всё в память
`Controllers/OrderExportController.cs:15` - в сыром SQL стоят `orders` и `status` без кавычек. В модели нет snake_case-конвенции, поэтому Npgsql-провайдер создаёт таблицу `"Orders"` и колонку `"Status"`. PostgreSQL приводит идентификаторы без кавычек к нижнему регистру, и запрос упадёт с `relation "orders" does not exist`.
`Controllers/OrderExportController.cs:14-24`: даже с исправленным SQL выгрузка по популярному статусу материализует до миллионов строк в список, затем в `StringBuilder`, затем в `byte[]`. Это три копии в памяти на запрос. Нужен LINQ-фильтр (заодно закрывает B1) и потоковая запись CSV в `Response.Body`.

### M7. P/Invoke к `libz` не загрузится в типовом рантайме и вызывается на каждый байт
`Services/Checksum.cs:7` - `DllImport("libz")`. На Linux загрузчик ищет `libz.so`. В runtime-образах обычно есть только `libz.so.1`, а симлинк `libz.so` ставит dev-пакет. На Windows `libz.dll` нет, и `uLong` там 32-битный, то есть сигнатура с `ulong` неверна.
Чем кончится: `DllNotFoundException`, и каждый запрос счёта отвечает 500. Если библиотека всё же найдётся, `Services/Checksum.cs:14-18` делает один нативный вызов на каждый байт PDF. В BCL есть управляемый `System.IO.Hashing.Crc32` (пакет System.IO.Hashing), P/Invoke здесь не нужен.

### M8. «PDF» не является валидным PDF
`Services/PdfRenderer.cs:13-22` - в файл пишутся сигнатура `%PDF-1.7` и следом plain text. Нет объектов, xref и trailer.
Чем кончится: клиент получает `application/pdf`, который просмотрщики не откроют или покажут как повреждённый. Бухгалтерия счёт использовать не сможет. Это заглушка, а в MR она заявлена как готовая функциональность.

### M9. Список рассылки: неограниченный `pageSize`, выборка целых сущностей с фото
`Controllers/CustomerReportsController.cs:41-49`:
- `pageSize` не ограничен сверху. `?pageSize=100000` отдаёт всю базу за один запрос, вместе с B2 это массовая выгрузка PII.
- Отрицательные `page`/`pageSize` и переполнение `page * pageSize` дают отрицательный OFFSET/LIMIT, PostgreSQL отвечает ошибкой, клиент получает 500.
- `ToListAsync()` материализует целые `Customer`, включая `Photo` (`byte[]`) и `Notes`, хотя нужен только email. 500 фото на страницу означают мегабайты с БД ради строк, да ещё с трекингом. Нужна проекция `Select(c => c.Email)` до `ToListAsync`.

## Minor

### m1. Итог счёта и строки считаются двумя запросами к БД
`Controllers/InvoiceController.cs:24-28,33` - `rows` объявлен как `IEnumerable` поверх `IQueryable` с отложенным выполнением. `Sum` на строке 28 выполняет запрос, `Render` на строке 33 выполняет его второй раз.
Чем кончится: лишний round-trip на каждый счёт. Если строки заказа поменяются между двумя запросами, итог в PDF разойдётся с суммой строк. Нужно материализовать один раз через `ToListAsync`.

### m2. Контрольная сумма считается не по отдаваемому файлу
`Controllers/InvoiceController.cs:35-39` - CRC считается по `pdf` без первых 8 байт, а в ответе отдаётся полный `pdf`.
Чем кончится: потребитель, который сверяет CRC скачанного файла, всегда получит несовпадение. Заголовок файла контрольной суммой не защищён. Контракт заголовка `X-Invoice-Checksum` нигде не описан.

### m3. `Task.Run` для CPU-работы в ASP.NET Core
`Controllers/InvoiceController.cs:37` - перенос вычисления на другой поток пула ничего не даёт: запрос всё равно ждёт результат, а переключение потока стоит накладных расходов. Считать нужно синхронно.

### m4. Необработанные ошибки сервиса курсов и нулевой курс
`Services/RateService.cs:14-15` - `dto!.Rate`: на ответ `null` будет `NullReferenceException`. Если курс равен 0, деление в `Services/CurrencyConverter.cs:19` и в `Controllers/InvoiceController.cs:26` бросит `DivideByZeroException`. Таймаут и повторы для HttpClient не настроены (`Program.cs:11-12`). Все эти случаи клиент видит как 500 без понятной причины.

### m5. Непроверенная валюта подставляется в путь запроса к внешнему сервису
`Services/RateService.cs:14` + `Controllers/InvoiceController.cs:44` - `currency` из query string без валидации попадает в относительный URL `rates/{currency}`. Значения вроде `../admin` или `x?y=` уводят запрос на другой путь хоста курсов, `currency=null` даёт `rates/`. Нужна проверка по белому списку ISO-4217.

### m6. Загрузка клиента целиком ради имени
`Controllers/CustomerReportsController.cs:16` - `FirstOrDefaultAsync` без проекции тянет `Photo` и `Notes`. Для сводки нужны только `Id` и `Name`.

### m7. `DateTime? since` из query сравнивается с UTC без учёта Kind
`Controllers/CustomerReportsController.cs:14,24,26` - при привязке модели значение со смещением (`...Z`/`+03:00`) приходит с `Kind=Local`, без смещения - с `Kind=Unspecified`. `CreatedAt` из `timestamptz` приходит с Kind Utc. Сравнение `DateTime` не учитывает Kind, поэтому на хосте с TZ не UTC окно сдвинется на величину смещения. Когда фильтр перенесут в БД (см. B3), Npgsql 6+ для `timestamptz` отклонит не-UTC `DateTime` исключением. Нужно явно приводить к UTC или принимать `DateTimeOffset`.

### m8. `CountAsync` вместо `AnyAsync` для проверки существования
`Controllers/CustomerReportsController.cs:36-37` - подсчёт всех заказов клиента там, где хватит `EXISTS`. Для клиентов с большим числом заказов это лишняя работа БД.

### m9. CSV и PDF зависят от культуры сервера и не экранируют поля
`Controllers/OrderExportController.cs:22` - `{o.Total}` форматируется в текущей культуре, в ru-RU разделителем будет запятая. `Number` пишется без экранирования: `;` или перевод строки ломают строку CSV, значения на `=`, `+`, `-`, `@` в Excel исполняются как формулы (CSV injection). `Services/PdfRenderer.cs:18-19` - суммы тоже в текущей культуре. Нужен `CultureInfo.InvariantCulture` и экранирование полей.

### m10. `CancellationToken` не пробрасывается в запросы к БД и HTTP
Все контроллеры (`CustomerReportsController.cs`, `InvoiceController.cs`, `OrderExportController.cs`) и `Services/RateService.cs:12`: если клиент разорвал соединение, тяжёлые запросы (B3, M6) продолжают грузить БД до конца.
