# Ревью MR: модуль возвратов

Контекст нагрузки: 2 млн заказов, ~15 тыс. возвратов в месяц (~45 тыс. за 90 дней), ~400 RPS, список возвратов открывают операторы поддержки постоянно.

Итого: 5 blocker, 4 major, 8 minor.

## Blocker

### B1. N+1 через lazy loading в списке возвратов
- **Где:** `Returns/ReturnsController.cs:27-33`, `Returns/ReturnMapper.cs:10-19`, `Program.cs:12`
- **Что не так:** список грузит сущности `ReturnRequest` целиком (с трекингом, без проекции), а `ReturnMapper.ToListItem` для каждой строки трогает `r.Lines`, `r.Order`, `r.Order.Lines`, `r.Order.Customer`. С `UseLazyLoadingProxies()` это до 4 отдельных запросов на каждую заявку. Колонки вроде `Reason` и все строки заказа тянутся, хотя в DTO нужны имя клиента, сумма и количество.
- **Чем кончится:** на странице по умолчанию (50) это 1 + 200 запросов, на `pageSize=100` 1 + 400 запросов. Страницу постоянно открывают операторы, так что она выедает пул соединений Npgsql (по умолчанию 100) и через него роняет latency всего API на 400 RPS. Нужна одна проекция `Select(r => new ReturnListItem(..., r.Order.Customer.Name, r.Lines.Sum(...), сумма через join с OrderLines))` с `AsNoTracking`. Lazy proxies лучше не включать глобально: из-за них N+1 не виден в коде.

### B2. Двойной возврат денег: нет идемпотентности и защиты от конкурентного одобрения
- **Где:** `Returns/ReturnService.cs:45-54`
- **Что не так:** статус проверяется в памяти (`Status != Requested`), потом идёт внешний вызов `RefundAsync`, и только затем `SaveChangesAsync`. Concurrency token нет, условного UPDATE нет, idempotency key в шлюз не передаётся.
- **Чем кончится:** (а) два оператора или двойной клик одобряют одновременно: оба читают `Requested`, шлюз делает два возврата денег. (б) `RefundAsync` прошёл, а `SaveChangesAsync` упал (таймаут БД, отмена запроса): деньги ушли, заявка осталась `Requested`, повторное одобрение вернёт деньги второй раз. Прямые финансовые потери. Нужно заранее перевести заявку в промежуточный статус условным апдейтом с проверкой статуса (или xmin/RowVersion) и передавать в шлюз idempotency key по id заявки.

### B3. Валидация количества не ограничивает возврат купленным
- **Где:** `Returns/ReturnValidator.cs:29`
- **Что не так:** условие `line.Quantity <= 0 || orderLine.Quantity < 0`. Вторая половина всегда ложна, поэтому `line.Quantity > orderLine.Quantity` не проверяется. Дубли одной `OrderLineId` внутри заявки тоже не отсекаются.
- **Чем кончится:** клиент купил 1 шт., а заявку подаёт на 100 шт. (или повторяет одну позицию 20 раз). `ApproveAsync` (`ReturnService.cs:49-50`) посчитает сумму от присланного количества и вернёт через шлюз больше, чем было оплачено. Проверка должна быть `line.Quantity > orderLine.Quantity`, с суммированием по одинаковым `OrderLineId`.

### B4. Нет аутентификации и авторизации на эндпоинтах с деньгами и ПДн
- **Где:** `Returns/ReturnsController.cs:8-53`, `Program.cs:8-34`
- **Что не так:** в пайплайне нет ни `[Authorize]`, ни `AddAuthentication`/`UseAuthorization`. Tenant определяется только по заголовку Host (`TenantFilter.cs:10`), а его задаёт клиент.
- **Чем кончится:** любой, кто знает хост тенанта, может одобрить возврат (`/approve`, вызывает возврат денег), отклонить чужие заявки и выгрузить список с именами клиентов. `Create` не проверяет, что заказ принадлежит вызывающему клиенту, поэтому можно завести возврат по чужому заказу. Нужна схема auth, роль оператора на `List`/`Approve`/`Reject` и проверка владельца заказа на `Create`.

### B5. sync-over-async в глобальном фильтре на каждом запросе
- **Где:** `Infrastructure/TenantFilter.cs:11`
- **Что не так:** `tenants.ResolveAsync(...).Result` в синхронном `IActionFilter`. Фильтр зарегистрирован глобально (`Program.cs:28`), поэтому на каждом запросе к любому контроллеру поток пула блокируется на время запроса к БД.
- **Чем кончится:** на 400 RPS при любом росте latency БД потоки пула заканчиваются, наступает thread pool starvation, и API останавливается целиком, включая запросы, не связанные с возвратами. Нужен `IAsyncActionFilter` с `await`.

## Major

### M1. Сбой уведомления после коммита превращает успешную операцию в 500
- **Где:** `Notifications/ReturnNotifier.cs:18-26`; вызовы в `Returns/ReturnService.cs:39, 56, 68`
- **Что не так:** ловится только `HttpRequestException`. Таймаут HttpClient (`TaskCanceledException`, по умолчанию через 100 с) и отмена пролетают наружу. Уведомление отправляется синхронно в запросе, уже после `SaveChangesAsync`.
- **Чем кончится:** если notify-сервис тормозит, одобрение или создание висит до 100 с, а потом возвращает 500, хотя деньги уже возвращены или заявка уже создана. Клиент повторяет `Create` и получает «уже есть заявка», оператор повторяет `Approve` и получает 404. Операторы решат, что операция не прошла. Уведомление нужно выносить из пути запроса (outbox или очередь), а до этого хотя бы задать короткий таймаут и не пропускать исключение наружу.

### M2. Гонка при создании: две активные заявки по одному заказу
- **Где:** `Returns/ReturnValidator.cs:21`, `Returns/ReturnService.cs:36-37`, `Migrations/20260910120000_AddReturns.cs:45`
- **Что не так:** «одна активная заявка на заказ» проверяется чтением перед вставкой. Уникального ограничения в БД нет: `IX_ReturnRequests_OrderId` не уникальный и не частичный.
- **Чем кончится:** два параллельных POST (двойной сабмит, ретрай клиента) создают две заявки по одному заказу. Если одобрить обе, товар возвращается дважды. Нужен частичный уникальный индекс `OrderId WHERE Status <> Rejected` и обработка нарушения уникальности.

### M3. Сверка: линейный поиск в цикле, O(n*m) по строкам
- **Где:** `Returns/ReturnsReconciliationJob.cs:32, 46`
- **Что не так:** `gatewayIds` имеет тип `List<string>`, и `Contains` вызывается внутри цикла по `refunded`.
- **Чем кончится:** за 90 дней с обеих сторон около 45 тыс. записей, это порядка 10^9 сравнений строк за прогон. Десятки секунд CPU на том же хосте, который держит 400 RPS, и время растёт квадратично с объёмом. Нужен `HashSet<string>` (`ToHashSet()`).

### M4. Сверка не ловит опасное направление расхождения
- **Где:** `Returns/ReturnsReconciliationJob.cs:37-51`
- **Что не так:** сверка проверяет только «у нас Refunded, в шлюзе нет». Обратное направление не проверяется: в шлюзе есть возврат, а заявка у нас не `Refunded` или не существует. Именно такое состояние создаёт сценарий B2(б), когда деньги ушли, а `SaveChanges` упал.
- **Чем кончится:** реальные потерянные деньги сверка не покажет, отчёт будет «0 missing». Нужно сопоставлять в обе стороны, по `RefundExternalId` и `OrderId`.

## Minor

### m1. Новый HttpClient на каждый вызов шлюза
- **Где:** `Returns/RefundGateway.cs:12, 21`
- **Что не так:** `new HttpClient` на каждый вызов, при этом `RefundGateway` зарегистрирован синглтоном и читает `IConfiguration` при каждом вызове. Таймаут не задан (100 с по умолчанию), политики ретраев нет.
- **Чем кончится:** при текущем темпе (~500 возвратов в день) исчерпание сокетов маловероятно, но каждый вызов открывает новое TCP/TLS-соединение, и при росте нагрузки или пачке одобрений копятся сокеты в TIME_WAIT. Лучше typed client через `AddHttpClient<RefundGateway>` с явным таймаутом.

### m2. Проверка наличия через счёт
- **Где:** `Returns/ReturnValidator.cs:21`
- **Что не так:** `CountAsync(...) > 0` вместо `AnyAsync`.
- **Чем кончится:** БД считает все подходящие строки вместо остановки на первой. На индексе `OrderId` строк мало, так что потери небольшие, но это лишняя работа на каждом создании.

### m3. Линейный поиск строки заказа в цикле
- **Где:** `Returns/ReturnMapper.cs:12`, `Returns/ReturnService.cs:50`
- **Что не так:** `Order.Lines.First(...)` вызывается внутри цикла по строкам возврата. Если строки нет (данные разошлись), `First` бросает исключение.
- **Чем кончится:** при потолке в 20 позиций цена небольшая, но одна битая заявка роняет всю страницу списка с 500. Решается вместе с B1 переносом суммы в SQL-проекцию.

### m4. Индекс не покрывает сортировку списка
- **Где:** `Migrations/20260910120000_AddReturns.cs:44`, `Returns/ReturnsController.cs:23-30`
- **Что не так:** индекс `(TenantId, Status)`, а запрос сортирует по `CreatedAt DESC` с offset-пагинацией. Без фильтра по статусу сортируются все заявки тенанта.
- **Чем кончится:** таблица растёт примерно на 180 тыс. строк в год, поэтому время отдачи списка будет расти, а глубокие страницы деградируют из-за OFFSET. Нужен индекс `(TenantId, Status, CreatedAt DESC)` плюс `(TenantId, CreatedAt DESC)`, в перспективе keyset-пагинация.

### m5. Запрос tenant в БД на каждый HTTP-запрос без кэша
- **Где:** `Infrastructure/TenantService.cs:20-23`, `Infrastructure/TenantFilter.cs:11`
- **Что не так:** соответствие host -> tenant почти не меняется, но читается из БД на каждом запросе.
- **Чем кончится:** 400 лишних round-trip в секунду и лишние соединения из пула. Лучше `IMemoryCache` с TTL.

### m6. Окно возврата считается по локальному времени сервера
- **Где:** `Returns/ReturnPolicy.cs:9`
- **Что не так:** `DateTime.Now` (local) сравнивается с `CreatedAt` из `timestamptz` (UTC). Внедрённый `IClock` при этом не используется.
- **Чем кончится:** на сервере с TZ, отличной от UTC, окно сдвигается на величину смещения, и заявку на границе 14 дней примут или отклонят неверно. Политику нельзя протестировать с фиксированным временем. Нужен `clock.UtcNow`.

### m7. Сверка стартует при каждом запуске пода и на каждой реплике
- **Где:** `Returns/ReturnsReconciliationJob.cs:13-25`
- **Что не так:** цикл `do/while` выполняет сверку сразу при старте, дальше раз в 24 ч от старта, а не ночью. Координации между репликами нет.
- **Чем кончится:** каждый деплой и рестарт запускает тяжёлую сверку (см. M3) в дневной пик. На N репликах она идёт N раз и шлёт в шлюз N запросов за 90 дней. Весь ответ шлюза (`RefundGateway.cs:22`) при этом одним куском грузится в память без пагинации, и если шлюз режет ответ страницей, остальное пойдёт в ложные «missing».

### m8. Location у созданной заявки указывает на список
- **Где:** `Returns/ReturnsController.cs:43`
- **Что не так:** `CreatedAtAction(nameof(List), new { id })` даёт `Location: /api/returns?id=N`. Это список с игнорируемым параметром, а не ресурс, GET по id нет.
- **Чем кончится:** клиент, который идёт по Location, получает первую страницу списка вместо созданной заявки.
