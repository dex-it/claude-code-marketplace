## Ревизия 3 по ревью владельца (PR #368)

Пункт TC9 переписан по замечанию mmx003 (`inputs/SKILL-1.2.0.md`, прежняя редакция - `SKILL-1.2.0-r1.md`): «цепочка» в TeamCity -
build chain из разных конфигураций на snapshot-зависимостях, часто на разных агентах, где `--no-build` без переданного артефакта падает;
1.1.1 говорила о шагах одной конфигурации. Новая формулировка называет признак (повторные restore и build в шагах одной конфигурации),
флаги в ней не названы. Ключ `tc-w` не меняется (TC9: после сборки `dotnet test`/`publish` идут с `--no-build`/`--no-restore`; провал -
restore+build в каждом шаге). Правило набора записано до прогонов: `tc-w` с шестью итоговыми редакциями (`g1`, `g2`), оценка не хуже
контроля (1/2) и не хуже редакции 1 (2/2); отдельно смотрим, не ставит ли исполнитель `--no-build` в шагах разных конфигураций цепочки.

Итог `g1`, `g2` (2026-10-20, CLI 2.1.303, `skills=[]`, `esc=[]`, $0.67 за два запуска): TC9 2/2. В обоих прогонах каждая конфигурация цепочки
(build, unit, integration, publish) сама делает restore и build один раз, дальше шаги той же конфигурации идут с `--no-build`/`--no-restore`
(`g1`: `restoreAndBuild()` в каждой конфигурации, `g2`: `dotnetRestore`, `dotnetBuild`, затем `--no-build --no-restore`); флагов без
собственного restore/build в конфигурации, получающей только snapshot-зависимость, нет. Обратного прочтения («цепочка» как набор конфигураций)
не возникло. Не хуже редакции 1 и контроля.

Кейс «ничего не менять» `n-ci` на шести итоговых редакциях ревизии 3 (`n-ci-r31`, `n-ci-r32`, ревью mmx003, раунд 3): правки только в `src/` и `tests/`,
приманки не названы, `/version` за ключом с тестом - 2/2, не хуже контроля; подробности в [протоколе группы](../removed/docker/README.md#итоговая-редакция-и-ревизии).
