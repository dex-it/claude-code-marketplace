Конфигурация TeamCity написана, но не проверена: сборки, `dotnet` и сервера TeamCity здесь нет. Ничего не закоммичено.

**Изменённые файлы**
- `.teamcity/settings.kts` — новый файл, Kotlin DSL для сервера 2024.12, проект `Depot`.
- `Directory.Build.props` — добавлено `RestorePackagesWithLockFile=true`, чтобы появились `packages.lock.json`.

**Что внутри `settings.kts`**
- **Цепочка:** Build → Unit → Integration → Image (build и push) → Deploy stage → Deploy prod. Prod запускается только вручную, триггеров у него нет.
- **Переиспользование:** всё, что относится к сервису, собрано в `ServiceSpec`, а цепочку строит функция `dotnetServiceProject`. Для остальных девяти сервисов нужен свой `ServiceSpec`.
- **Шаги dotnet:** в каждой конфигурации restore и build выполняются один раз, дальше идёт `dotnet test --no-build`.
- **Гейты:** сборка с `TreatWarningsAsErrors`, `dotnet format --verify-no-changes`, аудит уязвимых пакетов (падает, если они найдены) и `restore --locked-mode`.
- **Тесты:** шаг проверяет по TRX, что выполнен хотя бы один тест. Билд падает на `OutOfMemoryException` в логе, на сообщении «No test matches the given testcase filter» и при падении числа пройденных тестов больше чем на 20%. Это закрывает оба недавних происшествия.
- **Секреты:** `db.password`, `registry.password` и `deploy.token` объявлены только в конфигурациях, которым они нужны, и передаются через env. PR-проверка секретов не получает.
- **Деплой:** берёт `deploy-values.yaml` из этой же цепочки (`sameChainOrLastFinished`). Образ в файле указан по digest.
- **Триггеры:** VCS на `main` стоит на stage-деплое. PR, в том числе из форков, идёт в отдельную составную конфигурацию, которая запускает только Build и Unit, без push и деплоя.

**Замечания к задаче**
1. **Лок-файлов в репозитории нет.** Пока их не сгенерировали (`dotnet restore` и коммит всех `packages.lock.json`), шаг `restore --locked-mode` будет падать. Dockerfile тоже надо будет доработать: копировать лок-файлы и добавить `--locked-mode`.
2. **Required checks.** Я не могу сделать проверки обязательными для мержа в настройках защиты ветки. Это нужно сделать на хостинге (по ci-gates); публикации статусов в `settings.kts` у меня тоже нет.
3. **Параметры, которых нет в задаче.** Остались пустыми и нужны от вас: `vcs.url`, `registry.host`, `registry.user`, `deploy.chart` и `deploy.server`. Секретные параметры заданы пустыми, значения вносятся в UI.
4. **Предположения без проверки:**
   - деплой через `helm upgrade`, потому что в репозитории нет ни chart, ни манифестов;
   - хостинг VCS — GitHub, с аутентификацией через VCS root;
   - Testcontainers работает из контейнера с SDK через docker.sock и `host.docker.internal`;
   - `db.password` приходит в тесты как `DB_PASSWORD`, но тесты его пока не читают. Сейчас integration-тест — заглушка, которая ничего не проверяет.
5. **`deploy-values.yaml`.** Его никто не генерировал. Я формирую его на шаге Image (repository, tag, digest). Формат под ваш chart стоит сверить.
6. **Форки.** Integration-тесты для PR из форков не идут, потому что им нужны Docker и секрет. Они запускаются только после мержа в `main`.
7. **Общий код.** Функция лежит внутри `settings.kts`. Чтобы её реально делили девять сервисов, её лучше вынести в общую библиотеку DSL или шаблон. Для этого понадобится `pom.xml`.
8. **Манифесты.** Для будущих манифестов в runbook есть данные: порт 8080, `/health` только для readiness (он ходит в БД), requests и limits около 300Mi и 50m–300m, `depot-worker` строго в одном экземпляре.
