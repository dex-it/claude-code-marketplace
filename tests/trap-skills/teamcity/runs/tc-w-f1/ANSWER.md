Конфигурация TeamCity как код написана, но не проверена. Компиляции Kotlin DSL, сборки и запуска здесь не было, потому что доступен только git. Ничего не закоммичено.

**Файлы**
- `.teamcity/settings.kts` (новый). Проект `Depot` (id `Depot`), в нём один вызов `dotnetServiceChain(...)` с параметрами Depot.
- `.teamcity/DotnetServiceChain.kt` (новый). Общая цепочка: Build, затем Unit и Integration, затем Push, затем Stage, затем Prod. Prod запускается только вручную.
- `.teamcity/pom.xml` (новый). Нужен, чтобы `.kt` рядом с `settings.kts` компилировался. Версию Kotlin он берёт из родительского pom.
- `Directory.Build.props`. Добавлен `RestorePackagesWithLockFile=true`, чтобы работал `--locked-mode`.

**Что учтено из дисциплины и происшествий**
- **Шаги `dotnet`.** Везде `restore --locked-mode`, затем `build --no-restore`, затем `test --no-build --no-restore`.
- **Тесты, которые не запускались.** Unit и Integration падают, если выполнено меньше одного теста. Фильтры `Category=Contracts` и `Category=Integration`.
- **`OutOfMemoryException`.** Любая конфигурация падает, если в логе есть эта строка. То же для `Test host process crashed`.
- **Гейты.** В Build есть `dotnet format --verify-no-changes` и аудит уязвимостей (`dotnet list package --vulnerable`). Аудит падает и когда результата нет совсем, например при недоступном источнике пакетов.
- **Секреты.**
  - `db.password` есть только в Integration.
  - `registry.password` есть только в Push.
  - `deploy.token` есть только в Stage и Prod.
  - Все три объявлены как password-параметры, значения в репозитории не хранятся.
  - Push и деплои не запускаются для PR.
- **Триггеры.** PR (включая форки) запускает составную конфигурацию `Verify`, она доходит только до тестов. Stage запускается по VCS только на `main`.
- **Деплой.** Stage и Prod берут `deploy-values.yaml` из Push той же цепочки (`sameChainOrLastFinished`). Образ не пересобирается: Push кладёт его тег в этот файл.

**Замечания к задаче**
1. **Лок-файлов `packages.lock.json` в репозитории нет.** Я не мог их сгенерировать, поэтому первый запуск Restore упадёт. Нужно выполнить `dotnet restore` локально и закоммитить лок-файлы. Для Dockerfile лок-файлы тоже стоит копировать в слой restore.
2. **Откуда `deploy-values.yaml`, не сказано.** В репозитории его нет. Push генерирует минимальный файл (`image.repository` и `image.tag`). Нужна ваша схема файла.
3. **Инструмент деплоя в задаче не назван.** Я предположил `helm upgrade --install --atomic`. Параметры `deploy.chart` и `deploy.apiserver` пустые, `deploy.namespace` по умолчанию `depot-stage` и `depot-prod`. Токен передаётся через `HELM_KUBETOKEN`, а не аргументом.
4. **Параметры реестра.** Для `registry.url` стоит заглушка `registry.example.invalid`, `registry.user` пустой. Значения password-параметров нужно ввести в UI. Из-за пустого значения в DSL проверьте, что первая синхронизация не затрёт уже заданные секреты.
5. **PR из форков.**
   - Я допустил, что репозиторий на GitHub (`authType = vcsRoot()`, `EVERYBODY`). Если это GitLab или другой хостинг, блок `pullRequests` нужно заменить.
   - Код из форка исполняется в Integration, где доступен `db.password`. Это должен быть пароль одноразовой БД Testcontainers, не используемый нигде больше.
   - Тесты должны читать пароль из `POSTGRES_PASSWORD`. Нынешние тесты — заглушки и его не читают.
6. **Повторное использование.** `.kt` лежит в репозитории Depot. Для остальных девяти сервисов его нужно вынести в общий репозиторий или Maven-артефакт и подключить в `pom.xml`. Копировать файл девять раз не стоит.
7. **Версия Kotlin.** Её определяет родительский pom, номер я не проверял.
8. **Дублирование сборки.** Unit и Integration сами делают restore и build, потому что агенты могут быть разными, а `obj` содержит абсолютные пути. Это расходует время агента, зато надёжно.
9. **Обязательные проверки для мержа.** Required checks в защите ветки настраиваются на стороне хостинга, из репозитория их не включить. Нужно пометить обязательным `Verify`.
