Конфигурация TeamCity как код готова в рабочем дереве, не закоммичена. Я ничего не собирал и не запускал: Kotlin DSL не компилировался, имена API 2024.12 написаны по памяти и могут не сойтись.

**Изменённые файлы** (все новые):
- `.teamcity/settings.kts` — проект `Depot`. Это один вызов `servicePipeline(ServiceSpec(...))`.
- `.teamcity/ci/ServicePipeline.kt` — общая цепочка. Для каждого из девяти остальных сервисов нужен свой `ServiceSpec` (имя, проекты тестов, фильтры, образ, чарт).
- `.teamcity/pom.xml` — нужен, чтобы `settings.kts` видел пакет `ci`.

**Что в цепочке**
- Порядок: Build → Unit и Integration → Image (сборка и push) → Deploy stage → Deploy prod. Prod без триггеров, запускается кнопкой Run.
- Unit — тесты категории `Contracts`, Integration — `Integration`.
- Защита от двух недавних происшествий: билд падает, если тестов меньше одного, и падает, если в логе есть `System.OutOfMemoryException`, даже при нулевом коде `dotnet test`.
- Image строит образ из Dockerfile, пушит его и пишет `deploy-values.yaml` с репозиторием, тегом (ревизия) и digest. Файл публикуется как артефакт. Оба деплоя берут его и образ из той же цепочки.
- Триггеры: VCS на `main` запускает цепочку до stage. PR, включая форки, запускают отдельную проверку `Verify` (Build + Unit + Integration).
- Параметры `db.password`, `registry.password`, `deploy.token` объявлены как пароли с пустым значением. Реальные значения нужно задать на сервере, в репозиторий они не попадают.

**Замечания к задаче**
1. Я сам выбрал и вписал значения-заглушки с `TODO`: адрес репозитория, реестр и путь образа, Helm-чарт, адрес сервера TeamCity в `pom.xml`. Параметры `registry.user` и `deploy.{stage,prod}.apiserver` тоже добавил я и оставил пустыми. В задаче способ деплоя не описан, в репозитории нет ни чарта, ни манифестов. Я исходил из Helm с `--kube-token`; уточните, так ли это.
2. Хост PR-проверки я принял за GitHub (`pullRequests` с провайдером github). Если хост другой, этот блок надо заменить.
3. Сборка форков и секреты:
   - Код из форка может прочитать `db.password`, потому что его использует Integration, а Integration входит в `Verify`. Для PR нужен отдельный одноразовый тестовый пароль.
   - Секреты реестра и деплоя PR недоступны: Image, Stage и Prod запускаются только с `main`. Но это держится на триггере. Ручной запуск Stage или Prod с чужой ветки ничем не заблокирован, ограничьте права на запуск в TeamCity.
   - Тесты пока не читают `DB_PASSWORD`: интеграционный тест сейчас заглушка (`Assert.Equal(OK, OK)`), хотя README говорит про Postgres. Фильтр числом тестов пройдёт, а реальной проверки нет.
4. Шаг `dotnet publish` вынесен в Dockerfile, отдельно в CI я его не повторял. Build и тесты идут в контейнере `sdk:8.0.404`. Integration монтирует `docker.sock` и использует `--network host` для Testcontainers. Это надо проверить на реальных агентах.
5. Из `docs/runbook.md`: рядом с API работает `depot-worker`, и экземпляр должен быть ровно один. Чарт должен это гарантировать, например `replicas: 1` со стратегией `Recreate`. В `deploy-values.yaml` я это не прописывал, потому что чарта нет.
6. Для переиспользования лучше вынести `.teamcity/ci` в общий репозиторий или Maven-артефакт. Копировать его в девять репозиториев не стоит.
