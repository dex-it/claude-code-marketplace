Конфигурацию TeamCity написал, но не компилировал и не запускал. Сборок и сети нет, так что DSL и `pom.xml` не проверены.

**Файлы (новые, в `.teamcity/`, не закоммичены):**
- `settings.kts` — проект `Depot`, версия 2024.12. Только вызывает общую функцию.
- `DotnetServicePipeline.kt` — общая схема для всех .NET-сервисов. Сервис описывается через `ServiceSpec`. Цепочка: Build → Unit → Integration → Image → Stage → Prod.
- `pom.xml` — нужен, чтобы TeamCity собрал `.kt` рядом с `settings.kts`.

**Как закрыты пункты задачи:**
- **Нет повторных restore и build:** в каждой конфигурации restore и build выполняются один раз, дальше тесты идут с `--no-build --no-restore`.
- **Тесты, которые не запустились:** в обеих тестовых конфигурациях сборка падает, если выполнено меньше одного теста (`TEST_COUNT < 1`). Фильтры: `Category=Contracts` и `Category=Integration`.
- **`System.OutOfMemoryException`:** во всех конфигурациях сборка падает, если эта строка есть в логе, даже при коде возврата 0.
- **Минимум гейтов:** в Build есть `dotnet format --verify-no-changes` и аудит уязвимостей через `dotnet list package --vulnerable --include-transitive`. Аудит падает по тексту вывода, потому что сама команда всегда возвращает 0.
- **Секреты:** `db.password`, `registry.password` и `deploy.token` — параметры типа password с пустым значением. Пароль реестра передаётся в `docker login --password-stdin`, токен деплоя — через `HELM_KUBETOKEN`, чтобы не светиться в командной строке.
- **Деплой:** Stage и Prod зависят от Image через snapshot и берут `deploy-values.yaml` из той же цепочки (`sameChainOrLastFinished`). Prod запускается только вручную, без триггеров.
- **Триггеры:**
  - Push в `main` запускает Stage, а он тянет за собой всю цепочку.
  - PR (`pull/*`, фильтр авторов `EVERYBODY`, то есть и форки) запускает цепочку до Integration.
  - Image, Stage и Prod начинаются с проверки, что ветка — `main`.

**Замечания к задаче:**
1. **Лок-файлов нет.** В репозитории нет `packages.lock.json`, поэтому `dotnet restore --locked-mode` включить нельзя: он упадёт. Нужно сгенерировать лок-файлы (`RestorePackagesWithLockFile`), закоммитить их и добавить `--locked-mode` в Restore. По `ci-gates` это пока не выполнено.
2. **Обязательность проверок для мержа.** Required checks в защите ветки настраиваются на стороне Git-хостинга, из репозитория этого не сделать. Нужно отметить Build, Unit и Integration обязательными. Для статусов в PR, скорее всего, ещё понадобится `commitStatusPublisher` с токеном.
3. **Что я придумал сам.** В репозитории нет Helm-чарта и сведений о способе деплоя.
   - Я взял `helm upgrade --install --atomic` с параметрами `deploy.chart`, `deploy.apiserver` и `deploy.namespace` (`depot-stage`, `depot-prod`).
   - Также пустые параметры `registry.url`, `registry.user` и `env.DB_PASSWORD`. Как интеграционные тесты читают пароль БД, неизвестно.
   - Эти параметры и значения секретов нужно задать на сервере (credentialsJSON).
4. **PR из форков.** Это риск: чужой код выполняется на агентах с Docker и в сборке, где доступен `db.password`. Нужен отдельный пул агентов и тестовый пароль БД, не равный реальному. Настройки TeamCity для PR-веток нужно брать из `main`, иначе PR сможет подменить `settings.kts`.
5. **Девять других сервисов.** Функция лежит в репозитории Depot. Чтобы использовать её в остальных, вынесите `DotnetServicePipeline.kt` в общий репозиторий или Maven-артефакт, а в каждом сервисе оставьте только `settings.kts` со своим `ServiceSpec`.
6. **Нужна проверка.** `dotnet format` на существующем коде может упасть, а точные имена свойств DSL (например `failOnMetricChange`, `pullRequests`) нужно проверить на сервере 2024.12.
7. **Мелочи.**
   - Тег образа — номер сборки, он не привязан к дайджесту.
   - `depot-worker` должен быть ровно в одном экземпляре (`runbook.md`). `deploy-values.yaml` это не учитывает, это нужно решить в чарте.
