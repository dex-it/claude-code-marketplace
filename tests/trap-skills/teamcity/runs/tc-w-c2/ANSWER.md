Конфигурацию TeamCity как код я написала, но ничего не компилировала и не запускала: Maven, TeamCity и сети нет. Kotlin DSL и `pom.xml` проверены только чтением. Ничего не закоммичено.

**Новые файлы**
- `.teamcity/settings.kts` — проект `Depot`, версия 2024.12. Содержит один вызов `servicePipeline(ServiceSpec(...))`.
- `.teamcity/ServicePipeline.kt` — общая схема цепочки. Для остальных девяти сервисов нужен только свой `ServiceSpec`. Для переиспользования между репозиториями этот файл лучше вынести в общую DSL-библиотеку.
- `.teamcity/pom.xml` — Maven-обвязка DSL.

**Цепочка**
1. Build: restore и build.
2. Unit-тесты (`Category=Contracts`) и integration-тесты (`Category=Integration`), параллельно.
3. Образ и push, затем `deploy-values.yaml` с репозиторием, тегом и дайджестом. Он публикуется как артефакт.
4. Деплой на stage — автоматически на `main`.
5. Деплой на prod — без триггеров, запускается вручную.

Деплой берёт `deploy-values.yaml` и образ из этой же цепочки (`sameChainOrLastFinished`), а не «последний успешный».

**Защита от недавних происшествий**
- В тестовых конфигурациях билд падает, если тестов меньше одного.
- Билд падает на тексте `System.OutOfMemoryException`, `Test host process crashed` и `No test is available`.
- `dotnet test` может вернуть 0, но эти условия всё равно сделают билд красным.

**Триггеры и параметры**
- VCS-триггер стоит на всех ветках для build и тестов, а PR (включая форки) собираются через `pullRequests`.
- Push и деплой идут только с основной ветки: в триггере и в скрипте (проверка `branch.is_default`).
- `db.password` задан только в integration-конфигурации.
- `registry.password` задан только в push-конфигурации.
- `deploy.token` задан только в деплое.
- Все три — параметры типа password с пустыми значениями. Заполнить их нужно в UI или через `credentialsJSON`.

**Замечания к задаче**
1. В репозитории нет чарта, манифестов и описания способа деплоя. Я предположила `helm upgrade --install` по пути `deploy/chart` с параметрами `deploy.server` и `deploy.token`. Нужно уточнить реальный способ.
2. URL git-репозитория, адрес реестра и учётка VCS — заглушки (`git.example.com`, `registry.example.com`). Адрес сервера в `pom.xml` тоже заглушка (`teamcity.example.com`).
3. Тесты сейчас заглушки и пароль БД не читают. Я передаю его как `env.DB_PASSWORD`, но имя придётся согласовать с кодом тестов.
4. PR из форков запускают чужой код в integration-конфигурации, где лежит `db.password`. Значение должно быть одноразовым и использоваться только для Testcontainers. Лучше также включить в TeamCity подтверждение сборок от внешних авторов.
5. Токен деплоя один на stage и prod. Стоит завести отдельный токен для prod.
6. `depot-worker` должен работать в одном экземпляре (runbook), но в чарте этого не проверить. Нужна стратегия Recreate и replicas=1.
7. Тестовые конфигурации сами делают restore и build, потому что агенты разные и бинарники не передаются между ними.
8. Имена шагов и классов DSL (`dotnetRestore`, `failOnMetricChange`, `pullRequests`) написаны по памяти. Их нужно проверить на сервере через «Validate» или `mvn teamcity-configs:generate`.
