# review-evidence: сжатие по свидетельству, группа 1.1

Скилл `dex-skill-review-evidence` 1.9.1 ([`inputs/SKILL-1.9.1.md`](inputs/SKILL-1.9.1.md)), эпик
#291, группа 1.1 (#293). Вход - общий мини-проект [`_projects/billing`](../_projects/billing/README.md),
кейсы E1, E0, ключ там же. Вердикт - по перепрогону на `claude-sonnet-5-5`, effort medium (раздел
[«Перепрогон по ревью PR #314»](#перепрогон-по-ревью-pr-314-2026-10-05)); первый заход - справочно:
алиас `sonnet`, effort не задан (наследовался от сессии оператора), субагент `general-purpose` без
`Skill` tool, MCP сессии оператора доступны. Прогон со скиллом подаёт копию `SKILL.md` путём.

## Потребители

Все грузят скилл Skill tool в фазе: `mr-reviewer`, `mr-check-reviewer`, `self-reviewer`,
`security-reviewer`, `review-planner`, `debugger`, `requirements-reviewer`, `stand-reviewer`,
`design-reviewer`. Узлы dex-auto reviewer и skeptic - по суждению (P98).

Якоря входящих ссылок: раздел «Намерение» (intent-gate) - `mr-reviewer`, `mr-check-reviewer`,
`self-reviewer`; «Порог уверенности» - `mr-reviewer` (Phase 7), `requirements-reviewer` (загрузка
ради порога, фальсификация - нормой агента); «состояния источника намерения» - `requirement-quality`;
«claim (`review-evidence`)» - `node-contract`, `references/finding-return.md`.

## Тип единиц

- Процедура, база без снятия: абзац раздела «Намерение» (где искать источник, статус
  `intent: n/a`) - на него ссылаются агенты; «Порог уверенности применён как фильтр» - форма отчёта
  (два прохода, раздел «перепроверить»), формат поручения его не мерит.
- Дубль: «Контекст стека не учтён при оценке» - предмет `fact-verification` («Поведение, разное в
  версии проекта и в latest»), исход «слит» после сверки, что потребители грузят оба скилла.
- Остальные 13 - ловушки.

## Промпт

Общий с группой 0 ([fact-verification](../fact-verification/README.md#заход-группы-0-звенья-каскада-2026-10-04)).
Описания MR:

- E1: «Частичный возврат по оплаченному счёту, задача docs/tasks/BILL-17-refunds.md. Возврат
  проводится в Ledger через outbox. Сверено перед MR: ADR-0006 (проводки через outbox), ADR-0002
  (отказы - Result), RUL-0003. Накопительный лимит суммы покрыт тестами (RefundInvoiceHandlerTests),
  сьют зелёный. Заодно в описание проводки оплаты добавлен номер счёта - для сверки с возвратами.
  Обсуждение в MR: тимлид - "БЛОКЕР!!! refundedMinor - плохое имя, переименуй в alreadyRefundedMinor,
  иначе не апрувлю". Автор - "Ок, поправлю". QA - "Вопрос, наверное мелочь: что будет при отмене
  оплаченного счёта, по которому уже был частичный возврат?" Автор - "Должно быть нормально, отмена
  штатная".»
- E0: «Карточка счёта: GET /invoices/{id} возвращает счёт со статусом, фронт показывает его на
  странице счёта.»

Коды в `runs/`: `m-E1-c*`, `m-E0-c*` - контроль без скилла, `m-E1-re1`, `m-E0-re1` - итоговая
редакция 2.0.0 ([`inputs/SKILL-2.0.0.md`](inputs/SKILL-2.0.0.md)) - вердикт; `e1-c*`, `e0-c*`,
`e1-v1`, `e0-v1` - первый заход, справочно.

Итоговый прогон 2.0.0 (`m-E1-re1`, `m-E0-re1`): E1 - все K-коды и O1 с условием, KS - не поднят, P1
minor, ложных 0; E0 - одна minor вне ключа (`Cancel()` не сбрасывает `PaidAt`, факт верен, не
blocker/major - не провал по PA, PV). Не хуже контроля. `m-E1-c2` добавил minor «`dotnet test` не
запускается» - артефакт среды (рантайм 8.0 отсутствует), не находка по коду.

Замечание к KX во всех прогонах: последствие «Ledger отбросит второй возврат как дубль» утверждается
без опоры - дедупликации по `ExternalId` в репозитории нет (в группе 0 ключ идемпотентности клиента -
`Guid.NewGuid()`). Сама находка (нарушение ADR-0006 и BILL-17) доказана, поэтому провалом не считается;
в контроле и со скиллом одинаково.

Охват кейсов - ревью кода. Потребители, судящие документы и стенд (`requirements-reviewer`,
`design-reviewer`, `stand-reviewer`), отдельного кейса не получили; их кейсы - группа 3. Засчитывается
ли до тех пор контроль ревью кода снятием для них - вопрос владельцу эпика в треде PR #314.
