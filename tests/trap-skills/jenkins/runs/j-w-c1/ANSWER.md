Я добавил `Jenkinsfile` в корень репозитория. Ничего не запускал и не коммитил: Jenkins и сети здесь нет, так что синтаксис и работу пайплайна не проверял.

**Изменённые файлы:** только новый `Jenkinsfile`.

**Как устроен пайплайн**
- **Библиотека:** `depot-pipeline-lib@v1.4.0`. Это последний стабильный тег; `main` и `v1.5.0-rc1` брать нельзя. `notifySlack(currentBuild.currentResult)` вызывается в `post { always }`.
- **Одна нода для CI:** версия, сборка, тесты, образ и push идут на одной ноде с меткой `dotnet-linux`, потому что образ лежит в её локальном Docker. После сборки образ удаляется с ноды.
- **Тесты:** unit (`Category=Contracts`) и integration (`Category=Integration`) идут параллельно, оба с `--no-build` после общей сборки. Так параллельные запуски не конфликтуют в `bin/obj`. Каталог `TestResults` чистится в начале сборки.
- **Результаты тестов:** trx публикуются через `xunit(tools: [MSTest(...)])`.
- **Тег образа:** это `<наибольший тег vX.Y.Z по semver>-<номер сборки>`. Берутся только стабильные теги, `-rc` отбрасываются, сортировка `sort -V`. Если тегов нет, сборка падает.
- **Push, stage и prod:** выполняются только для `main`. Для PR, в том числе из форков, идут сборка, тесты и образ без секретов.
- **Секреты:** `registry-creds` читается через `--password-stdin` с временным `DOCKER_CONFIG`. `deploy-token` передаётся через переменную окружения shell в одинарных кавычках, а не через подстановку Groovy.
- **Подтверждение prod:** стадия идёт без агента, с `input` и таймаутом 3 дня, чтобы ожидание не занимало executor. Два `milestone()` вокруг `input` не дают подтвердить и выкатить старую сборку поверх новой.

**Замечания к задаче**
1. `./deploy.sh` в репозитории нет, и в нём нет параметра образа или тега. Не понятно, какую версию он выкатывает. Нужен параметр или договорённость, как он узнаёт `IMAGE_TAG`.
2. Токен передаётся аргументом (`--token`), поэтому он виден в `ps` на ноде. Лучше научить скрипт читать токен из переменной окружения или из stdin.
3. В `submitter: 'depot-leads'` я подставил название группы или пользователей по догадке. Его нужно заменить на реальное.
4. Сборки PR из форков запускают чужой код на постоянных нодах с доступом к Docker. В multibranch-job стоит выбрать доверие «только контрибьюторы» либо требовать подтверждения для PR от внешних авторов.
5. Для PR из форков `git fetch --tags` может не получить теги основного репозитория. Тогда стадия «Версия» упадёт, потому что тегов не найдётся.
6. Плагины, которые нужны Jenkins: xUnit (для trx), Pipeline Milestone Step, Credentials Binding, Docker CLI на нодах.
7. Тег `v1.5.0-rc1` библиотеки новее `v1.4.0`, но это rc, поэтому я его не брал. Если нужен `notifySlack` из `v1.5.0`, его надо дождаться в релизе.
