Я создал `Jenkinsfile` (declarative) в корне репозитория. Ничего не запускал и не коммитил: сборок и сети нет, так что синтаксис и работа пайплайна не проверены.

**Что в пайплайне**
- **Агенты и workspace:** глобальный `agent none`, на стадиях метка `dotnet-linux`. Сборка, проверки и образ идут в одном workspace. Он чистится через `cleanWs()` в `post always`, там же удаляется локальный образ.
- **Сборка:** `dotnet restore`, затем `build` без повторного restore.
- **Проверки (параллельно, `failFast true`):**
  - unit-тесты (`Category!=Integration`) и integration-тесты (`Category=Integration`, Postgres через Testcontainers);
  - статический анализ (`dotnet format --verify-no-changes`);
  - аудит уязвимых зависимостей.
- **Результаты тестов:** trx публикуются шагом `mstest` в `post always`.
- **Тег образа:** `<наибольший семвер-тег>-<номер сборки>`. Теги сортируются по версии с `versionsort.suffix=-`, поэтому `v1.10.0` выше `v1.9.3`, а `v1.5.0-rc1` ниже `v1.5.0`. Если подходящих тегов нет, сборка падает.
- **Push и stage:** только для `main`, с `beforeAgent true`.
  - Push использует `registry-creds`, а `DOCKER_CONFIG` лежит во временном каталоге и удаляется. Логин не остаётся на постоянном агенте.
  - Деплой на stage идёт с токеном `deploy-token` из окружения shell, через одинарные кавычки.
- **Prod:** сначала стадия `input` без агента, с таймаутом 3 дня, чтобы executor не простаивал, пока лид не ответит. Потом деплой на prod на агенте.
- **Slack:** библиотека подключена как `@Library('depot-pipeline-lib@v1.4.0')`, версия закреплена тегом, а не `main`. `notifySlack(currentBuild.currentResult)` вызывается в `post always`.
- **PR из форков:** для них выполняются только сборка, проверки и локальный образ. Push и деплой требуют `branch 'main'`, поэтому секреты форкам не доступны.

**Замечания к задаче**
1. **Лок-файлов нет.** `packages.lock.json` нет, а `RestorePackagesWithLockFile` не включён, поэтому restore идёт без `--locked-mode`. Это нарушает гейт «установка по лок-файлу». Нужно включить lock-файлы в `Directory.Build.props`, закоммитить их (сгенерировать надо там, где есть dotnet) и добавить `--locked-mode` в restore.
2. **Обязательность проверок для мержа.** Required checks в branch protection на GitHub задаются в настройках, не в репозитории. Их нужно включить для сборки, тестов, анализа и аудита.
3. **`deploy.sh` нет в репозитории.** Деплой на stage и prod упадёт, пока скрипт не добавят. Скрипт не принимает тег образа, только `--env`. Непонятно, как он узнаёт, какую версию выкатывать. Токен в аргументах виден в `ps` на агенте; лучше принимать его из переменной окружения.
4. **Кто подтверждает prod.** Кто из пользователей может подтверждать, в задаче не указано, поэтому `submitter` не задан. Сейчас подтвердить может любой, у кого есть права на сборку. Нужно указать группу или пользователя лида.
5. **Параллельные сборки `main`.** Сборка `main`, которая ждёт подтверждения, не блокирует следующую. Если лид подтвердит старую сборку после новой, на prod уйдёт устаревшая версия. Если нужно, добавлю `milestone` или `lock`.
6. **Настройки Jenkins, которые нужны для пайплайна:**
   - плагин MSTest для шага `mstest`;
   - в multibranch-job доверие к PR из форков только для участников (иначе форк может подменить Jenkinsfile);
   - credentials `registry-creds` и `deploy-token` ограничены этой папкой или job, а не видны всему контроллеру;
   - `git fetch --tags` на агентах работает.
7. **Версия библиотеки.** Выбран `v1.4.0`, так как `v1.5.0-rc1` является пререлизом. Если нужна другая версия, её можно заменить одной строкой.
