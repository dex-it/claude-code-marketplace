**Изменённые файлы:** только `Jenkinsfile` (новый).

**Что в нём сделано**
- **Агенты:** на весь пайплайн агент не назначен (`agent none`), ноды `dotnet-linux` берутся по стадиям. Ожидание подтверждения prod идёт без ноды, с таймаутом 3 дня, так что ответ лида на следующий день ничего не блокирует.
- **Стадии:**
  - подготовка (тег образа);
  - сборка;
  - тесты: unit (`Category!=Integration`) и integration (`Category=Integration`) параллельно, на уже собранном коде (`--no-build`);
  - образ;
  - push;
  - деплой на stage;
  - подтверждение;
  - деплой на prod.
- **Результаты тестов:** `.trx` публикуются шагом `mstest`. Старые результаты перед тестами удаляются, потому что workspace постоянный.
- **Тег образа:** `<наибольший vX.Y.Z>-<BUILD_NUMBER>`. Теги выбираются через `sort -V`, так что `v1.10.0` больше `v1.9.3`. Теги `-rc` отбрасываются. Перед этим делается `git fetch --tags`. Если подходящих тегов нет, сборка падает с понятной ошибкой.
- **Библиотека:** подключена как `depot-pipeline-lib@v1.4.0`. Я выбрал релизную метку, а не `v1.5.0-rc1` и не плавающий `main`. `notifySlack(currentBuild.currentResult)` вызывается в `post { always }`.
- **Секреты:** `registry-creds` и `deploy-token` подставляются через `withCredentials` и одинарные кавычки, а не через Groovy-интерполяцию. Логин в реестр делается с `--password-stdin` и отдельным `DOCKER_CONFIG`, который удаляется после push, чтобы он не остался на постоянной ноде.

**Замечания к задаче**
1. **Не описано, что делать с PR.** Я сделал push и оба деплоя только для `main` и не для PR. Тогда PR из форков (их собирают по условию) не получают `registry-creds` и `deploy-token`. Если нужно публиковать образы и с других веток, это надо уточнить.
2. **Риск от форков.** Сборка PR из форков запускает чужие тесты и `docker build` на постоянных нодах с Docker. В multibranch-job стоит выбрать стратегию доверия «Trusted revisions» или «Contributors», чтобы Jenkinsfile из форка не подменил наш. Лучше собирать такие PR на изолированных агентах.
3. **Токен в аргументе.** `./deploy.sh --token <токен>` виден в списке процессов (`ps`) на ноде. Рекомендую научить `deploy.sh` читать токен из переменной окружения или stdin.
4. **Нет `deploy.sh`.** Скрипта в репозитории нет, я исходил из интерфейса, который описан в задаче. Деплой делает `checkout scm`, поэтому скрипт должен лежать в репозитории. Образ или тег скрипту не передаются, так что откуда он знает, что выкатывать, из задачи неясно.
5. **Лид не определён.** Группа лидов для `input` не задана. В Jenkinsfile есть комментарий, куда добавить `submitter`. Сейчас подтвердить может любой, у кого есть право на запуск.
6. **Плагины и ограничения.**
   - Нужны плагины Pipeline, MSTest, Timestamper, Credentials Binding и Shared Library `depot-pipeline-lib`.
   - Неизвестно, требует ли `notifySlack` ноду. Я вызываю его без ноды.
   - `disableConcurrentBuilds` оставляет новые сборки `main` в очереди, пока предыдущая ждёт подтверждения prod. Если это мешает, уберите эту опцию.
