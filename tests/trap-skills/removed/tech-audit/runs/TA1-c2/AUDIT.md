# AUDIT: RFC-0007 «Перевод order-events на Redis Pub/Sub»

## Вердикт

**Не принимать.** Redis Pub/Sub не даёт гарантий доставки, которые есть у системы сейчас и которые требуются бизнесом. Выигрыша (простота, задержка) не хватает, чтобы оправдать потерю денег и журнала. Если RabbitMQ в тягость, нужна отдельная проработка альтернатив, например Redis Streams, но RFC этого не предлагает.

## Главная причина: семантика доставки

Требования из `docs/services.md`:

| Потребитель | Требование | Что даст Redis Pub/Sub |
|---|---|---|
| `billing-worker` | потеря события = счёт не выставлен | at-most-once: потеря при любом разрыве соединения, рестарте пода, деплое |
| `audit-sink` | обязан получить каждое событие | журнал с дырками, а это нарушает его назначение |
| `mailer` | письма клиенту | потери допустимы, но заметны |

Pub/Sub в Redis работает по схеме fire-and-forget:
- Сообщения нигде не хранятся. Не подписанный в момент `PUBLISH` потребитель событие теряет. Это любой рестарт, деплой в Kubernetes, сетевой сбой или переподключение.
- Подтверждений (ack) нет, повторов нет. Сейчас у нас quorum queue, ack после обработки и до 5 повторов. Всё это пропадает.
- Нет очереди и back-pressure. При пике 300 событий/с (в 7,5 раза выше среднего) медленный подписчик будет отключён Redis по `client-output-buffer-limit pubsub`, и он потеряет всё, что накопилось.
- Каждый потребитель получает копию (fan-out). Но масштабировать потребителя горизонтально нельзя: две реплики `billing-worker` обработают одно событие дважды, и в этом случае придётся делать дедупликацию. Competing consumers, как в очереди, не работают.
- Redis сейчас используется как кэш. Его конфигурация (отсутствие персистентности, eviction, возможно без HA) не рассчитана на критичные данные. Даже при настройке Pub/Sub не пишется на диск.

## Замечания по тексту RFC

1. **«Обратная совместимость сохранена» неверно.** Формат сообщения и правда не меняется, но меняется контракт: гарантии доставки, повторы, порядок при переподключении, отсутствие ack. Потребители рассчитывают именно на них.
2. **Outbox теряет смысл.** Сейчас `orders-api` публикует из outbox, и это даёт надёжность. Шаг 1 «заменяем публикацию из outbox на `PublishAsync`» убирает транзакционную гарантию. Заказ может быть записан, а событие потеряно (или наоборот). `PUBLISH` возвращает число получателей, и при 0 событие просто исчезает. Надо сохранить outbox и менять только транспорт, но тогда без ack outbox не поймёт, что событие доставлено.
3. **Шаг 3 опирается на несуществующий в репозитории стек.** В `services/orders-api` нет EF Core и `SaveChanges`: репозиторий написан на «голом» Npgsql (`OrderRepository.cs`). Dapper там тоже не нужен. Либо RFC писался не по этому коду, либо описывает другой сервис. Это надо уточнить.
4. **Идея «обработано» отдельной транзакцией разрушает идемпотентность.** Запись «обработано» отдельно от бизнес-записи даёт окно: падение между ними приводит либо к повторной обработке (двойной счёт), либо к потере (если отметили до выполнения). Для этого нужна одна транзакция с бизнес-изменением. Но даже так это лечит последствия не лечит причину отсутствия ack и повторов.
5. **Тезис «Redis уже есть» не учитывает эксплуатацию.** Redis у нас кэш, а команда эксплуатации (2 человека) знает RabbitMQ и PostgreSQL. Роль Redis меняется с «можно потерять» на «потеря = потеря денег». Нужны SLA, мониторинг, HA, план отказа. Простота тут кажущаяся.
6. **«Задержка меньше»** ничем не подтверждена (нет замеров). Для биллинга и писем разница в миллисекунды роли не играет.
7. **Релиз «за один раз, ночью»** без параллельной работы, без отката и без миграции очереди. Невозвращаемое отключение RabbitMQ после переключения означает, что вернуться нечем. Незавершённые сообщения в очереди на момент переключения не упоминаются вообще.
8. В RFC нет разделов о рисках, нагрузочном тесте, мониторинге, оценке трудозатрат и альтернативах.

## Побочные наблюдения по репозиторию

- `OrdersApi.csproj` уже содержит `StackExchange.Redis 2.7.33`, хотя в коде он не используется. Это стоит проверить (мёртвая зависимость или заготовка под RFC).
- В коде `orders-api` (`OrderService.CreateAsync`) нет ни outbox, ни публикации в RabbitMQ. Фактическое состояние публикации (где живёт outbox) в репозитории не подтверждено. В `migrations/` таблицы outbox тоже нет. Утверждения `docs/services.md` и RFC про outbox я проверить не смог.

## Рекомендации

1. RFC отклонить в текущем виде, статус «отклонено / нужна доработка».
2. Сформулировать, какую проблему мы решаем (стоимость эксплуатации RabbitMQ? задержка? сложность?). Сейчас в RFC это не названо, а нагрузка в 40–300 событий/с для RabbitMQ невелика.
3. Если нужно уйти с RabbitMQ, рассмотреть альтернативы с гарантиями: **Redis Streams** с consumer groups (ack, повторы, персистентность AOF, но требуют настроенного Redis и обучения), либо **PostgreSQL как очередь** (outbox + `FOR UPDATE SKIP LOCKED`), так как команда знает Postgres. Для каждой нужны измерения при 300 событий/с, идемпотентность потребителей и план эксплуатации.
4. Любая миграция: двойная публикация (RabbitMQ + новый транспорт) в течение периода, сверка счётчиков событий у потребителей, откат без потери данных, отдельный этап для `audit-sink` и `billing-worker`.
5. До решения: проверить, что outbox действительно существует и где он.
