# Аудит RFC-0007: перевод order-events на Redis Pub/Sub

**Вердикт: не принимать.** Предложение не соответствует требованиям к доставке, описанным в `docs/services.md`. Подробности ниже.

## Контекст (из docs/services.md)
- Сейчас: RabbitMQ 3.12, quorum queue, ack после обработки, до 5 повторов, outbox в `orders-api`.
- Потребители: `billing-worker` (потеря события = счёт не выставлен), `audit-sink` (обязан получить каждое событие), `mailer`.
- Нагрузка 40 соб/с, пик 300 соб/с, это немного, и RabbitMQ с ней справляется.
- Эксплуатация: 2 человека, опыт RabbitMQ и PostgreSQL. Redis у них только кэш.

## Главная проблема: Redis Pub/Sub не даёт гарантий доставки
1. **At-most-once, без персистентности.** Сообщение уходит только подписчикам, подключённым в момент `PUBLISH`. Если `billing-worker` перезапускается, деплоится или теряет соединение, событие теряется безвозвратно. Для биллинга это недополученные деньги, для `audit-sink` нарушение требования «каждое событие».
2. **Нет ack и повторов.** Исчезает то, что даёт текущая схема: ack после обработки и до 5 повторов. RFC не предлагает замену.
3. **Нет очереди и разделения нагрузки.** Pub/Sub рассылает копию каждому подписчику. Если реплик `billing-worker` несколько (Kubernetes), каждая получит событие, и счёт может быть выставлен дважды. Если реплика одна, то нет масштабирования и нет отказоустойчивости.
4. **Медленный потребитель.** Клиент, не успевающий читать, накапливает буфер на стороне Redis. При превышении `client-output-buffer-limit` для pubsub соединение закрывается, и сообщения теряются без ошибки. Пик 300 соб/с делает это реальным сценарием.
5. **Outbox теряет смысл.** Сейчас outbox гарантирует, что событие не потеряется между БД и брокером. Если помечать запись отправленной после `PUBLISH`, который не сообщает, получил ли кто-то сообщение (он возвращает число подписчиков, и 0 не считается ошибкой), то outbox формально отработает, а событие пропадёт. Гарантия, ради которой outbox и был сделан, исчезает.
6. **Redis у нас кэш.** В документах про Redis сказано только «используется как кэш»; его конфигурация (eviction, AOF, HA) в репозитории не описана и, вероятно, не рассчитана на критичные данные. Фейловер Redis тоже теряет сообщения.

## Другие пункты RFC
- **«Обратная совместимость сохранена» неверно.** Формат события тот же, но семантика доставки другая (at-most-once вместо at-least-once с повторами). Потребители рассчитывают на повторы и, судя по описанию, на ack. Совместимость нарушена.
- **Dapper рядом с EF Core (в `OrdersApi.csproj` EF Core нет, есть только Npgsql, так что RFC опирается на то, чего в проекте нет), отдельная транзакция.** Запись «обработано» в одной транзакции, а остальные изменения через `SaveChanges` в другой, это потеря атомарности. Падение между ними даёт либо обработку без отметки (дубль), либо отметку без обработки (потеря события). Лишняя зависимость и второй способ доступа к данным не обоснованы. Идемпотентность надо делать в одной транзакции с EF Core, например с уникальным ключом `event_id` в таблице обработанных событий.
- **Переключение за один релиз, ночью.** Нет плана отката, нет параллельной работы двух брокеров, нет миграции сообщений в очереди (непрочитанные в RabbitMQ), нет проверки. «Отключаем RabbitMQ после переключения» делает откат невозможным.
- **Аргумент «задержка меньше».** Нет измерений. Для счетов, писем и журнала задержка в миллисекунды неважна, а нагрузка 300 соб/с для RabbitMQ невелика. Аргумент не оправдывает потерю гарантий.
- **«Redis уже есть».** Но как кэш. Превращение его в критичную шину добавляет в зону отказа ещё один компонент, а команда не имеет опыта его эксплуатации (HA, персистентность). Убирая RabbitMQ, мы отказываемся от того, что команда умеет эксплуатировать.
- В RFC нет разделов о рисках, мониторинге, нагрузочных тестах, альтернативах и оценке трудозатрат.
- Версия `StackExchange.Redis 2.7.33` уже указана в `services/orders-api/OrdersApi.csproj`, и это годится для кэша. Для нового сценария версию надо проверять отдельно, я не проверял (веба нет).

## Что можно сделать вместо
- **Оставить RabbitMQ.** Он закрывает требования и знаком команде. Если есть конкретная боль (задержка, стоимость, эксплуатация), надо описать её с цифрами в новом RFC.
- Если Redis всё же нужен, использовать **Redis Streams** с consumer groups, `XACK`, `XPENDING`/`XAUTOCLAIM` для повторов и AOF с `appendfsync everysec` или `always`. Это отдельный дизайн с тестами отказов. Даже так он слабее quorum queue по гарантиям при фейловере (репликация асинхронная), и это нужно сравнить с требованиями billing/audit. Не для billing без доказательств.
- Идемпотентность потребителей (таблица обработанных `event_id` в той же транзакции) стоит сделать в любом случае, потому что RabbitMQ даёт at-least-once.

## Если команда хочет продолжить
Доработать RFC: требования к доставке по каждому потребителю, сравнение вариантов с измерениями, план миграции с параллельным запуском и откатом, тест потери событий при рестарте потребителя, мониторинг, оценка нагрузки на эксплуатацию.
