# Ревью MR: feature/invoice-statement -> main (BILL-24, акт сверки клиента)

## Общий комментарий

Сборка ветки проходит без предупреждений. Рефактор котировки (`MoneyConversion.ConvertTo`) поведение не меняет: то же `Math.Round(..., ToEven)` в месте пересчёта, как требует ADR-0004. Эндпоинт, валидатор и хендлер лежат там, где велит RUL-0003.

Есть одно расхождение с задачей, которое меняет сумму в акте, и два места, где MR обходит принятые решения команды или идёт дальше задачи.

**Нужно поправить до слияния**

1. **В акт попадают отменённые счета** (`BuildStatementHandler.cs:23`). Задача: «Черновики и отменённые счета в акт не входят». Фильтр исключает только `Draft`, поэтому счёт со статусом `Cancelled` попадает в строки и в итог. Итог акта для бухгалтерии завышается.
2. **Собственный маппинг ошибок в HTTP** (`StatementHttpResults.cs`) дублирует `ResultHttpExtensions.ToHttp` и расходится с ADR-0002. Ответы идут не ProblemDetails с `code`, как у остальных эндпоинтов, а `{ error = ... }`. Неизвестная бизнес-ошибка уходит в 500 вместо 409. Клиент API получает два формата ошибок.

**Нужно убрать из MR (вне задачи)**

3. **Заготовка под выгрузку в Excel** (`IStatementFormatter.cs`, `StatementFormatterRegistry.cs`, `StatementRenderOptions`, регистрация в `StatementsModule`). Задача требует только JSON, а выгрузка с группировкой по месяцам вынесена в BILL-27, и по ней решения нет. Сейчас в коде есть реестр форматтеров с единственным членом, `StatementGrouping.ByMonth/ByStatus`, `SheetName`, `FreezeHeader`, `IncludeDrafts`. Ни один параметр не читается: `JsonStatementFormatter.Render` игнорирует `options`. Параметры угадывают требования будущей задачи, и когда решение по BILL-27 появится, их придётся переделывать.

**Замечания поменьше** даны ниже в комментариях к строкам.

Тесты в MR не требуются: задача их не просит (RUL-0002). XML-doc тоже не требуется (RUL-0001).

## Комментарии к строкам

### src/Billing.Api/Application/Handlers/Statements/BuildStatementHandler.cs

**Строка 23: блокер.** `.Where(i => i.Status != InvoiceStatus.Draft)` пропускает `Cancelled`. Задача требует исключить и черновики, и отменённые счета. Предложение: оставить только счета в статусах `Issued` и `Paid`, например `i.Status is InvoiceStatus.Issued or InvoiceStatus.Paid`. Явный список надёжнее отрицания: появится новый статус, и он не попадёт в акт молча. Нужен тест (или хотя бы ручная проверка) на акт со счетом `Cancelled`.

**Строка 21: замечание.** `ListByCustomerAsync` отдаёт все счета клиента, а период и статус отбираются в памяти. С InMemory-репозиторием это незаметно, но реальному хранилищу придётся читать всю историю клиента ради акта за месяц. Рекомендую принять в `ListByCustomerAsync` период (и при необходимости статусы) и фильтровать в запросе. Менять контракт проще сейчас, пока у метода один вызывающий.

**Строки 22-24: вопрос.** Дата счёта для границ периода берётся как `CreatedAt.UtcDateTime`. Для бухгалтерии не в UTC счёт, созданный в 23:30 по местному времени последнего дня периода, может попасть в соседний период. В задаче часовой пояс не указан. Подтвердите с автором задачи, что границы считаются по UTC, и зафиксируйте это в задаче. Правка кода не нужна, если ответ «UTC».

### src/Billing.Api/Api/StatementHttpResults.cs

**Весь файл: блокер.** Класс повторяет `ResultHttpExtensions.ToHttp`, но отвечает иначе. ADR-0002 говорит, что эндпоинт переводит ошибку в ProblemDetails по типу через `ResultHttpExtensions`. Здесь формат `{ error = Message }` без `code`, а `_ => 500` скрывает бизнес-ошибки, которые `ToHttp` отдаёт как 409. Предложение: удалить файл, в `StatementEndpoints` вызывать `.ToHttp(...)`. Если нужен другой статус, меняется общий `Problem(...)`, а не заводится второй маппер.

### src/Billing.Api/Api/StatementEndpoints.cs

**Строки 20-24: замечание.** После удаления форматтеров достаточно `Results.Ok(...)` с DTO ответа (как в `quote`). `Results.File(byte[], contentType)` для JSON-ответа странен: это ответ-файл, а не тело API. Заодно из эндпоинта уйдёт `StatementFormatterRegistry` как параметр.

### src/Billing.Api/Application/Statements/IStatementFormatter.cs

**Весь файл: убрать (вне задачи).** Задача: «Формат ответа - JSON». Excel и группировка по месяцам относятся к BILL-27, решения по ним нет. Интерфейс, enum `StatementFormat` с одним значением, `StatementGrouping` и `StatementRenderOptions` с четырьмя неиспользуемыми полями добавляют код и тип, которые никто не вызывает. Предложение: удалить файл, `StatementFormatterRegistry.cs`, `JsonStatementFormatter.cs` и регистрации в `StatementsModule`. Сериализацию ответа оставить анонимным или именованным DTO прямо в эндпоинте. Когда решение по BILL-27 будет принято, абстракцию можно ввести под известные требования.

### src/Billing.Api/Application/Statements/StatementFormatterRegistry.cs

**Строки 8-11: замечание.** Если реестр всё же останется: `Resolve` бросает `NotSupportedException` для незарегистрированного формата. Это ошибка программиста, а не бизнес-отказ, так что по ADR-0002 это допустимо, но при единственном формате ветка недостижима. Ещё один довод убрать реестр целиком.

### src/Billing.Api/Application/Handlers/Statements/BuildStatementValidator.cs

**Строка 10: замечание (необязательное).** `Length(3)` проверяет только длину кода валюты, как и в `CreateInvoiceValidator`. Код `ABC` пройдёт валидацию, а `FxRatesClient` получит ответ с ошибкой и вернёт 500 вместо 400. Это же поведение у `quote`, так что оставлять можно, но стоит завести отдельный тикет на общую проверку кодов валют.

### src/Billing.Api/Application/Handlers/Statements/BuildStatementHandler.cs (курсы)

**Строки 28-30: замечание (необязательное).** Курсы запрашиваются последовательно по одному на каждую валюту счетов. Для акта по клиенту с несколькими валютами это несколько HTTP-вызовов подряд. ADR-0005 принимает синхронный вызов в момент операции без кэша, поэтому по сути сделано верно. Параллелить через `Task.WhenAll` можно, если задержка станет проблемой. Заодно при совпадении валюты счёта и акта курс 1 можно не запрашивать.

### src/Billing.Api/Application/Fx/MoneyConversion.cs

**Без замечаний.** Поведение котировки сохранено, округление по ADR-0004 осталось в месте пересчёта.
