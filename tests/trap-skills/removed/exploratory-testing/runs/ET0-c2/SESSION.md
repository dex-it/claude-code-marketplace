## Дефекты

### D1 (высокий). Гонка при параллельных запусках: дублируются id, заказы теряются
Шаги: `rm scratch/p.json; export ORDERS_FILE=$PWD/scratch/p.json; for i in 1 2 3 4 5 6; do $R create --sku a --qty 1 --price 5 & done; wait; $R list`
Ожидалось: 6 заказов с id 1..6. Фактически: команды напечатали id `1 1 1 2 2 2`, в `list` только 2 заказа (4 потеряны).
Причина: load -> изменение -> save без блокировки/атомарной записи (src/orders.js). То же для `--ref`: 6 параллельных create с одним ref
дали «1» всем (здесь исход случайно верный, но защита от дублей не атомарна).
Это же ломает гарантию идемпотентности `--ref` при параллельных повторных отправках.

### D2 (средний). qty и price принимают нечисловые/недесятичные записи
Шаги: `$R create --sku x --qty 1e1 --price 100` -> id, заказ x10;
`$R create --sku x --qty 0x10 --price 0x10` -> заказ x16 с ценой 16 (2.56 в list);
`$R create --sku x --qty " 5 " --price 1e3` -> принят (x5, 50.00).
Ожидалось: «целое число центов»/«целое от 1 до 100» - только десятичные цифры, иначе ошибка кода 2. Причина: `Number()` вместо строгой проверки.

### D3 (средний). Нет верхней границы price: переполнение безопасных целых, вывод суммы неверный
Шаги: `$R create --sku x --qty 5 --price 99999999999999999999` -> принят; `$R list` -> `5 X x5 5000000000000000000.00 new`
(цена и total потеряли точность: 5e20 в double, хранится как 100000000000000000000, total = 5e20 и т.п.). Ожидалась ошибка `bad price`.

### D4 (низкий). id в pay/ship/cancel разбирается через Number()
Шаги: `$R pay 0x2` -> оплачен заказ №2; `$R pay 1e0` и `$R pay 2.0` работают как id 1 и 2 (`bad state ...` вместо `not found`).
Ожидалось: `not found` (код 4) для нечисловых id. Также `pay` без id и `pay abc` дают просто `not found`, без подсказки о неверном аргументе.

### D5 (низкий). Флаги без значения / пустой `--ref` молча игнорируются
Шаги: `$R create --sku x --qty 2 --price 5 --ref` и `--ref ""` (дважды) -> создаются три разных заказа (7, 8, 9), идемпотентности нет, ошибки нет.
Также `create --sku x --qty --price 5`: парсер съедает `--price` как значение qty, сообщение `qty must be 1..100` вводит в заблуждение.
Спека поведение не определяет - вопрос к автору: нужна ли ошибка?

### D6 (низкий / вопрос к спеке). Повторный `--ref` с другими параметрами молча отдаёт старый id
Шаги: `$R create --sku x --qty 2 --price 5 --ref R1` (-> 6), `$R create --sku y --qty 3 --price 7 --ref R1` -> `6`, без предупреждения о конфликте данных.
Спека такое допускает («печатается id уже созданного»), но стоит уточнить.

### D7 (низкий). Невалидный фильтр и битый файл
- `list --status bogus` -> `no orders` (код 0), а не ошибка о неизвестном статусе.
- Битый JSON в ORDERS_FILE -> сырое сообщение парсера JSON `Expected property name or '}'...` и код 1, без понятного текста.
