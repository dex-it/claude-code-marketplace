## Дефекты

### D1. Повторный `--ref` с другими/невалидными параметрами не возвращает прежний id (спека, п. 11)
Валидация параметров выполняется раньше поиска дубликата по `ref` (`src/orders.js`, `create`), а при валидных, но отличающихся параметрах возвращается прежний заказ целиком (тут OK).
Шаги:
1. `rm -f $ORDERS_FILE; orders create --sku ab-1 --qty 2 --price 1050 --ref R1` -> `1`
2. `orders create --sku zz --qty 0 --price 5 --ref R1`
- Ожидание: `1`, код 0 (спека: «независимо от остальных параметров повторной отправки»).
- Факт: `qty must be 1..100`, код 2. То же с `--qty 999`.
Замечание: формулировка спеки может быть спорной (ошибка qty vs идемпотентность) — стоит уточнить у владельца требований; сейчас реализация противоречит букве п. 11.

### D2. `list --status ""` не даёт `bad status`
Шаги: создать любой заказ; `orders list --status ""`.
- Ожидание: `bad status`, код 2 (допустимы только new/paid/shipped/cancelled).
- Факт: список всех заказов, код 0 (проверка `if (status && ...)` пропускает пустую строку). Аналогично `--sku ""` молча игнорируется фильтром (спека про это не говорит — уточнить).

### D3 (низкая, уточнить). Ведущие нули в id принимаются
`orders pay 01` обрабатывается как `pay 1` (в тесте перевёл shipped-заказ №1 в проверку состояния: `bad state shipped`). Спека допускает «только десятичные цифры», так что формально это не нарушение; отмечено как неоднозначность. Аналогично `--qty 0001`, `--price 005` приняты.

### D4 (низкая). Повреждённый ORDERS_FILE
При невалидном JSON выводится сырое сообщение `Expected property name or '}' in JSON at position 1 ...` без осмысленной ошибки (код 1). Спека не описывает; наблюдение.

### D5 (наблюдение). Повтор флага
`create ... --ref R1 --ref R2` молча берёт последнее значение (R2). Спека не определяет поведение.
