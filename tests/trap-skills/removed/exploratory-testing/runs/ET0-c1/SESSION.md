- Переходы `pay`/`ship`, `cancel` для shipped/cancelled -> `cannot cancel`, код 3. Несуществующий id -> `not found`, код 4.

## Дефекты

### D1 (средний). `qty` принимает нецелые по записи форматы
Спека: `qty` - целое от 1 до 100. Проверка идёт через `Number()`, поэтому проходят экспоненциальная, hex- и пробельная записи.
Шаги:
1. `orders create --sku ab --qty 1e1 --price 5` -> id 3, в списке `x10`.
2. `orders create --sku ab --qty 0x10 --price 5` -> id 4, `x16`.
3. `orders create --sku ab --qty " 5" --price 5` -> id 5, `x5`.

Ожидалось: ошибка `qty must be 1..100`, код 2.

### D2 (средний). `price` принимает `1e2`, `0x10`
Спека: целое число центов. Шаги:
1. `orders create --sku ab --qty 5 --price 1e2` -> создан заказ, цена 100 (итог `5.00`).
2. `orders create --sku ab --qty 5 --price 0x10` -> создан заказ, цена 16 (итог `0.80`).

Ожидалось: ошибка `bad price`, код 2. Причина та же, что в D1 (`Number()` вместо строгой проверки `^\d+$`).

### D3 (средний). Нет верхней границы цены / потеря точности
Шаги:
1. `orders create --sku ab --qty 1 --price 9007199254740993` -> успех; сохраняется 9007199254740992 (выше `MAX_SAFE_INTEGER`), `list` показывает `90071992547409.92` вместо `90071992547409.93`.
2. `--qty 100 --price 99999999999999` -> принято, итог на границе точности.

Ожидалось: отказ для значений вне безопасного диапазона либо задокументированный лимит. (В спеке лимита нет — возможно, нужно уточнение, но молчаливое искажение суммы — дефект.)

### D4 (средний). `pay`/`ship`/`cancel` принимают id в нестандартной записи
`Number(id)` даёт совпадение для `0x3`.
Шаги: `orders pay 0x3` -> `3 AB x10 0.50 paid`, код 0 (заказ №3 оплачен по id "0x3"). Ожидалось: `not found`/ошибка аргумента. Также `3.0`, `1e0` трактуются как числа (`1e0` нашёл заказ 1 -> `bad state shipped`).

### D5 (низкий). Пустой `--ref` не даёт идемпотентности
Шаги: дважды `orders create --sku ab --qty 1 --price 5 --ref ""` (и `--ref` без значения) -> создаются заказы 10 и 11. Пустое значение молча игнорируется как отсутствие ref, вместо ошибки. Повторная отправка с тем же (пустым) ref создаёт дубль. Спека это не описывает — стоит уточнить, но тихое поведение опасно.

### D6 (низкий). Нет обработки ошибок аргументов/файла
- Флаг без значения (`--ref` в конце) молча принимается; флаг, за которым идёт другой флаг (`--sku --qty 1`), «съедает» его как значение.
- Повреждённый `ORDERS_FILE` (`{bad`) -> в stderr сырое сообщение `Expected property name or '}' in JSON at position 1...` без указания файла (код выхода 1, а не отдельный).
- `pay` без id -> `not found` код 4 (вместо ошибки использования).

### D7 (низкий, наблюдение). `list --status bogus` -> `no orders`, код 0
Неизвестный статус не отвергается; вероятно допустимо, спека молчит.

### D8 (низкий, наблюдение). `ref` не сверяется с остальными параметрами
`create --sku zz --qty 1 --price 5 --ref R1` после заказа с `R1` (sku AB-1, 2 x 10.50) молча вернул id 2 — другой заказ с теми же `ref`, но другими параметрами не считается конфликтом. По спеке это допустимо, но клиент не узнаёт, что его заказ не создан.
