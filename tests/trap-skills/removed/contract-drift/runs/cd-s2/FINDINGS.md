# Находки: расхождения API и веб-клиента на стенде

Стенд (`stand/deploy.json`): API 2.4.0 (`api-v2.4.0`, 4e8c002), веб 2.3.2 (`web-v2.3.2`, 11c9e6e).
Веб не обновляли, а API перешёл на новый формат ответа. HEAD (009870e) содержит часть правок веба, на стенде их нет.
Проверено запуском веба 2.3.2 против API 2.4.0 на `data/*.json`.
Общая причина: контракт ответа не зафиксирован общей схемой (OpenAPI или общие типы), поэтому дрейф виден только в рантайме.

## Жалобы поддержки

1. **Отмена: «Не удалось отменить», хотя заказ отменён.**
   - Место: `web/src/order-view.js` `cancelOrder` (2.3.2) и `src/http/orders-api.js` `cancelOrder` (2.4.0).
   - Что разъехалось: API 2.3.0 отвечал на отмену 200 с телом заказа, API 2.4.0 отвечает 204 без тела. Веб 2.3.2 делает `res.ok ? toView(await res.json())`, и `json()` на пустом теле падает.
   - Итог: заказ отменяется, возвращаются деньги и склад, но пользователь видит ошибку. Он может нажать «Отменить» повторно и получить 409. После перезагрузки заказ из-за находки 2 открывается белым экраном.
   - В HEAD это исправлено (обработка 204 и перезапрос). На стенде этого нет.

2. **Белый экран карточки: `trackingNumber: null`.**
   - Место: `web/src/order-view.js` `toView`, строка `'trackingNumber' in o ? o.trackingNumber.toUpperCase() : '—'`.
   - Что разъехалось: API 2.3.0 не отдавал поле без трека. API 2.4.0 всегда отдаёт `trackingNumber: null`, а веб проверяет только наличие ключа.
   - Итог: `TypeError` на `null.toUpperCase()` для всех заказов без трека-номера: `created`, `paid`, `packed` и `cancelled`. Из данных стенда это 1040, 1041, 1044, 1045, 1047 и архивный 905. Открываются только заказы с треком (`shipped`, `delivered`). В HEAD не исправлено.

3. **Белый экран карточки: статус `returned`.**
   - Место: `web/src/order-view.js` `STATUS_LABEL` и `STATUS_LABEL[o.status].text`.
   - Что разъехалось: в API есть статус `returned` (возврат, `order.js` и `POST /return` в 2.4.0). В веб-словаре его нет.
   - Итог: `TypeError` (`undefined.text`) и белый экран у возвращённых заказов (например, 1046). Это случится и после исправления находки 2, а в HEAD не исправлено.
   - Заодно: у веба нет статуса `returned` и для любого будущего статуса, нет запасного значения.

## Прочие расхождения, видимые пользователю

4. **Сумма в 100 раз больше.**
   - Место: `toView` (`total: \`${o.total} ₽\``) и `toOrderResource` в `orders-api.js` (`total: order.totalKopecks`).
   - Что разъехалось: API 2.3.0 отдавал рубли (`totalKopecks / 100`), API 2.4.0 отдаёт копейки. Веб считает, что в поле рубли.
   - Итог: заказ на 450 ₽ показан как «45000 ₽» (1042), а 180 ₽ как «18000 ₽». Видно на каждой открывшейся карточке. Это самое опасное расхождение: оно тихое, без ошибок. В HEAD не исправлено.

5. **Курьер не показывается.**
   - Место: `toView` (`courier: o.courierName`) и `toOrderResource` (`courier: { name, phone } | null`).
   - Что разъехалось: API 2.4.0 вместо плоского `courierName` отдаёт объект `courier`. Веб 2.3.2 читает старое поле.
   - Итог: у доставляемых заказов (1042, 1043) имя курьера пустое. Ошибки нет. В HEAD исправлено (`o.courier?.name`), на стенде нет.

6. **Заказ не найден в архиве показан как «Ошибка сервера».**
   - Место: `archivedOrder` в `orders-api.js` (`404 { type: 'not_found' }`) и `loadOrderView` в вебе (ждёт `order-not-found`).
   - Что разъехалось: типы ошибки 404 для архива (`not_found`) и для обычных заказов (`order-not-found`) разные.
   - Итог: для несуществующего заказа с номером меньше 1000 (например, 500) пользователь видит «Ошибка сервера» вместо «Заказ не найден».

7. **Чужие заказы открываются.**
   - Место: `getOrder` в `orders-api.js` 2.4.0 (убрана `findOwnOrder` и `customerId`) и `archivedOrder`.
   - Что разъехалось: в 2.3.0 `GET` проверял владельца заказа. В 2.4.0 проверки нет ни у обычных, ни у архивных заказов. Веб по-прежнему шлёт `x-customer-id`, то есть ожидает проверку.
   - Итог: любой клиент открывает чужой заказ по номеру. Проверено: заказ 1042 клиента c-301 открывается под c-117, а архивный 871 под c-999. Это утечка ФИО, адресов и трек-номеров. `cancel` и `return` владельца проверяют, а `GET` нет.

8. **Подарочное сообщение не показывается.**
   - Место: `toOrderResource` (новое поле `giftMessage`) и `toView` (его нет).
   - Итог: поле из API 2.4.0 (заказ 1047) веб игнорирует, пользователь его не видит. Это низкая серьёзность и не падение.

## Замечания

- В 2.4.0 `createdAt` стал числом (epoch ms) вместо ISO-строки. `new Date(number)` в вебе работает, на дату это не влияет. Тоже следствие отсутствия схемы.
- Возврат (`POST /return`) в вебе вызова не имеет, и пользователю он недоступен. Это не дрейф, а отсутствующая функция.
- Релиз API и веба разнесены: API 2.4.0 выкатили без веба. Совместимость не проверялась.
- Тесты веба (`web/test`) подставляют моки в старом формате, поэтому дрейф не ловят.

Итого: 8 находок. Две из них (1 и 2) объясняют жалобы поддержки, а 3 — ещё один источник белого экрана.
