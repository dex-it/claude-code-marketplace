# Находки: расхождения API и веб-клиента на стенде

Стенд (`stand/deploy.json`): API 2.5.0 (`api-v2.5.0`), веб 2.4.0 (`web-v2.4.0`). Код веба между web-v2.4.0 и HEAD не менялся.

## 1. Формат даты доставки `eta`: API отдаёт `ДД.ММ.ГГГГ`, веб ждёт ISO `ГГГГ-ММ-ДД`

- Место: API - `src/http/orders-api.js`, `displayDate` и `toOrderResource` (коммит afae684, «поля карточки для мобильного приложения 1.3»). Веб - `web/src/order-view.js`, функция `day()` (`new Date(value)`), вызывается из `toView`.
- Что разъехалось: до 2.5.0 поле `eta` было `"2026-10-01"`. Теперь это `"01.10.2026"`. Веб 2.4.0 не обновлялся и по-прежнему разбирает значение через `new Date(...)`. Строка `"01.10.2026"` не является валидной датой, получается Invalid Date. Тесты веба прогоняются на ISO-фикстуре, поэтому дрейф они не ловят.
- Что увидит пользователь: в карточке любого заказа, где дата доставки уже известна (оплаченные и отгруженные заказы, доставленные, возвращённые, архивные с `eta`), в поле «Доставка» вместо «1 октября» будет «Invalid Date». Заказы без `eta` показывают «—» и не затронуты. Ошибки в консоли нет, карточка рисуется как обычно, поэтому сбой заметят только пользователи.
- Причина: контракт ответа не зафиксирован общей схемой (OpenAPI или общие типы). Формат поля поменяли под мобильное приложение 1.3, и веб-клиент об этом не узнал.
- Что делать: либо вернуть `eta` в ISO и форматировать для мобильного отдельным полем, либо выкатить веб, который разбирает `ДД.ММ.ГГГГ`. До выката в прод на стенде надо держать связку API и веба с одним форматом.

Замечание: смена регистра `trackingNumber` в 2.5.0 вреда не наносит. Веб и так приводит трек к верхнему регистру.
