# Находки: API 2.4.0 и веб 2.3.2 на стенде

На стенде (`stand/deploy.json`): API `api-v2.4.0`, веб `web-v2.3.2`. Веб остался на версии, написанной под API 2.3.0, а API 2.4.0 поменял контракт.
Коммит `9bbfe85` в main (`web/src/order-view.js`) на стенд не выкачен. Он чинит только пункты 1 и 4 и не трогает остальные.
Код не правился, всё найдено чтением кода и данных. Приложение не запускалось, тесты не гонялись.

## Причины двух жалоб

**Жалоба 1: «Не удалось отменить», хотя заказ отменён.** См. п. 1.
**Жалоба 2: белый экран карточки.** См. п. 2 и п. 3.

## Расхождения API и веба

1. **Отмена: ответ 204 без тела.**
   - Место: `src/http/orders-api.js:50` (`cancelOrder` возвращает `{ status: 204 }`); `web/src/order-view.js` (`cancelOrder`, `res.ok ? toView(await res.json())`).
   - Что разъехалось: в 2.3.0 отмена отвечала 200 с заказом, в 2.4.0 отвечает 204 без тела. Веб на 2xx вызывает `res.json()` на пустом теле, получает исключение, и срабатывает `catch`.
   - Итог: заказ на сервере уже `cancelled` (деньги возвращены, склад освобождён), а пользователь видит «Не удалось отменить». Он может нажать повторно и получит 409, который веб тоже покажет как «Не удалось отменить».
   - Фикс в main (`9bbfe85`) на стенде не развёрнут.

2. **Статус `returned` неизвестен вебу.**
   - Место: `STATUS_LABEL` в вебе (нет ключа `returned`) и `STATUS_LABEL[o.status].text` в `toView`; API: `returnOrder`, `POST /api/orders/:id/return`, статус `returned` (в данных заказ 1046).
   - Что разъехалось: API 2.4.0 ввёл статус `returned`, а веб знает только 6 статусов.
   - Итог: `STATUS_LABEL['returned']` равен `undefined`, `.text` бросает TypeError, карточка возвращённого заказа открывается белым экраном (в `loadOrderView` нет обработки). Касается и заказа, который пользователь только что вернул.

3. **`trackingNumber: null` для заказов без трека.**
   - Место: `toOrderResource` в `src/http/orders-api.js:13` (`trackingNumber: order.trackingNumber ?? null`); веб: `'trackingNumber' in o ? o.trackingNumber.toUpperCase() : '—'`.
   - Что разъехалось: в 2.3.0 поле отсутствовало, если трека нет. Теперь оно всегда есть и равно `null`. Проверка `in` в вебе проходит, и `null.toUpperCase()` бросает TypeError.
   - Итог: белый экран у всех заказов без трека: `created`, `paid`, `packed`, `cancelled`, `returned`. Из sample-данных это 1040, 1041, 1044, 1045, 1046, 1047. Работают только заказы с треком (`shipped`, `delivered`). Это основная причина «части заказов». Из-за неё после успешной отмены `loadOrderView` тоже даст белый экран вместо «Отменён», даже когда п. 1 исправлен.

4. **Курьер стал объектом.**
   - Место: API `courier: { name, phone } | null`; веб `courier: o.courierName`.
   - Что разъехалось: поле `courierName` убрано, вместо него `courier`. Веб читает старое поле.
   - Итог: имя курьера не показывается ни у одного заказа (`undefined`). Телефон курьера из API веб в любом случае не выводит.
   - Исправлено в main (`9bbfe85`), на стенде не развёрнуто.

5. **Сумма в копейках вместо рублей.**
   - Место: API `total: order.totalKopecks` (было `/ 100`); веб `` `${o.total} ₽` ``.
   - Что разъехалось: 2.3.0 отдавал рубли, 2.4.0 отдаёт целые копейки. Веб ничего не делит.
   - Итог: сумма завышена в 100 раз. Заказ на 360 ₽ показан как «36000 ₽», на 1 260 ₽ как «126000 ₽». Заметно на каждой карточке, которая вообще открывается. Дробная часть и форматирование тоже не обрабатываются.
   - В main не исправлено.

6. **Код 404 для архивных заказов.**
   - Место: `archivedOrder` в `src/http/orders-api.js:27` (`type: 'not_found'`); обычный 404 использует `order-not-found`; веб проверяет `body.type === 'order-not-found'`.
   - Что разъехалось: для заказов с id < 1000, которых нет в архиве, API отвечает другим типом ошибки.
   - Итог: вместо «Заказ не найден» пользователь видит «Ошибка сервера», как при сбое. Касается любого id < 1000, которого нет в `archive-sample.json`.
   - В main не исправлено.

7. **`giftMessage` не показывается.**
   - Место: API добавляет `giftMessage` в ресурс (`orders-api.js:15`, заказ 1047); `toView` его не читает.
   - Что разъехалось: новое поле API, в вебе под него нет отображения.
   - Итог: пользователь не видит подарочное сообщение в карточке («С днём рождения, Лена!»). Тип `createdAt` (ISO-строка → число ms) веб переваривает, `new Date(number)` работает, но формат поменялся без уведомления.

## Дефект API, который пользователь может увидеть (не расхождение с вебом)

8. **`GET /api/orders/:id` больше не проверяет владельца.**
   - Место: `getOrder` в `src/http/orders-api.js:34-39` (в 2.3.0 использовался `findOwnOrder` с `customerId`; в 2.4.0 вызывается `store.get(id)`, а `server.js` перестал передавать `customerId`). Архивные заказы тоже отдаются без проверки.
   - Что разъехалось: отмена и возврат по-прежнему проверяют `x-customer-id`, чтение — нет.
   - Итог: любой клиент по номеру увидит чужой заказ (состав, трек, имя и телефон курьера). Веб при этом отправляет `x-customer-id` и считает, что он учитывается.
   - Для ответа 404 на чужой заказ: раньше он давал `order-not-found`, теперь отдаёт 200.

## Вне объёма (замечено мимоходом, в счёт не входит)

- `src/eta.js`: `formatEtaForSms` использует `getMonth()` без +1 (месяц в SMS на единицу меньше), `estimateDelivery` считает по UTC, а не по Москве. В `withinReturnWindow` есть вопрос по границе окна (`<= 14` суток по формуле «полных суток»). Это не расхождение API и веба.
