# Расхождения API ↔ веб на стенде stage

Стенд (`stand/deploy.json`): API **2.4.0** (`api-v2.4.0`), веб **2.3.2** (`web-v2.3.2`). Веб не обновляли с контракта API 2.3.0.
Проверялся код по тегам, не HEAD: коммит 009870e («Веб: курьер из объекта courier, отмена с ответом 204») на стенд не выкатывался.
Корневая причина всех пунктов: контракт `GET /api/orders/:id` и `POST …/cancel` нигде не зафиксирован общей схемой (OpenAPI/общие типы). API 2.4.0 изменил его без правки веба, и тесты каждой стороны этого не видят.

## Причины двух жалоб

### 1. «Не удалось отменить», хотя заказ отменён
- Место: API `src/http/orders-api.js` `cancelOrder` → теперь `204` без тела; веб 2.3.2 `web/src/order-view.js` `cancelOrder`: `res.ok ? toView(await res.json())`.
- Что разъехалось: в 2.3.0 отмена отвечала `200` с заказом, в 2.4.0 — `204` без тела. Веб на `204` вызывает `res.json()` на пустом теле, получает исключение, и срабатывает `catch`.
- Итог: заказ в API уже `cancelled` (деньги возвращены, резерв снят), а пользователь видит «Не удалось отменить». Он может нажать повторно и получит 409 (тоже «Не удалось отменить»). Статус на экране не обновляется.

### 2. Белый экран карточки у части заказов
Это два независимых падения в `toView`, оба — необработанный `TypeError` при рендере:
- `trackingNumber`: API 2.4.0 всегда отдаёт поле, а для заказов без трека — `null` (раньше поле отсутствовало). Веб проверяет `'trackingNumber' in o` и вызывает `null.toUpperCase()`. Падают все заказы без трека: `created`, `paid`, `packed`, `cancelled` (на данных стенда 1040, 1041, 1044, 1045, 1047).
- Статус `returned`: API 2.4.0 ввёл статус (возврат), в `STATUS_LABEL` веба его нет. `STATUS_LABEL['returned'].text` падает (заказ 1046 и любой возвращённый). Падает до остальных полей, так что трек там не важен.
- Итог: нет карточки, нет сообщения об ошибке. Отменённый заказ без трека тоже падает, поэтому после отмены (если бы жалоба 1 была исправлена) карточка открывалась бы белым экраном.

## Остальные расхождения, видимые пользователю

3. **Сумма в 100 раз больше.** API: `total` — копейки (`totalKopecks`), раньше рубли (`/100`). Веб печатает `${o.total} ₽`. Заказ 1040 на 360 ₽ показывается как «36000 ₽». Видно на каждой карточке, у которой карточка вообще открывается.
4. **Курьер не показывается.** API: `courier: { name, phone } | null`, раньше `courierName`. Веб читает `o.courierName` → `undefined`. У отгруженных и доставленных заказов (1042, 1043) имя курьера пропало; телефона в вебе нет вообще. (В HEAD правка есть, на стенде нет.)
5. **Дата создания.** API: `createdAt` — число (epoch ms), раньше ISO-строка. Веб делает `new Date(createdAt)`, работает с обоими форматами; расхождение контрактное и пока безвредное. Если веб начнёт сравнивать или парсить строкой — сломается. Фиксирую как риск, а не как наблюдаемый дефект.
6. **Архивные заказы (id < 1000): неверный тип ошибки 404.** `archivedOrder` отвечает `{ type: 'not_found' }`, остальные места — `order-not-found`. Веб показывает «Заказ не найден» только по `order-not-found`, иначе «Ошибка сервера». Для несуществующего или не попавшего в архив номера < 1000 (в архиве только 871 и 905) пользователь видит «Ошибка сервера» вместо «Заказ не найден».
7. **Архивные заказы: нет проверки владельца.** `getOrder` в 2.4.0 больше не вызывает `findOwnOrder` и не читает `x-customer-id` (раньше 404 для чужого заказа). Любой клиент по номеру увидит чужой заказ, включая архив. Пользователю это видно как чужая карточка заказа. Веб заголовок отправляет, но API его игнорирует. Не расхождение формата, а потеря проверки при смене контракта.
8. **Новое поле `giftMessage` и возврат не поддержаны вебом.** `giftMessage` приходит (заказ 1047), веб его не показывает. Эндпоинта `POST /api/orders/:id/return` в вебе нет, возврата из UI нет. Пользователь не может оформить возврат, о котором говорит API.
9. **Ответ 409 на отмену.** API: `{ type: 'cancel-forbidden', message }` с понятным текстом; веб не читает тело и всегда пишет «Не удалось отменить». Причина отказа (заказ уже отгружен) пользователю не видна. Контракт не менялся в 2.4.0, но это потеря информации.

## Что сделать (не правил)
Выкатить веб ≥ HEAD с обработкой `204`, `courier`, копеек, `trackingNumber: null` и статуса `returned`. Единый тип `not_found`/`order-not-found`. Вернуть проверку владельца в `getOrder`. Зафиксировать контракт общей схемой и проверять её тестом на обеих сторонах.
