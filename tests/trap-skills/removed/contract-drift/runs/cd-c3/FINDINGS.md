# Расхождения API и веба на стенде

На стенде (`stand/deploy.json`): API 2.4.0 (`api-v2.4.0`, коммит 4e8c002) и веб 2.3.2 (`web-v2.3.2`, коммит 11c9e6e).
Веб 2.3.2 написан под контракт API 2.3.0. Исправления в `web/src/order-view.js` из коммита 009870e
(`courier?.name`, обработка 204) на стенд не выкатывались. Они есть в HEAD, но не в 2.3.2.
Сравнивал веб 2.3.2 с API 2.4.0. Код не правил, на стенде ничего не запускал: выводы сделаны по коду и данным.

## Причины жалоб поддержки

### 1. Отмена: веб пишет «Не удалось отменить», хотя заказ отменён
- Место: API `src/http/orders-api.js` `cancelOrder` отвечает `204` без тела (2.4.0). Веб `cancelOrder` в `web/src/order-view.js`
  (2.3.2) при `res.ok` делает `toView(await res.json())`.
- Что разъехалось: в 2.3.0 отмена возвращала заказ в теле, в 2.4.0 тело пустое.
  `res.json()` на пустом теле кидает исключение, и `catch` возвращает «Не удалось отменить».
- Итог: заказ на сервере уже `cancelled`, деньги возвращены, склад освобождён. Пользователь видит ошибку и жмёт отмену
  повторно. Второй запрос даёт 409 `cancel-forbidden`, и снова «Не удалось отменить». Карточка не обновляется.

### 2. Белый экран: `trackingNumber: null`
- Место: API `toOrderResource` всегда отдаёт `trackingNumber: order.trackingNumber ?? null`.
  Веб `toView` использует `'trackingNumber' in o ? o.trackingNumber.toUpperCase() : '—'`.
- Что разъехалось: раньше поле для заказа без трека отсутствовало. Теперь оно есть и равно `null`, проверка `in` истинна, и
  вызывается `null.toUpperCase()`.
- Итог: `TypeError` при построении карточки, белый экран. Затронуты все заказы без трек-номера: `created`, `paid`,
  `packed`, часть `cancelled` (на стенде 1040, 1041, 1044, 1045, 1047, архивный 905).

### 3. Белый экран: статус `returned`
- Место: API 2.4.0 добавил статус `returned` (`returnOrder`, `POST /api/orders/:id/return`).
  Веб `STATUS_LABEL` его не содержит, `STATUS_LABEL[o.status].text` падает.
- Итог: белый экран у каждого возвращённого заказа (на стенде 1046). После возврата через API карточка этого заказа тоже
  перестаёт открываться.

## Остальные расхождения, видимые пользователю

### 4. Сумма в копейках, веб считает рублями
- Место: API `total: order.totalKopecks`. Веб: `` `${o.total} ₽` ``.
- Итог: сумма завышена в 100 раз. Заказ на 360 ₽ показан как «36000 ₽», 1260 ₽ как «126000 ₽». Это видно на всех карточках,
  которые вообще открываются.

### 5. Курьер стал объектом
- Место: API `courier: { name, phone } | null`. Веб читает `o.courierName`.
- Итог: в карточке пустое значение (`undefined`) вместо имени курьера, даже когда курьер назначен. Телефон курьера не
  показывается вообще. Это поведение 2.3.2 без исправления 009870e.

### 6. Архивные заказы: другой тип ошибки 404
- Место: API `archivedOrder` отвечает `404 { type: 'not_found' }`, а для обычных заказов `{ type: 'order-not-found' }`
  (`src/http/orders-api.js`). Веб различает только `order-not-found`.
- Итог: для отсутствующего архивного заказа (номер < 1000, которого нет в архиве, например 500) вместо «Заказ не найден»
  пользователь видит «Ошибка сервера». Внутри API типы ошибок тоже не согласованы.

### 7. Заказ из архива и чужой заказ открываются без проверки владельца
- Место: API `getOrder` не сверяет `x-customer-id` с `order.customerId` ни для архива, ни для обычных заказов.
  Это делает только `findOwnOrder` в отмене и возврате. Веб заголовок отправляет.
- Итог: клиент по номеру открывает чужой заказ (адрес, состав, курьер), например `c-117` читает архивный 905 клиента `c-301`.
  Веб при этом покажет его как свой. Это не расхождение форматов, но видно пользователю и нарушает ожидаемое поведение.

### 8. Возврат не поддержан в вебе
- Место: API `POST /api/orders/:id/return` (204) и поле `giftMessage`. В вебе нет ни вызова, ни отображения (`giftMessage`
  игнорируется).
- Итог: возврат из веба сделать нельзя. Подарочная подпись заказа (например 1047) не показывается. Сам заказ 1047 открыть
  нельзя, см. п. 2.
