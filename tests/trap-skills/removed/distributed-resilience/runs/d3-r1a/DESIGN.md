# DESIGN: BILL-42 — счёт по тарифу клиента из CRM

## 1. Решение в двух абзацах

Billing держит у себя **локальную реплику текущего тарифа каждого клиента** и считает сумму счёта по ней, не обращаясь к CRM на пути создания счёта. Реплика наполняется событиями `CustomerTariffChanged` из RabbitMQ (идемпотентно, с защитой от переупорядочивания). Синхронный `GET /v1/customers/{id}/tariff` используется только как запасной путь, когда тарифа клиента в реплике нет (новый клиент, потерянное событие), — с жёсткими лимитами.

Рассчитанные цена за единицу, скидка и версия тарифа **фиксируются в счёте** в момент создания. Дальнейшие изменения тарифа уже выставленные счета не затрагивают. При недоступности CRM счета существующих клиентов создаются как обычно; счёт клиента без тарифа в реплике получает управляемый отказ `503` + `Retry-After` с разбросом.

## 2. Почему не синхронный вызов (расхождение с ADR-0005)

ADR-0005 требует синхронного вызова справочника без кэша. Для тарифа он не подходит:

- ночная пачка (~200 тыс. счетов) совпадает с окном обслуживания CRM (1–2 ч); синхронный вызов остановит всю пачку, что противоречит требованию задачи;
- ADR-0005 обосновывает «без кэша» требованием регулятора к курсу на момент операции. Для тарифа такого требования нет: семантика «действует для счетов, созданных после изменения» допускает задержку доставки изменения (см. §7).

**Нужен ADR-0008** («Тариф клиента — реплика по событиям, не синхронный вызов»). Он ограничен областью «тариф клиента» и ADR-0005 для курсов и налогов не меняет. ADR-0008 — это §2–§4 и §7 данного документа. Принимает его команда; до этого статус Proposed.

Отвергнуто:
- *Синхронный вызов на каждый счёт* — см. выше.
- *Кэш с TTL, наполняемый вызовами* — ночью ~200 тыс. промахов приходятся на недоступный CRM; при TTL изменение виднее позже, чем по событию; нет ответа для клиента, которого ни разу не запрашивали.
- *Только события, без запасного пути* — новый клиент или потерянное событие превращаются в постоянный отказ.

## 3. Модель домена (контекст Billing)

Тариф в Billing — собственная модель на языке Billing; имена полей CRM остаются в anti-corruption слое (Infrastructure) и в домен не попадают.

**`CustomerTariff`** — отдельный агрегат (идентичность — `CustomerId`), одна запись на клиента, коллекций нет, растущих без границы частей нет.
- `UnitPrice: Money` (минорные единицы + валюта, ADR-0004);
- `Discount: DiscountRate` — value object, доля в базисных пунктах (целое 0..10000); конечный формат в CRM уточнить (§10);
- `EffectiveFrom: DateTimeOffset` — время изменения по CRM, она же версия тарифа;
- метод `Replace(candidate)` — единственный способ сменить состояние: принимает кандидата, только если `EffectiveFrom` строго новее текущего; возвращает исход `Applied | Stale`. Переход состояния не выносится в хендлер;
- метод `PriceFor(quantity)` → `Result<InvoicePricing>`: считает сумму. Формула: `gross = unitPrice.Minor * quantity` (checked, переполнение — `ValidationError`), `amount = gross − gross * discount / 10000`; округление банковское (`ToEven`), один раз в конце (ADR-0004). Расчёт — чистая доменная логика, проверяемая юнит-тестом без HTTP.

**`InvoicePricing`** — value object внутри `Invoice`: `Quantity`, `UnitPrice`, `Discount`, `TariffVersion` (= `EffectiveFrom` применённого тарифа). Хранится, потому что читатель есть: объяснение суммы клиенту/при споре и аудит («по какому тарифу выставлено»). Эти значения нельзя вывести из `Amount` после следующей смены тарифа. `Amount` остаётся хранимой суммой (по ней идут проводки), `Invoice` создаётся только через методы сущности, а не через публичный `init` всех полей — для нового пути создания вводится фабрика `Invoice.Create(customer, pricing, dueDate, now)`, внутри которой `Amount` берётся из `pricing`, и переход в `Issued` делает сама сущность.

Транзакция создания счёта меняет один агрегат (`Invoice`); `CustomerTariff` только читается. Событие тарифа меняет один агрегат `CustomerTariff`. Агрегаты не делят транзакцию.

Новые ошибки (`BillingError`, ADR-0002): `TariffNotFoundError` (у клиента нет тарифа в CRM → `422`, `tariff.not_found`), `TariffUnavailableError` (тарифа нет в реплике и CRM недоступна → `503`, `tariff.unavailable`, заголовок `Retry-After`). Маппинг добавить в `ResultHttpExtensions`.

## 4. Поток создания счёта

`CreateInvoiceHandler` (команда меняется на `CustomerId, Quantity, DueDate`; сумма и валюта больше не приходят от вызывающего):

1. валидация (количество > 0, верхняя граница; клиент задан);
2. проверка ключа идемпотентности (§5): ключ уже есть → вернуть тот же `InvoiceId`;
3. `ICustomerTariffRepository.FindAsync(customerId)` — чтение по первичному ключу, без сети;
4. нет в реплике → порт `ITariffSource.FetchAsync(customerId)` (HTTP к CRM, §6), результат записывается в реплику тем же `Replace` (по тем же правилам версии);
5. `tariff.PriceFor(quantity)` → `Invoice.Create(...)`, `AddAsync` вместе с записью ключа идемпотентности — одна транзакция; проводка в Ledger — как сейчас (outbox, ADR-0006), не меняется.

Валюта счёта — валюта тарифа.

## 5. Контракт API

`POST /invoices`
- Запрос: `{ customerId, quantity, dueDate }`; заголовок `Idempotency-Key` обязателен.
- `201 { id }`; повтор с тем же ключом — `201`/`200` с тем же `id`, без второго счёта.
- Ошибки: `422 tariff.not_found`, `422 validation`, `503 tariff.unavailable` + `Retry-After`.
- Контракт ломающий (`amountMinor`, `currency` убираются). Поддержка обеих форм одновременно неоднозначна (чья сумма главнее), поэтому — переключение вместе с вызывающими (в первую очередь ночная пачка), согласовать срок. Версионирование пути не вводим: потребителей мало и они известны.

Идемпотентность нужна независимо от CRM: пачка повторяет запросы после `503`/таймаута, без ключа повтор даёт дубль счёта. Хранение: `invoice_idempotency(key PK, invoice_id, created_at)`, чистка по сроку (напр. 7 суток). Ключ обязателен только на этом эндпоинте.

Событие (входящее, контракт CRM): `CustomerTariffChanged { customerId, tariff, changedAt }`. Billing ничего в брокер не публикует.

## 6. Хранилище

Текущий код — in-memory (`Infrastructure/Persistence`); ниже схема для боевой СУБД, реализация за теми же портами.

`customer_tariffs`
- `customer_id` — PK (чтение по ключу, ~сотни–тысячи в секунду выдерживает без дополнительных индексов);
- `unit_price_minor bigint`, `currency char(3)`, `discount_bp int`;
- `effective_from timestamptz` — версия.

Запись — один атомарный upsert: `INSERT … ON CONFLICT (customer_id) DO UPDATE … WHERE excluded.effective_from > customer_tariffs.effective_from`. Благодаря условию:
- дубликаты (at-least-once) не меняют состояние;
- события в другом порядке не откатывают тариф на старый;
- конкурентные потребители и запасной путь не портят друг друга.
Если `effective_from` равен, а содержимое различается — оставляем имеющееся, пишем warning (CRM нарушила инвариант).

Отдельной таблицы истории тарифов нет: нужное для аудита записано в счёт (`InvoicePricing`). Колонок `received_at`/`updated_at` без читателя не вводим.

`invoices`: добавляются `quantity`, `unit_price_minor`, `discount_bp`, `tariff_version`; уже существующие счета остаются без них (nullable только для старых строк).

`invoice_idempotency` — см. §5.

Репозиторий тарифов: `FindAsync(CustomerId)` и `ApplyAsync(CustomerTariff candidate)` — узкие методы, specification не нужен (простой запрос).

## 7. Согласованность и «действует для созданных после изменения»

- Реплика догоняет CRM с задержкой доставки события. Счёт, созданный в окне между изменением и применением события, будет выставлен по прежнему тарифу. Это принятая цена автономности; в счёте записан `TariffVersion`, так что причина видна. Цель по задержке (предложение): p99 < 1 мин; алерт на > 5 мин (§9).
- Задержка в нормальном режиме мала, при недоступности брокера/CRM растёт; в этот период новые изменения тарифов не видны — по требованию задачи создание счёта от CRM не зависит.
- Потерянное событие (редко при at-least-once, но возможно при сбросе очереди): запасной путь покрывает только отсутствующий тариф, не устаревший. Для сверки нужна выгрузка от CRM (§10); без неё ограничиваемся метриками.

## 8. Failure modes

| Что случилось | Поведение | Механика |
|---|---|---|
| CRM в обслуживании 1–2 ч (ночная пачка) | Существующие клиенты — счета создаются по реплике, без деградации | Путь создания не ходит в CRM при наличии тарифа |
| То же, клиента нет в реплике | `503 tariff.unavailable` + `Retry-After` | Быстрый отказ, не зависание потока |
| Рост нагрузки ×10 (3 млн/сут, ~2 млн в ночь) | Чтение по PK, узкое место — запись счёта и outbox, не тариф | Реплика не добавляет внешних вызовов; масштабирование — репликами Billing |
| Массовые промахи реплики (холодный старт, пустая реплика) | Лавина запросов в CRM не допускается | Bulkhead: лимит параллельных вызовов к CRM (напр. 20); single-flight на `CustomerId`; circuit breaker; сверх лимита — `503`, не очередь потоков |
| Окончание простоя CRM: пачка повторяет накопившееся | Повторы не должны прийти синхронным валом | Повторы клиента CRM — `AddStandardResilienceHandler` (ADR-0007) с `UseJitter = true` и ограниченным числом попыток; `Retry-After` в `503` задаётся случайным в диапазоне (напр. 30–120 с), чтобы пачка не возвращалась одномоментно; вызывающей стороне пачки — требование повторять с экспоненциальной задержкой и разбросом |
| RabbitMQ недоступен / отставание очереди | Реплика устаревает, счета создаются по последнему известному тарифу | Метрика отставания, алерт; потребитель переподключается сам |
| Дубли и перестановка событий | Не влияют | Upsert по версии (§6) |
| «Ядовитое» сообщение | Не блокирует очередь | Ограниченное число повторов → dead-letter очередь, алерт |
| Падение Billing между записью счёта и ответом | Повтор запроса даёт тот же счёт | Идемпотентность (§5) |

Запасной путь к CRM: короткий таймаут попытки и общий таймаут запроса (цель — не более нескольких секунд), потому что за ним стоит пользовательский/пакетный запрос; точные значения — в `CrmTariffOptions` по образцу `FxOptions`/`LedgerOptions`.

## 9. Observability

Метрики:
- `tariff_replica_lag_seconds` (now − `changedAt` последнего применённого события) — главный SLI актуальности;
- `tariff_events_total{outcome=applied|stale|duplicate|failed}`, длина очереди и dead-letter очереди;
- `tariff_lookup_total{source=replica|crm_fallback|miss}`, длительность и ошибки запасного вызова, состояние circuit breaker, занятость bulkhead;
- `invoice_create_total{result}` с разбивкой по кодам ошибок `tariff.*`; доля `503` в пачке.

Логи (структурные, `ILogger<T>`): применённая/пропущенная версия тарифа с `customerId` и версиями; warning на равный `effective_from` с разным содержимым; открытие breaker. Суммы и тарифы в лог не пишем сверх нужного.

Трассировка: span на создание счёта с атрибутом `tariff.source`; контекст трассы из сообщения RabbitMQ в потребителе, если CRM передаёт заголовки.

Health: liveness — процесс жив. Readiness — доступна СУБД и потребитель очереди запущен; **недоступность CRM readiness не роняет** (иначе мы сами создадим нужный нам отказ). Алерт, а не readiness, — отставание реплики больше порога.

## 10. Структура и размещение кода

Срез по фиче внутри существующих слоёв (структура проекта: Domain / Application / Infrastructure — без `Shared`/`Common`):

- `Domain/`: `CustomerTariff`, `DiscountRate`, `InvoicePricing`, ошибки тарифа; `Invoice.Create`.
- `Application/Abstractions/`: `ICustomerTariffRepository`, `ITariffSource` (порт запасного пути).
- `Application/Handlers/CustomerTariffs/ApplyCustomerTariffHandler` (+ валидатор рядом, RUL-0003) — применяет кандидата из события и из запасного пути; `Application/Handlers/Invoices/CreateInvoiceHandler` — изменяется.
- `Infrastructure/Crm/`: `CrmTariffClient` (HTTP, ADR-0007), `CrmTariffOptions`, DTO CRM и перевод в `CustomerTariff` (ACL), потребитель RabbitMQ `CustomerTariffChangedConsumer`.
- `Infrastructure/Persistence/`: реализации репозитория тарифов и идемпотентности.
- `Modules/CrmModule.cs` — регистрация клиента и потребителя по образцу `LedgerModule`/`FxModule`.

Новые проекты не вводятся; зависимости только внутрь (Infrastructure → Application → Domain). Потребитель вызывает хендлер, не репозиторий напрямую. Тесты в MR — по RUL-0002 не требуются задачей; логику расчёта и `Replace` рекомендуется покрыть юнит-тестами домена при реализации.

## 11. Открытые вопросы к команде Sales (CRM)

1. Формат скидки (процент, доля, базисные пункты) и валюты цены; допустима ли разная валюта у клиентов.
2. Поведение для клиента без тарифа: `404` или тариф по умолчанию?
3. Гарантируется ли монотонность `changedAt` на клиента и точность до миллисекунды.
4. Начальная загрузка и сверка: есть ли пакетная выгрузка/повтор событий (replay) для наполнения реплики и исправления потерь? Без неё первый запуск наполняется запасным путём.
5. Допустимая нагрузка на `GET /v1/customers/{id}/tariff` и рекомендуемый rate limit.
6. Заголовки трассировки и ключ сообщения в RabbitMQ (маршрутизация по `customerId` сохранила бы порядок на клиента).

## 12. Порядок внедрения

1. ADR-0008 принять.
2. Миграции хранилища, домен, потребитель событий — реплика наполняется, на счета не влияет.
3. Начальное наполнение (§10 п.4).
4. Запасной путь, идемпотентность, новый контракт `POST /invoices`; переключение вызывающих вместе со старым контрактом по согласованному сроку.
