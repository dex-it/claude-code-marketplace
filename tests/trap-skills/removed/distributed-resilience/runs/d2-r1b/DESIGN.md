# DESIGN: BILL-41 - оплата счёта с баланса Wallet

Статус: предложение. Код не пишется, документ - вход для реализации и ADR.

## 1. Суть решения

Wallet - внешний сервис без общей транзакции с нашей БД. Двойное списание и потеря денег исключаются
сочетанием трёх вещей:

1. **Состояние попытки оплаты живёт в агрегате `Invoice`** и меняется только его методами; захват
   счёта под оплату - короткая транзакция с оптимистичной проверкой версии.
2. **Вызов Wallet идёт вне транзакции БД** с детерминированным `Idempotency-Key`, который выводится
   из счёта и номера попытки. Любой повтор (другая реплика, восстановление после падения, второй клик)
   шлёт тот же ключ, Wallet возвращает прежний результат.
3. **Всё, что после списания, идёт через outbox в той же транзакции, что `Paid`**: проводка Ledger
   (ADR-0006), чек, и при отмене - возврат на баланс. Ledger и Notifications на оплату не влияют.

Неопределённый исход вызова Wallet (таймаут, 5xx, обрыв) - не ошибка и не «не оплачено»: счёт остаётся
в `PaymentPending`, а повтор с тем же ключом доводит оплату до конца.

## 2. Домен

Домен говорит словами Billing («оплата», «попытка»), а не словами Wallet: `debits`, `credits`,
`Idempotency-Key` остаются в Infrastructure.

### Invoice (единственный агрегат в сценарии)

Новый статус `PaymentPending` (в JSON - строкой, контракт с фронтом, коммит 2ca40d4). Граф:

```
Issued --BeginPayment--> PaymentPending --CompletePayment--> Paid
                              |--DeclinePayment--> Issued
Paid --Cancel--> Cancelled      Issued --Cancel--> Cancelled      (из PaymentPending - нельзя)
```

Новые хранимые поля, у каждого есть читатель:

| Поле | Читатель |
|---|---|
| `PaymentAttempt` (int, 0 по умолчанию) | выводит ключ идемпотентности `invoice-payment-{InvoiceId}-{PaymentAttempt}` |
| `LastPaymentAttemptAt` (timestamptz?) | срок аренды `PaymentPending` (восстановление) и отбор ночного задания «сегодня ещё не пробовали» |
| `PaidFromWallet` (bool) | `CancelInvoiceHandler`: нужен ли возврат на баланс |

Ключ в БД не хранится - он выводится из `InvoiceId` и `PaymentAttempt`. Истории попыток нет:
коллекция не растёт, а журнал при необходимости - логи и метрики.

Методы (переходы только через них, публичных сеттеров нет):

- `BeginPayment(now, lease)` - из `Issued`: `PaymentAttempt` увеличивается **только если предыдущая
  попытка завершилась отказом** (`LastPaymentAttemptAt` задан, статус `Issued`), ставит `PaymentPending`
  и `LastPaymentAttemptAt = now`. Из `PaymentPending` с истёкшей арендой - «возобновление»: номер
  попытки тот же, ключ тот же, аренда продлевается. Из `PaymentPending` с живой арендой - отказ
  `PaymentInProgress`. Из остальных статусов - `InvoiceInvalidStateError`.
- `CompletePayment(now)` - из `PaymentPending`: `Paid`, `PaidAt`, `PaidFromWallet = true`. Из `Paid`
  идемпотентно возвращает «уже сделано» (чтобы два конкурирующих завершения не удвоили outbox).
- `DeclinePayment()` - из `PaymentPending` обратно в `Issued`; следующая попытка получит новый номер.

Почему номер попытки, а не один ключ на счёт: если Wallet запоминает и отказы, повтор с тем же
ключом после пополнения баланса вернул бы старый отказ. Номер растёт только после **подтверждённого**
отказа; при неопределённом исходе ключ не меняется, поэтому двойного списания нет.

Новые ошибки (ADR-0002): `PaymentInProgressError` (`invoice.payment_in_progress`),
`PaymentDeclinedError` (`payment.declined`, с причиной - `InsufficientFunds`, `WalletBlocked`,
`CurrencyMismatch`), `PaymentOutcomeUnknownError` (`payment.outcome_unknown`).

### Что не агрегат

Исход `Charged/Declined/Unknown` - значение порта, а не сущность. Сообщения outbox - не агрегаты.
В одной транзакции всегда один счёт и его outbox-записи.

## 3. Слои и структура

Остаёмся в существующей структуре (один проект `Billing.Api`, папка на слой): сценариев мало,
отдельных проектов слоёв и `Shared` не заводим, цикла зависимостей нет: Domain ← Application ←
Infrastructure/Api.

Application (хендлеры по RUL-0003):

- `Handlers/Invoices/PayInvoiceFromWalletHandler.cs` (+ `PayInvoiceFromWalletCommand(InvoiceId)`):
  один хендлер на ручную оплату, ночное задание и восстановление - так это один и тот же код пути.
- Правка `CancelInvoiceHandler`: для `Paid` с `PaidFromWallet` в той же единице работы кладёт
  `WalletRefundRequested` (без этого отмена оплаченного с баланса счёта теряет деньги клиента).
- `Abstractions/IWalletGateway.cs`: `ChargeAsync(CustomerId, Money, PaymentKey, ct)` →
  `WalletChargeOutcome` (`Charged`, `Declined(reason)`, `Unknown`) и `RefundAsync(...)`. Сетевая
  неопределённость - значение `Unknown`, не исключение; исключение - для ошибки программиста.
- `Abstractions/IInvoiceRepository.cs`: добавляется один метод выбора кандидатов ночного задания -
  `ListIdsDueForAutoPaymentAsync(dueOn, attemptedBefore, afterId, limit)` (keyset, только `InvoiceId`).
  Specification-базы в проекте нет, дублирующей пары «метод + specification» не возникает.
  `ListByStatusAsync` для 40 тысяч счетов не применяется.
- `Messages/WalletRefundRequested.cs`, `Messages/ReceiptRequested.cs`.
- `LedgerPostingRequested` с `ExternalId = pay-{InvoiceId}` - то же соглашение, что у существующего
  `PayInvoiceHandler`, поэтому Ledger не примет вторую проводку на тот же счёт. `ILedgerGateway` в
  новом коде не используется (ADR-0006).

Infrastructure:

- `Infrastructure/Wallet/` - `WalletClient`, `WalletOptions`, `WalletGateway` (маппинг на
  `POST /wallets/{customerId}/debits|credits` и `Idempotency-Key`), `WalletRefundDispatcher`.
- `Infrastructure/Notifications/` - `NotificationsClient`, `ReceiptOutboxDispatcher`.
- `Infrastructure/Wallet/WalletAutoPayJob.cs` - `BackgroundService`, ночное задание.
- `Modules/WalletModule.cs`, `Modules/NotificationsModule.cs` - регистрация, как `LedgerModule`.
- Api: `POST /invoices/{id:guid}/pay-from-wallet` в `InvoiceEndpoints`.

Старый `/invoices/{id}/pay` и `PayInvoiceHandler` не трогаем (его долг по ADR-0006 - отдельная
правка). Он уже требует `Status == Issued`, поэтому счёт в `PaymentPending` им не оплатить:
взаимное исключение с новым путём даёт состояние, а не договорённость.

Бизнес-логику проверяет юнит-тест без HTTP: `Invoice` (граф переходов) и хендлер с подменой
`IWalletGateway`. Тесты в MR - если их потребует задача (RUL-0002); для проверки сценариев ниже они
рекомендуются.

## 4. Последовательность оплаты (ручная и автоматическая)

1. **Tx1 (короткая).** Загрузить счёт, `BeginPayment`, сохранить с проверкой версии
   (`UPDATE ... WHERE id = @id AND version = @v`). Конфликт версии - читаем счёт заново: если он уже
   `PaymentPending` - `PaymentInProgress`; если `Paid` - «уже оплачен»; в ночном задании - пропуск.
   Соединение с БД возвращается в пул до вызова Wallet.
2. **Вызов Wallet** `ChargeAsync(customerId, amount, ключ)` без транзакции.
3. **Исход:**
   - `Charged` → **Tx2:** `CompletePayment` + в outbox `LedgerPostingRequested` + `ReceiptRequested`;
     одна транзакция, одна проверка версии. Если версия ушла (конкурент уже завершил) - перечитать,
     `Paid` - успех без повторной записи в outbox.
   - `Declined` → `DeclinePayment`, сохранить, вернуть `PaymentDeclinedError` (ручная: 409/422 по
     таблице `ResultHttpExtensions`; ночная: учесть и идти дальше).
   - `Unknown` → ничего не менять: счёт остаётся `PaymentPending`. Ручная оплата отвечает `202
     Accepted` с `payment.outcome_unknown`; кабинет показывает «оплата обрабатывается».
4. Падение реплики между шагами 1 и 3 - счёт остаётся `PaymentPending`; по истечении аренды
   (раздел 7) любая реплика повторяет шаг 2 с тем же ключом. Если списание уже прошло, Wallet вернёт
   прежний успех, и шаг 3 завершится без второго списания. Если Tx2 не удалась после успешного
   списания - то же самое.

Ручная оплата выполняет шаги 1-3 синхронно с собственным бюджетом 25 секунд (linked
`CancellationToken`). Бюджет исчерпан - ответ `202`, дальше счёт доводит восстановление. Запрос
пользователя не висит минуту+ из-за повторов конвейера.

## 5. Как исключено двойное списание

| Угроза | Защита |
|---|---|
| Клик в кабинете и ночное задание одновременно | `BeginPayment` под проверкой версии: выигрывает один; проигравший получает `PaymentInProgress`/пропуск |
| Три реплики запускают задание | Состояние на счёте + лидерство (раздел 7); корректность от лидерства не зависит |
| Повтор после таймаута или падения | Тот же ключ `invoice-payment-{id}-{attempt}`, Wallet возвращает прежний результат |
| Повтор конвейера устойчивости внутри одного вызова | Тот же ключ (запрос неизменён); POST с ключом безопасно повторять |
| Аренда истекла, а исходный вызов ещё жив (Wallet отвечает до 40 с) | Оба шлют один ключ; завершение идемпотентно (`CompletePayment` из `Paid`) |
| Отмена счёта во время оплаты | `Cancel` из `PaymentPending` запрещён |
| Старый `/pay` на тот же счёт | Требует `Issued` |
| Отказ → новая попытка | Новый номер попытки только после подтверждённого `Declined` |
| Ledger дважды | `ExternalId = pay-{id}` уникален, outbox - at-least-once, Ledger дедуплицирует |

Потеря денег: списание без `Paid` невозможно «насовсем» - счёт остаётся `PaymentPending`, и
восстановление доводит его до `Paid`; `Paid` + проводка + чек пишутся атомарно; отмена оплаченного
счёта возвращает деньги через `WalletRefundRequested`.

## 6. Хранение (Postgres, BILL-34)

Предусловие: `IOutbox` должен лежать в той же БД, что счета. Нынешние `InMemory*` не дают единицы
работы между счётом и outbox - реализация на Postgres обязательна до включения функции.

`invoices` (изменения):

- `status text not null` - добавляется значение `PaymentPending`;
- `payment_attempt int not null default 0`;
- `last_payment_attempt_at timestamptz null`;
- `paid_from_wallet boolean not null default false`;
- `version int not null` (оптимистичная блокировка; если BILL-34 уже ввёл версию - используем её).

Индексы:

- частичный `(due_date, id) WHERE status = 'Issued'` - выборка кандидатов ночи;
- частичный `(last_payment_attempt_at) WHERE status = 'PaymentPending'` - восстановление.

`outbox` (по ADR-0006, если ещё не такой): `id uuid pk`, `type text`, `payload jsonb`,
`created_at`, `sent_at null`, `attempts int`, `next_attempt_at`. Индекс `(next_attempt_at) WHERE
sent_at IS NULL`. Диспетчеры берут записи `FOR UPDATE SKIP LOCKED` (три реплики не отправляют одно и
то же), разные `type` обрабатываются разными диспетчерами.

Автосписание включено у клиента - данные, которых в Billing нет (см. вопрос 1). Предлагается таблица
`customer_payment_settings(customer_id pk, auto_pay_enabled bool)` внутри Billing; выбор кандидатов
присоединяет её на чтение, в агрегат `Invoice` флаг не попадает.

## 7. Ночное задание

`WalletAutoPayJob` - `BackgroundService`, работает на каждой реплике, но активна одна.

- **Лидерство.** Перед проходом `pg_try_advisory_lock(<ключ задания>)` на выделенном соединении;
  неудача - пауза и повторная попытка. Если лидер упал, соединение закрывается и замок берёт другая
  реплика; проход продолжается с того места, где остановился, потому что прогресс - состояние
  счетов. Корректность (раздел 5) от замка не зависит, он только убирает 3-кратную конкуренцию.
- **Окно.** Запуск ночью по расписанию; кандидат - `status = Issued`, `due_date <= сегодня`,
  автосписание включено, `last_payment_attempt_at` раньше начала сегодняшних суток (счёт с отказом
  не долбим каждые минуты; следующая попытка - следующей ночью). Дата «сегодня» - вопрос 3.
- **Обход.** Keyset-страницы по `(due_date, id)`, по 500 id, затем для каждого `PayInvoiceFromWalletHandler`
  - тот же код, что у ручной оплаты.
- **Конкурентность.** Не более 16 одновременных оплат (настройка), общий `SemaphoreSlim` на процесс
  также ограничивает ручные оплаты. 40 тысяч при медианной задержке ~1 с - около 40 минут; при
  деградации Wallet до 10 с и выше окно растягивается, это нужно обсудить с Payments (вопрос 4).
- **Деградация Wallet.** Подряд идущие `Unknown` (порог 10) - задание ставит себя на паузу,
  не захватывая новые счета (иначе 40 тысяч счетов окажутся в `PaymentPending`). Пауза - экспоненциальная
  со **случайным разбросом** (full jitter, 30 с .. 5 мин), после неё один пробный счёт; успех - наращиваем
  параллелизм ступенями 1 → 4 → 16. Так три реплики и пачка счетов не бьют по только что поднявшемуся
  Wallet одновременным залпом.
- **Восстановление.** Каждый проход (и отдельный тик раз в минуту) сначала забирает
  `PaymentPending` с `last_payment_attempt_at < now - lease` и прогоняет их тем же хендлером с тем же
  ключом. Аренда = 2 минуты (больше полного таймаута конвейера Wallet, раздел 8); повторы идут с тем же
  jitter и тем же ограничителем параллелизма.
- **Долгий неопределённый исход.** Счёт, остающийся `PaymentPending` дольше 24 ч - алерт для ручной
  сверки с Payments; повторы продолжаются тем же ключом (безопасно).
- **Остановка.** По `stoppingToken` задание заканчивает текущие вызовы, новых не берёт; недоделанное
  подберёт восстановление.

## 8. HTTP-клиенты и изоляция

Правила ADR-0007: каждый клиент - `AddHttpClient<T>` + `AddStandardResilienceHandler()`; `AddPolicyHandler`
не используется. `FxRatesClient` не правим, его перевод - при его следующей правке.

**WalletClient** - собственный клиент и собственный конвейер, не общий с FX:

- таймаут попытки 45 с (Wallet отвечает до 30-40 с; стандартные 10 с дали бы ложные таймауты и лишние
  повторы), общий таймаут запроса 100 с, повторы - 2 (метод небезопасный, но запрос с ключом
  идемпотентен, повторы разрешены), `SamplingDuration` circuit breaker не меньше удвоенного таймаута
  попытки (требование библиотеки);
- ограничение соединений `SocketsHttpHandler.MaxConnectionsPerServer` на этом клиенте;
- открытый breaker → `Unknown`-подобный исход «не отправлено»: ночное задание уходит в паузу
  (раздел 7), ручная оплата отвечает `202`/`503` без захвата счёта, если breaker открыт до шага 1.

**Почему котировки не пострадают.** FX и Wallet - разные клиенты, пулы соединений и breaker-ы;
соединение с БД не держится во время вызова Wallet, поэтому медленный Wallet не опустошает пул,
которым пользуется `/quote`; параллелизм оплат ограничен семафором; задание идёт ночью, вне пика
продаж. Если на практике этого мало, задание выносится в отдельную роль развёртывания (тот же образ
с флагом) - в этой правке не делаем.

**NotificationsClient** - свой конвейер, короткие таймауты (попытка 5 с).

## 9. Сбои соседей

| Сосед | Поведение |
|---|---|
| Wallet медленный (до 40 с) | Таймаут попытки 45 с; ручная оплата отдаёт `202` после 25 с; ночное задание снижает параллелизм по пороговой логике |
| Wallet лежит 3-5 минут | Подряд `Unknown` → пауза с jitter; счета в `PaymentPending` доводит восстановление; breaker не даёт копить вызовы |
| Wallet лежит до 30 минут | То же; новые счета не захватываются; алерты (раздел 10); при росте очереди - выключатель задания в конфиге |
| Wallet отвечает отказом | `DeclinePayment`, счёт `Issued`, следующая попытка следующей ночью |
| Ledger недоступен | Оплата проходит; проводки копятся в outbox, диспетчер повторяет (ADR-0006) |
| Notifications недоступны/медленные | Оплата проходит; `ReceiptRequested` повторяется ограниченно (5 попыток, растущая пауза с jitter, до ~1 ч), затем отбрасывается с метрикой - чек некритичен |
| Postgres недоступен | Оплата не начинается; если упал Tx2 - счёт `PaymentPending`, довод восстановлением |
| Падение реплики | См. шаг 4 раздела 4; аренда и лидерство переходят к живой реплике |

Рост нагрузки в 10×: первым упирается Wallet (его собственная ёмкость, не наша) - защищают
ограничитель параллелизма, пауза задания и breaker; вторым - outbox-диспетчеры (пачка проводок за ночь
~40 тысяч): диспетчер Ledger остаётся последовательным, но с `SKIP LOCKED` его можно масштабировать,
пока Ledger переносит; лаг outbox - метрика.

## 10. Наблюдаемость

Метрики: `wallet_charge_total{outcome}`, `wallet_charge_duration_seconds`, `invoices_payment_pending`
(gauge) и возраст старейшего, `autopay_run_{candidates,paid,declined,unknown}`, `autopay_paused`,
`outbox_lag_seconds{type}`, `outbox_dead_total{type}`, `payment_cas_conflicts_total`.

Логи (структурные, через `ILogger<T>`, как требует предложенный RUL-0004): `InvoiceId`, `PaymentAttempt`,
ключ, исход, номер ретрая; без сумм и данных клиента сверх `CustomerId`.

Трейсы: корневой span на оплату, дочерние - Tx1, вызов Wallet, Tx2; ключ - атрибутом span.

Алерты: `PaymentPending` старше 24 ч; breaker Wallet открыт более 10 мин; лаг outbox Ledger > 15 мин;
ночное задание не завершилось к концу окна; любой `Declined` по причине `CurrencyMismatch`.

Liveness - без зависимостей. Readiness - БД; недоступность Wallet и Notifications readiness **не**
снимает (иначе реплики уйдут из-под балансировщика и перестанут отдавать `/quote`).

## 11. API

`POST /invoices/{id}/pay-from-wallet` (тело пусто):

| Код | Когда |
|---|---|
| `204` | оплачен |
| `202` + `{code: "payment.outcome_unknown"}` | исход неизвестен, оплату доведёт восстановление; повторный вызов безопасен |
| `404` | `invoice.not_found` |
| `409` | `invoice.invalid_state` / `invoice.payment_in_progress` |
| `422` | `payment.declined` с причиной в `code`-деталях |

Идемпотентность: повторный вызов безопасен по построению (состояние + ключ Wallet), отдельный заголовок
`Idempotency-Key` от кабинета не нужен. События наружу не публикуются; статус счёта - `PaymentPending`
- строкой, и это новое значение enum нужно согласовать с фронтом заранее.

## 12. Допущения и открытые вопросы

Нужны ответы до реализации; решение построено так, чтобы не зависеть от «неудобного» ответа, но
параметры изменятся.

1. Где хранится «автосписание включено»? Принято: таблица внутри Billing (раздел 6); если флаг у
   другой команды - порт чтения вместо таблицы.
2. Контракт Wallet: коды ответа для отказов (недостаточно средств, чужая валюта) и неопределённости;
   хранит ли он отказы по ключу; срок хранения ключа (должен быть не меньше суток); есть ли чтение
   результата по ключу. Допущение: 2xx - успех, 4xx - подтверждённый отказ, остальное и таймаут - `Unknown`.
3. «Срок наступил» - дата по UTC или по часовому поясу клиента; время запуска ночного окна.
4. Допустимая нагрузка Wallet для 40 тысяч оплат за ночь (параллелизм 16 - допущение) и ожидаемое окно.
5. Валюта баланса и счёта: допущение - списание в валюте счёта, расхождение - `Declined(CurrencyMismatch)`;
   конвертация в эту правку не входит.
6. Нужен ли возврат на баланс при отмене оплаченного счёта (заложен, потому что иначе деньги теряются);
   процесс возврата для уже отправленных проводок Ledger - как у существующей отмены (`cancel-{id}`).

## 13. Что не делаем

Распределённых транзакций и sagas-оркестратора; кэша ответов Wallet; перевода `PayInvoiceHandler` и
`FxRatesClient` на новые ADR (отдельные правки); отдельных проектов слоёв; истории попыток; ручной
сверки в интерфейсе.

## 14. Предлагаемые ADR

- ADR-0008: оплата с внешнего баланса - состояние попытки в агрегате, детерминированный ключ
  идемпотентности, вызов вне транзакции, outbox после списания.
- ADR-0009: фоновые задания на нескольких репликах - advisory lock для лидерства, корректность на
  состоянии и CAS.
