Формат: файл и место - что не так и чем кончится - уровень. Код не менялся, сборка и запуск не выполнялись, выводы сделаны по чтению кода.

- `Outbox/OutboxDispatcher.cs:12-25` (ExecuteAsync) - sync-over-async (`.GetAwaiter().GetResult()`) внутри `lock`. `TakeBatchAsync` у памяти возвращает готовый Task, поэтому до первого настоящего `await` код выполняется синхронно в `StartAsync` хоста. Один зависший POST (2 с × 3 попытки × до 50 сообщений, то есть до 5 минут) блокирует старт приложения и поток пула. При остановке хост не может завершиться: токен не проверяется внутри батча - Critical
- `Outbox/OutboxDispatcher.cs:44-46` (catch) - в `catch` идёт обращение к БД, и оно не обёрнуто в `try`. Если БД недоступна (вероятно, когда Payments тоже лежит), исключение вылетает из `ExecuteAsync`. По умолчанию .NET останавливает хост, то есть весь orders-api падает из-за сбоя фонового отправителя. Ещё одна причина падения: `ex.Message` с апострофом ломает INSERT - Critical
- `Outbox/OutboxDispatcher.cs:46` - SQL строится конкатенацией с `ex.Message` (текст ответа и исключения нам не принадлежит). Это SQL-инъекция. Любое сообщение с `'` даёт синтаксическую ошибку, и ошибка не записывается. Нужны параметры - Critical
- `Outbox/OutboxDispatcher.cs:27-49` - после 3 неудачных попыток метод молча делает `return`. Сообщение уже убрано из очереди и больше не вернётся: событие о платеже теряется без следа (запись в `outbox_errors` не считается обработкой), нет ни dead-letter, ни возврата в очередь - Critical
- `Outbox/MemoryOutboxQueue.cs:5-20` + `Outbox/IOutboxQueue.cs:7` - очередь хранится в памяти, а контракт обещает "после возврата сообщение будет доставлено". Рестарт, деплой или OOM теряют всё, что не отправлено. `TakeBatchAsync` забирает сообщения без подтверждения (нет ack/lease): падение между Take и отправкой - потеря. Это не outbox: запись не в одной транзакции с заказом (dual write), и таблица `outbox` из `MarkSentAsync` с этой очередью не связана - Critical
- `Outbox/OutboxDispatcher.cs:36-40` - у отправки семантика at-least-once без защиты от дублей. Если POST прошёл, а `MarkSentAsync` упал (он внутри того же `try`), исключение считается ошибкой публикации и запрос повторяется. Платёж создаётся повторно, если Payments не дедуплицирует по `Id` (в тело `Id` уходит, но заголовка Idempotency-Key нет и контракта нет). `_published` при этом уже увеличен - Critical

Компонент не работает совсем. Если зарегистрировать только диспетчер без именованного клиента с `BaseAddress`, относительный URI `/payments/create` даст `InvalidOperationException` на каждой попытке - Critical

После перехода на таблицу это даст повторную рассылку. Нет захвата строк (`FOR UPDATE SKIP LOCKED`), поэтому две реплики будут слать одно и то же - Medium
