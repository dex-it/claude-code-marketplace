# AUDIT: services/orders-api/Outbox

Формат: файл и место - что не так и чем кончится - уровень.

- `IOutboxQueue.cs:7`, `PgOutboxQueue.cs:9-16` (EnqueueAsync) - запись в outbox идёт отдельным соединением и транзакцией, не той, где сохраняется заказ; это двойная запись, а не outbox: если упадёт процесс или БД между сохранением заказа и Enqueue (или наоборот), заказ останется без платежа либо платёж уйдёт по несохранённому заказу - Critical
- `Program.cs:6-7`, `Orders/OrderService.cs` - `OutboxDispatcher`, `IOutboxQueue`, именованный HttpClient `payments` (нужен `BaseAddress`, иначе относительный `/payments/create` падает) не зарегистрированы, и `EnqueueAsync` нигде не вызывается; сейчас компонент не работает вообще: платежи не создаются, ошибок при этом не видно - Critical
- `OutboxDispatcher.cs:22-27` + `PgOutboxQueue.cs:22` - любая неудача публикации (в том числе постоянная, например 400) оставляет строку в outbox; через 30 с она снова берётся, без счётчика попыток, backoff и dead-letter. Выборка идёт по `created_at`, поэтому 50 «ядовитых» старых сообщений навсегда занимают весь батч и блокируют доставку новых (head-of-line blocking); платежи встают, в логах только Warning - Critical
- `OutboxDispatcher.cs:22-27,37` + `PgOutboxQueue.cs:22` - блокировка фиксированная (30 с), а батч из 50 сообщений обрабатывается последовательно; у HttpClient таймаут по умолчанию 100 с и нет продления лока. При медленном payments лок хвоста батча истекает, другой экземпляр (или следующая итерация) берёт те же сообщения, и один платёж создаётся параллельно дважды; спасает только то, что payments действительно соблюдает `Idempotency-Key` - Critical
- `OutboxDispatcher.cs:37-44` - после успешного POST отметка `sent_at` пишется отдельным запросом; если БД недоступна или произошла отмена, платёж создан, а строка остаётся неотправленной и уходит повторно (дубль, если payments не дедуплицирует ключ). Исключение глотается как Warning, а `_published` уже увеличен, то есть метрика врёт - Medium
- `OutboxDispatcher.cs:22-27` / `PgOutboxQueue.cs:22` - порядок не гарантируется: `returning` не сохраняет порядок `created_at`, несколько экземпляров берут разные сообщения одного заказа параллельно, повторная доставка идёт позже следующих. Если для платежей важна очерёдность событий заказа (создание - отмена), она нарушится - Medium
- `OutboxDispatcher.cs:28` - после каждого батча безусловная пауза 1 с, даже если батч полный: пропускная способность не больше 50 сообщений/с на экземпляр минус время HTTP (при последовательной отправке и 100-мс ответах реально около 10/с). Пиковая нагрузка копит бэклог, задержка платежей растёт без предела; в простое каждый экземпляр раз в секунду опрашивает БД - Medium
- `PgOutboxQueue.cs:22` - таблица outbox не чистится: отправленные строки копятся вечно; без частичного индекса по `(created_at) where sent_at is null` запрос с `order by created_at ... for update skip locked` со временем деградирует до сканирования и блокирует всё больше строк. Индексов и ретенции в репозитории нет - Medium
- `OutboxDispatcher.cs:42` - `update ... set sent_at = now()` без условия `sent_at is null` и без проверки владения локом: при повторной доставке `sent_at` перезаписывается, а запоздавший воркер снимает чужой лок (`locked_until = null`). Данные искажаются, но потерь нет - Minor
- `OutboxDispatcher.cs:40-44` - на каждое сообщение открывается новое соединение к БД (из пула) ради одного UPDATE; при 50 сообщениях подряд лишняя нагрузка на пул и 50 отдельных round-trip вместо одного пакетного UPDATE по id - Minor
- `OutboxDispatcher.cs:26` - при недоступном payments на каждое из 50 сообщений пишется Warning со стеком каждые ~30 с: шум в логах, нет circuit breaker, сервис после восстановления получает сразу весь накопленный бэклог - Minor
- `PgOutboxQueue.cs:13` - `OutboxMessage.CreatedAt` из приложения молча отбрасывается, время ставит БД (`now()`), это согласовано с `locked_until` и `sent_at`, которые тоже считаются по времени БД (правило команды выполнено). Но контракт вводит в заблуждение: вызывающий думает, что его время сохранено; к тому же `now()` - время начала транзакции, а не коммита - Minor
- `OutboxDispatcher.cs:7,39` - `_published` инкрементируется, но нигде не читается и не экспортируется как метрика; наблюдаемости нет (ни глубины очереди, ни возраста старейшего сообщения, ни числа попыток) - Minor
- `OutboxDispatcher.cs:25` - при остановке сервиса `return` посреди батча оставляет необработанные сообщения под локом ещё до 30 с: после рестарта доставка задерживается, потерь нет - Minor
