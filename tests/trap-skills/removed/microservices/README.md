# [снят] microservices: сжатие по свидетельству, группа 1.2

Скилл `dex-skill-microservices` 1.2.1 ([`inputs/SKILL-1.2.1.md`](inputs/SKILL-1.2.1.md)), эпик #291,
группа 1.2 (#294). Итог - скилл снят целиком, строка в реестре [`tests/README.md`](../../../README.md).

Вход, исполнитель (`claude-sonnet-5-5`, effort medium, MCP нет), промпты и правило засчитывания -
общие для группы, в протоколе [solid](../../solid/README.md#заход-группы-12-2026-10-05). Со скиллом
прогонов нет: снятие по контролю. Здесь - выходы A3 (PayGate, BILL-37), D1 (взыскание, BILL-40), D2
(оплата с баланса Wallet, BILL-41), D3 (счёт по тарифу CRM, BILL-42): `runs/`. Те же прогоны A3 и D2
засчитываются [distributed-resilience](../distributed-resilience/README.md), A3 - ещё `ddd` (D-i,
D-v). Прогоны `n1`, `n2` - редакции `solid`, `ddd`, `clean-architecture`: по ним видно, что сжатие
соседей охват единиц этого скилла не сужает.

**D2 M-h и исправление сверки.** Исходная сверка D2 называла одно допустимое решение - компенсацию
(зачисление обратно) при сбое после списания или при уже оплаченном счёте. `d2-c1` выбрал вариант,
который сверка D1 M-h допускает, а D2 - нет: отмена счёта при активном списании отклоняется, прежний
путь оплаты отказывает при активной попытке, неизвестный исход доводится повтором с тем же ключом; о
компенсации молчит. По исходной сверке - провал. Сверка исправлена после `d2-c1` записью в ключе
billing с причиной (коммит `8d22684d`): «либо блокировка / порядок, исключающие такое состояние».

Исправление в пользу снятия не засчитывается. После него взяты два новых прогона контроля, `d2-c4`
и `d2-c5`; сверка к ним записана до прогона. Обе судятся и по исходной сверке:

| Прогон | Исходная сверка | Исправленная | Основание |
|---|---|---|---|
| `d2-c1` | 0 | 1 | компенсации нет, состояние исключено блокировкой |
| `d2-c2` | 1 | 1 | компенсация названа |
| `d2-c3` | 1 | 1 | компенсация названа |
| `d2-c4` | 1 | 1 | отмена выиграла гонку после списания - возврат `POST /wallets/{c}/credits` с ключом, до успеха |
| `d2-c5` | 1 | 1 | компенсация явно отвергнута с причиной: блокировка `Paying` исключает путь; возврат - ручной |

`d2-c5` по исходной сверке засчитан общим правилом проектирования ключа («ловушка явно отвергнута с
причиной»); причина отказа - блокировка, то есть вариант исправленной сверки. Компенсацию
проектируют `d2-c2`, `d2-c3`, `d2-c4`. Итог по исходной сверке - 4/5, D1 - 2/2. Провал `d2-c1` разобран
до причины (метод, шаг 3): дефект сверки, исполнитель выбрал верный дизайн; норму он не растит.
Единица снята; решение - вопрос владельцу ниже.

Основание исправления - несогласованность ключа, а не подгонка под прогон: вариант «порядок шагов,
при котором частичный сбой не оставляет расхождения» стоял в сверке D1 M-h, записанной до первого
прогона (`de84187a`), а D2 ту же единицу ловушки судил без него. Исправление выравнивает D2 по D1.

Чем M-h отличается от D-u и D-g `ddd` (контроль 2/3: 1/2 в паре и добор `a1-c3`; пункты остались):
их промахи - пропуск ситуации при согласованном ключе, такой промах сам держит единицу, и добор его
не отменяет. Единственный промах M-h - по ключу, не согласованному с D1; по согласованному ключу
пара `d2-c1`, `d2-c2` - 2/2. `d2-c4`, `d2-c5` взяты не добором к паре: сверка к ним записана до
прогона, и они судятся по исходной сверке.

**Прогоны D2.** По записи в ключе billing после ревью PR #316 каждая единица D2 судится по всем
прогонам контроля `d2-c1` - `d2-c5`: M-h - выше, M-i и M-j - 5/5. Единицы R - в
[distributed-resilience](../distributed-resilience/README.md#вердикт).

**Приманки и охват.** A3: PF (кэш курса FX), PO, PR, PC - не подняты blocker/major ни в одном наборе;
O1 (подпись вебхука), O2 (неполный платёж) - 2/2. Находка «Application зависит от конкретного
`FxRatesClient`» (`a3-n2a`, `a3-n2b`, major) - про новый код `PaymentWebhookHandler`, не приманка PF и
не PQ (та - вне диффа). В n2 (`d1-n2*`, `d2-n2*`, `d3-n2*`, `a3-n2*`, набор без этого скилла) все
единицы M - 2/2: сужения охвата нет.

## Открыто

- Решение D2 M-h (владелец, 05.10.2026): снятие принято. `d2-c1` ситуацию распознал и исключил
  её блокировкой - это верный дизайн, который допускает сверка D1; провал по исходной сверке D2 -
  дефект сверки, назвавшей одно решение там, где их два. Ключ, принимающий только готовое решение,
  меряет совпадение с ним, а не распознавание ситуации.
- Дизайн-потребители (`api-designer`, `security-reviewer`) не мерились: кейсы - ревью и проектирование
  `architect`.
