# DESIGN: BILL-40 — взыскание просроченных счетов

Статус: предложение. Код не входит; решение ложится в ADR после согласования (ADR-0008).

## 1. Решение в одном абзаце

Взыскание — **модуль внутри сервиса Billing** (`Collections`), а не отдельный сервис. Раз в сутки
фоновый воркер находит просроченные счета и ведёт по каждому «дело взыскания» (`CollectionCase`) с
журналом шагов. Всё, что уходит наружу (проводка пени в Ledger, письмо в RabbitMQ, передача
коллекторам по HTTP), сначала записывается в outbox в той же транзакции, что и изменение дела, и
отправляется фоном с повторами — по схеме ADR-0006. Оплата останавливает дело; начисленная пеня
остаётся.

## 2. Где живёт взыскание, и почему не микросервисы

Отвергнуто: микросервис Collections и три сервиса (напоминания / пени / коллекторы).

- Команда — 3 разработчика, DevOps нет, деплой — один сервис руками раз в неделю, сквозной
  трассировки нет. Каждый новый сервис — это отдельный деплой, мониторинг, версионирование
  контрактов и отладка сбоя «письмо ушло, пени нет» без трассировки. Срок — 6 недель.
- Collections нужны статус, сумма, срок счёта и право **менять** счёт (пеня видна в счёте), а
  оплата должна атомарно останавливать взыскание. Это сильная связность с данными Billing;
  в отдельном сервисе она превращается в распределённую согласованность.
- Правила пеней и сроков не устоялись: границы модулей лучше менять, пока это папки в одном
  проекте, а не контракты между сервисами.
- «Read-only пользователь к БД Billing» отвергнуто отдельно: чужой сервис привязывается к схеме
  таблиц, схема перестаёт быть нашей внутренностью, а менять счёт (пеня) всё равно пришлось бы
  через API. В модульном варианте вопрос не возникает — доступ через `IInvoiceRepository`.
- Условие пересмотра: если появится отдельная команда/нагрузка/ритм релизов у взыскания. Чтобы
  вынос был дешёвым, модуль ходит к счетам только через абстракции (`IInvoiceRepository`,
  `IOutbox`), не через таблицы напрямую, и не использует внутренности других модулей.

## 3. Структура модуля (по соглашениям репозитория)

- `Domain/Collections/`: `CollectionCase`, `CollectionStep` (enum: Reminder3, Reminder10,
  Reminder30, PenaltyAccrual, CollectorHandoff), `CollectionEvent`, `PenaltyAccrual`, правила
  (`CollectionPolicy`).
- `Application/Handlers/Collections/`: `RunCollectionsHandler` (один проход по просроченным),
  `GetCollectionHistoryHandler` — по RUL-0003 (`HandleAsync`, валидатор отдельным файлом).
  Бизнес-отказы — `Result` и наследники `BillingError` (ADR-0002), напр. `collection.not_found`.
- `Application/Abstractions/`: `ICollectionRepository`, `ICollectorGateway`;
  `IOutbox` существующий.
- `Application/Messages/`: `LedgerPostingRequested` (существующий), `CollectionsEmailRequested`,
  `CollectorHandoffRequested`.
- `Infrastructure/Collections/`: воркер-планировщик, диспетчеры outbox для RabbitMQ и коллекторов,
  `CollectorClient`.
- `Modules/CollectionsModule.cs` — регистрация, как `LedgerModule`/`FxModule`.

## 4. Как получаем данные счетов

В процессе, через `IInvoiceRepository`. Сейчас есть только `ListByStatusAsync(Issued)`; добавляем
выборку просроченных `ListOverdueAsync(DateOnly today)` (Issued и `DueDate < today`). Статуса
«просрочен» в `InvoiceStatus` нет и **не вводим**: просрочка — производная от `Issued` + `DueDate`,
отдельный статус разойдётся с реальностью при смене даты. Хранилище сейчас in-memory; после BILL-34
(Postgres) выборка идёт индексом по `(Status, DueDate)`. Работаем батчами, чтобы не тянуть все
счета в память.

## 5. Модель данных

- `CollectionCase`: `InvoiceId` (уникален), `State` (Active / Stopped / HandedOver), `OpenedAt`,
  `StoppedAt`, `StopReason` (Paid / Cancelled / HandedOver).
- `CollectionEvent` (журнал, только добавление): `CaseId`, `Step`, `OccurredAt`, `Status`
  (Queued / Sent / Failed), `Details` (ссылка на ExternalId проводки, id письма, id дела у
  коллекторов, текст ошибки). Уникальный ключ `(InvoiceId, Step, Day)` — защита от дублей.
- `PenaltyAccrual`: `InvoiceId`, `Date` (календарный день начисления), `Amount` (`Money`),
  `LedgerExternalId`. Уникален `(InvoiceId, Date)`.
- Outbox: существующий `IOutbox` расширяется (в БД — таблица с `Type`, `Payload`, `Attempts`,
  `NextAttemptAt`, `SentAt`); `LedgerOutboxDispatcher` сегодня фильтрует только
  `LedgerPostingRequested` и повторяет без счётчика попыток — для новых типов нужны счётчик и
  backoff, иначе «ядовитое» сообщение блокирует очередь.

## 6. Расписание и шаги

Воркер (`BackgroundService`, как `LedgerOutboxDispatcher`, тик по `TimeProvider`) — раз в сутки
и при старте. На счёт считает `daysOverdue = today - DueDate`. Каждый шаг выполняется по
принципу «догнать»: если воркер не работал, пропущенные шаги и дни пени выполняются при следующем
проходе, а не теряются; идемпотентность — уникальными ключами из §5.

| Шаг | Условие | Действие |
|---|---|---|
| Письма | `daysOverdue ≥ 3 / 10 / 30`, шаг ещё не записан | `CollectionsEmailRequested` в outbox |
| Пеня | `daysOverdue ≥ 10`, на каждый день без записи | `PenaltyAccrual` + `LedgerPostingRequested` в outbox |
| Передача | `daysOverdue ≥ 60`, не передан | `CollectorHandoffRequested` в outbox |

Пороги (3/10/30/60), ставка (0.1%) и база пени живут в `CollectionsOptions` (appsettings,
`ValidateOnStart`), не в коде: юристы правила ещё уточняют. Правило смены правил: изменённая
ставка действует на будущие начисления, уже начисленные не пересчитываются.

### Пеня

- Сумма дня = `Amount * 0.1%`, считается в минорных единицах (ADR-0004), банковское округление до
  минорной единицы; база — сумма счёта (простая, без капитализации). Валюта — валюта счёта.
- Одна проводка на день: `ExternalId = penalty-{invoiceId}-{yyyyMMdd}` — Ledger дедуплицирует
  повтор (как в ADR-0006).
- `PenaltyAccrual` и запись в outbox — в одной единице работы с `CollectionEvent`. Хендлер Ledger
  напрямую **не вызывает** (ADR-0006: новый код через `ILedgerGateway` не пишется).
- Видимость: сумма пени в счёте — не поле `Invoice`, а сумма `PenaltyAccrual` по счёту,
  возвращаемая в ответе по счёту (`penaltyMinor`) и в данных личного кабинета. Деньги к оплате =
  `Amount + penalty`; как именно принимать оплату с пеней — открытый вопрос №2. Тип поля в JSON —
  как в остальных DTO (`…Minor`, long).
- Ограничение: проводка в Ledger может запаздывать на минуты (outbox); счёт и ЛК показывают
  начисление сразу — источник правды по сумме в Billing, Ledger догоняет.

### Письма

- Notifications принимает события из RabbitMQ и доставляет at-least-once, то есть возможен
  дубль письма. Мы публикуем `CollectionsEmailRequested { MessageId, InvoiceId, CustomerId,
  Template, DaysOverdue, Amount, Penalty }` с детерминированным
  `MessageId = collections-{invoiceId}-{step}`, чтобы Notifications могли дедуплицировать
  (нужно согласовать, открытый вопрос №3). Публикуем с publisher confirms из outbox-диспетчера.
- Мы тоже at-least-once: если брокер подтвердил, а пометка `SentAt` не сохранилась — отправка
  повторится с тем же `MessageId`. Дубль письма клиенту — допустимая, но редкая цена.
- Содержимое письма в Billing не формируем: только данные события, шаблон — у Comms.
- Недоступность брокера: сообщения копятся в outbox, шаги взыскания не блокируются.

### Передача коллекторам

- Отдельный `CollectorClient` на `AddHttpClient<T>` + `.AddStandardResilienceHandler()` (ADR-0007;
  `AddPolicyHandler` не используем). Вызов — только из диспетчера outbox, не из воркера и не из
  запроса пользователя.
- Запрос идемпотентен по `invoiceId` как ключу дедупликации (заголовок/поле — по API агентства,
  открытый вопрос №4). Хранится id дела у агентства в `CollectionEvent.Details`.
- Повторы и circuit breaker — ресилиенс-обработчик плюс повтор outbox со счётчиком попыток;
  после N неудач дело помечается `Failed`, поддержка видит это в истории, алерт на счётчик.
- Передача необратима. Поэтому перед отправкой диспетчер **перечитывает статус счёта** и
  отменяет передачу, если счёт уже оплачен (§7).

## 7. Оплата и остановка взыскания

- Оплата и остановка в одной единице работы: `PayInvoiceHandler` переводит счёт в `Paid`; воркер
  и диспетчеры на каждом шаге проверяют `Status == Issued` и закрывают дело
  (`Stopped/Paid`). Отдельной «команды остановки» не нужно — состояние счёта и есть источник
  правды, что исключает рассинхрон.
- Уже начисленные `PenaltyAccrual` и их проводки остаются, неотправленные проводки пени
  доотправляются. Новые не создаются. Отмена счёта (`Cancel`) — тоже остановка; судьба
  начисленной пени при отмене — открытый вопрос №5.
- Гонка: оплата между проверкой и отправкой. Для писем и пени — допустимо (максимум одно лишнее
  письмо / день пени, уже начисленный день остаётся по условию). Для передачи коллекторам —
  перечитывание статуса перед отправкой; остаточное окно закрываем процедурой отзыва у агентства
  (открытый вопрос №4). `PayInvoiceHandler` вызывает Ledger напрямую (долг ADR-0006) — к
  взысканию не относится, но при его переводе на outbox менять семантику не нужно.

## 8. История для поддержки

`GET /invoices/{id}/collections` (в `InvoiceEndpoints`/отдельной группе): состояние дела,
журнал `CollectionEvent` по времени (письма, пени, передача, ошибки), итоговая пеня. Поиск по
номеру счёта — по `InvoiceId`. Для ответа «клиент говорит, что письма не было» журнал хранит
`MessageId` и статус отправки. Контракт — enum строками (коммит 302c85b), деньги — `…Minor`.
Доступ — роль поддержки (способ авторизации в сервисе пока не описан, уточнить).

## 9. Сбои соседей

| Сосед | Сбой | Поведение |
|---|---|---|
| Ledger | недоступен минуты/часы | пеня копится в `PenaltyAccrual`, проводки в outbox, повтор на тике; `ExternalId` защищает от дублей |
| RabbitMQ | недоступен | письма в outbox, шаги дела не блокируются; письмо уйдёт позже (при длинной задержке — письмо «3 дня» придёт позже срока; допустимо) |
| Notifications | дубль доставки | дедуп по `MessageId` на их стороне; у нас — детерминированный id |
| Агентство | 5xx/таймаут/breaker | ресилиенс + повтор outbox, после N попыток `Failed` + алерт; дело не теряется |
| Агентство | 4xx (отказ принять) | не повторяем, `Failed` с причиной, ручное разбирательство |
| Billing | падение воркера посреди прохода | следующий проход «догоняет» (§6), уникальные ключи не дают дублей |

## 10. Наблюдаемость

Трассировки между сервисами нет, зато модуль в одном процессе: структурные логи с
`InvoiceId`, `Step`, `ExternalId` (RUL-0004 в статусе Proposed, но соглашение разумное);
метрики: размер очереди outbox, число `Failed`, возраст самого старого неотправленного
сообщения.

## 11. План по неделям (6 недель, 3 разработчика)

1. Модель, миграции, `CollectionsOptions`, `ListOverdueAsync`.
2. Воркер, шаги письма/пеня, outbox со счётчиком попыток.
3. Диспетчер RabbitMQ; согласование контракта события с Comms.
4. `CollectorClient`, диспетчер передачи; согласование API агентства.
5. История для поддержки, пеня в ответе по счёту/ЛК.
6. Сквозная проверка на стенде, алерты, запас на правки правил юристов.

Тесты в рамках задачи не требуются (RUL-0002); сложные места — расчёт пени и «догоняющие» шаги —
стоит покрыть по решению команды.

## 12. Открытые вопросы (блокируют часть работ)

1. **Правила юристов**: 10-й день — включительно? Пеня за день 10 начисляется в этот же день или
   со следующего? Есть ли потолок пени? Пеня не начисляется на пеню (принято по умолчанию).
2. **Оплата с пеней**: оплата принимается на `Amount + пеня`? Частичная оплата останавливает ли
   взыскание? Сейчас `PayInvoiceHandler` принимает счёт как есть, `Invoice.Amount` неизменяемо.
3. **Notifications**: дедуплицируют ли по `MessageId`; формат события; какой язык/шаблон.
4. **Агентство**: идемпотентность запросов, отзыв/закрытие дела при поздней оплате, формат
   данных клиента (персональные данные — согласование с юристами/безопасностью), SLA.
5. **Отмена счёта**: что с начисленной пеней.
6. **Часовой пояс** границы суток для `DueDate` (`DateOnly`) и расписания воркера.
7. **Несколько инстансов Billing** (если появятся): воркер нужно защитить блокировкой
   (advisory lock Postgres) — сейчас сервис один, но уникальные ключи §5 всё равно спасут от дублей.
