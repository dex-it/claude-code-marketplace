# DESIGN: BILL-41 - оплата счёта с баланса Wallet

Статус: предложение. Код не входит в этот документ.

## 1. Ключевые решения

1. **Платёж - отдельная сущность `WalletPayment`** с состояниями, а не побочный эффект в хендлере. Намерение записывается в Postgres *до* вызова Wallet, поэтому любой сбой (таймаут, падение реплики, рестарт) можно доиграть.
2. **Идемпотентность списания** - `Idempotency-Key = WalletPayment.Id` (GUID, генерируется при создании намерения и хранится в БД). Все повторы одного платежа идут с тем же ключом.
3. **Один активный платёж на счёт** - частичный уникальный индекс в Postgres. Он, а не блокировки в коде, исключает двойное списание между ручной оплатой и ночным заданием, между репликами и между повторными кликами.
4. **Таймаут Wallet - это «неизвестно», а не «отказ».** Платёж остаётся в `Pending`/`Debiting` и доигрывается с тем же ключом. В `Failed` он переходит только по определённому ответу Wallet (4xx-отказ).
5. **Ledger - только через outbox** (ADR-0006), в одной транзакции с `Paid`. **Чек** - тоже через outbox, отдельным сообщением, best-effort.
6. **Вызовы Wallet изолированы от котировок**: отдельный `HttpClient` со своим ограничением параллелизма; соединение с БД и транзакция во время вызова Wallet не удерживаются.
7. **Ночное задание** - два этапа (планирование намерений, обработка пачками с lease и `FOR UPDATE SKIP LOCKED`), работает на всех репликах безопасно без выбора лидера.

## 2. Модель данных (Postgres, BILL-34)

Таблица `wallet_payments`:

| Поле | Назначение |
|---|---|
| `id` (uuid) | он же `Idempotency-Key` дебета; `refund-{id}` - ключ возврата |
| `invoice_id`, `customer_id` | связь |
| `amount_minor` (bigint), `currency` | копия суммы счёта на момент создания (ADR-0004), не пересчитывается |
| `source` | `Manual` / `AutoDebit` |
| `state` | `Pending` → `Debited` → `Completed`; ветки `Failed` (определённый отказ), `Refunding` → `Refunded` |
| `attempts`, `last_error`, `next_attempt_at` | доигрывание с backoff |
| `locked_until`, `locked_by` | lease обработчика |
| `created_at`, `updated_at` | |

Индексы и ограничения:
- `UNIQUE (invoice_id) WHERE state IN ('Pending','Debited','Completed','Refunding')` - не более одного живого платежа на счёт. `Failed` не блокирует новую попытку (новая попытка = новый `id` = новый ключ).
- индекс `(state, next_attempt_at)` для выборки работы.

`Invoice` получает токен оптимистичной конкурентности (`xmin` или `version`); переход `Issued → Paid` выполняется условно (`WHERE status = 'Issued'`). Это страхует и от старого `POST /invoices/{id}/pay`, см. §7.

Нужно в абстракциях: единица работы, общая для `IInvoiceRepository`, репозитория платежей и `IOutbox` (ADR-0006 требует «в той же единице работы»). Сейчас реализации in-memory (`InMemoryStore`); транзакционная Postgres-реализация - зависимость от BILL-34, в рамках этой задачи не выдумывается.

## 3. Последовательность шагов оплаты

Общий процессор `WalletPaymentProcessor` (используется и ручным путём, и ночным заданием):

1. **Намерение (транзакция 1, короткая).** Счёт `Issued`, сумма > 0, валюта счёта = валюте кошелька. `INSERT wallet_payments (state=Pending)`. Нарушение уникального индекса → возвращаем существующий активный платёж (не ошибка сервера): `Completed` → счёт уже оплачен; `Pending/Debited` → «в процессе».
2. **Захват lease**: `UPDATE ... SET locked_until = now()+lease WHERE id=@id AND (locked_until IS NULL OR locked_until < now())`. Не получили - платёж ведёт другой обработчик, выходим («в процессе»).
3. **Списание** `POST /wallets/{customerId}/debits` с `Idempotency-Key = id`, без открытых транзакций и блокировок.
   - успех → `state = Debited` (короткая запись, сразу);
   - определённый отказ (недостаточно средств, кошелёк закрыт и т. п.) → `Failed` + причина; счёт остаётся `Issued`;
   - таймаут / 5xx / обрыв / открытый circuit breaker → состояние не меняем, `attempts++`, `next_attempt_at` по backoff, lease снимается. Доигрывает фоновый воркер (§6) с тем же ключом.
4. **Завершение (транзакция 2, одна).** Условно `Issued → Paid` + `PaidAt`; `payment.state = Completed`; в outbox: `LedgerPostingRequested("pay-{invoiceId}", Amount, ...)` и `ReceiptRequested`. `ExternalId` проводки уникален на операцию, дубль на стороне Ledger безвреден.
5. **Фон**: `LedgerOutboxDispatcher` отправляет проводку; отдельный диспетчер чеков шлёт чек в Notifications.

Если после успешного дебета счёт уже не `Issued` (отменён/оплачен иначе, условный `UPDATE` не прошёл) - платёж уходит в `Refunding`, воркер делает `POST /credits` с ключом `refund-{id}`. Деньги не остаются «зависшими».

## 4. Ручная оплата `POST /invoices/{id}/pay-from-wallet`

Хендлер `PayInvoiceFromWalletHandler` в `Application/Handlers/Invoices/` с отдельным валидатором (RUL-0003), возвращает `Result<T>` (ADR-0002). Новые ошибки: `WalletInsufficientFundsError` (422, `wallet.insufficient_funds`), `WalletCurrencyMismatchError`, `PaymentInProgress` не ошибка, а исход.

- Хендлер проходит шаги 1-4 inline, но с **бюджетом запроса ~10 с** (через `CancellationToken` с таймаутом, независимый от HTTP-таймаута самого Wallet-клиента).
- Уложились → `200/204`, счёт `Paid`.
- Не уложились или Wallet не отвечает → **`202 Accepted`** с телом `{ paymentId, state }`; платёж доигрывается в фоне. Клиент опрашивает `GET /invoices/{id}` (статус) либо `GET /invoices/{id}/wallet-payment`. Пользователю не показываем «ошибка, повторите» - иначе он повторит и получит путаницу; повтор клика безопасен (§5), но 202 понятнее.
- Уже есть активный платёж → `202` с тем же `paymentId` (ручной клик в момент автосписания).
- Определённый отказ → `422` с `code`.

## 5. Как исключено двойное списание и потеря денег

| Угроза | Защита |
|---|---|
| Клик в кабинете одновременно с автосписанием | Уникальный индекс активного платёжа на счёт; проигравший получает существующий платёж. Плюс lease и условный `Issued → Paid`. |
| Две реплики берут один платёж | Lease + `SKIP LOCKED`; даже при гонке одинаковый `Idempotency-Key` → Wallet вернёт прежний результат. |
| Таймаут при списании, но Wallet списал | Состояние не `Failed`; повтор с тем же ключом возвращает исход. |
| Реплика упала между дебетом и записью `Debited/Paid` | Намерение уже в БД; воркер по истёкшему lease повторяет дебет с тем же ключом, получает прежний успех, завершает. |
| Дебет прошёл, счёт отменили | `Refunding` → credit с ключом `refund-{id}` (идемпотентно). Отмена счёта при живом платеже в `Pending/Debited` отклоняется как `invoice.invalid_state` (правка `CancelInvoiceHandler`). |
| Двойная проводка | `ExternalId = pay-{invoiceId}`, outbox в одной транзакции с `Paid`. |

Допущение, которое надо подтвердить с Payments: **срок хранения `Idempotency-Key` в Wallet** должен быть больше максимального времени доигрывания (инцидент до 30 мин + запас; рекомендуем потребовать ≥ 24 ч). Платёж в `Pending` старше этого срока не повторяем автоматически, а выносим на ручной разбор (алерт).

## 6. Сбои и медленные ответы

**Wallet** (30-40 с под нагрузкой, 3-5 мин в релиз, до 30 мин при инциденте).
- Клиент `IWalletClient` на `AddHttpClient<WalletClient>` + `.AddStandardResilienceHandler()` (ADR-0007; `AddPolicyHandler`/ADR-0003 не используем), с **явно изменёнными дефолтами**: `AttemptTimeout` ≈ 60 с (выше хвоста 30-40 с, иначе стандартные 10 с оборвут нормальные ответы), `TotalRequestTimeout` ≈ 2 мин, `Retry.MaxRetryAttempts` = 0-1 (повторами управляет конечный автомат платежа, иначе умножение попыток); circuit breaker включён, `SamplingDuration` ≥ 2×`AttemptTimeout` (иначе валидация опций упадёт при старте). Повтор POST допустим только потому, что есть `Idempotency-Key`.
- Открытый breaker = быстрый отказ без нагрузки на Wallet; платёж остаётся `Pending`, ночное задание приостанавливает выборку и возобновляет по таймеру.
- Backoff доигрывания: 1, 2, 5, 15 мин, далее каждые 30 мин. Платёж не «сдаётся» сам; только алерт по возрасту.
- Релиз Wallet (3-5 мин) и инциденты (до 30 мин) не теряют платежи: они переживают в `Pending`.

**Ledger.** Недоступность не влияет на оплату: проводка ждёт в outbox, диспетчер повторяет на следующем тике (ADR-0006). Счёт `Paid` без проводки существует лишь короткое время и всегда имеет сообщение в outbox. Алерт на возраст неотправленных проводок.

**Notifications.** Чек некритичен: отдельное outbox-сообщение, ограниченное число повторов (например 5 с backoff), после чего сообщение помечается `Abandoned` и логируется. Недоступность Notifications не откатывает и не задерживает оплату и не блокирует очередь проводок (отдельный диспетчер/тип сообщений).

**Падение реплики** - см. §5; lease истекает, платёж подбирает другая.

### Изоляция от котировок
`/invoices/{id}/quote` критичен и зависит от FX. Чтобы медленный Wallet его не задушил:
- отдельные `HttpClient`/handler для Wallet и FX, общего breaker/пула нет;
- потолок параллельных вызовов Wallet на реплику (например 16, настраивается) через ограничитель (`SemaphoreSlim`/bulkhead), чтобы 40-секундные вызовы не занимали все потоки, сокеты и соединения с БД;
- во время вызова Wallet нет открытой транзакции и соединения с БД (транзакции 1 и 2 короткие);
- ручной путь имеет приоритет: резервируем часть слотов (например 4) для ручных оплат, ночной воркер их не занимает;
- `FxRatesClient`/`FxModule` не меняем в этой задаче (ADR-0007 переводит его на новый обработчик при следующей правке; здесь она не нужна). ADR-0005 (синхронный справочник без кэша) к Wallet не относится: Wallet - не справочник.

## 7. Ночное задание автосписания

Хостед-сервис `AutoDebitJob`, запускается на **каждой** реплике, корректность не зависит от числа запущенных экземпляров.

**Этап A - планирование** (каждая реплика, идемпотентно):
`INSERT INTO wallet_payments (...) SELECT ... FROM invoices i WHERE status='Issued' AND due_date <= current_date AND <у клиента включено автосписание> ON CONFLICT DO NOTHING` (конфликт на частичном уникальном индексе). Если у платежа в `Failed` за сегодня уже есть попытка, новую в ту же ночь не создаём (не долбим кошелёк без средств); следующая попытка - в следующую ночь, пока счёт `Issued`.
Для защиты от одновременного планирования несколькими репликами можно взять `pg_try_advisory_xact_lock`, но он нужен лишь для экономии работы, не для корректности.

**Этап B - обработка**: цикл по тику (например раз в 10-30 с в окне ночного прогона и далее для хвоста):
- выбрать пачку `Pending` с `next_attempt_at <= now()` и свободным lease: `FOR UPDATE SKIP LOCKED LIMIT N`, проставить `locked_until`, закоммитить;
- обрабатывать пачку с ограничением параллелизма (§6) шагами 3-4;
- реплики естественно делят работу, повторная обработка исключена lease'ом и ключом.

**Пропускная способность.** ~40 тыс. счетов в пиковую ночь. При штатной задержке Wallet (сотни мс) и 3×16 слотах - минуты. В худшем случае (все ответы 30-40 с) ≈ 40000×35 с / 48 ≈ 8 ч: прогон не укладывается в ночь, но корректен - остаток доигрывается утром при снижении нагрузки; кроме того breaker защитит Wallet. Лимит параллелизма и размер пачки - в конфигурации, согласуются с Payments (RPS, который Wallet готов принимать).

**Ночной прогон не вредит клиентам**: автосписание не должно проходить по счёту, который клиент в этот момент оплачивает вручную - обеспечено §5. Мёртвые/Failed платежи не блокируют счёт и показываются в кабинете причиной.

**Старый `POST /invoices/{id}/pay` и `PayInvoiceHandler`**: он оплачивает без Wallet и обращается к `ILedgerGateway` напрямую (долг по ADR-0006). Новый код этот паттерн не наследует. Для задачи BILL-41 минимум: `PayInvoiceHandler` не должен «перебивать» живой `WalletPayment` (проверка активного платежа + условный переход статуса), иначе возможна оплата счёта дважды (Wallet + прямая проводка). Перевод его на outbox - отдельная правка, в этот дизайн не входит.

## 8. Состав изменений (для плана реализации)

- `Domain`: `WalletPayment`, состояния, ошибки; `Invoice` - условный переход в `Paid`, версия.
- `Application`: `IWalletClient`, `IWalletPaymentRepository`, `IUnitOfWork`; `PayInvoiceFromWalletHandler` (+валидатор), `WalletPaymentProcessor`; сообщения `ReceiptRequested`; правка `CancelInvoiceHandler` и `PayInvoiceHandler`.
- `Infrastructure`: `WalletClient` (+`WalletOptions`, `WalletModule` с `AddStandardResilienceHandler`), Postgres-репозитории (BILL-34), `AutoDebitJob`, `WalletRecoveryWorker`, диспетчер чеков.
- `Api`: `POST /invoices/{id}/pay-from-wallet`, чтение статуса платежа.
- Наблюдаемость: метрики по состояниям платежей, возрасту `Pending`, `Refunding`, breaker, возрасту outbox; алерты.
- Оформить ADR-0008 «Оплата с Wallet: платёж как конечный автомат + идемпотентный ключ» (не часть этого файла).

## 9. Открытые вопросы

1. Срок жизни `Idempotency-Key` в Wallet и есть ли `GET` платежа по ключу для сверки (в описании API его нет).
2. Где хранится флаг автосписания клиента (в Billing нет сущности клиента) - источник и кто его обслуживает.
3. Валюта кошелька и счёта: при несовпадении сейчас отказ (`WalletCurrencyMismatchError`); конвертация через FX не предполагается без отдельного решения.
4. Возврат на Wallet при отмене уже оплаченного счёта (сейчас `CancelInvoiceHandler` делает только сторнирующую проводку): нужен ли credit - решить с продуктом; механизм `Refunding` для этого готов.
5. Допустимая нагрузка Wallet по RPS для ночного прогона.
6. Готовность транзакционной Postgres-реализации (BILL-34): сейчас в коде in-memory хранилище и outbox.
