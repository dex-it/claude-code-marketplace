# DESIGN: BILL-42 - счёт по тарифу клиента из CRM

Статус: проект, код не написан. Ветка `feature/tariffs-design`.

## 1. Решение в одном абзаце

Billing держит у себя **локальную реплику тарифов** (по одной записи на клиента). Реплику ведёт
консьюмер события `CustomerTariffChanged`. При создании счёта тариф читается из реплики, CRM в
горячем пути не участвует. Единственный синхронный вызов `GET /v1/customers/{id}/tariff` - на
**промахе** реплики (клиента ещё не видели); результат кладётся в реплику «только если записи нет».
Если на промахе CRM недоступна - счёт не создаётся, клиент получает 503 с кодом
`tariff.unavailable` и повторяет запрос. Счёт хранит количество и **применённые условия тарифа**;
сумма выводится из них.

## 2. Почему так

Требования, которые определяют форму решения:

- 300 тыс. счетов в сутки, 200 тыс. - ночной пачкой, а CRM по ночам уходит в обслуживание на 1-2 часа:
  синхронный вызов на каждый счёт ломает именно ночную пачку. Значит, горячий путь читает локальные данные.
- Тариф меняется несколько раз в месяц на клиента: данные редкие, реплика почти всегда актуальна.
- Новый тариф действует «для счетов, созданных после изменения»: счёт фиксирует тариф на момент создания,
  последующие изменения старые счета не пересчитывают.
- События at-least-once без порядка: применение должно быть идемпотентным и устойчивым к перестановке.

### Рассмотренные варианты

| Вариант | Итог |
|---|---|
| Синхронный GET в CRM на каждый счёт (как ADR-0005) | Отвергнут: ночное окно CRM делает создание счетов невозможным, прямо нарушает требование задачи. |
| Синхронный GET + кэш с TTL | Отвергнут: после истечения TTL во время обслуживания CRM всё равно отказ; TTL - произвольная граница устаревания при том, что есть события. |
| Только события, без GET | Отвергнут: клиент без события (до подписки, потерянное сообщение, новый клиент) не получит счёт никогда. |
| **Реплика по событиям + GET на промахе** | Принят. |
| Создавать счёт «в ожидании цены» и досчитывать после ответа CRM | Отвергнут: появляется состояние счёта и второй путь, суммы нет в ответе `POST`; выгода - только для редких новых клиентов. |

### Отношение к ADR-0005

ADR-0005 требует синхронный вызов без кэша для **курсов и налогов**, потому что регулятор требует курс
на момент операции. Тариф клиента - не регуляторный справочник: у него нет требования «на момент
операции» с точностью до секунды, а требование BILL-42 о независимости от CRM прямо противоположно
доводу ADR-0005. ADR-0005 не отменяется и не меняется; решение оформляется новым ADR-0008 (черновик в
разделе 9), который фиксирует границу: ADR-0005 - для регуляторных справочников, тарифы - по ADR-0008.

## 3. Модель домена (контекст Billing)

Имена - язык Billing, не CRM: в домене нет `Tariff`-DTO из ответа CRM и его полей.

- **`CustomerTariff`** - агрегат реплики. Корень, идентичность - `CustomerId`. Поля: `CustomerId`,
  `Terms` (`TariffTerms`), `ChangedAt` (время изменения в CRM, `DateTimeOffset`).
  Метод `Apply(TariffTerms terms, DateTimeOffset changedAt)` - единственный способ сменить состояние:
  принимает, только если `changedAt` строго новее текущего, и возвращает признак «применено».
  Равное или старое время - тихий пропуск. Это даёт идемпотентность (дубль) и устойчивость к
  перестановке (старое событие после нового) одним правилом внутри сущности.
  `ChangedAt` нужен для этого сравнения, поэтому у поля есть читатель.
- **`TariffTerms`** - value object: `UnitPrice` (`Money`, минорные единицы по ADR-0004, валюта внутри),
  `DiscountBasisPoints` (целое, 0..10000; 1 бп = 0.01 %). Метод `PriceFor(int quantity)` -
  расчёт суммы живёт в value object, не в хендлере: данные тарифа считает сам тариф.
  Алгоритм (только целые): `gross = quantity * UnitPrice.Minor` (с проверкой переполнения),
  `discount = round_half_even(gross * bp / 10000)`, результат `gross - discount`. Банковское округление -
  по ADR-0004, округление в месте расчёта.
- **`Invoice`** (существующий агрегат) меняется: вместо заданной снаружи `Amount` хранит `Quantity`
  и `AppliedTariff` (`TariffTerms`) - снимок условий на момент создания. `Amount` становится
  вычисляемым свойством `AppliedTariff.PriceFor(Quantity)`, отдельно не хранится (хранить его и
  условия вместе - выводимое поле, расхождение возможно). Зачем хранить условия, а не только сумму:
  тариф потом изменится, и по счёту должно быть видно, из чего получена сумма (споры, аудит).
  Потребители `Invoice.Amount` (оплата, отмена, котировка) не меняются.
  Переход состояния по-прежнему только методами `Invoice`.

Границы агрегатов: `CustomerTariff` и `Invoice` - разные агрегаты, ссылаются друг на друга по
`CustomerId`/значению. Создание счёта меняет только `Invoice`; запись реплики - отдельная операция
(см. 4.2), две записи не объединяются в одну транзакцию. Репозиторий один - для корня
`CustomerTariff`; дочерних сущностей нет. Коллекций, растущих без границы, нет: запись одна на клиента.

## 4. Потоки

### 4.1. Создание счёта (`POST /invoices`)

1. Валидация команды: `Quantity > 0`, существующий `CustomerId`-формат. Валюты и суммы во входе больше нет.
2. Провайдер тарифа (4.2) возвращает `TariffTerms` или ошибку.
3. Создание `Invoice` с `Quantity` и `AppliedTariff`, `Issue()`, `AddAsync`.
4. Ответ как сейчас (`201`, `id`).

На горячем пути - одно чтение реплики по ключу, без сети. Для ночной пачки (~200 тыс.) это единицы
тысяч чтений в минуту по первичному ключу.

### 4.2. Получение тарифа при создании счёта

Отдельный класс Application `CustomerTariffProvider` (`Application/Handlers/Tariffs/`) с одной
причиной изменения - «как достать условия клиента». Хендлер счёта не смешивает с этим шаги разного
уровня.

1. `ICustomerTariffs.FindAsync(customerId)` (репозиторий реплики). Найдено - вернуть `Terms`.
2. Не найдено - `ICrmTariffSource.FetchAsync(customerId)` (порт, реализация - HTTP-клиент CRM):
   - успех - `ICustomerTariffs.AddIfAbsentAsync(...)`, вернуть условия;
   - CRM ответила «нет тарифа» (404) - `TariffNotFoundError`;
   - CRM недоступна / таймаут / открыт circuit breaker - `TariffUnavailableError`.
3. Результат GET **никогда не перезаписывает** существующую запись. В ответе CRM по задаче нет времени
   изменения, поэтому сравнить его с событием нельзя, и «поздний» GET мог бы затереть более новый
   тариф из события. Вставка только при отсутствии безопасна. Если у GET есть `changedAt`/версия, его
   можно применять через тот же `Apply` (вопрос 1 в разделе 8).
4. Отрицательный результат (нет тарифа, CRM недоступна) не кэшируется: следующий запрос снова
   проверит реплику (за это время мог прийти пришедший событием тариф).

Порт `ICrmTariffSource` нужен: Application не зависит от Infrastructure, а бизнес-логику провайдера
проверяем без HTTP и без RabbitMQ.

### 4.3. Приём `CustomerTariffChanged`

- Консьюмер RabbitMQ в `Infrastructure/Messaging/`; он только десериализует сообщение (контракт CRM
  остаётся в Infrastructure, имена CRM в домен не попадают), мапит в `ApplyTariffCommand` и вызывает
  `ApplyTariffHandler` (`Application/Handlers/Tariffs/`, RUL-0003).
- Хендлер: найти `CustomerTariff`; нет - создать из события; есть - `Apply(terms, changedAt)`;
  сохранить условным апсертом (`WHERE changed_at < @new`), чтобы два параллельных консьюмера не
  дали обратного порядка.
- Ack после успешного сохранения. Пропуск «старое/дубль» - тоже успех (ack).
- Некорректное сообщение (не парсится, скидка вне 0..10000, неизвестная валюта) - в dead-letter очередь,
  не бесконечный requeue.
- Очередь долговечная, у Billing своя; параллелизм консьюмера безопасен благодаря идемпотентному `Apply`.

## 5. Поведение при недоступности CRM

| Ситуация | Поведение |
|---|---|
| Клиент есть в реплике, CRM недоступна (ночь, падение) | Счёт создаётся по реплике. Это основной сценарий требования. |
| Клиента нет в реплике, CRM недоступна | `TariffUnavailableError`, HTTP 503, `Retry-After`; счёт не создаётся. Ночная пачка повторяет запрос позже. |
| Клиента нет в CRM | `TariffNotFoundError`, отказ с кодом `tariff.not_found`, не ретраится. |
| RabbitMQ недоступен, CRM работает | Реплика устаревает; счета считаются по последнему известному тарифу. См. риски. |

`TariffUnavailableError` - ожидаемый исход (ADR-0002), значением `Result`, не исключением; для него в
`ResultHttpExtensions` добавляется ветка 503 (сейчас остальное падает в 409). `TariffNotFoundError` -
наследник `NotFoundError`, но он про отсутствие тарифа, а не счёта: код `tariff.not_found` отличает его
от `invoice.not_found`.

HTTP-клиент CRM - `AddHttpClient<T>` + `.AddStandardResilienceHandler()` (ADR-0007), `AddPolicyHandler`
не используется. Таймаут запроса на промахе - короткий (секунды), чтобы запрос на создание счёта не
висел; значения - в `CrmOptions` по образцу `FxOptions`/`LedgerOptions`. Circuit breaker не даёт
долбить CRM в обслуживание.

## 6. Контракт API

`POST /invoices` (ломающее изменение, согласовать с фронтом; enum в JSON строками - d30cfa9):

- запрос: `customerId`, `quantity`, `dueDate`. `amountMinor` и `currency` убираются: сумма и валюта
  определяются тарифом. Имя `quantity` - количество единиц услуги (не `count`/`value`).
- ответ `201`: `id`. Рекомендую добавить в ответ `amountMinor` и `currency`: вызывающий больше не знает
  сумму заранее, а считать её у себя ему нельзя. Это дополнение, не поломка.
- ошибки: `400 validation`, `404 tariff.not_found`, `503 tariff.unavailable`.

## 7. Расположение в коде (по срезам, без новых слоёв-папок)

Структура репозитория остаётся: `Domain/`, `Application/`, `Infrastructure/`, `Modules/`.

- `Domain/`: `CustomerTariff`, `TariffTerms`, ошибки `TariffNotFoundError`, `TariffUnavailableError`;
  правка `Invoice`; `CustomerId` уже есть.
- `Application/Abstractions/`: `ICustomerTariffs`, `ICrmTariffSource`.
- `Application/Handlers/Tariffs/`: `ApplyTariffHandler`, `ApplyTariffCommand`, `CustomerTariffProvider`.
- `Application/Handlers/Invoices/`: правка `CreateInvoiceCommand` (+ `Quantity`, - `AmountMinor`/`Currency`),
  `CreateInvoiceHandler`, `CreateInvoiceValidator`.
- `Infrastructure/Crm/`: `CrmTariffClient` (реализует `ICrmTariffSource`, DTO ответа CRM здесь),
  `CrmOptions`. `Infrastructure/Messaging/`: консьюмер `CustomerTariffChanged`.
  `Infrastructure/Persistence/`: реализация `ICustomerTariffs` (сейчас in-memory, как остальное).
- `Modules/`: `TariffsModule` (регистрация), вызов из `Program.cs` рядом с остальными модулями.
- Зависимости пакетов: `Microsoft.Extensions.Http.Resilience` и клиент RabbitMQ; новые проекты и общие
  `Common`/`Shared` не создаём, ссылки между слоями идут внутрь (Infrastructure -> Application -> Domain).
- Старый `QuoteInvoiceHandler` зависит от `FxRatesClient` из Infrastructure напрямую - это существующий
  долг, в BILL-42 не трогаем и не копируем.

## 8. Риски, допущения, вопросы к Sales

1. **Формат тарифа в CRM не описан в задаче.** Допущено: цена за единицу в минорных единицах с валютой,
   скидка - процент. Нужно подтвердить единицы и точность скидки (целые бп или дробный процент) и
   есть ли в ответе `GET` время изменения/версия. Без версии GET применяется только как вставка при
   отсутствии (4.2). Если CRM отдаёт цену десятичным числом - конвертация в минорные единицы
   делается в `CrmTariffClient` один раз, `decimal` дальше не идёт (ADR-0004).
2. **Задержка между изменением тарифа и событием.** Счёт, созданный сразу после изменения, может
   получить старый тариф. При асинхронной реплике полностью исключить нельзя; допущение: окно
   секунды-минуты приемлемо для Sales. Если нет - потребуется синхронная проверка, что возвращает зависимость
   от CRM, и это отдельное обсуждение.
3. **Потерянные события при долгом отказе RabbitMQ** оставляют реплику устаревшей без явного признака.
   Минимум: метрика возраста последнего применённого события и алерт; сверка реплики с CRM фоном
   в рамках этой задачи не делается (нет списочного эндпоинта, преждевременно).
4. **Холодный старт.** Реплика пуста; клиенты наполняют её по мере промахов и событий. Ночная пачка
   в первый раз после выката даст всплеск GET в CRM; он ограничен circuit breaker и
   числом уникальных клиентов. Если окажется проблемой - попросить у Sales bulk-выгрузку.
5. **Часы.** Порядок событий решается только по `changedAt` из CRM, одним источником времени, часы Billing не
   участвуют.
6. Деньги: переполнение `long` при `quantity * UnitPrice` - явная ошибка валидации/домена, а не молчаливое
   усечение. Верхняя граница `quantity` - в валидаторе (значение согласовать).
7. Тесты: задача их не требует (RUL-0002), поэтому в MR они не обязательны. Логика расчёта и `Apply`
   в домене проверяется без HTTP; если команда решит добавить - начинать с `PriceFor` и `Apply`.

## 9. Черновик ADR-0008 (записать в `docs/adr/` вместе с реализацией)

> **ADR-0008: Тариф клиента - из локальной реплики по событиям CRM, а не синхронным вызовом**
> Статус: Proposed.
> **Решение.** Billing хранит `CustomerTariff` (реплика), обновляемый из `CustomerTariffChanged`
> идемпотентным `Apply` по времени изменения. Счёт создаётся по реплике и сохраняет применённые условия.
> Синхронный GET к CRM - только на промахе реплики, результат вставляется, если записи нет.
> **Почему.** Создание счёта (300 тыс./сут, 200 тыс. ночью) не должно зависеть от окон и падений CRM.
> Тариф меняется редко; регуляторного требования «на момент операции» у него нет (в отличие от ADR-0005).
> **Цена.** Тариф может отставать от CRM на задержку доставки события; на промахе при недоступной
> CRM счёт не создаётся.
> **Отвергнуто.** Синхронный GET на каждый счёт; GET с кэшем TTL; только события без GET; счёт «в
> ожидании цены».
