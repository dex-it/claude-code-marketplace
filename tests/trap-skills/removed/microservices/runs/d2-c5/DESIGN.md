# DESIGN: BILL-41 — оплата счёта с баланса Wallet

Статус: предложение. Код не пишется. После согласования оформить как ADR-0008 (ADR-0001).

## 1. Суть решения

1. Двойное списание исключают два независимых механизма: **одна живая попытка оплаты на счёт**
   (уникальность в Postgres) и **детерминированный `Idempotency-Key` на попытку**, одинаковый для
   кабинета, ночного задания и восстановления.
2. Вызов Wallet не делается внутри транзакции БД и не держит блокировок. Перед вызовом пишем
   намерение (попытка `Pending`, счёт `Paying`), после ответа в одной транзакции пишем итог.
3. Неопределённый исход (таймаут, обрыв, сбой Wallet) — не отказ. Попытка остаётся `Pending`, её
   довершает фоновый «добиватель» повтором того же запроса с тем же ключом.
4. Проводка в Ledger и чек — через outbox, в одной транзакции с `Paid` (ADR-0006). Ни Ledger, ни
   Notifications не влияют на то, оплачен ли счёт.
5. Wallet изолирован от остального сервиса: свой HTTP-клиент, свой конвейер устойчивости, свой лимит
   параллелизма. Котировки (`/quote`, FX) не зависят от состояния Wallet.

## 2. Что хранится и где (Postgres, BILL-34)

Опирается на BILL-34: текущие `InMemoryStore`/`InMemoryOutbox` не дают общей транзакции со счётом.
Нужен outbox в той же БД и той же единице работы. Без этого схема не реализуется.

**`invoices`**: новый статус `Paying` (`Issued → Paying → Paid`, при отказе `Paying → Issued`).
Переходы только условным `UPDATE … WHERE status = 'Issued'` (или проверка версии); результат
«0 строк» означает, что счёт уже взят кем-то другим. `Paying` не отдаётся ни одним текущим DTO;
если появится DTO счёта, enum идёт строкой по контракту с фронтом (коммит 2ca40d4) и значение надо
согласовать с фронтом заранее. `CancelInvoiceHandler` разрешает отмену только из `Issued`, поэтому
отмена платящегося счёта вернёт `invoice.invalid_state`.

**`wallet_payment_attempts`**:

| Поле | Смысл |
|---|---|
| `id`, `invoice_id`, `customer_id` | |
| `attempt_no` | номер попытки по счёту |
| `idempotency_key` | `bill-{invoiceId}-{attemptNo}`, детерминированный, уникальный |
| `amount_minor`, `currency` | копия суммы счёта на момент попытки (ADR-0004) |
| `status` | `Pending` / `Debited` / `Completed` / `Rejected` |
| `source` | `Manual` / `Auto` |
| `lease_until`, `lease_owner` | аренда на обработку репликой |
| `wallet_ref`, `reject_code` | идентификатор списания из ответа Wallet; код отказа |
| `created_at`, `updated_at`, `retry_count`, `next_attempt_at` | |

Частичный уникальный индекс: `UNIQUE (invoice_id) WHERE status IN ('Pending','Debited')`. Это
жёсткая гарантия одной живой попытки, даже если логика в коде ошибётся.

Ключ завязан на `attempt_no`, а не на счёт: Wallet по тому же ключу вернёт прежний результат,
включая отказ, поэтому после `Rejected` новая попытка (повторный клик клиента) обязана иметь новый
ключ. Пока попытка жива, ключ один, и все повторы вызова дают тот же результат.

**Outbox**: `LedgerPostingRequested(ExternalId = "pay-{invoiceId}", …)` и новое
`ReceiptRequested(invoiceId, customerId, dedupKey = "receipt-{invoiceId}")`.

**Настройки клиента**: флаг автосписания и его хранилище в задаче не описаны (вопрос 1).

## 3. Последовательность оплаты

Общий код — один `PayInvoiceFromWalletHandler` (RUL-0003, `Application/Handlers/Invoices/`,
валидатор отдельным файлом). `HandleAsync(команда, ct)` возвращает `Result<…>` (ADR-0002). Новый
порт `IWalletGateway` в `Application/Abstractions`, реализация — `Infrastructure/Wallet`,
регистрация — `Modules/WalletModule`. `ILedgerGateway` не используется. Существующий
`PayInvoiceHandler` и `POST /invoices/{id}/pay` не меняем, это долг из ADR-0006, отдельная правка.

**Шаг 1. Claim (одна короткая транзакция).**
Загрузить счёт; не найден — `invoice.not_found`. Условно перевести `Issued → Paying` и вставить
попытку `Pending` с ключом и арендой. Если счёт не `Issued`:
- есть живая попытка этого же счёта — вернуть текущее состояние (клик «оплатить» повторно или
  параллельно с ночным заданием — не ошибка, см. §5);
- иначе (`Paid`, `Cancelled`, `Draft`) — `invoice.invalid_state`.

**Шаг 2. Debit (вне транзакции).**
`POST /wallets/{customerId}/debits` с `Idempotency-Key` попытки и суммой из попытки. Исходы:
- 2xx — `Debited`, шаг 3;
- определённый отказ (4xx: нехватка средств, кошелёк заблокирован) — шаг 4;
- таймаут, обрыв, 5xx, открытый circuit breaker — исход неизвестен или не выполнен, попытка остаётся
  `Pending`, шаг 5.

**Шаг 3. Завершение (одна транзакция).**
Попытка `Debited → Completed`, счёт `Paying → Paid` (`PaidAt`), в outbox `LedgerPostingRequested` и
`ReceiptRequested`. Откат этой транзакции не страшен: попытка остаётся `Pending`/`Debited`, и
добиватель повторит шаг 2 (Wallet вернёт прежний результат по ключу) и шаг 3.

**Шаг 4. Отказ (одна транзакция).**
Попытка `Rejected` с `reject_code`, счёт `Paying → Issued`. Клиенту — бизнес-ошибка
`wallet.insufficient_funds` / `wallet.rejected` (новые наследники `BillingError`, перевод в
ProblemDetails через `ResultHttpExtensions`).

**Шаг 5. Неопределённость.**
Ручной путь возвращает **`202 Accepted`** с состоянием «оплата выполняется» (счёт `Paying`),
кабинет опрашивает счёт. Продолжение за добивателем. Деньги не считаются потерянными и счёт не
возвращается в `Issued`, пока Wallet не дал определённого ответа.

## 4. Поведение при сбоях

| Сбой | Что происходит |
|---|---|
| Wallet медленный (30–40 с) | Ручной запрос ждёт не дольше бюджета запроса (старт 15 с, настраивается), затем `202`; вызов продолжает добиватель. Поток не блокируется (async), соединения ограничены лимитом параллелизма. Ночью ждём ответ целиком. |
| Wallet лежит минуты/полчаса | Circuit breaker открывается; ночное задание перестаёт брать новые счета (иначе перебирает 40 тыс. счетов в пустую), ручные получают `202` (или быстрый `wallet.unavailable`, если breaker открыт и попытка ещё не создана — см. ниже). Попытки `Pending` добиваются с экспоненциальным backoff и jitter (`next_attempt_at`). |
| Таймаут после успешного списания в Wallet | Повтор с тем же ключом возвращает прежний результат — второго списания нет. |
| Падение реплики между шагами 2 и 3 | Аренда истекает, попытку подбирает любая реплика (§6) и повторяет шаг 2 с тем же ключом. |
| Ledger недоступен | Не влияет на оплату. Проводка уходит из outbox, когда Ledger вернётся; `ExternalId` уникален, повтор безопасен. |
| Notifications недоступен/медленный | Не влияет на оплату. Чек — отдельное сообщение outbox со своим диспетчером, ограниченное число повторов с backoff, затем отбрасывание с логом и метрикой. Чек не блокирует `Paid`, ни Ledger-диспетчер. |
| Мёртвая попытка (`Pending` > порога, напр. 1 час) | Алерт для ручного разбора. Автоматически в `Rejected` не переводим: без ответа Wallet это риск потерять списание. |

Если breaker открыт на шаге 1, попытку лучше не создавать: быстрый отказ `wallet.unavailable`
без смены статуса счёта. Если же попытка уже создана — она остаётся `Pending` (см. выше).

Ограничения Wallet не скрываем: в ADR-0007 `AddStandardResilienceHandler` по умолчанию ставит
таймаут попытки 10 с и общий 30 с. Для Wallet эти значения нужно переопределить: иначе мы сами
обрываем нормальные медленные ответы и повторами добавляем нагрузку на уже перегруженный Wallet.
Предлагаемые стартовые значения (настройка в `Wallet` секции `appsettings`, подбор с командой
Payments):
- таймаут попытки 45 с, общий таймаут 2 мин;
- повторов на HTTP-уровне 1 (с jitter), основной повтор — на уровне попыток добивателя;
- circuit breaker: окно выборки не меньше 2× таймаута попытки (требование библиотеки), порог
  отказов 50%, минимальная нагрузка 10, пауза 1 мин;
- повтор безопасен только потому, что оба запроса (debits) идемпотентны по ключу.

## 5. Как исключено двойное списание

- **Кабинет + ночное задание в одну минуту.** Обе стороны делают шаг 1. Условный `UPDATE` +
  частичный уникальный индекс пропускают ровно одну. Проигравший не вызывает Wallet: при ручном
  пути возвращает текущее состояние попытки (`202`, либо `200`/идемпотентный ответ, если уже
  `Paid`), при автосписании пропускает счёт.
- **Повторный клик, ретрай клиента, повтор HTTP-запроса.** Живая попытка одна, ключ один; Wallet по
  ключу вернёт прежний результат.
- **Потеря ответа.** Всегда повторяем с тем же ключом, никогда не создаём новую попытку, пока
  старая `Pending`/`Debited`.
- **Новая попытка после отказа.** Только из `Rejected`, с новым `attempt_no` и ключом; деньги по
  отказанной попытке не списывались.
- **Три реплики.** Ни одна проверка не живёт в памяти процесса — всё в Postgres.
- **Отмена счёта во время оплаты.** Невозможна (`Paying`), см. §2.
- **Компенсация.** Нужна только если списание произошло, а счёт оплатить нельзя. Из-за блокировки
  `Paying` такого пути нет; `credits` используется лишь для ручной корректировки при разборе
  инцидентов, с ключом `refund-{attemptId}`. Автоматического возврата не закладываем.

## 6. Ночное задание

- Запускается на **каждой** реплике (как сейчас), но не дублирует работу: пакетный claim.
  Транзакция выбирает пачку (например 200) счетов `Issued`, `due_date <= сегодня`, автосписание
  включено, `ORDER BY due_date, id … FOR UPDATE SKIP LOCKED`, переводит их в `Paying`, вставляет
  попытки `Pending` с `lease_until` и коммитит. Реплики не пересекаются, лидер не нужен.
- Затем реплика обрабатывает свою пачку (шаги 2–4) с ограничением параллелизма (старт 20 на
  реплику, итого 60; согласовать с Payments). Аренда продлевается, пока идёт работа.
- **Добиватель** — тот же цикл, берёт попытки `Pending`/`Debited` с истёкшей арендой и
  `next_attempt_at <= now` и выполняет шаг 2 → 3/4. Это единственный механизм восстановления; ночной
  claim новых счетов и добивание сосуществуют в одном `BackgroundService`.
- Оценка: 40 тыс. счетов при 60 параллельных и ответе 30–40 с в худшем случае ≈ 7 ч; при нормальной
  задержке — минуты. Задание запускается по окну (с 00:00, повтор тиком раз в минуту, пока есть
  работа) и дорабатывает остаток следующим тиком/ночью.
- Ручной путь резервирует часть слотов Wallet: отдельный лимит (напр. 10) поверх ночного, чтобы
  ночная очередь не отнимала у клиента ручную оплату.
- Автосписание не перебирает отказ каждую минуту: при `Rejected` счёт получает следующую попытку
  автосписания не раньше следующих суток и не больше N раз за период (параметр, вопрос 3).
- Пик — последняя ночь месяца: SKIP LOCKED и пакеты масштабируются числом реплик без правок.
- Диспетчеры outbox (Ledger/чек) на трёх репликах тоже должны брать сообщения через
  `FOR UPDATE SKIP LOCKED`; сейчас `LedgerOutboxDispatcher` итерирует без блокировки. Дубль
  проводки безопасен только благодаря уникальному `ExternalId` — не полагаться на это как на
  основной механизм.

## 7. Изоляция от котировок (FX)

`/invoices/{id}/quote` и `FxRatesClient` не меняются и не делят с Wallet ничего: свой
`HttpClient`, свой пул соединений, свой circuit breaker, свои лимиты. Все вызовы Wallet
асинхронные, без `.Result`/`.Wait()`. Неограниченная очередь запросов на Wallet недопустима:
параллелизм ограничен (§6), лишнее ждёт или получает `202`/быстрый отказ, а не занимает потоки и
соединения Kestrel. Ночное задание не использует поток обслуживания запросов. Метрики Wallet
(латентность, breaker, глубина `Pending`) — отдельные, чтобы деградацию Wallet видно сразу.

`FxRatesClient` остаётся на `AddPolicyHandler` до следующей правки (ADR-0007); в рамках BILL-41 его
не трогаем.

## 8. API

`POST /invoices/{id}/pay-from-wallet` (рядом с существующими в `InvoiceEndpoints`):
- `204` — оплачено;
- `202` — оплата выполняется (неопределённость или идёт параллельная оплата);
- `404 invoice.not_found`, `409 invoice.invalid_state`, `422 wallet.insufficient_funds` /
  `wallet.rejected`, `503 wallet.unavailable` (быстрый отказ при открытом breaker до создания
  попытки).
Код статусов — на согласование с `ResultHttpExtensions`. Авторизация «счёт принадлежит клиенту»
— по общей схеме кабинета, вне этого дизайна.

## 9. Открытые вопросы

1. Где хранится флаг автосписания клиента (Billing или Wallet) и кто его меняет.
2. Валюта баланса Wallet и счёта: если могут различаться, нужен пересчёт по курсу (ADR-0005,
   синхронный FX на момент операции) — это отдельное решение; пока считаем, что совпадает, иначе
   отказ.
3. Политика повторов автосписания после `Rejected` (сколько раз, с каким интервалом).
4. Контракт Wallet: коды определённого отказа vs временного, поведение при повторе ключа с другой
   суммой, срок хранения ключей (должен покрывать «добиватель» минимум на сутки).
5. Контракт Notifications: идемпотентность по `dedupKey` и квоты.
6. Допустимая нагрузка Wallet со стороны ночного задания (лимит параллелизма).
7. Сроки BILL-34: схема, outbox и транзакции в Postgres — предпосылка реализации.
