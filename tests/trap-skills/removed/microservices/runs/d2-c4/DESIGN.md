# DESIGN: BILL-41 - оплата счёта с баланса Wallet

Код не пишется; документ - проектное решение. Опирается на ADR-0002 (Result), 0004 (деньги в минорных
единицах), 0006 (Ledger через outbox), 0007 (Resilience-обработчик вместо Polly), RUL-0003 (хендлеры).

## 1. Главные решения

1. **Платёж - отдельная сущность `WalletPayment` (попытка списания) в Postgres.** Вызов Wallet идёт вне
   транзакции БД, а результат фиксируется второй короткой транзакцией. Состояние «ушли в Wallet, ответа нет»
   хранится явно и переживает падение реплики.
2. **Двойное списание исключают три слоя:** (а) детерминированный `Idempotency-Key` на попытку, (б) уникальность
   активной попытки по счёту в Postgres, (в) условный переход счёта `Issued -> Paid` (версия строки).
3. **Неопределённый исход (таймаут, 5xx, обрыв) - не ошибка, а `Pending`.** Он добивается повтором *с тем же
   ключом*, пока Wallet не даст определённый ответ. Отказ считаем только по явному ответу Wallet.
4. **Wallet изолирован от котировок:** свой `HttpClient` со своим resilience-конвейером, свой лимит
   параллелизма, никакого удержания соединения БД на время вызова. Медленный Wallet не должен трогать `/quote`.
5. **Ночное задание - не «одна реплика»:** все три реплики берут работу пачками через claim
   (`FOR UPDATE SKIP LOCKED` + lease). Дубли исключены данными, а не выбором лидера.
6. **Ledger и чек - через outbox в той же транзакции, что и `Paid`.** Недоступность Ledger/Notifications
   не влияет на оплату.

## 2. Что хранится и где (Postgres, БД Billing; зависит от BILL-34)

Сейчас хранилище и outbox - `InMemory*`; по ADR-0006 outbox должен писаться в одной транзакции со счётом, поэтому
для BILL-41 нужны Postgres-реализации `IInvoiceRepository` и `IOutbox` из BILL-34 (допущение, см. §10).

**`wallet_payments`** (одна строка - одна попытка списания)

| Поле | Смысл |
|---|---|
| `id`, `invoice_id`, `customer_id` | |
| `attempt_no` | номер попытки по счёту, начиная с 1 |
| `idempotency_key` | `billing:invoice:{invoiceId}:debit:{attempt_no}` - строится из данных, не случайный |
| `amount_minor`, `currency` | копия суммы счёта на момент попытки (ADR-0004) |
| `source` | `Manual` / `Auto` |
| `status` | `Pending`, `Succeeded`, `Declined` (явный отказ Wallet), `Released` (в Wallet не уходили) |
| `lease_until`, `lease_owner` | кто сейчас ведёт попытку; истёкший lease = можно подобрать другой реплике |
| `wallet_tx_id`, `decline_reason` | ответ Wallet |
| `sent_at` | пишется *до* вызова Wallet: если не null, исход может быть неизвестен |
| `created_at`, `finished_at` | |

Ограничения:
- `UNIQUE (invoice_id, attempt_no)`;
- **частичный уникальный индекс `UNIQUE (invoice_id) WHERE status IN ('Pending','Succeeded')`** - у счёта не
  бывает двух живых попыток и после успеха нельзя завести новую. Именно он решает гонку «кабинет vs ночь».

**`invoices`**: добавить `version` (optimistic concurrency) и `auto_debit_last_attempt_on` (дата, чтобы не списывать
дважды за ночь; см. §6). Переход в `Paid` - `UPDATE ... SET status='Paid' ... WHERE id=@id AND status='Issued'
AND version=@v`; 0 строк - переход проиграл.

**Outbox** (ADR-0006): новые сообщения `ReceiptRequested(InvoiceId, CustomerId, Amount, PaidAt)` рядом с
`LedgerPostingRequested`. Статус отправки, число попыток, `next_attempt_at` - в строке outbox.

Флаг автосписания клиента - см. открытый вопрос §10.

## 3. Последовательность ручной оплаты

`POST /invoices/{id}/pay-from-wallet` -> `PayInvoiceFromWalletHandler` (Application/Handlers/Invoices, валидатор
рядом, RUL-0003; возвращает `Result`, ADR-0002).

```
Кабинет            Billing                              Postgres                 Wallet
  | POST pay-from-wallet |                                  |                        |
  |--------------------->| 1. tx1: счёт Issued?             |                        |
  |                      |    INSERT wallet_payments        |                        |
  |                      |    (Pending, attempt_no=N+1,     |                        |
  |                      |     lease, sent_at=now)  ------->|                        |
  |                      |    unique-нарушение -> см. §5    |                        |
  |                      | 2. (БЕЗ транзакции и без         |                        |
  |                      |    удержания соединения БД)      |                        |
  |                      |    POST /wallets/{c}/debits  --------------------------->|
  |                      |    Idempotency-Key: ключ попытки |                        |
  |                      |<--------------------------- 200 / 4xx-отказ / таймаут ---|
  |                      | 3. tx2 (только если определённый ответ):                  |
  |                      |    Succeeded: payment=Succeeded; invoice Issued->Paid     |
  |                      |    (условно, по version); outbox += LedgerPostingRequested|
  |                      |    + ReceiptRequested ---------->|                        |
  |<---------------------| 204 (оплачено)                   |                        |
```

Исходы:

| Ответ Wallet | Действие | Ответ API |
|---|---|---|
| успех | tx2 как выше | `204` |
| явный отказ (нет средств, кошелёк закрыт) | payment=`Declined`, счёт остаётся `Issued` | `409 wallet.insufficient_funds` (и т.п.) |
| таймаут / 5xx / обрыв после отправки | payment остаётся `Pending`, дальше ведёт sweeper (§7) | `202 Accepted`, тело `{status: "Pending"}` |
| circuit breaker открыт / запрос не ушёл | payment=`Released` (в Wallet ничего не отправлено), счёт не тронут | `503 wallet.unavailable`, `Retry-After` |

Бюджет ожидания ручного запроса - **8 с** (конфиг): хендлер ждёт результат вызова не дольше и отвечает `202`,
не обрывая сам вызов. Вызов в Wallet идёт с собственным токеном (таймаут конвейера), **не с `ct` запроса**: если
клиент закрыл вкладку, списание не должно оборваться посередине и остаться неопределённым. Кабинет узнаёт итог
через `GET /invoices/{id}` (статус `Paid`) или `GET /invoices/{id}/wallet-payment` (статус попытки).

Повторное нажатие: счёт уже `Paid` через Wallet - идемпотентный `204`; есть `Pending` - `202` с текущим статусом,
вторая попытка не создаётся.

## 4. Как исключено двойное списание

1. **Один ключ на одну попытку, ключ детерминирован** (`invoice + attempt_no`). Любой повтор - из хендлера, sweeper,
   другой реплики после падения - уходит с тем же ключом, Wallet возвращает прежний результат (его контракт).
2. **Новый `attempt_no` создаётся только после явного `Declined`/`Released`.** Это важно: повтор отказанного
   ключа вернёт тот же отказ, а клиент мог пополнить баланс. Неопределённую попытку новой не заменяем никогда.
3. **Частичный уникальный индекс** запрещает две живые попытки на счёт - одновременное нажатие и ночное
   списание не могут оба получить новую попытку.
4. **Условный `Issued -> Paid`**: даже при баге выше счёт оплачивается один раз; проигравший переход - сигнал для
   сверки (§8), а не повод списывать снова.
5. **Всё, что может быть выполнено дважды, идемпотентно:** проводка (`ExternalId = pay-{invoiceId}`, уникален на
   операцию, ADR-0006), чек (at-least-once, дубль чека допустим).

Ключевое требование к Wallet (Payments): хранение ключей идемпотентности не меньше **7 суток** (наши повторы идут
часами при инциденте и могут переходить через ночь) и возврат *того же* результата, в том числе отказа, при
повторе. Если срок меньше - дизайн в части повторов неприменим, нужен GET по ключу/попытке (см. §10).

## 5. Гонка «кабинет vs автосписание»

Обе стороны идут через один путь создания попытки (§3, шаг 1). Если вставка упёрлась в частичный индекс:
- активная попытка `Pending` -> ручной запрос не создаёт вторую, а присоединяется: ждёт её исход в рамках бюджета
  8 с (опрос строки) и отвечает `204`/`202` по результату; ночное задание, наоборот, пропускает такой счёт;
- активная `Succeeded` -> счёт уже оплачен, ответ идемпотентный.

Даже если ручной запрос и ночной воркер оба дойдут до вызова Wallet с одним ключом (lease истёк у зависшей
попытки), Wallet вернёт один результат, а tx2 выполнится один раз благодаря условному переходу. Lease нужен для
экономии вызовов, а не для корректности.

Смежные пути, которые обязаны сходиться в тот же механизм:
- `POST /invoices/{id}/pay` (существующий `PayInvoiceHandler`) должен проверять, что нет `Pending`/`Succeeded`
  попытки, и менять статус тем же условным переходом; иначе обычная оплата и Wallet могут оплатить счёт дважды.
  Попутно его прямой вызов `ILedgerGateway` - долг по ADR-0006; `ExternalId` у обоих путей общий (`pay-{id}`), так
  что проводка не задвоится. Перевод на outbox - отдельной правкой, но условный переход нужен в этом же MR.
- `CancelInvoiceHandler`: отмена счёта с `Pending`-попыткой отклоняется (`invoice.payment_in_progress`, 409).
  Если отмена всё же выиграла гонку до tx2, а Wallet успел списать - tx2 видит `Cancelled` и вместо `Paid`
  создаёт возврат: `POST /wallets/{c}/credits`, ключ `billing:invoice:{id}:refund:{attempt_no}`, через тот же
  sweeper (попытка помечается `Succeeded`, счёт остаётся `Cancelled`, возврат ведётся до успеха, алерт). Деньги не
  теряются ни в одном порядке событий.

## 6. Ночное задание автосписания

Размещение: `WalletAutoDebitJob : BackgroundService` в `Infrastructure/Wallet`, запускается на всех репликах;
логика одного счёта - `AutoDebitInvoiceHandler` (тот же путь, что и ручной, `source=Auto`).

**Выбор работы.** Каждая реплика в окне (по умолчанию 00:00-06:00 UTC, конфиг) тикает раз в 30 с и берёт пачку
(50 счетов) запросом:
`Issued`, `due_date <= сегодня`, автосписание включено, нет живой попытки, `auto_debit_last_attempt_on < сегодня`
(или null), число подряд `Declined` < лимита (3) - `ORDER BY due_date, id FOR UPDATE SKIP LOCKED LIMIT 50`.
В той же короткой транзакции для каждого счёта создаётся `Pending`-попытка с lease (5 мин) и проставляется
`auto_debit_last_attempt_on`. Транзакция закрывается, потом идут вызовы в Wallet. Реплики не пересекаются по
построению; падение реплики даёт истёкший lease, и попытку подбирает sweeper (§7) - с тем же ключом.

**Один счёт - одна попытка за ночь:** `Declined` (нет средств) повторяем только в следующую ночь, до лимита; после
лимита счёт выпадает из автосписания, клиенту уходит уведомление (best effort).

**Пропускная способность.** 40 тыс. счетов за окно 6 ч - около 1.9 запроса/с. При нормальной задержке (сотни
мс) хватает 1-2 параллельных вызовов; при деградации Wallet (30-40 с) нужно ~`1.9 x 40` = 76 параллельных - это
мы *не* делаем намеренно. Параллелизм ночного задания: **8 на реплику (24 суммарно)**, конфиг; при деградации
задание просто не успеет, и остаток добирается в окне следующей ночи/после окна на малом параллелизме
(1 на реплику) - счёт не теряется, срок просрочки растёт на сутки, это приемлемее, чем перегрузить Wallet и
собственный `/quote`. Цифру 24 согласовать с Payments (§10).

**Реакция на недоступность.** Если конвейер сообщает об открытом breaker или N подряд неопределённых исходов -
воркер замирает на backoff (30 с -> 5 мин), не вычитывая новые пачки: во время релиза Wallet (3-5 мин) и
инцидента (до 30 мин) не копим тысячи `Pending`. Уже взятые счета возвращаются в `Released` (в Wallet не
уходили) и берутся снова.

**Приоритет ручной оплаты.** Лимиты параллелизма раздельные: ручной путь - свой резерв (10 слотов на реплику),
ночной - свои 8. Ночь не вытесняет кабинет.

**Пик последней ночи месяца** - тот же алгоритм: работа в БД, а не в памяти, поэтому рестарт реплики или
деплой ночью ничего не теряют.

## 7. Sweeper неопределённых попыток

`WalletPaymentSweeper : BackgroundService`, на всех репликах, тик 15 с. Берёт `Pending` с истёкшим lease и
`sent_at is not null` (`SKIP LOCKED`), повторяет `debit` **с тем же ключом**, затем tx2 (успех/отказ). Повторы с
нарастающей паузой; **попытка не бросается по таймауту** - без определённого ответа Wallet платёж остаётся
`Pending` сколько нужно. Если `Pending` старше 2 ч - алерт и метрика (деньги могли быть списаны, нужен человек),
но автоматического «отката» нет. `Pending` с `sent_at is null` (реплика упала до вызова) - безопасно
переводится в `Released`.

## 8. Wallet: HTTP-клиент и устойчивость

- Порт `IWalletGateway` (`DebitAsync`, `CreditAsync`) в `Application/Abstractions`; реализация `WalletClient` и
  `WalletOptions` в `Infrastructure/Wallet`, регистрация - `WalletModule` (`AddHttpClient<WalletClient>` +
  **`AddStandardResilienceHandler`**, ADR-0007; `AddPolicyHandler` не используем). `FxModule` не трогаем.
- Wallet-ответы переводятся в типизированный результат: `Succeeded`, `Declined(reason)`, `Unknown`. Только
  `Declined` меняет состояние на отказ; всё остальное (таймаут, 5xx, 429, обрыв, `BrokenCircuitException` после
  отправки) - `Unknown`. `4xx`, означающие *наш* дефект запроса (400/422), - не отказ клиента, а ошибка
  программиста: исключение + алерт, попытка остаётся `Pending`.
- Настройки конвейера (стандартные значения не подходят: таймаут попытки 10 с короче реальных 30-40 с):
  таймаут попытки 45 с, общий таймаут запроса 100 с, повторов 1 (POST безопасен благодаря ключу; основной повтор -
  sweeper), breaker: окно выборки не меньше 2x таймаута попытки (требование валидации опций), порог 50 %,
  минимум 10 запросов, пауза 30 с. Значения - в `WalletOptions` (`ValidateOnStart`).
- **Изоляция от `/quote`:** отдельный типизированный клиент -> отдельный пул соединений
  (`SocketsHttpHandler.MaxConnectionsPerServer` ограничить сверху), всё `async` (потоки не блокируются),
  параллелизм Wallet-вызовов ограничен семафорами из §6 (ручной резерв + ночной пул), соединения БД во время
  вызова не удерживаются. Результат: даже при ответах по 40 с занято не более ~34 подключений и ни одного
  потока/соединения БД, разделяемых с `FxRatesClient`. Котировки не зависят от Wallet.
  Если после нагрузочной проверки ночная работа всё же мешает API - вынести job в отдельный deployment того же
  образа (дизайн для этого уже пригоден, т.к. работа берётся из БД).

## 9. Ledger и Notifications

**Ledger.** Новый код ничего не вызывает у Ledger напрямую: tx2 кладёт `LedgerPostingRequested(ExternalId=
"pay-{invoiceId}", Amount, "Invoice payment (wallet)")` в outbox вместе с `Paid`. Недоступность Ledger - только
задержка проводки (ADR-0006), оплата и ответ клиенту не страдают. Условия на три реплики: диспетчер outbox
выбирает сообщения `SKIP LOCKED` (сейчас он обходит in-memory очередь; при переезде на Postgres это обязательно);
дубли гасит уникальный `ExternalId` в Ledger.

**Notifications (чек, некритично).** `ReceiptRequested` - в outbox в той же tx2, но отправляется *отдельным*
диспетчером со своим бюджетом: отправка at-least-once, ограниченное число попыток с backoff, TTL 24 ч, затем
сообщение закрывается как `Expired` с логом. Сбой/медлительность Notifications не задерживает Ledger-диспетчер
(текущий диспетчер на `LedgerUnavailableException` делает `break` и стопорит очередь - разные типы сообщений
не должны блокировать друг друга) и не влияет на статус `Paid`. Клиент Notifications - свой `HttpClient` с
`AddStandardResilienceHandler`, короткие таймауты.

## 10. Ошибки и коды API (ADR-0002)

Новые наследники `BillingError`: `WalletInsufficientFundsError` (`wallet.insufficient_funds`, 409),
`WalletDeclinedError` (`wallet.declined`, 409), `WalletUnavailableError` (`wallet.unavailable`, 503),
`PaymentInProgressError` (`invoice.payment_in_progress`, 409; 202 - только когда ждём собственную попытку).
Сбой инфраструктуры (БД, баг запроса) - исключение. Существующие `invoice.not_found`/`invoice.invalid_state` -
как есть. Перечисления в JSON - строками (коммит 2ca40d4).

## 11. Сверка и наблюдаемость

- Метрики: `Pending` по возрасту, число `Released`, доля `Declined`, состояние breaker, задержка Wallet (p50/p99),
  глубина outbox по типам.
- Ночная сверка: счета `Issued` с `Succeeded`-попыткой (проигравший условный переход) и `Cancelled` со списанием -
  алерт; запрос по таблицам Billing, без обращения к Wallet.
- Логи - структурные (`ILogger<T>`, RUL-0004 в статусе Proposed, но совпадает с практикой).

## 12. Порядок внедрения

1. Миграции: `wallet_payments`, поля `invoices`, outbox в Postgres (если не сделано в BILL-34).
2. `IWalletGateway` + `WalletClient` + `WalletModule` с лимитами.
3. `PayInvoiceFromWalletHandler`, эндпоинты, правка `PayInvoiceHandler` (условный переход, проверка попытки) и
   `CancelInvoiceHandler`.
4. Sweeper, затем `WalletAutoDebitJob` (включается флагом конфигурации; сначала на малом параллелизме).
5. Диспетчер чеков.

Тесты в задаче не затребованы (RUL-0002); сценарии, которые стоит прогнать в тестовом окружении до релиза:
гонка кабинет/ночь, падение реплики между шагами 2 и 3, ответ Wallet после таймаута, отмена во время `Pending`.

## 13. Открытые вопросы / допущения

1. **Payments:** срок хранения `Idempotency-Key` (нужно >= 7 суток) и что повтор отказанного запроса возвращает
   тот же отказ; допустимая параллельная нагрузка (заложено 24 ночью + резерв ручных); есть ли чтение платежа по
   ключу (позволило бы разбирать долгие `Pending`).
2. **Валюта кошелька:** предполагается, что кошелёк в валюте счёта. Если нет - пересчёт по ADR-0005 синхронным
   вызовом FX и фиксация курса в попытке; в этот дизайн не включено.
3. **Флаг автосписания:** откуда читается (таблица настроек клиента в БД Billing - допущено; либо сервис клиентов).
4. **Часовой пояс окна** ночного задания и допустимая просрочка при недоборе за ночь (бизнес).
5. **Postgres-outbox/репозиторий (BILL-34):** допущено, что поставляет транзакцию, общую для счёта, попытки и
   outbox. Без неё ADR-0006 для этой задачи не соблюсти.
