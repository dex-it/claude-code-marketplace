# DESIGN: BILL-40, взыскание просроченных счетов

Статус: предложение. Код не пишется, ниже только решение.

## 1. Решение в одном абзаце

Взыскание - **модуль внутри Billing**, а не отдельный сервис. У модуля свой агрегат `CollectionCase` (одно дело взыскания на счёт), свои таблицы в той же БД, свой фоновый воркер. Счёт модуль читает через `IInvoiceRepository` в том же процессе. Пени - проводки через outbox (ADR-0006). Письма - события в RabbitMQ через тот же outbox. Передача коллекторам - состояние дела плюс воркер, который зовёт HTTP API агентства. Выделение в сервис остаётся возможным, потому что граница модуля проведена по портам (раздел 8).

## 2. Почему не микросервис (ни один, ни три)

Ограничения из задачи: 3 разработчика, нет DevOps, релиз один сервис раз в неделю руками, нет трассировки между сервисами, срок 6 недель, правила пеней и сроков ещё меняются.

- Отдельный сервис Collections означает второй деплой, второй пайплайн и межсервисный контракт на данные счетов. Он ещё сильнее ломает правило «оплата останавливает взыскание»: оплата и дело окажутся в разных процессах без общей транзакции и без трассировки. Выигрыша от независимого масштабирования нет: нагрузка - один проход в день по просроченным счетам.
- Три сервиса (напоминания, пени, коллекторы) - это три деплоя, и все три работают с одним и тем же делом: «день просрочки», «что уже сделано», «оплачен ли счёт». Это один жизненный цикл и один агрегат, резать его по шагам нельзя. Правила, которые юристы ещё меняют, пришлось бы менять согласованно в трёх местах.
- Read-only пользователь к БД Billing: Collections привязывается к схеме таблиц Billing (BILL-34 её ещё трогает) в обход домена и контракта. Прав на запись нет, поэтому «обновить счёт» всё равно пришлось бы делать отдельным каналом. Мы отвергаем это даже как временный шаг: в монолите доступ к счёту и так есть, без обхода.

Критерии, при которых вернёмся к выделению: у модуля появляется своя команда, или нагрузка/релизный цикл расходится с Billing, или появляется DevOps и сквозная трассировка. Это фиксируем как ADR после согласования (раздел 10).

## 3. Модель домена

Контекст один (Billing), модуль `Collections` в нём - отдельный агрегат, не часть `Invoice`.

**`CollectionCase`** - корень агрегата. Ссылается на счёт только по `InvoiceId` (другой агрегат, объектной ссылки нет). На один `InvoiceId` не больше одного дела (уникальный индекс).

Состояние:
- `Id`, `InvoiceId`, `Version` (оптимистичная конкуренция);
- `Status`: `Active`, `Stopped` (оплата или отмена счёта), `HandedOver`;
- `Steps` - журнал выполненных шагов. Шаг: вид (`Reminder`, `Penalty`, `HandoverRequested`, `HandoverConfirmed`, `Stopped`), номер дня просрочки, время, для пени - `Money`, для передачи - ссылка дела в агентстве.

Чего в состоянии **нет** намеренно:
- числа дней просрочки: оно выводится из `Invoice.DueDate` и `TimeProvider`;
- суммы начисленной пени: это сумма шагов `Penalty`, считается из журнала, отдельным полем не хранится;
- копии суммы, срока и статуса счёта: источник один - `Invoice`.

Поведение (все переходы - только методы агрегата, хендлеры состояние не меняют):
- `Advance(daysOverdue, invoice Amount, policy, at)` возвращает список намерений (напоминание, пеня, запрос передачи) и записывает соответствующие шаги. Шаг вида «день N» не выполняется повторно: ключ шага `(вид, день)` уникален внутри дела. Это даёт идемпотентность и догонку пропущенных дней после простоя воркера.
- `ConfirmHandover(agencyReference, at)`, `Stop(reason, at)`. Из `Stopped` и `HandedOver` `Advance` ничего не делает; недопустимые переходы возвращают `BillingError` (ADR-0002).

**`CollectionPolicy`** - значение домена: дни напоминаний (3, 10, 30), день начала пени (10), ставка пени (0.1% в день), день передачи (60). Берётся из конфигурации (`CollectionOptions`), в коде не зашито: юристы правила ещё уточняют. Пеня считается в целых минорных единицах (ADR-0004): `Amount.Minor * ставка`, банковское округление до минорной единицы, внутри домена, `decimal` наружу не выходит.

Размер агрегата ограничен: шаги идут только по лестнице (3 письма, до ~51 дня пени, передача), это порядка 55 записей. Граница действует, пока пеня не копится после передачи (вопрос 3).

Репозиторий - только `ICollectionCaseRepository` для корня (`FindByInvoiceAsync`, `AddAsync`, `SaveAsync`). Репозитория для шагов нет. Specification не вводим.

## 4. Как получает данные счетов

Читает `IInvoiceRepository` в процессе. Для выборки просроченных добавляется один узкий метод `ListOverdueAsync(DateOnly asOf, CancellationToken)`: условие простое (статус `Issued` и `DueDate < asOf`), specification здесь не нужна, и второго способа выразить тот же сценарий рядом не появляется. «Просрочен» - выводимое свойство, статус `Invoice` не расширяем.

Модель `Invoice` и её переходы не меняются.

## 5. Как работает процесс

Воркер `CollectionsWorker` (BackgroundService, по образцу `LedgerOutboxDispatcher`, `PeriodicTimer`, тик раз в час; день считается по `TimeProvider`). Тик вызывает хендлер `AdvanceCollectionsHandler`:

1. `ListOverdueAsync` - список просроченных счетов.
2. Для каждого: найти или создать дело; **перечитать счёт**; если он не `Issued`, вызвать `Stop` и завершить. Это и есть «оплата останавливает взыскание»: источник истины - счёт, проверка перед каждым действием, отдельное событие об оплате не нужно. `PayInvoiceHandler` не меняем (его долг по ADR-0006 остаётся отдельной правкой).
3. `Advance` возвращает намерения; хендлер в **одной единице работы** сохраняет дело и кладёт сообщения в outbox. Транзакция затрагивает один агрегат плюс outbox, как в `CancelInvoiceHandler`.
4. Счёт, дело которого уже `Stopped`/`HandedOver`, из выборки исключается отдельным условием выборки дел, чтобы тик не рос с историей.

Ошибка по одному счёту не останавливает проход по остальным: логируется (`ILogger<T>`, структурные поля `InvoiceId`, `CaseId`), счёт будет взят на следующем тике.

Структура файлов, как принято в проекте (слои в одном `Billing.Api`, срез по фиче внутри слоя; RUL-0003):
- `Domain/Collections/`: `CollectionCase`, `CollectionPolicy`, `CollectionStep`, ошибки дела;
- `Application/Abstractions/`: `ICollectionCaseRepository`, `ICollectionAgencyGateway`;
- `Application/Handlers/Collections/`: `AdvanceCollectionsHandler`, `GetCollectionHistoryHandler`, `GetInvoicePenaltyHandler` (команды/запросы рядом, валидаторы отдельными файлами, если нужны);
- `Application/Messages/`: `InvoiceReminderRequested`, `CollectionPenaltyPosted` не нужен - пеня идёт существующим `LedgerPostingRequested`;
- `Infrastructure/Collections/`: репозиторий, воркер, клиент агентства, публикатор в RabbitMQ;
- `Modules/CollectionsModule.cs` - регистрация (по образцу `LedgerModule`).

Новых проектов, `Shared`/`Common` и циклических ссылок нет. Зависимости: Infrastructure -> Application -> Domain.

## 6. Пени и обновление счёта

- Пеня: шаг `Penalty` на день N (с 10-го, по policy) и сообщение `LedgerPostingRequested` с `ExternalId = penalty-{InvoiceId}-{N}` в outbox (ADR-0006). Дублей проводки нет: шаг дня уникален, `ExternalId` уникален на операцию. `ILedgerGateway` не используем.
- Счёт «обновлять» не нужно: `Invoice.Amount` неизменна, начисленная пеня - данные дела. Чтобы пеня была видна в счёте и в личном кабинете, ответ API счёта дополняется полем `PenaltyAccrued` (`Money`, 0 если дела нет), его собирает `GetInvoicePenaltyHandler` из дела. Это чтение двух агрегатов без записи в оба. Имя поля - по значению, не `Amount`/`Value`.
- Оплата останавливает дальнейшее начисление, уже начисленное остаётся: шаги и проводки не отменяются, `Stop` ничего не откатывает.
- Оплата счёта идёт на `Invoice.Amount` (как сейчас), вопрос про оплату вместе с пеней вынесен в раздел 10.

## 7. Письма и передача коллекторам

**Письма.** На дни 3, 10, 30 шаг `Reminder` и сообщение `InvoiceReminderRequested(MessageId, InvoiceId, CustomerId, DaysOverdue, ...)` в outbox. Отдельный диспетчер публикует в RabbitMQ (фильтр по типу, как в `LedgerOutboxDispatcher`) и помечает отправленным только после подтверждения брокера (publisher confirms).
- Notifications доставляет at-least-once, значит возможны дубли. `MessageId` детерминирован: `reminder-{InvoiceId}-{DaysOverdue}`, Comms использует его для дедупликации. Это условие контракта, согласуем с Comms (вопрос 5).
- Журнал фиксирует «письмо запрошено», а не «доставлено»: подтверждения доставки у нас нет. Поддержка видит это в истории.
- Имена полей события - доменные, контракт согласуется с Comms до начала кода.

**Передача.** На день 60 `Advance` ставит шаг `HandoverRequested`. Дальше воркер (тот же тик) для дел в этом состоянии вызывает `ICollectionAgencyGateway.HandOverAsync(...)`. Перед вызовом снова перечитывается счёт: передача необратима, оплаченный счёт отдавать нельзя. При успехе `ConfirmHandover(agencyReference)`. Выбор в пользу состояния и воркера, а не outbox: результат вызова должен вернуться в дело, а для этого нужна вторая транзакция.
- Порт `ICollectionAgencyGateway` в Application описан доменными именами; имена и формат API агентства живут только в `Infrastructure/Collections` (анти-коррупционный слой), в домен не попадают.
- HTTP-клиент: `AddHttpClient<T>` с `.AddStandardResilienceHandler()` (ADR-0007), `AddPolicyHandler` не используем.
- Идемпотентность: в запросе ключ `InvoiceId`, чтобы повтор после потерянного ответа не создал дубль у агентства (вопрос 4).

**Поддержка.** `GetCollectionHistoryHandler` и `GET /invoices/{id}/collection` отдают журнал шагов дела: письма, пени, передача, остановка. Дополнительного хранилища истории нет, журнал и есть история.

## 8. Сбои соседей

| Сбой | Что происходит | Что видно |
|---|---|---|
| Ledger недоступен | Шаг пени записан, проводка ждёт в outbox, диспетчер повторяет (ADR-0006). Дело не блокируется. | Неотправленные записи outbox. |
| RabbitMQ недоступен | Письма копятся в outbox, уходят после восстановления. Срок письма может сдвинуться, шаг при этом записан в срок. | Неотправленные письма. |
| Notifications недоступен/дублирует | Брокер хранит сообщения; дубли гасятся по `MessageId`. | - |
| Агентство недоступно | Дело остаётся `HandoverRequested`, повтор на следующих тиках; стандартный resilience-обработчик режет повторы и размыкает circuit breaker. Пени и письма не страдают. | Дела в `HandoverRequested` дольше суток. |
| Воркер не работал N дней | Следующий тик догоняет дни по идемпотентным шагам; пени за пропущенные дни начисляются по номерам дней, а не «за тик». | - |
| Два экземпляра Billing | Конфликт версии дела и уникальность ключа шага; второй просто пропускает. | - |
| Гонка оплаты и шага | Счёт перечитывается перед действием; остаётся окно в доли секунды между перечиткой и сохранением. Письмо или пеня, ушедшие в этом окне, считаем допустимым остаточным риском (вопрос 6). Передачу окно не затрагивает: она в отдельном шаге с перечиткой. | - |

Трассировки между сервисами нет, поэтому наблюдаемость - логи со структурными полями и два сигнала: возраст старейшей неотправленной записи outbox и число дел в `HandoverRequested` дольше суток. Оба нужны к релизу.

Что мешает выделению позже: порты `IInvoiceRepository` (для Collections - будет клиент счетов) и `IOutbox`/агентство уже изолированы; данные дела лежат в своих таблицах без внешних ключей на счета.

## 9. Допущения

- В репозитории счета и outbox пока in-memory (`InMemoryStore`), а в задаче счета в Postgres (BILL-34). Допускаем, что к релизу есть durable-хранилище с транзакцией «дело + outbox»; без него гарантии разделов 5-8 не выполняются. Таблицы дел идут той же миграцией/БД.
- Время - UTC, день просрочки считается по `DueDate` (`DateOnly`) и дате `TimeProvider`.
- Валюта пени равна валюте счёта.

## 10. Открытые вопросы (блокируют правила, не архитектуру)

1. День начала пени: «с 10-го» включительно? Начисляется ли пеня за 10-й день? Это параметр `CollectionPolicy`.
2. Оплата счёта: клиент платит `Amount` или `Amount + пеня`? Сейчас `PayInvoiceHandler` принимает счёт по `Amount`. От ответа зависит, меняется ли оплата.
3. Копится ли пеня после передачи коллекторам (до 60-го дня или дальше)? Если да, журнал шагов растёт без границы, и пеню придётся хранить агрегатом (суммой по дням) вместо шагов.
4. Поддерживает ли агентство ключ идемпотентности? Какие персональные данные должника можно передавать (юристы/комплаенс)?
5. Контракт с Comms: имя и поля события, дедупликация по `MessageId`, нужна ли обратная связь о доставке.
6. Допустим ли остаточный риск письма/пени, ушедших одновременно с оплатой?
7. Поддержка ищет «по номеру счёта», а в модели `Invoice` номера нет, есть только `InvoiceId` (Guid). Нужен ли человекочитаемый номер и кто его выдаёт?
8. Нужен ли ADR на решение «модуль, а не сервис» с критериями выделения (раздел 2): предлагаю оформить после согласования как ADR-0008.

## 11. План на 6 недель (ориентир)

1. Нед. 1: ответы на вопросы 1-5, контракт с Comms и агентством, durable-хранилище.
2. Нед. 2-3: домен (`CollectionCase`, `CollectionPolicy`), репозиторий, воркер, пени через outbox.
3. Нед. 4: письма (outbox -> RabbitMQ), поле `PenaltyAccrued`, история для поддержки.
4. Нед. 5: передача агентству, сигналы наблюдаемости.
5. Нед. 6: прогон на стенде, запас на правку правил юристов.
