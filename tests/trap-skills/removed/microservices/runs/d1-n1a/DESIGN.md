# DESIGN: BILL-40 — взыскание просроченных счетов

Статус: проект на согласование. Код не пишется; решение опирается на ADR-0002, 0004, 0006, 0007 и RUL-0003.

## 1. Решение в одном абзаце

Взыскание — **модуль внутри сервиса Billing**, не отдельный сервис. Новый агрегат `CollectionCase` (одно дело на просроченный счёт) ведёт стадии и историю действий. Фоновый процесс раз в сутки (интервал в настройках) проходит по просроченным счетам и продвигает дела. Все побочные эффекты (проводка пени, письмо, передача коллекторам) идут через outbox, как в ADR-0006. Счёт взыскание не меняет: пеня в счёте и в кабинете показывается чтением из дела.

## 2. Где живёт взыскание: модуль в Billing

Причины:
- Три разработчика, один сервис, ручной релиз раз в неделю, нет DevOps и нет трассировки. Второй сервис — это второй деплой, свой мониторинг и свои миграции, и всё это на тех же трёх людях.
- Срок 6 недель при правилах, которые юристы ещё уточняют. Правила (пороги, ставка) будут меняться; менять их в одном сервисе дешевле, чем согласовывать контракт между двумя.
- Взыскание сильно связано со счётом: ему нужны статус, сумма, срок, и оно пишет в Ledger через ту же outbox-схему.

Отвергнуто:
- **Отдельный микросервис Collections (продакт).** Выигрыш — независимый деплой и масштаб — сейчас не нужен: нагрузка — суточный проход, команда одна. Цена — синхронизация данных счетов, распределённые сбои, отсутствие трассировки.
- **Три сервиса (напоминания / пени / коллекторы).** Это три шага одного процесса над одним делом с общим состоянием. Разрезав их, получим распределённую сагу ради шагов, у которых нет разных причин изменения. Отклонено жёстче предыдущего варианта.
- **Read-only пользователь к БД Billing.** Связывает второй сервис со схемой, которой владеет Billing (BILL-34), в обход инвариантов счёта; схему нельзя менять без согласования. Внутри модуля проблема не возникает: данные счетов берутся через `IInvoiceRepository`.

Условия пересмотра (выделять сервис, только если появится): отдельная команда-владелец взыскания, нагрузка, требующая независимого масштабирования, или разные требования к релизному циклу. Границу под это закладываем сейчас дёшево: модуль зависит от счёта только через `IInvoiceRepository` и его данные, а счёт о модуле не знает (см. п. 3).

## 3. Модель и границы

Ubiquitous language: *просрочка* (дни после `DueDate`), *дело взыскания* (`CollectionCase`), *напоминание*, *пеня*, *передача коллекторам*.

### Агрегат `CollectionCase`
- Корень, ссылка на счёт — по `InvoiceId` (не по объекту). Один счёт — не более одного дела.
- Состояние: `Active`, `Stopped` (оплата или отмена счёта), `HandedOver`.
- Содержимое:
  - `StartedAt`;
  - накопленная пеня `AccruedPenalty` (`Money`, ADR-0004) и дата, по которую она начислена, `PenaltyAccruedThrough`;
  - журнал действий `Actions`. Запись — тип (напоминание N-го уровня / начисление пени / передача), время, `ExternalId` или ключ идемпотентности, статус запроса.
- Журнал ограничен жизненным циклом дела: напоминаний ровно 3, начислений пени не больше одного на сутки с 10-го по 60-й день, передача одна; на 60-м дне дело закрывается. Неограниченного роста нет.
- Репозитория для записей журнала нет: он дочерний; доступ только через `ICollectionCaseRepository` (корень: `FindByInvoiceAsync`, `ListActiveAsync`, `AddAsync`, `SaveAsync`).
- Все переходы — методы агрегата: `Advance(...)` (решает, что пора сделать, и фиксирует это), `Stop(reason)`, `MarkHandedOver()`. Публичных сеттеров нет.
- `AccruedPenalty` — не выводимое поле: ставка и порог могут смениться, начисленное должно остаться как зафиксировано. Читатель — представление счёта и поддержка.

### Расчёт: у кого чьи данные
- Срок и сумма принадлежат `Invoice`. Просрочку считает счёт: `Invoice.DaysOverdue(DateOnly today)`. Дело получает в `Advance` сумму (`Money`) и число дней аргументами, к полям счёта не тянется.
- Пеня: value object `CollectionPolicy` (пороги 3/10/30/60, ставка 0.1 %, из конфигурации — юристы ещё меняют правила). Метод считает накопленную пеню за N дней от `Money`: целые минорные единицы, банковское округление **один раз** от накопленного итога, начисляется разность с уже начисленным — округление по дням не накапливает погрешность. Основа — сумма счёта, без сложного процента. Domain `IOptions` не видит: политику собирает Infrastructure/Modules и передаёт в хендлер.
- Ничего в `Invoice` не добавляется, кроме `DaysOverdue`: счёт не знает о взыскании.

### Транзакции
Одна операция — одно дело. Хендлер меняет только `CollectionCase` и кладёт сообщения в outbox в одной единице работы. Счёт в той же транзакции не меняется (два агрегата в одной транзакции — запрещено).

## 4. Как получает данные счетов

Через `IInvoiceRepository` внутри процесса. Для прохода берём существующий `ListByStatusAsync(Issued)` и отбираем просроченные доменным методом `DaysOverdue`. Узкий метод «просроченные на дату» добавляем только когда объём выдачи станет проблемой (после BILL-34, на Postgres). Свою копию данных счёта дело не хранит.

## 5. Процесс (сценарии, срезом по фиче)

Структура RUL-0003, без новых проектов, без Shared/Common:

- `Domain/Collections/` — `CollectionCase`, `CollectionPolicy`, ошибки (`CollectionCaseNotFoundError` и т. п., наследники `BillingError`, ADR-0002).
- `Application/Abstractions/ICollectionCaseRepository.cs`; сообщения — в `Application/Messages/`.
- `Application/Handlers/CollectionCases/` — по хендлеру на сценарий, у каждого `HandleAsync(команда, ct)`:
  - `AdvanceCollectionCaseHandler` — продвинуть дело одного счёта;
  - `GetCollectionCaseHandler` — история для поддержки.
  Обход всех счетов — это не бизнес-логика, а цикл `BackgroundService`, вызывающий хендлер по одному счёту.
- `Infrastructure/Collections/` — `CollectionScheduler` (BackgroundService), `Infrastructure/Notifications/`, `Infrastructure/Collectors/` — исходящие диспетчеры; `Modules/CollectionsModule.cs` — регистрация (как `LedgerModule`).

Продвижение дела (`AdvanceCollectionCaseHandler`) для одного счёта:
1. Счёт не `Issued` (оплачен/отменён) — `Stop`, больше ничего не делать. Это и есть «оплата останавливает взыскание»: `PayInvoiceHandler` не меняется, пеня не откатывается.
2. Нет дела и счёт просрочен — создать.
3. `Advance(сумма, дни просрочки, политика)` возвращает действия, которые пора выполнить и которые ещё не выполнены: напоминания на 3/10/30 день, начисление пени с 10-го дня, передача на 60-й. Каждому — детерминированный ключ: `reminder-{invoiceId}-{level}`, `penalty-{invoiceId}-{throughDate}`, `handover-{invoiceId}`.
4. Для каждого действия — сообщение в outbox: `LedgerPostingRequested` (проводка пени, ADR-0006; `ILedgerGateway` напрямую не используем), `CollectionReminderRequested`, `DebtHandoverRequested`.
5. `SaveAsync(case)` с оптимистичной версией.

Догонка после простоя (деплой раз в неделю, сбои): если пропущено несколько напоминаний, отправляется только последнее из наступивших, остальные в журнале помечены как пропущенные — клиенту не должны прийти три письма сразу. Пеня догоняется за все пропущенные сутки одной проводкой.

Повторный запуск идемпотентен: действие с тем же ключом в журнале не создаётся второй раз. Экземпляр Billing пока один; оптимистичная версия защищает на случай второго.

## 6. Пеня видна в счёте и кабинете

Пеня остаётся в агрегате дела; ответ по счёту собирается чтением: запрос по счёту дополнительно читает `ICollectionCaseRepository.FindByInvoiceAsync` и добавляет в представление поле `accruedPenalty` и `penaltyAccruedThrough`. Двойной записи (в счёт и в дело) нет, расхождение невозможно. Личный кабинет берёт данные из API Billing. Имена полей контракта — по значению (`accruedPenalty`), не `amount`/`value`; enum — строками (коммит 302c85b).

Для поддержки: `GET` по номеру счёта возвращает дело и журнал: письма, пени, передача. Статусы честные: «письмо **запрошено**» — Notifications не сообщает о доставке, поэтому слово «отправлено» не используем.

## 7. Письма

Событие `CollectionReminderRequested` публикуется в RabbitMQ диспетчером из outbox (по образцу `LedgerOutboxDispatcher`; отметка `SentAt` после подтверждения брокера). Содержимое: ключ сообщения (детерминированный, см. п. 5), `CustomerId`, `InvoiceId`, `ReminderLevel` (3/10/30 дней просрочки), `DueDate`, сумма счёта. Имена — доменные; поля внешнего API Notifications в модель не попадают, преобразование — в Infrastructure.

At-least-once с обеих сторон: у нас повтор при сбое подтверждения, у Notifications — повторная доставка. Дедупликацию письма по ключу сообщения делает Notifications; **нужно согласовать с Comms** (п. 10). Если они дедупликацию не гарантируют, дубль письма — принятый риск.

## 8. Передача коллекторам

Переход дела в передачу и сообщение `DebtHandoverRequested` — одной транзакцией. Диспетчер в Infrastructure вызывает HTTP API агентства; клиент — `AddHttpClient<T>` с `AddStandardResilienceHandler()` (ADR-0007; `AddPolicyHandler` не используем). Ключ идемпотентности — `handover-{invoiceId}`.
- Перед отправкой диспетчер перечитывает счёт; если он оплачен/отменён — передачу не отправляет, дело `Stop`.
- Постоянный отказ агентства (4xx) — дело получает статус «передача не удалась», повторов нет, видно поддержке. Временный (сеть, 5xx, circuit breaker) — повтор на следующем тике.
- Остаточный риск: оплата между перепроверкой и приёмом агентством. Закрывается процессом (отзыв у агентства вручную); автоматического отзыва в первой версии нет.

## 9. Сбои соседей

| Сосед недоступен | Что происходит |
|---|---|
| Ledger | Проводка пени ждёт в outbox, дело уже отражает начисление; диспетчер Ledger повторяет (ADR-0006). `ExternalId` проводки не даёт задвоения. |
| RabbitMQ / Notifications | Письмо ждёт в outbox; при длительном простое письмо 3-го дня может уйти позже. Если к отправке уже наступил следующий порог — уходит актуальное, не накопленные. |
| Агентство | Резилиенс-пайплайн, затем повтор по тику; дело остаётся в «передаётся». |
| Процесс Billing лежит | Всё догоняется следующим проходом (п. 5). |

Наблюдаемость без трассировки: структурные логи `ILogger<T>` с `InvoiceId` и ключом действия в каждой записи; журнал дела — сквозная история по одному счёту. Тревога на «сообщение в outbox старше N часов» (порог — в настройках).

## 10. Допущения и открытые вопросы

Требуют ответа до релиза; закладываем в настройки, а не в код:
1. **Юристы:** пороги, ставка, основа пени (сумма счёта, без сложного процента — допущение), нужна ли пеня за день оплаты, откат пени при отмене счёта (в задаче не описан — не делаем).
2. **Comms:** дедупликация по ключу сообщения, формат события, откуда Notifications берёт адрес клиента (мы шлём `CustomerId`).
3. **Агентство:** поддержка ключа идемпотентности, API отзыва, состав передаваемых данных клиента (персональные данные — нужно согласие юристов).
4. Часовой пояс «сегодня» для `DueDate` (`DateOnly`): допущение — UTC через `TimeProvider`.
5. Персистентность: сейчас хранилище in-memory; атомарность «дело + outbox» по-настоящему появляется с Postgres (BILL-34). До этого срок релиза в прод зависит от BILL-34.

## 11. План (6 недель, 3 разработчика)

1. Н1–2: домен (`CollectionCase`, `CollectionPolicy`, `Invoice.DaysOverdue`), хендлер продвижения, проводки пени через outbox; логика проверяется без HTTP.
2. Н3: планировщик, представление пени в счёте, история для поддержки.
3. Н4: письма (согласование с Comms параллельно с Н1).
4. Н5: передача коллекторам.
5. Н6: догонка, сбои, настройки по итогам юристов, ADR-0008 «взыскание — модуль Billing».

После согласования оформить решение как ADR-0008 (в рамках этого задания файл не создаётся).
