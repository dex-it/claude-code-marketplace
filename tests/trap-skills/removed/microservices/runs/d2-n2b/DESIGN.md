# DESIGN: BILL-41 - оплата счёта с предоплаченного баланса

## 1. Суть решения

Оплата - двухфазная операция над одним агрегатом `Invoice`, вызов Wallet стоит между двумя короткими
транзакциями и в транзакцию не входит:

1. **Резервирование** (транзакция 1): `Issued -> PaymentInProgress`. Это и есть взаимное исключение
   ручной оплаты и ночного задания.
2. **Списание в Wallet** вне транзакции, с детерминированным `Idempotency-Key`.
3. **Завершение** (транзакция 2): `PaymentInProgress -> Paid` + в той же единице работы проводка и чек
   в outbox. Или, при однозначном отказе Wallet, возврат в `Issued`.

Неоднозначный исход (таймаут, обрыв, 5xx, открытый breaker) счёт **не откатывает**: он остаётся
`PaymentInProgress`, а фоновый «доводчик» повторяет то же списание с тем же ключом, пока не получит
однозначный ответ. Двойное списание исключают два независимых барьера: CAS статуса в Billing и
идемпотентность Wallet. Потеря денег исключена тем, что неизвестный исход никогда не трактуется как «не списано».

## 2. Модель домена

Агрегат один - `Invoice`; репозитория для дочерних сущностей нет, отдельной сущности «платёж» нет.
В транзакции всегда один агрегат (плюс outbox-сообщения единицы работы, ADR-0006).

Изменения `Invoice` (все переходы - только методами сущности, каждый сам проверяет допустимость
исходного состояния и возвращает `Result` по ADR-0002; обработчики статус не присваивают):

- `InvoiceStatus` += `PaymentInProgress` (в JSON строкой, как принято в контракте).
- `BeginPayment(now)`: `Issued -> PaymentInProgress`, увеличивает `PaymentAttempt`, ставит `PaymentStartedAt`.
- `CompletePayment(now)`: `PaymentInProgress -> Paid`, `PaidAt`.
- `AbortPayment(now)`: `PaymentInProgress -> Issued` при однозначном отказе; ставит `PaymentDeclinedAt`.
- `Cancel()` теперь сам отказывает при `PaymentInProgress` (и `Paid`): отмена счёта посреди списания
  привела бы к списанным деньгам по отменённому счёту. Существующий `PayInvoiceHandler` проверяет
  `Status == Issued`, поэтому в `PaymentInProgress` тоже не пройдёт.

Хранимые поля добавляются только те, у которых есть читатель:

| Поле | Читатель |
|---|---|
| `PaymentAttempt` (int) | строит ключ идемпотентности `"{invoiceId}:{PaymentAttempt}"` |
| `PaymentStartedAt` | «доводчик» отбирает зависшие `PaymentInProgress` старше порога |
| `PaymentDeclinedAt` | выбор для автосписания: не пробовать повторно в ту же ночь |
| `Version` | оптимистичная блокировка репозитория |

Ключ не хранится, он выводится из счёта и номера попытки. Попытка нужна потому, что Wallet на повтор с
тем же ключом вернёт прежний результат, в том числе отказ «недостаточно средств»: после однозначного
отказа новая попытка обязана идти с новым ключом. Пока попытка не закрыта однозначно, ключ не
меняется - повтор безопасен.

Имена Wallet (`debit`, `credit`) в домен не попадают: домен говорит «оплата», «попытка оплаты».
`Money` - минорные единицы (ADR-0004), сумма списания = `Invoice.Amount` без пересчёта.
Кредитование (`/credits`) в BILL-41 не используется: возвратов нет, отмена списания не требуется, потому
что неоднозначное состояние всегда доводится до конца, а не откатывается.

Настройка автосписания - свойство клиента, а не счёта. В Billing сущности клиента нет; вводится
маленький агрегат `CustomerPaymentSettings(CustomerId, AutoPayEnabled)` со своей таблицей. Как её
включают - вне этой задачи (см. вопросы).

## 3. Слои и файлы

Структура остаётся как в репозитории (папка-на-слой в одном проекте, ссылки только внутрь, Shared/Common
не вводим). Правило RUL-0003: хендлер - `<Действие><Сущность>Handler`, один `HandleAsync`.

Application:
- `Abstractions/IWalletGateway` - порт: `ChargeAsync(WalletCharge{InvoiceId, Attempt, Amount}, ct)` возвращает
  один из исходов `Charged | Declined(reason) | Unknown` (недоступность, таймаут, 5xx - всегда `Unknown`; это
  не исключение, а ожидаемый исход). Ключ идемпотентности собирает адаптер из `InvoiceId` и `Attempt`.
- `Handlers/Invoices/PayInvoiceFromWalletHandler` - ручная оплата и единица работы автосписания по одному счёту.
- `Handlers/Invoices/PayDueInvoicesFromWalletHandler` - один прогон ночного задания (выбор + раздача счетов).
- `Handlers/Invoices/ResumePendingWalletPaymentsHandler` - «доводчик».
- `Messages/LedgerPostingRequested` (существует) и новое `ReceiptRequested(InvoiceId, CustomerId, Money)`.
- Расширение `IInvoiceRepository`: `FindDueForAutoPayAsync(today, batch, ct)` и
  `FindStalePaymentsAsync(olderThan, batch, ct)`; `SaveAsync` принимает ожидаемую `Version`, конфликт -
  `ConcurrentUpdate`. Specification не вводится: два простых запроса.

Infrastructure:
- `Wallet/WalletClient` (типизированный клиент), `WalletOptions`, `WalletGateway` - адаптер, единственное место с
  именами и DTO Wallet API.
- `Wallet/AutoPayJob` (`BackgroundService`) - только расписание и вызов хендлера; `Wallet/PendingPaymentsJob` - то же для «доводчика».
- `Notifications/NotificationsClient` и `ReceiptOutboxDispatcher` по образцу `LedgerOutboxDispatcher`.
- Модуль `WalletModule` и `NotificationsModule` в `Modules/`.

Api: `POST /invoices/{id}/pay-from-wallet` в `InvoiceEndpoints`.

Логика оплаты целиком в хендлерах за портами и проверяется подстановкой `IWalletGateway`/репозитория,
HTTP для этого не нужен.

## 4. Последовательность шагов (один счёт)

```
Загрузить Invoice(version v)
Tx1: invoice.BeginPayment(now)            -- нет -> InvoiceInvalidStateError (409)
     SaveAsync(expected v)                -- конфликт версии -> отказ, счёт взял другой
Wallet: ChargeAsync(invoiceId, attempt, amount)       [вне транзакции, с таймаутом вызывающего]
  Charged  -> Tx2: invoice.CompletePayment(now)
                   outbox += LedgerPostingRequested("pay-{invoiceId}", Amount, ...)
                   outbox += ReceiptRequested(...)
                   SaveAsync + outbox - одна фиксация (единица работы BILL-34)
  Declined -> Tx2: invoice.AbortPayment(now); вернуть бизнес-ошибку wallet.insufficient_funds
  Unknown  -> ничего не менять; счёт остаётся PaymentInProgress; доводчик продолжит
```

`ExternalId` проводки `pay-{invoiceId}` уникален на операцию оплаты счёта (счёт оплачивается один раз) -
повторная отправка из outbox безопасна. Хендлер Ledger не вызывает (ADR-0006); `ILedgerGateway` в новом коде не используется.
Долг в `PayInvoiceHandler` (прямой вызов Ledger) этой задачей не трогаем, но он не конфликтует: в
`PaymentInProgress` он счёт не примет.

Ручная оплата, HTTP-контракт:
- Эндпоинт ограничивает ожидание Wallet своим дедлайном (порядка 10 с), а не 30-40 с.
- `200 { invoiceId, status: "Paid" }` - списано.
- `202 { invoiceId, status: "PaymentInProgress" }` - исход неизвестен или дедлайн вышел; кабинет опрашивает счёт.
  Платёж при этом не отменяется: «доводчик» его завершит.
- `409` - счёт не `Issued` (в том числе его уже оплачивает автосписание), код `invoice.invalid_state`.
- `422`/ProblemDetails с `code = wallet.insufficient_funds` - однозначный отказ Wallet.
- Дедлайн ограничивает только ожидание ответа. Если ответ `Charged` пришёл, а запрос уже отменён, и
  Tx2 не выполнилась, счёт остаётся `PaymentInProgress`, доводчик повторит списание (вернётся прежний
  результат) и закончит оплату.

## 5. Исключение двойного списания

1. **CAS в Billing.** `BeginPayment` + `SaveAsync(expected version)` - в Postgres условное обновление
   (`WHERE id = @id AND version = @v`). Из гонки «клиент нажал» и «идёт автосписание» (в том числе между тремя
   репликами) выигрывает ровно одна сторона; проигравшая получает 409 и в Wallet не идёт.
2. **Идемпотентность Wallet.** Ключ `"{invoiceId}:{attempt}"` не меняется, пока попытка не закрыта
   однозначно. Любые повторы (ретраи HTTP, доводчик, рестарт реплики после падения между шагами) приводят
   к одному списанию.
3. **Завершение тоже под CAS.** Если доводчик и ручной запрос одновременно получили `Charged`, только одна
   `CompletePayment` пройдёт; вторая увидит `Paid` и вернёт успех без повторной проводки.
4. **Нет ложных откатов.** `AbortPayment` вызывается только на однозначный `Declined`.

Потеря денег исключена: списание без `Paid` возможно только как временное `PaymentInProgress`, которое
гарантированно доводится (§6); алерт на счета в этом состоянии старше 15 минут и на возраст самого старого.

## 6. Сбои и медленные ответы

**Wallet** (до 30-40 с под нагрузкой, 3-5 минут релиз, до 30 минут инцидент).
- Клиент по ADR-0007: `AddStandardResilienceHandler()`, а не `AddPolicyHandler`. Значения по умолчанию не подходят:
  таймаут попытки порядка 45-60 с, общий таймаут запроса - 2-3 минуты, breaker настроен под реальные
  инциденты. Повторы по HTTP безопасны только потому, что оба запроса идемпотентны по ключу.
- Окна недоступности (релиз, инцидент) - не отказ: `Unknown`, счёт остаётся `PaymentInProgress`.
  `PendingPaymentsJob` (каждую минуту, порция по `FOR UPDATE SKIP LOCKED`/ограниченный параллелизм) повторяет списание
  для счетов старше порога (2 мин, больше дедлайна ручного запроса), с нарастающей паузой между попытками при открытом breaker. Предела по времени нет:
  автоотказ по неизвестному исходу запрещён, только алерт.
- Открытый breaker означает «запрос не отправлен», но и его трактуем как `Unknown`: проще, безопасно, повтор идёт с тем же ключом.

**Изоляция от котировок.** `/quote` дёргается фронтом постоянно и критичен для продаж, Wallet медленный.
- У Wallet отдельный типизированный клиент: свой пул соединений, свой breaker и лимиты, ничего общего с `FxRatesClient`.
- Ночной прогон исполняется отдельной ролью развёртывания (тот же образ, `Role=worker`, одна-две реплики
  без пользовательского трафика), а не в API-репликах: 40 тысяч медленных вызовов не едят потоки, соединения и
  память реплик, обслуживающих котировки. В API-репликах `AutoPayJob` и `PendingPaymentsJob` выключены настройкой.
- Параллелизм списаний ограничен (например 8-16 на воркер): при задержке 30 с это 15-30 запросов/мин на воркер на один поток
  - достаточно для ночного окна. Конкретное число - конфигурация, подбирается по нагрузке и допустимой нагрузке на Wallet
  (согласовать с Payments).
- Ручная оплата ограничена дедлайном и не держит запрос 30-40 с.
- `FxRatesClient` по-прежнему на `AddPolicyHandler` (ADR-0007: переводится при следующей правке) - в этой задаче не меняется.

**Notifications.** Чек некритичен: `ReceiptRequested` кладётся в outbox вместе с оплатой, отправляется
`ReceiptOutboxDispatcher` с повторами и ограничением числа попыток; после исчерпания - запись в лог и сообщение
помечается неотправленным, оплату это не затрагивает. Идемпотентность чека - по ключу `"receipt-{invoiceId}"`, если Notifications
его поддерживает (иначе дубли чека допустимы, потери - нет; уточнить).

**Ledger.** Не в горячем пути (ADR-0006): недоступность Ledger не влияет на оплату и не блокирует ответ.
Проводка уходит `LedgerOutboxDispatcher` позже. Состояние «Paid, а проводки ещё нет» штатно и конечно.

**Падение реплики** между Tx1 и Tx2: счёт остаётся `PaymentInProgress`, доводчик заканчивает по тому же ключу.

## 7. Ночное задание

- Запуск: `AutoPayJob` в роли worker, по расписанию после наступления суток (в часовом поясе, который задаёт
  бизнес - см. вопросы), один прогон = цикл по порциям до исчерпания кандидатов. Запуск на каждой реплике API
  прекращается.
- Выбор кандидатов: `Status = Issued`, `DueDate <= today`, `AutoPayEnabled`, `PaymentDeclinedAt` не сегодня; keyset-порции (например по 200),
  без загрузки 40 тысяч в память (текущий `ListByStatusAsync` для этого не годится и не используется).
- Каждый счёт обрабатывается тем же `PayInvoiceFromWalletHandler`, что и ручная оплата; отдельной логики
  списания у задания нет.
- Безопасность при нескольких экземплярах: два воркера (рестарт, ошибка деплоя, остатки старой версии)
  не дублируют списание - счёт берётся через CAS, а порция ещё и `SKIP LOCKED`. Эксклюзивность запуска - не
  условие корректности, только экономия работы (дополнительно можно взять `pg_try_advisory_lock` на прогон).
- Повторный прогон в ту же ночь (перезапуск) идемпотентен: оплаченные и взятые счета не выбираются.
- Однозначный отказ (`Declined`): счёт возвращается в `Issued`, ставится `PaymentDeclinedAt`, до следующей ночи не пробуется.
- Деградация Wallet: если подряд накапливаются `Unknown` (порог, например 20) - прогон останавливает выдачу новых
  счетов и ждёт восстановления с нарастающей паузой, чтобы не перевести всю ночную партию в `PaymentInProgress`.
  Уже взятые доводятся доводчиком. Пик последней ночи месяца (40 тысяч) укладывается по расчёту §6 в несколько часов.
- Метрики и алерты: кандидатов/оплачено/отказано/неизвестно за прогон, возраст старейшего `PaymentInProgress`, длительность прогона.

## 8. Что хранится и где (Postgres, BILL-34)

- `invoices`: статус (+`PaymentInProgress`), `payment_attempt`, `payment_started_at`, `payment_declined_at`, `version`; индекс под
  выбор кандидатов автосписания (статус, срок) и под зависшие платежи (статус, `payment_started_at`).
- `customer_payment_settings`: `customer_id`, `auto_pay_enabled`.
- `outbox`: существующая таблица; новые типы `ReceiptRequested`. Диспетчеры берут сообщения с `SKIP LOCKED`, чтобы
  три реплики не слали одно и то же (дубли Ledger всё равно гасит `ExternalId`).
- Состояние Wallet и баланс клиента в Billing не копируются - источник истины Wallet.

Текущие `InMemory*` реализации обновляются в том же объёме (условное сохранение по `Version`), чтобы поведение совпадало.

## 9. Рассмотренные и отвергнутые варианты

- **Вызов Wallet внутри транзакции БД.** Держит соединение и блокировку 30-40 с (до получаса в инцидент); отвергнуто.
- **Откат `PaymentInProgress -> Issued` по таймауту.** Если Wallet списал, но ответ потерян, получим деньги списанными при неоплаченном
  счёте и повторное списание; отвергнуто.
- **Компенсирующий `credit` при сомнении.** Лишняя операция с деньгами; повтор по идемпотентному ключу проще и надёжнее.
- **Отдельный агрегат/репозиторий «WalletPayment».** Состояние оплаты - инвариант счёта (нельзя отменить, нельзя оплатить дважды), он живёт в
  `Invoice`; два агрегата в одной транзакции были бы нарушением границы.
- **Ночное задание в API-репликах с распределённой блокировкой.** Нагрузка на реплики с котировками; отвергнуто в пользу роли worker.
- **Ключ идемпотентности случайный (Guid) на каждый вызов.** Не защищает от повтора после падения; отвергнуто.

## 10. Допущения и вопросы

1. Валюта баланса Wallet совпадает с валютой счёта; иначе нужен пересчёт по ADR-0005 (в задаче не описано).
2. Как `Declined` отличается от `Unknown` в ответах Wallet (коды 4xx/5xx и тело) - подтвердить с командой Payments; решение исходит из того, что
   повтор с тем же ключом возвращает прежний результат, включая отказ, и что ключ хранится не короче максимального времени
   зависания (до нескольких часов) - срок хранения ключей уточнить.
3. Поддерживает ли Notifications идемпотентность чека.
4. Часовой пояс «срок наступил» и время запуска ночного окна.
5. Кто и где включает `AutoPayEnabled` (в BILL-41 только читается).
6. Размер ночного окна и допустимый RPS на Wallet - от этого параметры параллелизма.
