# DESIGN: BILL-42 - счёт по тарифу клиента из CRM

## Решение кратко

Billing держит у себя **локальную реплику тарифов** (по одной актуальной записи на клиента). Реплика
наполняется событиями `CustomerTariffChanged` из RabbitMQ. Создание счёта читает тариф **только из
реплики** и не ходит в CRM на горячем пути. Синхронный `GET /v1/customers/{id}/tariff` - только
запасной путь для клиента, которого в реплике ещё нет, и для фоновой сверки. В счёте сохраняется
**снимок применённого тарифа**.

## Почему так

- 300 тыс. счетов в сутки, 200 тыс. в ночной пачке, а CRM ночью недоступна 1-2 часа и падает на
  десятки минут. Синхронный вызов на каждый счёт (ADR-0005) означает отказ ночной пачки в
  обслуживание CRM. Требование задачи «создание счёта не зависит от доступности CRM» синхронным
  вызовом не выполнить.
- Тариф меняется несколько раз в месяц, то есть почти не меняется. Реплика почти всегда актуальна.
- Событие уже публикуется, доставка at-least-once; это источник наполнения.

### Отношение к ADR-0005

ADR-0005 («справочные сервисы синхронно, без кэша») остаётся в силе для курсов и налогов. Его причина -
требование регулятора на курс в момент операции. Для тарифа такого требования нет: задача прямо
допускает, что новый тариф действует для счетов «после изменения», а доступность важнее. Тариф - не
«справочный сервис» из ADR-0005, а данные другой команды, реплицируемые событием. Решение расходится с
духом ADR-0005, поэтому нужен **новый ADR-0008** («Тариф клиента - локальная реплика по событиям CRM»)
со ссылкой «не распространяется ADR-0005 на тарифы». ADR-0005 не правится и не отменяется. Файл ADR-0008
в рамках этой задачи не создаётся (сдаётся только DESIGN.md), его пишет исполнитель вместе с кодом.

## Что хранит Billing

### Реплика тарифа `CustomerTariff` (одна запись на клиента)

| Поле | Тип | Примечание |
|---|---|---|
| CustomerId | CustomerId | ключ |
| UnitPrice | `Money` (минорные единицы + валюта) | цена за единицу услуги, ADR-0004 |
| DiscountBp | int | скидка клиента в базисных пунктах (0..10000) |
| ChangedAt | DateTimeOffset? | время изменения из события; версия записи. Для записи, полученной по GET без времени, - null |
| ReceivedAt | DateTimeOffset | когда Billing обновил запись (для сверки и метрики возраста) |

Порт `ITariffStore` (Application/Abstractions): `FindAsync`, `UpsertIfNewerAsync`, `InsertIfAbsentAsync`.
Реализация по аналогии с остальным хранением - `Infrastructure/Persistence`. Сейчас там
`InMemoryStore`; для продакшена реплика должна лежать в **durable-хранилище**, иначе рестарт сервиса
во время простоя CRM даёт пустую реплику и отказы. Выбор СУБД - за рамками задачи, зависит от
выбранного для счетов хранилища.

### Снимок в счёте

В `Invoice` добавляются: `Quantity` (long), `UnitPrice` (Money), `DiscountBp`, `TariffChangedAt`.
`Amount` остаётся итоговой суммой. Зачем: сумма воспроизводима и объяснима клиенту после смены тарифа;
спор «по какому тарифу выставили» решается без CRM.

## Правила расчёта

`Amount = round_half_even(Quantity * UnitPrice.Minor * (10000 - DiscountBp) / 10000)`

- Только целые числа, `decimal` не используется (ADR-0004); банковское округление до минорной единицы
  один раз, в конце, в месте расчёта. Скидка применяется к итогу строки, не к цене за единицу.
- Умножение в `checked`-контексте; переполнение - `ValidationError`.
- Валюта счёта - валюта тарифа.
- Расчёт - чистая функция в Domain (например, `InvoicePricing`), без IO.
- Итог должен быть > 0, иначе `ValidationError` (как сейчас для `AmountMinor`).

## Получение тарифа в момент создания счёта

`CreateInvoiceHandler` (RUL-0003: класс остаётся, метод `HandleAsync`):

1. Валидатор: `Quantity > 0`, а не `AmountMinor`/`Currency`.
2. `ITariffStore.FindAsync(customerId)`.
3. **Есть в реплике** - считаем по ней, CRM не вызывается. Это 100% обычных случаев.
4. **Нет в реплике** (новый клиент, потерянное событие, пустая реплика) - запасной путь:
   `ITariffGateway.GetAsync` к CRM, затем `InsertIfAbsentAsync` и расчёт.
5. CRM недоступна и записи нет - отказ `TariffUnavailableError` (бизнес-ошибка в `Result`, ADR-0002,
   код `tariff.unavailable`, HTTP 503 с `Retry-After`). Если CRM ответила, что клиента нет -
   `CustomerNotFoundError` (`NotFoundError`, 404).
6. Подставлять сумму от вызывающего или «тариф по умолчанию» **нельзя**: выставили бы неверную сумму.

Устаревшее значение из реплики при недоступности CRM **не считается отказом**: именно на нём и
работаем. Возраст записи не ограничиваем по TTL (иначе зависимость от CRM вернётся), но следим за ним
метрикой и сверкой.

### Клиент CRM

`ITariffGateway` в Application, `CrmTariffClient` в `Infrastructure/Crm` с `CrmOptions`
(BaseUrl, валидация при старте как у Fx/Ledger), модуль `CrmModule`. Устойчивость - по **ADR-0007**:
`AddHttpClient<T>().AddStandardResilienceHandler()`, не `AddPolicyHandler`. Запасной путь короткий
по таймауту: он стоит на пути запроса пользователя, и при падении CRM circuit breaker быстро отсекает
вызовы. Новый пакет `Microsoft.Extensions.Http.Resilience` в csproj.

## Потребление событий

`TariffChangedConsumer` - `BackgroundService` в `Infrastructure/Crm`, подписка на очередь Billing,
привязанную к обмену, где CRM публикует `CustomerTariffChanged`. Нужен клиент RabbitMQ (новая
зависимость, пакет согласовать с командой).

- **Идемпотентность и порядок.** Доставка at-least-once, порядок не гарантирован, поэтому применение -
  `UpsertIfNewerAsync`: запись заменяется, только если `event.ChangedAt` строго больше `ChangedAt`
  записи (запись с `ChangedAt = null` заменяется любым событием). Дубликаты и опоздавшие старые события
  становятся no-op. Сравнение атомарно (условный UPDATE / compare-and-set), без «прочитал-записал».
- **Подтверждение** (`ack`) - после успешной записи. Ошибка хранилища - `nack` с возвратом в очередь.
  Невалидное сообщение (скидка вне 0..10000, неверная валюта, нет id) - в dead-letter очередь, с
  логом `LogWarning` и счётчиком.
- Очередь durable, сообщения persistent, на стороне Billing - ограничение prefetch.
- Событие несёт весь новый тариф, так что дополнительный вызов CRM для применения не нужен.

## Сверка (защита от потерянных событий)

Событие может потеряться (сбой обмена, очередь создана позже подписки). `TariffReconciler` -
фоновая задача: раз в сутки, днём, медленным потоком (лимит запросов в секунду) берёт записи с
`ReceivedAt` старше N часов, запрашивает тариф у CRM и применяет `UpsertIfNewerAsync`. Для ответа без
времени изменения используется `InsertIfAbsent`-семантика не нужна: обновление идёт только при
расхождении значений, `ChangedAt` ставится в null (его перекроет любое следующее событие). При
недоступности CRM сверка пропускает тик и ничего не ломает. Основной поток счетов от неё не зависит.

Первичное наполнение: одноразовый прогрев перед включением фичи (список клиентов у CRM / по клиентам
из существующих счетов) через тот же клиент, плюс запасной путь выше для всего, что прогрев пропустил.

## Гонка запасного пути и события

Если запасной GET и событие по одному клиенту идут одновременно: GET пишет через `InsertIfAbsent`
(не затирает уже пришедшее событие), событие пишет через `UpsertIfNewer`. Остаточный риск: GET вернул
старое значение, а событие с более новым уже было принято до записи - `InsertIfAbsent` его не
затрёт. Обратный случай (запись GET с `ChangedAt = null`, затем приходит более старое событие)
сходится при доставке более нового события, так как доставка at-least-once. Принимаем.

## Контракт API

`POST /invoices` - **ломающее изменение**, согласовать с фронтом заранее:

- Было: `{customerId, amountMinor, currency, dueDate}`.
- Станет: `{customerId, quantity, dueDate}`. `amountMinor` и `currency` из запроса убираются (сумма и
  валюта считаются Billing). Принимать их «на всякий случай» нельзя - два источника суммы.
- Ответ 201 `{id}` как сейчас; добавить в ответ `amountMinor`/`currency` (enum - строками по контракту
  d30cfa9, здесь enum нет). Новые ошибки: 404 `customer.not_found`, 503 `tariff.unavailable`,
  422/400 `validation` как сейчас. Маппинг в ProblemDetails - в `ResultHttpExtensions` по типу ошибки.
- Идемпотентность создания счёта не входит в эту задачу; при ретраях клиента после 503 дублей нет,
  так как счёт при отказе не создан.

## Изменения по слоям

- Domain: `CustomerTariff`, `InvoicePricing`, поля снимка в `Invoice`, ошибки
  `TariffUnavailableError`, `CustomerNotFoundError`.
- Application: `ITariffStore`, `ITariffGateway`; `CreateInvoiceCommand(CustomerId, Quantity, DueDate)`,
  `CreateInvoiceHandler`, `CreateInvoiceValidator`.
- Infrastructure: `Crm/` (клиент, опции, consumer, reconciler), хранилище реплики.
- Api: `CreateInvoiceRequest`, ответ, маппинг ошибок.
- Modules: `CrmModule`, регистрация в `Program.cs`; `appsettings.json` - секции `Crm` и `RabbitMq`.
- docs: ADR-0008.

`FxRatesClient` и `AddPolicyHandler` в `FxModule` не трогаем (по ADR-0007 переводится при следующей
правке самого Fx, не в этой задаче). Вызов Ledger - как сейчас через outbox, сумма проводки берётся из
`Amount` счёта; `PayInvoiceHandler` не меняется.

## Наблюдаемость

Метрики: доля созданных счетов через запасной путь, число `tariff.unavailable`, возраст самой старой и
медианный возраст записи реплики, лаг события (`now - ChangedAt`), размер DLQ, число отброшенных
как устаревшие событий. Алерты: рост `tariff.unavailable`, лаг события выше порога, непустая DLQ.
Логи - структурные плейсхолдеры через `ILogger<T>`.

## Допущения и вопросы к Sales/CRM

Контракт CRM в задаче не расписан, принято следующее; расхождение меняет только маппинг:

1. Тариф содержит цену за единицу в минорных единицах, валюту и скидку. Скидка принята в базисных
   пунктах; если CRM отдаёт проценты с дробью, пересчитать в bp на границе клиента/consumer'а, а не
   хранить `decimal` (ADR-0004). Нужно подтвердить формат и валюту.
2. Тариф **один** на клиента (без разных услуг, периодов и объёмных ступеней).
3. В событии `ChangedAt` - время на стороне CRM, монотонное для клиента. Если часы CRM не монотонны,
   нужен номер версии в событии: **попросить Sales добавить `Version`**.
4. У ответа GET нет времени изменения - просим добавить; тогда запасной путь и сверка используют ту же
   версию и особый случай `ChangedAt = null` исчезает.
5. Допустимый лаг события: счёт, созданный сразу после смены тарифа, может быть выставлен по старому
   тарифу. Требование задачи («после изменения») этим допускается; допустимый лаг (предложение: секунды
   в норме, до минут при деградации) подтвердить с бизнесом.
6. Задача не говорит о пересчёте уже выставленных счетов - **не пересчитываем**, снимок неизменен.

## Отвергнутые варианты

- **Синхронный вызов CRM на каждый счёт** - ночная пачка зависит от CRM, противоречит задаче.
- **Синхронный вызов + кэш с TTL** - при истечении TTL во время простоя CRM тот же отказ; нужно
  держать стухший кэш, то есть та же реплика, но без точности событий.
- **Очередь/outbox «счёт без суммы, досчитать потом»** - счёт с неизвестной суммой в Ledger и у клиента;
  усложняет состояния счёта, требования задачи этого не просят.
- **Принимать сумму от вызывающего как fallback** - два источника суммы, неверные счета.
- **Читать БД CRM / общая таблица** - связность команд.
- **Ставить в запрос ночной пачки прогрев тарифов в начале** - не снимает зависимость, если CRM в
  обслуживании.
