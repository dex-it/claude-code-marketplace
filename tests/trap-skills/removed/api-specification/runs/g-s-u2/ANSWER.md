## Замечания к постановке
1. **FR-21 и FR-05 противоречат друг другу.** Серия до 52 недель (~364 дня), а бронь не может быть дальше 90 дней. Я принял, что FR-05 проверяется только для первой брони серии, остальные — по FR-08/FR-09. Нужно подтвердить; иначе реальный максимум серии около 13.
2. **FR-22 исходит из неверной предпосылки.** Числового идентификатора у комнаты сейчас нет: `Room.Id` — slug, и брони ссылаются на него (`Booking.RoomId`). Для реализации понадобится новый столбец и миграция.
3. **FR-21: что отменяет «серию целиком».** Я принял: все активные брони, включая уже прошедшие. Если прошедшие трогать не нужно, это решение стоит принять отдельно.
4. **FR-21: повторение в UTC.** Шаг 7 суток в UTC, поэтому в локальном времени после перехода на летнее время встреча «поедет» на час. Нужно решение: хранить таймзону серии или принять как есть.
5. **FR-21: поток событий.** Серия на 52 брони даёт 52 события в ленте. Для группировки в событие добавлено `seriesId`.
6. **FR-23 не задаёт ряд деталей, я принял:**
   - окно `[startsAt, startsAt+10 мин)`;
   - подтверждает владелец или администратор;
   - непросвещённая бронь становится `released`, это не событие ленты и не отмена;
   - отмена `released`-брони возвращает 204 без изменения.
7. **Идемпотентность `createBooking` (вне задачи).** `POST /api/v1/bookings` по-прежнему без защиты от повтора: повтор после потерянного ответа даст 409 `booking-overlap` с собственной бронью. Для мобильной сети с плохой связью стоит завести отдельную задачу и добавить `Idempotency-Key`.
8. **Контракт опережает код.** README требует менять контракт и код в одном MR; здесь по условию задачи только контракт. Это отмечено в CHANGELOG.
9. **Тесты.** Для проверок конкурентности серии и идемпотентности `Idempotency-Key` по дисциплине нужна реальная PostgreSQL, не InMemory/Sqlite.
