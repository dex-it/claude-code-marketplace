## Изменённые файлы
- `api/openapi.yaml`
- `api/CHANGELOG.md` (запись 1.3.0)

## Что добавлено
- **FR-20:** `GET /api/v1/rooms/by-numeric-id/{roomNumericId}/events` — лента от новых к старым.
  - Постраничный вывод keyset-курсором по `(occurredAt, id)`, `nextCursor: null` в конце истории.
  - Новые события клиент получает повтором запроса без курсора.
- **FR-21:**
  - `POST /api/v1/booking-series` — `repeatCount` 2..52, создаётся целиком или не создаётся.
  - `DELETE /api/v1/booking-series/{seriesId}` — идемпотентная отмена серии.
  - В `Booking` добавлено `seriesId`.
- **FR-22:**
  - `Room.numericId` и `Booking.roomNumericId`.
  - `GET /api/v1/rooms/by-numeric-id/{roomNumericId}`.
  - Фильтр `roomNumericId` в `listBookings`.
  - При создании брони и серии комната задаётся одним из `roomId` / `roomNumericId` (`oneOf`).
- **FR-23:**
  - `POST /api/v1/bookings/{bookingId}/check-in` — идемпотентен, повтор после закрытия окна возвращает тот же 200.
  - Статус `released`, поле `checkedInAt`.
  - Коды `check-in-too-early`, `check-in-window-closed`, `booking-released`.
- **По дисциплине:**
  - У каждой новой операции есть `x-traced-from`, пример ответа и пример ошибки.
  - У создания серии описан повтор (`Idempotency-Key`).
  - В существующих примерах добавлены новые обязательные поля.

## Замечания к постановке
1. **FR-21 и FR-05 противоречат друг другу.** Серия из 52 еженедельных броней выходит за 90 дней. Я закрепил, что FR-05 проверяется только для первой брони. Нужно решение продукта.
2. **FR-22 и текущий контракт.**
   - Сейчас `Room.id` — slug и используется как ссылка (`roomId` в брони, путь `/rooms/{roomId}`). После переименования такие ссылки ломаются у всех клиентов, не только мобильных.
   - Я добавил числовой id аддитивно и slug не устаревал. Нужно решить, объявлять ли slug-ссылки устаревшими, со сроком.
   - Сегмент `by-numeric-id` фактически занимает слово как slug комнаты.
3. **Отмена серии «целиком».** Не сказано, затрагивает ли она уже прошедшие брони. В контракте отменяются все активные.
4. **Кто делает check-in.** Не указано, поэтому по аналогии с FR-10 это владелец или администратор.
5. **Права на отмену серии:** FR-21 даёт их владельцу серии и администратору. Для отдельных броней серии права остаются по FR-10.
6. **События ленты.** FR-20 перечисляет только создание, перенос и отмену. Освобождение брони по FR-23 событием не считается. Нужно уточнить, нужен ли тип `booking-released`.
7. **Существующий `createBooking` не идемпотентен** — клиент при потере ответа не может безопасно повторить запрос. Для мобильного клиента с плохой связью стоит добавить `Idempotency-Key` и туда; сейчас я лишь описал поведение повтора в описании операции.
8. **`cancelBooking` для `released` брони** в контракте не определён.
9. **Релиз `released` для старых клиентов:** новое значение `status` совместимо только для клиентов, которые игнорируют неизвестные значения. Это зафиксировано в схеме, но потребителей стоит предупредить.
