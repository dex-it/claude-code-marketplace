# Review: приёмка заказов, webhook оплаты, выбор склада отгрузки

Файлы: OrderConfirmation.cs, OrderIntake.cs, PaymentWebhook.cs, ShippingPlanner.cs.
Остальные файлы каталога прочитаны только для контекста (модель, DbContext, конвенции).

## Blocker

### 1. PaymentWebhook.cs:18-41 - нет идемпотентности по `ExternalId`
`Handle` для каждого `notice` без проверки создаёт `Payment` (строки 22-29), переводит заказ в
`Paid` (30) и начисляет бонус (38) - независимо от того, обрабатывался ли уже платёж с этим
`ExternalId`. Уникального индекса на `Payment.ExternalId` в `ShopDbContext` нет (нет
`OnModelCreating` вовсе), так что повторная доставка одного и того же вебхука (стандартное
at-least-once поведение провайдеров оплаты, на что явно намекает комментарий у поля
`ExternalId` в Model.cs:65 - "id платежа у провайдера") создаст второй `Payment` и второй раз
начислит 1% бонуса на счёт клиента. Кончится задвоением платежа в истории и удвоенным бонусом
при любом retry вебхука.

### 2. PaymentWebhook.cs:32-37 - get-or-create `BonusAccount` не защищён ни от батча, ни от конкурентности
`SingleOrDefaultAsync` (32) всегда идёт в БД, а не в already-tracked change tracker: вновь
созданный, но ещё не сохранённый `BonusAccount` (35-36) не сохраняется до единого
`SaveChangesAsync` после всего `foreach` (41). Два сценария:
- в одном `batch.Payments` две записи с одним `CustomerId` (два заказа одного клиента в одной
  выгрузке) - вторая итерация не увидит несохранённый аккаунт первой, создаст ВТОРОЙ
  `BonusAccount` с тем же `CustomerId`;
- два конкурентных вызова `Handle` для одного клиента (разные заказы, разные вебхуки) - тот же
  check-then-act race, БД ничем не защищена (нет unique constraint на `CustomerId`).

Кончится дублем `BonusAccount` на одного клиента (бонус размазан по двум строкам) и тем, что
ЛЮБОЙ следующий платёж этого клиента крашит `Handle` намертво: `SingleOrDefaultAsync` бросает
`InvalidOperationException` при >1 совпадении.

### 3. ShippingPlanner.cs:27-29 - `warehouses.OrderBy(...).First()` на пустой коллекции
Если ни один склад не набрал нужный `qty` (строки 18-21 `withStock` пуст, или ни один
`Warehouse` не попал в фильтр 23-25) - `warehouses` пуст, и `.First()` бросает
`InvalidOperationException: Sequence contains no elements`. "Товара нет ни на одном складе" -
штатный, ожидаемый исход (не invariant-нарушение), а не EF-error. Кончится необработанным
исключением (500) вместо содержательного "нет доступного склада" для вызывающего кода.

### 4. ShippingPlanner.cs:31-33 - `AverageAsync` на пустой коллекции
`s.DeliveryDays!.Value` даёт неnullable `int`-селектор, поэтому используется бросающий overload
`Average` (семантика LINQ-to-Objects, EF Core её воспроизводит: пустой результат -> `throw`, а
не `null`/`0`). `DeliveryDays` проставляется только "при доставке" (Model.cs:95), то есть у
свежего склада или склада без завершённых отправлений `_db.Shipments.Where(...)` пуст всегда.
Кончится крашем `ChooseWarehouse` именно на нормальном случае (новый/малоактивный склад
оказался ближайшим и со стоком), а не на краевом.

## Major

### 5. PaymentWebhook.cs:30 - `order.Status = "Paid"` без проверки текущего статуса
Нет guard'а на `order.Status` перед переходом. Заказ, отклонённый в `OrderIntake.Accept`
(`Status = "Rejected"`, OrderIntake.cs:23, например из-за >50 позиций), при поступлении оплаты
молча становится `"Paid"` - платёж принимается по заказу, который система сама отклонила.
Кончится нарушением бизнес-инварианта "оплачен может быть только принятый заказ" без единого
предупреждения в логах/исключении.

### 6. PaymentWebhook.cs:18-41 - один `SaveChangesAsync` на весь батч, нет изоляции по notice
`SingleAsync` (20) бросает, если `OrderId` из notice не найден (или задвоен) - исключение уйдёт
наверх ДО единственного `SaveChangesAsync` (41), то есть ни один из уже обработанных в этом же
`foreach` платежей текущего батча не сохранится. Кончится тем, что один "плохой" `OrderId` в
батче блокирует запись остальных легитимных платежей батча, а вызывающая сторона не узнает,
какие notice всё-таки прошли.

### 7. OrderIntake.cs:16-28 - `items.Any()/Count()/Sum()` трижды выполняют один и тот же запрос
`ItemsOf` (10-11) возвращает `IQueryable`, приведённый к `IEnumerable` через `AsEnumerable()` -
он остаётся отложенным запросом. `items.Any()` (18), `items.Count()` (21) и
`items.Sum(...)` (28) - три независимых вызова `Enumerable`-методов, каждый заново шлёт запрос
в БД (три round-trip'а вместо одного `ToListAsync`). Кончится 3x нагрузкой на БД на каждый
`Accept()` и, в теории, разными результатами `Count`/`Sum` при параллельном изменении позиций
заказа между вызовами.

### 8. OrderIntake.cs:13-31 - `Accept` не проверяет текущий `order.Status`
Метод безусловно читает заказ по `Id` (15) и в конце пишет `"Rejected"` (23) либо
`"Accepted"` (29), не глядя, что там было раньше. Повторный вызов `Accept` для уже
`"Confirmed"` или `"Paid"` заказа откатит статус назад на `"Accepted"`/`"Rejected"`, потеряв
факт подтверждения/оплаты. Кончится откатом состояния заказа при любом повторном/неупорядоченном
вызове `Accept`.

### 9. OrderConfirmation.cs:17 - `Customers.FindAsync` внутри `foreach` по всем pending-заказам
Для каждого заказа из `pending` (13) отдельный round-trip в `Customers` (17) - классический N+1
в ночной batch-job, которая по описанию (комментарий на строке 10) может обходить произвольное
число "New"-заказов. Кончится линейным ростом числа запросов к БД с числом pending-заказов
вместо одного batched `Where(c => ids.Contains(c.Id))`.

## Minor

### 10. OrderIntake.cs:10-11 - `ItemsOf` не использует `AsNoTracking`
Позиции заказа читаются как tracked-сущности, хотя `Accept` их не мутирует (мутируется только
`order`). Кончится лишней нагрузкой на change tracker (тем более что метод и так гоняет тот же
запрос трижды - находка 7).
