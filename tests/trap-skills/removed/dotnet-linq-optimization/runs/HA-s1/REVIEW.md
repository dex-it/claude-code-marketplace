# Review MR: SalesReport.cs, CustomerExport.cs, CatalogSearch.cs, StockImport.cs

Ревью по ловушкам LINQ/EF Core команды (см. SKILL.md dotnet-linq-optimization). Описания MR нет,
контекст восстановлен по остальным файлам каталога (Model.cs, ShopDbContext.cs, ProductRepository.cs).

## Находки

### 1. SalesReport.cs:20,26 - фильтрация IsActive в памяти после загрузки всей таблицы Product
`var products = await _products.GetAllAsync(ct);` (ProductRepository.GetAllAsync -> `_db.Products.ToListAsync(ct)`,
без Where и без Select) грузит ВСЕ продукты, все столбцы, включая `Image` (`byte[]`). Фильтр
`.Where(p => p.IsActive)` (строка 26) применяется потом, в C#, а не в SQL.
Чем кончится: с ростом каталога (и особенно с ростом `Image`-блобов) отчёт по продажам тянет через
сеть весь Products целиком, хотя нужны только Id/Name активных продуктов. Классический
"ToList() в начале цепочки - фильтрация в памяти" (SKILL.md, LINQ to Entities) + "Загружает всю
entity для списка" одновременно.
Severity: **major**

### 2. SalesReport.cs:21-23 - OrderItems грузится как полная entity, без AsNoTracking
Запрос `_db.OrderItems.Where(...).ToListAsync(ct)` не проецирует результат (нужны только
ProductId/Qty/Price) и не помечен `AsNoTracking()`, хотя метод чисто read-only (отчёт). Каждая
строка OrderItem заводится под Change Tracker без необходимости.
Чем кончится: лишний трафик (лишние столбцы Id/OrderId) и лишняя память/CPU на снапшоты Change
Tracker на отчёте, который ничего не сохраняет.
Severity: **minor**

### 3. SalesReport.cs:29 - O(products x items) вложенный скан вместо группировки
`var sold = items.Where(i => i.ProductId == p.Id).ToList();` выполняется внутри `.Select(p => ...)`
по всем продуктам - то есть для каждого продукта заново линейно сканируется весь список `items`.
Чем кончится: сложность O(P x I). При каталоге в тысячи продуктов и десятках тысяч позиций заказов
за период это миллионы сравнений на одном запросе отчёта - деградация вплотную к таймауту при росте
данных. Тот же механизм, что в ловушке "FirstOrDefault вместо Dictionary" (SKILL.md), только внутри
Select: нужно один раз сгруппировать `items` в `ToLookup(i => i.ProductId)` / `Dictionary` и брать
O(1) на продукт.
Severity: **major**

### 4. CustomerExport.cs:19-21 - Distinct() на entity-объектах после AsNoTracking не дедуплицирует
`_db.Orders.AsNoTracking().Include(o => o.Customer)...` затем `orders.Select(o => o.Customer).Distinct()`.
`AsNoTracking()` (без `WithIdentityResolution`) не резолвит идентичность навигаций: каждая строка
Order с одинаковым CustomerId материализует НОВЫЙ объект `Customer` (класс `Customer` в Model.cs не
переопределяет Equals/GetHashCode). `Distinct()` сравнивает по ссылке (ReferenceEquals) и не находит
совпадений между разными инстансами одного клиента.
Чем кончится: клиент с несколькими заказами в периоде попадёт в выгрузку для CRM несколько раз -
ровно тот клиентский кейс, ради которого метод и написан ("клиенты, делавшие заказы в периоде"), не
дедуплицируется. Молчаливый функциональный баг, а не перф-деградация: метод выглядит корректным
(`.Distinct()` на месте), но не работает. Точное совпадение с ловушкой "Distinct() на объектах -
сравнение по ссылке" (SKILL.md). Фикс: `.DistinctBy(o => o.Customer.Id)` либо `GroupBy` по CustomerId
до выбора представителя.
Severity: **blocker**

### 5. CustomerExport.cs:26-27 - CountAsync(...) > 0 вместо AnyAsync(...)
`await _db.Orders.CountAsync(o => o.CustomerId == customerId, ct) > 0` считает все совпадающие
строки, хотя нужен только факт существования.
Чем кончится: лишняя работа СУБД (COUNT по всем заказам клиента вместо EXISTS с остановкой на
первой строке); для клиента с большой историей заказов - неоправданно дорогая проверка ради
булева результата. Точное совпадение с ловушкой "Count() > 0 вместо Any()" (SKILL.md).
Severity: **minor**

### 6. CatalogSearch.cs:16-36 - ToListAsync() продублирован в каждой ветке вместо одного конца цепочки
Метод `Search` строит 4 практически идентичных запроса (все 4 комбинации `category`/`maxPrice`),
каждый с собственным `.Select(Card).ToListAsync(ct)`, вместо того чтобы собрать один `IQueryable`
условными `.Where(...)` и материализовать один раз в конце.
Чем кончится: то, что сегодня отличается только двумя условиями `Where`, при добавлении третьего
опционального фильтра (сортировка, наличие на складе, диапазон дат) раздуется до 8 веток - и любое
следующее изменение (пагинация, доп. сортировка, доп. фильтр) придётся синхронно вносить в каждую
ветку. Разъезд веток при рефакторинге - молчаливый баг (забыли обновить одну из 4 копий), а не
компиляционная ошибка. Точное совпадение с ловушкой "ToListAsync() в каждой ветке условия"
(SKILL.md, "Динамические запросы").
Severity: **major**

### 7. StockImport.cs:27 - FirstOrDefault по списку внутри foreach по строкам CSV
`var product = products.FirstOrDefault(p => p.Id == id);` вызывается на каждой строке файла
поставщика, при том что `products` - список ВСЕХ продуктов (строка 15), загруженный целиком один раз.
Чем кончится: сложность O(N_products x M_строк_csv). Для среднего каталога и файла остатков на
несколько тысяч строк - миллионы сравнений на одном импорте; с ростом каталога или частоты приёма
файлов от поставщика job деградирует до неприемлемого времени выполнения. Точное совпадение с
ловушкой "FirstOrDefault вместо Dictionary" (SKILL.md): нужен `products.ToDictionary(p => p.Id)` и
`TryGetValue` за O(1).
Severity: **major**

### 8. StockImport.cs:34-35 - повтор productId в CSV задваивает счётчик Updated без дедупликации
Если один и тот же `productId` встречается в файле поставщика несколько раз (разные строки с разным
`qty`), код применяет последнее значение (что само по себе безопасно - идемпотентная перезапись
Stock), но инкрементирует `updated` на КАЖДОЕ совпадение (строка 35), а не на уникальный продукт.
Чем кончится: `ImportResult.Updated` не отражает количество реально изменённых товаров - вводит в
заблуждение оператора, читающего отчёт об импорте ("обновлено 200", а по факту уникальных товаров
150). Контракт "один id - одна операция" из ловушки "Дубликаты во входном батче без дедупликации"
(SKILL.md) для счётчика метрики не выдержан, хотя для самого Stock это не критично.
Severity: **minor**
