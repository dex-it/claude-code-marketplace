# Ревью MR: приемка заказов, webhook оплаты, выбор склада отгрузки

Файлы MR: OrderConfirmation.cs, OrderIntake.cs, PaymentWebhook.cs, ShippingPlanner.cs.
Остальные файлы каталога прочитаны для контекста конвенций (AsNoTracking в CatalogSearch.cs/CustomerExport.cs,
пакетная загрузка вместо N+1 в StockImport.cs).

## PaymentWebhook.cs

### 1. PaymentWebhook.cs:32-37 - дубль BonusAccount при двух платежах одного клиента в одном batch
Что не так: `SingleOrDefaultAsync(a => a.CustomerId == order.CustomerId, ct)` всегда идет в БД - EF Core
не подмешивает в результат запроса еще не сохраненные (Added, не SaveChanges) сущности. Если в одном
`PaymentBatch` два платежа за разные заказы одного клиента, для первого создается новый `BonusAccount`
и добавляется в контекст, но не сохраняется до конца всего `Handle`. Для второго платежа того же
клиента запрос снова не находит счет (в БД его еще нет) и создает ВТОРОЙ `BonusAccount` с тем же
`CustomerId`. `SaveChangesAsync` в конце сохранит обе строки.
Чем кончится: баланс бонусов клиента расщепляется на две строки (тихая порча данных, сумма бонуса за
первый платеж не видна в счете, который читают дальше), а следующий вызов `SingleOrDefaultAsync` по
этому `CustomerId` бросает `InvalidOperationException: Sequence contains more than one element` -
webhook начинает падать на этом клиенте.
Severity: blocker.

### 2. PaymentWebhook.cs:16-41 - нет идемпотентности по PaymentNotice.ExternalId
Что не так: `Handle` не проверяет, обработан ли уже `notice.ExternalId`, прежде чем добавлять
`Payment` и начислять бонус. Уникального ограничения на `ExternalId` в модели/контексте тоже нет
(`Model.cs:64-69`, `ShopDbContext.cs` без Fluent API).
Чем кончится: платежные провайдеры доставляют webhook at-least-once (retry по таймауту/отсутствию
200 OK). Повторная доставка того же уведомления создает вторую строку `Payment` с тем же
`ExternalId` и повторно начисляет 1% бонуса на счет клиента - двойное начисление денег клиенту без
факта повторной оплаты.
Severity: blocker.

### 3. PaymentWebhook.cs:20 - несуществующий/невалидный OrderId в одном платеже роняет весь batch
Что не так: `_db.Orders.SingleAsync(o => o.Id == notice.OrderId, ct)` внутри `foreach` без try/catch.
`SaveChangesAsync` вызывается один раз после всего цикла (строка 41), явной транзакции по каждому
элементу нет.
Чем кончится: если хотя бы один `PaymentNotice` в batch ссылается на неизвестный/пока не созданный
`OrderId`, `SingleAsync` бросает исключение, весь `Handle` прерывается до `SaveChangesAsync` - ни один
платеж из batch (включая корректные) не сохраняется. Провайдер получит ошибку и повторит доставку
всего batch целиком, что для уже успешно обработанных ранее платежей превращается в дубли по
находке #2.
Severity: major.

### 4. PaymentWebhook.cs:32-38 - lost update баланса бонусного счета между параллельными вызовами
Что не так: чтение `account.Balance` и его инкремент (`account.Balance += ...`) разнесены без
optimistic concurrency token на `BonusAccount` (в `Model.cs:55-60` его нет) и без блокировки строки.
Чем кончится: если два отдельных webhook-запроса (разные HTTP-вызовы, разные экземпляры
`ShopDbContext`) одновременно обрабатывают платежи одного клиента, оба читают одинаковый `Balance`,
инкрементируют в памяти и сохраняют - один инкремент теряется, клиент получает меньше бонуса, чем
должен.
Severity: major.

### 5. PaymentWebhook.cs:38 - бонус не округляется до цены валюты
Что не так: `account.Balance += notice.Amount * BonusRate` без округления до 2 знаков; при
многократном начислении дробные копейки накапливаются в `Balance` без округления по установленному
правилу.
Чем кончится: расхождение отображаемого/ожидаемого баланса с суммой, которую по факту можно списать
округлением - не критично для функциональности, но требует явного решения о правиле округления.
Severity: minor.

## OrderIntake.cs

### 6. OrderIntake.cs:10-11 и 18/21/28 - IQueryable, приведенный к IEnumerable, выполняет отдельный
### запрос к БД на каждое перечисление
Что не так: `ItemsOf` возвращает `_db.OrderItems.Where(...).AsEnumerable()` - `AsEnumerable()` не
материализует результат, просто меняет статический тип на `IEnumerable<OrderItem>`. Все последующие
вызовы (`items.Any()` на строке 18, `items.Count()` на строке 21, `items.Sum(...)` на строке 28)
из-за статического типа резолвятся в `Enumerable.*` (LINQ to Objects), а не в `Queryable.*` - каждый
вызов заново перечисляет исходный `IQueryable`, то есть заново выполняет SQL-запрос к БД и тянет
строки по сети, а агрегации (`Count`, `Sum`) считаются на клиенте, а не в SQL.
Чем кончится: на каждый `Accept` - три отдельных обращения к БД вместо одного (или одного
агрегирующего запроса), лишняя нагрузка на хот-пути приемки заказа. Дополнительно: если данные
`OrderItem` для заказа меняются между вызовами (гонка с другим процессом), проверка `Count() > 50` и
итоговый `Sum` считаются по разным снимкам данных - `order.Total` может не соответствовать набору
позиций, который прошел проверку лимита.
Severity: major.

## OrderConfirmation.cs

### 7. OrderConfirmation.cs:17 - N+1 запрос клиента внутри цикла по заказам
Что не так: `_db.Customers.FindAsync(new object[] { order.CustomerId }, ct)` вызывается для каждого
заказа из `pending` по отдельности, вместо одной пакетной загрузки клиентов по списку `CustomerId`
(как в `StockImport.cs:15`, где продукты грузятся один раз до цикла).
Чем кончится: ночной job с ростом числа новых заказов линейно увеличивает число запросов к БД (по
одному на заказ, в худшем случае по одному на каждого клиента) - деградация времени выполнения job
и лишняя нагрузка на БД пропорционально размеру очереди `New`-заказов.
Severity: major.

## ShippingPlanner.cs

### 8. ShippingPlanner.cs:27-29 - `.First()` падает, если ни один склад не набрал остаток
Что не так: `warehouses.OrderBy(...).First()` вызывается без проверки на пустую коллекцию. Если для
`productId`/`qty` не нашлось ни одного склада с `s.Qty >= qty` (строка 19), `withStock` пустой,
`warehouses` тоже пустой, и `.First()` бросает `InvalidOperationException: Sequence contains no
elements`. В классе уже есть метод `DefaultWarehouse()` (строка 12-13), который выглядит как
подготовленный fallback, но `ChooseWarehouse` его не использует ни в этом, ни в соседнем случае (см.
находку #9).
Чем кончится: выбор склада отгрузки падает необработанным исключением на обычном для e-commerce
сценарии - товар закончился на всех складах сразу (либо запрошенное количество нигде не набирается).
Severity: blocker.

### 9. ShippingPlanner.cs:31-33 - `AverageAsync` падает, если у выбранного склада нет завершенных доставок
Что не так: `_db.Shipments.Where(s => s.WarehouseId == nearest.Id && s.DeliveryDays != null)
.AverageAsync(...)` бросает `InvalidOperationException: Sequence contains no elements`, если у
`nearest` склада нет ни одной отправки с проставленным `DeliveryDays` (новый склад, либо все текущие
отправки еще в пути и `DeliveryDays` для них не проставлен - см. `Model.cs:95`, поле "проставляется
при доставке").
Чем кончится: как только ближайший по геометрии склад с достаточным остатком оказывается новым или
без истории завершенных доставок, весь вызов `ChooseWarehouse` падает - при этом склад по факту
пригоден для отгрузки, просто без накопленной статистики.
Severity: blocker.

### 10. ShippingPlanner.cs:23-25, 31-33 - нет AsNoTracking на read-only запросах
Что не так: запросы `_db.Warehouses.Where(...).ToListAsync(ct)` и запрос в `AverageAsync` читают
данные, которые в этом методе не модифицируются, но не помечены `AsNoTracking()` - в отличие от
принятой в проекте практики для чисто читающих запросов (`CatalogSearch.cs:19,24,29,33`,
`CustomerExport.cs:14`).
Чем кончится: лишние накладные расходы change tracker на сущности, которые никогда не будут
сохранены через этот контекст - не влияет на корректность, только на накладные расходы запроса.
Severity: minor.
