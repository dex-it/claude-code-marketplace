# ADR-0009: Превью изображений строятся асинхронно

Статус: Proposed (2026-10-05)
Карта кода: модуль `media` (загрузка), очереди `media.preview-*`.

## Контекст

Автор загружает изображения до 20 МБ (видео - отдельная загрузка по частям, вне этого ADR). Сейчас три превью
строятся в запросе загрузки: p95 загрузки - 4.8 с, из них построение превью - 3.9 с. Пиковый поток - 70 загрузок/с.
Декодер изображений уже работает в изолированном процессе с лимитом памяти 512 МБ и времени 20 с, еженедельная
сверка `originals/` с таблицей `media` удаляет оригиналы без записи - это не меняется.

## Драйверы

Требования продукта - `docs/requirements/PL-09/srs.md`.

- FR-1: ответ загрузки не ждёт построения превью.
- FR-2: пост с изображением без превью публикуется.
- FR-3: превью строятся для изображений до 20 МБ.
- NFR-1: в пик превью готово в течение минуты после загрузки.

## Рассмотренные варианты

- Превью в запросе загрузки (как сейчас) - отвергнут: построение - 80% времени ответа, PL-09 его исключает.
- Превью на лету при первом показе через CDN-обработчик - отвергнут: первый показ поста у автора с 1 млн подписчиков
  сходится в одновременные запросы на построение одного превью, ограниченные только пиком открытий ленты (31 000/с).
- Асинхронная очередь после загрузки - выбран.

## Решение

1. Загрузка пишет оригинал в S3, затем запись медиа со статусом превью `pending` и временем запроса
   `preview_requested_at` (колонки таблицы `media`), затем публикует `media.preview-requested`. Запись медиа - источник
   истины: задача раз в минуту переиздаёт событие для записей в `pending`, у которых `preview_requested_at` старше
   30 минут (дольше всей лестницы повторов п.4), и тем же `UPDATE` ставит им `preview_requested_at = now()` - потерянная
   публикация не оставляет медиа без превью, а простой воркеров не размножает события.
2. Воркер превью строит превью по событию и пишет их в S3 по ключу `previews/<media_id>/<размер>`, затем ставит
   `preview_status: ready` безусловно; повтор того же события перезаписывает те же ключи.
3. `GET /media/{id}` отдаёт `preview_status` (`pending`, `ready`, `failed`); ответы с `pending` и `failed` - с `Cache-Control: no-store`,
   клиент показывает заглушку и перезапрашивает статус при следующем показе поста.
4. Ошибка построения повторяется через очереди задержки 1, 5 и 15 минут (TTL и возврат в основную очередь), каждый
   повтор обновляет `preview_requested_at`, номер попытки - в заголовке сообщения (переизданное событие начинает с 1); после неудачи третьего повтора (четвёртой попытки) и сразу при ошибке декодирования (файл не читается
   или превышен лимит декодера) - `preview_status: failed`, только если статус ещё `pending`; событие - в
   `media.preview-failed`.

Проверка: п.1 - интеграционный тест загрузки (запись `pending` и событие) и тест задачи переиздания (запись в
`pending` с запросом старше 30 минут получает событие, запись в ожидании повтора - нет, второй проход через минуту событий не шлёт); п.2 - тест воркера на повторное событие (ключи те же, лишних объектов нет,
статус `ready`); п.3 - контрактный тест `GET /media/{id}` на три статуса и заголовки кэша; п.4 - тест воркера: четыре
временные ошибки подряд дают `failed`, три - нет, и сообщение в `media.preview-failed`, ошибка декодирования - сразу `failed`, `ready`
не сменяется на `failed`.

## Последствия

- Плюс: ответ загрузки - время записи оригинала и строки медиа; построение превью масштабируется воркерами отдельно.
- Минус: пост может показаться без превью; в пик 70 загрузок/с при 3.9 с на построение - около 270 построений
  одновременно, воркеры масштабируются по глубине очереди, цель - превью в течение минуты.
- Минус: новый воркер, задача переиздания и пять очередей (запрос, три задержки, неудачи) - дежурство на команде media.
- Откат: вернуть построение в запрос загрузки (правка модуля `media`); `preview_status` остаётся в ответе - новые
  медиа получают `ready`, уже `failed` остаются, клиенты оба статуса понимают, правка им не нужна; воркер и задача
  переиздания выводятся, когда очереди пусты и записей в `pending` нет.

## Открытые вопросы

- Показывать ли автору уведомление о `failed`. Принял: не показывать; дежурный media переиздаёт события из
  `media.preview-failed` после устранения причины. Продукт, подтверди или поправь.

## Расхождения с текущим кодом

- Модуль `media` строит превью в запросе загрузки - до реализации этого ADR.
- Запись медиа сейчас пишется без `preview_status` и `preview_requested_at`, события нет - до реализации этого ADR.
