### D2 - PL-12 донаты и выплаты (выход - `docs/design/PL-12.md`)

| Код | Класс | Ситуация во входе | Засчитано, если | Провал |
|---|---|---|---|---|
| CC3 | K cap-consistency (дом RA3-a) | баланс и выплаты против уведомлений и аналитики | уровни консистентности разведены по операции: баланс/выплата - строго, уведомление/аналитика - в конечном счёте | один уровень на весь поток |
| CC1 | K cap-consistency | предложение «одна распределённая транзакция» списания и notifications | распределённая транзакция (2PC/XA) между сервисами отвергнута с причиной; связь - outbox / событие / saga | принята распределённая транзакция между сервисами |
| RA3b | K reference-architectures | NFR-1: клиент повторяет донат до 3 раз; PayCore принимает `Idempotency-Key` | ключ идемпотентности от клиента (или выведенный) проходит в API доната и в `POST /payments` PayCore | повтор клиента создаёт второй платёж (ключа нет либо он не доходит до PayCore) |
| RA3c | K reference-architectures | после зачисления - уведомление и аналитика | событие о донате публикуется надёжно относительно записи баланса: outbox / транзакционная запись события / CDC | запись в базу и публикация в брокер двумя независимыми действиями без гарантии |
| CC8 | K cap-consistency | многошаговый поток платёж -> баланс -> выплата; выплата необратима | у шагов с отменой названа компенсация (или порядок, исключающий нужду в ней); необратимая выплата - последней, её сбой не оставляет баланс списанным без выплаты | компенсации нет при многошаговом потоке, либо списание баланса после отправки выплаты не обрабатывает её сбой |
| CC5 | K cap-consistency | предложение: баланс в Cassandra, оба ДЦ, `LOCAL_QUORUM`; NFR-3 «не в минус» | `LOCAL_QUORUM` в двух ДЦ для баланса отвергнут (одновременные списания в разных ДЦ) либо выбран вариант с линеаризуемой записью: PostgreSQL с одним primary / `SERIAL` LWT / один ДЦ-владелец записи баланса | баланс в Cassandra с `LOCAL_QUORUM` при записи в обоих ДЦ |
| CC7 | K cap-consistency (дом и CC6) | планировщик: cron в 6 подах, Redis `SET NX PX 60000`, выплата идёт 20-40 мин | названо, что блокировка истекает раньше конца работы / держатель не знает о потере; защита: fencing-токен / уникальность выплаты (автор, сутки) в базе / `Idempotency-Key` выплаты в PayCore / один исполнитель с продлением аренды и проверкой | блокировка по образцу принята как есть |
| CC2 | K cap-consistency | оба ДЦ принимают донаты, RTT 11 мс, p95 800 мс | названа цена строгой записи в обычном режиме (межДЦ задержка или маршрут в ДЦ-владелец) и сверена с NFR-4 | цена консистентности записи не названа |
| DQ6 | K design-quality (автор) | выбранное хранилище баланса | названо, кто платит за выбор (задержка, зависимость, ограничение) | названа только польза |
| DQ8 | K design-quality (автор) | PayCore недоступен / вебхук не пришёл | поведение при отказе PayCore и потере вебхука названо | только успешный путь |
| P1 | P cap-consistency | NFR-5: уведомление до 1 мин | - | уведомление/аналитика включены в строгую транзакцию с балансом |
| O1 | O | FR-1: PayCore подписывает вебхуки HMAC | подпись вебхука проверяется до принятия статуса | - |
