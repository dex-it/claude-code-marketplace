# SRS: Часы сверх пакета (фича 02)

## Рамка

Предмет - бронь переговорной сверх пакета часов компании с оплатой картой компании, лимит расходов
компании и учёт этих расходов. Граница: сервис ведёт брони, удержания, лимиты и учёт платежей;
приём карты и списание денег - у провайдера (ADR-001); бухгалтерский учёт площадки и компании - вне
сервиса. Смежные системы: платёжный провайдер (платежи, возвраты, привязка карт - вебхуками),
учётная система площадки (пакеты часов).

## Функциональные требования

- **FR-2001** Когда часов пакета на выбранную бронь не хватает и у компании привязана карта и задан
  лимит, система показывает стоимость брони сверх пакета и остаток месячного лимита компании.
  Основание: UC-2001 шаг 1. Проверка: пример на данных.
- **FR-2002** Стоимость брони сверх пакета - часы брони, округлённые вверх до получаса, умноженные на
  1,5 тарифа часа пакета компании. Основание: UC-2001 шаг 1, D-4, FR-1002. Проверка: пример на данных.
- **FR-2003** Если стоимость брони больше остатка лимита компании, система отказывает в брони и
  сообщает остаток лимита; удержание не создаётся. Основание: UC-2001 1a, D-1. Проверка: пример на
  данных.
- **FR-2004** Когда сотрудник подтверждает бронь сверх пакета, комната удерживается за ним в статусе
  «ожидает оплаты» и недоступна другим броням: удержание берётся блокировкой строки комнаты
  `SELECT ... FOR UPDATE` внутри транзакции создания брони, а запись удержания пишется в таблицу
  `room_holds`. Основание: UC-2001 шаг 3, D-2. Проверка: пример на данных.
- **FR-2005** Когда провайдер вебхуком сообщил об успешной оплате, бронь переходит в статус
  «подтверждена», а сотрудник получает номер брони. Результат оплаты сервис принимает только
  вебхуком провайдера, по таймеру провайдер не опрашивается (ADR-001). Основание: UC-2001 шаги 4-5, D-2, ADR-001. Проверка: пример на
  данных с имитацией вебхука.
- **FR-2006** При подтверждении брони сверх пакета остаток лимита компании уменьшается на стоимость
  брони: система увеличивает поле `spent_minor` (bigint, копейки) строки компании в таблице
  `company_limits` командой `UPDATE ... SET spent_minor = spent_minor + :cost` в той же транзакции, что
  и перевод брони в «подтверждена»; остаток - разность `limit_minor` и `spent_minor`. Основание:
  UC-2001 шаг 5, D-1. Проверка: пример на данных.
- **FR-2007** Если провайдер отклонил оплату, удержание комнаты снимается, сотрудник получает
  сообщение «оплата отклонена», лимит не меняется. Основание: UC-2001 4a. Проверка: пример на данных с
  имитацией вебхука.
- **FR-2008** Если провайдер отклонил оплату, администратор компании получает уведомление с именем
  сотрудника, временем брони и причиной отказа от провайдера. Основание: UC-2001 4a. Проверка: пример
  на данных; инспекция журнала уведомлений.
- **FR-2009** Если подтверждение оплаты не пришло за 15 минут удержания, система снимает удержание,
  отменяет платёж у провайдера и сообщает сотруднику, что бронь не состоялась. Основание: UC-2001 4b,
  D-7. Проверка: пример на данных с задержанным вебхуком.
- **FR-2010** Вебхук без верной подписи провайдера отклоняется и пишется в журнал безопасности.
  Основание: ADR-001. Проверка: пример на данных; инспекция журнала безопасности.
- **FR-2011** Когда сотрудник отменяет оплаченную бронь сверх пакета, комната освобождается и у
  провайдера создаётся возврат. Сумма возврата - открытый пункт D-8. Основание: UC-2002 шаг 2.
  Проверка: пример на данных.
- **FR-2012** Когда провайдер сообщил об успешном возврате, остаток лимита компании увеличивается на
  сумму возврата, сотрудник получает сообщение о возврате. Основание: UC-2002 шаг 4. Проверка: пример
  на данных с имитацией вебхука.
- **FR-2013** Если провайдер отклонил возврат, финансы площадки и администратор компании получают
  уведомление с номером брони и суммой; бронь остаётся отменённой. Основание: UC-2002 3a. Проверка:
  пример на данных; инспекция журнала уведомлений.
- **FR-2014** Сверхпакетная бронь доступна, только когда у компании привязана карта и задан лимит; иначе
  сотрудник получает отказ «пакет исчерпан» по FR-1004. Основание: UC-2003 2a, D-1. Проверка: пример
  на данных.
- **FR-2015** Когда администратор компании выбирает месяц, система показывает расходы его компании
  сверх пакета за этот месяц по сотрудникам: API отдаёт все платежи месяца одним JSON-массивом, а
  группировку по сотрудникам и сортировку выполняет React-компонент `SpendTable` в браузере.
  Основание: UC-2004 шаг 2. Проверка: пример на данных.
- **FR-2016** Если у компании за выбранный месяц нет расходов сверх пакета, система сообщает «расходов
  нет», выгрузка недоступна. Основание: UC-2004 2a. Проверка: пример на данных.
- **FR-2017** Администратор компании выгружает расходы компании сверх пакета за выбранный месяц
  файлом: сотрудник, номер брони, время брони, сумма. Основание: UC-2004 шаг 3. Проверка: пример на
  данных.
- **FR-2018** Финансовый менеджер площадки выгружает за выбранный месяц все платежи и возвраты с
  номером брони, компанией, суммой, датой и идентификатором операции у провайдера. Основание: UC-2005
  шаг 2, BR-2004. Проверка: пример на данных; сверка выгрузки с отчётом провайдера за тестовый месяц.
- **FR-2019** Если у площадки за выбранный месяц нет платежей и возвратов, система сообщает «операций
  нет». Основание: UC-2005 2a. Проверка: пример на данных.
- **FR-2020** В начале календарного месяца использованный лимит каждой компании обнуляется.
  Основание: BR-2003 (несценарная ветка). Проверка: пример на данных.

## Нефункциональные требования

- Отклик API - **NFR-0001**, доступность - **NFR-0002** (продуктовый уровень).
- **NFR-2001** Брони, платежи и расходы компании доступны только её сотрудникам и администратору (свои
  брони - сотруднику, все брони компании - администратору); запрос данных другой компании получает
  «не найдено». Номера броней и выгрузок не последовательные. Основание: BR-2003, ADR-002, D-4 фичи
  01. Проверка: разбор модели доступа; пример на данных (запрос данных другой компании).
- **NFR-2002** Платежи и возвраты хранятся 5 лет в кластере PostgreSQL сервиса (ADR-002) и не
  удаляются по запросу компании. Основание: BR-2004, интервью 03.09.2026 (финансы). Проверка:
  инспекция конфигурации хранения.
- **NFR-2003** Данные карты сервис не получает и не хранит - только токен провайдера; ключи API и
  секрет подписи вебхуков провайдера хранятся вне кода и конфигурации репозитория. Основание: ADR-001.
  Проверка: инспекция кода и конфигурации.
- **NFR-2004** Выгрузка платежей месяца (FR-2018) готова не дольше чем за 30 с при 5 000 операций в
  месяце. Замер: на стенде, от запроса до готового файла. Основание: BR-2004. Проверка: замер на
  стенде.
- **NFR-2005** Сервис работает минимум в трёх репликах приложения за балансировщиком; при загрузке
  CPU выше 70% включается автомасштабирование (Kubernetes HPA, до 8 реплик). Основание: NFR-0002.
  Проверка: инспекция манифестов развёртывания.
