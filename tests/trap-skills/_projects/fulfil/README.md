# Мини-проект Fulfil: вход наборов группы 4.3

Сервис исполнения заказов на .NET 10 (ASP.NET Core, один проект `src/Fulfil`): оба брокера в разных потоках,
Redis, MongoDB и Elasticsearch в `docker-compose.yml`. Вход наборов [kafka](../../kafka/README.md),
[rabbitmq](../../rabbitmq/README.md), [redis](../../redis/README.md), [mongodb](../../mongodb/README.md),
[elasticsearch](../../elasticsearch/README.md) (эпик #291, #304). Файл - ключ для судьи, исполнителю не подаётся:
`setup.sh` его в каталог прогона не копирует.

```
setup.sh <dest> [ветка]   разворачивает git-репозиторий: stages/* - коммиты main, branches/<имя>/* - ветка feature/<имя> от main
stages/1-service          main: домен, порты (IPaymentGateway, IPriceSource, ICatalogSource), FulfilOptions, compose, ADR-0001/0002
branches/                 код - order-stream, payment-flow, price-cache, order-history, product-search, volume-discount (только задача);
                          ревью - kafka-pipeline, payment-saga, catalog-cache, order-archive, catalog-search, catalog-sync (чистая)
run-group-4-3.sh          раннер: промпты кода и ревью дословно, флаги исполнителя, выход в <скилл>/runs/<кейс>-<набор><N>/
```

Теги образов `kafka`, `schema-registry`, `rabbitmq`, `redis`, `mongo` сверены по реестру Docker Hub 19.10.2026; тег
Elasticsearch назван по версии клиента, реестр не сверялся. Образы не тянулись, compose не поднимался. Версии пакетов

## Правила набора (записаны до первого прогона)

1. Исполнитель - `claude-sonnet-5-5`, `--effort medium`, `--restricted --strict-mcp-config`, без `Skill` tool и веба, Bash
   только `git`. Каталог прогона `$G43_WORK` вне репозитория: на пути нет `CLAUDE.md` (раннер проверяет при старте, и
   `~/.claude/CLAUDE.md` нет). Набор контроля - `c`, прогонов на кейс два (`c1`, `c2`); добор и повторы - только заранее
   объявленным правилом ниже.
2. Единица снимается, если в каждом кейсе, где ситуация воспроизведена, верны оба прогона контроля (метод, шаг 2:
   и для потребителя, который такой код пишет, когда ситуация воспроизведена ревью). Кейс, где ситуация не возникла
   (исполнитель не создал код, в котором она есть, а задача её не требовала), клетку даёт `n/a`; единица с одними `n/a`
   получает `unverifiable`, а не снятие.
3. Правило подмножества: каждая единица судится по всем прогонам набора, в которых для неё есть клетка. Выбор
   подмножества - только заранее и для всех единиц. Провал одного прогона в паре держит единицу.
4. Ревью. K засчитан, если находка стоит в месте ключа и называет последствие, снимаемое исправлением; слово ловушки и
   severity не требуются. P - провал, если находка по приманке просит правки с severity blocker или major (minor -
   замечание, не провал). O - засчитан, если названа ошибка по существу. Находки сверх ключа в коде MR, которые
   судья сам признаёт настоящими, в вердикт не идут (Н).
5. Код. K засчитан, если решение из графы «Засчитывается» есть в месте, где задача создаёт ситуацию. Ситуация есть,
   решения нет - провал. Решение, заданное средой кейса (ADR, compose, дефолт клиента, существующий код main),
   исполнителю не засчитывается: ситуация должна требовать его выбора. N-G: провал - правка вне домена и тестов
   (брокер, хранилище, compose), неверное правило скидки.
6. Дефект кейса (мина, неоднозначная формулировка, ключ, не выводимый из задачи) разбирается до причины, правится в
   кейсе, прогоны до правки уходят в `runs/` с пометкой и в счёт не идут; ключ после прогона правится записью с
   причиной, в пользу снятия не засчитывается.
7. Судья ведёт таблицу «единица - кейс - прогон - 0/1 - место в выходе»; вердикт по единице и находки сверх ключа
   проверяет оператор по выходу (выборочно и по всем спорным клеткам).
8. Редакции со скиллом (дописано после контроля, до прогонов со скиллом). Лестница формы: первая редакция `n` - пункты-названия
   только для единиц, не снятых контролем; прогон `n` - кейсы, где единица не снята (код и ревью своего скилла), по два
   прогона, плюс кейсы N. Единица, не вернувшая 2/2 на названии, идёт на следующую ступень (факт версии, исход) и
   перепрогоняется тем же правилом. Потолок - три ревизии на единицу, дальше «Открыто». Кейсы N-G и N-RV берут итоговые
   редакции всех пяти скиллов вместе (один прогон = все пять файлов в `discipline`), по два прогона каждого: консервативная
   проверка «не хуже контроля» на ложные правки и приманки.
9. Потолок расходов - $30 по `total_cost_usd` суммарно по сменам; `--max-budget-usd 2.5` на прогон.
10. Ревизия `r` (ревью mmx003 по PR #369, 20.10.2026; записана до прогонов `r`). Правка тел: пункты mongodb (копия изменяемых данных
    другой сущности; список читает документы целиком, когда нужна часть полей), elasticsearch (текст на языке с морфологией),
    rabbitmq (сохранение данных и публикация события) переведены с формулировок фикстуры на признак ситуации; в redis возвращён
    пункт C4 «Конкурентные промахи горячего ключа идут в источник каждый» (дубль с `dotnet-resilience` H1 не доказан: тот пункт -
    `IMemoryCache.GetOrCreate` внутри процесса, redis стек-нейтрален). Файлы - `inputs/SKILL-1.2.0-r.md` каждого скилла.
    Прогоны `r`: по два на кейс G-M, RV-M, G-E, RV-E, G-B, RV-B, G-C, RV-C (скилл своего кейса, `r1`, `r2`) и N-G, N-RV
    (пять файлов `r` вместе, `kafka` - 1.2.0). Ключ не меняется. Критерий: единицы своих пунктов не хуже набора `n`, остальные
    не хуже контроля `c` (шум n=2 называется шумом, не снятием); C4 судится как единица пункта: RV-C 2/2 против контроля 0/2
    (G-C - клетка единицы, не наблюдаемая); приманки и ложные blocker/major в N-кейсах не хуже `f`. Исходы заносятся в
    протоколы скиллов отдельной строкой, прогоны `n`, `o`, `f` не пересчитываются.
11. Добор по просадкам вне правленых пунктов (вопрос владельца по PR #369; записано до прогонов добора). Клетки: RV-M M11 и M4
    (r 0/2 и 0-1/2 против контроля 2/2), RV-B B7 и O1 (r 1/2 против 2/2), G-B B2 (r 1/2 против 2/2). Добор: по два прогона
    **обеих** рук на те же кейсы RV-M, RV-B, G-B - редакция группы `r3`, `r4` (скилл своего кейса, `inputs/SKILL-1.2.0-r.md`)
    и контроль `c3`, `c4` (без скилла); итого n=4 на клетку в каждой руке, 12 прогонов, прогоны `c1`, `c2`, `r1`, `r2` не
    пересчитываются. Раннер и промпты те же, что в правиле 10; перед запуском печатается команда и проверяется, что в
    `discipline` лежит ровно файл своего скилла (руке `c` - ничего). Судится только перечень клеток выше, ключ не меняется.
    Критерий по клетке (k - число засчитанных прогонов из 4): **шум**, если `k_c - k_r <= 1` (в том числе когда контроль сам
    не берёт клетку в `c3`/`c4`); **просадка подтверждена**, если `k_c - k_r >= 2`. Подтверждённая просадка различается по
    выходу провальных прогонов `r`: **сужение охвата** - ни место ключа, ни его последствие не названы (редакция сместила
    внимание на свои пункты); иначе - расхождение судейства, не сужение. Клетка, спорная по ключу хотя бы в одном прогоне
    (`?` судьи, подтверждено оператором как спорная), считается по букве ключа, но единица выносится в «Открыто» с ключом
    спорной клетки, и вердикт по ней не закрывающий. Исход: клетка «шум» - в протокол скилла строка «шум n=4», правок нет;
    «просадка, сужение охвата» - лестница формы для затронутого скилла (название -> факт версии -> исход и граница, правка
    тела одной фразой по шагу 4 метода, правка в версии `s`, файл `inputs/SKILL-1.2.0-s.md`), перепрогон по два на кейс
    скилла плюс его N-кейсы и кейсы, чьи единицы задела фраза; потолок - три ревизии, дальше «Открыто»; «просадка без
    сужения» - в «Открыто» без правки тела. Судей одновременно не больше двух; потолок расходов добора - $10 по
    `total_cost_usd`, `--max-budget-usd 2.5` на прогон; каталог не бампается.
12. Ревизия по ревью mmx003 на PR #381 (записана до прогонов). (а) Правило 11 применяется по букве: исход B2 в G-B определяется

    «сужение охвата» не объявляется, исход - «просадка подтверждена, без сужения»; единица B2 - в «Открыто» (клетка `r2` спорная),

    Перепрогон не нужен: тело не меняется относительно проверенной редакции `r`. (б) mongodb: пятое название (M11) вводит

## Ключ: код (G-K, G-B, G-C, G-M, G-E)

«Засчитывается» - перечень допустимых решений; любое из них в месте, где задача создаёт ситуацию, - 1. Решение,
которого нет в перечне, судья относит к ближайшему допустимому по смыслу и записывает; спорное решает оператор до
вердикта по единице.

### G-K (FUL-11, Confluent.Kafka 2.16.0)

| Код | Ситуация в задаче | Засчитывается |
|---|---|---|
| K1 | публикация `orders.status-changed` (п. 2) | результат доставки не теряется: `await ProduceAsync` с реакцией на `ProduceException`, либо `Produce` с обработчиком отчёта доставки, который не только пишет в лог без последствий (повтор, пометка, исключение). Провал: `Produce` без обработчика; `ProduceAsync` без `await` и без продолжения |
| K2 | та же публикация | ключ сообщения - стабильный бизнес-ключ (`OrderId`; допустим `CustomerId`). Провал: ключ не задан или случаен |
| K3 | остановка сервиса при rolling update (ADR-0002) | `Flush` с таймаутом при остановке до `Dispose` продьюсера; `n/a`, если все публикации ожидаются через `await ProduceAsync` и буфера нет |
| K4 | продьюсер сервиса | `EnableIdempotence = true`. Провал: не задано (дефолт librdkafka - `false`) |
| K5 | потребитель `orders.placed` | смещение фиксируется после записи в MongoDB: `EnableAutoCommit=false` и `Commit` после обработки, либо `EnableAutoOffsetStore=false` и `StoreOffset` после обработки при автокоммите. Провал: дефолты (`StoreOffset` до обработки) |
| K6 | 3 реплики, rolling update (смена владельцев партиций) | обработчик отзыва партиций, фиксирующий обработанное; либо фиксация после каждого сообщения (нет накопленных несохранённых смещений). Провал: накопленные несохранённые смещения и нет обработчика |
| K7 | `$inc` на `customers` (п. 1) | повторная доставка того же `OrderId` не учитывается дважды: уникальный ключ обработанных, условный апдейт с проверкой `OrderId`, идемпотентная форма (пересчёт из заказов). Провал: безусловный `$inc` |
| K8 | сообщение, которое не разбирается или не обрабатывается | ограниченное число повторов, затем передача на разбор с сохранением содержимого и причины (топик `*.DLT`, коллекция `dead_letters`) и продвижение. Провал: бесконечный повтор на месте; пропуск, оставляющий только строку лога; падение сервиса |
| K9 | пакетный импорт (п. 3) | смещение фиксируется только после успешной записи всей пачки (или за последним успешно записанным); при ошибке пачка повторяется или уходит на разбор. Провал: фиксация в `finally`/до записи/по `Last()` при исключении |
| K10 | два формата события (п. 4) | читаются оба формата: `GiftWrap` необязательно с умолчанием `false`, неизвестные поля не роняют разбор; либо реестр схем с проверкой совместимости. Провал: разбор падает на сообщении без поля (`required`, строгий разбор) |

### G-B (FUL-12, RabbitMQ.Client 7.2.2, MassTransit 8.5.11)

| Код | Ситуация | Засчитывается |
|---|---|---|
| B1 | прямой консьюмер `warehouse.inbound` (п. 4) | `autoAck: false`; `BasicAckAsync` после записи в MongoDB; при ошибке `BasicNackAsync`/`BasicRejectAsync` без возврата в ту же очередь. Провал: `autoAck: true` |
