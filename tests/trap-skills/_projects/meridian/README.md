# Мини-проект Meridian: большой репозиторий для ADR, гейта обоснования и свода правил

Вход набора [codebase-conventions](../../codebase-conventions/README.md), заход «большой репозиторий»
(#311, эпик #291); документы-кейсы для потребителей-документов подготовлены в #432 (раздел в конце, прогонов нет). Мини-проект [billing](../billing/README.md) мал: все ADR и свод читаются одной
командой, поиск источника не измерен. Здесь поиск источника нетривиален. Файл - ключ для судьи,
исполнителю не подаётся: генератор его в каталог прогона не копирует. **Ключ записан и закоммичен
до первого прогона контроля; правка ключа после прогона в пользу снятия не засчитывается.**

```
generate.py <dest> [ветка]   генератор: git-репозиторий с тремя коммитами main и двумя ветками MR; детерминирован
docs_data.py                 тексты ADR (три места), записей, свода правил, handbook
hot_code.py                  код с ключом: libs, shipping, payments, catalog, orders и правки веток
setup.sh <dest> [ветка]      обёртка над generate.py (по образцу соседних проектов)
run-big-repo.sh              раннер: промпты, флаги исполнителя, выход в codebase-conventions/runs/big-*
doc_cases.py                 документы-кейсы #432 (дизайн-документ, набор требований): шаблоны и слоты ключа
check-doc-cases.py           проверка документов-кейсов без исполнителя: мутации различаются только слотами ключа
make-doc-arms.py             выдержки из агентов `design-reviewer`, `requirements-reviewer` -> codebase-conventions/inputs/
```

Воспроизведение: `bash setup.sh <пустой каталог> [main | feature/partial-refunds | feature/tariff-cache]`,
нужны `git` и `python3`; сеть и dotnet не нужны. Результат (около 285 файлов, 68 единиц ADR) в
репозиторий не коммитится: он детерминированно строится генератором. Код не собирается (пакетов нет),
исполнитель работает без dotnet, прогон судится по диффу и тексту. Это граница мерила: поведение при
сборке не проверяется.

## Устройство

Монорепозиторий .NET 8: `libs/` (Meridian.Common, Meridian.Contracts), `services/` (orders, payments,
shipping, catalog, inventory, notifications, identity, reporting; около 15 файлов кода на сервис),
`docs/`, `platform/`, `architecture/`. `README.md` в корне называет каталоги, ADR и свод не упоминает.
`CLAUDE.md` и CONTRIBUTING нет.

**ADR в трёх местах, 68 единиц** (`.docs_layout` называет только `adr: docs/adr/`):

- `docs/adr/ADR-0001..0034-*.md` - платформенные;
- `services/<сервис>/docs/decisions/<ПРЕФИКС>-ADR-NNN-*.md` - сервисные (SHP, PAY, CAT, ORD, INV, NTF, IDN, RPT);
- `architecture/records/REC-01..12-*.adr.md` - записи до ADR, другой формат (`Status:` латиницей).

Статусы: Accepted, Superseded by, Deprecated, Rejected, Proposed.

**Цепочки supersede (длиннее одного звена, через места):**

| Предмет | Цепочка | Действует |
|---|---|---|
| повторы исходящего HTTP | REC-04 (цикл в клиенте) -> ADR-0011 (Polly `AddPolicyHandler`) -> ADR-0019 (свой `AddResilienceHandler`) -> ADR-0026 | ADR-0026: `AddStandardResilienceHandler()` |
| публикация событий | REC-07 (`IBus` после сохранения) -> ADR-0009 (outbox с опросом) -> ADR-0021 | ADR-0021: `IOutbox.EnqueueAsync` в единице работы, имя `<Агрегат><Прошедшее>IntegrationEvent` |
| вызовы PSP | PAY-ADR-002 (через очередь) -> PAY-ADR-003 | PAY-ADR-003: синхронно в запросе |
| кэш тарифов | CAT-ADR-001 (без кэша) -> CAT-ADR-002 | CAT-ADR-002: кэш в процессе, TTL до 5 минут, устаревание допустимо |

**Свод правил** - `platform/handbook/engineering-rules/` (четыре файла и `README.md`, RUL-0001..0022).
Адрес - ключ `rulebook` в `.docs_layout`. Находится и обычным поиском: строка `RUL-` и заголовок
«Свод правил команд Meridian» в `grep -r`, папка называется `engineering-rules` и лежит рядом с
handbook. Ключ не обязателен для поиска: контроль не проваливается от незнания формата.
`Proposed`: RUL-0005, RUL-0014, RUL-0019; `Deprecated`: RUL-0022.

**Легаси-соседи ближе к правке, чем ADR.** В `services/shipping` хендлеры публикуют через `IBus`,
бросают исключения, берут `DateTime.UtcNow`, клиент перевозчика повторяет циклом по REC-04, сумма
`Shipment.DeclaredValue` - `decimal`. В `services/payments` модуль регистрирует Polly со ссылкой на
ADR-0011, хендлер захвата бросает и публикует через `IBus`. Современные образцы есть в `orders`
(`PlaceOrderHandler`, `OrdersModule`) и `inventory`; в остальных сервисах преобладает легаси. Сервисные
ADR называют легаси-хендлеры долгом (SHP-ADR-002, PAY-ADR-004).

## Исполнитель

`claude -p`, `claude-sonnet-5-5`, `--effort medium`, `--restricted --strict-mcp-config`,
`--disable-slash-commands`, инструменты Read Write Edit Glob Grep и `Bash(git *)`, без `Skill` в
контроле, без `dotnet`, без MCP. Каталог прогона - вне репозитория, на пути нет `CLAUDE.md`
(проверяет раннер). Общий исполнитель без нормы узла dex-auto. Потолок на прогон `--max-budget-usd 3`.
Прогон со скиллом подаёт копию `SKILL.md` путём (как в billing): 1.12.0 для прогонов до правки 2, итоговую
1.13.0 из ветки для `big-n0-v3-t*`; адрес свода через
`project-docs-map` исполнителю недоступен как Skill, поэтому со скиллом мерится название пункта.

**N0: «ничего не менять»** (`feature/tariff-cache` против `main`). Код верен в редакции после правки 2
(ниже): `PricingTariffSource` бросает исключение и на `null`-теле, и на пустом списке (`tariffs is { Count: > 0 }
? tariffs : throw`), поэтому пустой ответ не кэшируется; в кэше массив; блокирующих примитивов нет. Приманки:
P5 - кэш в процессе с TTL 5 минут, устаревание и расхождение экземпляров (CAT-ADR-002, `Accepted`;
CAT-ADR-001 «без кэша» - отменён); P6 - синхронный вызов Pricing (ADR-0025, `Accepted`); P7 - нет тестов в MR
(RUL-0016); P8 - отсутствие защиты от одновременных промахов кэша (single-flight): решение осознанное,
GET списка тарифов идемпотентен, лишние вызовы ограничены `AddStandardResilienceHandler` из ADR-0026, а
кэш на единственном ключе при TTL 5 минут промахивается редко; находка о нём допустима только как minor
(в счёт не идёт), severity blocker/major по ней - приманка сработала. Верный исход: ни одной находки
severity blocker/major и ни одной находки о P5-P8 как о дефекте выше minor. Допустимо (в счёт не идёт):
minor вне приманок.

**Дефект кейса N0, найденный прогоном `big-n0-c1` (правка кейса, не ключа в пользу снятия).** В первой
редакции `PricingTariffSource` возвращал `[]` на пустом ответе и `CachedTariffSource` кэшировал пустой
список на TTL, без защиты от одновременных промахов, с изменяемым `List` в кэше: контроль нашёл
настоящий major (пустой список на 5 минут) и два настоящих minor. Кейс не был «чистым». Исправлено
в `hot_code.py`: пустой ответ - исключение, `SemaphoreSlim` с повторной проверкой, в кэше массив.
`big-n0-c1` не засчитывается (дефект кейса, правится в кейсе, норму не растит); к приманкам добавлена
P7 (находка «нет тестов» ложна по RUL-0016) - ужесточение. Засчитываются прогоны `big-n0-c2` и далее.

**Второй дефект кейса N0, найденный ревью PR #399 (правка 2, до перепрогона).** Правка 1 оставила два
изъяна. Во-первых, `PricingTariffSource` бросал только на `null`-теле (`?? throw`), а пустой список `[]`
проходил и кэшировался на TTL - то самое событие, из-за которого признан дефектом `big-n0-c1`; по
сырым `REVIEW.md` прогонов `c2`-`c6`, `d1`-`d5`, `t1`-`t10` (20 прогонов правки 1) это отметили 13
(`c2`, `c4`-`c6`, `d2`, `d3`, `d5`, `t1`-`t5`, `t7`), так что ключ «Код верен» в этой редакции не соответствовал коду. Во-вторых, статический
`SemaphoreSlim` `Gate` держался на всё время HTTP-вызова с ретраями `AddStandardResilienceHandler`: при
недоступном Pricing очередь ожидающих шла последовательно (каждый ожидающий после отказа предыдущего
повторял вызов сам), `c6` и `t1`-`t4`, `t6` ставили по нему major. Решение: `Gate` - настоящее
замечание к коду (держать блокировку на время сетевого вызова с ретраями нельзя без отдельного
решения о границе ожидания), поэтому оно убрано минимальной правкой, а не оправдано как single-flight:
`CachedTariffSource` проверяет кэш, при промахе зовёт `PricingTariffSource` и кладёт результат; повторная
проверка и семафор удалены. Отсутствие single-flight названо приманкой P8 (допустимо только minor).
Пустой ответ - исключение: `tariffs is { Count: > 0 } ? tariffs : throw`. Ключ и правка кейса закоммичены
до перепрогона (коммит записан в протоколе `codebase-conventions/README.md`). Прогоны на правке 1
(`big-n0-c1`-`c6`, `d1`-`d5`, `t1`-`t10`) остаются в `runs/` как есть и относятся к кейсу до правки 2; новые
прогоны - под id `big-n0-v3-c*` (контроль, описание MR v2) и `big-n0-v3-t*` (скилл 1.13.0, описание MR v2).

**Описание MR, версия 2 (наборы `d` и `t`).** Прогоны v1 (`c`, `s`) дали контролю 5/5 по R1 и N0, но
в N0 источник приманок (CAT-ADR-002, ADR-0025) в журнале прочитан не был, а описания MR сами
оправдывали приманки («синхронно», «на 5 минут»): контроль проходил, не обращаясь к ADR. Это
нечувствительность кейса, а не дефект кода. Описания v2 оговорок не несут (R1 - без «синхронно»; N0 -
без «в процессе» и срока); правка идёт в сторону ужесточения, v1 остаётся в протоколе как есть. Для
каждого прогона добавляется диагностика по журналу: прочитан ли источник приманки и ключевых
решений (файл ADR или свода открыт либо его содержимое попало в выдачу поиска).

## Засчитывание

- **Ловушка** засчитана, если находка стоит в месте ключа и её исход снимает дефект или его симптом;
  слово ловушки не требуется. **Приманка** сработала, если находка объявляет приманку дефектом (любой
  severity), не ссылаясь на покрывающий её источник.
- **Ось 6, «легаси-сосед против `Accepted` ADR»:** D1, D2, D4, D5 в F1; KA, KE, KD в R1.
  **«Находка против `Accepted` ADR»:** P1, P5, P6. **`Superseded` / `Deprecated`:** D1 и D2 (цепочки; код,
  следующий звену цепочки, провален), KS, ловушки P1 и P5 (отменённый ADR говорит обратное).
- **Свод:** D3, D6, KR, KN, KL; приманки P3, P4 (`Proposed`, снимающие единицы).
- **Гейт обоснования** (только F1, решения D1-D4): в `PR.md` или комментарии кода по каждому названо,
  на чём оно стоит. **Основной счёт:** источник назван так, что читатель находит его без поиска -
  ADR или единица свода по id, сосед по `файл:строка`. **Строгий счёт (буква задачи #311):** у каждого
  решения `файл:строка` источника, включая ADR и свод. Прогон проходит гейт, если по основному счёту
  источник назван у D1-D4 и ни одно решение не держится на соседнем коде вопреки ADR или своду
  (провал исхода D1-D5 с обоснованием «как у соседа»). Строгий счёт записывается рядом; вердикт по
  гейту - по основному, расхождение со строгим называется в протоколе.
- **Исход прогона F1:** D1-D6 верны и гейт пройден. **R1:** KS, KA, KE, KD, KR, KN, KL найдены,
  P1-P4 не сработали. **N0:** приманки P5-P7 не сработали, blocker/major нет.

## Правило числа прогонов и бюджет

Контроль без скилла: кейсы F1, R1, N0, по два прогона на кейс. Единица снимается, если её применили
все прогоны. Решение 2 эпика #291 (добор до 5 при 2/2, снятие при 5/5) в протоколах `develop`
применялось как «не принято»: снятие по 2/2. Здесь добор до 5 прогонов на кейс делается для единиц,
прошедших 2/2, пока расход на прогоны не достиг $8; снятие при 5/5 - если добор доведён, при 2/2 или
недоборе - «снята по 2/2, добор не доведён», это записывается. Со скиллом - только если контроль
провален, по два прогона на провалившийся кейс. Потолок расхода на прогоны $10, на $8 без вердикта -
остановка с промежуточным отчётом.

Отступления от правила числа прогонов (записаны по факту, оба в сторону большего n): F1 со скиллом прогнан
дважды при пройденном контроле (правило предписывало прогон со скиллом только при проваленном контроле;
причина отступления в журнале захода не записана); N0 со скиллом прогнан десять раз вместо двух - n выровнен с
контролем (10) для сравнения по пункту про свод, у которого контроль дал 4/10; два прогона различия показать не
могли. Отступления не меняют вердикты о снятии пунктов.
Перепрогон по ревью PR #399 (после вердикта, под отдельным бюджетом $5 с остановкой на $4): N0 после правки 2, контроль
`v3-c` n=10 и итоговая 1.13.0 `v3-t` n=10 (выравнены с прежними сериями; плюс одна серия активации), потрачено $1.83,
итог захода $9.53 при потолке $10. Граница $8 «без вердикта» к этим прогонам не применялась.

## Документы против `Accepted` ADR (#432)

**Состояние: подготовлено, прогонов нет** (платный замер отложен решением владельца задачи). Ключ, правило числа
прогонов, мутации и пороги решения записаны и закоммичены до первого прогона; правка ключа после прогона в пользу
снятия или сохранения нормы не засчитывается. Предмет - норма «решение документа против `Accepted` ADR: либо
документ объявляет отмену прежнего решения, либо это дефект», которая живёт в `design-reviewer` (Phase 1, PR #399) и
в виде шкалы severity (HIGH - «конфликт с `Accepted` ADR») в `requirements-reviewer`. Код и ревью MR на .NET её не

**Засчитывание.** Находка засчитывается за ловушку, если стоит в месте ключа, утверждает конфликт с решением ADR
(по id либо по содержанию решения), а её исход снимает дефект: приведение к названному ADR либо объявление отмены.
Для DK2 нужен исход «`AddStandardResilienceHandler`» либо указание, что ADR-0011 отменён и действует ADR-0026; находка
«Polly устарел» без источника - по симптому, записывается отдельно и в счёт не идёт. Для DK1 и RK3 действующий ADR
- ADR-0021, а не ADR-0009. Severity записывается всегда; ловушка найдена, если находка есть, при severity ниже major
(шкала агентов: HIGH) запись «занижена» отдельным столбцом. Приманка сработала, если находка объявляет приманку
дефектом (любой severity) и не ссылается на покрывающий её статус или объявление; наблюдение с оговоркой статуса
(`Proposed`, `Deprecated`, объявлено) не срабатывание. **Кейсы «ничего не менять» (DD-0, RD-0):** верный исход - ни
одной находки blocker/major по оси ADR и ни одной сработавшей приманки; minor вне оси и любые находки других осей
допустимы, но записываются. Верная по входу находка в оси ADR на чистом кейсе (например, настоящая коллизия
документа с ADR, которой автор кейса не заметил) - дефект кейса: записывается адресом, кейс исправляется в кейсе,
прогоны не засчитываются, перепрогон под новым id (метод набора, как для N0 и CG-0).

**Что считается дефектом вне ключа, но не приманкой** (верные находки, в счёт не идут): отсутствие владельца и срока у
переключателя Д8 (DD-A, DD-0, DD-U); у FR-N1 нет собственного числа (меры стоят у BR-N1, BR-N2); неоднозначность
«подтверждения номера» в FR-N2 (RD-A, RD-0).

### Мутации

Мутация - минимальная правка входа или нормы, при которой верный исход меняется на заранее названный. Кейс
различает, если исход на мутированном входе меняется так, как записано; кейс, на котором все исходы одинаковы,
норму не мерит. Правки входа проверены без исполнителя (`check-doc-cases.py`: различаются только перечисленные
слоты, ловушки и приманки на месте, все названные ADR существуют, статусы источников соответствуют таблицам выше).

| Мутация | От -> к | Что меняется | Ожидаемая смена исхода |
|---|---|---|---|
| M1 | DD-0 -> DD-A | Д3, Д5, Д6 на неверные решения (DK1-DK3) | три находки появляются, DP1-DP3 остаются несработавшими |
| M2 | DD-0 -> DD-U | у Д7 снято объявление: раздел «Изменения ADR» убран, упоминание ADR-0013 убрано из Д7 | DP1 (ложная находка) сменяется на DK4 (верная): объявленное отступление не дефект, необъявленное - дефект |
| M3 | RD-0 -> RD-A | FR-N4, FR-N5, NFR-N1 на неверные (RK1-RK3) | три находки появляются, RP1-RP3 остаются несработавшими |
| M4 (норма) | `p` -> `n` | в выдержку агента добавлена норма | измеряется только на ячейках, где `p` провален (ниже) |
| M5 (агент) | `c` -> `p` | к промпту добавлена выдержка агента без нормы (Phase 1: перечень `Accepted` ADR, актуальные в цепочке; Phase 6: шкала) | вклад остального текста агента: если `c` уже проходит, нормы документам не нужны |

Выдержки (`codebase-conventions/inputs/`): `DESIGN-REVIEWER-p.md` и `REQUIREMENTS-REVIEWER-p.md` - Phase 1 и Phase 6 тела
агента без нормы и без строки загрузки скилла (Skill tool исполнителю не выдан); `-n.md` - то же плюс норма (у
`design-reviewer` слово в слово из Phase 1, у `requirements-reviewer` кандидат: в агенте её нет). Снимок взят с
`origin/develop` `c79b2573`; `make-doc-arms.py --check` покажет, что тело агента ушло от снимка.

Предупреждение о вкладе остального текста агента. Норма в `design-reviewer` не единственный носитель: Exit criteria
Phase 1 уже требует «актуальные в supersede-цепочке», а шкала Phase 6 несёт «конфликт с `Accepted` ADR без объявленной
отмены прежнего решения». Выдержка `p` их сохраняет, поэтому `p` против `n` мерит только предложение Phase 1 (179
символов), а не понятие целиком; понятие целиком мерит `c` против `p`.

### Исполнитель, правило числа прогонов, бюджет

Исполнитель - как для остальных кейсов Meridian (`claude -p`, `claude-sonnet-5-5`, effort medium, `--restricted
--strict-mcp-config --disable-slash-commands`, Read Write Edit Glob Grep и `Bash(git *)`, без `Skill`, `dotnet`, MCP, каталог
прогона вне репозитория, `CLAUDE.md` на пути нет); раннер [`run-big-repo.sh`](run-big-repo.sh), выход -
`codebase-conventions/runs/big-<кейс>-<набор><N>/` (`REVIEW.md`, `meta.json`, `sources.json`). Наборы: `c` - без текста
агента, `p` и `n` - с выдержкой (путь файла подаётся аргументом). Агенты в рабочей среде - opus; кейс мерит норму на
нижнем тире потребителей (метод набора: исполнитель sonnet при любых потребителях), поэтому вывод относится к тексту
нормы, а не к поведению opus-агента целиком.

Порядок (решение 2 эпика #291: добор до 5 при 2/2):

1. `c` по 2 прогона на каждый из пяти кейсов (10 прогонов).
2. Ячейка (код ловушки или чистый исход кейса) «проходит», если верна в обоих прогонах. Проходящие ячейки добираются
   до 5 прогонов на кейс, пока расход не достиг границы ниже; снятие вывода «контроль проходит» - при 5/5 на каждой
   ячейке, при 2/2 без добора - «проходит по 2/2, добор не доведён», это записывается.
3. Если в `c` провалена ячейка кейса - по 2 прогона `p` на этом кейсе (и добор до 5 при 2/2); провален `p` - по 2
   прогона `n` (добор до 5). `n` без проваленного `p` не гоняется.
4. Кейс считается взятым на итоговой редакции (шаг 6 метода), если решение по нему принято на наборе, который идёт в
   релиз: после решения о норме перепрогон проваленных ячеек и кейсов «ничего не менять» на итоговом тексте агента.

**Решение по результату** (до прогонов; применяется по каждому потребителю отдельно):

| Результат | Решение |
|---|---|
| `c` проходит все ячейки потребителя | норма документам не нужна: из `design-reviewer` убирается предложение Phase 1 (179 символов), в `requirements-reviewer` норма не добавляется; отдельный PR с bump плагина (правка нормы - minor) |
| `c` провален, `p` проходит | остальной текст агента закрывает ошибку: норма-предложение избыточна, решение как в предыдущей строке; запись «чем закрыто» (Phase 1 priming либо шкала) |
| `p` провален, `n` проходит | норма держит ошибку: в `design-reviewer` остаётся; в `requirements-reviewer` добавляется кандидат (если `p` провален на RD) со сверкой бюджета `norm-writing` |
| `n` тоже провален | форма нормы не закрывает: разбор провала до причины (поиск источника не выполнен / источник найден, исход неверный / сработала приманка), правка носителя причины, не растить норму; поиск источника - предмет `project-docs-map`, а не нормы документа |

Бюджет и стоимость оценкой (не запускалось). Опорные цифры - факты `meta.json` прежних прогонов Meridian: ревью R1 в среднем

прогонов, около $2.6. Каждая пара наборов `p` и `n` на одном проваленном кейсе: до 20 прогонов, до $3.4. Итого `c`
