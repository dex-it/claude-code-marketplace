# RFC-0008 Redis Streams для order-events: сначала параллельная доставка

Автор: команда orders. Статус: на согласовании.

## Проблема и цель
Очередь `order-events` на RabbitMQ обслуживается вручную: два человека, обновления кластера дважды в год занимают по дню. Цель - убрать отдельный кластер брокера, не ослабив гарантию «каждое событие обработано хотя бы раз» и не потеряв ни одного события при отказе узла Redis. Если ничего не менять: эксплуатационные расходы остаются, срок поддержки RabbitMQ 3.12 - до 2027-06, к этому сроку обновление придётся делать в любом случае.

## Альтернативы
| Вариант | Доставка | Эксплуатация | Решение |
|---|---|---|---|
| RabbitMQ как есть | at-least-once | кластер, 2 дня/год | запасной, откат |
| Redis Pub/Sub | at-most-once, без хранения: при разрыве подписчика события теряются | нет кластера | отклонён: audit-sink и billing-worker не терпят потерь |
| Redis Streams + consumer groups, `XACK` | at-least-once, хранение, pending-список | Redis Sentinel уже есть | выбран |

## Гарантия доставки
Источник истины - таблица `outbox` в PostgreSQL (`orders-api` пишет в неё в транзакции заказа, как сегодня). Redis Stream - только транспорт: диспетчер читает `outbox`, делает `XADD`, помечает строку отправленной после подтверждения; строка удаляется из `outbox` через 7 суток. Redis работает с `appendonly yes`, `appendfsync always`, `maxmemory-policy noeviction`, отдельным экземпляром под стримы (кэш остаётся на своём). `MAXLEN` не используется: поток обрезается только `XTRIM MINID` по событиям, подтверждённым всеми группами. Событие, потерянное при failover Sentinel, диспетчер находит сверкой `outbox` и стрима по `event_id` раз в минуту и публикует повторно; дубли гасит идемпотентность обработчиков по `event_id` (проверено в billing-worker, mailer, audit-sink: уникальный ключ на `event_id`).

## Было - стало
| Сценарий | Было (RabbitMQ) | Станет (Streams) | Риск и мера |
|---|---|---|---|
| Потребитель упал до ack | сообщение вернётся, до 5 повторов | остаётся в pending, `XAUTOCLAIM` через 60 с; после 5 доставок (`delivery count` из `XPENDING`) - в стрим `order-events:dead` | вероятность средняя, последствие - задержка до минуты; алерт на `dead` > 0 |
| Пик 300 событий/с, потребитель стоит час | очередь растёт | стрим растёт (около 1 КБ на событие - порядка 1 ГБ в час при пике), `noeviction` | вероятность низкая, последствие - остановка записи при переполнении памяти; алерт на 70% `maxmemory`, лимит 8 ГБ |
| Потеря Redis-ноды | quorum queue переживает | failover Sentinel, часть записей может не дойти до реплики | вероятность низкая, последствие - потери нет: сверка с `outbox` публикует пропущенное в течение минуты |
| Дубль события | возможен | возможен | обработчики идемпотентны по `event_id` |

## Потребители и совместимость
Потребители перечислены в `docs/services.md`: `billing-worker`, `mailer`, `audit-sink` - все три переводятся, контракт события не меняется (`event_id`, `type`, `payload`). Параллельная доставка: две недели публикуем в оба брокера, сверяем по `event_id`, не по счётчикам; переключение каждого потребителя - после семи суток без расхождений и после прогона отказов (останов мастера Redis под нагрузкой 300 событий/с, останов потребителя на час, переполнение памяти).

## Откат
До отключения RabbitMQ - переключение флагом `events.broker`, потребители читают оба источника. После - RabbitMQ поднимается из образа за 4 часа, события за этот срок берутся из `outbox`.

## Вне рамок RFC
Меняется только транспорт `order-events`; остальные очереди, схема событий, мониторинг Redis сверх перечисленных алертов и безопасность доступа к Redis (закрыта отдельной задачей OB-13, работа выполнена: доступ по ACL и сети кластера) не входят. Нагрузочное тестирование и прогон отказов - часть этого RFC, условие переключения (см. «Потребители и совместимость»).

## Оценка
Условия переключения проверяемы, отказ узла Redis не теряет события за счёт `outbox`.
