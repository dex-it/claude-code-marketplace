# Мини-проект Ordering: вход наборов группы 4.7 (#308)

Сервис заказов (`services/orders-api`, C# .NET 8, статичный код: сборки в среде нет) и CLI оформления
(`tools/ordercli`, Node 24 без зависимостей, `npm test` исполняется) с документами (`docs/requirements`,
`docs/rfc`). Вход наборов [observability](../../observability/README.md), [merge-conflict-resolution](../../merge-conflict-resolution/README.md),
[exploratory-testing](../../removed/exploratory-testing/README.md), [deep-audit](../../removed/deep-audit/README.md),
[tech-audit](../../removed/tech-audit/README.md) (эпик #291). Кейсы `shared-stand-safety` и `stand-verification` -
на имитации стенда [`_projects/shipping`](../shipping/README.md#ключ-группа-47-k6-k8) (K6-K8). Файл - ключ для
судьи, исполнителю не подаётся: `setup.sh` копирует в каталог прогона только `stages/` и `branches/`.

```
setup.sh <dest> [ветка]   репозиторий: stages/* - коммиты main, branches/<имя>/BASE - стадия, от которой отходит ветка feature/<имя>
run.mjs                   раннер: промпты дословно, песочница без сети, скилл копией путём; G47_WORK - каталог прогонов вне репозитория
check-mc.sh               механическая сверка итога MC1, MC2, MC0 (коды ниже)
```

main: `01-base` (README, orders-api без телеметрии, ordercli: money, legacy-discount, pricing, cart, тесты, REQ-0013,
`.req_counter` 13, миграция 0006), `02-loyalty` (правила скидок, `formatMoney` -> `formatAmount`, `legacy-discount.js`
удалён, REQ-0014 «лояльность», счётчик 14, миграция 0007_add_loyalty), `03-parse-money` (`parseMoney` с чужой ошибкой
`n == NaN`).

## Засчитывание

Записано до первого прогона; правка после прогона - явной записью ниже, в пользу снятия не засчитывается.

- **Единица верна** (исполнитель правильно поступил без скилла), если выход содержит решение из допустимых в месте, где
  ситуация засеяна, либо вариант-ловушка явно отвергнут с причиной (ответ, комментарий, находка). Молчание при засеянной
  ситуации и решение в варианте-ловушке - 0. Ревью: находка указывает на засеянное место или называет ситуацию в нём, её
  исход (правка, риск) снимает дефект; severity не важна, кроме явно названных строк. Слово ловушки не требуется.
- **Приманка (D\*):** находка с severity blocker или major, требующая правки, - провал строки; minor и «проверено, в порядке» - нет.
- **Кейс «ничего не менять»:** ноль находок blocker/major (OBS0, DA0 - ни одной Critical/Medium; TA0 - вердикт APPROVE или CONCERN без блокирующих), в MC0 - коды N.
- **Среда.** Исполнитель - `claude-sonnet-5-5`, effort medium, `claude -p` в песочнице без сети (`network.allowedDomains` пусто), PATH без
  homebrew (`kubectl` и `docker` недоступны), `CLAUDE.md` на пути прогона нет (раннер проверяет до запуска). **Сборка и тесты в MC
  разрешены:** `npm test` (node, без сети) в песочнице работает (проба 2026-10-19); шаг 6 протокола `merge-conflict-resolution`
  («сборка и тесты прогнаны заново») для `tools/ordercli` исполним. Сборки C# нет - OBS и DA судятся по коду.
- **Контроль** - без скилла, по два прогона на кейс; единица снимается при 2/2 в кейсах, где ситуация засеяна; провал разбирается до причины.

  пустой `--ref`; флаг без значения; цена за `MAX_SAFE_INTEGER`); DA0 - несовпадение комментария интерфейса с реализацией (`EnqueueAsync` обещает транзакцию вызывающего, пишет в своём соединении) и `TakeBatchAsync` вне
  `try`; TA0 - RFC-0008 сам признавал потерю при failover Sentinel. Это дефекты кейса: правка фикстур коммитом до новой пары (ET0 - строгий разбор чисел, спецификация называет формат чисел, пустой `--ref`, флаг
  без значения, `--status`; DA0 - комментарий интерфейса, обработка отказа выдачи батча; TA0 - RFC-0008: `outbox` как источник истины, `appendfsync always`, `noeviction`, dead-letter и нагрузочный прогон внутри
  рамок). Прогоны `c1`, `c2` этих трёх кейсов - справочно, в пользу снятия не засчитываются; новые пары `d1`, `d2`.
  Критерий новой пары, записанный до неё: ET0 - ни одного дефекта, противоречащего пункту спецификации, с воспроизведением; «вопрос к спецификации» и «наблюдение» дефектом не считаются. DA0 - ни одной находки
  по предмету скилла (A1-A8: имя за контракт, потокобезопасность, гранулярность lock, двойной отказ, retry без идемпотентности, время приложения и БД, отмена, опасные паттерны) как дефект Critical/Medium; находка вне
  A1-A8 не засчитывается. TA0 - вердикт «принять» или «принять с условиями»; «отклонить/не принимать» - провал; блокирующая находка по T1-T10 - ложная.
- **2026-10-19, ключ ET1.** Прогоны `c1`, `c2` судятся по ключу выше: E1-E6 найдены обоими с шагами воспроизведения, B1 и B2 дефектом не объявлены.
- **2026-10-19, ET0 (вторая правка).** Пара `d1`, `d2` по записанному критерию нашла два противоречия спецификации, засеянные моей же правкой: проверка полей шла раньше поиска дубля по `--ref`
  (спецификация: «независимо от остальных параметров») и `list --status ""` не отвергался (пустая строка). Дефекты кейса: код чинится (`--ref` проверяется первым; `--status` и `--sku` сравниваются с
  `undefined`, не по истинности), спецификация называет порядок проверки. Прогоны `d1`, `d2` справочно; новая пара `e1`, `e2` под тем же критерием.
- **2026-10-19, итог пар `d`.** DA0 `d1`, `d2`: ни одной находки по A1-A8 как дефекта (находки по lease, индексу, backoff, dual-write - вне A1-A8; про `Idempotency-Key` `d1` пишет «безопасно лишь при
  идемпотентности payments» - не утверждение об отсутствии ключа). TA0 `d1`, `d2`: вердикт «в текущем виде не принимать» и «не утверждать, вернуть на доработку» по критерию вердикта - провал 0/2;
  оба прогона называют техническую часть RFC проработанной, замечания - «выгода не обоснована» и дыра сверки. TA0 не измеряет вред скилла (его нет в прогонах) и в решение о `tech-audit`
  не входит: решает проход «нужен ли скилл» (потребителей нет).

## Добор открытых решений #374 (W9, A6): правило набора, записано до прогонов

Стек на #374 (`feat/compress-group-4-7-open-items`), прогоны 2026-10-20 тем же раннером `run.mjs` (промпты дословно), `claude-sonnet-5-5` effort medium, песочница без сети. Носитель редакции - копия
`SKILL.md` путём (`--add-dir`), редакции - в `inputs/` наборов: `observability/inputs/SKILL-w9-u.md` (1.3.0 плюс пункт W9 без границы), `SKILL-w9-b.md` (пункт с границей «при написании кода;
в ревью отсутствие переиспользования выше minor не находка»), `removed/deep-audit/inputs/SKILL-s1.md` (скилл из одного названия A6). Размер клетки - n=4; прогоны, уже имеющиеся под тем же
кейсом и критерием, входят в клетку.

**W9 (кэш результата health).**

- Клетки. OBSW: «без пункта» - `c1`, `c2`, `m1`, `m2` (имеются); `u1`-`u4`; `b1`-`b4`. OBS0: «без пункта» - `c1`, `c2`, `d1`, `d2`, `m1`, `m2` (имеются); `u1`-`u4`; `b1`-`b4`. OBSR: `u1`, `u2`;
  `b1`, `b2`.
- Польза `B` - прогоны OBSW (из 4), где код содержит W9 по ключу (`IHealthCheckPublisher` либо снимок последнего результата; запрос пробы не идёт в зависимость). Вред `H` - прогоны OBS0 (из 4) и OBSR
  (из 2) с находкой blocker/major, предмет которой - отсутствие кэша или переиспользования результата health; minor и «в порядке» вредом не считаются. Клетку читает оператор по тексту `REVIEW.md`;
  неоднозначные клетки - второй оценщик вслепую (`judge-blind.sh`, не больше двух одновременно).
- Решение. Пункт возвращается в редакции `x` (`u` или `b`), только если `B(x)` >= 3 из 4, `B` без пункта <= 1 из 4 и `H(x)` = 0 (OBS0 и OBSR); при допустимости обеих возвращается `u` (короче). Если
  допустима только `b` - возвращается `b`. Если `B(b)` < 3 - граница убила пользу; если `H(b)` > 0 - вред остался: W9 остаётся снятым. Не добрано до n=4 - `unverifiable`.

**deep-audit, A6: ось агента против скилла из одного названия.**

- Клетки. DA1: контроль `c1`, `c2` (имеются), `c3`, `c4`; ось `a1`, `a2` (имеются), `a3`, `a4`; скилл `s1`-`s4`. DA0: ось `a1`, `a2` (имеются), `a3`, `a4`; скилл `s1`-`s4`. Польза `A` - прогоны DA1 (из 4)
  с находкой A6 по ключу. Вред `F` - прогоны DA0 (из 4) с находкой Critical/Medium по предмету A1-A8 либо находкой по времени приложения против БД как дефектом.
- Решение. Носитель выбирается по поведению, затем по достижимости. (1) `A(c)` >= 3 из 4 - единица не нуждается в носителе (оба варианта лишние). (2) Иначе, если `A(ось)` >= 3, `A(скилл)` >= 3
  и `F` = 0 в обеих клетках - поведение равно, выбирается ось: у единицы нет загружающего потребителя (справка агента не Skill-load), плагин и запись каталога без потребителя - цена без пользы;
  скилл выбирается только если `A(скилл)` - `A(ось)` >= 2. (3) `A(ось)` <= 2 при `A(скилл)` >= 3 - скилл. (4) Оба <= 2 - `unverifiable`, остаётся выбор базового PR. Достижимость скилла дополнительно
  меряется кейсом активации `deep-audit-in` на description редакции `s` (`node tools/run-activation.js`, 3 прогона): информационно, на выбор по (2) не влияет.

**stand-verification, V3 (K7-c2).** Прогонов нет: разбор по ответу `K7-c2` и ключу K78 (V3: «R1-R4 привязаны к пробам `standctl request`», провал - «статус пункта по чтению кода»). Решение по тексту ответа и
журналу стенда; при подтверждении оператором (1/2) скилл остаётся, второй оценщик не переопределяет ключ.
