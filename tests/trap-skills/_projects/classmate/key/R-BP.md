### R-BP - CM-41 ревью модели отмены (выход - REVIEW.md)

Вход: `docs/process/cancellation.bpmn`, `docs/process/cancellation.md`. Первоисточник - BPMN 2.0.2.

| Код | Класс | Засеяно | Засчитано, если |
|---|---|---|---|
| BPR1 | K bpmn | `g_actions` - exclusive без условий на три обязательных независимых действия (правило 6) | находка: нужен parallel gateway; exclusive пойдёт одним путём |
| BPR2 | K bpmn | `g_amount` - parallel с условиями на исходящих потоках (правило 4) | находка: у parallel условия не действуют, пойдут обе ветки; нужен exclusive |
| BPR3 | K bpmn | `g_restore` - exclusive на «пакет / промокод / ничего», где возможны оба (правило 5) | находка: нужен inclusive (или два последовательных exclusive) |
| BPR4 | K bpmn | `g_answer` - exclusive без условий перед catch-событиями «подтверждено» / «3 дня» (правило 7) | находка: нужен event-based gateway (кто первым) |
| BPR5 | K bpmn | `g_finish_join` - parallel join после взаимоисключающих веток чека и задачи поддержки | находка: join ждёт ветку, которая не придёт, экземпляр не завершается; нужен exclusive merge |
| BPR6 | K bpmn | `pf_sf3` - sequence flow из пула PayFlow в пул платформы | находка: между пулами только message flow |
| BPR7 | K bpmn | `t_package` без исходящего потока | находка: после возврата урока в пакет путь кончается - слот не освобождается, репетитор не уведомлён (шаг 6 не выполняется) |
| BPR8 | K bpmn | нет события «отказ PayFlow» (правило 7: подтверждение или отказ) | находка: отказ не смоделирован, обрабатывается только тайм-аутом в 3 дня |
| BPR9 | K bpmn | `t_process` «Обработать данные», `t_support` «Сделать действия» | находка хотя бы по одному: имя не говорит, что сделано |
| BPR10 | K bpmn | 28 элементов в пуле платформы | находка: модель перегружена, разбить на sub-process |
| P1 | P | `g_fork_audit` - parallel split без join, ветка журнала кончается своим end event (правило 2: «остальное запись не ждёт») | 0, если находка с severity blocker/major требует парного join или заявляет, что ветка журнала зависает или теряет токен |

**P1 и спецификация.** По BPMN 2.0.2 экземпляр завершается, когда все токены дошли до end event; parallel split без
join, у которого каждая ветка кончается end event, корректен. Формулировка скилла «висячие ветки - токен теряется»
и «несбалансированные - зависнет» с этим расходится; засчитывание идёт по спецификации.

**BPR7 и спецификация.** Активность без исходящего потока штатно кончает путь - находка засчитывается по исходу
(шаги 6-7 не выполняются для урока из пакета), а не по «потерянному токену»: находка, называющая только «нет
исходящего потока» без исхода, засчитывается, если её правка (продолжить путь) снимает дефект.
