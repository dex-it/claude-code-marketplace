# Review Thread Delivery

Ловушки доставки ревью в UI хостинга. Находки полезны только если автор может работать с ними построчно: видеть приоритет, прыгать к коду, отмечать сделанное. Один длинный комментарий со списком «критичные / важные» этого не даёт. Правило: один тред равен одной находке, привязанной к конкретной строке нативным механизмом платформы.

## Гранулярность тредов

### Несколько находок в одном треде

Неправильно: связка разных проблем (security плюс нейминг плюс тест) в одном комментарии.
Правильно: один тред на одно нарушение. Одно нарушение в нескольких местах - один тред с перечнем мест; два нарушения на одной строке - два треда.
Почему: тред это единица, которую отмечают как resolved; смешав несколько проблем, автор не может закрыть одну, не закрыв все, и часть теряется.

### Один гигантский комментарий вместо тредов

Неправильно: всё ревью опубликовано одним общим комментарием с разделами по severity.
Правильно: каждая находка отдельным inline-тредом; общий комментарий допустим только как короткий overview.
Почему: общий комментарий не привязан к строкам и не резолвится по пунктам, поэтому автор не понимает, что из него уже сделано, а что нет.

## Привязка к коду

> Каким каналом слать тред (native MCP хостинга приоритетом, gh/glab фолбэк) - см. node-contract «Канал доступа к хостингу»; этот skill канал не выбирает. Упоминания gh api / glab api ниже - CLI-фолбэк, не выбор канала: на native-пути привязку, SHA и публикацию серии несёт операция канала (pending-батч), а лайфцикл (план -> публикация -> reply -> resolve) сохраняет смысл на обоих каналах.

### Привязка через текст «см. file:line»

Неправильно: тело комментария содержит «смотри File.cs строка 42» без нативной inline-привязки.
Правильно: создать тред нативным API с позицией на нужную строку (gh api на pulls/comments с path, line и side, для удалённой строки side=LEFT; glab api на discussions с объектом position, для удалённой строки old_path и old_line); тело без текстовой ссылки.
Почему: текстовая ссылка не кликабельна и устаревает при сдвиге строк; нативная привязка следует за кодом и открывает дифф в нужном месте.

### Тред привязан к неверному SHA

Неправильно: комментарий создаётся без актуальных SHA-якорей диффа, попадает на устаревшую версию.
Правильно: взять актуальные diff_refs (base/head/start sha для glab, head commit для gh) и привязать тред к ним.
Почему: привязка к старому SHA вешает комментарий на строку, которой уже нет, и автор видит замечание не там, где проблема.

### Вложенная позиция передана флагом с ключом в скобках

Неправильно: `glab api ... -f 'position[new_line]=42'` - позиция полем флага с ключом в скобках.
Правильно: position - вложенным объектом JSON-тела, поданного через `--input` (stdin - `--input -`); после создания в ответе проверить, что позиция у треда есть.
Почему: `glab api` шлёт поля JSON-телом, и ключ со скобками уходит литеральным именем, а не путём во вложенный объект. Хостинг отвечает `201` и заводит тред на MR целиком без привязки к строке: отказа нет, дефект виден только в интерфейсе.

### Выборка поля флагом `--jq` у glab

Неправильно: `glab api "projects/:id/merge_requests/:iid" --jq '.diff_refs'` по аналогии с `gh api`.
Правильно: у `glab api` флага `--jq` нет - поле выбирается внешним `jq` по пайпу; `jq` в среде нет - `diff_refs` разбирается из полного ответа.
Почему: команда падает на `Unknown flag`, SHA-якоря остаются пустыми, и тред, созданный следом, уходит без привязки к строке.

### Многострочное тело передано литералом

Неправильно: `-f body="..."` с markdown-телом треда в аргументе команды.
Правильно: тело из файла через `-F body=@<файл>` (`-f` шлёт литеральную строку, не содержимое файла).
Почему: переносы строк и спецсимволы ломаются экранированием аргумента, и тред публикуется искажённым без ошибки.

## Содержание

### Severity не в первой строке

Неправильно: уровень критичности упомянут где-то в середине текста или отсутствует.
Правильно: первая строка тела треда содержит severity, затем суть в 2-4 предложения и конкретный fix.
Почему: автор сканирует треды быстро; без severity в начале он не отличает блокер от мелочи и тратит время не на то.

### Overview дублирует содержимое тредов

Неправильно: общий комментарий пересказывает каждую находку, которая уже есть в треде.
Правильно: overview только считает (N блокеров, M важных) и отсылает к тредам; детали живут в тредах.
Почему: дублирование заставляет читать одно и то же дважды и расходится при правке тредов, создавая два разных текста об одной находке.

## Жизненный цикл

### Ответ по прежней находке заведён новым тредом

Неправильно: апдейт по прежней находке опубликован новым тредом или общим комментарием.
Правильно: reply в существующий тред - GitLab: note в `discussions/<id>/notes`; GitHub: комментарий в `pulls/<PR>/comments` с `in_reply_to` корневого комментария.
Почему: новый тред отрывает ответ от истории обсуждения, а прежний остаётся открытым без статуса.

### Resolve без протокола

Неправильно: тред закрывают по факту коммита, без явного действия resolve и без критерия «что считается закрытым».
Правильно: resolve выполняется отдельным вызовом API после публикации ответа; в ответе указано, чем именно закрыто (sha фикса или причина снятия).
Почему: коммит сам по себе не закрывает тред в UI; без явного resolve тред висит открытым, а без причины в ответе непонятно, исправлено или отклонено.

### Чужой тред тронут без основания

Неправильно: reply, resolve или unresolve в треде, созданном другим ревьюером.
Правильно: трогать только свои треды; чужие не резолвить и не переоткрывать без явной команды.
Почему: чужой resolve стирает контекст обсуждения и решение за другого человека, ломая прозрачность ревью для команды.

### Запись в MR без разрешения

Неправильно: треды публикуются сразу после черновика, без разрешения на запись.
Правильно: запись идёт только по разрешению. У главного потока - команда оператора после показанного плана тредов (file:line, severity, заголовок). У агента, запущенного другим узлом, - `publish: true` во входе; без него план уходит в выход, а не в MR. Серия публикуется так, как её даёт канал: pending-батчем одним вызовом, где он есть, иначе запросом на тред со стопом на первой ошибке.
Почему: публикация в чужой MR необратима в глазах автора и команды; план до записи ловит ошибочные и грубые формулировки до того, как их увидят, а у запущенного агента подтверждать некому - разрешение приходит полем.
