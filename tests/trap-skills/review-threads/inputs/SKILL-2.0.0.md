# Review Threads

<!-- skill-type: process -->

Находка полезна автору, когда она стоит у своей строки, читается по приоритету и закрывается отдельно от
других. Канал записи (native MCP хостинга, иначе `gh`/`glab`) выбирает node-contract «Канал доступа к
хостингу»; правила ниже действуют на любом канале.

## Форма

- Тред - одно нарушение у его строки, привязанное механизмом хостинга. Два нарушения в одной находке
  ревью, даже на соседних строках, - два треда; одно нарушение в нескольких местах - один тред, прочие
  места названы в теле.
- Первая строка тела - severity, дальше суть и исправление.
- Общий комментарий - только счёт находок по severity и отсылка к тредам; содержание находок в нём не
  повторяется. Ревью целиком одним комментарием не публикуется.

## Жизненный цикл

- Ответ по прежней находке - reply в её тред: GitLab - note в `discussions/<id>/notes`; GitHub -
  `in_reply_to` корневого комментария либо `pulls/<PR>/comments/<id>/replies`. Не новый тред, не общий
  комментарий и не тело review.
- Resolve - отдельным вызовом после ответа, в ответе названо, чем закрыто: коммит фикса или причина
  снятия. Не закрыто - ответ без resolve. На GitHub тред резолвит только GraphQL `resolveReviewThread`.
- Чужие треды без явной команды не трогаются: ни reply, ни resolve, ни unresolve.

## Запись

Запись в MR - только по разрешению: у главного потока - команда оператора после показанного плана тредов
(file:line, severity, заголовок); у агента, запущенного другим узлом, - `publish: true` во входе, без него
план уходит в выход. Серия публикуется, как её даёт канал: pending-батчем одним вызовом, где он есть,
иначе запросом на тред со стопом на первой ошибке.

## Ловушки записи

- `glab api` (сверено на 1.116.0) не вкладывает ключи `-f`/`-F`: `position[new_line]=42` уходит полем с
  литеральным именем, хостинг отвечает 201 и заводит тред без привязки к строке.
