Задача FUL-15 реализована в рабочем дереве, без коммита. Код не собирался и не запускался, так что API клиента `Elastic.Clients.Elasticsearch` 9.5.3 не проверено: возможны мелкие ошибки компиляции, например в агрегациях, `SortOptions` и PIT.

**Изменённые файлы**
- `src/Fulfil/Program.cs`: регистрация клиента Elasticsearch, поиска и индексатора, вызов `MapSearch`.
- `src/Fulfil/Options/FulfilOptions.cs`: добавлены `ProductsAlias`, `IndexBatchSize`, `IndexParallelism`.
- `src/Fulfil/Search/ProductDocument.cs`: документ, DTO запроса и ответа.
- `src/Fulfil/Search/CatalogIndexer.cs`: создание индекса, заливка, переключение алиаса.
- `src/Fulfil/Search/ProductSearch.cs`: поиск с фасетами и выгрузка.
- `src/Fulfil/Search/SearchEndpoints.cs`: `GET /search`, `GET /search/export`, `POST /search/reindex`.

**Принятые решения**
- **Пересборка.** Каждая пересборка создаёт новый индекс `fulfil-products-<время>`, и поиск идёт через алиас. После заливки алиас переключается атомарно, старый индекс удаляется. Так витрина не останавливается, а смена схемы — это обычная пересборка. Заливка идёт параллельными bulk-пачками по 5000 документов, 4 потока, с повторами. На время заливки отключены refresh и реплики. Это нужно, чтобы 3 млн товаров укладывались в час.
- **Русский и английский текст.** У названия и описания есть подполя `.ru` (анализатор `russian`) и `.en` (`english`). Поиск идёт по ним, вес названия ×3. Для сортировки по названию есть отдельное подполе `name.sort` с нижним регистром.
- **Выдача и категории.** Фильтр по категории вынесен в `post_filter`, поэтому список категорий считается по запросу и цене, а не сужается до выбранной категории. Страницы глубже 10 000 записей дают 400, для них есть `/search/export`.
- **Выгрузка.** Использует point-in-time и `search_after`, сортировка по `sku`, отдаётся потоком, лимит 200 000.

**Что осталось**
- У `ICatalogSource` в репозитории нет реализации, и в DI она не зарегистрирована. Пока её нет, `POST /search/reindex` упадёт при создании `CatalogIndexer`.
- Ночной запуск рассчитан на CronJob в Kubernetes, который один раз вызывает `/search/reindex`. Защита от параллельных пересборок есть только внутри одной реплики.
