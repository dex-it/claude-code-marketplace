# Контракт интерфейса - оракул спеки

**Оракул судит готовый контракт и даёт вердикт для метки `quality-checks`.** Норма состава - `interface-definition-openapi`; здесь дефекты, которые норма формально пропускает: спека валидна по схеме, а договором не является.

Своему артефакту вердикта не ставят: оракул прогоняет судья, не автор (`node-contract`, п.7 ядра). Оракул был объявлен заделом в реестре типов и до этой редакции не существовал - тип `api-spec` закрывался записью `unverifiable`.

## Схемы и типы

### Тип назван без ограничений
Плохо: поле объявлено строкой или числом, границы не заданы
Правильно: длина и допустимый алфавит у строки, диапазон у числа, единица измерения там, где величина размерная. Проверка: по описанию поля можно написать генератор корректных значений
Почему: неограниченный тип означает, что валидацию каждая сторона придумывает сама; расхождение обнаруживается на данных, которые обе стороны считали допустимыми

### Обязательность поля не объявлена
Плохо: поле присутствует в примере, но не помечено обязательным и не помечено необязательным
Правильно: обязательность объявлена явно для каждого поля запроса и ответа. Проверка: по спеке видно, что произойдёт, если поле не прислать
Почему: молчание читается по-разному по разные стороны стыка: отправитель считает поле необязательным, получатель падает без него

### Формат величины подразумевается
Плохо: `timestamp`, `amount`, `duration` без указания представления
Правильно: назван формат и часовой пояс у времени, валюта и минорные единицы у денег, единица у длительности. Проверка: два независимых разработчика реализуют одинаково
Почему: деньги в копейках против рублей и время в UTC против локального - классические расхождения, которые проходят все тесты и ломают расчёты

## Ошибки и поведение

### Описаны только успешные исходы
Плохо: у операции указан ответ 200 и общий 500
Правильно: закрытый перечень исходов: что при неверном входе, при отсутствии объекта, при конфликте, при отказе зависимости, при превышении лимита - и что вызывающему делать с каждым
Почему: вызывающий обязан обработать отказ; не описанный в контракте, он обрабатывается по факту наблюдения в проде, разными способами у разных потребителей

### Ошибка не отличима по коду
Плохо: все прикладные отказы возвращают один код с текстом в теле
Правильно: машиночитаемый признак причины, по которому вызывающий выбирает поведение. Проверка: можно ли различить «повторить позже» и «повторять бессмысленно», не разбирая текст
Почему: разбор человекочитаемого текста ломается при первой правке формулировки, и повтор запроса выбирается наугад - обычно в сторону бесконечного ретрая

### Идемпотентность и повтор не описаны
Плохо: про повторный вызов не сказано ничего
Правильно: названо, какие операции безопасно повторять и по какому ключу; для неидемпотентных - что произойдёт при повторе
Почему: сеть теряет ответы, а не запросы: повтор случится независимо от того, описан он или нет. Неописанный даёт двойные списания

## Совместимость

### Ломающее изменение выдано за совместимое
Плохо: новое поле сделано обязательным, тип сужен, код ошибки изменён - версия не поднята
Правильно: класс изменения назван до правки; граница проходит по тому, ломается ли работающий потребитель, а не по объёму диффа
Почему: потребитель узнаёт о ломающем изменении в момент отказа, а не в момент чтения changelog; откат чужого релиза стоит дороже новой версии

### Расширение перечня значений сочтено безопасным по умолчанию
Плохо: в перечень добавлено значение, правило обработки неизвестного нигде не объявлено
Правильно: правило «неизвестное значение игнорируется» либо иное объявлено в контракте заранее; не объявлено - расширение ломающее
Почему: потребитель, разбирающий перечень исчерпывающе, падает на новом значении. Это самый частый ломающий сдвиг, который обе стороны считают безобидным

### Перечень потребителей не собран
Плохо: «мы никого не сломаем» без списка тех, кто вызывает операцию
Правильно: перечень известных потребителей приложен к ломающему изменению вместе с планом миграции и сроком жизни предыдущей версии
Почему: ненайденный потребитель не равен отсутствующему; проверка занимает час, а инцидент от несогласованной правки - несколько дней

### Устаревание объявлено без срока и замены
Плохо: операция помечена устаревшей, дальше ничего
Правильно: с какой версии, чем заменена, до какого срока поддерживается. Проверка: потребитель может составить план перехода, не задавая вопросов
Почему: пометка без плана не двигает никого: потребители продолжают использовать операцию, и удалить её нельзя годами

## Договор в целом

### Спека написана по готовому коду
Плохо: контракт сгенерирован из реализации и фиксирует то, что получилось
Правильно: контракт порождается вместе с решением и проверяется против реализации, а не выводится из неё. Проверка: есть ли в спеке хоть одно требование, которому код пока не соответствует
Почему: спека, выведенная из кода, не может его ограничивать: любое поведение реализации автоматически становится нормой, включая случайное

### Примеры только успешные
Плохо: у операции один пример - удачный запрос и ответ
Правильно: пример на каждый класс исхода, включая ошибочный. Проверка: по примерам можно собрать контрактный тест, покрывающий отказы
Почему: примеры используются как тесты и как документация; набор из одних успехов документирует половину договора и тестирует ту же половину

### Операция не привязана к требованию
Плохо: в контракте есть операция, которой не соответствует ни одно требование
Правильно: `traced from` на `FR-NNN`; нет родителя - операция либо лишняя, либо вскрыла незаписанное требование. Проверка: по каждой операции назван вызывающий сценарий
Почему: публичная точка без основания остаётся навсегда: удалить её страшно, потому что неизвестно, кто и зачем ею пользуется
