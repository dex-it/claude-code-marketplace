# Ревью MR !4127 (сервисы заказов и каталога для админки)

## Критичные (critical)

1. **Migrations/20260920_OrderCategories.cs (`Up`) + Model.cs (`Order.Category`) + Services/OrderAdmin.cs (`UpdateOrder`)** — миграция дропает колонку `Orders.Category` (`mb.DropColumn("Category", "Orders")`), но модель сущности (`Order.Category`, `string`) не тронута и продолжает маппиться на эту колонку по конвенции, а `OrderAdmin.UpdateOrder` явно пишет в неё (`order.Category = edit.Category`). После применения миграции любой запрос/сохранение `Order` (в том числе `SELECT` со всеми колонками в `GetCard`, `ExportForCustomer`, `OverdueReport` и `SaveChanges` в `UpdateOrder`) упадёт в рантайме с ошибкой БД «column "Category" does not exist». MR не согласован: либо модель должна получить `Categories`/`OrderCategories` навигации и `Category`-строка убрана, либо миграция не должна дропать колонку в этом MR.

2. **Migrations/20260920_OrderCategories.cs (`Up`)** — схемная миграция создаёт `Categories`/`OrderCategories`, но не переносит существующие значения `Orders.Category` в них (нет `INSERT INTO "Categories" ... ; INSERT INTO "OrderCategories" ...` до `DropColumn`). Это ровно кейс «схемная миграция без data migration для исторических данных» из EF-скилла: после деплоя исторические категории заказов молча теряются, новый код их не увидит.

3. **Services/CatalogService.cs, `Reserve`** — `FOR UPDATE` выполняется без обёртки в явную транзакцию (`BeginTransactionAsync`). Блокировка строки снимается сразу после завершения `SELECT`, а `UPDATE` (через `SaveChangesAsync`) идёт отдельным автокоммитом. Между этими двумя запросами два параллельных вызова `Reserve` на один и тот же `productId` могут оба пройти проверку `product.Stock < qty` по «старому» значению и оба списать остаток — overselling остатка на складе. Нужно `await using var tx = await _db.Database.BeginTransactionAsync();` вокруг `SELECT ... FOR UPDATE` → проверка → `SaveChanges` → `Commit`.

4. **Services/CatalogService.cs, `Search`** — несоответствие алиасов в динамически собираемом `FromSqlRaw`: шаблон объявляет алиас `p` (`FROM "Products" p`), а условия строятся с полным именем таблицы (`"Products"."Category" = ...`, `"Products"."Price" = ...`). PostgreSQL не резолвит `"Products"` как отдельный источник, когда таблице задан алиас `p`, и бросит `missing FROM-clause entry for table "Products"` в рантайме при ЛЮБОМ вызове с `category != null` или `minPrice != null` — то есть метод фактически неработоспособен во всех случаях кроме пустого фильтра. Нужно использовать алиас `p` и в условиях: `p."Category" = @p0` и т.д.

5. **Services/OrderAdmin.cs, `RecalcTotal`** — пересчёт суммы заказа не учитывает количество: `order.Total = order.Items.Sum(i => prices[i.ProductId])`. По контексту модели `Product.Price` — цена за единицу, `OrderItem.Qty` — количество, значит должно быть `prices[i.ProductId] * i.Qty`. Сейчас сумма заказа занижена для любой позиции с `Qty > 1` — финансовая ошибка в проде.

6. **Services/OrderQueries.cs, `GetProductBySku`** — `_db.Products.AsNoTracking().SingleAsync(p => p.Sku == sku)`, но по описанию модели SKU уникален только в рамках склада, а не глобально («один SKU лежит на нескольких складах»). Метод не принимает склад и обязательно бросит `InvalidOperationException` («Sequence contains more than one element») для любого SKU, присутствующего на 2+ складах, — а это, по описанию домена, штатная ситуация, а не редкий край. Нужно либо добавить параметр `warehouse` и фильтровать по нему, либо возвращать коллекцию/самую релевантную запись явно.

7. **Workers/OverdueNotifier.cs, конструктор** — `ShopDbContext` инжектируется напрямую в `BackgroundService`, который регистрируется как `AddHostedService` (эффективно singleton), тогда как `AddDbContext` даёт `Scoped` время жизни. Это классический captive dependency: при включённой валидации скоупов (dev-окружение по умолчанию в ASP.NET Core) приложение упадёт при старте; в проде — один и тот же `DbContext`/Change Tracker живёт всё время работы сервиса, растёт бесконечно и не thread-safe при параллельном использовании из других мест. Нужно инжектировать `IServiceScopeFactory` и создавать `CreateScope()`/резолвить `ShopDbContext` на каждой итерации цикла.

## Высокие (high)

8. **Services/OrderAdmin.cs, `UpdateOrder`** — нет concurrency-токена (`RowVersion`/`UseXminAsConcurrencyToken`) на `Order`, при этом в MR явно описан сценарий «в админке несколько операторов правят заказы одновременно». Сейчас второй оператор молча перезатирает правки первого без исключения о конфликте («last write wins»). То же применимо к `RecalcTotal`, которая тоже читает-и-сохраняет `Order` без токена.

9. **Services/OrderAdmin.cs, `OverdueReport`** — фильтр «просрочен» применяется в памяти после полной материализации: `_repo.GetAllAsync()` тянет ВСЮ таблицу `Orders` (без проекции, без `AsNoTracking`), и только потом `all.Where(o => o.IsOverdue(now))`. При «у крупных клиентов тысячи заказов» (из описания MR) и учитывая, что это отчёт по всей базе, а не по одному клиенту, — это полное сканирование таблицы в приложение вместо `WHERE` на сервере. Нужно переносить условие `IsOverdue` в SQL-транслируемый вид (аналогично тому, как уже сделано в `OverdueNotifier`) и убрать зависимость от `List`-репозитория.

10. **Services/OrderQueries.cs, `ExportForCustomer`** — два коллекционных `Include` (`Items`, `Payments`) на результате из МНОЖЕСТВА заказов (выгрузка заказов клиента, а у крупных клиентов — тысячи заказов) без `AsSplitQuery()`. Это ровно cartesian explosion из EF-скилла: JOIN по двум коллекциям одновременно раздувает результат в декартово произведение строк. Нужно добавить `.AsSplitQuery()`.

11. **Services/CatalogService.cs, `Reprice`** — товары загружаются трекаемыми (`ToListAsync()` без `AsNoTracking`), после чего к уже отслеживаемым сущностям применяется `_db.UpdateRange(products)` перед `SaveChangesAsync`. `UpdateRange` на tracked-сущностях помечает ВСЕ свойства как `Modified`, включая `Stock`, `Sku`, `Warehouse`. Если между чтением и записью в этой транзакции конкурентно отработает `Reserve` (уменьшит `Stock`), `Reprice` перезапишет `Stock` устаревшим прочитанным значением — потеря конкурентного обновления остатка. Кроме того, для точечного умножения цены на коэффициент стоит использовать `ExecuteUpdateAsync` вместо цикла `SaveChanges` (см. чек-лист Bulk Operations).

12. **Services/OrderQueries.cs, `LastShippedAt`** — `MaxAsync(o => o.ShippedAt)` возвращает `null`, если у клиента нет отгруженных заказов (либо заказов вообще нет) — для nullable-колонки это штатный результат, а не «пока не бывает». Дальше `last!.Value` — `null-forgiving` без предшествующего WHERE-фильтра на непустое значение — уронит `NullReferenceException` в рантайме для любого клиента без отгрузок. Нужно фильтровать `o.ShippedAt != null` до агрегации и/или возвращать `DateTime?` из метода.

## Средние/низкие (medium/low)

13. **Services/OrderQueries.cs, `GetCard`** (medium/low) — `AsSplitQuery()` применён к точечной выборке одного заказа по `Id` (`FirstOrDefaultAsync`). Для single-entity запроса, наоборот, split query — анти-паттерн из чек-листа: лишний round-trip к БД там, где один JOIN эффективнее. Похоже, `AsSplitQuery` и его отсутствие в `ExportForCustomer` (см. п.10) перепутаны местами.

14. **Workers/OverdueNotifier.cs, `ExecuteAsync`** (low) — каждую итерацию (раз в минуту) в `AuditLogs` добавляется новая запись для ВСЕХ ещё-не-отгруженных просроченных заказов без отметки «уже залогировано»/окна по времени последней проверки. Пока заказ остаётся просроченным, на каждый цикл будет создаваться новая строка audit-лога на этот же заказ — таблица `AuditLogs` растёт неограниченно с частотой раз в минуту на каждый висящий просроченный заказ. Возможно, это осознанное поведение по описанию MR, но стоит подтвердить с автором — иначе нужен признак «уже уведомлён» или сравнение с последней записью.

15. **Program.cs** (low) — глобально включён `UseLazyLoadingProxies()`, при этом в `Order` (Model.cs) только навигация `Customer` объявлена `virtual`, `Items`/`Payments` — нет. В сочетании с активным использованием `AsNoTracking()` в новых сервисах это создаёт риск скрытого ленивого догруза (N+1) при любом будущем обращении к `order.Customer` без `Include`, а для `AsNoTracking`-сущностей ленивая загрузка вообще ненадёжна вне времени жизни контекста. Стоит проверить, действительно ли лениво-загружаемые прокси нужны в этом сервисе, учитывая, что все новые query-методы и так явно используют `Include`/проекции.
