# Review: SalesReport.cs, CustomerExport.cs, CatalogSearch.cs, StockImport.cs

Контекст: EF Core 8 + Npgsql 8, .NET 8. В `ShopDbContext` (существующий код) нет `OnModelCreating`,
конвертеров и конфигурации колонок — значит все `DateTime`-свойства (в т.ч. `Order.CreatedAt`)
маппятся по конвенции Npgsql 8 в `timestamp with time zone` и требуют `DateTime.Kind == Utc`.
`HasQueryFilter`/soft-delete и миграции в модели не найдены — соответствующие пункты чек-листа
к этому MR не относятся.

---

## SalesReport.cs

**SalesReport.cs:18** — `Build(DateTime from, DateTime to, ...)` без нормализации `Kind` передаётся
дальше в фильтр по `Order.CreatedAt` (колонка `timestamptz` по конвенции). Если вызывающий код
передаст `DateTime` с `Kind=Unspecified` (типичный результат `DateTime.Parse`/биндинга из
HTTP-параметров) или `Kind=Local`, Npgsql на записи параметра либо бросит исключение, либо
трактует значение не так, как ожидалось, и отчёт по факту фильтруется не по тем границам периода.
Severity: **major**.

**SalesReport.cs:21-23** — `_db.OrderItems.Where(...).ToListAsync(ct)` без `AsNoTracking()`,
хотя метод строго read-only (формирование отчёта). Все выбранные `OrderItem` попадают под
change tracking без необходимости — лишняя память и CPU на снапшоты, деградирует с ростом
периода/количества заказов. Severity: **major**.

**SalesReport.cs:20** — `_products.GetAllAsync(ct)` (существующий `ProductRepository.GetAllAsync`)
тянет весь каталог товаров с трекингом для чисто читающего отчёта; вызывающий код (эта строка)
не использует untracked-путь. Тот же класс проблемы, что и выше, но эффект слабее (каталог обычно
меньше `OrderItems` за период). Severity: **minor**.

## CustomerExport.cs

**CustomerExport.cs:13-23** (материализация — строки 13-17, `Select+Distinct` — строки 19-23) —
запрос идёт с `.AsNoTracking().Include(o => o.Customer)`. No-tracking отключает identity resolution,
поэтому для клиента с двумя и более заказами в периоде EF материализует **разные экземпляры**
`Customer` на каждый `Order`. `Customer` не переопределяет `Equals`/`GetHashCode`, значит
`.Distinct()` сравнивает по ссылке и не схлопывает такие дубликаты. Метод существует ровно для
того, чтобы выгрузить уникальных клиентов в CRM (см. комментарий к методу) — на практике для
любого повторного клиента в выборке будет дубль, что приведёт к дублирующимся записям/рассылкам
в CRM. Это системная, стопроцентно воспроизводимая ошибка при обычных данных (клиент с >1 заказом
в периоде), а не крайний случай. Severity: **blocker**.

**CustomerExport.cs:11,16** — тот же риск с `Kind` у `from`/`to` относительно `Order.CreatedAt`
(`timestamptz`), что и в SalesReport.cs:18. Severity: **major**.

**CustomerExport.cs:27** — `await _db.Orders.CountAsync(o => o.CustomerId == customerId, ct) > 0`
вместо `AnyAsync(...)`. Прямое нарушение пункта чек-листа команды ("Проверка наличия через
`CountAsync() > 0`"): Postgres считает все совпадающие строки вместо остановки на первой через
`EXISTS`, стоимость растёт с числом заказов клиента. Severity: **major**.

## CatalogSearch.cs

**CatalogSearch.cs:16-36** — ни в одной из четырёх веток нет `Take`/`Skip`/лимита страницы,
включая ветку без фильтров (`category == null && maxPrice == null`), которая вернёт весь активный
каталог целиком. С ростом каталога это растущий по размеру и времени ответ без верхней границы —
для поиска по каталогу (публичный сценарий, вероятны широкие/пустые фильтры) это риск деградации
и больших ответов на проде. Severity: **major**.

**CatalogSearch.cs:10-36** — четыре почти идентичных блока запроса (общий фильтр `p.IsActive`
и общий `Select(Card)` продублированы в каждой ветке). Функциональной ошибки нет — во всех
ветках условие `IsActive` присутствует одинаково — но при будущем изменении бизнес-правила
(например, добавление ещё одного фильтра или recheck видимости) легко поправить не все 4 копии.
Severity: **minor**.

## StockImport.cs

**StockImport.cs:15,27** — весь `Products` целиком грузится в память (строка 15), а затем на
**каждую** строку CSV выполняется линейный `FirstOrDefault` по этому списку (строка 27) —
`O(число_товаров × число_строк_файла)`. На реальном файле поставщика с большим каталогом это
деградирует до недопустимого времени импорта/риска таймаута. Severity: **major**.

**StockImport.cs:21,34** — `int.TryParse(parts[1], out var qty)` пропускает отрицательные числа
как валидные (`"-5"` парсится успешно), и `product.Stock = qty` (строка 34) присваивает это
значение без проверки на `>= 0`. Битая/повреждённая строка от поставщика с отрицательным
количеством молча запишет отрицательный остаток вместо попадания в `invalid`, что дальше ломает
предположения потребителей `Stock` (например, `ShippingPlanner.ChooseWarehouse` фильтрует
`s.Qty >= qty` — отрицательные остатки некорректно участвуют в такой логике "есть на складе").
Severity: **major**.

**StockImport.cs:18-36** — дубли `productId` во входном файле не детектируются (пункт чек-листа
"Дубли во входном списке id"): каждая дублирующая строка независимо находит тот же `Product` через
`FirstOrDefault` и увеличивает `updated` заново, хотя по факту меняется один и тот же товар.
Итоговый `ImportResult.Updated` может быть больше числа реально изменённых товаров — метрика,
на которую полагается вызывающий код/оператор для контроля импорта, вводит в заблуждение и
маскирует некорректный/задублированный файл поставщика (побеждает последняя строка молча,
без объяснения бизнес-правила "kто выигрывает"). Severity: **minor**.
