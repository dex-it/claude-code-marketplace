# Review MR: SalesReport.cs, CustomerExport.cs, CatalogSearch.cs, StockImport.cs

Контекст: EF Core 8 + Npgsql 8, .NET 8. Проверено по чек-листу `ef/SKILL.md` (нетранслируемые фильтры, трекинг read-only выборок, DateTime/Npgsql timestamptz, soft-delete+FK, миграции на prod) плюс общие замечания по корректности/производительности. Модель (`Model.cs`) не содержит явной конфигурации типов колонок (`OnModelCreating` в `ShopDbContext.cs` отсутствует), поэтому для `DateTime`-свойств без атрибутов действует поведение Npgsql 6+ по умолчанию: колонка `timestamptz`, запись требует `Kind=Utc`.

---

## Блокеры (blocker)

### SalesReport.cs:18,22 — DateTime без гарантии Kind=Utc против timestamptz-колонки
Метод `Build(DateTime from, DateTime to, ...)` принимает произвольные `DateTime` и сравнивает их с `Order.CreatedAt` (свойство без явного маппинга типа → колонка `timestamptz`, Npgsql 6+ требует `Kind=Utc` при записи параметра). Ни валидации, ни `DateTime.SpecifyKind(...)`/`ToUniversalTime()` нет. Любой вызов с `Kind=Unspecified` (например, `new DateTime(2024,1,1)`, `DateTime.Parse` без офсета) или `Kind=Local` (`DateTime.Now`) приведёт к рантайм-исключению Npgsql при выполнении запроса ("Cannot write DateTime with Kind=... to PostgreSQL type 'timestamp with time zone'"). Это самый естественный способ вызвать метод, так что упадёт с высокой вероятностью в проде.
**Severity: blocker**

### CustomerExport.cs:11,16 — та же проблема Kind у DateTime-параметров
`CustomersWithOrders(DateTime from, DateTime to, ...)` сравнивает параметры с `Order.CreatedAt` (`timestamptz`) без приведения к `Kind=Utc`. При вызове с `Kind=Unspecified`/`Local` запрос упадёт с исключением Npgsql в момент `ToListAsync`.
**Severity: blocker**

### CustomerExport.cs:14,19-21 — `Distinct()` не дедуплицирует клиентов из-за `AsNoTracking` без identity resolution
Запрос выполняется с `AsNoTracking()` (без `AsNoTrackingWithIdentityResolution()`), поэтому для одного и того же `Customer`, встретившегося в разных заказах периода, EF Core материализует **разные объекты** (identity resolution в no-tracking запросах по умолчанию не выполняется). `Customer` не переопределяет `Equals`/`GetHashCode`, значит `.Distinct()` на строке 21 сравнивает по ссылке и фактически не убирает дубликаты. Итог: клиент, оформивший несколько заказов за период, попадёт в выгрузку для CRM несколько раз — притом что назначение метода и комментарий ("Клиенты, делавшие заказы в периоде") прямо предполагают уникальный список. Риск дублей писем/начислений в CRM по числу заказов клиента.
**Severity: blocker**

## Существенные (major)

### SalesReport.cs:21-23 — трекается read-only выборка `OrderItems`
Отчёт только читает данные (`Build` формирует `List<ProductSalesRow>`), но запрос к `_db.OrderItems` не помечен `AsNoTracking()`. Для отчёта за широкий период это означает ненужный change-tracking (снапшоты, память, лишняя нагрузка на GC) на потенциально большом наборе строк — при регулярном построении отчётов на боевых объёмах заметно увеличивает время ответа/потребление памяти.
**Severity: major**

### SalesReport.cs:20 — тот же отчёт тянет весь каталог товаров трекаемым способом
`_products.GetAllAsync(ct)` (см. `ProductRepository.cs`) возвращает **все** товары без `AsNoTracking` и без фильтрации, хотя ниже они фильтруются по `IsActive` уже в памяти. Для read-only отчёта это двойная цена: лишний трекинг + перекачка неактивных товаров, которые тут же выбрасываются. Правильнее было бы либо добавить в репозиторий no-tracking метод, либо запрашивать сразу отфильтрованный, некэшируемый список.
**Severity: major**

### StockImport.cs:27 — поиск товара по CSV-строке через `FirstOrDefault` по `List<Product>`
`products.FirstOrDefault(p => p.Id == id)` выполняется в цикле по каждой строке CSV поверх списка **всех** товаров (см. также следующий пункт) — это O(N×M) в худшем случае. На реальных объёмах (десятки/сотни тысяч товаров и строк импорта) это может превратить импорт остатков в задачу, которая не укладывается в разумное время/таймаут джоба. Нужен `Dictionary<Guid, Product>` для O(1)-подстановки.
**Severity: major**

### StockImport.cs:21,34 — отрицательное количество принимается как валидное
`int.TryParse(parts[1], out var qty)` успешно парсит отрицательные числа ("-5" и т.п.), после чего строка 34 безусловно пишет `product.Stock = qty`. Строка попадает в `updated`, а не в `invalid`/`unknown`. Нет проверки `qty >= 0`. Битые/некорректные данные от поставщика молча портят остаток на складе отрицательным значением — данные полагаются валидными, хотя семантически это невозможное состояние.
**Severity: major**

## Незначительные (minor)

### StockImport.cs:15 — весь `Products` грузится в память безусловно
`_db.Products.ToListAsync(ct)` тянет всю таблицу вне зависимости от того, сколько записей реально есть в CSV. При большом каталоге и небольшом файле остатков это лишняя память/время на старте импорта; лучше сначала собрать `Id` из файла и выбрать только нужные строки (`Where(p => ids.Contains(p.Id))`).
**Severity: minor**

### StockImport.cs:18 — синхронное чтение файла в async-методе и отсутствие проверки `ct` в цикле
`File.ReadLines(csvPath)` — блокирующий I/O внутри `async Task<ImportResult>`, занимает поток на всё время построчного чтения большого файла. Плюс `ct` нигде не проверяется внутри `foreach` (только неявно попадёт в `SaveChangesAsync` в конце) — отмена импорта долгого файла не сработает, пока не закончится весь цикл.
**Severity: minor**

### CustomerExport.cs:26-27 — `CountAsync(...) > 0` вместо `AnyAsync`
Для проверки существования достаточно `AnyAsync`, которая транслируется в `EXISTS` и не требует подсчёта всех совпадений. `CountAsync` семантически избыточен для булевого вопроса "есть ли заказы" — лишняя (пусть и небольшая) нагрузка на БД при частых вызовах.
**Severity: minor**

### CatalogSearch.cs:16-36 — дублирование логики запроса в четырёх ветках `if`
Метод `Search` копирует одну и ту же цепочку `_db.Products.AsNoTracking().Where(...).Select(Card).ToListAsync(ct)` четыре раза, различаясь только условием `Where`. Функционально не баг (везде корректно используется `AsNoTracking`, фильтры транслируемые), но при следующем изменении фильтрации легко поправить одну ветку и забыть остальные три. Стоит собрать единый `IQueryable` с последовательным добавлением условий по `category`/`maxPrice`.
**Severity: minor**
