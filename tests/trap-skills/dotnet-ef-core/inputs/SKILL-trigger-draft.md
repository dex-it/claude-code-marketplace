# Entity Framework Core - ловушки

Каждая ловушка называет ситуацию, в которой нужна проверка, и что сверить. Решение выбирается по
документации EF Core / Npgsql версии из манифеста проекта, а не по памяти.

## Запросы

### Условие фильтра, которое EF может не транслировать
Плохо: часть условия фильтра записана методом модели или другим C#-кодом, и её проверку решено отложить до после материализации
Правильно: проверь по документации версии, транслируется ли каждое условие в SQL; нетранслируемое переведи в транслируемую форму до материализации
Почему: в процесс уходят все строки, прошедшие серверную часть фильтра; на большой таблице - тайм-аут или OOM

### Выборка только для чтения
Плохо: данные для отчёта или показа материализуются обычным запросом контекста как сущности
Правильно: проверь, попадают ли эти сущности в Change Tracker, и нужно ли это для задачи
Почему: Change Tracker держит снимок каждой сущности и сравнивает их на `DetectChanges`

## Маппинг

### DateTime и тип колонки Npgsql
Плохо: `DateTime` пишется в колонку или сравнивается с ней, а тип колонки (`timestamp` / `timestamptz`) выведен по памяти - в том числе у свойства без явного `HasColumnType`
Правильно: установи тип колонки - явный в конфигурации либо по конвенции провайдера, сверив её с документацией Npgsql версии проекта, - и какой `Kind` провайдер принимает для этого типа; сверь с ним запись, чтение и параметры запроса
Почему: Npgsql 6+ бросает на несовпадении `Kind` и типа колонки - и при сохранении сущности, и в параметре запроса

## Удаление

### Soft-delete при связях с зависимыми
Плохо: `HasQueryFilter(o => !o.IsDeleted)` на сущности с зависимыми по required FK, а поведение удаления связи не выбрано явно
Правильно: выбери `OnDelete` для каждой такой связи, сверив по документации EF Core версии проекта, что делает каждый вариант с каскадом в БД и с удалением сирот из коллекции в коде
Почему: soft-delete - UPDATE, а FK в БД остаётся с каскадом: физический `DELETE` родителя скриптом или вручную удаляет дочерние строки навсегда

## Миграции

### Применение миграции на production
Плохо: `dotnet ef database update` или `Database.Migrate()` шагом production-пайплайна
Правильно: проверь, какой SQL уйдёт в production и кто увидит его до применения; способ применения выбери по документации EF Core о применении миграций на production
Почему: EF генерирует блокирующие `ALTER TABLE` и операции с потерей данных; без ревью они уходят в production непросмотренными
