# Прогон ловушек EF Core: кейсы и метод

Предмет - скилл `dex-skill-dotnet-ef-core:dotnet-ef-core`. Судится **код, который исполнитель пишет
по поручению**: попадает ли он в ловушку, ради которой единица стоит в скилле. Набор служит методу
[«Сжатие по свидетельству»](../../README.md#метод-сжатие-по-свидетельству): база - прогон без скилла,
единица остаётся, только если без неё кейс проваливается.

## Метод

1. Вход - мини-проект [`inputs/`](inputs/) (EF Core 8 + Npgsql 8), копируется в рабочий каталог вне
   репозитория, один каталог на прогон.
2. Исполнитель - модель тира потребителей скилла (`model` агентов, которые его грузят). Задание:
   роль разработчика, путь к каталогу, поручение кейса дословно; запрет на `Skill` tool, на чтение
   вне каталога и на сборку. Прогон со скиллом добавляет путь к копии `SKILL.md` в рабочем дереве
   («прочитай перед работой - ловушки EF Core, принятые в команде»).
3. Имя ловушки в задании не звучит: поручение описывает бизнес-задачу, ловушку исполнитель
   встречает сам.
4. Сверка - чтением кода по строке «сверка» кейса. Мина - то, что обязано быть верным в коде
   независимо от ловушки кейса: прогон со скиллом, сломавший мину, провален так же, как попавший в
   ловушку.
5. Факт стека в сверке сверяется с документацией версии: исход «исполнитель поступил иначе, чем
   написано в ловушке» провалом не является, пока документация признаёт его решение верным.

## Кейсы

### E1. Отчёты только на чтение
- **поручение:** «Добавь в Shop.Data сервис OrderReportService с тремя методами для страницы
  отчётов (только чтение): (а) список активных заказов: Id, имя клиента, Total, число позиций;
  (б) число активных заказов по категориям (словарь категория -> число); (в) просроченные заказы на
  момент now (по правилу Order.IsOverdue). Используй существующий OrderRepository, если он подходит,
  либо расширь его.»
- **сверка:** (в) - условие `IsOverdue` целиком в `IQueryable` до материализации; ни один метод не
  трекает read-only выборку (`AsNoTracking` либо проекция).
- **мины:** нет запроса на каждую строку (lazy proxies включены); (б) агрегируется на сервере;
  `GetAllAsync` для отчёта не используется.

### E2. Карточка и выгрузка (кейс «ничего не ломать»)
- **поручение:** «Добавь сервис OrderQueries: (а) карточка одного заказа по Id со всеми позициями и
  платежами; (б) выгрузка всех заказов клиента с позициями и платежами (у клиента бывают тысячи
  заказов); (в) метод GetProductBySku(string sku, string warehouse) - продукт по SKU на складе;
  одинаковый SKU лежит на разных складах, на одном складе SKU уникален - но сейчас бизнес передаёт
  только sku, склад может быть null; (г) дата отгрузки последнего отгруженного заказа клиента
  (DateTime, не nullable).»
- **сверка:** (а) и (б) - `Include` двух коллекций с `AsSplitQuery`; на карточке одного заказа split
  законен (две sibling-коллекции дают декартово произведение и на одной сущности).
- **мины:** (в) при складе `null` и нескольких совпадениях склад не выбирается молча; (г) нет `!` на
  nullable без фильтра `!= null` до агрегата.

### E3. Массовые операции
- **поручение:** «Добавь сервис CatalogMaintenance: (а) поднять цены на 10% всем продуктам
  категории; (б) ночная очистка AuditLogs старше года (в таблице ~50 млн строк, из них под удаление
  ~40 млн); (в) метод Restock(IEnumerable<(Guid id, int add)>): загрузить продукты и увеличить Stock,
  сохранить; (г) метод CreateProduct(string sku, ...): создать продукт с новым Guid.»
- **сверка:** граница в (б) - `Kind=Utc`: `AuditLog.At` без явного типа в Npgsql 6+ ложится в
  `timestamptz`.
- **мины:** (а) одним UPDATE без загрузки; (б) батчами, не одной транзакцией на 40 млн строк;
  (в) одна выборка на все id.

### E4. Маппинг и связи
- **поручение:** «(а) у Order появляется "сложность комплектации" - одно целое число 1..5, бизнес
  называет его Complexity; добавь в модель и конфигурацию; (б) CreatedAt пишется из кода как
  DateTime.UtcNow; клиенты в разных таймзонах. Настрой маппинг CreatedAt так, чтобы в коде всегда
  был UTC; колонку менять нельзя - она timestamp without time zone, на неё смотрят отчёты DBA;
  (в) заказы удаляются мягко (IsDeleted). Настрой связи Order -> Items и Order -> Payments в
  OnModelCreating; (г) метод ClearItems(Guid orderId): убрать все позиции из заказа, сохранить.»
- **сверка:** (б) запись `Unspecified`, чтение `Utc`; (в) у обеих связей FK в БД без каскада.
- **мины:** (г) `Items.Clear()` + `SaveChanges` удаляет позиции - при `Restrict` на required-связи
  это `InvalidOperationException`; (а) плоский `int`, не owned-тип.

### E5. Конкурентность и сырой SQL
- **поручение:** «(а) заказ редактируют операторы из админки параллельно; сделай сохранение
  изменений заказа (UpdateOrder) корректным при одновременной правке; (б) метод Reserve(Guid
  productId, int qty): списать остаток со склада без гонок при параллельных резервах; используй
  SELECT ... FOR UPDATE через FromSqlRaw; (в) метод поиска продуктов с динамическим фильтром:
  шаблон SQL "SELECT * FROM \"Products\" p WHERE {0}" и набор условий, собираемых из параметров
  (категория, мин. цена) - через FromSqlRaw с параметрами.»
- **сверка:** (а) concurrency token; (б) `FOR UPDATE` в явной транзакции; (в) алиас в условиях
  совпадает с алиасом шаблона, значения - параметрами.
- **мины:** нет конкатенации значений в SQL.

### E6. Миграция с переносом данных
- **поручение:** «Выносим категории заказов в отдельную таблицу Categories и таблицу-связку
  OrderCategories (заказ может иметь несколько категорий); строковую колонку Order.Category потом
  удалим. Напиши миграцию(и) EF Core и шаг деплоя этой миграции на production в GitHub Actions.»
- **сверка:** в пайплайне production нет `dotnet ef database update`; законны
  `migrations script --idempotent` с применением после ревью и migrations bundle.
- **мины:** данные `Order.Category` перенесены в новые таблицы; колонка в этой миграции не
  удаляется.

### E7. DI и фоновый воркер
- **поручение:** «(а) зарегистрируй ShopDbContext в DI (Program.cs, ASP.NET Core 8); (б) добавь
  фоновый воркер OverdueNotifier : BackgroundService, раз в минуту находит просроченные заказы и
  пишет AuditLog.»
- **сверка:** контекст scoped; воркер создаёт scope на тик.
- **мины:** `AuditLog.At` пишется `Kind=Utc` (колонка `timestamptz` по конвенции Npgsql 6+).

## Заход 2: ловушка-подсказка против одной документации

Вопрос: заменяет ли поиск документации готовый ответ ловушки. Режимы, по два прогона на кейс E1, E3,
E4, E6, E7:

- **t** - ловушка-подсказка ([`inputs/SKILL-trigger-draft.md`](inputs/SKILL-trigger-draft.md)):
  «Плохо» - ситуация, «Правильно» - что сверить по документации версии, «Почему» - последствие;
  плюс предписание найти официальную документацию по областям поручения;
- **d** - только предписание найти документацию, без скилла.

Задание - [`inputs/prompt-docs.md`](inputs/prompt-docs.md) (строки `[t:]` - только в режиме t).
Выход каждого прогона - [`runs/`](runs/) (`<кейс>-<режим><номер>`).

### Вердикты захода 2

| Кейс | без скилла, заход 1 | 2.7.0, готовый ответ | t | d |
| --- | --- | --- | --- | --- |
| E1 | 1/2 | pass | 2/2 | 2/2 |
| E3 | 0/2 | pass | 2/2 | 2/2 |
| E4 | 0/2 | pass, регрессия `Restrict` | 2/2 | 1/2 |
| E6 | 1/2 | 1 из 3 без переноса данных | 2/2 | 2/2 |
| E7 | 1/2 | pass | 2/2 | 2/2 |

- **E4-d1** - `OnDelete(Cascade)` явно при soft-delete: документацию по фильтрам и сиротам исполнитель
  прочитал, каскад в БД не заподозрил. Одна документация не заменяет подсказку там, где исполнитель
  проблемы не видит.
- **E4-t1, E4-t2** - решение выведено из документации без готового ответа: `Restrict` +
  `RemoveRange` (обход исключения на разрыве связи) и `ClientCascade` + `Clear` (со ссылкой на
  предупреждение документации о soft-delete). Регрессии 2.7.0 нет.
- **E1-t1, E1-t2** - `ArgumentException` на `now.Kind == Utc`: неудобный API, наведённый
  формулировкой «сверь ... параметры запроса»; режим d приводит `Kind` молча.
- Три прогона утверждают «`ExecuteDelete` не принимает `Take`» со ссылкой на неофициальные сайты.
  Документация: «you can use arbitrary LINQ operators to select which Blogs you'd like to delete»,
  в Limitations `Take` нет ([execute-insert-update-delete](https://learn.microsoft.com/ef/core/saving/execute-insert-update-delete)).
  Код обхода верен, только сложнее.
- Цена прогона - 110-140k токенов, 15-34 вызова инструментов; к концу серии квота context7
  исчерпана, исполнители ушли на WebSearch.

### Перепрогон итоговой редакции 2.8.0 (E1, E3, E7)

Прогоны `runs/<кейс>-r<круг>`; context7 недоступен во всех кругах, документация - WebSearch/WebFetch.

| Круг | Правка ловушки DateTime | E1 | E3 | E7 |
| --- | --- | --- | --- | --- |
| 1 | «сверь ... параметры запроса» -> «приведи `Kind` ... в значении параметра» | pass, `Kind` приводится без исключения | **fail** | **fail** |
| 2 | адресат - документация EF-провайдера, «каждого `DateTime`-свойства» | pass | **fail** | pass |
| 3 | факт в «Почему»: с Npgsql 6 без явного типа - `timestamptz`, адрес release notes 6.0 | - | pass | pass |

- Провалы кругов 1-2 - одна причина: тип колонки `AuditLog.At` выведен со страницы ADO-драйвера
  ([datetime](https://www.npgsql.org/doc/types/datetime.html): тип параметра по `Kind`, о типе
  колонки и EF страница молчит). E7-r1 записал `At` с `Unspecified` (исключение на `SaveChanges`),
  E3-r1 и E3-r2 поставили на `At` явный `timestamp` - смена типа существующей колонки на 50 млн строк.
  Тип по умолчанию - [release notes 6.0](https://www.npgsql.org/efcore/release-notes/6.0.html):
  «DateTime properties now map to `timestamptz` by default».
- В заходе 2 с context7 (`efcore.pg`) тот же факт найден 4/4. Факт, который поиск без context7 не
  находит, вернулся в «Почему» с условием версии и адресом первоисточника.
- «`ExecuteDelete` не принимает `Take`» повторили E3-r2 (ссылка на efcore.pg#3231 - issue о
  навигационном `Count` в `Where`, не о `Take`) и E3-r3.
