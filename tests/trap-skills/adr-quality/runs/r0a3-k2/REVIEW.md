- Решение п.1, Расхождения с текущим кодом - миграция существующих строк `media` не описана: у старых записей нет `preview_status`/`preview_requested_at`, а п.3 знает только три статуса; клиент получит `null`/отсутствие поля на старых медиа, задача переиздания либо их игнорирует, либо (при `NULL` как «не ready») заливает очередь построений по всей истории - major
- Решение п.2, Откат - схема ключей `previews/<media_id>/<размер>` объявлена нормой, но не сказано, совпадает ли она с ключами, под которыми превью пишет текущий `buildPreviews`; в «Расхождениях» этого нет. Если не совпадает - две раскладки в S3 и ссылки на старые превью ломаются, откат формат хранения не возвращает; цена отката по ключам не названа - major
- Последствия (минус про 270 построений), п.4 Контекста - ~270 одновременных построений при изолированном декодере с лимитом 512 МБ - это порядка 135 ГБ памяти воркеров; ёмкость не рассчитана, «масштабируются по глубине очереди» - без потолка и проверки. В пик очередь растёт, превью приходят позже минуты - major
- Решение п.1 vs Последствия - задача переиздания берёт любой `pending` старше 30 минут, в том числе сообщения, просто стоящие в основной очереди при бэклоге; в тестах покрыт только случай «ожидает повтора». При затяжном бэклоге переиздание плодит дубли и увеличивает нагрузку - положительная обратная связь, превью ещё позже - major
- Последствия - «цель - превью в течение минуты» появилась в дизайне, во входе (PL-09) её нет; источник не указан, владельца у требования нет, проверки (метрика/алерт) нет. Цель останется декларацией, а срыв никто не заметит - minor
- Решение п.3 - заглушка и повторный запрос статуса «при следующем показе поста» - поведение клиента, проверки нет (контрактный тест покрывает только сервер); для статуса `pending` нет и срока, после которого клиент перестаёт ждать. Клиенты реализуют по-разному, автор долго видит пост без превью - minor
- Откат - «клиенты оба статуса понимают, правка им не нужна»: поле `preview_status` в ответе новое (в коде его нет), утверждение о клиентах ничем не подкреплено, а это контракт наружу (мобильные, веб, партнёры). Откат окажется невозможен без выпуска клиентов - minor
- Контекст, Решение п.1 - порядок «оригинал в S3, затем запись `media`» опирается на еженедельную сверку, удаляющую оригиналы без записи; окно между этими шагами (и сбой записи после S3) не разобрано. Сверка может удалить оригинал загружаемого файла, запись укажет на несуществующий объект, воркер даст `failed`, автор ответ об успехе уже получил - minor
- Последствия (минус про дежурство) - дежурство по новому воркеру, задаче и пяти очередям возложено на команду media без указанного согласования с ней и с платформой (эксплуатирует RabbitMQ); решение закрыто внутри ADR без адресата - minor
- Решение п.2 - превью удалённого медиа/поста (ADR-0001: физическое удаление через 30 дней) нигде не чистятся, сверка покрывает только `originals/`; осиротевшие объекты в `previews/` копятся и не учтены в ADR - minor
