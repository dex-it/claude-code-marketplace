- Решение п.3, Последствия «Откат» - в `GET /media/{id}` появляются статусы `pending`/`failed`, раньше превью у существующего медиа было всегда; версии клиентов, API партнёров и Postline Studio (поддержка 5 лет) не названы, «клиенты оба статуса понимают» ничем не подкреплено; старые клиенты покажут битую картинку или сломают рендер поста, откат контракта наружу невозможен - major
- Решение п.1-3, Расхождения с текущим кодом - уже существующие записи `media` без `preview_status`/`preview_requested_at` и их превью (ключи старой схемы) не описаны: нет бэкфилла и значения `GET` для таких записей; задача переиздания их не видит, клиент получит пустой статус и зависнет на заглушке для всей истории - major
- Последствия «Минус» (270 построений одновременно) - декодер ограничен 512 МБ на процесс, т.е. ~135 ГБ памяти воркеров на пике не оценены ни по ресурсам, ни по стоимости, нет границы масштабирования; на пике воркеры упрутся в лимит кластера, очередь растёт, превью не успевают - major
- Решение п.4 - превышение лимита декодера (20 с, 512 МБ) приравнено к ошибке декодирования и ведёт сразу в `failed`; при перегрузке воркеров (п. выше) валидные изображения получат `failed` навсегда без повтора, автору не сообщается, чинит только дежурный вручную - major
- Последствия «Минус», Проверка - «цель - превью в течение минуты» и «масштабируются по глубине очереди» не из PL-09 (там только «не ждёт»), а инженерная цель без пометки источника и без проверки/алерта; нарушение никто не заметит - minor
- Решение п.1 - потерянная публикация после записи `pending` восстанавливается только через 30+ минут при цели в минуту; пост остаётся с заглушкой, при этом у задачи нет упоминания индекса под выборку `pending` по `preview_requested_at` на большой таблице `media` - minor
- Решение п.3 - `no-store` на `pending` плюс «перезапрашивает при каждом показе»: открытие ленты (до 31 000/с) с постом крупного автора превращается в поток запросов статуса в api; поведение клиента - норма без проверки (контрактный тест только серверный) - minor
- Последствия «Откат» - записи в `pending` на момент отката и уже `failed` остаются с заглушкой без пути восстановления (`failed` не переиздаётся задачей); часть медиа навсегда без превью - minor
- Последствия «Минус» (новый воркер, задача, пять очередей) - редакция Postline Studio (on-prem, бинарная поставка, без интернета) не упомянута: не сказано, входит ли воркер превью и RabbitMQ в поставку и как эксплуатируется у клиента; у Studio превью перестанут строиться или потребуют ручной настройки - minor
