- Решение п.3 (`no-store` для `pending`/`failed`) против отвергнутого варианта «на лету» - пока превью `pending` (цель - минута, при простое дольше), каждый подписчик автора с 1 млн открывает пост и каждый показ идёт мимо кэша в api и реплику PostgreSQL; тот же шторм по пику открытий ленты (31 000/с), из-за которого отвергнут вариант 2, только перенесён на чтение статуса; для `failed` шторм постоянный, пока пост показывается - major
- Решение п.1 («простой воркеров не размножает события») + п.2 (воркер перестраивает, даже если уже `ready`) - при простоте воркеров дольше 30 минут задача переиздаёт каждую `pending`-запись каждые 30 минут (при 70/с около 126 тыс. событий за цикл), после восстановления дубли строятся заново по 3.9 с, очередь и время восстановления растут кратно; утверждение в тексте неверно, воркер должен пропускать `ready` - major
- Расхождения с текущим кодом / п.3 - нет правила для уже существующих записей `media` и для записей от старых подов во время rolling-деплоя: `preview_status` у них пустой, контрактный тест покрывает только три статуса, клиент получит неопределённое значение и покажет заглушку у старых постов или упадёт; нужны бэкфилл или явное «пусто = ready» - major
- Открытые вопросы + п.4 - `failed` терминален: автор не узнаёт и не может повторить, а переиздание дежурным «после устранения причины» бессмысленно для нечитаемого файла (ошибка декодирования не устраняется); пост навсегда с заглушкой, решение по продукту принято самим автором ADR и не подтверждено, принимать с неснятым вопросом нельзя - major
- Решение п.3 - не определено, как клиент получает адреса превью (ключи `previews/<media_id>/<размер>` в S3, а `GET /media/{id}` отдаёт только статус; размеры, префикс CDN, права доступа не названы), контракт нельзя реализовать и проверить одинаково в api и клиентах - major
- Контекст (сверка `originals/`) + п.1 - оригинал пишется в S3 раньше записи `media`; сверка, попавшая в окно между ними (или при неудачной/повторной записи строки), безвозвратно удалит единственную копию; нужен порог возраста объекта в сверке. Ключи `previews/` сверкой не покрыты: превью удалённого или недописанного медиа остаются навсегда - minor
- Решение п.4 - превышение лимита декодера по времени (20 с) считается ошибкой декодирования и сразу даёт `failed`, хотя при нагрузке (около 270 параллельных построений) это временная ошибка; на пике часть нормальных файлов получит `failed` без повторов - minor
- Последствия (масштабирование) - не названы лимит воркеров и память: 270 параллельных декодеров по 512 МБ - до ~138 ГБ, масштабирование по глубине очереди отстаёт от пика; нет метрик и алертов (возраст старейшей `pending`, глубина очередей, доля `failed`), цель «в течение минуты» не измеряется, а дежурство отдано команде media - minor
- Решение п.1 - при потере публикации после записи строки заглушка живёт до 30+ минут при цели «в течение минуты»; для выборки каждую минуту по `status`/`preview_requested_at` по большой таблице `media` не указан частичный индекс; несколько экземпляров задачи не оговорены (нужен атомарный `UPDATE ... RETURNING`) - minor
- Решение п.4 - не сказано, шлётся ли событие в `media.preview-failed`, когда статус не сменился (уже `ready`/`failed`), и какой номер попытки у события, переизданного дежурным из `media.preview-failed`; шум в очереди неудач и возможный повторный проход по лестнице - minor
- Последствия / п.3 - клиент перезапрашивает статус только «при следующем показе поста»: у подписчиков с уже открытой лентой заглушка остаётся до обновления, хотя превью готово через минуту; ожидание продукта по PL-09 не проверено - minor
