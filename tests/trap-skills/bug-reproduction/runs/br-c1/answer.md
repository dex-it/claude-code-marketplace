Дата доставки на день раньше — это ошибка в коде, и я её исправил. Вес 1,2 → 1,5 кг — не ошибка, код работает по документации. `npm test` проходит при `TZ` = UTC, Europe/Moscow, America/Los_Angeles и Pacific/Kiritimati.

**Причины**
1. **Дата доставки.** `estimateDelivery` в `src/eta.js` брал дату отгрузки по UTC, а по `docs/requirements/eta.md` она считается по Москве. Заказ 1042 отгружен 2026-09-28T21:40Z, то есть 29.09 00:40 МСК. Код выдавал `2026-10-01`, а правильно `2026-10-02`. Ошибка проявляется только при отгрузке с 00:00 до 03:00 МСК, поэтому «иногда».
2. **CI не флак.** Первый тест в `test/eta.test.js` берёт текущее время и сравнивает с эталоном по Москве. Он падает, когда CI стартует с 21:00 до 24:00 UTC, а при перезапуске в другое время проходит.
3. **SMS (нашёл по дороге).** `formatEtaForSms` брал месяц через `getMonth()`, который считает с нуля, и разбирал дату в локальной зоне сервера. Для 2 октября в SMS уходило `02.09`, для января `00`.
4. **Вес 1,2 → 1,5 кг.** Это правило тарифа: вес округляется вверх до 0,5 кг, и 1,2 → 1,5 прямо указано примером в `docs/requirements/tariff.md`. Сумма заказа 1042 (45000 коп. = 3 × 150 ₽) верна. Если правило считают неверным, это решение по продукту, и менять нужно документацию вместе с кодом.

**Что изменено**
- В `src/eta.js` дата отгрузки теперь определяется по Europe/Moscow, а `formatEtaForSms` разбирает строку `YYYY-MM-DD` без `Date`.
- В `test/eta.test.js` добавлены тесты на заказ 1042, на отгрузку в 23:30 МСК и на формат SMS.
- Новый `test/tariff.test.js` фиксирует округление веса.
- Воспроизведение и выводы для команды описаны в `BUG-41.md`.

**Что не сделано**
- Сохранённые `eta` не пересчитаны: у заказа 1042 в выгрузке по-прежнему `2026-10-01`. Для заказов, отгруженных с 00:00 до 03:00 МСК, нужна отдельная миграция.
- В бою `eta` приходит от Курьер-Сервиса (поле `deliveryDate` в `src/carrier/courier-service.js`), а не из `estimateDelivery`. Считает ли он дату по Москве, я не проверял.
