# BUG-41: дата доставки в трекинге на день раньше

## Воспроизведение

Заказ 1042 (`data/orders-sample.json`): зона B, стандарт, `shippedAt = 2026-09-28T21:40:00Z`.
По Москве это 29.09 00:40 (вторник), срок 3 рабочих дня -> ожидается **2026-10-02**.

```
node -e "import('./src/eta.js').then(m=>console.log(m.estimateDelivery('2026-09-28T21:40:00Z','B')))"
```

До исправления: `2026-10-01` (то же значение лежит в `eta` заказа). Результат не зависит от `TZ` сервера.
Проявляется только при отгрузке с 21:00 до 24:00 UTC (00:00-03:00 МСК), поэтому «иногда».

SMS: `formatEtaForSms('2026-10-02')` давал `02.09` (ожидается `02.10`) - месяц брался через `getMonth()` (с нуля).
Для января получалось `00`. Это второй дефект, он не про «на день раньше», но тоже виден клиенту.

## Причина

1. `estimateDelivery` брал дату отгрузки из UTC, а по `docs/requirements/eta.md` она определяется по Москве.
   Для отгрузки между 21:00 и 24:00 UTC дата отсчёта оказывалась на день раньше.
2. `formatEtaForSms` использовал `getMonth()` (0-11) и разбор даты в локальной зоне сервера.
3. «Флак» `test/eta.test.js` - не флак: первый тест берёт `new Date()` и сравнивает с эталоном по Москве.
   Он падает, когда CI запускается с 21:00 до 24:00 UTC, и проходит при перезапуске в другое время.

## Вес 1,2 кг -> 1,5 кг

Не баг. По `docs/requirements/tariff.md` тарифицируемый вес округляется вверх до 0,5 кг (1,2 -> 1,5),
пример в доке - ровно этот случай. Код соответствует. Для заказа 1042 сумма 45000 коп. = 3 x 150 ₽ верна.
Изменений нет; добавлен тест, фиксирующий поведение. Если поддержка считает правило неправильным - это
продуктовое решение, а не исправление кода.

## Исправление

- `src/eta.js`: дата отгрузки определяется по Europe/Moscow, `formatEtaForSms` разбирает строку без `Date`.
- Тесты: `test/eta.test.js` (отгрузка после 21:00 UTC, 23:30 МСК, формат SMS), `test/tariff.test.js` (округление веса).
  Прогон `npm test` при `TZ` = UTC, Europe/Moscow, America/Los_Angeles, Pacific/Kiritimati - всё зелёное.

## Не сделано

- Уже сохранённые `eta` в данных не пересчитаны (например, у 1042 в выгрузке всё ещё `2026-10-01`).
  `eta` заказов, отгруженных между 00:00 и 03:00 МСК, нужно пересчитать отдельной миграцией.
- В бою `eta` приходит от Курьер-Сервиса (`src/carrier/courier-service.js`, поле `deliveryDate`), а не из
  `estimateDelivery`; считает ли он дату по Москве, не проверялось.
