# BUG-41: дата доставки в трекинге на день раньше

## Воспроизведение

Детерминированно, без зависимости от текущего времени и часового пояса машины:

```
node -e "import('./src/eta.js').then(m => console.log(m.estimateDelivery('2026-09-28T21:40:00Z', 'B')))"
```

Заказ 1042 (`data/orders-sample.json`): `shippedAt` = `2026-09-28T21:40:00Z` = 29.09 00:40 МСК (вторник),
зона B, стандарт, 3 рабочих дня. По требованиям (`docs/requirements/eta.md`) - `2026-10-02`.
До исправления выдавало `2026-10-01` (это же значение лежит в выгрузке).

Условие: отгрузка с 21:00 до 24:00 UTC (00:00-03:00 МСК). `estimateDelivery` брал дату отгрузки по UTC,
а не по Москве, поэтому счёт шёл со вчерашнего дня. Граница: `20:59:00Z` -> `2026-10-01` (верно),
`21:00:00Z` -> `2026-10-02`.

## Почему «флак» в CI

`test/eta.test.js` («отгрузка сейчас») берёт `new Date()`. Тест падал только когда CI запускался
между 21:00 и 24:00 UTC, при перезапуске время уже было другим. Это не флак, а тот же баг, зависящий
от времени запуска. Теперь есть фиксированные тесты на границу суток.

## Причина

`src/eta.js`: `new Date(shippedAt)` + `setUTCDate` - календарный день определялся по UTC.

## Исправление

- `estimateDelivery`: дата отгрузки берётся по Europe/Moscow (`Intl.DateTimeFormat`), дальше счёт рабочих дней как раньше.
- Попутно, тот же модуль: `formatEtaForSms` использовал `getMonth()` (нумерация с 0) - SMS показывала
  `02.09` вместо `02.10`. Теперь формат собирается из строки `YYYY-MM-DD`, без часовых поясов.
- Тесты: заказ 1042, граница суток, формат SMS.

## «1,2 кг посчитали как 1,5 кг»

Не баг. По `docs/requirements/tariff.md` тарифицируемый вес округляется вверх до 0,5 кг
(1,2 -> 1,5), в самом документе это пример. Сумма заказа 1042 (450 ₽ = 3 x 150 ₽) корректна.
Код не менялся; если округление нужно менять - это решение по продукту/тарифу.

## Не затронуто

Уже сохранённые заказы с неверным `eta` (в т. ч. 1042 в выгрузке) не пересчитывались.
