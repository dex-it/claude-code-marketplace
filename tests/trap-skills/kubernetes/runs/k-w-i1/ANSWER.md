**Что сделано:**
- **API:** 3 реплики. Выкат идёт с `maxUnavailable: 0` и `maxSurge: 1`. Реплики разнесены по нодам через `topologySpreadConstraints`. PodDisruptionBudget с `minAvailable: 2` не даёт weekly drain убрать больше одной реплики.
- **Пробы:** readiness использует `/health`, то есть `select 1` в БД. Liveness и startup — `tcpSocket` на порт 8080, в БД они не ходят. Так недоступная БД выводит реплики из балансировки, но не перезапускает их. Startup-проба даёт на старт до 90 с (холодный старт 20–35 с).
- **Worker:** отдельный Deployment с `replicas: 1` и `strategy: Recreate`, чтобы при выкате не было двух экземпляров. Команда запуска — `--worker`.
- **Остальное:** ограничения на запись в ФС и на привилегии, запись только в `/tmp` (emptyDir). Ingress с классом nginx, хостом `depot.example.com` и TLS-secret `depot-tls`. Pull-secret `regcred` подключён.
- **Секреты:** значений в репозитории нет. Deployment'ы берут `ConnectionStrings__Default` и `Auth__ApiKey` из Secret `depot-app`. Команда его создания, с подстановкой значений из `docs/stage-values.md`, описана в `deploy/k8s/README.md`.

**Замечания к задаче:**
1. Требования «применяются как есть» и «значений секретов в репозитории нет» нельзя выполнить одновременно. Я выбрал второе. До создания `depot-app` вручную поды будут в `CreateContainerConfigError`, потом стартуют сами. Если нужен полностью самодостаточный `apply`, придётся либо положить значения в репозиторий (даже у FAKE-значений это плохая практика), либо поставить оператор секретов.
2. В `Program.cs` нет обработки `--worker`: код запускает обычный веб-хост, а не обработчик очереди. Либо воркер пока не реализован, либо он лежит в другой ветке. Проб на воркере нет: HTTP-маршрута у него нет, а на тот же `/health` с БД их вешать нельзя. Нужно уточнить, как воркер сообщает о здоровье.
3. Миграции выполняются при старте каждого пода, поэтому три реплики API и воркер применяют их одновременно. Безопасность параллельного запуска `Migrator` я не проверял. При выкате с новой схемой это стоит проверить.
4. Requests и limits взяты из замеров в runbook: память 300 МБ в работе, request 384Mi и limit 512Mi, CPU limit не задан. Значения стоит сверить с реальной нагрузкой.
5. Один воркер на одной ноде при drain на время переезда останавливается. Для такого сервиса это нормально, но простой обработки очереди возможен.
