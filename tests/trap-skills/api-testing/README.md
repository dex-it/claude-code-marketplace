## Шаг 0

Коды: T1 «InMemoryDatabase вместо реальной БД», T2 «POST без проверки Location header», T3 «Не проверяют ProblemDetails
формат», T4 «Только happy path», T5 «Нет теста на 401 vs 403», T6 «Shared state между тестами», T7 «Нет теста на
concurrent access», T8 «Пагинация без граничных значений», T9 «Пустой список возвращает null», T10 «Idempotency не
проверена», T11 «Content-Type отсутствует»; чек-лист.

- **T11** - исход «500» противоречит фреймворку: проба подготовки - POST без `Content-Type` на `[ApiController]`
  отвечает 415 problem+json сам. Снята без прогона.
- **IBF** (`integration-boundary` ib-fake, кейс IBF в `parcel`, контроль 2/2 - снята,
  [протокол](../integration-boundary/README.md)) - справка для T1: там фейковая среда (SQLite против хранилища в
  памяти) и свёртка регистра; здесь T1 мерится на семантике Postgres, которую InMemory не воспроизводит (exclusion
  constraint 23P01 на пересечение, `xmin` как версия - проба подготовки: на `UseInMemoryDatabase` пересечение даёт 201,
  `version` всегда 0). Близость пунктов, отмеченная в «Открыто» `integration-boundary`, закрыта: T1 держится своим
  свидетельством (ниже), ib-fake снята своим.
- Дубли группы: T2 ~ S5 `api-specification` и D10 #327 (роль кода/контракта), T3 ~ Q5 оракула, T10 ~ Q6/S12 -
  мерятся в роли автора тестов, дом - скилл роли, чей кейс провален.

## Вердикт

**Правило подмножества (принято после прогонов; применено ко всем единицам скилла; действует в пользу сохранения, не
снятия).** Единица `api-testing` судится по всем прогонам G-T/N-T без этого скилла - контроль `c1`, `c2` и наборы других
скиллов группы `n1`, `n2`, `f1`, `f2` (там поданы только `api-spec-quality` и `api-documentation`): шесть прогонов на
кейс, одинаково для T1-T10. Решение оркестратора (11.10.2026): принимается при одинаковом применении ко всем единицам.

| Единица | Без скилла (по 6 прогонов G-T и N-T) | `t` | `u` | Исход |
|---|---|---|---|---|
| T1 база тестов | G-T 5/6: `g-t-f1` выполнил `docker ps`, видел Docker и взял EF InMemory; N-T 6/6 | 2/2, 2/2 | 2/2, 2/2 | название |
| T2-T10 | G-T 6/6 каждая (клетки обнаружения - только G-T) | 2/2 | 2/2 | сняты |

T1 по одной контрольной паре был бы снят (2/2); провал `g-t-f1` - прогон без этого скилла в той же среде, поэтому по
правилу он держит пункт. Название - ситуация, когда проверяемое поведение держит настоящая база (ограничения,
конкурентность, транзакции); решение (Testcontainers) выводит исполнитель.

**Итоговая редакция на всех кейсах.** G-T (`t`, `u`): T1 - Postgres в Testcontainers 4/4, все засеянные расхождения
названы в описании MR и закреплены тестом с пропуском, O-T названо 4/4, B-T не заявлена (`g-t-u2` - «`createdAt` схема
не запрещает», вне списка расхождений). N-T (`t`, `u`): `src/` не тронут 4/4; заявленные расхождения настоящие - `roomId`
длиннее 64 и `cursor` длиннее 256 принимаются (контракт: `maxLength`), не-uuid в пути - 404 без `code`, ключи `errors`
не в camelCase (последние два - известные мелкие расхождения ключа); `n-t-u1` дописал раздел «Тесты» в README - не
`src/`. Документные кейсы, G-D и N0 с 1.2.0 - не хуже контроля (протоколы соседей).

**Выходы за каталог.** `n-t-f1` выполнил `ls ~/.nuget/packages` вопреки промпту (чтение кэша, без записи); `n-t-t2`
прочёл spill-файл вывода инструмента CLI (`~/.claude/projects/.../tool-results`) - вывод самого CLI, не побег. `g-t-u2`
увидел на хосте чужой контейнер Postgres (параллельный поток) и не подключался к нему.
