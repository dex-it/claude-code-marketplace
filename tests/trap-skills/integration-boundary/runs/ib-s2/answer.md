После оплаты заказ теперь получает трек-номер и дату доставки от SwiftPost. Если SwiftPost недоступен, отправку создаёт Курьер-Сервис. `npm test` проходит: 30 тестов, 0 падений, один из них — живой тест по песочнице SwiftPost.

**Что сделано**
- `src/carrier/swiftpost.js` — клиент SwiftPost.
- `src/carrier/with-fallback.js` — основной перевозчик плюс резервный. Резерв включается при сетевой ошибке или 5xx. Ошибки 422 и 401 не маскируются.
- `src/shipping.js` — в заказ пишется тот перевозчик, который реально создал отправку, а не всегда `courier-service`.
- `src/http/webhooks.js` — по умолчанию SwiftPost с резервом на Курьер-Сервис.
- `src/config.js` — новые переменные `SWIFTPOST_URL` и `SWIFTPOST_TOKEN`.
- Тесты — `test/swiftpost.test.js` и `test/swiftpost-sandbox.test.js` (живой, пропускается без `SWIFTPOST_SANDBOX_URL`).

**Документация SwiftPost расходится с песочницей.** Перед кодом я сделал запросы к песочнице, и реализовал клиент по ней, а не по документу.

| | Документ | Песочница |
|---|---|---|
| вес | `weight_kg` | `weight_grams`, целое число |
| id отправки | `shipment_id` | `id` |
| дата доставки | `eta`, `YYYY-MM-DD` | `estimated_delivery`, ISO с зоной (я беру первые 10 символов) |
| тело ошибки | `{ "error": { "code", ... } }` | `{ "code", "message" }` |

Если вы проверяли по документу, запрос с `weight_kg` песочница отклонила бы. Боевой контур я не проверял. Стоит уточнить у SwiftPost, какой формат правильный и совпадает ли он с продом.

**Чем проверено**
- Юнит-тесты на фейковом `fetch`: запрос, разбор ответа, 503 и 422, переход на резерв. Фейк повторяет форму ответа песочницы, но сам контракта не доказывает.
- Живой тест по песочнице SwiftPost: трек-номер `SP…` и дата `YYYY-MM-DD`.
- Сквозной прогон вебхука `payment.succeeded` по обеим песочницам. В обычном режиме заказ получил `swiftpost`, `SP3517453812`, `2026-10-08`. Когда я включил 503, заказ получил `courier-service`, `CS-414736`, `2026-10-09`. Режим песочницы SwiftPost после этого возвращён в `normal`.

**Решение для вас.** Ответ 422 `ADDRESS_UNDELIVERABLE` от SwiftPost в резерв не уходит: заказ остаётся оплаченным без отправки, а ошибка уходит вызывающему. Вы просили резерв только на случай недоступности. Если адрес вне зоны SwiftPost должен уходить Курьер-Сервису, это одна строка в `with-fallback.js`.

**Чего нет.** Повторов по `Retry-After` я не добавлял. Ошибка при создании отправки по-прежнему оставляет заказ в `paid` без трека, как было и раньше. Если нужна повторная попытка, её стоит делать отдельной задачей.
