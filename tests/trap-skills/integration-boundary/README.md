Скилл `dex-skill-integration-boundary` 1.0.0 ([`inputs/SKILL-1.0.0.md`](inputs/SKILL-1.0.0.md)) -> 1.1.0
([`inputs/SKILL-1.1.0.md`](inputs/SKILL-1.1.0.md)), эпик #291, группа 2.4 (#299, часть 1 из 2: тесты). Итог - 7
ловушек и чек-лист -> 3 названия: ib-mock и ib-green (контроль 2/3), слой сборки ib-layer (`unverifiable`).

Вход - мини-проект [`_projects/parcel`](../_projects/parcel/README.md), кейсы IB, IBF, N0; ключ, сверка и перечень
допустимых решений - в README мини-проекта, записаны коммитом до своих прогонов (IB - `89b89ea1`, исправление кейса
`606094f8`; IBF - `7e481bd0`). Исполнитель, среда, порядок прогонов и засчитывание - как в
[test-design](../removed/test-design/README.md#порядок-прогонов-записан-до-первого-прогона): `claude-sonnet-5-5`,
effort medium, Claude Code 2.1.291, без MCP; контроль общий. Прогоны `*-c*` - контроль, `*-s*` и `n0-ib1` - редакция
1.1.0 (итоговая, ревизий не было); со скиллом промпт дополнен строкой «Перед работой прочитай <SKILL> -
дисциплина, принятая в команде», копия `SKILL.md` подана путём. После прогонов в `description` 1.1.0 триггер «in-memory
fake» заменён на «мок внешнего API» (пункта фейковой среды в теле нет); тело то же.

## Шаг 0: тип, дом, дубли

7 H3-ловушек, сноска на `testability` и чек-лист из 7 пунктов, повторяющий ловушки названиями. Процедур нет.

- **Контракт.** Дом - `contract-drift`: «Двусторонний контракт проверен только со стороны потребителя» наследует
  вердикт `contract-drift` по кейсу CD (CD-V - сверка обеих сторон по фактическим версиям); контрактная часть
  «Слой сборки и контракта пропущен» (устаревший клиент против схемы) - тоже. Здесь остаётся граница доверия к
  тесту: мок против реальной границы, точка входа, развилки, фейковая среда.
- **Сноска на `testability`.** Строка не меняет ни одного действия исполнителя; каждое имя плагина в теле -
  обязательство поставки (решение по `post-merge-remediation` в #299 и по `stand-verification` в #293). Судьба -
  вместе с редакцией.

## Единицы без кейса (решение оркестратора 2026-10-06, до прогонов смены 2)

Без свидетельства единица не снимается. Кейс заводится, где ситуация воспроизводится в `parcel` дёшево и
надёжно; иначе - `unverifiable`, единица остаётся названием, строка «Открыто: до кейса» (прецеденты группы 1:
`testability` `Guid.NewGuid()`, `solid` S-c).

- **ib-fake** - кейс IBF: прод на SQLite (`node:sqlite` в Node 24 без зависимостей), тесты на хранилище в
  памяти; расхождение семантики - свёртка регистра кириллицы. Ключ - README мини-проекта, коммитом до прогонов.
- **ib-layer, слой сборки** (сгенерированный клиент или типы против актуальной схемы) - `unverifiable`: в
  мини-проекте без зависимостей нет шага сборки и типизации, а заведение схемы и генерации - предмет #303
  (`api-specification`) и механики TS (#298). Название остаётся, «Открыто: до кейса».

Контроль IB - три прогона: первая пара `ib-c1`, `ib-c2` - дефект кейса (исходник песочницы в репозитории прогона,
README мини-проекта), не засчитана; новая пара `ib-c3`, `ib-c4` дала IB-M 1/2, по порядку прогонов кейс получил
третий прогон `ib-c5` на все единицы (IB-M да). IB-M 2/3 - единица не снимается.

Провал `ib-c4` разобран до причины: реальный путь прогнан (curl по песочнице и e2e через вебхук), поле
`estimated_delivery` найдено, но записано в `eta` без приведения к дате. Это провал записанного критерия IB-M, но
по механизму - приведение формата ответа границы, а не мок по документации; README проекта к тому же допускает даты
«`YYYY-MM-DD` или ISO 8601 с зоной». Минимальный выбор по методу - записанный критерий: единицы ib-mock и ib-green
остаются названиями; вопрос - в «Открыто».

Приманки и дефекты вне скилла: P-cs (Курьер-Сервис в кг) чист - контроль 3/3, 1.1.0 3/3; O1 IB (токен в `src/`) не
допущен ни в одном прогоне. IBF: O1 (SQL-инъекция в `byCustomer`) названа - контроль 2/2, 1.1.0 2/2; P-iso
(сортировка ISO-строкой) не поднята 4/4. N0 (`n0-ib1`): дифф - только `src/notify/sms.js` и `test/sms.test.js`,
интеграционного прогона шлюза нет; в ответе - наблюдение «длина SMS на кириллице - проверьте на стороне шлюза» без
заявления дефекта, по ключу N0 не провал. Итоговая редакция не хуже контроля на всех кейсах.

## Открыто

- IB-M держит два названия на одном провале контроля из трёх, причина которого - формат даты из ответа границы
  (см. выше). Если владелец эпика сочтёт провал `ib-c4` вне предмета ib-mock и ib-green (дефект кейса:
  README допускает ISO с зоной), обе единицы снимаются, скилл остаётся с одним названием слоя сборки.
- Слой сборки ib-layer - `unverifiable`: в мини-проекте без зависимостей нет шага сборки, типизации и генерации
  клиента; кейс требует схемы и генерации - предмет #303 (`api-specification`) и механики TS (#298). До кейса.
- Сторона ревью (`stand-reviewer`, `bug-finder`) отдельно не мерилась: кейсы IB, IBF - поручения автору.
