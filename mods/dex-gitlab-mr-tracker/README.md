# dex-gitlab-mr-tracker

Merge request GitLab, за которым не надо ходить в браузер.

Мод берёт проект из git-remote той папки, в которой открыта сессия, находит MR текущей ветки и держит его перед глазами: строка над полем ввода несёт состояние, merge status, пайплайн, счётчик тредов, комментариев, коммитов и апрувов; панель `/mr` раскрывает то же подробно, с каждым тредом по файлу и строке. Когда ревьюер открывает тред, отвечает в нём, ставит апрув или падает пайплайн - в сессию приходит тост и строка в транскрипт. Команда `/mr threads` выписывает открытые треды текстом, и модель читает их как задание на правки. MR под наблюдением может быть несколько - своей ветки, названные руками, пришедшие ссылкой, - и у наблюдения есть общий список: `/mr list` сводит их в перечень с итогом сверху.

Это **мод** - плагин на function hooks: TypeScript, который исполняется внутри процесса Claude Code, а не команда оболочки на событие. Function hooks в раннем доступе и включаются переменной окружения (см. «Установка»).

## Требования

- Claude Code с поддержкой function hooks (проверено на 2.1.272) и `CLAUDE_CODE_ENABLE_FUNCTION_HOOKS=1`.
- Доступ к GitLab одним из двух способов:
  - [`glab`](https://gitlab.com/gitlab-org/cli), залогиненный в нужный хост (`glab auth login --hostname gitlab.example.com`) - рекомендуемый путь: он уже знает и self-managed хосты, и токены;
  - либо personal access token со scope `read_api` в `GITLAB_TOKEN` (или `GLAB_TOKEN`, или в настройке `token` мода) - тогда мод ходит в REST сам.
- Сессия открыта в клоне проекта GitLab; хост и путь проекта берутся из remote (`origin` по умолчанию).
- Необязательно: macOS для звука (`afplay`) и `open` для «открыть в браузере»; на Linux пробуется `xdg-open`.

## Установка

1. Включить function hooks. В `~/.claude/settings.json`:

   ```json
   { "env": { "CLAUDE_CODE_ENABLE_FUNCTION_HOOKS": "1" } }
   ```

   Без этого мод поставится, но ничего делать не будет. Для одной сессии хватит префикса: `CLAUDE_CODE_ENABLE_FUNCTION_HOOKS=1 claude`.

2. Поставить из каталога:

   ```sh
   claude plugin install dex-gitlab-mr-tracker@dex-claude-marketplace
   ```

   Попробовать без установки, из клона каталога:

   ```sh
   CLAUDE_CODE_ENABLE_FUNCTION_HOOKS=1 claude --plugin-dir mods/dex-gitlab-mr-tracker
   ```

3. Открыть сессию в проекте GitLab на ветке, у которой есть MR. Строка появится над полем ввода в течение нескольких секунд.

## Использование

- **MR текущей ветки** подхватывается сам и переключается вместе с веткой. Отключается настройкой `autoWatchBranch`.
- **`/mr`** - открыть или закрыть панель: общий список, когда MR несколько, иначе детали одного.
- **`/mr list`** (или `/mr ls`) - открыть общий список наблюдения и выписать его в транскрипт: итог и по строке на MR с причиной и ссылкой.
- **`/mr 123`**, **`/mr <ссылка>`** - добавить MR (в том числе из чужого проекта - ссылка несёт хост и путь) и показать его.
- **`/mr threads`** - выписать открытые треды в транскрипт: файл, строка, автор, число комментариев, первая строка и ссылка на заметку. Это вход для модели: после него можно просто сказать «закрой замечания».
- **`/mr status`** - то же про состояние MR одним блоком.
- **`/mr refresh`** - опросить GitLab сейчас.
- **`/mr drop [123 | all]`** - снять с отслеживания.
- **`/mr repo group/proj`** (или `/mr project`) - назвать проект по умолчанию руками. Формы адреса: `group/proj`, `group/sub/proj`, `gitlab.example.com/group/proj`, ссылка на проект или на MR (хвост `/-/merge_requests/...` отбрасывается) и адрес remote в любой форме, включая `git@gitlab.example.com:group/proj.git`. Хост опознаётся по точке в первом сегменте: `a/b` - проект на прежнем хосте, `gitlab.example.com/a/b` - хост и проект. Группа с точкой при этом не теряется: если первый сегмент прочитать хостом и проекта не останется, весь путь читается проектом (`my.group/proj`). Одиночный сегмент без `/` адресом не считается. Проект на другом хосте пересобирает источник данных под этот хост; если хоста нет ни в remote, ни в настройках, его надо назвать вместе с проектом.
- **`/mr repo` без аргумента** - показать выбранный проект и откуда он взят: `remote`, `настройки` или `команды`. Команда отвечает и тогда, когда проект не выбран вовсе (сессия открыта не в клоне): назвать проект - её же работа, поэтому проверка источника данных стоит после неё, и в ответ приходит причина, по которой проекта нет.
- **Ссылка на MR целым промптом** включает и выключает наблюдение, не тратя ход модели; ссылка внутри обычного промпта просто добавляет MR.
- **MR, который открыл Claude** (`glab mr create` через Bash, либо ссылка в его ответе), берётся под наблюдение сам.
- **Кнопки** строки - «открыть», «детали», «×» - нарисованы приглушённо и жмутся мышью либо с клавиатуры: `ctrl+x tab` берёт полосу над вводом в фокус. В панели свои кнопки: «открыть в браузере», «снять с отслеживания» и **«треды в промпт»** - открытые треды уедут контекстом следующего промпта один раз.

## Как читать строку

```
proj!128 opened · mergeable · ci success · ●2/7 · ✎24 · ↑12 · ✔1/2 · Фикс гонки в очереди
```

- **`proj!128`** - проект и номер MR. Ссылка кликается там, где терминал рендерит гиперссылки (Ghostty, iTerm2, WezTerm - да; Terminal.app - нет, останется текстом); в остальных случаях открывает кнопка «открыть».
- **состояние** - `opened`, `draft`, `merged`, `closed`.
- **merge status** - `detailed_merge_status` GitLab как есть, раскрашенный по смыслу: зелёный `mergeable`; красное требует вмешательства в MR или ветку (`conflict`, `need_rebase`, `commits_status`, `requested_changes`, `merge_request_blocked`, `security_policy_violations`, `locked_paths`, `locked_lfs_files`); серое не требует ничего (`draft_status`, `not_open`, `merge_time`); жёлтое - штатный гейт ещё не пройден (`ci_still_running`, `ci_must_pass`, `not_approved`, `discussions_not_resolved`, `checking`, `unchecked` и прочие). Набор значений GitLab расширяет от версии к версии, поэтому незнакомое значение рисуется жёлтым как есть, а не прячется.
- **`ci`** - статус пайплайна последнего коммита.
- **`●2/7`** - открытых тредов из тех, что можно закрыть. Обсуждения без резолва считаются отдельно и видны в панели.
- **`✎24`** - все комментарии MR, **`↑12`** - коммиты (`12+` значит, что страница заполнилась и это нижняя оценка), **`✔1/2`** - апрувы.
- **`опрос не удался`** в конце - последний запрос не прошёл, показаны прежние значения.

Больше трёх MR полоса строками не рисует вовсе: вместо них идёт один итог - `MR 7`, сколько из них ждут вас, ждут гейта и не ждут, сумма открытых тредов (`●9`), у скольких опрос не удался, - и кнопка «список», которая открывает общий список наблюдения. Десять строк над полем ввода съедают экран, а «что ждёт меня» на них всё равно не читается.

## Когда мод опрашивает GitLab

Три повода, и все три - сами, без кнопки:

- **таймер** - раз в `pollSeconds` (по умолчанию минута, минимум 15 секунд);
- **конец хода модели** - вы возвращаетесь к промпту и видите то, что в GitLab сейчас, а не то, что было на последнем тике;
- **своя команда в Bash**, меняющая MR: `git push`, `git commit`, любое действие `glab mr`.

Два последних повода не дублируют таймер: MR, опрошенный меньше 20 секунд назад, пропускается. Принудительный опрос - `/mr refresh`.

## Что приходит в сессию

Каждый опрос сравнивается с предыдущим. Первая загрузка MR не объявляет ничего. Дальше в транскрипт ложится строка (она остаётся в истории), а поверх - тост:

- состояние и `draft`, merge status, пайплайн;
- **новый тред** - с файлом, строкой, автором и первой строкой замечания;
- **тред закрыт** и **тред открыт заново**;
- **новые комментарии** в известном треде;
- **новые коммиты** и force push;
- **апрувы**.

Настройка `notify`: `all` (по умолчанию), `important` (без отдельных комментариев в тредах) и `off`. Звук (`sound`) по умолчанию выключен.

Смена проекта командой `/mr repo` наблюдение не обнуляет: снимается только MR, найденный по прежней ветке - он принадлежал прежнему проекту, - и в ответ команда называет MR, найденный по той же ветке в новом. MR, отмеченные руками или пришедшие ссылкой, остаются: у каждого свой адрес, и проект по умолчанию их не касается.

## Настройки

Правятся через `/config`, раздел мода.

| Поле | По умолчанию | Смысл |
| --- | --- | --- |
| `remote` | `origin` | remote, из URL которого берутся хост и путь проекта |
| `host`, `project` | пусто | задать вручную, если из remote не выводятся |
| `pollSeconds` | `60` | период опроса, не меньше 15 секунд |
| `autoWatchBranch` | `true` | искать MR текущей ветки |
| `backend` | `auto` | `auto` - glab, иначе REST с токеном; `glab`; `api` |
| `token` | пусто | PAT со scope `read_api` для источника `api` |
| `notify` | `all` | что объявлять |
| `sound` | `false` | звук на изменение (macOS) |

## Общий список наблюдения

Общий список отвечает на один вопрос - что из наблюдаемого ждёт вас, - и этим отличается от панели одного MR, которая отвечает, что именно там. Открывает его `/mr list`, а `/mr` без слова - сам, когда MR больше одного; та же команда печатает список текстом в транскрипт, так что его читает и модель.

Сверху итог: сколько MR всего, сколько из них ждут вас, ждут гейта и не ждут, сумма открытых тредов по всем MR и у скольких последний опрос не удался. Ноль не печатается - строки в итоге нет вовсе, а группу `данных нет` считает только текстовый дубль. Ниже по строке на MR: значок внимания, метка, причина тем же цветом и название приглушённо. Хост перед меткой появляется, только когда в списке больше одного инстанса GitLab.

Строки отсортированы по группам внимания, сначала то, что ждёт человека: `ждёт вас`, `ждёт гейта`, `данных нет`, `не ждёт`. Внутри группы - порядок добавления.

- **`●` красным, «ждёт вас»** - открытый MR, у которого сработала хотя бы одна причина. Проверки идут в порядке работы, и причина называется одна, первая сработавшая: конфликт держит всё, красный пайплайн держит мерж, треды ждут ответа. Отсюда и три вида причины: красный merge status (сам `detailed_merge_status` и есть причина), `пайплайн: failed`, `3 открытых тредов`. Перечислить в одной строке всё сразу значит не сказать ничего.
- **`●` жёлтым, «ждёт гейта»** - открытый MR, у которого ни одна из причин не сработала и который не черновик: штатный гейт ещё не пройден, делать нечего. В колонке причины стоит merge status: жёлтого уровня он её и называет (`ci_still_running`, `not_approved`, `discussions_not_resolved` и прочие), а `mergeable` там значит, что гейт держит не он.
- **`?` серым, «данных нет»** - первого опроса ещё нет. На месте причины стоит текст ошибки, а пока опрос идёт - так и сказано; пустой причины у строки не бывает.
- **`✓` серым, «не ждёт»** - делать нечего и не будет: MR смержен или закрыт, либо это черновик без конфликта, красного пайплайна и открытых тредов. Draft проверяется после причин, а не до: черновик с конфликтом всё равно ждёт автора.

Из списка в детали - нажатием на метку MR в строке (подсказка внизу списка: «нажмите номер MR, чтобы открыть детали»). Обратно - кнопка «к списку» в деталях; она нарисована, пока наблюдается больше одного MR. Кнопка «список» в итоге полосы над вводом ведёт туда же. Снимаете с отслеживания тот MR, чьи детали открыты, а другие остались - панель возвращается к списку, а не подставляет соседа; со снятием последнего панель закрывается.

## Где садится панель

Место и размер панели выбирает Claude Code, мод на них не влияет - `$.ui.open` параметра ширины не имеет вовсе, а ширина тела приходит в отрисовку только на чтение.

| Режим терминала | Где панель | Ширина | Высота |
|---|---|---|---|
| Fullscreen (alternate screen), от 110 колонок | доком сбоку от транскрипта | узкая колонка, не настраивается никем | во весь экран |
| Главный экран (`CLAUDE_CODE_NO_FLICKER=0`, и по умолчанию в tmux), любая ширина | над полем ввода | вся ширина терминала | по содержимому MR, не больше половины экрана |

Отсюда практическое следствие: широкая панель - это главный экран, а не док. В доке адрес треда ужимается с головы (`.../Eye/Command/CreateEyeLinesData.cs:54`), чтобы имя файла и строка оставались видны на любой ширине.

## Пределы

- Один опрос MR - три запроса (сам MR, треды, коммиты) плюс запрос апрувов, пока инстанс на него отвечает; после первого отказа (404/403 - эндпоинт апрувов есть не во всех редакциях) мод перестаёт его спрашивать до конца сессии.
- Треды читаются постранично; очень длинное обсуждение через REST-источник обрывается после нескольких страниц, через `glab` берётся целиком.
- Список наблюдения - он же общий список - живёт в памяти сессии: перезапуск или горячая перезагрузка мода начинают с MR текущей ветки заново.
- `/mr repo` меняет проект по умолчанию только для этой сессии: в `/config` он не пишется, и следующая сессия снова берёт проект из remote или из настроек.
- Панель и строка рисуются только в интерактивной сессии; в `-p` работают команды, но опрос по таймеру не запускается.
- Rate limit GitLab специально не обрабатывается: отказ виден как `опрос не удался`, следующий опрос повторит запрос.
- Число коммитов - длина одной страницы; для MR длиннее страницы показывается `N+`.

## Разработка

```sh
npm run typecheck:mods                     # tsc по mods/ (входит в npm run validate)
npm run test:mods                          # прогон чистой половины
claude plugin validate mods/dex-gitlab-mr-tracker   # манифест, перечень хуков и вызовов $
```

Контракт типов - `mods/types/claude-code.d.ts`, пишется командой `/plugin-types` и руками не правится. Устройство класса, инструментарий и self-check - [MOD_FRAMEWORK.md](https://github.com/dex-it/claude-code-marketplace/blob/main/docs/MOD_FRAMEWORK.md).

Правки подхватываются горячей перезагрузкой запущенной сессии; если перезагрузка сорвалась на середине, транскрипт скажет об этом - помогает перезапуск сессии.
