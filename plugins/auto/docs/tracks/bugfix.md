## 1. Назначение и граница

Трек доводит один баг от симптома до локального коммита с независимой верификацией и саморевью.

- **Рабочий каталог** - каталог сессии `/auto` на её текущей ветке, он же каталог каждого узла; каталог и ветку
  готовит оркестратор, вызвавший `/auto`. Трек дерева не заводит и ветку не переключает: коммиты ложатся в текущую.
  Первый прогон цели - на чистом дереве без коммитов ветки (`ahead` 0): всё незакоммиченное и ахед дальше - работа
  трека; иначе главный поток ставит `blocked` до прогона (`auto.md`, «Каталог»).
- **Трек решает только по фактам:** `status` узла, значение перечня (`diagnosis-check`,
  `conflict-status`), exit code, хэш файла, счётчик, наличие поля. Что факт значит - решает узел.
- **Доменное суждение ведут узлы по своим нормам:** причину - дебаггер, приёмку диагноза - кодер по
  своему файлу узла, качество правки - саморевьюер.
- **Спор узлов трек не судит:** он останавливается и отдаёт спор оператору. Автоматического второго
  круга «кодер - дебаггер» внутри прогона нет.
- Вне трека: сдача кода - push ветки цели и PR/MR по санкции `--pr` ведёт `/auto` после сдачи
  `complete` ([deliver.md](deliver.md)); деплой, миграции данных, выбор стороны в противоречии требований:
  его делает оператор правкой источника
  либо пунктом цели с пометкой «ответ оператора», и расхождение источника с таким пунктом противоречием не судится (B154).

## 3. Вход и состояние между прогонами

**Вход** (`args`): `task, symptom, expected, env, done, boundary, mode, cwd, source, goal_path, scripts, findings_top`
(`scripts` - каталог скриптов плагина, из него верификатор берёт `verify.py`);
при «продолжить» - `resume: true` и поля из auto-ledger: `trail` (пройденные шаги, передаются узлам),
`open_findings` (реестр находок, массив) и `repro`; оба - значением либо строкой JSON, как их печатает `ledger.py`;
`prior_missing` (нехватка, которую оставил прогон трека, - `Нехватка трека` цели, не `Нехватка`: кто какую пишет - R11 [ledger.md](../ledger.md)) и `goal_decisions` (`### Решения` файла трека по всем прогонам) - в шапку узлам и в промпт саморевью (B254).
`open_findings` не JSON-массив - строка `degraded`, записи ledger остаются открытыми, а прогон `complete` не отдаёт (разрыв).
`goal_path` - только адрес в шапке узлов: файлы и корпус дебаггер ищет сам, из файла цели их не берёт (B63).
`done` либо `boundary` пусты - шапка отсылает к разделу `## Критерий «готово»` либо `## Граница` файла цели, без
`goal_path` - «не подан» и граница по умолчанию; пропуск - строка `degraded` (B152, B153).
`findings_top` - вывод `ledger.py top TASK bugfix` при каждом прогоне: новые находки - `F<findings_top+k>`, выход несёт поле обратно для `finish.sh`; не подан - `N<k>` и строка `degraded` (R10 [ledger.md](../ledger.md); B226, B227).

**Решения трек принимает только по `repro`** (раздел «Контекст», последняя непустая строка по всем
прогонам), по наличию `trail` и непустому реестру `open_findings`. Журнал хранит все прогоны: улика каждого круга - в «Контексте» своего прогона, ответ
дебаггера - первой строкой `reproduction` следующего, причина остановки - строкой «Решений».

| Поле `repro` | Кто пишет | Смысл |
|---|---|---|
| `root_cause`, `files`, `reproduction`, `expected-basis`, `fix_proposal` | дебаггер | диагноз; `root_cause` пуст - диагноза нет; `reproduction` называет коммит диагноза (SHA), на нём кодер принимает диагноз; `fix_proposal` - решение исправления (устройство, цена, граничные входы, поведения под тесты), кодеру основой плана: отступление - пунктом плана с причиной (B234) |
| `repro_test`, `repro_blob` | дебаггер | путь теста и снимок `git hash-object -w` |
| `accepted` | трек, из первого не-`disputed-*` `diagnosis-check` кодера, кроме `n/a` при тесте в диагнозе | приёмка состоялась; новый диагноз сбрасывает |
| `accepted_blob` | трек, хэш верификации круга, на котором `harness-fixed` записан приёмкой и был первым исходом | ожидание гейта вместо `repro_blob` (I4); новый диагноз сбрасывает |
| `accepted_pending` | трек: `harness-fixed` первым исходом записан, прогнанной верификации его круга ещё не было; в записи ledger без поля - нет | снимок берёт верификация возобновления (I4); новый диагноз сбрасывает |
| `dispute` | трек, из `dispute` кодера при споре о диагнозе (T10, T11) | улика для следующего вызова дебаггера |
| `stack`, `build_cmd`, `test_cmd`, `prepare_cmd` | подготовка дерева этого прогона; команды сборки и тестов - ещё кодер (T13a) | техконтекст; из ledger берётся только по T1a |

**Форма сброса** `{ root_cause: '', files: [] }`: пустой «Контекст» прошлую запись ledger не перекрывает,
поэтому сброс диагноза пишется этой формой.

## 5. Инварианты

- **I1.** Ветка трека читает только факт (раздел 1). Решение о значении факта - поле узла.
- **I2.** Дебаггер продуктовый код не меняет; его тест остаётся незакоммиченным до кодера.
- **I3.** Приёмка одна на диагноз: исход первой попытки фиксируется до верификации и переживает ledger;
  следующему исполнителю сообщается со снимком, не предписывается заново. Новый диагноз её сбрасывает.
  `n/a` при тесте в диагнозе приёмкой не записывается, но первым исходом остаётся.
- **I4.** Правка теста ловится прогоном снимка ожидания на итоговом коде (T22a), а не отчётом кодера и не байтами
  файла: дописанное в файл рядом с тестом разрыва не даёт. Ожидание - `repro_blob`, после `harness-fixed` первым
  исходом - хэш верификации его круга (`accepted_blob`); круг оборвался до верификации (`accepted_pending`) - хэш
  верификации возобновления, первой после него и до новой попытки кодера (B120, B124, B125); поздний `harness-fixed`
  снимка не получает и на возобновлении (B123). Обвязку на круге приёмки и строку теста, снятую или изменённую при
  зелёном снимке, судит ревью. Хэш и ожидание сверяются без краевых
  пробелов (B146-B148). Удалённый тест (хэш - не шестнадцатеричная строка) - разрыв всегда, и без снимка; тест без
  снимка и снимок без пути теста - строка `degraded`, без пути ожидания нет (B149).
- **I5.** Дебаггер вызывается не больше одного раза за прогон.
- **I6.** Каждый не-`complete` выход несёт `where` и нехватку; путь оставленного в дереве теста назван.
- **I7.** Решение, отменяющее диагноз (противоречие, спор об ожидаемом), пишет в ledger форму сброса.
- **I8.** Статус находки меняют только переходы [domain.md](../domain.md) §3: кодер находку не закрывает, его
  `prior` disputed - строка `decisions` с его основанием.
- **I9.** Находка уходит кодеру с критерием закрытия и последней уликой реестра: без них он закрывает её по своему прочтению (B155, B156).
- **I10.** Находка, ждущая пробы (`awaitsProbe`, [domain.md](../domain.md) §2), кодеру не подаётся - ни правкой по
  находкам, ни из ledger на возобновлении - и остаётся открытой; держащая порог - `where` называет пробу вместо улики,
  прочая - строка `decisions` «нужна проба». Пометку снимает ревью записью `prior` с пустым `premise`; дальше находка
  идёт штатно (B176-B178).
- **I11.** Находка и статус ревьюера - claim: в реестр они входят выходом скептика; без него - находками ревьюера, и
  трек не отдаёт `complete`, если скептик был вызван (T16c). Ревью со снимком правки и скептиком - одно на прогон,
  сверка правки - не больше одной на правку по находкам.
- **I12.** `blocked` из сбоя узла (узел не вернул выход либо вернул `blocked`: подготовка, диагност, кодер, верификатор) несёт `node_failure: true`; `blocked` самого трека (T0, противоречие источников, спор об ожидаемом) его не несёт. `finish.sh` нехватку сбоя узла в `Нехватку трека` не пишет ([ledger.md](../ledger.md) R11): иначе `продолжить` отдало бы её кодеру как недоделанное на зелёном дереве (B265).
