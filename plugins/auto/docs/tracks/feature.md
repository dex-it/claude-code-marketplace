## 1. Назначение и граница

Трек доводит цель разработки до локальных коммитов, подтверждённых внешним фактом - прогоном сборки и
тестов в рабочем каталоге, - и саморевью без открытых P0/P1.

- **Рабочий каталог** - каталог сессии `/auto` на её текущей ветке, он же каталог каждого узла; каталог и ветку
  готовит оркестратор, вызвавший `/auto`. Трек дерева не заводит и ветку не переключает: коммиты ложатся в текущую.
  Первый прогон цели - на чистом дереве без коммитов ветки (`ahead` 0): всё незакоммиченное и ахед дальше - работа
  трека; иначе главный поток ставит `blocked` до прогона (`auto.md`, «Каталог»).
- **Push, деплой, миграции данных и удаление вне рабочего каталога не делает никто** - стоп-линия.
- **Трек решает только по фактам:** `status` узла, enum-поля выхода, числа верификатора, длина
  перечней. Что значит находка и закрыта ли она - решают узлы.
- **Порог допуска** - зелёная верификация, ноль открытых P0/P1 в реестре прогона ([ledger.md](../ledger.md), R9,
  R10), ни одного разрыва (T19). `review-verdict` - сигнал оператору, порогом не
  является.
- Вне трека: сдача кода - push ветки цели и PR/MR по санкции `--pr` ведёт `/auto` после сдачи
  `complete` ([deliver.md](deliver.md)); выбор стороны в противоречии источников требований, ответы автору.

## 3. Вход и состояние между прогонами

**Вход** (`args`): `task, goal, done, boundary, mode, cwd, source, goal_path, resume, trail, open_findings,
ctx, prior_missing, goal_decisions, scripts, findings_top`; `scripts` - каталог скриптов плагина, из него верификатор берёт `verify.py`.

- `goal_path` - только адрес в шапке узлов: файлы и корпус разведка ищет сама, из файла цели их не берёт (F85).
- `done` либо `boundary` пусты - шапка отсылает к разделу `## Критерий «готово»` либо `## Граница` файла цели, без
  `goal_path` - «не подан» и граница по умолчанию; пропуск - строка `degraded` (F91, F92).
- `findings_top` - вывод `ledger.py top TASK feature` при каждом прогоне: новые находки - `F<findings_top+k>`, выход несёт поле обратно для `finish.sh`; не подан - `N<k>` и строка `degraded` (R10 [ledger.md](../ledger.md); F169, F170).
- `resume` со `trail` - возобновление: `trail` - сделанные шаги, `ctx` - разведка прошлого прогона,
  `open_findings` - реестр ledger (`ledger.py findings TASK feature`); оба - объектом либо строкой JSON, как их печатает `ledger.py`.
- `prior_missing` - нехватка прошлого прогона (`Нехватка` цели), `goal_decisions` - `### Решения` файла трека по всем прогонам: на возобновлении оба - в шапку узлам и в промпт саморевью (F207); непустая `prior_missing` заводит попытку кодера и при коммитах трека на зелёном дереве (T8, F206).
- `resume` без `trail` - прогона по цели не было: трек идёт как первый, строка в `decisions`.
- `ctx` не в форме разведки (нет непустого `requirements` либо `files`, `conflicts` не перечнем) - разведка
  выводится узлом заново, подмена - строкой `degraded`; разведка прошлого прогона не `complete`, в том числе форма сброса T4, - тоже
  заново, строкой `decisions` (F173). `open_findings` не JSON-массив - строка `degraded`, записи ledger остаются открытыми, а
  прогон `complete` не отдаёт (разрыв).
- Техконтекст (`stack`, команды) из ledger берётся только по T1a, иначе - узел подготовки этого прогона. База на
  дереве с правками трека не замеряется (`n/a`) - в дело идёт база прошлого прогона из `trail`, шаг `1-tree`.

`finish.sh` пишет возврат в реестр: `prior` - реестр прогона, запись со своим статусом по `id`; открытые
находки - разность реестра, находка без события прогона остаётся открытой.

## 5. Инварианты

- **I1.** Ветка трека читает только факт (раздел 1). Решение о значении факта - поле узла.
- **I2.** `complete` - только при внешнем факте: команда сборки или тестов есть, прогон зелёный по
  числам раннера (T10: падения базы зелени не отнимают), на ветке трека есть свои коммиты.
- **I3.** Каждая петля ограничена потолком в скрипте: правка - 3, правка по находкам - 2, ревью - 1 на прогон со снимком правки и скептиком, сверка правки - не больше одной на правку по находкам.
- **I4.** Статус находки меняют только переходы [domain.md](../domain.md) §3: кодер находку не закрывает; молчание узла
  о находке и статус вне словаря реестра её не закрывают - она `unverified` с пометкой.
- **I5.** Выбор стороны в противоречии источников требований не делает ни один узел трека (T4): сторону выбирает оператор - правкой источника либо пунктом цели с пометкой «ответ оператора», и расхождение источника с таким пунктом противоречием не судится (F93). Допущение разведки, при котором прямое требование источника не исполняется, - противоречие; допущение там, где источник молчит, - единица R/I (F159).
- **I6.** Каждый не-`complete` выход несёт `where`; `blocked` - непустой `missing`.
- **I7.** Решения узлов копятся по всем попыткам, а не только по последней; оспоренная кодером прежняя находка (`prior` disputed) - решение с его основанием.
- **I8.** Находка уходит кодеру с критерием закрытия и последней уликой реестра: без них он закрывает её по своему прочтению (F94, F95).
- **I9.** Находка, ждущая пробы (`awaitsProbe`, [domain.md](../domain.md) §2), кодеру не подаётся - ни правкой по
  находкам, ни из ledger на возобновлении - и остаётся открытой; держащая порог - `where` называет пробу вместо улики,
  прочая - строка `decisions` «нужна проба». Пометку снимает ревью записью `prior` с пустым `premise`; дальше находка
  идёт штатно (F110, F111).
- **I10.** Находка и статус ревьюера - claim: в реестр они входят выходом скептика; без него - находками ревьюера, и
  трек не отдаёт `complete`, если скептик был вызван (T12c). Место правки без записи `roots` и решение, названное скептиком в `roots-missed`, - тоже
  не `complete`.
