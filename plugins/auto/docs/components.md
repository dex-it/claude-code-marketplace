# dex-auto: носители плагина

Справочник для того, кто правит плагин: что несёт каждый файл `dex-auto/` и почему движок устроен так. Пользователю
хватает [README плагина](../dex-auto/README.md); порядок правки треков - [CLAUDE.md](../CLAUDE.md).
Правило состава - компонент есть только там, где наблюдён названный отказ; дизайн-записки и протокол зондов -
[engine-components.md](notes/engine-components.md), [artifacts.md](notes/artifacts.md), [probes.md](notes/probes.md).

## Почему `python3`

`python3` в `PATH` - обязателен. На нём написаны ledger и оба хука: разбор
события и машинных полей цели ведётся строго, а не построчным `grep`, потому что невидимый байт
и вариация формата гасили сверку молча и снимали сторожа при живой цели. Без интерпретатора цель
не заводится, а хуки отвечают по своему исходу отказа: `Stop` пропускает остановку (иначе ход нечем закончить), `SessionStart`
сообщает, что цель не поднята. Сдача исхода (`finish.sh`) идёт своим гейтом и тем же разбором.
Других зависимостей у движка нет: `jq` он больше не требует нигде - JSON возврата разбирается
стандартной библиотекой. Сдача кода по `--pr` требует remote `origin` и канала к его хостингу,
доступного в среде (инструмент хостинга, CLI или API с авторизацией); канала нет - PR не открывается,
причина - строкой `PR:` цели, исход цели остаётся `complete`.

## Носители

| Носитель | Обязательство |
|---|---|
| `hooks/scripts/dexauto.py` | дом чтения и записи: поля шапки ledger, разделы файла трека, разбор события хука; отказ разбора отдаётся отдельным исходом и с «полей нет» не смешивается |
| `commands/onboard.md` | вход проекта: чистое дерево до любой записи, каталогу без файлов - `git init`; пустой проект - `interactive` при доступном `AskUserQuestion`, скелет - только при стеке в описании; в `interactive` назначение, стороны и граница продукта вопросом, вызов `tracks/onboard.js`, затем блок `templates/flow.md` и раздел сборки и гейтов (по `dex-skill-project-baseline`) между маркерами в `CLAUDE.md` своим коммитом; в `interactive` приёмка либо `git revert` коммитов вызова; свод правил не собирает; push нет |
| `templates/flow.md` | порядок работы проекта для `CLAUDE.md`: цикл требования (`/goal`) -> разработка (ветка, `/auto` по треку feature либо bugfix) -> фиксация истины, затем `--pr` и слив человеком |
| `commands/goal.md` | подготовка цели трека feature или bugfix из тикета, issue, спеки или формулировки: разделы `00-goal.md` (цель с видом и источником, критерий, граница) с источником у каждой строки; для feature - проба черновика `tracks/goal.js`; вопросы оператору одним пакетом, цель остаётся открытой на `Ожидает: оператор` |
| `commands/auto.md` | вход (трек по первому слову либо по `Вид:` подготовленной цели), ledger, вызов `Workflow`, исполнение критерия «готово» и решения по открытым находкам; по `--pr` - сдача кода после `complete`; `продолжить` - тот же трек с верификации |
| `tracks/feature.js` | трек feature: подготовка дерева (стек по реестру) -> контекст R/I -> проектировщик `dex-auto:designer` (до первой попытки, без коммитов трека) -> кодер `dex-auto:coder` x верификация (потолок 3) -> снимок мест правки -> саморевью, одно на прогон -> `dex-auto:skeptic` (при P0/P1) -> правка по находкам, держащим порог, и предложенным кодеру на решение (потолок 2) -> сверка правки по её дельте после правки, купленной обязательной находкой либо красной верификацией; статус первым полем каждой схемы |
| `tracks/bugfix.js` | трек bugfix: диагност `dex-auto:debugger` воспроизводит и находит первопричину (код не меняет) -> кодер `dex-auto:coder` лечит первопричину x верификация (потолок 3) -> снимок мест правки -> саморевью -> `dex-auto:skeptic` -> правка по находкам, держащим порог, и сверка правки - как в feature |
| `tracks/review.js` | трек ревью, read-only: предмет ревью - MR из канала хостинга либо своя ветка (`local`) из git против целевой, каталог на head -> `dex-auto:reviewer` (первичное ревью либо дельта, ось безопасности - его) -> `dex-auto:skeptic`: фальсификация находок, исходов осей, решений и статусов прежних, покрытие, итоговый вердикт -> инлайн-треды только при `--post`, при `local` - не публикуется |
| `tracks/record.js` | трек фиксации истины, вызывает `/auto` после цели `complete` и до сдачи кода; ledger не пишет (исход в `Фиксация:` пишет команда): фиксатор `dex-auto:recorder` пишет дельту корпуса проекта на ветке цели -> сверщик `dex-auto:corpus-checker` судит её против кода ветки один раз, без правок; расхождение, предмет без единицы, файл вне корпуса - в исход с названной нехваткой |
| `tracks/onboard.js` | трек входа в проект, вызывает `/onboard`; ledger не пишет: пустому проекту со стеком скелетник `dex-auto:scaffolder` закладывает скелет, верификатор подтверждает его зелёным прогоном, иначе `blocked` -> составитель `dex-auto:onboarder` находит либо разворачивает корпус и пишет уровень 0 -> сверщик `dex-auto:corpus-checker` судит дельту против кода репозитория один раз, без правок; расхождение корпуса с кодом, предмет без единицы, файл вне корпуса - в исход с названной нехваткой |
| `tracks/goal.js` | проба черновика цели feature для `/goal`, не трек: `goal-reader` выписывает решения об исходе, мере и границе, которых нет в черновике и источнике, нарушение черновиком источника (`breaks`) - первым и с меткой; на выводимое, допущения и вопросы их делит `/goal`; на диск не пишет |
| `agents/goal-reader.md` | узел пробы `/goal`: цель узла, определение домысла и смысл каждого поля выдачи; схема в `tracks/goal.js` держит только форму выдачи, модель - таблица узлов трека; инструменты только на чтение |
| `tracks/deliver.js` | сдача кода по `--pr` после `complete`, не трек: `deliverer` пушит ветку цели без перезаписи и открывает PR/MR (готовым к ревью, `--draft` - черновиком; `--base` либо ветка по умолчанию у remote) либо обновляет открытый; ревьюер не назначается; ledger не пишет |
| `agents/deliverer.md` | узел сдачи: канал хостинга выбирает из доступного в среде (инструмент хостинга, CLI, API), описание PR/MR - из цели, последнего прогона и диффа; смысл каждого поля выдачи |
| `agents/reviewer.md` | узел саморевью feature и bugfix и ревью MR либо своей ветки трека review: цель - находки правки цели с уликой: дефекты против ожиданий зависящих от правки, техдолг, улучшения; корень и легитимность каждого решения правки с размоткой по входам и прежнему поведению; severity по последствию, смысл полей выдачи; схема и модель - в треке |
| `agents/skeptic.md` | узел фальсификации саморевью feature и bugfix и ревью MR либо своей ветки: находки ревьюера, исходы его осей, его решения и статусы прежних - claim, сверка с кодом ревизии, решения правки вне перечня ревьюера, покрытие изменённого поведения тестами, итоговый вердикт по словарю стыка; схема и модель - в треке |
| `agents/debugger.md` | узел диагноза bugfix на любом стеке: цель - первопричина, пережившая попытки опровержения, и красный воспроизводящий тест без правки продукта; определения первопричины и попытки опровержения, смысл полей выдачи; схема и модель - в треке |
| `agents/designer.md` | узел проектирования feature до кода: решение по каждой R/I - устройство, цена операций и граница ресурса, граничные входы, задетые потребители, поведения под тесты; fact-check цены и стороннего API; код не меняет; схема и модель - в треке |
| `agents/recorder.md` | узел фиксации истины трека record: корпус проекта по его раскладке, единица на каждое изменение поведения и решение правки со `status: review`, `origin` source / derived (выведенная из кода - к приёмке), принятая единица описывает предмет - `covered`, против правки - `conflicts`, коммит с трейлером `Dex-Auto-Record: yes`, без единицы - `unrecorded` с причиной; продуктовый код не меняет; схема и модель - в треке |
| `agents/onboarder.md` | узел входа трека onboard: корпус найден (`found`, значения существующих ключей раскладки не правятся, недостающие ключ и счётчик дописываются, отличия раскладки от нормы - `layout`, не переносится) либо развёрнут (`deployed`); единица уровня 0 на назначение продукта и решение устройства, видимое в коде, со `status: review`, выведенная из кода - `derived`; существующая единица не правится - `covered` либо `conflicts`; карта, документы правил проекта и запреты для `CLAUDE.md` - `map`, `rules`, `guards`, правил из кода не выводит; коммит с трейлером `Dex-Auto-Onboard: yes`; продуктовый код не меняет; схема и модель - в треке |
| `agents/scaffolder.md` | узел скелета пустого проекта трека onboard: стек оператора по реестру, baseline целиком по норме закладки нового проекта - сборка, модуль без предметной логики, тест со smoke-тестом, типы и линтер, `.gitignore`, CI по платформе remote, README; версии - лок-файлом менеджера пакетов; бизнес-код и архитектуру не выбирает; коммит с трейлером `Dex-Auto-Onboard: scaffold`; схема и модель - в треке |
| `agents/corpus-checker.md` | узел сверки треков record и onboard, предмет называет вход: корпус есть или нет своим поиском, каждая единица дельты - `upheld` / `contradicted` / `unverifiable` против кода, постановки и статуса `review` с уликой, предмет без единицы, ложный `covered` или `unrecorded` - `missed`, файл вне корпуса в коммитах составителя с трейлером входа - `foreign`; корпус и код не меняет; схема и модель - в треке |
| `agents/coder.md` | узел реализации feature и bugfix на любом стеке: цель - план реализации до правки с трассой каждого изменения на требование, правило проекта (CLAUDE.md, ADR, гайды, конвенции) или отраслевой стандарт, затем правка по плану; где каждое требование закреплено тестом и потребители изменённого не затронуты либо поправлены; схема и модель - в треке |
| `hooks/scripts/ledger.py` | единственный читатель и писатель машинных строк ledger; адрес `<config>/projects/<slug>/ledger/<TASK>/`; `trail` отдаёт исполнителей прошлых прогонов, `decisions` - их `### Решения`, `findings` - разность реестра находок JSON-массивом (открытые, `partial`, непроверенные) для возобновления и ревью |
| `hooks/scripts/finish.sh` + `finish.py` | сдача исхода: возврат `Workflow` со stdin -> файл трека `01-<трек>.md` (петли, исполнители, открытые и снятые находки, решения, строки `degraded`), реестр находок `01-<трек>.findings.jsonl` с `id` на каждую и машинные строки цели; исход и нехватку решает главный поток, скрипт только пишет |
| `hooks/scripts/verify.py` | прогон верификатора кодом, не моделью: вход - hex от JSON `{build, test, known, snap, hash_path}`; `build_ok` - код выхода сборки, счётчики и `failing` - из отчёта раннера (JUnit XML либо TRX в `$DEX_AUTO_JUNIT_DIR`, прерванный прогон - `<aborted>`), новые красные перезапускаются один раз (`flaky`, потолок `DEX_AUTO_FLAKY_MAX`); прогон отсоединён, `--wait OUT` дожидается отчёта, потолок `DEX_AUTO_VERIFY_LIMIT` гасит группу процессов; `dirty` снимается до прогона |
| `hooks/scripts/session-start.py` | `startup\|resume\|compact`: находит открытую цель и инжектит адрес, первое действие и вызовы `ledger.py` полным путём; числа открытых целей не судит, `clear` исключён намеренно |
| `hooks/scripts/run-hook.sh` | гейт `python3` перед хуком (у `finish.sh` свой, с исходом «пиши `Edit`»): интерпретатор есть - передаёт событие хуку, нет - применяет исход отказа, свой у каждого события |
| `hooks/scripts/stop-guard.py` | при открытой цели этой сессии (владелец - сессия последней записи `ledger.py` либо `finish.sh`) останавливает ход кодом 2, пока нет `Статус: закрыт`, `Исход: blocked` с нехваткой или `Ожидает:` со словом `оператор` первым (уточнение причины дописывается следом) в `interactive`; своего потолка нет - повторные блоки снимает платформа (`CLAUDE_CODE_STOP_HOOK_BLOCK_CAP`); вызовы `ledger.py` в причине - полным путём; цель другой сессии и цель без владельца ход не держат - их называет `session-start.py` |

Узлы треков - агент каталога `Explore` и узлы плагина
(`agents/`: диагност bugfix, проектировщик feature, кодер feature и bugfix, ревьюер саморевью и трека ревью, скептик трека ревью, фиксатор и сверщик трека record, скелетник и составитель трека onboard, проба `/goal`); стек по реестру `dex-skill-stack-registry` определяет узел подготовки дерева feature и bugfix; требования источника против критерия «готово» судят оракулом `dex-skill-requirement-quality` - `/goal` при постановке, предполёт `/auto` до запуска трека, узел разведки в треке.
Неустановленный агент каталога заменяется `general-purpose` с ролью в промпте, замена попадает в возврат
полем `degraded` и в решения файла трека. Узел плагина замены не имеет: диагност или кодер не отработал - трек `blocked`;
саморевьюер - ревью без выхода, трек `partial`; ревьюер или скептик трека ревью - трек `blocked`; причина в `degraded`; узел пробы - проба `unverifiable`, и это названо в выходе `/goal`. Фиксатор трека record, скелетник и составитель трека onboard - трек `blocked`, сверщик - `partial`.

## Регистрация треков

Зависимость у движка одна - `python3` (раздел «Почему `python3`»); `finish.sh` без него не пишет, и
разделы файла трека тогда пишутся `Edit` по той же форме. `Workflow` - платформенный тул
Claude Code; команда, чьё тело его вызывает, считается явным согласием оператора на оркестрацию.
Скрипты `tracks/` плагин регистрирует как workflow (поле `workflows` в `plugin.json`), и команды
зовут их по имени `dex-auto:dex-auto-<трек>`. Поэтому они видны и в списке `/`, но вход (`args`)
собирают только команды: прямой вызов без них останавливается на входе, трек `blocked`.
