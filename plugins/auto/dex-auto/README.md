# dex-auto

Автономные треки под одну открытую цель - feature, bugfix и ревью чужого MR: команды `/goal` и `/auto`, ledger вне
рабочего дерева, Workflow-скрипт на трек, сдача исхода скриптом, три сторожевых хука. Правило состава - компонент есть только там, где
наблюдён названный отказ; дизайн-записки и протокол зондов лежат в каталоге:
[engine-components.md](https://github.com/dex-it/claude-code-marketplace/blob/main/plugins/auto/docs/notes/engine-components.md),
[artifacts.md](https://github.com/dex-it/claude-code-marketplace/blob/main/plugins/auto/docs/notes/artifacts.md),
[probes.md](https://github.com/dex-it/claude-code-marketplace/blob/main/plugins/auto/docs/notes/probes.md).

## Требования

`python3` в `PATH` - обязателен. На нём написаны ledger, дерево трека и все три хука: разбор
события и машинных полей цели ведётся строго, а не построчным `grep`, потому что невидимый байт
и вариация формата гасили сверку молча и снимали сторожа при живой цели. Без интерпретатора цель
не заводится, а хуки отвечают по своему исходу отказа: `PreToolUse` отбивает вызов узла с
названной причиной, `Stop` пропускает остановку (иначе ход нечем закончить), `SessionStart`
сообщает, что цель не поднята. Сдача исхода (`finish.sh`) идёт своим гейтом и тем же разбором.
Других зависимостей у движка нет: `jq` он больше не требует нигде - JSON возврата разбирается
стандартной библиотекой. Сдача кода по `--pr` требует remote `origin` и канала к его хостингу,
доступного в среде (инструмент хостинга, CLI или API с авторизацией); канала нет - PR не открывается,
причина - строкой `PR:` цели, исход цели остаётся `complete`.

## Что внутри

| Носитель | Обязательство |
|---|---|
| `hooks/scripts/dexauto.py` | дом чтения и записи: поля шапки ledger, разделы файла трека, адреса дерева, разбор события хука; отказ разбора отдаётся отдельным исходом и с «полей нет» не смешивается |
| `commands/goal.md` | подготовка цели трека feature или bugfix из тикета, issue, спеки или формулировки: разделы `00-goal.md` (цель с видом и источником, критерий, граница) с источником у каждой строки; для feature - проба черновика `tracks/goal.js`; вопросы оператору одним пакетом, цель остаётся открытой на `Ожидает: оператор` |
| `commands/auto.md` | вход (трек по первому слову либо по `Вид:` подготовленной цели), ledger, вызов `Workflow`, исполнение критерия «готово» и решения по открытым находкам; по `--pr` - сдача кода после `complete`; `продолжить` - тот же трек с верификации |
| `tracks/feature.js` | трек feature: подготовка дерева (стек по реестру) -> контекст R/I -> кодер `dex-auto:coder` x верификация (потолок 3) -> саморевью -> правка по находкам (потолок 1) -> повторное саморевью, если правка не замкнута (`uncovered` не «нет» либо `dependents-status` не `none`) или верификация не зелёная; статус первым полем каждой схемы |
| `tracks/bugfix.js` | трек bugfix: диагност `dex-auto:debugger` воспроизводит и находит первопричину (код не меняет) -> кодер `dex-auto:coder` лечит первопричину x верификация (потолок 3) -> саморевью -> правка по находкам (потолок 1) -> повторное саморевью на тех же условиях, что в feature |
| `tracks/review.js` | трек ревью, read-only: предмет ревью, дерево на head -> `dex-auto:reviewer` (первичное ревью либо дельта, ось безопасности - его) -> `dex-auto:skeptic`: фальсификация находок и статусов прежних, покрытие, итоговый вердикт -> инлайн-треды только при `--post` |
| `tracks/goal.js` | проба черновика цели feature для `/goal`, не трек: `goal-reader` выписывает решения об исходе, мере и границе, которых нет в черновике и источнике, нарушение черновиком источника (`breaks`) - первым и с меткой; на выводимое, допущения и вопросы их делит `/goal`; на диск не пишет |
| `agents/goal-reader.md` | узел пробы `/goal`: цель узла, определение домысла и смысл каждого поля выдачи; схема в `tracks/goal.js` держит только форму выдачи, модель - таблица узлов трека; инструменты только на чтение |
| `tracks/deliver.js` | сдача кода по `--pr` после `complete`, не трек: `deliverer` пушит ветку `auto/<TASK>` без перезаписи и открывает PR/MR (готовым к ревью, `--draft` - черновиком; `--base` либо ветка по умолчанию у remote) либо обновляет открытый; ревьюер не назначается; ledger не пишет |
| `agents/deliverer.md` | узел сдачи: канал хостинга выбирает из доступного в среде (инструмент хостинга, CLI, API), описание PR/MR - из цели, последнего прогона и диффа; смысл каждого поля выдачи |
| `agents/reviewer.md` | узел саморевью feature и bugfix: цель - находки правки цели с уликой: дефекты против ожиданий зависящих от правки, техдолг, улучшения; severity по последствию, смысл полей выдачи; схема и модель - в треке |
| `agents/skeptic.md` | узел фальсификации трека ревью: находки ревьюера и статусы прежних - claim, сверка с кодом ревизии, покрытие изменённого поведения тестами, итоговый вердикт по словарю стыка; схема и модель - в треке |
| `agents/debugger.md` | узел диагноза bugfix на любом стеке: цель - первопричина, пережившая попытки опровержения, и красный воспроизводящий тест без правки продукта; определения первопричины и попытки опровержения, смысл полей выдачи; схема и модель - в треке |
| `agents/coder.md` | узел реализации feature и bugfix на любом стеке: цель - план реализации до правки с трассой каждого изменения на требование, правило проекта (CLAUDE.md, ADR, гайды, конвенции) или отраслевой стандарт, затем правка по плану; где каждое требование закреплено тестом и потребители изменённого не затронуты либо поправлены; схема и модель - в треке |
| `hooks/scripts/ledger.py` | единственный читатель и писатель машинных строк ledger; адрес `<config>/projects/<slug>/ledger/<TASK>/`; `trail` отдаёт исполнителей прошлых прогонов, `findings` - разность реестра находок JSON-массивом (открытые, `partial`, непроверенные) для возобновления и ревью |
| `hooks/scripts/finish.sh` + `finish.py` | сдача исхода: возврат `Workflow` со stdin -> файл трека `01-<трек>.md` (петли, исполнители, открытые и снятые находки, решения, строки `degraded`), реестр находок `01-<трек>.findings.jsonl` с `id` на каждую и машинные строки цели; исход и нехватку решает главный поток, скрипт только пишет |
| `hooks/scripts/worktree.py` | дерево трека: `path TASK` (`--detach` для ревью) заводит либо переиспользует соседа дерева сессии `<корень>-<TASK>` (у подмодуля - соседа внешнего суперпроекта) на ветке `auto/<TASK>` и пишет в его git-каталог метку каталога запуска - по ней ledger находит ключ из дерева, `where TASK` и `main` отдают адреса, ничего не создавая, `drop TASK` снимает дерево без `--force` и на отказе git называет его причину; коммиты остаются в ветке. Окружение, уводящее git (`GIT_DIR` и соседи), - отказ любой команды |
| `hooks/scripts/tree-guard.py` | `PreToolUse` на пишущие инструменты и `Bash`, страховка изоляции: узел трека - любой субагент, кроме запущенного `Agent` (узел `Workflow` отличим от него только местом транскрипта), - не трогает дерево сессии: стартовал в нём - отказ любому вызову, в дереве трека - отказ команде и правке, ведущим в дерево сессии (путь канонизируется); узел чужого `Workflow` в дереве сессии при открытой цели с деревом получает тот же отказ; главный поток и субагенты `Agent` не сторожатся |
| `hooks/scripts/session-start.py` | `startup\|resume\|compact`: находит открытую цель и инжектит адрес и первое действие; числа открытых целей не судит, `clear` исключён намеренно |
| `hooks/scripts/run-hook.sh` | гейт `python3` перед хуком (у `finish.sh` свой, с исходом «пиши `Edit`»): интерпретатор есть - передаёт событие хуку, нет - применяет исход отказа, свой у каждого события |
| `hooks/scripts/stop-guard.py` | при открытой цели останавливает ход кодом 2, пока нет `Статус: закрыт`, `Исход: blocked` с нехваткой или `Ожидает:` со словом `оператор` первым (уточнение причины дописывается следом) в `interactive`; своего потолка нет - повторные блоки снимает платформа (`CLAUDE_CODE_STOP_HOOK_BLOCK_CAP`) |

Узлы треков - агент каталога `Explore` и узлы плагина
(`agents/`: диагност bugfix, кодер feature и bugfix, ревьюер саморевью и трека ревью, скептик трека ревью, проба `/goal`); стек по реестру `dex-skill-stack-registry` определяет узел подготовки дерева feature и bugfix; требования источника против критерия «готово» судят оракулом `dex-skill-requirement-quality` - `/goal` при постановке, предполёт `/auto` до запуска трека, узел разведки в треке.
Неустановленный агент каталога заменяется `general-purpose` с ролью в промпте, замена попадает в возврат
полем `degraded` и в решения файла трека. Узел плагина замены не имеет: диагност или кодер не отработал - трек `blocked`;
саморевьюер - ревью без выхода, трек `partial`; ревьюер или скептик трека ревью - трек `blocked`; причина в `degraded`; узел пробы - проба `unverifiable`, и это названо в выходе `/goal`.

## Установка и требования

```bash
/plugin install dex-auto@dex-marketplace
```

Порядок для feature и bugfix: `/goal <тикет | issue | путь | формулировка>` -> правка разделов при
необходимости -> `/auto TASK` (трек по `Вид:` цели). Без подготовки: `/auto bugfix TASK <цель>` или
`/auto feature TASK <цель>`. Ревью: `/auto review <MR>`.

Реестр стеков `dex-skill-stack-registry` и оракул `dex-skill-requirement-quality` ставятся отдельно (бандлом роли
либо поштучно).
Зависимость у движка одна - `python3` (раздел «Требования»); `finish.sh` без него не пишет, и
разделы файла трека тогда пишутся `Edit` по той же форме. `Workflow` - платформенный тул
Claude Code; команда, чьё тело его вызывает, считается явным согласием оператора на оркестрацию.
Скрипты `tracks/` плагин регистрирует как workflow (поле `workflows` в `plugin.json`), и команды
зовут их по имени `dex-auto:dex-auto-<трек>`. Поэтому они видны и в списке `/`, но вход (`args`)
собирают только команды: прямой вызов без них останавливается на входе, трек `blocked`.

## Границы

- Push без `--pr`, деплой, миграции данных и необратимое удаление - стоп-линии: прогон останавливается и
  называет их оператору. По `--pr` пушится только своя ветка `auto/<TASK>` и только после `complete`;
  merge и approve - за оператором.
- Трек работает в своём git worktree рядом с деревом сессии на ветке `auto/<TASK>`, а не в нём самом:
  чужая незакоммиченная работа не заворачивает верификацию, и коммиты цели не ложатся на чужую
  ветку. Главный поток входит в дерево до запуска трека и выходит перед сдачей исхода, узлы стартуют в нём. В
  feature и bugfix узел подготовки ставит зависимости по манифесту стека и замеряет сборку и тесты
  до правок: упавшее до правок судится унаследованным, а не внесённым. Исход `complete` дерево
  снимает (ветка с коммитами остаётся, push - оператор либо сдача кода по `--pr`), `partial` и `blocked` - оставляет под
  `/auto TASK продолжить`. Дерево не завелось либо вход в него отказал - цель уходит в `blocked`,
  прогона не было.
- Резюме прогона по id живёт только в той же сессии; после обрыва - `/auto TASK продолжить`:
  трек начинает с верификации, зелёное дерево с коммитами не переделывается, красное уходит
  кодеру вместе с перечнем сделанного из ledger; незакрытые находки прошлого прогона идут кодеру
  тем же входом, саморевью выносит статус каждой по её `id`, и зелёное дерево под ними трек мимо правки не выпускает.
- Узел, ответивший не `complete`, цель закрытой не сдаёт на любом шаге, а не только на первых:
  отказ верификатора отличается от красных тестов и не проедает потолок правок, отказ кодера и
  саморевьюера уходит наверх нехваткой, непроверенная ось security и неопубликованный тред
  названы в исходе. Решения узлов едут в ledger при любом исходе (зонд P18).
- Противоречие источников о том, что считать готовым (критерий приёмки владельца против критерия
  «готово» цели), трек стороной не закрывает: узел разведки называет его перечнем, прогон встаёт
  до фазы правки и возвращает обе стороны оператору. Сведённое узлом противоречие ниже по треку
  ненаблюдаемо, а выбранная им сторона уезжает в коммит и закрепляется тестом.
- Запись в чужой MR - только по флагу `--post`; без него находки возвращаются перечнем.
- Три трека (feature, bugfix, ревью с ревизией дельты по `--delta`). Реестр зон и подъём по
  намерению заводятся только после наблюдённого отказа выбора трека.
