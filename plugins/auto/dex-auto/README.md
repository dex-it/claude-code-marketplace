# dex-auto

Автономные треки под одну открытую цель - feature, bugfix и ревью чужого MR: команды `/goal` и `/auto`, ledger вне
рабочего дерева, Workflow-скрипт на трек, сдача исхода скриптом, три сторожевых хука. Правило состава - компонент есть только там, где
наблюдён названный отказ; дизайн-записки и протокол зондов лежат в каталоге:
[engine-components.md](https://github.com/dex-it/claude-code-marketplace/blob/main/plugins/auto/docs/notes/engine-components.md),
[artifacts.md](https://github.com/dex-it/claude-code-marketplace/blob/main/plugins/auto/docs/notes/artifacts.md),
[probes.md](https://github.com/dex-it/claude-code-marketplace/blob/main/plugins/auto/docs/notes/probes.md).

## Требования

`python3` в `PATH` - обязателен. На нём написаны ledger, дерево трека и все три хука: разбор
события и машинных полей цели ведётся строго, а не построчным `grep`, потому что невидимый байт
и вариация формата гасили сверку молча и снимали сторожа при живой цели. Без интерпретатора цель
не заводится, а хуки отвечают по своему исходу отказа: `PreToolUse` отбивает вызов узла с
названной причиной, `Stop` пропускает остановку (иначе ход нечем закончить), `SessionStart`
сообщает, что цель не поднята. Сдача исхода (`finish.sh`) идёт своим гейтом и тем же разбором.
Других зависимостей у движка нет: `jq` он больше не требует нигде - JSON возврата разбирается
стандартной библиотекой.

## Что внутри

| Носитель | Обязательство |
|---|---|
| `hooks/scripts/dexauto.py` | дом чтения и записи: поля шапки ledger, разделы файла трека, адреса дерева, разбор события хука; отказ разбора отдаётся отдельным исходом и с «полей нет» не смешивается |
| `commands/goal.md` | подготовка цели трека feature или bugfix из тикета, issue, спеки или формулировки: разделы `00-goal.md` (цель с видом и источником, критерий, граница) с источником у каждой строки; для feature - проба черновика `tracks/goal.js`; вопросы оператору одним пакетом, цель остаётся открытой на `Ожидает: оператор` |
| `commands/auto.md` | вход (трек по первому слову либо по `Вид:` подготовленной цели), ledger, вызов `Workflow`, исполнение критерия «готово» и решения по открытым находкам; `продолжить` - тот же трек с верификации |
| `tracks/feature.js` | трек feature: контекст R/I (стек по реестру) -> кодер по стеку x верификация (потолок 3) -> саморевью -> правка по находкам (потолок 1) -> повторное саморевью, если правка не замкнута (`uncovered` не «нет» либо `dependents-status` не `none`) или верификация не зелёная; статус первым полем каждой схемы |
| `tracks/bugfix.js` | трек bugfix: `debugger` воспроизводит и находит первопричину (код не меняет) -> кодер по стеку лечит первопричину x верификация (потолок 3) -> саморевью -> правка по находкам (потолок 1) -> повторное саморевью на тех же условиях, что в feature |
| `tracks/review.js` | трек ревью, read-only: предмет ревью -> `mr-reviewer` (или `mr-check-reviewer` на дельте) + `security-reviewer` по поверхности -> скептик: фальсификация находок и статусов прежних, покрытие, итоговый вердикт -> инлайн-треды только при `--post` |
| `tracks/goal.js` | проба черновика цели feature для `/goal`, не трек: `implementer-reader` выписывает решения об исходе, мере и границе, которых нет в черновике и источнике -> классификатор на чтение делит их на выводимые из кода с якорем `файл:строка` и вопросы оператору; на диск не пишет |
| `hooks/scripts/ledger.py` | единственный читатель и писатель машинных строк ledger; адрес `<config>/projects/<slug>/ledger/<TASK>/`; `trail` отдаёт исполнителей прошлых прогонов, `findings` - разность реестра находок JSON-массивом (открытые, `partial`, непроверенные) для возобновления и ревью |
| `hooks/scripts/finish.sh` + `finish.py` | сдача исхода: возврат `Workflow` со stdin -> файл трека `01-<трек>.md` (петли, исполнители, открытые и снятые находки, решения, замены узлов), реестр находок `01-<трек>.findings.jsonl` с `id` на каждую и машинные строки цели; исход и нехватку решает главный поток, скрипт только пишет |
| `hooks/scripts/worktree.py` | дерево трека: `path TASK` (`--detach` для ревью) заводит либо переиспользует `<repo>-<TASK>` на ветке `auto/<TASK>` и пишет в его git-каталог метку каталога запуска - по ней ledger находит ключ из дерева, `where TASK` и `main` отдают адреса, ничего не создавая, `drop TASK` снимает дерево и отказывает на незакоммиченном; коммиты остаются в ветке |
| `hooks/scripts/tree-guard.py` | `PreToolUse` на пишущие инструменты и `Bash`, страховка изоляции: узел трека - любой субагент, кроме запущенного `Agent` (узел `Workflow` отличим от него только местом транскрипта), - не трогает дерево сессии: стартовал в нём - отказ любому вызову, в дереве трека - отказ команде и правке, ведущим в дерево сессии (путь канонизируется); узел чужого `Workflow` в дереве сессии при открытой цели с деревом получает тот же отказ; главный поток и субагенты `Agent` не сторожатся |
| `hooks/scripts/session-start.py` | `startup\|resume\|compact`: находит открытую цель и инжектит адрес и первое действие; числа открытых целей не судит, `clear` исключён намеренно |
| `hooks/scripts/run-hook.sh` | гейт `python3` перед хуком (у `finish.sh` свой, с исходом «пиши `Edit`»): интерпретатор есть - передаёт событие хуку, нет - применяет исход отказа, свой у каждого события |
| `hooks/scripts/stop-guard.py` | при открытой цели останавливает ход кодом 2, пока нет `Статус: закрыт`, `Исход: blocked` с нехваткой или `Ожидает:` со словом `оператор` первым (уточнение причины дописывается следом) в `interactive`; своего потолка нет - повторные блоки снимает платформа (`CLAUDE_CODE_STOP_HOOK_BLOCK_CAP`) |

Узлы треков - агенты каталога (`Explore`, `dex-debugger`, кодер по стеку `dex-ts-fullstack-coder` /
`dex-dotnet-coder`, `dex-self-reviewer`, `dex-mr-reviewer`, `dex-mr-check-reviewer`,
`dex-security-reviewer`); стек узел определяет по реестру `dex-skill-stack-registry`; требования источника против критерия «готово» судят оракулом `dex-skill-requirement-quality` - `/goal` при постановке, предполёт `/auto` до запуска трека, узел разведки в треке.
Неустановленный агент заменяется `general-purpose` с ролью в промпте, замена попадает в возврат
полем `degraded` и в решения файла трека. Узел пробы `/goal` - `dex-implementer-reader`, без замены:
нет агента - проба `unverifiable`, и это названо в выходе `/goal`.

## Установка и требования

```bash
/plugin install dex-auto@dex-marketplace
```

Порядок для feature и bugfix: `/goal <тикет | issue | путь | формулировка>` -> правка разделов при
необходимости -> `/auto TASK` (трек по `Вид:` цели). Без подготовки: `/auto bugfix TASK <цель>` или
`/auto feature TASK <цель>`. Ревью: `/auto review <MR>`.

Кодеры, `dex-debugger`, ревьюеры, `dex-implementer-reader` и реестр стеков ставятся отдельно (бандлом роли либо поштучно).
Зависимость у движка одна - `python3` (раздел «Требования»); `finish.sh` без него не пишет, и
разделы файла трека тогда пишутся `Edit` по той же форме. `Workflow` - платформенный тул
Claude Code; команда, чьё тело его вызывает, считается явным согласием оператора на оркестрацию.

## Границы

- Push, деплой, миграции данных и необратимое удаление - стоп-линии: прогон останавливается и
  называет их оператору.
- Трек работает в своём git worktree `<repo>-<TASK>` на ветке `auto/<TASK>`, а не в дереве сессии:
  чужая незакоммиченная работа не заворачивает верификацию, и коммиты цели не ложатся на чужую
  ветку. Главный поток входит в дерево до запуска трека и выходит после сдачи исхода, узлы стартуют в нём. В
  feature и bugfix узел подготовки ставит зависимости по манифесту стека и замеряет сборку и тесты
  до правок: упавшее до правок судится унаследованным, а не внесённым. Исход `complete` дерево
  снимает (ветка с коммитами остаётся, push делает оператор), `partial` и `blocked` - оставляет под
  `/auto TASK продолжить`. Дерево не завелось либо вход в него отказал - цель уходит в `blocked`,
  прогона не было.
- Резюме прогона по id живёт только в той же сессии; после обрыва - `/auto TASK продолжить`:
  трек начинает с верификации, зелёное дерево с коммитами не переделывается, красное уходит
  кодеру вместе с перечнем сделанного из ledger; незакрытые находки прошлого прогона идут кодеру
  тем же входом, саморевью выносит статус каждой по её `id`, и зелёное дерево под ними трек мимо правки не выпускает.
- Узел, ответивший не `complete`, цель закрытой не сдаёт на любом шаге, а не только на первых:
  отказ верификатора отличается от красных тестов и не проедает потолок правок, отказ кодера и
  саморевьюера уходит наверх нехваткой, непроверенная ось security и неопубликованный тред
  названы в исходе. Решения узлов едут в ledger при любом исходе (зонд P18).
- Противоречие источников о том, что считать готовым (критерий приёмки владельца против критерия
  «готово» цели), трек стороной не закрывает: узел разведки называет его перечнем, прогон встаёт
  до фазы правки и возвращает обе стороны оператору. Сведённое узлом противоречие ниже по треку
  ненаблюдаемо, а выбранная им сторона уезжает в коммит и закрепляется тестом.
- Запись в чужой MR - только по флагу `--post`; без него находки возвращаются перечнем.
- Три трека (feature, bugfix, ревью с ревизией дельты по `--delta`). Реестр зон и подъём по
  намерению заводятся только после наблюдённого отказа выбора трека.
