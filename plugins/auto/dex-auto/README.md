# dex-auto

Автономные треки под одну открытую цель - feature, bugfix, ревью чужого MR и фиксация истины, плюс вход проекта в агентскую работу: команды `/onboard`, `/goal` и `/auto`, ledger вне
рабочего дерева, Workflow-скрипт на трек, сдача исхода скриптом, два сторожевых хука. Правило состава - компонент есть только там, где
наблюдён названный отказ; дизайн-записки и протокол зондов лежат в каталоге:
[engine-components.md](https://github.com/dex-it/claude-code-marketplace/blob/main/plugins/auto/docs/notes/engine-components.md),
[artifacts.md](https://github.com/dex-it/claude-code-marketplace/blob/main/plugins/auto/docs/notes/artifacts.md),
[probes.md](https://github.com/dex-it/claude-code-marketplace/blob/main/plugins/auto/docs/notes/probes.md).

## Быстрый старт

1. **Установка** - маркетплейс добавлен в Claude Code (`/plugin marketplace add dex-it/claude-code-marketplace`),
   затем из клона каталога: `./install-bundle/install-bundle.sh auto` (`install-bundle.ps1 auto` на Windows).
   Бандл `dex-bundle-auto` ставит `dex-auto` вместе со скиллами его узлов; без них узел возвращает `blocked` либо
   `partial`.
2. **Вход проекта** - в репозитории с чистым рабочим деревом `/dex-auto:onboard [описание продукта] [--interactive]`:
   корпус документации найден либо развёрнут, BRD продукта и ADR решений устройства из кода - единицами
   `status: review`, порядок работы и команды сборки, тестов и гейтов - блоком в `CLAUDE.md`. С `--interactive`
   команда спрашивает назначение, стороны и границу продукта и в конце даёт принять либо откатить дельту.
3. **Приёмка** - единицы `review` читает человек и принятую переводит в `status: approved`: с этого момента она
   обязывает.
   Выведенные из кода (`derived`) перечислены в выходе команды.
4. **Работа** - по блоку «Порядок работы» в `CLAUDE.md` проекта: `/dex-auto:goal` -> своя ветка ->
   `/dex-auto:auto TASK` -> `/dex-auto:auto TASK --pr` -> слив человеком.

## Требования

`python3` в `PATH` - обязателен. На нём написаны ledger и оба хука: разбор
события и машинных полей цели ведётся строго, а не построчным `grep`, потому что невидимый байт
и вариация формата гасили сверку молча и снимали сторожа при живой цели. Без интерпретатора цель
не заводится, а хуки отвечают по своему исходу отказа: `Stop` пропускает остановку (иначе ход нечем закончить), `SessionStart`
сообщает, что цель не поднята. Сдача исхода (`finish.sh`) идёт своим гейтом и тем же разбором.
Других зависимостей у движка нет: `jq` он больше не требует нигде - JSON возврата разбирается
стандартной библиотекой. Сдача кода по `--pr` требует remote `origin` и канала к его хостингу,
доступного в среде (инструмент хостинга, CLI или API с авторизацией); канала нет - PR не открывается,
причина - строкой `PR:` цели, исход цели остаётся `complete`.

| `hooks/scripts/finish.sh` + `finish.py` | сдача исхода: возврат `Workflow` со stdin -> файл трека `01-<трек>.md` (петли, исполнители, открытые и снятые находки, решения, строки `degraded`), реестр находок `01-<трек>.findings.jsonl` с `id` на каждую и машинные строки цели; исход и нехватку решает главный поток, скрипт только пишет |

| `hooks/scripts/session-start.py` | `startup\|resume\|compact`: находит открытую цель и инжектит адрес и первое действие; числа открытых целей не судит, `clear` исключён намеренно |
| `hooks/scripts/run-hook.sh` | гейт `python3` перед хуком (у `finish.sh` свой, с исходом «пиши `Edit`»): интерпретатор есть - передаёт событие хуку, нет - применяет исход отказа, свой у каждого события |
| `hooks/scripts/stop-guard.py` | при открытой цели этой сессии (владелец - сессия последней записи `ledger.py` либо `finish.sh`) останавливает ход кодом 2, пока нет `Статус: закрыт`, `Исход: blocked` с нехваткой или `Ожидает:` со словом `оператор` первым (уточнение причины дописывается следом) в `interactive`; своего потолка нет - повторные блоки снимает платформа (`CLAUDE_CODE_STOP_HOOK_BLOCK_CAP`); цель другой сессии и цель без владельца ход не держат - их называет `session-start.py` |

Узлы треков - агент каталога `Explore` и узлы плагина
(`agents/`: диагност bugfix, проектировщик feature, кодер feature и bugfix, ревьюер саморевью и трека ревью, скептик трека ревью, фиксатор и сверщик трека record, составитель трека onboard, проба `/goal`); стек по реестру `dex-skill-stack-registry` определяет узел подготовки дерева feature и bugfix; требования источника против критерия «готово» судят оракулом `dex-skill-requirement-quality` - `/goal` при постановке, предполёт `/auto` до запуска трека, узел разведки в треке.
Неустановленный агент каталога заменяется `general-purpose` с ролью в промпте, замена попадает в возврат
полем `degraded` и в решения файла трека. Узел плагина замены не имеет: диагност или кодер не отработал - трек `blocked`;
саморевьюер - ревью без выхода, трек `partial`; ревьюер или скептик трека ревью - трек `blocked`; причина в `degraded`; узел пробы - проба `unverifiable`, и это названо в выходе `/goal`. Фиксатор трека record и составитель трека onboard - трек `blocked`, сверщик - `partial`.

## Установка и требования

```bash
/plugin install dex-auto@dex-claude-marketplace
```

Вход проекта - один раз, на чистом дереве: `/onboard [описание продукта | путь]` - корпус, уровень 0 и порядок работы в
`CLAUDE.md`. Порядок для feature и bugfix: `/goal <тикет | issue | путь | формулировка>` -> правка разделов при
необходимости -> `/auto TASK` (трек по `Вид:` цели). Без подготовки: `/auto bugfix TASK <цель>` или
`/auto feature TASK <цель>`. Ревью: `/auto review <MR>`.
После `complete` feature или bugfix `/auto` фиксирует истину треком record до сдачи кода: исход - строкой
`Фиксация:` цели и в описании PR/MR; с `--interactive` дельту принимает либо отклоняет оператор.

Реестр стеков `dex-skill-stack-registry`, оракул `dex-skill-requirement-quality`, скиллы корпуса треков record и onboard
`dex-skill-project-docs-map`, `dex-skill-docs-layout`, `dex-skill-legacy-reconstruction` и гейтов `/onboard`
`dex-skill-project-baseline` ставятся отдельно (бандлом роли либо поштучно).
Зависимость у движка одна - `python3` (раздел «Требования»); `finish.sh` без него не пишет, и
разделы файла трека тогда пишутся `Edit` по той же форме. `Workflow` - платформенный тул
Claude Code; команда, чьё тело его вызывает, считается явным согласием оператора на оркестрацию.
Скрипты `tracks/` плагин регистрирует как workflow (поле `workflows` в `plugin.json`), и команды
зовут их по имени `dex-auto:dex-auto-<трек>`. Поэтому они видны и в списке `/`, но вход (`args`)
собирают только команды: прямой вызов без них останавливается на входе, трек `blocked`.

## Границы

- Push без `--pr`, деплой, миграции данных и необратимое удаление - стоп-линии: прогон останавливается и
  называет их оператору. По `--pr` пушится только ветка цели и только после `complete`;
  merge и approve - за оператором.
- Трек работает в каталоге сессии `/auto` на её текущей ветке: дерево и ветку под цель готовит оркестратор,
  вызвавший команду, - трек своих не заводит и ветку не переключает; для review он же ставит HEAD на head SHA
  MR, иначе ревью `partial`. Первый прогон feature и bugfix - на чистом дереве без коммитов ветки,
  иначе `blocked` до прогона. В feature и bugfix узел подготовки ставит
  зависимости по манифесту стека и замеряет сборку и тесты до правок: упавшее до правок судится унаследованным,
  а не внесённым.
- Резюме прогона по id живёт только в той же сессии; после обрыва - `/auto TASK продолжить`:
  трек начинает с верификации, зелёное дерево с коммитами не переделывается, красное уходит
  кодеру вместе с перечнем сделанного из ledger; незакрытые находки прошлого прогона идут кодеру
  тем же входом, саморевью выносит статус каждой по её `id`, и зелёное дерево под ними трек мимо правки не выпускает.
- Узел, ответивший не `complete`, цель закрытой не сдаёт на любом шаге, а не только на первых:
  отказ верификатора отличается от красных тестов и не проедает потолок правок, отказ кодера и
  саморевьюера уходит наверх нехваткой, непроверенная ось security и неопубликованный тред
  названы в исходе. Решения узлов едут в ledger при любом исходе (зонд P18).
- Противоречие источников о том, что считать готовым (критерий приёмки владельца против критерия
  «готово» цели), трек стороной не закрывает: узел разведки называет его перечнем, прогон встаёт
  до фазы правки и возвращает обе стороны оператору. Сведённое узлом противоречие ниже по треку
  ненаблюдаемо, а выбранная им сторона уезжает в коммит и закрепляется тестом.
- Запись в чужой MR - только по флагу `--post`; без него находки возвращаются перечнем.
- Три трека (feature, bugfix, ревью с ревизией дельты по `--delta`). Реестр зон и подъём по
  намерению заводятся только после наблюдённого отказа выбора трека.
