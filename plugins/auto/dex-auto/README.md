# dex-auto

Автономная разработка в Claude Code: ставишь задачу - агенты проектируют, пишут код с тестами, ревьюят свою правку,
записывают сделанное в документацию проекта и открывают PR. Готовность подтверждает не модель, а внешний факт -
прогон сборки и тестов, независимая проверка находок ревью; что довести не удалось, названо статусом с причиной.

Для разработчика в любом проекте, новом или существующем, который хочет отдавать задачу целиком и читать итог, а не
перепроверять работу.

## Установка

Нужны Claude Code, `git` и `python3` в `PATH` (на нём журнал задачи и хуки). Для PR/MR - канал к хостингу с
авторизацией: `gh`, `glab` или MCP-сервер хостинга. Установка бандлом идёт из клона каталога и требует `jq`.

```bash
# в Claude Code
/plugin marketplace add dex-it/claude-code-marketplace

# в терминале
git clone https://github.com/dex-it/claude-code-marketplace
cd claude-code-marketplace
./install-bundle/install-bundle.sh auto        # Windows: .\install-bundle\install-bundle.ps1 auto
```

Бандл `dex-bundle-auto` ставит плагин вместе со скиллами его агентов. Плагин без бандла
(`/plugin install dex-auto@dex-claude-marketplace`) запустится, но агент без своего скилла вернёт `blocked` либо
`partial`.

## Быстрый старт

### 1. Подключить проект - один раз

В корне репозитория с чистым рабочим деревом:

```
/dex-auto:onboard "CRM для отдела продаж: сделки, контакты, воронка"
```

- **Пустой проект** (в git только README, LICENSE, `.gitignore`, `CLAUDE.md`, `.docs_layout`, `docs/`). Пустой
  каталог вне git команда сама заводит `git init`. Описания нет - команда спросит назначение продукта, стороны и
  границу без флага `--interactive` (в прогоне без человека, headless, вопросов нет). Стек не назван - скелета
  нет, только документация и `CLAUDE.md`. Стек назван в описании - сначала скелет на нём: сборка, модуль, тест
  со smoke-тестом, проверка типов и линтер, `.gitignore`, CI, README - отдельным коммитом, зелёным по сборке и
  тестам; незелёный скелет команда откатывает. Бизнес-код и архитектуру скелет не выбирает:
  ```
  /dex-auto:onboard "CRM для отдела продаж на TypeScript, Node.js"
  ```
- Находит документацию проекта либо разворачивает раскладку под неё (файл `.docs_layout`).
- По коду и описанию пишет BRD продукта (назначение, стороны, граница) и ADR на решения устройства, видимые в коде.
  Каждый документ - со статусом `review`, то есть черновик. Существующие документы не правит: совпадение и
  противоречие с ними называет в ответе.
- Дописывает в `CLAUDE.md` блок между маркерами `<!-- >>> dex-auto: flow -->` и `<!-- <<< dex-auto: flow -->`:
  порядок работы, команды сборки, тестов и линтера, карту репозитория, ссылки на правила проекта и запреты. Остальной
  текст файла не трогает.
- Отвечает перечнем готовности репозитория (см. «Что нужно в репозитории»): чего нет, не заводит, а предлагает.
- Коммитит это в текущую ветку. Код существующего проекта не меняет, push не делает.

Описание продукта можно не давать - его выведут из README и кода. С `--interactive` команда сама спросит назначение
продукта и в конце даст принять дельту либо откатить её.

Затем прочитай созданные документы и принятые переведи в `status: approved`: с этого момента они обязывают агентов.
Документы с пометкой `derived` в ответе выведены из кода - это реконструкция, а не слово владельца продукта,
читай их особенно внимательно.

### 2. Поставить задачу

```
/dex-auto:goal PROJ-123                    # тикет трекера (через его MCP)
/dex-auto:goal owner/repo#42               # GitHub issue
/dex-auto:goal docs/spec/export.md         # файл спецификации
/dex-auto:goal "экспорт сделок в CSV ломает кириллицу"
```

Команда читает источник и пишет цель: что должно стать иначе, критерий «готово» в проверяемой форме, граница
«чего не трогаем» и вид - `feature` либо `bugfix`. У каждого утверждения - ссылка на источник либо пометка
«допущение». Чего из источника и кода не вывести, спрашивает пачками вопросов. Имя задачи (`TASK`) - ключ тикета,
`owner-repo-N` либо пара слов предмета; команда его выводит вместе со строкой запуска. Код не трогает.

### 3. Разработка

Своя ветка от базы, рабочее дерево чистое:

```
git switch -c feature/csv-export
/dex-auto:auto PROJ-123
```

- **feature**: проектирование -> код с тестами -> сборка и тесты (до трёх попыток) -> саморевью, серьёзные находки
  проверяет второй агент -> правка по найденному и сверка этой правки.
- **bugfix**: сначала воспроизведение красным тестом и поиск первопричины, затем лечение причины и те же проверки.

Итог - локальные коммиты. После `complete` сама идёт **фиксация истины**: изменение поведения и принятые решения
записываются в документацию проекта (BRD, ADR, FR, NFR, критерии приёмки) той же веткой, со статусом `review`, и
сверяются с кодом.

Задача без `/goal`: `/dex-auto:auto bugfix TASK <симптом>` либо `/dex-auto:auto feature TASK <цель>`.

### 4. PR

```
/dex-auto:auto PROJ-123 --pr               # --draft - черновиком, --base develop - целевая ветка
```

Пушит ветку задачи и открывает PR/MR с описанием из цели, прогона и фиксации. Флаг можно дать сразу на шаге 3 -
PR откроется после `complete`. Ревьюера не назначает, merge - за тобой.

### Ревью чужого MR либо своей ветки

```
gh pr checkout 7                           # HEAD - на head-коммите MR, иначе ревью partial
/dex-auto:auto review owner/repo#7         # находки списком
/dex-auto:auto review owner/repo#7 --post  # и треды у строк MR
/dex-auto:auto review owner/repo#7 --delta <sha прошлого ревью>   # только изменения с прошлого раза
/dex-auto:auto review --local              # своя ветка до MR против ветки по умолчанию
/dex-auto:auto review --local --base develop   # против develop
```

Код MR не меняет, approve и merge не делает. Каждая находка проверена вторым агентом по коду до выдачи.
Свою ветку не правит: находки - тебе либо треку `bugfix`; незакоммиченные правки в ревью не входят.

## Что нужно в репозитории

Агент работает тем лучше, чем больше проект говорит о себе сам. `/onboard` настраивает то, что выводится из
репозитория, и называет остальное перечнем готовности.

| Что | Зачем агенту | Кто заводит |
|---|---|---|
| Сборка и тесты одной командой | готовность правки подтверждает прогон, а не слово модели | скелет пустого проекта со стеком; иначе - ты |
| CI на push и MR | те же гейты на каждой ветке | скелет; иначе - ты |
| `.gitignore` | сборка не оставляет в дереве мусора, прогон видит только правку | скелет; иначе - ты |
| Секретов нет в git | секрет в дереве попадает в контекст агента и в его выдачу | ты |
| Документация по `.docs_layout` | назначение продукта и решения - из корпуса, а не догадкой по коду | `/onboard` |
| `CLAUDE.md` до 200 строк | его читает каждый агент, длинный файл исполняется хуже | `/onboard` пишет свой блок; остальное - ты |
| Правила проекта | ревью судит по ним, а не только по практике стека | ты либо `/dex-rulebook-miner:rulebook` |

**Блок в `CLAUDE.md`.** Его пишет `/onboard` и переписывает при повторном вызове.

- **Порядок работы** - цикл «требования -> разработка -> фиксация истины»: `goal` -> `auto` по треку -> фиксация, затем PR.
- **Сборка и гейты** - команда на каждую ось либо `нет`.
- **Карта** - каталоги верхнего уровня и точки входа.
- **Правила** - ссылки на документы проекта, объявленные нормой: гайд вклада и стиля, свод правил, вложенные
  `CLAUDE.md` и `AGENTS.md`. Правил из кода `/onboard` не выводит. Свода нет - он собирается из истории ревью MR:
  `/dex-rulebook-miner:rulebook` (ставится бандлом); пустому проекту это не предлагается - истории ещё нет.
- **Запреты** - пути, которые руками не правятся, с уликой: сгенерированный код, вендоренные зависимости, лок-файлы.

Свои правила и договорённости пиши в `CLAUDE.md` вне маркеров - их `/onboard` не трогает, а ревьюер читает как норму.

## Чем кончается прогон

Первая строка ответа - исход:

| Исход | Что значит | Что делать |
|---|---|---|
| `complete` | критерий «готово» исполнен и проверен | смотреть коммиты, строки `Фиксация:` и `PR:` |
| `partial` | доведено не всё - открытые находки, непроверенная ось | у каждой находки в ответе решение: `отложено` либо `блокирует` |
| `blocked` | не хватает входа либо агент не отработал; причина - строкой `Нехватка:` | дать недостающее и написать `/dex-auto:auto TASK продолжить` |

`продолжить` начинает с проверки текущего дерева: зелёное с коммитами не переделывается, красное идёт на доработку
вместе с тем, что уже сделано. Цель, начатая до 9.7.0, на первом `продолжить` идёт без нехватки прошлого прогона трека
(строка `Нехватка трека:` появилась в 9.7.0): недоделанное назови в `## Критерий «готово»` цели.

**Где состояние.** Журнал задачи лежит вне репозитория: `~/.claude/projects/<проект>/ledger/<TASK>/`
(`$CLAUDE_CONFIG_DIR` вместо `~/.claude`, если задан); `<проект>` - каталог запуска сессии, поэтому цель, поставленная
в одном worktree, в другом не видна. `00-goal.md` - цель и её строки `Исход:`, `Нехватка:`,
`Фиксация:`, `PR:`; `01-<трек>.md` - ход прогона, находки и решения по ним. Оборвалась сессия - в новой хук сам
напомнит об открытой задаче.

**Режим.** По умолчанию вопрос к тебе превращается в `blocked` с причиной. С `--interactive` агенты спрашивают по
ходу и дают принять либо отклонить фиксацию истины; `/goal` сам подскажет флаг, если в цели остались допущения.

## Словарь

- **Цель, `TASK`** - одна задача: что должно стать иначе, критерий «готово», граница. Открыта, пока не сдан исход.
- **Трек** - порядок работы агентов под вид задачи: `feature`, `bugfix`, `review`; служебные - `onboard` и `record`.
- **Критерий «готово»** - чем, не читая код правки, отличить сделанное от несделанного.
- **Корпус** - документация проекта; где что лежит, записано в `.docs_layout`.
- **Уровень 0** - верх корпуса: BRD (зачем продукт, для кого, чего не делает) и ADR (решения устройства).
- **Фиксация истины** - запись сделанного в корпус той же веткой, что и код: к сливу документация описывает то, что
  сливается.
- **`review` / `approved`** - черновик документа корпуса / принятый человеком, обязывающий агентов.

## Границы

- Push - только с `--pr`. Merge, approve, деплой, миграции данных и необратимое удаление не делает: прогон
  останавливается и называет такой шаг.
- Ветку не создаёт и не переключает. Первый прогон feature и bugfix - на чистом дереве без своих коммитов ветки,
  иначе `blocked` до старта.
- Требования заранее не анализирует: `/goal` ставит одну задачу, а требования продукта записываются постфактум
  фиксацией истины - сделанное и принятое становится опорой следующих задач.
- Противоречие источников о том, что считать готовым, не решает сам - останавливается и показывает обе стороны.
- В чужой MR пишет только с `--post`.

Устройство плагина для того, кто его правит, -
[components.md](https://github.com/dex-it/claude-code-marketplace/blob/main/plugins/auto/docs/components.md).
