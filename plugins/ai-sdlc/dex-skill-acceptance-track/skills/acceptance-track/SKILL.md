# Acceptance Track

Трек ведёт слитую фичу от развёрнутого стенда до вердикта приёмки против требований. Объект -
развёрнутый стенд, не исходник и не diff; фича уже в основной ветке, приёмка идёт после мерджа.
Вызывается движком `dex-sdlc:engine` - отдельно от него не запускается: движок ведёт цикл и
стоп-линию, трек - порядок этой зоны.

**Зелёный деплой - не доказательство.** Pod `Running`, health 200, чистый merge, «пайплайн зелёный»
доказывают, что код выкатился, не что фича работает. Каждое требование закрывается пробой на стенде
(запрос, сценарий, наблюдаемый эффект), не передеплоем и не чтением кода.

**Пробы трек не гоняет сам.** Прогон проб против требований делегируется
`dex-stand-reviewer:stand-reviewer`, ремедиация подтверждённых дефектов - `dex-bug-fixer:bug-fixer`.
Работой трека остаются привязка образа, оракул из корпуса, приёмка наблюдений, фальсификация находок
и доведение фиксов (`channel: self`).

**Граница с соседями.** `dex-skill-mr-review-track:mr-review-track` смотрит diff до мерджа; здесь -
поведение после. `dex-skill-diagnostics-track:diagnostics-track` идёт от симптома к первопричине;
здесь идём от требования к пробе - поломка может и не всплыть.

## Обзор фаз

| # | Фаза | Кто исполняет |
|---|---|---|
| 0 | Image-to-Code Binding | трек (сам) |
| 1 | Oracle & Probes | трек (сам) |
| 2 | Run Probes | `dex-stand-reviewer:stand-reviewer` |
| 3 | Neighbor Regression | `dex-stand-reviewer:stand-reviewer` |
| 4 | Falsify Findings | трек (сам) |
| 5 | Remediation & Re-probe | `dex-bug-fixer:bug-fixer`, трек доводит |

## Phase 0: Image-to-Code Binding

Goal: установить, что именно крутится на стенде, до любой пробы.

**Input (handoff):** контракт стыка - `dex-skill-node-contract:node-contract`. `[blocking]` стенд
(адрес/окружение) и фича, которая принимается (ветка, merge-коммит либо номер задачи). Стенда нет
или доступа к нему нет -> `status: blocked` наверх: приёмка по описанию не проводится.
`[default-ok]` `mode` (дефолт `autonomous`), `deploy` (дефолт `false` - трек read-only, см.
Boundaries), расположение аналитического корпуса (сквозное поле), `quality-checks`, путь к журналу
решений, доступы к логам/метрикам/трейсам.

Output: образ или тег на стенде -> merge-коммит, из которого собран (sha назван); способ, которым
привязка установлена (метка образа, лейбл деплоймента, эндпоинт версии).
Exit criteria: sha назван и подтверждён источником с самого стенда. Образ не содержит merge-коммита
фичи (старее) -> приёмка невозможна: выкат этот трек не делает - `status: blocked` наверх с
указанием, какой образ на стенде и какой sha нужен. `mode` определяет адресата возврата
(`node-contract` D.11), не отменяет halt.

Mandatory: yes - без привязки приёмка проверяет неизвестно что: «работает» и «работает старая
версия» неразличимы, и вердикт достаётся не той сборке.

## Phase 1: Oracle & Probes

Goal: получить множество требований с диска и назначить каждому пробу.

Требования читаются из аналитического корпуса по расположению из сквозного поля; поле не пришло -
вызови `Skill` `dex-skill-project-docs-map:project-docs-map`. Читаются `FR-NNN`/`NFR-NNN` с методом
проверки, `AC` историй, сценарии `UC` с расширениями (оттуда пробы на негативные ветки), `non-goals`,
`INV-NNN` конституции и применимые `NFR-P-NNN`. Состав и терминал недостижимого корпуса -
`node-contract`, `references/quality-and-review.md` п.7.

Output: таблица «требование -> проба»: что дёрнуть, что ожидаем наблюдать, чем наблюдение
фиксируется (ответ, лог, метрика, трейс).
Exit criteria: каждое требование имеет пробу либо явный исход «не проверяемо на стенде» с причиной.
Требование без пробы = непроверенное, а не пройденное. Корпус недостижим (адреса нет И поиск пуст) ->
пробы строятся от `success criteria` работы, и это объявляется статусом `requirements-coverage:
unverifiable` с указанием, где искали.

Mandatory: yes - без оракула с диска приёмка идёт по пересказу требований в задаче, и требование, не
доехавшее до неё, никем не проверяется.

## Phase 2: Run Probes

Goal: получить наблюдения по каждой пробе.

Делегируй `dex-stand-reviewer:stand-reviewer` с пробами Phase 1 и привязкой Phase 0. Каждое
утверждение о поведении опирается на наблюдение: команда + вывод, id лога/трейса, метрика, скриншот.
Выдуманный ответ стенда запрещён; недоступный источник - явный статус «недоступен» с указанием
какого, не молчание.

Output: по каждой пробе - наблюдение и вердикт (прошла | провалилась | источник недоступен).
Exit criteria: проб без вердикта нет; под каждым вердиктом лежит наблюдение либо явный «недоступен».

Mandatory: yes - вердикт без наблюдения есть мнение о стенде, а мнение о стенде расходится с
поведением стенда ровно там, где это дороже всего.

## Phase 3: Neighbor Regression

Goal: проверить, что слитая фича не задела соседнее.

Фича могла задеть то, что рядом (общие эндпоинты, шина, схема, общий кэш). Пробы ставятся не только
на новое поведение, но и на соседний путь, который фича трогала; какие пути соседние - даёт
`dex-skill-completeness-mapping:completeness-mapping` по затронутым контрактам, не догадка «вроде
не связано».

Output: перечень соседних путей с вердиктом по каждому.
Exit criteria: перечень построен по карте потребителей затронутых контрактов; путь, который проверить
не удалось, назван с причиной.

Mandatory: yes - регрессия соседа не всплывает в пробах на новое поведение и обнаруживается
пользователем, а не приёмкой.

## Phase 4: Falsify Findings

Goal: опровергнуть каждую находку прежде, чем заводить дефект.

Находка на стенде - гипотеза: «упало» может быть тестовыми данными, чужим стендом, устаревшим
образом, правами. Опровергни, прежде чем заводить: воспроизведи, сверь с кодом merge-коммита Phase 0,
исключи окружение.

Output: подтверждённые дефекты с воспроизведением и severity; снятые находки с причиной снятия.
Exit criteria: находок без исхода нет; для каждого подтверждённого дефекта названо, чем исключено
окружение.

Mandatory: yes - дефект окружения, заведённый как дефект фичи, уводит ремедиацию в правку кода,
который работает.

## Phase 5: Remediation & Re-probe

Goal: довести подтверждённые дефекты до исправленного и проверенного на том же стенде.

Подтверждённые дефекты -> follow-up ветка, не правка общей ветки. Пачку багов чинит
`dex-bug-fixer:bug-fixer` (лечит корень), но заканчивается на локальных коммитах: push, саморевью и
MR остаются за этим треком в порядке сдачи движка (шаг 8). Push и создание MR - outward-facing
действия: право даёт поле входа оркестратора, не режим (`node-contract`, «Outward-facing действие =
санкция оркестратора»); санкции нет -> коммиты остаются локальными, и это называется в выходе.

Довести до конца: MR влит -> фикс выкачен на стенд -> повторная проба там же, где баг найден.
«Тесты зелёные» и «MR влит» приёмкой не считаются - фикс, не проверенный на стенде, не проверен.

Output: по каждому дефекту - ветка, коммиты, статус MR, результат повторной пробы на стенде.
Exit criteria: каждый дефект доведён до зелёной повторной пробы либо отложен явно - заведённая задача
с владельцем и строка в выходе. Дефектов нет - фаза закрывается статусом `n/a` с этой причиной.
Выката ждать нечем (нет прав, стенд не обновляется) -> `status: partial` с перечнем непроверенных
фиксов, не вердикт «принято».

Mandatory: условная - обязательна при наличии хотя бы одного подтверждённого дефекта Phase 4; без
дефектов закрывается `n/a` с причиной, молчаливый пропуск запрещён.

## Выход трека (handoff)

**Output:** первым полем `status` (словарь исхода - `node-contract`), затем: привязка образа к
merge-коммиту (sha + чем установлена); таблица «требование -> проба -> наблюдение -> вердикт» с
исходом по каждому требованию; `requirements-coverage` (`unverifiable` + место поиска, если корпус
недостижим); результат регрессии соседей; подтверждённые дефекты с воспроизведением и severity;
снятые находки с причиной; статус ремедиации по каждому дефекту, включая результат повторной пробы;
отложенное с владельцем и номером задачи; недоступные источники наблюдения поимённо; допущения;
решения, принятые за оператора, отдельным перечнем; сквозные поля входа как есть; перечень
незакрытого при `partial`/`blocked`.

Читатель выхода - движок (шаг 8, сдача). Первопричина, которую проба не объясняет, уходит в
`dex-skill-diagnostics-track:diagnostics-track`, правка кода - в
`dex-skill-bugfix-track:bugfix-track` через трек разработки.

**Exit criteria:** Output несёт все перечисленные поля; `complete` выдаётся только когда каждое
требование имеет исход и каждый подтверждённый дефект доведён до зелёной повторной пробы; иначе
`partial`/`blocked` с перечнем.

**Mandatory:** yes - приёмка без сводного выхода не отличает проверенное от недоступного, и
отложенный дефект теряется вместе с окном, в котором его нашли.

## Саморевью трека

Не принят ли зелёный деплой за работающую фичу; привязан ли образ к merge-коммиту (а не «наверное,
свежий»); есть ли наблюдение под каждым утверждением (или явный «недоступен»); не выдуман ли вывод
стенда; фальсифицирована ли каждая находка (окружение, данные, права исключены); верифицирован ли
фикс на стенде, а не только тестами; не мутировал ли общий стенд.

## Boundaries

- Read-only: стенд общий - не мутируй (не перезапускай, не правь конфиг, не чисти БД). Нужен
  мутирующий шаг для проверки -> выноси предложением с санкцией `deploy`, не выполняй.
- Правку кода трек не делает: дефекты уходят в ремедиацию отдельным узлом.
- Выкат и передеплой - outward-facing действия по санкции оркестратора, не по режиму.
- Требование без пробы считается непроверенным, а не пройденным, в любом отчёте.
