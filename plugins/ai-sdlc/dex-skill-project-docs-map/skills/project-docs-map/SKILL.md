# Карта документации проекта

Предмет - **расположение** корпуса (принятые требования, ADR, спеки), не его содержание: что извлечь, решает вызывающий узел по своей задаче.

## 1. Дом путей - `.docs_layout` в корне репозитория

Пути к корпусу - **обязательный атрибут проекта**. Читаются в начале работы, до выводов о том, что требуется и как принято.

Имя файла фиксировано конвенцией, поэтому адрес известен без записи о том, где он записан. Форма - строка на путь:

```
root: docs/requirements/
adr: docs/adr/
specs: docs/specs/
counter: docs/requirements/.req_counter
```

Обе формы пути штатны - правило, требующее доки рядом с кодом, отсекает типичный случай:

| Форма | Пример | Особенность |
|---|---|---|
| каталог репозитория | `docs/requirements/`, `docs/adr/` | читается всегда |
| отдельный репозиторий | путь клона либо URL | может быть не склонирован либо закрыт по правам - п.4 |

Путей фич в файле нет: где лежит корпус фичи, выводится поиском в `root` по номеру. Раскладки под фичи нет вовсе (чужой корпус, ступень 3 `artifact-naming`) - связь берётся из номеров в самих единицах, тем же проходом, которым строится счётчик (п.5).

**Файла нет, а раздел путей есть в `CLAUDE.md`** - работать по нему и завести `.docs_layout` тем же заходом: прежняя норма держала пути там, и на старых проектах они остались. Расходятся - **находка, а не выбор одного из двух**: пути могли развести по разным корпусам, и какой из них действующий, решает человек.

**Корпус проекта != рабочее состояние задачи.** Документация задачи (`docs/<TASK>/` и корпус выше) в
git и едет с MR; **auto-ledger** - журнал автономной работы (`dex-skill-autonomous-task`) - лежит вне
рабочего дерева и в корпус не пишется. Запись не по назначению даёт либо утечку служебного состояния
в MR, либо потерю документации задачи вместе со средой.

## 2. Файла нет - искать и записать

Отсутствие путей - нехватка **инженерная**: восполняется самостоятельно в любом режиме, наверх не эскалируется, работу не останавливает.

1. Искать по стандартным местам: `docs/`, `docs/adr/`, `docs/decisions/`, `*.adr.md`, `docs/requirements/`, `docs/specs/`.
2. Найденное проверить на принадлежность проекту (п.3).
3. Прошло проверку -> завести `.docs_layout` в корне **текущего** репозитория. Корень определяй `git rev-parse --show-toplevel`; нет `Bash` в tools узла - бери корень рабочего каталога, а неоднозначность корня (вложенный репозиторий, монорепа) фиксируй пунктом выхода и запись не делай.
4. Запись отразить явным пунктом выхода: что записано и на основании чего найдено (`node-contract` п.5 - решение узла в выход, не молча).

Ничего не найдено -> зафиксировать это пунктом выхода и работать по восстановленному из кода контексту. Отсутствие корпуса halt'ом не является.

## 3. Принадлежность проекту - по содержимому, не по соседству

Найденные доки относятся к этому проекту, если **называют** его продукт, сервис или репозиторий. Файловое соседство доказательством не является: монорепа, соседний клон и submodule дают доки чужого проекта на расстоянии одного каталога.

Подтвердить принадлежность не удалось -> пути идут в выход пунктом, **запись не делается**. Догадка в чужой файл не пишется.

## 4. Пути есть, корпус недостижим - статус, не молчание

Три состояния различаются, и каждое имеет свой терминал:

| Состояние | Действие |
|---|---|
| путей нет | п.2 - искать, записать найденное |
| пути есть, корпус читается | сверяться, как предписывает задача узла |
| пути есть, корпус недостижим (не склонирован, закрыт по правам, каталог пуст) | `unverifiable` + причина в выход |

Недостижимость **не** трактуется как «сверка не нужна» и **не** чинится подменой путей на локальные. Молча пропущенная сверка превращается в «проверено, конфликтов нет» на узле ниже, который метке доверился.

Исключение одно, и оно в п.5: недостижимый **счётчик** даёт остановку, а не пометку.

## 5. `.req_counter` - счётчики номеров

Номер единицы не ищется максимумом по корпусу, а берётся инкрементом счётчика. `.req_counter` - **директория, и ключ в ней - файл**: имя файла есть ключ, содержимое - одно число, последний выданный номер.

```
.req_counter/feature      -> 02
.req_counter/01.BR        -> 1004
.req_counter/01.UC        -> 1002
.req_counter/01.FR        -> 1017
.req_counter/01.NFR       -> 1005
.req_counter/02.BR        -> 2003
```

| Ключ | Что даёт |
|---|---|
| `feature` | номер последней заведённой фичи; новой - плюс один |
| `NN.<КЛАСС>` | последний номер класса в блоке фичи `NN`; новой единице - плюс один |

Значение - **полный номер**, а не младший разряд: он читается без пересчёта в уме и не даёт соврать про блок. Выдача - три действия одним заходом: прочитал файл ключа, увеличил, записал. **Файл пишется тем же действием, каким заводится единица**, а не «потом»: счётчик, отставший от корпуса, выдаёт занятый номер.

Ключ на класс, а не на фичу целиком: `FR` и `NFR` пишутся параллельными ветками, и общий ключ вернул бы им гонку, которой в схеме нет.

**Файл на ключ, а не строка в общем файле** - разница видна при слиянии. Строки одного файла сталкиваются от соседства: два прогона по разным фичам и две параллельные ветки одной правят соседние строки, конфликт приходит там, где двойной выдачи нет, и разбор столкновений превращается в рутину, которую быстро начинают гасить выбором стороны. Разведённые по файлам ключи сливаются чисто, а конфликт остаётся ровно на том ключе, за который боролись двое, - то есть только там, где номер и правда выдан дважды (п.6).

**Счётчик один на корпус, а не на репозиторий.** Реп у продукта бывает много, требования принадлежат продукту: одна фича, сделанная тремя сервисами, имеет один блок номеров, иначе трасса рвётся на границе репозитория. Отсюда раскладка: `.docs_layout` - в каждой репе (он указатель, ключ `counter`), `.req_counter` - один, при корпусе. Разные продукты со своими корпусами имеют свои счётчики, и пересекаться им нечем.

**Директории нет - она строится один раз.** Значения восстанавливаются сплошным проходом по номерам, уже стоящим в единицах корпуса, - по классам и блокам, а не по папкам раскладки: на чужой раскладке каталогов под фичи нет вовсе, а номера есть. Проход заводит файл на каждый встреченный ключ. Корпус пуст - директория пуста, первая фича получает `01`. Дальше читаются файлы, повторного прохода нет; путь к заведённой директории пишется в `.docs_layout` тем же действием.

**Счётчик отстал от корпуса - чинится по корпусу, и это находка.** Единица, написанная мимо конвейера, номер заняла, а файл ключа не тронула: значение подтягивается до максимального в корпусе, факт называется в выходе. Обратное расхождение - счётчик больше максимума - штатно: так выглядят дырки от снятых единиц.

**Счётчик недостижим - `blocked`, а не номер вслепую.** Путь записан, файл ключа не прочитать и не записать (репозиторий корпуса не склонирован, закрыт по правам) - номер не выдаётся: это не случай «корпус не читается» из п.4. Там работа идёт дальше с пометкой, и несверенное названо; здесь узел собирается **записать** номер, который молча столкнёт два набора единиц в одном блоке, а вскроется это, когда единицы уже уехали в код. Терминал - `status: blocked` с указанием, чего не хватает и что нужно, чтобы счётчик читался. Клонировать репозиторий узлы зоны 1 не могут - инструмента у них нет.

**Снятие счётчик назад не откручивает.** Фича снята - `feature` не уменьшается, её блок остаётся дыркой; то же для единицы. Иначе следующая фича получает блок, в котором уже лежат чужие единицы и ссылки на них, и происходит это невидимо.

## 6. Конфликт в `.req_counter` - сигнал, что номер выдан дважды

Ключ - файл, поэтому конфликт слияния приходит только там, где две стороны увеличили **один и тот же** ключ, и означает он ровно одно: номер выдан двум единицам. Соседние ключи - другая фича, параллельная ветка `NFR` - сливаются чисто, потому что столкновения в них нет. **Конфликт читается как факт, а не как текст**, и без него совпавшие номера разошлись бы молча: в самих единицах они лежат в разных файлах и сливаются без единого признака.

Выбор стороны запрещён: «взять свою», «взять входящую», «взять большую» гасят сигнал, оставляя столкновение в корпусе. Порядок разрешения:

1. Значение ключа - **максимум обеих сторон**.
2. Перенумеровывается **входящая** сторона, та, что ещё не в базе: её номера с меньшей вероятностью успели разойтись. Конфликт по ключу `feature` - перенумеровывается блок фичи целиком (`2001…` -> `3001…`); по ключу `NN.<КЛАСС>` - только столкнувшиеся единицы.
3. Правятся не только сами единицы, но и ссылки на них: трасса в историях и `AC`, записи `quality-checks`, `decision-log`. Область поиска - **корень корпуса**, а не папка фичи: мера, обслуживающая несколько фич, лежит вне неё.
4. Проверка после: двух единиц с одним номером в корпусе нет, счётчик не меньше максимального номера в корпусе.
5. Номер успел уйти **за пределы корпуса** - в код, тесты, тикеты: правка внутри репозитория делается, внешнее называется находкой. Тикеты и чужие системы узел не переписывает.

Разрешает тот, кто ведёт слияние (`dex-conflict-resolver`), либо дирижёр, если столкновение всплыло внутри прогона.

## 7. Сверка по предмету узла - обязательна

Корпус прочитан -> свериться по своему предмету:

- **новое требование** - не дублирует и не противоречит принятому; номер берётся в блоке своей фичи и в своём классе - не заново с единицы и не сквозняком по проекту (`dex-skill-unit-identity:unit-identity`);
- **решение** - покрыто `Accepted` ADR либо отклонение от него обосновано явно (детали ADR-осей - `dex-skill-codebase-conventions`, ось 6);
- **спека/дизайн** - опирается на действующую версию, не на `Superseded`.

Расхождение найдено -> находка в выход по контракту узла, не тихая правка чужого артефакта.
