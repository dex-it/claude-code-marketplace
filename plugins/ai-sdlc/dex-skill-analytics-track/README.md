# dex-skill-analytics-track

Трек зоны требований (аналитика/требования) движка `dex-sdlc`: ведёт путь «идея -> BRD -> сценарии -> `FR`/`NFR`
-> stories с критериями» до набора, по которому пишется код.

## Состав

| Артефакт | Что делает |
|---|---|
| Skill `analytics-track` | 7 фаз, две безусловные остановки оператора, проба готовности, дельта-прогон |

Вызывается движком `dex-sdlc:engine` - трек не запускается отдельно от него: движок ведёт цикл,
стоп-линию и возобновление, трек - порядок этой зоны.

## Как работает

```
вход (тема / проработанная идея / чужой документ / правка принятого)
  |
  v
Phase 1: Bootstrap - ключ прогона, классификация, номер фичи
  |
  v
Phase 2: Цели -> BRD          (dex-business-analyst:business-requirements-analyst)
  |  ОСТАНОВКА 1: границы и цели
  v
Phase 3: Сценарии -> UC       (dex-usecase-analyst:usecase-analyst)
  |
  v
Phase 4: Правила и меры -> FR/NFR   (dex-requirements-analyst:requirements-analyst)
  |
  v
Phase 5: Нарезка -> истории с AC    (dex-user-story-analyst:user-story-analyst)
  |
  v
Phase 6: Проба готовности          (dex-implementer-reader:implementer-reader)
  |  ОСТАНОВКА 2 (финальная): приёмка набора вместе с остатком пробы
  v
Phase 7: Handoff -> зона дизайна (/design)
```

`NFR` идут своей веткой от `BR` и ограничений среды, сценариев не ждут. Правка принятой единицы идёт
не с начала, а дельтой: род изменения объявляется, задетое считается по трассе, остановка - после
пересчёта.

## Два следа

- `decision-log` - в корпусе фичи, едет с MR: решения оператора, допущения, находки гейтов с
  разрешением. Пишет только трек. Живёт в git, поэтому переживает отдельный прогон по построению.
- `auto-ledger` (ключ `TASK`) - история движения внутри одного прогона; трек заводит и ведёт его как
  любой другой, движок его не подменяет. Отдельного файла состояния фичи между прогонами нет:
  продолжение (номер, разрешённые пути, закрытые фазы) читается заново сканированием корпуса на
  каждом Bootstrap, а не кэшем.

## Режим

`interactive` (от `/feature`) - диалог с explicit approval на обеих остановках. `autonomous` (спавн
узлом в стеке треков) - полномочную ось трек закрывает выводом из уже принятого, каждое такое решение
идёт отдельным списком «принято за оператора» в выходе и в `decision-log`.

## Границы

- Артефакты пишут составители, не трек - написав артефакт сам, трек теряет право судить его на
  гейте.
- Апрув в `interactive` всегда явный ответ оператора; авто-approve нет.
- Согласование чужих готовых требований - `/review-requirements`, не эта команда.
- Правая граница - принятый набор. Дизайн и спека - зона дизайна (`/design`), задачи и код там же не
  порождаются.

## Использование

Напрямую не вызывается - через команды движка:

```
/feature                                  # тема запрашивается в диалоге
/feature личный кабинет с экспортом отчётов
/feature docs/brd/payments.md             # чужой готовый BRD - входная приёмка
/feature-check                            # проверка своего уже собранного набора, без нового прогона
```
