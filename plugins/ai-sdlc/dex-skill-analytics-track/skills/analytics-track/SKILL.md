# Analytics Track

Трек зоны требований: ведёт прогон «идея -> цели -> сценарии -> правила и меры -> истории с критериями» до
набора, по которому пишется код. Артефакты пишут составители-субагенты (`dex-business-analyst:business-requirements-analyst` -> BRD с `BR-NNN`,
`dex-usecase-analyst:usecase-analyst` -> сценарии `UC`, `dex-requirements-analyst:requirements-analyst` -> `FR`/`NFR`,
`dex-user-story-analyst:user-story-analyst` -> истории с `AC`, `dex-implementer-reader:implementer-reader` -> проба готовности;
`subagent_type` резолвится только полной формой `{плагин}:{агент}`, голое имя даёт `Agent type not found`). Трек классифицирует
вход, спавнит их, судит набор целиком, ведёт следы и собирает единственную остановку оператора. Правая граница - принятый набор;
дальше зона дизайна, другой владелец и другой апрув. **Поднят напрямую, без движка** - подними `dex-sdlc:engine`,
войди через шаг 1: без него нет auto-ledger, стоп-линии, режима.

**Составители обоих уровней кода не читают**: `business-requirements-analyst` не порождает
`FR`/`NFR`, `requirements-analyst` не производит спеку; код оба видят только когда конвейер идёт по
коду без ТЗ (`dex-skill-legacy-reconstruction:legacy-reconstruction`).

**Порядок конвейера задан входами, а не прозой:** `BR` -> `UC` -> `FR` -> нарезка в истории; `NFR`
идут своей веткой от `BR` и ограничений среды и сценариев не ждут. Несценарная ветка - фича без
наблюдаемого актором поведения (миграция, регламент, техдолг) - идёт от `BR` сразу к правилам; это
условие с проверкой и объявленным основанием, а не исход по умолчанию.

**Гейт и остановка - разные вещи.** Гейт качества проходит каждая фаза: оракул единицы и оракул
набора прогоняются треком, вердикт пишется в `quality-checks`. Безусловная остановка оператора
**одна** - финальная приёмка набора; до неё остановка условная и возникает, только когда без ответа
не построить следующую фазу: невыводимая находка либо затронутая полномочная ось. **Ось - предмет
решения, по которому у фичи возможны разные исходы с разной ценой; полномочная - та, где цена ошибки
лежит вне артефакта.** Оси не берутся из перечня: их видно при разборе фичи, называешь их ты либо оператор.
**Фаза, закрывшаяся без остановки, апрува себе не выдаёт:** её
артефакт стоит в `review` до финальной приёмки - отсутствие вопросов означает, что их не возникло, а
не что документ принят.

**Оператору предъявляется решение, а не список находок.** Находка сортируется по разрешимости
(`node-contract`, «Первый вопрос - выводимость»): выводимая закрывается здесь - возвратом
составителю либо решением трека - и предъявляется строкой «принято X, потому что Y» в общем списке;
невыводимая предъявляется вопросом с вариантами и рекомендацией. Оператор подтверждает оба класса,
но разной ценой внимания: невыводимое - поштучно, принятое - списком целиком. Ни одна находка при
этом не пропадает - устранённая живёт в `decision-log`, принятая под запись - в перечне долга.

**Находки гейта едут вниз вместе с меткой.** Составитель нижнего звена получает не только
`quality-checks`, но и перечень находок пройденных гейтов с их статусом: метка без находок не
говорит, чем источник дефектен, и составитель достраивает догадкой. Принято под запись - не то же,
что устранено.

**Трек ведёт два следа с разным охватом, и они не сливаются.** `decision-log` лежит в корпусе фичи,
едет с MR и несёт основания: решения оператора, допущения с исходом, открытые пункты, находки
гейтов с их разрешением - живёт в git и переживает отдельный прогон. `auto-ledger`
([[P-auto-ledger]] в `dex-sdlc:engine`, ключ `TASK`) - история движения **внутри одного прогона**:
трек ведёт его как любой другой, от шага 1 до шага 8 запуска, и следующий прогон того же ключа фичи
его не находит - у него свой `TASK`. Между прогонами трек не хранит ничего вне корпуса: где
остановились, какие фазы закрыты, какие вопросы без ответа - читается сканированием корпуса
(`references/bootstrap-state.md`), а не отдельным файлом состояния.

**`decision-log` пишет трек, и только он.** Составители возвращают строки решений в своём выходе;
трек дописывает их тем же действием, каким закрывает фазу. Правила ведения -
`dex-skill-decision-log:decision-log`, загрузи перед первой записью.

**Единицы нумерует их автор, трек держит только номер фичи.** Младший разряд составитель берёт
инкрементом файла своего ключа в `.req_counter` - отсюда **двух составителей одного класса
параллельно не спавнить** (гонка настоящая); дырки не переиспользуются. **Номер фичи** трек берёт из
счётчика: путь - ключ `counter` из `.docs_layout` в корне репозитория, новой фиче значение плюс
один, файл ключа записывается тем же действием, каким номер выдан; номер пришёл явным полем входа -
счётчик не спрашивай, файл ключа подтяни всё равно. **Путь записан, а файл недостижим** (репозиторий
корпуса не склонирован, закрыт по правам) -> `status: blocked` с указанием, чего не хватает: номер
вслепую не выдавай - он молча столкнёт два набора единиц в одном блоке. Разрядность, сбор счётчика
на занятом проекте, исчерпанный блок, снятая фича и конфликт `.req_counter` при слиянии -
`references/numbering.md`, читать до выдачи номера. Тождество единицы -
`dex-skill-unit-identity:unit-identity`, его же читают составители.

**Режим - из входа (`mode`), дефолт `autonomous`:**

- `interactive` (передан командой `/feature`, канал к оператору ЕСТЬ): остановки - диалог с explicit
  approval, молчание апрувом не считается; невыводимое предъявляется вопросами с вариантами,
  выводимое - списком принятых решений.
- `autonomous` (оператора в петле нет): **полномочную ось закрывает трек, и каждое такое решение
  выводится из уже принятого** - действующего набора требований, записей `decision-log`, внешних
  норм. Без такого основания пункт остаётся открытым. Закрытые так пункты идут **отдельным списком
  в выходе** - что решено, из чего выведено, что было альтернативой, - и каждое пишется в
  `decision-log` с пометкой «принято за оператора», чтобы отличаться от решения человека.

Режим не детектируется по обстановке: он объявлен явно - поле `mode` handoff либо указание
оператора в задаче; нет ни того, ни другого -> `autonomous`.
Режим меняет **способ закрытия** полномочной оси, а не право закрыть её без основания: свободный
выбор запрещён в обоих режимах.

**Составители спавнятся с режимом трека, тем же значением:** вниз едет планка, не канал - в
`interactive` невыводимое возвращается сразу и своим решением не закрывается (`node-contract`,
D.11). Трек артефактов не пишет: иначе он их автор и судить их на гейте уже не вправе
(`node-contract` п.7 раздела B), а другого судьи в зоне требований нет. Запись сверх auto-ledger -
`decision-log`.

## Phases

```
Phase 1: Bootstrap                  [mandatory]   ключ прогона, состояние корпуса, первый прогон или дельта
Phase 2: Цели -> BRD                [conditional] предъявления оператору здесь нет
Phase 3: Сценарии -> UC             [conditional] несценарная ветка объявляется с основанием
Phase 4: Правила и меры -> FR/NFR   [mandatory]   ветка мер идёт параллельно, сценариев не ждёт
Phase 5: Нарезка -> истории с AC    [mandatory]
Phase 6: Проба готовности + приёмка [mandatory]   + ЕДИНСТВЕННАЯ ОСТАНОВКА
Phase 7: Handoff                    [mandatory]
```

## Ключ прогона

**Ключ прогона - имя фичи, и определяется в Bootstrap заново на каждом прогоне.** Вход несёт папку
фичи или явный ключ - берётся он; иначе слаг строится из темы и ищется среди фич корпуса: точное совпадение - продолжение прогона, похожие -
вопрос оператору (`autonomous` - решение трека строкой «принято за оператора»), пусто - фича новая.
**Совпадение фиксируется по корпусу, а не по новой формулировке темы**: слаг принятой фичи берётся
из найденного пути. Построение слага, источники ключа и ветки исхода - `references/run-key.md`.

**Продолжение прогона - то же чтение, каким Bootstrap открывается всегда**
(`references/bootstrap-state.md`): какие артефакты классов уже на диске и их статусы, записи
`quality-checks`, открытые пункты `decision-log`; короткого пути мимо чтения у дельты нет, общая
рамка - `references/ledger-and-recovery.md` движка. Свёртка контекста внутри прогона - `auto-ledger`
(шаг 2 «Возобновления»), не эта процедура.

## Phase 1: Bootstrap

**Goal:** Определить ключ прогона, состояние корпуса и род работы: первый прогон или правка принятого.

**Input (handoff):** контракт стыка - `dex-skill-node-contract:node-contract`. Принимает:
`[blocking]` предмет работы (тема / проработанная идея / путь к чужому документу / правка принятой
единицы / реализованное без постановки - пути области кода, при наличии с черновой формулировкой
автора); `[default-ok]` `mode` (дефолт `autonomous`), `constraints`, `non-goals`, `quality-checks`,
`approve`. Предмет пуст и режим `interactive` -> запросить одним вопросом; пуст и режим
`autonomous` -> бизнес-ось без основания -> `status: blocked`, тему не выдумывать.

**Что установлено до классификации** (состав, источники и терминал каждой ветки -
`references/bootstrap-state.md`, читать оттуда): ключ прогона; расположение корпуса и разрешённые
пути; номер фичи из `.req_counter`; прочитанный `decision-log`; состояние корпуса по классам с
поиском совпадения по ключу тождества; сверка текста единиц с судимой версией `quality-checks`;
форма указателя на судимое. Недоступное называется статусом с причиной, отсутствие места для
записи - `status: blocked`; молча не пропускается ничто.

**Output:** ключ прогона; расположение корпуса; номер фичи с названным источником (сквозное поле
схемы называется так же); классификация входа одним из шести значений с основанием:

- **сырая тема** -> Phase 2 целиком; **проработанная идея** -> Phase 2 без шторма; **чужой готовый
документ** -> разбор на единицы по классам с входной приёмкой, не переписывание; **правка
принятого** -> дельта вместо Phase 2-5; **реализованное без постановки** -> требования по факту
наблюдаемого поведения области и контрактов её границ; **не единица конвейера требований** ->
`status: blocked` с названным основанием, `BR` ради прохождения конвейера не сочиняется.

Признак значения, охват чтения, терминалы веток и запрет подменять «не единицу конвейера» разбором
сырой темы - `references/input-classification.md`: значение по памяти уводит рефакторинг в BRD.

Плюс объём (одна фича / эпик) и `constraints`/`non-goals` из входа.

**Exit criteria:** ключ прогона установлен и назван в Output вместе с основанием (совпадение с
корпусом или новая фича); классификация стоит одним из шести значений с основанием; разрешённые пути
записаны. Классификация «непонятно» не допускается: сомнение между сырой темой и проработанной
идеей -> считать вход сырым. На «не единицу конвейера» это правило не распространяется: она вывод о
том, что требований из входа не выводится, и разбором сырой темы не подменяется.

**Mandatory:** yes

## Дельта-прогон: правка принятой единицы

Вход - правка принятого, в том числе **изменение внешнего основания** (политика, регламент, ADR,
норма среды, на которую единица сослалась видом основания): обход стартует так же, как от правки `BR`.
Порядок - `references/delta-run.md`, читать целиком до правки файлов, по памяти не воспроизводить:
род изменения, обход по трассе, точка остановки оператора, чужая единица, расщепление.

## Phase 2: Цели -> BRD

**Goal:** Получить BRD с нумерованными `BR-NNN` и мерой успеха, покрывающий нужды источника; здесь
набирается материал и закрываются гейты качества.

**Conditional, skip_if:** классификация = «чужой готовый документ» и его приёмка пройдена, либо род
работы - дельта. Приёмка нашла дефект -> фаза не пропускается: дефект закрывается на остановке Phase 6.

**Интервью строится на замыкание, а не на полноту.** Спрашивается только то, без чего смысл фичи не
замыкается, в порядке убывания производных: чью нужду закрывает -> граница фичи -> мера успеха.
Выводимое из сказанного и из корпуса уровня 0 идёт списком принятых решений к остановке Phase 6, не
вопросом. Незамкнутость (цель без меры, граница не названа) добирается вопросом здесь; неполнота
(неразобранный сценарий, характеристика, смежная область) - открытым пунктом, вопросом не
становится. **Нижней границы у числа вопросов нет:** всё замкнуто выводом - остановка идёт без
вопросов; добирать вопросы до «приличного» объёма запрещено. **Замыкание
считается по достижению цели, состав - по MVP:** цель фичи, для которой набор не даёт пути
достижения (ни сценария, ни правила, которым она берётся), - незамкнутость, а не неполнота:
добирается здесь, открытым пунктом не уходит; входит то, без чего `MOE` цели не берётся,
остальное - следующий прогон: MVP раньше полноты.

**Корпус уровня 0 существует - второго BRD не заводится.** BRD продукта один на продукт, его ведёт
зона продукта (трек `dex-skill-product-track:product-track` `[справочно]`). Нашёлся при чтении корпуса
в Bootstrap -> цели фичи трассируются на его `BR-NNN`, а не порождаются заново. Фиче понадобилась
цель уровня продукта (признак: переживает удаление любой одной фичи), новый термин словаря или новый
инвариант -> это правка уровня 0: пункт уходит **возвратом в зону продукта** и ждёт её ответа -
идентификатор заведённой единицы либо отказ с причиной, - а здесь не заводится. Корпуса уровня 0 в
проекте нет -> фаза идёт как описано ниже, и это называется строкой выхода: набор стоит на целях
фичи, продуктового основания под ними нет.

**Output:**

- **Материал источника** - при классификации «реализованное без постановки»: наблюдаемое поведение
  области и результат сверки с черновой формулировкой автора (расхождение - строкой в
  `decision-log`); при сырой теме: разобранные с оператором нужды, цели, акторы, границы
  (`interactive`); в `autonomous` шторм без оператора не имитируется - материал берётся из входа,
  недостающее закрывается выводом из принятого либо остаётся открытым пунктом.
- **BRD** - спавн `dex-business-analyst:business-requirements-analyst` (передать: материал
  источника, `constraints`, расположение корпуса, номер фичи, путь `decision-log`,
  `mode` трека; классификация «реализованное без постановки» -> дополнительно пути области и
  контракты её границ, иначе составитель получит brownfield-задачу без предмета чтения и вернёт
  `blocked`). Выход принимается по `node-contract`: `status`, путь, перечень `BR-NNN` с
  мерой успеха, невыводимое, допущения, `non-goals`, конфликты целей с ценой, `quality-checks`,
  занятые номера, строки решений.
- **Гейт качества - два слоя**: единица (`dex-skill-requirement-quality:requirement-quality` по
  каждому `BR`) и набор (`dex-skill-requirement-set-quality:requirement-set-quality` **самим треком**
  против источника, вместе с нормативом этапа `dex-skill-business-analysis-29148:business-analysis-29148`).
  Записи ставишь ты, `self-check` составителя прогона не заменяет.
- **`decision-log`** - один файл на фичу для всех фаз, путь идёт сквозным полем; несёт находки
  каждого гейта **с их исходом** и строки решений составителей.

Что судит каждый слой, поля записей, терминал незагрузившегося норматива и требование исхода у
находки - `references/gates-and-decision-log.md`.

**Exit criteria:** BRD существует по зафиксированному пути; `status` его шапки взят из перечня
публикационного цикла (значение из словаря исхода узла - `complete`/`partial` - возвращается автору
как нехватка обязательного поля); `integrity-events` в выходе составителя разобрано до приёмки по
существу; `decision-log` создан файлом и несёт находки гейта с исходами плюс строки решений (запись
прозой в ответе трека требования не закрывает - следующая фаза читает файл, а не переписку); записи
`quality-checks` обоих слоёв несут `verdict` и версию текста, по которой судили.

**Апрува здесь нет, и BRD его не получает:** документ выходит со `status: review`, принятые статусы
единицы берут на остановке Phase 6. Невыводимое, всплывшее здесь, копится перечнем к остановке -
кроме случая, когда без ответа не построить следующую фазу: тогда вопрос задаётся здесь и его факт
называется в `decision-log`. `autonomous` - каждое решение с основанием и альтернативой уходит в
список «принято за оператора» и в `decision-log`; основания нет -> пункт открыт, набор не завершён.

**Mandatory:** yes

## Phase 3: Сценарии -> UC

**Goal:** Получить сценарии с ветками: кто, при каких условиях, что происходит и что если не так.

**Conditional, skip_if:** объявлена несценарная ветка - у фичи нет наблюдаемого актором поведения
(миграция, регламент, техдолг). Объявление несёт основание и уходит в `decision-log`: иначе
ветка становится способом пропустить разбор.

**Output:**

- **Сценарии** - спавн `dex-usecase-analyst:usecase-analyst` (передать: путь BRD и перечень
  `BR-NNN`, взятых в разбор, расположение корпуса, номер фичи, `mode` трека; классификация
  «реализованное без постановки» -> дополнительно пути области: без них узел выведет ход сценария
  из целей вместо наблюдаемого поведения). Выход: пути сценариев, `UC-...` с трассой на `BR`, расширения без исхода, строки решений.
- **Гейт качества - два слоя.** Слой единицы: `requirement-quality` по каждому сценарию, норма
  письма `dex-skill-use-cases:use-cases`, оракул `dex-skill-use-case-quality:use-case-quality`,
  норматив состава `dex-skill-use-cases-cockburn:use-cases-cockburn`; три предмета не сводятся и друг
  друга не заменяют - `references/gates-and-decision-log.md`. Слой набора: покрытие ребра `BR -> UC` считает судья, не
  производитель и не потребитель: каждое `BR` раскрыто сценарием, ушло в ветку мер, признано
  несценарным или объявлено вне объёма с основанием; сценарий без `BR` - незаказанный объём. Записи
  `{artifact: usecases, check: ..., verdict, revision}` и `{artifact: requirement-set, ...}`.

**Exit criteria:** каждое `BR` входа имеет явный исход; у каждого расширения либо исход, либо
открытый пункт; записи обоих слоёв проставлены с версией; находки и решения дописаны в
`decision-log`. Безусловной остановки здесь нет; условная - невыводимая находка или полномочная ось.

**Mandatory:** yes

## Phase 4: Правила и меры -> FR/NFR

**Goal:** Получить правила из шагов и расширений сценариев и меры своей веткой от целей и среды; у
каждой единицы назван метод проверки.

**Output:**

- **Свод** - спавн `dex-requirements-analyst:requirements-analyst` (передать: пути сценариев и
  перечень `UC-...` со статусами, путь BRD и `BR-NNN`, ограничения среды, действующие рамки - ADR,
  описание архитектуры - ссылками, расположение корпуса, номер фичи, `quality-checks` **и перечень
  находок пройденных гейтов с их статусом**, `mode` трека). Спавн ветки мер не откладывается до готовности Phase 3. Выход: `FR-NNN`/`NFR-NNN` с
  трассой и методом верификации, покрытие входа, находки стыка, строки решений, занятые номера.
- **Гейт качества - два слоя.** Слой единицы: `requirement-quality`, включая ось «метод проверки
  назван» - не назван, вердикт `unverifiable`. Слой набора: `requirement-set-quality` против
  сценариев и BRD как источников. Вместе с оракулом загрузи норматив этапа
  `dex-skill-system-requirements-29148:system-requirements-29148`: полнота состава свода судится
  против него, не по памяти - отсутствующий раздел без статуса, признак незаполненности при формально
  заполненном разделе и требование без метода верификации суть находки гейта. Сверх
  оракула считается **стык `UC -> FR`**:
  каждый шаг и каждое расширение дали правило либо помечены «без правила» с основанием либо подняты
  открытым пунктом; сценарий, не давший ни одного правила, - находка, а не пройденный стык. Ветки
  сверяются между собой: правило, делающее меру недостижимой, - находка стыка набора, а не дефект
  одной из двух единиц.

Требование, законно не имеющее родителя, записывается единой формой `traced from: none` + вид
основания + пометка «находка гейта, принята»: самодельная формулировка в поле трассы читается нижним
звеном как отсутствие поля, и требование теряется при срезе объёма.

**Exit criteria:** каждый шаг и каждое расширение имеет исход; каждая характеристика чеклиста качеств
дала меру либо объявлена неприменимой с основанием; у каждой единицы назван вид основания и метод
проверки; записи обоих слоёв с версией проставлены; находки и решения - в `decision-log`.

**Mandatory:** yes

## Phase 5: Нарезка -> истории с AC

**Goal:** Нарезать сценарии в истории и получить критерии приёмки: примеры правил, назначенные
проверки применимых мер, названные non-goals.

**Output:**

- **Истории** - спавн `dex-user-story-analyst:user-story-analyst` (передать: пути сценариев с их
  ветками, `FR-NNN` для нарезки, применимые `NFR` перечнем ID с путём свода, `non-goals`,
  расположение корпуса, номер фичи, `quality-checks` **и находки всех пройденных гейтов**,
  `mode` трека). **Критерии рождаются здесь**: черновик берётся с веток сценария, окончательный
  критерий дополняется правилами и мерами. Обратный порядок запрещён: правило, извлечённое из готовых
  критериев задним числом, не несёт ничего сверх учёта и делает историю вторым домом поведения.
- **Гейт качества - два слоя.** Слой единицы: `requirement-quality` по историям. Слой набора:
  `requirement-set-quality` против сценариев и свода как источников плюс **полнота с двух сторон** -
  каждая ветка сценария покрыта хотя бы одним критерием в какой-нибудь истории, и каждое правило
  породило хотя бы один критерий. Непокрытая ветка и правило без примера - находки, а не умолчание.

**Покрытие судится по телу требования, не по наличию метки:** критерии закрывают требование целиком
-> «покрыто»; закрывают до границы известного, остаток ждёт решения -> «покрыто частично» + чего не
хватает, и частичность стоит в самой таблице покрытия. **Требование без единого критерия покрытым не
считается ни при каком обосновании:** метод верификации `Inspection` объясняет, почему критерий не
пишется исполняемым, но исхода не отменяет - такое требование идёт как «покрыто частично» с названным
остатком либо как `non-goal` с основанием. Формулировка вроде «покрыто структурно» выглядит закрытой,
следа не оставляет и снимает требование с контроля молча.

Критерий, выходящий за текст своего правила, метку сохраняет, но помечается расширением с
основанием. **Расширение, вводящее аспект, которого в наборе нет вовсе** (класс угрозы, режим
отказа, свойство качества), в критерии не остаётся: оно поднимается требованием уровня системы -
находка, `FR`/`NFR` дописывается в свод Phase 4, критерий получает метку нового требования. Валидная
метка чужого правила иначе проводит новый аспект в реализацию мимо обоих гейтов.

**Exit criteria:** каждое правило и каждая применимая мера имеют явный исход - покрыты либо
переведены в `non-goals` с основанием; каждая ветка сценария покрыта либо названа находкой; записи
обоих слоёв с версией проставлены; находки и решения - в `decision-log`.

**Mandatory:** yes

## Phase 6: Проба готовности и приёмка набора

**Goal:** Проверить то, ради чего конвейер существует: по набору пишется код без единого вопроса
наружу, - и предъявить оператору результат вместе с остатком.

**Output:**

- **Проба** - спавн `dex-implementer-reader:implementer-reader` сплошным чтением: следа прогона
  (`decision-log`, находки гейтов, прошлый список домыслов) ему не передавать. Запись
  `{artifact: requirement-set, check: implementer-readiness, verdict}` ставит он, не трек.
- **Разбор списка домыслов**: каждый пункт получает исход (возврат в порождающий класс новой
  единицей либо явное «на усмотрение реализации» с основанием) и запись в `decision-log`.
- **Сходимость считаешь ты** по перечням предметов из записей меток соседних ревизий, не по строкам
  и не по `decision-log`. Потолок - две ревизии в `interactive`, три в `autonomous`.

Состав входа пробы, правило «новая единица против дополнения существующей», счёт различимых
предметов и терминалы непродуктивной ревизии - `references/readiness-probe.md`: по памяти механика
счёта воспроизводится с подгонкой.

**ОСТАНОВКА (безусловная, единственная в треке):** приёмка набора целиком - границы и цели из
Phase 2 предъявляются здесь же, вместе со сценариями, правилами, мерами и историями, а результат
пробы - вместе с остатком: хвост разбора входит в ту же пачку, иначе порог достаточности
становится второй остановкой. Форма предъявления: выводимое - списком принятых решений,
невыводимое - вопросом с вариантами и рекомендацией; полномочная ось вопросом всегда. В
`autonomous` остановка закрывается выводом из принятого, и **список «принято за оператора»
предъявляется первым** - он и есть предмет первой встречи с человеком.

**Ответ оператора - вход, а не предмет разбора**; **отказ - третий исход**, не разновидность апрува;
**открытый пункт набор не держит** - незамкнутое закрывается здесь, неполнота едет в следующий
прогон. Конфликтующие ответы, перепрогон после отказа, решение «принять под запись» -
`references/readiness-probe.md`, «Остановка».

**Exit criteria:** проба прогнана и её запись стоит в `quality-checks` (не прогнана - `verdict:
unverifiable` с причиной, не молчание); последняя запись `implementer-readiness` подписана
`implementer-reader` и несёт `passed`; иначе набор идёт на остановку с остатком, и порог берётся
только решением оператора «принять под запись» с перечнем долга, не твоей подписью поверх вердикта
судьи; каждый пункт списка домыслов имеет исход и записан в `decision-log` предметом и местом; убыль
против прошлой ревизии посчитана по предметам обоих перечней, и счёт восстановим по записям метки без
памяти сессии; предъявленное оператору сверено с `decision-log` поимённо - у каждой находки, помеченной
вопросом, есть ответ, у каждой закрытой треком - основание; расхождение закрывается до апрува задать
пропущенное, а не пометкой; статусы единиц подняты до принятых только после апрува.

**Mandatory:** yes

## Phase 7: Handoff

**Goal:** Передать принятый результат так, чтобы зона дизайна приняла его без перепроверки требований.

**Output (handoff):** первым полем `status` (словарь исхода - `node-contract`), затем: путь BRD и
`BR-NNN` с мерой успеха; пути сценариев и `UC-...` с ветками и их исходами; перечень
`FR-NNN`/`NFR-NNN` с видом основания и методом проверки; истории с критериями и метками правил;
покрытие по каждому ребру - `BR -> UC`, `BR/среда -> NFR`, `UC -> FR`, `FR/NFR -> AC` - с явным
исходом у каждой единицы; `non-goals`; `constraints/risks`; расположение корпуса и номер фичи
(сквозные поля); **список решений, принятых за оператора, отдельным перечнем** - что решено, из чего
выведено, что было альтернативой; путь `decision-log`; открытые пункты, если остались; список
домыслов пробы с исходами; `quality-checks` со всеми записями (пришедшие сверху переносятся как
есть; записи слоёв ставишь ты как судья гейтов, запись готовности ставит `implementer-reader`);
`status` каждого артефакта в шапке его документа - `approved` проставляется по исходу приёмки, при
незамкнутом пункте потолок `review` с названной причиной, а открытый пункт неполноты потолка не
опускает. Проверенность отдельным полем не дублируется:
она читается из `quality-checks`. Это вход зоны дизайна; задачи и код здесь не порождаются.
Блоки «Допущения и спорное» и «Задействованы» шага 8 движка накладываются на этот же выход, не
дублируют его отдельным документом.

**Exit criteria:** Output содержит все перечисленные поля; шапка каждого артефакта несёт
проставленный `status`; `status: complete` выдаётся только когда безусловная остановка закрыта и
открытых пунктов нет; иначе `blocked`/`partial` с перечнем незакрытого.

**Mandatory:** yes

## Boundaries

- Не сращивать классы: правило прямо из цели мимо сценария и критерий прямо из цели мимо правила -
  обход звена.
- Не поднимать закрытое из памяти сессии. Развилка ищется в `decision-log` до предъявления оператору
  - и на первом заходе, и после свёртки контекста. Записи нет -> вопрос задаётся заново и
  записывается; запись есть -> она действует, а несогласие оформляется пересмотром, не молчаливым
  новым выбором.
- Не заводить отдельный файл состояния сверх `auto-ledger` и `decision-log` - продолжение прогона
  восстанавливается сканированием корпуса; вторая копия того же факта расходится с ним молча.
- Не решать вне правила режима ни один невыводимый пункт, к какой бы оси он ни относился:
  `interactive` - форму назначает тест на самом пункте: назван отклонённый вариант сопоставимой цены
  -> **вопрос** оператору поштучно; вне артефакта есть общепринятый дефолт, а альтернатива не названа
  либо заведомо хуже -> **допущение** с исходом, подтверждается пачкой; `autonomous` - вывод из
  принятого с записью «принято за оператора». Третьего способа нет, и имя оси способа не меняет:
  пункт, у которого назван отклонённый вариант сопоставимой цены, выбран, а не выведен, и объявление
  «ось инженерная, не бизнесовая» права закрыть его самому не даёт.
- Не подписывать чужую проверку: запись `{check: implementer-readiness}` ставит `implementer-reader`,
  ты её адресат. Подписанная тобой, она при сверке читается как отсутствующая - порог допуска не
  взят; вердикт судьи снимает только новый прогон пробы либо решение оператора «принять под запись».
- Не дочинять чужой документ молча. Дефект - находка оператору либо вывод из принятого с записью;
  правку вносит автор. Полное согласование чужих требований - `dex-requirements-reviewer:requirements-reviewer`.
- Не заходить в зону дизайна и не нарезать задачи/код: выполнимость, архитектура, спека, ADR -
  `dex-architect:architect` `[справочно]` в зоне дизайна.
- Skill-оракул не загрузился -> не останавливаться: гейт по своим знаниям, в Output «гейт N без
  проверки `<skill>`» + `verdict: unverifiable` с причиной - молчанием проверка не закрывается.
