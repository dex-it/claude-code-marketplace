# Followup Track

Цель = закрыть раунд ревью на СВОЁМ MR и довести его до мерджа; код пишем, но только под замечания.
Вход - **треды ревью на моём MR** (URL/ID + `LAST_REVIEW_SHA`) ИЛИ **переход из Development Track**
(ревью пришло на MR, который только что сдан).

**Не путать с «Ревью входящего MR» (`dex-skill-mr-review-track:mr-review-track`).** Там ревью чужого,
read-only, выход = треды. Здесь ревьюют меня: вход - замечания, выход - правки + ответы + чистая
дельта. Роли исполнителей противоположные (`review-planner`/`mr-check-reviewer` против `mr-reviewer`).

**Не путать с Development Track.** Там вход - спека, «готово» = фича реализована. Здесь вход -
список замечаний, «готово» = каждое замечание закрыто и дельта чиста. Реализация новой
функциональности сюда не входит: замечание, требующее фичи сверх MR, - отдельная задача (гейт scope
ниже).

`mode` трек-специфично не меняет: неясности идут тред-вопросом ревьюеру всегда (шаг 2, async), не
блокирующим диалогом с оператором - дефолт движка («Решения и фиксация неуверенности») действует
одинаково в обоих режимах.

## Конвейер

1. **Сбор раунда.** Треды ревью (канал хостинга по `dex-skill-node-contract:node-contract` «Канал
   доступа к хостингу»: native MCP приоритетом, фолбэк `gh`/`glab` по конвенции проекта),
   `LAST_REVIEW_SHA` (на какой ревизии ревьюили), свой diff **с момента ревью** - автор мог уже
   что-то поправить. Ground truth - код в **своей ветке**, не в базовой.
2. **Классификация и верификация.** Каждое замечание - **проверь чтением кода**, валидно ли оно
   **сейчас**: исправленное поздним коммитом отсеивается, устаревшее (ревьюили старую ревизию) -
   тоже. Замечание ревьюера - claim, не факт: правдоподобное замечание разваливается при сверке с
   кодом. Классы: *принять* (баг/риск подтверждён) / *отклонить* (сверка показала - неверно; нужен
   ответ с доводом и `file:line`) / *уже исправлено* (назвать коммит) / *вне scope* (валидно, но не
   про этот MR - отдельная задача + ответ в тред) / *неясно* (замечание допускает два прочтения -
   уточни у ревьюера тредом, не трактуй за него удобным способом). Делегируй `review-planner`.
3. **План правок P0..P3** с blast radius. Замечание не закрывается «перепиской»: либо правка, либо
   мотивированный отказ с доводом. Молчаливое игнорирование треда = провал трека.
4. **Правки теми же профильными узлами.** Тип узла определяет исполнителя как в Development Track:
   код -> coder под стек, тесты -> тест-агент, security-находка -> security-ревьюер (не coder).
   Замечание про поведение - фиксируется тестом red->green, как любой найденный баг; замечание про
   покрытие - добор по осям (happy-path / негатив / краевые / все ветки логики), не «дописал один
   тест». Лечи корень, не текст замечания: ревьюер показал симптом на одной строке - та же ошибка в
   соседних местах чинится тоже, иначе следующий раунд вернёт то же.
5. **Ответы в треды.** На каждое замечание - ответ: что сделал (коммит) либо почему отклонил (довод
   + `file:line`). Отклонение без довода - не отклонение.
6. **Ре-ревью дельты.** Делегируй ре-ревью-агенту дельты (`mr-check-reviewer`), не первичному
   ревьюеру: он смотрит `range-diff` с `LAST_REVIEW_SHA`, статус прежних находок и новые находки
   только в дельте. Саморевью движка его не заменяет - независимый взгляд обязателен. Свежие
   находки -> петля с шага 2 (новый раунд).

**Потолок - 5 раундов, дальше решение по каждой открытой находке.** Счётчик раундов ведётся явно,
иначе шестой неотличим от второго. На шестом петля останавливается, и по каждой открытой находке
выносится решение с обоснованием: `отложено` (причина, владелец, место записи - трекер или тред)
либо `блокирует` (мердж не идёт, названо чего не хватает). Решения идут в выход трека поимённо;
сброс находки молчанием запрещён.

**Ревьюер молчит** (не ответил на довод отклонения, не разъяснил неясное) - не блокируйся: остальные
замечания добиты, вопрос опубликован тредом, статус трека - `partial` с поимённым списком, чего
ждём.

## Гейт scope - ничего сверх замечаний

Правка идёт только под замечание. Заодно-рефакторинг, «причесал по пути», новая функциональность в
этом же diff - scope-creep: раздувает дельту, ломает ре-ревью (`range-diff` тонет в шуме),
привязывает мердж MR к необязательной работе. Увидел по ходу проблему вне замечаний - отдельная
задача, строкой в блок сдачи, не в этот diff.

Исключение: правка обязательна для корректности правки-по-замечанию (чинишь корень, а он в соседнем
файле). Тогда она в scope и называется явной строкой в блоке сдачи, не протаскивается молча.

## Конфликты с базой

Ветка живёт раунд ревью - база успевает уехать. Перед ре-ревью дельты сверься с актуальной
`origin/<target>`; база ушла вперёд - подтяни её и разреши конфликты (`dex-conflict-resolver:conflict-resolver`;
чистое автослияние сохранности не доказывает - после слияния прогони сборку и тесты заново, и сверь,
что оба намерения на месте). Ре-ревью на ветке, которая не собирается с текущей базой, ничего не
доказывает.

## Верификация трека («готово»)

1. Каждое замечание имеет исход из пяти классов: правка (коммит назван) / отказ (довод в треде) /
   уже исправлено (коммит назван) / вне scope (задача заведена) / неясно (вопрос опубликован, ждём -
   трек `partial`, не `complete`). Замечание без исхода = трек не закрыт.
2. Ре-ревью дельты чистое - прежние находки закрыты, новых в дельте нет.
3. Прогон зелёный - сборка/тесты/линт после правок (не «было зелено до»).
4. Scope не расширен - в diff нет ничего сверх замечаний и названных исключений.

## Саморевью трека

Не принято ли слепо замечание, которое сверка с кодом опровергает; не отклонено ли валидное
замечание «из упрямства»; закрыт ли корень, а не строка из треда; не протащена ли лишняя работа мимо
гейта scope; на каждый ли баг из ревью есть тест red->green; нет ли LLM-маркеров в ответах ревьюеру.
