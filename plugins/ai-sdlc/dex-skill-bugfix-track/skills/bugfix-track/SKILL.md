# Bugfix Track

Под-вид `dex-skill-development-track:development-track` `[справочно]`: вход - его Phase 1,
классификация «баг-фикс»; фазы ниже разворачиваются внутри его фаз реализации и возвращают результат
туда же.

**Поднят напрямую, не из development-track** (его нет в стеке треков вызова): подними
`dex-skill-development-track:development-track` и войди через его классификацию - включая голое
поручение «почини баг X».

**Исполнителя red-теста и фикса выбирает трек** по критерию движка («Как выбрать исполнителя»), и
оба идут одному исполнителю: фикс понятен и локализован - трек пишет сам, через явно поднятый скилл
стека, строкой `channel: self` с причиной и именем скилла; иначе Phase 1 и Phase 3 исполняет
профильный coder-узел под стек манифеста (`dex-dotnet-coder:dotnet-coder` `[справочно]`,
`dex-ts-fullstack-coder:ts-fullstack-assistant` `[справочно]`).
**Тип исполнителя порогом не меняется:** поиск первопричины сверх очевидного ведёт
`dex-debugger:debugger`, не coder; добор тестов сверх red-теста - tester-узел; фазы и их Exit
criteria от выбора исполнителя не меняются. Работой трека остаются воспроизведение, оракул
дефекта, приёмка первопричины и регресс-проход (`channel: self`).

**Возобновление.** Свёртка внутри прогона - «Возобновление» движка по auto-ledger; новый прогон
ledger не находит, порядок для него - «Восстановление между прогонами»
(`references/ledger-and-recovery.md` движка). Носители состояния этой зоны: падающий red-тест и
коммиты в ветке - состояние фикса читается прогоном тестов, не памятью.

**Свой `mode` под-вид не принимает:** режим (`interactive`/`autonomous`) наследуется от вызвавшего
Development Track. Он меняет адресата возврата там, где фаза упирается (Phase 0 - дефект не
воспроизвёлся, Phase 2 - корень не дался), не право пропустить фазу. В делегированные вызовы
(Phase 2 - `dex-debugger:debugger`, Phase 3 - coder-узел) едет тем же значением: узлу - планка
эскалации, канал к оператору остаётся у трека (`node-contract`, D.11).

## Обзор фаз

| # | Фаза | Кто исполняет |
|---|---|---|
| 0 | Reproduce | трек (сам) |
| 1 | Red Test | исполнитель по критерию шапки, трек принимает |
| 2 | Root Cause | трек (сам) либо `dex-debugger:debugger` |
| 3 | Minimal Fix | исполнитель по критерию шапки |
| 4 | Green & Regression | трек (сам) + tester-узел на добор класса |

## Phase 0: Reproduce

Goal: наблюдать дефект своими глазами до любой правки.

**Input (handoff):** контракт стыка - `dex-skill-node-contract:node-contract`. `[blocking]` симптом:
что наблюдается и где (тикет, баг-репорт, «падает вот тут»); симптома нет вовсе -> возврат в
Development Track статусом `blocked`. `[default-ok]` ожидаемое поведение (не пришло -
реконструируется из требований, кода и конвенций и идёт в выход допущением с источником вывода, не
молча), способ воспроизведения, ветка и стек (не пришли - по git и манифесту), расположение
аналитического корпуса (сквозное поле), `quality-checks`.

Output: минимальные шаги воспроизведения (вход, окружение, наблюдаемый результат), ожидаемое
поведение с источником (требование из корпуса, конвенция, реконструкция-допущение).
Exit criteria: дефект воспроизведён и наблюдение зафиксировано (команда + вывод, лог, трейс), либо
воспроизвести не удалось - тогда `interactive` спроси у оператора условия, `autonomous` верни
`status: blocked` в Development Track с перечнем испробованного.

Mandatory: yes

## Phase 1: Red Test

Goal: закрепить дефект тестом через реальный путь.
Output: тест, падающий на текущем коде по той же причине, что и дефект; путь и имя теста названы.
Exit criteria: тест red до фикса, и его падение вызвано дефектом, а не суррогатом (подменённый
внутренний метод, ассерт на промежуточном состоянии, мок того самого узла, где живёт дефект). Тест
red по другой причине - переписать, не принимать.

Mandatory: yes

## Phase 2: Root Cause

Goal: дойти до первопричины, а не до строки из репорта.
Output: цепочка «симптом -> механизм -> первопричина» с уликой на каждое звено (`file:line`, лог,
трейс); класс дефекта назван (гонка, неинициализированное состояние, потерянная ветка, контракт
разъехался и т.п.).
Сложнее очевидного - делегируй `dex-debugger:debugger`; его вывод - гипотеза, перепроверь
первоисточником до фикса.

**Гейт первопричины.** Корень не дался за 2-3 подхода - фаза не закрывается симптоматической
правкой: `interactive` - предъяви оператору, что известно и чего не хватает; `autonomous` -
`status: blocked` в Development Track. Обходной путь - только с заведённым тикетом на корень,
названным в выходе.

Mandatory: yes

## Phase 3: Minimal Fix

Goal: устранить первопричину минимальной правкой.
Output: правка от выбранного исполнителя; перечень затронутых файлов; всё, что было замечено рядом
и не входит в фикс, - отдельным перечнем наблюдений.
Exit criteria: правка лечит звено первопричины Phase 2, а не звено симптома; в diff нет ничего сверх
фикса и его теста. Смешанное «почини и заодно причеши» разделяется на баг-фикс и рефакторинг, не
один diff.

Mandatory: yes

## Phase 4: Green & Regression

Goal: подтвердить фикс и проверить, что дыра того же класса не живёт по соседству.
Output: red-тест Phase 1 зелёный; полный прогон build/test; регресс-проход - поиск того же класса
дефекта в соседних местах (`dex-skill-completeness-mapping:completeness-mapping` для потребителей
затронутого контракта), исход по каждому найденному месту: закрыто тем же фиксом | отдельный тикет |
не применимо с причиной. Добор тестов сверх red-теста - tester-узел под стек, не трек.
Exit criteria: red-тест green, полный прогон зелёный либо провал назван явно, регресс-проход проведён
и его результат назван поимённо.

Mandatory: yes

## «Разберись и почини» - это Разработка

Диагностический запрос без отдельного тикета на баг - Разработка (под-вид баг-фикс): разбор «что и
почему» идёт по Phase 0-2 выше, отдельного аналитического артефакта нет.

## Выход под-вида (handoff)

**Output:** первым полем `status` (словарь исхода - `node-contract`), затем: путь и имя red-теста;
цепочка первопричины с уликами; перечень коммитов фикса (sha + суть); `run-status` полного прогона;
результат регресс-прохода поимённо; отложенное с номером тикета и владельцем; допущения (в том числе
реконструированное ожидаемое поведение) с источником вывода; решения, принятые за оператора,
отдельным перечнем; сквозные поля входа как есть.

**Exit criteria:** Output несёт все перечисленные поля; `complete` выдаётся только при зелёном
red-тесте, зелёном полном прогоне и проведённом регресс-проходе; иначе `partial`/`blocked` с
перечнем незакрытого.

**Mandatory:** yes

## Boundaries

- Под-вид заканчивается на коммитах фикса: push, MR и мердж ведёт Development Track, сюда они не
  переносятся.
- Предмет - исходник. Работающий стенд или дамп ведёт
  `dex-skill-diagnostics-track:diagnostics-track` `[справочно]`, сюда возвращаются с первопричиной.
