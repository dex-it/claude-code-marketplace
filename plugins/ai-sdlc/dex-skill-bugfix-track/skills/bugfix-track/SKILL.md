# Bugfix Track

Под-вид `dex-skill-development-track:development-track` (Phase 1, классификация «баг-фикс»), не
отдельный аналитический трек и не отдельный вход движка - своей команды нет (`/fix` не создаётся).
Development-track переключает на этот файл при классификации, а не заводит параллельный маршрут.
Свой `mode` не принимает: режим (`interactive`/`autonomous`) наследуется от вызвавшего Development
Track - отдельного входа с этим полем здесь нет, потому что нет отдельной команды.

## Процедура

Воспроизведи дефект -> **тест red через реальный путь** (не суррогат) -> **root-cause до
первопричины** (сложнее очевидного - делегируй `dex-debugger:debugger`, не гадай сам; лечи корень,
не строку из репорта) -> **минимальный** фикс -> green -> регресс-проход. Корень не дался за 2-3
подхода -> блокер; обходной путь - только с заведённым тикетом, не молчаливая замена фикса.

## «Разберись и почини» - это Разработка

Диагностический запрос без отдельного тикета на баг - это Разработка (под-вид баг-фикс), не
отдельный аналитический трек. Автономный разбор «что и почему» - фаза context/root-cause внутри
баг-фикса: вывод `dex-debugger:debugger` остаётся гипотезой, перепроверь первоисточником сам, веди
фикс дальше по процедуре выше. Отдельного аналитического артефакта нет - выход - MR + тест
red->green.

## Boundaries

- Тест-DoD - тест, воспроизводящий дефект, обязателен; фикс без red-теста до правки не считается
  диагностированным.
- Смешанное «почини и заодно причеши» - раздели на баг-фикс и рефакторинг, не один diff.
- Регресс-проход после green обязателен - иначе фикс закрывает симптом, не подтверждает отсутствие
  соседних дыр того же класса.
