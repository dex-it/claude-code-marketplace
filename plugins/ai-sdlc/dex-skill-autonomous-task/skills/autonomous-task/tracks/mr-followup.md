# Трек «Обработка ревью своего MR» - дельта сверх таблицы

> Дополнение к строке «Обработка ревью своего MR» таблицы треков в `SKILL.md`. Ядро читает этот
> файл, определив трек (mandatory-Read из шага 1) - до плана. Якоря `P-*`/`I-*` - в костяке
> `SKILL.md`, который в контексте всегда. Файлы других треков не читаются: всё нужное этому
> треку - здесь.

*Цель = закрыть раунд ревью на СВОЁМ MR и довести его до мерджа; код пишем, но только под
замечания.* Вход - **треды ревью на моём MR** (URL/ID + `LAST_REVIEW_SHA`) ИЛИ **переход из
«Разработки»** (ревью пришло на MR, который я только что сдал).

**Не путать с «Ревью входящего MR».** Там я ревьюю чужое, read-only, выход = треды. Здесь
ревьюют меня: вход - замечания, выход - правки + ответы + чистая дельта. Роли исполнителей
противоположные (`review-planner`/`mr-check-reviewer` против `mr-reviewer`).

**Не путать с «Разработкой».** Там вход - спека, «готово» = фича реализована. Здесь вход -
список замечаний, «готово» = каждое замечание закрыто и дельта чиста. Реализация новой
функциональности сюда не входит: замечание, требующее фичи сверх MR, - отдельная задача
(см. гейт scope ниже).

## Конвейер

1. **Сбор раунда.** Треды ревью (канал хостинга по node-contract «Канал доступа к хостингу»:
   native MCP приоритетом, фолбэк `gh`/`glab` по конвенции проекта), `LAST_REVIEW_SHA` (на какой
   ревизии ревьюили), свой diff **с момента ревью** - автор мог уже что-то поправить.
   Ground truth - код в **своей ветке** ([[P-branch]]), не в `develop`.
2. **Классификация и верификация.** Каждое замечание - **проверь чтением кода**, валидно ли
   оно **сейчас**: исправленное поздним коммитом отсеивается, устаревшее (ревьюили старую
   ревизию) - тоже. Замечание ревьюера - **claim, не факт** ([[P-recon]]): правдоподобное
   замечание разваливается при сверке с кодом. Классы: *принять* (баг/риск подтверждён) /
   *отклонить* (сверка показала - неверно; нужен ответ с доводом и `file:line`) /
   *уже исправлено* (назвать коммит) / *вне scope* (валидно, но не про этот MR - отдельная
   задача + ответ в тред) / *неясно* (замечание допускает два прочтения - **уточни у ревьюера
   тредом**, не трактуй за него удобным способом). Делегируй `review-planner` (тип узла - план
   правок по ревью).
3. **План правок P0..P3** с blast radius. Замечание не закрывается «перепиской»: либо правка,
   либо мотивированный отказ с доводом. Молчаливое игнорирование треда = провал трека.
4. **Правки теми же профильными.** Тип узла определяет исполнителя как в «Разработке»: код ->
   coder под стек, тесты -> тест-агент, security-находка -> security-ревьюер (не coder).
   **Замечание про поведение - фиксируется тестом red->green**, как любой найденный баг
   (`SKILL.md`, универсальные принципы); замечание про покрытие - добор по осям (happy-path /
   негатив / краевые / все ветки логики), не «дописал один тест».
   **Лечи корень, не текст замечания** ([[P-root]]): ревьюер показал симптом на одной строке -
   та же ошибка в соседних местах чинится тоже, иначе следующий раунд вернёт то же.
5. **Ответы в треды.** На каждое замечание - ответ: что сделал (коммит) либо почему отклонил
   (довод + `file:line`). Отклонение без довода - не отклонение.
6. **Ре-ревью дельты.** Делегируй **ре-ревью-агенту дельты** (`mr-check-reviewer`), не
   первичному ревьюеру: он смотрит `range-diff` с `LAST_REVIEW_SHA`, статус прежних находок и новые
   находки **только в дельте**. Саморевью (шаг 7 костяка) его **не заменяет** - независимый
   взгляд обязателен. Свежие находки -> петля с шага 2 (новый раунд), пока дельта не чиста.

**Ревьюер молчит** (не ответил на довод отклонения, не разъяснил *неясное*) - **не блокируйся**:
остальные замечания добиты, вопрос опубликован тредом, статус трека - `partial` с поимённым
списком, чего ждём. Бесконечное ожидание = провал; но и молча трактовать неясное за ревьюера
нельзя - висит явным пунктом, не растворяется.

## Гейт scope - ничего сверх замечаний

**Правка идёт только под замечание.** Заодно-рефакторинг, «причесал по пути», новая
функциональность в этом же diff - **scope-creep**: раздувает дельту, ломает ре-ревью
(`range-diff` тонет в шуме), привязывает мердж MR к необязательной работе. Увидел по ходу
проблему вне замечаний - **отдельная задача**, строкой в блок сдачи, не в этот diff.

Исключение: правка **обязательна для корректности** правки-по-замечанию (чинишь корень, а он
в соседнем файле - [[P-root]]). Тогда она в scope и **называется явной строкой** в блоке
сдачи, не протаскивается молча.

## Конфликты с базой

Ветка живёт раунд ревью - **база успевает уехать**. Перед ре-ревью дельты (шаг 6) сверься с
актуальной `origin/<target>` ([[P-branch]]); база ушла вперёд - **подтяни её и разреши
конфликты** (тип узла - интегратор веток, `conflict-resolver`; чистое автослияние сохранности
не доказывает - после слияния прогони сборку и тесты заново, и сверь, что оба намерения на
месте). Ре-ревью на ветке, которая не собирается с текущей базой, ничего не доказывает.

## Верификация трека («готово»)

1. **Каждое замечание** имеет исход из пяти классов (шаг 2): правка (коммит назван) / отказ
   (довод в треде) / уже исправлено (коммит назван) / вне scope (задача заведена) / неясно
   (вопрос опубликован, ждём - трек `partial`, не `complete`). Замечание без исхода = трек не
   закрыт; «вроде обсудили» исходом не считается.
2. **Ре-ревью дельты чистое** - прежние находки закрыты, новых в дельте нет.
3. **Прогон зелёный** - сборка/тесты/линт после правок (не «было зелено до»).
4. **Scope не расширен** - в diff нет ничего сверх замечаний и названных исключений.

## Саморевью трека

Не принято ли слепо замечание, которое сверка с кодом опровергает; не отклонено ли валидное
замечание «из упрямства»; закрыт ли **корень**, а не строка из треда; не протащена ли лишняя
работа мимо гейта scope; на каждый ли баг из ревью есть тест red->green; нет ли LLM-маркеров в
ответах ревьюеру.
