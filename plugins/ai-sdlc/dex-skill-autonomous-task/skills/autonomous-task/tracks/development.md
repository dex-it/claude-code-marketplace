# Трек «Разработка» - дельта сверх таблицы

> Дополнение к строке «Разработка» таблицы треков в `SKILL.md`. Ядро читает этот файл, определив
> трек «Разработка» (mandatory-Read из шага 1 цикла) - **до плана**. Слоты (выполнение/верификация/
> артефакт) - в таблице ядра; план/ревью/сдача и якоря `P-*`/`I-*` - в костяке `SKILL.md`, который
> в контексте всегда. Норму соседнего трека сюда не тянем: всё нужное этому треку - здесь. Чужой
> файл читается в одном случае - при смене трека (ниже).

Под-вид определи **до плана** (критерий «готово» и роль тестов спутать нельзя):

- **фича** - новое поведение, тесты под него (TDD). **Тест-DoD
  фичи = матрица покрытия (+) дельта трека (все пункты, не подмножество):** оси
  happy / негатив / краевые / все ветки **через реальный путь**, прогнанные
  **живьём до внешней границы** (граница интеграции - ниже), плюс **регрессия потребителей** -
  тесты задетых вызывающих, стык не сломан. Покрыто меньше - фича НЕ готова; отрезанный
  пункт - строкой в блок сдачи с обоснованием, не молчанием.
- **баг-фикс** - тесты воспроизводят дефект;
- **рефакторинг** - поведение НЕ меняется; тесты - сейфти-нет, зелёные без правки ассертов.

Смешанное «почини и заодно причеши» -> раздели на под-виды, не в один diff.

**Дизайн по ходу фичи остаётся здесь.** Инженерные развилки инкремента (контракт метода, границы
модуля, паттерн под задачу) решаются внутри трека до плана, самостоятельно с обоснованием
([[I-decide]]) - это не повод уходить из «Разработки».

**Pre-check «нужен ли ADR» - до плана.** Сначала найди действующие ADR - расположение по
`dex-skill-project-docs-map` (пути - `.docs_layout` в корне репозитория, файла нет -> поиск по стандартным
местам); недостижимы -> `unverifiable` + причина в блок сдачи, не «ADR нет». Затем порог,
операциональный - вводится ли правило, не «значимость на глаз»: применить существующее -> план +
ссылка на действующий ADR; ввести новое правило/паттерн -> ADR в той же ветке до плана. Новый паттерн, заведённый молча, становится
прецедентом для всего проекта мимо ревью.

**Работа без спеки и без формальных требований - штатный режим**, а не дефект входа: требования
восстанавливаешь из тикета, кода и конвенций (R/I), неочевидное фиксируешь допущением в блоке
сдачи. **Просят дизайн-документ самим результатом** (спроектировать сервис/модуль/API до
реализации) - собирай черновик из кода и конвенций и возвращай `status: partial` с перечнем
незакрытых развилок и указанием зоны 2 (`/design`), где он доводится с оператором; `complete` не
выдавай - несогласованный дизайн не артефакт зоны 2.
**Саморевью - 3 обязательных прохода** (не один): (1) код под стек, (2) архитектура
(слои/контракты/зависимости/NFR), (3) **security** (auth, доступ, данные, ввод, секреты) -
security **отдельный проход даже если «чисто»**, не растворять в ревью кода; + доменные по
нужде (перф, миграции, API-контракт).

**Пирамида: тестируй ВСЕ узлы цепочки, не один лист.** Декомпозиция
на модули -> unit на КАЖДЫЙ модуль -> сборка (tsc/контракты) -> **интеграционный прогон всего
пути живьём**. Unit изолированного модуля **не закрывает фичу**: баг живёт на *стыке* модулей
и на границе с чужой системой. **Граница интеграции = там, где наш код отдаёт управление
внешней системе** (внешний API, БД, очередь, чужой сервис) - мок этой границы **врёт о
контракте** (мок принял `mediaType:"image"` - реальный Google API отверг 400; unit был
зелёным, прод падал). Поэтому: (а) **до** написания тестов **выясни и зафиксируй точку входа**
- кто и как реально вызывает фичу в проде (не угадывай сигнатуру по ходу); (б) для
LLM/внешних-API/IO обязателен **живой прогон реального пути** до самой границы, не только
unit-форма того, что мы отправляем; (в) если у пути есть **развилки** (primary/fallback
провайдер, retry-ветка, разные адаптеры) - прогнать **каждую** ветку: это разные получатели
с разными контрактами (два провайдера у LLM-приложения - частный случай). Зелёный unit при
непокрытой интеграции = **фича не проверена**, даже если «тесты зелены».

- **баг-фикс:** воспроизведи дефект -> **тест red через реальный путь** (не суррогат) ->
  **root-cause до первопричины** (делегируй; лечи корень - [[P-root]]) -> **минимальный**
  фикс -> green -> регресс-проход. Корень не дался за 2-3 подхода -> блокер; обходной путь -
  только с заведённым тикетом.
- **рефакторинг** *(инвариант: внешнее поведение неизменно)*: **сначала сейфти-нет** (нет
  покрытия - допиши тесты на поведение как есть) -> структурные правки **малыми шагами**,
  после каждого тесты зелёные **без изменения ассертов** (поменял ассерт - это уже не
  рефакторинг, стоп) -> «готово»: тот же contract/API/выход, структура и читаемость лучше,
  мёртвый код удалён. Саморевью: арх-проход главный, security если трогались границы. Баг
  по пути - **отдельная цель**, не правь молча.

**Пришло внешнее ревью на твой MR -> это отдельный трек** «Обработка ревью своего MR»: другой вход
(список замечаний, не спека) и другое «готово» (каждое замечание закрыто, дельта чиста). Переключи
трек и прочитай его дельту - файл и путь по карте шага 1 костяка. Разбор замечаний, ответы в треды
и ре-ревью дельты нормированы там, здесь их нет.

## Интеграция с базой - слот перед сдачей

Ветка живёт дольше пары дней - **база уехала**. Перед сдачей (шаг 8 костяка: MR/коммит)
сверься с актуальной `origin/<target>` ([[P-branch]]): база ушла вперёд -> **подтяни её в свою
ветку и разреши конфликты** до оформления MR. Пропуск слота ловится не тобой, а ревьюером или
CI - и возвращает работу назад.

Главный враг - **не маркеры конфликта, а тихая потеря**: автослияние прошло чисто, маркеров
нет, а сторона (твоя или базы) молча выпала. **Чистое автослияние сохранности не доказывает** -
после слияния прогони сборку и тесты **заново** (зелёные до слияния ничего не говорят о после)
и сверь, что оба намерения на месте.

Слот **делегируется** (тип узла - интегратор/разрешение конфликтов, `conflict-resolver`), не
делается «на глаз» руками. Конфликт разрешён сведением **обоих** намерений; выбор «взять свою
сторону целиком» / «взять базу целиком» - решение, а не дефолт: обоснуй строкой в блоке сдачи.

**«Разберись и почини» - это «Разработка» (баг-фикс), не отдельный аналитический трек.**
Автономный разбор «что и почему» - **фаза контекста/root-cause внутри баг-фикса**: делегируй
аналитическим/диагностическим агентам, забери вывод как гипотезу, **перепроверь первоисточником
сам** ([[P-recon]]), веди фикс по треку. Отдельного аналитического артефакта нет - выход баг-фикса
(MR + тест red->green).

**Добор покрытия ведётся по тем же осям и профильным исполнителем.** TDD red->green (тесты ведут
код) - встроенная механика «Разработки»; добор сверх него - делегируй тест-агенту под стек, веди
матрицу осей (выше), назови оставшиеся gap'ы строкой в блоке сдачи без тихого усечения. Своей
тестовой механики трек не изобретает.
