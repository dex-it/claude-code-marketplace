# Product Track

Трек зоны продукта: ведёт прогон «стороны и границы -> цели с мерой -> язык -> инварианты и сквозные
меры» до принятого **корпуса уровня 0**. Артефакты пишут составители-субагенты
(`dex-business-analyst:business-requirements-analyst` -> BRD продукта с `BR-NNN`,
`dex-domain-analyst:domain-analyst` -> доменная модель и конституция; `subagent_type` резолвится
только полной формой `{плагин}:{агент}`, голое имя даёт `Agent type not found`). Трек классифицирует
вход, спавнит их, судит корпус целиком, ведёт следы и собирает единственную остановку оператора.
**Поднят напрямую, без движка** - подними `dex-sdlc:engine`, войди через шаг 1: без него нет
auto-ledger, стоп-линии, режима.

**Уровень 0 - то, что верно для продукта целиком.** Уровни: 0 - продукт, 1 - фича, 2 - реализация,
3 - код и тесты; это единственный ряд, который нумеруется (зоны называются именем предмета).
Признак принадлежности единицы к уровню 0 проверяемый: **она переживает удаление любой одной фичи**.
Цель, которая исчезает вместе с фичей, - цель фичи, и её место в зоне требований.

**Корпус уровня 0 - один на продукт.** BRD продукта один (по ключу `product`), словарь
один, конституция одна. Зона требований второго продуктового BRD не заводит: её документ - BRD фичи
в дереве фичи, и цели фичи трассируются на `BR-NNN` продукта, когда подходящая цель здесь найдена
(не найдена -> трасса не ставится, факт называется строкой выхода узла требований).
Фича, которой нужна новая цель уровня продукта, новый термин или новый
инвариант, - это **правка уровня 0**, и она идёт сюда возвратом (раздел «Дельта-прогон»), а не
заводится в корпусе фичи. Второй документ того же класса рядом с принятым - не расширение, а
расхождение: две редакции одной нормы живут молча, и ни одна не становится ложной.

**Режим - из входа (`mode`), дефолт `autonomous`:**

- `interactive` (передан командой `/product`, канал к оператору ЕСТЬ): остановки - диалог с explicit
  approval; невыводимое предъявляется вопросами с вариантами и рекомендацией, выводимое - списком
  принятых решений. Молчание апрувом не считается.
- `autonomous` (спавн узлом, канала НЕТ): **полномочную ось закрывает трек, и каждое такое решение
  выводится из уже принятого** - действующего корпуса, записей `decision-log`, внешних норм. Без
  такого основания пункт остаётся открытым. Закрытые так пункты идут отдельным списком в выходе и
  пишутся в `decision-log` с пометкой «принято за оператора»: это предмет первой же встречи с
  оператором.

Режим не детектируется по обстановке - он объявлен входом; нет поля `mode` -> `autonomous`.

**Полномочная ось здесь - норма зоны, а не исключение.** Ось - предмет решения, по которому
возможны разные исходы с разной ценой; полномочная - та, где цена ошибки лежит вне артефакта.
Уровень 0 состоит из таких осей почти целиком: кому служит продукт, что вне охвата, каким именем
называется сущность, что считается инвариантом. Поэтому остановка безусловна, и в `autonomous` трек
закрывает её только выводом из принятого - свободный выбор запрещён в обоих режимах.

**Составители - autonomous-субагенты.** Спавн через `Agent` канала к оператору не даёт; составитель
невыводимое возвращает в своём выходе, а трек адресует его оператору (`interactive`) либо закрывает
выводом из принятого (`autonomous`). **Трек сам артефактов не пишет** - написав артефакт, он
становится его автором и теряет право судить его на гейте (`node-contract` п.7 раздела B). Запись
сверх auto-ledger - `decision-log`.

**Номер фичи в единицах уровня 0 не выдаётся.** `BR` продукта, `INV` и `NFR-P` принадлежат продукту:
их ключи в `.req_counter` идут без старшего разряда фичи. Составителю это передаётся полем
`level: product` - без него он возьмёт номер фичи из счётчика и заведёт фиктивную фичу под
продуктовый документ. Счётчик недостижим -> `status: blocked`, номер вслепую не выдаётся.

**Возобновление и продолжение прогона.** Свёртка контекста внутри прогона - «Возобновление» движка
(`dex-sdlc:engine`) по auto-ledger. Новый прогон по тому же предмету ledger не находит: состояние
читается от намерения (тикет, спека, план, `decision-log`) и от того, что фактически лежит - рамка в
`references/ledger-and-recovery.md` движка, раздел «Восстановление между прогонами». Носитель
состояния этой зоны: принятый корпус уровня 0 на диске (BRD продукта, доменная модель, конституция)
вместе с их записями `quality-checks` и открытыми пунктами `decision-log` - «Состояние корпуса»
Bootstrap читает его на каждом прогоне. Не восстановилось ни одним носителем - строка в сдаче, не
догадка.

## Phases

```
Phase 1: Bootstrap                          [mandatory]   расположение корпуса, род работы: первый прогон или дельта
Phase 2: Стороны и границы -> BRD продукта  [conditional] предъявления оператору здесь нет
Phase 3: Язык -> доменная модель            [mandatory]   расхождения имён сводятся решением, не молча
Phase 4: Инварианты и меры -> конституция   [mandatory]   каждая единица с основанием и методом проверки
Phase 5: Приёмка корпуса уровня 0           [mandatory]   + ЕДИНСТВЕННАЯ ОСТАНОВКА
Phase 6: Handoff                            [mandatory]
```

## Phase 1: Bootstrap

**Goal:** Установить расположение корпуса уровня 0, его состояние и род работы - первый прогон или
правка принятого.

**Input (handoff):** контракт стыка - `dex-skill-node-contract:node-contract`. Принимает:
`[blocking]` предмет работы (продукт/идея продукта, чужой документ путём, либо названная правка
принятой единицы); `[default-ok]` `mode` (дефолт `autonomous`), `constraints`, `non-goals`,
`quality-checks`, `approve`. Предмет пуст и режим `interactive` -> запросить одним вопросом; пуст и
`autonomous` -> бизнес-ось без основания -> `status: blocked`, продукт за автора не выдумывать.

**Что установлено до классификации:**

- **Расположение корпуса - ключи `product` и `domain` в `.docs_layout`** (`product` - BRD продукта,
  `domain` - словарь и конституция). Пришло сквозным полем - берётся как есть. Не пришло ->
  `dex-skill-project-docs-map:project-docs-map`: ключи есть - пути берутся оттуда; ключей нет ->
  уровень 0 в проекте не заведён, пути ищутся ступенями скилла (артефакт класса уже лежит -> каталог
  и форма имени с образца; образца нет -> дерево норматива раскладки
  `dex-skill-docs-layout:docs-layout`, границу его применения держит
  `dex-skill-artifact-naming:artifact-naming`), и **ключи
  записываются в `.docs_layout` тем же заходом** - записать их обязан ты, узлы `Bash` не несут и
  корень репозитория не определяют. Факт записи - строка выхода: что записано и на каком основании
  найдено. Разрешённые пути едут сквозными полями дальше, чтобы узлы не разрешали их заново.
- **Состояние корпуса:** какие из трёх артефактов уже на диске, их `status`, записи
  `quality-checks`, открытые пункты `decision-log`. Отдельного файла состояния трек не ведёт -
  продолжение читается из корпуса.
- **Род работы.** Ни одного артефакта класса нет -> первый прогон. Есть принятый и вход называет
  правку - дельта (раздел ниже). Есть принятый, а вход сформулирован как новая тема продукта ->
  это не второй корпус: тема разбирается как правка принятого, и расхождение с ним называется
  находкой, а не поводом завести вторую редакцию.

**Exit criteria:** Пути всех трёх артефактов разрешены и названы; состояние каждого установлено
чтением диска, а не предположением; род работы объявлен строкой. Записать некуда вовсе (ни одна
ступень не дала места) -> `status: blocked` с указанием непрошедшей ступени.

**Mandatory:** yes - работа над вторым экземпляром принятого корпуса неотличима от работы над первым,
пока диск не прочитан.

## Phase 2: Стороны и границы -> BRD продукта

**Goal:** Получить BRD продукта: кому служит, что считается успехом с мерой `MOE`, что вне охвата,
что нельзя ухудшить ради целей. Апрува оператора фаза не собирает - он один на корпус и берётся в
Phase 5; здесь набирается материал и закрываются гейты качества.

**Conditional, skip_if:** BRD продукта принят (`status: approved`, записи гейтов на месте) и род
работы не затрагивает его единиц. Затрагивает - фаза идёт по дельте, не пропускается.

**Output:**

- **Материал источника** - при сырой идее: разобранные с оператором стороны, их нужды, границы
  (`interactive`); в `autonomous` шторм без оператора не имитируется - материал берётся из входа и
  из корпуса, недостающее закрывается выводом из принятого либо остаётся открытым пунктом.
- **Интервью строится на замыкание, а не на полноту.** Спрашивается только то, без чего смысл не
  замыкается, и в порядке убывания производных: сторона и её нужда -> граница охвата -> мера
  успеха -> что нельзя ухудшить. Выводимое из уже сказанного не спрашивается, а идёт в список
  принятых решений к остановке Phase 5. Незамкнутость и неполнота разведены: цель без `MOE`, термин
  без дома, инвариант без метода проверки, пустой `non-goals` без решения - незамкнутость, она
  добирается вопросом здесь; неназванная фича, характеристика или деталь - неполнота, она идёт
  открытым пунктом в следующий прогон и вопросом не становится. Иначе интервью растёт по объёму
  продукта, а первая фича не стартует, пока описан не весь. **Нижней границы у числа вопросов нет:**
  всё замкнуто выводом из сказанного -> остановка идёт без единого вопроса, и это лучший исход, а не
  недоработанное интервью; добирать вопросы до «приличного» объёма запрещено.
- **Замыкание считается по достижению цели, а состав - по MVP.** Цель, `MOE` которой принятым
  составом не берётся (из корпуса не видно, чем она достигается), - незамкнутость: добирается здесь
  и открытым пунктом не уходит. В состав входит то, без чего `MOE` названной цели не берётся;
  остальное - следующий прогон (`BR-011`).
- **BRD продукта** - спавн `dex-business-analyst:business-requirements-analyst` (передать: материал
  источника, `constraints`, расположение корпуса, **`level: product`**, путь `decision-log`,
  `mode: autonomous`). Выход принимается по `node-contract`.
- **Гейт качества - два слоя.** Слой единицы: `dex-skill-requirement-quality:requirement-quality` по
  каждому `BR`, запись `{artifact: BRD, check: requirement-quality, verdict, revision}` ставишь ты -
  `self-check` составителя её не заменяет. Слой набора:
  `dex-skill-requirement-set-quality:requirement-set-quality` самим треком против источника - полнота
  множества составителю не видна. Вместе с оракулом загрузи норматив этапа
  `dex-skill-business-analysis-29148:business-analysis-29148`; не загрузился -> `verdict: unverifiable` по этой
  оси с причиной.
- **`decision-log`** - один файл на корпус уровня 0, путь разрешается в Phase 1 и едет сквозным
  полем. Несёт находки каждого гейта **с их исходом** и строки решений составителей. Находка,
  записанная без исхода, гейт не закрывает.

**Exit criteria:** BRD существует по зафиксированному пути; `status` его шапки взят из перечня
публикационного цикла; каждое `BR` несёт `MOE`; перечень `non-goals` не пуст **или** его пустота
объявлена решением с основанием (продукт без границ - не описанный продукт, а неразобранный);
`decision-log` создан файлом и несёт находки гейта с исходами (запись прозой в ответе трека
требования не закрывает - следующая фаза читает файл); записи `quality-checks` обоих слоёв несут
`verdict` и ревизию текста, по которой судили.

**Апрува здесь нет, и BRD его не получает.** Документ выходит из фазы со `status: review`;
`approved` он берёт только на остановке Phase 5 вместе со словарём и конституцией. Невыводимое,
всплывшее в этой фазе, не задаётся отдельным обращением - копится перечнем к остановке, кроме
случая, когда без ответа не построить следующую фазу: тогда вопрос задаётся здесь и его факт
называется в `decision-log`. `autonomous` - каждое решение с основанием и альтернативой уходит в
список «принято за оператора» и в `decision-log`; основания нет -> пункт остаётся открытым, корпус
не завершён.

**Mandatory:** yes - цели продукта раскладываются вниз на все фичи; без BRD словарь и инварианты
формулировать не из чего. Цена отложенного апрува названа: Phase 3 и 4 идут на непринятом BRD, и
отказ на Phase 5 переделывает их вместе с ним - это принято сознательно, одна остановка с полной
картиной дешевле двух с половинной.

## Phase 3: Язык -> доменная модель

**Goal:** Получить словарь: один термин - один смысл - один дом определения, - чтобы норма,
написанная в одном артефакте, читалась так же в другом.

**Output:**

- **Доменная модель** - спавн `dex-domain-analyst:domain-analyst` (передать: расположение корпуса,
  путь BRD и его `BR-NNN`, перечень источников языка - принятые требования, ADR, нормативные
  документы проекта, - предмет `доменная модель`, `level: product`, путь `decision-log`,
  `mode: autonomous`).
- **Разбор расхождений имён.** Каждый пункт из выхода составителя получает исход: сведено к одному
  имени с основанием, признано двумя разными терминами разных контекстов, либо предъявлено оператору
  (`interactive`) / закрыто выводом из принятого (`autonomous`). **Имя - полномочная ось**: оно
  уезжает в код, API и внешние документы, и цена ошибки лежит вне словаря. Каждый пункт с исходом -
  запись в `decision-log`.
- **Гейт качества.** Оракула типа «доменная модель» в реестре нет -> запись
  `{artifact: domain-model, check: domain-model-quality, verdict: unverifiable, причина: «оракул для
  типа не существует»}`. Молчанием проверка не закрывается: отсутствие оракула - названный факт, а
  не отсутствие метки. Проверяемое без оракула трек проверяет сам и называет результат: у каждого
  термина есть дом либо строка раздела «Термины без дома» с местом употребления.

**Exit criteria:** Словарь существует по зафиксированному пути; каждый термин несёт дом либо стоит
в разделе «Термины без дома»; каждое расхождение имён имеет исход в `decision-log`; запись
`quality-checks` по типу стоит с `verdict` (`unverifiable` с причиной - валидный исход, пустота -
нет).

**Mandatory:** yes - инварианты следующей фазы формулируются в терминах словаря; собранные до него,
они опираются на имена, у которых нет одного смысла.

## Phase 4: Инварианты и меры -> конституция

**Goal:** Получить конституцию: `INV-NNN` - утверждения, истинные во всех состояниях корпуса, и
`NFR-P-NNN` - сквозные меры качества, применимые ко всем артефактам, - каждая единица с основанием и
методом проверки.

**Output:**

- **Конституция** - спавн `dex-domain-analyst:domain-analyst` (передать то же плюс путь принятого
  словаря и предмет `конституция`). Один узел на оба артефакта - инвариант формулируется в терминах
  словаря, и разведённые по разным авторам они расходятся молча.
- **Гейт качества - два слоя.** Слой единицы: `requirement-quality` по каждому `INV` и `NFR-P` -
  тип «требование, единица на любом уровне» покрывает их реестром. Слой набора:
  `requirement-set-quality` треком - непротиворечивость единиц между собой и с `BR` продукта.
  Записи `{artifact, check, verdict, revision}` ставишь ты.
- **Проверка основания - твоя, не составителя.** Каждая единица несёт `traced from` на `BR-NNN` либо
  указатель внешней нормы (путь и ревизия, идентификатор ADR). Единица без основания в документ не
  входит: она блокирует работу проекта, а владельца, который её снимет, у неё нет. Перечень
  «предложено, основания нет» из выхода составителя идёт на остановку решением, а не в документ.
- **Проверка метода - твоя же.** У каждой единицы назван метод проверки с пометкой, автоматическая
  она или ручная. Пометка «автоматическая» проверяется существованием проверки в инструменте, а не
  намерением её завести; не существует -> ручная, и это записано.

**Exit criteria:** Конституция существует по зафиксированному пути; каждая единица несёт основание и
метод проверки с честной пометкой; записи обоих слоёв `quality-checks` несут `verdict` и ревизию;
единицы без основания названы перечнем и не попали в документ; термины, на которых стоят единицы,
имеют записи в словаре (сверка поимённо, результат в `decision-log`).

**Mandatory:** yes - инвариант действует на весь корпус: его дефект дороже дефекта требования одной
фичи во столько раз, сколько артефактов на него сослалось.

## Phase 5: Приёмка корпуса уровня 0

**Goal:** Проверить корпус как целое и предъявить оператору результат вместе с остатком.

**Output:**

- **Сверка трёх артефактов между собой** - то, чего не видит ни один из составителей: каждая
  единица конституции трассируется на `BR` продукта либо на внешнюю норму; каждый термин, на котором
  стоит `BR`, `INV` или `NFR-P`, имеет запись в словаре; anti-metrics BRD не противоречат `NFR-P`
  (мера, которую конституция требует поднимать, не стоит в перечне того, что нельзя ухудшать, без
  названной цены разрешения конфликта). Каждое расхождение - находка с исходом.
- **Проверка выводимости вниз** - на корпус будут ссылаться фичи: `BR` без `MOE`, `INV` без метода
  проверки и термин без дома читаются вниз как разрешение решать самому. Каждый такой случай -
  находка либо явное решение «отдаём на усмотрение зоны требований» с основанием и записью.
- **Записи гейтов** сведены в один перечень: тип артефакта, проверка, вердикт, ревизия. Тип без
  оракула стоит с `unverifiable` и причиной.

**ОСТАНОВКА (безусловная, единственная в треке):** приёмка корпуса целиком - стороны, цели и
границы из Phase 2 предъявляются здесь же, вместе со словарём и конституцией. Форма предъявления -
выводимое списком принятых решений, невыводимое вопросами с вариантами и рекомендацией, полномочная
ось вопросом всегда. В `autonomous` остановка закрывается выводом из принятого, и **список «принято
за оператора» предъявляется первым**.

**Ответ оператора - вход, а не предмет разбора.** Применяется как есть, включая ответ без
обоснования; дальше пересчитывается задетое и показывается, что изменилось. Конфликт ответа с
принятым называется находкой - обе формулировки и задетые единицы, - но выбор остаётся за
оператором.

**Открытый пункт корпус не держит.** Незамкнутое (цель без `MOE`, термин без дома, инвариант без
метода проверки) закрывается здесь и апрув блокирует. Неполнота - неназванная сторона, характеристика
или область, - в блокеры не идёт: она уходит открытым пунктом в выход и в следующий прогон, а корпус
передаётся вниз замкнутым по тому, что в нём есть.

**Отказ оператора - третий исход, не разновидность апрува:** находки уходят составителю на
доработку, слой набора перепрогоняется по новой ревизии, приёмка проходится заново. Проход при
неустранённых находках возможен только явным решением «принять под запись» - оно фиксируется в
`decision-log` вместе с перечнем принятого долга.

**Exit criteria:** Сверка трёх артефактов выполнена и её находки имеют исход в `decision-log`;
предъявленное оператору сверено с `decision-log` поимённо - у каждой находки, помеченной вопросом,
есть ответ, у каждой закрытой треком - основание; статусы документов подняты до `approved` только
после апрува, при незамкнутом пункте потолок `review` с названной причиной; открытый пункт
неполноты потолка не опускает - он назван перечнем.

**Mandatory:** yes - три артефакта, принятые поодиночке, противоречат друг другу тем чаще, чем
дольше живут: несогласованность видна только на сверке.

## Phase 6: Handoff

**Goal:** Передать принятый корпус так, чтобы зона требований опиралась на него, не перепроверяя.

**Output (handoff):** первым полем `status` (словарь исхода - `node-contract`), затем: пути трёх
артефактов; `BR-NNN` с `MOE` и `non-goals`; anti-metrics; перечень `INV-NNN` и `NFR-P-NNN` с
основанием и методом проверки; перечень терминов с домами и перечень оставшихся без дома;
**список решений, принятых за оператора, отдельным перечнем** - что решено, из чего выведено, что
было альтернативой; путь `decision-log`; расположение корпуса - разрешённые ключи `.docs_layout`, установленные Phase 1 (сквозное поле `node-contract` п.6: зона требований берёт их как есть и своего поиска не запускает); открытые пункты, если остались; `quality-checks` со всеми
записями; `status` каждого артефакта в шапке его документа. Это вход зоны требований (`/feature`):
цели фичи трассируются на `BR-NNN` продукта, единицы фичи проверяются против `INV`/`NFR-P`. Задачи,
сценарии и код здесь не порождаются.

**Exit criteria:** Output содержит все перечисленные поля; шапка каждого артефакта несёт
проставленный `status`; `status: complete` выдаётся только когда безусловная остановка закрыта и
незамкнутых пунктов нет; открытый пункт неполноты `complete` не отменяет - он идёт перечнем в
выходе; незакрытая остановка либо незамкнутость -> `blocked`/`partial` с перечнем.

**Mandatory:** yes - без сводного выхода зона требований либо перепроверяет уровень 0 заново, либо
принимает его на веру.

## Дельта-прогон: правка принятого уровня 0

Вход - правка принятой единицы, а не новый продукт. Правкой считается и **изменение внешнего
основания**: регламент, норма среды, ADR, на которые единица сослалась. Второй источник входа -
**возврат из зоны требований**: фиче понадобилась цель, термин или инвариант уровня продукта.

1. **Род изменения объявляется до правки файлов** - уточнение формулировки, смена ограничения,
   расширение области, снятие (`dex-skill-unit-identity:unit-identity`). Род определяет, что
   пересчитывать.
2. **Задетое считается поиском по идентификатору единицы** (изменилось внешнее основание - по его
   указателю) **по всему корпусу проекта, а не по одной папке**: на уровень 0 ссылаются все фичи, и
   обход, ограниченный корнем уровня 0, до потребителей не доходит вовсе. Хранимого списка «что из
   меня выведено» у единицы нет - это принятое сужение: обратное поле протухает молча, поиск не
   протухает. Обход конечен - единица входит в него один раз.
3. **Оператор останавливается после пересчёта задетого, а не до правки.** До пересчёта неизвестно,
   что потянется. Правка уровня 0 задевает чужие наборы почти всегда - остановка безусловна.
4. **Чужую единицу правит её владелец.** Задевший переводит её в `review` с пометкой «основание
   изменено» и называет, что изменилось; текст соседнего набора не переписывает.
5. Каждая задетая единица получает исход - пересмотрена, признана незатронутой с основанием или
   снята; апрув отзывается в изменяемой части, не во всём документе. Единицы, чей исход выводится,
   идут без вопроса.
6. **Возврат из зоны требований закрывается ответом ей**: что заведено (новый `BR`/термин/`INV` с
   идентификатором) либо почему отказано - «это цель фичи, уровня продукта не переживает». Ответ без
   идентификатора или без причины отказа оставляет фичу без терминала: она заведёт своё.

Расщепление: исходная единица снимается с записью «заменено на X, Y», потомки получают свои номера,
ссылки снизу переадресуются по предмету. Висячей ссылки на снятый ID не остаётся.

## Boundaries

- Не писать артефакты уровня 0 самому - их порождают составители; написав артефакт, ты становишься
  его автором и теряешь право судить его на гейте. Запись на диск сверх `auto-ledger` -
  `decision-log`.
- Не заводить второй BRD, второй словарь или вторую конституцию рядом с принятым. Новая тема
  продукта - правка принятого через дельта-прогон.
- Не спускаться на уровень фичи: сценарии, `FR`/`NFR` фичи, истории и задачи - зона требований
  (`/feature`). Признак нарушения: у единицы появился актор с ходом либо условие срабатывания одной
  операции.
- Не поднимать цель фичи до `BR` продукта без проверки: единица уровня 0 переживает удаление любой
  одной фичи. Не переживает - отказ с этой причиной, а не запись «на всякий случай».
- Не заводить `INV` без основания и не превращать пожелание в инвариант словом «всегда»: единица без
  `traced from` идёт на остановку решением, а не в документ.
- Не апрувить за оператора в `interactive`: апрув всегда явный ответ, молчание апрувом не считается.
  В `autonomous` закрывать полномочную ось **только выводом из принятого**; основания нет -> пункт
  остаётся открытым и едет наверх.
- Не сводить расхождение имён молча и не откладывать его «до кода»: имя, разошедшееся на уровне 0,
  расходится в каждом артефакте, который его употребит.
- Не заводить отдельный файл состояния сверх `auto-ledger` и `decision-log` - продолжение прогона
  восстанавливается чтением корпуса.
- Не отдавать `decision-log` на запись составителям: один файл - один писатель, остальные возвращают
  строки решений в выходе.
- Не подписывать чужую проверку и не выдавать отсутствие оракула за пройденную проверку: тип без
  оракула закрывается записью `unverifiable` с причиной, не пустым местом.
- Не решать архитектуру и не оценивать техническую выполнимость - это зона дизайна (`/design`).
- Skill-оракул не загрузился -> не останавливаться: гейт по своим знаниям, в Output «гейт N без
  проверки `<skill>`» + `verdict: unverifiable` с причиной - молчанием проверка не закрывается.
