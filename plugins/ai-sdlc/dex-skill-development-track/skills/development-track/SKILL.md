# Development Track

Трек ведёт фичу от ТЗ (или его отсутствия) до серии локальных коммитов без push. Вызывается
движком `dex-sdlc:engine` (`/implement`) и отдельно от него не запускается: движок ведёт цикл и
стоп-линию, трек - порядок этой зоны.

**Работа без спеки и без формальных требований - штатный вход, не дефект.** Тикет в строку, баг без
описания, «почини вот это»: требования восстанавливаешь сам из тикета, кода и конвенций (R/I по
`dex-skill-node-contract:node-contract`), недостающее - допущением. Просят design-документ самим
результатом, а не код - работа не эта: `status: partial` с указанием на зону дизайна, документ
кодом не подменяется.

**Исполнителя правки выбирает трек** по критерию движка («Как выбрать исполнителя»): много файлов
или гипотез - профильный узел под стек манифеста (`dex-dotnet-coder:dotnet-coder` `[справочно]`,
`dex-ts-fullstack-coder:ts-fullstack-assistant` `[справочно]` и т.п.); правка понятна и локализована -
трек пишет сам, через явно поднятый скилл стека, и решение «сам» несёт строку журнала
`channel: self` с причиной и именем скилла - без строки оно не принято.
**Тип исполнителя порогом не меняется:** добор покрытия сверх TDD ведёт tester-узел, саморевью зоны -
свой узел, не тот же coder. Планирование, дизайн, фальсификация плана и финальная верификация -
работа трека всегда (`channel: self`); в инвентаризации Phase 2 треку принадлежат постановка блоков
и сведение фактов, сам сбор он вправе разложить по суб-агентам разведки.

**Возобновление.** Свёртка внутри прогона - «Возобновление» движка по auto-ledger. Новый прогон по
тому же предмету ledger не находит: состояние читается от намерения (тикет, спека, план,
`decision-log`) и от того, что фактически лежит - рамка в `references/ledger-and-recovery.md`
движка, раздел «Восстановление между прогонами». Носители состояния этой зоны: целевая ветка с
коммитами, открытый MR, прогон сборки и тестов, edit-план. Не восстановилось ни одним - строка в
сдаче, не догадка.

**Режим совпадает с ярусом:** трек грузится в тело исполнителя, `interactive` в фазах ниже
адресует возврат оператору. Вниз, в делегированные узлы, тем же значением едет планка эскалации,
канал не едет (`node-contract`, D.11).

## Обзор фаз

| # | Фаза | Кто исполняет |
|---|---|---|
| 0 | Project Conventions | трек (сам) |
| 1 | Decompose Spec | трек (сам) |
| 2 | Architecture Inventory | трек (сам, вправе развести блоки по суб-агентам разведки) |
| 3 | Research Unknowns | трек (сам) |
| 4 | Design | трек (сам) |
| 5 | Executable Edit Plan | трек (сам) |
| 6 | Falsify Plan | трек (сам) |
| 7 | Implement with Verify | исполнитель правки по критерию шапки, трек координирует и коммитит |
| 8 | Final Self-Verification | трек (сам) + tester-узел на добор покрытия |

## Phase 0: Project Conventions

Goal: восстановить действующие конвенции проекта раньше любого решения по дизайну.
Output: загружен `dex-skill-codebase-conventions:codebase-conventions` и
`dex-skill-project-baseline:project-baseline` (если есть в каталоге проекта); стиль коммитов, слой
тестов, структура каталогов - зафиксированы как база для Phase 4.
Exit criteria: конвенции названы с precedent (файл/пример), не общим «обычно так делают».

Mandatory: yes

## Phase 1: Decompose Spec

Goal: превратить вход (ТЗ, тикет, «почини это») в R/I-требования, success criteria, non-goals; выбрать
под-вид работы и режим тестирования.

**Input (handoff):** контракт стыка - `dex-skill-node-contract:node-contract`. `[blocking]`
постановка в любой форме: дизайн-документ с implementation plan (из зоны дизайна), набор
`FR-NNN`/`NFR-NNN` со stories (из зоны требований), тикет либо задача словами. Постановки нет вовсе ->
halt + возврат вызывающему: кодировать нечего, догадкой она не восполняется. `[default-ok]` `mode`
(дефолт `autonomous`), `quality-checks` пришедших артефактов, путь к журналу решений, ветка и стек
(не пришли - определяются по git и манифесту затронутой папки), под-вид работы (не пришёл -
выбирается здесь же ниже).
Output: R/I по `node-contract`, success criteria, non-goals, список открытых вопросов (порог
confidence и ветки по режиму - Boundaries).

**Входная приёмка** - по правилу движка (шаг 2) и `node-contract` п.9 (носители метки, ветки по
вердикту, разница «пришёл по стыку / подан вне стыка»); оракул по типу из реестра там же:
`design-quality` для дизайн-документа, `requirement-quality` для требований и историй.
**`/implement` штатно запускают вне стыка** - прямо на пути к дизайн-документу или на тикете, и обе
ветки имеют терминал:
- артефакт зоны (дизайн-документ, implementation plan, набор `FR`/`NFR`, stories) -> приёмка
  обязательна независимо от того, приехал ли handoff; вердикт не `passed` -> код по неодобренному
  артефакту не пишется: `interactive` - предъяви оператору, `autonomous` - `status: blocked` наверх
  с перечнем непройденного;
- тикет, «почини это», устная постановка -> артефактом зоны не является, метки нет по природе,
  приёмка неприменима: требования восстанавливаются, как сказано в шапке, и это не блокер.

**Под-вид - выбери здесь, он определяет DoD теста на Phase 8:**

| Под-вид | Тест-DoD |
|---|---|
| Фича | полная матрица покрытия по осям + регресс потребителей затронутого контракта |
| Баг-фикс | тест, воспроизводящий дефект, red до фикса, green после. Вызови `Skill` -> `dex-skill-bugfix-track:bugfix-track` - процедура и связь с «Разберись и почини» живут там |
| Рефакторинг | safety-net тесты на неизменное поведение, малые шаги, изменившийся assert внутри рефакторинга - стоп, не рефакторинг |

Режим теста - `tdd` (red-green-refactor по умолчанию) либо `test-after` (когда TDD объективно не
применим - explicit reason в выходе, не тихий выбор).
Exit criteria: под-вид назван, режим теста назван с обоснованием, R/I полны для перехода к
инвентаризации, и по каждому артефакту входа назван исход приёмки (доверие метке / прогнанный
оракул с вердиктом / `unverifiable` с причиной) - неформальная постановка называется ею явно.

Mandatory: yes

## Phase 2: Architecture Inventory

Goal: инвентаризировать точки соприкосновения с существующей архитектурой до дизайна.
Output: 4 блока - Touchpoints (что трогаем), Reuse (что переиспользуем вместо нового), Neighbor
patterns (как решена соседняя задача), Contracts (входы/выходы затронутых границ - через
`dex-skill-completeness-mapping:completeness-mapping`, не только `LSP findReferences`: он не
пересекает проекцию DTO/маппера).
Крупное ТЗ - разведи блоки через `Agent`, по одному блоку на суб-агента разведки; узел, пишущий
код (Phase 7), на разведку не бери.
Exit criteria: все 4 блока закрыты фактами с диска, не предположением о «как обычно».

Mandatory: yes

## Phase 3: Research Unknowns

Goal: закрыть зависимости от внешнего знания (библиотека, протокол, версия API), если по инвентаризации
остались открытые.
Output: для каждой неизвестной - факт с источником (`context7`/`WebSearch`) либо явное допущение,
если факт недоступен.
Exit criteria: ни одна неизвестная Phase 2 не осталась без исхода; пропуск фазы - только по
условию Mandatory ниже.

Mandatory: no - единственная опциональная фаза трека. Пропуск допустим ТОЛЬКО когда Phase 2 не
оставила ни одной неизвестной, и фиксируется в выходе статусом `n/a` с этой причиной; неизвестная
есть, но источник недоступен - фаза исполнена, исход `unverifiable` + допущение, а не пропуск.

## Phase 4: Design

Goal: спроектировать решение на найденных прецедентах, не на «лучшей практике» вообще.
Output: архитектурное решение, контракты (успех/ошибка), решение по обработке ошибок; по стеку из
манифеста - загрузка профильных skills по реестру (`dex-skill-stack-registry:stack-registry`,
тематические + `dex-skill-<стек>-*`).

**Гейт первоисточника**: каждое решение по конвенции несёт именованный прецедент (файл, PR, ADR) либо
явное допущение с меткой - решение без того и другого возвращается на Phase 2/3, не проходит дальше.
Возврат прецедента не дал: `interactive` - спроси оператора до Phase 5, `autonomous` - зафиксируй
допущение с источником вывода и веди его в выход трека; самим фактом ненахождения гейт не закрывается.

**Pre-check «нужен ли ADR» - до плана**: порог - цена отмены решения, а не новизна нормы. Считай
перечнем задетого при отмене: только код своего модуля -> строка в журнал решений, ADR не нужен;
миграция данных, смена контракта с внешним потребителем, переписывание написанного по этому решению
кода в других модулях или репозиториях, публично зафиксированный формат (схема хранения, вид
идентификаторов, публичный API) -> ADR обязателен до Phase 5 (`dex-adr-writer:adr-writer`). Место и
принятые ADR - `dex-skill-project-docs-map:project-docs-map`; карта недоступна или перечень задетого
выяснить не удалось -> `unverifiable` с причиной и ADR заводится: неизвестная цена отмены считается
высокой, молчанием pre-check не закрывается.
Exit criteria: решение и контракты зафиксированы, ADR-статус (нужен/не нужен/оформлен) явный.

Mandatory: yes

## Phase 5: Executable Edit Plan

Goal: разложить дизайн в edit-план P1..Pn, исполнимый по одной правке за раз.
Output: P1..Pn с файлами, сутью правки, success criteria на шаг, порядком под режим теста (`tdd`:
тест раньше кода на каждом Pi; `test-after`: код, затем тест в рамках того же Pi).
Exit criteria: каждый Pi атомарен и верифицируем изолированно; порядок шагов не создаёт промежуточного
недопустимого состояния (сборка не ломается между шагами дольше одного Pi).

Mandatory: yes

## Phase 6: Falsify Plan

Goal: попытаться опровергнуть свой же план до исполнения - найти шаг, который не даст заявленного
success criteria, или зависимость между Pi, не отражённую в порядке.

Вызови `Skill` -> `dex-skill-plan-quality:plan-quality` и фальсифицируй план по его осям: связь шага
с требованиями, порядок и зависимости, проверяемость исхода без автора, контракты пересекаемых
границ, откат необратимого шага.
Метку `quality-checks` по итогу не ставь - автор edit-плана здесь ты, а автор себе вердикт не ставит
(`node-contract` п.7 раздела B); результат идёт в `self-check` выхода. Skill не загрузился -> в выходе
строка «Phase 6 без проверки `plan-quality`» + `unverifiable` с причиной, фазу это не закрывает -
проход по перечисленным осям выполняется своими силами.

Output: план подтверждён либо переработан с указанием, что именно не проходило фальсификацию;
`self-check` по `plan-quality` (либо `unverifiable` с причиной).
Exit criteria: план либо прошёл фальсификацию, либо переработан и прогнан повторно - не «пропущено,
выглядело нормально»; `self-check` по осям чеклиста в выходе есть.

Mandatory: yes

## Phase 7: Implement with Verify

Goal: исполнить P1..Pn по одной правке за раз, с локальной верификацией и коммитом после каждой;
исполнителя правки выбираешь по критерию шапки (профильный узел под стек либо трек сам).

Режим - из входа трека (Phase 1). Цикл `оформляй`/`делай`/`стоп` - тот же механизм режима на
уровне edit-плана: в `interactive` `оформляй` - полный P1..Pn на явный approve оператора,
`делай` - исполнение по одному Pi, `стоп` - остановка перед следующим Pi; в `autonomous` тот же план
проходит без ожидания - список принятых решений уходит в выход трека тем же порядком, что и любое
решение, принятое за оператора (движок, шаг 4 «Допущения»).

Вход исполнителю на каждый Pi: сама правка, применимые R/I и success criteria с метками, ось теста
Phase 4 (интеграционная граница ниже), режим `tdd`/`test-after`. Код и тест правки пишутся инлайн
одним исполнителем (red-green-refactor или code-then-test), на выходе - изменённые файлы + статус
build/test + fact-check: генерация теста не выносится отдельно ни тест-агенту, ни второму узлу.
Трек принимает результат против success criteria шага, коммитит (стиль проекта) и переходит к
следующему Pi; расхождение с критерием - фикс тем же исполнителем в рамках Pi, не молчаливая приёмка.

Exit criteria: все Pi закрыты коммитами либо явно отложены со статусом и причиной; ни одна правка
не принята без прогона build/test по затронутому коду.

Mandatory: yes

## Граница интеграции

Тестируй ВСЕ узлы цепочки, не только входную точку - юнит изолированного модуля не закрывает фичу,
дыра живёт на стыке и на границе с чужой системой. Механику (мок против реального контракта, точка
входа до теста, каждая ветка/fallback отдельно) держит
`dex-skill-integration-boundary:integration-boundary` - грузит его исполнитель правки Phase 7,
когда правка трогает внешнюю границу (LLM/внешний API/IO).

## Phase 8: Final Self-Verification

Goal: подтвердить успех фичи против success criteria и закрыть покрытие.
Output: полный прогон build/test, coverage-gate по контракту `dex-skill-test-coverage:test-coverage`
(порог и статус деградации - там, не повтор здесь), скан diff на запрещённые паттерны
(TODO, заглушки, silent fallback, debug-вывод, hardcoded secrets, отключённые тесты, спекулятивный
код, дубли утилит). Разрыв покрытия - делегируется tester-узлу под стек
(`dex-dotnet-tester:dotnet-test-writer` `[справочно]`/`dex-ts-tester:ts-test-writer` `[справочно]`) по тем же осям, что уже
считаны в Phase 5/7 - трек не изобретает свою тест-механику и не пишет добор сам.

**Покрытие требований проверяется отдельно от покрытия кода:** coverage-gate меряет строки и ветки,
и требование без единого теста порог берёт молча. Вызови `Skill` -> `dex-skill-test-track:test-track`
(Phase 3, Requirements Back-Edge) и закрой обратное ребро: по каждому `FR`/`NFR`/`AC`/`INV` - тест
или явный исход (покрыто на другом уровне | автотестом не проверяемо с причиной | разрыв -> добор
тем же tester-узлом). **Множество требований берётся из корпуса на диске, не из пересказа во входе**
(механика и терминал недостижимого корпуса - там же). Корпуса нет и требований во входе не было ->
ребро от success criteria Phase 1.

Провал coverage-gate или незакрытое требование обратного ребра порог сам не понижает: `interactive` -
предъяви оператору выбор (добор тестами | принятый разрыв с причиной), `autonomous` - добор тем же
tester-узлом, добор не закрыл -> `status: partial` с перечнем непокрытого. Понизить порог или
переписать success criteria под фактический результат нельзя ни в одном режиме.

Exit criteria: success criteria из Phase 1 закрыты фактом прогона; coverage-gate и forbidden-patterns
пройдены либо провал явно назван в выходе; обратное ребро закрыто - каждое требование входа несёт
тест либо названный исход.

Mandatory: yes

## Саморевью зоны

Шаг 7 движка «Саморевью» для этой зоны; глубину и состав проходов задаёт трек - ниже.
Запусти узел `dex-self-reviewer:self-reviewer` через `Agent`.

**Момент запуска - по режиму** (шаг 7 движка): `autonomous` - сразу после Phase 8; `interactive` -
после подтверждения оператором, что правки завершены, до него узел не спавнится. Подтверждения нет -
трек ждёт, шаг не снимается: `complete` без исполненного саморевью не выдаётся.

Вход узлу: `intent` - success criteria Phase 1 и edit-план Phase 5, плюс `mode` трека. Пути не
подавай.

Состав фокусов узлу не диктуй. Отчёт принимай, **только если по каждой оси назван исход** - активна
она на этом diff или нет, security включительно; ось без исхода - непройденная.

Маршрут по находкам решает трек: блокеры и красные пункты чеклиста закрываются правкой тем же
порядком, что и Phase 7 (профильный узел на правку), после чего саморевью повторяется по новой
дельте. Незакрытое - перечнем в выход трека со `status: partial`.

## Интеграция с базой - слот перед сдачей

Перед Phase 8 (или сразу после, если ветка отстала от базы за время работы) - подтяни базовую ветку
через `dex-conflict-resolver:conflict-resolver`, не построчно вручную: риск здесь - тихая потеря
стороны, а не сам факт конфликта. После слияния пересбор и перепрогон тестов обязательны, «зелёное»
до слияния не считается. «Взял свою сторону целиком» - решение, которое трек обосновывает в выходе,
не дефолт.

## Выход трека (handoff)

**Output (handoff):** первым полем `status` (словарь исхода - `node-contract`), затем: ветка и
перечень коммитов (sha + что в каждом); R/I и success criteria Phase 1 с исходом по каждому -
закрыт фактом прогона либо не закрыт с причиной; run-status build/test последнего прогона;
coverage-gate значением против порога; обратное ребро требование -> тест с исходом по каждому
требованию (Phase 8); под-вид работы и режим теста; допущения, каждое с источником вывода;
**решения, принятые за оператора, отдельным перечнем** - что решено, из чего выведено, что было
альтернативой; открытые наблюдения вне скоупа этой фичи; `quality-checks` (пришедшие сверху
переносятся как есть, записи по артефактам входа ставишь ты - их автором ты не являешься);
перечень незакрытого при `partial`/`blocked`.

Работа заканчивается на локальных коммитах: push, MR и мердж этот трек не делает. Выход адресован
движку (шаг 8, сдача), не следующему треку: маршрут решает он.

**Exit criteria:** Output несёт все перечисленные поля; `complete` выдаётся только когда success
criteria закрыты фактом прогона, обратное ребро закрыто и саморевью зоны исполнено; иначе
`partial`/`blocked` с перечнем.

**Mandatory:** yes

## Переход в другой трек

Внешнее ревью на уже сданный MR этой фичи - это отдельный трек `dex-skill-followup-track:followup-track` `[справочно]`,
не продолжение Phase 7/8: работа над найденным ревьюером переходом переоткрывается уже там, а не
здесь. «Разберись и почини» без отдельного тикета на баг - под-вид баг-фикс (Phase 1), не отдельный
аналитический трек: полная процедура, включая автономный разбор «что и почему», -
`dex-skill-bugfix-track:bugfix-track` `[справочно]`.

## Boundaries

- Confidence ниже 80% в трактовке или подходе - вопрос оператору (`interactive`) либо допущение с
  пометкой (`autonomous`), не код по предположению.
- Скоуп - предмет правки и только он: одна и та же по смыслу правка во всех носителях - один Pi.
  Замечание другого предмета - в открытые наблюдения.
- Новая зависимость - только когда ни один механизм проекта задачу не закрывает; выбор назван с
  причиной.
