# Development Track

Трек ведёт фичу от ТЗ (или его отсутствия) до серии локальных коммитов без push - staff-level
инженерная дисциплина: декомпозиция, инвентаризация архитектуры, дизайн с именованным
первоисточником, исполняемый edit-план, фальсификация плана, реализация с локальной верификацией
на каждом шаге, финальное саморевью с coverage-гейтом. Вызывается движком `dex-sdlc:engine`
(`/implement`) - трек не запускается отдельно от него, движок ведёт цикл и стоп-линию, трек - порядок
этой зоны.

**Работа без спеки и без формальных требований - штатный вход, не дефект.** Тикет в одну строку,
баг без описания, «почини вот это» - требования восстанавливаешь сам из тикета, кода и конвенций
(R/I по `dex-skill-node-contract:node-contract`), недостающее фиксируешь допущением. Просят design-документ
самим результатом (а не код) - это не эта работа: возвращай `status: partial` с указанием на зону
дизайна (`/design`), не подменяй документ кодом.

**Написание кода трек не делает сам.** Правки Phase 7 трек раскладывает на профильный узел под
стек манифеста (`dex-dotnet-coder:dotnet-coder`, `dex-ts-fullstack-coder:ts-fullstack-assistant`
и т.п., выбор - по «Как выбрать исполнителя» движка, шаг 3) - монолит-оркестратор, кодирующий сам
через Edit/Write, дублирует движок и теряет идиоматику стека (RED-проверено). Добор покрытия сверх
TDD и security-проход - тоже отдельные узлы, не тот же coder и не сам трек. Планирование,
инвентаризация, дизайн, фальсификация плана и финальная верификация остаются работой трека
(`channel: self`) - это не написание production-кода, а его контур.

## Обзор фаз

| # | Фаза | Кто исполняет |
|---|---|---|
| 0 | Project Conventions | трек (сам) |
| 1 | Decompose Spec | трек (сам) |
| 2 | Architecture Inventory | трек (сам, вправе развести блоки по суб-агентам разведки) |
| 3 | Research Unknowns | трек (сам) |
| 4 | Design | трек (сам) |
| 5 | Executable Edit Plan | трек (сам) |
| 6 | Falsify Plan | трек (сам) |
| 7 | Implement with Verify | coder-узел на правку, трек координирует и коммитит |
| 8 | Final Self-Verification | трек (сам) + tester-узел на добор покрытия |

## Phase 0: Project Conventions

Goal: восстановить действующие конвенции проекта раньше любого решения по дизайну.
Output: загружен `dex-skill-codebase-conventions:codebase-conventions` и
`dex-skill-project-baseline:project-baseline` (если есть в каталоге проекта); стиль коммитов, слой
тестов, структура каталогов - зафиксированы как база для Phase 4.
Exit criteria: конвенции названы с precedent (файл/пример), не общим «обычно так делают».

Mandatory: yes - без снятых конвенций Phase 4 выбирает решение «как принято вообще», и правка
расходится с проектом уже на ревью.

## Phase 1: Decompose Spec

Goal: превратить вход (ТЗ, тикет, «почини это») в R/I-требования, success criteria, non-goals; выбрать
под-вид работы и режим тестирования.

**Input (handoff):** контракт стыка - `dex-skill-node-contract:node-contract`. `[blocking]`
постановка в любой форме: дизайн-документ с implementation plan (из `/design`), набор
`FR-NNN`/`NFR-NNN` со stories (из `/feature`), тикет либо задача словами. Постановки нет вовсе ->
halt + возврат вызывающему: кодировать нечего, догадкой она не восполняется. `[default-ok]` `mode`
(дефолт `autonomous`), `quality-checks` пришедших артефактов, путь к журналу решений, ветка и стек
(не пришли - определяются по git и манифесту затронутой папки), под-вид работы (не пришёл -
выбирается здесь же ниже).
Output: R/I по `node-contract`, success criteria, non-goals, список открытых вопросов (confidence
<80% в трактовке - вопрос, не допущение).

**Входная приёмка артефактов входа** идёт здесь по общему правилу движка (шаг 2) и
`node-contract` п.9 - носители метки, ветки по вердикту, разница «пришёл по стыку / подан вне
стыка»; в треке не повторяются. Оракул берётся по типу из реестра `node-contract`: `design-quality`
для дизайн-документа, `requirement-quality` для требований и историй.

Своё у этого трека одно: **`/implement` штатно запускают вне стыка** - прямо на пути к дизайн-
документу или на тикете. Отсюда две ветки, и обе имеют терминал:
- вход - артефакт зоны (дизайн-документ, implementation plan, набор `FR`/`NFR`, stories) ->
  приёмка обязательна независимо от того, приехал ли handoff; вердикт не `passed` -> код по
  неодобренному артефакту не пишется: `interactive` - предъяви оператору, `autonomous` -
  `status: blocked` наверх с перечнем непройденного;
- вход - тикет, «почини это», устная постановка -> артефактом зоны не является, метки нет по
  природе, приёмка неприменима: требования восстанавливаются, как сказано выше, и это не блокер.

**Под-вид - выбери здесь, он определяет DoD теста на Phase 8:**

| Под-вид | Тест-DoD |
|---|---|
| Фича | полная матрица покрытия по осям + регресс потребителей затронутого контракта |
| Баг-фикс | тест, воспроизводящий дефект, red до фикса, green после. Вызови `Skill` -> `dex-skill-bugfix-track:bugfix-track` - процедура и связь с «Разберись и почини» живут там, не здесь |
| Рефакторинг | safety-net тесты на неизменное поведение, малые шаги, изменившийся assert внутри рефакторинга - стоп, не рефакторинг |

Режим теста - `tdd` (red-green-refactor по умолчанию) либо `test-after` (когда TDD объективно не
применим - explicit reason в выходе, не тихий выбор).
Exit criteria: под-вид назван, режим теста назван с обоснованием, R/I полны для перехода к
инвентаризации, и по каждому артефакту входа назван исход приёмки (доверие метке / прогнанный
оракул с вердиктом / `unverifiable` с причиной) - неформальная постановка называется ею явно.

Mandatory: yes - без R/I и success criteria «готово» на Phase 8 проверять нечем, оно становится
мнением исполнителя.

## Phase 2: Architecture Inventory

Goal: инвентаризировать точки соприкосновения с существующей архитектурой до дизайна.
Output: 4 блока - Touchpoints (что трогаем), Reuse (что переиспользуем вместо нового), Neighbor
patterns (как решена соседняя задача), Contracts (входы/выходы затронутых границ - через
`dex-skill-completeness-mapping:completeness-mapping`, не только `LSP findReferences`, у него не
пересекает проекцию DTO/маппера).
Крупное ТЗ - разведи блоки через `Agent`, по одному блоку на суб-агента разведки; не через coder-узел
Phase 7, это ещё не написание кода.
Exit criteria: все 4 блока закрыты фактами с диска, не предположением о «как обычно».

Mandatory: yes - правка без карты точек соприкосновения ломает потребителей, которых никто не искал.

## Phase 3: Research Unknowns

Goal: закрыть зависимости от внешнего знания (библиотека, протокол, версия API), если по инвентаризации
остались открытые.
Output: для каждой неизвестной - факт с источником (`context7`/`WebSearch`) либо явное допущение,
если факт недоступен.
Exit criteria: фаза опциональна - пропускается явно (не молчанием), если Phase 2 не оставила
неизвестных.

Mandatory: no - единственная опциональная фаза трека. Пропуск допустим ТОЛЬКО когда Phase 2 не
оставила ни одной неизвестной, и фиксируется в выходе статусом `n/a` с этой причиной; неизвестная
есть, но источник недоступен - фаза исполнена, исход `unverifiable` + допущение, а не пропуск.

## Phase 4: Design

Goal: спроектировать решение на найденных прецедентах, не на «лучшей практике» вообще.
Output: архитектурное решение, контракты (успех/ошибка), решение по обработке ошибок; по стеку из
манифеста - загрузка профильных skills по реестру (`dex-skill-stack-registry:stack-registry`,
тематические + `dex-skill-<стек>-*`).

**Гейт первоисточника**: каждое решение по конвенции несёт именованный прецедент (файл, PR, ADR) либо
явное допущение с меткой - решение без того и другого возвращается на Phase 2/3, не проходит дальше.
Возврат прецедента не дал: `interactive` - спроси оператора до Phase 5, `autonomous` - зафиксируй
допущение с источником вывода и веди его в выход трека; самим фактом ненахождения гейт не закрывается.

**Pre-check «нужен ли ADR» - до плана**: через `dex-skill-project-docs-map:project-docs-map` проверь,
вводит ли решение новое архитектурное правило (не факт кода). Вводит - ADR обязателен до Phase 5
(`dex-adr-writer:adr-writer`); карта недоступна - `unverifiable` с причиной в выходе, не молчание.
Exit criteria: решение и контракты зафиксированы, ADR-статус (нужен/не нужен/оформлен) явный.

Mandatory: yes - без зафиксированного решения edit-план собирается из догадок, и расхождение
всплывает уже коммитами.

## Phase 5: Executable Edit Plan

Goal: разложить дизайн в edit-план P1..Pn, исполнимый по одной правке за раз.
Output: P1..Pn с файлами, сутью правки, success criteria на шаг, порядком под режим теста (`tdd`:
тест раньше кода на каждом Pi; `test-after`: код, затем тест в рамках того же Pi).
Exit criteria: каждый Pi атомарен и верифицируем изолированно; порядок шагов не создаёт промежуточного
недопустимого состояния (сборка не ломается между шагами дольше одного Pi).

Mandatory: yes - без разложения на верифицируемые шаги Phase 7 правит широко и откатывает целиком,
а `interactive` теряет предмет approve.

## Phase 6: Falsify Plan

Goal: попытаться опровергнуть свой же план до исполнения - найти шаг, который не даст заявленного
success criteria, или зависимость между Pi, не отражённую в порядке.
Output: план подтверждён либо переработан с указанием, что именно не проходило фальсификацию.
Exit criteria: план либо прошёл фальсификацию, либо переработан и прогнан повторно - не «пропущено,
выглядело нормально».

Mandatory: yes - дефект порядка шагов стоит дешевле на плане, чем половиной исполненных коммитов.

## Phase 7: Implement with Verify

Goal: исполнить P1..Pn, каждую правку - руками профильного coder-узла под стек, с локальной
верификацией и коммитом после каждого шага.

Источник режима - вход трека (`mode`), нет поля -> `autonomous`
(`dex-skill-node-contract:node-contract`, инвариант D п.11). Цикл `оформляй`/`делай`/`стоп` - это
**реализация общего механизма режима движка/node-contract** на уровне edit-плана, не отдельно
придуманная лексика трека: в `interactive` `оформляй` - полный P1..Pn на явный approve оператора,
`делай` - исполнение по одному Pi, `стоп` - остановка перед следующим Pi; в `autonomous` тот же план
проходит без ожидания - список принятых решений уходит в выход трека тем же порядком, что и любое
решение, принятое за оператора (движок, «Решения и фиксация неуверенности»).

Output на каждый Pi: спавн coder-узла с входом - сама правка, применимые R/I и success criteria с
метками, ось теста Phase 4 (интеграционная граница ниже), режим `tdd`/`test-after`. Узел пишет код
и тест этой правки инлайн сам (red-green-refactor или code-then-test) и отдаёт изменённые файлы +
статус build/test + fact-check - генерация теста не делегируется отдельно ни тест-агенту, ни треку.
Трек принимает результат против success criteria шага, коммитит (стиль проекта) и переходит к
следующему Pi; расхождение с критерием - фикс тем же узлом в рамках Pi, не молчаливое приемка.

Exit criteria: все Pi закрыты коммитами либо явно отложены со статусом и причиной; ни одна правка
не принята без прогона узлом build/test для затронутого кода.

Mandatory: yes - это фаза, ради которой трек существует.

## Граница интеграции

Тестируй ВСЕ узлы цепочки, не только входную точку - юнит изолированного модуля не закрывает фичу,
дыра живёт на стыке и на границе с чужой системой. Механику (мок против реального контракта, точка
входа до теста, каждая ветка/fallback отдельно) держит
`dex-skill-integration-boundary:integration-boundary` - грузит его coder-узел Phase 7 на правках,
трогающих внешнюю границу (LLM/внешний API/IO), не трек.

## Phase 8: Final Self-Verification

Goal: подтвердить успех фичи против success criteria и закрыть покрытие, не отдельными Edit-правками
трека, а через профильный tester-узел.
Output: полный прогон build/test, coverage-gate по контракту `dex-skill-test-coverage:test-coverage`
(порог и статус деградации - там, не повтор здесь), скан diff на запрещённые паттерны
(TODO, заглушки, silent fallback, debug-вывод, hardcoded secrets, отключённые тесты, спекулятивный
код, дубли утилит). Разрыв покрытия - делегируется tester-узлу под стек
(`dex-dotnet-tester:dotnet-test-writer`/`dex-ts-tester:ts-test-writer`) по тем же осям, что уже
считаны в Phase 5/7 - трек не изобретает свою тест-механику и не пишет добор сам.

**Покрытие требований проверяется отдельно от покрытия кода.** Coverage-gate меряет строки и ветки,
и требование без единого теста порог берёт молча. Вызови `Skill` -> `dex-skill-test-track:test-track`
(раздел «Покрытие требований») и закрой обратное ребро: по каждому `FR`/`NFR`/`AC` со входа - тест
или явный исход (покрыто на другом уровне | автотестом не проверяемо с причиной | разрыв -> добор
тем же tester-узлом). Требований на входе не было -> ребро от success criteria Phase 1.

Провал coverage-gate или незакрытое требование обратного ребра порог сам не понижает: `interactive` -
предъяви оператору выбор (добор тестами | принятый разрыв с причиной), `autonomous` - добор тем же
tester-узлом, добор не закрыл -> `status: partial` с перечнем непокрытого. Понизить порог или
переписать success criteria под фактический результат нельзя ни в одном режиме.

Exit criteria: success criteria из Phase 1 закрыты фактом прогона; coverage-gate и forbidden-patterns
пройдены либо провал явно назван в выходе; обратное ребро закрыто - каждое требование входа несёт
тест либо названный исход.

Mandatory: yes - зелёный прогон отдельных Pi не значит, что фича собрана целиком: регрессия живёт
на стыке шагов, а непокрытое требование без обратного ребра не наблюдаемо вовсе.

## Саморевью зоны - 3 обязательных прохода

Отвечает шагу 7 движка «Саморевью» для этой зоны: код-под-стек, архитектура, security - все три
обязательны, даже если предыдущие два прошли чисто. Код и архитектуру трек критически перечитывает
сам (`channel: self`) - автор правки уже coder-узел Phase 7, независимость от автора этим сохранена.
**Security - всегда отдельный узел** (`dex-security-reviewer:security-reviewer`), не трек и не тот же
coder: ревью своей же реализации автором или прокси-автором - дыра, независимого взгляда нет
(RED-проверено в движке).

## Интеграция с базой - слот перед сдачей

Перед Phase 8 (или сразу после, если ветка отстала от базы за время работы) - подтяни базовую ветку
через `dex-conflict-resolver:conflict-resolver`, не разрешай конфликты вручную построчно: тихая
потеря стороны - главный риск здесь, не сам факт конфликта. После слияния - обязательный пересбор и
перепрогон тестов, не доверие «зелёному» до слияния. «Взял свою сторону целиком» на конфликте -
решение, которое трек обязан обосновать в выходе, не принимать по умолчанию.

## Выход трека (handoff)

**Output (handoff):** первым полем `status` (словарь исхода - `node-contract`), затем: ветка и
перечень коммитов (sha + что в каждом); R/I и success criteria Phase 1 с исходом по каждому -
закрыт фактом прогона либо не закрыт с причиной; run-status build/test последнего прогона;
coverage-gate значением против порога; обратное ребро требование -> тест с исходом по каждому
требованию (Phase 8); под-вид работы и режим теста; допущения, каждое с источником вывода;
**решения, принятые за оператора, отдельным перечнем** - что решено, из чего выведено, что было
альтернативой; открытые наблюдения вне скоупа этой фичи; `quality-checks` (пришедшие сверху
переносятся как есть, записи по артефактам входа ставишь ты - их автором ты не являешься);
перечень незакрытого при `partial`/`blocked`.

Работа заканчивается на локальных коммитах: push, MR и мердж этот трек не делает - следующий шаг
`/self-review`, внешнее ревью на сданный MR ведёт `dex-skill-followup-track:followup-track`.
Читатель выхода - движок (шаг 8, сдача), не следующий трек напрямую: маршрут решает он.

**Exit criteria:** Output несёт все перечисленные поля; `complete` выдаётся только когда success
criteria закрыты фактом прогона и обратное ребро закрыто; иначе `partial`/`blocked` с перечнем.

**Mandatory:** yes - без сводного выхода сдача движка пересобирает состояние работы по памяти, а
принятые за оператора решения и незакрытые требования теряются молча.

## Переход в другой трек

Внешнее ревью на уже сданный MR этой фичи - это отдельный трек `dex-skill-followup-track:followup-track`,
не продолжение Phase 7/8: работа над найденным ревьюером переходом переоткрывается уже там, а не
здесь. «Разберись и почини» без отдельного тикета на баг - под-вид баг-фикс (Phase 1), не отдельный
аналитический трек: полная процедура, включая автономный разбор «что и почему», -
`dex-skill-bugfix-track:bugfix-track`, не повтор здесь.

## Boundaries

- Confidence ниже 80 в трактовке или подходе - вопрос оператору, не код по предположению.
- Тесты входят в скоуп правки: пишет их coder-узел инлайн по ходу своей правки (Phase 7); отдельный
  tester-узел - только добор покрытия сверх TDD (Phase 8), не замена инлайн-тестов.
- Конвенции проекта важнее общей «лучшей практики»; отступление без именованного прецедента - явное
  допущение в выходе, не тихая замена (гейт первоисточника, Phase 4).
- Не править файлы вне списка Pi edit-плана; замеченное рядом - в открытые наблюдения, не в скоуп
  этой фичи.
- Новая зависимость - только если ни один существующий механизм проекта не закрывает задачу, и выбор
  назван с причиной.
- Работа заканчивается на локальных коммитах: ни push, ни MR, ни merge - это `/self-review` и
  следующий шаг.
- Написание production-кода трек не берёт на себя даже временно - Phase 7 всегда узел под стек
  (см. вводный абзац); монолитное исполнение силами трека - дефект переноса, не сокращение пути.
