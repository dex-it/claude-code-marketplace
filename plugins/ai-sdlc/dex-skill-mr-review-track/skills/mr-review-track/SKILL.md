# MR Review Track

Трек ведёт чужой MR от указателя на него до опубликованных находок и закрытой ревизии; выход -
комментарии, не правки. Вызывается движком `dex-sdlc:engine` - отдельно от него не запускается:
движок ведёт цикл и стоп-линию, трек - порядок этой зоны.

**Исполнителя выбирает трек** по критерию движка («Как выбрать исполнителя»): diff точечный и
предмет один - трек судит сам, через явно поднятый профильный скилл, строкой `channel: self` с
причиной и именем скилла; иначе первичное ревью ведёт `dex-mr-reviewer:mr-reviewer`,
поверхность безопасности - `dex-security-reviewer:security-reviewer` отдельным узлом, не тем же
ревьюером; ре-ревью дельты -
`dex-mr-check-reviewer:mr-check-reviewer`. Работой трека остаются сбор входа, фокусы, приёмка находок
против кода, публикация и закрытие ревизии (`channel: self`).

**Не путать с «Обработкой ревью своего MR» (`dex-skill-followup-track:followup-track` `[справочно]`):**
там ревьюют меня, выход - правки; здесь ревьюю я, выход - треды.

**Возобновление.** Свёртка внутри прогона - «Возобновление» движка по auto-ledger; новый прогон
ledger не находит, порядок для него - «Восстановление между прогонами»
(`references/ledger-and-recovery.md` движка), включая исход, когда не восстановилось ничем. Носитель
состояния этой зоны: треды на хостинге и SHA прошедшей ревизии (`LAST_REVIEW_SHA`) - от него
считается дельта.

## Обзор фаз

| # | Фаза | Кто исполняет |
|---|---|---|
| 0 | Intake & Intent | трек (сам) |
| 1 | Review Fan-out | `dex-mr-reviewer:mr-reviewer` + `dex-security-reviewer:security-reviewer` |
| 2 | Coverage Focus | трек (сам) |
| 3 | Falsify | трек (сам) |
| 4 | Publish Threads | трек (сам), по санкции `publish` |
| 5 | Revision Close | трек (сам) + `dex-mr-check-reviewer:mr-check-reviewer` на дельте |

## Phase 0: Intake & Intent

Goal: собрать предмет ревью и источник намерения, против которого diff судится.

**Input (handoff):** контракт стыка - `dex-skill-node-contract:node-contract`. `[blocking]` указатели
на MR/PR (URL или ID) и `SHA` под ревью. Указателей нет -> `status: blocked` наверх. `[default-ok]` `mode` (дефолт `autonomous`), `publish` (дефолт
`false` - см. Phase 4), `intent` (источник намерения; не пришёл - берётся из аналитического корпуса,
расположение - сквозное поле, нет и его - вызови `Skill`
`dex-skill-project-docs-map:project-docs-map`), `quality-checks`, путь к журналу решений.

Канал доступа к хостингу - `node-contract`, `references/hosting-channel.md`. Код читается с диска в
ветке MR, не из текста handoff (`node-contract`, «Транспорт артефакта»).

Output: предмет ревью (`diff-scope` путями + база + SHA), источник намерения с адресом, режим и
санкция `publish`.
Exit criteria: diff получен и его объём назван числом файлов; источник намерения назван адресом либо
`intent: n/a` с причиной - «намерения не нашлось» без указания, где искали, исходом не является.

Mandatory: yes

## Phase 1: Review Fan-out

Goal: получить находки по осям - `language` (корректность), `architecture`, `business`,
`regressions`, `security`, `performance`. Имена осей - этот словарь: исход и находка адресуют ось
им, не переводом.

**Ось идёт в работу по характеру изменения, а не списком.** Какие оси задеты, решает исполнитель по
diff; незадетая ось не запускается и получает явный исход (`<ось>: n/a` + чего в diff нет), а не
молчание. Безусловный прогон всех осей на любом diff запрещён.

Делегируй `dex-mr-reviewer:mr-reviewer` на активные оси кода и
`dex-security-reviewer:security-reviewer` - на ось `security` отдельным узлом, когда diff её
задевает (аутентификация, авторизация, обработка внешнего ввода, секреты, граница доверия,
зависимости).

Output: находки от каждого узла с `anchor` (`file:line`), `severity`, `closure` (критерий закрытия) и
уликой; перечень осей с исходом каждой, включая `n/a` с основанием.
Exit criteria: каждая ось имеет исход - находки, явное «чисто, проверено X» либо `n/a` с названным
основанием; узел, который не отработал, назван вместе с тем, что из-за этого не проверено.

Mandatory: yes

## Phase 2: Coverage Focus

Goal: отдельно проверить, что изменённое поведение проверяется тестами.

Изменённое или новое поведение должно иметь тесты через реальный путь; нет покрытия, слабое или
тавтологичное покрытие, непокрытые краевые случаи - находка с `severity`, не молчание. Достаточность
меряй по осям - общий якорь движка `dex-sdlc:engine` [[P-axes]], механика - `dex-skill-test-track:test-track`
`[справочно]`. Один happy-path покрытием не считается.

Output: вердикт по покрытию diff с перечнем непокрытых веток; для каждой - находка либо явный исход
(покрыто на другом уровне - назвать каком | не проверяемо автотестом - причина).
Exit criteria: вердикт вынесен по всему изменённому поведению, а не по выборке файлов.

Mandatory: yes

**Тесты здесь не пишутся:** недостаток покрытия выносится находкой либо задачей на
`dex-skill-test-track:test-track` `[справочно]`.

## Phase 3: Falsify

Goal: опровергнуть каждую находку прежде, чем она попадёт автору.

Находка узла - claim, не факт. Сверь с кодом в ветке MR: не закрыта ли она соседним коммитом, не
опирается ли на неверное чтение контракта, воспроизводится ли описанный сценарий. Не выдержавшая
сверки находка снимается с указанием, чем опровергнута, - в выход трека, не в треды автору.

Output: перечень подтверждённых находок с уликой и перечень снятых с причиной снятия.
Exit criteria: каждая находка Phase 1-2 либо подтверждена уликой, либо снята с названной причиной;
находок без исхода нет.

Mandatory: yes

## Phase 4: Publish Threads

Goal: донести подтверждённые находки до автора инлайн-тредами.

**Публикация в чужой MR - outward-facing действие: право даёт санкция, не режим**
(`node-contract`, «Outward-facing действие = явная санкция»). При канале (тело исполняет главный
цикл, `interactive`) санкцию даёт команда оператора на сам акт; при спавне узлом (любой `mode`) - поле
`publish: true` во входе. Санкции нет -> находки идут в выход трека перечнем, готовым к публикации, и
трек называет это явно.

Бизнес- или intent-неясность по diff -> тред-вопрос автору (async), остальное публикуй не вставая в
ожидание. Технику и качество не спрашивают - выносят находкой.

Output: опубликованные треды с адресами либо готовый к публикации перечень; `severity` и `closure` в
каждом.
Exit criteria: каждая подтверждённая находка имеет тред либо строку в перечне; канал хостинга отказал
- назови, что не опубликовано, и верни находки в выходе, не теряй их.

Mandatory: yes

## Phase 5: Revision Close

Goal: закрыть ревизию - разобрать ответы автора и проверить дельту.

**Ответ автора - claim, не факт**: вердикт «поправил» и довод «так задумано» верифицируются чтением
кода до снятия находки. Не подтвердилось - находка остаётся открытой с уликой.

Вторая ревизия -> `dex-mr-check-reviewer:mr-check-reviewer` на дельту (`range-diff` от SHA прошлого
ревизии), не первичному ревьюеру.

Output: статус каждой находки (закрыта правкой - коммит назван | закрыта доводом, проверенным по коду |
остаётся открытой | отложена с владельцем); вердикт по дельте; решение ревизии.
Exit criteria: находок без статуса нет; ревью закрывается по разрешённым тредам, а не по факту
публикации. Автор молчит - не блокируйся: статус трека `partial` с поимённым перечнем, чего ждём.

Mandatory: yes

## Режимы

Режим совпадает с ярусом: трек грузится в тело исполнителя, `interactive` адресует возврат
оператору. Состав фаз он не меняет: `interactive` - неясность решения о severity или снятии находки
предъявляется оператору; `autonomous` - решение принимается и идёт в выход перечнем «принято за
оператора». От режима не зависит одно: intent-неясность по diff всегда идёт тред-вопросом автору
(Phase 4, async), а не блокирующим диалогом с оператором. Право на публикацию режимом не выдаётся -
только полем `publish` (Phase 4).

Вниз режим едет тем же значением во все делегированные вызовы: узлу - планка эскалации, канал к
оператору остаётся у трека (`node-contract`, D.11).

## Выход трека (handoff)

**Output:** первым полем `status` (словарь исхода - `node-contract`), затем: предмет ревью (MR/PR,
SHA, объём diff); источник намерения либо `intent: n/a` с причиной; подтверждённые находки с
`anchor`/`severity`/`closure`/уликой; снятые находки с причиной снятия; вердикт по покрытию;
исход фокуса безопасности; опубликованные треды с адресами либо перечень неопубликованного с
причиной; статус каждой находки после ответов автора; вердикт по дельте второй ревизии; допущения;
решения, принятые за оператора, отдельным перечнем; сквозные поля входа как есть; перечень
незакрытого при `partial`/`blocked`.

Читатель выхода - движок (шаг 8, сдача); правки по находкам ведёт автор MR своим треком
(`dex-skill-followup-track:followup-track` `[справочно]`).

**Exit criteria:** Output несёт все перечисленные поля; `complete` выдаётся только когда каждая
находка имеет статус и каждый фокус - исход; иначе `partial`/`blocked` с перечнем.

**Mandatory:** yes

## Boundaries

- Read-only: код трек не правит и тесты не пишет ни в одном режиме.
- Публикация в чужой MR - только по санкции (Phase 4), ни в одном режиме без неё.
