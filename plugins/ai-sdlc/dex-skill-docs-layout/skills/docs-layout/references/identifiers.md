# Идентификаторы корпуса и трассировка

## Схема

| Жанр | ID | Дом ID |
|---|---|---|
| BRD продукта | `BR-NNN` | единственный BRD продукта |
| BRD фичи | `BR-NNN` из того же пространства, блок номеров за фичей | BRD своей фичи |
| Use Case | `UC-{ФИЧА}-NNN` | файл на сценарий |
| SRS | `FR-NNN`, `NFR-NNN` - сквозные по корпусу, за фичей закреплён блок номеров | SRS своей фичи |
| story | `ST-NNN` из блока своей фичи | файл на историю в `stories/` своей фичи |
| use case | `UC-{ФИЧА}-NNN`, где `{ФИЧА}` - **слаг папки фичи в верхнем регистре без номера** (`01-installation` -> `INSTALLATION`), сокращения не изобретаются | файл на сценарий в папке фичи |
| ADR | `ADR-NNNN`, сквозной, номера не переиспользуются | файл на решение |
| `.feature` (производная форма) | тег со ссылкой на `FR-NNN` плюс шапка «источник и его ревизия» | файл на фичу |

Норма самой нумерации живёт не здесь: продолжение сквозной последовательности по принятым требованиям корпуса - предмет этапа требований, здесь только схема и распределение блоков.

> см. dex-skill-project-docs-map:project-docs-map - сверка с принятым при чтении чужого корпуса

## Трассировка

Цепочка: `BR` продукта -> `BR` фичи -> `FR`/`NFR` -> story с AC. Use case разворачивает `FR` своей фичи и ссылается на него. В воздухе не висит ничего: у требования фичи есть родитель уровнем выше.

**`.feature` стыком цепочки не является.** Файл производен от AC истории и держится ссылкой на её ревизию; тег `FR-NNN` в нём - удобство навигации и разрешимость при падении, а не звено трассы. Считать его звеном значило бы считать покрытие требования дважды: один раз по AC на гейте stories, второй по собранному из тех же AC тексту.

Отдельного сквозного реестра-файла не заводим: карта трассировки собирается из корпуса и вердикта не несёт - судится набор SRS, а не карта.

**Вниз трасса атрибутом не хранится.** Требование несёт `traced from` вверх, ссылки вниз нет ни у кого. Значит обратный обход - «что производно от `BR-101`» - делается поиском по корпусу, и он работает ровно до тех пор, пока идентификаторы стабильны.

**Ищется идентификатор, а не поле `traced from`, и это не придирка к формулировке.** Ссылку вверх звенья носят в разных формах: `BR` фичи и `FR` - полем `traced from`; story - меткой `[FR-NNN]` внутри текста AC; use case - перечнем в разделе трассировки и меткой у расширения; `.feature` - тегом `@FR-NNN`. Поиск по строке `traced from` найдёт один класс производных из четырёх и отчитается пустым результатом там, где производных трое. Замер на модельном корпусе: у `FR-102` поиск по полю дал ноль файлов при трёх реально ссылающихся документах. Это дополнительный довод против префиксных ID: переезд требования между фичами переписал бы номер, и обратный обход порвался бы на всех, кто на него ссылался.

## Дом `FR`/`NFR`: SRS своей фичи при сквозном номере

Расположение и номер отвечают на разные вопросы, и разводить их - осознанное решение, а не недосмотр.

- **Дом - SRS своей фичи.** Дома-файла для требования каталог до этого не предписывал: упоминание `docs/requirements/` в карте документации - список мест, где ищут **чужой** корпус, а не указание, куда писать свой.
- **Форма ID остаётся сквозной** - `FR-NNN`, `NFR-NNN` по всему корпусу. Идентификатор - вечный якорь трассировки: на него ссылаются `.feature`, ADR и тесты.
- **Префиксный ID вида `SRS-INST-FUNC-001` отвергнут.** Границы фич подвижны - таблица границ сама показывает спорные места, - и переезд требования между фичами переписывал бы номер сразу в четырёх местах.
- **Принадлежность фиче несёт расположение и атрибут `feature`**, не номер. Читаемость сохраняется, якорь остаётся.
- **Параллельная работа без коллизий** - за фичей закрепляется блок номеров (installation 100-199, configuration 200-299) при едином пространстве.

Блок выдаётся вместе с папкой фичи и записывается рядом с таблицей границ: два аналитика, начавшие с `FR-001` в разных фичах, дают коллизию, которую видно только при слиянии.
