# Целевое дерево корпуса

Корпус живёт в `docs/` в корне решения. Отдельного репозитория документации нет; глубина - не больше трёх уровней от `docs/`.

## Правило размещения

- **`01-product` делится по фичам целиком**: на фичу папка, в ней BRD фичи, SRS фичи, `stories/` и журнал решений. Общий BRD продукта лежит файлом на уровне `01-product` - бизнес-требования фич выводятся из его списка, а не заводятся заново.
- **Истории живут в папке своей фичи, а не отдельным разделом**: они нарезка `FR` той же фичи и переезжают вместе с ней. Вынос историй наверх повторил бы ошибку префиксного ID - подвижная граница фичи потребовала бы переносить файлы.
- **Журнал решений один на фичу и лежит рядом с её BRD** (`decisions-{фича}.md`). Продуктового журнала нет: решения уровня продукта принимаются на гейте BRD продукта и пишутся в журнал той фичи, чей прогон их вызвал, - второй журнал рядом с общим BRD разошёлся бы с первым молча.
- **PRD отдельным жанром не заводится**: документ, который в наброске звался PRD фичи, - это BRD уровня фичи. Один жанр, уровень различает путь.
- **Use cases вынесены отдельным разделом** с папкой на фичу: сценариев на фичу несколько, и они разворачивают требования, а не повторяют их. Имя папки - слаг фичи без номера (`03-hub-core` -> `hub-core`), тот же слаг стоит в идентификаторе сценария: сокращать его на своё усмотрение нельзя, иначе папка и ID разъезжаются и обратный обход по идентификатору перестаёт находить файл.
- **BRD продукта, SAD и план верификации по фичам не дробятся**: дробление заставило бы дублировать общее.
- **ADR по папкам фич не раскладывается вовсе**: одно решение задевает несколько фич сразу. Привязка - поле шапки `relates_to: hub, operation`.
- **Контракты интерфейсов в `docs/` не лежат** - их дом рядом с кодом (`api/`, `proto/`), архитектура несёт только ссылку.
- **`{фича}` в именах файлов - слаг без номера.** Папка несёт номер (`01-installation`), имя файла внутри неё - нет (`BRD-installation.md`, `SRS-installation.md`, `decisions-installation.md`): номер папки меняется при перестановке фич, и имя файла тянуть за ним значит переписывать ссылки.
- **Глубина не больше трёх уровней** от `docs/`; префикс фичи в имени файла заменяет вложенность для поиска.
- **Границы фич объявляются явно до написания SRS**, иначе SRS и use cases соседних фич перекрываются. Форма - таблица «фича / покрывает / не покрывает» рядом с корпусом.

## Минимум обязательного

Таблица «какой жанр обязателен всегда, какой по размеру фичи» живёт в `SKILL.md`, блок 3, и здесь не дублируется: две копии одного перечня расходятся молча, а расхождение всплывает на приёмке корпуса.

## Формат идеи: one-pager, дорастающий до canvas

Идея входит в корпус одним файлом `IDEA-NN-{слаг}.md`, формат меняется по мере созревания и объявляется полем `format` в шапке. Обязательное поле ровно одно - статус: отклонённое не должно обсуждаться заново через полгода.

- **one-pager (proposal)** - четыре блока на страницу: идея одной фразой, польза и кому, порядок величины усилий, что станет понятно после проверки. Цель формата - не потерять мысль и дать её обсудить, а не описать решение.
- **opportunity canvas (brief)** - тот же файл, когда идею начали разбирать: проблема, кто страдает, как решают сегодня, гипотеза решения, как поймём что сработало, риски.

**Переход в конвейер.** Canvas со статусом «принято» порождает фичу: она получает номер и папку в `01-product/`, гипотеза решения переезжает в BRD фичи бизнес-требованиями, «как поймём что сработало» становится их MOE, риски - входом в раздел рисков BRD. Идея, не дошедшая до принятия, остаётся в `00-strategy` со своим статусом и никуда не тянется.

Идея оракулом не судится, порога `approved` не берёт и входом гейта не является: судить незрелую мысль нечем, а требовать от неё состава - способ отбить желание её записывать.
