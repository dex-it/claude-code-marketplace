# Раскладка корпуса документации

Предмет - **куда кладётся документ и что обязательно завести**. Содержание документа здесь не пишется и не судится: состав жанра даёт норматив своего этапа, вердикт - оракул типа.

| Условие | Файл |
|---|---|
| раскладываешь корпус, разворачиваешь заготовку, сверяешь чужое дерево с целевым | `references/tree.md` |
| заводишь идентификатор, распределяешь блок номеров, строишь трассировку | `references/identifiers.md` |

Оба **читать до записи в корпус**, по памяти дерево не воспроизводить: расхождение в одном уровне разводит документы по двум местам, и это обнаруживается на следующем этапе, когда ссылки уже проставлены.

## 1. Дерево верхнего уровня

| Каталог | Что несёт | Дробится по фичам |
|---|---|---|
| `00-strategy/` | идеи: one-pager и opportunity canvas, статус каждой | нет, файл на идею |
| `01-product/` | BRD продукта плюс папка на фичу: BRD и SRS фичи, `stories/` с историями и AC, журнал решений фичи | **да, целиком** |
| `02-use-cases/` | сценарии: папка на фичу, файл на сценарий | да |
| `03-architecture/` | `design/` - SAD продукта, `adr/` - решения | нет |
| `04-verification/` | план верификации продукта, `bdd/` - `.feature` на фичу | нет, дробится только `bdd/` |

Полное дерево с именами файлов - `references/tree.md`. Имена фич там иллюстративны: переносится структура, не набор фич.

## 2. Правило размещения

Решения, из которых выводится всё остальное:

- **уровень различает путь, а не жанр.** BRD продукта и BRD фичи - один жанр на двух уровнях; отдельного PRD нет;
- **что общее для продукта, по фичам не дробится** - BRD продукта, SAD, план верификации. Дробление заставило бы дублировать общее;
- **ADR не раскладывается по фичам вовсе**: одно решение задевает несколько фич сразу, привязка идёт полем шапки `relates_to`, а не расположением;
- **контракты интерфейсов вне `docs/`** - дом рядом с кодом (`api/`, `proto/`), архитектура несёт ссылку;
- **глубина не больше трёх уровней** от `docs/`; префикс фичи в имени файла заменяет вложенность.

Границы фич объявляются явно **до** написания SRS: без них SRS и use cases соседних фич перекрываются, а обнаруживается это при первом же противоречии требований.

## 3. Минимум обязательного

Норма без этого блока читается как «пиши всё», и корпус не заводят вовсе.

| Жанр | Когда обязателен |
|---|---|
| BRD продукта, BRD фичи, SRS фичи | всегда |
| истории с AC (`stories/` фичи) | всегда: покрытие требований считается по AC и только по ним |
| журнал решений фичи | всегда, когда фича прошла хотя бы один гейт |
| ADR | всегда, когда решение выбрано из альтернатив |
| Use Case, формат `normative` | фича со сценарным поведением, а не одна операция |
| SAD | продукт целиком, обновляется при смене устройства |
| план верификации | фича идёт в регресс |

**`.feature` в обязательные не входит.** Это производная форма AC истории, собираемая по явному запросу (`/bdd`), а не жанр корпуса: своего содержания не несёт, порога `approved` не берёт, покрытия не добавляет. Её отсутствие пробелом корпуса не является ни при каком условии; её наличие обязывает только к одному - шапка называет источник и ревизию, по которой файл собран.

**Эскиз UC отдельным жанром не считается.** Это тот же файл в рабочем формате (`format: sketch`), заводимый при выводе требований и дорастающий до нормативного; второго документа рядом не появляется, отдельной папки под черновики нет. Обязательность в таблице относится к нормативному формату: фича со сценарным поведением, у которой файл остался эскизом, - пробел корпуса, а не заготовка.

Отсутствие жанра, которого в таблице нет, дефектом раскладки не является. Отсутствие обязательного всегда либо обязательного по условию, когда условие выполнено, - пробел корпуса: он называется пунктом выхода, а не восполняется молча этим skill.

## 4. Идентификаторы

`BR-NNN` (оба уровня), `UC-{ФИЧА}-NNN`, `FR-NNN` и `NFR-NNN`, `ST-NNN` (история), `ADR-NNNN`. Дом требования - SRS своей фичи, при этом номер остаётся **сквозным** по корпусу, а за фичей закрепляется блок (installation 100-199, configuration 200-299). Принадлежность фиче несёт расположение и атрибут `feature`, не номер.

**Блок распространяется на все единицы со сквозным номером**: истории фичи 01 идут `ST-101`, `ST-102` - иначе два прогона по разным фичам выдадут по `ST-001`, и коллизия всплывёт при слиянии, когда ссылки уже проставлены. `UC` в блоке не нуждается: имя фичи стоит в самом идентификаторе, и нумерация внутри него локальная, с `001`.

Норма самой нумерации живёт не здесь - её предмет этап требований; здесь схема, распределение блоков и цепочка трассировки. Разбор, почему префиксный ID отвергнут, и полная схема - `references/identifiers.md`.

## 5. Процедура

Порядок обязателен: пропуск первого шага даёт запись в чужой корпус либо второй корпус рядом с существующим.

1. **Установить, где корпус.** Ответ даёт правило карты документации проекта: раздел путей в `CLAUDE.md`, при его отсутствии - поиск по стандартным местам с проверкой принадлежности проекту. Этот skill его не запускает - механизма «skill вызывает skill» не существует; карту грузит ведущий работу узел, либо путь приходит на входе. Ответа нет ни оттуда, ни со входа -> корпус считается ненайденным, переход на шаг 3.
   > см. dex-skill-project-docs-map:project-docs-map
2. **Сверить найденное с деревом** (`references/tree.md`): какие каталоги есть, какие пусты, какой документ лежит не на своём уровне. Результат сверки - список, а не суждение о качестве документов.
3. **Корпуса нет -> предложить развернуть заготовку**: каталоги дерева плюс `docs/README.md` с картой «какой документ на какой вопрос отвечает». Заготовка разворачивается **пустой**: файлы жанров создаёт их этап, а не этот шаг. Предложение отклонено или согласия спросить не у кого -> путь и причина идут пунктом выхода, дерево не создаётся. **Разворачивает тот узел, который держит расположение сквозным полем** - в зоне требований это дирижёр. Составитель, дошедший до этого шага, дерева не создаёт даже при наличии согласия: два составителя, начавшие параллельно, дадут две папки с одним номером фичи, и разойдутся они молча.
4. **Корпус разложен иначе -> назвать расхождения списком**, по каждому: что лежит, где лежит, куда легло бы по дереву. Перенос - решение владельца корпуса, отдельное от этой сверки: молча не переносить, чужую раскладку целевой не подменять. Расхождений нет -> сказать это явно, молчание читается как непройденная сверка.

## 6. Границы

- **не судит содержание документа** - вердикт даёт оракул типа по реестру контракта узла, а раскладка отвечает только за место;
- **не пишет документы** - состав каждого жанра держит норматив его этапа;
- **не заводит требования и не присваивает номера** - здесь схема ID, не нумерация;
- **не подменяет карту документации проекта**: та отвечает «где корпус в этом проекте» и ведёт раздел путей в `CLAUDE.md`, этот skill - «куда класть новое и чего не хватает». Раздел путей дублировать нельзя, иначе два источника разойдутся.
