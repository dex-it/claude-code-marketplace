# Раскладка корпуса документации

Предмет - **куда кладётся документ и что обязательно завести**. Содержание документа здесь не пишется и не судится: состав жанра даёт норматив своего этапа, вердикт - оракул типа.

| Условие | Файл |
|---|---|
| раскладываешь корпус, разворачиваешь заготовку, сверяешь чужое дерево с целевым | `references/tree.md` |
| заводишь идентификатор, распределяешь блок номеров, строишь трассировку | `references/identifiers.md` |

Оба **читать до записи в корпус**, по памяти дерево не воспроизводить: расхождение в одном уровне разводит документы по двум местам, и это обнаруживается на следующем этапе, когда ссылки уже проставлены.

## 1. Дерево верхнего уровня

| Каталог | Что несёт | Ключ | Дробится по фичам |
|---|---|---|---|
| `00-strategy/` | идеи: one-pager и opportunity canvas, статус каждой | `strategy` | нет, файл на идею |
| `01-product/` | BRD продукта, доменная модель, конституция; ниже - папка на каждую фичу | `product`, `domain`, `root` | нет |
| `01-product/<NN>-<слаг>/` | корпус фичи: BRD и SRS фичи, `stories/` с историями и AC, журнал решений | раскрытие `root` | **да, целиком** |
| `02-use-cases/` | сценарии: папка на фичу, файл на сценарий | `usecases` | да |
| `03-architecture/design/` | SAD продукта и дизайн-документы | `specs` | нет |
| `03-architecture/adr/` | решения, привязка к фичам полем шапки | `adr` | нет |
| `04-verification/` | план верификации продукта, `bdd/` - `.feature` на фичу | `verification` | нет, дробится только `bdd/` |
| `05-plans/` | планы реализации: файл на прогон, имя несёт задачу | `plans` | нет |
| `.req_counter/` | счётчик номеров, файл на ключ | `counter` | нет |

Полное дерево с именами файлов - `references/tree.md`. Имена фич там иллюстративны: переносится структура, не набор фич.

**Полнота дерева меряется ключами файла путей**, а не жанрами: каждый ключ `.docs_layout` обязан встретиться в колонке «Ключ». Ключ адресует класс, а не строку дерева: значение ключа целиком ложится в файл путей, поэтому каталог с шаблоном `<NN>-<слаг>` ключом не адресуется - он стоит раскрытием того, у которого ключ есть, и фича ищется в нём по номеру. Класс, у которого ключ есть, а места в дереве нет, разложат по догадке - и заводить его вторым деревом уже поздно. Ключ - адрес, каталог - дефолт: на занятом корпусе первый ведёт ко второму, а не наоборот.

**Несколько адресов на один каталог штатны.** В дефолтном дереве `root`, `product` и `domain` дают один путь, и уровень 0 отличается от корпуса фичи не каталогом, а местом в нём: фича лежит папкой `<NN>-<слаг>`, уровень 0 - файлами рядом с этими папками. Обход набора фичи идёт по её папке, поэтому уровень 0 в него не попадает; на занятом корпусе пути расходятся, и решает ключ.

## 2. Правило размещения

Решения, из которых выводится всё остальное:

- **уровень различает путь, а не жанр.** BRD продукта и BRD фичи - один жанр на двух уровнях; отдельного PRD нет;
- **что общее для продукта, по фичам не дробится** - BRD продукта, SAD, план верификации. Дробление заставило бы дублировать общее;
- **ADR не раскладывается по фичам вовсе**: одно решение задевает несколько фич сразу, привязка идёт полем шапки `relates_to`, а не расположением;
- **контракты интерфейсов вне `docs/`** - дом рядом с кодом (`api/`, `proto/`), архитектура несёт ссылку;
- **глубина не больше трёх уровней** от `docs/`; префикс фичи в имени файла заменяет вложенность.

Границы фич объявляются явно **до** написания SRS: без них SRS и use cases соседних фич перекрываются, а обнаруживается это при первом же противоречии требований.

## 3. Минимум обязательного

Норма без этого блока читается как «пиши всё», и корпус не заводят вовсе.

| Жанр | Когда обязателен |
|---|---|
| BRD продукта, BRD фичи, SRS фичи | всегда |
| истории с AC (`stories/` фичи) | всегда: покрытие требований считается по AC и только по ним |
| журнал решений фичи | всегда, когда фича прошла хотя бы один гейт |
| ADR | всегда, когда решение выбрано из альтернатив |
| Use Case | фича со сценарным поведением, а не одна операция |
| SAD | продукт целиком, обновляется при смене устройства |
| план верификации | фича идёт в регресс |

**`.feature` в обязательные не входит.** Это производная форма AC истории, собираемая по явному запросу (`/bdd`), а не жанр корпуса: своего содержания не несёт, порога `approved` не берёт, покрытия не добавляет. Её отсутствие пробелом корпуса не является ни при каком условии; её наличие обязывает только к одному - шапка называет источник и ревизию, по которой файл собран.

Отсутствие жанра, которого в таблице нет, дефектом раскладки не является. Отсутствие обязательного всегда либо обязательного по условию, когда условие выполнено, - пробел корпуса: он называется пунктом выхода, а не восполняется молча этим skill.

## 4. Идентификаторы

`BR-NNN` (оба уровня), `UC-{ФИЧА}-NNN`, `FR-NNN` и `NFR-NNN`, `ST-NNN` (история), `ADR-NNNN`. Дом требования - SRS своей фичи, при этом номер остаётся **сквозным** по корпусу, а за фичей закрепляется блок в тысячу номеров - фича `01` нумерует с `1001`, фича `02` с `2001` (дом нормы - `dex-skill-unit-identity:unit-identity`). Принадлежность фиче несёт расположение и атрибут `feature`, не номер.

**Блок распространяется на все единицы со сквозным номером**, `UC` в том числе: истории фичи 01 идут `ST-1001`, `ST-1002`, сценарии - `UC-{ФИЧА}-1001`, `-1002`. Иначе два прогона по разным фичам выдадут по `ST-001` и по `UC-...-001`, и коллизия всплывёт при слиянии, когда ссылки уже проставлены. Номер выдаёт счётчик ключом своего класса (`NN.UC`, `NN.ST`), а не подсчёт файлов в папке; слаг фичи в идентификаторе `UC` - читаемость и обратный обход, не второй способ нумерации.

Норма самой нумерации живёт не здесь - её предмет этап требований; здесь схема, распределение блоков и цепочка трассировки. Разбор, почему префиксный ID отвергнут, и полная схема - `references/identifiers.md`.

## 5. Процедура

Порядок обязателен: пропуск первого шага даёт запись в чужой корпус либо второй корпус рядом с существующим.

1. **Установить, где корпус.** Ответ даёт карта документации проекта `dex-skill-project-docs-map:project-docs-map`: ключи файла путей `.docs_layout` в корне репозитория, при его отсутствии - поиск по стандартным местам с проверкой принадлежности проекту. Этот skill её не запускает - механизма «skill вызывает skill» не существует; карту грузит ведущий работу узел, либо путь приходит на входе. Ответа нет ни оттуда, ни со входа -> корпус считается ненайденным, переход на шаг 3.

   **Адресуют корпус ключи, а не имена каталогов отсюда.** Дерево ниже - дефолт для пустого места; развернули заготовку - ключи дописываются тем же действием, и дальше путь берётся из них. Занятый корпус диктует раскладку сам, и его имена сильнее этого дерева.
2. **Сверить найденное с деревом** (`references/tree.md`): какие каталоги есть, какие пусты, какой документ лежит не на своём уровне. Результат сверки - список, а не суждение о качестве документов.
3. **Корпуса нет -> предложить развернуть заготовку**: каталоги дерева плюс `docs/README.md` с картой «какой документ на какой вопрос отвечает». Заготовка разворачивается **пустой**: файлы жанров создаёт их этап, а не этот шаг. Предложение отклонено или согласия спросить не у кого -> путь и причина идут пунктом выхода, дерево не создаётся. **Разворачивает тот узел, который держит расположение сквозным полем** - в зоне требований это трек (`dex-skill-analytics-track:analytics-track` `[справочно]`), не составитель. Составитель, дошедший до этого шага, дерева не создаёт даже при наличии согласия: два составителя, начавшие параллельно, дадут две папки с одним номером фичи, и разойдутся они молча.
4. **Корпус разложен иначе -> назвать расхождения списком**, по каждому: что лежит, где лежит, куда легло бы по дереву. Перенос - решение владельца корпуса, отдельное от этой сверки: молча не переносить, чужую раскладку целевой не подменять. Расхождений нет -> сказать это явно, молчание читается как непройденная сверка.

## 6. Границы

- **не судит содержание документа** - вердикт даёт оракул типа по реестру контракта узла, а раскладка отвечает только за место;
- **не пишет документы** - состав каждого жанра держит норматив его этапа;
- **не заводит требования и не присваивает номера** - здесь схема ID, не нумерация;
- **не подменяет карту документации проекта**: та отвечает «где корпус в этом проекте» и ведёт файл путей `.docs_layout`, этот skill - «куда класть новое и чего не хватает». Ключи дублировать нельзя, иначе два источника разойдутся;
- **не ставит метку и не ведёт ревизию** - это `dex-skill-node-contract:node-contract`: метка `quality-checks`, пороги и потолок ревизий.
