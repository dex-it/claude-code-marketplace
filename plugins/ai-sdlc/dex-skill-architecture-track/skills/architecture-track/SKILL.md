# Architecture Track

Трек ведёт бизнес-задачу (или выход зоны требований) от требований до одобренного design-документа -
входа трека «Разработка», не до кода. Вызывается движком `dex-sdlc:engine` (`/design`) - трек не
запускается отдельно от него, движок ведёт цикл и стоп-линию, трек - порядок этой зоны.

**Архитектурное решение трек не делает сам.** Match / alternatives / decide / deep-dive - работа
узла `dex-architect:architect` (стек-нейтральный) или `dex-architect-dotnet:architect-dotnet`
(.NET) - монолит-оркестратор, решающий архитектуру силами трека, дублирует движок и теряет
специализацию узла (тот же failure mode, что у development-track с кодом). Требования, capacity,
implementation-план и диспетчинг документации (Phase 0-1-2-4-5) - работа трека (`channel: self`);
дизайн-решение (Phase 3) и приёмка (Phase 6) - всегда делегированы.

## Обзор фаз

| # | Фаза | Кто исполняет |
|---|---|---|
| 0 | Bootstrap | трек (сам) |
| 1 | Understand Requirements | трек (сам) |
| 2 | Capacity Estimation | трек (сам) |
| 3 | Design Decision | `architect` / `architect-dotnet` по стеку |
| 4 | Implementation Plan | трек (сам) |
| 5 | Document | `adr-writer` / `api-designer` / `diagram-creator`, условно |
| 6 | Design Acceptance | `design-reviewer` |

## Phase 0: Bootstrap

Goal: восстановить контекст репо и уже принятые решения раньше любого нового шага - не дать Phase 1
переоткрыть то, что решено.

Output: recall sources (`CLAUDE.md` / init-сообщения / прежний диалог, либо явная пометка
«greenfield»); стек проекта по манифесту затронутой папки (`*.csproj`/`*.sln` -> `dotnet`, иначе
стек-нейтрально - решает выбор узла в Phase 3); перечень `Accepted` ADR и путь к журналу решений
через `dex-skill-project-docs-map:project-docs-map`; классификация запроса - новый дизайн или
дельта-прогон над уже принятым решением (найдено совпадение в журнале/ADR -> дельта, см. Phase 1).

Exit criteria: источники контекста названы явно; корпус недостижим -> `unverifiable` + путь, где
искали, не молчание.

Skip_if: все источники контекста пусты **и** поиск ADR/журнала по стандартным местам
(`project-docs-map` п.2) пуст - тогда фаза сворачивается в строку «greenfield, контекста нет» с
названными путями поиска, переход в Phase 1.

Mandatory: yes - без recall Phase 1 запрашивает то, что уже решено, и Phase 3 получает контекст,
расходящийся с реальным репо.

## Phase 1: Understand Requirements

Goal: перевести бизнес-задачу (или выход зоны требований) в проверяемые FR/NFR и security/data-sensitivity
слоты - вход для Phase 2/3.

**Input (handoff):** контракт стыка - `dex-skill-node-contract:node-contract`. Принимаемые поля:
`[blocking]` постановка - бизнес-задача **либо** полный набор зоны требований (`FR-NNN`/`NFR-NNN`
+ user stories с метками, из `/feature`); вход только BRD (`BR-NNN`+MOE, без системного уровня) -
принимается, но `FR`/`NFR` выводит эта фаза сама с пометкой «звено зоны требований не пройдено» и
рекомендацией прогнать `/feature` - молча засчитывать выведенное за набор зоны требований запрещено, метки
`quality-checks` у него нет. `[default-ok]` NFR (DAU/latency/consistency/data-sensitivity),
constraints (команда, compliance, стек), `mode` (дефолт `autonomous`), `quality-checks` от
составителя. Постановка отсутствует -> halt + возврат оркестратору (нечего проектировать); NFR/
constraints не заданы -> обоснованные дефолты, допущением в Output.

**Входная приёмка по метке** (`node-contract` раздел C п.9): вход несёт
`{artifact: BRD|stories|requirements, check: requirement-quality, verdict: passed}` -> доверяй
метке, не дублируй полный обход (находка вопреки метке -> `contradicted`, `status: blocked`,
возврат вызывающему). Метки нет либо `verdict != passed` -> прогони `dex-skill-requirement-quality:
requirement-quality` сам в этой фазе.

**Сверка с журналом решений - до предъявления** (`node-contract`, «Журнал решений»): развилка
Phase 0 классифицирована как дельта -> найди её в журнале/`Accepted` ADR раньше вопроса; найдена -
решение действует, повторный вопрос запрещён; нужен пересмотр - назови отменяемую запись и
переоткрытый риск явно.

Output: JTBD, top 3-5 FR, NFR (DAU/MAU, latency P50/P95/P99, availability, consistency tolerance),
security & data sensitivity (классификация данных, authN/authZ модель, secrets handling, audit log,
threat model), constraints (команда, compliance, существующий стек), success metrics.

Exit criteria: каждый слот заполнен явным ответом либо пометкой «не определено».

**Гейт (блокирующий - см. «Режимы и гейты» ниже):** бюджетная/продуктовая рамка и приоритет между
конфликтующими NFR - решение оператора в `interactive` (работа встаёт до ответа), в `autonomous` -
`partial` с перечнем несогласованного (внешний оракул недостижим, движок сам не решает). Все прочие
слоты - неблокирующие: `interactive` - вопрос-с-предложением, работа идёт на предложенном варианте
если оператор не возразил; `autonomous` - обоснованный дефолт, допущением в Output.

Mandatory: yes.

В этой фазе загружай императивно: `dex-skill-nfr:nfr`, `dex-skill-requirement-quality:
requirement-quality`.

## Phase 2: Capacity Estimation

Goal: back-of-envelope read/write QPS, storage, bandwidth - опора для выбора storage/cache/sharding
в Phase 3.

Output: таблица расчётов с явными допущениями.

Exit criteria: цифры зафиксированы; `interactive` - подтверждены оператором (порядок величин),
`autonomous` - обоснованы допущениями (подтверждать некому). Неблокирующий гейт (см. таблицу ниже).

Mandatory: yes.

В этой фазе загружай императивно: `dex-skill-capacity-planning:capacity-planning`.

## Phase 3: Design Decision (delegated)

Goal: получить архитектурное решение - match / alternatives / decide / deep-dive - от
специализированного узла; трек само решение не принимает и не переигрывает.

**Диспетчинг по стеку** (реестр держит трек, механизм - «Как выбрать исполнителя» движка):
манифест затронутой папки несёт `*.csproj`/`*.sln`/`Directory.Build.props` -> `dex-architect-dotnet:
architect-dotnet`; иначе -> `dex-architect:architect`. Монорепо - по папке, не по корню.

Input узлу: FR/NFR (Phase 1), цифры (Phase 2), constraints, `mode`, `quality-checks`, `Accepted` ADR
+ путь к журналу решений (Phase 0). Узел исполняет свой внутренний порядок (Reference Architecture
Match -> Propose Alternatives -> Decide -> Deep Dive) и отдаёт по `node-contract`: `status`, дизайн-
решение (выбранная альтернатива + отвергнутые + CAP/PACELC trade-off), deep-dive разделы,
`quality-checks`, `self-check`, `fact-check`, допущения, свои строки в журнал решений (дописывает
сам - `node-contract`, «каждый узел, принявший решение... свои строки»).

**Гейт (см. «Режимы и гейты» ниже):** выбор между технически равными альтернативами и содержание
deep-dive - неблокирующий: `interactive` - трек предъявляет решение с обоснованием и идёт дальше на
предложенном варианте, явного апрува не ждёт. Узел в ходе Deep Dive вскрыл бюджетную рамку или
конфликт NFR-приоритетов, не видный в Phase 1 -> `status: blocked` (правило стыка, бизнес-природа) -
трек эскалирует как блокирующий гейт этой фазы тем же путём, что Phase 1.

Exit criteria: `status: complete` от узла. `blocked`/`partial` - трек не переходит в Phase 4:
`interactive` - предъявляет блокер оператору, `autonomous` - `partial` наверх с перечнем.

Mandatory: yes.

## Phase 4: Implementation Plan

Goal: разложить принятое в Phase 3 решение на исполнимые инкременты - вход трека «Разработка».

Output: инкременты в логической последовательности (walking skeleton -> vertical slices ->
scale-out, состав по решению Phase 3, не процедурно); на каждый - scope, dependencies, risks, DoD,
success metric, критерии приёмки инкремента с метками `[FR-NNN]`/`[NFR-NNN]` (`FR`/`NFR` без
критерия - дыра спеки, не молчаливый пропуск). Обязательный пункт - перечень ожидаемых артефактов
сверх кода (ADR, тесты по приоритету, конфиги/миграции, доки, MR по затронутым репозиториям);
неназванный артефакт исполнителем не производится.

**Skip-условие (свёрнутая форма):** один инкремент с DoD и success metric, если решение Phase 3 -
точечное изменение в существующем сервисе, без нового сервиса/интеграции/bounded context, без новой
инфраструктуры, без миграции данных, без нового deploy-pipeline. Хоть один признак false -> полный
план.

Exit criteria: план даёт конкретные задачи на ближайший инкремент; каждый `FR`/`NFR` Phase 1 покрыт
критерием приёмки хотя бы одного инкремента.

Mandatory: yes - без него нечего вручать `development-track`.

**Решения этой фазы (объём инкрементов, порядок) - собственные строки трека в журнал**
(`node-contract`, «дописывает каждый узел, принявший решение»): трек не переписывает чужие строки
(Phase 3 - за узлом), только добавляет свои.

## Phase 5: Document (delegated, условно)

Goal: зафиксировать решение Phase 3 в форме для долговременного хранения - по типу артефакта, не
монолитным Document-шагом.

Диспетчинг - независимые условные вызовы, можно параллельно:

- **Новое архитектурное правило** (pre-check через `dex-skill-project-docs-map:project-docs-map` -
  решение вводит норму, не факт кода) -> обязателен `dex-adr-writer:adr-writer` (Input: решение +
  drivers + отвергнутые альтернативы из Phase 3).
- **Новый/изменённый API-контракт** -> `dex-api-designer:api-designer` (Input: что за API +
  потребители).
- **Структурная диаграмма затребована** (`interactive` - оператором, `autonomous` - полем
  «требуемые артефакты» во входе трека) или сложность решения того требует -> `dex-diagram-creator:
  diagram-creator`.

Exit criteria: каждый затребованный/обязательный по pre-check артефакт создан с путём на диске;
не затребованный - явная пометка «не затребовано», не тишина.

Skip_if: прототип/spike, тривиальное решение, ADR pre-check отрицательный и ничего не затребовано.
Skip снимает документ, не запись в журнал - строки Phase 3/4 дописываются в журнал при любом исходе
этой фазы.

Когда mandatory: ADR pre-check положительный, либо документация затребована вызывающим.

## Phase 6: Design Acceptance (delegated)

Goal: приёмка design-документа судьёй до передачи в `development-track` - без этого шага решение
уходит дальше без независимого взгляда (пробел, которого не было у монолитного узла, и который этот
пакет закрывает явно).

Input `dex-design-reviewer:design-reviewer`: путь к документу(ам) Phase 3/5, источник требований
(Phase 1 FR/NFR), `set` с диска (весь пакет решения, не один файл). Узел судит - оракулы NFR /
требований / ADR / архитектуры, полнота набора, severity; документ не мутирует.

**Цикл автор-судья**: находки -> возврат на доработку `dex-architect:architect`/
`dex-architect-dotnet:architect-dotnet` (тот же узел Phase 3, не трек) -> повторная приёмка. Потолок
раундов и решение по каждой открытой находке - `docs/AGENT_FRAMEWORK.md#inter-agent-handoff-
последовательный-стык`.

**Гейт (блокирующий):** вердикт не `passed` -> трек не отдаёт хэндофф `development-track` молча -
`interactive`: возврат на доработку либо эскалация оператору при исчерпанном потолке раундов;
`autonomous`: `partial` наверх с перечнем несогласованного.

Метка `quality-checks` (`design-quality`) - в шапке файла дизайна, ставит `design-reviewer`; автор
(`architect`/`architect-dotnet`) себе эту метку не ставит (`node-contract` п.7).

Exit criteria: `verdict: passed` в шапке документа, либо явный блокер (см. гейт).

Mandatory: yes.

**Handoff в `development-track`:** Implementation Plan (Phase 4) + одобренный design-документ
(Phase 3/5, `quality-checks: design-quality passed`) + путь к журналу решений + `quality-checks`
сквозным полем. Маршрут решает движок, не этот трек.

## Режимы и гейты

Гейт блокирующий тогда и только тогда, когда решение стоит на внешнем оракуле - источнике вне кода,
требований и фактов о системе (бюджетная/продуктовая рамка, приоритет между конфликтующими NFR).
Решение, выводимое из материала (выбор между технически равными альтернативами, deep-dive), не
блокирует ни в каком режиме.

| Гейт | Тип | `interactive` | `autonomous` |
|---|---|---|---|
| Бюджетная/продуктовая рамка, приоритет NFR (Phase 1, поздний Phase 3) | блокирующий | работа встаёт, решает оператор | `partial` + перечень несогласованного |
| Выбор альтернатив, deep-dive (Phase 3) | неблокирующий | предъяви + продолжай на предложенном | решает трек/узел, допущением в Output |
| Вердикт `design-reviewer` не `passed` (Phase 6) | блокирующий | возврат на доработку / эскалация | `partial` + перечень |

`mode` - вход трека, дефолт `autonomous` (`node-contract`, инвариант D п.11); передаётся без
изменения во все делегированные вызовы Phase 3/5/6 - узел сам не «детектирует» канал.

## Журнал решений и трейл

Каждый узел, принявший решение, дописывает журнал **своими** строками (`node-contract`, «Журнал
решений») - `architect`/`architect-dotnet` за Phase 3, трек сам за Phase 1 (эскалированные гейты) и
Phase 4 (объём инкрементов). Журнал не передан на входе -> трек заводит файл рядом с design-
документом и называет путь в выходе.

Trail-запись за каждый шаг несёт канал - `self` (Phase 0/1/2/4) или `delegated` (Phase 3/5/6), при
`self` - имя удержанного скилла (движок, «Возобновление»). Auto-ledger сводит блок «Задействованы»
по обеим колонкам разом.

## Boundaries

- Собственного дизайн-решения трек не принимает и не переигрывает узел Phase 3 - см. вводный абзац.
- Ревью уже реализованной кодовой архитектуры (`/review-arch`) - точечный вход у `dex-architect`
  напрямую, не через этот трек: другой источник входа (код, не бизнес-задача), другой объём.
- Confidence ниже 80 в трактовке требования - вопрос оператору (`interactive`) или допущение с
  пометкой (`autonomous`), не угадывание.
- Код трек и узлы этой зоны не пишут - выход зоны дизайна всегда design-документ + implementation plan,
  не правки в репозитории.
