# Синхрон трекера с ходом работы

Механика ведения трекера задач для процесса, который доводит работу до конца сам. Решётка
событий и правило зонтика одинаковы для Jira, GitLab issues, GitHub issues, их аналогов и их
отсутствия (нет трекера в проекте - весь скилл не применяется, точку вызова и это условие держит
вызывающий процесс).

**Не входит:** как именно двигать статус в конкретном трекере (имя перехода в Jira против поля в
GitLab, вызов через MCP против CLI-обёртки, поиск задачи по имени ветки). Есть в проекте
CLI-обёртка трекера - вызывающий процесс использует её напрямую, этот скилл в выбор конкретной
команды не вмешивается.

## Кто трогает трекер

Трекер трогает только главный цикл процесса. Суб-агент, которому делегирован кусок работы, прав
на трекер не имеет и статус сам не двигает - знание о смене статуса возвращается наверх через
обычный выход суб-агента, а действие в трекере делает вызывающий.

**Статус двигаешь в момент смены фазы, не батчем в конце.** «Допишу статусы под-задач в конце» -
запрещено: к сдаче расхождение уже накоплено, и финальный шаг его не ловит. Каждое событие ниже
двигает трекер тем же действием, каким событие случилось.

## Источник события - выход узла, не наблюдение трекера

Знание «пора двигать статус» берётся из **выхода узла**, который выполнил кусок работы (контракт
`dex-skill-node-contract:node-contract`, поле `status: complete/blocked/partial`), сверенного с
чеклистом хода работы, который ведёт вызывающий процесс (auto-ledger движка) - не из
периодического наблюдения за состоянием трекера и не из сигнала суб-агента помимо его собственного
выхода. Трекер - зеркало чеклиста, не источник истины о том, что сделано.

## Решётка событий

Точные имена фаз/статусов берутся из процесса самого трекера в проекте (иногда шире трёх
колонок ниже - тогда каждая дополнительная фаза сверяется по тому же принципу: событие -> статус,
без пропуска середины цепочки).

| Событие | Действие в трекере | Когда |
|---|---|---|
| взял под-задачу в работу | -> «в работе» (или эквивалент) | первым действием, до правок кода |
| узел вернул `complete` по куску | -> «на ревью» (или эквивалент) | тем же шагом, не дожидаясь сдачи всего трека |
| артефакт влит (MR/PR смёржен) | -> закрываешь под-задачу | сразу после мерджа |

## Правило зонтика

Каждую под-задачу двигаешь отдельно - «зонтик в работе» не значит «все его под-задачи двинуты».
Перевод статуса своей задачи вперёд обратим и не требует запроса разрешения (перевод назад или
удаление задачи - решение вызывающего процесса, эта ось сюда не входит).

Зонтик (эпик над задачами, задача над под-задачами - одно правило на любом уровне вложенности)
движется по агрегату частей: подвинул статус ребёнка - сразу же проверь агрегат родителя.
**Дефолт - зонтик стоит в фазе самой отстающей части**: хоть один ребёнок «в работе» - зонтик не
опережает; все дети минимум «на ревью» - зонтик «на ревью»; все дети в терминальной фазе -
двигаешь **сам зонтик** в терминальную, не держишь родителя открытым при закрытых детях.

Любое расхождение «в чеклисте хода работы шаг сделан, в трекере прежняя фаза» (включая родителя
при уже сведённых детях) - провал синхрона, фиксируется на том шаге, где возник, не переносится
на потом.

## Комментирование и публикация

Публикация во внешний канал (комментарий в трекер, апдейт описания задачи) идёт по
последовательности **показать -> получить «ок» -> опубликовать**, если процесс работает в режиме
с оператором в петле; в автономном режиме - публикуется финальный текст, не промежуточный.
«Превью» как отдельное состояние в трекер не публикуется.

## Прикрепление файлов

Стандарт - вложение через API/MCP самого трекера (например Jira `attachments`, GitLab
`POST /projects/:id/uploads`; у GitHub REST вложений в issue нет - только веб-UI).
Если канал не видит локальный путь на диске (API/MCP работает с содержимым, не с файловой
системой вызывающего) - откат: инлайнить содержимое файла в тело задачи или комментария вместо
вложения, с явной пометкой, что это откат, а не вложение. Молчаливая замена вложения на голую
ссылку без пометки - тот же провал синхрона, что и рассинхрон статуса.
