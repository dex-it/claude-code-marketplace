# Запуск исполнителей: вызов, ожидание, расход, журнал, триаж

## Вызов

Поля вызова `Agent`:

- `model` и `effort` - из строки задачи плана, обе явно. Приоритет модели: параметр вызова выше
  frontmatter агента, выше `CLAUDE_CODE_SUBAGENT_MODEL`, выше модели сессии;
  `CLAUDE_CODE_SUBAGENT_MODEL_FORCE=1` навязывает модель из переменной всем субагентам.
- `prompt` - две строки: `Прочитай бриф <абсолютный путь> и выполни его.` и принятые решения по
  неоднозначностям, не попавшие в бриф (или «нет»); на повторе третьей строкой текст провала.
  Ответ - по разделу «Возврат» брифа; отчёт в файл исполнитель не пишет, его записывает
  оркестратор.
- `description` - `<id> <цель в 3-5 словах>`.
- `subagent_type` не передаётся, когда доступен агент общего назначения; без него вызов
  отклоняется, если `general-purpose` среди агентов нет - тогда пакет не исполняется, вопрос
  пользователю.

`name` не передаётся. `model`, которой нет в плане, не передаётся. Изоляция `worktree` не
используется: её результат живёт в отдельной ветке вне рабочего дерева, а пакет и проверки лежат
в рабочем.

## Ожидание

Волна независимых задач идёт одним сообщением с несколькими вызовами `Agent`. Если в схеме
вызова есть `run_in_background`, для волны ставь `false`: сообщение вернётся, когда вернутся все
исполнители. Фоновый запуск оправдан, только если оркестратору есть чем заняться параллельно
(`self`-задача, проверка уже принятого). Фоновый исполнитель сообщает о завершении
уведомлением, по которому оркестратор получает ход снова (так ведёт себя и `claude -p`): ждать
нужно им, не опросом, а ход со словами «исполнитель ещё работает» не завершение (см. «Цикл»).

Размер волны не больше `max_parallel`, даже если задач больше и они независимы: разбей на волны
и переходи к следующей, когда предыдущая принята. Предел платформы (20 одновременных
субагентов, вложенность до трёх уровней по умолчанию) стоит выше плана и план не заменяет.

## Расход

Уведомление о завершении исполнителя содержит один счётчик токенов (`total_tokens` или
`subagent_tokens`), `tool_uses` и `duration_ms`. Разбивки на вход, выход и кеш нет, и это, судя
по росту числа между событиями одного исполнителя, размер контекста, а не оплаченные токены
(вывод из наблюдения, не подтверждён). Поэтому в журнал идут счётчик и `tool_uses`, цена по
ним не считается, а сравнение с расчётом плана идёт в тех же единицах. Точная цена известна
только в `claude -p`: `modelUsage` и `total_cost_usd` результата включают субагентов, `usage`
их не включает. Фактический effort исполнителя в уведомлении не виден: в журнал идёт заданный
планом.

## Журнал

Правь `ledger.json` точечно (`jq` или Edit), а не пересоздавай целиком. Порядок записей:

1. Перед запуском: `status: running`, `spawned` + число запущенных; `attempt` + 1 только для
   ступени лестницы (см. скилл).
2. После приёма: `status`, `evidence` (одна строка «команда -> результат»), `tokens`,
   `duration_ms`. Когда задача терминальна, в её строке `routing_log` пишется `outcome`:
   `done@<попытка>/<модель>/<effort>`, `blocked` или `dropped`.
3. После переплана: запись в `changes` и строка в «Журнал изменений плана».

Записи, ключи латиницей: задача - `id`, `status` (`pending` | `running` | `done` | `failed` |
`blocked` | `dropped`; `failed` - проверка не пройдена, ждёт следующей попытки), `category`,
`model`, `effort`, `attempt`, `depends`, `report`, `evidence`, `reason`, `tokens`,
`duration_ms`; `routing_log` - `task`, `axes` (`A`, `B`, `N`, `V`), `category`, `rated_by`
(`planner` | `orchestrator` | `triage`), `outcome`; `changes` - `what`, `why`. Чужие ключи в
журнал не вводятся. Задача из `NEW_SUBTASKS` получает запись в `tasks` и в `routing_log` в одном
изменении.

## Триаж на haiku

Условия и политика - в разделе «Маршрутизация новых задач» плана. Механика вызова: `model:
haiku`, `effort: medium`, `prompt` - путь к `briefs/_triage.md` и описание задачи до 150 слов.
Ответ - один JSON-объект; он не разбирается либо поле вне допустимых значений - триаж отброшен,
оценка инлайн. Категорию выводишь по таблице плана ты, не модель.

## Основания платформенных утверждений

Сверено 2026-10-08. Отказ инструмента записи у субагента для файлов-отчётов с сообщением
«Subagents should return findings as text, not write report files» - наблюдение прогона
2026-10-08 (версия 2.1.294): пять из тринадцати исполнителей получили отказ на `REPORT.md` и
`reports/<id>.md`, остальные записали такие же файлы; правила, по которым срабатывает отказ,
не установлены. Страница субагентов Claude Code (code.claude.com/docs/en/sub-agents): порядок
выбора модели субагента, предел одновременных субагентов, вложенность до трёх уровней по
умолчанию, возобновление через `SendMessage`, условие `subagent_type`. Страница команд агентов
(agent-teams): именованный вызов `Agent` при включённых командах запускает участника команды.
Параметр `effort` в вызове `Agent` в тех страницах не описан: его наличие и то, что вызов с ним
проходит, подтверждены схемой инструмента и пробным запуском версии 2.1.294; приоритет
относительно `CLAUDE_CODE_EFFORT_LEVEL` не проверен. Состав уведомления о завершении и ожидание
фоновых исполнителей в `claude -p` - замер 2026-10-08 на версии 2.1.294.
