# Запуск исполнителей: вызов, ожидание, расход, триаж

## Вызов

Поля вызова `Agent`:

- `model` и `effort` - из строки задачи плана, обе явно. Приоритет модели: параметр вызова выше
  frontmatter агента, выше переменной `CLAUDE_CODE_SUBAGENT_MODEL`, выше модели сессии.
- `prompt` - три строки: `Прочитай бриф <путь> и выполни его.`, `Отчёт пиши в <путь>.`, принятые
  решения по неоднозначностям, не попавшие в бриф (или «нет»). Ответ - по разделу «Возврат» брифа.
- `description` - `<id> <цель в 3-5 словах>`.
- `subagent_type` не нужен: подходит агент общего назначения.
- `isolation: "worktree"` - когда задачи одной волны меняют код одного репозитория. Для остальных
  изоляция лишняя: параллельные создания worktree могли сталкиваться на блокировках git.

Не передавай `name`. Не передавай `model`, которой нет в плане.

## Ожидание

Волна независимых задач идёт одним сообщением с несколькими вызовами `Agent`. Если в схеме
вызова есть `run_in_background`, для волны ставь `false`: сообщение вернётся, когда вернутся все
исполнители. Фоновый запуск оправдан, только если оркестратору есть чем заняться параллельно
(`self`-задача, проверка уже принятого). Фоновый исполнитель сообщает о завершении
уведомлением, по которому оркестратор получает ход снова (так ведёт себя и `claude -p`, замер
2026-10-08): ждать нужно им, не опросом, а ход со словами «исполнитель ещё работает» - не
завершение (см. «Цикл» в скилле).

Исполнитель, возвращающий результат за пределами ожидаемого времени, не убивается без причины.
Оборванный результат (частичный вывод, достигнутый лимит ходов) - триггер эскалации, не повод ждать.

## Расход

Уведомление о завершении исполнителя содержит `total_tokens` / `subagent_tokens`, `tool_uses`,
`duration_ms`. Они идут в запись задачи: `tokens`, `duration_ms`. Фактический effort исполнителя в уведомлении не виден: в журнал
идёт заданный планом. Цену считай по таблице цен
плана; нет таблицы - пиши токены без цены, не придумывай её. В headless-прогоне `modelUsage` и
`total_cost_usd` результата включают субагентов; `usage` их не включает.

## Журнал

Правь `ledger.json` точечно (`jq` или Edit), а не пересоздавай целиком. Порядок записей:

1. Перед запуском: `status: running`, `attempt` + 1, общий `spawned` + число запущенных.
2. После приёма: `status`, `evidence` (одна строка «команда -> результат»), `tokens`,
   `duration_ms`.
3. После переплана: запись в `changes` и строка в «Журнал изменений плана».

Возобновление читает только журнал: `running` без отчёта в `reports/` - оборван.

## Триаж на haiku

Условия - в «Маршрутизации новых задач» плана. Вызов: `model: haiku`, `effort: medium`, `prompt` -
путь к `briefs/_triage.md` и описание задачи до 150 слов. Ответ - один JSON-объект; разберёшь его
сам: не разбирается, либо любое поле вне допустимых значений - триаж отброшен, оценка инлайн.
Категорию выводишь по таблице плана ты, не модель. `confidence < 0.6`, `B = 2` или
`needs_planner` - поднять тир либо оценить инлайн; два прогона расходятся - берётся большая
оценка по каждой оси.

## Размер волны

Запуск больше `max_parallel` не допускается, даже если задач много и они независимы. Разбей на
волны; переходи к следующей, когда предыдущая принята. Предел платформы (20 одновременных
субагентов, глубина вложенности 3 по умолчанию) - потолок выше плана и план не заменяет.
