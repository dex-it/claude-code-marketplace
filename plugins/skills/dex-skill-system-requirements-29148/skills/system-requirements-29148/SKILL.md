# Этап системных требований: что производим и когда готово

Норматив выхода этапа - **Software requirements specification (SRS)** в границах одной фичи. Один дом состава для составителя и для судящего - ревьюера требований и дирижёра на гейте набора: иначе судья проверяет полноту по памяти, а состав живёт в шаблоне выхода составителя, которого судья не видит.

Здесь только норма этапа. Ловушки формулировок - `requirement-quality`, дефекты набора - `requirement-set-quality`, уровень бизнес-требований - `business-analysis`, контракт стыка узлов - `node-contract`.

## 1. Вход и охват

**Обязательное поле входа ровно одно - принятый материал уровня выше**: BRD фичи с `BR-NNN` и MOE, либо тикет или бриф на его месте, либо код без постановки при brownfield-реконструкции. Его нет -> `status: blocked`, оба режима: выводить требования не из чего, а придуманное бизнес-основание неотличимо от настоящего только до первого гейта.

**Охват - одна фича, не продукт.** Стандарт различает информационные элементы по классу требования и охват не нормирует вовсе, поэтому деление по фичам - решение каталога: `SRS-{фича}.md` лежит в папке своей фичи, границы фичи объявлены до начала работы. Разделы, общие для продукта (перспектива продукта, характеристики пользователей, определения), заполняются один раз и в SRS фичи входят **ссылкой, не копией**: две копии расходятся молча, и расхождение всплывает на приёмке.

Режим приходит полем `mode` (дом - `node-contract`); поля нет -> `autonomous`. Различение факта и воли постановщика, порядок вопросов в `interactive` - те же, что на бизнес-уровне, дублировать их здесь незачем.

> см. dex-skill-business-analysis:business-analysis - режим сбора и разряд нехватки

Останавливает этап безусловно только противоречие внутри принятого материала, которое нельзя разрешить, не выбрав за постановщика необратимо.

## 2. Состав артефакта

20 подразделов по 29148 §9.6 (§9.6.1 - §9.6.20). Раздел без содержания закрывается **явным статусом с причиной** (проверка 3 в разделе 4): молчание не отличимо от забывчивости и не даёт перейти к `review`.

| Раздел | Что несёт | Признак незаполненности |
|---|---|---|
| SRS overview | назначение документа и сводка по нему | дан обзор продукта вместо сводки по документу |
| Purpose | для чего это ПО и для чего документ | пересказ бизнес-цели без перехода к ПО |
| Scope | какой продукт специфицируется, что делает, как согласуется с вышестоящим | граница ПО не названа: непонятно, что вне продукта |
| Product perspective | частью какой системы является ПО, соединения, режимы, ограничения памяти, настройка под площадку | перечислены только внутренние части, внешние соединения не названы |
| Product functions | сводка функций без подробностей | подробности требований втянуты в сводку |
| User characteristics | классы пользователей и то, чем они влияют на требования | список ролей без влияния на требования |
| Limitations | что сужает выбор решения: регулятор, оборудование, параллельная работа, язык, протоколы, критичность | смешаны с требованиями и получили ID |
| Assumptions and dependencies | на что рассчитываем и что изменит требования | смешаны с ограничениями: допущение - то, на что рассчитываем, ограничение - то, что предписано |
| Apportioning of requirements | что адресовано каким частям ПО, что отложено в будущие версии | отложенное не отделено от текущего объёма |
| Specified requirements | сами требования, разложенные по классам ниже | классы перемешаны, требование лежит вне своего класса |
| External interfaces | требования к внешним стыкам | стык назван без диапазона, точности, единицы и формата |
| Functions | функциональные требования | требование описывает реализацию, а не наблюдаемое поведение |
| Usability requirements | требования к удобству | качество названо словом без наблюдаемого признака |
| Performance requirements | производительность и ёмкость | число без условий измерения |
| Logical database requirements | требования к данным | описана схема БД вместо требований к данным |
| Design constraints | предписанные решения | ограничение без причины, по которой выбор сужен |
| Standards compliance | соответствие стандартам | назван стандарт без пункта и без метода проверки |
| Software system attributes | атрибуты качества системы | атрибут без меры и без метода верификации |
| Verification | подход к проверке набора целиком, порядок и методы по классам | подменяет поле метода у отдельного требования вместо того, чтобы дополнять |
| Supporting information | образцы форматов, материалы обследований, особые указания | не сказано, входит пункт в состав требований или нет |

**Добавки сверх норматива** ведутся и называются добавками, иначе при сверке не отличить требование стандарта от нашего решения:

- **метаданные документа** - версия, дата, владелец, перечень изменённых разделов относительно предыдущей редакции;
- **незакрытые пункты** - каждый с владельцем и сроком; раздел пуст - так и пишется;
- **цитата источника** у каждого требования (раздел 3).

**Объём раздела - по материалу, не по числу разделов.** Сказать нечего -> статус из проверки 3, не абзац-филлер.

## 3. Атрибуты единицы

Требование системного уровня несёт:

| Атрибут | Содержание |
|---|---|
| `ID` | `FR-NNN` либо `NFR-NNN`, нумерация сквозная по корпусу из блока, закреплённого за фичей; новая с чистого листа не заводится при существующих принятых |
| `traced from` | `BR-NNN` своей фичи; родителя законно нет -> единая форма `traced from: none` с источником ожидания, самодельная формулировка читается нижним звеном как отсутствие поля |
| `rationale` | четыре пункта: **reason** (почему требование существует), **assumptions** (на что опирались), **relationships** (связь с эксплуатацией, ссылка на сценарий), **design constraints** (способ задан - почему решение сужено) |
| `verification method` | осмотр, анализ, демонстрация, испытание - и чем именно проверяется |
| `verification level` | на каком уровне сборки проверяется |
| `feature` | фича, которой требование принадлежит; принадлежность несёт атрибут и расположение, не номер |
| `класс` | подраздел состава из раздела 2, в который требование попадает |
| `приоритет` | обязательно, желательно, возможно, отложено в будущую версию |
| `источник` | артефакт, координата в нём, автор, плюс дословная цитата, из которой требование выведено |

**Метод верификации обязателен, и это сужение сверх стандарта, названное сужением.** Требование без метода - декларация: «проверяемое» ничем не подтверждено. **Одного метода не всегда достаточно**: полная верификация части требований требует более одного, и записывать надо все применяемые, а не выбирать один ради формы.

**MOE здесь нет, здесь MOP.** Мера успеха стороны живёт на уровне `BR` и валидируется; требование системы несёт производную от неё количественную меру и верифицируется. Одна MOE нормально раскрывается несколькими требованиями с разными MOP. Требовать MOE от `FR` - ложное срабатывание, как и требовать числа от `BR`.

Числовое требование без условий измерения дефектно: число, полученное на другой нагрузке, другом объёме данных или другом окружении, проверяет не то требование.

## 4. Проверки содержания

Три проверки, каждая - активный поиск, а не «если бросилось в глаза». Формальная заполненность разделов ни одну не закрывает.

**1. Покрытие бизнес-уровня.** По каждому `BR-NNN` входа: раскрыто хотя бы одним требованием либо объявлено `non-goal` с основанием из входа. Третьего исхода нет. Бизнес-цель, до которой не дошло ни одно требование системы, дальше по конвейеру не всплывёт - её потерю обнаружат на приёмке, когда объём уже согласован. Обратная сторона той же проверки: требование без родителя - осиротевшее, и это находка, а не мелочь оформления.

**2. Проверяемость каждого требования.** По каждому: назван метод верификации, назван предмет проверки, а у количественного требования - условия измерения. Формулировка, для которой нельзя назвать способ проверки, - не требование: она возвращается в переформулировку либо поднимается наверх как нехватка воли постановщика. Отдельный проход - по атрибутам качества: слово («быстро», «надёжно», «удобно») без наблюдаемого признака проходит формальную проверку заполненности и не проходит эту.

**3. Требование против ограничения и допущения.** Три вида смешиваются чаще всего, и смешение прячет предмет спора: требование говорит, что система обязана делать; ограничение - что нам предписано и почему выбор сужен; допущение - на что мы рассчитываем и что изменит требования, если окажется неверным. Предписанное решение, попавшее в раздел требований и получившее ID, делает необсуждаемым то, что подлежало обсуждению. Незаполненный раздел закрывается одним из двух статусов: `n/a` с причиной (раздел неприменим) либо «нет данных» с причиной и номером открытого вопроса (применим, ответа нет); до `approved` второй должен быть закрыт.

## 5. Готовность документа

Целевой статус - **`review`** с записями оракулов: цикл шапки `draft` -> `review` -> `approved` -> `archived`, но порог `approved` для SRS обязательным не объявлен - его несут BRS и ADR, где решение дорого откатить. Составитель поднимает документ до `review` и выше не поднимает: записи оракулов и апрув приходят на гейте, статус за ними проставляет ведущий гейт узел.

| Статус | Достигнут, когда |
|---|---|
| `draft` | документ порождён, состав неполон |
| `review` | все разделы состава присутствуют; пустой - только со статусом из проверки 3; каждое требование несёт атрибуты раздела 3 |
| `approved` | `quality-checks` несёт `requirement-quality` и `requirement-set-quality` с `verdict: passed` от судьи, полнота состава сверена против этого норматива, открытых вопросов по документу не осталось |
| `archived` | документ выведен из обращения; заменён - со ссылкой на заменяющий |

Проверенность живёт в `quality-checks`, не в статусе, и запись делает **судья - узел, не писавший документ**. Составитель прогоняет оракулы как самоконтроль и отчитывается полем `self-check`; проверкой для приёмника это не является.

## 6. Выход этапа

- путь к SRS в репозитории - в папке своей фичи, место берётся из конвенций проекта, не хардкодится;
- перечень `FR-NNN` и `NFR-NNN` с методом верификации у каждого;
- покрытие бизнес-уровня из проверки 1: по каждому `BR-NNN` входа - раскрыто или `non-goal` с основанием;
- требования, законно не имеющие родителя, единой формой `traced from: none`;
- ограничения и допущения, разделённые между собой и отделённые от требований;
- незакрытые пункты с владельцем и сроком;
- `quality-checks` - сквозное поле, переносится со входа как есть, в том числе в шапку файла требований; своих записей по порождённым здесь требованиям составитель не делает;
- `self-check` - что прогнано и что устранено, либо причина непрогона;
- `status` документа из его шапки.

Это вход этапов сценариев, архитектуры и планирования верификации. Маршрут решает оркестратор.

**Exit criteria:** документ сохранён в папке своей фичи; все разделы состава присутствуют или помечены статусом; каждое требование несёт `ID`, `traced from`, `rationale`, метод верификации и класс; три проверки раздела 4 прогнаны; покрытие каждого `BR-NNN` входа названо явно; `self-check` заполнен; `status` проставлен в шапке.
