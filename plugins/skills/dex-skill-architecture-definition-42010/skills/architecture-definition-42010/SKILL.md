# Этап архитектуры: что производим и когда готово

Норматив выхода этапа - **архитектурное описание (SAD)** на продукт плюс **ADR** на каждое решение, выбранное из альтернатив. Один дом состава для составителя и для судящего - ревьюера дизайна: иначе судья проверяет полноту по памяти.

Здесь только норма этапа. Ловушки решений - `adr-quality`, дефекты дизайна - `design-quality`, требования на входе - `system-requirements-29148`, контракт стыка узлов - `node-contract`.

## 1. Вход и охват

**Обязательное поле входа ровно одно - требования, прошедшие свой гейт**: `FR`/`NFR` с меткой `quality-checks` и `verdict: passed`. Их нет -> `status: blocked` в обоих режимах: архитектура без требований проектирует догадку, и проверить её не против чего.

**Вход не перепроверяется по существу.** Метка означает, что требования судил оракул; архитектор доверяет ей и не открывает второй круг требований. Найденный дефект требования - находка наверх (`requirement-defect`), а не тихая правка на своём уровне.

**Охват - продукт целиком, не фича.** SAD один и по фичам не дробится: устройство системы общее, а дробление заставило бы дублировать общее в каждой папке. Обновляется, когда меняется устройство, а не когда добавили экран.

## 2. Состав артефакта

Стандарт задаёт **каркас**: описание организуется вокруг concerns заинтересованных сторон, и каждый concern закрыт хотя бы одним view. Практический шаблон - **arc42, двенадцать разделов**; он и есть форма выхода этапа.

**Статусы сверки:** каркас concerns и views - `unverifiable`, текст §5-§6 42010 за paywall; перечень двенадцати разделов arc42 - `verified` по странице arc42.org; то, что составом взят именно arc42, а не выгрузка из стандарта, - решение каталога, а не требование 42010.

| Раздел arc42 | Что несёт | Признак незаполненности |
|---|---|---|
| Introduction & Goals | задачи системы, ключевые требования, целевые качества, стороны | цели переписаны из BRD без отбора: не видно, какие из них двигают архитектуру |
| Constraints | технические и организационные ограничения | смешаны с решениями: ограничение объясняет, почему выбор сужен, решение - что выбрано |
| Context & Scope | границы системы, внешние соседи, интерфейсы | назван только технический контекст, деловой пропущен |
| Solution Strategy | ключевые решения одной таблицей: цель качества -> подход | подход назван без связи с качеством, которое он обеспечивает |
| Building Block View | статическая декомпозиция по уровням | уровень раскрыт без причины: показано всё подряд вместо того, что нужно читателю |
| Runtime View | сценарии взаимодействия во времени | взяты только успешные пути, отказ и деградация не показаны |
| Deployment View | инфраструктура, узлы, отображение блоков на них | среда одна, хотя стенд и прод различаются существенно |
| Crosscutting Concepts | сквозные механизмы: ошибки, безопасность, логирование, транзакции, миграции | механизм назван словом, не сказано, как он применяется единообразно |
| Architectural Decisions | реестр решений со ссылками на ADR | тело решения переписано в SAD вместо ссылки, две копии расходятся |
| Quality Requirements | дерево качеств и сценарии качества | качество названо прилагательным без сценария и меры |
| Risks & Technical Debt | риски и принятый долг | риск без того, что делает его контролируемым |
| Glossary | термины предметной области и их соответствие терминам кода | термин заказчика и термин кода смешаны, а не сопоставлены |

Раздел без содержания закрывается **явным статусом с причиной** (проверка 3 в разделе 4), а не молчанием и не абзацем-филлером.

**Схемы живут внутри разделов, отдельным жанром не заводятся.** Нотация - C4: контекст, контейнеры, компоненты, код; уровень выбирается по вопросу читателя, а не рисуется весь. Диаграмма без вопроса, на который она отвечает, - украшение.

## 3. Атрибуты единиц

Единиц две: **view** и **решение**.

| Атрибут view | Содержание |
|---|---|
| `concern` | какой вопрос стороны закрывает; view без concern не нужен никому |
| `stakeholder` | чей это вопрос |
| `notation` | чем нарисован и на каком уровне C4 |
| `model kinds` | какие элементы и связи допустимы в этом виде |

| Атрибут решения | Содержание |
|---|---|
| `ID` | `ADR-NNNN`, сквозной по корпусу, номера не переиспользуются |
| `relates_to` | фичи, которых решение касается; по папкам фич ADR не раскладывается |
| `status` | перечень MADR; порогу этапа отвечает `Accepted` |
| `drivers` | какие требования и качества давят на выбор, со ссылками на `FR`/`NFR` |
| `options` | рассмотренные варианты, не только выбранный |
| `consequences` | что выиграли и **что потеряли**; односторонние последствия - признак неразобранного решения |

## 4. Проверки содержания

**1. Каждый concern закрыт хотя бы одним view, каждый view отвечает чьему-то concern.** Проверяется в обе стороны: незакрытый concern - дыра описания, view без concern - работа, которую никто не заказывал. Сторона, чей concern не назван вовсе, обнаруживается позже всех - обычно на приёмке.

**2. Граница «решение в SAD против решения в ADR».** Решение, выбранное **из альтернатив**, уходит в ADR целиком; в SAD остаётся строка реестра со ссылкой. Решение без альтернатив - запись в SAD, не ADR. Признак нарушения в обе стороны: ADR, у которого раздел рассмотренных вариантов пуст либо содержит соломенное чучело; SAD, в котором развилка описана прозой с «мы решили», и причина отказа от других вариантов нигде не записана - через год её восстанавливают заново.

**3. Качество названо сценарием, а не прилагательным; незаполненный раздел закрыт статусом.** «Система должна быть масштабируемой» проверке не поддаётся: сценарий качества несёт источник воздействия, само воздействие, условия и измеримый отклик. Незаполненный раздел закрывается одним из двух: `n/a` с причиной либо «нет данных» с причиной и номером открытого вопроса; до `approved` второй должен быть закрыт.

## 5. Готовность документа

| Статус | Достигнут, когда |
|---|---|
| `draft` | документ порождён, состав неполон |
| `review` | все двенадцать разделов присутствуют либо помечены статусом; каждый view несёт concern |
| `approved` | `quality-checks` несёт `design-quality` (и `design-set-quality` по набору) с `verdict: passed` от судьи, открытых вопросов не осталось |
| `archived` | выведен из обращения, со ссылкой на заменяющий |

У ADR перечень статусов свой - MADR; порогу отвечает `Accepted`, и для ADR `approved`-эквивалент обязателен: решение дорого откатывать.

Составитель поднимает документ до `review` и выше не поднимает; записи оракулов ставит судья.

## 6. Выход этапа

- путь к SAD в репозитории и пути заведённых ADR;
- реестр решений: `ADR-NNNN`, статус, `relates_to`;
- перечень concerns с указанием, какой view каждый закрывает;
- требования, которые архитектура не может удовлетворить в текущем виде, - наверх находкой, не молча;
- принятый технический долг и риски с тем, что делает их контролируемыми;
- `quality-checks` - переносится со входа как есть; своих записей составитель не делает;
- `self-check` - что прогнано и что устранено;
- `status` документа из шапки.

Это вход этапов определения интерфейсов и планирования верификации.

**Exit criteria:** SAD сохранён; двенадцать разделов присутствуют или помечены статусом; каждый concern закрыт view; каждое решение из альтернатив вынесено в ADR со статусом и последствиями в обе стороны; три проверки раздела 4 прогнаны; `self-check` заполнен; `status` проставлен.
