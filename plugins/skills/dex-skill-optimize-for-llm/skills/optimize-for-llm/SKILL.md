# Оптимизация markdown-инструкции под LLM

<!-- skill-type: process -->

Артефакт читает **модель**, не человек. Цель: донести механизм/условие/исход минимумом токенов без
потери однозначности и нормативной силы. CLAUDE.md и тело агента в контексте на каждом проходе, тело
skill - по срабатыванию, `description` - в листинге скиллов; лишний токен бьёт там, где артефакт в контексте, а
чем длиннее носитель, тем выше риск, что важное в нём утонет.

Единственное исключение из scope: артефакт читает человек глазами (README, маркетинг, UI-копирайт) -
тогда скилл не применять.

> Принцип «писать для LLM» живёт в CLAUDE.md (правило «Формулировки в артефактах пишутся для LLM ...»); здесь его операционализация.
> Текст, который читает человек: dex-skill-output-hygiene.

## Приоритеты при конфликте

Строгий порядок. Нижний приоритет НИКОГДА не жертвует верхним; минимизация токенов уступает всегда.

1. **Нормативная сила и грабли.** Лазейки закрыты, обязательные статусы на месте, escape-условия узкие, границы инструмента сохранены. Непримиримо ни с чем ниже.
2. **Однозначность.** Каждая единица читается одним способом. Жертвовать ради неё можно только токенами, не нормативной силой.
3. **Минимум токенов.** Режется ТОЛЬКО то, что не задевает нормативную силу и однозначность.

Гейт на каждую правку (он же финальная проверка): принять, только если ВСЕ пункты выполнены - смысл сохранён, однозначность не упала, нормативная сила и грабли на месте, escape-условия не шире прежних. Любой пункт не выполнен -> откатить правку.

## Что резать

- **Повествовательную воду и вводные обороты.** «Стоит отметить, что», «как известно», «в целом», «давайте рассмотрим» - выкинуть. Критерий: убирается ли слово/оборот без потери смысла или однозначности? Да -> убрать.
- **Историю и мотивацию установки.** «Раньше тут было», «изначально», команды инсталляции (`uv tool install ...`, `dotnet tool install ...`) - модель применяет инструмент, а не переустанавливает. Оставить *как вызвать*, не *как поставить*. Режется история носителя и установка инструмента, не обоснование правила: «почему два круга, а не четыре» переносит правило на случай, которого в перечне нет, - без него правило работает только на буквально названных. Обоснование сжимается до механизма, не выбрасывается.
- **Дубли внутри одного носителя.** Одна мысль/факт - один нормативный дом. Повтор в двух местах -> ссылка или слияние. Две строки таблицы про родственные команды (`cfg`/`dfg`/`slice`) -> одна. Повтор между носителями, которые читаются раздельно (агент не читает `docs/` каталога, skill не читает тело агента), дублем не является: сводить его ссылкой можно, только если исполнитель эту ссылку физически откроет. Иначе рез меняет самодостаточную формулировку на отсылку в недоступный текст, и правило исчезает для того, кому адресовано. Не дубль и слово, сужающее предмет («**отсутствующая** ветка», «**внешний** вызов»), даже когда соседняя фраза звучит близко; не дубль и два правила, совпадающие текстом, но расходящиеся условием применения, - слияние уносит одно из условий.
- **Развёрнутые bash-примеры**, когда приём держится в однострочнике без потери граблей и флагов. Несколько примеров, различающихся только оформлением, -> один канонический, остальные через `·`-перечень. Примеры, различающиеся контекстом (чтение vs запись), edge case или показанной лазейкой, не сводятся: сведение сужает правило до оставленного случая.
- **Пересказ кода словами.** Рядом код-блок/команда -> словесное описание того же не нужно.
- **Инструкции делать то, что модель делает и так.** «Перепроверь ответ», «убедись ещё раз перед выводом», «двойная проверка результата», «думай шаг за шагом» - складываются с собственным поведением модели и дают лишние проходы, не качество. «После каждого инструмента дай сводку», «объявляй, что собираешься сделать» режутся по другой причине: это калибровка нарратива под прошлое поколение, а не дубль дефолта - сводку после инструмента модель как раз склонна пропускать, и такая инструкция штатно возвращает видимость. Снимается там, где видимость не нужна, а не как избыточная. Режется **инструкция, а не проверка**: шаг, приносящий новый факт извне (прогон теста, вывод компилятора, сверка с источником, перечитанный файл), остаётся - он не самоперечитывание. Критерий: «что нового появляется по итогу шага?» Ничего - шаг держится на догадке, что без напоминания модель поленится; это допущение прошлого поколения. Одно исключение из критерия: требование следа нового факта не приносит и всё равно не режется - оно делает шаг наблюдаемым (см. «Что нельзя ослаблять»). Охват правила - тир артефакта: на `model: opus` (Opus 5) инструкция самопроверки удаляется, модель проверяет себя сама и унаследованная инструкция даёт переверификацию; на прочих тирах кросс-модельный гайд называет self-check против явных критериев надёжно ловящим ошибки - там инструкция режется, только если шаг не приносит внешнего факта И сверка со страницей своей модели это подтвердила, а страницы у тира нет - `unverifiable`, инструкция остаётся. Независимая сверка под правило не подпадает, хотя читает уже прочитанное: чужие глаза в чистом контексте приносят факт, которого у автора нет в принципе, - как его текст читается без памяти о замысле.
- **Осторожность общим фоном там, где есть отдельный порог.** «Сообщай только значимое», «не поднимай лишнего», «будь консервативен» в роли или в фазе сбора исполняются буквально и срезают охват: часть реальных находок не доходит до оценки. Если в артефакте есть шаг отсева (severity, confidence, фильтр) - формулировка про цену ложного срабатывания живёт рядом с ним, а не в общем описании. Шага отсева нет - формулировка не режется, а становится порогом с названным критерием («поднимай находку от severity X и выше»): снятая без замены, она убирает единственный фильтр артефакта.

## Что нельзя ослаблять (приоритет «нормативная сила и грабли»)

- **Нормативную силу.** Сжимаем подачу, не правило. Лазейки, обязательные статусы (`n/a`+почему, `unverifiable`, `contradicted`), обоснования «почему mandatory», верифицируемые ограничения (точный счётчик/формат/значение: `TTL=300`, `widget:{id}`, «ровно 5 секций») - не сокращать и не размывать («около 300», «в нужном формате»). Лаконичность != ослабление проверки.
- **Требование следа в выходе.** «Назвать в отчёте», «приложить перечень», «исход по каждому пункту» - не оформление: это единственное, чем шаг наблюдаем. Снял требование - шаг остался в тексте, но его пропуск неотличим от выполнения, и пропускают молча. Режется формулировка требования, не требование.
- **Нажим - калибровать, не накручивать.** Нормативную силу несёт формулировка + размещение + явный статус, не текстовый акцент. Стопка CAPS / «CRITICAL: ОБЯЗАН» силы не добавляет: на новых моделях избыток нажима склонен перетриггеривать, а текстовый акцент сам по себе - ненадёжный рычаг внимания. Одно чёткое нормативное утверждение бьёт тот же смысл капсом. Это не послабление: правило остаётся, гасится только дубль-нажим.
- **Кванторы и логические операторы - не нажим.** «только», «всегда», «ни один», «каждый», «ровно», «единственный», «не иначе как» задают объём правила, а не тон: «порог берётся решением оператора» и «порог берётся **только** решением оператора» разрешают разные множества исходов. Гасится накрутка (CAPS, «CRITICAL: ОБЯЗАН»), квантор остаётся. Проверка, что перед тобой: убери слово - изменился ли перечень допустимого? Изменился - это квантор, вернуть.
- **Связки логики - не вводные обороты.** «а не X», «иначе», «поэтому», «при этом» несут отрицательную половину правила, причину и условие: «возвращается сценарием, **а не** правилом» без второй половины правило разрешает. Замена союза на тире стирает вид связи - причинность и перечисление читаются одинаково. Режется «стоит отметить», не «а не».
- **Терминал каждой ветки.** «Если X -> Y» без «иначе -> что» разрешает остановку на ветке. Рез союзной конструкции («иначе», «не нашёл - тогда») уносит исход второй половины, и правило остаётся определённым только на названном случае. Ветка без исхода после реза - откат правки, не находка на потом.
- **Escape-условия - сужать.** Размытый escape - дефект: исполнитель сам решает, что «не нужно», и закрывает шаг молчанием. Сузить до конкретного условия + фиксации пропуска явным статусом; недоступность инструмента переключает на запасной, не отменяет шаг. Плохо: «пропусти, если не смог». Правильно: «пропусти ТОЛЬКО если X недоступен (`command -v X` пуст); зафиксируй статусом `n/a` + причина». Это ужесточение, не рез.
- **Охват правила.** Множество предметов, на которые правило распространяется, названо явно: с названного пункта на соседний модель инструкцию молча не переносит. Охват часто выражен не квантором, а хвостом фразы («не только свои строки», «в каждой фазе, не только в первой»), и хвост при резе выглядит накруткой. Убрал - правило осталось грамматичным и стало применяться к меньшему множеству. Проверка: убери слово - изменился ли перечень предметов, к которым правило относится?
- **Грабли и границы инструмента.** «C#: статики не видит -> `LSP incomingCalls`», «`findReferences` per-symbol» - это и есть ценность, ради неё артефакт существует.
- **Однозначность.** Сокращение породило двусмысленность («может ли исполнитель прочитать так, что правило к нему не относится?») -> вернуть слово.
- **Степени свободы - строгость по умолчанию.** По умолчанию закрывать лазейки и сужать escape. Единственное исключение: у задачи реально несколько валидных подходов - тогда не выдумывать единственный обязательный путь, но зафиксировать свободу явно с критерием выбора («выбери по X: A | B»), не «по усмотрению». Свобода молчанием запрещена и в исключении.

## Как писать после реза

- **Механизм + условие + исход**, не пересказ. «Ошибка X = причина Y» вместо абзаца про X.
- **Порядок и приоритет - нумерованным списком, не прозой.** Последовательность шагов / разрешение конфликта выразить нумерацией 1->2->3 с явным правилом («нижний не отменяет верхний», «при конфликте вердиктов приоритет у ...»). Проза «сначала..., обычно..., при необходимости...» оставляет порядок на усмотрение исполнителя. Плохо: «проверь типы, можно также прогнать линтер». Правильно: «1. type-check. 2. lint. При конфликте приоритет у type-check».
- **Таблица вместо прозы**, когда это «вход -> инструмент/исход» (выбор инструмента, маппинг ситуация->действие).
- **Смена формы теряет то, чего в новой форме нет.** Таблица не держит причинность и отрицательную половину («и не в следующий круг»); один канонический пример вместо пары «Плохо / Правильно» уносит показанную лазейку; императив теряет субъекта и модальность («обязан» vs «может»); строка рядом с кодом часто несёт инвариант, из кода не выводимый («работает, только когда вход отсортирован»). Перед сменой формы - сверить по чеклисту шага 2, что переносимое утверждение в новой форме выразимо; невыразимо - форма не меняется.
- **Требование к форме - позитивно, запрет - только второй половиной.** «Не делай X» целевого поведения не называет, и замену модель берёт из множества шире нужного. Плохо: «не пиши развёрнутые сниппеты». Правильно: «в примере - имя API или условие срабатывания». Отрицание остаётся там, где сужает названный целевой исход («возвращается сценарием, а не правилом»): это вторая половина правила, не единственная его формулировка.
- **Именованный тег - когда в носителе смешаны правило и материал.** Блок, который читается как целое и должен отличаться от окружающего (вставленный дифф, корпус, пример-вход), обернуть в `<имя>`. Где разделителем уже работает markdown-заголовок, тег - накладные токены. Требование к выходу тегами не задавать: инструкция, называющая внутренние теги по имени, слабее общей формы, а на Opus 5 с выключенным thinking повышает их протечку в видимый ответ.
- **Сухо.** Императив, не повествование. «Бери LSP», не «рекомендуется обратиться к LSP».
- **Языко/проекто-нейтрально**, если артефакт общий. Имена конкретного проекта (`UpCore`, `MergeRequest`) в общем правиле -> обобщить (`dst = src.Field` вместо `DTO = entity.Prop`).

## Информационная архитектура

Оптимизируется не только проза, но и где живёт текст. Носитель делит окно с историей и другими артефактами: что в нём, то платит токенами, пока он в контексте.

- **Тонкий носитель + деталь по требованию.** Что нужно всегда и для срабатывания - inline; что нужно редко или во взаимоисключающих ветках - в отдельный материал, читаемый по требованию.
- **Ссылки one-level-deep.** На доп-материал ссылаться прямо из носителя, не цепочкой «файл -> файл -> файл»: вложенные читаются частично и теряют контекст.
- **Длинный материал - с оглавлением сверху**, иначе при частичном чтении не виден его объём.
- **Высокоприоритетное нормативное - в начало носителя**: частичное/превью-чтение охватывает начало надёжнее хвоста. Правило о носителе нормы; в промпте с длинным входом порядок обратный - материал вверху, запрос и инструкции после него (замерено: до +30% качества ответа при запросе в конце).
- **Лимиты размера носителя и `description` не хардкодить** - дрейфуют; нормативный дом цифр - [docs/SKILL_FRAMEWORK.md](https://github.com/dex-it/claude-code-marketplace/blob/main/docs/SKILL_FRAMEWORK.md).

## Поле срабатывания (description)

Для артефакта, чьё обнаружение зависит от поля активации (skill, агент, команда): это поле - главный рычаг, по нему артефакт выбирается из множества; читается до тела, не по триггеру. У артефакта, который грузят императивно по имени (process-skill), это поле не главный рычаг выбора и сокращается как накладные, но нормативную форму активации не теряет: активаторы у process-skill смягчены, а не сняты - границу держит [docs/SKILL_FRAMEWORK.md](https://github.com/dex-it/claude-code-marketplace/blob/main/docs/SKILL_FRAMEWORK.md#калибровка-валидатора-по-типу).

- **Что + когда, в 3-м лице.** «Переписывает X, активируется при Y», не «я помогу» и не «ты можешь»: смешанное лицо ломает обнаружение.
- **Anchor + aspects, не entry-points.** Anchor - стек/тема (`ef core`, `DDD`); aspects - темы верхнего уровня (по любой попадает запрос в scope). Конкретный API/симптом - entry-point: матчится буквально и раздувает поле, не давая охвата.
- **Без повествования в зоне триггеров.** Внутри списка активаторов - только активаторы; преамбулу и исключения вынести из него.
- **Нормативную форму активации не ронять.** Обязательная форма поля (явная фраза-триггер платформы + минимум активаторов; форма и цифры - [docs/SKILL_FRAMEWORK.md](https://github.com/dex-it/claude-code-marketplace/blob/main/docs/SKILL_FRAMEWORK.md)) нормативна, не вода. Рез и перефраз description сохраняют фразу-триггер и не уводят число активаторов ниже минимума. Плохо: «Активируется при ...» -> «Activates when ...» или активаторы срезаны под лимит - поле перестаёт матчиться.
- **Расхождение поля с телом - находка, не предмет реза.** Аспект в `description`, которому в теле нет ни одной единицы, молча не снимается: сужение поля меняет охват артефакта. Возвращается владельцу с обеими развилками (снять аспект / дописать единицу), в отчёте - строкой.
- **Бюджет длины и минимум активаторов** - см. [docs/SKILL_FRAMEWORK.md](https://github.com/dex-it/claude-code-marketplace/blob/main/docs/SKILL_FRAMEWORK.md) (детали anchor+aspects для skill там же, не дублировать).

## Обязательная сверка фактов

Любое утверждение о поведении инструмента/API/платформы (флаги, лимиты, какой бинарь установлен, поддержка поля) - **проверить перед фиксацией**, не писать по «общеизвестному»:

- наличие бинаря/сервера - `command -v` / PATH;
- поведение CLI - `--help` / живой прогон;
- API библиотеки - context7 -> WebSearch.

## Порядок работы

1. Прочитать артефакт **целиком** (текущее состояние, не по памяти - мог измениться).
2. **Снять чеклист смыслов с оригинала - до первой правки.** Разобрать носитель на атомарные утверждения, по одному на строку, покрывая весь текст: что оригинал предписывает, запрещает, определяет, обосновывает и утверждает о поведении инструмента. Категории-минимум: обязательные действия и терминалы их ветвей, статусы ухода от проверки, требования к следу в выходе, кванторы и связки логики, числа и форматы, определяемые термины, escape-условия, грабли, обоснования правил, инварианты. Перечень - нижняя граница, не объём: смысл, не попавший в чеклист, сверкой шага 7 не ловится вовсе, и все известные потери реза - именно классы, которых в перечне не было. Полнота проверяется обратным ходом: предложение оригинала, не отражённое ни в одном утверждении, пропущено; «это вода» решается на шаге 4, не здесь. Чеклист, составленный после реза, берётся из памяти о намерении - а помнит её тот, кто резал, и она дочитывает в текст смысл, которого там уже нет.
3. Выписать техфакты к сверке -> проверить (см. выше).
4. Переписать по «что резать / что нельзя ослаблять / как писать / информационная архитектура / поле срабатывания».
5. После реза - `rg` по ключевым терминам удалённых кусков: не осталось ли **висячих ссылок** («см. раздел ниже» на удалённый раздел), битых перекрёстных ссылок и **висячих терминов** - каждый термин, употреблённый дальше по носителю, определён выше. Дефиниция синтаксического маркера не имеет («круг непродуктивен» читается как обычное сказуемое) и режется как оборот, а её потребитель стоит абзацем ниже, вне поля правки.
6. Прогнать гейт по приоритетам на каждую правку (см. «Приоритеты при конфликте»), диф по смыслу, не только по объёму. Любой пункт гейта не выполнен -> откатить эту правку.
7. Проверить результат **эмпирически, не на глаз**:
   - дельта: строки/токены до->после (рез без числа - не рез);
   - re-derive **чужими глазами**: субагенту даётся финальный текст целиком и вопросы чеклиста шага 2 - без оригинала, без диффа, без намерения правки; его ответы сличаются с чеклистом. Каждый пункт чеклиста получает исход: `derived` - чужой читатель воспроизводит утверждение по финальному тексту в том же объёме; `lost` - не воспроизводит, правка откатывается, и расхождение в объёме или условии (правило стало шире, уже, мягче) - тоже `lost`, не только молчание; `dropped` - срезано намеренно, с основанием из «что резать». Пункт без исхода не проверен, а не сохранён. Автор реза этой проверкой не заменяется: он помнит замысел и достраивает недостающее - тот же механизм, ради которого проба готовности набора идёт в чистом контексте. `Agent` недоступен - чеклист сверяется чтением финального текста файла целиком (не диффа: потеря живёт в связи между абзацами, а дифф показывает фрагменты), и в отчёте это называется самопроверкой;
   - отчёт о резе несёт дельту числом и чеклист шага 2 с исходом по каждому пункту. Чеклиста в отчёте нет - рез не сдан: шаг, не оставляющий следа в выходе, пропускается молча (проверено прогоном - исполнитель признал оба шага невыполненными, лазейки в тексте не найдя);
   - правка `description`: trigger-check - активаторы срабатывают на реалистичных запросах в scope и НЕ срабатывают на близких вне scope (near-miss);
   - провал на пробе -> рефлексия по ОДНОМУ провалу: почему инструкция к нему привела -> одна точечная правка против причины -> перепроверка по якорю (re-derive/проба/валидатор), не по мнению; оставить лучший вариант;
   - глубже (парный baseline, слепое A/B, held-out near-miss, worst-of-N, downstream-следование инструкции) - [references/eval-protocol.md](references/eval-protocol.md).
