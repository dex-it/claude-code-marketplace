# Этап определения интерфейсов: что производим и когда готово

Норматив выхода этапа - **машиночитаемый контракт** стыка: OpenAPI для HTTP, AsyncAPI для событий и очередей, IDL для gRPC. Форма выбирается по природе стыка, а не по привычке команды.

Здесь только норма этапа. Архитектурный контекст - `architecture-definition-42010`, требования на входе - `system-requirements-29148`, контракт стыка узлов - `node-contract`.

## 1. Вход и дом артефакта

**Обязательное поле входа - названный стык**: кто с кем обменивается и по какому поводу, плюс требования, которые этот обмен обслуживает. Стыка нет -> `status: blocked`: контракт без второй стороны специфицирует монолог.

**Дом контракта - рядом с кодом, не в `docs/`** (`api/`, `proto/`, рядом с реализующим модулем). Причина не вкусовая: контракт машиночитаем и участвует в сборке, генерации и контрактных тестах, а копия в документации расходится с рабочей молча. Архитектурное описание несёт **ссылку** на контракт, не его тело.

Контракт **порождается вместе с решением, а не после реализации**: спецификация, написанная по готовому коду, фиксирует то, что получилось, и теряет свойство договора.

## 2. Состав артефакта

| Блок | Что несёт | Признак незаполненности |
|---|---|---|
| Идентификация | имя контракта, версия, владелец, к какому продукту и фиче относится | версия отсутствует либо совпадает с версией сервиса, хотя меняется по своим правилам |
| Операции | каждая операция: устойчивый идентификатор, назначение, кто вызывает | назначение пересказывает имя метода |
| Схемы данных | входы и выходы: типы, обязательность, диапазоны, единицы измерения, формат | тип назван без ограничений; строка без длины и алфавита |
| Ошибки | закрытый перечень исходов на операцию: код, условие, что делать вызывающему | перечислены только успешные исходы, ошибка обобщена в «500» |
| Идемпотентность и повтор | какие операции безопасно повторять и по какому ключу | повтор не описан вовсе, вызывающий домысливает |
| Аутентификация и права | схема аутентификации, кто и что вправе вызывать | схема названа, границы прав по операциям - нет |
| Ограничения обращения | лимиты частоты, размеры полезной нагрузки, тайм-ауты | лимит живёт в конфиге, вызывающий узнаёт о нём по отказу |
| Совместимость и версия | текущая версия, правило изменения, срок поддержки предыдущей | правило не названо, каждое изменение обсуждается заново |
| Примеры | пример запроса и ответа на операцию, включая ошибочный | примеры только успешные, они же используются как тесты |

**Событийный стык несёт то же плюс своё:** имя канала, ключ партиционирования, порядок и его гарантии, дедупликация, поведение при повторной доставке, схема эволюции сообщения.

Блок без содержания закрывается **явным статусом с причиной** (проверка 3), а не молчанием.

## 3. Атрибуты единицы

Единица - операция или сообщение.

| Атрибут | Содержание |
|---|---|
| `ID` | устойчивый идентификатор операции, не меняющийся при переименовании пути |
| `traced from` | `FR-NNN`, который этот стык обслуживает; стык без требования - кандидат на снятие |
| `direction` | кто инициирует и кто отвечает |
| `errors` | закрытый перечень исходов, каждый с условием и действием вызывающего |
| `compatibility` | к какому классу изменений относится текущая правка |
| `deprecation` | если операция выводится: с какой версии, чем заменена, до какого срока поддерживается |

## 4. Проверки содержания

**1. Класс изменения назван до правки, а не после.** Изменения делятся на два класса, и граница проходит по тому, ломается ли работающий потребитель, а не по объёму правки.

| Класс | Примеры | Что требуется |
|---|---|---|
| совместимое | новое необязательное поле, новая операция, новый необязательный параметр, расширение перечня **исходящих** значений при объявленном правиле «неизвестное игнорируется» | правка версии по своему правилу, потребителя не трогаем |
| ломающее | удаление или переименование поля и операции, обязательность нового поля, сужение типа или диапазона, смена кода ошибки, смена семантики при том же имени, новое значение в перечне, который потребитель разбирает исчерпывающе | новая версия, срок жизни предыдущей, план миграции и перечень известных потребителей |

Ловушка обеих сторон: **расширение перечня значений** считают совместимым по умолчанию. Оно совместимо только если правило обработки неизвестного значения объявлено в контракте заранее.

**2. Каждый потребитель ломающего изменения назван.** «Мы никого не сломаем» без перечня потребителей - предположение. Перечень собирается до правки; потребитель, которого не нашли, - это не отсутствие потребителя.

**3. Ошибочные исходы описаны наравне с успешными; незаполненный блок закрыт статусом.** Активный проход по каждой операции: что вернётся при неверном входе, при отсутствии объекта, при конфликте, при отказе зависимости, при превышении лимита - и что вызывающему с этим делать. Незаполненный блок закрывается `n/a` с причиной либо «нет данных» с причиной и номером открытого вопроса.

## 5. Готовность документа

| Статус | Достигнут, когда |
|---|---|
| `draft` | контракт порождён, часть операций без схем или ошибок |
| `review` | все блоки состава присутствуют либо помечены статусом; каждая операция несёт схемы, ошибки и пример |
| `approved` | контракт принят обеими сторонами стыка, класс изменений назван, ломающее сопровождено планом миграции |
| `archived` | версия выведена из обращения, названа заменяющая |

Оракул контракта (`api-spec-quality`) в каталоге объявлен заделом и на момент этой редакции не создан: до его появления ось судейства закрывается записью `unverifiable` с причиной, а не молчанием и не подобранной заменой.

## 6. Выход этапа

- путь к контракту рядом с кодом и ссылка на него из архитектурного описания;
- перечень операций с `traced from` на требования;
- класс изменений текущей правки и, если он ломающий, перечень потребителей и план миграции;
- решения о версионировании, ушедшие в ADR, - ссылками;
- `quality-checks` - переносится со входа как есть;
- `self-check` - что прогнано и что устранено;
- `status` контракта.

Это вход этапа планирования верификации: контрактные тесты растут отсюда.

**Exit criteria:** контракт сохранён рядом с кодом; блоки состава присутствуют или помечены статусом; каждая операция несёт схемы, закрытый перечень ошибок и пример, включая ошибочный; класс изменения назван; ломающее изменение несёт перечень потребителей и план миграции; `self-check` заполнен; `status` проставлен.
