# Baseline проекта - гейты качества

Гейты - проверка типов, линтер, тесты и прогон того и другого в CI. Отсутствие гейта
симптома не даёт: билд зелёный, вопросов никто не задаёт, правка уходит непроверенной.
Поэтому наличие проверяется **шагом погружения в проект**, а не в ответ на жалобу -
жалобы не будет.

Вход - **первое погружение в контекст проекта на любой стадии**, не только закладка
нового. Возраст проекта, размер кодовой базы и тема текущей задачи вход не отменяют.

## 1. Сначала - что проект уже решил

Гейта нет - это либо незнание, либо принятое решение. Различает только запись, поэтому
до любых предложений найди её: раздел документации в `CLAUDE.md`, `docs/adr/`,
`docs/decisions/`, `*.adr.md`.

- Решение найдено (`Accepted`, не `Superseded`) -> следуй ему и **не переспрашивай**;
  вопрос закрыт, пока не наступило условие пересмотра из самого решения.
- Решения нет -> шаг 2.

> Расположение корпуса решений проекта устанавливает `dex-skill-project-docs-map`
> (грузит агент в той же фазе), актуальность статуса и supersede-цепочку -
> `dex-skill-codebase-conventions`. Сноска для человека: skill не загружает skill.

## 2. Что проверять: наличие артефакта, не его качество

| Гейт | dotnet | ts / js | python |
|---|---|---|---|
| Типы и статический анализ | `EnableNETAnalyzers` + `AnalysisMode` в `Directory.Build.props`, severity правил в `.editorconfig` | `tsconfig.json`; проект на `.js`/`.mjs` - `jsconfig.json` с `checkJs` | `mypy` / `pyright` в `pyproject.toml` или своём конфиге |
| Линтер и формат | `EnforceCodeStyleInBuild`, шаг `dotnet format` | `eslint.config.*` или `biome.json` | `ruff` в `pyproject.toml`; иначе `flake8` / `black` со своими конфигами |
| Тесты | тест-проект в решении и его прогон | скрипт `test` в `package.json` | `pytest` и его конфигурация |
| Прогон в CI | ось общая для всех стеков: сборка, тесты и аудит зависимостей идут на push/MR. Проверяется факт гейта, не платформа CI |

Проверка закрывается наличием артефакта. Настроенный, но неверный гейт - предмет
стековых skills (`dex-skill-dotnet-code-quality`, `dex-skill-ts-patterns`, skills
платформы CI), не этого.

Стека нет в таблице - оси те же: чем в этом стеке ловятся типы, стиль и регрессии и чем
это прогоняется на push. Отсутствие строки не означает, что гейты не нужны.

## 3. Гейта нет - действие зависит от роли

| Роль в этом вызове | Действие |
|---|---|
| Правишь код (реализация, фикс, рефактор) | назови отсутствующее **до** правок и предложи завести; цена входа даётся числом - включи, прогони, назови количество ошибок на текущем коде |
| Ревьюишь чужое изменение | отсутствие гейта - находка о проекте, а не условие приёмки MR; в требование к автору не превращается |
| Диагностируешь или читаешь код | назови в выводе как ограничение доказательности: без гейта «работает» опирается на чтение, а не на прогон |

До правок, а не после: на живом коде счёт ошибок растёт, правка без гейта увеличивает
его молча, а поднятый позже гейт краснеет разом - и цену уже не разделить. «Проект уже
большой», «задача сейчас не про это», «код и так собирается» - не основания пропустить
проверку, а причина назвать цену входа числом.

Гейт красный на существующем коде - не отключай правило и не смягчай конфиг: зафиксируй
число ошибок, почини задетое своей правкой, остальное вынеси отдельной задачей.

## 4. Отказ фиксируется решением, а не памятью

Человек отказался заводить гейт - это решение проекта, и оно записывается: какой гейт,
почему не заводим, чем компенсируем, при каком условии пересматриваем. Носитель - ADR в
корпусе решений проекта (устройство файла - `dex-skill-adr-quality`).

Не записал - на следующем касании проекта вопрос всплывёт снова, и отказ будет выглядеть
как незнание. Записал - шаг 1 закрывает вопрос молча.

Отказ снимает гейт, но не заменяет его: зелёный билд после отказа за проверенность кода
не выдаётся, а вывод несёт, чем проверка была ограничена.

Правила проекта изменились - гейт завели, порог сменили, отказ отозвали - правится
**существующее** решение: сам гейт, следствия, условие пересмотра; как норма менялась,
держит git. Новый ADR - только если выбранный вариант заменён другим; двух действующих
решений по одному предмету не остаётся ни в том, ни в другом случае.

## 5. Закладка нового проекта

### Новый проект с нуля
Плохо: создать скелет голым шаблоном и отложить гигиену «на потом» - без гейтов, без
централизованных версий зависимостей
Правильно: заложить baseline целиком **по дефолту**, без переспроса
Почему: нарушать нечего - чужих конвенций нет. Golden path задаётся сразу, и весь
последующий код пишется уже под активным гейтом; докрутить гигиену в проекте с
накопленным кодом дороже, и под гейтом всё краснеет разом

### Новый проект внутри существующего решения
Плохо: заложить свой baseline поверх - продублировать версии зависимостей, переопределить
общие настройки сборки, навязать свой конфиг линтера
Правильно: прочитать существующие общие настройки, **унаследовать** их, добавить только
недостающее для нового проекта; версии зависимостей - в общий файл версий, не локально
Почему: решение уже задаёт baseline на своём уровне. Конфликт «мой baseline vs правила
решения» решается в пользу решения - это конвенции владельца, не твои

## Границы

### Baseline - технический скелет, не бизнес-логика и не тесты
Плохо: под видом «baseline» создавать бизнес-логику, тест-проект или выбирать
архитектурный стиль и разбиение на слои
Правильно: baseline - **технический** скелет (структура + конфигурация + гейты).
Бизнес-код и тест-проект - по явному запросу; выбор архитектуры - отдельная задача
Почему: baseline - инвариант «проект настроен правильно», он не подменяет ни реализацию
фичи, ни архитектурное проектирование

### Проверка наличия - не аудит настроенного
Плохо: развернуть шаг 2 в полный аудит качества - разобрать профиль предупреждений,
пороги покрытия, состав правил линтера
Правильно: установить факт «есть / нет» по каждой оси и остановиться; глубина - предмет
стековых skills и профильного аудита
Почему: погружение в контекст не должно вырождаться в отдельную работу; иначе шаг
пропустят целиком как слишком дорогой
