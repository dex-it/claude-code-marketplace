# User Stories — ловушки

## Формулировка

### Story без value (So that)
Плохо: "Как пользователь, я хочу страницу настроек" — нет зачем
Правильно: "Как пользователь, я хочу настроить уведомления, чтобы получать только релевантные"
Почему: без value нельзя приоритизировать, команда не понимает зачем строить

### Техзадача как story
Плохо: "Как разработчик, я хочу внедрить Repository pattern"
Правильно: это Task внутри story, не отдельная story. Story = пользовательская ценность
Почему: tech task без user value не проходит INVEST (Valuable), прячет реальную потребность

### Технологии в description
Плохо: "Использовать Redis для кэширования, RabbitMQ для очередей"
Правильно: технологии в Technical Notes, description описывает поведение
Почему: story = обещание разговора, технические детали решаются при refinement с командой

## INVEST

### Not Independent
Плохо: "Зависит от story X" — нельзя взять в спринт без другой story
Правильно: включи зависимость в scope или объедини stories
Почему: зависимая story блокируется если предшественник не готов, спринт проваливается

### Not Negotiable
Плохо: детальная спецификация на 3 страницы с точными UI layout
Правильно: story = обещание разговора, детали уточняются при refinement
Почему: жёсткая спецификация убивает креативность команды и не учитывает технические реалии

### Not Estimable
Плохо: "Слишком много неизвестных, не можем оценить"
Правильно: Spike story для исследования (timeboxed), потом оценка основной story
Почему: без оценки невозможно планировать спринт, spike снимает неопределённость

### Not Small (13+ SP)
Плохо: story на 13+ story points, работа на 2+ спринта
Правильно: split по workflow (happy path, errors), rules (валидация, права), data (CRUD)
Почему: большая story не помещается в спринт, прогресс непредсказуем

## Acceptance Criteria

### AC нетестируемые
Плохо: "Всё работает правильно" или "Работает корректно"
Правильно: Given-When-Then с конкретными значениями: `Given 3 неверных пароля When ввод 4-го Then блокировка 15 мин`
Почему: QA не может проверить "правильно", конкретные значения = автоматизируемый тест

### Только happy path в AC
Плохо: AC покрывает только успешный сценарий
Правильно: happy path + error + edge cases: неверный пароль, блокировка, истёкший токен, SQL injection
Почему: 80% багов в error handling. AC без edge cases = баги обнаруживаются на production

### Пустые данные не учтены
Плохо: AC не описывает поведение при пустом списке
Правильно: "Given 0 элементов Then показать 'Нет данных'" — не null, не пустая страница
Почему: пустое состояние = первый опыт пользователя, null ломает UI

### Concurrent access не учтён
Плохо: AC для одного пользователя, нет сценария одновременного доступа
Правильно: "Given два пользователя редактируют одновременно Then второй получает conflict"
Почему: без concurrency AC — last write wins, данные первого пользователя потеряны

### Спецсимволы и граничные значения
Плохо: AC только для "нормальных" данных
Правильно: имя O'Brien (апостроф), текст 500 символов (лимит), timezone разных часовых поясов
Почему: спецсимволы ломают SQL/HTML, длинный текст ломает layout, timezone = разные даты

## Место в конвейере требований

### Критерий написан при правиле, а не при истории

Неправильно: правило заводится сразу с примером на конкретных данных, история потом забирает готовый критерий.
Правильно: правило пишется с методом проверки - чем убедиться, что оно соблюдается; пример на данных рождается при нарезке в историю, черновик берётся с веток сценария.
Почему: одно правило проявляется в нескольких историях разными примерами, и написанный при правиле пример пришлось бы растаскивать по ним руками. К тому же между правилом и историей встают меры `NFR`, которых в сценарии нет вовсе, - критерий, написанный до них, будет переписан.

### Правило извлекают из готовых критериев задним числом

Неправильно: команда пишет истории с критериями, а свод правил собирается потом - вычиткой критериев.
Правильно: порядок обратным не бывает: правило выводится из сценария, критерий - пример к правилу. Обнаружилось поведение, которого нет ни в одном правиле, - это находка, а не повод завести правило из критерия.
Почему: правило, извлечённое из `AC`, не несёт ничего сверх учёта уже написанного и делает историю вторым домом поведения. Дальше правка правила не задевает критерии, а правка критериев молча меняет норму.

### Критерий не несёт метки своего правила

Неправильно: критерии перечислены списком, к какому правилу каждый относится - видно только автору.
Правильно: у критерия стоит метка его правила; критерий без правила в набор не входит - это находка, а не мелочь оформления. Мера `NFR` попадает в историю ссылкой на ID и назначенной проверкой, а не переписанным числом.
Почему: без метки нельзя посчитать ни покрытие правил примерами, ни задетое при правке: правило меняется, а какие критерии переписывать - неизвестно. Переписанное же число расходится с мерой при первой её правке, и история продолжает проверять отменённый порог.

### Полноту проверяют с одной стороны

Неправильно: проверено, что у каждого правила есть пример, - нарезка считается полной.
Правильно: полнота считается с двух сторон: каждая ветка сценария покрыта хотя бы одним критерием в какой-нибудь истории, и каждое правило породило хотя бы один критерий. Непокрытая ветка и правило без примера - находки.
Почему: односторонняя проверка сходится на том, что написано, и молчит о том, чего нет: ветка, для которой не завели правила, не даст и критерия, а по правилам всё будет покрыто. Именно так теряются отказные ветки - у них нет ни правила, ни примера, и предъявить пропажу нечему.

### Примеры подбирают на глаз

Неправильно: критерии пишутся по вдохновению - что вспомнилось про границы и ошибки.
Правильно: примеры подбираются техниками тест-дизайна - границы, классы эквивалентности, таблица решений, переходы состояний; дом у этих техник один, второй копией он не заводится (`dex-skill-test-design`).
Почему: подбор на глаз даёт плотное покрытие середины диапазона и пустоту на краях, где и живут дефекты. Кроме того, набор критериев, собранный без техники, невозможно проверить на полноту - непонятно, относительно чего он полон.

### Вопрос, оставшийся без ответа, закрывают критерием-догадкой

Неправильно: при нарезке выяснилось, что поведение в каком-то случае неизвестно, - критерий пишется по здравому смыслу.
Правильно: невыводимое идёт наверх пачкой в форме «предлагаю X, потому что Y»; история с открытым пунктом в работу не отдаётся завершённой.
Почему: критерий - последняя инстанция перед кодом, и догадка в нём становится нормой без единого решения: разработчик реализует, тест закрепляет, и вопрос больше никогда не задаётся.

## Чек-лист

- Story даёт value пользователю (не техзадача)
- INVEST: все 6 критериев проверены
- AC: happy path + error + edge cases
- AC: конкретные значения (не "правильно работает")
- Нет технологий в description
- Size: 1-8 SP (13+ -> split)
- Пропущенные сценарии проверены (пустые данные, concurrent, спецсимволы)
- У каждого критерия стоит метка его правила, мера NFR - ссылкой на ID
- Полнота посчитана с двух сторон: ветки сценария покрыты, правила дали примеры
- Открытых пунктов в истории нет (догадкой критерий не закрывается)
