# ADR - ловушки написания

**ADR - спецификация, по которой пишут код, а не описание того, что код уже делает.** Ловушки
ниже - частные случаи одного отклонения: автор писал ADR по коду, имея код перед глазами.
Применимо к написанию и к ревью чужого ADR.

## Норма vs состояние кода

### Норма и текущая реализация вперемешку
Плохо: «Решение» описывает норму и тут же состояние кода («сейчас 9 мапперов из 13»)
Правильно: «Решение» - только целевая норма; состояние реализации - отдельным разделом-приложением в конце. Проверка: удали приложение - «Решение» обязано остаться полным и осмысленным
Почему: приложение протухает с первой правкой кода, норма протухать с ним не должна. Смешение делает спорным любое расхождение - непонятно, норма это или описание

### Констатация вместо предписания
Плохо: пункт нормы - утверждение о свойстве системы («идентичность детерминирована», «мапперов девять»)
Правильно: исполнимая инструкция в императиве - что делаю / чего не делаю. Проверка: «что конкретно я должен написать в коде?»; нет ответа -> наблюдение, не норма
Почему: ADR - действующее ограничение на код. Констатацию нельзя ни выполнить, ни нарушить - значит ограничением она не является

### Пункт нормы без проверки
Плохо: пункт говорит, как правильно, но нарушение ничем не ловится
Правильно: правило (императив) + проверка (тест/гейт/ревью, ловящий нарушение) + почему (цена); обоснование после правила
Почему: правило, за нарушение которого ничего не происходит, де-факто отсутствует. Обоснование перед правилом заставляет удерживать контекст, не зная, к чему он

### file:line и имена классов в норме
Плохо: норма опирается на `FooMapper` / `src/x.cs:42` как на несущий элемент; таблица «триггер -> файл:строка» вместо правила
Правильно: норма в терминах домена («тип конфигурации -> формат X»). Якоря - только в карте кода в шапке (навигация) и в приложении о расхождениях (доказательство факта). Проверка: скрой имена файлов и числа из реализации - норма обязана остаться формулируемой
Почему: имя класса переживает один рефакторинг, норма обязана пережить все. Числа вида «9 из 13» - факт о коде, а не норма

## Границы и полнота

### ADR с дырой внутри своих границ
Плохо: контракт границы (эндпоинты, модели сообщений, форматы, структуры данных) не описан - «смотри код»
Правильно: знание, без которого код не написать, входит в ADR отдельным разделом; вынесенное за границы - поимённо, со ссылкой на владеющий ADR. Проверка: инженер без единой строчки кода реализует подсистему по ADR, не задав ни одного вопроса
Почему: дыра отправляет читателя в код за недостающим, и код снова становится источником нормы - разделение нормы и состояния обходится с чёрного хода

### Открытый вопрос без дефолта
Плохо: открытые вопросы блокируют принятие ADR; среди них - выводимое из кода и источников
Правильно: только не выводимое (продуктовое/бизнес-намерение), у каждого - рабочий дефолт + обоснование + предложение владельцу («принял X, потому что Y; подтверди или поправь»)
Почему: ADR не должен ждать - ответ владельца уточняет формулировку, но не является условием принятия. Вопрос, выводимый из кода/источника, - невыполненная работа автора

## Обоснование

### Источники требований смешаны в одну кучу
Плохо: все пункты одинаково «обязательные»
Правильно: у каждого пункта - источник, источники не смешиваются: обязательное по внешнему источнику (ломает контракт платформы/стандарта) / инженерно обязательный фикс (источник не требует, цена предъявлена) / инженерный инвариант (нужен для предсказуемости) / рекомендация
Почему: когда всё «обязательное», приоритет не читается. Разный источник - разная очередь внедрения и разный вес в споре

### «Обязательно по стандарту» без цитаты
Плохо: ярлык «обязательное по внешнему источнику» опирается на пересказ источника
Правильно: дословная цитата, где требование сформулировано явно. Нет цитаты -> это инженерный вывод, перемаркировать
Почему: пересказ незаметно расширяет требование до желаемого. Формально соблюдённый стандарт при нарушенной семантике - типовой случай завышенного ярлыка

### Вывод, опровергнутый сверкой, заменён тихо
Плохо: сверка с источником развернула ранний вывод - текст просто переписан на новый
Правильно: опровергнутое реверсится и помечается реверсом явно («это реверс первоначального вывода»); смягчение вместо реверса не годится
Почему: тихая замена прячет, почему раньше считалось иначе, и вывод возвращается следующим автором. Практика, наблюдаемая в коде, - не аргумент о должном: она ровно то, что проверяется

## Работа с файлом ADR

### Перезапись поверх чужих правок
Плохо: ADR перезаписан целиком по локальной копии
Правильно: перед перезаписью - fetch + сверка с целевой веткой; после - сверить перенос поимённо по диффу ревьюера, не по памяти
Почему: правки ревьюера могли уехать в базу, пока локальная копия отставала. Затёртая правка не видна ни в одном тесте

### Перенумерация пунктов
Плохо: пункты сдвинуты, ссылки в соседних документах не тронуты
Правильно: пункты ADR - публичный якорь (описательные документы, планы, журналы, соседние ADR); сдвинул нумерацию -> свип по всем документам, включая подпункты
Почему: `п.7.4` -> `п.7.3` ловится только точным поиском; ссылка молча начинает указывать на другое правило

### DoD-чекбокс по намерению
Плохо: пункт отмечен `[x]`, потому что автор собирался это сделать
Правильно: закрывая чекбокс - открыть артефакт и убедиться глазами; обнаружил фиктивный -> закрыть с пометкой, почему был фиктивным, не тихо доделать
Почему: чекбокс - утверждение о факте; отмеченный по намерению превращает DoD в декорацию
