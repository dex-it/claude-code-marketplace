# Таксон единицы свода

Читается до заведения первой единицы и при каждом сомнении в значении. По памяти схемы не воспроизводятся: внешние схемы переименовывают категории между редакциями, и значение без версии через год утверждает не то, что утверждало при записи.

## Почему таксономия, а не свободный тег

Решение не стилистическое. SARIF 2.1.0 (OASIS Standard incorporating Approved Errata) в определении поля `tags` (§3.8.2.1) рекомендует: теги не использовать (SHOULD NOT), чтобы отнести находку или правило к категории классификации, - для этого использовать таксономии (SHOULD, §3.19.3); и там же отдельно сказано, что правило действует **и для собственной схемы, определённой внутри инженерной команды**. Причина техническая: таксономия несёт описание категории и адрес её определения, тег не несёт ничего, кроме строки.

Второй довод - замеренный. Свободные теги дают длинный хвост: на корпусе Stack Overflow из более чем 38 тысяч тегов четверть использована меньше десяти раз (Beyer, Pinzger, ICPC 2015, замер сентября 2014). Хвост не ищется и не сопровождается.

Третий довод против иерархии внутри собственной схемы: согласованность разметки при плоском списке дескрипторов выше, чем при тезаурусе - 39.5% против 27.7% на трёх абстрактах и 63 разметчиках (Soler Monreal, Gil-Leiva, Information Research 16(4), 2011, paper 502), и разрыв тем больше, чем опытнее разметчик. Поэтому собственная схема плоская, а иерархию несут внешние схемы, где она нормирована.

## Форма значения

```
<схема>:<значение>@<версия схемы>
```

Версия обязательна у каждой схемы, включая собственную. Единица несёт **один** обязательный таксон собственной схемы и сколько угодно необязательных внешних.

## Собственная схема: `internal`, версия 2

Версия двигается при каждом изменении перечня значений: одно и то же имя схемы с разным набором значений делает записанный таксон неоднозначным, и найти это нечем.

Перечень закрыт. Значения, которого здесь нет, в своде не бывает: расширение схемы - правка этого файла, а не решение прогона.

| Значение | Что относим |
|---|---|
| `naming` | имена типов, файлов, методов, веток, коммитов |
| `layout` | где лежит артефакт, как разбит на файлы, границы модуля |
| `signature-convention` | форма публичной сигнатуры: порядок параметров, суффиксы, обязательные аргументы |
| `error-handling` | форма отказа: исключение против результата, иерархия ошибок, какие отказы вообще логируются |
| `integration` | как подключается внешний ресурс: клиент, конфигурация, регистрация |
| `testing` | что покрывается, чем, где лежит тест, что считается достаточным |
| `review-process` | как ведётся ревью: что блокирует, кто согласует, что делает автор с замечанием |
| `delivery` | ветвление, форма MR, порядок раската |
| `documentation` | что и где документируется, форма комментария и записи решения |
| `security` | обращение с секретами, правами доступа, входными данными на границе доверия |
| `performance` | доступ к данным, round-trip, аллокации, материализация на горячем пути |
| `concurrency` | потокобезопасность, отмена, тайм-ауты, идемпотентность, границы транзакций |
| `compatibility` | обратная совместимость публичного контракта, версионирование, миграции данных |
| `observability` | уровни и состав логов, метрики, трейсы, корреляция |
| `dependencies` | какие библиотеки допускаются, как выбираются версии, чем закрывается уязвимость в них |

Значение выбирается по **предмету правила**, а не по слову в цитате. Правило про имя переменной в тесте - `naming`, не `testing`: таксон отвечает на «о чём правило», а раздел свода строится по нему.

Правило подпадает под два значения одинаково - берётся **более узкое по предмету**, а при равной узости то, что стоит выше в таблице; второе называется в выходе. Порядок таблицы служит последним разрешением ничьей потому, что предсказание «по какому значению будут искать» у двух узлов расходится, а раздел свода строится по таксону: единица переезжала бы между файлами от прогона к прогону. Порядок таблицы служит разрешением ничьей потому, что предсказание «по какому значению будут искать» у двух узлов расходится, а раздел свода строится по таксону: единица переезжала бы между файлами от прогона к прогону. Не подпадает ни под одно - единица не заводится, а нехватка значения называется пунктом выхода как дефект схемы: расширять её на ходу значит завести одиночное значение, которым больше никто не воспользуется.

## Внешние схемы

Подключаются, когда правило ложится на нормированную категорию. Значение берётся из первоисточника, не по памяти; версия ставится та, по которой сверяли.

| Схема | Что даёт | На что смотреть при выборе значения |
|---|---|---|
| `cwe` | класс слабости кода | уровень абстракции: значения уровня Base и Variant пригодны, значение-категория - нет; у части значений первоисточник прямо запрещает или не рекомендует их использование для разметки |
| `owasp` | категория риска приложения | редакция меняет состав категорий и их номера, поэтому версия схемы обязательна |
| `iso25010` | характеристика качества продукта | редакция 2023 переименовала часть характеристик; имя берётся из действующей редакции |

Внешнее значение не заменяет собственного: собственная схема строит разделы свода, внешняя даёт стык с чужими инструментами.

## Сверка версии

Версия схемы сверяется **при заведении единицы**, а не при чтении свода. Значение, унаследованное из прошлого прогона, при обновлении единицы пересверяется; расхождение действующей редакции с записанной - находка, закрываемая обновлением значения и версии, и обе стороны называются в выходе.

Сверить не удалось - таксон внешней схемы не ставится вовсе, и это лучше, чем поставленный на память: отсутствующий стык виден, а неверный - нет.
