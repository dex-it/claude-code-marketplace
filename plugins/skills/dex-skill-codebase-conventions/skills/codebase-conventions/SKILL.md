# Codebase conventions - ловушки и anti-patterns

Конвенция - произвольный выбор, ценный только единообразием: правильного ответа в вакууме нет, есть «как принято здесь». Этим она отличается от технической best-practice, где правильность объективна.

Добавляешь класс, метод, файл - сверься с соседями того же типа. Ниже 6 осей (последняя - ADR поверх соседского кода) + граница «что копировать, а что нет».

## Гейт обоснования - над всеми осями

Каждое решение по осям ниже стоит на **названном первоисточнике**: `file:line` соседа-образца, id `Accepted` ADR или enforced-правило (`.editorconfig` / analyzer / lint). Прецедента в проекте нет - решение становится **записанным допущением** («выбрал X, потому что Y; альтернатива Z»), не тихим дефолтом. Опора на prior или «так обычно принято» без названного первоисточника - решение необосновано: это угадывание, а не следование проекту, и разнобой пойдёт с первой копипасты.

Оси обоснования различаются источником, требование назвать его - общее: *конвенция* (произвольный выбор) стоит на соседе или ADR; *техническое решение* (lifetime DI, throw vs Result, sync vs async, тип бросаемого исключения под семантику) - на свойстве кода или требовании, не на «как у соседа». Принадлежность исключения базовой иерархии подсистемы - конвенция слоя (ось 3). Итог: **ни одно решение не стоит на неизученном дефолте.**

## Ось 1: Форма представления одного смысла

### Один смысл - несколько форм; новый код выбрал не ту, что соседи
Плохо: у типа есть типизированный конструктор и строковый DSL (`new Range(from, to)` vs `Range.Parse("[N:M]")`); соседи берут типизированный путь, новый код - DSL
Правильно: поиск по имени типа - какую форму использует большинство соседей; следовать ей либо явно обосновать отступление
Почему: две формы одного смысла заставляют читателя выяснять «почему здесь иначе», а DSL переносит ошибки из compile-time в runtime. Конвенция теряет силу с первой копипасты нового стиля

### Возврат значения не в той форме, что соседи в слое
Плохо: соседи слоя возвращают `Result<T>` на error-path, новый метод бросает исключение или `null`; либо наоборот - везде throw, новый молча возвращает пустое
Правильно: посмотреть 2-3 соседних метода слоя - throw / Result / nullable / Option; держать единую форму во всём слое
Почему: caller строит обработку под форму слоя (try/catch, pattern-match, null-check). Метод в другой форме ломает паттерн вызова и провоцирует пропуск ошибки

## Ось 2: Имя через назначение vs через реализацию

### Имя по реализации, хотя соседи именуются по назначению
Плохо: поле `HasImplementation` при соседних `HasOnboarding`, `IsActivated`; `ProcessDataInLoopHandler` при соседях `<Domain>CompletedHandler`
Правильно: поиск по соседям той же роли (Handler / Repository / Component) - на какой оси они именуются; следовать ей
Почему: слой задаёт один словарь, имя на другой оси выпадает из ряда. Имя по реализации устаревает при рефакторинге ветки, по назначению - переживает его

### Тип ошибки вне доменного словаря проекта
Плохо: в проекте есть `OrderNotFoundError`, `OrderInvalidStateError`, а новый код кидает generic со строкой (`InvalidOperationException("Order not in Draft")`)
Правильно: взять существующее доменное исключение или добавить рядом по той же конвенции (наследование, namespace, нейминг)
Почему: тип ошибки - часть API слоя: `catch (OrderInvalidStateError)` на generic не сработает, обработка теряет специфичность. Доменный словарь работает, только пока пронизывает все слои контекста

### Doc-комментарий называет конкретного потребителя типа
Плохо: `/// <summary>Employee info (used by ReportingService)</summary>` - имя клиента в doc-комментарии
Правильно: описывать, ЧТО содержит тип или делает метод; потребители - в арх-документе, не в коде
Почему: имя потребителя устаревает при смене интеграции или втором клиенте, и комментарий превращается в дезинформацию

### Имя класса/метода не переименовано при смене поведения
Плохо: `CreateOrderConsumer` переписан под Update-семантику; `DetectItems` после переезда обнаружения просто добавляет строки
Правильно: переименовать вслед за смыслом (`UpdateOrderConsumer`, `AddItems`); мешает техническое препятствие - TODO с причиной в теле и в описании MR
Почему: расхождение имени с поведением - скрытый баг чтения: логику ищут по старому имени и не находят либо предполагают прежнюю семантику и заводят дубль

### Разнобой порядка слов в парных типах
Плохо: `OrderRawData` (субъект впереди) + `ProcessOrderResult` (глагол впереди) для одной операции
Правильно: одна ось на пару - `OrderRawData` + `OrderResult` либо `ProcessOrderInput` + `ProcessOrderResult`
Почему: пара input/result читается вместе; разный порядок слов маскирует связь и требует контекстного поиска

## Ось 3: Сквозная конвенция слоя

### Метод не следует общей конвенции сигнатуры слоя
Плохо: соседи принимают токен отмены последним параметром (`CancellationToken ct`, `AbortSignal signal`), новый - без него, с другим именем или без суффикса `Async`, который есть у всех
Правильно: посмотреть 2-3 соседних метода слоя на общую ось сигнатуры (отмена, логгер, корреляционный id, суффикс) и следовать ей
Почему: пайплайны cancellation / tracing / retry держатся на однородности сигнатуры - метод без токена ломает graceful shutdown цепочки, разное имя параметра ломает кодогенерацию

### Артефакт не следует общему правилу слоя (структура / атрибуты / базовый тип)
Плохо: все Validator'ы наследуют базовый тип, новый - ручной; все Controller'ы помечены маркером (`[ApiController]`, `@Controller`), новый нет; все DTO иммутабельны, новый мутабельный; парные исключения подсистемы наследуют разные базы (`ContentTooLargeException : SubsystemException` рядом с `DiscriminatorException : Exception`)
Правильно: сверить 2-3 соседних артефакта на базовый тип, обязательные атрибуты, иммутабельность; следовать единому правилу. Исключение сознательно вне иерархии (framework-level) - задокументировать в контракте метода (`<exception>` / `@throws` / docstring Raises)
Почему: правило слоя - договор для потребляющей механики (auth-middleware ищет маркер, validation-pipeline - базовый тип, `catch` базы подсистемы - полную иерархию). Артефакт вне правила выпадает из неё: остаётся без auth или без валидации, а у исключений дыра необнаружима - компилятор молчит, тест не пишут, всплывает непойманным в проде

### Сущностный ID передаётся сырым `Guid` вопреки typed-id соседей
Плохо: `client.Send(projectId, data)`, где метод ждёт `repositoryId` - оба `Guid`, компилятор перепутанный ID не ловит
Правильно: соседи используют typed-id (`ProjectId`, `RepositoryId`) - новый код принимает тот же тип, не сырой `Guid`
Почему: примитивы разных сущностей взаимозаменяемы для компилятора; отступление от typed-id убирает единственную защиту, и ошибка всплывает битой ссылкой в данных, а не на сборке

## Ось 4: Расположение артефакта

### Файл положен не туда, где лежат соседи того же типа
Плохо: новый Handler в `Application/Services/`, когда все Handler'ы лежат в `Application/Handlers/<Feature>/`
Правильно: до создания файла - поиск по суффиксу или роли (`*Handler.*`, `*.component.*`); положить рядом с соседями
Почему: файлы ищут по конвенции. Файл «не там» невидим при ревью соседних изменений, дублируется при следующем рефакторинге и ломает auto-discovery (DI-сканеры по namespace, build-globs)

### Логика положена не в тот слой / класс, где живёт у соседей
Плохо: валидация размазана между Controller, Handler и Validator, тогда как у соседей она вся в `*Validator`; маппинг entity -> DTO в каждом Handler при общем профиле у соседей
Правильно: посмотреть, где у соседей живут те же обязанности (валидация, маппинг, авторизация, логирование), и следовать тому же месту
Почему: одна обязанность в одном месте - основа cross-cutting правок; размытое расположение требует править N мест, одно из которых забудут

## Ось 5: Способ интеграции с внешним ресурсом

### Способ работы с внешним ресурсом расходится с соседями
Плохо: у соседей HTTP-клиент через фабрику или shared instance (`IHttpClientFactory`, `axios.create()`), новый код - `new HttpClient()` напрямую; соседи читают конфиг типизированным provider'ом, новый - env напрямую
Правильно: посмотреть, как у соседей подключён тот же тип ресурса (HTTP / config / log / cache / messaging), и следовать ему
Почему: способ интеграции несёт невидимые сбоку контракты - фабрика даёт обновление DNS и обёртку retry, типизированный конфиг даёт валидацию и hot-reload. Уход с конвенции отрезает новый код от них: отдельный клиент течёт сокетами, env не валидируется

### Регистрация / конфигурирование сделаны не тем способом, что у соседей
Плохо: соседние options идут типизированной секцией конфига, новый - singleton с захардкоженными значениями; соседние модули регистрируются extension'ом (`AddOrderModule()`), новый - россыпью в композиционном корне
Правильно: посмотреть, как соседи регистрируют тот же класс артефактов (options, сервисы, hosted services, декораторы), и держать единый стиль
Почему: единый стиль регистрации даёт одну точку расширения - декоратор или валидатор навешивается правкой одного места. Разнобой требует обходить все места поодиночке, новое пропускают. Hardcoded options теряют конфигурируемость по средам

## Граница: конвенция vs техническое решение

### Скопирована «конвенция», которая на деле - техническое решение
Плохо: «у соседа Singleton - делаю так же» без проверки на mutable state, captive dependency и thread-safety; «у соседа throw - и я throw» без проверки, нужна ли клиенту обработка через Result; «сосед `async` - и я `async`» при отсутствии IO
Правильно: копировать у соседей конвенции (форма представления, нейминг, структура папок, сигнатура слоя, способ интеграции); обосновывать под свой код технические решения (lifetime DI, throw vs Result, sync vs async, тип исключения под семантику - принадлежность базовой иерархии подсистемы при этом конвенция слоя, ось 3)
Почему: для конвенции «правильно» вне проекта не существует, ценность и есть единство; для технического решения валидность зависит от свойств конкретного кода. Слепо скопированный Singleton наследует captive dependency или race condition, скопированный throw - утечку технического исключения в API. Перед копированием спроси: это произвольный выбор или решение под требования?

## Ось 6: Зафиксированное решение (ADR) поверх «как у соседей»

ADR (`docs/adr/`, `docs/decisions/`, `*.adr.md`, MADR) - конвенция, поднятая до нормы: принятое решение перекрывает то, как сделано у большинства соседей, потому что сосед мог отстать от решения. Погружаясь в проект, перечисли ADR и их статусы до выводов по соседнему коду.

### ADR-решение проигнорировано в пользу «как у соседей»
Плохо: при `ADR-014: межсервисное взаимодействие через очередь` новый код шлёт прямой HTTP, потому что «сосед тоже шлёт» (сосед - легаси до ADR)
Правильно: конфликт «сосед в коде» vs `Accepted` ADR решается в пользу ADR, легаси-сосед считается долгом, не образцом; отступление - только с явным обоснованием в ADR или MR
Почему: ADR фиксирует решение на будущее, код отстаёт от него постепенно. Копировать легаси-соседа значит тиражировать то, что ADR уже отменил

### Находка/правка против Accepted ADR подсвечена дефектом (а не осознанным trade-off)
Плохо: ревью метит багом «синхронный вызов вместо очереди», хотя `ADR-022` принял синхронный путь для этого контура; либо наоборот - код идёт вразрез с `Accepted` ADR и никем не помечен
Правильно: сверить находку с ADR до вердикта - покрытое `Accepted` ADR отклонение пометить «по ADR-NNN» и не подсвечивать; непокрытое - подсветить с указанием нарушенного ADR
Почему: ADR - маркер принятого решения наравне с `TODO`+тикет. Подсветка взвешенного решения - ложный шум, пропуск нарушения `Accepted` ADR - пропущенная регрессия; различает только сверка, не вид кода

### Использован отменённый ADR вместо актуального в supersede-цепочке
Плохо: код или ревью опирается на `ADR-007`, не заметив `Status: Superseded by ADR-019`
Правильно: проверять поле `Status` каждого ADR - `Deprecated` / `Superseded by ADR-NNN` означает «не норма»; идти по цепочке до актуального `Accepted`
Почему: ADR не удаляют при замене, а помечают `Superseded`, сохраняя историю. Принять отменённый за действующий - следовать норме, которую проект сознательно отверг

## Чек-лист перед PR

- [ ] **Гейт обоснования:** на каждое решение назван первоисточник (`file:line` соседа / `ADR-NNN` / enforced-правило) либо записано допущение, где прецедента нет?
- [ ] Решение по теме изменения покрыто `Accepted` ADR - следую ему, не легаси-соседу; отклонение помечено «по ADR-NNN» или подсвечено?
- [ ] Есть соседи того же типа - какие из 6 осей применимы?
- [ ] Форма представления (возврат, конструирование, иммутабельность) - как у соседей?
- [ ] Имя - на той же оси, что у соседей в слое?
- [ ] Сигнатура, атрибуты, базовый тип - по общему правилу слоя?
- [ ] Файл лежит с соседями того же суффикса; обязанности (валидация, маппинг, auth) - там же, где у них?
- [ ] Способ интеграции с внешним ресурсом - тот же, что у соседей?
- [ ] Копируя техническое решение (lifetime, exception, sync/async, throw vs Result), проверил его валидность для своего кода, а не только наличие у соседа?
- [ ] Отступление от конвенции обосновано в коде или в описании MR?
