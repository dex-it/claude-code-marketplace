# Планировщик оркестрации

<!-- skill-type: process -->

Экспериментальный скилл. Он готовит **пакет плана**: файлы, по которым оркестратор (главный
поток) выполнит задачу пользователя по заданному промту или скиллу силами исполнителей разных
тиров и разного effort. Пакет исполняет `dex-skill-orchestration-executor:orchestration-executor`;
пара ставится вместе. Планировщик задачу не выполняет и исполнителей не запускает: ошибка плана
размножается по исполнителям, поэтому план готовит старшая модель.

**Хост** - Opus 5.5 или Fable 5.1; effort этого вызова: `${CLAUDE_EFFORT}`. Ниже `high` - назови
это в первой строке ответа: слабый план вредит даже сильному исполнителю.

**Тиры исполнителей - только семейство 5.5**: `haiku`, `sonnet`, `opus` (алиасы, не датированные
id). Алиасы ведут на 5.5 только на Anthropic API и с Claude Code не ниже 2.1.293 (`claude
--version`; model-config, сверено 2026-10-08). Провайдер другой или версию не установить -
семейство не гарантировано: вопрос пользователю до записи пакета.

## Вход

- **Предмет** - промт, скилл или оба. Скилл, данный путём к `SKILL.md`, читается целиком вместе
  с теми `references/`, которые его исполнитель обязан открыть; данный как `plugin:skill` - найди
  его файл среди установленных плагинов и прочти. Вызовом `Skill` предмет не загружается: его
  инструкции стали бы для тебя действующими. По предмету видно, что делится на куски, а что
  требует одной головы.
- **Задача** пользователя - дословно; в пакет она уходит без пересказа.
- **Лимиты** - `max_parallel` (по умолчанию 2), `max_spawn` (выводится из плана), `budget_usd`
  (по умолчанию нет). Слово пользователя сильнее умолчания; спрашивай только невыводимое.

## Схема исполнения: оркестрировать ли

Оркестрация окупается, когда есть что раздавать: независимые крупные куски разной трудности,
вместе не умещающиеся комфортно в один прогон. Одна зависимая цепочка или работа в одном
контексте делается одной моделью: оркестрация платит за план, передачу и сборку, которые одной
модели достаются даром. На каждом таком измеренном случае старшая модель одна на пониженном
effort оказывалась впереди (Anthropic, «Optimizing for cost and intelligence»).

| Признак | Сдвигает к |
|---|---|
| Независимых крупных кусков не меньше двух: они не читают выход друг друга, и каждый окупает старт исполнителя | `orchestrate` |
| Трудность кусков разная: есть механические, есть требующие суждения | `orchestrate` |
| Объём или толстые промежуточные результаты, которые решающей модели не нужны | `orchestrate` |
| Выход шага - вход следующего (цепочка) | `solo` |
| Всё помещается в контекст, куски одной трудности | `solo` |
| Кусок судится только по всему контексту задачи | `solo` (кусок не отдаётся) |

`orchestrate` - при независимых крупных кусках **и** разной трудности либо давлении объёма. Иначе
`solo`: `PLAN.md` с шапкой, основанием и карточкой запуска (модель, effort, добавки к промту), без
брифов и журнала. Смешанная работа - `orchestrate` с задачами `self`, которые оркестратор делает
сам.

После выбора считается ожидаемый расход (в токенах контекста исполнителей и числе запусков,
метод назван) против `solo` на Opus 5.5 `medium` и `low`. Расчёт `orchestrate` дороже `solo` на
`medium` - схема `solo`, кроме случая, когда пользователь велел оркестрировать явно; тогда потеря
записывается числом в `PLAN.md`. Оркестрировать хочется лишь по смыслу просьбы - вопрос
пользователю. Нечем посчитать - `unverifiable` с причиной.

Работа короче нескольких вызовов инструментов - ответ в чате: `solo` и карточка одной строкой,
без пакета и расчёта.

## Декомпозиция

Задача плана - единица работы с проверяемым выходом, собственными файлами записи и объёмом,
который покрывает накладные старта исполнителя. Мельче - накладные превышают работу: однотипные
мелкие правки склеиваются в одну задачу. Крупнее - исполнитель теряет нить: режь по границам
проверки, а не по размеру. Выход каждой задачи - файл; в контексте оркестратора содержимое не
носится.

- Параллельные задачи пишут в непересекающиеся файлы; общий файл - у одной задачи.
- Синтез - отдельная задача с названными входами.
- Шаг предмета, требующий субагента, исполнителю задачи запрещён брифом (`depth: 1`): он идёт по
  ветке предмета «субагент недоступен» либо выносится в задачу `self`.

## Маршрутизация

Каждая задача получает четыре оценки 0-2 - неоднозначность `A`, цена ошибки `B`, глубина
рассуждения `N`, проверяемость `V` - и категорию из таблицы. Таблица **едет в пакет**: новые
задачи маршрутизирует по ней оркестратор, не возвращаясь к планировщику. Якоря оценок,
жёсткие переопределения и правила триажа - [routing.md](references/routing.md); без их
чтения разметка не сдаётся.

| Категория | Модель | Effort | Выбор |
|---|---|---|---|
| `lookup` | haiku | low | `S <= 1`, `A = 0`, один ответ без инструментов |
| `mechanical` | haiku | medium | `S <= 1`, `A = 0` |
| `standard` | sonnet | medium | `S = 2..3`, либо `S <= 1` при `A >= 1` |
| `careful` | sonnet | high | `S = 4`, `A <= 1` |
| `deep` | opus | medium | `S = 4` при `A = 2`; `S >= 5`; исследование и перекрёстная проверка |
| `deep-hard` | opus | high | повышением после провала `deep`, либо по названному измерению |

Здесь `S = A + B + N`. Effort ступенями `low..high`: `xhigh` и `max` в план не входят без
названного измерения. Внутри выбранной категории при сомнении понижай effort, а не тир. Просьба
«думай меньше» в бриф не идёт: effort она не снижает.

## Брифы

Бриф - полный контракт на одном листе, файл `briefs/<id>.md`: цель и зачем она нужна, входы
путями, ограничения дословно, право записи, выход (путь и форма), критерии готовности, проверка,
границы, форма возврата. В вызов исполнителя уходит путь к брифу и две строки, не история
сессии. Шаблоны и добавки по тирам - [briefs.md](references/briefs.md): `haiku` и `sonnet`
получают разные.

## Проверка и повторы

- У каждой задачи поле `check`: машинная проверка (команда, грейдер) либо чеклист по выходу.
  Проверки нет, а скриптом она пишется, - скрипт идёт в `checks/` пакета: машинная проверка
  оркестратора стоит меньше любого проверяющего исполнителя.
- Независимая проверка назначается задачам с `B=2` или `V=2` и сама является задачей графа: у неё
  бриф, тир и место в `max_spawn`. Независимая - значит другим путём к свидетельству:
  перезапуск, повторная выборка, воспроизведение. Вторая модель, перечитывающая тот же артефакт,
  независимой не считается. Иного пути нет - проверяющий не назначается, исход `нечем проверить`
  идёт пользователю.
- Повторы идут по сигналу, а не по самооценке исполнителя. Лестница повторов живёт в
  исполнителе; в плане записываются только исключения из неё.

## Пакет

Каталог пакета - по просьбе пользователя, иначе `.orchestration/<slug>/` рядом с рабочей
директорией задачи. Оркестратору план рекомендует модель и effort: он платит за каждое чтение
пакета и отчётов, поэтому на длинном пакете это отдельное решение, а не `opus` по умолчанию.
Файлы: `PLAN.md` (схема исполнения, лимиты, таблицы, инструкции оркестратору), `briefs/*.md`
(включая `_template.md` и, если нужен триаж, `_triage.md`), `ledger.json` (начальное состояние),
`checks/`. Формат - [pack-format.md](references/pack-format.md). Пакет самодостаточен
относительно планировщика: оркестратор исполняет его по скиллу-исполнителю и не открывает ни этот
скилл, ни его `references/`.

## Самопроверка перед сдачей

Исход по каждому пункту - строкой в разделе «Допущения и риски» `PLAN.md`; не прошёл пункт -
правка пакета до сдачи.

- Граф зависимостей без циклов; у каждой задачи есть бриф, `check`, а у задач `agent` - модель и
  effort явно.
- Ни одной задачи `B=2` на `haiku`; проверяющий не ниже автора; параллельные записи не пересекаются.
- Число одновременных исполнителей не выше `max_parallel`; `max_spawn` покрывает задачи, проверки,
  триаж и запас на повторы; потолок попыток задан.
- Ни одной модели вне 5.5; ни одного датированного id.
- В брифах нет просьбы «думай меньше» и нет просьбы выписать цепочку рассуждений: второе может
  быть отклонено классификатором, нужны краткое объяснение и свидетельства.
- Расчёт расхода со сравнением с `solo` есть, метод назван.

Неясная задача, лимиты, которые друг другу противоречат, схема, расходящаяся с явной просьбой
пользователя, - вопрос пользователю до записи пакета, а не допущение.

Основания правил и их оговорки - [evidence.md](references/evidence.md); при планировании файл не
читается, он нужен ревью.
