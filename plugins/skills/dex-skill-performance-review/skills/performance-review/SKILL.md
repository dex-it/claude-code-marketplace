# Производительность - ловушки ревью diff'а

Момент - ревью изменения, поиск перф-грабки до прода (не рантайм-профилирование). Оси - где искать; 4 принципа - что не так. Паттерн вне списка граблей судится по принципу.

1. Не делай в цикле то, что делается разом: round-trip, запрос, вызов границы, аллокация, компиляция regex, захват лока. Инвариант цикла выносится наружу.
2. Не тащи в память больше/раньше, чем нужно: overfetch, весь файл/payload, жадная материализация ветки, которая может не понадобиться, unbounded cache.
3. Работай со ссылкой/потоком, не с копией: стрим vs буфер, срез vs копия, пул vs new.
4. Переноси работу туда, где дешевле: фильтр/агрегация в источник, независимое - в параллель, дорогое - за проверку (уровень лога, ленивое вычисление).

## Доступ к данным

### N+1: запрос/навигация в цикле по коллекции
Плохо: цикл по родителям, внутри - обращение к ленивой навигации или отдельный запрос на дочерние (1 запрос + N)
Правильно: eager-загрузка/join одним запросом (EF `Include`, Django `select_related`, Prisma `include`) или батч по всем ключам разом
Почему: N round-trip'ов вместо одного - латентность растёт линейно от размера коллекции, в diff видно как запрос под циклом

### Unbounded result set - нет пагинации
Плохо: выборка «все строки» без `Take`/`LIMIT`/курсора - таблица растёт, ответ и память вместе с ней
Правильно: страница/курсор с явным пределом; для внутренних обходов - потоковая выборка порциями
Почему: работает на тестовых данных, деградирует в проде по мере роста таблицы - severity зависит от роста, подтверди контекстом

### Overfetch колонок - нет проекции
Плохо: тянется вся сущность (`SELECT *`), потребитель читает 2-3 поля
Правильно: проекция в источнике на нужные поля (`Select` в DTO, `.only()`, `select`)
Почему: лишние колонки - трафик, память, ломается покрывающий индекс; проекция сдвигает отбор в БД

### exists вместо count/материализации
Плохо: `Count() > 0` или загрузка коллекции ради проверки «есть ли хоть один»
Правильно: `AnyAsync`/`.exists()`/`findFirst` - БД останавливается на первом совпадении
Почему: count сканирует все строки, материализация тащит их в память; для «есть ли» нужен только факт наличия

## I/O: как ходим к ресурсу

Не «сколько данных» (overfetch выше), а физика доступа.

### Запись/запрос в цикле вместо батча
Плохо: `SaveChanges`/`INSERT`/сетевой вызов на каждой итерации
Правильно: накопить и отправить пакетом (`AddRange`+один `SaveChanges`, `bulk_create`, `createMany`)
Почему: round-trip на элемент. Python-оговорка: DBAPI `executemany` драйвер-зависим и не гарантирует один INSERT - истинный батч в Postgres через `execute_values`/`execute_batch`

### Клиент/соединение/хендл на итерацию
Плохо: `new HttpClient()`/новая сессия/пул соединений создаётся на каждый запрос
Правильно: переиспользуемый долгоживущий клиент (инъекция/фабрика), пул на процесс
Почему: короткоживущий HTTP-хендлер оставляет сокеты в TIME_WAIT - под нагрузкой исчерпание портов, а не «нельзя dispose»

### Весь payload/файл в память вместо стрима
Плохо: `ReadAllText`/`response.content`/`readFileSync` на крупном источнике - весь объём в память разом
Правильно: потоковое чтение (`ReadLines`/`iter_content`/`createReadStream`), обработка по мере поступления
Почему: пик памяти = размер файла; на большом входе OOM. Стрим держит константное окно

## Асинхронность и конкурентность

Оговорка JS: часть ловушек этой оси - специфика потоковой модели рантайма. Однопоточный event loop -> нет гонок за разделяемую память и ручных потоков/локов, но блокировка единственного потока синхронной работой - аналогичная, часто более острая проблема (весь процесс встаёт, не один поток пула).

### await-in-loop независимых операций
Плохо: `await` по одному в цикле, где операции не зависят друг от друга - сумма латентностей
Правильно: запуск всех и ожидание разом (`Task.WhenAll`, `asyncio.gather`, `Promise.all(map)`)
Почему: независимые I/O ждут последовательно вместо параллельно; общее время падает с суммы до максимума

### sync-over-async
Плохо: `.Result`/`.Wait()`, синхронный `requests` в `async`-функции, `time.sleep` в корутине
Правильно: `await` до конца цепочки; в async-контексте - async-клиент и `asyncio.sleep`
Почему: блокирует поток пула на ожидании - под нагрузкой thread-pool starvation и деградация throughput

### Лок вокруг тяжёлой/IO-операции
Плохо: критическая секция охватывает IO или долгий счёт - потоки стоят в очереди на лок
Правильно: сузить секцию до общей структуры; .NET - под `Monitor`/`lock` только синхронная работа (`await` в теле `lock` не компилируется, CS1996)
Почему: лок вокруг IO сериализует то, что могло идти параллельно - пропускная способность падает до одного потока

### Тяжёлая операция на потоке запроса - развилка I/O vs CPU
Плохо: наивное «оберни в async» без различения природы; `Task.Run` вокруг CPU-работы в хендлере
Правильно: I/O-bound -> async-API (поток свободен на ожидании); CPU-bound (хеш/парсинг/сжатие) -> в фон/очередь/worker, вне горячего пути
Почему: `Task.Run` вокруг CPU не улучшает масштабируемость - переносит занятость на другой поток пула, счёт держит поток; `async` лечит только ожидание, не счёт

## Материализация и коллекции

### Needless materialization ради len/any
Плохо: `list(gen)`/`ToList` только чтобы взять длину или проверить наличие
Правильно: работать с ленивым источником; для наличия - `Any`/`any`, для счёта - агрегат в источнике
Почему: материализация тащит всю последовательность в память, хотя нужен один факт

### Поиск в списке O(n) в цикле
Плохо: `list.Contains`/`in list`/`.find` внутри цикла по другой коллекции - структурный O(n^2)
Правильно: построить `HashSet`/`Set`/`dict` один раз, искать за O(1)
Почему: вложенный линейный поиск квадратичен по размеру; на больших коллекциях время растёт как n^2

### Повторный обход lazy/исчерпанного источника
Плохо: одна ленивая последовательность обходится дважды (или итерируется уже исчерпанный поток)
Правильно: материализовать один раз, если нужны оба прохода; иначе один проход
Почему: повторный обход генератора/`IEnumerable` перезапускает вычисление (или отдаёт пусто на исчерпанном) - лишняя работа либо тихий баг

### (Де)сериализация/маппинг в цикле
Плохо: создание сериализатора/options или рефлексия-маппера на каждой итерации; маппинг в память вместо проекции
Правильно: переиспользовать настроенный `JsonSerializer`/options; отбор полей проекцией в источнике
Почему: пересборка сериализатора и рефлексия per-item - инвариант цикла, выносится наружу (принцип 1)

## Память, строки, массивы

### Аллокация инвариантного в горячем цикле
Плохо: объект/буфер/делегат, не зависящий от итерации, создаётся внутри цикла
Правильно: вынести создание наружу; для частых буферов - пул (`ArrayPool`) вместо `new`
Почему: аллокация на итерацию давит GC на горячем пути; инвариант цикла считается один раз

### Конкатенация строк в цикле
Плохо: `s += ...` в цикле - хрупкий паттерн, легко даёт O(n^2)
Правильно: билдер/аккумулятор (`StringBuilder`, `''.join`, `arr.join`)
Почему: движки имеют оптимизации (V8 rope, CPython in-place), но квадратичность не гарантирована - на промахе оптимизации копируется вся строка на шаг

### Regex создаётся/компилируется в цикле
Плохо: паттерн строится/компилируется на каждой итерации
Правильно: скомпилировать один раз вне цикла (`Regex` в поле/статик, `re.compile`); Python - компилировать явно, не полагаться на внутренний кэш `re`
Почему: компиляция паттерна - инвариант цикла (принцип 1); кэш `re` спасает не всегда и его размер не контракт

### Catastrophic backtracking / ReDoS
Плохо: вложенные квантификаторы (`(a+)+`, `(.*)*`) на неограниченном входе
Правильно: переписать без перекрывающихся квантификаторов; ограничить длину входа; атомарные группы/possessive где есть
Почему: экспоненциальное время матчинга от длины входа - здесь только перф-грань (время), вектор атаки - у security

### Удержание крупного объекта / срез vs копия / unbounded cache
Плохо: живая ссылка/подписка держит крупный граф после надобности; копия большой структуры вместо среза; кэш без границы
Правильно: обрезать время жизни (отписка, слабая ссылка); срез/`Span`/view вместо копии; кэш с пределом (`lru_cache(maxsize)`, `SizeLimit`, LRU+TTL)
Почему: удержание и лишние копии раздувают память; unbounded cache растёт без потолка до OOM

## Граница натив<->управляемый код

### Минимизируй пересечения границы
Плохо: вызов в натив/из натива per-item в цикле - маршалинг и копия на каждый переход
Правильно: батчировать данные, один вызов на пакет; передавать ссылку/буфер, не копию per-call
Почему: пересечение границы (P/Invoke, N-API, WASM, векторизация) дорого фиксированной ценой - число переходов важнее объёма в одном

## Чек-лист ревью

- N+1: запрос/навигация под циклом по коллекции -> eager/join/батч
- Выборка без предела (`Take`/`LIMIT`/курсор) - пагинация или потоковая порция
- Проекция на нужные поля, не вся сущность (overfetch)
- `Any`/exists вместо `Count>0`/материализации для проверки наличия
- Запись/запрос пакетом, не в цикле (батч; Postgres - `execute_values`, не голый `executemany`)
- Долгоживущий HTTP-клиент/соединение, не создание per-request (socket exhaustion)
- Стрим на крупном файле/payload, не чтение целиком
- Независимые await - разом (`WhenAll`/`gather`/`Promise.all`), не в цикле
- Нет sync-over-async (`.Result`/`.Wait`/sync-IO в async)
- Критическая секция без IO/долгого счёта; CPU-работа - в фон, не `Task.Run` в хендлере
- Поиск в цикле через хеш-структуру, не линейный `Contains`/`in`
- Сериализатор/regex/инвариант создаётся вне цикла, не на итерации
- Строки - билдер/join в цикле, не `+=`
- Кэш с границей (maxsize/LRU+TTL), не unbounded
- Граница натив: батч, не per-item маршалинг
- Условно (подтверди контекстом, severity от горячести): дорогой аргумент лога вычисляется до проверки уровня (`LogDebug($"{expensive()}")` считает всегда) - вынести за уровень; SELECT без индекса - только если в PR есть и миграция колонки, и горячий фильтр по ней
