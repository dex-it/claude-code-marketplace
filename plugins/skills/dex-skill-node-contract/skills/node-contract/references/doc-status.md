# Готовность артефакта: цикл статуса, порог допуска, апрув

Материал `node-contract` по требованию; условие чтения - таблица «Материалы по требованию» в
`SKILL.md`.

## Готовность артефакта: `status` документа и порог допуска

Отдельного поля состояния в handoff нет. Готовность читается из двух источников:
**проверенность** - запись `quality-checks` по этому типу; **принятость** -
поле `status` в шапке самого документа, публикационный цикл `draft` -> `review` -> `approved` ->
`archived` (`doc-standards`).

| Переход | Условие |
|---|---|
| `draft -> review` | состав по нормативу этапа заполнен целиком; пустой раздел - только с явной пометкой «нет», не молчанием |
| `review -> approved` | `quality-checks` несёт запись **судьи** по этому типу с `verdict: passed` (`self-check` автора порога не даёт), апрув уполномоченной стороны зафиксирован И открытых вопросов по артефакту не осталось (закрыты ответом либо решением в самом артефакте); дальнейшие изменения идут через процедуру. Судья не вызван либо вопрос открыт -> потолок `review`, незакрытое называется в выходе |
| `approved -> archived` | документ выведен из обращения; заменён другим - ссылка на заменяющий обязательна |

**Порог допуска к следующему этапу:** запись `quality-checks` с `verdict: passed` по типу - для всех
входных артефактов; `status: approved` дополнительно для BRS и ADR, где решение дорого откатить.
Оракула для типа не существует -> запись `unverifiable` с этой причиной, порог **допуска** сводится
к заполненному составу, а порог `approved` не берётся до появления оракула (реестр в `references/quality-mark.md`): допуск дальше по
конвейеру не равен принятости. **Производная форма выведена из этого правила** (там же): своего статуса она
не несёт вовсе. Готовность у неё читается иначе: ревизия источника в шапке совпадает с текущей
версией источника -> актуальна, разошлась -> устарела и пересобирается. Приёмник, получивший её без
ревизии, возвращает нехватку именно ревизии, не `status`.

Шапки нет либо `status` в ней не проставлен -> исход по
происхождению входа, тем же различением, что в п.9 SKILL.md: документ приехал **по стыку** -> это
нехватка обязательного поля, а не `draft`, и возврат автору; документ подан **вне стыка** (путь от
оператора, файл из репозитория, писал человек) -> цикл публикации по нему просто не ведётся:
`draft` тоже не домысливается, а называется в выходе как «вне цикла». Порог допуска берётся
проверенностью, и для типов, которым сверх неё нужен `approved` (BRS, ADR), отсутствие цикла -
блокер: `status: blocked` с этой причиной, а не тихий пропуск оси принятости.

**Документ, не порождённый конвейером - отдельный случай, а не тот же возврат:** автора в маршруте
у него нет, и возврат уходит в никуда.

Случай опознаётся по совокупности признаков, не по одному: нет шапки **и** нет файла-метки рядом
**и** в истории документа нет узла-автора. Один признак сам по себе ничего не значит - забытая
шапка при живом авторе это обычная нехватка обязательного поля, и исход у неё прежний.

| Что сделал приёмник | Когда | Что записывает |
|---|---|---|
| принял как **источник**, не как проверенный вход | документ нужен для контекста, решения на нём не строятся | `{artifact, path, check: <тип>, verdict: unverifiable}` с причиной «документ вне конвейера: шапки и метки нет, автор в маршруте отсутствует» |
| провёл **через приёмку**: проставил шапку со `status: draft` и прогнал оракул типа | документ становится входом этапа, и на нём строится решение | вердикт оракула плюс отдельным пунктом выхода: какая шапка проставлена и на каком основании |

Оба пути законны. Чего не бывает: **шапка не проставляется молча**, и проставленная задним числом
не даёт `approved`. Приведение унаследованного корпуса к норме - отдельная работа, а не побочный
эффект прохода одного узла: узел называет расхождение и идёт дальше, чужой корпус по пути не
переписывая.

**Значение `status` шапки сверяется с закрытым перечнем цикла до разбора содержания.** Годных
значений четыре (`draft`/`review`/`approved`/`archived`; у ADR - перечень MADR, исключение ниже);
значение вне перечня - нехватка обязательного поля, и здесь происхождение входа ничего не меняет:
возврат автору, вне стыка - вызвавшему, с указанием файла и негодного значения; содержание не
разбирается. Испорченное поле - не то же, что не ведущийся цикл: первое домысливать нечем. Типичная
подмена - значение из словаря **исхода узла** (`complete`, `partial`).

**Исключение - ADR.** Ось статуса задана внешним каноном MADR (`Proposed` / `Accepted` /
`Deprecated` / `Superseded`), порогу `approved` отвечает `Accepted`: перечень у ADR свой,
соответствие порогу - по этой строке.

`status` документа - не `status` узла: первый стоит в шапке файла и говорит о документе, второй едет
первым полем выхода и говорит о работе узла. Носители разные, читается по носителю.

## Апрув и его граница

**Апрув меняет форму по ярусу, а не по режиму, и ни на одном не исчезает.** При канале (тело
исполняет главный цикл, `interactive`) - ответ оператора на гейте; спавненному узлу санкция приходит
полем входа `approve: true` от вызывающей стороны при любом `mode` (та же ось, что
`publish`/`apply`/`deploy`). Поля нет либо `false` -> потолок `review` (`Proposed` у ADR) плюс пункт
выхода «до порога не поднято: санкции на приёмку нет». Себе апрув узел не выдаёт ни в одном режиме;
недостижимость порога права обойти его молча не даёт - артефакт под потолком штатен, тихий
`approved` нет.

**`approve` санкционирует приёмку артефакта, а не бизнес-решения внутри него.** Открытый вопрос
полномочной оси (определение - `SKILL.md`, «Outward-facing действие») поле `approve` не закрывает: вопрос
остаётся открытым, порог не берётся по правилу выше, при спавне узлом (любой `mode`) вопрос едет
наверх - адресата меняет ярус, не режим, и права решить за оператора не даёт ни один из них.
`approve: true` при таком открытом вопросе читается как санкция принять **остальное**, не как ответ
на него.
