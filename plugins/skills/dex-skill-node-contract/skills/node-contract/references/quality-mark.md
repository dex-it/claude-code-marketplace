# Метка качества: запись, носитель, вердикт, входная приёмка

Материал `node-contract` по требованию; условие чтения - таблица «Материалы по требованию» в
`SKILL.md`.

Содержание:
1. Реестр «тип артефакта -> оракул»
2. Ключ записи и значения `artifact`
3. Носитель метки = файл рядом с артефактом
4. Значения `verdict`: границы случаев
5. Входная приёмка артефакта по метке `quality-checks`

## Реестр «тип артефакта -> оракул»

Метка `quality-checks` и входная приёмка опираются на соответствие типа артефакта его оракулу:

| Тип артефакта | Оракул | Кто судит (автор - никогда) |
|---|---|---|
| требование, единица - на любом уровне (`BR` из BRD, сценарий `UC`, `FR`/`NFR` системного уровня, story) | `requirement-quality` | судья на гейте требований, ревьюер требований ИЛИ потребитель-единица |
| набор требований | `requirement-set-quality` | вызывающая сторона (видит весь набор) |
| набор требований, проверка допуска к разработке (`check: implementer-readiness`) | проба готовности - чтение корпуса в чистом контексте, оракула-skill у неё нет | только читатель-реализатор (`implementer-reader`); вызывающая сторона - адресат вердикта, не его автор |
| ADR | `adr-quality` | ревьюер дизайна ИЛИ потребитель |
| use case | `use-case-quality` | судья на гейте требований, ревьюер требований (предмет - сценарии) ИЛИ потребитель сценария |
| API-спека | `api-spec-quality` | ревьюер дизайна ИЛИ потребитель контракта |
| дизайн-документ (решение фичи целиком: драйверы, альтернативы, deep dive) | `design-quality` | ревьюер дизайна |
| план реализации (инкременты дизайна, edit-план разработки) | `plan-quality` | ревьюер дизайна ИЛИ потребитель плана; автор плана - никогда |
| доменная модель уровня 0 (словарь: термин - значение - дом - «не путать с») | `domain-model-quality`: оракула-skill под этим именем нет -> `unverifiable` + причина «оракул для типа не существует»; проверяемое без оракула (у термина есть дом либо строка «Термины без дома» с местом употребления) судит вызывающая сторона и называет результат | судья корпуса уровня 0 |
| единица конституции уровня 0 (`INV`, `NFR-P`) | `requirement-quality` - строка «требование, единица на любом уровне» покрывает их; набор судится `requirement-set-quality` против `BR` продукта | судья корпуса уровня 0 ИЛИ ревьюер требований |
| набор артефактов дизайна, тип `design-set` (дизайн + ADR + спеки одной работы как целое) | `design-set-quality`: оракула-skill под этим именем нет, оси набора несёт фаза ревьюера дизайна - комплектность, непротиворечивость между документами, согласованность статусов | ревьюер дизайна (вход - перечень путей всего набора) |
| свод правил проекта, тип `rulebook` (что принято в репозитории: единицы `RUL` с якорем, индекс, реестр источников, наблюдения) | `dex-rulebook-miner:rulebook-quality` `[справочно]` - судит свод как документ; «верное правило или нет» решает владелец корпуса и оракулу не подлежит | ведущая сбор свода сторона (сама содержания свода не пишет) ИЛИ потребитель свода |

Реестр держится явной таблицей (точное имя, не вероятностный матч по `description`). По конвенции
имя оракула = `{тип}-quality`, а плагин выводится из имени - `dex-skill-{тип}-quality`. Оракул,
едущий внутри плагина-владельца, из имени не выводится и стоит в таблице полной формой.

**Реестр индексируется парой «тип + проверка», не одним типом.** У типа бывает несколько проверок с
разными судьями (набор требований: оракул набора у судьи, проба готовности у читателя-реализатора).
Право на одну проверку второй не даёт: запись с чужим `check` при сверке читается как отсутствующая -
порог по ней не взят, движение по конвейеру ею не открывается.

**Правило «автор - никогда» разводит роли, но не модели:** вызывающая сторона и узел - одна модель
сессии. Где цена ошибки высока, вердикт подпирается внешним фактом (прогон, тест, первоисточник), не
вторым мнением той же модели.

**Тип без оракула: запись ставит судья, ожидание объявляет автор.** `unverifiable` - вердикт, и
своему артефакту автор его не пишет (п.7 `SKILL.md`). До суда автор объявляет ожидаемую проверку полем,
синтаксически отличным от вердикта:

```
pending-judgement:
  - {check: use-case-quality, reason: "судья в маршруте не назначен", by: author}
```

Поле вердиктом не является и порога не даёт - приёмник читает его как названное ожидание, не как
прогон. Значение `pending` в `verdict` не заводится - перечень закрыт.

**Производная форма собственного типа не получает.** Артефакт, собираемый по команде из принятого
источника без содержания сверх него (`.feature` из AC истории, выгрузка, сводка), в реестр не
заводится, метку `quality-checks` не носит и по циклу статуса не идёт: порог берёт источник, а
производное держится **ссылкой на его версию** - совпадает с текущей версией источника -> актуально,
разошлась -> устарело; пришло без ссылки - возвращается нехватка ссылки, не `status`. Расхождение - дефект производного: оно
пересобирается, источник не правится. Сборка вскрыла нехватку в источнике -> находка наверх по форме `references/finding-return.md`, в
производном молча не дописывается. Признак подмены - производное, которое начали править напрямую: с
этого момента оно не источник, и расхождение пересборкой не разрешается.

## Ключ записи и значения `artifact`

**Ключ - тип плюс путь артефакта, не один тип.** Запись покрывает названный экземпляр. Несколько
артефактов одного типа в одной работе (шесть ADR по фиче) дают либо запись на каждый, либо одну
агрегированную - и тогда она обязана перечислить единицы, по которым вердикт расходится с общим.
Молчаливая агрегация запрещена в обе стороны: `failed` без перечня читается как «плохи все», и
годные единицы возвращаются в работу; `passed` без перечня закрывает от перепроверки те, которых
судья не смотрел.

**Значения ключа `artifact`.** Тип единицы требования источники называют по-разному - `BRD`,
`stories`, `requirements`: один тип и один оракул, потребитель обязан матчить любую из трёх форм.
Отдельные типы: `requirement-set` (набор требований любого уровня - `BR`, `FR`/`NFR`, stories;
уровень различает путь, не тип), `design-set` (набор артефактов дизайна), `ADR`, `api-spec`,
`design`, `use-case` (сценарий использования), `rulebook` (свод правил проекта). Форма записи
свободна, тип - нет: значения вне этого перечня в метку не пишутся. Тип породённого артефакта в реестре отсутствует -> запись
`unverifiable` под ближайшим подходящим типом не делается: тип не подменяется, нехватка называется
отдельным полем выхода как дефект каталога.

## Носитель метки = файл рядом с артефактом, поле handoff - индекс

Носитель метки - файл `<имя-артефакта>.checks.md` рядом с судимым артефактом; судья чужой артефакт
не мутирует, а вердикт, оставленный только в тексте ответа, метки не даёт. Набор судится
по документу, который его несёт; набор из нескольких файлов - метка рядом с корнем набора, корень
назван в записи.

**Блок в файле заводит автор при первом выпуске, дописывает судья.** Артефакт, созданный с нуля,
несёт блок `quality-checks` в шапке (форматы без шапки - расширение, `x-quality-checks`) с
унаследованными со входа записями; входных записей не было -> блок с явной пометкой «входных записей
нет», не отсутствие блока. Свои записи по чужому артефакту судья кладёт в `<имя-артефакта>.checks.md`
рядом; оба носителя приёмник берёт тем же чтением с диска. Провал класса - первая посадка: узел
создаёт файл с нуля и возвращает поле в handoff, блока в файле не заводя.

Поле `quality-checks` в handoff остаётся индексом для вызывающей стороны - маршрутизировать без
обхода диска. **Старшинство при расхождении: `.checks.md` > блок в шапке > поле handoff** - по тому,
кто пишет: вердикт судьи, ведение автора, ручной перенос промежуточными узлами. Судья без
инструмента записи этот пункт контракта исполнить не может -> `status: blocked` с названным
недостающим инструментом; оставить вердикт в ответе - не выход.

## Значения `verdict`: границы случаев

Перечень закрыт: `passed` (оракул прогнан, дефектов не осталось), `failed` (прогнан, дефект остался
неустранённым здесь - перечень дефектов в поле), `unverifiable` (прогон не состоялся).

**Исход узла, `verdict` и потолок статуса артефакта - три разные оси;** исход автора и судьи при
`failed` - п.7 `SKILL.md`. `partial` у судьи - только по непройденному пункту **своего** контракта:
канал доставки не выбран, метка не записана, ревизия требует решения вызывающей стороны.

**У `unverifiable` причина обязательна и называет, чего именно не было:** судья не вызван в
маршруте / оракула либо норматива для этой оси не существует (задел каталога) / типа нет в реестре
вовсе / оракул недоступен в среде И ось по знанию не применена. Причина эти случаи и различает:
«типа нет в реестре» - дефект нормы каталога, он дополнительно называется в выходе узла, а не
растворяется в метке.

**Оракул в реестре есть, текст недоступен (не установлен, не загрузился), а судья ось применил по
знанию** -> вердикт с признаком `degraded: <чего не было>`, не `unverifiable`: прогон состоялся, и
`passed`/`failed` без пометки скрывают, что критерий взят из памяти. Граница по факту прогона, не по
доступности: ось не применена вовсе -> `unverifiable`; применена без норматива -> вердикт +
`degraded`.

**Ось, заведённая судьёй за отсутствием оракула, вердиктом по типу не становится:** метка остаётся
`unverifiable` («оракула для типа не существует»), находки едут в поле находок, ось названа
авторской.

**`contradicted` - не из этого перечня.** Три значения выше - про **свой** прогон; `contradicted`
ставится только поверх **чужой** записи опровергающим узлом: `verdict` пришедшей записи
переписывается на `contradicted`, исходное значение и опровергающая находка называются рядом. Свою
запись `contradicted` не получает никогда.

**`verdict` несёт финальное состояние артефакта на выходе узла, не историю прогонов:** дефект,
найденный и устранённый здесь же, даёт `passed`. История находок и их закрытия живёт в журнале
гейтов прозой: форму `{artifact, check, verdict}` журнал не воспроизводит - вторая запись по той же
паре даёт приёмнику два значения одного факта, и он берёт встреченное первым. `failed` рядом с
закрытыми находками и `status: complete` - противоречие: одно из двух записано неверно.

**Вердикт судит свой артефакт; дефект источника - находка вверх, не `failed` своему.** Дефект,
неустранимый никакой правкой своего артефакта, потому что дыра лежит во входном (требование не
покрывает путь, которого нет в его источнике), в свой `verdict` не входит: он едет отдельным полем
находок с названным артефактом-адресатом, а свой вердикт выносится по тому, что автор мог закрыть.
Сомнение «мой дефект или источника» -> считать своим.

## Входная приёмка артефакта по метке `quality-checks`

Запись ищется по **этому экземпляру** во всех трёх носителях, старшинство - «Носитель метки» выше.
Запись в handoff при пустом файле приёмку не закрывает.

**Блока в файле нет - ветка по происхождению входа** (признак - п.9 `SKILL.md`):

- **по стыку** -> блок обязан быть, его отсутствие - дефект производителя: нехватка обязательного
  поля, возврат автору по форме `references/finding-return.md` до разбора содержания, ревизия на это
  не тратится;
- **вне стыка** -> «не судился»: прогони оракул типа сам и поставь свою запись (ты не автор, запрет
  п.7 `SKILL.md` на тебя не распространяется), дальше - по веткам ниже.

Запись по типу без пути экземпляр не покрывает, кроме агрегированной с перечнем единиц («Ключ записи и значения `artifact`»):

- запись `{тип, путь, check, verdict: passed}` есть -> проверку не дублировать (п.7 `SKILL.md`):
  `passed` судьи принимается без перепроверки, а ложная метка вскрывается **употреблением** -
  наткнувшийся на расхождение переписывает запись на `contradicted` с указанием находки, и терминал
  у него тот же, что у дефекта, найденного оракулом: `status: blocked` + перечень, возврат
  вызывающему. `self-check` автора такой записью не является - оракул прогоняется, как если бы поля не было;
  запись с `degraded` доверие сохраняет, пометка переносится дальше как есть;
- записи нет ИЛИ `verdict != passed` -> прогнать оракул типа по реестру («Реестр «тип артефакта -> оракул»»); оракула для типа нет
  либо типа нет в реестре -> своя запись `unverifiable` с этой причиной;
- оракул нашёл дефект -> `status: blocked` + перечень, возврат вызывающему. Чужой артефакт
  потребитель НЕ дочиняет - чинит автор.
