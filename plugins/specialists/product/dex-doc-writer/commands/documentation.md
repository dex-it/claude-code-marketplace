# /documentation

Написать техническую документацию: нормативный текст, факты только из кода и конфигов, синхрон со
стандартом жанра.

## Input

Тип документа (tech spec / README / release notes / API doc / architecture doc / runbook /
migration guide / onboarding guide / ADR) и источник содержания - код, ТЗ, обсуждение. Опционально
путь записи, целевая аудитория, шаблон. Тип не указан -> запроси, не угадывай; источника содержания
нет -> работа не начинается, скажи чего не хватает.

## Порядок делегирования

1. **Документ** - `dex-doc-writer:doc-writer`. Вход: тип, источник содержания, аудитория, путь записи.
2. **По жанру** - `dex-adr-writer:adr-writer`, когда предмет является решением с ценой отмены; `dex-diagram-creator:diagram-creator`,
   когда жанр требует C4, sequence, ER или state. Вход каждому: тот же источник плюс готовый текст.

## Output

- Готовый документ по чеклисту жанра из `dex-skill-doc-standards:doc-standards`
- По каждому техническому факту (версия, конфиг, имя API, поведение) - сверка с `file:line` либо
  статус «не подтверждён»; ни одного `[TODO]`/`[TBD]` в финале
- Незакрытые места - с причиной по каждому, не тихим пропуском
- ADR и диаграммы - отдельными файлами там, где жанр их требует

## Constraints

- Факты - из кода и конфигов, не из памяти и не из соседних доков (протухают)
- Аудитория и стандарт проекта - технический выбор исполнителя, не вопрос оператору
- Существующий документ на ту же тему - предложи обновление, не плоди дубль
- Тривиальный предмет без бизнес-логики - предупреди о низкой ценности документа, не пиши молча
