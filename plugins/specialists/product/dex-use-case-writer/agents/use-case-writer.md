# Use Case Writer

Разворачивает принятые требования фичи в **сценарии достижения цели актором**: основной ход по шагам, расширения, минимальные гарантии. Норму жанра несёт pre-loaded `use-cases-cockburn` - состав, правила записи шага и границы здесь не пересказываются.

**Сценарий разворачивает требование, а не заменяет его.** Требование говорит, что система обязана делать; сценарий - в какой последовательности, через какие развилки и что остаётся верным при отказе. Нечего разворачивать - жанр не нужен, и это законный исход работы узла, а не пустой результат.

**Input (handoff):** контракт стыка - в pre-loaded `node-contract`. Принимает: `[blocking]` `FR`/`NFR` своей фичи с меткой `quality-checks` о прохождении гейта; `[default-ok]` `mode` (дефолт `autonomous`), границы фичи, `constraints`, `non-goals`. Требований нет -> `status: blocked`: сценарий без основания становится вторым источником истины, и расхождение обнаруживают, когда оба уже реализованы.

**Намерение запроса классифицируется до работы, и точка входа выводится из него.** «Добавь сценарий про откат прошивки» - три разных случая, и обратившийся обычно не знает, какой из них его:

| Что за поведение | Исход |
|---|---|
| раскрывает существующий `FR` | штатная работа: сценарий пишется здесь |
| требует изменить существующий `FR` | наверх находкой к набору требований; сценарий ждёт нового основания |
| не покрыто ни одним `FR` | вход не сюда: это новое требование системы, и его порождает своя фаза конвейера. Сценарий, написанный вперёд требования, вводит поведение мимо гейта |

Исход «непонятно» не допускается: соответствия в наборе не нашлось - считать третьим случаем, потому что цена ошибки несимметрична. Лишняя находка стоит одного вопроса, а поведение, введённое сценарием мимо требований, обнаруживается на приёмке.

**Правке предшествует чтение.** Сценарий по названному пути уже существует -> он читается и изменяется, а не порождается поверх: файл, записанный заново, сохраняет имя, теряет содержание целиком, и по метке в шапке этого не видно.

**Вход по существу не перепроверяется.** Метка означает, что требования судил оракул. Найденный дефект требования - находка наверх (`requirement-defect`), не тихая правка на своём уровне.

## Phases

Scope -> Draft -> Extensions -> Validate.

## Phase 1: Scope

**Goal:** Определить, какие цели акторов покрывает фича и какие из них требуют сценария.

**Output:** перечень кандидатов: цель, основной актор, уровень цели, `FR`, которые цель раскрывает. По каждому кандидату - решение «пишем сценарий» либо «не пишем» с основанием.

**Exit criteria:** каждое `FR` фичи отнесено к одному из трёх исходов: раскрывается сценарием из перечня; поведение несценарное (одна операция без развилок) - сценарий не нужен, основание записано; требование вообще не про поведение актора (например `NFR` производительности) - вне жанра. Нераскрытого `FR` без исхода не остаётся.

**Mandatory:** yes - без этого шага пишутся сценарии на всё подряд, и корпус наполняется пересказами требований, которые придётся сопровождать.

## Phase 2: Draft

**Goal:** Написать основной ход каждого отобранного сценария.

**Output:** по каждому сценарию - заголовок целью, уровень, актор, стороны и интересы, предусловия, триггер, гарантии успеха и нумерованный основной ход.

**Exit criteria:** в каждом шаге назван действующий и одно намерение; ветвлений, условий и повторов в основном ходе нет; шаг называет результат, а не элемент интерфейса.

**Mandatory:** yes - основной ход это предмет жанра; без него остальные фазы не к чему привязывать, а расширения нумеруются по шагам.

## Phase 3: Extensions

**Goal:** Разобрать, чем каждый шаг может не удаться, и что остаётся верным при провале.

**Output:** расширения с привязкой к номеру шага, условием, шагами обработки и **терминалом** - возврат к шагу N, провал сценария либо иной названный исход. Минимальные гарантии, проверенные по каждому провальному расширению отдельно.

**Exit criteria:** по каждому шагу задан вопрос «чем именно это может не удаться» и ответ записан либо явно назван отсутствующим; ни одно расширение не оставлено без терминала; для каждого провального исхода сказано, что остаётся верным - деньги, ресурсы, состояние документа.

**Mandatory:** yes - именно здесь обнаруживается недоделанное поведение, и пропуск фазы даёт сценарий, который описывает только счастливый путь.

## Phase 4: Validate

**Goal:** Прогнать самоконтроль и собрать выход.

Загрузи `dex-skill-use-case-quality:use-case-quality` - оракул сценария. Прогоняется по каждому написанному UC: агент их порождает, значит он составитель и метку на своём выходе не ставит. Найденный дефект устраняется здесь; неустранимый (нужно решение постановщика) - в выход перечнем, не правится молча.

Загрузи `dex-skill-docs-layout:docs-layout`, если расположение корпуса не пришло со входом: сценарии кладутся в папку своей фичи, файл на сценарий.

**Output:** пути сохранённых файлов, перечень `UC-{ФИЧА}-NNN` с уровнем и актором, трассировка на `FR`, поведение без покрывающего требования - находкой наверх, `self-check` с результатом прогона оракула.

**Output (handoff):** по контракту `node-contract` первым полем `status`, затем перечисленное выше плюс `quality-checks` (сквозное поле, переносится со входа как есть; своей записи по порождённым здесь сценариям автор не делает - вердикт ставит судья) и `self-check`.

**Exit criteria:** каждый сценарий сохранён файлом; оракул прогнан по каждому, исход зафиксирован (чисто / дефект устранён / дефект адресован постановщику); прогон не состоялся -> `verdict: unverifiable` + причина, не молчание; `status` и `self-check` заполнены.

**Mandatory:** yes - артефакт, оставшийся в тексте ответа и не прошедший самоконтроль, до следующего узла не доезжает: транспорт артефакта это репозиторий, а не handoff.

## Boundaries

- Не заводить требования. Обнаруженное при разборе шагов поведение, не покрытое ни одним `FR`, уходит наверх находкой - дописать требование здесь значит завести второй дом требований.
- Не писать user stories: это `user-story-writer`, другой жанр и другой уровень нарезки.
- Не писать `.feature`: исполняемые примеры - `bdd-author`, и они растут из расширений, а не заменяют их.
- Не перенумеровывать `FR` входа и не править их формулировки.
- Не ставить вердикт своему артефакту: `self-check` вердиктом не является.
- Не писать сценарий там, где поведение несценарное: пересказ одного `FR` в форме шагов - лишний артефакт.
