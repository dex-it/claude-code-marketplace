# /use-cases

Развернуть требования фичи в сценарии использования. Работу ведёт `dex-use-case-writer:use-case-writer`.

## Goal

Получить `docs/02-use-cases/{фича}/UC-{ФИЧА}-NNN-*.md` по требованиям этой фичи, с трассировкой на `FR` и прогнанным оракулом сценария.

## Input

Аргумент - фича. Не указана - спросить.

**Входной контракт несёт два указателя, а не один** - иначе узел вне `/feature` работает вслепую:

- **путь к SRS фичи** (`01-product/NN-{фича}/SRS-{фича}.md`) - источник `FR`, которые разворачиваются;
- **путь к журналу гейтов** этой фичи - перечень находок пройденных гейтов с их статусом.

Второй указатель обязателен по той же причине, по какой дирижёр передаёт находки вниз: метка `quality-checks` сообщает, что источник дефектен, и не сообщает чем. Без журнала составитель достраивает недостающее догадкой, и дефект уезжает в сценарии незаметно.

Журнал не найден - не выдумывать: сказать явным пунктом выхода «журнал гейтов не найден, находки верхних уровней неизвестны» и продолжить; путь к SRS отсутствует либо файл не читается -> остановка, сценарии писать не из чего.

**Исход «вход не сюда» - штатный.** Прежде чем писать, узел классифицирует намерение запроса: поведение раскрывает существующий `FR`, требует его изменить либо не покрыто ни одним требованием. В третьем случае сценарий не пишется - запрос уходит наверх новым требованием (таблица исходов - в теле `dex-use-case-writer:use-case-writer`). Формулировка «добавь сценарий про X» точкой входа не управляет: её выводит классификация, а не тот, кто просит.

## Output

- файлы сценариев в папке фичи;
- таблица покрытия: какое `FR` развёрнуто сценарием, какое признано несценарным с основанием;
- находки наверх: поведение, обнаруженное при разборе шагов и не покрытое ни одним требованием;
- `self-check` с результатом прогона `use-case-quality`.

Метку `quality-checks` по сценариям ставит судья, не эта команда.
