# /review-requirements

Провалидировать и согласовать чужой готовый набор требований как документ - не переписать его.

## Goal

Провести документ требований через фазы агента `requirements-reviewer`: входная приёмка по метке `quality-checks`, Domain Priming, дефекты единиц (`requirement-quality`), дефекты набора против источника (`requirement-set-quality`), Fact Verification, Cross-Linking, Severity Calibration, Output Labeling, Report.

## Input

Первый аргумент - путь к документу требований (BRD, эпик, набор stories). Второй, опциональный - путь к источнику (исходный BRD, цели, запрос заказчика): без него оси полноты и трассировки набора закрываются статусом `n/a (источник не предоставлен)`, остальные оси прогоняются полностью.

## Output

- Verdict (APPROVE / REQUEST_CHANGES / NEEDS_DISCUSSION) со счётчиком меток
- Находки, сгруппированные по корневой причине: якорь (идентификатор требования + `file:line`), severity, confidence, метка 🟢🟡🟠🔴🟣, `closure`, сформулированная для автора правка
- Метки `quality-checks` по прогнанным оракулам + блок пропущенных проверок со статусами
- Выбранный оператором канал доставки правок автору

## Constraints

- Документ автора не редактируется: агент без `Write`/`Edit`, правку вносит автор или оператор
- Требования не дописываются за автора - дыра предъявляется находкой
- Находки предъявляются оператору, не отправляются автору напрямую; канал доставки (задача в трекер ИЛИ правка в документ) выбирает оператор, агент его молча не выбирает
- Возражение автора - claim: снимается только подтверждением цитатой из документа или источника
- Дизайн-документ (спека, ADR, диаграммы) - предмет `/review-design`, не этой команды

Делегировать агенту `requirements-reviewer` с **`mode: interactive`** во входе: команда исполняется главным циклом, канал к оператору есть. Без явного `interactive` агент уйдёт в `autonomous` - вернёт находки в Output, не проведя по ним оператора и не зафиксировав канал доставки.
