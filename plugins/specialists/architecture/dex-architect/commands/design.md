# /design

Провести бизнес-задачу от требований до одобренного design-документа и плана реализации.

## Goal

Получить дизайн-решение с названными альтернативами и trade-off'ами, план реализации файлом и
вердикты приёмки на обоих. Решение принимает узел, не эта команда.

## Input

Аргумент - постановка в одной из двух форм:

- **бизнес-задача в свободной форме** («нужен сервис уведомлений», «как переехать с монолита на
  сервисы») - требования уточняются на шаге 1;
- **путь к принятым требованиям** (`FR`/`NFR` системного уровня и user stories). Вход только с
  `BR-NNN`, без системного уровня, принимается как бизнес-задача: `FR`/`NFR` выводятся здесь же и
  помечаются допущениями - принятым набором они не считаются.

Аргумент не передан -> запроси постановку первым сообщением, работа не начинается.
Стек (.NET vs нейтральный) определи по манифесту затронутой папки; спрашивать не нужно.

## Порядок делегирования

1. **Требования и capacity** - собери сам: `FR`/`NFR`, security и чувствительность данных,
   ограничения среды, метрики успеха, оценка нагрузки таблицей. Требования пришли с меткой
   `quality-checks: passed` - повторный обход не дублируй.
2. **Дизайн-решение** - `dex-architect:architect`, при .NET-манифесте `dex-architect-dotnet:architect-dotnet` `[справочно]`. Вход: требования,
   capacity, ограничения. Выход: reference-match, минимум 2 жизнеспособные альтернативы с
   диаграммами, решение с CAP/PACELC, deep dive (storage, API, кэш, отказы, безопасность,
   наблюдаемость).
3. **Документы по надобности** - `dex-adr-writer:adr-writer` (порог: цена отмены решения - миграция данных,
   контракт с внешним потребителем, чужой код по решению), `dex-api-designer:api-designer` (пересекается граница
   контракта), `dex-diagram-creator:diagram-creator`.
4. **Приёмка** - `dex-design-reviewer:design-reviewer`. Вход: design-документ и план. Судит оба.

## Output

- Требования (FR/NFR + security + ограничения + метрики успеха) и capacity-таблица
- Design-документ: reference-match, альтернативы, решение с trade-off'ами, deep dive
- Implementation plan **файлом**: walking skeleton -> vertical slices -> scale-out; критерии приёмки
  с метками `[FR-NNN]`/`[NFR-NNN]`, контракты пересекаемых границ, артефакты сверх кода
- Вердикты `dex-design-reviewer:design-reviewer`: `design-quality: passed` в шапке design-документа и `plan-quality:
  passed` в шапке плана. Любой не `passed` -> возврат на доработку, работа не сдана

## Constraints

- Дизайн-решение принимает узел, не эта команда: своего решения вместо ответа `dex-architect:architect` не пиши
- Минимум 2 жизнеспособные альтернативы; одна - результат не принят
- Бюджетная рамка и приоритет между конфликтующими NFR - блокирующий вопрос оператору, работа
  встаёт до ответа; выбор между технически равными альтернативами - неблокирующий: предъяви и иди
- Приёмка обязательна: без обоих вердиктов `passed` результат дальше не передаётся

Следующий шаг - `/implement`: его вход - путь одобренного плана и design-документа.
