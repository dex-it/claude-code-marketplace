# dex-design-reviewer

Ревьюер чужого **дизайн-документа** (спека, ADR, диаграммы, дизайн-раздел RFC) по рецепту **Reviewer**. Предмет - текст решения **до** того, как по нему начали кодить: полнота и измеримость NFR, дефекты требований внутри документа, обоснованность ADR-решений, консистентность выбранной модели, слои и доменные границы.

Симметричный слот зоны дизайна: `/design` порождает дизайн, `/review-design` принимает чужой. Разные роли и разные агенты - создатель предвзят к своему решению, как кодер к своему коду.

## Команда

`/review-design <путь к дизайн-документу> [источник требований]` - ревью и согласование. Второй аргумент (BRD, stories, задача) включает сверку «дизайн решает поставленное»; без него проверяются дефекты самого документа.

## Граница с `/review-arch`

Разные предметы, не дубль:

| | `/review-design` (этот плагин) | `/review-arch` (`dex-architect`) |
|---|---|---|
| Предмет | дизайн-документ, спека, ADR | реализованный код проекта |
| Момент | до написания кода | после |
| Якорь находки | раздел/пункт документа | `file:line` |
| Типовые находки | NFR без числа, решение без альтернатив, конфликт с Accepted ADR, невыполнимое требование | N+1, циклические зависимости, утечка слоёв, отсутствие health checks |

Запрос на ревью кодовой базы агент не берёт - возвращает перенаправление на `/review-arch`.

## Архитектура

Команда `/review-design` тонкая: делегирует агенту `design-reviewer`, а проводку оператора по находкам и выбор канала доставки ведёт сама. `mode: interactive` спавненному агенту во вход не передаётся - канала к оператору у него нет физически (`node-contract`, D.11). Фазы агента: Context (входная приёмка по метке `quality-checks`) -> Domain Priming -> Skill-Based Deep Scan -> Fact Verification -> Cross-Linking -> Severity Calibration -> Deferred Decision Triage -> Output Labeling -> Report.

Агент **не мутирует чужой документ**: `Write`/`Edit` отсутствуют намеренно. Находки предъявляются оператору, правки формулируются автору, канал доставки (задача в трекер либо правка в документ) выбирает оператор в диалоге. Это отделяет «судить» от «чинить», как в код-ревью.

Режим - из входа: `interactive` от команды (диалог с оператором), дефолт `autonomous` при спавне узлом (находки и verdict в Output наверх, канал доставки помечается невыбранным).

## Skills

Pre-load: `dex-skill-node-contract` (рантайм-контракт узла, входная приёмка по метке).

Императивно в Phase 2: `dex-skill-design-quality` - безусловно, когда документ дизайн (решение фичи целиком: драйверы, альтернативы, deep dive, план), в том числе когда ADR и спека лежат в нём разделами; на голом ADR, диаграмме или спеке контракта не грузится. По аспектам документа - `dex-skill-nfr`, `dex-skill-requirement-quality`, `dex-skill-adr-quality`, `dex-skill-doc-standards`; по стилю проекта - `dex-skill-cap-consistency`, `dex-skill-clean-architecture`, `dex-skill-ddd`. Контекст и дисциплина: `dex-skill-codebase-conventions`, `dex-skill-fact-verification`, `dex-skill-review-evidence`, `dex-skill-output-hygiene`.

## Связанные плагины

- `dex-skill-architecture-track` - трек `/design`, порождающий дизайн-документ.
- `dex-architect` - Decide-узел `architecture-track` и ревьюер архитектуры кода (`/review-arch`).
- `dex-requirements-reviewer` - симметричная приёмка чужих требований (зона требований).
- `dex-adr-writer` - фиксация согласованного решения в ADR.
