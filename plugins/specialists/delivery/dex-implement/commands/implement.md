# /implement

Реализовать фичу по ТЗ в стиле проекта, без долгов и хвостов. Финиш - готовые локальные коммиты;
push и MR отдельно.

## Input

Аргумент - ТЗ в свободной форме или ссылка на тикет. Опционально base-branch и feature-branch (ветки
нет - её создание входит в план). Стек определяется по манифесту затронутой папки, явно указывать не
нужно. Аргумент не передан -> запроси ТЗ первым вопросом.

## Порядок делегирования

Порядок ведёт главный поток: канал к оператору и команды цикла (`оформляй` / `делай` / `стоп`) есть
только у него. Узлам вниз идёт планка эскалации `interactive`, но не канал - невыводимое они
возвращают сюда.

| Порядок | Кто | Что даёт |
|---|---|---|
| 1 | здесь, в главном потоке | R/I из ТЗ, success criteria, non-goals, инвентаризация архитектуры по коду, edit-план P1..Pn с локальной проверкой каждой правки. План до передачи прогоняется через `Skill` -> `dex-skill-plan-quality:plan-quality` как самопроверка автора; исход прогона идёт в `self-check`, а не в апрув себе. Плана нет - исполнителю нечего передать |
| 2 | кодер своего стека: `dex-dotnet-coder:dotnet-coder` `[справочно]`, `dex-ts-fullstack-coder:ts-fullstack-assistant` `[справочно]` | код после команды `делай`, по одной правке за раз с верификацией после каждой; на вход R/I, success criteria и его часть плана |
| 3 | тестописатель своего стека: `dex-dotnet-tester:dotnet-test-writer` `[справочно]`, `dex-ts-tester:ts-test-writer` `[справочно]` | тесты; на вход diff-scope и success criteria как оракул |
| 4 | `dex-adr-writer:adr-writer` | ADR, когда решение выходит за пределы модуля (контракт, схема данных, зависимость, граница сервиса): без записи основание теряется в истории коммитов. Решение локально - строка «ADR: n/a» с указанием, что именно решалось |
| 5 | `dex-self-reviewer:self-reviewer` | саморевью дельты перед сдачей; находки закрываются тем же порядком, что и правки плана |

Стек не выводится из манифеста либо в репозитории их несколько - спроси, какой брать; молча выбирать
исполнителя нельзя. Стек определён, но кодера или тестописателя под него в установке нет - работа
останавливается статусом `blocked` с именем недостающего плагина: писать код и тесты вместо узла эта
команда не вправе.

## Output

- Требования R/I, success criteria, non-goals, вопросы перед стартом
- Архитектурное решение и edit-план P1..Pn с локальной проверкой каждой правки
- После команды `делай` - серия локальных коммитов, по одной правке за раз с верификацией
- Статус под-задачи в трекере двигается тем же действием, каким наступило событие («взял в работу»
  на старте правки, «готово» на сдаче): решётку прав и форму записи даёт `Skill` ->
  `dex-skill-issue-tracking:issue-tracking`. Трекера в проекте нет - строка `n/a`
- Решения, принятые за оператора, - перечнем, каждое с основанием; форма записи и место хранения -
  `Skill` -> `dex-skill-decision-log:decision-log`. Ни одного не принято - строка `n/a`, не молчание
- Финальный отчёт: success criteria с исходом, результат полного прогона сборки и тестов, закрытые
  R/I, находки саморевью; push не сделан

## Constraints

- Скоуп равен ТЗ; замеченное рядом - в открытые наблюдения, не в эту фичу
- Запрещены TODO, заглушки, silent fallback, debug-вывод, hardcoded secrets, отключённые тесты,
  спекулятивный код, дубли утилит
- Confidence ниже 80 в трактовке или подходе - вопрос, не код
- Работа заканчивается на локальных коммитах: ни push, ни MR, ни merge

Команды цикла: `оформляй` (полный план), `делай` (исполнение по одной правке), `стоп` (прекратить).
Следующий шаг - `/self-review`.
