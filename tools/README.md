# Tools

Dev-утилиты для Claude Code marketplace.

Этот файл описывает, **что** ловят валидаторы: правила, их идентификаторы, уровни и механизмы отбора. **Каждое число живёт ровно в одном месте** - копия расходится молча, именно так этот README и разошёлся с кодом. Носитель определяется тем, рассуждает ли о пороге фреймворк. Порог, который фреймворк обосновывает и на который ссылается своими правилами (размер артефакта, лимиты `description` у skill и агента), живёт в его доке - [AGENT_FRAMEWORK.md](../docs/AGENT_FRAMEWORK.md), [SKILL_FRAMEWORK.md](../docs/SKILL_FRAMEWORK.md), [COMMAND_FRAMEWORK.md](../docs/COMMAND_FRAMEWORK.md) - парно константе валидатора и правится одним коммитом с ней; здесь такое правило названо без числа. Чисто механический порог, о котором фреймворк не рассуждает, дома не имеет, и его единственный носитель - этот файл: он назван числом прямо в пункте правила. Адрес даётся до раздела, когда все числа правила лежат в одном разделе (так у порогов размера команды), и до документа, когда они разбросаны: у скилла потолок fence и порог числа H3-секций стоят вне разделов-лимитов, и адрес до раздела промахивался бы мимо числа. Поведение правил проверено зондом: артефакт-пример ставился ровно на границу и прогонялся.

## validate-agent.js

Валидатор агентов, проверяющий соответствие [Agent Framework](../docs/AGENT_FRAMEWORK.md).

### Что проверяет

Список перечисляет нарушения, которые валидатор ловит. Уровень указан у каждого; где не указано - ERROR.

**Frontmatter:**

- Отсутствие обязательного поля `name`, `description` или `tools` (правило `frontmatter-required`, константа `REQUIRED_FRONTMATTER_FIELDS`)
- Отсутствие поля `model` - отдельное правило `frontmatter-model-missing`, не часть предыдущего
- Запрещённое поле `allowed-tools` (для доступа к инструментам есть `tools:`)
- Поле `skills:` со значением, отличным от `node-contract` (правило `frontmatter-skills-not-preloadable`). Само поле не запрещено: pre-load разрешён ровно одному безусловному process-skill, и обе полные формы записи проходят - `node-contract` и `dex-skill-node-contract:node-contract`. Прочие скиллы грузятся императивно через Skill tool в фазах. Список разрешённых к pre-load - константа `ALLOWED_PRELOAD_SKILLS` в валидаторе
- Значение `skills:` в виде голого имени плагина, без скилла (правило `frontmatter-skills-bare-plugin-name`): `dex-skill-node-contract` не резолвится, плагин молча пропускается
- Судья артефакта не загружает норматив его этапа императивно (правило `stage-normative-reader-missing`, карта `STAGE_NORMATIVE_READERS`). Критерий попадания в карту - наличие у агента оси полноты состава, а не отсутствие оракула типа: оракулы жанров (`use-case-quality`, `api-spec-quality`) состав не судят и сами отсылают к нормативу, поэтому судья попадает в карту и при живом оракуле. Норматив, судьи которому маршрут не назначил (`verification-planning-29119`), строки не получает - исполнять её некому
- Значение `skills:` с неизвестным именем скилла при известном плагине (правило `frontmatter-skills-unknown-skill`). Обратный случай не ловится ничем: опечатка в половине-плагине (`dex-skill-nodecontract:node-contract`) даёт ноль ошибок, потому что нормализация берёт часть после последнего `:`, а неизвестный плагин объявлен вне области проверки. Зонд: правка половины-плагина - 0 ошибок, правка половины-скилла - 2
- Имя файла не совпадает с полем `name` (правило `agent-file-name-mismatch`; сравнивается basename без `.md`)
- Файл агента лежит в подкаталоге `agents/` (правило `agent-file-nested`). Рантайм поставляет такой файл под трёхсегментным именем `{plugin}:{dir}:{name}`, и ссылка `{plugin}:{name}` на него не резолвится, а `agent-file-name-mismatch` при этом молчит: имя файла с `name` совпадает. Сегмент `agents/` берётся последним вхождением - иначе каталог `agents` выше по дереву (в абсолютном пути прогона) дал бы ложное срабатывание на плоском файле
- Во фронтматтере нет pre-load контракта стыка (правило `frontmatter-skills-missing`). Соседние `frontmatter-skills-*` судят уже написанное значение и на отсутствие поля молчат - замер мутацией: снятый целиком блок `skills:` давал 0 ошибок. Исключений по «узловости» у правила нет: контракт стыка исполняет сам агент, а не вызывающий
- Description короче 50 символов. Это единственный порог `description` агента, у которого дома во фреймворке нет: `AGENT_FRAMEWORK.md` рассуждает о верхних лимитах и о нижнем не говорит, поэтому число названо здесь
- Description длиннее мягкого порога - WARNING (`frontmatter-description-long`), длиннее проектного потолка - ERROR (`frontmatter-description-too-long`). Ярусы взаимоисключающие. Верхнего яруса под платформенный лимит у агентов нет: платформенный лимит на description агента не задокументирован
- Значение `model` вне набора `opus` / `sonnet` / `haiku` / `fable` / `inherit` или полного идентификатора модели (правило `frontmatter-model-invalid`). Само значение `inherit` валидатор пропускает, хотя фреймворк требует явный тир
- Значение `effort` вне набора `low` / `medium` / `high` / `xhigh` / `max` (`frontmatter-effort-invalid`), а также `effort` при `model: haiku` (`frontmatter-effort-unsupported-model`: у этого тира оси effort нет)
- Избыточное `permissionMode: default` (`frontmatter-permissionmode-default`)
- Неполный каскад под fact-check (`factcheck-cascade-incomplete`): тело зовёт `dex-skill-fact-verification:fact-verification`, а в `tools` нет `ToolSearch`, `WebSearch` или `WebFetch`
- Description не содержит ни «Триггеры», ни «Активируется», ни «trigger» - Claude Code матчит агентов по ключевым словам. Засчитывается любое из трёх, регистр не важен (правило `frontmatter-description-no-triggers`); сообщение валидатора называет «Триггеры» и «trigger», а «Активируется» в нём не упомянут вовсе, но «Активируется при ...» проверку проходит
- Отсутствие `Skill` в `tools:` - агент не сможет императивно загружать skills. Правило смотрит только на строковую форму `tools: A, B, C`: если `tools` записан YAML-списком, оно пропускается целиком и отсутствие `Skill` не ловится. Зонд: тот же набор без `Skill` строкой - ERROR, списком - 0 ошибок. Сейчас дыра латентна (все агенты каталога пишут строкой), но `validateFactcheckCascade` в том же файле список к строке нормализует - то есть внутри одного валидатора формы разобраны по-разному

Ограничения на размер файла агента валидатор не накладывает.

**Phase-level:**

- Каждый агент должен иметь секции `## Phase N:`
- Каждая фаза должна иметь атрибут `**Goal:**`
- Каждая фаза должна иметь атрибут `**Exit criteria:**`
- Mandatory-фаза без обоснования (фреймворк требует объяснять «зачем mandatory»). Правило смотрит не на наличие продолжения, а на его длину: хвост после `yes` короче 10 символов после trim - ERROR. Зонд: `yes - abcdefg` (9 символов) падает, `yes - abcdefgh` (10) проходит, то есть отговорка в пару слов не засчитывается
- Фраза из чёрного списка («агент понял», «анализ завершён») - они описывают внутреннее состояние, а не observable outcome. Несмотря на имя правила (`phase-non-observable-exit`) и текст его сообщения, ищется она **во всём теле фазы**, а не только в `Exit criteria`: фраза в `Goal` даёт ту же ошибку. Зонд: «анализ завершён» в `Goal` при чистом `Exit criteria` - ERROR
- Фаза содержит нумерованный список из >=4 пунктов - потенциально процедурное описание (фреймворк требует декларативный стиль)
- Слипшийся лейбл-атрибут (`glued-attribute-block`): `**Goal:**`, `**Output (handoff):**`, `**Gate ...:**` или любой другой `**Лейбл:**` стоит внутри одного paragraph-узла не на первой его строке. Без пустой строки markdown сливает соседние блоки в один абзац, и нормативный пункт перестаёт читаться отдельно. Отбор по AST, а не построчный: заголовки и code fence в paragraph не попадают, поэтому ложных срабатываний на них нет, а префикс контейнера (отступ пункта списка, `>` цитаты) снимается перед проверкой. Длина лейбла не ограничена: верхняя граница отсекала бы длинные лейблы от проверки молча. Единственное правило группы, которое не гейтится фазами: смотрит всё тело файла, а не только секции `## Phase N:`
- В теле нет `**Input (handoff)` либо `**Output (handoff)` (правила `handoff-input-missing`, `handoff-output-missing`). Объявленная сигнатура - требование к каждому агенту, а не только к узлу цепочки; проверяется присутствие атрибута в теле, а не его фаза

**Skill references:**

- Упомянутый в теле агента плагин `dex-skill-X` отсутствует в `marketplace.json`. Правило видит только закрытую форму в бэктиках `` `dex-skill-X:skill` ``: голое `dex-skill-X` без имени скилла под проверку не попадает вовсе (не «падает», а остаётся невидимым). Существование самого скилла внутри плагина не проверяется. Проверка гейтится фазами: агент без секций `## Phase N:` получает `no-phases`, и ссылки на скиллы у него не проверяются ни одной

**Общее для всех четырёх валидаторов:** нечитаемый файл даёт `read-failed` (ERROR) - отдельное правило, не молчаливый пропуск.

### Установка

Из корня репозитория:

```bash
npm install
```

Устанавливает dev-зависимости: `gray-matter`, `remark`, `remark-gfm`, `remark-parse`, `unified`, `unist-util-visit`. Папка `node_modules` игнорируется git, `package-lock.json` коммитится. `remark-gfm` несущая, а не косметическая: без неё GFM-таблицы разбираются как параграфы, и ветка «реестровая таблица» в `process-empty` перестаёт срабатывать.

### Запуск

```bash
# Один файл
node tools/validate-agent.js plugins/specialists/dotnet/dex-dotnet-coder/agents/dotnet-coder.md

# Все агенты каталога (обход plugins/ целиком)
node tools/validate-agent.js all
```

Через npm scripts:

```bash
npm run validate              # agents + skills + commands + bundles
npm run validate:agents       # только агенты
```

### Коды возврата

- `0` - чисто
- `1` - найдена хотя бы одна ошибка

### Как добавить новую проверку

1. Откройте `tools/validate-agent.js`
2. Найдите функцию своего уровня проверки: `validateFrontmatter`, `validateFileNameMatchesName`, `validatePhases`, `validateFactcheckCascade`, `validateSkillReferences`, `validateAttributeBlocks`. Уровня в списке нет - заводите новую функцию и вызывайте её из `validateFile`, иначе правило не отработает ни на одном файле
3. Добавьте новое правило - push в `findings` с полями `level: ERROR`, `rule` (kebab-case идентификатор) и `message`
4. Прогоните `node tools/validate-agent.js all` чтобы убедиться, что правило не создаёт массовых false positives на существующих агентах
5. Обновите этот README с описанием нового правила - и порог тоже, если правило его вводит

### Ограничения текущей версии

В первой версии не реализованы:

- Проверка output -> input цепочки между фазами (требует семантического анализа)
- Проверка дублирования содержимого skills в теле агента (требует парсинга SKILL.md)
- Проверка соответствия `tools:` во frontmatter реально используемым tools в теле агента

Эти проверки - кандидаты для второй версии после того, как фреймворк стабилизируется на большем количестве мигрированных агентов.

## validate-skill.js

Валидатор skills, проверяющий соответствие [Skill Framework](../docs/SKILL_FRAMEWORK.md).

### Что проверяет

Уровень указан у каждого пункта; где не указано - ERROR. Числа порогов - в [SKILL_FRAMEWORK.md](../docs/SKILL_FRAMEWORK.md).

- Отсутствие обязательного frontmatter поля `name` или `description`
- Запрещённое поле `keywords` (не поддерживается Claude Code для skills)
- Description не содержит «Активируется при» / «Triggers» - единственный механизм автоматической активации
- Description короче минимальной длины
- Description длиннее мягкого порога - WARNING (`description-long`), длиннее проектного потолка - ERROR (`description-too-long`), длиннее хард-лимита Claude Code - ERROR (`description-exceeds-claude-limit`). Ярусы взаимоисключающие. **Важный зазор:** кап платформы на одну запись действует на **сумму** `description` и `when_to_use`, а валидатор меряет только `description` - сумму не проверяет никто, и скилл может пройти прогон, но быть обрезан в листинге. Второй механизм с тем же следствием - бюджет всего листинга (описан в [SKILL_FRAMEWORK.md](../docs/SKILL_FRAMEWORK.md)); его валидатор не проверяет в принципе, потому что зависит он не от файла, а от состава установленных скиллов
- Меньше порогового числа ключевых слов после «Активируется при» - ERROR у обычного скилла, WARNING у process-skill
- Размер файла выше проектной рекомендации - ERROR (`size-exceeds-recommended`). У process-skill не проверяется: от проектного порога он освобождён, платформенный потолок общий
- Размер файла выше официальной рекомендации Anthropic - ERROR (`size-exceeds-hard-limit`). Это рекомендация, а не платформенное усечение. Ярусы размера, как и ярусы description, взаимоисключающие: файл выше верхнего порога даёт только `size-exceeds-hard-limit`, `size-exceeds-recommended` при этом молчит
- Меньше порогового числа H3-секций (слишком мало ловушек)
- Fenced code block длиннее потолка (принцип «pointer, не код»)
- H3-ловушка без триады «Плохо / Правильно / Почему»
- Заголовки в стиле документации («Как настроить X», «Что такое Y», «Шаг N»). Правило смотрит только H2 и H3: тот же заголовок на H1 или H4 проходит молча

**Вторая ось: process-skill.** Скилл, кодирующий процесс, а не ловушки стека, живёт по другим порогам. Опознаётся по полю `name` во frontmatter (не по пути и не по каталогу), список имён - константа в валидаторе. Для такого скилла:

- порог размера свой, выше обычного, а рекомендация Anthropic не применяется вовсе
- проверка на минимум H3-секций не применяется - у процесса ловушек нет
- вместе с ней отключается и требование триады у H3 (`trap-missing-triad`): обе trap-эвристики выключаются одним возвратом в коде, поэтому H3 процесса это развилка или правило, а не ловушка
- вместо неё работает `process-empty`: реестровая таблица либо пороговое число H2-секций с правилами. Иначе скилл считается заглушкой, эксплуатирующей освобождение от ловушек
- отсутствие фразы активации в `description` понижено до WARNING (`description-no-activation`), как и нехватка ключевых слов

### Запуск

```bash
# Один файл
node tools/validate-skill.js plugins/skills/dex-skill-dotnet-ef-core/skills/dotnet-ef-core/SKILL.md

# Все skills в plugins/skills/
node tools/validate-skill.js all
```

Через npm scripts:

```bash
npm run validate              # agents + skills + commands + bundles
npm run validate:skills       # только skills
```

### Коды возврата

- `0` - чисто
- `1` - найдена хотя бы одна ошибка

## validate-command.js

Валидатор команд, проверяющий соответствие [Command Framework](../docs/COMMAND_FRAMEWORK.md).

### Что проверяет

Все правила этого валидатора - уровня ERROR. Пороги размера файла - в [COMMAND_FRAMEWORK.md](../docs/COMMAND_FRAMEWORK.md), раздел «Размер»: о них фреймворк рассуждает («перевалила потолок - это агент»). Пороги блоков внутри тела фреймворк не обсуждает, поэтому названы здесь и больше нигде не живут.

- Отсутствие обязательного frontmatter поля `description`
- Размер файла выше жёсткого потолка (`size-exceeds-hard-limit`, вердикт «это должен быть агент с фазами»). Исключений у этого порога нет
- Размер файла выше потолка точечной команды (`size-exceeds-recommended`). Для команд из allowlist `PIPELINE_COMMANDS` порог поднят, жёсткий потолок при этом не двигается. Allowlist сверяется по точному basename файла
- Нумерованный список >= 5 пунктов (процедурное описание вместо Goal + Output). У агентов тот же по смыслу порог другой - там >= 4
- Fenced code block длиннее 5 строк (команда описывает цель, а не содержит скрипты)
- Два и более bash-блока суммарной длиной > 10 строк (CLI-скрипты вместо декларативного описания). В счёт идут блоки с языком `bash`, `sh` или `shell`; блоки в 3 строки и короче отбрасываются и в сумму не входят, прочие языки не считаются вовсе. Потолок fence и это правило независимы: блок, уже нарушивший потолок, из суммы не выпадает, и файл получает обе ошибки сразу. Следствие двух порогов вместе: пока каждый блок укладывается в потолок fence, двух блоков не хватает - максимум 5 + 5 при нужных > 10; на двух блоках правило срабатывает только тогда, когда потолок fence уже нарушен. Без нарушения потолка минимум - три блока по 4 строки. Проверено зондом: два блока по 8 строк дают `bash-script-detected` и два `code-fence-too-long` сразу, два по 5 - тишину, три по 4 - только `bash-script-detected`
- Заголовки в стиле документации («Как настроить X», «Что такое Y», «Шаг N»). Правило смотрит только H2 и H3: тот же заголовок на H1 или H4 проходит молча

### Запуск

```bash
# Один файл
node tools/validate-command.js plugins/specialists/dotnet/dex-dotnet-coder/commands/build.md

# Все команды в plugins/
node tools/validate-command.js all
```

Через npm scripts:

```bash
npm run validate              # agents + skills + commands + bundles
npm run validate:commands     # только команды
```

### Коды возврата

- `0` - чисто
- `1` - найдена хотя бы одна ошибка

## validate-bundle.js

Валидатор замкнутости бандла: каждый бандл должен быть **целостным** - содержать в составе все артефакты, названные телами его компонентов. Состав разложен на два списка: `includes[]` - профиль роли, ради которого бандл собран; `dependencies[]` - подтянутое замыканием от профильного. Установка ставит оба, правила судят объединение.

**Этот валидатор входит в CI.** Workflow `.github/workflows/validate-agents.yml` вызывает его шагом `Validate bundles` наравне с валидаторами агентов, скиллов и команд; следом идут мета-гейт `validate-rules-documented.js` и прогон фикстур `test-rules.js` - шесть шагов, не четыре. Фильтра путей на `pull_request` нет намеренно (основание - в шапке workflow: required-чек, который не запустился, не считается пройденным), поэтому незамкнутый бандл останавливается на любом PR, включая правку одного `bundle.json`.

### Зачем

Установка плоская: `install-bundle.sh` ставит ровно то, что перечислено в `includes[]` и `dependencies[]`, каскада «специалист -> его скиллы» нет. Артефакт, названный в теле компонента, но отсутствующий в составе, не установится - исполнитель молча деградирует (ветка graceful degradation). Валидатор ловит такой рассинхрон до коммита.

### Что проверяет

- **bundle-not-closed** (error) - агент состава называет артефакт, которого в составе нет. Обязанность снимает только пометка `` `[справочно]` `` вплотную за вызовом: она объявляет артефакт вариантом, чужим проекту (чужой стек, чужая зона). Исключений по имени артефакта у правила нет: угадывание условности по префиксу стека и по совпадению предмета снято - замером показано, что оно гасило большинство обязательных рёбер трек-записей
- **include-not-in-marketplace** (error) - компонент состава не зарегистрирован в `marketplace.json` (иначе `install-bundle` упадёт)
- **empty-includes** (error) - у бандла пуст `includes[]`: профильного состава нет, а `dependencies[]` его не заменяет
- **dependency-also-included** (error) - компонент стоит в обоих списках сразу
- **version-mismatch** (warning) - версия в `plugin.json` бандла не равна версии этого бандла в `marketplace.json` (реальная двухместная синхронизация; в `bundle.json` версии нет)

Перечень выше - правила замыкания, ради которых валидатор заведён; он держит и другие - синхронизации каталога, разведение списков состава, `authorOnly[]`. Полный реестр с уровнями и нормой - [VALIDATOR_RULES.md](../docs/VALIDATOR_RULES.md#toolsvalidate-bundlejs); здесь не дублируется - копия разошлась бы молча.

### Запуск

```bash
# Один бандл (по имени, директории или пути к bundle.json)
node tools/validate-bundle.js dex-bundle-architect

# Все бандлы
node tools/validate-bundle.js all
```

Через npm scripts:

```bash
npm run validate              # agents + skills + commands + bundles
npm run validate:bundles      # только бандлы
```

### Коды возврата

- `0` - чисто
- `1` - найдена хотя бы одна ошибка

## propagation-cost.js

### Зачем

У центрального свойства схемы («новая зона - новый плагин, ядро при этом не правится») не было ни
одного замера: численный гейт Z1 снят решением оператора, другого эксперимента у модульности нет.
Метрика закрывает эту дыру - она отвечает ровно на вопрос «куда расходится правка» и считается за
секунды на любой ревизии, поэтому сравнима между ними.

Метод - MacCormack, Baldwin, Rusnak: DSM «элемент x элемент», её транзитивное замыкание
(visibility matrix), метрика = плотность замыкания, «the proportion of elements that could be
affected, on average, when a change is made to one element». Точка отсчёта авторов - Mozilla:
17.35% до перепроектирования, 2.78% после.

### Что считает

- **Элемент** - скилл (со всеми файлами своей директории, включая `references/`) либо агент.
- **Ребро A -> B** - тело A называет B.
- **Наибольший цикл** - сильно связная компонента: A достижим из B и B из A. Внутри неё нет
  направления, поэтому утверждение «ядро выше модулей в порядке зависимостей» в ней непроверяемо.

### Правило ребра задаётся явно

Число без правила бессмысленно, поэтому правило печатается вместе с числом всегда, в обоих
форматах вывода: строкой `Правило ребра:` в человекочитаемом и полем `rule` в `--json`. Умолчание в
коде есть (`loose`), и `npm run metrics:propagation` идёт без флага - защищает не отсутствие
умолчания, а невозможность получить число без его правила:

| `--rule` | Ребро | Чем полезно |
| --- | --- | --- |
| `canonical` | только каноническая форма `` `плагин:имя` `` | резолвимые ссылки, форма каталога |
| `loose` (дефолт) | каноническая **или** голое имя элемента в бэктиках | плюс ссылки старой нотации |

Голое имя ловится только в бэктиках: без них `engine` и `architect` встречаются прозой и дают
рёбра там, где ссылки нет.

### Точки отсчёта (замер 25.08.2026)

| Ревизия | `canonical` | цикл | `loose` | цикл |
| --- | --- | --- | --- | --- |
| `origin/develop` | 2.14% | 2 | 24.53% | 39 |
| `1fc58274` (ветка `docs/sdlc-engine-tracks`) | 14.57% | 35 | 32.36% | 56 |

**Вывод от правила не зависит, абсолютное число зависит.** Связность выросла на всех правилах
(+12.4 / +7.8 процентных пункта), наибольший цикл вырос везде, и в него входят движок и все
двенадцать треков. Это цена расщепления, а не приговор ему: справочник зон лежит внутри ядра,
потому что иначе голое поручение резолвить нечем.

Замер ревьюера PR #213 воспроизведён независимо: по `canonical` числа совпали все четыре
(2.14 / 14.57, циклы 2 / 35). Его широкое правило сначала не восстанавливалось, потом восстановилось
заменой одного предиката - и разошлись мы ровно на двух битах: ловить ли голое имя вне бэктиков и
считать ли дефис границей слова.

| Правило голого имени | `develop` | цикл | `1fc58274` | цикл |
| --- | --- | --- | --- | --- |
| только в бэктиках (наш `loose`) | 24.53% | 39 | 32.36% | 56 |
| где угодно, граница `[^A-Za-z0-9-]` | 27.32% | 43 | 34.61% | 60 |
| где угодно, граница `\b` | 35.88% | 54 | 42.16% | 73 |

Третья строка выше второй потому, что при `\b` дефис считается границей и `development-track`
матчится внутри `dex-skill-development-track` - имя директории плагина засчитывается ссылкой на
скилл.

Берём первую строку, и основание не во вкусе, а в разборе лишних рёбер. У широкого правила их 38 из
745: пятнадцать набираются на трёх словах языка (`docker`, `architect`, `observability`, плюс
`storage engine` и «runtime-инструменты (debugger, profiler)»), но остальные - настоящие ссылки без
бэктиков («эскалировать к architect», «вход следующего узла (tester или self-reviewer)»). Широкое
правило ошибается в обе стороны, узкое - в одну и детерминированно.

Побочное число, которое метрика отдаёт даром: разница `canonical` и `loose` - это доля графа,
написанная не канонической формой. На `develop` 150 рёбер из 569 (26%), на ветке 160 из 707 (23%).
Норма каталога - полная форма `{плагин}:{имя}`, и четверть связей ей не следует.

### Граница метрики

Документальная перекрёстная ссылка считается зависимостью. Для вопроса «куда расходится правка»
это верное прочтение: переименовали раздел - ссылающийся текст надо править. Для вопроса «что
сломается в рантайме» - неверное: ссылка в прозе рантайм не ломает.

### Запуск

```bash
npm run metrics:propagation                        # loose, кратко
node tools/propagation-cost.js --rule=canonical
node tools/propagation-cost.js --top=10            # плюс самые «расходящиеся» элементы
node tools/propagation-cost.js --json              # машинный вывод, включая состав цикла
```

Замер на другой ревизии - через `MARKETPLACE_ROOT` на распакованное дерево
(`git archive <ref> | tar -x -C <dir>`), как это сделано для таблицы выше.

### Коды возврата

- `0` - замер выполнен (порога метрика не ставит: гейтом она станет, когда наберётся история)

## validate-readme.js

Витрина `README.md` против витрины каталога: назван ли в README каждый плагин.

### Зачем

README - второй носитель состава каталога, и генератора у него нет: он правится руками,
а расходится молча. Замер 01.09.2026 при закрытии остатка #110 дал цену расхождения -
85 плагинов из 245 не были названы ни одной из двух форм (замер этим же инструментом на
базе PR, `b846fd6f`). `sync-marketplace.js --check` этого не видит:
он судит пару `plugin.json` x `marketplace.json`, README в его предмет не входит. До
переименования в общую конвенцию `validate-*.js` инструмент жил вне гейта регрессии
(`tools/test-rules.js`): зелёный прогон на живом каталоге доказывал отсутствие предмета
(README полон), а не работоспособность самих проверок.

### Что проверяет

- Плагин витрины не назван в README в позиции имени плагина (правило
  `readme-plugin-unnamed`). Позиций три, и форму имени в каждой задаёт шапка таблицы:
  `| Bundle |` - короткая форма бандла (`architect` -> `dex-bundle-architect`), прочие
  витрины - полное имя (`dex-architect`), `| Skills |` - короткая форма скилла
  (`ddd` -> `dex-skill-ddd`). Проза и прочие колонки в предмет не входят: там то же
  слово называет агента, команду или внешний бинарь
- Ссылка README не резолвится в витрину (правило `readme-row-ghost`) - обратная сторона
  предыдущего: без неё переименование или удаление плагина оставляет ссылку на мёртвое
  имя, а односторонний гейт остаётся зелёным на ней. Перечень позиций у обоих правил
  общий, одной функцией: разойдись они, плагин считался бы названным там, где имя
  принадлежит не ему. Таблица `Skills` называет скилл, и обычно плагин зовётся
  `dex-skill-<скилл>`; где это не так (движок `dex-sdlc` везёт скилл `engine`), имя
  резолвится через владельца скилла. Владельцы читаются с дерева при каждом прогоне -
  список исключений в коде протухал бы молча, а дерево есть тот же источник, по
  которому витрина и заполняется

Почему имя читается позиционно, а не поиском слова по файлу: короткая форма не
инъективна - `architect` делят специалист `dex-architect` и бандл `dex-bundle-architect`,
`sdlc` - движок и бандл `dex-bundle-sdlc`. Поиск слова на этом ложно зеленеет:
фальсификация на живом README (снятие строки бандла) находки не дала - покрытие
закрылось именем агента из строки специалиста. Требовать в спорном случае полную форму
нельзя: колонка `Bundle` несёт аргумент установщика (`install-bundle.sh architect`), и
подмена короткого имени полным сделала бы витрину неверной. Шапка таблицы снимает
неоднозначность без правки витрины. Крой привязан к шапке и по второй причине: сверка
любого code-span подряд дала бы 14 ложных имён из 170 - в таблицах CLI-инструментов в
той же позиции стоят имена внешних бинарей (`gh`, `psql`), замер 01.09.2026
- Версия в подвале README не равна версии витрины, включая случай, когда строка подвала
  не найдена вовсе (правило `readme-version-drift`) - подвал README третий носитель
  версии каталога, и он уже расходился (на базе PR подвал стоял на `5.4.0` при `5.85.0`
  в витрине). Сверяется ровно строка подвала, а не любое вхождение номера в текст

Позиции читаются в тексте без код-блоков: строка `| dex-... |` внутри примера
показывает форму записи, а не называет плагин. Читай её - и образец закрывал бы
покрытие собой, а имя-заглушка приезжало бы мёртвой ссылкой. Тот же приём и по той же
причине стоит в `validate-agent.js`: сигнатура handoff внутри примера свидетелем не
считается.

Содержание строки не судится: устаревшее описание ловит ревью. Предмет здесь один -
состав каталога против состава витрины, а не текст строки.

### Запуск

```bash
npm run readme:check                  # то же, отдельным npm-скриптом
node tools/validate-readme.js all
```

### Коды возврата

- `0` - чисто, все плагины названы
- `1` - есть хотя бы одна находка (`readme-plugin-unnamed` / `readme-row-ghost` / `readme-version-drift`)
- `2` - `marketplace.json` или `README.md` не прочитаны (отказ инструмента, не находка правила)
